Amazon Aurora

⚡ Aurora Serverless の高速スケーリング
瞬時に最大 12 ACU、1 秒以内に確保

📅 リリース日: 2026 年 8 月 5 日 | 🗄️ サービス: Amazon Aurora Serverless | 🤖 エージェント型 AI などのバースト性ワークロード向け

📌 概要

Aurora Serverless のスケールアップが高速化され、スケールアップイベント時に 1 秒以内で最大 12 ACU の初期キャパシティを即座に提供できるようになりました。需要の増加に応じて 最大 256 ACU まで継続的にスケールアップし、ワークロード終了後は 0 ACU までスケールダウンします。

活動のバースト、長いアイドル期間、予測不可能なトラフィックパターンを特徴とするエージェント型 AI (Agentic AI) アプリケーションに特に適しています。プラットフォームバージョン 3 / 4 のすべての Aurora Serverless クラスターでデフォルト有効・設定変更不要です。

🐢 Before: アップデート前の課題
  • スケールアップが段階的な増分で行われ、突発的な負荷スパイク直後に十分なキャパシティへ到達するまで時間を要する場合があった
  • 現在のキャパシティが小さいほど増分も小さく、0 ACU や低キャパシティからの急激な負荷増加への追従が課題だった
  • スケールアップの待ち時間回避のため最小 ACU を高めに設定する必要があり、アイドル期間のコストが増加していた
🚀 After: アップデート後の改善
  • スケールアップイベント時に 1 秒以内で最大 12 ACU の初期キャパシティを即座に確保
  • 需要の増加に応じて最大 256 ACU まで継続スケールアップし、終了後は 0 ACU までスケールダウンしてコスト効率を維持
  • プラットフォームバージョン 3 / 4 では設定変更なしでデフォルト有効、追加作業なしで恩恵を受けられる

エージェント型 AI などのバースト性ワークロードに対して、アップデート後は 1 秒以内に最大 12 ACU の初期キャパシティを即座に提供し、その後も需要に応じて最大 256 ACU までスケールする流れを示しています。

💡 主要機能

⚡ 1. 瞬時の初期キャパシティ確保 (最大 12 ACU / 1 秒以内)
  • スケールアップイベント時に、1 秒以内で最大 12 ACU まで即座にキャパシティを引き上げ
  • 従来の段階的なスケーリングと比較して、突発的な負荷スパイクへの初動が大幅に高速化
  • 1 ACU は約 2 GiB のメモリと対応する CPU、ネットワークリソースの組み合わせ
📈 2. 最大 256 ACU までの継続的なスケールアップ
  • 初期の高速スケールアップ後も、需要の増加に応じて最大 256 ACU まで継続してスケール
  • データベース接続が開いている間、SQL トランザクションの実行中でも中断なくスケーリング
💤 3. 0 ACU へのスケールダウン (自動一時停止)
  • ワークロード終了後は 0 ACU までスケールダウンし、アイドル期間中のコンピューティングコストをゼロにできる
  • 長いアイドル期間を持つエージェント型 AI アプリケーションのコスト最適化に有効
✅ 4. デフォルト有効 (設定変更不要)
  • プラットフォームバージョン 3 / 4 のすべての Aurora Serverless クラスターでデフォルトで有効
  • アプリケーションコードや接続文字列の変更も不要

Bash Serverless プラットフォームバージョンの取得 
aws rds describe-db-clusters \
  --db-cluster-identifier my-aurora-cluster \
  --query "DBClusters[0].ServerlessV2PlatformVersion"

🛠️ 設定方法

📌 前提条件

✓Aurora Serverless クラスター (Aurora MySQL または Aurora PostgreSQL) が存在すること
✓本機能を利用するにはプラットフォームバージョン 3 または 4 で稼働していること
✓0 ACU へのスケールダウンを利用する場合は、対応エンジンバージョン (Aurora MySQL 3.08.0 以上、Aurora PostgreSQL 13.15 / 14.12 / 15.7 / 16.3 以上) であること

🚀 手順

1
現在のプラットフォームバージョンを確認する
Bash
aws rds describe-db-clusters \
  --db-cluster-identifier my-aurora-cluster \
  --query "DBClusters[0].ServerlessV2PlatformVersion"

「3」または「4」が返される場合、本機能はすでに有効です。

2
プラットフォームバージョン 1 / 2 の場合はアップグレードする
Bash保留中のメンテナンスアクションを確認
aws rds describe-pending-maintenance-actions \
  --resource-identifier arn:aws:rds:ap-northeast-1:123456789012:cluster:my-aurora-cluster

保留中のメンテナンスの適用、クラスターの停止と再起動、またはブルー / グリーンデプロイのいずれかの方法でプラットフォームバージョン 4 に直接アップグレードできます。

3
キャパシティ範囲を確認する
Bash
aws rds describe-db-clusters \
  --db-cluster-identifier my-aurora-cluster \
  --query "DBClusters[0].ServerlessV2ScalingConfiguration"

バースト性ワークロードでコストを最小化したい場合は最小キャパシティを 0 ACU に、ピーク需要に対応するため最大キャパシティを十分な値 (最大 256 ACU) に設定します。

⚖️ メリット・制約事項

✅ メリット

💼 ビジネス面

  • コスト効率の向上: スパイク対策として最小 ACU を高めに維持する必要性が減り、アイドル期間は 0 ACU まで下げてコスト削減
  • 追加作業ゼロ: プラットフォームバージョン 3 / 4 ではデフォルト有効で既存クラスターは自動的に恩恵を受ける
  • AI アプリケーションの俊敏な展開: キャパシティプランニングなしでデータベースを提供可能

🔧 技術面

  • 応答性の向上: コールドスタートやスパイク直後のレイテンシー悪化を軽減
  • 中断のないスケーリング: 接続やトランザクションを維持したままスケーリング実行
  • 広いスケーリングレンジ: 0-256 ACU で、単一クラスターでバーストとアイドルの両極端に対応
⚠️ 制約事項・考慮点

🚫 制限事項

  • プラットフォームバージョン 3 / 4 のクラスターが対象。バージョン 1 / 2 はバージョン 4 へのアップグレードが必要
  • プラットフォームバージョン 4 の利用可能リージョンは限定 (東京、大阪を含む主要リージョンで利用可能)
  • 実際のスケーリング範囲は、エンジンバージョンとプラットフォームバージョンのうち能力が低い方で決まる

💭 考慮すべき点

  • 0 ACU からの再開には処理時間が発生するため、レイテンシー要件が厳しい場合は最小キャパシティ設定値を検討
  • 瞬時に 12 ACU まで到達することでキャパシティ消費が短時間で増える可能性があるため、ServerlessDatabaseCapacity / ACUUtilization メトリクスでの監視を推奨
  • バッファプールはスケールダウン時に縮小されるため、ワーキングセットを保持したい場合は最小 ACU をワークロードに合わせて設定

🎯 ユースケース

🤖 ユースケース 1: エージェント型 AI アプリケーションのバックエンド

シナリオ: AI エージェントがユーザーのリクエストに応じて自律的にタスクを実行し、データベースへ突発的に大量のクエリを発行。タスク完了後は長時間アイドル状態になる。

Bash実装例
aws rds create-db-cluster \
  --db-cluster-identifier agentic-ai-db \
  --engine aurora-postgresql \
  --engine-version 16.3 \
  --serverless-v2-scaling-configuration MinCapacity=0,MaxCapacity=64
💡 効果: タスク開始時に 1 秒以内で最大 12 ACU まで即座にスケールし、完了後は 0 ACU までスケールダウン。応答性とコスト効率を両立。
📊 ユースケース 2: 不定期に実行されるバッチ・レポート処理

シナリオ: 月次レポートや不定期の集計バッチなど、実行タイミングが予測しにくく、実行時には大きなキャパシティが必要な処理を行う。

Bash実装例
aws rds modify-db-cluster \
  --db-cluster-identifier reporting-db \
  --serverless-v2-scaling-configuration MinCapacity=0,MaxCapacity=256
💡 効果: バッチ開始直後に高い初期キャパシティが確保され、処理時間の短縮が期待できる。処理完了後は 0 ACU まで下がり、待機コストが発生しない。
🌐 ユースケース 3: トラフィックが予測不能な新規アプリケーション

シナリオ: リリース直後でトラフィックパターンが読めない新規 Web アプリケーションや SaaS で、急激なユーザー増加に備えたい。

Bash実装例
aws rds describe-db-clusters \
  --db-cluster-identifier new-app-db \
  --query "DBClusters[0].ServerlessV2PlatformVersion"
💡 効果: プラットフォームバージョン 3 / 4 であれば設定変更なしで高速スケーリングが有効。突発的なトラフィックスパイクにもデータベースがボトルネックになりにくい。

💰 料金

Aurora Serverless は従量課金制で、データベースがアクティブな間に消費したキャパシティに対して ACU 時間単位 (秒単位の課金) で料金が発生します。

✓今回のアップデートによる追加料金はなし。実際に消費したキャパシティ分のみが課金される
✓0 ACU までスケールダウンしている間は、コンピューティング料金は発生しない
⚠️ストレージおよび I/O 料金は別途発生する

詳細は Amazon Aurora 料金ページ を参照してください。

📝 まとめ

Aurora Serverless が 1 秒以内に最大 12 ACU まで瞬時にスケールアップできるようになり、エージェント型 AI をはじめとするバースト性ワークロードへの適合性が大きく向上しました。

プラットフォームバージョン 3 / 4 のクラスターでは設定変更なしでデフォルト有効のため、まず ServerlessV2PlatformVersion で自クラスターのバージョンを確認し、バージョン 1 / 2 の場合はプラットフォームバージョン 4 へのアップグレードを検討することを推奨します。
