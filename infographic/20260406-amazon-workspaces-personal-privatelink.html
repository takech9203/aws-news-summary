Amazon WorkSpaces Personal

PrivateLink VPC エンドポイントの
一意な DNS 名サポート

マルチアカウント環境での DNS 競合を解消し、大規模展開を簡素化

2026 年 4 月 6 日

📋 概要

Amazon WorkSpaces Personal が AWS PrivateLink の各 VPC エンドポイントに対して、一意かつパブリックに解決可能な DNS 名を提供するようになりました。これにより、複数の AWS VPC やアカウントにまたがって WorkSpaces を展開する際に、DNS 解決の競合を回避できます。DNS 名はパブリックに解決可能ですが、プライベート IP アドレスに解決されるため、セキュリティを維持しながら設定を簡素化します。

❌ BEFORE: アップデート前の課題
• 全エンドポイントが同じ汎用 DNS 名を共有し、DNS 競合が発生
• マルチアカウント環境でトラフィックの正確なルーティングが困難
• カスタム Route 53 設定や回避策が必要
✅ AFTER: アップデート後の改善
• 各エンドポイントにグローバルに一意な DNS 名を自動割り当て
• マルチアカウント環境でのトラフィックルーティングが適切に
• Route 53 追加設定不要、AWS が自動管理
• 従来の DNS 設定との後方互換性を維持

⚡ 主要機能

🔑 グローバルに一意な DNS 名の自動割り当て

各インターフェイス VPC エンドポイントに対して、AWS が管理するグローバルに一意な DNS 名が自動的に割り当てられます。従来の汎用 DNS 名も引き続き利用可能で、後方互換性が維持されます。DNS 名はパブリックに解決可能ですが、プライベート IP アドレスに解決されるため、対応する VPC 内からのみアクセス可能です。

🔄 AWS マネージドライフサイクル管理

一意の DNS 名は AWS によってライフサイクル全体を通じて自動管理されます。追加の Route 53 設定は不要で、エンドポイントの作成時に自動的に割り当てられ、削除時に自動的にクリーンアップされます。

🌐 マルチアカウント環境でのトラフィックルーティング

集中型 DNS インフラストラクチャを持つ環境で、各エンドポイントへのトラフィックを正確にルーティング可能。複数の VPC やアカウントにまたがる大規模な WorkSpaces 展開をサポートします。

🛠️ 設定方法

前提条件: Amazon WorkSpaces Personal が利用可能なリージョンの AWS アカウント、VPC および PrivateLink の設定権限を持つ IAM ロール、既存の VPC 環境

ステップ 1: VPC エンドポイントの作成

Bash VPC エンドポイント作成 
aws ec2 create-vpc-endpoint \
  --vpc-id vpc-12345678 \
  --service-name com.amazonaws.ap-northeast-1.workspaces \
  --vpc-endpoint-type Interface \
  --subnet-ids subnet-abcdef12 \
  --security-group-ids sg-12345678

作成後、自動的にグローバルに一意な DNS 名が割り当てられます。

ステップ 2: エンドポイントの DNS 名を確認

Bash DNS 名の確認 
aws ec2 describe-vpc-endpoints \
  --vpc-endpoint-ids vpce-0123456789abcdef0 \
  --query 'VpcEndpoints[].DnsEntries'

従来の汎用 DNS 名に加えて、一意な DNS 名が表示されます。

ステップ 3: DNS ルーティングの設定

マルチアカウント環境の集中型 DNS インフラストラクチャで、各 VPC エンドポイントの一意な DNS 名を使用してルーティングルールを設定します。追加の Route 53 設定は不要です。

⚠️ 制限事項・考慮点

• AWS PrivateLink の利用料金は引き続き適用

• VPC エンドポイント数の上限はリージョンごとのサービスクォータに従う
• マルチアカウント環境では新しい一意の DNS 名への移行を推奨

🎯 ユースケース

🏢 ユースケース 1: マルチアカウント環境での WorkSpaces 展開

大企業が部門ごとに異なる AWS アカウントを使用しており、各アカウントで WorkSpaces Personal を展開。集中型 DNS サーバーから各 VPC のエンドポイントに正確にトラフィックをルーティングする必要がある。

Bash マルチアカウント DNS ルーティング例 
# アカウント A の VPC エンドポイント
# DNS: vpce-aaa111.workspaces.ap-northeast-1.vpce.amazonaws.com

# アカウント B の VPC エンドポイント
# DNS: vpce-bbb222.workspaces.ap-northeast-1.vpce.amazonaws.com

# 集中型 DNS で各エンドポイントの一意な DNS 名を使用して
# 適切な VPC にルーティング
✅ DNS 競合なしに各部門の WorkSpaces 環境を正確に分離・管理でき、セキュリティとガバナンスを維持
🌐 ユースケース 2: ハブアンドスポーク型ネットワークアーキテクチャ

Transit Gateway を使用したハブアンドスポーク型ネットワーク構成で、共有サービス VPC に集中型 DNS Resolver を配置している環境。複数のスポーク VPC から WorkSpaces にアクセスする。

Bash 条件付きフォワーディングルール設定 
# 共有サービス VPC の Route 53 Resolver で
# 各スポーク VPC の一意なエンドポイント DNS 名への
# 条件付きフォワーディングルールを設定
aws route53resolver create-resolver-rule \
  --rule-type FORWARD \
  --domain-name "vpce-xxx.workspaces.ap-northeast-1.vpce.amazonaws.com" \
  --target-ips "Ip=10.0.1.10"
✅ 集中型ネットワークアーキテクチャにおいて、各スポーク VPC の WorkSpaces トラフィックを正確にルーティング可能
🔒 ユースケース 3: 規制要件対応のネットワーク分離

金融機関や医療機関など、規制要件により本番環境と開発環境のネットワークを厳密に分離する必要がある組織。各環境で WorkSpaces を使用しているが、DNS レベルでの分離が求められる。

Bash 環境分離の DNS 構成例 
# 本番環境 VPC エンドポイント
# vpce-prod123.workspaces.ap-northeast-1.vpce.amazonaws.com
# -> 10.1.0.x (本番 VPC 内のプライベート IP)

# 開発環境 VPC エンドポイント
# vpce-dev456.workspaces.ap-northeast-1.vpce.amazonaws.com
# -> 10.2.0.x (開発 VPC 内のプライベート IP)
✅ DNS レベルで環境を完全に分離し、規制要件への準拠を技術的に証明可能
