☁️ Amazon EKS (EKS Auto Mode)

EKS Auto Mode が Pod 単位のセキュリティグループに対応

📅 リリース日: 2026 年 11 月 11 日 ｜ 機能: Security groups for Pods (Pod 単位のセキュリティグループ割り当て)

📝 概要

Amazon EKS Auto Mode が security groups for Pods をサポートしました。 個々の Pod に専用の EC2 セキュリティグループルールを適用でき、同一ノード上で稼働する異なるワークロードに異なるセキュリティグループを割り当てられます。 アプリケーションごとに個別のノードプールを作成することなく、Pod レベルのネットワークセグメンテーションを実現できます。

対象の Pod は SecurityGroupPolicy リソースで定義し、ポリシーに一致した Pod には ノードのトランクインターフェイスにアタッチされた専用のブランチ ENI が割り当てられます。 実装には Kubernetes の Dynamic Resource Allocation (DRA) を活用しています。 ポリシーに一致しない Pod は従来どおりノードのセキュリティグループを使用します。

❌ Before: アップデート前の課題
  • Pod 単位でセキュリティグループを割り当てる手段がなく、Pod はノードのセキュリティグループを共有
  • NodeClass の podSecurityGroupSelectorTerms はノード上の全 Pod に同一セットを適用。ワークロード分離にはノードプール分割が必要
  • RDS や ElastiCache へのアクセスを特定ワークロードのみに限定することが困難
  • VPC CNI 版の security groups for Pods は EKS Auto Mode ノードには適用不可
✅ After: アップデート後の改善
  • 同一ノード上の Pod ごとに異なるセキュリティグループを割り当て可能。ノードプール分割なしでセグメンテーション実現
  • SecurityGroupPolicy で Pod ラベルまたはサービスアカウントラベルによる柔軟な対象選択
  • セキュリティグループで接続を許可するデータストアへのアクセスを該当 Pod のみに限定
  • 非 Auto Mode クラスターと同等の運用モデルを EKS Auto Mode でも利用可能

💡 SecurityGroupPolicy に一致した Pod A には専用のブランチ ENI が割り当てられ、指定したセキュリティグループのみが適用されます。ポリシーに一致しない Pod B は従来どおりノードのセキュリティグループを使用します。

⚙️ 主要機能

📜 1. SecurityGroupPolicy リソースによる Pod 単位の割り当て
  • eks.amazonaws.com/v1 API グループの SecurityGroupPolicy で対象 Pod とセキュリティグループを宣言的に定義
  • podSelector、serviceAccountSelector、またはその両方で対象を選択。両方設定時は両方に一致する Pod のみ対象
  • アドミッション Webhook がリソースクレームを自動注入するため、Pod スペック自体の変更は不要
  • ポリシーに一致しない Pod はノードのセキュリティグループを引き続き使用
🌿 2. ブランチ ENI による独立したトラフィック評価
  • 一致した Pod にはノードのトランクインターフェイスにアタッチされた専用ブランチ ENI を割り当て
  • Pod の送受信トラフィックは、ノードのセキュリティグループとは独立してブランチ ENI 上の指定セキュリティグループで評価
  • 同一ノード上の Pod 間トラフィックにも適用 (オープンソース VPC CNI の standard モードとは異なる動作)
🎯 3. 柔軟なセキュリティグループ選択
  • securityGroupSelectorTerms で ID、名前、タグのいずれかにより指定 (1 タームに最大 30 個、各タームは OR 評価)
  • name や tags によるタームは動的に再解決されるため、ポリシーを編集しなくても実効セキュリティグループが変化し得る
  • nodeSelector (karpenter.sh/nodepool キーのみ) で特定の NodePool にポリシーを限定可能
🔗 4. ネイティブ DRA によるオプトイン方式 (代替手段)
  • 各 SecurityGroupPolicy に対してコントローラーが ResourceClaimTemplate を自動生成
  • Pod スペックの resourceClaims からテンプレートを直接参照し、ラベルマッチングを使わず明示的に関連付けることも可能

📄 SecurityGroupPolicy の定義例

YAML SecurityGroupPolicy 定義例 
apiVersion: eks.amazonaws.com/v1
kind: SecurityGroupPolicy
metadata:
  name: my-sgp
  namespace: my-namespace
spec:
  podSelector:
    matchLabels:
      app: my-app
  securityGroupSelectorTerms:
    - id: sg-0123456789abcdef0

🛠️ 設定方法

✅ 前提条件

✓Kubernetes 1.36 以降で稼働する EKS Auto Mode クラスター
✓クラスターの IAM ロールに AmazonEKSNetworkingPolicy 管理ポリシーに加えて ec2:CreateNetworkInterfacePermission を許可するポリシーステートメントを付与
✓Pod に適用するセキュリティグループをクラスターの VPC に作成済みであること
1
セキュリティグループの準備

EKS Auto Mode は同一ノード上の Pod 間トラフィックにもセキュリティグループを適用するため、同じポリシー配下の Pod 同士が通信する場合は自己参照のインバウンドルールを追加します。

Bash自己参照インバウンドルールの追加
# 同一ポリシー配下の Pod 間通信が必要な場合、自己参照のインバウンドルールを追加
aws ec2 authorize-security-group-ingress --group-id sg-0123456789abcdef0 \
  --source-group sg-0123456789abcdef0 --protocol -1
2
SecurityGroupPolicy の作成

podSelector または serviceAccountSelector で対象 Pod を、securityGroupSelectorTerms で適用するセキュリティグループを指定して適用します。

Bash
kubectl apply -f my-sgp.yaml
3
ポリシーの解決状態の確認
Bash
kubectl get securitygrouppolicies.eks.amazonaws.com my-sgp -n my-namespace -o yaml

status.securityGroups に解決された ID が、status.conditions[] の SecurityGroupsResolved に解決結果が表示されます。False の場合は reason フィールド (no_sgs_matched、sg_quota_exceeded、invalid_spec、resolution_error) で失敗原因を確認できます。

⚠️ 解決に失敗したポリシーに一致する Pod は、ノードのセキュリティグループで起動されるのではなく Pending のままになる点に注意してください。
4
Pod へのリソースクレーム注入の確認
Bash
kubectl get pod <pod-name> -o jsonpath='{.spec.resourceClaims}'

結果が空の場合は、Pod のラベルが同一ネームスペース内のどの SecurityGroupPolicy にも一致していないことを示します。

💡 メリット

💼 ビジネス面

✓インフラコストの最適化: ワークロードの分離のためだけにノードプールを分割する必要がなくなり、ノードの集約率を高められる
✓コンプライアンス対応の強化: 決済処理や個人情報を扱うワークロードへのネットワークアクセスを Pod 単位で制御でき、監査要件に対応しやすくなる
✓追加コストなし: EKS Auto Mode の一部として追加料金なしで利用可能

🔧 技術面

✓既存の AWS ネットワーク制御との統合: セキュリティグループで接続を許可する RDS や ElastiCache などに対し、VPC 内の他リソースと同じモデルでアクセス制御できる
✓宣言的かつ Pod スペック変更不要: SecurityGroupPolicy を適用するだけで、アドミッション Webhook が対象 Pod に自動的にリソースクレームを注入する
✓同一ノード内トラフィックの確実な制御: 同一ノード上の Pod 間通信にもセキュリティグループが適用され、意図しない水平方向のアクセスを防止できる
✓非 Auto Mode からの移行が容易: VPC CNI 版から podSelector と serviceAccountSelector をそのまま引き継げるフィールドマッピングが用意されている

⚠️ デメリット・制約事項

🚧 制限事項

⚠Kubernetes 1.36 以降の EKS Auto Mode クラスターでのみ利用可能
⚠1 つの Pod に一致できるポリシーは最大 1 つ。複数ポリシーに一致した Pod は拒否されるため、セレクターはポリシー間で重複しないように設計が必要
⚠ポリシーが解決できるセキュリティグループは最大 16 個だが、ENI あたりの VPC クォータはデフォルト 5 個。6 個以上を使用する場合は事前のクォータ引き上げが必要
⚠IPv6 クラスターで enableV4Egress が有効 (デフォルト) の場合、Pod の IPv4 エグレストラフィックはノードの ENI 経由となり、Pod のセキュリティグループでは評価されない
⚠代替 CNI プラグインやネットワークポリシープラグインとの併用は不可 (EKS Auto Mode 組み込みネットワーキングの Pod にのみ適用)
⚠トランク対応インスタンスタイプのうち ENI スロットが 2 つしかないものでは、本機能と Pod 用の個別サブネット機能を同時に利用できない

🤔 考慮すべき点

💭ブランチ ENI はノードの ENI スロットと IP アドレスを消費するため、ノードの実効 maxPods が低下する。既存の NodePool で導入する場合はノードのリサイクルが推奨される
💭同一ノードを対象とするポリシーは 5 個以下に抑えることを強く推奨。超過するとスケジューリング遅延や、大規模環境での Karpenter と kube-scheduler のリソース消費増加のリスク
💭IMDS、EKS Pod Identity Agent、kubelet のヘルスチェック、CoreDNS といったノードローカルエンドポイントとの通信はセキュリティグループ評価の対象外 (固定の例外セットで、カスタマイズ不可)
💭クラスターを 1.36 以降にアップグレードした直後は、コントロールプレーンコンポーネントの再起動完了まで数分間、本機能が利用できない場合がある
💭EKS Auto Mode を無効化する前に、ポリシー配下の Pod を終了させてすべての SecurityGroupPolicy を削除しておくことが推奨される

🎯 ユースケース

💳 ユースケース 1: 決済ワークロードのデータベースアクセス制限

シナリオ: 同一クラスター上で決済処理アプリケーションと一般的な Web アプリケーションが稼働しており、決済用の Amazon RDS データベースには決済処理 Pod のみがアクセスできるようにしたい。

YAML実装例
apiVersion: eks.amazonaws.com/v1
kind: SecurityGroupPolicy
metadata:
  name: payment-sgp
  namespace: payment
spec:
  podSelector:
    matchLabels:
      app: payment-api
  securityGroupSelectorTerms:
    - id: sg-payment0123456789

RDS のセキュリティグループで sg-payment0123456789 からのインバウンドのみを許可します。

効果: 決済処理 Pod だけがデータベースに到達でき、同一ノード上の他の Pod からのアクセスはネットワークレベルで遮断される。
💰 ユースケース 2: ノードプール分割からの統合によるコスト削減

シナリオ: これまでセキュリティ要件の異なるワークロードごとにノードプールを分割し、ノードレベルのセキュリティグループで分離していたため、ノードの集約率が低くコストがかさんでいた。

YAML実装例
apiVersion: eks.amazonaws.com/v1
kind: SecurityGroupPolicy
metadata:
  name: internal-api-sgp
  namespace: backend
spec:
  serviceAccountSelector:
    matchLabels:
      security-tier: internal
  securityGroupSelectorTerms:
    - tags:
        Team: platform
効果: 複数のワークロードを同一ノードプールに統合しつつ Pod 単位の分離を維持でき、ノード台数と運用対象の NodePool 数を削減できる。
🔄 ユースケース 3: 非 Auto Mode クラスターからの移行

シナリオ: マネージドノードグループで VPC CNI 版の security groups for Pods を利用しており、EKS Auto Mode への移行後も同等の Pod 単位のネットワーク制御を維持したい。

YAML移行前後のスペック比較
# 移行前 vpcresources.k8s.aws/v1beta1
spec:
  securityGroups:
    groupIds:
      - sg-0123456789abcdef0

# 移行後 eks.amazonaws.com/v1
spec:
  securityGroupSelectorTerms:
    - id: sg-0123456789abcdef0
効果: podSelector と serviceAccountSelector はそのまま引き継げるため、最小限のマニフェスト変更で移行可能。移行期間中は両方の API グループのポリシーを併存させることで、Auto Mode ノードと非 Auto Mode ノードの両方で Pod を保護できる。

💰 料金と利用可能リージョン

✓料金: Security groups for Pods は EKS Auto Mode の一部として追加料金なしで利用できます。EKS Auto Mode 自体の料金 (管理対象の EC2 インスタンスに対する管理料金) と、EC2 インスタンスなどの基盤リソースの料金は通常どおり発生します。
✓リージョン: EKS Auto Mode が利用可能なすべての AWS リージョンで利用できます。

🔗 関連サービス・機能

🧩 Amazon VPC CNI の security groups for Pods

非 Auto Mode クラスター向けの同等機能。vpcresources.k8s.aws/v1beta1 API グループを使用し、スペックの互換性はないが移行パスが用意されている。

🖥️ NodeClass の podSecurityGroupSelectorTerms

ノード上のすべての Pod に同一のセキュリティグループを適用する EKS Auto Mode の既存機能。本機能と併用可能。

⚙️ Kubernetes Dynamic Resource Allocation (DRA)

本機能の実装基盤。ブランチ ENI のスロットをデバイスとしてスケジューラーが割り当てる。

🗄️ Amazon RDS / Amazon ElastiCache

セキュリティグループでアクセスを許可するデータストア。本機能により Pod 単位でのアクセス制御が可能になる。

📌 まとめ

EKS Auto Mode でも Pod 単位のセキュリティグループ割り当てが可能になり、非 Auto Mode クラスターとの機能差分が 1 つ解消されました。 セキュリティグループベースでアクセス制御しているデータストアを利用する環境や、分離要件のためにノードプールを分割している環境では、 クラスターの Kubernetes 1.36 以降へのアップグレードと SecurityGroupPolicy の導入を検討する価値があります。

導入時は、Pod あたり 1 ポリシーの制約、ENI あたりのセキュリティグループクォータ (デフォルト 5 個)、 ノードの実効 maxPods への影響を事前に確認してください。
