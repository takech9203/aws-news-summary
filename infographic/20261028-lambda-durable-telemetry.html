⚡ AWS Lambda

Durable Functions のライブテレメトリエクスポート

📅 リリース日: 2026 年 10 月 28 日 | Durable Execution Telemetry Exporter プラグイン + Telemetry MCP サーバー

📝 概要

AWS Lambda durable functions に、実行履歴をライブでエクスポートできる Durable Execution Telemetry Exporter プラグインが追加されました。 durable 実行のステップごとの履歴 (実行ステータス、各オペレーションの所要時間、ステップの入出力、エラー情報) を記録し、 CloudWatch Logs、S3 (Athena 連携)、DynamoDB、Aurora、OpenSearch Service など 13 種類の組み込みエクスポーターに自動送信します。

あわせてリリースされた Telemetry MCP サーバーにより、 Kiro や Claude Code などの MCP 対応 AI エージェントから 「最近失敗した実行を一覧して原因を調べて」といった自然言語での照会が可能になります。

❌ Before - アップデート前の課題
  • 1 つの durable 実行が複数の Lambda 呼び出しに分散し、呼び出し単位のログでは実行全体を追跡しにくい
  • 実行履歴は標準の保持期間を超えて保存できず、長期的な運用・ビジネス分析が困難
  • 外部データストアへの保存には独自の計装コードや収集基盤の実装が必要
✅ After - アップデート後の改善
  • プラグインを 1 行追加するだけで、実行ごとの完全な JSON レコードを自動エクスポート
  • 保持期間を超えた長期保存と、運用・ビジネスインサイトの抽出が可能に
  • 機密フィールドのマスキングとサンプリングレートでデータ量とプライバシーを制御
  • MCP サーバー経由で AI エージェントが自然言語でテレメトリを照会可能に

Telemetry Exporter プラグインはハンドラーと同一プロセス内で動作し、durable 実行のライフサイクルを購読して実行ごとの累積スナップショットを構築します。 レコードは設定したすべてのエクスポーターに並列で送信され、MCP サーバー経由で AI エージェントから読み取り専用で照会できます。

🚀 主要機能

1️⃣ Durable Execution Telemetry Exporter プラグイン

→ durable 実行ごとに 1 つの完全な JSON レコード (DurableExecutionTelemetryRecord) を生成

→ 実行 ARN、実行名、関数名、ステータス、開始・終了時刻、所要時間、入出力、各オペレーションの履歴を含む

→ ハンドラーと同一プロセスで動作し、チェックポイントされた状態から呼び出しごとに累積スナップショットを再構築

→ TypeScript、Python、Java、Go 向けにオープンソースで提供

2️⃣ 13 種類の組み込みエクスポーター

→ LambdaLogExporter: 関数自身のロググループに出力 (追加 IAM 不要、デフォルト)

→ CloudWatchLogs / S3 / DynamoDB / Aurora / Redshift / OpenSearch の各 Exporter

→ EventBridge / Firehose / SQS / OTel / Http / File の各 Exporter

→ S3Exporter は Hive 形式パーティション year=YYYY/month=MM/day=DD/ で書き込み、AWS Glue / Amazon Athena での分析に最適化

3️⃣ データ量とプライバシーの制御

→ emitMode: on-complete (完了時に 1 回、デフォルト) / on-failure (失敗時のみ、最小オーバーヘッド) / on-change (準リアルタイム)

→ samplingRate: 実行 ARN のハッシュに基づく決定的サンプリングで、実行単位の一貫性を保証

→ content トランスフォームによる入出力の機密フィールドのマスキング

→ エクスポーターごとの maxRecordSizeBytes によるレコードサイズ制御 (超過時は truncated: true フラグ付きで切り詰め)

4️⃣ Durable Execution Telemetry MCP サーバー

→ ローカル stdio サーバーとして動作し、Kiro、Claude Code、Cursor などの MCP 対応エージェントから照会可能

→ 5 つのツールを提供: test_destination、describe_schema、list_executions、get_execution、query

→ SQL 系の送信先では SELECT / WITH ... SELECT のみ許可される読み取り専用設計

→ 設定は環境変数のみで行い、認証情報は標準の AWS SDK プロバイダーチェーンを使用

⚙️ 設定方法

✅ 前提条件

✓AWS Lambda durable functions を利用していること
✓Durable Execution SDK (TypeScript、Python、Java、Go のいずれか) で関数を実装していること
✓エクスポート先リソース (S3 バケット、DynamoDB テーブルなど) への書き込み権限 (LambdaLogExporter の場合は不要)
1
プラグインのインストール
Bashnpm でインストール
npm install @aws/durable-execution-sdk-js-telemetry-exporter

TypeScript の場合、npm でテレメトリエクスポータープラグインのパッケージをインストールします。

2
ハンドラーへのプラグイン追加
TypeScript1 行でプラグインを有効化
import { withDurableExecution } from "@aws/durable-execution-sdk-js";
import { durableExecutionTelemetry } from "@aws/durable-execution-sdk-js-telemetry-exporter";

export const lambdaHandler = withDurableExecution(handler, {
  plugins: [durableExecutionTelemetry({})],
});

設定なしの場合、デフォルトの LambdaLogExporter が関数自身の CloudWatch ロググループに JSON を出力します (追加の IAM 設定は不要)。

3
エクスポート先とサンプリングの設定
TypeScript複数エクスポーター + マスキング + サンプリング
const telemetry = durableExecutionTelemetry({
  emitMode: "on-complete",
  samplingRate: 0.1,
  content: {
    input: (event) => ({ orderId: event.orderId }),
    output: (result) => ({ status: result.status }),
  },
  exporters: [
    new S3Exporter({ bucket: "my-telemetry-bucket" }),
    new DynamoDBExporter({ tableName: "durable-execution-telemetry-live" }),
  ],
});

複数のエクスポーターを設定するとレコードが並列に送信されます。samplingRate でデータ量を制御し、content トランスフォームで機密フィールドをマスキングします。

4
MCP サーバーのセットアップ
BashKiro への MCP サーバー登録
kiro-cli mcp add \
  --name durable-telemetry \
  --command npx \
  --args "-y,@aws/durable-execution-sdk-js-telemetry-mcp" \
  --env DURABLE_TELEMETRY_DESTINATION_TYPE=dynamodb \
  --env DURABLE_TELEMETRY_DYNAMODB_TABLE_NAME=durable-execution-telemetry-live \
  --env DURABLE_TELEMETRY_REGION=us-east-1 \
  --scope workspace

送信先の種類やテーブル名は環境変数で指定し、認証情報は標準の AWS SDK プロバイダーチェーンから取得されます。

💡 メリット

💼 ビジネス面

✓追加費用なし: プラグインと MCP サーバーは追加料金なしで利用可能 (送信先リソースの費用のみ発生)
✓ビジネスインサイトの抽出: 実行履歴を Athena や Redshift で分析し、注文処理時間や失敗率などの業務指標を把握
✓障害対応の迅速化: AI エージェント経由で失敗した実行を自然言語で調査でき、MTTR を短縮

🔧 技術面

✓1 行の設定で導入可能: カスタム計装コードや別エージェントが不要で、既存の durable functions にすぐ適用
✓決定的サンプリング: 実行 ARN のハッシュに基づくため、サンプリング対象の実行はすべてのレコードが揃う
✓読み取り専用の安全な AI 連携: MCP サーバーは SELECT 系クエリのみ許可し、書き込み操作を事前に拒否

⚠️ デメリット・制約事項

🚧 制限事項

✗デフォルトでは入出力がそのまま記録されるため、本番環境では content トランスフォームによるマスキング設定が実質必須
✗呼び出しを伴わずに発生する STOPPED や TIMED_OUT 状態はプラグインから観測できず、EventBridge のライフサイクルイベントで補完が必要
✗operationDetail の full-tree モードは pluginsConfig.childOperationsDepth の設定が必要で、リプレイコストが増加

🤔 考慮すべき点

⚠️テレメトリ自体は無料だが、送信先のコスト (CloudWatch Logs のインジェスト、DynamoDB の書き込みなど) が発生するため、samplingRate と emitMode で制御する
⚠️オペレーション名はそのままフィールドとして使用されるため、. を避け、英数字と -、_ のみを使用することを推奨
⚠️レコードサイズが maxRecordSizeBytes を超えると送信先ごとに切り詰めが発生 (オペレーション結果、古いオペレーション、入出力の順)

🎯 ユースケース

🌙 ユースケース 1: オンコールエンジニアの障害調査

シナリオ: 深夜に注文処理ワークフローの失敗アラートが発生し、オンコールエンジニアが迅速に原因を特定したい。

TextKiro への自然言語での問い合わせ
「過去 1 時間で失敗した order-processor の実行を一覧して、
最も多い失敗ステップと原因を教えて」

効果: 各データストアのクエリ言語を知らなくても、AI エージェントが list_executions と get_execution ツールで失敗実行を特定し、エラー内容まで提示するため、調査時間を大幅に短縮できる。

📊 ユースケース 2: CloudWatch Logs Insights による失敗分析

シナリオ: 追加インフラなしで、失敗した durable 実行を定常的にモニタリングしたい。

Logs Insights失敗実行のクエリ
fields executionName, status, durationMs
| filter recordType = "DurableExecutionTelemetry" and status = "FAILED"
| sort durationMs desc

効果: デフォルトの LambdaLogExporter のみで、IAM 追加設定なしに失敗実行の一覧と所要時間を即座に分析できる。

📈 ユースケース 3: Athena による長期的なビジネス分析

シナリオ: アナリストが特定顧客のトランザクション履歴や月次の処理傾向を SQL で分析したい。

TypeScriptS3 への長期アーカイブ設定
const telemetry = durableExecutionTelemetry({
  exporters: [new S3Exporter({ bucket: "order-telemetry-archive" })],
});
// S3 には year=YYYY/month=MM/day=DD/ 形式のパーティションで保存され、
// Glue / Athena からそのまま SQL でクエリ可能

効果: 標準の実行履歴保持期間を超えてデータを保持し、パーティション化されたデータに対する低コストな SQL 分析が可能になる。

💰 料金・利用可能リージョン

💵 料金

→ プラグインおよび MCP サーバーは追加料金なしで利用可能

→ エクスポート先リソースの利用料金 (CloudWatch Logs のインジェスト料金、DynamoDB の書き込み料金、S3 のストレージ料金など) は別途発生

→ samplingRate と emitMode の設定によりコストを制御可能

🌍 利用可能リージョン

→ Lambda durable functions をサポートするすべての AWS リージョンで利用可能

🔗 関連サービス・機能

  • AWS Lambda durable functions: 本プラグインの対象機能。最長 1 年間実行できる回復力の高いマルチステップアプリケーションや AI ワークフローを構築できる
  • Amazon CloudWatch Logs: デフォルトのエクスポート先。Logs Insights で即座にクエリ可能
  • Amazon Athena / Amazon S3: 長期保存と SQL 分析のためのエクスポート先。Hive 形式パーティションに対応
  • Amazon EventBridge: テレメトリ連携によるアラートや自動修復のほか、プラグインが観測できない STOPPED / TIMED_OUT 状態の補完にも使用
  • Kiro: MCP サーバー経由でテレメトリデータを自然言語で照会できる AWS の AI 搭載 IDE

📌 まとめ

Lambda durable functions の実行履歴を 1 行の設定で 13 種類の送信先にエクスポートできるようになり、 長期保存・分析・AI エージェントによる自然言語での照会まで一気通貫で実現できるようになりました。
