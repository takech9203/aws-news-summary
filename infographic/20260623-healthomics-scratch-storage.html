🧬 AWS HealthOmics

プライベートワークフロー向け
エフェメラルストレージ

📅 リリース: 2026 年 6 月 23 日

📌 概要

AWS HealthOmics に、プライベートワークフロー向けの エフェメラルストレージ (一時的なスクラッチ領域) が追加されました。各ワークフロータスクに専用のローカルボリュームが /tmp にマウントされ、ゲノム配列アラインメント、BAM ソート、バリアントコールなど大量のスクラッチデータを生成する I/O 集約ワークロードの実行時間を短縮し、コストを削減します。AWS HealthOmics は HIPAA 適格なフルマネージドのバイオインフォマティクスワークフローサービスです。

🔴 アップデート前の課題

  • スクラッチ I/O が共有ファイルシステム (run storage) に書き込まれ、同時実行タスク間で I/O 帯域を奪い合いパフォーマンスが不安定
  • 共有ファイルシステムのスロットリングで、アラインメントや BAM ソートの処理時間が長期化
  • スクラッチ用に多くの run storage をプロビジョニングする必要がありコスト増加

🟢 アップデート後の改善

  • 各タスクに専用ローカルボリュームを /tmp にマウントし、スクラッチ I/O を共有 FS から分離
  • 専用 IOPS とスループットで I/O のばらつきとスロットリングを軽減し、パフォーマンスが安定
  • 実行時間が短縮されコンピューティングコストを削減。Static run storage のプロビジョニング量も削減可能

各タスクが個別の暗号化されたローカルボリュームを /tmp に持ち、スクラッチ I/O を共有ファイルシステムから分離します。各ボリュームはタスク終了時に削除されます。

⭐ 主要機能

📦 タスクごとの専用ローカルボリューム

  • 各ワークフロータスクインスタンスに専用ストレージを /tmp にマウント
  • 専用 IOPS とスループットを割り当て、他タスクと帯域を奪い合わない
  • 多くのワークフロー言語は /tmp (および $TMP、$TMPDIR) を使用するため変更不要なケースが多い

📐 柔軟なストレージサイズ設定

  • デフォルト 16 GiB を追加料金なしで提供 (Standard / Compute 最適化 / Memory 最適化の全タイプ)
  • disk ディレクティブで 1 タスクあたり最大 3,072 GiB まで増設可能
  • サイズは 16 GiB 単位で切り上げ (16、32、48 … 最大 3,072 GiB)

🎛️ 実行時の有効化と無効化

  • StartRun API の scratchStorageMode を LOCAL に設定して有効化
  • 設定は実行内の全タスクに適用され、CPU インスタンスのみが対象
  • 障害切り分け時などは SHARED を指定して無効化できる

🔒 暗号化とライフサイクル管理

  • サービス管理の AWS KMS キーで保存時に暗号化
  • GPU インスタンスはボリュームごとに固有キーでハードウェア暗号化、終了時にキー破棄
  • アタッチとライフサイクルは HealthOmics が管理、追加 IAM 権限は不要

📈 CloudWatch によるモニタリング

  • タスクごとのメトリクスを CloudWatch マニフェストログに書き込み
  • プロビジョニング量 scratchStorageReservedGiB と使用量 scratchStorageUtilizedGiB を確認
  • 過剰・過少プロビジョニングの判断に活用できる

⚙️ 設定方法

前提条件

✓AWS HealthOmics のプライベートワークフローが作成済み
✓HealthOmics サービスロール (実行ロール) が設定済み
✓WDL / Nextflow / CWL のいずれかで記述されたワークフロー定義がある

ステップ 1: スクラッチ I/O を /tmp に向ける (WDL の例)

WDLsamtools sort の一時ファイルを /tmp に
task sort_bam {
    runtime {
        cpu:  16
        disks: "700 GiB"
    }
    command <<<
        samtools sort -T /tmp/sort_buffer ~{input_bam} -o ~{output_bam}
    >>>
}

700 GiB はヒントとして扱われ、次の 16 GiB ティア (704 GiB) に切り上げられます。-T /tmp/sort_buffer でツールの一時ファイルを /tmp に向けることが重要です。

ステップ 2: scratchStorageMode を LOCAL にして実行を開始

BashAWS CLI: start-run
aws omics start-run \
    --workflow-id <workflow-id> \
    --role-arn arn:aws:iam::123456789012:role/OmicsServiceRole \
    --output-uri s3://amzn-s3-demo-bucket/output-folder/ \
    --parameters file:///path/to/parameters.json \
    --scratch-storage-mode LOCAL

省略した場合は SHARED (デフォルト) となり、エフェメラルストレージは有効化されません。

ステップ 3: 有効なモードを確認

BashAWS CLI: get-run
aws omics get-run --id <run-id>

応答の scratchStorageMode フィールドを確認します。StartRun リクエストで明示的に渡した場合のみ応答に含まれます。

✅ メリット

💼 ビジネス面

  • コスト削減: I/O バウンドタスクの実行時間短縮でコンピューティングコスト削減。Static run storage のプロビジョニング量も削減
  • デフォルト無料枠: 各タスク 16 GiB が追加料金なし
  • HIPAA 適格: 機密性の高いゲノムデータを扱うワークロードを高速化

🛠️ 技術面

  • 安定したパフォーマンス: 専用 IOPS とスループットでスロットリングや I/O のばらつきを軽減
  • 変更不要なケースが多い: /tmp に書き込むタスクは自動的にエフェメラルストレージを使用
  • 可観測性: CloudWatch マニフェストログでサイジングを最適化

⚠️ デメリット・制約事項

制限事項

✗永続化されない。タスク終了時に常に削除され、/tmp のデータをタスク出力やワークフロー出力にできない (実行時に失敗)
✗タスク間で共有されない。各タスクは隔離されたボリュームを持つ
✗タスク実行中にサイズを変更できない (開始時に固定)
!CPU タスクの最大は 3,072 GiB。超過要求は 3,072 GiB でプロビジョニングされ run ログに警告 (タスクは失敗しない)
!SHARED モードでは CPU タスクの disk / tmpdirMin 等のディレクティブが無視される

考慮すべき点

!作業ディレクトリ (input/、./、out/ など) に書き込むワークフローは自動では恩恵を受けない。/tmp または $TMPDIR にリダイレクトが必要
!式ベースの disk ディレクティブ評価結果が 3,072 GiB を超えると実行時に失敗し、それまでのコンピューティングコストが課金される
!$TMPDIR が別の場所にマッピングされていないことを確認する

🎯 ユースケース

1. BAM のソートとバリアントコール

大きな BAM / CRAM ファイルを繰り返し読み書きするバリアントコールワークフロー。数百 GiB 規模のスクラッチ領域が必要。

WDL
runtime { cpu: 16, disks: "400 GiB" }
command <<<
    samtools sort -T /tmp/sort_buffer ~{input_bam} -o ~{sorted_bam}
    bcftools sort -T /tmp ~{vcf} -o ~{output_vcf}
>>>

→ 効果: スクラッチ I/O が専用ボリュームに向けられソート処理が高速化。実行時間とコストを削減。

2. RNA-Seq 融合遺伝子検出

大きな中間 BAM を生成し、生 FASTQ とアラインメント出力を同時保持。大きなスクラッチディスク (例: 512 GiB / タスク) が必要。

Nextflow
process fusion_detect {
    disk '512 GB'
    script:
    """
    STAR --runThreadN 16 --readFilesIn reads.fastq --outTmpDir /tmp/star_tmp --outFileNamePrefix out_
    """
}

→ 効果: 大容量の一時ファイルを高速ローカルボリュームに保持し、共有 FS への負荷を回避。

3. デノボゲノムアセンブリ

ロングリードアセンブリで生リードと一時的なアセンブリ成果物を繰り返し書き換える、メモリ・ディスク集約的なワークフロー。数 TiB のエフェメラルストレージが必要な場合も。

CWL
requirements:
  ResourceRequirement:
    coresMin: 16
    tmpdirMin: 2097152   # 2,048 GiB を MiB で指定

→ 効果: 大容量スクラッチを専用ボリュームで確保し、アセンブリ工程のパフォーマンスを安定化。

💰 料金

デフォルトの 16 GiB / タスクは追加料金なし。デフォルトを超えてプロビジョニングしたストレージ分のみ課金されます。デフォルト超過分の要求は最も近いティアに切り上げられます。GPU インスタンスの NVMe はインスタンス料金に含まれ追加料金は発生しません。

使用量課金対象
16 GiB (デフォルト) / タスク課金なし
400 GiB / タスクデフォルト超過分 (384 GiB) が課金対象
GPU インスタンスの NVMe課金なし (インスタンス料金に含まれる)

📝 まとめ

AWS HealthOmics のエフェメラルストレージは、ゲノム配列アラインメントや BAM ソート、バリアントコールなど I/O 集約的なバイオインフォマティクスワークフローのパフォーマンスを安定させ、コストを削減する重要なアップデートです。デフォルトの 16 GiB は無料で、多くの場合ワークフローの変更なしに恩恵を受けられます。まずは scratchStorageMode: LOCAL で実行を開始し、CloudWatch マニフェストログの使用量メトリクスを確認しながら disk ディレクティブで適切なサイズに調整することを推奨します。
