Amazon OpenSearch Serverless

⏱️ 次世代 OpenSearch Serverless における時系列コレクションの提供開始

📅 リリース日: 2026 年 10 月 28 日 | 機能: 時系列コレクション (Time series collections)

📝 概要

次世代の Amazon OpenSearch Serverless で、時系列コレクションがサポートされました。ログ、メトリクス、トレース、イベントデータといった時系列データを、クラスターのプロビジョニングや管理なしで取り込み、保存、分析できる新しいコレクションタイプです。

取り込みスパイクを自動的に吸収しながら直近のデータを高速にクエリでき、低コストのウォームストレージティアが新たに追加されました。さらにアラートと異常検知が組み込みで提供され、別ツールなしで問題の通知や異常なパターンの検出が可能です。

❌ アップデート前の課題

  • ホット / ウォームのティアリングをインデックス単位で柔軟に制御できず、長期履歴データの低コスト保持が難しかった
  • Serverless コレクションにはアラートや異常検知が組み込まれておらず、問題検知には別のツールや仕組みが必要だった
  • アイドル時にもコンピューティングが稼働し続けるため、間欠的なワークロードではコスト効率が低かった

✅ アップデート後の改善

  • ホットティアとウォームティア (Amazon S3) の 2 層構成により、直近データの高速クエリと長期データの低コスト保持を同一コレクション内で両立
  • インデックス設定 (index.warm.after、index.data.retention) だけでティアリングと保持期間を制御。別途ライフサイクルポリシーが不要
  • アラートモニター (per-query、per-bucket、PPL) と Random Cut Forest による異常検知が組み込みで利用可能
  • 取り込みスパイク時に数秒でスケールし、アイドル時はゼロまでスケールダウン

ドキュメントは取り込み時にホットティアと Amazon S3 の両方へ書き込まれ、設定した期間を過ぎるとホットコピーが削除されてウォームティアのみに残ります。ウォームデータへのクエリ時はデータがホットティアへロードされ、2 回目以降はホットティアの速度でクエリできます。

⚙️ 主要機能

1️⃣ 時系列コレクションタイプ

次世代 OpenSearch Serverless の新しいコレクションタイプ (TIMESERIES)。ログ、メトリクス、トレース、イベントデータの取り込み、保存、分析に最適化。1 コレクションあたり最大 100 TB のホットストレージをサポートし、すべてのドキュメントにタイムスタンプが必須 (デフォルトは @timestamp、index.timestamp_field で変更可能)。

2️⃣ ホット / ウォームの 2 層ストレージティア

取り込み時にホットティアと Amazon S3 の両方へ書き込み。index.warm.after でホットティアの保持期間をインデックス単位で設定 (最小 1 日から最大 10 年、デフォルト 1 日)。ウォームデータへの初回クエリはロードが発生するため遅くなるが、2 回目以降はホットティアの速度で実行。両ティアにまたがるクエリも単一のレスポンスで結果を返却。

3️⃣ インデックスレベルのデータ保持設定

index.data.retention で保持期間を日数で指定 (1 日から 3,650 日)。インデックスまたはインデックステンプレートに直接設定でき、別途ライフサイクルポリシーが不要。ティアリング (速度とコストの制御) と保持期間 (削除の制御) は独立して設定可能。

4️⃣ 自動スケーリングとスケールトゥゼロ

取り込みスパイク時に数秒でコンピューティングがスケールし、アイドル時はゼロまでスケールダウン。コレクショングループで共有コンピューティング上限を OCU (OpenSearch Compute Unit) 単位で定義。

5️⃣ 組み込みのアラートと異常検知

per-query モニター: 単一値のしきい値監視 (例: 平均レイテンシ) / per-bucket モニター: グループごとの個別評価 (例: ホストごとのエラー率) / PPL モニター: Piped Processing Language による複雑な条件定義 / 異常検知: Random Cut Forest (RCF) が正常パターンを学習し、固定しきい値なしでほぼリアルタイムに逸脱を検出。

📄 インデックステンプレートの設定例

JSON インデックステンプレート 
PUT /_index_template/app-logs
{
  "index_patterns": ["app-logs*"],
  "template": {
    "settings": {
      "index.timestamp_field": "event_time",
      "index.warm.after": "7d",
      "index.data.retention": "30"
    }
  }
}

🛠️ 設定方法

前提条件

  • 次世代 OpenSearch Serverless が利用可能なリージョンであること
  • OpenSearch Serverless の操作権限を持つ IAM プリンシパルがあること
  • AWS CLI を使用する場合は最新バージョンへ更新しておくこと
1
コレクショングループの作成

次世代 (NEXTGEN) のコレクショングループを作成し、共有コンピューティングの上限と下限を OCU 単位で定義。最小値を 0 に設定することで、アイドル時のスケールトゥゼロが有効になります。

Bash AWS CLI 
aws opensearchserverless create-collection-group \
    --name app-logs-group \
    --generation NEXTGEN \
    --standby-replicas ENABLED \
    --capacity-limits '{
        "minIndexingCapacityInOCU": 0,
        "minSearchCapacityInOCU": 0,
        "maxIndexingCapacityInOCU": 96,
        "maxSearchCapacityInOCU": 96
    }'
2
ネットワークポリシーとデータアクセスポリシーの作成

ネットワークアクセス (パブリックまたは VPC) を定義するネットワークポリシーと、IAM プリンシパルに対する操作権限を定義するデータアクセスポリシーを作成。コンソールの「Express Create」を使用すると、コレクショングループ、暗号化、ネットワークアクセス、データアクセスをワンクリックでまとめてセットアップできます。

3
時系列コレクションの作成

コレクションタイプに TIMESERIES を指定して時系列コレクションを作成。この例では AWS 所有キーによる暗号化を使用しています。

Bash AWS CLI 
aws opensearchserverless create-collection \
    --name app-logs \
    --type TIMESERIES \
    --collection-group-name app-logs-group \
    --encryption-config aWSOwnedKey=true
4
インデックステンプレートの作成とデータ取り込み

タイムスタンプフィールド、ホット保持期間 (index.warm.after)、データ保持期間 (index.data.retention) を定義したインデックステンプレートを作成し、データを取り込み。取り込み後は Observability ワークスペースでダッシュボード、モニター、異常検知ディテクターを設定できます。

⚖️ メリット・デメリット

💼 ビジネス面のメリット

✓ストレージコストの削減: アクセス頻度の低いデータを低コストのウォームティアへ自動移行し、数か月から数年の長期履歴を低コストで検索可能な状態に保てる
✓運用負荷の軽減: クラスターのプロビジョニングや管理、ライフサイクルポリシーの運用が不要になり、インデックス設定のみでデータ管理が完結する
✓コンピューティングコストの最適化: スケールトゥゼロにより、間欠的なワークロードではアイドル時のコンピューティングコストが発生しない

🔧 技術面のメリット

✓取り込みスパイクへの自動対応: 数秒でスケールするコンピューティングにより、急激なログ量の増加にも自動的に対応できる
✓ツール統合の簡素化: アラートと異常検知が組み込まれたため、別の監視ツールとの連携や運用が不要になる
✓透過的なティア間クエリ: ホットとウォームにまたがるクエリも単一レスポンスで返却されるため、アプリケーション側でティアを意識する必要がない

🚫 制限事項

✗すべてのドキュメントにタイムスタンプが必須であり、欠落、null、不正な値を持つドキュメントは拒否される
✗タイムスタンプはインデックス後に変更できない
✗ホット保持期間 (index.warm.after) は最小 1 日であり、保持期間 (index.data.retention) を超える値は設定できない
✗データ保持期間は最大 3,650 日 (10 年)

⚠️ 考慮すべき点

⚠ウォームティアのデータへの初回クエリは、ホットティアへのロードが発生するため遅くなる。頻繁にアクセスするデータはホット保持期間を長めに設定する検討が必要
⚠コレクショングループの最大 OCU 設定はコスト上限と性能上限の両方に影響するため、ワークロードに応じた調整が必要
⚠次世代 OpenSearch Serverless を前提とした機能であり、従来 (Classic) のコレクションとは挙動が異なる

🎯 ユースケース

📱 ユースケース 1: アプリケーションモニタリング

シナリオ: マイクロサービスのアプリケーションログを集約し、直近 1 週間は高速に分析しつつ、監査やトレンド分析のために 1 年間保持したい。

JSON インデックステンプレート設定 
PUT /_index_template/app-logs
{
  "index_patterns": ["app-logs*"],
  "template": {
    "settings": {
      "index.warm.after": "7d",
      "index.data.retention": "365"
    }
  }
}

効果: 直近 7 日間のログはホットティアで高速にクエリでき、それ以降はウォームティアで低コストに保持。per-bucket モニターでホストごとのエラー率を監視し、問題発生時に通知を受け取れる。

🔒 ユースケース 2: セキュリティ分析

シナリオ: VPC フローログや認証ログなどのセキュリティログを長期間保持し、インシデント調査時に過去データまで遡って検索したい。

JSON インデックステンプレート設定 
PUT /_index_template/security-logs
{
  "index_patterns": ["security-logs*"],
  "template": {
    "settings": {
      "index.warm.after": "30d",
      "index.data.retention": "1095"
    }
  }
}

効果: 3 年分のセキュリティログを同一コレクション内で検索可能に保ちつつ、ストレージコストを抑制。異常検知 (RCF) により、固定しきい値では捉えにくい不審なアクセスパターンを自動検出できる。

📡 ユースケース 3: IoT テレメトリ

シナリオ: 大量の IoT デバイスから送信されるテレメトリデータを取り込み、送信量の急増にも自動で対応しながらコストを最適化したい。

Bash コレクショングループ設定 
aws opensearchserverless create-collection-group \
    --name iot-telemetry-group \
    --generation NEXTGEN \
    --capacity-limits '{
        "minIndexingCapacityInOCU": 0,
        "minSearchCapacityInOCU": 0,
        "maxIndexingCapacityInOCU": 48,
        "maxSearchCapacityInOCU": 48
    }'

効果: デバイスからの取り込みスパイクを自動的に吸収し、夜間などアイドル時はコンピューティングがゼロまでスケールダウンしてコストを削減できる。

💰 料金

消費したコンピューティング (OCU 単位) に加え、ホットストレージとウォームストレージがそれぞれ GB - 月単位で課金されます。ホットティアの料金は、現在ホットティアに存在するデータに対してのみ適用されます。新しいウォームストレージティアの料金詳細は、Amazon OpenSearch Service の料金ページを参照してください。

🌍 利用可能リージョン

次世代 Amazon OpenSearch Serverless が提供されているすべての AWS 商用リージョンで利用可能です。リージョンの一覧は AWS General Reference のサービスエンドポイントを参照してください。

🔗 関連サービス・機能

☁️ Amazon OpenSearch Service

マネージド型の OpenSearch クラスターを提供するサービス。Serverless はそのサーバーレスオプション。

🪣 Amazon S3

ウォームティアのストレージ基盤として使用され、低コストの長期保持を実現。

📈 Amazon CloudWatch

メトリクスやログの収集元として、OpenSearch Serverless への取り込みパイプラインと組み合わせて利用可能。

🚚 Amazon OpenSearch Ingestion

各種ソースから OpenSearch Serverless コレクションへデータを取り込むためのマネージドパイプライン。

💡 まとめ

次世代 Amazon OpenSearch Serverless の時系列コレクションは、ホット / ウォームの 2 層ティアリング、インデックスレベルの保持設定、スケールトゥゼロ、組み込みのアラートと異常検知により、オブザーバビリティワークロードの運用とコストを大きく改善するアップデートです。

ログ分析やセキュリティ分析で OpenSearch Serverless を利用中、または検討中の場合は、ワークロードのアクセスパターンに応じた index.warm.after と index.data.retention の設計から検証を始めることを推奨します。
