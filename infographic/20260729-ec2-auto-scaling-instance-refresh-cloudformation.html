🔄 CloudFormation での Instance Refresh サポート

新しい更新ポリシー AutoScalingInstanceRefresh でスタック更新時にインスタンスを安全にローリング置換  |  リリース日: 2026 年 7 月 29 日

📌 概要

CloudFormation スタックの更新でインスタンスの置き換えが必要なプロパティ (起動テンプレートやサブネット構成など) が変更されると、CloudFormation が自動的に Instance Refresh をトリガーし、Auto Scaling グループ内のインスタンスを安全にローリング置換します。

Instance Refresh が持つ豊富なデプロイ制御機能 (ルートボリューム置換、launch-before-terminate、CloudWatch アラーム監視、チェックポイントとベイクタイム) を CloudFormation のワークフロー内で直接利用可能。更新中もスケーリングポリシーやヘルスチェックは有効なまま維持され、失敗時は標準のスタックロールバックで元の構成に復元されます。

❌ Before: アップデート前の課題
  • AutoScalingRollingUpdate / AutoScalingReplacingUpdate では Instance Refresh 固有の機能 (スキップマッチング、チェックポイント、アラーム監視、ルートボリューム置換) を利用できなかった
  • Instance Refresh を使うにはスタック更新後に StartInstanceRefresh API を別途呼び出す運用 (カスタムリソースや CI/CD の追加ステップ) が必要
  • AutoScalingRollingUpdate では更新中に Auto Scaling プロセスを停止するのが一般的で、スケーリング動作に制約
✅ After: アップデート後の改善
  • UpdatePolicy に AutoScalingInstanceRefresh を宣言するだけで、スタック更新時に Instance Refresh が自動実行
  • launch-before-terminate (MinHealthy 100 / MaxHealthy 最大 200) で容量を維持したまま置き換え可能
  • アラーム監視、チェックポイント、ベイクタイムによる段階的デプロイを IaC で宣言的に構成
  • 更新中もスケーリングポリシーとヘルスチェックが有効。失敗時はスタックロールバックで自動復旧

スタック更新でインスタンス置き換えが必要なプロパティ変更を検出すると Instance Refresh が自動開始され、CloudWatch アラーム監視のもとで段階的にインスタンスが置き換えられます。

⚙️ 主要機能

1️⃣ AutoScalingInstanceRefresh 更新ポリシー
  • AWS::AutoScaling::AutoScalingGroup リソースの UpdatePolicy 属性に宣言する新しいポリシー
  • 自動トリガー対象プロパティ: LaunchTemplate、MixedInstancesPolicy、VPCZoneIdentifier、AvailabilityZones、AvailabilityZoneIds、PlacementGroup
  • Strategy は Rolling (通常のインスタンス置換) と ReplaceRootVolume (ルートボリュームのみ置換するインプレース更新) を選択可能
2️⃣ 柔軟なデプロイ制御 (Preferences)
  • MinHealthyPercentage / MaxHealthyPercentage: 100/200 の組み合わせで launch-before-terminate (新インスタンス起動後に旧インスタンスを終了) を実現
  • CheckpointPercentages / CheckpointDelay: 進捗しきい値ごとに一時停止する段階的デプロイ
  • BakeTime: 完了前の待機時間 (最大 172,800 秒 = 48 時間) で安定性を確認
  • SkipMatching (デフォルト true): 構成が一致するインスタンスの置き換えをスキップ
  • ScaleInProtectedInstances / StandbyInstances: 保護中や Standby インスタンスの扱いを指定 (デフォルト Wait)
3️⃣ CloudWatch アラームによる監視とロールバック
  • AlarmSpecification に最大 10 個の CloudWatch アラームを指定可能
  • アラームのしきい値超過時、CloudFormation がスタックをロールバックし、新しい Instance Refresh で元の構成へ復元
  • 更新中もスケーリングポリシーとヘルスチェックは有効なまま維持
4️⃣ インスタンス準備完了の確認 (lifecycle hook 連携)
  • Instance Refresh は cfn-signal ヘルパースクリプトをサポートしない
  • ブートストラップ完了を待つには autoscaling:EC2_INSTANCE_LAUNCHING ライフサイクルフックを使用し、CompleteLifecycleAction API で完了を通知

📄 テンプレート構文 (YAML)

YAML UpdatePolicy の全プロパティ指定例 
UpdatePolicy:
  AutoScalingInstanceRefresh:
    Strategy: Rolling
    Preferences:
      AlarmSpecification:
        Alarms:
          - my-cloudwatch-alarm
      BakeTime: 600
      CheckpointDelay: 300
      CheckpointPercentages:
        - 33
        - 66
        - 100
      InstanceWarmup: 120
      MaxHealthyPercentage: 200
      MinHealthyPercentage: 100
      ScaleInProtectedInstances: Wait
      SkipMatching: true
      StandbyInstances: Wait

🔧 設定方法

✅ 前提条件

✓AWS::AutoScaling::AutoScalingGroup リソースを含む CloudFormation スタックがあること
✓同一の Auto Scaling グループに AutoScalingRollingUpdate ポリシーを併用していないこと (併用するとスタック更新が失敗)
✓アラームベースのロールバックを使用する場合は、監視対象の CloudWatch アラームを事前に作成
1
テンプレートに UpdatePolicy を追加
YAML launch-before-terminate 構成で容量を維持 
ASG:
  Type: AWS::AutoScaling::AutoScalingGroup
  Properties:
    VPCZoneIdentifier:
      - subnet-aaa
      - subnet-bbb
    LaunchTemplate:
      LaunchTemplateId: !Ref MyLaunchTemplate
      Version: !GetAtt MyLaunchTemplate.LatestVersionNumber
    MaxSize: '4'
    MinSize: '1'
  UpdatePolicy:
    AutoScalingInstanceRefresh:
      Strategy: Rolling
      Preferences:
        MinHealthyPercentage: 100
        MaxHealthyPercentage: 200
        SkipMatching: true
2
スタックを更新

起動テンプレートの AMI 変更など、トリガー対象プロパティを変更してスタックを更新すると、CloudFormation が Instance Refresh を自動的に開始します。

Bash AWS CLI でスタック更新 
aws cloudformation update-stack \
  --stack-name my-asg-stack \
  --template-body file://template.yaml \
  --capabilities CAPABILITY_IAM
3
進捗の確認

置き換え済みインスタンスの割合やステータスを確認します。スタックイベント (describe-stack-events) からも進行状況を追跡できます。

Bash Instance Refresh の進捗確認 
aws autoscaling describe-instance-refreshes \
  --auto-scaling-group-name my-asg

💡 メリット

💼 ビジネス面
✓デプロイの安全性向上: アラーム監視、チェックポイント、ベイクタイムで問題を早期検出し自動ロールバック。AMI 更新に伴う障害リスクを低減
✓運用工数の削減: スタック更新後の Instance Refresh 手動起動や CI/CD の追加ステップが不要に
✓可用性の維持: launch-before-terminate により置き換え中も必要な容量を維持
🛠️ 技術面
✓IaC の一貫性: 置き換え戦略までテンプレートで宣言的に管理し、環境間の構成差異を防止
✓スケーリング機能の継続: 更新中もスケーリングポリシーとヘルスチェックが有効なまま動作
✓効率的な置き換え: SkipMatching で不要な置き換えをスキップ
✓インプレース更新: ReplaceRootVolume で AMI 変更のみの場合はルートボリュームだけを更新

⚠️ デメリット・制約事項

🚫 制限事項

✗AutoScalingInstanceRefresh と AutoScalingRollingUpdate は同じ Auto Scaling グループに同時指定不可 (指定するとスタック更新が失敗)
✗CloudFormation が開始した Instance Refresh に RollbackInstanceRefresh API は使用不可 (取り消しは CancelInstanceRefresh API またはスタックロールバック)
✗同時実行できる Instance Refresh は 1 つのみ。ユーザー開始の Refresh 実行中にスタック更新すると失敗する可能性
✗ReplaceRootVolume 戦略では ImageId の変更のみ許可
✗cfn-signal ヘルパースクリプトは非サポート (代わりにライフサイクルフックを使用)
✗スタック更新の各方向 (フォワード / ロールバック) は CloudFormation のリソースタイムアウトである 36 時間が上限

🤔 考慮すべき点

⚠長時間の Instance Refresh は一時認証情報の有効期限を超える可能性があるため、スタックにサービスロールの設定を推奨
⚠InstanceWarmup 未指定時は DefaultInstanceWarmup → HealthCheckGracePeriod の順で使用。すべてのケースで DefaultInstanceWarmup の設定を推奨
⚠AutoScalingRollingUpdate からの移行時は、SuspendProcesses や WaitOnResourceSignals (cfn-signal ベースの検証) をライフサイクルフックベースへ見直しが必要

🎯 ユースケース

1. AMI の定期更新を安全にデプロイ

シナリオ: セキュリティパッチ適用済みのゴールデン AMI を毎月ロールアウト。デプロイ起因のエラー増加を自動検出してロールバックしたい。

YAML
UpdatePolicy:
  AutoScalingInstanceRefresh:
    Strategy: Rolling
    Preferences:
      CheckpointPercentages: [33, 66, 100]
      CheckpointDelay: 300
      BakeTime: 600
      AlarmSpecification:
        Alarms:
          - high-5xx-error-rate-alarm
✅ 効果: 33%、66%、100% の各チェックポイントで 5 分間停止し、エラー率アラーム発火時は自動的にスタックロールバックが実行され、旧 AMI の構成に復元。
2. 容量を維持したままインスタンスタイプを変更

シナリオ: ピークトラフィック処理中のサービスで、旧世代から Graviton ベースのインスタンスへ移行。置き換え中も処理能力を落とせない。

YAML
UpdatePolicy:
  AutoScalingInstanceRefresh:
    Strategy: Rolling
    Preferences:
      MinHealthyPercentage: 100
      MaxHealthyPercentage: 200
      InstanceWarmup: 180
✅ 効果: launch-before-terminate 動作により、新インスタンスが InService になってから旧インスタンスを終了。置き換え中も希望容量の 100% を常に維持。
3. AMI のみの変更をルートボリューム置換で高速適用

シナリオ: インスタンスストアのローカルデータやネットワーク接続を維持したまま、OS イメージのみを更新したい。

YAML
UpdatePolicy:
  AutoScalingInstanceRefresh:
    Strategy: ReplaceRootVolume
    Preferences:
      MinHealthyPercentage: 90
      MaxHealthyPercentage: 100
✅ 効果: インスタンス自体を置き換えずルートボリュームのみを新しい AMI の内容に置換するインプレース更新で、インスタンス起動のオーバーヘッドを削減。

📝 まとめ

CloudFormation の AutoScalingInstanceRefresh 更新ポリシーにより、Instance Refresh の高度なデプロイ制御 (launch-before-terminate、チェックポイント、アラーム監視、ルートボリューム置換) を IaC で宣言的に利用できるようになりました。

✓現在 AutoScalingRollingUpdate を使用している場合は、スケーリング機能を維持したまま更新できる本ポリシーへの移行を検討する価値あり
✓まずは非本番環境のスタックで Strategy: Rolling と SkipMatching を有効にした構成から試すことを推奨
