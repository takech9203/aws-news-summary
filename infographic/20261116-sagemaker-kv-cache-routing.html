Amazon SageMaker AI

🧭 リアルタイム推論エンドポイントの
KV キャッシュアウェアルーティング

📅 リリース日: 2026 年 11 月 16 日 | 機能: KV cache-aware routing for real-time inference endpoints

📝 概要

SageMaker AI のリアルタイム推論エンドポイントが、KV (Key-Value) キャッシュの状態に基づくリクエストルーティングをサポート。各リクエストを、プロンプトの先頭部分と最も長く一致する KV キャッシュを保持するインスタンスへルーティングし、長いプロンプトや繰り返しの多いプロンプトを扱う LLM ワークロードの TTFT (Time to First Token) を短縮できます。

vLLM コンテナがキャッシュブロックの保存・破棄を SageMaker AI に報告し、そのライブビューをルーティング判断に利用。一致が見つからない場合は負荷ベースルーティングに自動フォールバックするため、リクエストが滞留することはありません。

TTFT 短縮
プレフィックス再計算を回避
追加料金なし
既存のインスタンス料金のみ
設定 1 箇所 + 環境変数 1 つ
RoutingStrategy: KV_AWARE

❌ Before: アップデート前の課題

  • キャッシュを持たないインスタンスに到達すると、プレフィックスの KV キャッシュを再計算し TTFT が増大
  • 高負荷インスタンスでは GPU メモリ確保のためキャッシュが破棄 (eviction) され、ヒット率が低下
  • 既存の PREFIX_AWARE はハッシュベースのスティッキー割り当てで、実際のキャッシュ保持状況や負荷を考慮できない

✅ After: アップデート後の改善

  • プロンプト先頭部分と最長一致するキャッシュ保持インスタンスへルーティングし、再計算を回避
  • キャッシュ一致の長さ x 負荷を加味した動的ルーティングで、高負荷・GPU メモリ逼迫時も効率的に処理
  • KV_AWARE 設定 + 環境変数 1 つで有効化。既存 API と OpenAI 互換ペイロードをそのまま利用可能

vLLM コンテナが KV キャッシュブロックの保存・破棄イベントをエンドポイントに報告し、エンドポイントはプロンプト先頭部分の最長一致と各インスタンスの負荷を加味してルーティング先を決定します。一致が見つからない場合は負荷ベースのルーティングにフォールバックします。

⚙️ 主要機能

1️⃣ KV キャッシュ状態に基づく動的ルーティング
  • プロンプト先頭部分と最も長く一致する KV キャッシュを保持するインスタンスへルーティング
  • キャッシュ一致の長さと各インスタンスのビジー状態を重み付けして判断
  • 推論コンポーネント使用時は、呼び出されたコンポーネントのコピー間で同様に選択
2️⃣ キャッシュ状態のライブビュー
  • vLLM コンテナが保存・破棄したキャッシュブロックを SageMaker AI に報告
  • キャッシュの実態をリアルタイムに把握してルーティングに反映
  • オブザーバビリティメトリクスとして KV キャッシュヒット率を提供
3️⃣ 負荷ベースルーティングへの自動フォールバック
  • キャッシュ照合が遅い場合や一致なしの場合は LEAST_OUTSTANDING_REQUESTS と同様の負荷ベースルーティングで継続
  • リクエストが確実に処理されることを保証
4️⃣ シンプルな有効化と互換性
  • RoutingStrategy を KV_AWARE に設定し、環境変数を 1 つ追加するだけで有効化
  • 呼び出しは既存の API と OpenAI 互換ペイロードをそのまま使用可能
  • LoRA アダプターを含む、単一モデルエンドポイントと推論コンポーネントの両方をサポート

🔬 技術仕様

ルーティング戦略の比較

ルーティング戦略動作適したケース
LEAST_OUTSTANDING_REQUESTS 処理余力の大きいインスタンスにルーティング 一般的なワークロード
RANDOM ランダムに選択したインスタンスにルーティング 均一な負荷分散
PREFIX_AWARE 同じプロンプトプレフィックスを共有するリクエストを同じインスタンス / コピーにルーティング 安定した共有プロンプト、短いプロンプト、中程度の負荷
KV_AWARENEW プロンプト先頭部分の KV キャッシュ最長一致と負荷を加味してルーティング 長いプロンプト、高負荷、限られた GPU メモリ

利用要件

項目詳細
対応エンドポイント単一モデルエンドポイントおよび推論コンポーネント (LoRA アダプター含む)

設定例

JSON プロダクションバリアントの設定 
{
  "ProductionVariants": [

      "ModelName": "my-llm-model",
      "InstanceType": "ml.g6.12xlarge",
      "InitialInstanceCount": 2,
      "RoutingConfig": {
        "RoutingStrategy": "KV_AWARE"
      }

  ]

🛠️ 設定方法

前提条件

✓AWS vLLM Deep Learning Container バージョン 0.33.0 以降を使用したモデルであること
✓GPU インスタンスを使用し、2 つ以上のインスタンスまたは推論コンポーネントコピーを構成すること
✓最新の AWS SDK または AWS CLI にアップデートしておくこと

手順

1
モデルの作成
Bash vLLM DLC を使用するモデルを作成 
aws sagemaker create-model \
  --model-name my-llm-model \
  --primary-container '{
    "Image": "<vLLM DLC 0.33.0 以降のイメージ URI>",
    "ModelDataUrl": "s3://my-bucket/model/",
    "Environment": {
      "<キャッシュイベント報告用の環境変数>": "<値>"
    }
  }' \
  --execution-role-arn arn:aws:iam::123456789012:role/SageMakerRole

コンテナがキャッシュブロックの保存・破棄イベントを SageMaker AI に報告するための環境変数を 1 つ追加します (具体的な環境変数名は公式ドキュメントを参照してください)。

2
エンドポイント設定の作成
Bash RoutingStrategy に KV_AWARE を指定 
aws sagemaker create-endpoint-config \
  --endpoint-config-name my-llm-endpoint-config \
  --production-variants '[
    {
      "VariantName": "AllTraffic",
      "ModelName": "my-llm-model",
      "InstanceType": "ml.g6.12xlarge",
      "InitialInstanceCount": 2,
      "RoutingConfig": {
        "RoutingStrategy": "KV_AWARE"
      }
    }
  ]'

KV キャッシュアウェアルーティングを機能させるため、インスタンス数は 2 以上を指定します。

3
エンドポイントの作成と呼び出し
Bash 従来と同じ API で呼び出し 
aws sagemaker create-endpoint \
  --endpoint-name my-llm-endpoint \
  --endpoint-config-name my-llm-endpoint-config

aws sagemaker-runtime invoke-endpoint \
  --endpoint-name my-llm-endpoint \
  --content-type application/json \
  --body '{"messages": [{"role": "user", "content": "こんにちは"}]}' \
  output.json

OpenAI 互換ペイロードもそのまま利用でき、呼び出し側のコード変更は不要です。

💡 メリット

💼 ビジネス面

✓応答性の向上による UX 改善: TTFT 短縮でチャットボットやエージェントの体感速度が向上
✓追加コストなし: 既存のエンドポイント料金のまま性能を改善
✓インフラ効率の向上: キャッシュ再計算を減らし、同じインスタンス数でより多くのリクエストを処理できる可能性

🔧 技術面

✓冗長なプレフィックス計算の削減: 最長一致キャッシュへのルーティングで再計算を回避
✓キャッシュ破棄を考慮した動的判断: 実際のキャッシュ保持状況を反映したルーティング
✓フォールバックによる可用性確保: 一致なしでも負荷ベースルーティングで処理継続
✓KV キャッシュヒット率の可視化: メトリクスで効果を定量評価

⚠️ デメリット・制約事項

🚧 制限事項

✗AWS vLLM Deep Learning Container バージョン 0.33.0 以降が必要。他のサービングコンテナでは利用不可
✗2 つ以上のインスタンスまたは推論コンポーネントコピーが必要
✗GPU インスタンスのみのサポート

🤔 考慮すべき点

⚠️安定した共有プロンプト、短いプロンプト、中程度の負荷では PREFIX_AWARE の方が適する場合がある
⚠️KV_AWARE は長いプロンプト、高負荷、限られた GPU メモリで最も効果を発揮
⚠️KV キャッシュヒット率メトリクスで効果を検証し、ワークロードに応じて戦略を選択することを推奨

🎯 ユースケース

💬 ユースケース 1: 長いシステムプロンプトを共有するチャットボット

シナリオ: 数千トークンのシステムプロンプトと会話履歴を含むマルチターンチャットをセルフホスト LLM で提供。ターンごとにプレフィックスが再計算され、応答開始が遅い。

JSON
{
  "RoutingConfig": { "RoutingStrategy": "KV_AWARE" }
}

効果: 同一会話の後続リクエストが、その会話のキャッシュを保持するインスタンスへルーティングされ、TTFT が短縮される。

📚 ユースケース 2: RAG アプリケーションでの長文ドキュメント処理

シナリオ: 同じドキュメントセットをコンテキストとして複数の質問に回答する RAG アプリケーションで、ドキュメント部分のプレフィックス計算が繰り返し発生。

JSON
{
  "VariantName": "AllTraffic",
  "InstanceType": "ml.g6.12xlarge",
  "InitialInstanceCount": 4,
  "RoutingConfig": { "RoutingStrategy": "KV_AWARE" }
}

効果: 同一ドキュメントを参照するリクエストがキャッシュ保持インスタンスに集約され、GPU の計算リソースを生成処理に集中できる。

🧩 ユースケース 3: LoRA アダプターを多数ホストする推論コンポーネント構成

シナリオ: 推論コンポーネントで複数の LoRA アダプターをホストし、高負荷かつ GPU メモリが逼迫した状態で運用。キャッシュ破棄が頻発し、ヒット率が安定しない。

実装: 推論コンポーネントのコピーを 2 以上に設定し、エンドポイント設定で RoutingStrategy を KV_AWARE に変更。KV キャッシュヒット率メトリクスでヒット率を監視。

効果: キャッシュの保存・破棄状況と負荷をリアルタイムに考慮したルーティングにより、高負荷・限られた GPU メモリの条件下でもキャッシュヒット率を維持しやすくなる。

💰 料金・利用可能リージョン

💵 料金

KV キャッシュアウェアルーティングの利用に追加料金はかかりません。SageMaker AI リアルタイム推論エンドポイントの通常のインスタンス料金のみが発生します。

🌏 利用可能リージョン

Amazon SageMaker AI が提供されているすべての AWS リージョンで利用可能です。

📌 まとめ

KV キャッシュアウェアルーティングにより、SageMaker AI 上のセルフホスト LLM で、長いプロンプトや高負荷のワークロードにおける TTFT を追加料金なしで短縮できるようになりました。vLLM DLC 0.33.0 以降と 2 つ以上のインスタンスという要件を満たす環境であれば、RoutingStrategy を KV_AWARE に変更するだけで導入できます。チャットボット、RAG、エージェントなどの LLM ワークロードを運用しているユーザーは、KV キャッシュヒット率メトリクスを確認しながら効果を検証することを推奨します。
