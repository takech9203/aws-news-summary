📌 概要

Amazon CloudWatch Logs が、ログイベントに AWS リソースタグを付加 (エンリッチ) する機能を追加しました。チームの所有者、環境、コストセンター、アプリケーション名といったメタデータで、ログをフィルタリング・検索・分析できます。

最大のポイントは ロギングコードの変更が一切不要 なこと。CloudWatch Logs が取り込み (ingestion) 時点でリソースタグをログイベントに直接付加するため、カスタムパイプラインなしですぐにタグでスコープを絞り込めます。メトリクスへのタグ付加と同じ「テレメトリ向けリソースタグ」基盤を共有し、追加コストなし で利用できます。

😓 Before — 従来の課題
  • アプリ側でログメッセージにタグ情報を埋め込む必要があった
  • Lambda などで独自のログ加工パイプラインを構築・運用
  • リソース追加・変更のたびに修正・保守が発生
🎉 After — 改善後
  • ロギングコードを変更せずタグでログを絞り込める
  • カスタムパイプラインの構築が不要に
  • @aws.tag.env 等のファセットで Logs Insights クエリが可能

CloudWatch は Resource Explorer から取得したタグ情報を使い、ログ取り込み時にログイベントへタグを付加します。運用担当者は Logs Insights でタグをファセットとして指定し、分析範囲を絞り込めます。

⚡ 主要機能

1️⃣ 取り込み時のタグエンリッチメント
  • ログイベント取り込み時点で関連する AWS リソースタグを自動付加
  • アプリのロギングインストルメンテーションの変更が不要
  • サポート対象リソースから出力されるログが対象
2️⃣ タグベースの CloudWatch Logs Insights クエリ
  • ファセットでログをクエリ可能: @aws.tag.env @aws.tag.team
  • 例: filter @aws.tag.env = 'production'
  • カスタムパイプラインなしですぐにタグでスコープを絞り込める
3️⃣ メトリクスを含むテレメトリ全体での統一
  • 同じ機能でメトリクスにもタグが付加される
  • タグベースの Metrics Insights クエリ、CloudWatch アラーム、PromQL に対応
  • 組織のタグ付け戦略を監視全体で一貫して活用できる

コンソールから有効化する場合は observabilityadmin:GetTelemetryEnrichmentStatus 権限も必要です。

⚙️ 設定方法

📋 前提条件

  • テレメトリ向けリソースタグの有効化に必要な IAM 権限を保有
  • 対象リソースに適切なタグ (例: env、team、cost-center) が付与済み
  • 利用対象が対応リージョンであること

ステップ 1: コンソールから有効化

CloudWatch
コンソールを開く
→
[Settings] を
選択
→

for telemetry] をオン

この操作で Resource Explorer のインデックスとマネージドビューが作成され、エンリッチメントが開始されます。

ステップ 2: AWS CLI から有効化

BashAWS CLI
aws observabilityadmin start-telemetry-enrichment

一度有効化すると、無効化するまで機能は有効なままです。

ステップ 3: AWS CloudFormation から有効化

YAMLCloudFormation テンプレート
Resources:
  TelemetryEnrichment:
    Type: AWS::ObservabilityAdmin::TelemetryEnrichment
    Properties:
      Scope: ACCOUNT

Infrastructure as Code で一貫して管理したい場合に有効です。

✅ メリット

💼 ビジネス面

  • 運用コストの削減: カスタムパイプラインの構築・保守が不要
  • インシデント対応の迅速化: チーム・環境・コストセンター単位ですぐ絞り込み
  • 追加料金なし: 導入のハードルが低い

🛠️ 技術面

  • コード変更不要: 既存のロギングのまま分析が可能
  • メトリクスとの一貫性: 同じタグ戦略をログ・メトリクスに適用
  • 既存タグの活用: 運用中のリソースタグをそのまま利用

⚠️ デメリット・制約事項

🚫 制限事項

  • 一部リージョン (UAE、Bahrain、Tel Aviv) では利用不可
  • ログ対応リソースタイプは限定的 (メトリクスのみ対応も多い)
  • 有効化に Resource Explorer のインデックス作成と複数の IAM 権限が必要

💡 考慮すべき点

  • 有効化で Resource Explorer のインデックス等が自動作成される
  • 一貫したタグ付け戦略 (命名規則) の整備が重要
  • タグ値の反映タイミングは Resource Explorer のインデックス更新に依存

🎯 ユースケース

1️⃣ 環境単位でのログ絞り込み
シナリオ: 本番環境の問題調査時に、本番リソースのログだけを横断的に確認したい。
Logs Insights
filter @aws.tag.env = 'production'
| sort @timestamp desc
| limit 100
✅ 開発・ステージング環境のノイズを除外し、本番ログだけに素早く絞り込める。
2️⃣ チーム所有リソースの調査
シナリオ: マイクロサービス環境で、特定チーム所有のログのみを抽出してトラブルシュート。
Logs Insights
filter @aws.tag.team = 'payments' and @aws.tag.env = 'production'
| stats count(*) by bin(5m)
✅ チーム境界に沿った調査が可能。関係ないチームのログを参照せずに済む。
3️⃣ コストセンター単位での利用分析
シナリオ: コストセンターごとにエラー傾向を把握し、チャージバックや改善対象を特定。
Logs Insights
filter @aws.tag.cost-center = 'cc-1234'
| filter @message like /ERROR/
| stats count(*) as errorCount by @aws.tag.app
✅ コスト配分と運用品質の両面から、組織的な分析が可能になる。

🔗 関連サービス・機能

  • AWS Resource Explorer: タグ情報のインデックス化とマネージドビューを提供。エンリッチメントの基盤。
  • Amazon CloudWatch (Metrics Insights / アラーム): 同機能でメトリクスのタグベースクエリ・アラートが可能。
  • AWS Observability Admin (observabilityadmin): テレメトリエンリッチメントの有効化・状態確認 API を提供。
  • CloudWatch Logs Insights: @aws.tag.<キー> ファセットでタグベースのログクエリを実行。

📝 まとめ

このアップデートにより、ロギングコードの変更やカスタムパイプラインの構築なしに、リソースタグでログを絞り込み・分析できるようになりました。追加コストなしで利用でき、メトリクスとも統一されたタグベースの監視が実現できます。組織でタグ付け戦略を運用しているお客様は、CloudWatch Settings から本機能を有効化し、Logs Insights でのタグベースクエリを検証することを推奨します。
