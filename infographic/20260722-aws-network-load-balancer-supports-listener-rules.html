AWS Network Load Balancer

⚖️ リスナールールによる
カスタムトラフィックルーティング

送信元 IP アドレスタイプで IPv4 / IPv6 を振り分け
2026年7月22日
機能: Listener Rules

📌 概要

AWS Network Load Balancer (NLB) がリスナールールをサポートし、送信元 IP アドレスタイプ (IPv4 / IPv6) に基づいて接続を異なるターゲットグループへルーティングできるようになりました。 単一のデュアルスタック NLB で、IPv6 クライアントのトラフィックを IPv6 ターゲットへ、IPv4 クライアントのトラフィックを IPv4 ターゲットへ振り分けられます。

レイヤー 3 での条件付きルーティングにより、プロトコル変換や追加インフラなしで、両アドレスファミリーのクライアント IP をエンドツーエンドで保持できます。既存のデュアルスタック NLB に再作成なしで追加でき、TCP / UDP / TCP_UDP / TLS の各リスナーで利用可能です。

❌ アップデート前の課題
✗単一 NLB で IPv4/IPv6 両対応するには DNS で分割した 2 台のロードバランサーが必要だった
✗1 つのターゲットグループへ集約するとプロトコル変換でクライアント IP が失われた
✗IPv6 への段階的移行で追加インフラと運用の複雑さが発生していた
➡️
✅ アップデート後の改善
✓単一のデュアルスタック NLB で送信元 IP タイプに基づく振り分けが可能に
✓プロトコル変換が不要になり、IPv4/IPv6 両方でクライアント IP をエンドツーエンド保持
✓既存 NLB に再作成なしでルール追加でき、運用がシンプルに

デュアルスタック NLB がリスナールールで送信元 IP アドレスタイプを判定し、同一アドレスファミリーのターゲットグループへ振り分ける流れ

⚡ 主要機能

🔀 送信元 IP アドレスタイプによる条件付きルーティング
  • リスナールールの条件 (SourceIpConfig) に IpAddressType フィールド (ipv4 / ipv6) を指定
  • 送信元が IPv4 か IPv6 かに応じて接続を異なるターゲットグループへ振り分け
  • レイヤー 3 での条件付きルーティングにより同一アドレスファミリーのターゲットへ到達
🔒 クライアント IP アドレスのエンドツーエンド保持
  • プロトコル変換を行わないため、IPv4/IPv6 両方でクライアントの元 IP を保持
  • ターゲット側でクライアント IP を用いたアクセス制御やロギングが引き続き可能
🛠️ 既存 NLB への非破壊的な適用
  • 既存のデュアルスタック NLB に対して再作成なしでルールを追加可能
  • TCP、UDP、TCP_UDP、TLS の各リスナーで利用可能
  • 接続ドレイン、スティッキネス、クロスゾーン負荷分散、加重ターゲットグループ、クライアント IP 保持など既存機能と互換

リスナールール設定例

JSON リスナールール定義 
{
  "Conditions": [
    {
      "Field": "source-ip",
      "SourceIpConfig": {
        "IpAddressType": "ipv6"
      }
    }
  ],
  "Actions": [
    {
      "Type": "forward",
      "TargetGroupArn": "arn:aws:elasticloadbalancing:region:account-id:targetgroup/ipv6-targets/xxxxxxxx"
    }
  ]
}

📝 設定方法

前提条件

1. デュアルスタック (IPv4 と IPv6 両方) が有効化された NLB が存在  /  2. IPv4 用と IPv6 用のターゲットグループがそれぞれ作成済み  /  3. リスナー (TCP / UDP / TCP_UDP / TLS のいずれか) が構成済み
1
IPv6 トラフィック向けのリスナールールを作成
Bashcreate-rule (IPv6)
aws elbv2 create-rule \
    --listener-arn arn:aws:elasticloadbalancing:region:account-id:listener/net/my-nlb/xxxx/yyyy \
    --priority 10 \
    --conditions '[{"Field":"source-ip","SourceIpConfig":{"IpAddressType":"ipv6"}}]' \
    --actions '[{"Type":"forward","TargetGroupArn":"arn:aws:elasticloadbalancing:region:account-id:targetgroup/ipv6-targets/xxxx"}]'
2
IPv4 トラフィック向けのリスナールールを作成
Bashcreate-rule (IPv4)
aws elbv2 create-rule \
    --listener-arn arn:aws:elasticloadbalancing:region:account-id:listener/net/my-nlb/xxxx/yyyy \
    --priority 20 \
    --conditions '[{"Field":"source-ip","SourceIpConfig":{"IpAddressType":"ipv4"}}]' \
    --actions '[{"Type":"forward","TargetGroupArn":"arn:aws:elasticloadbalancing:region:account-id:targetgroup/ipv4-targets/xxxx"}]'
3
ルールの確認
Bashdescribe-rules
aws elbv2 describe-rules \
    --listener-arn arn:aws:elasticloadbalancing:region:account-id:listener/net/my-nlb/xxxx/yyyy

💡 メリット

💰 ビジネス面

  • インフラコスト削減: 2 台のロードバランサーを 1 台に統合
  • IPv6 移行の円滑化: 既存 IPv4 環境を維持しつつ段階的に対応
  • 追加料金なし: リスナールール機能自体は無料

⚙️ 技術面

  • クライアント IP の保持: プロトコル変換を排除しエンドツーエンド保持
  • 非破壊的な導入: 既存デュアルスタック NLB に再作成なしで適用
  • 既存機能との互換性: 接続ドレイン、スティッキネス、加重 TG などと併用可

⚠️ デメリット・制約事項

制限事項

  • サポートされる条件は送信元 IP アドレスタイプ (IpAddressType) のマッチングであり、デュアルスタック NLB が前提
  • ターゲットグループは IPv4 用と IPv6 用をそれぞれ用意する必要がある

考慮すべき点

  • ルールの優先度 (priority) で評価順序が決まるため、条件の重複や意図しないマッチングを防ぐ設計が必要
  • 既存の DNS ベース分割構成から移行する場合は、切り替え時のトラフィック挙動を検証する

🎯 ユースケース

1. デュアルスタック環境でのクライアント IP 保持

シナリオ: IPv4/IPv6 両クライアントにサービスを提供しつつ、アクセスログや IP ベースのアクセス制御のためクライアント IP を保持したい。

IPv6 クライアント → NLB (リスナールール: ipv6) → IPv6 ターゲットグループ IPv4 クライアント → NLB (リスナールール: ipv4) → IPv4 ターゲットグループ

効果: プロトコル変換なしで、両アドレスファミリーのクライアント IP を保持したまま適切なターゲットへ振り分け。

2. ロードバランサーの統合によるコスト最適化

シナリオ: IPv4 用と IPv6 用に 2 台の NLB を DNS で分割していた構成を単一の NLB に統合したい。

既存: nlb-v4 (IPv4) + nlb-v6 (IPv6) を DNS で分割 統合後: 単一デュアルスタック NLB + リスナールールで振り分け

効果: 運用対象が 1 台になり、管理の複雑さと運用負荷を削減。

3. IPv6 への段階的移行

シナリオ: 既存の IPv4 ターゲットを維持しながら、IPv6 対応ターゲットを追加して段階的に移行したい。

IPv4 トラフィック → 既存 IPv4 ターゲットグループ (現行維持) IPv6 トラフィック → 新規 IPv6 ターゲットグループ (順次拡大)

効果: 既存環境への影響を抑えつつ IPv6 対応を段階的に進められる。

🔗 関連サービス・機能

•
Elastic Load Balancing (ELB): NLB は ELB のロードバランサータイプの 1 つ。リスナールールは ELB API (elasticloadbalancing) で構成する。
•
Amazon VPC: デュアルスタック構成では VPC およびサブネットで IPv4/IPv6 両アドレスファミリーの有効化が必要。
•
Application Load Balancer (ALB): 従来からリスナールールをサポートし、レイヤー 7 の条件による柔軟なルーティングが可能。
