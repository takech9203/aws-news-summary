Slurm クラスター向け MinCount による最小キャパシティ要件

Minimum Capacity Requirements with Continuous Provisioning
2026-05-27

📋 概要

Amazon SageMaker HyperPod の Slurm オーケストレーション環境において、継続的プロビジョニング (Continuous Provisioning) と組み合わせて使用できる最小キャパシティ要件 (MinCount) 機能がリリースされました。インスタンスグループが InService ステータスに遷移する前に、最低限プロビジョニングされるべきインスタンス数を指定できます。

継続的プロビジョニングは 2026 年 3 月にリリースされた機能で、利用可能な部分的キャパシティでクラスターをプロビジョニングし、ジョブを迅速に開始できるようにするものです。MinCount はこの動作に下限値を追加し、クラスターが「準備完了」と見なされる前に保証される最小ノード数を確保します。

🔄 Before / After 比較

❌ Before
  • 1 台でも起動すればクラスターが InService に遷移
  • 分散トレーニングに必要な最小ノード数が揃う前にジョブスケジューリング開始
  • SLA やコスト効率目標の最小 GPU 数を保証する仕組みがない
  • 不完全な状態での InService で手動確認が必要
✅ After
  • MinInstanceCount で最小インスタンス数確保まで InService 遷移をブロック
  • 固定ノード数が揃ってからジョブスケジューリング開始
  • 3 時間タイムアウトで自動ロールバック、無期限待機を防止
  • MinCount 達成後も TargetCount まで段階的スケールアップ継続

⚡ 主要機能

🎯
最小キャパシティ要件
MinInstanceCount パラメータで最小プロビジョニング数を 0 ~ InstanceCount の間で指定。デフォルトは Compute: 0、Controller/Login: 1
🔒
ステータス管理とミューテーション制御
MinCount 未達成時は Creating/Updating ステータスを維持。BatchAddClusterNodes 等の操作がブロックされ、削除と MinCount/TargetCount 変更のみ許可
🔄
自動ロールバック機構
3 時間以内に MinCount 未達成で自動ロールバック。新規は (0,0) にリセット、既存は前回 InService 時の値に復元
📡
イベント通知
最小キャパシティ達成時・ロールバック開始時にイベント発行。ListClusterEvents API で進捗監視可能

🔧 技術仕様

MinCount パラメータ仕様

項目 詳細
パラメータ名 MinInstanceCount
対象 API CreateCluster、UpdateCluster
有効範囲 0 ~ InstanceCount
デフォルト値 0 (Compute)、1 (Controller/Login)
前提条件 NodeProvisioningMode が Continuous に設定
タイムアウト 3 時間

インスタンスグループステータス遷移

ステータス 条件 許可される操作
Creating 新規作成時、CurrentCount < MinCount MinCount/TargetCount 変更、削除
Updating 更新時、CurrentCount < MinCount MinCount/TargetCount 変更、削除
InService MinCount ≤ CurrentCount ≤ TargetCount 全ての操作

💻 設定方法

前提条件

  • SageMaker HyperPod クラスターが Slurm オーケストレーションで構成されていること
  • NodeProvisioningMode が Continuous に設定されていること
  • Slurm プロビジョニングパラメータが API ペイロードの SlurmConfig フィールドで提供されていること
  • 適切な IAM 実行ロールが設定されていること

🎯 ユースケース

1. PyTorch FSDP による大規模言語モデルトレーニング
70B パラメータの LLM を PyTorch FSDP で分散トレーニング。16 ノードを計画しているが、最低 8 ノードでトレーニング設定を調整して開始可能。
MinInstanceCount: 8, InstanceCount: 16
✅ 8 ノード確保でトレーニング開始。残り 8 ノードは非同期追加。部分キャパシティでの無効なジョブ開始を防止
2. NVIDIA NeMo による Megatron 並列トレーニング
テンソル並列度 8、パイプライン並列度 4 の設定で最低 32 GPU (4 ノード x 8 GPU) が必要。部分的なノードでは実行不可。
MinInstanceCount: 4, InstanceCount: 4
✅ MinCount = InstanceCount で all-or-nothing 動作を実現。3 時間以内に全ノード確保できなければ自動ロールバック
3. SLA 保証付きマルチテナントトレーニング環境
複数チームが共有するクラスターで、チーム A に最低 8 ノード、チーム B に最低 4 ノードを保証。各インスタンスグループで個別に MinCount を管理。
✅ 一方のチームのキャパシティ不足がもう一方に影響しない。SLA の定量的保証が API レベルで実現

✅ メリット

ビジネス面

  • SLA 保証の確保: 最小 GPU 数を保証し分散トレーニングジョブの SLA を確実に達成
  • コスト効率の最適化: 必要最小限のリソース確保後にジョブ開始し無駄な実行を防止
  • 運用の自動化: 3 時間タイムアウトと自動ロールバックで手動介入なしに異常回復

技術面

  • 分散トレーニングの信頼性向上: PyTorch FSDP、Megatron-LM 等で必要な固定ノード数保証
  • 段階的スケーリング: MinCount 達成後も TargetCount まで非同期インスタンス追加
  • イベント駆動型監視: ListClusterEvents API でリアルタイム追跡
  • 既存ワークフローとの互換性: MinCount 0 で従来動作を維持

⚠️ 制約事項・注意点

  • MinCount は継続的プロビジョニング (NodeProvisioningMode: Continuous) が有効なクラスターでのみ利用可能
  • レガシーの provisioning_parameters.json を使用するクラスターでは非対応
  • MinCount は永続的な最小キャパシティ保証ではなく、InService 遷移時の閾値のみ保証
  • 通常運用中の異常インスタンス交換やメンテナンス時に MinCount を一時的に下回る可能性あり
  • SlurmConfigStrategy パラメータは継続的プロビジョニングと併用不可
  • マルチヘッドノード構成は継続的プロビジョニングでは非対応
  • 3 時間のタイムアウトはリージョンのキャパシティ状況によっては不十分な場合あり
  • Creating/Updating 中は一部の管理操作が制限される
  • MinCount = InstanceCount 設定では継続的プロビジョニングのメリットが失われる
