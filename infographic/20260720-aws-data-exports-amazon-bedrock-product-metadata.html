Amazon Bedrock 標準化製品メタデータ

Cost and Usage Report (CUR 2.0) で、生成 AI のコストを一貫した構造化属性で分析可能に

📌 概要

AWS は AWS Data Exports (CUR 2.0) において、Amazon Bedrock 向けの標準化された製品メタデータの提供を開始しました。FinOps チームやクラウド管理者は、一貫性のある構造化された属性を使って Amazon Bedrock のコストを理解できます。

追加された標準化属性は モデルプロバイダー、モデル名、料金単位、推論タイプ、機能 (サービングモード) の 5 つ。さらに、すべての Bedrock コストを統合する統一製品ファミリー名「Amazon Bedrock」も導入されました。

💡 この機能は AWS Data Exports を利用する Amazon Bedrock のお客様に対して、追加費用なし・デフォルトで利用可能です。

🔄 アップデート前後の比較

😰 Before (課題)
  • 説明テキストをパースしてモデルプロバイダー・モデル名を特定する独自ロジックが必要
  • 入力トークンと出力トークンのコスト分離が困難
  • On-Demand と Batch のコストを比較する統一手段がない
  • Bedrock コストが単一の製品ファミリーとして一貫して識別されない
😊 After (改善)
  • モデルプロバイダー・モデル名・推論タイプ・機能を標準化属性として直接利用
  • 自由記述フィールドのパースが不要に
  • product_pricing_unit や map 列キーでフィルタ・グループ化・比較が可能
  • 統一された「Amazon Bedrock」製品ファミリー名で単一カテゴリーとして識別

Amazon Bedrock の使用状況が標準化メタデータ付きで CUR 2.0 にエクスポートされ、S3 経由で Athena やデータウェアハウスに取り込まれて FinOps チームが分析する流れ

⭐ 主要機能

1️⃣ 標準化された製品属性の追加
  • モデルプロバイダー、モデル名、料金単位、推論タイプ、機能の 5 つの標準化属性を提供
  • 各属性は Bedrock のコストドライバーを表現し、明細行に値が存在する場合にのみ付与
  • 自由記述の説明フィールドを解析せずにコストを次元別に分析可能
2️⃣ 統一された製品ファミリー名
  • product_product_family 列にすべての Bedrock 明細行で統一値「Amazon Bedrock」を設定
  • すべての Amazon Bedrock 使用量を単一の製品ファミリーで識別可能
3️⃣ CUR 2.0 での提供方式
  • モデルプロバイダー・モデル名・推論タイプ・機能は product map 列内のキーとして提供
  • 料金単位 (product_pricing_unit) は独立列として提供
  • map 列のキーはドット演算子 (例: product.provider) で個別列としてクエリ可能

product map 列の仕組み

CUR 2.0 の product 列は、複数の製品属性を map<string, string> 型のキーバリューで保持します。サービス固有の追加属性が map 内のキーとして格納され、ドット演算子でクエリできます。

SQLAthena でモデルプロバイダー別にコストを集計
-- Athena で Amazon Bedrock のコストをモデルプロバイダー別に集計する例
SELECT
    product.provider          AS model_provider,
    product.model             AS model_name,
    product.inference_type    AS inference_type,
    product.feature           AS serving_mode,
    product_pricing_unit      AS pricing_unit,
    SUM(line_item_unblended_cost) AS total_cost
FROM
    cur2_table
WHERE
    product_product_family = 'Amazon Bedrock'
GROUP BY
    1, 2, 3, 4, 5
ORDER BY
    total_cost DESC;

✅ メリット

💼 ビジネス面

  • コスト可視化の向上: モデル・プロバイダーごとの支出を正確に把握
  • チャージバックの容易化: 部門・プロジェクトへのコスト配賦が容易に
  • 追加費用なし: デフォルトで提供、追加コストなし

🛠️ 技術面

  • カスタムパース不要: 独自ロジックの構築・保守が不要
  • 構造化クエリ: map キーを個別列のように SQL で分析
  • 一貫性のあるスキーマ: 時系列・アカウント間で一貫分析

⚠️ デメリット・制約事項

制限事項

  • 標準化属性は明細行に値が存在する場合のみ product map 列に出現
  • プロバイダー・モデル名等は map 列内キーのため、クエリ時にドット演算子が必要
  • 本機能は CUR 2.0 が対象。レガシー CUR とは列構成が異なる

考慮すべき点

  • 説明フィールドのパースに依存する既存クエリ・ダッシュボードは標準化属性へ更新が望ましい
  • map キーの値 (モデル名等) は Bedrock コンソールのモデルカタログの名称に対応

🎯 ユースケース

① モデルプロバイダー別のコスト比較
シナリオ: 複数プロバイダー (Amazon, Anthropic, Meta など) を併用する組織が、プロバイダーごとの支出を比較したい。
SQL
SELECT product.provider AS provider,
       SUM(line_item_unblended_cost) AS cost
FROM cur2_table
WHERE product_product_family = 'Amazon Bedrock'
GROUP BY 1 ORDER BY cost DESC;
📈 効果: プロバイダーごとの支出割合を可視化し、コスト最適化やモデル選定の判断に活用。
② 入力・出力トークンコストの分離分析
シナリオ: プロンプト設計改善のために、入力トークンと出力トークンのコスト内訳を把握したい。
SQL
SELECT product.inference_type AS token_type,
       SUM(line_item_unblended_cost) AS cost
FROM cur2_table
WHERE product_product_family = 'Amazon Bedrock'
GROUP BY 1;
📈 効果: トークンタイプ別のコスト構造が明確になり、プロンプトエンジニアリングによる削減効果を測定。
③ On-Demand と Batch のコスト比較
シナリオ: 推論サービングモードの選択がコストに与える影響を評価したい。
SQL
SELECT product.feature AS serving_mode,
       SUM(line_item_unblended_cost) AS cost
FROM cur2_table
WHERE product_product_family = 'Amazon Bedrock'
GROUP BY 1;
📈 効果: On-Demand と Batch のコスト差を定量把握し、バッチ処理への移行によるコスト最適化を検討。

📝 まとめ

このアップデートにより、Amazon Bedrock のコストをモデルプロバイダー・モデル名・推論タイプ・サービングモードといった標準化属性で分析でき、FinOps チームは独自パースロジックなしで正確なコスト配賦を実現できます。

追加費用なしでデフォルト利用可能なため、生成 AI ワークロードを運用するお客様は、CUR 2.0 エクスポートのクエリを標準化属性を使う形に更新し、コスト可視化とチャージバックの高度化を進めることが推奨されます。
