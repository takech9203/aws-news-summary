Amazon ElastiCache のノードベースクラスターに、13 の新しい CloudWatch メトリクスが追加されました。ネットワークスロットリング、メモリフラグメンテーション、コネクション枯渇を CloudWatch から直接検出できるようになります。

Before / After

❌ Before

  • 生のバイトカウンターからベースラインを手動計算
  • 個別ノードで INFO コマンドを実行 (高い運用負荷)
  • インスタンスタイプ変更時にアラーム閾値を再設定
  • メモリフラグメンテーション検出がリアクティブ
  • Pub/Sub チャネル利用状況の把握が困難

✅ After

  • ベースライン比のパーセンテージで表示 (ポータブルなアラーム)
  • CloudWatch のみで診断完結 (INFO コマンド不要)
  • フラグメンテーション・接続拒否をリアルタイム監視
  • プロアクティブな対応が可能に
  • Pub/Sub チャネル数の監視で移行判断データを取得

⚡ 主要機能

🌐 ネットワークキャパシティメトリクス

NetworkBaselineUsageInPercentage / NetworkBaselineUsageOutPercentage: インバウンド/アウトバウンドのネットワーク使用率 (インスタンスベースライン比)

NetworkBaselineMaxUsageInPercentage / NetworkBaselineMaxUsageOutPercentage: 1 秒あたりのピーク使用率

→ 100% 超はバーストクレジット消費中。持続するとスロットリング発生

🧠 メモリヘルスメトリクス

UsedMemoryDataset: エンジンオーバーヘッドを除いた実データのメモリ消費量

AllocatorFragmentationBytes / AllocatorFragmentationRatio: フラグメンテーション量と比率

MajorPageFaults: OS レベルのページフォルト (メモリプレッシャーの指標)

🔌 接続ヘルスメトリクス

BlockedConnections: ブロッキングコマンドで待機中の接続数

RejectedConnections: maxclients 制限到達により拒否された接続数

→ 非ゼロの場合、maxclients 引き上げまたはコネクションプールリーク調査が必要

📡 Pub/Sub ワークロードメトリクス

PubSubChannels: アクティブなクラシック Pub/Sub チャネル数

PubSubShardChannels: アクティブなシャード Pub/Sub チャネル数

→ クラシックチャネル増加時はシャード Pub/Sub への切り替えを検討

📈 コマンドスループットメトリクス

ProcessedCommands: 全コマンドタイプにわたる合計コマンドスループット

🛠️ 設定方法

💡 前提条件: ElastiCache ノードベースクラスターが稼働中であること。メトリクスは自動的に発行されるため、追加設定は不要です。

ステップ 1: CloudWatch コンソールでメトリクスを確認

Bash メトリクス一覧の確認 
aws cloudwatch list-metrics \
  --namespace "AWS/ElastiCache" \
  --metric-name "NetworkBaselineUsageInPercentage"

ステップ 2: ネットワークスロットリングアラームの設定

Bash 使用率 90% 超過アラーム 
aws cloudwatch put-metric-alarm \
  --alarm-name "ElastiCache-NetworkBaselineUsage-High" \
  --namespace "AWS/ElastiCache" \
  --metric-name "NetworkBaselineUsageInPercentage" \
  --dimensions Name=CacheClusterId,Value=my-cluster \
  --statistic Average \
  --period 300 \
  --threshold 90 \
  --comparison-operator GreaterThanThreshold \
  --evaluation-periods 3 \
  --alarm-actions "arn:aws:sns:ap-northeast-1:123456789012:my-topic"

ステップ 3: メモリフラグメンテーション監視

Bash フラグメンテーション比率 1.5 超過アラーム 
aws cloudwatch put-metric-alarm \
  --alarm-name "ElastiCache-MemoryFragmentation-High" \
  --namespace "AWS/ElastiCache" \
  --metric-name "AllocatorFragmentationRatio" \
  --dimensions Name=CacheClusterId,Value=my-cluster \
  --statistic Average \
  --period 300 \
  --threshold 1.5 \
  --comparison-operator GreaterThanThreshold \
  --evaluation-periods 2 \
  --alarm-actions "arn:aws:sns:ap-northeast-1:123456789012:my-topic"

ステップ 4: 接続拒否の検出

Bash RejectedConnections 即時検出 
aws cloudwatch put-metric-alarm \
  --alarm-name "ElastiCache-RejectedConnections" \
  --namespace "AWS/ElastiCache" \
  --metric-name "RejectedConnections" \
  --dimensions Name=CacheClusterId,Value=my-cluster \
  --statistic Sum \
  --period 60 \
  --threshold 0 \
  --comparison-operator GreaterThanThreshold \
  --evaluation-periods 1 \
  --alarm-actions "arn:aws:sns:ap-northeast-1:123456789012:my-topic"

✅ メリット

ビジネス面

  • 💰 運用コスト削減: ノードごとの手動監視が不要になり、運用チームの工数を削減
  • 🛡️ ダウンタイム予防: ネットワークスロットリングやメモリ枯渇を事前に検知し、障害発生前に対処可能
  • 📐 キャパシティプランニング効率化: ベースライン比メトリクスにより、スケールアップ/アウトの適切なタイミングを判断可能

技術面

  • 🔄 ポータブルなアラーム: ベースライン比のパーセンテージ表示により、インスタンスタイプ変更時にアラーム閾値の再設定が不要
  • ⚡ バースト検出: Max バリアントにより、平均メトリクスでは隠れてしまう 1 秒単位のバーストを捕捉
  • 🧩 フラグメンテーション可視化: AllocatorFragmentationRatio により activedefrag で対処可能なフラグメンテーションを特定
  • 🖥️ CLI クエリ不要: INFO コマンドを実行することなくエンジン内部状態を把握可能

⚠️ デメリット・制約事項

  • ❌ ノードベースクラスター限定: ElastiCache Serverless には適用されない
  • ⏰ 保持期間: CloudWatch 標準の 15 か月。長期トレンド分析には別途データ保存が必要
  • 📏 粒度制限: CloudWatch 標準の最小 1 分に依存
  • 💡 バースト注意: 一時的な 100% 超は即問題ではないが、持続的バーストはクレジット枯渇
  • ⚙️ activedefrag: 有効化はパフォーマンスへの影響を考慮して判断
  • 💲 大規模クラスター: アラームや API コールの料金が増加する可能性

🎯 ユースケース

🛒 ユースケース 1: ネットワークスロットリングの早期検出

シナリオ: e コマースサイトでセール期間中にトラフィックが急増し、ネットワーク帯域が逼迫する状況を事前に検知したい

効果: バーストクレジット枯渇前にスケールアップを実行し、セール中のレイテンシ増加やタイムアウトを防止

Bash ピーク使用率監視 
aws cloudwatch put-metric-alarm \
  --alarm-name "ElastiCache-NetworkBurst-Warning" \
  --namespace "AWS/ElastiCache" \
  --metric-name "NetworkBaselineMaxUsageInPercentage" \
  --dimensions Name=CacheClusterId,Value=ecommerce-cache \
  --statistic Maximum \
  --period 60 \
  --threshold 100 \
  --comparison-operator GreaterThanThreshold \
  --evaluation-periods 5

🧠 ユースケース 2: メモリフラグメンテーションの自動対処

シナリオ: 長期稼働ノードでメモリフラグメンテーションが蓄積し、有効メモリ量が減少する問題に対処したい

効果: フラグメンテーション比率が閾値を超えた際に SSM Automation で activedefrag を自動有効化し、メモリ断片化を解消

JSON 自動修復アラーム設定 
{
  "AlarmName": "ElastiCache-Fragmentation-AutoRemediation",
  "MetricName": "AllocatorFragmentationRatio",
  "Namespace": "AWS/ElastiCache",
  "Threshold": 1.5,
  "ComparisonOperator": "GreaterThanThreshold",
  "AlarmActions": [
    "arn:aws:ssm:ap-northeast-1:123456789012:automation-definition/EnableActiveDefrag"
  ]
}

🔌 ユースケース 3: コネクションプールリークの検出

シナリオ: マイクロサービスアーキテクチャで多数のアプリケーションが接続し、コネクションプールリークにより maxclients 上限に到達する問題を検出したい

効果: 接続数が maxclients に近づく前に警告を発し、コネクションプールの設定見直しやリーク調査を促進

Bash 接続枯渇検出アラーム 
aws cloudwatch put-metric-alarm \
  --alarm-name "ElastiCache-ConnectionExhaustion" \
  --namespace "AWS/ElastiCache" \
  --metric-name "ConnectionsConnected" \
  --dimensions Name=CacheClusterId,Value=microservices-cache \
  --statistic Average \
  --period 300 \
  --threshold 4000 \
  --comparison-operator GreaterThanThreshold \
  --evaluation-periods 2
