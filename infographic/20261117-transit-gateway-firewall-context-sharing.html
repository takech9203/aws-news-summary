🔀 Transit Gateway: ファイアウォールへのリソースコンテキスト共有

IP アドレスではなく AWS リソースの定義でセグメンテーションポリシーを記述
📅 リリース日: 2026 年 11 月 17 日

📝 概要

AWS Transit Gateway が、アタッチされたファイアウォールなどのセキュリティサービスへのリソースコンテキスト共有をサポートしました。 IP アドレスだけでなく、VPC、VPC サブネット、VPC セキュリティグループ、Transit Gateway アタッチメントをファイアウォールポリシーで直接参照できます。

Transit Gateway はファイアウォールに送信するトラフィックにリソースコンテキストを埋め込むため、ファイアウォールは最初のパケットから適切なポリシーを適用できます。 IP アドレスの変化に応じたルール更新は不要です。

❌ アップデート前の課題
  • ファイアウォールは IP アドレスでトラフィックをセグメント化する必要があり、IP ベースのルールは計画と維持が困難
  • タグによるセグメンテーションは定期同期方式のため、同期の合間に起動した新しいワークロードを見逃す可能性
  • IP アドレスが変化するたびにファイアウォールルールの更新が必要
✅ アップデート後の改善
  • VPC、サブネット、セキュリティグループ、TGW アタッチメントといったワークロード定義に基づいてセグメンテーションを適用
  • トラフィックにコンテキストが埋め込まれ、最初のパケットから正しいポリシーを適用
  • 短命な Lambda 関数のような動的ワークロードにも、トラフィック送信開始と同時にポリシーを適用

AWS Network Manager のコンテキストストアが Transit Gateway に接続されたリソースを監視し、そのコンテキストをファイアウォールと共有します。 Transit Gateway はファイアウォールへ送信するトラフィックにリソースコンテキストを埋め込むため、ファイアウォールは最初のパケットからリソースベースのポリシーを適用できます。

⚡ 主要機能

🎯 リソースコンテキストによるファイアウォールポリシー

IP アドレスに加えて VPC、VPC サブネット、VPC セキュリティグループ、TGW アタッチメントをポリシーで参照可能。 ワークロードやアタッチメントの定義に基づくセグメンテーションを適用でき、IP 変化に応じたルール更新が不要。

📋 コンテキストストア (AWS Network Manager)

グローバルネットワーク内にコンテキストストアを作成し、Transit Gateway を関連付けて利用。 接続されたリソースのコンテキストを監視してセキュリティサービスと共有。 複数リージョンの TGW を 1 つのストアに関連付け可能 (各リソースのリージョン情報を含む)。

🚀 ファーストパケットからのポリシー適用

トラフィックにリソースコンテキストが埋め込まれるため、最初のパケットから正しいポリシーを適用。 タグ同期方式と異なり新規ワークロードの見逃しが発生せず、短命な Lambda 関数にも即座に適用可能。

🛡️ 対応ファイアウォール

AWS Network Firewall: コンテキスト対応のステートフルルールグループで、コンテキストストアを参照する ContextSets を通じて AWS リソース ID をルールで参照可能。
Palo Alto Networks Software Firewalls: IP ベースのルールと併用する形でリソースコンテキストポリシーをサポート。

🛠️ 設定方法

前提条件

✓グローバルネットワークを作成し、リソースコンテキストを共有したい Transit Gateway を登録していること
✓ファイアウォールをネットワークファンクションアタッチメント経由で TGW に接続し、検査が必要なトラフィックをアタッチメントにルーティングしていること
✓AWS Network Manager でコンテキストストアとその TGW 関連付けを作成・管理する権限を持っていること

手順

1
コンテキストストアの作成
BashAWS CLI
aws networkmanager create-context-store \
  --global-network-id global-network-0123456789abcdef0 \
  --description "Context store for TGW firewall segmentation"

グローバルネットワーク内にコンテキストストアを作成します。グローバルネットワークあたり 1 つ作成できます。

2
Transit Gateway の関連付け
BashAWS CLI
aws networkmanager associate-context-store \
  --context-store-id <context-store-id> \
  --transit-gateway-arn arn:aws:ec2:ap-northeast-1:123456789012:transit-gateway/tgw-0123456789abcdef0

関連付け後、コンテキストストアは TGW に接続されたリソースの監視を開始します。複数リージョンの TGW を同一のストアに関連付けできます。

3
コンテキストの確認とファイアウォールポリシーの設定
BashAWS CLI
# 収集されたリソースコンテキストの一覧を確認
aws networkmanager list-contexts \
  --context-store-id <context-store-id>

収集されたリソースコンテキスト (VPC、サブネット、セキュリティグループ、アタッチメント) を確認します。 個々のコンテキストレコードの参照は API / AWS CLI を使用します (コンソールではストアと関連付けの表示のみ)。 その後、AWS Network Firewall のコンテキスト対応ステートフルルールグループなど、ファイアウォール側でリソースコンテキストを参照するポリシーを設定します。

⚖️ メリットと制約事項

💼 ビジネス面のメリット

✓運用コストの削減: IP 変化に応じたルール更新が不要になり、ポリシー維持負荷を大幅に軽減
✓セキュリティリスクの低減: タグ同期の合間の新規ワークロード見逃しがなくなり、最初のパケットから確実に適用
✓ガバナンスの向上: 環境分離ポリシーをリソース定義に基づいて宣言的に適用可能

🔬 技術面のメリット

✓意図ベースのセグメンテーション: ワークロードの論理的な定義でポリシーを記述
✓動的ワークロードへの即時適用: 短命な Lambda 関数にも送信した瞬間から適用
✓マルチリージョン対応: 複数リージョンの TGW を 1 つのストアに関連付け可能
✓ハイブリッド接続の検査: Direct Connect / Site-to-Site VPN 経由のトラフィックへの共通検査ポリシーが容易

⚠️ 制限事項

⚠グローバルネットワークあたりコンテキストストアは 1 つまで
⚠TGW は 1 つのコンテキストストアにのみ関連付け可能
⚠対象は AWS Network Firewall / Gateway Load Balancer タイプのネットワークファンクションアタッチメント経由のトラフィックのみ
⚠コンテキストに含まれるセキュリティグループは最大 5 つ (6 つ以上の場合は情報が含まれない)
⚠リージョン間 TGW ピアリングアタッチメントをまたぐ共有は不可
⚠中東 (バーレーン) および中東 (UAE) リージョンでは利用不可

💭 考慮すべき点

💡事前にグローバルネットワーク作成、TGW 登録、ネットワークファンクションアタッチメント経由のファイアウォール接続が必要
💡個々のコンテキストレコード参照は API / CLI のみ (コンソールはストアと関連付けの表示に限定)
💡対応ファイアウォールは現時点で AWS Network Firewall と Palo Alto Networks Software Firewalls

💡 ユースケース

1️⃣ Web 層と DB 層の間のマイクロセグメンテーション

シナリオ3 層アーキテクチャで Web 層から DB 層へのトラフィックにのみ脅威保護を適用したい。オートスケーリングで IP アドレスは頻繁に変化する。

実装コンテキストストアを作成して TGW を関連付け、Network Firewall のコンテキスト対応ステートフルルールグループで「Web 層 SG → DB 層 SG」のトラフィックを ContextSets で指定し IPS 検査を適用。

効果スケールイン・アウトで IP が変化してもルール更新が不要になり、セキュリティグループの定義に基づいた一貫した脅威保護を実現。

2️⃣ 開発環境から本番環境への到達ブロック

シナリオ同一の TGW に接続された開発 VPC と本番 VPC の間で、開発環境から本番環境へのアクセスを確実に遮断したい。

実装コンテキストストアで開発 VPC と本番 VPC のコンテキストを共有し、ファイアウォールポリシーで「開発 VPC → 本番 VPC」のトラフィックを VPC ID ベースで拒否。

効果VPC の CIDR 変更や VPC 追加のたびに IP ベースのルールを見直す必要がなくなり、環境分離ポリシーを宣言的に維持。

3️⃣ ハイブリッド接続トラフィックへの共通検査ポリシー

シナリオオンプレミスから Direct Connect および Site-to-Site VPN 経由で AWS に入るすべてのトラフィックに共通のインスペクションポリシーを適用したい。

実装コンテキストストアに TGW を関連付けて Direct Connect / VPN アタッチメントのコンテキストを共有し、アタッチメントタイプを条件に共通の検査ルールを定義。

効果接続回線の追加や変更があってもアタッチメント単位のポリシーがそのまま適用され、ハイブリッド環境の入口対策を一元化。

💰 料金と利用可能リージョン

💵 料金

公式発表には本機能に関する追加料金の記載はありません。 AWS Transit Gateway のデータ処理料金とアタッチメント料金、および AWS Network Firewall などのファイアウォール側の料金が通常どおり適用されます。 最新の料金は各サービスの料金ページを確認してください。

🌍 利用可能リージョン

AWS Transit Gateway が利用可能なすべての商用 AWS リージョンで利用可能。 ただし中東 (バーレーン) と中東 (UAE) は除く。 AWS GovCloud (US-East) および AWS GovCloud (US-West) リージョンでも利用可能。

🔗 関連サービス・機能

  • AWS Network Manager: コンテキストストアの作成・管理と TGW の関連付けを行うサービス。グローバルネットワークにコンテキストストアを配置
  • AWS Network Firewall: コンテキスト対応ステートフルルールグループにより、ContextSets を通じてリソースコンテキストをルールで参照可能
  • TGW ネットワークファンクションアタッチメント: ファイアウォールを TGW に接続する仕組み。コンテキスト共有は AWS Network Firewall / Gateway Load Balancer タイプのアタッチメント経由のトラフィックが対象
  • AWS Direct Connect / AWS Site-to-Site VPN: これらのアタッチメント経由で AWS に入るトラフィックにも、アタッチメントベースの共通検査ポリシーを適用可能

🎯 まとめ

AWS Transit Gateway のコンテキスト共有により、ファイアウォールのセグメンテーションポリシーを IP アドレスではなく VPC、サブネット、セキュリティグループ、アタッチメントといった AWS リソースの定義に基づいて記述できるようになりました。 IP ベースルールの維持負荷やタグ同期によるワークロード見逃しの課題を解消し、最初のパケットから確実にポリシーを適用できます。

Transit Gateway 配下でファイアウォールによる East-West 検査やハイブリッド接続の検査を行っている場合は、 AWS Network Manager でのコンテキストストア作成から検証を開始することを推奨します。
