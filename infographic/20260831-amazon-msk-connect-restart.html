Amazon MSK Connect

🔄 コネクタ再起動機能 (RestartConnector API)

📅 リリース日: 2026 年 8 月 31 日 ｜ Amazon Managed Streaming for Apache Kafka Connect

📌 概要

Amazon MSK Connect が、コネクタとそのタスクを再起動する機能をサポートしました。 コネクタ全体とすべてのタスクを再起動することも、失敗したタスクのみを選択的に再起動することも可能になり、 ストリーミングデータパイプラインの迅速な復旧が実現します。

再起動は障害からの復旧だけでなく、正常なコネクタに対しても実行でき、認証情報のローテーションなど外部依存関係の変更反映にも活用できます。 再起動時にはコネクタの設定とコミット済みオフセットが保持されるため、データの重複や欠落を最小限に抑えながら処理を再開できます。

API 1 回
呼び出しだけで障害復旧が完結
追加料金なし
MSK Connect の通常料金のみ
全リージョン
MSK Connect 利用可能リージョンで提供

❌ アップデート前の課題

🔻コネクタやタスクの失敗時は削除して再作成が必要で、ダウンタイムと運用負荷が発生
🔻削除・再作成の間はパイプラインが停止し、ストリーミング処理の遅延やデータ滞留の原因に
🔻一時的な障害や認証情報の更新などを反映する軽量な手段がなかった

✅ アップデート後の改善

🔺コネクタ全体、または失敗したタスクのみを API 1 回の呼び出しで再起動可能に
🔺設定とコミット済みオフセットが保持され、削除・再作成なしで復旧時間を大幅短縮
🔺正常なコネクタにも再起動を実行でき、外部依存関係の変更反映に利用可能

🏗️ アーキテクチャ図

sequenceDiagram
    participant U as 👤 運用者
    participant API as 🔌 MSK Connect API
    participant C as ⚙️ コネクタ
    participant T as 📦 タスク群

    U->>API: RestartConnector 呼び出し<br/>onlyFailedTasks を指定
    API-->>U: connectorOperationArn を返却
    Note over C: 状態が RESTARTING に遷移
    alt onlyFailedTasks = true
        API->>T: 失敗したタスクのみ再起動
    else onlyFailedTasks = false
        API->>C: コネクタ全体と全タスクを再起動
    end
    Note over T: 設定とコミット済みオフセットを保持
    U->>API: DescribeConnectorOperation で進捗確認
    API-->>U: RESTART_IN_PROGRESS / RESTART_COMPLETE / RESTART_FAILED

RestartConnector API は非同期で動作し、返却されたオペレーション ARN を DescribeConnectorOperation で追跡することで、再起動の進捗と結果を確認できます。

⚡ 主要機能

🔄 1. コネクタ全体の再起動

コネクタとそのすべてのタスクをまとめて再起動。設定とコミット済みオフセットが保持され、前回の処理位置から再開されるため、削除・再作成が不要になりダウンタイムを最小化できます。

🎯 2. 失敗したタスクのみの選択的再起動

onlyFailedTasks を true に設定すると失敗したタスクだけを再起動。正常に稼働しているタスクには影響を与えず、部分的な障害からピンポイントで復旧できます。

💚 3. 正常なコネクタへの再起動

失敗したタスクが存在しない正常なコネクタにも実行可能。一時的な問題の解消や、認証情報のローテーションなど外部システム・依存関係の変更反映に活用できます。

📡 4. 非同期オペレーションとしての追跡

RestartConnector はオペレーション ARN を返す非同期 API。DescribeConnectorOperation / ListConnectorOperations で状態 (RESTART_IN_PROGRESS、RESTART_COMPLETE、RESTART_FAILED) を確認でき、コネクタ状態として RESTARTING が追加されました。

🛠️ 設定方法

前提条件

✓Amazon MSK Connect でコネクタが作成済みであること
✓AWS CLI / SDK 利用時は kafkaconnect:RestartConnector を含む IAM 権限が付与されていること
✓RestartConnector API に対応した最新の AWS CLI / SDK バージョンを使用していること

手順

1
対象コネクタの状態を確認する
Bashコネクタ状態の確認
aws kafkaconnect describe-connector \
  --connector-arn arn:aws:kafkaconnect:ap-northeast-1:123456789012:connector/my-connector/xxxx

現在の状態 (connectorState) と stateDescription に含まれる失敗理由を確認します。失敗したタスクがある場合は選択的再起動を検討します。

2
コネクタを再起動する
BashRestartConnector の実行
# 失敗したタスクのみを再起動する場合
aws kafkaconnect restart-connector \
  --connector-arn arn:aws:kafkaconnect:ap-northeast-1:123456789012:connector/my-connector/xxxx \
  --only-failed-tasks

# コネクタ全体とすべてのタスクを再起動する場合
aws kafkaconnect restart-connector \
  --connector-arn arn:aws:kafkaconnect:ap-northeast-1:123456789012:connector/my-connector/xxxx \
  --no-only-failed-tasks

--only-failed-tasks を指定すると失敗したタスクのみが再起動され、正常なタスクは影響を受けません。レスポンスとしてコネクタオペレーション ARN が返されます。

3
再起動の進捗を確認する
Bashオペレーション状態の確認
aws kafkaconnect describe-connector-operation \
  --connector-operation-arn arn:aws:kafkaconnect:ap-northeast-1:123456789012:connector-operation/...

connectorOperationState が RESTART_COMPLETE になれば完了です。RESTART_FAILED の場合は errorInfo フィールドで失敗原因を確認します。

💡 メリットとデメリット・制約事項

📈 ビジネス面のメリット

✓ダウンタイムの削減: 削除・再作成が不要になり、パイプラインの停止時間を最小化
✓運用コストの低減: 障害復旧が API 1 回の呼び出しに簡素化され、運用負荷を軽減
✓データ鮮度の維持: 迅速な復旧により、下流システムへのデータ供給遅延を抑制

⚙️ 技術面のメリット

✓オフセットの保持: 前回の処理位置から正確に再開でき、データの重複・欠落リスクを抑制
✓選択的な復旧: onlyFailedTasks により正常なタスクの処理を中断させない
✓自動化との親和性: 非同期 API と追跡 API により、CloudWatch アラームと組み合わせた自動復旧を構築しやすい

⚠️ 制限事項

✗コネクタ全体の再起動中は、当該コネクタのデータ処理が一時的に停止する
✗再起動は根本原因 (認証エラー、設定ミスなど) を解決しないため、原因が残ると再度失敗する可能性がある
✗非同期オペレーションのため、完了までの時間はコネクタ構成やタスク数に依存する

🤔 考慮すべき点

⚠自動化する場合は、無限リトライを避けるため再試行回数の上限やアラート通知を設計に含める
⚠kafkaconnect:RestartConnector 権限は必要な運用ロールにのみ付与し、最小権限を維持する
⚠根本原因の調査には、CloudWatch Logs などのワーカーログ確認を併用する

🎯 ユースケース

1️⃣ 失敗したタスクの迅速な復旧

シナリオ: S3 シンクコネクタの一部タスクが一時的なネットワーク障害で FAILED 状態になり、パーティションの一部でデータ配信が停止している。

Bash失敗タスクのみ再起動
aws kafkaconnect restart-connector \
  --connector-arn <connector-arn> \
  --only-failed-tasks

効果: 失敗したタスクのみが再起動され、正常なタスクを中断せずにパイプライン全体を復旧。コミット済みオフセットから再開されるため、データの欠落を防げる。

2️⃣ 外部システムの認証情報ローテーション後の反映

シナリオ: 接続先データベースのパスワードをローテーションしたため、コネクタに新しい接続を確立させたい。コネクタ自体は正常に稼働している。

Bashコネクタ全体を再起動
aws kafkaconnect restart-connector \
  --connector-arn <connector-arn> \
  --no-only-failed-tasks

効果: 削除・再作成することなく全タスクが再起動され、新しい認証情報で接続が再確立される。設定変更を伴わない依存関係の更新を短時間で反映できる。

3️⃣ CloudWatch アラームと連携した自動復旧

シナリオ: コネクタのタスク失敗を検知したら、自動的に失敗タスクを再起動する自己修復型のパイプラインを構築したい。

PythonLambda 関数での自動復旧処理の例
# Lambda 関数での自動復旧処理の例
import boto3

client = boto3.client('kafkaconnect')

def handler(event, context):
    connector_arn = event['connectorArn']
    response = client.restart_connector(
        connectorArn=connector_arn,
        onlyFailedTasks=True
    )
    return {'operationArn': response['connectorOperationArn']}

効果: 障害検知から復旧までを自動化し、手動対応なしでパイプラインの可用性を向上。オペレーション ARN の追跡で復旧結果の監視も自動化できる。

💰 料金と利用可能リージョン

💵 料金
本機能は追加料金なしで利用できます。Amazon MSK Connect の通常料金 (コネクタが使用する MSK Connect Unit (MCU) 単位の時間課金) のみが適用され、再起動操作自体への課金は発生しません。
🌏 利用可能リージョン
Amazon MSK Connect が利用可能なすべての AWS リージョンで提供されます (東京リージョンを含む)。

📝 まとめ

Amazon MSK Connect のコネクタ再起動機能により、これまで削除・再作成が必要だった障害復旧が API 1 回の呼び出しで完結し、ストリーミングデータパイプラインのダウンタイムと運用負荷が大幅に削減されます。 MSK Connect を利用しているチームは、既存の障害対応 Runbook を RestartConnector ベースの手順に更新し、 CloudWatch アラームと組み合わせた自動復旧の導入を検討することを推奨します。
