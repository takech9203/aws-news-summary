Amazon ECS

🚪 Amazon ECS Gateway

ECS サービス向けマネージドイングレスソリューション ─ ALB の構築・管理を ECS に委任
📅 リリース日: 2026 年 10 月 20 日

📝 概要

Amazon ECS Gateway は、ALB とその関連リソースを動的にプロビジョニング・管理する新しいアカウントレベルのリソースです。リスナー、ターゲットグループ、セキュリティグループ、ACM 証明書などがユーザーの AWS アカウント内に自動作成され、コンテナアプリケーションのイングレスネットワーキング構成が大幅に簡素化されます。

プラットフォームチームがネットワーキング標準を一度定義してクラスターに関連付けると、アプリケーションチームはゲートウェイコネクタを追加するだけでオプトインでき、ネットワーキングの専門知識なしに標準を継承できます。各サービスには一意の HTTPS ホスト名が付与され、ホストベースルーティングで最大 25 サービスが 1 つの ALB を共有します。

25
1 つの ALB を共有できる最大サービス数
$0
ECS Gateway 自体の追加料金 (基盤リソースのみ課金)
全リージョン
AWS 商用リージョンで利用可能 (東京・大阪含む)

❌ Before: アップデート前の課題

  • サービスごとに ALB、リスナー、ターゲットグループ、セキュリティグループ、ACM 証明書を個別に設計・構築
  • ネットワーキング標準 (公開範囲、WAF、ログ) をサービス横断で一貫適用する仕組みがなくガバナンス維持が困難
  • アプリケーションチームにネットワーキングの専門知識が必要でデプロイ速度が低下
  • サービスごとの ALB 作成でコスト増大、手動共有ではリスナールールや優先順位の管理が煩雑
  • イングレスインフラのライフサイクル管理を自前で実施

✅ After: アップデート後の改善

  • プラットフォームチームが標準を一度定義するだけで、接続する全サービスに自動適用
  • アプリケーションチームはゲートウェイコネクタパラメータの追加だけでイングレスを利用可能
  • 最大 25 サービスで ALB を共有し、ホストベースルーティングと一意の DNS ホスト名でコスト削減とエンドポイント維持を両立
  • ALB のプロビジョニング・追加・削除までライフサイクル全体を ECS が自動管理
  • リソースは全てユーザーアカウント内に作成され、CloudWatch 標準メトリクスでそのまま監視可能

本機能は awsvpc ネットワークモードを使用する ECS サービスで、すべての起動タイプ (EC2、Fargate、ECS Managed Instances) に対応します。

ECS Gateway は複数のクラスターに関連付けることができ、オプトインしたサービスに対して共有 ALB を自動プロビジョニングします。クライアントからの HTTPS リクエストは、各サービスの一意のホスト名に基づくホストベースルーティングで該当サービスにルーティングされます。

⚡ 主要機能

1️⃣ 一元的なネットワーキング標準の定義と継承

  • ネットワーキング (公開範囲、サブネット)、セキュリティ (セキュリティグループ、AWS WAF Web ACL)、運用 (アクセスログ、ロードバランサー容量上限) を一度定義
  • ゲートウェイとクラスターの関連付けは多対多で柔軟に構成可能
  • アプリケーションチームはゲートウェイコネクタの追加だけで標準を継承

2️⃣ ALB とライフサイクルの完全自動管理

  • 最初のサービス接続時に ALB、リスナー、セキュリティグループを作成 (作成・関連付け時点ではプロビジョニングなし)
  • 容量のある ALB を再利用し、容量到達時には新しい ALB を自動追加
  • 最後のサービス切断時に ALB を自動削除し、不要なコストの発生を防止

3️⃣ ホストベースルーティングと一意の DNS ホスト名

  • 各サービスに https://<unique-id>.ecs.<region>.on.aws 形式の HTTPS ホスト名を自動付与
  • 最大 25 サービスで 1 つの ALB を共有し、ホストベースルーティングでトラフィックを振り分け
  • ACM 証明書、リスナールール、ターゲットグループ、サービス用セキュリティグループをサービスごとに自動作成

4️⃣ 透明性の高いインフラと標準的な監視

  • 全リソースはユーザーのアカウント内に作成され、コンソール・API から直接確認・管理可能
  • AmazonECSManaged=true タグと aws:ecs:gateway-arn システムタグでリソースの特定が容易
  • CloudWatch の標準 ALB メトリクスと ELB のターゲットヘルス情報で監視可能

🛠️ 設定方法

✅ 前提条件

✓ECS がインフラをプロビジョニングするために引き受ける IAM ロール (インフラストラクチャロール) を用意していること
✓対象の ECS サービスが awsvpc ネットワークモードを使用していること
✓ゲートウェイとクラスターが同一アカウント・同一 VPC 内にあり、ゲートウェイのサブネットがサービスの使用するすべてのアベイラビリティーゾーンをカバーしていること
1

ゲートウェイの作成 (プラットフォームチーム)

BashAWS CLI
aws ecs create-gateway \
  --name my-team-gateway \
  --infrastructure-role-arn arn:aws:iam::123456789012:role/ECSGatewayRole \
  --configuration '{
    "HostSharedAlb": {
      "networkConfiguration": {
        "subnets": ["subnet-080779f9bd887757a", "subnet-0a1b2c3d4e5f67890"],
        "ipAddressType": "ipv4"
      },
      "scheme": "internet-facing"
    }
  }'

名前、インフラストラクチャロール、ロードバランシングスキーム (インターネット向けまたは VPC 内部)、サブネットなどを指定します。この時点ではインフラはプロビジョニングされません。名前、スキーム、VPC、サブネット、IP アドレスタイプ、リスナーのプロトコルとポートは作成後に変更できません。

2

ゲートウェイとクラスターの関連付け

BashAWS CLI
aws ecs associate-gateway-with-cluster \
  --gateway my-team-gateway \
  --cluster arn:aws:ecs:us-east-1:123456789012:cluster/my-cluster

ゲートウェイを ECS クラスターに関連付け、そのクラスター内のサービスからゲートウェイを利用可能にします。関連付けは多対多で設定できます。

3

サービスのオプトイン (アプリケーションチーム)

BashAWS CLI
aws ecs create-service \
  --cluster my-cluster \
  --service my-api-service \
  --task-definition my-api-service:1 \
  --gateway-connectors '[{
    "portName": "api",
    "filters": {"accessTypes": ["PUBLIC"]}
  }]'

サービスの作成または更新時に --gateway-connectors パラメータを追加してオプトインします。デプロイ時に ECS は互換性のあるすべてのゲートウェイにサービスを接続し、ACM 証明書、一意の DNS ホスト名、リスナールール、ターゲットグループ、セキュリティグループをプロビジョニングします。ルートが ACTIVE になると、一意の HTTPS エンドポイントでアクセス可能になります。

既存サービスを移行する場合は、既存のロードバランサー設定とゲートウェイの両方のイングレス経路を並行稼働させて検証し、問題がなければ旧設定を削除する段階的な移行が可能です。

💡 メリット

💼 ビジネス面

✓デプロイ速度の向上: ネットワーキングの専門知識なしにサービスを公開でき、リリースまでのリードタイムが短縮
✓コスト最適化: 最大 25 サービスで 1 つの ALB を共有し、インフラコストを大幅に削減
✓ガバナンスの強化: ネットワーキング・セキュリティ標準を一元的に定義・適用し、サービス横断で一貫した統制を実現

⚙️ 技術面

✓運用負荷の削減: ALB のプロビジョニングから削除までライフサイクル全体を ECS が自動管理
✓透明性の確保: 全リソースがアカウント内に作成され、タグにより管理リソースを容易に特定可能
✓標準的な監視との統合: HealthyHostCount、TargetResponseTime、HTTPCode_Target_5XX_Count などの標準 ALB メトリクスをそのまま利用可能

⚠️ デメリット・制約事項

🚫 制限事項

✗ゲートウェイは HTTPS (ポート 443) のみをサポート
✗awsvpc ネットワークモードが必須 (bridge、host、none モードは接続不可)
✗ゲートウェイとクラスターは同一アカウント必須 (クロスアカウント構成は非対応)
✗サービスあたりのゲートウェイコネクタは 1 つのみ (1 つのコネクタで複数ゲートウェイへの接続は可能)
✗ECS Express Mode のサービスには非対応
✗名前、タイプ、スキーム、リスナーポート・プロトコル、サブネット、IP アドレスタイプは作成後に変更不可 (変更には新しいゲートウェイの作成とサービスの移行が必要)

🤔 考慮すべき点

⚠サービスはゲートウェイを名前で選択できず、クラスターに関連付けられた互換性のあるすべてのゲートウェイに接続される
⚠ECS は ALB 間でサービスを再配置 (統合) しないため、部分的に使用された ALB が複数残る場合がある
⚠ECS の管理外で管理対象リソースを変更・削除すると、自動修復されずトラフィック停止やデプロイ失敗の原因となる
⚠maxAlbCount (デフォルト 10) に到達し ALB に空きがない場合、新しいサービスのデプロイは失敗する
⚠DNS ホスト名は自動生成形式であり、カスタムドメインの設定は公式ドキュメントで確認が必要

🎯 ユースケース

🏢 ユースケース 1: プラットフォームチームによるマルチクラスター環境の統制

シナリオ: 複数の開発チームがそれぞれの ECS クラスターでマイクロサービスを運用しており、組織全体のネットワーキング・セキュリティ標準 (WAF、アクセスログ、公開範囲) を統一的に適用したい。

Bash実装例
# WAF とアクセスログを設定したゲートウェイを作成し、複数クラスターに関連付け
aws ecs create-gateway --name org-standard-gateway \
  --infrastructure-role-arn arn:aws:iam::123456789012:role/ECSGatewayRole \
  --configuration '{"HostSharedAlb": {...}}'

aws ecs associate-gateway-with-cluster --gateway org-standard-gateway --cluster team-a-cluster
aws ecs associate-gateway-with-cluster --gateway org-standard-gateway --cluster team-b-cluster

✨ 効果: 全チームのサービスが同一のセキュリティ標準を自動的に継承し、ガバナンスを維持しながら各チームの自律的なデプロイが可能になる。

💰 ユースケース 2: 多数のマイクロサービスにおける ALB コストの最適化

シナリオ: 20 以上のマイクロサービスをそれぞれ独立した ALB で公開しており、ALB の時間課金が積み上がってコストが増大している。

Bash実装例
# 各サービスをゲートウェイにオプトインして ALB を共有
aws ecs update-service \
  --cluster my-cluster \
  --service service-01 \
  --gateway-connectors '[{"portName": "web"}]'

✨ 効果: 最大 25 サービスが 1 つの ALB を共有し、各サービスは一意のホスト名を維持したまま ALB の台数と時間課金を大幅に削減できる。

🧪 ユースケース 3: 開発・検証環境のエフェメラルなサービス公開

シナリオ: 機能ブランチごとに検証用のサービスを頻繁に作成・削除しており、その都度ロードバランサーやターゲットグループを構成・削除する運用が負担になっている。

Bash実装例
# 検証用サービスの作成時にコネクタを追加するだけで HTTPS エンドポイントを取得
aws ecs create-service \
  --cluster dev-cluster \
  --service feature-branch-service \
  --task-definition feature-app:5 \
  --gateway-connectors '[{"portName": "app"}]'

✨ 効果: サービス作成と同時に HTTPS エンドポイントが自動付与され、サービス削除時にはルートと関連リソースが自動クリーンアップされるため、検証環境の運用負荷がほぼゼロになる。

💰 料金

Amazon ECS Gateway 自体の利用に追加料金はかかりません。サービスがゲートウェイに接続した際にアカウント内にプロビジョニングされる基盤リソースに対してのみ、通常の料金が発生します。

→Application Load Balancer の時間料金および LCU 料金
→Amazon CloudWatch のログ・メトリクス料金 (アクセスログなどを有効化した場合)
→データ転送料金
💡 25 サービスで 1 つの ALB を共有できるため、サービスごとに ALB を作成する構成と比較して ALB 料金を最大で約 1/25 に抑えられる可能性があります。

🌏 利用可能リージョン

すべての AWS 商用リージョンで利用可能です (東京・大阪リージョンを含む)。

🔗 関連サービス・機能

⚖️ Elastic Load Balancing (ALB): ゲートウェイがプロビジョニング・管理する中核リソース。ホストベースルーティングとターゲットヘルス情報を提供
🔐 AWS Certificate Manager (ACM): 各サービスの一意の HTTPS ホスト名に対する証明書を自動発行・管理
🛡️ AWS WAF: ゲートウェイに Web ACL を設定することで、接続するすべてのサービスに Web アプリケーション保護を一括適用可能
📊 Amazon CloudWatch: 標準の ALB メトリクスによる監視とアラーム設定に利用
🔄 Amazon ECS Service Connect: サービス間 (East-West) 通信を簡素化する既存機能。ECS Gateway は外部からのイングレス (North-South) 通信を担い、相互補完の関係

📌 まとめ

Amazon ECS Gateway は、ECS サービスのイングレスネットワーキングにおける「プラットフォームチームによる統制」と「アプリケーションチームの俊敏性」を両立させる重要なアップデートです。ALB の共有によるコスト最適化とライフサイクルの完全自動管理により、特に多数のマイクロサービスを運用する組織に大きな価値をもたらします。まずは開発環境のクラスターでゲートウェイを作成し、既存サービスの並行稼働による段階的な移行を検証することを推奨します。
