🤖 AWS DevOps Agent
Access Profiles と AWS Organizations サポート

AWS DevOps Agent 📅 リリース日: 2026 年 11 月 23 日

📌 概要

AWS DevOps Agent に、エージェントインスタンスに対するガバナンスと制御を強化する 2 つの新機能が追加されました。

🎫 Access Profiles
Agent Space 内の IAM Identity Center ユーザーを定義済みの権限セットにリンク。スキルやメモリの作成・更新を特定のユーザーのみに限定するなど、ユーザーごとのきめ細かな権限制御が可能になります。
🏢 AWS Organizations サポート
組織単位 (OU) または組織ルートを選択するだけで、対象の各メンバーアカウントにアクセスロールを自動展開し、Agent Space のセカンダリアカウントとして追加。アカウントを 1 つずつ接続する必要はありません。

複数アカウント環境で AWS DevOps Agent を運用するプラットフォームチームや、AI エージェントの利用に統制を求めるガバナンス担当者にとって重要な機能強化です。

❌ Before: アップデート前の課題
  • Web アプリへのアクセスはユーザー・グループ単位の追加のみで、操作権限を細かく分けられなかった
  • スキル・メモリの作成・更新を特定ユーザーに限定することが困難だった
  • 複数アカウントの監視はアカウントを 1 つずつ接続する必要があり、大規模組織では運用負荷が高かった
  • 組織のアカウント追加・移動時に Agent Space の設定を手動で追従させる必要があった
✅ After: アップデート後の改善
  • Access Profiles でユーザーを権限セットにリンクし、操作権限をユーザー単位で制御可能に
  • スキル・メモリの作成・更新を選択した一部のユーザーのみに限定可能に
  • OU または組織ルートの指定だけでアクセスロール展開と Agent Space への関連付けを自動化
  • OU への参加で自動追加、離脱でロール削除と、組織構造の変化に自動追従

⚙️ 主要機能

1. 🎫 Access Profiles によるユーザー権限制御
  • Agent Space 内の IAM Identity Center ユーザーを定義済みの権限セットにリンク
  • スキルやメモリの作成・更新といった操作を、選択した一部のユーザーに限定可能
  • 外部 IdP (Okta、Microsoft Entra ID、Ping Identity) との連携を含む IAM Identity Center 認証と組み合わせて統制を強化
2. 🏢 AWS Organizations サポートによるアカウントの自動整合
  • OU または組織ルートを選択すると、各メンバーアカウントにアクセスロール (AIDevOpsAgentSpaceRole-*) を展開し、セカンダリアカウントとして追加
  • ロール展開には CloudFormation StackSets (サービスマネージド権限) を使用し、AIDevOpsAgentAccessPolicy 管理ポリシーをアタッチ
  • 1 つの関連付けで OU 全体、または OU 配下の特定アカウントのリスト (最大 1,000 アカウント) をカバー
3. 🔄 組織構造の変化への自動追従
  • アカウントが OU に参加すると自動的にカバレッジへ追加、OU から外れるとロールを削除
  • 変更通知により通常は数分以内に反映。遅延時も 6〜9 時間ごとの定期チェックで検出
  • 組織からアカウントが離脱すると、即座に認証情報の発行を停止
4. 👥 委任管理者のサポート
  • Agent Space は管理アカウントまたは委任管理者アカウント (プライマリアカウント) に作成可能
  • 管理アカウントの使用を最小化するため、委任管理者アカウントの利用を推奨
  • aidevops.amazonaws.com と member.org.stacksets.cloudformation.amazonaws.com の両方への登録が必要 (それぞれ最大 5 アカウント)

ステップ 1: 信頼されたアクセスの有効化

Bash 管理アカウントで実行 
# AWS DevOps Agent の信頼されたアクセスを有効化 (管理アカウントで実行)
aws organizations enable-aws-service-access \
    --service-principal aidevops.amazonaws.com

# CloudFormation StackSets の信頼されたアクセスをアクティブ化
aws cloudformation activate-organizations-access

# 両方が有効になったことを確認
aws organizations list-aws-service-access-for-organization
aws cloudformation describe-organizations-access

StackSets には enable-aws-service-access ではなく activate-organizations-access を使用する点に注意 (必要なサービスリンクロールが作成されないため)。確認コマンドの出力に aidevops.amazonaws.com が含まれ、Status が ENABLED であれば完了です。

ステップ 2: 委任管理者の登録 (推奨)

Bash 管理アカウントで実行 
# AWS DevOps Agent の委任管理者を登録
aws organizations register-delegated-administrator \
    --account-id <DELEGATED_ADMIN_ACCOUNT_ID> \
    --service-principal aidevops.amazonaws.com

# CloudFormation StackSets の委任管理者も登録
aws organizations register-delegated-administrator \
    --account-id <DELEGATED_ADMIN_ACCOUNT_ID> \
    --service-principal member.org.stacksets.cloudformation.amazonaws.com

組織の管理と AWS DevOps Agent の運用を分離できます。コンソールで信頼されたアクセスを有効化した際に委任管理者を選択した場合、このステップは不要です。

ステップ 3: 組織モードの Agent Space と organization association の作成

Bash プライマリアカウントで実行 
# 組織モードで Agent Space を作成 (プライマリアカウントで実行)
aws devops-agent create-agent-space \
    --name "MyOrgAgentSpace" \
    --aws-source-mode organization \
    --region <REGION>

# OU 全体をカバーする organization association を作成
aws devops-agent associate-service \
    --agent-space-id <AGENT_SPACE_ID> \
    --service-id aws \
    --configuration '{
      "sourceAwsOrg": {
        "accountType": "source",
        "organizationalUnit": {
          "organizationalUnitId": "<OU_ID>"
        }
      }
    }' \
    --region <REGION>

# デプロイ状況を確認
aws devops-agent get-association \
    --agent-space-id <AGENT_SPACE_ID> \
    --association-id <ASSOCIATION_ID> \
    --region <REGION>

特定アカウントのみをカバーする場合は organizationalUnit に accountIds を追加し、組織全体をカバーする場合はルート ID (r-*) を指定します。デプロイ中はステータスが pending-confirmation となり、完了すると valid に変わります。大規模組織ではデプロイに数時間かかる場合があります。コンソールでは Agent Space 作成時の Agent scope ページで Organization を選択します。

ステップ 4: Access Profiles の設定

Agent Space の IAM Identity Center 認証を設定した上で、Agent Space 内で IAM Identity Center ユーザーを権限セットにリンクします。スキルやメモリの作成・更新を許可するユーザーを限定するプロファイルを割り当てることで、エージェントの挙動に影響する操作を統制できます。詳細は AWS DevOps Agent ユーザーガイドを参照してください。

💡 メリット

💼 ビジネス面

✓ガバナンスの強化: スキルやメモリの変更を特定のユーザーに限定することで、AI エージェントの挙動に対する組織的な統制を確立でき、監査要件への対応が容易になる
✓運用コストの削減: 組織内の数百〜数千のアカウントを個別に接続する作業が不要になり、マルチアカウント環境での導入・運用の工数を大幅に削減できる
✓スケーラブルな展開: 1 つの Agent Space で最大 3,000 アカウントをカバーでき、組織全体への AI DevOps エージェントの展開が現実的になる

🔧 技術面

✓組織構造への自動追従: アカウントの OU への参加・離脱を自動検出し、ロールの展開・削除を自動で行うため、構成ドリフトが発生しない
✓最小権限の原則: メンバーアカウントのロールは AWS DevOps Agent のみが引き受け可能で、組織の関連付けでカバーされるアカウントでは読み取り専用アクションのみが使用される
✓監査可能性: エージェントの API 呼び出しは各メンバーアカウントの CloudTrail に AIDevOpsAgentSpaceRole-* ロールのセッションとして記録される
✓即時のアクセス遮断手段: 信頼されたアクセスの無効化、関連付けのスコープ変更、SCP の適用といった複数のレイヤーでアクセスを停止できる

⚠️ デメリット・制約事項

🚧 制限事項

✗組織の関連付けでカバーされるアカウントでは directed actions (エージェントによる書き込みアクション) を使用できない。昇格ロールを登録できないため、読み取り専用アクションのみ (プライマリアカウントと対応サードパーティ統合では引き続き利用可能)
✗組織モードの Agent Space には、個別に接続したセカンダリアカウントを併用できない
✗Agent Space が委任管理者アカウントにある場合、管理アカウントのリソースは調査できない
✗組織モードは AWS GovCloud (US) リージョンと中国リージョンでは利用できない
✗関連付けの OU は後から変更できない。別の OU をカバーするには新しい関連付けを作成する必要がある

🤔 考慮すべき点

⚠CloudFormation StackSets の委任管理者は組織内のすべてのアカウントにデプロイできる強い権限を持つため、信頼できるアカウントのみに登録する
⚠デプロイ中にスタックセットやロールを手動で編集・削除すると、デプロイの遅延やアクセス断の原因になる。アクセス停止には正規の手段を使用する
⚠大規模組織ではロール展開に数時間かかる場合がある
⚠クォータ (関連付け 20 件、カバーアカウント 3,000 件など) は現時点で引き上げ不可

🎯 ユースケース

1️⃣ エンタープライズ全体への DevOps Agent 展開

シナリオ: 数百のアカウントを持つ企業が、組織全体の本番ワークロードを 1 つの Agent Space で監視・調査したい。

実装例:

  1. 管理アカウントで aidevops.amazonaws.com と CloudFormation StackSets の信頼されたアクセスを有効化
  2. 運用チームのアカウントを委任管理者として登録
  3. 委任管理者アカウントに組織モードの Agent Space を作成
  4. 本番ワークロード用 OU を指定して organization association を作成

効果: アカウントを個別接続することなく、OU 配下の全アカウントが自動的に監視対象となる。新規アカウントが OU に追加されても自動でカバレッジに含まれ、運用負荷を最小化できる。

2️⃣ スキル・メモリ管理の統制

シナリオ: プラットフォームチームがエージェントのスキルとメモリの品質を管理しており、一般の開発者による変更を防ぎたい。

実装例:

  1. Agent Space に IAM Identity Center 認証を設定
  2. Access Profiles で、プラットフォームチームのユーザーのみにスキル・メモリの作成・更新権限を持つプロファイルをリンク
  3. 一般開発者には調査結果の閲覧やチャットなどの利用権限のみを付与

効果: エージェントの挙動を左右するスキル・メモリの変更が統制され、意図しない変更や品質低下を防止できる。一般開発者は引き続きエージェントを活用できる。

3️⃣ 段階的な導入と選択的なアカウントカバレッジ

シナリオ: まず特定の開発アカウント群で AWS DevOps Agent を評価し、その後本番 OU 全体へ展開したい。

実装例:

  1. 評価フェーズ: organization association の accountIds に評価対象アカウントのみを指定して作成
  2. 展開フェーズ: update-association で accountIds を削除し、OU 全体のカバレッジに切り替え

効果: 同じ Agent Space と関連付けを使ったまま、特定アカウントのリストから OU 全体へスコープを拡大でき、段階的な導入をスムーズに進められる。

📝 まとめ

AWS DevOps Agent は、マルチアカウント環境でのスケーラブルな展開 (AWS Organizations サポート) とユーザー単位のきめ細かな権限統制 (Access Profiles) の両方を備え、エンタープライズでの本格導入に必要なガバナンス基盤が整いました。

✓複数アカウントで DevOps Agent の利用を検討している場合は、まず管理アカウントで信頼されたアクセスを有効化し、委任管理者アカウントに組織モードの Agent Space を作成して評価することを推奨
✓あわせて、スキルやメモリの変更権限を Access Profiles で統制する運用設計も検討
