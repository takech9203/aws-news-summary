Amazon SageMaker Unified Studio

⚙️ Workflows で PythonOperator / BashOperator をサポート

サーバーレスビジュアルワークフローで任意の Python 関数・シェルコマンドを直接実行 | リリース日: 2026 年 9 月 3 日

📌 概要

Amazon SageMaker Unified Studio Workflows が、Apache Airflow のコアオペレーターである PythonOperator と BashOperator をサポートしました。 サーバーレスワークフロー内で任意の Python 関数やシェルコマンドを、 別途コンピューティングリソースをプロビジョニングすることなく直接実行できます。

この機能は Workflows の基盤である Amazon MWAA Serverless の新機能として提供され、 ビジュアルエディタのタスクパネルからオペレーターをキャンバスにドラッグし、 スクリプトファイルを指定するだけでカスタムコードをタスクとして実行できます。

❌ アップデート前の課題
  • AWS サービス連携用オペレーター (80 以上) のみ対応で、任意のカスタムコードを直接実行できなかった
  • 軽量なデータ変換のために Lambda 関数や ECS タスクを別途作成・管理する必要があった
  • カスタムロジックのためだけに別サービスの IAM ロール、デプロイパイプライン、監視設定が必要だった
✅ アップデート後の改善
  • PythonOperator で任意の Python 関数をタスクとして直接実行可能
  • BashOperator でシェルコマンド・スクリプトをタスクとして直接実行可能
  • ビジュアルエディタでスクリプトをアップロードするだけで完結、Lambda / ECS へのオフロード不要
  • タスク出力を {{ タスク名.output }} 形式で他タスクから参照可能

従来は Lambda や ECS にオフロードしていたカスタムロジックを、S3 にアップロードしたスクリプトファイルを参照する PythonOperator / BashOperator としてワークフロー内で直接実行できるようになりました。

🚀 主要機能

🐍 1. PythonOperator: Python 関数の直接実行

任意の Python callable をワークフローのタスクとして実行。ビジュアルエディタでは、アップロードした Python ファイルと関数名 (module_name.function_name 形式) を指定するだけで設定完了。

→ Op arguments (位置引数のリスト) と Op kwargs (キーワード引数の辞書) で関数に引数を渡すことが可能。YAML では airflow.providers.standard.operators.python.PythonOperator (Airflow 3 形式) を指定。

💻 2. BashOperator: シェルコマンド / スクリプトの直接実行

Bash コマンド、コマンドの組み合わせ、または .sh スクリプトへの参照をタスクとして実行。コマンドフィールドはテンプレート値をサポートし、他のタスクの出力やワークフロー変数を参照可能。

→ YAML では airflow.providers.standard.operators.bash.BashOperator として指定。

📤 3. ビジュアルエディタからのファイルアップロード

ワークフロー設定の Storage セクションから .py / .sh / .zip ファイルをアップロード。単一ファイルは zip 化不要。複数ファイルは .zip アーカイブとして S3 に保存され、実行時に展開される。

→ サードパーティの Python 依存関係は pip install --target ./package でローカルにインストールし、スクリプトと一緒にアップロードすることで利用可能。

🔗 4. タスク間のデータ連携

PythonOperator / BashOperator の出力は {{ タスク名.output }} 構文で他のタスクから参照可能。AWS サービスオペレーターとカスタムコードタスクを組み合わせた DAG を構築できる。

📝 YAML ワークフロー定義の例

YAML PythonOperator / BashOperator の定義例 
my_dag:
  start_date: "2024-01-01"
  schedule: null
  tasks:
    python_task:
      operator: airflow.providers.standard.operators.python.PythonOperator
      python_callable: my_module.hello_world
    bash_task:
      operator: airflow.providers.standard.operators.bash.BashOperator
      bash_command: "echo 'Hello from bash' && date"

🛠️ 設定方法

✅ 前提条件

✓Amazon SageMaker Unified Studio のプロジェクトが作成済みであること
✓オペレーターが参照する Python (.py) または Bash (.sh) ファイルを準備しておくこと
✓(MWAA Serverless API を直接使用する場合) コードと DAG ファイルを保存する S3 バケットと、S3 バケットへのアクセス権限を持つ実行ロール

📋 手順

1
ビジュアルワークフローの作成

SageMaker Unified Studio にログインし、[Workflows] から [Create new workflow] を選択してビジュアルワークフローエディタを開き、ワークフローに名前を付けて保存します。

2
オペレーターファイルのアップロード

エディタの設定 (歯車アイコン) から [Storage] を展開し、[Python/Bash Operator Files] で .py / .sh / .zip ファイルをアップロードして保存します。ファイルは zip 化されて S3 に保存され、ワークフロー定義から参照されます。

3
PythonOperator タスクの追加

タスク検索ウィンドウの [General Purpose] カテゴリから [Python Operator] をキャンバスに追加し、[Python Callable] でアップロード済みの Python ファイルと関数名を指定します。必要に応じて Op arguments (例: [us-east-1, gold, 100]) や Op kwargs を設定します。

4
BashOperator タスクの追加

[Bash Operator] をキャンバスに追加し、[Bash command] フィールドにコマンドまたは .sh スクリプトへの参照を入力します。テンプレート値をサポートするため、他のタスクの出力 (例: {{ Bash-task.output }}) やワークフロー変数を参照できます。

5
タスクの接続と実行

各タスクの + 記号同士を接続して実行順序を定義し、保存します。実行後は [View runs] からタスクごとの出力とログを確認できます。ログは CloudWatch Logs の /aws/mwaa-serverless/{ワークフロー名}/ ロググループに出力されます。

📦 サードパーティ依存関係のパッケージング

Bash 実行環境向け依存関係の準備 
# ソースファイルと依存関係を 1 つのディレクトリに集約
mkdir my_package
cp my_module.py my_package/

# 実行環境 (Python 3.12 / Linux x86_64) 向けの依存関係をインストール
pip install -r requirements.txt --target my_package \
  --platform manylinux2014_x86_64 \
  --python-version 3.12 \
  --only-binary=:all:

# アーカイブのルートに全ファイルを配置した zip を作成
cd my_package
zip -r ../my_package.zip . -x "*__pycache__*" "*.pyc"

⚠️ --platform / --python-version / --only-binary フラグにより、MWAA Serverless ワーカーの実行環境である Python 3.12 / Linux x86_64 用のホイールを取得します。これらを指定しないとローカルマシン向けのパッケージがインストールされ、実行時のインポートが失敗します。

⚖️ メリットと制約事項

💼 ビジネス面のメリット

✓開発速度の向上: Lambda / ECS の別途構築・デプロイ工程が不要になり、パイプライン構築のリードタイムが短縮
✓運用コストの削減: 管理対象コンポーネントが減り、個別の IAM ロール設定、デプロイパイプライン、監視設定の運用負荷が軽減
✓ローコードとカスタムコードの両立: ドラッグアンドドロップの操作性を保ちながら、必要な箇所だけカスタムコードを組み込める

🔬 技術面のメリット

✓サーバーレス実行: プロビジョニングやスケーリング管理が不要
✓Airflow 標準互換: Apache Airflow 3 標準と同じ指定方法で、既存 DAG からの移行が容易
✓認証情報の自動解決: 実行ロールの認証情報が自動で利用可能、コード内の認証設定が不要
✓コードのバージョニング: 作成・更新のたびにイミュータブルなワークフローバージョンとしてスナップショット

⚠️ 制限事項

✗コードファイル / zip 展開後の最大サイズは 250 MB
✗アカウント内の全ワークフロー合計コードストレージは 75 GB まで
✗実行環境は Python 3.12 / Linux x86_64 固定
✗タスクあたり 1 vCPU / 3 GiB のため、大規模処理には Glue や EMR など専用オペレーターが適する
✗プリインストールパッケージと同名のパッケージを同梱しても、プリインストール版が優先される

💡 考慮すべき点

⚠デフォルトはインターネットアクセスなし。外部 API 呼び出しには NetworkConfiguration で VPC を指定
⚠__pycache__ をコードパッケージに含めると、バイトコード非互換で失敗する可能性があるため除外する
⚠AWS Managed Tasks として MWAA の料金体系に基づく課金が発生
⚠本番では S3 バージョニングを有効化し、VersionId 指定による再現性のあるデプロイを推奨

🎯 ユースケース

📊 ユースケース 1: ETL パイプライン内の軽量データ変換

シナリオ: Glue ジョブで抽出したデータに対して、ロード前に軽量なフォーマット変換やバリデーションを行いたい。従来はこの処理のためだけに Lambda 関数を作成していた。

YAML Glue + PythonOperator の ETL パイプライン 
etl_dag:
  start_date: "2026-09-01"
  schedule: "0 2 * * *"
  tasks:
    extract:
      operator: airflow.providers.amazon.aws.operators.glue.GlueJobOperator
      job_name: extract-job
    transform:
      operator: airflow.providers.standard.operators.python.PythonOperator
      python_callable: transforms.normalize_records
      dependencies: [extract]
    load:
      operator: airflow.providers.amazon.aws.operators.glue.GlueJobOperator
      job_name: load-job
      dependencies: [transform]
✅ 効果: Lambda 関数の作成・デプロイ・監視が不要になり、変換ロジックをワークフローと一体でバージョン管理できる。
💻 ユースケース 2: シェルスクリプトによる前処理・後処理

シナリオ: 分析ジョブの前にファイルの整形やチェックサム検証をシェルコマンドで行い、ジョブ完了後に結果の後処理を実行したい。

Text BashOperator による前処理・後処理の構成 
BashOperator タスク 1 (前処理):
  Bash command: bash preprocess.sh {{ workflow.params.input_path }}

AthenaOperator タスク (分析クエリ実行)

BashOperator タスク 2 (後処理):
  Bash command: echo "Query finished" && bash postprocess.sh {{ Athena-task.output }}
✅ 効果: 既存のシェルスクリプト資産を ECS タスク化することなくそのままワークフローに組み込め、テンプレート構文で前段タスクの出力も参照できる。
🔧 ユースケース 3: boto3 を使った AWS リソースのカスタム操作

シナリオ: 標準オペレーターでカバーされていない AWS API 操作 (カスタムタグ付け、独自の条件チェックなど) をパイプラインの途中で実行したい。

Python custom_ops.py (アップロードするコードパッケージに含める) 
import boto3

def tag_processed_objects(bucket, prefix):
    s3 = boto3.client("s3")  # 実行ロールの認証情報が自動で解決される
    response = s3.list_objects_v2(Bucket=bucket, Prefix=prefix)
    for obj in response.get("Contents", []):
        s3.put_object_tagging(
            Bucket=bucket,
            Key=obj["Key"],
            Tagging={"TagSet": [{"Key": "status", "Value": "processed"}]},
        )
✅ 効果: プリインストールされた boto3 と自動解決される実行ロール認証情報により、認証設定なしで任意の AWS API 操作をタスクとして実行できる。

🔗 関連サービス・機能

→Amazon MWAA Serverless: サーバーレスワークフローの実行基盤。今回のオペレーターサポートは MWAA Serverless の機能として提供

📝 まとめ

SageMaker Unified Studio のサーバーレスビジュアルワークフローで PythonOperator と BashOperator が利用可能になり、Lambda や ECS を経由せずにカスタムコードをパイプラインへ直接組み込めるようになりました。

標準オペレーターでカバーできない軽量なデータ変換やスクリプト実行を含むパイプラインの構築・運用が大幅に簡素化されます。 ETL パイプラインにカスタムロジックを組み込んでいるチームは、既存の Lambda / ECS ベースの補助処理を本機能で置き換えられないか検討することをおすすめします。
