AWS IAM / Service Reference Information 📅 2026 年 10 月 21 日

🔐 サービスリファレンス情報がグローバル条件キー・サービス名・データプレーン分類をサポート

IAM ポリシー管理の自動化に必要な 3 つのメタデータを機械可読な JSON で提供開始

📋 概要

AWS は、IAM ポリシー管理の自動化を支援する機械可読な JSON 形式のサービスリファレンス情報 (Service Reference Information) を拡張し、3 つの新しい情報を提供開始しました。これらのメタデータを既存のポリシー管理ツールやワークフローに直接組み込み、手作業を削減しながらポリシーをサービスの更新に追従させることが容易になります。

❌ Before: アップデート前の課題
  • グローバル条件キーの一覧は IAM ユーザーガイドのドキュメントページにのみ記載され、機械的な取得・検証が困難だった
  • サービスプレフィックス (例: s3) しか含まれず、読みやすいサービス名のマッピングを自前で管理する必要があった
  • データプレーン操作かコントロールプレーン操作かを機械的に判別できず、権限の分析・分類が手作業だった
✅ After: アップデート後の改善
  • global-condition-keys.json から、すべての aws: 条件キー (名前、説明、ドキュメントページ、型) を取得可能に
  • ServiceName フィールドで識別子から表示名 (例: S3) への変換を自動化
  • Annotations.Properties の IsDataPlane でデータ/コントロールプレーン操作をプログラムで分類可能に

ポリシー管理ツールがサービスリファレンス情報の各エンドポイントから JSON を定期取得し、グローバル条件キーの検証やデータプレーン操作の分類を自動化して IAM ポリシーやガードレールの作成・維持に活用する流れを示しています。

⚡ 主要機能

1. 🌐 グローバル条件キーの機械可読ファイル提供

→ https://servicereference.us-east-1.amazonaws.com/v1/global-condition-keys.json から、すべての aws: プレフィックスのグローバル条件キーを単一ファイルで取得可能

→ 各キーには Name (キー名)、Description (説明)、DocPage (ドキュメントページのパス)、Types (値の型、例: Bool、Date、ArrayOfString) が含まれる

→ 従来はドキュメントページでのみ提供されていた情報を、ツールから直接参照・検証できる

2. 🏷️ ServiceName フィールドの追加

→ 各サービスの JSON ファイルのトップレベル、Name フィールドの直後に ServiceName フィールドが追加

→ サービス識別子 (例: s3) に対応する人間が読みやすい名称 (例: S3) を提供

→ レポート生成やダッシュボード表示など、ユーザー向け出力でのサービス名表記を自動化できる

3. 📊 IsDataPlane プロパティによるデータプレーン分類

→ 各アクションの Annotations.Properties 配下に IsDataPlane プロパティが追加

→ データを操作するアクション (例: S3 の GetObject は true) と、リソース自体を作成・設定・管理するコントロールプレーン操作 (例: S3 の CreateBucket は false) を区別できる

→ 分類はアクションを認可するオペレーションの AWS CloudTrail イベントカテゴリに基づいて導出される

→ 既存の IsList、IsPermissionManagement、IsTaggingOnly、IsWrite プロパティと組み合わせて利用可能

🔧 技術仕様

📡 提供されるエンドポイント

エンドポイント内容
https://servicereference.us-east-1.amazonaws.com/ リファレンス情報が利用可能な AWS サービスの一覧と各 JSON の URL
.../v1/global-condition-keys.json NEW グローバル条件キーの一覧 (今回追加)
.../v1/mapping.json SDK サービス名からサービスリファレンスへのマッピング
.../v1/{service}/{service}.json サービスごとのアクション、リソース、条件キー、オペレーション情報

🏷️ アクションプロパティ (Annotations.Properties)

プロパティ意味
IsDataPlane NEWリソース内のデータやコンテンツを操作するアクション (今回追加)
IsListリソースの一覧や基本メタデータを取得するアクション
IsPermissionManagementIAM 権限やアクセス認証情報を変更できるアクション
IsTaggingOnlyタグのみを変更するアクション
IsWriteリソースを変更できるアクション
⚠️ 注意: これらのプロパティは相互排他ではなく、複数が true になる場合があります。また、IsDataPlane は、アクションを認可するオペレーションのうち少なくとも 1 つに CloudTrail イベントカテゴリが存在する場合にのみ付与されます。プロパティが存在しない場合、そのアクションはまだ分類されていないことを意味します。

🛠️ 設定方法

✅ 前提条件

✓インターネットに接続できる環境 (エンドポイントはパブリックアクセス可能で、認証は不要)
✓JSON を処理できるツール (curl、jq、各種プログラミング言語など)
✓事前の AWS アカウント設定やリソース作成は不要

ステップ 1: グローバル条件キーの一覧を取得する

Bash グローバル条件キーの取得 
curl -s "https://servicereference.us-east-1.amazonaws.com/v1/global-condition-keys.json" | \
    jq '.[] | {Name, Types}'

キー名と値の型を抽出します。ポリシーで使用している条件キーの妥当性チェックや、ポリシー作成支援ツールの補完候補の生成に活用できます。

ステップ 2: ServiceName フィールドを確認する

Bash サービス名の取得 
curl -s "https://servicereference.us-east-1.amazonaws.com/v1/s3/s3.json" | \
    jq '{Name, ServiceName}'

サービス識別子 s3 と人間が読みやすい名称を取得します。レポートやダッシュボードでのサービス名表示に利用できます。

ステップ 3: データプレーン操作のアクションを抽出する

Bash データプレーンアクションの抽出 
curl -s "https://servicereference.us-east-1.amazonaws.com/v1/s3/s3.json" | \
    jq '.Actions[] | select(.Annotations.Properties.IsDataPlane == true) | .Name'

データそのものへのアクセスを許可するアクション (GetObject、DeleteObject など) を抽出します。データアクセス権限の棚卸しや、データプレーン操作を制限するガードレール設計に活用できます。

💡 メリット

💼 ビジネス面

✓ポリシー管理の運用コスト削減: グローバル条件キーやサービス名のマッピングを自前で管理・更新する必要がなくなり、手作業によるメンテナンス工数を削減
✓セキュリティガバナンスの強化: データプレーン操作を機械的に分類でき、データアクセス権限の棚卸しや最小権限の徹底が組織的に進めやすくなる
✓追加コスト不要: サービスリファレンス情報は追加料金なしで利用できる

⚙️ 技術面

✓機械可読な単一ソース: ドキュメントのスクレイピングや手動転記に頼らず、公式の JSON ファイルから正確な情報を自動取得
✓既存ワークフローへの統合が容易: CI/CD パイプラインやポリシー検証ツールに curl と jq だけで組み込める
✓権限分類の精度向上: IsDataPlane は CloudTrail イベントカテゴリに基づくため、独自のヒューリスティックより信頼性の高い分類が可能

⚠️ デメリット・制約事項

🚧 制限事項

✗サービスリファレンス情報への変更が反映されるまで最大 24 時間かかる場合がある
✗IsDataPlane は CloudTrail イベントカテゴリが存在する場合にのみ付与され、存在しないアクションは未分類となる
✗オペレーションからアクションへのマッピング (AuthorizedActions) は未対応のサービスがあり、その場合プロパティが省略される

🤔 考慮すべき点

⚠認可アクション情報には、Forward Access Sessions によって呼び出されるオペレーションに必要な権限は含まれない
⚠Service Authorization Reference (ドキュメントページ) とは表示形式やメタデータが異なる場合がある
⚠アクションプロパティは相互排他ではないため、複数プロパティが true になるケースを考慮した分類ロジックが必要

🎯 ユースケース

1. 🔍 ポリシーリンターでのグローバル条件キー検証

シナリオ: 社内の IAM ポリシー検証パイプラインで、ポリシーに記述された条件キーのタイプミスや廃止されたキーを検出したい。

Bash条件キーの照合リスト生成
# グローバル条件キーの一覧をキャッシュし、ポリシー内の aws: キーを照合
curl -s "https://servicereference.us-east-1.amazonaws.com/v1/global-condition-keys.json" \
    -o /tmp/global-condition-keys.json
jq -r '.[].Name' /tmp/global-condition-keys.json > /tmp/valid-global-keys.txt

効果: デプロイ前に無効な条件キーを自動検出でき、意図しない権限許可 (条件が評価されず常に不一致になるケースなど) を未然に防止できます。

2. 📊 データアクセス権限の棚卸しレポート

シナリオ: セキュリティチームが、各ロールに付与されたアクションのうちデータプレーン操作 (顧客データへの直接アクセス) に該当するものを定期的にレポートしたい。

Bashデータプレーンアクション一覧の生成
# サービスごとにデータプレーンアクションの一覧を生成
for svc in s3 dynamodb; do
  curl -s "https://servicereference.us-east-1.amazonaws.com/v1/${svc}/${svc}.json" | \
    jq -r '.Actions[] | select(.Annotations.Properties.IsDataPlane == true) | "\(input_filename) \(.Name)"'
done

効果: データアクセスに関わる権限を機械的に抽出でき、最小権限の監査やコンプライアンスレポート作成の工数を大幅に削減できます。

3. 🖥️ ダッシュボードでのサービス名表示の自動化

シナリオ: IAM Access Analyzer や独自の権限分析ツールの結果を表示するダッシュボードで、サービスプレフィックス (例: aps) ではなくわかりやすいサービス名を表示したい。

Bash表示名の取得
# サービス識別子から表示名を取得
curl -s "https://servicereference.us-east-1.amazonaws.com/v1/s3/s3.json" | \
    jq -r '.ServiceName'

効果: サービス名マッピングテーブルの自前管理が不要になり、新サービス追加時もダッシュボードが自動的に正しい表示名を取得できます。

💰 料金・利用可能リージョン

💵 料金

サービスリファレンス情報は追加料金なしで利用できます。エンドポイントはパブリックに公開されており、AWS アカウントや認証情報も不要です。

🌍 利用可能リージョン

エンドポイントは servicereference.us-east-1.amazonaws.com でホストされ、インターネット経由でどこからでもアクセス可能です。提供される情報は特定リージョンに依存しないグローバルなメタデータです。

🔗 関連サービス・機能

  • AWS Identity and Access Management (IAM): サービスリファレンス情報は IAM ポリシーの作成・検証・管理の自動化を支援するメタデータを提供する
  • IAM Access Analyzer: 各アクションの SupportedBy フィールドで、Access Analyzer のポリシー生成が対応しているかを確認できる
  • AWS CloudTrail: IsDataPlane の分類は CloudTrail のイベントカテゴリに基づいて導出される
  • AWS Organizations / SCP: データプレーン操作の分類やグローバル条件キーの一覧は、組織全体のガードレール (サービスコントロールポリシー) 設計にも活用できる

📝 まとめ

今回のアップデートにより、IAM ポリシー管理の自動化に必要なグローバル条件キー、サービス名、データプレーン分類という 3 つの重要なメタデータが機械可読な形式で取得できるようになりました。

ポリシー検証ツールや権限監査の仕組みを運用している組織は、自前で管理していたマッピングやヒューリスティックをこの公式データソースに置き換えることを推奨します。まずは global-condition-keys.json と関心のあるサービスの JSON を取得し、既存のポリシー管理ワークフローへの統合を検討してください。
