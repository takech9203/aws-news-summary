AWS Lambda Amazon SQS

⚡ AWS Lambda が SQS FIFO キューで
最大 10,000 メッセージのバッチサイズをサポート

📅 リリース日: 2026 年 11 月 20 日 | プロビジョンドモードのイベントソースマッピングで利用可能

📝 概要

AWS Lambda は、Amazon SQS FIFO キューをイベントソースとするイベントソースマッピング (ESM) において、プロビジョンドモード使用時の最大バッチサイズを従来の 10 メッセージから 10,000 メッセージへと大幅に拡張しました。あわせて、最大 300 秒のバッチウィンドウ (MaximumBatchingWindowInSeconds) を設定できるようになり、大量の順序保証付きメッセージをより少ない呼び出し回数で処理できます。

金融取引、注文処理、在庫更新といった厳密な順序保証と重複排除が求められるワークロードで、メッセージグループ内の順序保証を維持したまま、呼び出し回数の削減とスループット向上を実現します。アプリケーションの再設計は不要で、設定変更のみで対応できます。

❌ Before: アップデート前の課題
  • SQS FIFO の ESM はバッチサイズが最大 10 メッセージに制限
  • 大量メッセージ処理には呼び出し回数を増やす必要があり、呼び出しコストが増加
  • まとめて処理するには独自のバッファリング機構が必要で、運用負荷が高い
✅ After: アップデート後の改善
  • プロビジョンドモードで最大 10,000 メッセージのバッチサイズを設定可能
  • 最大 300 秒のバッチウィンドウでメッセージを蓄積してからまとめて処理
  • メッセージグループごとの順序保証を維持したまま高スループットを実現
  • アプリケーションの再設計や独自バッファリング機構が不要

複数のメッセージグループから届いたメッセージを、プロビジョンドモードの専用イベントポーラーが最大 10,000 メッセージのバッチにまとめて Lambda 関数を呼び出す流れを示しています。各メッセージグループ内の順序は維持されます。

🚀 主要機能

📈 1. 最大バッチサイズの拡張 (10 → 10,000 メッセージ)

プロビジョンドモードの SQS FIFO イベントソースマッピングで最大 10,000 メッセージを設定可能。呼び出し回数が削減され、呼び出しあたりの処理効率とスループットが向上します。バッチサイズが 10 を超える場合は、1 秒以上のバッチウィンドウの設定が必要です。

⏱️ 2. 最大 300 秒のバッチウィンドウ

MaximumBatchingWindowInSeconds を最大 300 秒まで設定可能。バッチウィンドウの満了、呼び出しペイロードサイズ上限への到達、最大バッチサイズへの到達のいずれかの条件を満たすまでメッセージを蓄積してから関数を呼び出します。

🔒 3. メッセージグループ単位の順序保証の維持

SQS は、あるメッセージグループの先行メッセージが処理中 (インフライト) の間、そのグループから追加のメッセージを返しません。このため 1 つのバッチに含まれる同一メッセージグループのメッセージは最大 10 件です。より大きなバッチを構成するには、メッセージを多くのメッセージグループに分散して送信します。

⚡ 4. プロビジョンドモードによる高スループット

専用のイベントポーラーを最小 2 から最大 10,000 まで設定可能。デフォルトモード比で 3 倍高速なスケーリング (毎分最大 1,000 同時実行の増加) と 80 倍の同時実行数 (最大 100,000 同時実行) をサポートします。

🛠️ 設定方法

✅ 前提条件

✓Amazon SQS FIFO キューが作成済みであること
✓Lambda 関数と SQS FIFO キューが同一リージョンに存在すること (アカウントは別でも可)
✓イベントソースマッピングでプロビジョンドモードを有効化すること (バッチサイズ 10 超にはプロビジョンドモードとバッチウィンドウ 1 秒以上が必須)

ステップ 1: プロビジョンドモードを有効化してイベントソースマッピングを作成

Bash AWS CLI - 新規作成 
aws lambda create-event-source-mapping \
    --function-name process-orders \
    --event-source-arn arn:aws:sqs:ap-northeast-1:123456789012:orders.fifo \
    --batch-size 10000 \
    --maximum-batching-window-in-seconds 60 \
    --provisioned-poller-config '{"MinimumPollers": 5, "MaximumPollers": 100}'

バッチサイズ 10,000、バッチウィンドウ 60 秒、プロビジョンドモード (最小ポーラー 5、最大ポーラー 100) のイベントソースマッピングを新規作成します。

ステップ 2: 既存のイベントソースマッピングを更新する場合

Bash AWS CLI - 既存設定の更新 
aws lambda update-event-source-mapping \
    --uuid a1b2c3d4-5678-90ab-cdef-EXAMPLE11111 \
    --batch-size 10000 \
    --maximum-batching-window-in-seconds 60 \
    --provisioned-poller-config '{"MinimumPollers": 5, "MaximumPollers": 100}'

既存のイベントソースマッピングの UUID を指定して、バッチサイズとバッチウィンドウ、プロビジョンドモードの設定を更新します。

ステップ 3: プロビジョンドモードを解除する場合

Bash AWS CLI - プロビジョンドモード解除 
aws lambda update-event-source-mapping \
    --uuid a1b2c3d4-5678-90ab-cdef-EXAMPLE11111 \
    --provisioned-poller-config '{}' \
    --maximum-batching-window-in-seconds 0 \
    --batch-size 10

バッチウィンドウを 0、バッチサイズを 10 以下に戻す操作を、解除前または同一の UpdateEventSourceMapping リクエスト内で行う必要があります。

💡 補足

マネジメントコンソール、AWS SDK、AWS CloudFormation、AWS CDK、AWS SAM でも同様に設定できます。また、Agent Toolkit for AWS を利用すると、Kiro、Claude Code、Codex などのコーディングアシスタント経由での設定も可能です。

⚖️ メリットと制約事項

💼 ビジネス面のメリット

✓コスト効率の向上: 呼び出し回数の削減により呼び出し課金とオーバーヘッドが減少
✓再設計不要: 既存の SQS FIFO + Lambda 構成を変更せず、設定変更のみで対応
✓運用負荷の軽減: 独自のバッファリング機構やメッセージ集約処理の構築・運用が不要

🔧 技術面のメリット

✓スループットの向上: 1 回の呼び出しで最大 10,000 メッセージを処理
✓順序保証の維持: FIFO キューの順序保証と重複排除の特性を維持
✓柔軟なバッチ制御: 最大 300 秒のバッチウィンドウでレイテンシーとスループットのバランスを調整

🚧 制限事項

✗バッチサイズ 10,000 はプロビジョンドモードの SQS FIFO ESM でのみ利用可能 (デフォルトモードは最大 10)
✗バッチサイズ 10 超の場合、1 秒以上のバッチウィンドウが必須
✗1 バッチ内の同一メッセージグループのメッセージは最大 10 件 (多数のグループへの分散が必要)
✗最大同時実行数 (Maximum Concurrency) 設定と併用不可
✗呼び出しペイロード上限 (同期 6 MB) 到達時はバッチサイズ上限前に関数を呼び出し

⚠️ 考慮すべき点

⚠プロビジョンドモードはイベントポーラーに対する追加料金が発生
⚠バッチウィンドウを長くするとレイテンシーが増加するため要件に応じた調整が必要
⚠部分バッチ応答 (ReportBatchItemFailures) の実装が重要
⚠at-least-once 配信のため関数コードの冪等性を確保
⚠関数のタイムアウト・メモリ設定、キューの可視性タイムアウトの見直しが必要

💡 ユースケース

💳 ユースケース 1: 金融取引の順序保証付き一括処理

シナリオ: 証券取引システムで、口座ごとの取引イベントを厳密な順序で処理しつつ、ピーク時には秒間数万件のメッセージを処理する必要がある。

Bash 実装例 
aws lambda create-event-source-mapping \
    --function-name process-trades \
    --event-source-arn arn:aws:sqs:ap-northeast-1:123456789012:trades.fifo \
    --batch-size 10000 \
    --maximum-batching-window-in-seconds 5 \
    --provisioned-poller-config '{"MinimumPollers": 20, "MaximumPollers": 500}' \
    --function-response-types "ReportBatchItemFailures"
✅ 効果: 口座 ID をメッセージグループ ID とすることで口座単位の順序を保証しながら、多数の口座のメッセージを 1 回の呼び出しでまとめて処理し、呼び出し回数とコストを削減できる。
🛒 ユースケース 2: EC サイトの注文処理パイプライン

シナリオ: セール期間中に急増する注文イベントを、注文 ID 単位の順序を維持しながら在庫引当や決済処理に連携する。従来はバッチサイズ 10 の制限により呼び出し回数が膨大になっていた。

Bash 実装例 
aws lambda update-event-source-mapping \
    --uuid a1b2c3d4-5678-90ab-cdef-EXAMPLE11111 \
    --batch-size 5000 \
    --maximum-batching-window-in-seconds 10 \
    --provisioned-poller-config '{"MinimumPollers": 10, "MaximumPollers": 200}'
✅ 効果: 既存アーキテクチャを変更せずに設定変更のみでスループットを向上でき、セールなどのスパイク時もプロビジョンドモードの高速スケーリングで安定した処理を実現できる。
📦 ユースケース 3: 在庫更新イベントの集約処理

シナリオ: 多数の店舗・倉庫から送信される在庫更新イベントを SKU 単位の順序で処理し、データベースへの書き込みをまとめて実行したい。1 件ずつの処理ではデータベース接続のオーバーヘッドが大きい。

Python 部分バッチ応答を使用したバルク書き込み 
def handler(event, context):
    updates = []
    failures = []
    for record in event["Records"]:
        try:
            updates.append(parse_inventory_update(record["body"]))
        except Exception:
            failures.append({"itemIdentifier": record["messageId"]})
    # 最大 10,000 件の更新をまとめてバルク書き込み
    bulk_write_inventory(updates)
    return {"batchItemFailures": failures}
✅ 効果: 大きなバッチをバルク書き込みに活用することで、データベースへの接続回数とトランザクション数を削減し、全体の処理効率を大幅に改善できる。

💰 料金と利用可能リージョン

💵 料金

バッチサイズの拡張自体に追加料金はありませんが、前提となるプロビジョンドモードの利用には、イベントポーラーに対する追加料金が発生します。これに加えて、通常の Lambda 料金 (リクエスト数と実行時間) および Amazon SQS の API リクエスト料金が適用されます。

バッチサイズを大きくすると呼び出し回数が減るためリクエスト課金は削減されますが、1 回あたりの実行時間は長くなる可能性があるため、ワークロードに応じた試算を推奨します。詳細は AWS Lambda 料金ページを参照してください。

すべての AWS 商用リージョンで利用可能です (東京・大阪リージョンを含む)。

🎯 まとめ

SQS FIFO キューと Lambda の組み合わせにおける最大 10 メッセージというバッチサイズの制約が、プロビジョンドモードで最大 10,000 メッセージへと 1,000 倍に拡張され、順序保証を維持したまま高ボリュームワークロードを少ない呼び出し回数で処理できるようになりました。

金融取引や注文処理などの順序保証が必要な大規模ワークロードを運用している場合は、プロビジョンドモードの追加コストと部分バッチ応答の実装を考慮したうえで、バッチサイズとバッチウィンドウの最適化を検討することを推奨します。
