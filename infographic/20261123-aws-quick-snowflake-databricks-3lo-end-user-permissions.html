AWS Quick 📅 2026 年 11 月 23 日リリース

🔐 Snowflake / Databricks 向け 3LO によるアイデンティティ認識型アクセス

Three-legged OAuth (3LO) とエンドユーザー権限のサポートで、クエリをエンドユーザー自身の ID で実行

📋 概要

AWS Quick が Snowflake および Databricks の構造化データソースに対する three-legged OAuth (3LO) と エンドユーザー権限のサポートを発表。Chat、インタラクティブダッシュボード、Apps の利用時に、 クエリはエンドユーザー自身の Snowflake / Databricks の ID で実行されます。

Snowflake や Databricks Unity Catalog で設定済みのガバナンスポリシー (行・列レベルの制御、テーブル / ビューへのアクセス権限) が ソースプラットフォーム側でそのまま適用されるため、Quick 側で同じポリシーを再作成する必要はありません。

3LO では、エンドユーザーが自身の ID で認可を行い、Quick はユーザー単位のトークンを使用してソースプラットフォームにクエリを実行します。 アクセス制御はソースプラットフォーム側で適用されるため、各ユーザーには自分の権限で許可されたデータのみが表示されます。

⚡ 主要機能

🔑 Three-legged OAuth (3LO) によるエンドユーザー認証
Snowflake / Databricks のデータソース作成時に認証方式として 3LO を選択可能。エンドユーザーは自身の OAuth ログインで認証し、クエリは各ユーザー自身の ID で実行。Chat、インタラクティブダッシュボード、Apps のすべての利用体験で適用。
🪪 信頼されたアイデンティティ伝播 Trusted Identity Propagation
データソース作成時にオプションを有効化することで、ユーザー ID がソースシステムに伝播。有効化しない場合は作成者の資格情報が接続に埋め込まれ、全ユーザーが作成者の権限を共有する点に注意。
🛡️ ソースプラットフォーム側でのガバナンス適用
Snowflake のアクセス制御や Databricks Unity Catalog の ACL に基づき、行・列レベルの制限やテーブル / ビューへのアクセスがソース側で適用。Quick 側で RLS / CLS ルールを再作成する必要がなく、ポリシーの二重管理を解消。
🗂️ OAuth クライアントアプリケーションの一元管理
Quick アカウント管理者は、アカウント設定の [Manage OAuth Client Applications] で OAuth クライアントアプリケーションを登録・管理可能。Snowflake 用、Databricks 用をそれぞれ設定できる。

🛠️ 設定方法

前提条件

→AWS Quick アカウントがあり、管理者権限を持つユーザーがアカウント設定を変更できること
→Snowflake / Databricks 側で OAuth クライアントアプリケーション (クライアント ID、シークレット、トークン / 認可エンドポイント) が構成済みであること
→エンドユーザーごとに Snowflake / Databricks のアカウントと適切なアクセス権限が付与されていること
→対象データセットが DirectQuery であること (SPICE データセットは 3LO によるエンドユーザー権限に非対応)

設定手順

1
🛡️ 管理者による OAuth クライアントアプリケーションの登録
Quick コンソールで [Manage Account] → [Security] の [Manage OAuth Client Applications] を選択。[Add OAuth client application] で Config ID、クライアント ID / シークレット、トークン / 認可エンドポイント URL、OAuth スコープなどを入力し、Data source type で SNOWFLAKE または DATABRICKS を選択して保存。
2
📦 作成者による 3LO データソースの作成
[Create Data Source] で Snowflake または Databricks を選択し、認証方式として [3LO] を選択。接続情報を入力 (Databricks の場合はアカウントに関連付けられたメールアドレスも入力) し、[Trusted Identity Propagation] を必ず選択して [Create data source] を実行。
3
👤 エンドユーザーによる認証とダッシュボードの利用
作成者がデータソースとダッシュボードの両方をエンドユーザーに共有。エンドユーザーは Quick にサインインし、[Data Source] ページで自身の Snowflake / Databricks の OAuth ログインで認証して保存。以降、ダッシュボードでは自身の権限で許可されたデータのみが表示される。
⚠️ 重要な注意点
Trusted Identity Propagation を選択しない場合、作成者の資格情報が接続に埋め込まれ、すべてのユーザーが作成者の権限を共有してしまうため注意してください。

💡 メリット

ビジネス面

✓ガバナンスの一元化: 行・列レベルのアクセス制御を Snowflake / Databricks Unity Catalog 側で一元管理でき、二重管理によるポリシー不整合リスクを排除
✓コンプライアンス強化: 誰がどのデータにアクセスしたかがエンドユーザー単位で記録され、監査対応が容易に
✓展開スピードの向上: Quick 側で権限設定を再構築する必要がなく、既存のガバナンス体制のまま分析体験を迅速に全社展開

技術面

✓エンドユーザー単位のクエリ実行: クエリがエンドユーザー自身の ID で実行され、ソースプラットフォームのアクセス制御がそのまま機能
✓設定の簡素化: 管理者が OAuth クライアントアプリケーションを一度登録すれば、作成者はデータソース作成時に 3LO を選択するだけ
✓既存フローとの共存: Databricks の agentic カタログ体験は PAT と 3LO の両方で動作し、3LO によるアイデンティティ強制はオプションかつ追加的な機能

⚠️ デメリット・制約事項

制限事項

✗3LO によるエンドユーザー権限は DirectQuery データセットのみでサポートされ、SPICE データセットでは利用不可
✗データセットを SPICE に切り替えた場合や変換を適用した場合、アイデンティティ強制は適用されない
✗エンドユーザーごとに Snowflake / Databricks のアカウントが必要

考慮すべき点

⚠Trusted Identity Propagation を有効化しないと全ユーザーが作成者の権限を共有してしまうため、設定の確認が重要
⚠エンドユーザーは初回利用時にデータソースページで自身の資格情報による認証が必要。利用開始手順の周知を
⚠DirectQuery 実行のため、ソース側のコンピューティングコスト (Snowflake ウェアハウス、Databricks クラスターなど) とクエリパフォーマンスを考慮
⚠3LO を利用しない場合は、従来どおり PAT などで接続し、Quick 側の RLS / CLS ルールで権限を手動管理することも引き続き可能

🎯 ユースケース

📈 1. 部門別の売上データを単一ダッシュボードで提供
シナリオ: Snowflake に全社の売上データを保持し、行レベルポリシーで営業担当者が自部門のデータのみ参照できるよう制御している企業が、Quick のダッシュボードを全営業部門に展開したい。
手順実装例
1. 管理者が Quick に Snowflake 用 OAuth クライアントアプリケーションを登録
2. データキュレーターが 3LO + Trusted Identity Propagation で
   Snowflake データソースと DirectQuery データセットを作成
3. 単一の売上ダッシュボードを全営業部門に共有
✅ 効果: 部門ごとにダッシュボードやデータセットを複製する必要がなく、Snowflake の行レベルポリシーに基づいて各担当者には自部門のデータのみが表示される。
💬 2. Unity Catalog のガバナンスを活かした自然言語分析
シナリオ: Databricks Unity Catalog で列レベルのマスキングやテーブルアクセス制御を運用している企業が、Quick の Chat 機能による自然言語でのデータ探索を安全に開放したい。
手順実装例
1. 管理者が Databricks 用 OAuth クライアントアプリケーションを登録
2. 3LO 認証のデータソースを作成し、Trusted Identity Propagation を有効化
3. エンドユーザーが自身の Databricks ID で認証し、Chat でデータに質問
✅ 効果: Chat 経由のクエリも各ユーザーの Unity Catalog 権限で実行され、マスキング対象の列や権限のないテーブルが露出するリスクを排除しながら自然言語分析を提供できる。
🔒 3. 機密データを扱う Apps のアクセス制御
シナリオ: 人事・財務などの機密データを扱う業務アプリケーションを Quick の Apps で構築し、閲覧者の役職や所属に応じたデータアクセス制御を実現したい。
手順実装例
1. ソースプラットフォーム側で役職・所属に応じた行・列レベルポリシーを定義
2. 3LO 認証のデータソースを使用して Apps を構築
3. エンドユーザーは自身の ID で認証して Apps を利用
✅ 効果: アプリケーション側で複雑な権限ロジックを実装することなく、ソースプラットフォームのポリシーがそのまま適用された安全な業務アプリケーションを提供できる。

💰 料金・利用可能リージョン

💵 料金
3LO とエンドユーザー権限のサポート自体に追加料金はありません。AWS Quick の利用料金に加えて、DirectQuery の実行に伴う Snowflake / Databricks 側のコンピューティング料金が発生します。詳細は AWS Quick の料金ページを参照してください。
🌍 利用可能リージョン
AWS Quick が利用可能なすべてのリージョンで利用できます。最新のリージョン一覧は Quick のリージョンに関するドキュメントを参照してください。

🔗 関連サービス・機能

→Snowflake: AWS パートナーのデータクラウドプラットフォーム。行・列レベルのアクセス制御を含むガバナンスポリシーが 3LO 経由でそのまま適用される
→Databricks Unity Catalog: Databricks の統合ガバナンスソリューション。ACL に基づくテーブルアクセスやデータフィルターが Quick のエンドユーザーに適用される
→AWS Secrets Manager: OAuth クライアント資格情報 (2LO) を使用する場合の資格情報の保管に利用
→Amazon VPC: VPC 内の Snowflake / Databricks や IdP への接続には VPC 接続 ARN を設定可能

📝 まとめ

AWS Quick の 3LO サポートにより、Snowflake / Databricks Unity Catalog で定義済みのガバナンスポリシーをそのまま活かした エンドユーザー単位のアクセス制御が実現しました。権限管理の二重化を解消しながら、 Chat・ダッシュボード・Apps を安全に全社展開できます。

Snowflake や Databricks をデータ基盤として利用している組織は、OAuth クライアントアプリケーションの登録と DirectQuery データセットでの 3LO 設定を検討することを推奨します。
