AWS Network Firewall

🛡️ 次世代ファイアウォール (NGFW) ポリシーを発表

📅 リリース日: 2026 年 11 月 10 日 | 新リソースタイプ FirewallPolicyV2 でアクセス制御と脅威検知をレイヤー分離

📝 概要

AWS Network Firewall が新しいポリシーモデル 次世代ファイアウォール (NGFW) ポリシーを発表。 よりシンプルなポリシー構造と拡張されたルールキャパシティにより、Amazon VPC を保護するアクセス制御と脅威検知の管理が容易になります。

NGFW ポリシーは Classic ポリシーとは別のリソースタイプ (FirewallPolicyV2) として提供され、 アクセス制御を担うファイアウォールエンジンと、侵入検知・防御を担うIPS エンジンの 2 つの独立したインスペクションエンジンに保護を分離します。既存の Classic ポリシーはそのまま動作し、IPS ルールは後方互換性が維持されます。 AWS は新規のファイアウォールには NGFW ポリシーの利用を推奨しています。

😣 Before: アップデート前の課題
  • アクセス制御ルールと脅威検知ルールを同じステートフルルールエンジン内で混在管理する必要があり、ポリシー構造が複雑化しやすい
  • ファイアウォールルールと IPS ルールが同じキャパシティを共有し、一方を増やすと他方を削る必要があった
  • 共有しないルールでも、ルールグループ作成時に事前のキャパシティ割り当てが必要だった
😀 After: アップデート後の改善
  • ファイアウォール保護と IPS 保護がレイヤーとして分離され、ポリシー管理が容易に
  • それぞれ専用のキャパシティを持ち、キャパシティのトレードオフが不要に
  • 共有しないルールは埋め込みルールグループとして定義でき、事前割り当てなしでオンデマンドにキャパシティを利用可能に
  • すべてのルールがステートフルに評価され、完全なコネクションコンテキストに基づく一貫したトラフィック処理を実現

デフォルト拒否のファイアウォールエンジンでアクセス制御を行い、 通過を許可されたトラフィックに対してデフォルト許可のIPS エンジンで脅威検知・防御を行う 2 層構造です。

⚡ 主要機能

🧱 1. レイヤー化された保護構造
ファイアウォール保護 (アクセス制御) と IPS 保護 (脅威検知・防御) を別々のレイヤーとして定義。 ファイアウォールエンジンはデフォルト拒否で未許可トラフィックをブロックし、IPS エンジンはデフォルト許可でルールに一致した既知の脅威を検知・ブロック。 役割が明確に分離され、ポリシーの意図が読み取りやすくなります。
🚫 2. デフォルト拒否のアクセス制御
承認済みトラフィックのみを許可するファイアウォールルールを記述可能。承認済みドメインへのトラフィックのみ許可する構成など、 FQDN やプロトコルコンテキストに基づく制御に対応します。
🔍 3. IPS ルールの柔軟な選択肢
AWS 提供のマネージドルールグループや AWS Marketplace パートナーのルールグループを利用可能。 マネージドルールグループは新しい脅威の出現に応じて自動更新され、カスタム IPS ルールグループの作成にも対応します。
📊 4. 独立したルールキャパシティ
ファイアウォールルールと IPS ルールがそれぞれ専用のキャパシティを保持。 従来のようにアクセス制御ルールと IPS ルールでキャパシティをトレードオフする必要がありません。
📦 5. 埋め込みルールグループ (インラインルール)
ポリシー間で共有しないルールは、ポリシー内に直接記述する埋め込みルールグループとして定義可能。 事前のキャパシティ割り当てが不要で、オンデマンドにキャパシティを利用できます。
🔄 6. ステートフルな評価
NGFW ポリシー配下のすべてのルールはステートフルで、完全なコネクションコンテキストに基づいて評価。 ステートレスルールグループは使用せず、一貫したトラフィック処理を実現します。

🔧 技術仕様: Classic ポリシーと NGFW ポリシーの比較

項目 Classic ポリシー NGFW ポリシー
リソースタイプ FirewallPolicy FirewallPolicyV2
エンジン構成 ステートレスエンジン + ステートフルエンジン ファイアウォールエンジン + IPS エンジン
デフォルト動作 エンジン単位で設定 ファイアウォールエンジンはデフォルト拒否、IPS エンジンはデフォルト許可
ルールキャパシティ ルールグループ単位で事前割り当て エンジンごとに独立、埋め込みルールはオンデマンド
ルール評価 ステートレス / ステートフル混在 すべてステートフル
既存ポリシーへの影響 引き続き完全サポート 新規ファイアウォールに推奨

⚠️ 1 つのファイアウォールには Classic ポリシーまたは NGFW ポリシーのいずれか一方のみを関連付けできます。

🛠️ 設定方法

前提条件

✓AWS Network Firewall を利用できる AWS アカウント
✓Network Firewall のポリシー・ルールグループ操作権限を持つ IAM プリンシパル
✓ファイアウォールエンドポイントを配置する VPC とサブネット
1
NGFW ポリシーの作成
Bash create-firewall-policy-v2 
aws network-firewall create-firewall-policy-v2 \
  --firewall-policy-v2-name my-ngfw-policy \
  --firewall-policy-v2 '{
    "FirewallRuleGroupEntries": [
      {
        "Priority": 10,
        "ResourceArn": "arn:aws:network-firewall:ap-northeast-1:123456789012:firewall-rule-group/allow-approved-domains"
      }
    ],
    "IPSRuleGroupEntries": [
      {
        "Priority": 10,
        "ResourceArn": "arn:aws:network-firewall:ap-northeast-1:123456789012:ips-rule-group/managed-threat-rules"
      }
    ]
  }'

ファイアウォールセクション (アクセス制御) と IPS セクション (脅威検知) にそれぞれルールグループを優先度付きで登録します。 共有不要なルールは InlineRuleGroup として埋め込みルールを直接記述することもできます。

2
ポリシーの確認
Bash describe-firewall-policy-v2 
aws network-firewall describe-firewall-policy-v2 \
  --firewall-policy-v2-name my-ngfw-policy

登録されたルールグループ、デフォルトアクション、ポリシーモードなどを確認します。

3
ファイアウォールへの関連付け

作成した NGFW ポリシーをファイアウォールエンドポイントまたはファイアウォールエンドポイント関連付けに関連付けます。 1 つのファイアウォールに関連付けできるのは Classic ポリシーまたは NGFW ポリシーのいずれか一方のみである点に注意してください。

💡 メリット

💼 ビジネス面
✓追加料金なし: 既存の Network Firewall の料金体系のまま新しいポリシーモデルの利点を得られる
✓運用コストの削減: アクセス制御と脅威検知の分離により、ポリシーのレビューや監査が容易になり、セキュリティ運用の工数を削減
✓段階的な移行が可能: Classic ポリシーは引き続き完全サポートされ、業務影響なく計画的に移行できる
⚙️ 技術面
✓明確な責務分離: デフォルト拒否のファイアウォールエンジンとデフォルト許可の IPS エンジンにより、各レイヤーの役割と期待される動作が明確に
✓キャパシティ管理の簡素化: 独立したキャパシティとオンデマンドの埋め込みルールにより、事前のキャパシティ設計の負担を軽減
✓一貫したステートフル評価: ステートレス・ステートフル混在による評価順序の複雑さがなくなる

⚠️ デメリット・制約事項

🚧 制限事項
✗1 つのファイアウォールに関連付けできるのは Classic ポリシーまたは NGFW ポリシーのいずれか一方のみ
✗ステートレスルールグループを使用しないため、ステートレスルールに依存した既存構成はそのまま移行できない
✗既存ポリシーの設定を自動で変換する仕組みは発表内容には含まれていない
🤔 考慮すべき点
⚠新規ファイアウォールには NGFW ポリシーが推奨されるため、今後の設計標準として NGFW ポリシーを前提にすることを検討
⚠Classic ポリシーからの移行では、ステートレスルールの扱いやルール評価順序の違いを事前に検証する必要がある
⚠IaC (CloudFormation、Terraform など) のテンプレートは新しいリソースタイプへの対応状況を確認する必要がある

🎯 ユースケース

🌐 1. 承認済みドメインのみへのアウトバウンド通信許可

シナリオ: 社内ワークロードからインターネットへのアウトバウンド通信を、業務上承認されたドメインのみに制限したい。

実装: ファイアウォールセクション (デフォルト拒否) に承認済みドメインリストへの HTTPS 通信を許可するルールを登録。その他のアウトバウンド通信はデフォルトでドロップ。

✅ 効果: デフォルト拒否のファイアウォールエンジンにより、許可リスト方式のアクセス制御をシンプルに実現でき、意図しない外部通信を防止。
🛡️ 2. マネージドルールによる脅威防御の自動更新

シナリオ: 既知の脆弱性や脅威に対する防御を、運用負荷をかけずに常に最新の状態に保ちたい。

実装: IPS セクション (デフォルト許可) に AWS マネージド IPS ルールグループを登録。必要に応じて AWS Marketplace パートナーのルールグループを追加。

✅ 効果: マネージドルールグループは新しい脅威の出現に応じて自動更新されるため、シグネチャ管理の運用負荷なしに最新の脅威防御を維持。
📊 3. アクセス制御と IPS のキャパシティ競合の解消

シナリオ: Classic ポリシーでアクセス制御ルールと IPS ルールが同じキャパシティを共有しており、ルール追加のたびにキャパシティ調整が必要。

実装: NGFW ポリシーへ移行し、アクセス制御ルールをファイアウォールセクション、IPS ルールを IPS セクションへ配置。ポリシー固有のルールは埋め込みルールグループとして定義。

✅ 効果: 独立したキャパシティにより一方のルール追加が他方を圧迫することがなくなり、埋め込みルールは事前割り当てなしで利用可能。

📌 まとめ

NGFW ポリシーは、アクセス制御と脅威検知をレイヤーとして分離し、 独立したルールキャパシティと埋め込みルールグループにより ポリシー管理を大幅に簡素化するアップデートです。追加料金なしで全商用リージョンと GovCloud (US) で利用でき、 既存の Classic ポリシーも引き続きサポートされます。

✓新規のファイアウォール構築では NGFW ポリシーの採用を検討
✓既存環境ではステートレスルールの扱いを含めた移行計画の策定を推奨
