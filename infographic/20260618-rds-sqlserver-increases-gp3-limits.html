プロビジョンドパフォーマンスを大幅拡張

📅 リリース日
2026 年 6 月 18 日

📌 概要

Amazon RDS for SQL Server は、General Purpose (gp3) ストレージのボリュームレベル上限を大幅に引き上げました。1 つの gp3 ボリュームで 最大 64 TiB / 80,000 IOPS / 2,000 MiB/s までスケールできるようになり、高スループット OLTP や大規模分析など I/O 要件の厳しいワークロードを単一ボリュームで高性能に運用できます。

さらに追加ストレージボリュームを構成すると、DB インスタンスあたり最大 3 つの gp3 / io2 ボリュームを追加でき、インスタンス合計容量を 最大 256 TiB まで拡張可能です。料金体系に変更はなく、追加コストなしで上限拡張の恩恵を受けられます。

⚖️ アップデート前後の比較

⛔ Before（従来の課題）

  • 1 ボリューム最大 16 TiB で大規模 DB に容量不足
  • プロビジョンド IOPS は最大 16,000 IOPS でボトルネック
  • スループットは最大 1,000 MiB/s に制限

✅ After（改善後）

  • 1 ボリューム最大 64 TiB（4 倍）までスケール
  • 最大 80,000 IOPS（5 倍）をプロビジョニング可能
  • 最大 2,000 MiB/s（2 倍）のスループット
  • 単一ボリュームで完結しストレージ管理がシンプルに

🚀 主要機能

① ボリュームサイズの拡張

1 つの gp3 ボリュームを最大 64 TiB（従来 16 TiB の 4 倍）までスケール可能。単一ボリュームで大規模データベースを格納でき、ストレージ構成がシンプルになります。

② プロビジョンド IOPS の引き上げ

1 ボリュームで最大 80,000 IOPS（従来 16,000 の 5 倍）。高スループットの OLTP システムなど、I/O 要件の厳しいワークロードに対応します。

③ スループットの引き上げ

1 ボリュームで最大 2,000 MiB/s（従来 1,000 の 2 倍）。大規模分析ワークロードのシーケンシャル I/O 性能を強化します。

④ 追加ストレージボリュームとの組み合わせ

DB インスタンスあたり最大 3 つの gp3 / io2 ボリュームを追加でき、合計 最大 256 TiB まで拡張可能。gp3 と io2 を混在させ、コストとパフォーマンスを最適化できます。

⚙️ 設定方法

前提条件

✓Amazon RDS for SQL Server の DB インスタンスを利用していること
✓ストレージタイプが gp3 であること
✓プロビジョニングする IOPS・スループットを活用できる DB インスタンスクラスを選択していること

ステップ 1: 既存インスタンスのストレージを変更する

既存インスタンスを 32 TiB（32,768 GiB）に拡張し、40,000 IOPS / 1,500 MiB/s に設定。--apply-immediately で即時適用します。

Bashmodify-db-instance
aws rds modify-db-instance \
    --db-instance-identifier my-sqlserver-instance \
    --allocated-storage 32768 \
    --storage-type gp3 \
    --iops 40000 \
    --storage-throughput 1500 \
    --apply-immediately

ステップ 2: 新規インスタンス作成時に高性能 gp3 を指定する

64 TiB（65,536 GiB）の gp3 に最大値の 80,000 IOPS / 2,000 MiB/s をプロビジョニングした新規インスタンスを作成します。

Bashcreate-db-instance
aws rds create-db-instance \
    --db-instance-identifier new-sqlserver-instance \
    --engine sqlserver-se \
    --db-instance-class db.r6i.4xlarge \
    --allocated-storage 65536 \
    --storage-type gp3 \
    --iops 80000 \
    --storage-throughput 2000 \
    --master-username admin \
    --master-user-password <パスワード>

ステップ 3: 追加ストレージボリュームを構成する

合計容量を 256 TiB まで拡張する場合は、RDS マネジメントコンソールまたは CLI から追加ストレージボリューム（最大 3 つの gp3 / io2）を構成します。各ボリュームに個別にストレージタイプ・サイズ・性能を設定でき、アクセス頻度の高いデータと低いデータを使い分けられます。

💡 メリット

🏢 ビジネス面

✓大規模ワークロードの集約: 単一インスタンスで最大 256 TiB を扱え、分割やシャーディングの必要性を低減
✓コスト効率: ベースラインを超えた分のみ課金され、要件に応じた最適なコスト配分が可能
✓料金変更なし: 追加コストなしで上限拡張の恩恵を受けられる

🛠️ 技術面

✓性能スケーラビリティ: 単一ボリュームで最大 80,000 IOPS / 2,000 MiB/s を確保
✓管理の簡素化: 大容量を単一ボリュームで構成でき、分割による複雑さを軽減
✓柔軟な構成: 追加ボリュームで gp3 と io2 を混在でき、アクセスパターンに応じて最適化

⚠️ デメリット・制約事項

制限事項

!プロビジョニングした IOPS・スループットは、インスタンスクラスのネットワーク帯域や EBS 最適化上限を超えて利用できない
!インスタンスクラスの上限が低い場合、性能をフル活用できない可能性がある
!性能を最大限引き出すには、十分な帯域と IOPS をサポートする現行世代インスタンスクラスの選択が必要

考慮すべき点

!ストレージタイプ・性能を変更するとボリュームが optimizing 状態となり、変更中は性能が一時的に変動する場合がある
!1 → 複数ボリュームへの変更では、移行に大量の IOPS・スループットを消費し時間を要することがある
!IOPS とストレージ（GiB）の比率には制約があるため、事前に要件を確認する

🎯 ユースケース

① 高スループット OLTP システム

シナリオ: 大量トランザクションを処理する基幹業務システムで、従来の 16,000 IOPS 上限がボトルネックになっていた。

実装例: gp3 / 80,000 IOPS / 2,000 MiB/s

→ 効果: 単一ボリュームで従来の 5 倍の IOPS を確保し、トランザクション処理のレイテンシーとスループットを改善。

② 大規模分析ワークロード

シナリオ: 数十 TiB 規模のデータウェアハウスを、複数ボリュームに分割せず単一インスタンスで運用したい。

実装例: プライマリ gp3 64 TiB + 追加 gp3 / io2 最大 3 つ（合計最大 256 TiB）

→ 効果: ストレージ分割の管理オーバーヘッドを抑えつつ、大規模データセットを単一インスタンスで保持。

③ コストとパフォーマンスの両立

シナリオ: アクセス頻度の高いデータとアーカイブ用コールドデータを同一インスタンスで管理したい。

実装例: プライマリ + 追加 1 = io2（高頻度）/ 追加 2・3 = gp3（アーカイブ）

→ 効果: ホットデータを高性能 io2、コールドデータをコスト効率の高い gp3 に配置し最適化。

💰 料金・利用可能リージョン

💴 料金

今回のアップデートに伴う料金体系の変更はありません。プロビジョニングしたストレージ容量と、ベースライン（3,000 IOPS / 125 MiB/s）を超えてプロビジョニングした追加 IOPS およびスループットに対してのみ料金を支払います。

🌐 利用可能リージョン

リージョンごとの提供状況については、Amazon RDS for SQL Server の料金ページを参照してください。

🔗 関連サービス・機能

→Amazon EBS (gp3 / io2): RDS のストレージ基盤となるブロックストレージ。今回拡張されたのは gp3 ボリュームの上限
→Amazon RDS 追加ストレージボリューム: SQL Server / Oracle で最大 3 つの追加ボリュームを構成し合計容量を拡張する機能
→Amazon RDS ストレージ自動スケーリング: 容量を需要に応じて自動拡張。IOPS とストレージ容量の比率制約が同様に適用される

✅ まとめ

このアップデートにより、Amazon RDS for SQL Server の gp3 ボリュームは単一ボリュームで 最大 64 TiB / 80,000 IOPS / 2,000 MiB/s までスケールでき、追加ストレージボリュームと組み合わせてインスタンスあたり 最大 256 TiB を実現できます。料金変更なしで大規模かつ I/O 集約型の SQL Server ワークロードに対応できるため、性能不足やストレージ分割に課題を抱えている場合は、対象インスタンスのストレージ構成の見直しを検討することをお勧めします。
