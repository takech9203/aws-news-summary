AWS Deadline Cloud

🎬 Deadline Cloud モニターで
アクセス可能リソースを直接検索・表示

リリース日: 2026 年 10 月 13 日 | スコープ付きユーザーのセルフサービスリソース検出

📝 概要

AWS Deadline Cloud は、Deadline Cloud モニターでユーザーが自身のアクセス可能なリソースを直接検索・表示できる機能を発表しました。特定のキュー、フリート、ジョブのみにスコープされたアクセス権を持つユーザーが、管理者に問い合わせることなく利用できるリソースを発見できます。

モニターは、アクセスできるキュー、到達に必要な親リソースの ID、およびアクセスレベルを表示します。直接付与された権限と、グループメンバーシップから継承された権限の両方をカバーします。

❌ アップデート前の課題

  • 特定キューのみアクセス可能なユーザーは、モニター接続のために管理者からファーム ID を取得する必要があった
  • どのリソースにどのレベルでアクセスできるかをモニター上で確認する手段がなかった
  • 権限レベルが異なるメンバーごとに接続情報を個別に案内する必要があり、オンボーディングに手間がかかっていた

✅ アップデート後の改善

  • モニターから直接、アクセスできるキュー、親リソースの ID、アクセスレベルを確認できる
  • 直接付与とグループ継承の両方の権限が表示され、権限の由来を問わずリソースを発見できる
  • 権限レベルの違いに関係なく、単一のモニター URL を共有するだけで全メンバーが利用を開始できる

スコープされた権限を持つユーザーがモニターにサインインすると、新しい ListMemberships API を通じてアクセス可能なリソースが自動的に検出され、ファーム ID を事前に知らなくても目的のキューに到達できます。

⚡ 主要機能

🔍 1. アクセス可能リソースの自動検出

  • モニターがユーザーのアクセスできるキューを一覧表示
  • キューに到達するために必要な親リソース (ファーム) の ID も合わせて表示され、管理者への問い合わせが不要に
  • 各リソースに対するアクセスレベルも確認可能

👥 2. 直接権限とグループ継承権限の両対応

  • リソースに直接追加されたユーザーの権限を表示
  • AWS IAM Identity Center のグループメンバーシップを通じて継承された権限も表示
  • 権限の付与経路に関係なく、同じ方法でリソースを発見できる

🔗 3. 単一モニター URL でのチーム運用

  • 権限レベルが異なるメンバーが混在するチームでも、同じモニター URL を共有できる
  • 各ユーザーには自身がアクセスできるリソースのみが表示される
  • オンボーディング時の個別の接続情報の案内が不要に

🛠️ 4. 管理者向けのリソースアクセス管理との連携

  • コンソールの「User management」の「Resource access」タブで、全リージョンにわたるファーム、キュー、フリートへのアクセスを確認可能
  • 同じタブからアクセスレベルの変更やアクセスの取り消しも可能
  • 「Granted through」列により、直接付与かグループ継承かを判別できる

🔧 設定方法

前提条件

1AWS Deadline Cloud のファーム、キュー、フリートが作成済みであること
2ユーザーが AWS IAM Identity Center で管理され、ファーム、キュー、フリートのいずれかに直接またはグループ経由でアクセス権が付与されていること
3Deadline Cloud モニターの URL がチームに共有されていること

手順

1

ユーザーにリソースへのアクセス権を付与する (管理者)

Deadline Cloud コンソールで対象のファーム、キュー、またはフリートを開き、ユーザーまたはグループにアクセスレベル (VIEWER、CONTRIBUTOR、MANAGER、OWNER) を割り当てます。グループに付与した場合、グループ所属ユーザーに権限が継承されます。

2

ユーザーがモニターにサインインする

ユーザーは共有されたモニター URL にアクセスし、IAM Identity Center の認証情報でサインインします。ファーム ID を事前に知る必要はありません。

3

アクセス可能なリソースを確認する

サインイン後、モニターにアクセス可能なキューの一覧、到達に必要な親リソースの ID、およびアクセスレベルが表示されます。ユーザーは目的のキューを選択し、ジョブの投入や監視を開始できます。

4

管理者がリソースアクセスを確認・変更する (必要に応じて)

管理者は左ナビゲーションから「User management」を選択し、「Groups」または「Users」タブで対象を選択後、「Resource access」タブを開きます。ここでアクセスレベルの変更やアクセスの取り消しが可能です。ファームへのアクセスを取り消すと、内部のキューとフリートへのアクセスも取り消されます。

💡 メリット

💼 ビジネス面

  • オンボーディングの迅速化: 接続情報の個別案内が不要になり、プロジェクト参加までの時間を短縮
  • 運用負荷の削減: 「どのファーム ID に接続すればよいか」という問い合わせがなくなり、サポートコストを削減
  • チーム運用の簡素化: 単一のモニター URL の共有だけで済み、ドキュメント管理が容易に

⚙️ 技術面

  • セルフサービスのリソース検出: ListMemberships API により、プログラムからもメンバーシップを検出可能
  • 最小権限の原則との両立: キュー単位の細かい権限設計を維持したまま、ユーザビリティを損なわないアクセス導線を提供
  • 権限の可視性向上: 直接付与とグループ継承の両方が表示され、アクセス権の全体像を把握しやすい

⚠️ デメリット・制約事項

🚧 制限事項

  • ジョブへのアクセス権はジョブの投入によって付与されるため、「Resource access」タブからは編集できない
  • グループから継承された権限はユーザー個別には変更できず、グループ側の変更または ID ソースでの所属変更が必要
  • アカウントポリシーでブロックされているリージョンの情報は確認できない (確認できないリージョンはタブ上に明示される)

🤔 考慮すべき点

  • 本機能はアクセス権の「発見」を容易にするものであり、権限自体を変更するものではない。権限管理は引き続き管理者側の設計が重要
  • グループ経由の権限継承を活用する場合、IAM Identity Center 側のグループ設計とライフサイクル管理の整備が必要

🎯 ユースケース

🎨 ユースケース 1: 外部協力アーティストのオンボーディング

シナリオ: VFX スタジオが外部の協力アーティストをプロジェクトに迎え、特定のキューのみに CONTRIBUTOR 権限を付与する。

  1. 管理者が対象キューで外部アーティストのグループに CONTRIBUTOR を割り当て
  2. チーム共通のモニター URL を案内
  3. アーティストはサインインするだけでアクセス可能なキューを発見し、ジョブを投入

✅ 効果: ファーム ID の個別案内が不要になり、外部メンバーの参加当日からレンダージョブの投入を開始できる。

🔄 ユースケース 2: 複数プロジェクトを横断するアーティストの作業切り替え

シナリオ: 複数のプロジェクト (キュー) にまたがってアサインされているアーティストが、担当するキューを自分で確認して作業を切り替える。

  1. アーティストがモニターにサインイン
  2. アクセス可能なキューの一覧と各キューのアクセスレベルを確認
  3. 作業対象のキューを選択してジョブのステータスを監視・投入

✅ 効果: プロジェクトごとの接続情報を管理する手間がなくなり、担当キューの確認と切り替えがモニター上で完結する。

📋 ユースケース 3: 管理者による権限の棚卸し

シナリオ: 管理者が四半期ごとにユーザーとグループのリソースアクセスを棚卸しし、不要な権限を取り消す。

  1. Deadline Cloud コンソールの User management を開く
  2. 対象ユーザーまたはグループの Resource access タブで全リージョンの権限を確認
  3. Granted through 列で直接付与の権限を特定し、不要なものを Revoke access で取り消し

✅ 効果: 全リージョンにわたる権限の全体像を 1 つのタブで確認でき、最小権限の維持とコンプライアンス対応が容易になる。

💰 料金

この機能自体に追加料金はありません。AWS Deadline Cloud の利用料金は、使用したコンピューティングリソース (フリートのワーカー) と使用ベースライセンスなどに基づく従量課金です。

🌍 利用可能リージョン

AWS Deadline Cloud が利用可能なすべての AWS リージョンで利用できます。

📌 まとめ

今回のアップデートにより、スコープされた権限を持つユーザーがファーム ID を知らなくても Deadline Cloud モニターから自分のリソースを発見できるようになり、レンダーファーム運用のオンボーディングと日常業務が大幅に簡素化されます。キュー単位の最小権限設計を採用しているチームは、単一のモニター URL への移行と、新しい ListMemberships API を活用したワークフローの見直しを検討することを推奨します。
