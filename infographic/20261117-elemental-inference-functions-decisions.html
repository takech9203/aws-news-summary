AWS Elemental Inference

🎬 Functions と Customer Decisions でライブ映像分析をカスタマイズ

カスタムモデル・プロンプト・決定による独自分析を同一パイプラインで実現 | リリース日: 2026 年 11 月 17 日

📋 概要

AWS Elemental Inference で、ライブ映像の分析方法を 2 つの方法でカスタマイズできるようになりました。 どちらも縦型動画作成 (スマートクロップ) やスマート字幕などの組み込み機能と同じパイプライン上で動作し、 結果は既存の GetMetadata API から取得できます。別のパイプラインを構築する必要はありません。

🏷️ Customer Decisions

コンテキストメタデータのカスタム決定

yes/no 質問や「1 つを選ぶ」カテゴリを Question Set として定義するだけで、シーンごとの判定結果と信頼度スコアを取得。

→ モデル選択・プロンプト記述は不要

🧩 Functions

カスタム分析

Amazon Bedrock のマルチモーダル基盤モデルと JSONata 式を指定して、映像に対する独自の質問 (カスタムプロンプト) を実行。

→ オープンエンドな回答・カスタム形式に対応

❌ アップデート前の課題
  • コンテキストメタデータの分類は IAB カテゴリ、GARM レーティング、ラベル、ムードなどの組み込みフィールドに限定され、独自の分類基準を追加できなかった
  • 独自の AI 分析 (スポンサーロゴ露出の測定など) には、取り込み・フレーム抽出・モデル呼び出し・結果統合を含む独自パイプラインが別途必要だった
  • 組み込み機能と独自分析の結果が別々の場所に出力され、タイムライン上での統合が困難だった
✅ アップデート後の改善
  • Question Set に yes/no 質問や「1 つを選ぶ」カテゴリを定義するだけで、独自の判定と信頼度スコアをシーンごとに取得可能に
  • Functions により、Bedrock モデルと JSONata 式を指定するだけで独自分析を同一パイプライン上で実行可能に
  • 組み込み機能と独自分析の結果が同じメタデータタイムラインに書き込まれ、GetMetadata API だけで一括取得可能に

組み込み機能、Question Set による決定、Functions によるカスタム分析がすべて同じパイプライン上で動作し、結果は単一のメタデータタイムラインに統合されて GetMetadata API から取得できます。

⚡ 主要機能

🏷️ 1. Customer Decisions (コンテキストメタデータ決定)
  • yes/no 質問 (例: 「このシーンは天気予報か」) や「1 つを選ぶ」カテゴリ (例: ジャンル分類) を Question Set として定義
  • 各シーンに対して、定義したすべてのラベルと質問について判定結果と信頼度スコアが返される
  • 標準の IAB カテゴリ、GARM レーティング、ムードフィールドと並んで customQuestions オブジェクトとして返され、信頼度がしきい値を満たした時点でワークフローをトリガー可能
  • モデルの選択やプロンプトの記述は不要
  • Question Set は DRAFT の更新とバージョン発行によって管理し、フィードの customQuestions 設定で参照
🧩 2. Functions (カスタム分析)
  • Amazon Bedrock モデルと、リクエスト/レスポンスを整形する JSONata 式を指定して関数を定義
  • 関数をフィードにアタッチし、実行頻度を選択。1 つの関数を同一アカウント内の複数のフィードにアタッチ可能
  • モデルはユーザー自身のアカウント内でユーザーが制御するロールの下で実行され、モデル選択・アクセス許可・スループットクォータを自身で管理
  • オープンエンドな回答、カスタムレスポンス形式、コンテキストメタデータでカバーされない分析 (スポンサーロゴ露出の測定など) に最適
  • パススルー関数: モデルを呼び出さず、生成済みメタデータを独自スキーマに整形するだけの関数も定義可能 (モデルコストなし)
🔗 3. 既存パイプラインとの統合
  • どちらの機能も縦型動画作成やスマート字幕などの組み込み機能と同じパイプラインで動作
  • 結果は同じメタデータタイムラインに書き込まれ、既存の GetMetadata API で取得可能
  • 障害の分離: 関数が失敗してもフィードの他の出力は正常に継続し、該当ウィンドウの関数メタデータが存在しないだけで済む

❓ Question Set の質問タイプ

JSON Question Set の定義例 
{
  "name": "my-question-set",
  "yesNo": [
    {
      "name": "is-weather-report",
      "question": "Is this scene a weather report?"
    }
  ],
  "chooseOne": [
    {
      "name": "genre",
      "question": "What is the genre of this scene?",
      "options": [
        { "name": "news", "text": "News" },
        { "name": "sports", "text": "Sports" },
        { "name": "drama", "text": "Drama" }
      ]
    }
  ]
}

CreateQuestionSet API では、yes/no 質問 (yesNo)、選択肢ごとの yes/no 判定 (yesNoPerOption)、単一選択 (chooseOne) の 3 種類の質問タイプを定義できます。

🛠️ 設定方法

✅ 前提条件

✓AWS Elemental Inference のフィードが作成済みであること
✓Customer Decisions を使用する場合、フィードでコンテキストメタデータ出力が有効であること
✓Functions でモデルを呼び出す場合、Amazon Bedrock で使用するモデルへのアクセスが有効化されており、Elemental Inference がモデルを呼び出すための IAM ロールが用意されていること
1
Question Set の作成 (Customer Decisions の場合)
Bash Question Set の作成 
aws elemental-inference create-question-set \
  --name "my-decisions" \
  --yes-no '[{"name": "is-weather-report", "question": "Is this scene a weather report?"}]' \
  --choose-one '[{"name": "genre", "question": "What is the genre?", "options": [{"name": "news", "text": "News"}, {"name": "sports", "text": "Sports"}]}]'

yes/no 質問と単一選択カテゴリを含む Question Set を作成します。作成後、CreateQuestionSetVersion でバージョンを発行し、フィードの customQuestions 設定から参照します。

2
Function の作成 (Functions の場合)
Bash Function の作成 
aws elemental-inference create-function \
  --name "sponsor-logo-exposure" \
  --cli-input-json file://function-definition.json

Amazon Bedrock モデルの指定と、リクエスト/レスポンスを整形する JSONata 式を含む関数定義から関数を作成します。作成した関数はフィードにアタッチし、実行頻度を選択します。

3
GetMetadata API で結果を取得
Bash メタデータの取得 
aws elemental-inference get-metadata \
  --feed-id "my-feed-id"

組み込み機能のメタデータと同じタイムラインから、Customer Decisions の判定結果 (customQuestions オブジェクト) と Functions の分析結果を取得します。信頼度スコアがしきい値を満たした場合に後続ワークフローを実行する、といった制御が可能です。

👍 メリット

💼 ビジネス面

✓独自分析の迅速な実現: スポンサーロゴ露出の測定や自社基準のコンテンツ分類など、ビジネス固有の分析要件を専用パイプラインの構築なしで実現できる
✓広告ターゲティングの精緻化: IAB や GARM などの標準分類に加えて、自社定義のカテゴリや判定でシーンを分類し、コンテキスト広告の精度を高められる
✓コスト効率: Functions 自体は追加料金なしで利用でき、パススルー関数ならモデルコストもかからないため、小さく始めて拡張できる

⚙️ 技術面

✓単一パイプラインへの統合: 組み込み機能と独自分析が同じパイプライン・同じメタデータタイムラインで動作し、GetMetadata API だけで結果を取得できる
✓信頼度スコアによる制御: Customer Decisions はすべてのラベルと質問に信頼度スコアを返すため、しきい値ベースの自動化ワークフローを構築しやすい
✓障害の分離: 関数が失敗してもフィードの他の出力は正常に継続するため、独自分析の追加が本番配信の安定性に影響しない
✓モデルとコストの自己管理: Functions の Bedrock モデルはユーザー自身のアカウントとロールで実行されるため、モデル選択・アクセス許可・クォータを自身で制御できる

⚠️ デメリット・制約事項

🚧 制限事項

✗Customer Decisions の利用には、フィードでコンテキストメタデータ出力が有効であることが必要
✗Customer Decisions はラベルと yes/no・単一選択形式で答えられる判定に限定される (オープンエンドな回答には Functions が必要)
✗Question Set にはテキストルールや数の制限がある (詳細はユーザーガイドの「Limits and text rules for question sets」を参照)
✗Functions の実行には、フィードで少なくとも 1 つの機能がアクティブであることが必要

🤔 考慮すべき点

⚠Functions で Amazon Bedrock モデルを呼び出す場合、Bedrock の使用料金が別途発生するため、実行頻度の設定がコストに直結する
⚠Functions のリクエスト/レスポンス整形には JSONata 式の記述が必要で、学習コストがある
⚠モデルはユーザーアカウントの Bedrock スループットクォータを消費するため、他ワークロードとのクォータ競合に注意が必要

💡 ユースケース

🏟️ ユースケース 1: スポンサーロゴ露出の測定

シナリオ: スポーツ中継の放送事業者が、スポンサー契約の価値を証明するために、ライブ配信中のスポンサーロゴの露出時間を測定したい。

実装例:

  • Amazon Bedrock のマルチモーダルモデルを指定した Function を作成
  • JSONata 式で「フレーム内に表示されているスポンサーロゴと表示位置を列挙する」プロンプトを構成し、レスポンスを独自スキーマに整形
  • 中継フィードにアタッチし、実行頻度を設定
  • GetMetadata API で露出データを取得し、レポーティング基盤に集計
✨ 効果: 専用の映像分析パイプラインを構築せずに、スポンサーレポートを自動生成できる。
🎯 ユースケース 2: 自社基準によるコンテキスト広告ターゲティング

シナリオ: ストリーミング事業者が、標準の IAB カテゴリに加えて自社定義のジャンル分類と「天気予報のシーンか」という判定に基づいて広告を出し分けたい。

実装例:

  • chooseOne でジャンル (ニュース/スポーツ/ドラマなど)、yesNo で「天気予報か」を定義した Question Set を作成
  • バージョンを発行し、フィードの customQuestions 設定にアタッチ
  • GetMetadata API のレスポンスで各シーンの判定と信頼度スコアを取得
  • 信頼度がしきい値を超えた場合に、広告デシジョニングサーバーへカスタムパラメータとして連携
✨ 効果: モデル選択やプロンプト作成なしで、自社基準のコンテキスト広告が実現できる。
🔄 ユースケース 3: 既存メタデータの独自スキーマへの変換

シナリオ: 自社の MAM (メディアアセット管理) システムが独自のメタデータスキーマを採用しており、Elemental Inference の出力をそのまま取り込めない。

実装例:

  • モデルを呼び出さないパススルー Function を作成
  • JSONata 式で、組み込みのコンテキストメタデータを MAM システムのスキーマに整形
  • GetMetadata API から整形済みメタデータを取得し、MAM に直接取り込み
✨ 効果: モデルコストゼロで、変換レイヤーの開発・運用なしにスキーマ変換を実現できる。

🔗 関連サービス・機能

📝 まとめ

AWS Elemental Inference のカスタマイズ性が大きく向上し、Question Set による簡易な判定追加から、 Bedrock モデルと JSONata によるフルカスタム分析まで、要件に応じた 2 段階の選択肢が提供されました。 独自パイプラインを構築せずにライブ映像の独自分析を同一のメタデータタイムラインに統合できるため、 コンテキスト広告やスポンサー分析に取り組む放送・ストリーミング事業者は、まず Customer Decisions で判定を追加し、 より高度な要件には Functions を検討することを推奨します。
