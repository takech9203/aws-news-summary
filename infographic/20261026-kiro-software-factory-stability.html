🏭 週 1,000 PR のソフトウェアファクトリーを安定稼働させる方法

Kiro Crew による大規模 AI 開発の品質・安定性確保プラクティス
📅 リリース日: 2026 年 10 月 26 日

📋 概要

Kiro チームは、3 人のエンジニアとエージェントの「クルー」で週 1,000 件のプルリクエストをマージするソフトウェアファクトリーを、どのように壊さず安定稼働させているかを解説する Blog 記事を公開しました。新機能の発表ではなく、Kiro Crew の開発で実際に使われている品質保証の仕組みと、その進化の 5 つのステージを解説するエンジニアリング記事です。

出発点は「人間は、自分が書いておらず 1 行ずつ読んでもいないコードを含む PR に責任を持てるのか」という問いです。チームの答えは、信頼の源泉を人間のコードリーディングからテストと自動チェックに移すこと。「人間が読むより信頼できる自動テストとチェックをどう構築するか」という問題に置き換えています。

🔄 「PR を知っている」ことの再定義

PR 番号を問われたら差分を暗記して答えるのではなく、クルーに尋ねてコード・テストエビデンス (スクリーンショット、動画、データ)・レビュー記録に基づく平易な要約を 1 分で得ます。CI がすべての PR に残すレビュー記録 (各レビュアーの指摘、修正や反証の経緯、チェック結果、最終的な準備完了判定) こそが、人間が責任を持つ対象です。

😰 記事が扱う課題

  • エージェントは数分でコードを書けるため速度は容易だが、人間が全行を読まずに「正しく、安全で、マージする価値がある」と確信することが困難
  • 人間による全件レビューは、サイドプロジェクト規模の変更量ですら 1 日も持たずに破綻
  • 「全コメント解決必須」などの厳格なルールは、E2E テストの欠如や際限のないレビューラウンドにより、品質ではなく摩擦を生んだ
  • レビューと修正のループを自動化すると、過剰設計や行き過ぎたセキュリティ修正という新たな問題が発生

✨ 記事が示す解決策

  • 信頼の基盤をテストと CI/CD に置き、テストカバレッジ 90% 超、役割別の複数 AI レビュアー、agentic testing を整備
  • すべての CI/CD チェック結果を単一の「PR Readiness」判定に集約し、prepare-pr スキルがグリーンになるまで修正ループを自律実行
  • レトロスペクティブと「コンダクター」エージェントにより、修正がサブシステム化する過剰設計を自動的に抑止
  • マージ後も、リリースゲート、多層のセキュリティチェック、定期リファクタリングで品質を維持

💡 Kiro Crew の自動化された PR 処理フローです。すべてのチェック結果が単一の PR Readiness 判定に集約され、prepare-pr スキルがグリーンになるまでループを回します。人間とエージェントが「完了」の定義を 1 つの判定で共有している点が特徴です。

📈 品質向上の 5 つのステージ

チームはシステム全体を最初から計画したのではなく、1 つの問題を解決すると次の問題が現れるという形で 5 段階に進化させました。記事は「実際のコードベースでコーディングエージェントを動かせば、同じ壁に同じ順序でぶつかるだろう」と述べています。

Stage 0人間による全件レビュー (即座に破綻)
  • 2026 年 3 月初頭、すべての変更を人手でレビューする体制を試みたが、1 日も持たなかった
  • 当時の Kiro Crew はサイドプロジェクトで変更量もはるかに少なかったにもかかわらず破綻し、レビュー自動化を迫られた
Stage 1自動レビュアー + 人間のパイプライン
  • 社内のビルド・レビューシステムの自動レビューボットを全変更に適用し、「全 AI コメントのマージ前解決」という厳格なルールを設定
  • 問題 1: E2E テストがなく、全コメントを解決してもアプリが壊れ、人間が手動テストとスクリーンショット添付を強いられた
  • 問題 2: コメントが何ラウンドにも分けて届き、小さな変更が 1 日がかりの往復や計画外の大きな変更に膨らんだ
  • 問題 3: レビュアーのルールがいつ・なぜ発火したかが見えず、チューニングできなかった
📝 教訓: 厳格なルールは「完全でチューニング可能なフィードバック」と「実プロダクトでの E2E テスト」の両方があって初めて機能する
Stage 2重要度ティアと 2 人目のレビュアー
  • コメントを重要度でティア分けし、ブロッキングと実質的な懸念は同一 PR で修正、軽微な指摘はフォローアップ Issue に回して PR を小さく保った
  • 独自のレビューエージェントを追加し、複数パスでスキャンして実質的なコメントを 1 ラウンドで出し切る設計に
  • AI レビュアーが人間の読解では通常見つからない深い問題を発見することが分かり、人手による 1 行ずつのレビューを手放す判断につながった
  • 人間主導のループで離脱するコントリビューターが出たため、同じテストと AI レビューをローカルで実行できる組み込みスキルを提供
Stage 3オープンソース化、本物の CI、多数のレビュアー
  • GitHub に移行し、全 PR でビルド・単体テスト・E2E テストを自動実行。テストポッドが隔離環境でコードを実行し、スクリーンショットと動画を PR に添付
  • フォークからの信頼されないコードと、信頼されたレビューワークフローを境界の反対側で実行するセキュリティ設計
  • レビュアーを役割で分割: 設計レビュアー、第一原理レビュアー、UX レビュアー。さらに異なるモデルファミリーでもスキャン (同一ファミリーは盲点を共有するため)
  • 単体・統合・フロントエンド・パッケージング・バンドルサイズ予算・カバレッジ下限・E2E と、異なる失敗クラスを捕捉するテスト群を整備。エージェントが最も間違えやすいのは統合部分
  • 「ブロッキング」の定義を統一: 具体的な位置、証拠、トリガー、帰結を示せない指摘は助言扱い。設計上の懸念は one-way door でない限り助言扱い
Stage 4ループを閉じる
  • prepare-pr スキルが、PR がグリーンになるまで「失敗した CI と指摘の取得 → 修正・証拠つき反証 → プッシュ → 再チェック」のループを自律実行
  • 80 以上のチェック結果を単一の「PR Readiness」判定に集約。「期待されるすべてのアクションが実行され、かつ合格した」ことを意味し、「まだ何も失敗していない」とは区別
  • PR をティア分類し、シンプルなティアは自動承認・自動マージ。それ以外は AI がレビュー案を起草して人間に提示
  • エージェントが PR 説明を固定テンプレート・平易な言葉・図解つきで記述し、コード変更のたびに書き直す。説明とコードの一致を検証する CI チェックも存在
Stage 5マージ後の仕組み
  • リリースゲート: リリース前にビルド済みプロダクトで追加テスト。agentic テストでは、エージェントが実アプリをインストールし、セッション開始、タスク実行、メモリ利用などのコアフローを操作
  • マージ後のセキュリティ: 毎時のコンプライアンスチェック、日次スキャン、ガードレール侵入を実際に試みる常時稼働のセキュリティボット、マネージドセキュリティインボックスの多層構成
  • 定期リファクタリング: 大きなファイル、重複ロジック、デッドコードを定期的に整理し、人間とエージェントの両方が変更しやすいコードベースを維持
  • チェック自体のスケーリング: 1 日 100 PR × 数十チェックで GitHub のレート制限に到達したため、CI アクションを段階実行 (ファストゲート)。レビューを AWS CodeCommit に、一部テストを自前ホストに移行
  • 開発プロセス: 全機能リクエストを構築前に分類。シンプルな変更は直接構築、中規模は 1 ページの設計書、複雑なものはチーム全体のレビューを必須に。最も高くつくバグは「ユーザーが必要としない機能」から生まれるため

⚠️ 乗り越えた 2 つの重大な問題

🧱 1. 過剰設計 (over-engineering)

レビューと修正のループが自律化すると最大の無駄の源泉に。レビュアーがエッジケースを指摘するとエージェントが仕組みを追加し、その仕組みのエッジケースがまた指摘され、5 ラウンド後には 10 行の修正が不要な小さなサブシステムに育ってしまう。

✅ 対策 1 - レトロスペクティブ: 同じ領域で数ラウンド続いた場合に自身の履歴を振り返り、停止・取り消し・より単純なアプローチを推奨。最初の一手は通常「不要になった仕組みの削除」
✅ 対策 2 - 比例原則: 修正は PR 説明に記載された問題を解決する直接的なコード変更に限定し、それ以上はフォローアップへ。例外は到達可能なクラッシュ、セキュリティホール、データ損失で、これらは常に修正
✅ 対策 3 - コンダクターエージェント: レトロスペクティブの推奨を読んで最初の判断を自ら下す第 2 のエージェント。コンダクターが判断できない場合のみ人間を呼ぶ
🔒 2. 行き過ぎたセキュリティ修正

AI はセキュリティに熱心で、1 つの実在する指摘に対して 3 層の防御、新しい設定フラグ、決して実行されない検証ステップを追加しがち。追加のたびに壊れうる新コードと次のレビューラウンドの指摘対象が増える。

  • 事例 1: レビューラウンドごとにエージェントサンドボックスが少しずつ強化され、合わせるとビルド実行やファイル読み取りといった通常作業が失敗 (紙の上では安全だが実用に耐えない)
  • 事例 2: 実行ファイルを専用フォルダーにコピーしてロックダウンする古典的な提案は、壊れうる要素を追加しながら「すでにマシンを掌握した攻撃者」という極めて稀なケースにしか備えない
✅ 結論: セキュリティ修正は「ユーザーが実際に到達可能な問題を、最小のコード変更で修正する」というシンプルなルールに従う

💡 今日から適用できる 7 つのプラクティス

記事は、読者のプロダクトに合わせて調整することを前提に、以下の提案を挙げています。

1
レビューコメントをティア分けする「全コメント解決」は厳格に聞こえるが、しばしば空回り (churn) を生む
2
すべてのコメントを 1 ラウンドで求める遅くても完全なレビュアーの方が、ラウンドをまたいで指摘を小出しにするレビュアーよりコストが低い
3
レビュアーを役割とモデルで分割する異なる問いと異なるモデルファミリーは異なる問題を捕捉する
4
チェックを単一の準備完了フラグに集約する「すべて実行され合格した」を意味させる。「まだ何も失敗していない」ではない
5
部分ではなくプロダクト全体をテストするリリース前に少なくとも 1 つは実フローを操作するステップを設ける
6
エージェントループにレトロスペクティブを入れ、第 2 のエージェントに最初の判断をさせる立ち止まるたびに人間が必要にならないようにする
7
セキュリティ修正を妥当な範囲に保つ厳格なチェックで実在する問題をあぶり出しつつ、修正自体は小さく直接的にする

🎯 メリット

💼 ビジネス面

  • スピードと品質の両立: 週 1,000 PR という速度を維持しながら、全変更が同一のレビュー・テスト・ゲートを通過したことをレビュー記録で証明できる
  • 人間の時間の最適配分: シンプルな PR の自動マージと AI によるレビュー案・PR 説明の生成により、人間は判断が本当に必要な箇所にのみ関与
  • 無駄な機能・修正の抑制: 機能リクエストの事前分類と修正の比例原則により、「ユーザーが必要としない機能」という最も高くつくバグを削減

⚙️ 技術面

  • 単一の完了シグナル: PR Readiness 判定により、人間とエージェントが「完了」の定義を共有し、エージェントが自律的にループを回せる
  • 多層防御の品質保証: 役割別・モデルファミリー別のレビュアー、失敗クラス別のテスト群、マージ後の継続チェックにより、すり抜けた問題も長くは生き残らない
  • 自己抑制機構: レトロスペクティブとコンダクターエージェントにより、自律ループの典型的な失敗である過剰設計を仕組みレベルで抑止

📌 制限事項

🤔 考慮すべき点

  • 大量の自動チェックは GitHub のレート制限やリソース制限に到達しうるため、チェックのグループ化や段階実行、実行基盤の分散といったスケーリング対策が必要
  • マージ前に全チェックを通過することと、時間の経過とともに健全であり続けることは別問題であり、マージ後も動き続けるチェックと機能選定プロセスが必要
  • 自律ループを導入する場合、過剰設計と行き過ぎたセキュリティ修正という副作用への対策をセットで設計する必要がある
