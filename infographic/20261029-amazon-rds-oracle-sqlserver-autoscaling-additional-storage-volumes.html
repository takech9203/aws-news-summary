Amazon RDS for Oracle Amazon RDS for SQL Server 📅 2026 年 10 月 29 日

🗄️ 追加ストレージボリュームの
ストレージ自動スケーリング対応

最大 3 つの追加ストレージボリュームも、ボリューム単位でダウンタイムなしの自動拡張が可能に

📌 概要

Amazon RDS for Oracle および Amazon RDS for SQL Server で、追加ストレージボリューム (Additional Storage Volumes) に対するストレージ自動スケーリングがサポートされました。これまでプライマリボリュームのみだった自動スケーリングが、最大 3 つまでアタッチできる追加ボリュームにも拡張され、各ボリュームを独立して自動拡張できます。

各ボリュームに最大ストレージしきい値を設定するだけで、RDS が使用量を継続的に監視し、容量が逼迫するとダウンタイムなしで自動拡張します。新規・既存インスタンスの両方で利用でき、コンソール / AWS CLI / RDS API から設定可能です。

❌ アップデート前の課題

✗自動スケーリングはプライマリボリュームのみ対象で、追加ボリュームには適用できなかった
✗追加ボリュームの容量は将来需要を予測して手動でプロビジョニングする必要があった
✗過小見積もりはストレージ枯渇によるダウンタイムのリスク、過大見積もりは未使用容量の不要なコストが発生

✅ アップデート後の改善

✓追加ボリュームごとに最大ストレージしきい値を設定し、自動スケーリングを個別に有効化できる
✓RDS が各ボリュームを継続監視し、空き容量が少なくなるとダウンタイムなしで自動拡張
✓容量計画の手間と、過小 / 過大プロビジョニングのリスクを軽減

プライマリボリュームと最大 3 つの追加ストレージボリュームそれぞれに最大ストレージしきい値を設定でき、RDS が各ボリュームを独立して監視・自動拡張します。

⚙️ 主要機能

1️⃣ ボリューム単位の独立した自動スケーリング

  • プライマリに加え、各追加ボリューム (Oracle: rdsdbdata2 / rdsdbdata3 / rdsdbdata4、SQL Server: H: / I: / J: ドライブ) ごとに有効化できる
  • 各ボリュームが独自の最大ストレージしきい値を持ち、RDS はボリュームごとに独立して評価・スケーリングを実行
  • トリガー条件・拡張増分・しきい値の制約はプライマリボリュームと同一

2️⃣ ダウンタイムなしの自動拡張

  • 空き容量が割り当てストレージの 10% 以下の状態が 5 分以上継続すると、ストレージ変更が自動開始
  • 拡張増分は「10 GiB」「割り当てストレージの 10%」「過去 1 時間の FreeStorageSpace メトリクスに基づく 7 時間先の予測増加量」のうち最大の値
  • 有効化・設定変更に DB の再起動は不要で、ダウンタイムは発生しない

3️⃣ ボリュームを識別できるイベント通知

  • 変更の開始・完了時に RDS-EVENT-0541 / RDS-EVENT-0542 が発行される
  • しきい値への到達・接近やスケーリング不可時には RDS-EVENT-0594 / RDS-EVENT-0595 / RDS-EVENT-0593 が発行され、対象ボリュームを識別可能
  • しきい値接近の通知を避けるには、しきい値を割り当てストレージの 26% 以上大きい値に設定することを推奨

4️⃣ 新規・既存インスタンスの両方に対応

  • 新規 DB インスタンス作成時、および既存 DB インスタンスの変更時のどちらでも設定可能
  • AWS Management Console、AWS CLI、RDS API から設定できる

🔧 設定パラメータ

modify-db-instance の --additional-storage-volumes JSON 配列内で、ボリュームごとに MaxAllocatedStorage フィールドを設定します。

JSON ボリューム設定の例 
[
  {
    "VolumeName": "rdsdbdata2",
    "StorageType": "gp3",
    "AllocatedStorage": 5000,
    "MaxAllocatedStorage": 10000
  }
]
✓MaxAllocatedStorage > AllocatedStorage: 当該ボリュームのストレージ自動スケーリングが有効になる
✗MaxAllocatedStorage = AllocatedStorage: 当該ボリュームのストレージ自動スケーリングが無効になる

🚀 設定方法

✅ 前提条件

✓RDS for Oracle または RDS for SQL Server の DB インスタンスを使用していること
✓追加ストレージボリュームが gp3 または io2 ストレージタイプであること (マグネティックストレージは非対応)
✓最大ストレージしきい値は現在の割り当てストレージより 10% 以上大きい値に設定すること (推奨は 26% 以上)

STEP 1追加ストレージボリュームの自動スケーリングを有効化

Bash 既存ボリュームの自動スケーリング有効化 
aws rds modify-db-instance \
    --db-instance-identifier mydbinstance \
    --additional-storage-volumes '[
        {
            "VolumeName": "rdsdbdata2",
            "StorageType": "gp3",
            "AllocatedStorage": 5000,
            "MaxAllocatedStorage": 10000
        }
    ]'

rdsdbdata2 の最大ストレージしきい値を 10,000 GiB に設定し、自動スケーリングを有効化します。

STEP 2新しい追加ストレージボリュームを自動スケーリング付きで追加

Bash 新規ボリュームの追加と自動スケーリング設定 
aws rds modify-db-instance \
    --db-instance-identifier mydbinstance \
    --additional-storage-volumes '[
        {
            "VolumeName": "rdsdbdata3",
            "StorageType": "gp3",
            "AllocatedStorage": 1000,
            "StorageThroughput": 725,
            "MaxAllocatedStorage": 5000
        }
    ]'

1,000 GiB の gp3 ボリュームを新規追加し、最大 5,000 GiB までの自動スケーリングを有効化します。

⚠️追加ストレージボリュームの追加は --no-apply-immediately の指定に関係なく即時適用される点に注意

STEP 3設定の確認

Bash 追加ストレージボリューム設定の確認 
aws rds describe-db-instances \
    --db-instance-identifier mydbinstance \
    --query "DBInstances[0].AdditionalStorageVolumes"

各ボリュームの AllocatedStorage と MaxAllocatedStorage の値を確認します。コンソールの場合は DB インスタンスの [設定] タブで [Add storage volume] を選択し、[Maximum storage threshold] を設定します。

💡 メリット

💼 ビジネス面

✓運用コストの削減: 容量計画と手動拡張作業が不要になり、DBA の運用負荷を軽減
✓コスト最適化: 過大なプロビジョニングが不要になり、実使用量に応じた支払いが可能
✓可用性の向上: ストレージ枯渇による計画外ダウンタイムのリスクを低減

🔧 技術面

✓ボリューム単位の細かな制御: データ特性に応じた個別の拡張ポリシーを適用可能
✓ダウンタイムなしの拡張: 再起動不要で、稼働中のワークロードに影響なし
✓可観測性: 対象ボリュームを識別できる RDS イベントで通知・監視の自動化が容易

⚠️ デメリット・制約事項

🚫 制限事項

✗自動スケーリングでストレージを縮小することはできない (一度拡張した割り当ては減らせない)
✗ストレージ変更は 24 時間以内に最大 4 回までで、前回の最適化完了まで次の変更は実行されない
✗大規模なデータロードでは自動スケーリングが追いつかず、ストレージフル状態が数時間継続する可能性がある
✗マグネティックストレージでは自動スケーリングを使用できない
✗自動スケーリング操作は AWS CloudTrail に記録されない

🤔 考慮すべき点

⚠️しきい値は現在の割り当てストレージの 10% 以上大きい値が必須、イベント通知を避けるには 26% 以上を推奨
⚠️io1 / io2 Block Express または gp3 では、IOPS としきい値の比率が許容範囲内である必要がある
⚠️手動のストレージ変更と同時に開始された場合は手動変更が優先され、自動スケーリングはキャンセルされる
⚠️意図しない大容量への拡張を防ぐため、しきい値は実際の利用傾向に基づいて慎重に設定する

🎯 ユースケース

1. SQL Server のデータとログを分離した構成での自動容量管理

シナリオ: データファイルをプライマリボリューム、インデックスや tempdb 関連のデータを追加ボリューム (H: ドライブ) に分離。データ増加のペースがドライブごとに異なり、個別の容量管理が負担になっている。

Bash実装例
aws rds modify-db-instance \
    --db-instance-identifier sqlserver-prod \
    --max-allocated-storage 8000 \
    --additional-storage-volumes '[
        {
            "VolumeName": "H:",
            "StorageType": "gp3",
            "AllocatedStorage": 2000,
            "MaxAllocatedStorage": 6000
        }
    ]'
✅ 効果: プライマリと H: ドライブが使用状況に応じて独立して自動拡張され、ドライブごとの容量監視と手動拡張作業が不要になる。

2. Oracle のホットデータとヒストリカルデータの階層化

シナリオ: 高パフォーマンスが必要なデータを io2 のプライマリボリュームに、増加し続けるヒストリカルデータを低コストな gp3 の追加ボリュームに配置。ヒストリカルデータの増加量が予測しにくい。

Bash実装例
aws rds modify-db-instance \
    --db-instance-identifier oracle-prod \
    --additional-storage-volumes '[
        {
            "VolumeName": "rdsdbdata2",
            "StorageType": "gp3",
            "AllocatedStorage": 10000,
            "MaxAllocatedStorage": 30000
        }
    ]'
✅ 効果: ヒストリカルデータ用ボリュームが需要に応じて最大 30,000 GiB まで自動拡張され、過大プロビジョニングによるコストと枯渇リスクの両方を回避できる。

3. 急成長するワークロードでの 256 TiB までの段階的拡張

シナリオ: 急成長中の SaaS アプリケーションで、単一ボリュームの上限を超えるストレージが必要になる見込み。複数の追加ボリュームを段階的に追加しながら、それぞれの容量管理を自動化したい。

Bash実装例
aws rds modify-db-instance \
    --db-instance-identifier saas-prod \
    --additional-storage-volumes '[
        {
            "VolumeName": "rdsdbdata2",
            "StorageType": "gp3",
            "AllocatedStorage": 5000,
            "MaxAllocatedStorage": 20000
        },
        {
            "VolumeName": "rdsdbdata3",
            "StorageType": "gp3",
            "AllocatedStorage": 5000,
            "MaxAllocatedStorage": 20000
        }
    ]'
✅ 効果: 複数ボリュームを組み合わせて最大 256 TiB まで拡張可能な構成を取りつつ、各ボリュームの拡張を自動化し運用負荷を最小限に抑えられる。

💰 料金・利用可能リージョン

💵 料金

本機能の利用自体に追加料金はかかりません。プロビジョニングされたストレージリソースに対してのみ料金が発生します。自動スケーリングで拡張された場合は、拡張後の割り当て容量に応じた標準の RDS ストレージ料金が適用されます。

  • RDS for Oracle の料金
  • RDS for SQL Server の料金

🌏 利用可能リージョン

すべての AWS 商用リージョンおよび AWS GovCloud (US) リージョンで利用可能です。

📝 まとめ

RDS for Oracle および RDS for SQL Server の追加ストレージボリュームがストレージ自動スケーリングに対応し、最大 256 TiB 構成の大規模データベースでもボリューム単位の容量管理を自動化できるようになりました。

追加ストレージボリュームを使用している場合は、各ボリュームに適切な最大ストレージしきい値 (割り当てストレージの 26% 以上大きい値を推奨) を設定し、ストレージ枯渇リスクと手動運用の負荷を低減することを推奨します。
