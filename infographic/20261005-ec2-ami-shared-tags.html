💿 Amazon EC2
AMI 共有タグ (Shared Tags for AMI)

リリース日: 2026 年 10 月 5 日
Amazon EC2 📅 2026-10-05 🌍 全 AWS リージョン 💰 追加料金なし

📋 概要

Amazon EC2 が AMI のタグ共有 (AMI Tag Sharing) をサポートしました。 タグキーに ec2:SharedTag/ プレフィックスを付けるだけで、 そのタグが AMI の共有先すべての AWS アカウントから参照可能になります。 特定アカウントへの共有、AWS Organizations 全体への共有、パブリック公開のいずれでも、共有タグは AMI とともに自動的に伝播します。

これにより、ゴールデン AMI のメタデータ (承認ステータス、パッチ適用日、OS バージョンなど) を配布するために必要だった SNS + Lambda によるカスタムタグレプリケーションワークフローが不要になります。

❌ Before: アップデート前の課題
  • AMI を共有してもタグは所有者アカウント内にとどまり、共有先から参照できなかった
  • SNS + Lambda で各アカウントの CreateTags を呼び出すカスタムレプリケーションパイプラインの構築・保守が必要
  • API 呼び出しがアカウント数 × リージョン数 × AMI 数に比例し、スロットリングや Lambda 実行失敗のリスク
  • タグ更新が即時反映されず、タグドリフト (不整合) が発生しやすい
✅ After: アップデート後の改善
  • ec2:SharedTag/ プレフィックスを付けるだけで全共有先からタグを参照可能
  • 所有者によるタグ更新は追加 API 呼び出しなしで自動伝播、レプリケーションワークフローが不要に
  • 共有先では読み取り専用のため、信頼できる単一の情報源 (Single Source of Truth) として管理可能

AMI 所有者が ec2:SharedTag/ プレフィックス付きのタグを作成すると、AMI の共有先アカウントすべてから読み取り専用でタグが参照可能になります。プレフィックスのないタグは所有者アカウント内でのみ参照できます。

⚙️ 主要機能

1️⃣ ec2:SharedTag/ プレフィックスによるタグ共有
  • タグキーの先頭に ec2:SharedTag/ を付けるだけで、共有先すべてのアカウントから参照可能
  • 特定アカウント、AWS Organizations / OU、パブリック公開のいずれの共有形態でも機能
  • プレフィックスのないタグは従来どおり所有者アカウント内のプライベートタグ
2️⃣ 読み取り専用の権限モデル
  • 共有タグの作成・変更・削除ができるのは AMI の所有者のみ
  • 共有先アカウントは参照のみ可能で、変更はできない
  • 共有先アカウントは共有 AMI に独自のプライベートタグを別途追加できる
3️⃣ 自動伝播によるレプリケーション不要化
  • 所有者がタグを更新すると、追加の API 呼び出しなしで共有先に即時反映
  • AMI を非推奨 (deprecated) にマークすると、すべての共有先で即座に可視化
4️⃣ クォータへの影響の明確化
  • 共有タグは所有者側の「リソースあたり 50 タグ」のクォータにのみカウント (共有タグ + プライベートタグの合計)
  • 共有先アカウントのタグクォータには一切影響しない

🔐 IAM / ABAC に関する注意点

共有先アカウントの ABAC (属性ベースアクセス制御) ポリシーは共有タグを評価対象とします。ただし、タグキーにプレフィックスが含まれる点に注意が必要です。

JSON 共有タグを条件とする IAM ポリシー例 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "ec2:RunInstances",
      "Resource": "arn:aws:ec2:*::image/ami-*",
      "Condition": {
        "StringEquals": {
          "aws:ResourceTag/ec2:SharedTag/status": "approved"
        }
      }
    }
  ]
}
⚠️ 既存の ABAC ポリシーが status=approved というタグキーを条件にしている場合、所有者が ec2:SharedTag/status=approved として共有するとキー名が一致せず、ポリシーは拒否と評価されます。共有タグを ABAC で利用する場合は、プレフィックスを含めた完全なキー名で条件を記述する必要があります。

🛠️ 設定方法

✅ 前提条件

✓AMI を所有している AWS アカウントであること (共有タグの作成は所有者のみ可能)
✓AMI が共有先アカウント、Organizations / OU、またはパブリックに共有されていること
✓タグ操作に必要な IAM 権限 (ec2:CreateTags、ec2:DeleteTags など) があること

ステップ 1: 既存の AMI に共有タグを作成する

Bash create-tags で共有タグを作成 
aws ec2 create-tags \
    --resources ami-0abcdef1234567890 \
    --tags Key=ec2:SharedTag/status,Value=approved

タグキーに ec2:SharedTag/ プレフィックスを付けて作成すると、共有先アカウントすべてから即座に参照可能になります。

ステップ 2: AMI 作成時に共有タグを付与する

Bash create-image と同時にタグ付与 
aws ec2 create-image \
    --instance-id i-1234567890abcdef0 \
    --name "My server" \
    --tag-specifications "ResourceType=image,Tags=[{Key=ec2:SharedTag/publicTag,Value=text}]"

--tag-specifications パラメータで AMI の作成と同時に共有タグを付与できます。ゴールデン AMI のビルドパイプラインへの組み込みに便利です。

ステップ 3: 共有タグを持つリソースを検索する

Bash describe-images でワイルドカード検索 
aws ec2 describe-images \
    --filters "Name=tag-key,Values=ec2:SharedTag/*"

タグキーフィルターにワイルドカードを指定して、共有タグが付与された AMI を一覧表示します。共有先アカウントからも同様のフィルターで承認済み AMI を検索できます。

ステップ 4: タグの共有を停止する

Bash delete-tags で共有を停止 
aws ec2 delete-tags \
    --resources ami-0abcdef1234567890 \
    --tags Key=ec2:SharedTag/status

プレフィックス付きのタグを削除すると共有が停止されます。タグの内容を所有者アカウント内に残したい場合は、プレフィックスなしのキーでタグを再作成します。

⚠️ デメリット・制約事項

🚧 制限事項

✗リリース時点では AMI リソースのみが対象 (スナップショットなど他の EC2 リソースは対象外)
✗共有タグの作成・変更・削除は所有者のみ可能で、共有先アカウントは値を修正できない
✗共有タグは所有者の 50 タグ / リソースのクォータにカウントされる (プライベートタグとの合計)
✗AMI コピー時に --copy-image-tags を指定しない場合は共有タグが引き継がれない

🤔 考慮すべき点

⚠共有タグは共有先すべてのアカウント (パブリック共有の場合は全アカウント) から参照可能なため、個人情報・機密情報・センシティブなデータをタグに含めないこと
⚠既存の ABAC ポリシーやタグベースの自動化は、プレフィックスを含むキー名 (ec2:SharedTag/status など) に合わせた修正が必要になる場合がある
⚠タグ値を設定できるのは所有者のみのため、共有タグをポリシーやワークフローの判断材料にする前に、所有者アカウントが信頼できることを確認する必要がある
⚠信頼できるアカウントの AMI のみを検出・起動可能にする Allowed AMIs 機能との併用を推奨 (まず監査モードで影響を確認してから適用)

🎯 ユースケース

💿 ユースケース 1: ゴールデン AMI の承認ステータス配布

シナリオ: 中央のビルドファクトリーアカウントでセキュリティ強化済みのゴールデン AMI を作成し、多数のワークロードアカウントへ共有。各アカウントでは承認済みイメージのみ起動を許可したい。

Bash 承認済み AMI に共有タグを付与 
# ビルドファクトリーアカウントで承認済み AMI に共有タグを付与
aws ec2 create-tags \
    --resources ami-0abcdef1234567890 \
    --tags Key=ec2:SharedTag/status,Value=approved \
           Key=ec2:SharedTag/patch-date,Value=2026-09-18

効果: 従来のアカウント・リージョン・AMI ごとの SNS + Lambda パイプライン全体を共有タグ 1 つで置き換え。イメージの非推奨マークも全アカウントへ即時反映。

🔐 ユースケース 2: ABAC による起動制御

シナリオ: ワークロードアカウント側で、承認済みタグを持つ AMI からのみインスタンス起動を許可する IAM ポリシーを運用したい。

JSON 承認済み AMI のみ起動を許可 
{
  "Effect": "Allow",
  "Action": "ec2:RunInstances",
  "Resource": "arn:aws:ec2:*::image/ami-*",
  "Condition": {
    "StringEquals": {
      "aws:ResourceTag/ec2:SharedTag/status": "approved"
    }
  }
}

効果: 所有者のみが設定できる読み取り専用の共有タグを条件とすることで、改ざんの心配なく承認済みイメージの利用を強制できる。キー名にプレフィックスを含める点に注意。

📦 ユースケース 3: ソフトウェアベンダーによるメタデータ公開

シナリオ: ソフトウェアベンダーがパブリック AMI を提供しており、OS バージョンや製品バージョンなどのメタデータを利用者に伝えたい。

Bash バージョン情報を共有タグで公開 
aws ec2 create-tags \
    --resources ami-0abcdef1234567890 \
    --tags Key=ec2:SharedTag/os-version,Value=al2023 \
           Key=ec2:SharedTag/product-version,Value=5.2.1

効果: パブリック共有された AMI でも共有タグが全アカウントから参照できるため、利用者は describe-images のタグフィルターで必要なバージョンの AMI を容易に特定できる。

ゴールデン AMI のビルドパイプラインに共有タグの付与を組み込み、承認フローを自動化できる

📝 まとめ

AMI の共有タグは、マルチアカウント環境におけるゴールデン AMI 運用の長年の課題であったタグレプリケーションを、 ec2:SharedTag/ プレフィックスという極めてシンプルな仕組みで解消するアップデートです。

✓カスタムのタグコピーパイプラインを運用している組織は、共有タグへの移行で運用負荷とタグドリフトのリスクを大幅に削減できる
✓移行時は既存の ABAC ポリシーのキー名修正を併せて実施する
✓Allowed AMIs 機能による所有者アカウントの信頼確認を併せて実施することを推奨
