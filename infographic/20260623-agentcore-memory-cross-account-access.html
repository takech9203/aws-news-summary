Amazon Bedrock AgentCore Memory

🔗 クロスアカウントアクセス対応

📅 2026年6月23日
Cross-Account Access

📌 概要

Amazon Bedrock AgentCore Memory がクロスアカウントアクセスに対応しました。 リソースベースのポリシーを使うことで、あるアカウントのプリンシパルが、別のアカウントにあるメモリリソースのデータプレーン API を呼び出せるようになり、メモリとエージェントを複数の AWS アカウントにまたがって構成できます。

このアップデートには 2 つの主要なシナリオがあります。

① 別アカウントからのデータプレーン操作

消費側アカウント (アカウント B) のプリンシパルが、所有者アカウント (アカウント A) のメモリに対してイベント作成・レコード書き込み・取得・セマンティック検索を実行。

② 別アカウントへの配信先 (デリバリー先)

アカウント A のメモリが、アカウント B の Amazon S3 / Amazon SNS / Amazon Kinesis Data Streams にペイロードやストリームイベントを配信。

🔄 Before / After

❌ アップデート前の課題

  • メモリとエージェントは同一アカウント内に配置が必須で、組織横断のマルチアカウント構成が困難
  • 中央集約型のメモリ基盤を複数チーム / アプリアカウントで共有できない
  • 配信先 (S3・SNS・Kinesis) を別アカウントに分離してデータガバナンスを実現する手段が限定的

✅ アップデート後の改善

  • リソースベースポリシーで別アカウントのプリンシパルにデータプレーン API 呼び出し権限を付与可能
  • 1 つのメモリを複数アカウントのエージェントから共有利用
  • 配信先を別アカウントに配置し、アカウント分離によるデータ管理を実現

アカウント B のプリンシパルが完全なメモリ ARN を指定してアカウント A のメモリにアクセスする「データプレーンアクセス」と、アカウント A のメモリ実行ロールがアカウント B の配信先にデータを送る「クロスアカウント配信先」の 2 つのフローを示しています。

⚙️ 主要機能

1. 別アカウントからのデータプレーンアクセス

  • アカウント A はメモリに PutResourcePolicy でリソースベースポリシーをアタッチし、アカウント B のプリンシパルにアクションを許可
  • アカウント B は 完全な ARN を memory-id に指定してデータプレーン API を呼び出し
  • AWS はリソースベースポリシーとアイデンティティベースポリシーの両方を評価し、双方が許可した場合のみ成功

2. クロスアカウント配信先

  • カスタム (セルフマネージド) ストラテジー / ストリーム配信を構成したメモリが、メモリ実行ロール経由で別アカウントの S3・SNS・Kinesis にペイロード配信
  • アカウント A 側に AgentCore を信頼するメモリ実行ロールを作成し、アカウント B 側の各リソースにポリシーを付与
  • メモリ作成時に実行ロール ARN とクロスアカウントリソース ARN を参照して構成

3. きめ細かなアクセス制御

  • データプレーンアクションを個別に許可でき、読み取り専用と読み書きのポリシーを分離可能
  • アカウントルートではなく特定の IAM ロールへ権限を付与し、最小権限の原則を適用
  • DeleteResourcePolicy で削除すると、以降のリクエストは AccessDeniedException を返す

🛠️ 設定方法

前提条件

✓アカウント A で作成済みのメモリリソースと、その完全な ARN
✓データプレーンアクセス: アカウント B 側に対象 bedrock-agentcore アクションを許可する IAM ロール / ユーザー
✓配信先: アカウント B 側に作成済みの S3 バケット / SNS トピック / Kinesis Data Stream

STEP 1メモリにリソースベースポリシーをアタッチ

Bashput-resource-policy (データプレーンアクセス)
aws bedrock-agentcore-control put-resource-policy \
    --region us-east-1 \
    --resource-arn "arn:aws:bedrock-agentcore:us-east-1:<account-A-id>:memory/<memory-id>" \
    --policy '{
        "Version": "2012-10-17",
        "Statement": [
            {
                "Sid": "AllowCrossAccountMemoryReadWrite",
                "Effect": "Allow",
                "Principal": { "AWS": "arn:aws:iam::<account-B-id>:root" },
                "Action": [
                    "bedrock-agentcore:CreateEvent",
                    "bedrock-agentcore:BatchCreateMemoryRecords",
                    "bedrock-agentcore:RetrieveMemoryRecords",
                    "bedrock-agentcore:GetMemoryRecord"
                ],
                "Resource": "arn:aws:bedrock-agentcore:us-east-1:<account-A-id>:memory/<memory-id>"
            }
        ]
    }'

本番環境では root ではなく特定の IAM ロールを指定し、最小権限を適用することを推奨します。

STEP 2アカウント B からデータプレーン API を呼び出し

Bashretrieve-memory-records (セマンティック検索)
aws bedrock-agentcore retrieve-memory-records \
    --region us-east-1 \
    --memory-id "arn:aws:bedrock-agentcore:us-east-1:<account-A-id>:memory/<memory-id>" \
    --namespace "preferences/user-123" \
    --search-criteria '{"searchQuery": "meeting preferences"}' \
    --max-results 10

完全な ARN を memory-id に指定。AWS はリソースベースポリシーとアイデンティティベースポリシーの両方を評価します。

STEP 3クロスアカウント配信先の構成

アカウント A に AgentCore を信頼するメモリ実行ロールを作成 (信頼ポリシーで bedrock-agentcore.amazonaws.com からの sts:AssumeRole を許可し aws:SourceArn でメモリ ARN に限定)。アカウント B 側の各リソースに実行ロールを許可するポリシーを付与し、メモリ作成時に両 ARN を参照します。

Bashcreate-memory (配信先を別アカウントに指定)
aws bedrock-agentcore-control create-memory \
    --region us-east-1 \
    --name "cross-account-memory" \
    --event-expiry-duration 30 \
    --memory-execution-role-arn "arn:aws:iam::<account-A-id>:role/MemoryCrossAccountRole" \
    --memory-strategies '[
      {
        "customMemoryStrategy": {
          "name": "cross_account_strategy",
          "configuration": {
            "selfManagedConfiguration": {
              "triggerConditions": [ {"messageBasedTrigger": {"messageCount": 5}} ],
              "invocationConfiguration": {
                "topicArn": "arn:aws:sns:us-east-1:<account-B-id>:memory-notifications",
                "payloadDeliveryBucketName": "<bucket-name>"
              },
              "historicalContextWindowSize": 10
            }
          }
        }
      }
    ]'

✓最小権限の適用: 特定の IAM ロールへ権限を付与し影響範囲を限定

⚠️ デメリット・制約事項

制限事項

!データプレーンアクセスは、リソースベースポリシーとアイデンティティベースポリシーの両方が許可している必要 (どちらかが明示的に拒否すると失敗)
!配信先のクロスアカウント構成は、メモリ作成時に実行ロールとリソース ARN を参照して設定する必要
!データプレーン API では、メモリ ID として短縮形ではなく完全な ARN を指定する必要

考慮すべき点

!ポリシー削除前に、他アカウントのアクティブなワークロードが当該アクセスに依存していないか確認
!影響範囲が広いため、アカウントルートではなく特定の IAM ロールへの付与を推奨
!読み取り専用の消費側と読み書きの生成側でポリシーステートメントを分離して管理

🎯 ユースケース

① 中央集約型メモリ基盤の共有

シナリオ: プラットフォームチームが専用アカウント (A) でメモリ基盤を一元管理し、複数の事業部門アカウント (B・C) のエージェントが利用。

A: 各事業部門のロールを許可するリソースベースポリシーをアタッチ / B・C: AgentMemoryReaderRole 等で完全な ARN を指定してアクセス

効果: メモリのスキーマや運用を中央で統制しつつ、各部門が同一のユーザーコンテキストを共有。

② データガバナンスのためのアカウント分離

シナリオ: メモリ実行アカウント (A) とデータ保管アカウント (B) を分離し、ペイロードを監査専用アカウントの S3 に集約。

A: メモリ実行ロールに S3 PutObject 権限を付与 / B: S3 バケットに実行ロールを許可するバケットポリシーを設定

効果: メモリ処理とデータ保管を職務分離し、コンプライアンス要件を満たすデータ管理を実現。

③ リアルタイムイベントのクロスアカウントストリーミング

シナリオ: メモリレコードの更新を別アカウントの分析基盤に流し込み、Kinesis Data Streams 経由でリアルタイム処理。

A: stream-delivery で B の Kinesis ストリーム ARN を参照 / B: ストリームに実行ロールの PutRecords を許可

効果: メモリ更新を別アカウントの分析・可視化パイプラインへリアルタイム連携。

📝 まとめ

クロスアカウントアクセス対応により、メモリリソース・利用エージェント・配信先を複数の AWS アカウントにまたがって構成できるようになりました。中央集約型メモリ基盤の共有やデータガバナンスのためのアカウント分離が容易になります。 マルチアカウント環境でエージェントを運用するお客様は、最小権限の原則に基づいてリソースベースポリシーを設計し、CloudTrail による監査と組み合わせて導入を検討することを推奨します。
