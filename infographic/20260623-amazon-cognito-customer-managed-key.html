🔐 Amazon Cognito

保存データ暗号化における
カスタマーマネージドキーのサポート

ユーザープールのデータを、お客様自身が管理する KMS キーで暗号化
2026.06.23 リリース日

📌 概要

Amazon Cognito のユーザープールの保存データ (data at rest) を、AWS KMS のカスタマーマネージドキー (CMK) で暗号化できるようになりました。これまではデフォルトの AWS 所有キーのみでしたが、今回のアップデートでお客様が作成・管理するキーを使用できます。

キーを掌握することで、組織のポリシーに沿ったライフサイクル管理が可能になり、キーの無効化・削除によって暗号化データへのアクセスを取り消せます。すべての使用状況は AWS CloudTrail で監査でき、金融・医療・公共部門などの厳しいコンプライアンス要件を持つ業界に特に有用です。

⛔ アップデート前の課題

  • 保存データは AWS 所有キーでのみ暗号化され、キーを制御できなかった
  • 組織独自のキー管理ポリシー (ローテーション・無効化・削除) を適用できなかった
  • キーによるアクセス取り消しという組織主導の制御手段がなかった
➜

✅ アップデート後の改善

  • お客様が管理する CMK でユーザープールのデータを暗号化できる
  • キーの無効化・削除で暗号化データへのアクセスを組織判断で取り消せる
  • CloudTrail でキーの全使用状況を監視・監査でき、コンプライアンス対応が容易に

エンドユーザーのデータはユーザープールに保存される際に CMK で暗号化され、キーポリシーによって Cognito サービスプリンシパルにのみ暗号化・復号操作が許可されます。キーの使用状況は CloudTrail に記録されます。

⚙️ 主要機能

🔑 CMK による保存データ暗号化

  • ユーザープールのデータを、お客様が AWS KMS で管理するキーで暗号化
  • デフォルトでは引き続き AWS 所有キーを使用
  • 暗号化設定をしなくても全データは保存時に暗号化される

🛡️ キーライフサイクルとアクセス制御の完全掌握

  • キーの作成・ローテーション・スケジュール削除を AWS KMS で管理
  • キーの無効化・削除で暗号化データへのアクセスを取り消せる
  • キーポリシーで Cognito からのアクセスを細かく制御

🆕 新規・既存ユーザープールへの設定

  • 新規作成時に CMK を設定できる
  • 既存プールを更新して CMK 使用へ変更できる
  • マネジメントコンソール・CLI・SDK のいずれからも設定可能

📊 CloudTrail による監査

  • CMK の全使用状況を CloudTrail で監視・監査
  • 認証基盤の保存データへのアクセスに対する可視性を確保

🔍 検索可能な暗号化 (PII の保護)

  • ユーザー属性検索における PII の機密性・完全性・可用性を保護
  • HMAC 値はユーザープールを暗号化する KMS キーで計算される
  • 対象属性: sub, email, phone_number, given_name, family_name, name, username, preferred_username, cognito:user_status

🔧 技術仕様

サポートされるキーの要件

キーの種類対称 (symmetric) KMS キーのみ。非対称キーは不可
リージョンユーザープールと同一リージョンのキーが必要
キー構成シングルリージョンキー & マルチリージョンキー (同一リージョン内) をサポート
指定方法KMS キーの ARN で指定。エイリアスは不可
デフォルトAWS 所有キー (AWS owned key)
対象データユーザープールのデータ (アイデンティティプールは変更不可)

API での設定 (KeyConfiguration)

CreateUserPool / UpdateUserPool の KeyConfiguration パラメータで設定します。

JSONCMK を指定
"KeyConfiguration": {
   "KeyType": "CUSTOMER_MANAGED_KEY",
   "KmsKeyArn": "arn:aws:kms:us-east-1:111122223333:key/a1b2c3d4-5678-90ab-cdef-EXAMPLE22222"
}
JSONAWS 所有キーに戻す
"KeyConfiguration": {
   "KeyType": "AWS_OWNED_KEY"
}
💡 DescribeUserPool のレスポンスに KeyConfiguration が含まれない場合、そのプールは AWS 所有キーで暗号化しています。

キーポリシーの設定

CMK を使用するには、Cognito のサービスプリンシパルが暗号化・復号操作を実行できるよう信頼する必要があります。

JSONキーポリシー抜粋 - Cognito サービスアクセス許可
{
    "Sid": "Allow Amazon Cognito service access",
    "Effect": "Allow",
    "Principal": {
        "Service": [
            "cognito-idp.amazonaws.com",
            "identitystore.amazonaws.com"
        ]
    },
    "Action": [
        "kms:Encrypt",
        "kms:Decrypt",
        "kms:ReEncrypt*",
        "kms:GenerateDataKeyWithoutPlainText"
    ],
    "Resource": "*",
    "Condition": {
        "ArnEquals": {
            "aws:SourceArn": [
                "arn:aws:cognito-idp:us-east-1:111122223333:userpool/us-east-1_EXAMPLE"
            ]
        },
        "StringEquals": {
            "aws:SourceAccount": ["111122223333"]
        },
        "StringLike": {
            "kms:EncryptionContext:aws:cognito-idp:userpool-arn": "arn:aws:cognito-idp:us-east-1:111122223333:userpool/us-east-1_EXAMPLE"
        }
    }
}
💡 このポリシーを記述する IAM プリンシパルには kms:PutKeyPolicy を含む書き込みアクセスが必要です。ログのエクスポート構成時は kms:GenerateDataKey と kms:Encrypt を含むステートメントを追加します。

🛠️ 設定方法

前提条件

✓Essentials または Plus ティアのユーザープールであること
✓ユーザープールと同一リージョンに対称 KMS キーが作成されていること
✓キーポリシーに Cognito サービスプリンシパルへのアクセス許可が設定されていること
✓kms:PutKeyPolicy 権限を持つ IAM プリンシパルがあること
1

KMS キーの作成とキーポリシー設定

Bash
# 対称 KMS キーを作成する
aws kms create-key \
  --description "Amazon Cognito user pool encryption key" \
  --key-usage ENCRYPT_DECRYPT \
  --key-spec SYMMETRIC_DEFAULT \
  --region us-east-1
2

コンソールでの暗号化設定

[ユーザープール] → 対象プール → [ユーザープールのセキュリティ] → [保存時の暗号化] → [編集] → [キータイプ] で [カスタマーマネージドキー] を選択 → ARN を入力 → [変更を保存]。

3

CLI または SDK での設定

Bash既存プールを CMK 暗号化に更新
aws cognito-idp update-user-pool \
  --user-pool-id us-east-1_EXAMPLE \
  --key-configuration KeyType=CUSTOMER_MANAGED_KEY,KmsKeyArn=arn:aws:kms:us-east-1:111122223333:key/a1b2c3d4-5678-90ab-cdef-EXAMPLE22222 \
  --region us-east-1

🎯 メリット

ビジネス面

✓データガバナンスの強化: 組織独自の暗号化キー管理ポリシーを認証基盤に適用
✓コンプライアンス対応: 規制要件に対しキー掌握の証跡を CloudTrail で提示
✓追加費用なし: 機能自体に追加料金は発生せず、標準の KMS 料金のみ

技術面

✓アクセス取り消しの即時性: キーの無効化・削除で組織主導の取り消しが可能
✓既存環境への適用: 既存プールを更新するだけで CMK へ移行
✓マルチリージョンキー対応: 同一リージョン内で災害復旧戦略と組み合わせ可能

⚠️ デメリット・制約事項

制限事項

✗対称 KMS キーのみサポート (非対称キーは不可)
✗キーはユーザープールと同一リージョンに存在する必要がある
✗キーの指定は ARN のみ (エイリアス不可)
✗アイデンティティプールは引き続き AWS 所有キーのみで変更不可
✗Essentials / Plus ティアのみ利用可能 (新規作成プールでは常に利用可能)

考慮すべき点

⚠キーを誤って削除・無効化するとデータにアクセスできなくなる。ライフサイクル管理を慎重に
⚠KMS の API 呼び出しに応じた標準の AWS KMS 料金が発生
⚠キーポリシー設定には kms:PutKeyPolicy 権限が必要 (適切な IAM 設計が前提)

💡 ユースケース

1. 規制業界における認証基盤のキー管理

シナリオ: 金融機関が顧客向け Web アプリの認証に Cognito を使用し、暗号化キーの自社掌握が規制要件。専用 CMK を作成・ローテーション設定し、プールに適用、CloudTrail で継続監査。

効果 ▶ 暗号化キーを自社管理し監査証跡を提示でき、規制要件への準拠を実証できる。

2. インシデント発生時のデータアクセス遮断

シナリオ: セキュリティインシデントが疑われる状況で、保存データへのアクセスを即座に遮断したい。

Bash
aws kms disable-key --key-id a1b2c3d4-5678-90ab-cdef-EXAMPLE22222

効果 ▶ キー無効化で暗号化・復号を停止し、データアクセスを組織主導で取り消せる。

3. 既存ユーザープールへのキー管理ポリシーの後付け適用

シナリオ: 本番稼働中のプールに、新たに策定した社内キー管理ポリシーを適用したい。update-user-pool で CMK に切り替え。

効果 ▶ 既存環境を再構築せず、プール更新だけで CMK へ移行できる。

📝 まとめ

Amazon Cognito の CMK サポートにより、認証基盤の保存データに対する暗号化キーをお客様自身が完全に掌握できるようになりました。キーの無効化によるアクセス取り消しや CloudTrail による監査は、データガバナンスやコンプライアンス要件が厳しい組織に大きな価値をもたらします。機能自体は追加料金なしで利用できるため、Essentials / Plus ティアの組織は、同一リージョンに対称 KMS キーを作成し、既存または新規プールへの適用を検討することを推奨します。
