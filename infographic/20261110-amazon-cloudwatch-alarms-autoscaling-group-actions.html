☁️ Amazon CloudWatch

🔔 PromQL アラームによる EC2 / Application Auto Scaling アクションのサポート

📅 リリース日: 2026 年 11 月 10 日 | 機能: CloudWatch PromQL alarms support for EC2 and Application Auto Scaling

📝 概要

PromQL (Prometheus Query Language) を使用する Amazon CloudWatch アラームが、 EC2 Auto Scaling および Application Auto Scaling の ステップスケーリングポリシーとシンプルスケーリングポリシーをトリガーできるようになりました。 ダッシュボードやアラートで使用しているものと同じ PromQL クエリを使って、CloudWatch 上の OpenTelemetry メトリクスに基づいてスケーリングできます。

OpenTelemetry を採用しているチームは、モニタリングとスケーリングを同一のメトリクスとクエリ言語に統合でき、 スケーリング用に従来形式のメトリクスアラームを別途維持する必要がなくなります。

❌ Before: アップデート前の課題
✗PromQL アラームから Auto Scaling のスケーリングポリシーを直接トリガーできなかった
✗OpenTelemetry メトリクスでのスケーリングには従来形式のアラームを別途作成・維持する必要があった
✗モニタリング用クエリとスケーリング用アラームが分離し、運用が二重化していた
✅ After: アップデート後の改善
✓PromQL アラームからステップ / シンプルスケーリングポリシーを直接トリガー可能に
✓ダッシュボードやアラートと同じ PromQL クエリをスケーリング判断に再利用可能に
✓モニタリングとスケーリングを単一のメトリクス基盤に統合可能に

OpenTelemetry メトリクスを PromQL クエリで評価する CloudWatch アラームが、ALARM 状態になるとスケーリングポリシーをトリガーし、EC2 Auto Scaling グループなどのリソースをスケーリングする流れを示しています。

⚡ 主要機能

1️⃣ PromQL アラームからの Auto Scaling アクション
✓PromQL アラームのアクションとして、EC2 Auto Scaling および Application Auto Scaling のスケーリングポリシーを指定可能
✓サポートされるポリシータイプはシンプルスケーリングとステップスケーリング
⚠️ターゲット追跡 (Target Tracking) は現時点で PromQL アラームのサポート対象外
2️⃣ ステップスケーリングでのしきい値超過量に基づく制御
✓しきい値をどの程度超過したかに応じて、適用されるステップ (スケーリング調整量) が決定される
✓クエリは単一の時系列を返す必要があり、その値をしきい値と比較して評価する
3️⃣ 複数の設定方法
✓CloudWatch コンソールでのアラーム作成・編集時に設定可能
✓PutMetricAlarm API、AWS CLI、AWS SDK、AWS CloudFormation にも対応

🔧 技術仕様

PromQL アラームと Auto Scaling 連携の仕様

項目詳細
クエリ言語PromQL (Prometheus Query Language)
対象メトリクスCloudWatch 上の OpenTelemetry メトリクスなど
クエリ要件スケーリング用途では単一の時系列を返し、しきい値と比較すること
対応スケーリングポリシーシンプルスケーリング、ステップスケーリング
非対応スケーリングポリシーターゲット追跡スケーリング
対応ターゲットEC2 Auto Scaling グループ、Application Auto Scaling 対象リソース
設定方法CloudWatch コンソール、PutMetricAlarm API、AWS CLI、AWS SDK、AWS CloudFormation

🛠️ 設定方法

前提条件

  • ✓ CloudWatch にメトリクス (OpenTelemetry メトリクスなど) が送信されていること
  • ✓ EC2 Auto Scaling グループまたは Application Auto Scaling の対象リソースが存在すること
  • ✓ シンプルスケーリングまたはステップスケーリングポリシーが作成済みであること

手順

1
スケーリングポリシーの作成
Bash ステップスケーリングポリシーの作成 
aws autoscaling put-scaling-policy \
  --auto-scaling-group-name my-asg \
  --policy-name my-step-scaling-policy \
  --policy-type StepScaling \
  --adjustment-type ChangeInCapacity \
  --step-adjustments "MetricIntervalLowerBound=0,MetricIntervalUpperBound=20,ScalingAdjustment=1" \
                     "MetricIntervalLowerBound=20,ScalingAdjustment=2"

しきい値の超過量が 0〜20 の場合は 1 台、20 以上の場合は 2 台を追加する設定です。実行結果として返される PolicyARN を次のステップで使用します。

2
PromQL アラームの作成とスケーリングアクションの関連付け

CloudWatch コンソールでアラームを作成する際に、[Select metric] から PromQL タブを選択して PromQL クエリを入力します。クエリはアラームが評価できるよう単一の時系列を返す必要があります。しきい値と評価期間を設定した後、アラームアクションとしてステップ 1 で作成したスケーリングポリシーを指定します。

API や CLI を使用する場合は、PutMetricAlarm の AlarmActions にスケーリングポリシーの ARN を指定します。

3
動作確認

アラームが ALARM 状態に遷移した際に、Auto Scaling グループのアクティビティ履歴でスケーリングアクションが実行されたことを確認します。CloudWatch コンソールのアラーム履歴と、EC2 Auto Scaling コンソールのアクティビティタブの両方で動作を検証できます。

💡 メリット

💼 ビジネス面

✓運用の統合: モニタリング、アラート、スケーリングを同一のメトリクスとクエリ言語に統合でき、運用コストを削減
✓OpenTelemetry 採用の促進: 移行時にスケーリング用の従来形式アラームを別途維持する必要がなくなり、移行の障壁が低下
✓追加コストなし: 標準の CloudWatch アラーム料金が適用され、新たな料金体系の学習や予算確保が不要

⚙️ 技術面

✓PromQL の表現力を活用: レート計算やラベルベースの集計など、柔軟なクエリをスケーリング判断に利用可能
✓きめ細かな制御: しきい値の超過量に応じて段階的にキャパシティを調整
✓IaC 対応: AWS CloudFormation でアラームとスケーリング設定をコードとして管理可能

⚠️ デメリット・制約事項

制限事項

⚠️ターゲット追跡 (Target Tracking) ポリシーは現時点で PromQL アラームのサポート対象外
⚠️スケーリング用途の PromQL クエリは単一の時系列を返す必要がある
⚠️CloudWatch PromQL アラームが利用可能なリージョンに限定される

考慮すべき点

→複数の時系列を返すクエリはスケーリングアラームとして使用できないため、集計関数などで単一系列に絞り込む設計が必要
→ターゲット追跡が必要なワークロードでは、引き続き従来形式のメトリクスアラームまたはターゲット追跡ポリシーの構成を検討する必要がある

🎯 ユースケース

📡 ユースケース 1: OpenTelemetry メトリクスに基づく EC2 Auto Scaling

シナリオ: アプリケーションが OpenTelemetry でリクエストレイテンシーやキュー長などのカスタムメトリクスを CloudWatch に送信しており、これらの値に基づいて EC2 Auto Scaling グループをスケーリングしたい。

PromQL 処理待ちキュー長の平均を評価 
avg({"app.worker.queue_depth"})

アラーム条件: queue_depth > 100 でステップスケーリングポリシーをトリガー

効果: ダッシュボードで監視している OpenTelemetry メトリクスをそのままスケーリング判断に使用でき、従来形式のメトリクス変換やアラームの二重管理が不要になります。

📊 ユースケース 2: ステップスケーリングによる負荷急増時の段階的な増強

シナリオ: トラフィックの急増時には一度に複数台のインスタンスを追加し、緩やかな増加時には 1 台ずつ追加したい。

💰 料金と利用可能リージョン

💵 料金

標準の CloudWatch アラーム料金が適用されます。PromQL アラームから Auto Scaling アクションをトリガーすること自体に追加料金は発生しません。詳細は CloudWatch の料金ページを参照してください。

🌍 利用可能リージョン

CloudWatch PromQL アラームが利用可能なすべての AWS リージョンで利用できます。

🔗 関連サービス・機能

→Amazon EC2 Auto Scaling: PromQL アラームからシンプル / ステップスケーリングポリシーをトリガーできる対象サービス
→Application Auto Scaling: ECS、DynamoDB など EC2 以外のリソースのスケーリングを管理するサービスで、同様に PromQL アラームと連携可能
→OpenTelemetry: CloudWatch に送信したメトリクスを PromQL で照会でき、今回のアップデートによりスケーリングにも活用可能
→AWS CloudFormation: PromQL アラームとスケーリングアクションの構成をコードとして管理可能

📌 まとめ

PromQL アラームが EC2 Auto Scaling および Application Auto Scaling のシンプル / ステップスケーリングポリシーをトリガーできるようになり、 OpenTelemetry メトリクスを中心としたモニタリングとスケーリングの統合が可能になりました。

✓OpenTelemetry を採用している、または採用を検討しているチームは、スケーリング用の従来形式アラームを PromQL アラームに統合できるか確認することを推奨
⚠️ターゲット追跡ポリシーは現時点で非対応のため、ワークロードごとに適切なポリシータイプを選択
