📋 概要

Amazon Bedrock AgentCore Identity が On-Behalf-Of (OBO) トークン交換 をサポートしました。開発者は認証済みユーザーに代わって保護されたリソースにセキュアにアクセスする AI エージェントを構築できるようになります。OAuth 2.0 Token Exchange (RFC 8693) に基づき、既存のアクセストークンをスコープダウンされた新しいトークンに交換し、ジャストインタイムかつ最小権限のアクセスを実現します。

Before

  • 各リソースごとに個別の同意フローが必要
  • ユーザー ID とエージェント ID を同時に含むトークン生成が困難
  • 過剰な権限を持つトークンが発行されるリスク

After

  • スコープダウンされたトークンに交換可能
  • 複数の同意フローが不要に
  • ジャストインタイムかつ最小権限のアクセス制御

🏗️ アーキテクチャ図

ユーザーの認証トークンが AgentCore Identity を介して OBO トークン交換され、エージェントが最小権限で外部リソースにアクセスするフローを示しています。

⚡ 主要機能

🔄 OBO トークン交換

  • OAuth 2.0 Token Exchange (RFC 8693) に基づくトークン交換メカニズム
  • 既存のアクセストークンを新しいスコープダウンされたアクセストークンに変換
  • 元のユーザー ID とエージェント ID の両方を新しいトークンに含める
  • 対象の保護リソースに特化したトークンを生成

🔒 最小権限アクセス制御

  • ジャストインタイムでのトークン発行
  • アウトバウンドリソースごとにスコープを限定
  • エージェントが必要以上の権限を持たないよう制御
  • セキュリティポリシーに準拠した委任アクセス

✨ シームレスなユーザー体験

  • ユーザーが複数の同意フローを完了する必要がない
  • 初回認証のみでエージェントが複数のリソースにアクセス可能
  • エージェントの透過的な認証処理

🛠️ 設定方法

前提条件

  • Amazon Bedrock AgentCore が利用可能なリージョンの AWS アカウント
  • AgentCore Gateway が設定済みであること
  • OAuth 2.0 プロバイダーが AgentCore Identity に登録済みであること
  • 外部リソースが OAuth 2.0 Token Exchange をサポートしていること

Step 1: OAuth プロバイダーの設定

Bash OAuth プロバイダー登録 
aws bedrock-agentcore-control create-oauth-provider \
  --name "my-oauth-provider" \
  --token-endpoint "https://idp.example.com/oauth2/token" \
  --client-id "your-client-id" \
  --client-secret-arn "arn:aws:secretsmanager:<region>:<account>:secret:oauth-secret"

Step 2: Gateway Target に OBO 認証を設定

Bash Gateway Target 設定 
aws bedrock-agentcore-control create-gateway-target \
  --gateway-identifier "my-gateway" \
  --name "my-target" \
  --target-configuration '{"mcp": {"mcpServer": {"endpoint": "https://api.example.com"}}}' \
  --credential-provider-configurations '[{
    "credentialProviderType": "OAUTH",
    "credentialProvider": {
      "oauthCredentialProvider": {
        "providerArn": "arn:aws:bedrock-agentcore:<region>:<account>:oauth-provider/my-oauth-provider",
        "scopes": ["api.read"],
        "grantType": "TOKEN_EXCHANGE"
      }
    }
  }]'

Step 3: エージェント Harness での利用

Bash Harness 作成 
aws bedrock-agentcore-control create-harness \
  --harness-name "my-agent" \
  --execution-role-arn "arn:aws:iam::<account>:role/AgentRole" \
  --tools '[{
    "type": "agentcore_gateway",
    "name": "external-api",
    "config": {
      "agentCoreGateway": {
        "gatewayArn": "arn:aws:bedrock-agentcore:<region>:<account>:gateway/my-gateway",
        "outboundAuth": {
          "oauth": {
            "providerArn": "arn:aws:bedrock-agentcore:<region>:<account>:oauth-provider/my-oauth-provider",
            "scopes": ["api.read"],
            "grantType": "TOKEN_EXCHANGE"
          }
        }
      }
    }
  }]'

認証プロバイダー設定 JSON

JSON credentialProviderConfigurations 
{
  "credentialProviderConfigurations": [
    {
      "credentialProviderType": "OAUTH",
      "credentialProvider": {
        "oauthCredentialProvider": {
          "providerArn": "arn:aws:bedrock-agentcore:<region>:<account>:oauth-provider/<name>",
          "scopes": ["api.read", "api.write"],
          "grantType": "TOKEN_EXCHANGE",
          "defaultReturnUrl": "https://your-app.example.com/callback"
        }
      }
    }
  ]
}

💡 ユースケース

🏢 エンタープライズ SaaS 統合エージェント

社員がチャットで AI エージェントに「今月の売上レポートを Salesforce から取得して」と依頼。エージェントはユーザーの権限範囲内で Salesforce API にアクセスする。

-> ユーザーは追加の認証なしに、自身の権限範囲内で Salesforce データにアクセスするエージェントを利用できる。

🔗 マルチサービスオーケストレーション

開発者が AI エージェントに「GitHub の PR をレビューし、Jira チケットを更新して、Slack で通知して」と依頼。エージェントは 3 つの異なるサービスにユーザーの権限でアクセス。

-> 1 回の認証でエージェントが複数のサービスにまたがるワークフローを実行でき、各サービスへのアクセスは最小権限に制限される。

🎧 カスタマーサポートエージェント

カスタマーサポート担当者が AI エージェントを使用して顧客の注文情報を確認し、返品処理を実行。エージェントは担当者の権限レベルに応じたアクセスのみ許可される。

-> サポート担当者の権限レベルがそのままエージェントに引き継がれ、不正な操作を防止しながら効率的なサポートを提供できる。

✅ メリット

ビジネス面

  • 複数の同意フローが不要になり、シームレスな体験
  • 最小権限の原則に準拠し、監査可能なアクセス制御
  • 委任認証の実装を AgentCore に委譲でき、開発効率向上

技術面

  • スコープダウンされたトークンでトークン漏洩リスクを最小化
  • RFC 8693 準拠で既存 IdP インフラとの互換性確保
  • リソースごとにスコープ指定可能でゼロトラスト実現

⚠️ 制約事項・考慮点

  • 外部リソース側が OAuth 2.0 Token Exchange をサポートしている必要がある
  • OBO トークンの有効期限は元のトークンの有効期限を超えることはできない
  • 対応している OAuth プロバイダーの設定が事前に必要
  • トークン交換の追加ステップによるレイテンシー増加を考慮
  • 既存の CLIENT_CREDENTIALS や AUTHORIZATION_CODE からの移行計画が必要
  • IdP 側での Token Exchange エンドポイントの設定とテストが必要

💰 料金

AgentCore Identity の OBO トークン交換機能の料金は、Amazon Bedrock AgentCore の利用料金に含まれます。追加のトークン交換リクエストに対する個別課金の詳細については、Amazon Bedrock AgentCore の料金ページを参照してください。
