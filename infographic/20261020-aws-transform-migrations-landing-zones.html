🏗️ AWS Transform
既存ランディングゾーンのサポート拡大と IaC 専用モード

AWS Transform for migrations 📅 2026 年 10 月 20 日

📋 概要

AWS Transform for migrations が、移行用ランディングゾーン構築で利用できる既存 AWS 環境のサポートを拡大しました。 AWS Control Tower ベースに加えて AWS Organizations のみで構築されたランディングゾーンにも対応し、 現在の環境を AWS ベストプラクティスと照合する基盤ギャップ分析により、不足している機能のみを追加構築できます。

あわせて IaC 専用モードが追加され、組織の分析と推奨事項の生成を行ったうえで、 移行計画に合わせた IaC を AWS CDK / Terraform / Landing Zone Accelerator (LZA) の 3 形式で生成できます。 管理アカウントへの直接アクセスを許可したくない組織は委任管理者 (DA) アカウント経由で接続でき、 独自のデプロイパイプラインを持つ組織は IaC のみを受け取れます。

❌ Before: アップデート前の課題

  • 既存ランディングゾーンがある環境 (ブラウンフィールド) では活用しにくく、ゼロからの構築や手動ギャップ分析が必要
  • デプロイには管理アカウントへの直接アクセス許可が必須で、セキュリティポリシー上許可できない組織では利用困難
  • LZA / Terraform / 独自 CI/CD を持つ組織は、エージェントの直接デプロイと自社の変更管理プロセスを両立しにくい

✅ After: アップデート後の改善

  • Control Tower / Organizations ベース両方の既存ランディングゾーンを検出し、ベストプラクティスとのギャップのみを推奨
  • IaC 専用モードにより、DA アカウント経由の読み取り権限のみで分析と IaC 生成が可能に。管理アカウントへの直接アクセスが不要
  • 生成された IaC (CDK / Terraform / LZA) を独自パイプラインでレビュー・デプロイでき、既存の変更管理プロセスに統合可能

ランディングゾーンエージェントは、既存環境 (Control Tower または Organizations ベース) のギャップ分析を行い、 コネクタタイプに応じて直接デプロイまたは IaC 生成のいずれかのモードで動作します。

⚡ 主要機能

🏢 1. 既存ランディングゾーンのサポート拡大 (ブラウンフィールド対応)
  • AWS Control Tower ベースと AWS Organizations のみで構築されたランディングゾーンの両方に対応
  • 既存の組織構造 (OU、アカウント、SCP) を検出し、AWS ベストプラクティスとの基盤ギャップ分析を実行
  • ギャップを埋める変更のみを推奨。ゼロからの構築や手動ギャップ分析が不要
  • 既存アカウントのメールアドレスからプラスアドレッシングの命名規則を推測し、同じパターンの継続を提案
🛡️ 2. IaC 専用モード
  • 組織の分析、推奨事項の生成、移行計画に合わせた IaC の生成までを実行。インフラの直接デプロイは行わない
  • 委任管理者 (DA) アカウントのコネクタ使用時に有効。権限は組織に対する読み取り・記述系操作に限定
  • Control Tower 未初期化の組織では、初期化用の IaC アーティファクトを生成し、ユーザー側のパイプラインでレビュー・デプロイ可能
📦 3. 3 つの IaC 形式での出力
🧩
AWS CDK

TypeScript プロジェクトとしてプログラマブルにデプロイ可能

🌍
Terraform

HCL テンプレートとしてランディングゾーンリソースを管理可能

🚀
LZA

LZA Universal Configuration 1.1.0 に基づく YAML 設定。ガバナンス・組織構造・ネットワークが事前構成済み

💡 ダウンロードしたファイルは SHA-256 チェックサムで改ざんの有無を検証可能

🎯 4. ランディングゾーン設計のエンドツーエンド支援
  • 基盤セットアップ: Control Tower、基盤 OU (Security / Infrastructure / Sandbox / Workloads など)、コアアカウント (Audit / Log Archive) の構成
  • ワークロードアカウント設計: 移行ウェーブ、ビジネスユニット、環境分離要件に基づく OU とアカウント構造の提案
  • SCP 管理: ベストプラクティスに基づく追加 SCP の推奨と、適用済み SCP とのギャップ確認

🛠️ 設定方法

前提条件

✓AWS Transform for migrations のワークスペースが作成済みであること
✓AWS Organizations の管理アカウント、または委任管理者 (DA) アカウントへのコネクタを作成できること
✓コネクタのターゲットリージョンが Control Tower のホームリージョンおよび IAM Identity Center のリージョンと一致していること

1
コネクタの作成とモードの選択

管理アカウントまたは委任管理者アカウントのいずれかを接続先として指定。管理アカウント指定でフルデプロイモード、委任管理者アカウント指定で IaC 専用モードで動作。コネクタ作成時にターゲットリージョン (Control Tower のホームリージョン) を指定します。

2
基盤ギャップ分析の実行

エージェントが既存の組織構造を検出し、Control Tower の有無を確認。既存ランディングゾーンがある場合は、ベストプラクティスとのギャップ (例: 「Security OU と Infrastructure OU はあるが Sandbox OU がない」) のみが報告されます。Control Tower 未導入の場合は、Control Tower ベースまたは Organizations のみの 2 つのアプローチから選択できます。

3
ワークロードアカウント設計と SCP の適用

移行計画フェーズのウェーブプランやサーバーとアプリケーションのマッピングをもとに、Workloads OU 配下の OU とアカウント構造を提案。提案内容は適用前にレビュー・修正でき、適用後も繰り返し調整可能。あわせて推奨 SCP を適用対象の OU を選んで設定します。

4
デプロイまたは IaC のダウンロード

「Deploy for me」(直接デプロイ) または「I'll deploy on my own」(IaC 生成) を選択。IaC の場合は CDK / Terraform / LZA のいずれかでダウンロードし、チェックサム検証後に独自パイプラインでデプロイします。

Bash SHA-256 チェックサム検証 
openssl dgst -sha256 -binary <file.zip> | base64
💡 直接デプロイの場合、デプロイリクエストは AWS Transform の Approvals タブを通じて Admin ロールを持つ承認者の明示的な承認を経てから実行されます。

✨ メリット

💼 ビジネス面

✓移行開始までの期間短縮: ギャップ分析と不足機能の追加構築を自動化し、通常数週間かかる手動の計画・設定作業を短縮
✓既存投資の活用: 構築済みの Control Tower / Organizations ベースのランディングゾーンを作り直さず、そのまま移行基盤として活用
✓ガバナンス要件への適合: 管理アカウントへのプログラマティックアクセスを制限する組織でも、DA アカウント経由で利用可能

⚙️ 技術面

✓最小権限での分析: IaC 専用モードでは権限が組織の読み取り・記述系操作に限定され、付与する権限を最小化
✓既存パイプラインとの統合: LZA、Terraform、CDK、独自 CI/CD など既存のデプロイパイプラインと変更管理プロセスに IaC を組み込める
✓ベストプラクティス準拠: 基盤 OU 構造、SCP、アカウント設計が AWS ベストプラクティスに基づいて推奨され、設計品質を担保しやすい

⚠️ デメリット・制約事項

制限事項

✗委任管理者アカウントのコネクタでは直接デプロイ不可 (Control Tower のランディングゾーンを DA アカウントからプロビジョニングできない技術的制約)
✗DA アカウント経由では Control Tower 管理下の既存 SCP の参照・変更不可。変更が必要な場合は管理アカウントへのコネクタ再設定が必要
✗デプロイ済みの OU やアカウントはエージェントから削除不可 (未デプロイの要素のみ削除可能)
✗Security OU は Control Tower 管理のため、エージェント経由でアカウントや SCP を追加できない

考慮すべき点

⚠コネクタのリージョンが Control Tower のホームリージョンおよび IAM Identity Center のリージョンと不一致の場合、Control Tower の初期化が失敗する
⚠LZA 形式でデプロイする場合、AWS Transform のアカウントと LZA インストールが同一の AWS Organization に属している必要がある
⚠移行ウェーブ内のサーバーは同一アカウントに配置される設計原則があり、アカウント分離要件によってはウェーブプランの見直しが必要になる場合がある

🎯 ユースケース

🗼 ユースケース 1: Control Tower 導入済み環境への移行基盤の追加構築

シナリオ: すでに AWS Control Tower でランディングゾーンを運用している企業が、VMware 環境からの大規模移行に向けてワークロードアカウントを整備したい。

実装例: 管理アカウントへのコネクタを作成しフルデプロイモードで接続 → 基盤ギャップ分析で不足 OU (例: Sandbox OU) のみ追加 → 移行ウェーブに基づくワークロード OU とアカウント構造の提案を確認し直接デプロイ

✅ 効果: 既存のランディングゾーンを作り直すことなく、ギャップのみを補完して移行基盤を短期間で整備できる。
🏦 ユースケース 2: 管理アカウントへのアクセスを制限している企業での IaC 生成

シナリオ: セキュリティポリシーにより管理アカウントへのプログラマティックアクセスを許可できない金融機関が、AWS Transform の設計支援のみを活用したい。

実装例: 委任管理者アカウントを作成し DA コネクタで接続 (IaC 専用モード) → 組織の分析と推奨事項の生成 → Terraform 形式で IaC を生成し、チェックサム検証後に社内の変更管理プロセスでレビュー → 社内 CI/CD パイプラインからデプロイ

✅ 効果: 管理アカウントへの権限付与なしで、ベストプラクティスに基づいた設計と IaC を入手し、既存の統制プロセスを維持したままデプロイできる。
🚀 ユースケース 3: LZA を利用中の組織でのワークロードアカウント拡張

シナリオ: Landing Zone Accelerator on AWS でランディングゾーンを管理している組織が、移行ウェーブに合わせたワークロードアカウントの追加設計を効率化したい。

実装例: 移行計画フェーズのウェーブプランを AWS Transform に取り込み → ビジネスユニットと環境分離要件に基づく OU / アカウント構造の提案を確認 → LZA Universal Configuration 形式の YAML を生成し、既存の LZA パイプラインでデプロイ

✅ 効果: 既存の LZA 運用を変更せずに、移行計画と整合したアカウント設計を自動生成し、設計工数を削減できる。

🔗 関連サービス・機能

→AWS Transform for migrations: VMware 環境などからの大規模移行をエージェント型 AI で支援するサービス。本アップデートの対象
→AWS Control Tower: マルチアカウント環境のガバナンスを提供。ランディングゾーンの基盤として利用され、既存環境のギャップ分析の対象

→AWS CDK / Terraform: IaC 専用モードで生成されるアーティファクトの出力形式

📝 まとめ

AWS Transform for migrations が既存の Control Tower および Organizations ベースのランディングゾーンに対応し、 基盤ギャップ分析によって不足分のみを補完できるようになりました。 さらに IaC 専用モードにより、管理アカウントへの直接アクセスを許可できない組織や、 独自のデプロイパイプラインを持つ組織でも利用しやすくなっています。

既存のランディングゾーンを保持したまま大規模移行を計画している場合は、 委任管理者アカウント経由でのギャップ分析と IaC 生成から試すことを推奨します。
