Amazon Neptune

🔄 オンラインインデックス再構築によるストレージ回収

📅 リリース日: 2026 年 10 月 27 日 ｜ 🏷️ 機能: Online Index Rebuild

📝 概要

Amazon Neptune Database が、データベースを稼働させたままインデックスのデフラグと未使用ストレージ領域の回収を実行できる「オンラインインデックス再構築」をサポートしました。 グラフデータベースでは、挿入・更新・削除の繰り返しでフラグメンテーションが蓄積し、データを削除しても VolumeBytesUsed が高止まりしたり、I/O コストが増加する課題がありました。

Gremlin、openCypher、SPARQL の読み取り・書き込みクエリを継続実行しながらインデックスをコンパクト化してストレージを回収し、クエリパフォーマンスを改善できます。

❌ アップデート前の課題

  • データ削除後もフラグメンテーションにより VolumeBytesUsed が高止まりし、ストレージコストを削減できない
  • 断片化したインデックスにより論理データが多くの物理ページに分散し、I/O コストとクエリレイテンシが増加
  • ストレージ回収にはエクスポート・再ロードやクラスター再作成など、ダウンタイムや運用負荷を伴う方法が必要

✅ アップデート後の改善

  • データベースをオンラインに保ったまま、インデックスのデフラグとストレージ回収が可能
  • ライターとリードレプリカの両方で、再構築中も読み取り・書き込みクエリを継続可能
  • スコープ・並列度・書き込みバッファサイズを調整し、影響と速度のバランスを制御可能
  • 80% 安全マージン、適応型スケジューリング、フェイルファストの安全機構を内蔵

管理者がライターインスタンスに対して再構築を開始すると、データベースをオンラインに保ったまま断片化したインデックスがコンパクト化され、未使用ストレージが回収されます。アプリケーションのクエリは再構築中も継続実行でき、リードレプリカは影響を受けません。

⚡ 主要機能

🟢 1. 無停止でのインデックス再構築

  • 再構築中も Gremlin、openCypher、SPARQL の読み取り・書き込みクエリを継続実行できる
  • リードレプリカは影響を受けず、通常どおり読み取りクエリを処理
  • データ損失は発生せず、再構築中の同時書き込みも通常どおりコミット

🎯 2. 柔軟なスコープ指定

  • ALL: クアッドとディクショナリの両方を再構築 (デフォルト)
  • QUADS: クアッドインデックスのみ (OSGP、PZSOG が有効な場合はそれらも対象)
  • DICTIONARIES: ディクショナリインデックスのみ
  • GetStorageInfo で回収可能な領域が多いコンポーネントを特定し、スコープを絞ると高速かつ低影響

🎛️ 3. チューニング可能なパラメータ

  • concurrency: 並列ワーカー数 (1〜ライターの最大 vCPU 数、デフォルト 1)
  • writeBufferSize: 同時書き込み追跡バッファ (LOW / MEDIUM / HIGH、デフォルト LOW)
  • 本番トラフィック並行時は低並列度、メンテナンスウィンドウでは高並列度と使い分け可能

🛡️ 4. ストレージ安全機構

  • 利用可能なボリューム領域に対して 80% の安全マージンを適用したストレージバジェット
  • 空き容量に応じて並列度を自動調整する適応型スケジューリング
  • ストレージ不足時はサイレントスキップせず即座に失敗させるフェイルファスト設計
  • VolumeBytesUsed が 100 TB 超のクラスターはデフォルトで拒否 (AWS サポート経由で対応可能)

🔌 5. ライフサイクル管理 API

  • StartIndexRebuild: 再構築の開始
  • GetIndexRebuildStatus: 進捗率 progressPercentage と推定完了時刻 estimatedEndTime の取得
  • ListIndexRebuilds: 再構築 ID の一覧取得
  • CancelIndexRebuild: ベストエフォートでのキャンセル

✅ 前提条件

✓ライターインスタンスがプロビジョンドインスタンスであること

📑 手順

1

ストレージ使用状況の確認

BashGetStorageInfo
aws neptunedata get-storage-info \
  --endpoint-url https://your-neptune-endpoint:8182

エントリ数に対してインデックスサイズが大きい場合はフラグメンテーションの兆候です。再構築前の VolumeBytesUsed をベースラインとして記録しておきます。

2

インデックス再構築の開始

BashStartIndexRebuild
# すべてのインデックスを再構築 (デフォルト)
aws neptunedata start-index-rebuild \
  --endpoint-url https://your-neptune-endpoint:8182

# クアッドインデックスのみ、並列度 4、書き込みバッファ HIGH で再構築
aws neptunedata start-index-rebuild \
  --endpoint-url https://your-neptune-endpoint:8182 \
  --scope QUADS \
  --concurrency 4 \
  --write-buffer-size HIGH

ライターインスタンスのエンドポイントに対して開始します。レスポンスの rebuildId は進捗確認やキャンセルに使用するため保存しておきます。

3

進捗のモニタリング

BashGetIndexRebuildStatus
aws neptunedata get-index-rebuild-status \
  --endpoint-url https://your-neptune-endpoint:8182 \
  --rebuild-id a1b2c3d4-e5f6-7890-abcd-ef1234567890

進捗率 (progressPercentage) と推定完了時刻 (estimatedEndTime) を定期的にポーリングして確認します。

4

結果の確認

BashGetStorageInfo (再実行)
aws neptunedata get-storage-info \
  --endpoint-url https://your-neptune-endpoint:8182

再構築完了後にストレージサイズの減少を確認します。CloudWatch の VolumeBytesUsed および VolumeBytesLeftTotal メトリクスでも推移を追跡できます。

💡 メリット

💼 ビジネス面

✓ストレージコストの削減: 高止まりしていたストレージ使用量を回収し、ストレージ課金と I/O コストを削減
✓ダウンタイムの排除: 従来はダウンタイムを伴ったストレージ最適化を、サービスを停止せずに実行
✓運用の計画性向上: 四半期ごとなどの定期メンテナンスに組み込みやすく、ストレージ上限到達を予防

🔬 技術面

✓クエリパフォーマンスの改善: コンパクト化により必要な物理ページ数が減り、I/O 効率が向上
✓きめ細かな制御: スコープ・並列度・書き込みバッファサイズで本番への影響を最小化
✓安全性の高い設計: ストレージバジェット、適応型スケジューリング、フェイルファストでストレージ枯渇を防止

⚠️ デメリット・制約事項

🚫 制限事項

✗クラスターあたり同時に実行できる再構築は 1 つのみ
✗Neptune Serverless のライターインスタンスでは実行不可 (リードレプリカはサーバーレスでも可)
✗再構築中はバルクロード API (POST /loader) と高速リセット API (ExecuteFastReset) が CancelledByMaintenanceException で拒否される
✗再構築履歴は直近の 1 件のみメモリ上に保持され、再起動やフェイルオーバーで失われる (永続的な履歴は将来対応予定)
✗VolumeBytesUsed が 100 TB を超えるクラスターでは AWS サポートへの相談が必要
✗再構築中、一部のクエリが一時的に CancelledByMaintenanceException で失敗する可能性がある (指数バックオフでのリトライが必要)

🤔 考慮すべき点

→再構築はバッファキャッシュと I/O をクエリと奪い合うため、小さな影響が出る可能性がある。BufferCacheHitRatio が 99.9% を下回る場合はスケールアップや並列度の低減を検討
→非常に重い同時ワークロードは再構築自体を失敗させる可能性がある。スコープや並列度を下げ、writeBufferSize を上げるか、トラフィックの少ない時間帯に実行
→キャンセルはベストエフォートであり、CANCELLED への到達に数分から数時間かかる場合がある
→フェイルオーバーやエンジン再起動で実行中の再構築は失われるが、データベースは正常に復旧し、再度開始できる
→最大で対象データの約 25% のスクラッチ領域が必要なため、空き容量に余裕を持って実行する

🎯 ユースケース

1️⃣ 大規模データ削除後のストレージ回収

シナリオ: 古いグラフデータを大量に削除したが、VolumeBytesUsed が削除前とほぼ変わらず、ストレージコストが下がらない。

Bash実装例
# ストレージ内訳を確認し、回収可能な領域を特定
aws neptunedata get-storage-info --endpoint-url https://your-neptune-endpoint:8182

# クアッドインデックスに絞って再構築
aws neptunedata start-index-rebuild \
  --endpoint-url https://your-neptune-endpoint:8182 \
  --scope QUADS

✅ 効果: 削除済みデータが占有していた断片化領域を回収し、VolumeBytesUsed とストレージ課金を実データ量に見合った水準まで削減できる。

2️⃣ ストレージ上限接近時の対処

シナリオ: クラスターのストレージ使用量が上限に近づいており、容量を確保する必要があるが、サービス停止は許容できない。

Bash実装例
# 本番トラフィックへの影響を抑えるため低い並列度で実行
aws neptunedata start-index-rebuild \
  --endpoint-url https://your-neptune-endpoint:8182 \
  --scope ALL \
  --concurrency 1 \
  --write-buffer-size MEDIUM

✅ 効果: サービスを稼働させたままストレージの空き容量を確保し、ストレージ上限到達による障害を未然に防げる。

3️⃣ 定期メンテナンスによるパフォーマンス維持

シナリオ: 更新頻度の高いグラフワークロードで、時間の経過とともにクエリレイテンシが悪化している。メンテナンスウィンドウ内で短時間に最適化したい。

Bash実装例
# メンテナンスウィンドウ中に高い並列度で高速に再構築
aws neptunedata start-index-rebuild \
  --endpoint-url https://your-neptune-endpoint:8182 \
  --scope ALL \
  --concurrency 8 \
  --write-buffer-size LOW

✅ 効果: 四半期ごとなどの定期実行によりインデックスを最適な状態に保ち、I/O 効率とクエリパフォーマンスを安定的に維持できる。ライターインスタンスを一時的にスケールアップすることで再構築時間をさらに短縮できる。

💰 料金・利用可能リージョン

💵 料金

オンラインインデックス再構築機能自体の追加料金に関する記載は、公式発表にはありません。再構築によりフラグメンテーションが解消されることで、ストレージ使用量と I/O コストの削減が期待できます。再構築中は一時的にスクラッチ領域 (最大で対象データの約 25%) を使用する点に注意してください。詳細は Amazon Neptune の料金ページを参照してください。

🌍 利用可能リージョン

Amazon Neptune Database が利用可能なすべての AWS リージョンで利用できます。Neptune エンジンリリース 1.5.0.0 以降が必要です。

🔗 関連サービス・機能

🔍 GetStorageInfo API

ストレージ使用状況の内訳を分析し、フラグメンテーションや回収可能な領域を特定する。再構築の前後で実行して効果を定量化する。

📊 Amazon CloudWatch

VolumeBytesUsed、VolumeBytesLeftTotal、BufferCacheHitRatio メトリクスで再構築の効果と影響をモニタリングする。

🧬 Neptune 高速クローン

書き込みを完全に停止できるワークロードでは、クローン上で再構築を実行してエンドポイントを切り替える代替手法も選択できる。

📌 まとめ

オンラインインデックス再構築により、Amazon Neptune のストレージ最適化がダウンタイムなしで実行可能になりました。 データ削除後に VolumeBytesUsed が高止まりしているクラスターや、長期運用でクエリパフォーマンスが低下しているクラスターでは、まず GetStorageInfo でフラグメンテーションの状況を確認し、エンジンリリース 1.5.0.0 以降へのアップグレードと再構築の実施を検討することを推奨します。

アプリケーション側では CancelledByMaintenanceException に対する指数バックオフのリトライ実装を事前に組み込んでおくことが重要です。
