Amazon EMR on EKS

🤖 Apache Spark
トラブルシューティングエージェント

自然言語で Spark ジョブの失敗を診断。自動化された根本原因分析と PySpark コードの推奨事項を提示し、EMR のすべてのデプロイオプションに対応
2026 年 7 月 10 日
リリース

📌 概要

Amazon EMR on EKS が Apache Spark トラブルシューティングエージェントに対応しました。データエンジニアは自然言語を使って Spark ジョブの失敗を診断でき、エージェントが自動的に根本原因分析 (root cause analysis) を実行し、修正のための PySpark コードの推奨事項を提示します。

このエージェントは、Spark History Server のデータ、分散環境のエグゼキューターログ、クラスター構成を分析し、メモリエラー、データスキュー、リソース競合、接続障害といった問題を特定します。従来は複数のログやメトリクスを手動で調査する必要があった原因究明を、AI が支援することで大幅に効率化します。

🧭 今回のリリースにより、トラブルシューティングエージェントは EMR on EC2、EMR Serverless、EMR on EKS のすべてのデプロイオプションをカバーするようになりました。EMR on EKS コンソールの [Troubleshoot with AI] のほか、MCP を通じて Kiro、Claude Code、Cursor などの AI コーディングエージェントからも利用できます。
🔴 アップデート前の課題
  • Spark ジョブが失敗した際に、分散環境に散在するエグゼキューターログや Spark History Server のデータを手動で調査する必要があった
  • メモリエラーやデータスキューなどの原因を特定するために、Spark に関する深い専門知識が求められた
  • EMR on EKS ではトラブルシューティングエージェントを利用できず、根本原因分析を自動化する手段が限られていた
🟢 アップデート後の改善
  • 自然言語でジョブの失敗を診断し、自動化された根本原因分析を受け取れるようになった
  • メモリエラー、データスキュー、リソース競合、接続障害の特定と PySpark コードの推奨が可能になった
  • EMR on EC2、EMR Serverless、EMR on EKS のすべてのデプロイオプションでエージェントが利用可能になった

失敗した Spark ジョブの診断データをエージェントが分析し、根本原因分析と PySpark の推奨事項を生成する流れを示しています。すべての操作は読み取り専用で IAM 認証され、AWS CloudTrail に記録されます。

🚀 主要機能

💬 自然言語によるジョブ失敗の診断
  • データエンジニアは自然言語でジョブの失敗について問い合わせできる
  • 分散ログや構成を手動で調査することなく、自動化された根本原因分析を受け取れる
  • 診断結果とあわせて、修正のための PySpark コードの推奨事項が提示される
🔍 複数データソースの自動分析
  • Spark History Server のデータを分析
  • 分散環境のエグゼキューターログを分析
  • クラスター構成を分析し、メモリエラー、データスキュー、リソース競合、接続障害を特定
☁️ すべての EMR デプロイオプションのサポート
  • 今回の EMR on EKS 対応により、EMR on EC2、EMR Serverless、EMR on EKS のすべてのデプロイオプションをカバー
  • 一貫したトラブルシューティング体験を EMR 全体で提供
🔌 複数のアクセス手段
  • EMR on EKS コンソールの失敗したジョブに表示される [Troubleshoot with AI] から利用可能
  • MCP を通じて Kiro、Claude Code、Cursor などの AI コーディングエージェントから利用可能

🎯 検出可能な問題

🧠 メモリエラー
OutOfMemory などのメモリ関連の失敗を特定し、メモリ設定やパーティション調整を推奨
⚖️ データスキュー
特定タスクへのデータ偏りを検出し、パーティション再分散などの改善策を提示
🔀 リソース競合
エグゼキューターやクラスターリソースの競合状態を分析
🔗 接続障害
分散環境での接続失敗を特定し、原因を明確化

🛠️ 設定方法

前提条件

  • Amazon EMR on EKS で Spark ジョブを実行していること
  • トラブルシューティングエージェントの利用に必要な IAM 権限が付与されていること
  • MCP 経由で利用する場合は、対応する AI コーディングエージェント (Kiro、Claude Code、Cursor など) を用意すること

ステップ 1: EMR on EKS のコンソールで、失敗したジョブを選択し、[Troubleshoot with AI] を選択します。エージェントが診断を開始し、根本原因分析と推奨される修正内容を提示します。

ステップ 2: MCP から利用する場合は、AI コーディングエージェント (Kiro、Claude Code、Cursor など) に MCP サーバーを設定します。設定後は、開発ツールから自然言語で EMR on EKS のジョブ失敗について診断を依頼できます。

💡 メリット

💼 ビジネス面

  • 障害復旧時間の短縮: 根本原因分析の自動化により、ジョブ失敗の原因究明にかかる時間を削減できる
  • 専門知識への依存の軽減: 自然言語での診断により、Spark の深い専門知識がなくても問題を特定しやすくなる
  • 運用の一貫性: すべての EMR デプロイオプションで同じトラブルシューティング体験を提供

🔧 技術面

  • 包括的な分析: Spark History Server、エグゼキューターログ、クラスター構成を横断的に分析
  • 実践的な推奨事項: 診断結果とあわせて PySpark コードの推奨が得られる
  • 既存ワークフローへの統合: MCP を通じて Kiro、Claude Code、Cursor などの開発ツールから直接利用できる

⚠️ デメリット・制約事項

制限事項

  • 利用可能リージョンは Amazon SageMaker Unified Studio が利用可能なリージョンに限られる
  • エージェントは読み取り専用で動作するため、修正の適用はユーザーが手動で行う必要がある

考慮すべき点

  • 診断精度は Spark History Server のデータやログの完全性に依存する
  • MCP 経由で利用する場合は、対応する AI コーディングエージェントの準備と設定が必要

🎯 ユースケース

🧠 ユースケース 1: メモリエラーの診断
シナリオ: EMR on EKS で実行した Spark ジョブが OutOfMemory エラーで失敗した状況。
効果: エージェントがエグゼキューターログとクラスター構成を分析し、メモリエラーの原因を特定して、メモリ設定やパーティション調整に関する PySpark コードの推奨事項を提示。
⚖️ ユースケース 2: データスキューの特定
シナリオ: 特定のタスクだけが極端に遅く、ジョブ全体のパフォーマンスが低下している状況。
効果: エージェントが Spark History Server のデータを分析し、データスキューを検出して、パーティション再分散などの改善策を推奨。
🔌 ユースケース 3: AI コーディングエージェントからの診断
シナリオ: 開発者が Claude Code や Cursor などのツールで開発しながら、EMR on EKS のジョブ失敗を確認したい状況。
効果: MCP を通じて開発ツールから自然言語で診断を依頼でき、コンテキストを切り替えることなく根本原因分析と修正案を得られる。

✅ まとめ

Apache Spark トラブルシューティングエージェントの EMR on EKS 対応により、Amazon EMR のすべてのデプロイオプションで自然言語による自動化されたジョブ診断が可能になりました。Spark History Server、エグゼキューターログ、クラスター構成を横断的に分析し、根本原因分析と実践的な PySpark コードの推奨を迅速に提示します。

Spark ジョブの障害対応に時間を要しているチームは、コンソールの [Troubleshoot with AI] や MCP 連携を活用し、まずは失敗したジョブでエージェントを試して、既存の運用ワークフローへの組み込みを検討することをおすすめします。
