AWS Lambda

⚡ AWS Lambda MicroVMs

分離・速度・状態保持を同時に実現する新しいサーバーレスコンピューティングプリミティブ
リリース日
2026-06-22

📌 概要

AWS は、ユーザーや AI が生成したコードを隔離された環境で実行するための新しいプリミティブ「AWS Lambda MicroVMs」を発表しました。 VM レベルの分離、ほぼ瞬時の起動・再開、セッションの状態保持を同時に提供し、仮想化インフラを管理せずに安全にコードを実行できます。

Lambda Function の月間 15 兆回超の呼び出しを支える Firecracker 仮想化技術の上に構築。 Dockerfile から MicroVM イメージを作成し、最大 8 時間にわたって一時停止 (suspend) / 再開 (resume) できます。

3 つの要素を同時に実現

🔒
分離
VM レベルでテナント間を強力に分離
⚡
速度
スナップショットからほぼ瞬時に起動・再開
💾
状態保持
メモリ・ディスク状態を保持したまま継続

🔄 アップデートによる変化

😓 Before：従来の課題
  • 強力な分離のため、自前で仮想化インフラやネットワークを構築・管理する必要
  • コンテナは起動が速い一方、VM レベルの分離やフル OS 機能を得にくい
  • アイドル維持は無駄なコスト、停止すると状態が失われる
🎉 After：改善後
  • インフラ管理なしでユーザー/ジョブごとに VM 分離環境を割り当て
  • スナップショット再開でマルチ GB セッションもほぼ瞬時に起動
  • アイドル時に一時停止し状態保持のままコスト削減、復帰時に完全復元

🏗️ アーキテクチャ / ライフサイクル

sequenceDiagram
    participant Dev as 👤 開発者
    participant API as 🔌 Lambda MicroVMs API
    participant S3 as 🪣 Amazon S3
    participant Img as 📦 MicroVM イメージ
    participant VM as 🖥️ MicroVM
    participant User as 👥 エンドユーザー

    Note over Dev,Img: イメージ作成フェーズ
    Dev->>S3: コードと Dockerfile を zip でアップロード
    Dev->>API: create-microvm-image を呼び出し
    API->>S3: アーティファクトを取得
    API->>Img: Dockerfile 実行 + アプリ初期化後にスナップショット取得

    Note over Dev,VM: 起動フェーズ
    Dev->>API: run-microvm を呼び出し
    API->>Img: スナップショットから復元
    API->>VM: MicroVM を起動
    API-->>Dev: 専用 HTTPS URL を返却

    Note over User,VM: 実行フェーズ
    User->>VM: HTTPS リクエスト + 認証ヘッダー
    VM-->>User: レスポンス

    Note over API,VM: ライフサイクル管理
    API->>VM: アイドル時に suspend-microvm
    User->>API: 再アクセス時に resume-microvm
    API->>VM: 状態を完全に復元
    Dev->>API: セッション終了時に MicroVM を終了

イメージ作成 → 起動 → 専用 HTTPS エンドポイント提供 → 一時停止・再開・終了までのライフサイクル

✨ 主要機能

🚀 スナップショットベースの高速起動
  • 事前初期化されたスナップショットから再開し、初期化処理をスキップ
  • コールドブートではなく復元のため、マルチ GB セッションもほぼ瞬時に起動
  • インストール済みパッケージ・ロード済みモデル・ファイルセットを保持
🔁 ライフサイクル制御
  • suspend / resume / terminate をプログラムまたはアイドルポリシーで制御
  • アイドル時の一時停止でメモリ・ディスク状態を保持したままコスト削減
  • 復帰時に状態を完全復元し「中断がなかったかのように」継続
🌐 柔軟なネットワーキング
  • 各 MicroVM に専用 HTTPS エンドポイント、ロードバランサー/イングレス不要
  • HTTP/2、gRPC、WebSockets をサポート
  • サービス提供の JWE 認証、egress はパブリック/VPC アクセスを設定可能
📊 柔軟なリソース割り当て
  • ベースラインでプロビジョニングし、ピーク時はベースラインの最大 4 倍まで垂直スケール
  • 実行中はベースライン料金、超過分はアクティブ使用時間のみ課金

主要な API オペレーション

オペレーション説明
create-microvm-imageDockerfile とコードからイメージを作成し、初期化済み環境のスナップショットを取得
run-microvmスナップショットから MicroVM を起動し、専用 HTTPS エンドポイントを返却
suspend-microvm実行中の MicroVM を一時停止し、状態を保持したままコスト削減
resume-microvm一時停止した MicroVM をメモリ・ディスク状態を保ったまま再開

アイドルポリシーの設定例

JSON15 分アイドルで自動 suspend、次のリクエストで自動 resume
{
  "maxIdleDurationSeconds": 900,
  "suspendedDurationSeconds": 300,
  "autoResumeEnabled": true
}

🛠️ 設定方法

前提条件

  • コードと Dockerfile を格納する Amazon S3 バケット
  • イメージビルド用の IAM ロールと MicroVM 実行用の IAM ロール
  • MicroVMs を利用可能なリージョンの AWS アカウント

ステップ 1: Dockerfile を準備して S3 にアップロード

DockerfileMicroVMs 用ベースイメージから構築
FROM public.ecr.aws/lambda/microvms:al2023-minimal
RUN dnf install -y python3 python3-pip && dnf clean all
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY app.py .
EXPOSE 5000
CMD ["gunicorn", "--bind", "0.0.0.0:5000", "app:app"]

ステップ 2: MicroVM イメージを作成

Bashcreate-microvm-image
aws lambda-microvms create-microvm-image \
  --code-artifact uri=<path/to/s3/artifact.zip> \
  --name <VM_image_name> \
  --base-image-arn arn:aws:lambda:us-east-1:aws:microvm-image:al2023-1 \
  --build-role-arn <IAM role ARN>

ビルドログは CloudWatch /aws/lambda/microvms/<image-name> にストリーミングされます。

ステップ 3: MicroVM を起動してトラフィックを送信

Bashrun-microvm
aws lambda-microvms run-microvm \
  --image-identifier arn:aws:lambda:<region>:<acct>:microvm-image:my-image \
  --execution-role-arn arn:aws:iam::<acct>:role/MicroVMExecutionRole \
  --idle-policy '{"maxIdleDurationSeconds":900,"suspendedDurationSeconds":300,"autoResumeEnabled":true}'

ネットワーク設定は不要。クライアントは短期認証トークンを X-aws-proxy-auth ヘッダーに付与してエンドポイントへリクエストします。

💡 メリット

📈 ビジネス面
  • インフラ管理の排除：仮想化基盤・LB・イングレスの構築運用が不要
  • アイドルコストの削減：状態を保持したまま実行コストを抑制
  • AI ワークロード最適化：AI 生成コードを安全に隔離実行
⚙️ 技術面
  • VM レベルの分離：フル OS 機能を持つ強力に分離された環境
  • 状態保持と高速再開：スナップショットからほぼ瞬時に復元
  • 柔軟なリソーススケール：ベースラインの最大 4 倍まで垂直スケール

⚠️ デメリット・制約事項

制限事項

  • 利用可能リージョンが 5 リージョンに限定 (バージニア北部・オハイオ・オレゴン・東京・アイルランド)
  • アーキテクチャは ARM64 に限定
  • 1 MicroVM あたり最大 16 vCPU / 32 GB メモリ / 32 GB ディスク / 8 時間の上限

考慮すべき点

  • 初期化時に一意コンテンツ生成や接続確立を行うアプリは、サービス提供のフックとの統合が必要な場合あり
  • イベント駆動型・リクエスト/レスポンス型は引き続き Lambda Function が適しており、相互補完的に使い分け
  • ビルドは Dockerfile を S3 にアップロードする運用が前提、CI/CD への組み込みを検討

🎯 ユースケース

1️⃣ インタラクティブなコーディング環境
SaaS 型オンライン IDE で、各ユーザーに隔離された編集・実行環境を提供。離席中はコストを抑え、復帰時は即座に再開。
ユーザーログイン時: run-microvm で専用 MicroVM を起動 アイドル 15 分後: ポリシーにより自動 suspend 再アクセス時: autoResumeEnabled により自動 resume (状態を完全復元)
✓ 強力に分離された環境を提供しつつ、アイドルコストを削減し作業状態を維持
2️⃣ AI 生成コードの実行サンドボックス
コーディングアシスタントが生成したコードを安全に実行・検証。信頼できないコードがホストやほかのテナントに影響しないようにする。
AI がコード生成 -> run-microvm で使い捨て MicroVM を起動 -> HTTPS エンドポイント経由でコードを実行・結果取得 -> セッション終了時に MicroVM を終了してリソース解放
✓ VM レベルの分離で AI 生成コードを安全に隔離実行、ジョブごとに新鮮な環境を高速起動
3️⃣ 脆弱性スキャンプラットフォーム
マルチテナントのセキュリティスキャンサービスで、各ジョブを隔離環境で実行しテナント間のデータ漏洩を防止。
スキャンジョブ受付 -> ジョブ専用 MicroVM を run-microvm で起動 -> 隔離環境内でスキャンツールを実行 -> 結果取得後に MicroVM を終了
✓ ジョブごとに独立した環境でテナント分離を担保、高速起動でスループット向上

📝 まとめ

AWS Lambda MicroVMs は、これまでトレードオフの関係にあった「分離」「速度」「状態保持」を同時に実現する新しいサーバーレスコンピューティングプリミティブです。 インタラクティブなコーディング環境、AI サンドボックス、脆弱性スキャンなどマルチテナントでコードを実行するアプリケーションを構築している場合は、 まず Dockerfile から MicroVM イメージを作成し、東京リージョンを含む利用可能リージョンで起動して、アイドルポリシーによるコスト最適化を含めた挙動を検証することをお勧めします。
