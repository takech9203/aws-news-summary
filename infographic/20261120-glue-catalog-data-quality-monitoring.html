🗄️ カタログ / データベースレベルの
データ品質モニタリング

📅 リリース日: 2026 年 11 月 20 日 | Data Quality Monitoring for Catalogs and Databases

📌 概要

AWS Glue Data Catalog に、カタログおよびデータベースレベルのデータ品質モニタリング機能が追加されました。 1 つの「データ品質評価設定」を作成するだけで、スコープ内のすべてのテーブルを一括でプロファイリング・評価できます。 後から追加されたテーブルも自動的に評価対象となるため、テーブルごとの個別セットアップや手動実行は不要です。

組み込みルールセット (SIMPLE / ADVANCED) と独自 DQDL ルールセットの両方に対応し、トリガーは「作成時に 1 回」「スケジュール」「メタデータ変更時 (Apache Iceberg のコミットを含む)」から組み合わせ可能。3 回以上の評価実行後は異常検知が統計のドリフトを自動でフラグします。

❌ Before: アップデート前の課題
  • 品質評価はテーブル単位で設定が必要。数百〜数千テーブル規模では設定・運用の負荷が大きい
  • 新しいテーブルが追加されるたびに、誰かが忘れずに品質チェックを設定する必要があった
  • データ変更のたびに評価するには、スケジューラーやイベント連携を自前で構築する必要があった
✅ After: アップデート後の改善
  • カタログ / データベース / テーブルの各レベルで 1 つの設定を作るだけで一括評価
  • 後から追加されたテーブルも自動的に評価対象に含まれ、設定漏れを防止
  • メタデータ変更 (Iceberg コミット含む) やスケジュールで継続的なモニタリングが可能
  • 明示ルール外の統計変化も異常検知で自動検出

1 つのデータ品質評価設定が、選択したトリガーに応じてスコープ内のすべてのテーブル (新規テーブルを含む) に対して評価実行を開始し、結果を API・Data Catalog テーブル・Amazon S3 で利用できる流れを示しています。

⚙️ 主要機能

1️⃣ カタログ / データベース / テーブルレベルの一括設定
  • CATALOG、DATABASE、TABLE の 3 レベルで評価設定を作成可能
  • TableNamePattern (glob パターン、例: orders_*) でスコープ内のテーブルを絞り込み可能
  • トリガー発火のたびにスコープを再評価。追加テーブルは自動的に対象へ、削除テーブルは自動的に対象外に
  • 設定が重複した場合は、より具体的なレベルが優先 (テーブル > データベース > カタログ)
2️⃣ 柔軟なトリガー
  • ONCE: 設定作成の約 1 分後に全テーブルを 1 回評価。以後、新規テーブルも作成時に 1 回評価
  • SCHEDULE: cron 式 (例: cron(0 6 * * ? *)) または rate 式 (例: rate(12 hours)) で定期実行。UTC 基準、最短 1 時間に 1 回。StartAt / EndAt で期間限定も可能
  • METADATA_CHANGE: スキーマ変更、テーブルプロパティ更新、ストレージ形式変更、Apache Iceberg のコミットなどをトリガーに評価
  • 複数トリガーの組み合わせが可能。各テーブルの評価は全設定・全トリガーを通じて最大 1 時間に 1 回に制限
3️⃣ 組み込みルールセットと独自 DQDL ルールセット
  • SIMPLE (デフォルト): RowCount、ColumnCount、Completeness、最小値 / 最大値、ColumnLength、Mean、Sum、StandardDeviation などを収集。シャッフル不要で最も低コスト
  • ADVANCED: SIMPLE に加えて Uniqueness、Entropy、DistinctValuesCount、Distribution を収集
  • 独自ルールセット: CreateDataQualityRuleset で作成した DQDL ルールセットを指定し、「すべてのテーブルは 1 行以上」のような組織標準を一律適用
4️⃣ 異常検知との連携
  • テーブルごとに 3 回以上評価を実行すると、統計値が期待範囲を外れた場合に異常としてフラグ
  • 明示的なルールで定義していない変化も検出可能。デフォルトで有効 (ObservationScope を NONE で無効化可能)
5️⃣ 結果の活用
  • 結果は各テーブルに紐づけて保存され、GetDataQualityResult、BatchGetDataQualityResult、ListDataQualityResults で取得可能
  • EvaluationRunMode (EVALUATION_CONFIG / ON_DEMAND) で設定由来とオンデマンドの結果を区別
  • 結果を Data Catalog 内の Apache Iceberg テーブルまたは Amazon S3 に書き出し可能
  • 結果到着時に Amazon EventBridge へイベントが発行され、アラートや通知を構築可能
6️⃣ Amazon SageMaker Unified Studio 統合
  • カタログページから、カタログまたはデータベース単位のプロファイリングを直接有効化可能

🛠️ 設定方法

✅ 前提条件

✓AWS Glue Data Catalog に、Amazon S3 または Amazon S3 Tables のデータを持つテーブルが 1 つ以上存在すること
✓評価設定のオペレーションを含む最新バージョンの AWS CLI または AWS SDK を使用すること
✓評価設定の管理権限と、設定用 IAM ロールの iam:PassRole 権限があること。Lake Formation 使用時は対象カタログ / データベース / テーブルへの Lake Formation 権限も必要 (ロールが DESCRIBE できないテーブルはスキップされ、データ読み取りには列・行フィルタなしの SELECT 権限が必要)

ステップ 1: 設定用 IAM ロールの作成

BashIAM ロールの作成
aws iam create-role \
  --role-name DataQualityEvaluationConfigRole \
  --assume-role-policy-document file://trust-policy.json

aws iam put-role-policy \
  --role-name DataQualityEvaluationConfigRole \
  --policy-name DataQualityEvaluationConfigPolicy \
  --policy-document file://permissions-policy.json

AWS Glue が引き受ける信頼ポリシーと、スコープ内のテーブル検出・評価実行・データ読み取りに必要な権限ポリシーを持つロールを作成します。ポリシーの内容は公式ドキュメントのテンプレートを使用します。

ステップ 2: データ品質評価設定の作成

Bashデータベースレベルの評価設定
aws glue create-data-quality-evaluation-config \
  --name my-database-config \
  --level DATABASE \
  --data-source '{
    "GlueTables": {
      "CatalogId": "111122223333",
      "DatabaseName": "my_database"
    }
  }' \
  --role DataQualityEvaluationConfigRole

ルールセットとトリガーを省略した場合、SIMPLE 組み込みルールセットと ONCE トリガーが使用され、約 1 分後にデータベース内の全テーブルの評価が開始されます。カタログ全体を毎日プロファイリングする場合は、--level CATALOG と --triggers SCHEDULE --schedule-expression "rate(24 hours)" を指定します。

ステップ 3: 結果の確認

Bash評価結果の一覧
aws glue list-data-quality-results \
  --filter '{
    "DataSource": {
      "GlueTable": {
        "DatabaseName": "my_database",
        "TableName": "my_table"
      }
    },
    "EvaluationRunMode": "EVALUATION_CONFIG",
    "DataQualityEvaluationConfig": "my-database-config"
  }'

テーブル・実行モード・設定名でフィルタして結果を一覧します。組み込みルールセットの場合は、結果の ProfileId を取得して aws glue list-data-quality-statistics --profile-id <profile-id> で収集された統計を確認します。

ステップ 4: 設定の管理 (必要に応じて)

Bash一時停止と再開
# 一時停止
aws glue update-data-quality-evaluation-config \
  --name my-database-config --pause-runs

# 再開
aws glue update-data-quality-evaluation-config \
  --name my-database-config --no-pause-runs

SCHEDULE または METADATA_CHANGE トリガーを含む設定は、削除せずに一時停止・再開できます。一時停止中は新規テーブルを含めて評価されず、停止中に逃した評価が後から実行されることはありません。

💡 メリット

💼 ビジネス面

✓運用負荷の大幅な削減: テーブルごとの個別設定が不要になり、数千テーブル規模のデータレイクでも 1 つの設定で監視可能
✓ガバナンスの標準化: 「すべてのテーブルは 1 行以上」「キー列は 99% 以上 complete」のような組織全体の品質基準を一律適用
✓データ信頼性の向上: 不正なデータが下流の分析・ML・レポートに到達する前に検出し、意思決定への悪影響を防止

🔧 技術面

✓新規テーブルの自動カバレッジ: トリガー発火時にスコープを再評価するため、追加テーブルも設定変更なしで監視対象に
✓Iceberg との親和性: METADATA_CHANGE トリガーで Apache Iceberg の各コミットを契機とした評価が可能
✓既存エコシステムとの統合: Data Quality API、EventBridge 連携、Data Catalog テーブル / S3 への書き出し、異常検知とそのまま連携
✓柔軟な優先順位制御: カタログ全体は低コストな SIMPLE で日次評価しつつ、重要テーブルだけ高頻度・厳格なルール評価に

⚠️ デメリット・制約事項

🚧 制限事項

✗各テーブルの評価は全設定・全トリガーを通じて最大 1 時間に 1 回 (ユーザー自身が開始するオンデマンド実行には影響しない)
✗評価設定はアカウント・リージョンごとに最大 1,000 件。評価実行は同時実行クォータに、統計は保存クォータにカウント
✗JDBC 経由のフェデレーテッドカタログのテーブル、JDBC 接続テーブル、Amazon Athena ビュー以外のビューはスキップされる
✗評価は保存後のデータ (data at rest) に対して実行され、データを書き込むジョブをブロック・停止するものではない (書き込み前のチェックには AWS Glue ETL ジョブのデータ品質機能を使用)
✗設定の名前・レベル・カタログは後から変更できない (変更するには新しい設定を作成)

🤔 考慮すべき点

⚠書き込み頻度が高い Iceberg テーブルで METADATA_CHANGE トリガーを使うと評価回数が増えコストがかさむため、SCHEDULE トリガーの利用を検討する
⚠カタログ / データベースレベルで独自ルールセットを使う場合、存在しない列を参照するルールはそのテーブルで失敗するため、RowCount > 0 のような汎用ルールを使い、テーブル固有のルールはテーブルレベル設定に分離する
⚠組み込みルールセットはアナライザーのみで構成されるため、ルールの合否結果や行レベル結果は生成されない (必要な場合は独自ルールセットを使用)
⚠ADVANCED ルールセットはデータのシャッフルを伴うため、特に distinct 値の多い列では SIMPLE よりコストが高くなる

🎯 ユースケース

📊 ユースケース 1: カタログ全体のベースラインプロファイリング

シナリオ: データレイク全体のテーブルについて、行数・欠損率・値の範囲などの基礎統計を毎日自動収集し、データの健全性を可視化したい。

Bashカタログレベル + 日次スケジュール
aws glue create-data-quality-evaluation-config \
  --name my-catalog-config \
  --level CATALOG \
  --data-source '{"GlueTables": {"CatalogId": "111122223333"}}' \
  --managed-ruleset-name SIMPLE \
  --triggers SCHEDULE \
  --schedule-expression "rate(24 hours)" \
  --role DataQualityEvaluationConfigRole
✅ 効果: 新規テーブルを含むカタログ内の全テーブルが毎日プロファイリングされ、統計の履歴が蓄積されて異常検知の学習データにもなる。
🔒 ユースケース 2: 重要テーブルの厳格な監視

シナリオ: カタログ全体は日次の軽量プロファイリングで監視しつつ、課金処理に使う重要テーブルだけは毎時、独自ルールで厳格にチェックしたい。

Bash独自 DQDL ルール + テーブルレベル設定
aws glue create-data-quality-ruleset \
  --name billing-ruleset \
  --ruleset 'Rules = [
    RowCount > 0,
    IsComplete "customer_id",
    IsUnique "transaction_id"
  ]'

aws glue create-data-quality-evaluation-config \
  --name billing-table-config \
  --level TABLE \
  --data-source '{
    "GlueTables": {
      "CatalogId": "111122223333",
      "DatabaseName": "finance",
      "TableNamePattern": "billing_transactions"
    }
  }' \
  --ruleset-name billing-ruleset \
  --triggers SCHEDULE \
  --schedule-expression "cron(0 * * * ? *)" \
  --role DataQualityEvaluationConfigRole
✅ 効果: テーブルレベル設定がカタログレベル設定より優先され、重要テーブルのみ高頻度・厳格なルールで評価される。他のテーブルはカタログレベル設定で引き続き評価される。
🧊 ユースケース 3: Iceberg テーブルの変更追従モニタリング

シナリオ: ストリーミングやバッチで更新される Apache Iceberg テーブル群について、スキーマ変更やデータ更新のたびに品質を評価し、統計の異常なドリフトを検出したい。

BashMETADATA_CHANGE + SCHEDULE の組み合わせ
aws glue create-data-quality-evaluation-config \
  --name iceberg-monitoring-config \
  --level DATABASE \
  --data-source '{
    "GlueTables": {
      "CatalogId": "111122223333",
      "DatabaseName": "lakehouse_db",
      "TableNamePattern": "events_*"
    }
  }' \
  --managed-ruleset-name ADVANCED \
  --triggers SCHEDULE METADATA_CHANGE \
  --schedule-expression "rate(12 hours)" \
  --role DataQualityEvaluationConfigRole
✅ 効果: Iceberg のコミットを含むメタデータ変更のたびに評価が実行され、3 回以上の実行後は異常検知が期待範囲外の統計値を自動でフラグする。EventBridge 連携でアラートも構築できる。

💰 料金

評価設定自体に料金はかかりません。設定が開始する各評価実行は、標準の AWS Glue Data Quality の DPU 時間課金で請求されます。

コスト制御の方法

✓TableNamePattern でスコープ内のテーブルを限定する
✓PreProcessingQuery で各テーブルの一部 (例: 直近 7 日分) のみを評価する
✓広いスコープの設定には低コストな SIMPLE ルールセットを選択する
✓データの変更頻度に合ったトリガーを選択する (更新頻度の高い Iceberg テーブルには METADATA_CHANGE ではなく SCHEDULE を検討)

詳細は AWS Glue 料金ページ を参照してください。

📝 まとめ

AWS Glue Data Catalog のカタログ / データベースレベルのデータ品質モニタリングにより、テーブルごとの個別設定なしで、データレイク全体の品質監視を 1 つの設定で実現できるようになりました。 新規テーブルの自動カバレッジ、Iceberg コミット連動のトリガー、異常検知との統合により、大規模環境でのデータガバナンスの運用負荷が大きく下がります。

まずは低コストな SIMPLE ルールセットと日次スケジュールでカタログ全体のベースラインプロファイリングを開始し、重要テーブルには独自 DQDL ルールによるテーブルレベル設定を追加することを推奨します。
