AWS Parallel Computing Service (PCS)

🔄 Slurm メジャーバージョンの
インプレースアップグレード

既存クラスターを再構築せず、ジョブを止めずに移行
2026-06-30
リリース日

📌 概要

AWS PCS が、既存クラスターに対するマネージドな Slurm インプレースメジャーバージョンアップグレードに対応。 クラスターを最大 3 メジャーバージョン先まで、実行中のジョブを中断することなく移行できます。

PCS は HPC (ハイパフォーマンスコンピューティング) ワークロードを Slurm で実行・スケーリングするマネージドサービスです。 今回のアップデートでは、コントローラー・アカウンティングデータベース・REST API といった PCS が管理するすべての Slurm コンポーネントのアップグレードを PCS 側が処理します。 アップグレードは Console、CLI、または UpdateCluster API でターゲットバージョンを指定するだけで開始できます。

❌ Before (これまで)
✗メジャーバージョン更新にはクラスターインフラの再構築が必要
✗実行中ジョブやアカウンティングデータへの影響を慎重に管理
✗各コンポーネントを個別に手動で更新する必要
✅ After (今回のアップデート)
✓インフラの再構築なしでバージョンアップグレード
✓実行中ジョブを中断せずにアップグレード
✓PCS 管理コンポーネントを一括でアップグレード

⚡ 主要機能

1. マネージドなインプレースアップグレード

  • 既存クラスターのインフラを再構築せずに Slurm メジャーバージョンを更新
  • 1 回の更新で最大 3 メジャーバージョン先まで移行 (4 つ以上先は複数ステップに分割)
  • Console、CLI、UpdateCluster API のいずれからでも実行可能

2. PCS マネージドコンポーネントの一括更新

  • Slurm コントローラーをターゲットのメジャーバージョンへ移行
  • アカウンティング有効時は、アカウンティングデータベースのデータをアップグレード後も保持
  • Slurm REST API 有効時は、UpdateCluster の一環として自動的に新バージョンへ更新

3. 実行中ジョブへの配慮

  • ローリング更新では、コンピュートノード上の実行中ジョブはコントローラーの一時停止に依存せず継続実行
  • キュー中のジョブは操作完了後に再開
  • アップグレード後、お客様の都合に合わせてコンピュートノードを新バージョンへ更新

🔧 技術仕様: バージョン互換性

1 回の更新で 3 つを超えるメジャーバージョンをスキップすることはできません。 ターゲットが 3 メジャーバージョン以上先の場合は複数の連続したステップで更新します。 クラスターとすべてのコンピュートノードは、更新開始前に同じ Slurm バージョンで動作している必要があります。

現在のクラスターバージョン互換性のあるターゲットバージョン
25.11該当なし (最新)
25.0525.11
24.11 (EOL)25.11, 25.05
24.05 (EOL)25.11, 25.05, 24.11
23.11 (EOL)(オプション 2 のみ) 25.05, 24.11, 24.05

項目オプション 1: ローリング更新オプション 2: フルフリートリサイクル

⚠️ アップグレード中の影響

項目詳細
新規ジョブの投入コントローラー停止中は新規ジョブの投入やスケジューラーコマンドの実行ができない
自動スケーリング更新中は一時停止。新規インスタンスの起動やスケールダウンによる終了は更新完了まで行われない
アカウンティングデータアカウンティング有効時はデータが保持され、ジョブレコードはバージョン変更後も残る
Slurm REST APIUpdateCluster の一環として自動更新。更新中はエンドポイントが利用不可で、クラスターが ACTIVE 状態に戻ると再開
📝 API 変更履歴: 2026/06/30 — PCS (UpdateCluster) でクラスター設定に Slurm のターゲットバージョンを指定可能になりました。

🛠️ 設定方法

前提条件

✓クラスターとすべてのコンピュートノードが同じ Slurm バージョン (バージョン "A") で動作
✓すべてのコンピュートノードがバージョン "A" の最新パッチと最新の AWS PCS エージェントで動作
✓ターゲットの Slurm バージョンと最新の AWS PCS エージェントを含む AMI を準備または特定

ステップ 1: ターゲット AMI の準備

ターゲットの Slurm バージョンと最新の AWS PCS エージェントを含む AMI をビルドまたは特定します。 ローリング更新 (オプション 1) では、現在と対象の両方の Slurm バージョンを含むデュアルバージョン AMI が必要です。

ステップ 2: クラスターの更新

BashUpdateCluster でターゲットバージョンを指定
aws pcs update-cluster \
  --cluster-identifier my-hpc-cluster \
  --scheduler '{"type":"SLURM","version":"25.11"}'

UpdateCluster 操作でコントローラーをターゲットのメジャーバージョンへ移行します。 アカウンティングデータベースと REST API も PCS が自動更新します。 バージョン更新と他の設定変更 (例: アカウンティングの有効化) を 1 回のリクエストにまとめることも可能です。

ステップ 3: コンピュートノードグループの更新

Bash新しい AMI へ向ける
aws pcs update-compute-node-group \
  --cluster-identifier my-hpc-cluster \
  --compute-node-group-identifier my-compute-group \
  --ami-id ami-0123456789abcdef0

各コンピュートノードグループを新しい AMI に向けて、新ノードがターゲットバージョンを使うようにします。 コントローラーのアップグレード完了後、お客様の都合に合わせて実施できます。 バージョン混在の期間は最小限に抑えることが推奨されます。

💡 メリット

ビジネス面

  • ダウンタイムの最小化: 実行中ジョブを中断せず HPC ワークロードの稼働を維持
  • 運用負荷の軽減: インフラ再構築が不要で運用作業を削減
  • 長期サポートの確保: 新バージョンは EOL までのサポート期間が長く保守しやすい

技術面

  • マネージドな一括更新: 3 コンポーネントを PCS が一括更新、手動対応不要
  • データの保全: アカウンティングデータを保持しジョブ履歴を維持
  • 柔軟な更新パス: ジョブ中断の許容度に応じて 2 パスから選択

🚧 デメリット・制約事項

制限事項

✗1 回の更新で 3 つを超えるメジャーバージョンをスキップできない (4 つ以上先は複数ステップ)
✗コントローラー停止中は新規ジョブの投入やスケジューラーコマンドの実行不可
✗更新中は自動スケーリングが一時停止
✗ローリング更新 (オプション 1) には最小コントローラーバージョン 24.05 が必要

考慮すべき点

⚠️バージョン "A" のノードが残る間は、ターゲットバージョン固有の Slurm 設定を追加しない (旧 slurmd が新パラメータを認識できない可能性)
⚠️バージョン混在の期間は最小限に抑えることが推奨
⚠️23.11 (EOL) からの更新はフルフリートリサイクル (オプション 2) のみ対応

🎯 ユースケース

1. EOL バージョンからの計画的アップグレード

シナリオ: 24.11 (EOL) で稼働する研究機関の HPC クラスターを、サポート期間の長い最新 25.11 へ移行したい。

Bash
aws pcs update-cluster \
  --cluster-identifier research-cluster \
  --scheduler '{"type":"SLURM","version":"25.11"}'

効果: 1 回の更新で最新バージョンへ移行でき、長期サポートとセキュリティパッチを確保。

2. 長時間ジョブを中断しないローリング更新

シナリオ: 数日間のシミュレーションジョブが実行中のクラスターで、ジョブを止めずに更新したい。

実装: デュアルバージョン AMI を準備しオプション 1 を選択。実行中ジョブはコントローラー停止に依存せず継続。

効果: 長時間ジョブを終了させずにコントローラーを更新でき、完了を待たずアップグレードを進められる。

3. 複数バージョンをまたぐ段階的アップグレード

シナリオ: 23.11 (EOL) のクラスターを 25.11 まで引き上げたいが、3 メジャーバージョンを超えるため 1 回では不可。

実装: 23.11 → 25.05 (オプション 2) → 25.11 のように複数の連続ステップで更新。

効果: バージョン互換性の制約を踏まえた段階的移行で、確実に最新バージョンへ到達。

💰 料金・利用可能リージョン

💴 料金: インプレースアップグレード機能自体に追加料金の記載はありません。 AWS PCS の通常料金 (クラスター管理料金 + 利用するコンピュート/ストレージリソースの料金) が適用されます。
🌐 利用可能リージョン: AWS PCS が利用可能なすべての AWS リージョンで提供されます。

関連サービス・機能

→Slurm: PCS がマネージドで提供するオープンソースのジョブスケジューラー。本機能はそのメジャーバージョンアップグレードが対象
→Amazon EC2: コンピュートノードグループの基盤。AMI を通じて Slurm バージョンを反映
→AWS PCS コンピュートノードグループ: コントローラー更新後に新しい AMI へ更新する対象

📝 まとめ

AWS PCS のマネージドな Slurm インプレースアップグレードにより、HPC クラスターを再構築せず、 実行中ジョブを中断することなく最大 3 メジャーバージョン先まで移行できるようになりました。

EOL バージョンを利用しているクラスターの管理者は、バージョン互換性の表とジョブ中断の許容度を確認し、 ローリング更新またはフルフリートリサイクルのいずれかのパスでアップグレード計画を立てることが推奨されます。
