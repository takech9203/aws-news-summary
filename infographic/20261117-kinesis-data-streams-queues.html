🌊 Amazon Kinesis Data Streams
キューによるストリーム消費の簡素化とコスト削減

Amazon Kinesis Data Streams 📅 リリース日: 2026 年 11 月 17 日

📌 概要

Kinesis Data Streams に新しい消費方式「キュー (Queues)」が登場。キューが各レコードの配信状態を追跡するため、コンシューマーはシャードをリースせずにレコードを直接受信し、処理完了時に確認応答 (acknowledge) し、シャード数を超えてスケールできます。KCL の代わりにキューを使用することで、データ処理コストを最大 43% 削減できます。

キューは Amazon SQS を基盤として構築され、at-least-once 配信、未確認レコードの再配信、組み込みデッドレター処理を提供。プロデューサーや既存のストリームコンシューマーを変更せずに、データを 1 回取り込むだけで、各アプリケーションがキュー経由またはストリームから直接レコードを消費できます。

プロデューサーは従来どおりストリームにデータを書き込み、キューコンシューマーは ReceiveQueueRecords でレコードを受信して AcknowledgeQueueRecords で確認応答します。既存のストリームコンシューマーと併用でき、未確認のまま受信回数が上限を超えたレコードは組み込みのデッドレター処理に移行します。

⚡ 主要機能

1️⃣ レコード単位の配信状態追跡
  • キューが各レコードの配信状態を追跡し、コンシューマーはシャードをリースせずにレコードを受信
  • 確認応答したレコードは再配信されず、可視性タイムアウト内に未確認のレコードは自動再配信 (at-least-once 配信)
  • 配信順序は保証されないため、順序に依存しない処理に適する
2️⃣ シャード数を超えたスケーリング
  • コンシューマーインスタンス数がシャード数に制約されず、ワークロードに応じてスケール可能
  • 受信スループットは実質無制限で、多数のコンシューマーインスタンスによる大量レコード受信に対応
  • DynamoDB テーブルやカスタムメトリクスの運用が不要になり、コンピューティングを効率的に利用
3️⃣ 組み込みデッドレター処理
  • 最大受信回数 (MaxReceiveCount、デフォルト 6 回) を超えた未確認レコードはデッドレターレコードに移行
  • ReceiveDeadLetterQueueRecords / RestoreDeadLetterQueueRecords などの専用 API で処理・復元が可能
  • レコードはストリームの保持期間が終了すると失効
4️⃣ キュー単位の CloudWatch メトリクス
  • VisibleQueueRecords、InFlightQueueRecords、VisibleDeadLetterQueueRecords などを各キューが発行
  • 受信待ちレコード数に基づくコンシューマーインスタンスのオートスケーリングが可能
  • 繰り返し失敗するレコードに対するアラーム設定が可能
5️⃣ 既存環境への無停止導入
  • プロデューサーや既存のストリームコンシューマーに変更は不要
  • 同一ストリームに対してキューと拡張ファンアウトコンシューマーを併用可能
  • Agent Toolkit for AWS の Kinesis Data Streams スキルも提供

🛠️ 設定方法

✅ 前提条件

✓オンデマンドキャパシティモード (On-demand Standard または On-demand Advantage) のデータストリームが存在すること
✓キューの作成・操作に必要な IAM 権限 (kinesis:CreateQueue、kinesis:ReceiveQueueRecords など) が付与されていること
✓サポート対象リージョンでストリームを運用していること

ステップ 1: キューの作成

Bash AWS CLI でキューを作成 
aws kinesis create-queue \
  --queue-name my-app-queue \
  --stream-configuration-list '[{"StreamARN": "arn:aws:kinesis:ap-northeast-1:123456789012:stream/my-stream"}]'

対象ストリームを指定してキューを作成します。キューは登録済みコンシューマー 1 つとしてカウントされます。デッドレター設定を省略した場合、MaxReceiveCount は 6 になります。

ステップ 2: レコードの受信と確認応答

Bash 受信と確認応答 
# キューからレコードを受信 (最大 10 件)
aws kinesis receive-queue-records \
  --queue-arn arn:aws:kinesis:ap-northeast-1:123456789012:stream/my-stream/queue/my-app-queue \
  --limit 10 \
  --wait-time-seconds 9

# 処理が完了したレコードを確認応答
aws kinesis acknowledge-queue-records \
  --queue-arn arn:aws:kinesis:ap-northeast-1:123456789012:stream/my-stream/queue/my-app-queue \
  --entries '[{"ReceiptHandle": "<受信時に取得した ReceiptHandle>"}]'

可視性タイムアウト内に確認応答しなかったレコードは自動的に再配信されます。

ステップ 3: モニタリングとデッドレター処理

Bash デッドレターレコードの確認と復元 
# デッドレターレコードを受信して内容を確認
aws kinesis receive-dead-letter-queue-records \
  --queue-arn arn:aws:kinesis:ap-northeast-1:123456789012:stream/my-stream/queue/my-app-queue

# 修正後にデッドレターレコードをキューへ復元
aws kinesis restore-dead-letter-queue-records \
  --queue-arn arn:aws:kinesis:ap-northeast-1:123456789012:stream/my-stream/queue/my-app-queue \
  --entries '[{"ReceiptHandle": "<デッドレター受信時の ReceiptHandle>"}]'

CloudWatch の VisibleQueueRecords メトリクスでコンシューマーのスケーリング、VisibleDeadLetterQueueRecords でアラーム設定を行うことを推奨します。

⚖️ メリットと制約事項

💪 ビジネス面のメリット

✓コスト削減: KCL 比でデータ処理コストを最大 43% 削減。DynamoDB テーブルの運用コストも不要に
✓開発速度の向上: シャードリース管理、チェックポイント処理、再試行ロジックの自前実装が不要になり、ビジネスロジックに集中できる
✓運用負荷の軽減: 配信状態追跡、再配信、デッドレター処理がマネージドで提供され、運用コンポーネントが削減される

🔬 技術面のメリット

✓柔軟なスケーリング: シャード数に制約されず、受信待ちレコード数に基づいてスケール可能
✓堅牢なエラーハンドリング: at-least-once 配信、可視性タイムアウトによる自動再配信、組み込みデッドレター処理を標準装備
✓既存環境との共存: プロデューサーや既存コンシューマーを変更せず、同一データを複数アプリケーションがキューまたはストリーム経由で消費可能

🚧 制限事項

✗オンデマンドキャパシティモードのストリームでのみ利用可能 (プロビジョンドモードは非対応)
✗レコードの配信順序は保証されない (順序依存の処理にはストリームコンシューマーを使用)
✗1 回の受信・確認応答呼び出しで扱えるのは最大 10 レコード
✗キューは拡張ファンアウトコンシューマーと登録済みコンシューマー上限 (Standard: 20、Advantage: 50) を共有する
✗ストリームの保持期間終了でレコードは失効する (未確認・デッドレターも含む)

💡 考慮すべき点

⚠️at-least-once 配信のため、まれに同一レコードが再配信される可能性があり、コンシューマーは冪等に設計する必要がある
⚠️課金はレコード受信のたびに発生するため、再配信やデッドレター受信が多いワークロードではコストが増加する (1 KB 未満は 1 KB として課金)
⚠️前のレコードに依存する処理 (ライブ分析、異常検知など) にはキューではなくストリームコンシューマーが適する
⚠️ポイントツーポイントメッセージングには Amazon SQS が第一の選択肢。同一レコードを複数アプリケーションで必要とする場合にキューを選択する

✅ 効果: DynamoDB テーブルとシャードリース管理が不要になり、処理コストを最大 43% 削減。ワーカー数をシャード数と無関係にスケールできる。
🛒 ユースケース 2: 注文処理と通知の並列ファンアウト

シナリオ: EC サイトの注文イベントを、注文処理サービスと通知サービスの両方が消費。各レコードは独立して処理可能で、失敗時の確実な再処理が求められる。

注文イベント → オンデマンドストリーム → キュー A (注文処理サービス) / キュー B (通知サービス)。各キューが独立して配信状態を追跡し、未確認レコードを再配信。

✅ 効果: 同一データを 1 回の取り込みで複数アプリケーションに配信。アプリケーションごとに独立した再配信・デッドレター処理が行われ、信頼性が向上する。
📊 ユースケース 3: ストリーム分析とレコード単位処理の共存

シナリオ: クリックストリームデータに対して、リアルタイム分析 (順序依存) とアーカイブ処理 (レコード独立) の両方を実行したい。

クリックストリーム → オンデマンドストリーム → 拡張ファンアウトコンシューマー (Managed Service for Apache Flink でリアルタイム分析) / キュー (アーカイブワーカーで S3 へ保存)。

✅ 効果: プロデューサーを変更せずに、処理特性に応じた最適な消費方式を使い分けられる。登録済みコンシューマーの枠内でキューと拡張ファンアウトを併用できる。

💰 料金

キューの利用料金は、キューコンシューマーが受信したデータ量 (GB 単位) に基づく従量課金です。再配信やデッドレターレコードの受信を含め、受信のたびに課金されます。1 KB 未満のレコードは 1 KB として課金され、空の受信には課金されません。

キャパシティモードキュー受信料金 (米国東部)
On-demand Standard0.040 USD/GB
On-demand Advantage0.016 USD/GB
🧮 料金例: 毎秒 1,000 レコード (各 3 KB、約 7,413 GB/月) をキューで処理した場合、On-demand Standard ではキュー料金約 296.50 USD/月 (データ取り込みやストリーム時間料金は別途)、On-demand Advantage では約 118.61 USD/月。最新の情報は 料金ページを参照してください。

🔗 関連サービス・機能

→Amazon SQS: キュー機能の基盤サービス。ポイントツーポイントメッセージングには SQS を直接使用し、同一レコードを複数アプリケーションで必要とする場合に Kinesis のキューを選択する
→Kinesis Client Library (KCL): 従来のシャードベース消費ライブラリ。順序依存の処理では引き続き有効だが、レコード独立の処理ではキューへの移行でコスト削減が可能
→Amazon CloudWatch: キューごとのメトリクス (VisibleQueueRecords、InFlightQueueRecords など) によるスケーリングとアラーム設定
→Amazon DynamoDB: KCL のリーステーブルとして必要だったが、キュー利用時は不要になる

📝 まとめ

Kinesis Data Streams のキュー機能は、KCL と DynamoDB テーブルの運用なしに、レコード単位の配信追跡・再配信・デッドレター処理を備えたストリーム消費を実現し、処理コストを最大 43% 削減します。ログ処理や注文処理のようにレコードを独立して処理するワークロードでは、既存のプロデューサーを変更することなく導入できるため、オンデマンドモードのストリームを運用している場合はキューへの移行を検討する価値があります。
