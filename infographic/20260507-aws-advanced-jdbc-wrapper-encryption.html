AWS Advanced JDBC Wrapper

KMS Encryption Plugin
クライアントサイドカラムレベル暗号化

2026-05-07

📋 概要

AWS Advanced JDBC Wrapper に KMS Encryption Plugin が追加。Java アプリケーションからデータベースへの書き込み時に、カラムレベルのクライアントサイド暗号化が可能に。機密データはデータベースに到達する前にアプリケーション側で暗号化され、データベースエンジン内では常に暗号化された状態で保持される。

既存の SQL、Spring、Hibernate、コネクションプールの設定を変更することなく、透過的な暗号化/復号を実現。

Before

  • encryption at rest / TLS ではDB エンジン内でデータが復号される
  • 認証情報漏洩や SQL インジェクションで機密データが平文で露出するリスク
  • PCI DSS / HIPAA / GDPR 対応にはアプリ側で個別実装が必要
  • カラムレベル暗号化にはコードの大幅な変更が必要

After

  • JDBC ドライバレベルで透過的に暗号化/復号、平文はアプリのみで参照可能
  • コード変更なしで既存の PreparedStatement / ResultSet で利用可能
  • HMAC 検証によりDB 側で改竄検知 (暗号鍵なし)
  • AWS KMS エンベロープ暗号化で鍵管理が安全かつ容易

🏗️ アーキテクチャ図

アプリケーションが PreparedStatement でデータを書き込む際、KMS Encryption Plugin が暗号化対象カラムを自動検出し、AWS KMS から取得したデータキーで暗号化してからデータベースに送信する。

⚙️ 主要機能

🔐 透過的カラムレベル暗号化

  • PreparedStatement と ResultSet を通じた自動暗号化/復号
  • SQL パーシングによる暗号化対象カラムの自動検出
  • SQL コメントアノテーションによる明示的なカラム指定も可能

🔑 AWS KMS 統合によるエンベロープ暗号化

  • AWS KMS がデータキーを生成・暗号化
  • データキーで実データを暗号化 (AES-256-GCM)
  • HMAC キーによるデータ整合性の検証
  • データキーのキャッシュによる KMS API コール削減

✅ HMAC ベースの整合性検証

  • PostgreSQL では encrypted_data カスタムドメイン型を提供
  • データベース側で暗号鍵なしに改竄を検知可能
  • INSERT/UPDATE 時にトリガーで自動検証

🔄 鍵ローテーション機能

  • KeyManagementUtility クラスによるプログラマティックな鍵ローテーション
  • 同一マスターキーでのデータキーローテーション
  • 新しいマスターキーへの移行にも対応

🛠️ 設定方法

前提条件

✓AWS アカウントと KMS へのアクセス権限
✓Amazon Aurora または Amazon RDS (PostgreSQL 12+ / MySQL 8.0+)
✓Java 8 以上の開発環境と AWS SDK for Java 2.x
✓AWS Advanced JDBC Wrapper の導入

Step 1: 暗号化メタデータスキーマを作成

SQL PostgreSQL - encrypt スキーマ作成 
-- PostgreSQL の場合
CREATE SCHEMA encrypt;
CREATE EXTENSION IF NOT EXISTS pgcrypto;

-- 鍵ストレージテーブル
CREATE TABLE encrypt.key_storage (
    id SERIAL PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    master_key_arn VARCHAR(512) NOT NULL,
    encrypted_data_key TEXT NOT NULL,
    hmac_key BYTEA NOT NULL,
    key_spec VARCHAR(50) DEFAULT 'AES_256',
    created_at TIMESTAMPTZ DEFAULT CURRENT_TIMESTAMP
);

-- 暗号化メタデータテーブル
CREATE TABLE encrypt.encryption_metadata (
    table_name VARCHAR(255) NOT NULL,
    column_name VARCHAR(255) NOT NULL,
    encryption_algorithm VARCHAR(50) NOT NULL,
    key_id INTEGER NOT NULL,
    PRIMARY KEY (table_name, column_name),
    FOREIGN KEY (key_id) REFERENCES encrypt.key_storage(id)
);

Step 2: AWS KMS マスターキーを作成

Bash KMS キー作成コマンド 
# KMS マスターキーの作成
aws kms create-key \
    --description "JDBC Encryption Master Key" \
    --key-usage ENCRYPT_DECRYPT \
    --key-spec SYMMETRIC_DEFAULT

# エイリアスの設定
aws kms create-alias \
    --alias-name alias/jdbc-encryption-key \
    --target-key-id <KEY_ID>

# 自動キーローテーションの有効化
aws kms enable-key-rotation --key-id <KEY_ID>

Step 3: JDBC 接続でプラグインを有効化

Java KMS Encryption Plugin 有効化 
Properties props = new Properties();

// KMS Encryption Plugin を有効化
props.setProperty("wrapperPlugins", "kmsEncryption");

// KMS マスターキーの設定
props.setProperty("kmsKeyArn",
    "arn:aws:kms:us-east-1:123456789012:key/...");
props.setProperty("kmsRegion", "us-east-1");

// メタデータスキーマの指定
props.setProperty("encryptionMetadataSchema", "encrypt");

// データキーキャッシュ TTL の設定
props.setProperty("dataKeyCacheTTL", "300");

// 接続の確立
String url = "jdbc:aws-wrapper:postgresql://mydb.cluster-xxx.us-east-1.rds.amazonaws.com:5432/mydb";
Connection conn = DriverManager.getConnection(url, props);

💡 メリット

📊 ビジネス面

  • コンプライアンス対応強化: PCI DSS / HIPAA / GDPR 要件をアプリケーション層暗号化で充足
  • 開発コスト削減: 既存コード変更不要、大規模リファクタリング不要
  • リスク軽減: DBA や攻撃者がDB にアクセスしても機密データ参照不可

🔧 技術面

  • ゼロコード変更: PreparedStatement / ResultSet がそのまま利用可能
  • Spring/Hibernate 互換: 既存 ORM やコネクションプールと併用可能
  • パフォーマンス最適化: データキーキャッシュで KMS API コール最小化
  • 鍵管理の安全性: 平文のデータキーはメモリ上にのみ存在

⚠️ 制限事項・考慮点

制限事項

✗暗号化カラムに対する WHERE 句での検索、ソート、インデックスは利用不可
✗対応 DB は PostgreSQL と MySQL 互換エンジンのみ (Oracle / SQL Server は非対応)
✗カラム型として PostgreSQL は encrypted_data 型 / BYTEA、MySQL は VARBINARY が必要

考慮すべき点

→データキーキャッシュ TTL はセキュリティとパフォーマンスのバランスで調整
→既存データの暗号化には移行作業 (全行の読み取り・再書き込み) が必要
→HMAC 検証用の DB セットアップ (スキーマ、テーブル、トリガー) が事前に必要
→KMS API のレート制限とコストを考慮した設計が必要

🎯 ユースケース

🏦 金融機関における個人情報保護

銀行のオンラインバンキングシステムで、顧客の口座番号やマイナンバーを DBA でも平文参照できないように暗号化。PCI DSS 要件を満たしつつ、通常の JDBC コードと同じように実装可能。

Java 口座番号・SSN の自動暗号化 
String sql = "INSERT INTO customers (name, account_number, ssn) VALUES (?, ?, ?)";
PreparedStatement stmt = conn.prepareStatement(sql);
stmt.setString(1, "田中太郎");
stmt.setString(2, "1234-5678-9012");  // 自動暗号化
stmt.setString(3, "123-45-6789");      // 自動暗号化
stmt.executeUpdate();

🏥 ヘルスケアシステムにおける医療記録の保護

電子カルテシステムで患者の診断情報や処方データを HIPAA 準拠で保護。DB 侵害時にも患者の医療情報が平文で漏洩しない。

Java 医療記録の暗号化 
String sql = "INSERT INTO medical_records (patient_id, diagnosis, prescription) VALUES (?, ?, ?)";
PreparedStatement stmt = conn.prepareStatement(sql);
stmt.setInt(1, patientId);
stmt.setString(2, "Type 2 Diabetes");  // 自動暗号化
stmt.setString(3, "Metformin 500mg");  // 自動暗号化
stmt.executeUpdate();

☁️ SaaS マルチテナント環境でのデータ分離

テナントごとに異なる KMS キーを使用してデータを暗号化。テナント A のキーではテナント B のデータを復号できないため、暗号レベルでのデータ分離を実現。

Java テナント固有キーの設定 
Properties props = new Properties();
props.setProperty("wrapperPlugins", "kmsEncryption");
props.setProperty("kmsKeyArn", tenantKmsKeyArn);  // テナント固有のキー
props.setProperty("kmsRegion", "us-east-1");

Connection conn = DriverManager.getConnection(url, props);
