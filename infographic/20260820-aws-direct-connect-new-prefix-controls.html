AWS Direct Connect

🔌 インバウンドプレフィックスコントロール
プレフィックス上限が最大 1,000 に拡張

📅 リリース日: 2026 年 8 月 20 日 ｜ 機能: Inbound Prefix Controls ｜ 💰 追加料金なし

📋 概要

AWS Direct Connect が、プライベート VIF およびトランジット VIF に対するインバウンド経路プレフィックスの割り当てを管理できる新機能 インバウンドプレフィックスコントロール を発表しました。 専用接続とホスト接続の両方で利用でき、オンプレミスネットワークから AWS へ BGP で広告できる経路プレフィックス数を VIF ごとに柔軟に割り当てられます。

従来は VIF あたり最大 100 プレフィックスに固定されていましたが、IPv4 / IPv6 それぞれ最大 1,000 プレフィックス (従来比 10 倍) まで割り当て可能になりました。 容量は接続レベルと Direct Connect ゲートウェイ (DXGW) レベルの 2 つの「プレフィックスプール」として管理されます。

❌ アップデート前の課題

✗VIF あたりのインバウンド経路プレフィックスが最大 100 に固定され変更不可
✗100 超の経路を持つ大規模ネットワークでは経路集約 (サマライズ) 作業が必要
✗集約が難しい場合は複数 VIF / 接続への分割が必要で、構成が複雑化しコストも増加

✅ アップデート後の改善

✓VIF ごとに IPv4 / IPv6 それぞれ最大 1,000 プレフィックスまで割り当て可能
✓接続レベルと DXGW レベルのプールからワークロードに応じてサイズを割り当て
✓同一接続上でトランジット VIF に 1,000、プライベート VIF に 50 など柔軟な配分が可能
✓接続速度に応じてプールがスケールし、LAG ではメンバー数に応じて拡大

💡 専用接続のプレフィックスプールから各 VIF に必要なプレフィックス数を割り当て、VIF を DXGW にアタッチすると DXGW 側のプール (上限 10,000) からも同じ値が消費される仕組みです。

⚙️ 主要機能

1️⃣ VIF ごとのプレフィックス割り当て
→プライベート / トランジット VIF の作成時または更新時に割り当て数を指定可能
→デフォルトはアドレスファミリー (IPv4 / IPv6) ごとに 100、最大 1,000 まで引き上げ可能
→さらに高い上限は SA / TAM 経由で個別リクエスト (ケースバイケースで審査)
2️⃣ 接続レベルのプレフィックスプール
→専用接続ごとに全 VIF で共有するプールを保持。サイズは接続速度で自動決定 (変更不可)
→1/10 Gbps: 5,000 ｜ 100 Gbps: 30,000 ｜ 400 Gbps: 50,000
→Pool size (Allowed) / Allocated / Available / In use の 4 状態で管理
3️⃣ DXGW レベルのプレフィックス上限
→DXGW ごとにアタッチ全 VIF の割り当て合計 (IPv4 + IPv6) で 10,000 の上限を共有
→VIF アタッチ数の上限は従来どおり 30。上限超過となるアタッチリクエストは拒否
→コンソールまたは DescribeDirectConnectGateways API の totalPrefixPoolAllocations で確認可能
4️⃣ LAG でのプールスケーリング
→プールサイズは課金対象メンバー接続数に応じてスケール (メンバーあたりのプール x アクティブメンバー数)
→1/10 Gbps LAG は最大 4 メンバー、100/400 Gbps LAG は最大 2 メンバー分
→メンバー削除でプールが割り当て合計を下回る場合、削除は拒否されるガードレールあり
5️⃣ ホスト接続・ホスト VIF のサポート
→ホスト接続では接続レベルのプールは使用されないが、VIF ごとの割り当ては顧客が設定可能
→ホスト VIF の割り当ては親接続の所有者アカウントが管理し、新規作成時は常にデフォルトの 100

📊 プレフィックスプールの 4 つの状態

状態説明
Pool size (Allowed)接続がサポートできるプレフィックスの総数。接続速度で決まり変更不可
Allocated各 VIF に予約されたプレフィックス数。VIF の作成 / 更新時に設定
Available (Unallocated)プールの残り。プールサイズから全 VIF の割り当て合計を引いた値
In useオンプレミスルーターが実際に広告しているプレフィックス数

🛠️ 設定方法

✅ 前提条件

✓AWS Direct Connect の専用接続またはホスト接続が作成済みであること
✓プライベート VIF またはトランジット VIF を作成する権限があること
✓割り当てを増やす場合、接続プールおよび DXGW プールに十分な空き容量があること

📝 手順

1
接続のプレフィックスプールを確認する

Direct Connect コンソールで対象の専用接続を開き、プールサイズ (Allowed)、割り当て済み (Allocated)、未割り当て (Available) を確認します。ホスト接続の場合、接続レベルのプール情報はコンソールに表示されません。

2
VIF 作成時にプレフィックス数を割り当てる

値を指定しない場合はアドレスファミリーごとにデフォルトの 100 が適用されます。既存 VIF の変更は UpdateVirtualInterfaceAttributes API を使用します。

Bash プライベート VIF 作成時に割り当てを指定する例 
aws directconnect create-private-virtual-interface \
  --connection-id dxcon-xxxxxxxx \
  --new-private-virtual-interface "virtualInterfaceName=my-private-vif,vlan=101,asn=65000,..."
3
DXGW の合計割り当てを確認する

レスポンスの totalPrefixPoolAllocations で合計割り当てを確認します。10,000 の上限に達すると新しい VIF のアタッチが拒否されるため、事前確認が重要です。

Bash DXGW の合計プレフィックス割り当てを確認 
aws directconnect describe-direct-connect-gateways
4
オンプレミス側の広告経路数を確認する

広告するプレフィックス数が VIF の割り当てを超えないよう BGP 設定を確認します。割り当てを超えて広告すると BGP セッションはダウン (BGP DOWN) し、アイドル状態になります。

⚖️ メリットと制約事項

💼 ビジネス面のメリット

✓回避策の排除によるコスト削減: 経路集約や VIF / 接続分割が不要になり、追加コストと運用負荷を削減
✓追加料金なし: 既存の Direct Connect 料金体系のまま利用可能
✓大規模ネットワーク対応: 従来比 10 倍の 1,000 プレフィックスでエンタープライズや通信事業者の構成に対応

🔧 技術面のメリット

✓ワークロード単位のサイジング: 同一接続上で VIF ごとに柔軟な割り当てが可能
✓速度に応じたスケーラビリティ: 接続速度や LAG メンバー数に応じてプールが拡大 (最大 50,000)
✓可視性の向上: 4 状態管理でプレフィックス消費状況をコンソールや API で把握

🚧 制限事項

✗割り当て超過の広告で VIF の BGP セッションがダウンし、アイドル状態になる
✗In use のプレフィックス数より小さい値には減らせない (先に広告数の削減が必要)
✗DXGW あたり IPv4 + IPv6 合算 10,000 が上限。超過するアタッチは拒否
✗パブリック VIF は管理対象外 (従来どおり 1,000 プレフィックス上限)
✗LAG メンバー削除は、削除後のプールが割り当て合計を下回る場合に拒否

⚠️ 考慮すべき点

⚠AWS Interconnect 接続は DXGW の上限のうち 2,000 プレフィックスを消費するため割り当て計画に注意
⚠1,000 超の割り当ては SA / TAM 経由の個別リクエスト (審査あり)
⚠ホスト接続はプール情報がコンソール非表示のため VIF 単位で管理
⚠BGP ダウン回避のため、広告予定数に対し余裕を持った割り当てを行う

💡 ユースケース

🏢 ユースケース 1: 大規模エンタープライズネットワークの経路集約からの脱却

シナリオ: 数百の拠点とデータセンターを持つ企業が、従来は 100 プレフィックス制限のために経路を集約して AWS へ広告。集約により一部トラフィックの経路制御が粗くなっていた。

Plan実装例
1. トランジット VIF の割り当てを 1,000 プレフィックスに更新
2. オンプレミスルーターの経路集約設定を解除し、詳細経路を広告
3. In use 値を監視し、割り当てに対する余裕を確認
✅ 効果: 詳細な経路情報をそのまま AWS へ広告でき、拠点単位の細やかなトラフィック制御と障害切り分けが可能になる。
📐 ユースケース 2: 同一接続上での VIF ごとの適切なサイジング

シナリオ: 1 本の 10 Gbps 専用接続上で、全社ネットワーク向けのトランジット VIF と、特定システム向けのプライベート VIF を運用。

Plan実装例
接続プール: IPv4 5,000 プレフィックス
- トランジット VIF: 1,000 プレフィックスを割り当て (全社経路向け)
- プライベート VIF: 50 プレフィックスを割り当て (特定システム向け)
- 残り 3,950 プレフィックスは将来の VIF 追加用に確保
✅ 効果: ワークロードの規模に応じた割り当てにより、プールを無駄なく活用しつつ将来の拡張余地を確保できる。
📡 ユースケース 3: LAG を使った大規模構成でのプール拡張

シナリオ: 通信事業者が 4 本の 10 Gbps 接続で LAG を構成し、多数の顧客向け VIF を収容。

Plan実装例
LAG プールサイズ: 20,000 プレフィックス/アドレスファミリー
  (10 Gbps メンバー 4 本 x 5,000)
- 各顧客 VIF に 500〜1,000 プレフィックスを割り当て
- メンバー削除前に割り当て合計がプールサイズ内に収まるよう調整
✅ 効果: メンバー接続数に応じてプールがスケールするため、多数の VIF に十分なプレフィックスを割り当てた大規模収容が可能になる。

🔗 関連サービス・機能

🌐 AWS Direct Connect ゲートウェイ

VIF のアタッチ先となるゲートウェイ。今回のアップデートで 10,000 プレフィックスの合計割り当てプールを持つようになった。

🚉 AWS Transit Gateway

トランジット VIF と DXGW を経由して複数 VPC への接続を集約するサービス。大規模経路広告の主要な接続先。

🔗 リンクアグリゲーショングループ (LAG)

複数の Direct Connect 接続を束ねる機能。メンバー接続数に応じてプレフィックスプールがスケールする。

🛰️ AWS Interconnect

DXGW にアタッチすると、DXGW の割り当て上限から 2,000 プレフィックスを消費する。

📝 まとめ

AWS Direct Connect のインバウンドプレフィックスコントロールにより、VIF あたりのインバウンド経路プレフィックスが従来の 100 から 最大 1,000 (IPv4 / IPv6 それぞれ) に拡張され、接続および DXGW レベルのプールからワークロードに応じた柔軟な割り当てが可能になりました。

→経路集約や VIF 分割といった回避策を運用中の場合は、割り当ての見直しによる構成の簡素化を検討
→割り当てを超えて広告すると BGP セッションがダウンするため、割り当て値と実際の広告経路数 (In use) の監視を運用に組み込むことが重要
