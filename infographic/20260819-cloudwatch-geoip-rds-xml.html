📊 CloudWatch pipelines に GeoIP・RDS・XML プロセッサが登場

ログのインジェスト時に解析・エンリッチをマネージドに実行 | リリース日: 2026 年 8 月 19 日

📝 概要

Amazon CloudWatch pipelines に、ログデータをインジェスト時に解析・エンリッチする 3 つの新プロセッサが追加されました。 Aurora の監査ログ・エラーログを構造化する parse_rds、XML 文字列を JSON に変換する parse_xml、 IP アドレスに地理情報を付加する geoip です。 各プロセッサは単独でも、1 つのパイプライン内で組み合わせても使用できます。

❌ Before: カスタム処理が必要

✗Aurora ログはエンジン固有形式で届き、独自の解析処理が必要
✗ログ内の XML は非構造化文字列のままでフィールド単位のクエリ不可
✗IP の位置情報付加に Lambda や外部 GeoIP データベースが必要

✅ After: インジェスト時にマネージド実行

✓parse_rds で Aurora 監査・エラーログを自動で構造化
✓parse_xml で XML を JSON に変換しフィールドとして展開
✓geoip で MaxMind により都市・国・座標・ASN を自動付加

各ログソースからのデータが CloudWatch pipelines の新プロセッサで解析・エンリッチされ、構造化された状態で CloudWatch Logs に保存されます。 XML パーサーと GeoIP プロセッサは 1 つのパイプライン内で組み合わせて使用できます。

⚙️ 主要機能

🗄️ Amazon RDS ログパーサー (parse_rds)

  • Amazon RDS Aurora のログデータを構造化フィールドに解析
  • パイプラインの data_source_name が amazon_rds の場合にのみ使用可能。data_source_type に一致する解析ロジックが自動適用
  • 追加パラメータなしの parse_rds: {} というシンプルな設定で利用可能

📄 XML パーサー (parse_xml)

  • 指定フィールド内の XML 文字列を JSON 形式に変換
  • プライマリパーサーが生成したフィールドに対して動作するため、パイプライン内でプライマリパーサーの後に配置
  • 1 パイプラインに最大 5 個、when パラメータによる条件付き実行に対応
  • XML の属性と子要素の両方が JSON のフィールドとして展開される

🌍 GeoIP エンリッチメントプロセッサ (geoip)

  • MaxMind データベースを使用し、IPv4 / IPv6 アドレスを地理情報に解決
  • 都市名・国名・国コード・大陸・緯度経度・郵便番号・タイムゾーン・CIDR・ASN・ASN 組織名など最大 12 種類のフィールドから選択して付加
  • 1 プロセッサで最大 10 個の IP フィールドを対象にでき、送信元 IP と宛先 IP を同時にエンリッチ可能

設定例: XML パーサーと GeoIP の組み合わせ

YAML parse_xml + geoip の組み合わせ 
processor:
  - parse_json:
      source: "@message"
  - parse_xml:
      source: "body"
      destination: "parsed_xml"
  - geoip:
      entries:
        - source: "src_ip"
          target: "src_geo"
          include_fields:
            - "city_name"
            - "country_name"
            - "country_iso_code"
            - "latitude"
            - "longitude"
            - "asn"
            - "asn_organization"
          when: '.src_ip != "127.0.0.1"'

JSON ログの body フィールド内の XML を構造化した後、送信元 IP に地理情報を付加する例です。 when 条件によりループバックアドレスをエンリッチ対象から除外しています。

🛠️ 設定方法

前提条件

✓CloudWatch pipelines が利用可能なリージョンでパイプラインを作成できること
✓parse_rds を使用する場合、データソースが Amazon RDS (Aurora ログ) であること
✓パイプラインの作成・更新に必要な IAM 権限を持っていること
1

パイプラインのプロセッサ設定を定義する

YAML最小構成
processor:
  - parse_rds: {}

Aurora ログをデータソースとするパイプラインに RDS ログパーサーを追加する最小構成です。data_source_type に応じた解析ロジックが自動適用されます。

2

パイプラインを作成または更新する

新しいプロセッサは AWS Management Console (CloudWatch > Pipelines)、AWS CLI、AWS SDK から既存または新規のパイプラインに追加できます。ログパイプラインは最大 20 個のプロセッサを定義順に順次適用します。

3

変換結果を確認する

処理されたログには変換メタデータが自動付与されます。「Keep original log」オプションを有効にすると元のログと比較できます。不正な形式の XML はパイプラインを失敗させず、元の @message を保持したまま @pipeline.processing.status = "error" が設定されます。

💡 メリット

💼 ビジネス面

✓コンプライアンス対応の迅速化: Aurora 監査ログが最初から構造化され、レポート作成・監査対応の時間を短縮
✓運用コストの削減: ログ再処理やカスタム解析基盤 (Lambda、外部 GeoIP DB) の構築・保守が不要
✓セキュリティ調査の高度化: 不審なアクセスの発信地域を即座に特定し、初動を短縮

🔧 技術面

✓インジェスト時の変換: 保存後すぐにフィールド単位の検索・集計が可能
✓フルマネージド: MaxMind データベースの管理・更新を含め AWS が管理
✓柔軟な組み合わせ: 単独でも既存のパーサー・トランスフォーマーとの組み合わせでも使用可能。when 条件式による制御にも対応 (parse_xml / geoip)

⚠️ デメリット・制約事項

制限事項

•parse_rds は data_source_name が amazon_rds の場合のみ使用可能で、条件付き実行 (when) は非対応
•parse_xml は 1 パイプラインに最大 5 個、XML のネストは最大 25 レベルまで
•geoip のエントリは最大 10 個、include_fields は 1〜12 個で指定
•ログパイプラインあたりのプロセッサ数は最大 20 個

考慮すべき点

•プロセッサ自体は追加料金なしだが、CloudWatch のログインジェスト・ストレージ料金は通常どおり適用
•GeoIP は MaxMind データベースに基づくため、IP によっては解決できない、または精度に差が出る場合がある
•エンリッチメントによりログイベントのサイズが増加し、インジェスト・ストレージ量に影響する可能性

🎯 ユースケース

1️⃣ Aurora 監査ログによるコンプライアンスレポート

シナリオ: 金融系システムで Aurora MySQL の監査ログを保存しており、監査人から特定ユーザーのデータベース操作履歴の提出を求められている。

YAML
processor:
  - parse_rds: {}

効果: 監査ログがユーザー名や操作種別などの構造化フィールドで保存され、CloudWatch Logs Insights でフィールド指定クエリを直接実行でき、レポート作成が大幅に効率化。

2️⃣ Windows イベントログのセキュリティ分析

シナリオ: Windows サーバー群のイベントログの詳細情報が XML ペイロードとして埋め込まれており、ログオン失敗の分析に手間がかかっている。

YAML
processor:
  - parse_json:
      source: "@message"
  - parse_xml:
      source: "event_data"
      destination: "parsed_event"
  - geoip:
      entries:
        - source: "parsed_event.IpAddress"
          target: "src_geo"
          include_fields:
            - "country_name"
            - "country_iso_code"
            - "city_name"

効果: XML が JSON に構造化され、送信元 IP が国・都市に解決されるため、通常と異なる地域からのログオン試行を即座に検出。

3️⃣ Web アクセスログの地理的トラフィック分析

シナリオ: グローバル展開する Web サービスで、アクセス元の地域分布を把握してコンテンツ配信やキャパシティ計画に活用したい。

YAML
processor:
  - parse_json:
      source: "@message"
  - geoip:
      entries:
        - source: "client_ip"
          target: "client_geo"
          include_fields:
            - "country_iso_code"
            - "city_name"
            - "latitude"
            - "longitude"
            - "asn_organization"

効果: アクセスログに国・都市・座標・ISP 情報が付加され、地域別のトラフィック集計やダッシュボードでの可視化を追加処理なしで実現。

💰 料金

新しいプロセッサの利用に追加料金はかかりません。 標準の CloudWatch のログインジェストおよびストレージ料金が適用されます。 詳細は Amazon CloudWatch 料金ページ を参照してください。

✅ まとめ

CloudWatch pipelines への GeoIP・RDS・XML プロセッサの追加により、これまでカスタム処理が必要だったログの構造化とエンリッチメントが インジェスト時にマネージドに実行できるようになりました。 Aurora ログの監査分析、XML を含むログのセキュリティ分析、IP アドレスベースの地理的分析を行っている場合は、 既存のパイプラインへの新プロセッサの追加を検討することをお勧めします。
