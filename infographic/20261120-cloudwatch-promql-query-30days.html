📊 PromQL クエリウィンドウを 30 日間に拡張

リリース日: 2026 年 11 月 20 日 | OpenTelemetry メトリクスに対する PromQL クエリの最大時間範囲が 7 日間から 30 日間へ

💡 概要

Amazon CloudWatch は、OpenTelemetry メトリクスに対する PromQL クエリの時間範囲を 7 日間から 30 日間に拡張しました。1 回のリクエストで 1 か月分のデータを取得でき、月次・週次のトレンド比較や、ローリング 30 日間の SLO 監視・エラーバジェット計算を単一のクエリで実現できます。

7 日 → 30 日
1 クエリの最大時間範囲が約 4 倍に
1 クエリ
30 日間 SLO とエラーバジェットを計算
追加料金なし
標準の CloudWatch 料金のみ

❌ Before: 7 日間の制限

✗start と end の間隔が最大 7 日間に制限
✗30 日間 SLO の可用性・エラーバジェット計算には複数クエリの結果結合が必要
✗7 日間ベースラインは単一の繁忙な週末に偏り、キャパシティ予測が不正確になりがち

✅ After: 30 日間に拡張

✓1 回のリクエストで最大 30 日間のメトリクスデータを取得
✓月次・週次のトレンド比較を単一ダッシュボードで可視化
✓30 日間ベースラインの CloudWatch アラームを設定可能
✓SLO 期間全体の可用性と残りのエラーバジェットを 1 クエリで計算

OTLP で取り込まれたメトリクスに対し、Query Studio、Prometheus 互換 API、CloudWatch アラームの各インターフェイスから最大 30 日間の PromQL クエリを実行できます。

🚀 主要機能

📅 クエリウィンドウの 30 日間への拡張
→1 回のリクエストにおける start と end の間隔が 7 日間から 30 日間に拡張
→[5m] のようなレンジセレクタはこの制限にカウントされない
→ウィンドウはメトリクス保持期間内の任意の位置に設定可能 (直近 30 日間に限定されない)
→30 日間を超える期間は、連続した複数リクエストの結果を結合して対応
🔔 30 日間ベースラインによるアラーム
→30 日間のベースラインを使用した CloudWatch アラームを設定可能
→SLO 期間全体のエラーバジェット消費を監視し、枯渇予測時に通知
📈 長期トレンドの可視化
→月次比較 month-over-month や週次比較 week-over-week を単一ダッシュボードで表示
→1 か月分の履歴に基づき、繁忙期に偏らない精度の高いキャパシティ予測が可能

⚙️ 技術仕様

PromQL クエリの制限事項

項目値補足
リクエストあたりの最大時間範囲30 日間今回 7 日間から拡張。start と end の間隔に適用
クエリリクエストの最大 TPS300/アカウント/query、/query_range が対象
ディスカバリリクエストの最大 TPS10/アカウント/series、/labels、/label_values が対象
同時実行クエリ数30/アカウント超過時は 429 エラー
クエリあたりの最大返却系列数500超過分は切り捨て
24 時間あたりの最大スキャン系列数100,000
24 時間あたりの最大スキャンサンプル数300,000,000
クエリ実行タイムアウト20 秒キュー待ちとストレージ取得時間を除く

クエリウィンドウ内のデータ解像度はデータの経過時間に依存し、CloudWatch のメトリクス保持ポリシーに従って古いデータポイントは集約されます。

IAM 権限

PromQL クエリの実行には cloudwatch:GetMetricData と cloudwatch:ListMetrics の両方の権限が必要です。

API エンドポイントパスHTTP メソッド必要なアクション
/api/v1/queryGET、POSTGetMetricData、ListMetrics
/api/v1/query_rangeGET、POSTGetMetricData、ListMetrics
/api/v1/seriesGET、POSTListMetrics
/api/v1/labelsGET、POSTListMetrics
/api/v1/label/{label_name}/valuesGETListMetrics
JSON IAM ポリシー例 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "cloudwatch:GetMetricData",
        "cloudwatch:ListMetrics"
      ],
      "Resource": "*"
    }
  ]
}

ステップ 1: Query Studio で 30 日間のクエリを実行する

CloudWatch コンソールの Query Studio で時間範囲として過去 30 日間を選択し、PromQL クエリを実行します。

PromQL リクエストレートの計算 
sum(rate({"http.server.requests", "@resource.service.name"="myservice"}[5m]))

ステップ 2: Prometheus 互換 API でレンジクエリを実行する

Grafana などの外部ツールやスクリプトからは /api/v1/query_range エンドポイントを使用します。

Bash 30 日間のレンジクエリ 
# start と end の間隔を最大 30 日間まで指定できる
POST /api/v1/query_range
  query=sum(rate({"http.server.requests"}[5m]))
  start=2026-10-21T00:00:00Z
  end=2026-11-20T00:00:00Z
  step=1h

ステップ 3: 30 日間ベースラインのアラームを作成する

CloudWatch アラームの作成時に PromQL クエリをデータソースとして指定し、30 日間ウィンドウに基づく条件を設定します。SLO のエラーバジェット消費率をしきい値とすることで、バジェット枯渇の予兆を検知できます。

🎯 ユースケース

1. 30 日間 SLO のエラーバジェット監視

ローリング 30 日間で可用性 99.9% の SLO を定義しているサービスで、SLO 期間全体の可用性と残りのエラーバジェットを継続的に監視。

PromQL過去 30 日間の可用性を 1 クエリで計算
1 - (
  sum(rate({"http.server.errors", "@resource.service.name"="myservice"}[5m]))
  /
  sum(rate({"http.server.requests", "@resource.service.name"="myservice"}[5m]))
)
✓効果: SLO 期間全体を単一クエリでカバーし、エラーバジェット枯渇の予測をアラームで早期検知
2. 月次・週次のトレンド比較ダッシュボード

リクエスト数やレイテンシーの前月比・前週比トレンドを経営層向けダッシュボードで可視化。

PromQL30 日間のリクエストレート推移を 1 時間解像度で取得
sum by ("@resource.service.name") (
  rate({"http.server.requests"}[1h])
)
✓効果: 複数クエリの結合が必要だった月次トレンドを、単一のクエリとダッシュボードで表示
3. 30 日間ベースラインによるキャパシティ予測

ピークトラフィックに備えたキャパシティ計画のため、直近 1 か月の利用傾向からリソース需要を予測。

PromQL同時アクティブリクエスト数の最大値を日次で把握
max_over_time({"http.server.active_requests", "@resource.service.name"="myservice"}[1d])
✓効果: 単一の繁忙な週末に偏っていた予測を 1 か月分のデータで平準化し、精度の高い計画を立案

⚖️ メリットと制約事項

✅ メリット

✓SLO 運用の効率化: 30 日間 SLO の可用性とエラーバジェットを 1 クエリで計算し、レポーティングの運用負荷を削減
✓追加コストなし: 本機能拡張に追加料金は発生しない
✓意思決定の精度向上: 1 か月分のデータに基づくトレンド分析でキャパシティ計画の判断材料が充実
✓クエリの簡素化: 7 日間ごとの分割・結合が不要になり単一リクエストに統合
✓ウィンドウ位置の柔軟性: 保持期間内の任意の位置に設定でき、過去の特定の 30 日間も分析可能

⚠️ 制約・考慮点

⚠30 日間を超える期間は複数リクエストに分割して結果を結合する必要がある
⚠最大返却系列数 500、24 時間あたりのスキャン上限 (系列 100,000 / サンプル 3 億) は引き続き適用
⚠クエリ実行タイムアウトは 20 秒。広い時間範囲 x 多数の系列の重いクエリはタイムアウトの可能性
⚠古い期間のデータは保持ポリシーにより集約され、解像度が低下する
⚠対象は OTLP 取り込みメトリクスと AWS エンリッチドベンドメトリクスのみ

💰 料金

今回のクエリウィンドウ拡張に追加料金はありません。PromQL クエリの利用自体には、CloudWatch の標準的な料金体系が適用されます。詳細は CloudWatch の料金ページを参照してください。

🔗 関連サービス・機能

🖥️ CloudWatch Query Studio

PromQL クエリをインタラクティブに実行できるコンソール上のクエリ環境。今回の拡張により 30 日間の分析が可能に。

🔔 CloudWatch アラーム

PromQL クエリをデータソースとしたアラームを作成でき、30 日間ベースラインの監視に活用可能。

📡 Amazon Managed Service for Prometheus

Prometheus 互換のフルマネージドモニタリングサービス。Prometheus ネイティブなワークロードにはこちらも選択肢。

📊 Amazon Managed Grafana

Prometheus 互換 API 経由で CloudWatch の PromQL クエリ結果を可視化可能。

📝 まとめ

CloudWatch の PromQL クエリウィンドウが 7 日間から 30 日間に拡張され、ローリング 30 日間の SLO 監視やエラーバジェット計算、月次トレンド分析を単一のクエリで実現できるようになりました。追加料金なしで利用できるため、OpenTelemetry メトリクスを CloudWatch に取り込んでいるチームは、SLO ダッシュボードやキャパシティ予測のクエリを 30 日間ウィンドウへ見直すことを推奨します。
