📋 概要

Aurora MySQL バージョン 3.14.0 (MySQL 8.0.46 互換) が一般提供開始。コミュニティ版のバグ修正に加えて、Aurora 固有のセキュリティ修正・可用性改善・一般的な改善が含まれます。

最大の注目点は、転送中データの暗号化に対するポスト量子 TLS (PQ-TLS) 鍵交換のサポート。TLS 1.3 でハイブリッド鍵交換グループ X25519MLKEM768 と SecP256r1MLKEM768 が導入され、将来の量子コンピュータによる脅威 (Harvest Now, Decrypt Later 攻撃) に備えた耐量子暗号の選択肢が提供されます。

❌ アップデート前の課題

  • TLS 鍵交換は古典的な楕円曲線のみで、量子コンピュータ実用化を見据えた長期的な機密性確保に課題
  • 一時テーブルや全文検索キャッシュの消費をリアルタイムに可視化する専用メトリクスがなく、逼迫を事前検知しにくい
  • DELETE した行の値の取得には事前に別途 SELECT が必要
  • マイナーバージョンアップグレード時のライター復帰に一定の時間を要していた

✅ アップデート後の改善

  • PQ-TLS 対応クライアントは自動的に耐量子共有秘密をネゴシエート、非対応クライアントは従来どおり接続継続
  • 新メトリクス AuroraTempTableVolumeTotalBytes と FTSCacheMemoryUsed で監視とアラーム設定が可能に
  • 単一テーブルの DELETE 文で RETURNING 句をサポート、1 ステートメントで削除行の値を取得
  • 3.08 以降からのアップグレードが高速化、ライターがより早く復帰 (オプトイン不要)

TLS 1.3 ハンドシェイク時に、PQ-TLS 対応クライアントは自動的にハイブリッド鍵交換グループをネゴシエートし、非対応クライアントは従来の楕円曲線グループで接続を継続します。アプリケーション側の互換性を損なわずに耐量子暗号へ段階的に移行できます。

⚡ 主要機能

🔐 ポスト量子 TLS (PQ-TLS) 鍵交換のサポート

TLS 1.3 接続向けにハイブリッド鍵交換グループ X25519MLKEM768 と SecP256r1MLKEM768 を導入。対応クライアントは自動的に耐量子共有秘密をネゴシエートし、非対応クライアントは古典的グループを継続使用するため既存アプリケーションへの影響なし。ネゴシエート結果はステータス変数 Aurora_ssl_named_group で確認可能。

🚀 マイナーバージョンアップグレードの高速化

バージョン 3.08 以降から本リリースへのアップグレードが高速化され、ライターインスタンスがより早くサービスに復帰。設定変更やオプトインは不要で自動適用。

📊 新しい CloudWatch メトリクス

AuroraTempTableVolumeTotalBytes: ライター上の内部/外部 InnoDB 一時テーブルスペースが使用するクラスターボリュームの合計バイト数。危険水準に達する前にアラームを設定可能。
FTSCacheMemoryUsed: 全テーブルにわたる InnoDB 全文検索 (FTS) キャッシュの合計メモリ使用量を把握可能。

📝 DELETE 文の RETURNING 句サポート

単一テーブルの DELETE 文で削除した行の値を直接返却可能になり、別途 SELECT クエリが不要に。RETURNING が予約語になったため、同名の識別子はバッククォートで囲む必要がある点に注意。

🔒 セキュリティ修正

SQL SECURITY DEFINER ルーチン内の SQL 文について Advanced Audit ログが呼び出し元クライアントのユーザーとホストを記録するよう修正。Write Forwarding 使用セッションで SET ROLE NONE がロール権限を正しくクリアしない問題を修正。高重大度 2 件、中重大度 30 件、低重大度 2 件の CVE 修正を含む。

🛡️ 可用性と一般的な改善

Write Forwarding のクエリキャンセル/タイムアウト時の問題修正、Global Database スイッチオーバー中のリーダー再起動の問題修正、Zero Downtime Patching (ZDP) の通信オーバーヘッド削減、並列クエリ有効時のハッシュジョインの結果不正の修正など。MySQL 8.0.46 の CREATE TABLE 行サイズ見積もり問題 (ERROR 1118) は 8.0.46 以前の動作を維持。

⚙️ 設定方法

📌 前提条件

✓Aurora MySQL バージョン 3 (MySQL 8.0 互換) クラスターを運用していること
✓アップグレード方式 (自動マイナーバージョンアップグレード、インプレース、スナップショット復元) を決定していること
✓PQ-TLS を利用する場合は、ハイブリッド鍵交換に対応したクライアントライブラリ (AWS-LC ベースのクライアントなど) を使用すること
1

対象クラスターの現在のバージョンを確認

BashAWS CLI
aws rds describe-db-clusters \
  --db-cluster-identifier my-aurora-cluster \
  --query "DBClusters[0].EngineVersion"

現在のエンジンバージョンを取得し、アップグレード元のバージョンを確認します。

2

インプレースアップグレードの実行

BashAWS CLI
aws rds modify-db-cluster \
  --db-cluster-identifier my-aurora-cluster \
  --engine-version 8.0.mysql_aurora.3.14.0 \
  --apply-immediately

--apply-immediately を指定すると即時に適用され、省略するとメンテナンスウィンドウで適用されます。バージョン 3.08 以降からのアップグレードでは高速化処理が自動的に適用されます。

3

自動マイナーバージョンアップグレードの有効化 (推奨)

BashAWS CLI
aws rds modify-db-instance \
  --db-instance-identifier my-aurora-instance \
  --auto-minor-version-upgrade \
  --apply-immediately

今後のマイナーバージョンはメンテナンスウィンドウ中に自動適用されます。大規模運用では AWS Organizations の Upgrade Rollout Policy による段階的な展開が推奨されています。

4

PQ-TLS 接続の確認

SQL接続確認
SHOW STATUS LIKE 'Aurora_ssl_named_group';

アップグレード後、PQ-TLS 対応クライアントから接続し、ハイブリッド鍵交換グループがネゴシエートされていることを確認します。

💼 ビジネス面

✓長期的なデータ保護: Harvest Now, Decrypt Later 攻撃への対策となり、規制業界や機密データを扱うワークロードの長期的なコンプライアンス要件に対応できる
✓運用コストの削減: アップグレードの高速化と Organizations Upgrade Rollout Policy の活用により、大規模環境でのアップグレード運用負荷とダウンタイムを削減できる
✓移行リスクの低減: PQ-TLS は対応クライアントのみが自動的に利用し、非対応クライアントは従来方式で接続継続のため、アプリケーション改修なしで段階的に導入できる

🔬 技術面

✓耐量子暗号への対応: ML-KEM と古典的楕円曲線のハイブリッド鍵交換で、古典暗号と耐量子暗号の両方の強度を確保
✓可観測性の向上: 一時テーブルボリュームと FTS キャッシュの新メトリクスで逼迫を事前検知し、CloudWatch アラームで自動通知
✓開発生産性の向上: DELETE ... RETURNING により削除行の値の取得が 1 ステートメントで完結し、ラウンドトリップを削減
✓信頼性の向上: Write Forwarding、Global Database スイッチオーバー、Enhanced Binlog、並列クエリなど多数の安定性修正を含む

⚠️ デメリット・制約事項

🚫 制限事項

✗PQ-TLS のハイブリッド鍵交換は TLS 1.3 接続が対象で、クライアント側の対応が必要
✗RETURNING 句は単一テーブルの DELETE 文のみでサポート
✗RETURNING が予約語になったため、returning という名前の識別子を使用している既存スキーマではバッククォートによる修正が必要になる場合がある

🤔 考慮すべき点

⚠アップグレード高速化の恩恵を受けられるのは、バージョン 3.08 以降からのアップグレード
⚠自動マイナーバージョンアップグレード有効時はメンテナンスウィンドウ中に実行されるため、業務影響の少ない時間帯に設定しておく必要がある
⚠コミュニティ版 MySQL 8.0.46 との細かな動作差異 (行サイズ見積もりなど) があるため、互換性を前提とする場合はリリースノートの確認が必要

シナリオ: 長期保存が必要な金融取引データを扱うシステムで、将来の量子コンピュータによる復号リスクに備え、転送中データの暗号化を耐量子暗号へ移行したい。

-- PQ-TLS 対応クライアントで接続後、ネゴシエート結果を確認

✨ 効果: アプリケーションの大規模な改修なしに、対応クライアントから順次 PQ-TLS 接続へ移行でき、長期的なデータ機密性の要件を満たせる。

🏢 ユースケース 2: 大規模マルチアカウント環境での計画的なアップグレード展開

シナリオ: AWS Organizations 配下の多数のアカウントで数百の Aurora MySQL クラスターを運用しており、検証環境から本番環境へ段階的にマイナーバージョンアップグレードを展開したい。

Bash実装例
# 自動マイナーバージョンアップグレードを有効化し、
# Organizations の Upgrade Rollout Policy で展開順序を制御

  --db-instance-identifier my-aurora-instance \
  --auto-minor-version-upgrade

✨ 効果: 検証環境で問題がないことを確認してから本番環境へ展開するフェーズドロールアウトを組織全体で統制でき、アップグレード起因の障害リスクを低減できる。

📈 ユースケース 3: 一時テーブル使用量の監視によるストレージ逼迫の予防

シナリオ: 分析系クエリが多いワークロードで、一時テーブルによるクラスターボリュームの消費が急増し、気付かないうちにストレージコストが増加していた。

Bash実装例
# 一時テーブルボリューム使用量に CloudWatch アラームを設定
aws cloudwatch put-metric-alarm \
  --alarm-name aurora-temp-table-volume-high \
  --namespace AWS/RDS \
  --metric-name AuroraTempTableVolumeTotalBytes \
  --dimensions Name=DBClusterIdentifier,Value=my-aurora-cluster \
  --statistic Maximum \
  --period 300 \
  --evaluation-periods 3 \
  --threshold 53687091200 \
  --comparison-operator GreaterThanThreshold \
  --alarm-actions arn:aws:sns:ap-northeast-1:123456789012:ops-alerts

✨ 効果: 一時テーブルの使用量が閾値 (例: 50 GB) を超えた時点で通知を受け取り、ストレージを大量消費するクエリを特定して事前に対処できる。
