Amazon CloudWatch - EKS Container Insights

☁️ EKS Container Insights によるオープンソース Kubernetes ツールの組み込みモニタリング

📅 リリース日: 2026 年 11 月 20 日 | 🏷️ 機能: オープンソース Kubernetes ツール向け組み込みモニタリング

📝 概要

Amazon CloudWatch の EKS Container Insights が、Amazon EKS クラスター上で稼働する オープンソース Kubernetes ツールの組み込みモニタリングを提供するようになりました。 対象は Karpenter、KEDA、vLLM、KServe、SGLang、Ray、Knative Serving の 7 つのツールで、 OTel Container Insights を有効化するだけで自動的にモニタリングが開始され、専用のダッシュボードが利用できます。

最大の価値は「すでに使用しているツールのダッシュボードを、Prometheus や Grafana を自前で運用することなく入手できる」点です。 AI 推論ワークロードではキュー内リクエスト数、Time to First Token、KV キャッシュ使用率を確認でき、 オートスケーリングでは失敗しているスケーラーやスケールループの所要時間が表示されます。 すべてのメトリクスに Pod、ワークロード、ノードのタグが付与されるため、遅延しているモデルサーバーを基盤ノードまで遡って追跡できます。

❌ アップデート前の課題

✗オープンソースツールのメトリクス可視化には Prometheus と Grafana の自前構築・運用が必要だった
✗ツールごとにスクレイプ設定やダッシュボードを個別に作成・保守する必要があり、運用負荷が高かった
✗ツールのメトリクスとノード・Pod の情報が分離しており、推論遅延やスケーリング失敗の原因切り分けに時間がかかった

✅ アップデート後の改善

✓OTel Container Insights を有効化するだけで、7 つのツールのモニタリングが自動的に開始される
✓Prometheus / Grafana の自前運用なしで、CloudWatch の組み込みダッシュボードを利用できる
✓全メトリクスに Pod / ワークロード / ノードのタグが付与され、遅いモデルサーバーを基盤ノードまでトレースできる

🛠️ 設定方法

📋 前提条件

✓Amazon EKS クラスターが稼働していること
✓amazon-cloudwatch-observability アドオンまたは Helm チャートのバージョン 8.0.0 以降を使用すること
✓モニタリング対象のオープンソースツール (Karpenter、KEDA、vLLM など) がクラスターにデプロイされていること

STEP 1現在のアドオンバージョンを確認する

Bash アドオンバージョンの確認 
aws eks describe-addon \
  --cluster-name <cluster-name> \
  --addon-name amazon-cloudwatch-observability \
  --query addon.addonVersion --output text

インストール済みの amazon-cloudwatch-observability アドオンのバージョンを表示します。v8.0.0 以降でない場合はアップグレードが必要です。

STEP 2OTel Container Insights を有効化する

Bash OTel Container Insights の有効化 
aws eks update-addon \
  --cluster-name <cluster-name> \
  --addon-name amazon-cloudwatch-observability \
  --configuration-values '{"otelContainerInsights":{"enabled":true}}'

このコマンドはアドオン設定全体を置き換えるため、他の設定値を使用している場合は既存の設定にマージして指定します。有効化すると、対象ツールのモニタリングが自動的に開始されます。

STEP 3CloudWatch コンソールでダッシュボードを確認する

⚠️ デメリット・制約事項

🚧 制限事項

⚠️アドオンおよび Helm チャートのバージョン 8.0.0 以降が必要
⚠️対応ツールは Karpenter、KEDA、vLLM、KServe、SGLang、Ray、Knative Serving の 7 つに限定される
⚠️CloudWatch が OpenTelemetry メトリクスをサポートするリージョンでのみ利用可能

🤔 考慮すべき点

⚠️メトリクスは Amazon EKS の OpenTelemetry 取り込みレート (1 GB あたり 0.08 USD) で課金されるため、取り込み量の増加によるコストを見積もる必要がある
⚠️既存バージョン (6.x / 7.x) からのアップグレード時は、メトリクスの系列やラベルの変更に伴い、既存のクエリ・ダッシュボード・アラームへの影響を事前に確認することが推奨される

🎯 ユースケース

1️⃣ vLLM による LLM 推論基盤のパフォーマンス監視

シナリオ: EKS 上で vLLM を使用して LLM 推論 API を提供しており、応答遅延の原因特定に時間がかかっている。

Bash 実装例 
aws eks update-addon \
  --cluster-name llm-inference-cluster \
  --addon-name amazon-cloudwatch-observability \
  --configuration-values '{"otelContainerInsights":{"enabled":true}}'

効果: モデルサーバーごとのキュー内リクエスト数、Time to First Token、KV キャッシュ使用率が組み込みダッシュボードで可視化され、遅延しているモデルサーバーを基盤ノードまで遡って特定できる。

2️⃣ KEDA によるイベント駆動オートスケーリングの健全性監視

シナリオ: KEDA でキューの深さに応じた Pod オートスケーリングを構成しているが、スケーラーの失敗に気づくのが遅れ、処理遅延が発生することがある。

Text 確認手順 
CloudWatch コンソール → Container Insights →
対象クラスターの KEDA ダッシュボードで
失敗しているスケーラーとスケールループ所要時間を確認

効果: 失敗しているスケーラーをダッシュボードで即座に特定でき、スケーリング不全による処理遅延を未然に防止できる。

3️⃣ Prometheus / Grafana 自前運用からの移行

シナリオ: Karpenter と Knative Serving の監視のために Prometheus と Grafana を自前で運用しており、監視基盤自体の保守 (バージョンアップ、ストレージ管理、可用性確保) が負担になっている。

Text 移行ステップ 
1. アドオンを v8.0.0 以降にアップグレード
2. OTel Container Insights を有効化
3. 組み込みダッシュボードで監視項目を検証
4. 自前運用の Prometheus / Grafana を段階的に廃止

効果: 監視基盤の自前運用が不要になり、マネージドな CloudWatch ダッシュボードに集約することで運用負荷とインフラコストを削減できる。

📦 CloudWatch Container Insights

コンテナワークロードのメトリクスとログを収集・可視化する機能。本アップデートは OTel Container Insights の拡張にあたる。

📡 AWS Distro for OpenTelemetry

OpenTelemetry の AWS ディストリビューション。OTel Container Insights は OpenTelemetry Collector を基盤としている。

✅ まとめ

EKS 上で広く使われるオープンソースツールのモニタリングが、OTel Container Insights の有効化だけで利用できるようになり、 Prometheus / Grafana の自前運用が不要になる重要なアップデートです。 特に vLLM や SGLang などで LLM 推論基盤を運用するチームにとって、Time to First Token や KV キャッシュ使用率を標準ダッシュボードで確認できる価値は大きいといえます。

✓推奨アクション: まずはアドオンを v8.0.0 以降にアップグレードし、検証環境で組み込みダッシュボードの内容を確認する
