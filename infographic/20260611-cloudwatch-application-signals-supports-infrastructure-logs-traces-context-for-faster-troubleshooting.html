Amazon CloudWatch Application Signals

📡 インフラ・ログ・トレースのコンテキストで
トラブルシューティングを高速化

サービスヘルスランキング＋新しいインフラ／ログ／トレースタブで、根本原因の特定を 1 か所に集約
リリース日
2026 年 6 月 11 日

🔍 概要

Amazon CloudWatch Application Signals に、アプリケーションマップ上の サービスヘルスランキング と、サービス概要ページ上の新しい 「インフラストラクチャ」「ログ」「トレース」タブ が追加されました。 運用担当者は不健全なサービスをトリアージし、基盤となるコンピューティング環境、ログスニペット、 トレースの詳細を 1 か所 で確認できます。

アプリケーションマップは、サービスをヘルス状態でランク付けし、Amazon EKS / ECS / AWS Lambda / Amazon EC2 の サービスノード上に ランタイムインジケーター を表示します。可観測性の主要シグナルである メトリクス・ログ・トレースを統合的に扱うことで、平均修復時間 (MTTR) の短縮 を目指す 運用チームやアプリケーション開発者が主な対象です。

⚠️ アップデート前の課題

  • ヘルス確認後、根本原因調査のため X-Ray や CloudWatch Logs など別ツールへの切り替えが必要だった
  • 不健全なサービスを直感的に把握しづらく、トリアージに時間がかかった
  • コンピューティング環境 (EKS / ECS / Lambda / EC2) の状態とアプリのシグナルを関連付ける手段が限られていた

✅ アップデート後の改善

  • アプリケーションマップでサービスをヘルス状態順にランク付けし、問題のあるサービスを素早く特定
  • インフラ・ログ・トレースタブにより 1 か所で根本原因を調査できる
  • ランタイムインジケーターと関連ツールへのディープリンクでツール間移動を削減

コンピューティング環境から収集されたメトリクス・ログ・トレースが Application Signals に集約され、 アプリケーションマップのヘルスランキングとサービス概要ページの 3 つのタブを通じて、 運用担当者が単一画面でトラブルシューティングを行えます。

⭐ 主要機能

① アプリケーションマップのサービスヘルスランキング

  • サービスをヘルス状態に基づいてランク付け
  • 不健全なサービスを視覚的に素早く特定し、トリアージを効率化
  • EKS / ECS / Lambda / EC2 のサービスノードにランタイムインジケーターを表示

② 🏗️ インフラストラクチャタブ

  • サービスを支えるコンピューティング・ランタイム環境とその構成要素を表示
  • キュレートされたデフォルトメトリクスで環境の状態を一目で確認
  • 関連モニタリングツールへのディープリンクで詳細な調査へ素早く遷移

③ 📋 ログタブ

  • サービスに関連するログスニペットをサービス概要ページ上で直接確認
  • 別ツールへ切り替えずに根本原因の手がかりを取得

④ 🔍 トレースタブ

  • サービスに関連するトレースの詳細をサービス概要ページ上で確認
  • メトリクス・ログと組み合わせて、リクエスト経路・遅延・エラー箇所を特定

🛠️ 設定方法

前提条件

  • 対象アプリで CloudWatch Application Signals が有効化されていること
  • サポート言語 (Java / Python / Node.js / .NET) で実装されていること
  • Amazon EKS / ECS / AWS Lambda / Amazon EC2 のいずれかで稼働していること

インフラ／ログ／トレース

コンソールまたは StartDiscovery API でサービスディスカバリーを開始するとトポロジーが自動検出されます。 アプリケーションマップでヘルス状態順にランク付けされたノードを選択し、サービス概要ページの各タブで コンピューティング環境・ログスニペット・トレース詳細を確認、必要に応じてディープリンクから関連ツールへ遷移します。

💡 メリット

📈 ビジネス面

  • MTTR の短縮: トリアージと根本原因調査を 1 か所で実施し障害解決を高速化
  • 運用負荷の軽減: 複数ツールの切り替えが不要に
  • 追加コストの抑制: 既存機能の拡張として提供、新ツール導入不要

🔧 技術面

  • コンテキストの一元化: インフラ・ログ・トレースを単一画面に集約し相関分析が容易
  • マルチプラットフォーム対応: EKS / ECS / Lambda / EC2 で統一されたヘルス可視化
  • ディープリンク連携: CloudWatch Logs や X-Ray へ素早く遷移

⚠️ デメリット・制約事項

  • Application Signals の利用には CloudWatch の課金が発生する
  • ランタイムインジケーターは Amazon EKS / ECS / AWS Lambda / Amazon EC2 でサポート
  • Application Signals は Canada West (Calgary) を除く すべての商用リージョンでサポート
  • サポート対象外のアーキテクチャでは、サービス名や環境名の手動指定が必要な場合がある
  • ログ・トレースの収集量に応じて CloudWatch Logs および X-Ray の料金が発生する

🎯 ユースケース

① マイクロサービス障害の迅速なトリアージ

シナリオ: 複数のマイクロサービスで構成された Amazon EKS 上のアプリでレイテンシー上昇が報告された。

効果: マップでヘルス状態順にサービスを確認し最も不健全なサービスを即座に特定。インフラタブでノードのリソース状況を確認し原因を素早く絞り込む。

② ログとトレースを併用した根本原因分析

シナリオ: AWS Lambda 関数でエラー率が上昇しているが原因が不明。

効果: トレースタブで失敗したリクエストの経路を確認し、ログタブで対応するエラーログスニペットを参照。ツールを切り替えずに根本原因を特定。

③ コンピューティング環境の健全性確認

シナリオ: Amazon ECS 上のサービスでパフォーマンス低下が発生している。

効果: インフラタブでコンテナ環境とキュレートされたデフォルトメトリクスを確認し、ディープリンクから関連ツールへ遷移して詳細を分析。

💰 料金・利用可能リージョン

本機能は CloudWatch Application Signals の一部として提供されます。利用には CloudWatch の料金が適用され、 収集されるシグナル (メトリクス・ログ・トレース) の量に応じて課金されます。

Amazon CloudWatch Application Signals がサポートされているすべての AWS リージョンで利用可能です。

🌏 サポート対象の全商用リージョン 🚫 Canada West (Calgary) を除く

📝 まとめ

このアップデートにより、CloudWatch Application Signals は不健全なサービスのトリアージから根本原因の特定までを単一画面で完結でき、 運用チームの MTTR 短縮に貢献します。

EKS / ECS / Lambda / EC2 を運用するチームは、アプリケーションマップのヘルスランキングと 新しいインフラ・ログ・トレースタブを活用し、トラブルシューティングのワークフローを見直すことを推奨します。
