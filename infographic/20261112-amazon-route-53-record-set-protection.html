Amazon Route 53

🛡️ レコードセット保護のサポート

重要な DNS レコードを誤った変更・削除から直接保護
📅 リリース日
2026 年 11 月 12 日

📌 概要

Amazon Route 53 がレコードセット保護 (Record Set Protection) に対応しました。ホストゾーン内の重要な DNS レコード (ゾーン apex、MX レコード、本番エンドポイントへのルーティングレコードなど) に保護を設定し、誤った変更や削除を防止できます。保護されたレコードへの変更リクエストは、権限を持つユーザーが保護を解除するまですべてブロックされます。

保護はレコードの名前とタイプの組み合わせで指定し、異なる set identifier を持つ weighted や latency などのルーティングポリシーレコードもまとめて保護されます。レコードが存在しない段階で予防的に保護を作成し、その名前・タイプでのレコード作成自体を防止することも可能です。各保護には最大 256 文字のコメントを付与でき、ブロック時のエラーメッセージに含まれます。

❌ アップデート前の課題
  • 重要レコードの保護手段は IAM ポリシーのみ
  • 全ユーザー・ロールの IAM ポリシーにレコードレベルの条件を個別に記述する必要があった
  • ブロック時に呼び出し元へ保護の有無や理由が伝わらなかった
  • ユーザー追加のたびにポリシーの整合性維持の運用負荷が発生
✅ アップデート後の改善
  • 名前とタイプを指定するだけでレコードを保護、IAM ポリシーへの条件記述が不要に
  • route53:* を持つプリンシパルを含むすべてのユーザー・ロールに適用、ポリシー条件で上書き不可
  • エラーメッセージに保護コメントが含まれ、理由と対処方法が伝わる
  • 予防的な保護で新規レコード作成も防止可能

保護されたレコードへの ChangeResourceRecordSets リクエストは、IAM 権限にかかわらず InvalidChangeBatch エラーでブロックされ、DeleteResourceRecordSetProtections 権限を持つ管理者が保護を解除した場合のみ変更が可能になります。

⚙️ 主要機能

1️⃣ 名前とタイプによるレコード保護
  • ホストゾーン内のレコード名とタイプの組み合わせで指定 (例: www.example.com と A)
  • 同じ名前・タイプのすべてのレコードをカバーし、異なる set identifier を持つ weighted、latency などのルーティングポリシーレコードも一括で保護 (一部のみの保護は不可)
  • ChangeResourceRecordSets が受け付けるすべてのレコードタイプを保護でき、ゾーン apex の NS・SOA レコードも対象
2️⃣ すべてのプリンシパルに適用される強制力
  • route53:* のフル権限を持つユーザーを含む、すべてのユーザー・ロールに適用
  • route53:ChangeResourceRecordSets に対する IAM ポリシー条件では上書き不可
  • CloudFormation、AWS CLI、SDK からの変更も同様に InvalidChangeBatch エラーでブロック
3️⃣ 予防的な保護 (レコードの事前予約)
  • レコードが存在しない名前・タイプに対しても保護を作成可能
  • 保護を削除するまで、その名前・タイプでのレコード作成を防止
  • 予約された名前は保護の一覧には表示されるが、レコードの一覧には表示されない
4️⃣ コメントによる理由の伝達
  • 各保護に最大 256 文字のコメントを付与可能
  • ブロック時のエラーメッセージにコメントが含まれ、呼び出し元が保護の理由や連絡先を把握できる
  • コメントの更新は不可 (変更する場合は保護を削除して再作成)
5️⃣ 全件一括処理のリクエスト
  • 保護の作成・削除は all-or-nothing (すべて処理されるか、まったく処理されないか)
  • ChangeResourceRecordSets も、いずれかの変更が保護に抵触した場合はリクエスト全体が拒否される

🔐 権限と保護解除の統制

保護の強度は route53:DeleteResourceRecordSetProtections 権限の統制に依存します。解除権限は少数の管理者に限定し、必要に応じて SCP での拒否も検討してください。保護関連の 3 つのアクションはホストゾーンリソースのみをサポートし、サービス固有の条件キーはサポートしません。

JSON 保護の解除を明示的に拒否するポリシー例 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Deny",
      "Action": "route53:DeleteResourceRecordSetProtections",
      "Resource": "arn:aws:route53:::hostedzone/*"
    }
  ]
}

🛠️ 設定方法

✅ 前提条件

✓Route 53 のパブリックまたはプライベートホストゾーンが存在すること
✓route53:CreateResourceRecordSetProtections などの保護関連アクションの権限を持つこと
✓AWS CLI を使用する場合は、本機能に対応したバージョンへ更新済みであること
🛡️ 保護の作成
→
📋 保護の一覧確認
→
🔓 解除 → 変更 → 再作成

ステップ 1: 保護の作成

Bash ゾーン apex の A・MX レコードに保護を作成 
aws route53 create-resource-record-set-protections \
    --hosted-zone-id Z1D633PJN98FT9 \
    --protections '[{"RecordName":"example.com","RecordType":"A","Comment":"Production apex. Contact the DNS team before changing."},{"RecordName":"example.com","RecordType":"MX"}]'

A レコードにはコメント付きの保護、MX レコードにはコメントなしの保護を設定。成功すると空のレスポンスが返ります。1 リクエストで最大 100 件まで指定できます。

ステップ 2: 保護の一覧確認

Bash ホストゾーン内の保護を一覧表示 
aws route53 list-resource-record-set-protections \
    --hosted-zone-id Z1D633PJN98FT9

結果はレコード名、レコードタイプの順にソートされ、RecordName は末尾にドットが付いた完全修飾形式で返されます。コンソールの場合は、ホストゾーン詳細ページの [Protections] タブで確認できます。

ステップ 3: 保護されたレコードを変更する場合

Bash 保護を削除してからレコードを変更 
aws route53 delete-resource-record-set-protections \
    --hosted-zone-id Z1D633PJN98FT9 \
    --protections '[{"RecordName":"example.com","RecordType":"A"}]'

保護を削除してからレコードを変更し、必要であれば保護を再作成します。保護が残っている状態でレコードを変更しようとすると、以下のようなエラーが返ります。

Text ブロック時のエラーメッセージ例 
RRSet with DNS name www.example.com., type A is protected and cannot be changed.
Protection comment: "Production apex. Contact the DNS team before changing.".
Call DeleteResourceRecordSetProtections for this record set before changing it.

💡 メリット

💼 ビジネス面
  • 障害リスクの低減: apex や MX などへのガードレールで、DNS 起因のサービス停止・メール不達のリスクを低減
  • 運用負荷の削減: IAM ポリシーへのレコードレベル条件の記述・維持が不要に
  • 円滑なコミュニケーション: 保護コメントで理由と連絡先がその場で伝わる
🔧 技術面
  • IAM 権限より強い強制力: route53:* を持つプリンシパルにも適用
  • ルーティングポリシーレコードの一括保護: weighted / latency レコードも 1 つの保護でカバー
  • 予防的な名前の予約: 意図しないレコード作成を防止
  • 監査性: 保護の操作は CloudTrail に記録

⚠️ デメリット・制約事項

🚧 制限事項

✗保護は名前とタイプ単位で適用され、特定の set identifier のレコードだけを保護することはできない
✗保護のコメントは更新不可 (変更には削除と再作成が必要)
✗保護の作成・削除は 1 リクエストあたり最大 100 件、一覧取得は 1 ページあたり最大 300 件
✗保護が残っているホストゾーンは削除できない (先にすべての保護の削除が必要)
✗ホストゾーンあたりの保護数にはクォータがあり、超過すると LimitsExceeded エラーになる

🤔 考慮すべき点

⚠保護の強度は route53:DeleteResourceRecordSetProtections 権限の統制に依存するため、解除権限を少数の管理者に限定し、SCP での拒否も検討する
⚠apex の NS・SOA レコードへの保護はユーザーの変更をブロックするが、Route 53 自身によるホストゾーン管理のための更新は妨げない
⚠CloudFormation などの IaC で保護対象レコードを管理している場合、スタック更新が InvalidChangeBatch エラーで失敗するため、変更時の運用フロー (保護の解除と再作成) の整備が必要
⚠加速リカバリ (accelerated recovery) の有効化・無効化中は、保護の作成・削除が Throttling エラーになる場合があり、リトライが必要

🎯 ユースケース

1. 本番ドメインのゾーン apex と MX レコードの保護

シナリオ: 複数のチームが同一ホストゾーンを管理しており、本番ドメインの apex レコードやメール配送に使う MX レコードの誤変更によるサービス停止・メール不達を防ぎたい。

Bash実装例
aws route53 create-resource-record-set-protections \
    --hosted-zone-id Z1D633PJN98FT9 \
    --protections '[
      {"RecordName":"example.com","RecordType":"A","Comment":"本番 apex。変更前に DNS チームへ連絡してください。"},
      {"RecordName":"example.com","RecordType":"MX","Comment":"メール配送用。変更前に DNS チームへ連絡してください。"}
    ]'

効果: フル権限を持つユーザーを含め、apex と MX レコードへの変更がすべてブロックされ、エラーメッセージのコメントで連絡先が伝わるため、意図しない変更による障害を防止できる。

2. ルーティングポリシーレコード群の一括保護

シナリオ: 本番エンドポイント www.example.com に weighted ルーティングの A レコードが複数存在し、トラフィック配分を誤って変更されるリスクを排除したい。

Bash実装例
aws route53 create-resource-record-set-protections \
    --hosted-zone-id Z1D633PJN98FT9 \
    --protections '[{"RecordName":"www.example.com","RecordType":"A","Comment":"本番トラフィック配分。変更は CAB 承認後に実施。"}]'

効果: 1 つの保護で、異なる set identifier を持つすべての weighted A レコードがまとめて保護され、トラフィック配分の意図しない変更を防止できる。

3. 予防的な保護による名前の予約

シナリオ: 将来の利用のために予約しておきたいサブドメイン名があり、他のチームがその名前・タイプでレコードを作成してしまうことを防ぎたい。

Bash実装例
aws route53 create-resource-record-set-protections \
    --hosted-zone-id Z1D633PJN98FT9 \
    --protections '[{"RecordName":"api.example.com","RecordType":"CNAME","Comment":"新 API 基盤用に予約済み。プラットフォームチーム管理。"}]'

効果: レコードが存在しない段階でも名前とタイプを予約でき、保護を削除するまで api.example.com の CNAME レコードの作成が防止される。

🔑 AWS IAM / サービスコントロールポリシー

route53:DeleteResourceRecordSetProtections 権限の統制が保護の実効性を左右する。SCP による解除権限の拒否と組み合わせることで統制を強化できる。

📜 AWS CloudTrail

保護の作成・削除・一覧取得の API 呼び出しが記録され、監査証跡として利用できる。

📦 AWS CloudFormation

保護対象レコードへのスタック経由の変更も同様にブロックされるため、IaC 運用では変更フローへの組み込みが必要。

⚡ Route 53 加速リカバリ

保護は加速リカバリの有効・無効やフェイルオーバー中も維持され、フェイルオーバー中も保護の作成・削除・一覧取得が可能。

📝 まとめ

Amazon Route 53 のレコードセット保護により、IAM ポリシーの複雑な条件記述なしに、重要な DNS レコードを誤変更から直接保護できるようになりました。保護はフル権限を持つユーザーにも適用される強力なガードレールであり、ブロック時にはコメント付きのエラーで理由が伝わるため、運用上の混乱も最小限に抑えられます。

💡 推奨アクション: 本番ドメインの apex、MX、重要エンドポイントのレコードから保護の適用を始め、あわせて DeleteResourceRecordSetProtections 権限の統制 (IAM・SCP) を整備することを推奨します。
