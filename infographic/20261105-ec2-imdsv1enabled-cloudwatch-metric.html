📊 ImdsV1Enabled CloudWatch メトリクスの公開

🗓️ リリース日: 2026 年 11 月 5 日 | IMDSv1 有効インスタンスを設定ベースで特定

💡 概要

Amazon EC2 は、インスタンスメタデータサービスバージョン 1 (IMDSv1) が有効になっている EC2 インスタンスを特定できる新しい CloudWatch メトリクス ImdsV1Enabled の公開を開始しました。各インスタンスの設定 (HttpTokens の値) に基づいて発行され、 値 1 は IMDSv1 が有効 (optional)、値 0 は IMDSv1 が無効 (required) を示します。

従来の MetadataNoToken は IMDSv1 の呼び出しが実際に発生したときのみ発行されるのに対し、 ImdsV1Enabled は設定そのものを反映するため、呼び出しがなくても「IMDSv1 を許可したまま」のインスタンスを特定できます。 IMDSv2 はトークンベース認証により SSRF (サーバーサイドリクエストフォージェリ) などへの多層防御を提供するため、全面移行を進めるセキュリティチームに有用です。

❌ Before: アップデート前の課題
  • MetadataNoToken は呼び出し発生時のみ発行され、「許可しているが呼び出しがない」インスタンスを検出できなかった
  • 複数アカウント・複数リージョンの棚卸しには describe-instances を定期実行する独自ツールの構築が必要だった
  • 移行進捗を継続的・定量的に可視化する標準的な手段がなかった
✅ After: アップデート後の改善
  • 設定に基づいて発行されるため、呼び出しがなくても IMDSv1 許可インスタンスを特定できる
  • CloudWatch ダッシュボードとアラームだけで、アカウント・リージョン横断の追跡が可能に
  • 独自ツールなしで IMDSv2 移行の残作業の把握と優先順位付けが可能に

各 EC2 インスタンスが自身の IMDS 設定に基づいて ImdsV1Enabled メトリクスを CloudWatch に発行し、 運用チームはダッシュボードとアラームで IMDSv1 を許可しているインスタンスを特定して IMDSv2 必須化を進めます。

⚙️ 主要機能

1️⃣ 設定ベースのメトリクス発行
✓AWS/EC2 名前空間に各インスタンスの IMDS 設定に基づいて発行
✓値 1: IMDSv1 有効 (HttpTokens = optional)、値 0: IMDSv1 無効 (HttpTokens = required)
✓呼び出しの有無に依存せず、IMDSv1 の利用がないインスタンスでも設定の棚卸しが可能
2️⃣ 移行進捗の定量的な追跡
✓Sum 統計で、そのアカウント・リージョンの IMDSv1 許可インスタンス数を把握
✓CloudWatch ダッシュボードで複数アカウント・複数リージョンの移行状況を一元的に可視化
✓CloudWatch アラームで IMDSv1 許可インスタンスの新規出現を検知
3️⃣ 既存の IMDS 関連メトリクスとの補完関係
✓MetadataNoToken: IMDSv1 でのアクセス回数を記録 (IMDSv1 有効時のみ発行)
✓MetadataNoTokenRejected: 無効化後に拒否された IMDSv1 呼び出し回数を記録 (IMDSv1 無効時のみ発行)
✓3 つのメトリクスの組み合わせで移行の各フェーズを漏れなくモニタリング

🔍 IMDS 関連メトリクスの比較

メトリクス発行条件用途
ImdsV1Enabled インスタンスの設定に基づき常時発行 IMDSv1 を許可しているインスタンスの特定、移行進捗の追跡
MetadataNoToken IMDSv1 有効時に IMDSv1 呼び出しが発生した場合 IMDSv1 を実際に使用しているソフトウェアの検出
MetadataNoTokenRejected IMDSv1 無効時に IMDSv1 呼び出しが拒否された場合 IMDSv1 無効化後の影響確認

MetadataNoToken と MetadataNoTokenRejected は相互排他であり、 HttpTokens = optional のときは前者のみ、required のときは後者のみが発行されます。

🛠️ 設定方法

📋 前提条件

  • EC2 インスタンスが起動していること
  • CloudWatch メトリクスを参照できる IAM 権限 (cloudwatch:GetMetricData、cloudwatch:ListMetrics など) があること
  • 設定変更を行う場合は ec2:ModifyInstanceMetadataOptions 権限があること

ステップ 1: IMDSv1 を許可しているインスタンス数を確認する

Bash Sum 統計の取得 
aws cloudwatch get-metric-statistics \
  --namespace AWS/EC2 \
  --metric-name ImdsV1Enabled \
  --start-time 2026-11-05T00:00:00Z \
  --end-time 2026-11-05T01:00:00Z \
  --period 300 \
  --statistics Sum

Sum の値が、その期間に IMDSv1 を許可している (HttpTokens = optional) インスタンスの数に相当します。

ステップ 2: IMDSv1 を許可している具体的なインスタンスを特定する

Bash 対象インスタンスの一覧化 
aws ec2 describe-instances \
  --filters "Name=metadata-options.http-tokens,Values=optional" \
  --query "Reservations[*].Instances[*].[InstanceId]" \
  --output text

metadata-options.http-tokens が optional のインスタンス ID の一覧を出力します。

ステップ 3: CloudWatch アラームを作成して継続的に監視する

Bash アラームの作成 
aws cloudwatch put-metric-alarm \
  --alarm-name imdsv1-enabled-instances \
  --namespace AWS/EC2 \
  --metric-name ImdsV1Enabled \
  --statistic Sum \
  --period 300 \
  --evaluation-periods 1 \
  --threshold 0 \
  --comparison-operator GreaterThanThreshold \
  --alarm-actions arn:aws:sns:ap-northeast-1:123456789012:imds-alerts

IMDSv1 を許可するインスタンスが 1 台でも存在する場合に SNS トピックへ通知します。

ステップ 4: 対象インスタンスで IMDSv2 を必須化する

Bash IMDSv2 の必須化 
aws ec2 modify-instance-metadata-options \
  --instance-id i-0123456789abcdef0 \
  --http-tokens required \
  --http-endpoint enabled

実行中のインスタンスに再起動なしで即時反映されます。無効化後は MetadataNoTokenRejected で拒否された IMDSv1 呼び出しの有無を監視します。

🎯 メリット

💼 ビジネス面
✓セキュリティ態勢の可視化: IMDSv2 移行の進捗を定量的に経営層や監査に報告できる
✓運用コストの削減: 横断的な棚卸しツールの独自開発・保守が不要になる
✓追加コストなし: メトリクスは追加料金なしで発行され、導入の障壁がない
🔧 技術面
✓設定ベースの検出: 呼び出しの有無に依存せず漏れなく検出できる
✓既存メトリクスとの補完: 2 つの既存メトリクスと組み合わせて全フェーズをカバー
✓自動化との親和性: アラームや EventBridge と連携し、検出から是正まで自動化できる

⚠️ デメリット・制約事項

制限事項

⚠️設定状態を示すのみであり、どのソフトウェアが IMDSv1 を使用しているかの特定には MetadataNoToken や IMDS Packet Analyzer の併用が必要
⚠️複数アカウントの集約表示には CloudWatch のクロスアカウントオブザーバビリティなどの追加設定が必要
⚠️メトリクスの確認だけでは是正されない。IMDSv2 必須化には ModifyInstanceMetadataOptions などによる設定変更が別途必要

考慮すべき点

💡IMDSv1 無効化前に MetadataNoToken で呼び出しゼロを確認し、SDK やエージェントを IMDSv2 対応バージョンへ更新しておく
💡恒久対策として、アカウントレベルの IMDS デフォルト設定 (ModifyInstanceMetadataDefaults) や AWS Organizations の宣言型ポリシーによる IMDSv2 強制の併用が推奨される

💼 ユースケース

📊 ユースケース 1: 組織全体の IMDSv2 移行進捗ダッシュボード

シナリオ: 複数アカウント・複数リージョンで数千台の EC2 インスタンスを運用し、IMDSv2 必須化を全社的に推進。

  1. CloudWatch クロスアカウントオブザーバビリティでモニタリングアカウントにメトリクスを集約
  2. ImdsV1Enabled の Sum をアカウント・リージョンごとにウィジェット化したダッシュボードを作成
  3. 週次で Sum の推移を確認し、残存インスタンスの多いアカウントから優先的に是正

効果: 独自の棚卸しスクリプトなしで移行進捗を一元的に可視化し、是正の優先順位付けが容易になる。

🔔 ユースケース 2: IMDSv1 許可インスタンスの新規出現の検知

シナリオ: IMDSv2 必須化完了後、古い AMI や起動テンプレートからの誤起動を防止したい。

  1. ImdsV1Enabled の Sum > 0 を条件とする CloudWatch アラームを作成
  2. アラームアクションで SNS トピックに通知し、セキュリティチームへエスカレーション
  3. 必要に応じて EventBridge と Lambda で ModifyInstanceMetadataOptions を自動実行

効果: 設定ドリフトを早期に検知し、IMDSv1 許可状態の放置を防止できる。

🛡️ ユースケース 3: IMDSv1 無効化前の安全確認

シナリオ: レガシーアプリケーションが稼働するインスタンス群で、影響を最小化しながら段階的に IMDSv2 必須化を進めたい。

  1. ImdsV1Enabled = 1 のインスタンスを対象リストとして抽出
  2. 各インスタンスの MetadataNoToken を監視し、IMDSv1 呼び出しゼロを一定期間確認
  3. IMDS Packet Analyzer で呼び出し元ソフトウェアを特定し、必要な更新を実施
  4. HttpTokens = required に変更後、MetadataNoTokenRejected で拒否呼び出しの有無を監視

効果: 3 つのメトリクスを組み合わせ、サービス影響のリスクを抑えた段階的な移行が可能になる。

📝 まとめ

ImdsV1Enabled メトリクスの登場により、IMDSv1 を許可しているインスタンスを呼び出しの有無にかかわらず、 追加コストなしで継続的に特定できるようになりました。 IMDSv2 への移行を進めている組織は、まず本メトリクスでアカウント・リージョン横断の現状を把握し、 MetadataNoToken / MetadataNoTokenRejected と組み合わせた段階的な IMDSv1 無効化を進めることを推奨します。
