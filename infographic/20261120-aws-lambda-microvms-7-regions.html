Lambda MicroVMs が 7 つの追加リージョンで利用可能に

📅 リリース日: 2026 年 11 月 20 日 | 機能: AWS Lambda MicroVMs のリージョン拡大

📌 概要

AWS Lambda MicroVMs が新たに 7 つの AWS リージョンで利用可能になり、対応リージョンは 合計 21 リージョンに拡大しました。Lambda MicroVMs は、VM レベルの分離、ほぼ瞬時の起動・再開、状態の保持を提供するサーバーレスコンピューティングプリミティブで、ユーザーや AI が生成したコードを安全に実行する環境として設計されています。

日本のユーザーにとっては、大阪リージョンでの提供開始により、国内でのマルチリージョン構成や低レイテンシーでの利用の選択肢が広がる点が注目です。

❌ Before: アップデート前の課題
  • 限られたリージョンでのみ提供され、大阪・ソウル・ロンドンなどのユーザーは他リージョンを利用する必要があった
  • エンドユーザーから遠いリージョンではインタラクティブなコード実行環境のレイテンシーが増加
  • データレジデンシー要件があるワークロードでは採用できないケースがあった
✅ After: アップデート後の改善
  • 7 リージョン追加で合計 21 リージョンで利用可能に
  • エンドユーザーに近いリージョンで MicroVM を起動し、インタラクティブなユースケースのレイテンシーを低減
  • 各国・地域のデータレジデンシー要件を満たしつつ、分離されたコード実行環境を構築可能に

Lambda MicroVMs の基本的な利用フローです。Dockerfile からスナップショットベースの MicroVM イメージを作成し、ユーザーセッションやジョブごとに分離された MicroVM を起動して、専用の HTTPS エンドポイント経由でアクセスします。今回のアップデートで、この仕組みを大阪を含む 7 つの追加リージョンで利用できるようになりました。

🚀 主要機能

🌏 1. 7 つの追加リージョンでの提供開始

アジアパシフィック (大阪)、アジアパシフィック (ソウル)、カナダ (中部)、欧州 (ロンドン)、欧州 (パリ)、南米 (サンパウロ)、米国西部 (北カリフォルニア) で利用可能になり、対応リージョンは合計 21 リージョンに拡大。最新状況は AWS Capabilities by Region ページで確認できます。

🔒 2. VM レベルの分離と高速な起動・再開

Firecracker 仮想化技術によるテナント間の強力な分離を実現。初期化済みスナップショットからの再開により、アプリケーションの初期化をスキップしてほぼ瞬時に起動。アイドル時はメモリとディスクの状態を保持したままサスペンドし、コストを削減します。

🌐 3. 柔軟なネットワークと接続性

ユーザーやジョブごとに専用の HTTPS エンドポイントを提供し、ロードバランサーなどの追加インフラは不要。HTTP/2、gRPC、WebSocket をサポートし、アウトバウンドはパブリックインターネットアクセスと VPC アクセスを設定可能です。

🛠️ 4. 多様な利用インターフェース

Lambda コンソール、AWS CloudFormation、AWS CDK から利用可能。Agent Toolkit for AWS を通じて、エージェント型開発ツールからも利用できます。

ステップ 1: アプリケーションのパッケージングとアップロード

BashS3 へのアップロード
zip -r my-microvm-app.zip app/ Dockerfile
aws s3 cp my-microvm-app.zip s3://my-bucket/my-microvm-app.zip --region ap-northeast-3

アプリケーションコードと Dockerfile を zip アーカイブにまとめ、大阪リージョンの Amazon S3 バケットにアップロードします。

ステップ 2: MicroVM イメージの作成

Bashcreate-microvm-image
aws lambda create-microvm-image \
  --code-artifact uri=s3://my-bucket/my-microvm-app.zip \
  --build-role-arn arn:aws:iam::123456789012:role/microvm-build-role \
  --region ap-northeast-3

Lambda が Dockerfile を実行してアプリケーションを起動し、完全に初期化された環境のスナップショットを MicroVM イメージとしてキャプチャします。

ステップ 3: MicroVM の起動と接続

Bashrun-microvm
aws lambda run-microvm \
  --microvm-image-arn <MicroVM イメージの ARN> \
  --region ap-northeast-3

ユーザーセッションやジョブごとに MicroVM を起動します。起動後は返却される専用 HTTPS エンドポイントにクライアントから接続できます。アイドル時は suspend-microvm、再開時は resume-microvm を呼び出すか、ライフサイクルポリシーで自動制御できます。

🎯 ユースケース

🤖 ユースケース 1: 国内向け AI コード実行サンドボックス

シナリオ: 日本国内のユーザー向けに、AI が生成したコードを安全に実行するサンドボックスを提供する。データを国内に保持する要件がある。

  1. 大阪リージョン ap-northeast-3 で MicroVM イメージを作成
  2. AI エージェントのコード実行リクエストごとに run-microvm で分離環境を起動
  3. 実行完了後に terminate で環境を破棄

効果: 国内リージョンで完結した低レイテンシーかつ安全なコード実行環境を、サーバー管理なしで提供できる。

🌍 ユースケース 2: グローバル展開するインタラクティブ開発環境

シナリオ: ブラウザベースの開発環境サービスを、欧州や南米のユーザーにも提供したい。

  1. ロンドン、パリ、サンパウロの各リージョンに同一の MicroVM イメージを展開
  2. ユーザーの所在地に近いリージョンでセッション用 MicroVM を起動
  3. アイドル時はライフサイクルポリシーで自動サスペンドし、再接続時に自動再開

効果: ユーザーの体感レイテンシーを低減しながら、アイドル時間のコストを抑制できる。

🏗️ ユースケース 3: マルチテナント CI/CD の分離実行基盤

シナリオ: 複数の顧客のビルド・テストジョブを実行する SaaS で、テナント間の強力な分離が必要。

  1. ビルドツールチェーンを含む Dockerfile から MicroVM イメージを作成
  2. ジョブごとに run-microvm で専用環境を起動し、ジョブ完了後に terminate
  3. VPC アクセスを設定し、プライベートなアーティファクトリポジトリに接続

効果: テナントごとに VM レベルで分離されたビルド環境を、高速な起動で提供できる。
