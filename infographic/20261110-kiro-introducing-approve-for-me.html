Kiro

🤖 Approve for me

LLM による承認レビュー機能 — 定型アクションは自動承認、危険なアクションは自動ブロック
📅 リリース日: 2026 年 11 月 10 日

📝 概要

AWS が提供する AI 搭載 IDE である Kiro に、新しい承認モード Approve for me が導入されました。Kiro IDE、Kiro CLI、Kiro Web のすべてで利用できます。 許可ルールでカバーされないアクションに対して Kiro が LLM レビュー (現在は Anthropic のモデル) を実行し、 定型的なアクションは自動承認、安全でないアクションはブロック、判断がつかない場合のみユーザーに確認します。

これまでは「すべて手動承認」「カスタム許可ルールの整備」「trust-all-tools で承認を完全オフ」の三択でした。 承認プロンプトの大半は形式的なものとなっており、承認疲れによって安全でないアクションを見逃すリスクが生じていました。

❌ Before: アップデート前の課題

  • 長時間のエージェントタスクでは、読み取り・書き込み・シェル実行のたびに承認が必要で、作業のフローが中断
  • 承認プロンプトの頻発により trust-all-tools を有効化し、安全でないアクションも無条件実行されるリスク
  • カスタムエージェントでの事前承認ルールの整備には手間がかかり、全アクションの網羅は困難

✅ After: アップデート後の改善

  • ルール未カバーのアクションを LLM がレビューし、定型的なアクションは自動承認されるため承認プロンプトが大幅減少
  • 安全でないアクションは自動ブロックされ、trust-all-tools よりも安全に作業を進められる
  • 判断が難しいアクションのみ確認が求められ、意思決定が本当に必要な場面に集中できる
🔀 権限モードメニューへの変更 (Changelog 2026-11-10)
チャットの Autopilot トグルが権限モードメニューに変更され、「Supervised」「Accept file changes (旧 Autopilot)」「Approve for me」の 3 つのモードから選択できるようになりました。

Approve for me 有効時のアクション承認フローです。ユーザーが設定した許可ルール (allow / ask / deny) が常に優先され、 ルールでカバーされないアクションのみが LLM レビューに送られます。

⚙️ 主要機能

🧠 LLM レビューによる自動承認 (evaluate)
  • 許可ルールは従来「許可 (allow)」「確認 (ask)」「拒否 (deny)」の 3 択だった
  • 4 つ目の選択肢 evaluate を追加し、ユーザー確認の代わりに LLM レビューがアクションをチェック
  • 有効化すると、allow / ask / deny のいずれのルールにもカバーされないアクションに evaluate が適用される
  • 現在、LLM レビューには Anthropic のモデルが使用される
📋 ユーザー設定の許可ルールが常に優先
  • 明示的に許可・拒否したアクションや「常に確認」とマークしたアクションは LLM レビューに送られない
  • 安全と判断すれば実行、安全でないと判断すればブロック、判断できない場合はユーザーに確認
  • ブロックを含むステップが 3 回連続すると、Kiro はユーザーへの確認に戻り、その理由をプロンプトに含める
🎛️ チャットの権限モードメニュー (Changelog より)
  • 従来の Autopilot トグルが権限モードメニューに変更
  • 「Supervised」「Accept file changes (旧 Autopilot)」「Approve for me」の 3 モードから選択可能
  • Kiro IDE では What's new のスイッチで全新規チャットに有効化、またはチャット入力欄のメニューから現在のチャットに対して選択
🛡️ 多層防御 (defense-in-depth) の一部としての位置付け
  • Approve for me は承認要否の判断を行うものであり、シェルコマンドの実行後のアクセス範囲は制限しない
  • Kiro IDE / CLI ではローカルサンドボックスを有効化でき、OS レベルの境界とアウトバウンドネットワークの既定ブロックを追加できる
  • Kiro Web のセッションは、すでにマネージドなクラウドサンドボックス内で実行されている

機能または基盤となる Anthropic モデルが利用できない環境では、従来の承認エクスペリエンスが継続されます。

🚀 設定方法

前提条件

✓Kiro の有料プランを利用していること
✓Kiro IDE 1.4.154 以降、または Kiro CLI 2.36 以降に更新していること (Kiro Web は更新不要)
✓us-east-1 または eu-central-1 で機能が利用可能であること

手順

1
Kiro を最新バージョンに更新する
Kiro IDE を 1.4.154 以降、Kiro CLI を 2.36 以降に更新します。新規ユーザーは kiro.dev のダウンロードページから入手できます。
2
Approve for me を有効にする
デフォルトで無効のため、明示的に有効化します。
Kiro IDE: What's new のスイッチで全新規チャットに有効化、またはチャット入力欄のメニューから現在のチャットに対して選択
Kiro CLI / Kiro Web: 各製品の権限モード設定から Approve for me を選択
3
必要に応じて許可ルールとサンドボックスを併用する
明示的に制御したいアクションには allow / ask / deny の許可ルールを設定します。これらのルールは LLM レビューより常に優先されます。さらに、Kiro IDE と Kiro CLI ではローカルサンドボックスを有効化することで、シェルコマンドの実行に OS レベルの境界を追加できます。

💡 メリット

💼 ビジネス面

✓開発フローの維持による生産性向上: 定型アクションの承認プロンプトが大幅に減少。社内ユーザーからは「以前は ls のような基本操作に 15 回の承認が必要だったタスクが、承認ゼロになった」との報告
✓trust-all-tools からの安全な移行: 承認疲れで trust-all-tools を使っていたユーザーが、重要なアクションへのコントロールを取り戻せる
✓本番ワークロードでのリスク低減: 安全でないアクションの自動ブロックにより、無条件実行に伴うリスクを抑制

🔬 技術面

✓許可ルールとの統合: 既存の allow / ask / deny ルールが常に優先され、既存設定を変更せずに導入できる
✓低レイテンシ: レビュー所要時間は中央値で 1 秒未満、作業テンポへの影響が小さい
✓多層防御との組み合わせ: ローカル / クラウドサンドボックスと組み合わせ、承認判断と実行時境界の複数レイヤーを構成

⚠️ デメリット・制約事項

制限事項

✗有料プランのユーザーのみ利用可能
✗LLM レビューの提供リージョンは us-east-1 と eu-central-1 に限定
✗機能または基盤の Anthropic モデルが利用できない環境では、従来の承認エクスペリエンスのまま
✗すべての承認プロンプトがなくなるわけではなく、判断が難しいアクションでは引き続きユーザー確認が行われる (安全側に倒す設計)

考慮すべき点

⚠LLM レビューに送られたアクションはプランの利用量として課金されるため、利用量への影響を考慮する必要がある
⚠承認要否の判断のみを行い、シェルコマンドのアクセス範囲は制限しない。実行時の保護にはローカルサンドボックスなど別レイヤーの併用を推奨
⚠LLM の判断に依存するため、重要な操作 (本番環境への反映、破壊的な変更など) には明示的な deny / ask ルールの設定が望ましい

🎯 ユースケース

1. 複数ファイルにまたがるリファクタリング

シナリオ: 大規模なコードベースで、複数ファイルの読み取り・編集・テスト実行を繰り返す長時間のリファクタリングタスクを Kiro に依頼する。

実装例: Approve for me を有効にしてタスクを依頼。ファイルの読み書きやテストスイートの実行といった定型アクションは LLM レビューが自動承認する。

効果: 従来はアクションごとに承認が必要で作業が中断されていたが、承認プロンプトが最小限になり、タスクが途切れずに進行する。

2. trust-all-tools を利用していたチームの安全性向上

シナリオ: 承認疲れを避けるために trust-all-tools を常用していたが、本番関連のリポジトリでは無条件実行のリスクが懸念されている。

実装例: trust-all-tools の代わりに Approve for me を有効にし、特に危険な操作 (デプロイコマンドや削除系コマンドなど) には deny / ask ルールを明示的に設定する。

効果: 日常的なアクションの快適さを維持しながら、安全でないアクションは自動ブロックまたはユーザー確認となり、リスクが低減する。

3. サンドボックスと組み合わせた多層防御

シナリオ: エージェントによるシェルコマンド実行を許可しつつ、ネットワークアクセスやファイルシステムへの影響範囲を制限したい。

実装例: Approve for me を有効にしたうえで、Kiro IDE / CLI のローカルサンドボックスを有効化する。アウトバウンドネットワークアクセスは明示的に許可しない限りブロックされる。

効果: 承認判断 (Approve for me) と実行時境界 (サンドボックス) の 2 つのレイヤーで保護され、単一レイヤーの見逃しを補完する多層防御が実現する。

💰 料金・利用可能リージョン

💳 料金
Approve for me は有料プランのユーザーが利用できます。LLM レビューに送られたアクションは、利用中のプランに対して課金されます。 許可ルールのみで処理されたアクション (社内データでは約 70%) は LLM レビューを経由しないため、課金対象のレビューは残りの一部に限られます。
🌏 利用可能リージョン
Kiro はグローバルに利用可能なサービスです。Approve for me の LLM レビューは、 us-east-1 (バージニア北部) および eu-central-1 (フランクフルト) で提供されます。

🔗 関連サービス・機能

Kiro 許可ルール (allow / ask / deny)
Approve for me より常に優先して適用されるユーザー定義ルール。明示的に制御したいアクションの指定に使用する。
Kiro ローカルサンドボックス
Kiro IDE / CLI でシェルコマンドの実行に OS レベルの境界を設ける機能。Approve for me と組み合わせて多層防御を構成する。
Kiro 権限モード (Supervised / Accept file changes)
今回の Changelog で Autopilot トグルから置き換えられた権限モードメニューの選択肢。用途に応じて使い分ける。

✨ まとめ

Approve for me は、「すべて承認するか、すべて信頼するか」という二択だったエージェントの承認モデルに、 LLM レビューによる第三の選択肢を導入するアップデートです。 許可ルールが優先される設計のため既存設定と安全に共存でき、trust-all-tools を常用していたユーザーには特に有効な代替手段となります。

有料プランを利用している場合は、Kiro IDE 1.4.154 以降または Kiro CLI 2.36 以降に更新し、次のタスクで有効化を試すことを推奨します。
