Amazon CloudWatch

🔀 CloudWatch pipelines
条件付きログルーティングとチェーンログパーサー

リリース日: 2026 年 10 月 14 日 | 機能: Conditional Log Routing / Chained Parsers

📋 概要

CloudWatch pipelines は、インフラストラクチャを管理することなくテレメトリデータを取り込み、変換し、CloudWatch にルーティングするフルマネージドサービスです。今回のアップデートで、ログデータの変換方法と送信先ロググループをより細かく制御できるようになりました。

🔀 条件付きログルーティング

処理済みフィールドに対する条件評価に基づき、各イベントを異なる CloudWatch ロググループへ送信。重大度、ソース、タイプごとにイベントを分離し、それぞれに適切な保持期間とアクセス制御を適用できます。

🔗 チェーンパーサー

複数のパーサープロセッサを順番に適用し、後段のパーサーが前段のパーサーで生成したフィールドを処理。例えば JSON エンベロープをパース → 抽出フィールドに Grok を適用という多段パースが可能です。

多様なログフォーマットが混在するログパイプラインを運用する運用チーム、SRE、セキュリティチームにとって有用なアップデートです。

Before / After

❌ アップデート前の課題
  • 多様なイベントタイプを単一のロググループにしか送信できず、種類ごとの保持期間やアクセス制御の分離には複数パイプラインや追加の仕組みが必要
  • JSON の中に Grok 形式のメッセージがネストする複合フォーマットを、1 つのパイプライン内で段階的にパースすることが困難
  • ログの振り分けや多段パースのために AWS Lambda や自前の ETL 処理など追加インフラストラクチャの構築・運用が必要
✅ アップデート後の改善
  • 処理済みフィールドの条件評価に基づき、イベントごとに異なる CloudWatch ロググループへルーティング可能
  • 複数のパーサープロセッサを連結し、前段のパーサーが抽出したフィールドを後段のパーサーで処理する多段パースが可能
  • 多様なログフォーマットの構造化と適切なロググループへの振り分けを、単一のパイプラインで完結

CloudWatch pipelines の構成要素

項目詳細
📥 ソースデータの取得元 (Amazon S3 バケット、CloudWatch Logs、サードパーティ統合など)。各パイプラインに 1 つ必須
⚙️ プロセッサテレメトリデータの変換、パース、エンリッチメントを実行。定義された順序で順次適用 (チェーンパーサーを含む)
📤 シンク処理済みデータの送信先。ログパイプラインは条件付きルーティング用に最大 10 個の順序付き cloudwatch_logs シンクを使用可能
🧩 拡張機能AWS Secrets Manager 統合による認証情報管理などの追加機能

🛠️ 設定方法

前提条件

✓CloudWatch pipelines が利用可能な AWS リージョンを使用していること
✓CloudWatch pipelines およびロググループを操作できる IAM 権限を持っていること
✓ルーティング先となるロググループの設計 (保持期間、アクセス制御) が完了していること

手順

1
パイプラインの作成画面を開く

CloudWatch コンソールの [テレメトリ設定] から [パイプライン] を選択し、新しいパイプラインを作成。ソースとして Amazon S3 バケット、CloudWatch Logs、サードパーティ統合などを指定します。

2
チェーンパーサーを設定する

プロセッサとして複数のパーサーを順番に追加。例えば 1 つ目で JSON エンベロープをパースし、2 つ目で抽出フィールドに Grok パーサーを適用。プロセッサは定義順に実行され、後段は前段が生成したフィールドを参照できます。

3
条件付きルーティングを設定する

処理済みフィールドの値 (重大度、ソース、タイプなど) に基づいて送信先ロググループを指定。最大 10 個の順序付きシンクを設定でき、条件に一致しないイベントのデフォルト送信先も指定します。

4
動作を確認する

デプロイ後、各ロググループに期待どおりのイベントが振り分けられているかを CloudWatch Logs Insights や Live Tail で確認します。

💡 メリット

💼 ビジネス面
✓コスト最適化: 重要度に応じた保持期間を設定し、不要な長期保存コストを削減
✓コンプライアンス対応: セキュリティログや監査ログを専用ロググループに分離し、適切なアクセス制御を適用
✓運用負荷の軽減: フルマネージドのため、ログ振り分け用の追加インフラストラクチャの構築・運用が不要
⚙️ 技術面
✓単一パイプラインで完結: 構造化とルーティングを 1 つのパイプラインで実現し、アーキテクチャがシンプルに
✓ネストフォーマット対応: JSON エンベロープ内の Grok 形式メッセージなどを段階的にパースして構造化
✓CloudWatch Logs 機能と互換: 処理後のログは Logs Insights、Anomaly Detection、Live Tail でそのまま利用可能

⚠️ デメリット・制約事項

制限事項

✗1 つのログパイプラインで使用できる順序付き cloudwatch_logs シンクは最大 10 個
✗パイプラインあたりのプロセッサは最大 20 個
✗アカウントあたりのログパイプライン数は 330 (CloudWatch Logs ソース用 300、その他ソース用 30)

考慮すべき点

⚠プロセッサを追加するとログイベントが変更され、元の生ログは保持されないため、原本保全が必要な場合は設計上の考慮が必要
⚠パイプライン定義はカスタマー提供キーで暗号化されないため、パスワード、API キー、個人情報 (PII) などの機密データを定義に含めてはならない
⚠CloudWatch Logs ソースはパイプライン処理前に、サードパーティおよび S3 バケットソースは処理後に課金計測されるため、ソースタイプごとの課金タイミングの違いに注意

🎯 ユースケース

1. 重大度ベースのログ分離と保持期間の最適化

シナリオ: INFO、WARN、ERROR が混在するアプリケーションログで、現状は単一ロググループのため全ログに同じ保持期間が適用されコストが膨らんでいる。

構成例重大度ベースのルーティング
パイプライン構成:
1. パーサー: JSON パースで severity フィールドを抽出
2. ルート 1: severity = ERROR → ロググループ app/errors (保持 1 年)
3. ルート 2: severity = WARN → ロググループ app/warnings (保持 90 日)
4. デフォルト: ロググループ app/info (保持 7 日)

✅ 効果: 重大度ごとに最適な保持期間を適用し、ストレージコストを削減しながら重要ログの長期保持を実現。

2. セキュリティログの分離とアクセス制御

シナリオ: アプリケーションログとセキュリティ監査イベントが同じログストリームに出力されており、セキュリティチームのみがアクセスできる専用ロググループへ監査イベントを分離したい。

構成例イベントタイプベースのルーティング
パイプライン構成:
1. パーサー: ログをパースして event_type フィールドを抽出
2. ルート 1: event_type = security_audit → ロググループ security/audit
   (セキュリティチームのみアクセス可能な IAM ポリシーを適用)
3. デフォルト: ロググループ app/general

✅ 効果: ロググループ単位の IAM アクセス制御により、最小権限の原則に沿ったセキュリティ監査ログの管理が可能。

3. ネストしたログフォーマットの多段パース

シナリオ: コンテナ基盤のログが JSON エンベロープでラップされ、message フィールド内に Apache 形式のアクセスログが格納されている。これまでは構造化できず、Logs Insights での分析が困難だった。

構成例チェーンパーサー + ルーティング
パイプライン構成:
1. パーサー 1: JSON パーサーでエンベロープをパースし message フィールドを抽出
2. パーサー 2: message フィールドに Grok パーサーを適用し
   クライアント IP、ステータスコード、レスポンスタイムなどを抽出
3. ルーティング: ステータスコード 5xx のイベントをエラー分析用ロググループへ送信

✅ 効果: ネストしたログを完全に構造化し、Logs Insights でのフィールドベース分析とエラーログの自動分離を同時に実現。

🔗 関連サービス・機能

📄 Amazon CloudWatch Logs

ルーティング先となるロググループを提供。Logs Insights、Anomaly Detection、Live Tail などの分析機能が処理済みログに対して利用可能。

🔄 CloudWatch Logs 変換 Log Transformers

ロググループレベルでのログ変換機能。CloudWatch pipelines は Log Transformers と後方互換性があります。

🔐 AWS Secrets Manager

パイプラインの拡張機能として統合でき、サードパーティソースへの接続に必要な認証情報を安全に管理できます。

📝 まとめ

CloudWatch pipelines の条件付きログルーティングとチェーンパーサーにより、多様なログフォーマットの構造化と適切なロググループへの振り分けを、追加インフラストラクチャなしで単一のパイプラインで実現できるようになりました。

重大度やイベントタイプごとの保持期間・アクセス制御の最適化はコスト削減とコンプライアンス強化に直結するため、現在 Lambda や外部ツールでログの振り分けを行っている場合は、CloudWatch pipelines への移行を検討することを推奨します。
