AWS CloudFormation / CDK
📅 リリース日: 2026 年 6 月 30 日

📌 概要 - デプロイ時間を最大 4 倍短縮

AWS は CloudFormation と CDK の新しいデプロイモード express モード を発表しました。 従来は各リソースが完全に安定化するまで待機していましたが、express モードでは リソース構成を適用した時点でスタック操作を完了とみなします。

トラフィック準備状況の確認、リージョン間のプロパゲーション、クリーンアップといった追加の安定化チェックは バックグラウンドで継続されます。例えば CloudFront ディストリビューションの作成は、 従来の 5 〜 10 分待ちから数秒で完了します。テンプレート変更は不要で、既存テンプレートやネストされたスタックでそのまま利用できます。

🐢 Before - 課題
  • リソースが完全に安定化するまで待機し、反復サイクルで毎回長い待ち時間が発生
  • CloudFront のように設定適用済みでも完了報告まで数分待つ必要があった
  • 失敗時はロールバック完了を待ってから修正・再試行する必要があり遅延
⚡ After - 改善
  • 構成適用時点で操作完了。デプロイ時間が最大 4 倍短縮
  • 安定化チェックはバックグラウンド継続、即座に次の作業へ
  • ロールバックがデフォルト無効化、即座に fix-and-retry が可能

express モードでは構成適用後すぐにスタック操作が完了し、安定化処理はバックグラウンドで進行します。

🔧 主要機能

✅ 1. 構成適用時点での操作完了
  • 標準モード: リソースが完全に安定化するまで待機 (例: EC2 が running になるまで)
  • express モード: 作成・更新・削除の API 呼び出しが成功した時点で完了とみなす
  • 完了後もリソースは初期化中・プロパゲーション中の場合がある
🔗 2. 依存関係の維持とエラーハンドリング
  • 依存関係の順序どおりにリソースを処理
  • 同一スタック内の依存リソースの失敗も適切に処理
  • スタックの状態がテンプレートからドリフトしない (CDK hotswap との違い)
↩️ 3. ロールバックのデフォルト無効化
  • express モードではロールバックがデフォルトで無効
  • 失敗してもロールバック完了を待たず、即座に fix-and-retry できる
  • disableRollback を false にすれば再有効化可能
📄 4. テンプレート変更不要・ネストされたスタック対応
  • 既存のすべての CloudFormation テンプレートでそのまま利用可能
  • 親スタックで指定すると、すべてのネストされたスタックに設定が伝播

⚙️ 設定方法

前提: CloudFormation サポートリージョン (全リージョンで利用可能)。CDK では --express 対応バージョンが必要。StackSets と AWS SAM は対象外。

ステップ 1: AWS CLI でスタックを作成

Bashcreate-stack with express mode
aws cloudformation create-stack --stack-name my-stack \
    --template-body file://my-template.yaml \
    --deployment-config '{"mode": "EXPRESS"}'

ステップ 2: CDK で express モードを使用

Bashcdk deploy
cdk deploy --express

ステップ 3: ロールバックを再有効化 (任意)

BashdisableRollback を false に設定
aws cloudformation create-stack --stack-name my-stack \
    --template-body file://my-template.yaml \
    --deployment-config '{"mode": "EXPRESS", "disableRollback": false}'

デプロイ設定 (JSON)

JSONdeployment-config
{
  "mode": "EXPRESS",
  "disableRollback": false
}

ビジネス面

✓開発生産性の向上: デプロイ待ち時間が最大 4 倍短縮、反復サイクルが高速化
✓AI エージェント活用の促進: 待ち時間削減で自律的なイテレーションを効率化
✓既存資産の活用: テンプレート変更不要で導入コストが低い

技術面

✓整合性の維持: CloudFormation 経由のため状態がドリフトしない
✓依存関係の保持: 高速化しても順序とエラーハンドリングは維持
✓柔軟なロールバック制御: デフォルト無効、必要に応じ再有効化

⚠️ デメリット・制約事項

制限事項

✗CloudFormation StackSets では利用不可
✗AWS SAM のデプロイでは利用不可
!カスタムリソース (Custom::* 等) はデフォルト挙動でレスポンスシグナルを待機 (ServiceTimeout で最大待機時間を設定可)

考慮すべき点

!完了後もリソースが完全稼働とは限らない (CloudFront 伝播、EC2 初期化、ECS 起動はバックグラウンド進行)
!完全な安定化を確認したい本番デプロイでは標準モードを推奨
!本番運用に流用する場合は disableRollback の設定を明示的に検討

🎯 ユースケース

1. 開発時の反復的なテンプレート編集
シナリオ: 開発者がテンプレートを繰り返し編集し、構成の妥当性を素早く確認したい
効果: 完全な安定化を待たず構成の妥当性を確認、フィードバックループが大幅短縮
2. CloudFront を含むスタックの高速デプロイ
シナリオ: CloudFront を含むスタックを頻繁にデプロイするが、伝播待ちの 5 〜 10 分がボトルネック
実装: cdk deploy --express
効果: 数秒で操作完了、伝播はバックグラウンド継続で開発の流れが止まらない
3. AI エージェントによるインフラ構築
シナリオ: AI エージェントが自律的にインフラを構築・反復、待ち時間がスループットを制約
効果: 待ち時間短縮＋ロールバック無効化で fix-and-retry が可能、反復効率が向上

📝 まとめ

CloudFormation / CDK の express モードは、リソースの完全な安定化を待たずに構成適用時点でスタック操作を完了させ、 デプロイ時間を最大 4 倍短縮する開発者向け機能です。テンプレート変更不要で既存環境にそのまま適用でき、ネストされたスタックや CDK にも対応します。 本番デプロイでは標準モードを維持しつつ、開発・反復ワークフローや AI エージェントによるインフラ構築では express モードを積極活用し、 フィードバックループの高速化を図ることが推奨されます。
