Amazon CloudFront

⚡ CloudFront Functions がネットワークコールに対応

📅 リリース日: 2026 年 11 月 18 日 | 🆕 cf.fetch() / cf.beacon() ヘルパーメソッド追加

📌 概要

CloudFront Functions が、リクエスト処理中にネットワークコールを実行できるようになりました。 新しいヘルパーメソッド cf.fetch() で API を呼び出してレスポンスを基に処理を分岐でき、 cf.beacon() でビューワーを待たせずにバックグラウンドで分析イベントを送信できます。

宛先は同じディストリビューションに設定済みのオリジンに限定され、OAC による SigV4 署名、VPC オリジン、 コネクション再利用、カスタムオリジンヘッダー、オリジン mTLS といった既存のオリジン設定をそのまま活用できます。 AI エージェントの権限チェックや不正検知連携など、最新のユースケースに対応します。

❌ Before: アップデート前の課題

  • CloudFront Functions から外部サービスを呼び出せず、動的データに基づく判断 (トークン失効チェック、認可判定) ができなかった
  • 外部データが必要なロジックは Lambda@Edge へ移行が必要で、コストとレイテンシーが増加
  • あるいはロジックをオリジン側へ戻す必要があり、エッジでの早期ブロックのメリットを失った
  • エッジからの分析イベント送信には別の仕組みが必要だった

✅ After: アップデート後の改善

  • cf.fetch() でビューワーリクエスト / レスポンス関数から API を呼び出し、応答に基づいて処理可能に
  • cf.beacon() でキャッシュ配信時も含め、ビューワーを待たせずに分析イベントを送信可能に
  • OAC、VPC オリジン、カスタムヘッダー、mTLS などのオリジン設定を関数コードで再実装せずに利用可能に
  • 認可チェックや不正検知などの軽量な連携を Lambda@Edge なしでエッジで完結

CloudFront Functions が cf.fetch() で認可サービスを同期呼び出しして結果に基づきリクエストを処理し、cf.beacon() で分析サービスへ非同期にイベントを送信する構成です。宛先はいずれも同じディストリビューションに設定済みのオリジンである必要があります。

🔧 主要機能

1️⃣ cf.fetch() メソッド — 同期型ネットワークコール

  • オリジンへリクエストを送信し、レスポンスを読み取る。Promise を返すため async / await で使用
  • path (必須) と options (必須) を指定し、options.originId で同一ディストリビューション上のオリジン ID を指定
  • method は GET / HEAD / POST / PUT / PATCH / DELETE / OPTIONS に対応 (大文字のみ、省略時は GET)
  • ボディを読むには includeBody: true が必要。text() / json() / bytes() / arrayBuffer() で取得 (読み取りは 1 回のみ)
  • エラーは TypeError / TimeoutError / InternalError / SyntaxError として通知。try / catch でフェイルオープン / フェイルクローズを設計

2️⃣ cf.beacon() メソッド — 非同期ベストエフォート送信

  • レスポンスを待たずにオリジンへリクエストを送信。分析イベントや監査レコードなど、ビューワーを待たせたくない用途向け
  • 即座に undefined を返し、関数の実行は継続される
  • logDeliveryErrors: true で、関数終了後の配信失敗を CloudWatch Logs で確認可能 (2xx / 3xx 以外を記録)

3️⃣ 既存オリジン設定の活用

  • OAC 設定済みオリジンへのコールは CloudFront が SigV4 で署名。認証情報をコードに埋め込み不要
  • VPC オリジンによりプライベートサブネット内のサービスを呼び出し可能。パブリックエンドポイント不要
  • CloudFront のウォームコネクションを再利用し、TCP / TLS セットアップを回避
  • カスタムオリジンヘッダー (共有シークレットなど) がコールにも付与される
  • オリジン mTLS 設定時は CloudFront がクライアント証明書を提示。関数側で証明書を扱わない

4️⃣ CloudFront KeyValueStore との使い分け

  • ネットワークコールが適する: リクエスト間でデータが変化し最新の回答が必要 (トークン失効、セグメント判定)、またはデータセットが大きい場合
  • KeyValueStore が適する: 静的 / 更新頻度の低いデータ (リダイレクトマップ、機能フラグ)、1 リクエストで複数回の参照が必要な場合
  • 併用も可能 (KeyValueStore で実験設定を読み、ネットワークコールでバリアントを割り当てるなど)

📨 リクエスト構築の仕様

⚠️ネットワークコールは一から構築されるため、ビューワーのヘッダー、Cookie、クエリ文字列は自動では転送されない (X-Forwarded-For、Via、CDN-Loop のみ自動付与)。必要な情報は headers / body で明示的に渡す
✗Accept-Encoding、Content-Length、TE、Transfer-Encoding ヘッダーの指定は不可 (TypeError が発生)
✓OAC を使わないカスタムオリジンでは host ヘッダーの上書きが可能 (S3 オリジンや OAC 付きオリジンでは不可)
✓x-amz-content-sha256 ヘッダーは自動付与。ただし Lambda 関数 URL への body 付き POST / PUT では、関数側で body の SHA-256 ダイジェストの設定が必要

📋 前提条件

✓CloudFront ディストリビューションと、呼び出し先オリジンが同一ディストリビューションに設定済みであること

1

ネットワークコールを行う関数を作成する

Bash JavaScript runtime 2.0 で関数を作成 
aws cloudfront create-function \
  --name auth-check-function \
  --function-config '{"Comment":"Authorization check with cf.fetch","Runtime":"cloudfront-js-2.0"}' \
  --function-code fileb://function.js

function.js には import cf from 'cloudfront'; で始まるコードを記述します。

2

関数コードで cf.fetch() を使用する

JavaScript フェイルクローズ型の認可チェック実装例 
import cf from 'cloudfront';

async function handler(event) {
    const request = event.request;
    const auth = request.headers['authorization'];

    if (!auth) {
        return { statusCode: 401, statusDescription: 'Unauthorized' };
    }

    try {
        const response = await cf.fetch('/v1/authorize', {
            originId: 'auth-service',
            method: 'POST',
            headers: { 'content-type': 'application/json' },
            body: JSON.stringify({ token: auth.value, uri: request.uri }),
            includeBody: true,
        });

        if (!response.ok) {
            return { statusCode: 403, statusDescription: 'Forbidden' };
        }

        const result = await response.json();
        request.headers['x-user-id'] = { value: result.userId };
        return request;
    } catch (e) {
        console.log('Authorization check failed: ' + e.name + ': ' + e.message);
        return { statusCode: 503, statusDescription: 'Service Unavailable' };
    }
}

ビューワーのトークンを認可サービスに送信し、承認された場合のみリクエストを通過させます。originId には同一ディストリビューション上のオリジン ID を指定します。

💡 メリット

💼 ビジネス面

✓アーキテクチャの簡素化とコスト最適化: 軽量な認可チェックや分析送信のためだけに Lambda@Edge を使う必要がなくなり、エッジ処理のコストと運用負荷を削減
✓セキュリティ強化: 疑わしいトラフィックを不正検知サービスと連携してエッジでブロック / チャレンジでき、オリジンへの不要な到達を防止
✓AI ワークロードへの対応: AI エージェントの権限や利用バジェットを API や MCP サーバーに到達する前に検証でき、AI トラフィックのガバナンスを実現

🔬 技術面

✓既存オリジン設定の再利用: OAC による SigV4 署名、VPC オリジン、mTLS、カスタムヘッダーを再実装せずに利用でき、認証情報をコードに埋め込まずに済む
✓低レイテンシー: CloudFront のウォームコネクションにより、TCP / TLS セットアップのオーバーヘッドを回避
✓ビューワー体験の維持: cf.beacon() はキャッシュ配信時でもビューワーを待たせずにイベントを送信でき、パフォーマンスに影響しない

⚠️ デメリット・制約事項

🚧 制限事項

✗1 回の関数呼び出しにつきネットワークコールは 1 回のみ (Promise.all() による複数コールも不可)
✗タイムアウトは 1 秒固定、リクエスト / レスポンスボディはそれぞれ最大 10 KB
✗宛先は同一ディストリビューションに設定済みのオリジンに限定され、任意の URL は指定不可
✗無料プランのディストリビューションでは利用不可
✗TestFunction API やコンソールのテストタブではネットワークコールを実行できない
✗Connection Functions および継続的デプロイ (continuous deployment) を使用するディストリビューションでは利用不可
✗AWS WAF はネットワークコールを検査しない (Web ACL が評価するのはビューワーリクエストのみ)
✗ネットワークコールのレスポンスはキャッシュされず、到達するたびに毎回実行される

🤔 考慮すべき点

⚠️cf.fetch() のエラーを catch しないと関数が失敗してビューワーに HTTP 503 が返る。フェイルオープン / フェイルクローズの方針を明確にして try / catch を必ず実装
⚠️遠方オリジンへの TLS 失敗やプライベート IP のオリジンは、1 秒制限により TimeoutError になる場合がある。プライベートネットワーク内のサービスには VPC オリジンを使用
⚠️cf.beacon() はベストエフォートであり、確実な配信が必要な用途には使用しない。失敗確認には logDeliveryErrors: true が必要
⚠️ビューワーリクエストの情報は自動転送されないため、オリジンが必要とする情報は headers / body で明示的に渡す設計が必要
⚠️高頻度参照で内容が静的なデータは、ネットワークコールではなく CloudFront KeyValueStore の利用を検討

🎯 ユースケース

🤖 ユースケース 1: AI エージェントトラフィックの認可とバジェット制御

シナリオ: API や MCP サーバーの手前で AI エージェントの権限と利用バジェットを検証し、超過したエージェントのリクエストをエッジでブロックしたい。

JavaScript エージェント認可チェック 
const response = await cf.fetch('/v1/agent-authorize', {
    originId: 'agent-control-plane',
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({ agentId: agentId, uri: request.uri }),
    includeBody: true,
});
if (!response.ok) {
    return { statusCode: 429, statusDescription: 'Budget Exceeded' };
}
✅ 効果: 認可されないリクエストがオリジンに到達する前にブロックされ、API / MCP サーバーの負荷とコストを削減できる。

🛡️ ユースケース 2: 不正検知サービスと連携したトラフィック制御

シナリオ: ボットや不正アクセスの疑いがあるトラフィックについて、社内の不正検知サービスにシグナルを送り、判定結果に応じてブロックまたはチャレンジを返したい。

JavaScript 不正検知サービスとの連携 
const response = await cf.fetch('/v1/fraud-check', {
    originId: 'fraud-service',
    method: 'POST',
    headers: { 'content-type': 'application/json' },
    body: JSON.stringify({ ip: event.viewer.ip, uri: request.uri }),
    includeBody: true,
});
const verdict = await response.json();
if (verdict.action === 'block') {
    return { statusCode: 403, statusDescription: 'Forbidden' };
}
✅ 効果: リアルタイムの判定に基づく動的なアクセス制御をエッジで実現し、オリジンを不正トラフィックから保護できる。

📈 ユースケース 3: キャッシュヒットを含む全リクエストの分析イベント収集

シナリオ: キャッシュから配信されるコンテンツも含め、全ビューワーリクエストの分析イベントを、配信パフォーマンスに影響を与えずに収集したい。

JavaScript cf.beacon() による非同期イベント送信 
import cf from 'cloudfront';

function handler(event) {
    const request = event.request;
    cf.beacon('/events', {
        originId: 'analytics-service',
        method: 'POST',
        headers: { 'content-type': 'application/json' },
        body: JSON.stringify({ uri: request.uri, viewerIp: event.viewer.ip }),
        logDeliveryErrors: true,
    });
    return request;
}
✅ 効果: ビューワーのレスポンスタイムに影響を与えず、キャッシュヒット時も含めた分析データをリアルタイムに収集できる。

🔗 関連サービス・機能

⚡ Lambda@Edge

より長い実行時間 (最大 30 秒) や複数のネットワークコールが必要な複雑な処理に適する。軽量な単一コールであれば CloudFront Functions への移行でコスト削減が可能。

🗂️ Amazon CloudFront KeyValueStore

静的 / 低頻度更新のデータをエッジで低レイテンシーに参照する機能。ネットワークコールと併用可能。

🏢 CloudFront VPC オリジン

プライベートサブネット内のサービスをパブリックエンドポイントなしでネットワークコールの宛先にできる。

🔐 オリジンアクセスコントロール OAC

ネットワークコールを SigV4 で自動署名し、プライベート S3 バケットや Lambda 関数 URL を認証情報なしで呼び出せる。

📝 まとめ

CloudFront Functions がネットワークコールに対応したことで、これまで Lambda@Edge やオリジン側に頼らざるを得なかった 動的な認可チェック、不正検知連携、分析イベント送信を エッジの軽量関数だけで完結できるようになりました。

1 コール / 呼び出し、1 秒タイムアウト、10 KB ボディという制約を踏まえ、まずは認可チェックやビーコン送信などの 軽量ユースケースから cf.fetch() / cf.beacon() の適用を検討することを推奨します。
