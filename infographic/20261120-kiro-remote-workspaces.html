Remote Workspaces

クラウドセッション / Dev Container / Remote SSH — コードとコンピュートがある場所に、フル IDE 体験を届ける

📝 概要

Kiro IDE が、コードとコンピュートが 実際に存在する場所 でワークスペースを開けるようになりました。最新の安定版から、クラウドセッションへの接続、Dev Container 内での実行、ネイティブ SSH 接続 の 3 つをサポート。ワークスペースがどこで動いていても、ファイル編集やターミナル操作を含む完全な IDE 体験がローカルと同じように利用できます。

これまでの「手元のマシンで動くフル IDE か、どこか別の場所で動くエージェントか」というトレードオフが解消され、ワークスペースを移しても IDE はそのまま付いてくる ようになります。

☁️

クラウドセッション

Kiro 管理のコンピュートに SSH 接続。ウィンドウを閉じてもエージェントは継続実行

📦

Dev Container

devcontainer.json からビルド / アタッチ。ローカルでもリモートでも実行可能

🏠

自前のコンピュート

追加インストールなしのネイティブ SSH で既存の VM・GPU マシンに接続

❌ アップデート前の課題

  • Kiro IDE はローカルワークスペースのみ対象で、クラウドセッションはブラウザ経由の操作が中心
  • devcontainer.json があっても IDE からコンテナ内で開けない (CLI は以前から対応)
  • 自前のビルドマシンや GPU マシンへの接続にはサードパーティ製リモート SSH 拡張が必要
  • 重いビルドやローカルツールチェーンの差異 (「自分のマシンでは動く」問題) への対処が困難

✅ アップデート後の改善

  • IDE からクラウドセッションに SSH 接続し、ファイルツリー・エディタ・ターミナルがクラウド側で動作
  • .devcontainer/devcontainer.json からローカル / リモートホスト上でコンテナをビルド / アタッチ
  • 追加インストールなしで自前の VM・ビルドマシン・社内開発基盤に SSH 接続してセッションを実行
  • 3 機能とも最新安定版に標準搭載、有効化やインストール作業は不要

Kiro IDE から 3 種類のリモートワークスペース (クラウドセッション / Dev Container / 自前のコンピュート) に接続する構成。Dev Container はローカルの Docker / Podman 上でも、SSH 接続したリモートホスト上でも実行できます。

⚡ 主要機能

☁️ 1. クラウドセッションを IDE から開く

  • IDE は SSH 経由 でセッションに接続し、ファイルツリー・エディタ・統合ターミナルはすべてクラウドセッション側のファイルシステムとシェルを操作
  • Sessions サイドバーまたは Agent Focus Mode でセッションを右クリックし [Open in IDE] を選択。Kiro Web で開始したセッションも同じリストに表示
  • ウィンドウを閉じたりアイドル状態にしても エージェントはクラウドで動き続ける ため、作業は停止しない
  • Enterprise プランでは管理者がクラウドセッションを VPC に接続 でき、プライベートレジストリ・社内サービス・データベースへ既存のネットワーク制御を維持したまま到達可能

📦 2. Dev Container のサポート (ローカル / リモート)

  • リポジトリの .devcontainer/devcontainer.json をもとにコンテナをビルドまたはアタッチし、セッションをコンテナ内で実行
  • ローカルでは Docker または Podman で動作。リモートでは SSH 接続 → コンテナにアタッチの 2 段階フロー (他のエディタと同様の方式)
  • コンテナ定義はリポジトリ内に保持されるため、チームメイトや CI と Kiro の実行環境が一致
  • 定義変更時は [Rebuild Container]、コンテナから抜けるには [Reopen Folder Locally] を選択
  • Kiro CLI は以前から Dev Container 内で実行可能。今回のリリースは IDE 側のギャップを埋めるもの

🏠 3. 自前のコンピュートへのネイティブ SSH 接続

  • サードパーティ製拡張機能が不要になり、追加インストールなし で Kiro IDE がネイティブに SSH 接続
  • 既存の VM・ビルドマシン・社内開発プラットフォーム上でセッションを実行
  • Kiro はコンピュートを提供せず課金もしないため、マシン・ネットワーク配置・セキュリティ態勢はユーザーの管理下 に残る
  • マネージドクラウドにない GPU マシンや特殊な Linux ビルドマシン、ネットワーク内部のホストに最適
  • エージェントとモデルの使用は通常どおり Kiro クレジットを消費

🔧 技術仕様

📊 3 つのリモートワークスペースの比較

項目 ☁️ クラウドセッション 📦 Dev Container 🏠 自前のコンピュート
実行場所 Kiro 管理のクラウドコンピュート 自分のマシンまたはリモートホスト上のコンテナ 既に運用しているマシン
コンピュート提供者 Kiro ユーザー (Docker または Podman) ユーザー
環境の定義 Kiro のデフォルト環境 リポジトリ内の devcontainer.json マシン上にあるもの
適した用途 重いビルド、クリーンなツールチェーン、ラップトップを占有したくない作業 再現可能な環境が必要なチーム 既存の Linux ビルドマシン、GPU マシン、ネットワーク配置の要件

🖧 自前のコンピュートのホスト要件

項目詳細
OS / アーキテクチャLinux (x86-64 または ARM64)
glibc2.28 以降
ディスク空き容量ホームディレクトリに 4 GiB 以上
その他必要なものは Kiro が自動インストール

🔄 エージェントの実行場所とデータの流れ

  • エージェントは ワークスペースと同じ場所 で実行される (クラウドセッションはクラウド環境、自前のコンピュートはそのホスト、Dev Container はコンテナ内)
  • プロジェクトファイルとコマンドはその環境内に留まり、ローカルには表示に必要なファイル内容・チャット・ターミナル出力・フォワードされたポートのみが届く
  • 通常のセッションと同様に、プロンプトと関連するコードコンテキストは Kiro の AI サービスに送信される
  • ローカルサンドボックスとは解決する課題が異なり、独立して併用可能。ローカルサンドボックスは作業をローカルに保ちつつエージェントのコマンド範囲を制限、リモートワークスペースはワークスペース自体を別のコンピュートへ移す

🛠️ 設定方法

✅ 前提条件

✓最新の安定版 Kiro IDE にアップデートしていること (3 機能とも標準で有効)
✓Dev Container を使用する場合: Docker 互換エンジン (Docker または Podman) と、リポジトリ内の .devcontainer/devcontainer.json
✓自前のコンピュートを使用する場合: ホスト要件を満たす Linux マシンと SSH アクセス
1

☁️ クラウドセッションを IDE で開く

Command Paletteクラウドセッション
コマンドパレット > Kiro: New Cloud Session
または Sessions サイドバーで既存セッションを右クリック > Open in IDE

新しいクラウドセッションを作成するか、既存のセッションで [Open in IDE] を選ぶと、そのセッションに SSH 接続された別のリモートウィンドウが開きます。

2

📦 Dev Container でワークスペースを開く

Command PaletteDev Container
コマンドパレット > Dev Containers: Reopen in Container

devcontainer.json を含むプロジェクトを開くと Kiro IDE が検出して [Reopen in Container] を提案。リモートの場合は先にリモートホストへ SSH 接続してから開き直すと、Docker は SSH ホスト側で実行されます。

3

🏠 自前のマシンに SSH 接続する

Command PaletteSSH ホスト
コマンドパレット > Kiro: Add New SSH Host… (ホストの保存)
コマンドパレット > Kiro: Connect to Host… (ホストへ接続)

ホストを保存するか既存の SSH 設定を利用し、接続後にホスト上のフォルダを開きます。保存したホストは Kiro ビューの [Remote environments] > [SSH Hosts] にも表示され、ウィンドウタイトルに接続先ホストが表示されます。

💼 ビジネス面

✓既存資産の活用: 既に運用しているビルドマシン・GPU マシン・社内開発基盤をそのまま Kiro の実行環境として利用でき、ハードウェアの重複投資を回避
✓セキュリティとガバナンスの維持: 自前のコンピュートではマシン・ネットワーク配置・セキュリティ態勢がユーザーの管理下に残り、Enterprise プランのクラウドセッションは VPC 接続により既存のネットワーク制御を維持
✓チームの環境統一: devcontainer.json による環境定義をチームメイト・CI・Kiro で共有でき、「自分のマシンでは動く」問題を軽減

⚙️ 技術面

✓ローカルと同一の IDE 体験: 接続先がどこであっても、ファイル編集・ターミナル操作を含むフル IDE がそのまま利用可能
✓エージェントの継続実行: クラウドセッションではウィンドウを閉じてもエージェントが動き続け、長時間のタスクをラップトップに縛られず進行
✓追加インストール不要: ネイティブ SSH 接続を含む 3 機能すべてが最新安定版に標準搭載

⚠️ デメリット・制約事項

🚧 制限事項

✗自前のコンピュートのホストは Linux (x86-64 / ARM64)、glibc 2.28 以降、ホームディレクトリに 4 GiB 以上の空き容量が必要
✗Dev Container の利用には Docker または Podman などの Docker 互換エンジンが必要
✗クラウドセッションの VPC 接続は Enterprise プランの管理者設定が必要
✗Kiro CLI はリモートワークスペースを開くことができない (今回のリリースは IDE が対象)

🤔 考慮すべき点

!リモートワークスペースでも、プロンプトと関連するコードコンテキストは Kiro の AI サービスに送信される
!自前のコンピュートではインフラの運用・セキュリティはユーザーの責任
!ローカルサンドボックスとは目的が異なるため、要件に応じて使い分けまたは併用を検討

🎯 ユースケース

🚀 ユースケース 1: 重いビルドをクラウドセッションにオフロード

シナリオ: ビルドやテストスイートが長時間化し、ラップトップのリソースを占有して他の作業が止まってしまう。

Steps実装例
1. コマンドパレットから Kiro: New Cloud Session を実行
2. Sessions サイドバーでセッションを右クリックし Open in IDE を選択
3. クラウドセッションのファイルシステム上でビルド・テストを実行

✅ 効果: 重い処理を Kiro 管理のコンピュートに移し、ウィンドウを閉じてもエージェントが作業を継続するため、ラップトップが解放される。

🤝 ユースケース 2: devcontainer.json によるチーム環境の統一

シナリオ: 開発者ごとにローカルツールチェーンが異なり、環境差異によるトラブルシューティングに時間がかかっている。

JSONC.devcontainer/devcontainer.json
// .devcontainer/devcontainer.json をリポジトリに配置
{
  "name": "project-dev",
  "image": "mcr.microsoft.com/devcontainers/base:ubuntu"
}
// Kiro IDE が検出したら Reopen in Container を選択

✅ 効果: チームメイトや CI と同一のコンテナ環境で Kiro のセッションが実行され、環境差異に起因する問題を排除できる。

🖥️ ユースケース 3: 社内 GPU マシンでのエージェント実行

シナリオ: マネージドクラウドでは提供されない GPU マシンや、社内ネットワーク内に配置されたビルドマシンで開発作業を行いたい。

Steps実装例
1. コマンドパレットから Kiro: Add New SSH Host… でホストを登録
2. Kiro: Connect to Host… で接続し、ホスト上のフォルダを開く
3. 必要なコンポーネントは Kiro が自動インストール

✅ 効果: 追加の拡張機能なしで既存マシンに接続でき、マシンのネットワーク位置とセキュリティ態勢を維持したままフル IDE とエージェントを利用できる。

💰 料金・利用可能リージョン

💳 料金

📌 まとめ

Kiro IDE が クラウドセッション・Dev Container・自前のマシン という 3 つのリモートワークスペースにネイティブ対応し、「フル IDE か、リモートで動くエージェントか」というトレードオフが解消されました。重いビルドのオフロード、チーム環境の統一、既存の GPU / ビルドマシンの活用など、コードとコンピュートの最適な配置を選びながら 同一の IDE 体験 を得られます。最新の安定版にアップデートするだけで追加設定なしに利用できるため、まずはクラウドセッションの [Open in IDE] や devcontainer.json のあるプロジェクトで試すことをお勧めします。
