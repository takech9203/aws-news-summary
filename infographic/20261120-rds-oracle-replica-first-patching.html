Amazon RDS for Oracle

🗄️ Replica First Patching サポート

📅 リリース日: 2026 年 11 月 20 日 | 🏷️ マイナーバージョンアップグレードのダウンタイム削減

📌 概要

Amazon RDS for Oracle が Replica First Patching をサポートしました。 マイナーバージョンアップグレードの際に、まず同一リージョン内のレプリカを先にアップグレードし、 準備ができたタイミングでスイッチオーバーすることで、プライマリ DB インスタンスのダウンタイムを削減します。 Oracle Enterprise Edition の DB インスタンスで利用できます。

プライマリが利用できなくなるのは、スイッチオーバー中と新プライマリでのアップグレード完了処理の間だけになります。 レプリカが読み取り専用モードであれば、スイッチオーバー前に読み取りトラフィックで新バージョンを検証できます。

❌ Before: アップデート前の課題
  • 標準のマイナーバージョンアップグレードでは、ソフトウェア更新中にプライマリがオフラインになり、アプリケーションが読み書きできなかった
  • 新しいマイナーエンジンバージョンを本番相当のトラフィックで事前検証する手段が限られていた
  • ダウンタイムを避けてパッチを先送りすると、セキュリティ修正の適用が遅れるリスクがあった
✅ After: アップデート後の改善
  • レプリカ側で先にソフトウェアを更新するため、プライマリの利用不可はスイッチオーバーと完了処理の間のみに短縮
  • 読み取り専用モードのレプリカなら、切り替え前に読み取りトラフィックで新バージョンを検証可能
  • 48 時間のウィンドウ内で、低トラフィック帯など任意のタイミングで切り替え可能
  • スイッチオーバー後は、旧プライマリやクロスリージョンレプリカも自動的に同じバージョンへ更新

🏗️ アーキテクチャ図

プライマリがトラフィックを処理し続ける間にレプリカを先にアップグレードし、任意のタイミングでスイッチオーバーすることで、ダウンタイムをスイッチオーバーとアップグレード完了処理の間だけに抑えます。

    participant P as 🗄️ プライマリ DB
    participant R as 🗄️ レプリカ DB

    RDS->>R: Oracle ソフトウェアを新バージョンに更新

    R-->>Ops: ステータス Patch pending switchover
    Note over R: 48 時間以内に読み取りで検証可能
    Ops->>RDS: スイッチオーバーを開始
    RDS->>P: Oracle Data Guard スイッチオーバー
    Note over R: レプリカが新プライマリに昇格
    RDS->>R: datapatch を実行しアップグレード完了
    RDS->>P: 旧プライマリと他レプリカを同バージョンへ更新

⚡ 主要機能

1️⃣ レプリカ先行アップグレードによるダウンタイム削減
  • レプリカのエンジンバージョンを変更すると、Amazon RDS がレプリカ側の Oracle ソフトウェアを新しいマイナーバージョンに置き換える。この間プライマリは影響を受けない
  • 切り替えには Oracle Data Guard スイッチオーバーが使用され、レプリカが新プライマリに、旧プライマリがレプリカになる
  • スイッチオーバー後、新プライマリで Oracle データディクショナリ更新 (datapatch) を実行して完了し、旧プライマリやクロスリージョンレプリカを含む他のレプリカも自動で同バージョンへアップグレード
2️⃣ 48 時間のスイッチオーバーウィンドウ
  • ステータスが replica-patched-pending-switchover (コンソール表示「Patch pending switchover」) になるとウィンドウ開始
  • ウィンドウ内であれば任意のタイミング (例: 低トラフィック帯) で切り替え可能。読み取り専用モードなら読み取りトラフィックで新バージョンを検証できる
  • 48 時間以内に切り替えなかった場合は、元のバージョンへ自動ロールバック (プライマリに影響なし)
  • ウィンドウ開始時と半分経過時に RDS イベント通知が送信される
3️⃣ Primary Endpoint との連携
  • アプリケーションは Primary Endpoint 経由での接続が推奨
  • 常に現在のプライマリに解決される DNS 名のため、スイッチオーバー後も接続文字列の変更が不要
  • Enterprise Edition のすべての DB インスタンスに追加料金なしで自動提供。インスタンスエンドポイント接続の場合はスイッチオーバー後に更新が必要

🧩 API 変更履歴

Replica First Patching 自体は既存の API (ModifyDBInstance、SwitchoverReadReplica、DescribeDBInstances) を使用するため、新しい API は追加されていません。関連する変更として、推奨される接続方法である Primary Endpoint が前日に API へ追加されています。

日付サービス変更内容
2026/11/19 rds 25 updated api methods - DBInstance に PrimaryEndpoint 構造体を追加。スイッチオーバー後に別の DNS 名へ再接続する必要がなくなる

🛠️ 設定方法

✅ 前提条件

✓プライマリが Oracle Database Enterprise Edition で稼働 (Standard Edition 2 は非対応)
✓同一リージョン内に Oracle レプリカが 1 つ以上あり、ステータスが available (読み取り専用モードには Active Data Guard が必要)
✓ターゲットが同一メジャーバージョン内の新しいマイナーバージョン (RU、MRP、SPB)
✓プライマリに同じターゲットバージョンへの保留中・スケジュール済みメンテナンスアクションがない
✓レプリカが Oracle Data Guard スイッチオーバーの要件 (自動バックアップの有効化など) を満たしている

ステップ 1: レプリカのアップグレード

Bashレプリカのエンジンバージョンを変更
aws rds modify-db-instance \
    --db-instance-identifier my-oracle-replica \
    --engine-version 19.0.0.0.ru-2026-07.rur-2026-07.r1 \
    --apply-immediately

--apply-immediately で即時開始、--no-apply-immediately でレプリカの次のメンテナンスウィンドウで実行。アップグレード中もプライマリは読み書きトラフィックを処理し続けます。

ステップ 2: レプリカのステータス監視

Bashステータスの確認
aws rds describe-db-instances \
    --db-instance-identifier my-oracle-replica \
    --query 'DBInstances[0].DBInstanceStatus'

upgrading → replica-patched-pending-switchover に変わると 48 時間のウィンドウが開始。残り時間は RDS コンソールの「Patch pending switchover」ステータスのポップアップで確認できます。イベント通知を受け取るには maintenance と notification の両方のカテゴリをサブスクライブします。

ステップ 3: 検証とスイッチオーバーの実行

Bashスイッチオーバーの開始
aws rds switchover-read-replica \
    --db-instance-identifier my-oracle-replica

読み取り専用モードの場合は、スイッチオーバー前に読み取りトラフィックで新バージョンを検証。スイッチオーバーで既存接続は切断されるため、低トラフィックの時間帯に計画することが推奨されます。

ステップ 4: アップグレードの確認

スイッチオーバー後、Amazon RDS が新プライマリで datapatch を実行して完了。新プライマリのステータスが available になり、ターゲットバージョンで稼働していることを確認します。その後、旧プライマリとクロスリージョンレプリカを含む他のレプリカが自動的に同バージョンへアップグレードされます。Primary Endpoint 経由の接続なら接続文字列の変更は不要です。

💡 メリット

💼 ビジネス面

✓ダウンタイムの削減: プライマリの利用不可がスイッチオーバーと完了処理の間だけになり、サービス停止の影響を最小化
✓パッチ適用の促進: ダウンタイムを理由としたパッチ先送りを減らし、ミッションクリティカルなワークロードを最新のマイナーバージョンに維持しやすくなる
✓追加コストなし: 機能自体に追加料金はなく、レプリカの通常料金のみ

⚙️ 技術面

✓事前検証が可能: 読み取り専用レプリカに読み取りトラフィックを送り、本番相当のワークロードで新バージョンを検証してから切り替え
✓切り替えタイミングの制御: 48 時間のウィンドウ内で、低トラフィック帯など任意のタイミングでスイッチオーバー可能
✓自動的な全体のバージョン統一: 旧プライマリやクロスリージョンレプリカを含む残りのレプリカを自動で同バージョンへ更新
✓安全なロールバック: ウィンドウ超過時や手動要求時に元のバージョンへロールバックされ、レプリケーションが再開。プライマリには影響なし

⚠️ デメリット・制約事項

🚫 制限事項

✗Oracle Enterprise Edition のみ対応 (Standard Edition 2 はレプリカ非対応のため利用不可)
✗マイナーバージョンアップグレードのみ対応。メジャーバージョンアップグレードには使用不可
✗アップグレード対象のレプリカはプライマリと同一リージョン内が必須 (クロスリージョンレプリカは先行アップグレード対象外)
✗同一プライマリに対して複数のレプリカで同時に実行することはできない
✗replica-patched-pending-switchover 状態のレプリカでは、オプショングループ・パラメータグループの変更ができない

🤔 考慮すべき点

⚠️AMVU が優先: プライマリのメンテナンスウィンドウがスイッチオーバー前に開始されるとレプリカはロールバックされ、標準の自動アップグレードが実行される。完了したい場合はウィンドウ開始前に切り替えるか、AMVU を一時的に無効化する
⚠️スイッチオーバー前にプライマリを直接アップグレードしたり、レプリカを昇格・プライマリを削除すると、レプリカは自動ロールバックされる
⚠️読み取り専用モードのレプリカでは、ソフトウェア置き換えの間、読み取りトラフィックが一時的に中断される。読み取り専用モードには Oracle Active Data Guard オプションが必要
⚠️スイッチオーバーで既存接続は切断されるため、アプリケーションには切断検知と再接続の仕組みが必要。Primary Endpoint の利用が推奨

🎯 ユースケース

1️⃣ ミッションクリティカルなシステムのセキュリティパッチ適用

シナリオ: 24 時間稼働の基幹システムで四半期ごとの Release Update (RU) を適用したいが、標準アップグレードのダウンタイムが業務影響の観点で許容しにくい。

Bash業務時間中に先行アップグレード、深夜に切り替え
# 1. レプリカを先行アップグレード (業務時間中でもプライマリに影響なし)
aws rds modify-db-instance \
    --db-instance-identifier prod-oracle-replica \
    --engine-version 19.0.0.0.ru-2026-10.rur-2026-10.r1 \
    --apply-immediately

# 2. 深夜の低トラフィック帯にスイッチオーバー
aws rds switchover-read-replica \
    --db-instance-identifier prod-oracle-replica
✅ 効果: ソフトウェア更新は業務時間中にレプリカ側で完了させ、プライマリの利用不可をスイッチオーバー前後のみに短縮。パッチ先送りを減らし、セキュリティ修正を迅速に適用できる。
2️⃣ 読み取りトラフィックによる新バージョンの事前検証

シナリオ: Active Data Guard の読み取り専用レプリカをレポート用途で利用しており、新しいマイナーバージョンが自社ワークロードで問題なく動作するかを本番相当のクエリで確認してから切り替えたい。

Bash検証後にスイッチオーバー、問題があればロールバック
# レプリカをアップグレード後、レポート系クエリを読み取り専用レプリカへ送信して検証
# 問題がなければ 48 時間以内にスイッチオーバー
aws rds switchover-read-replica \
    --db-instance-identifier prod-oracle-ro-replica

# 問題が見つかった場合は手動ロールバック (元のバージョンに戻す)
aws rds modify-db-instance \
    --db-instance-identifier prod-oracle-ro-replica \
    --engine-version 19.0.0.0.ru-2026-07.rur-2026-07.r1 \
    --apply-immediately
✅ 効果: 新バージョンを実際の読み取りワークロードで検証し、問題があればプライマリに影響を与えずロールバック可能。ウィンドウ超過による自動ロールバックに任せることもでき、意思決定に 48 時間の猶予が得られる。
3️⃣ Primary Endpoint と組み合わせた無変更スイッチオーバー運用

シナリオ: 複数のアプリケーションが同じ RDS for Oracle に接続しており、スイッチオーバーのたびに各チームへ接続先変更を依頼する運用コストを削減しつつ、定期的なパッチ適用サイクルを確立したい。

TextPrimary Endpoint への接続統一
# アプリケーションの接続先を Primary Endpoint に統一
rds-0123456789abcdef0123456789abcdef.primary.rds.amazonaws.com:1521

# クライアントの DNS キャッシュ TTL を短く設定 (例: JVM)
networkaddress.cache.ttl=60
✅ 効果: Primary Endpoint はスイッチオーバー後に自動的に新プライマリへ解決されるため、接続文字列の変更が不要。アプリケーションチームの作業なしでパッチ適用を定期サイクルとして運用できる。

💰 料金・利用可能リージョン

💵 料金

Replica First Patching に追加料金はありません。レプリカに対して通常の Amazon RDS for Oracle の料金 (DB インスタンス、ストレージなど) が適用されます。

読み取り専用モードのレプリカで新バージョンを検証する場合は Oracle Active Data Guard オプションが必要です。マウントモードのレプリカであれば Active Data Guard は不要です。

🌍 利用可能リージョン

Amazon RDS for Oracle が利用可能なすべての AWS 商用リージョンで利用できます。

🔗 関連サービス・機能

  • Primary Endpoint: 常に現在のプライマリに解決される DNS 名。スイッチオーバー後も接続文字列の変更が不要になるため併用が推奨 (2026 年 11 月 20 日に同時発表)
  • Oracle Data Guard スイッチオーバー: 切り替えに使用される仕組み。自動バックアップの有効化などの要件を満たす必要がある
  • RDS for Oracle リードレプリカ: 先行アップグレードの対象となる同一リージョンレプリカ。読み取り専用モード (Active Data Guard) またはマウントモードで構成可能
  • 自動マイナーバージョンアップグレード AMVU: スケジュールが重なった場合は AMVU が優先。完了前にメンテナンスウィンドウが開始されるとレプリカはロールバックされる
  • Amazon RDS イベント通知: ウィンドウの開始・半分経過・ロールバックなどのイベントを Amazon SNS 経由で受け取れる

📝 まとめ

Replica First Patching により、RDS for Oracle のマイナーバージョンアップグレードにおけるプライマリのダウンタイムが、 スイッチオーバーとアップグレード完了処理の間だけに短縮され、 48 時間のウィンドウ内で切り替えタイミングを制御しながら新バージョンを事前検証できるようになりました。

Enterprise Edition で同一リージョンレプリカを持つ環境であれば追加料金なしで利用できるため、 Primary Endpoint への接続移行と RDS イベント通知のサブスクライブを整備した上で、 次回のマイナーバージョンアップグレードから適用することを推奨します。
