📋 概要

Amazon CloudWatch Pipelines に条件付き処理と新しいDrop Events プロセッサが追加されました。特定の条件に基づいてプロセッサの実行をスキップしたり、不要なログエントリをフィルタリングして除外したりすることが可能になります。

条件付き処理は 21 種類のプロセッサで利用でき、プロセッサレベルの "run when" 条件とエントリレベルの条件の 2 つの粒度で制御が可能です。これらの機能は CloudWatch Pipelines が GA されているすべてのリージョンで追加コストなしで利用可能です。

🔄 Before / After

❌ アップデート前
  • すべてのプロセッサがすべてのログエントリに対して一律に実行され、条件制御できなかった
  • 不要なログエントリをパイプライン内でフィルタリングする手段がなかった
  • ログの種類に基づいて異なる変換を適用するには複数パイプラインが必要だった
✅ アップデート後
  • 21 種類のプロセッサに条件付き処理を設定でき、実行条件を制御可能に
  • Drop Events プロセッサにより不要なログエントリをパイプライン内で除外可能に
  • 単一パイプラインで条件に基づいた柔軟なログ変換が可能になり管理が簡素化

⚡ 主要機能

🎯 条件付き処理 - プロセッサレベル "run when" 条件
プロセッサ全体の実行をスキップするかどうかを条件で制御できます。21 種類のプロセッサで利用可能で、条件が満たされない場合はプロセッサの処理全体がスキップされ、ログエントリはそのまま次のプロセッサに渡されます。
📝 条件付き処理 - エントリレベル条件
個々のログエントリに対してアクションを適用するかどうかを制御できます。同一プロセッサ内でエントリごとに異なる処理を適用可能で、特定のフィールド値やパターンに基づいた精密なフィルタリングが可能です。
🗑️ Drop Events プロセッサ
不要なログエントリをパイプラインから完全に除外する新しいプロセッサです。条件に一致するログエントリを宛先に送信せずにドロップし、ログボリュームの削減と下流の処理コスト最適化に有効です。

⚙️ 設定方法

前提条件

1️⃣ AWS アカウントで CloudWatch Pipelines が利用可能なリージョンであること
2️⃣ CloudWatch Pipelines のパイプラインが作成済み、または新規作成予定であること
3️⃣ パイプラインの設定に必要な IAM 権限が付与されていること

ステップ 1: 条件付きプロセッサを含むパイプラインの作成

ソースフィールドが "web-server" の場合にのみ、ログエントリに "tier" フィールドを追加するプロセッサを設定します。

Bash 条件付き処理を含むパイプラインを作成 
aws logs create-pipeline \
  --pipeline-name "conditional-processing-pipeline" \
  --log-group-name "/aws/application/my-app" \
  --processors '[
    {
      "type": "AddEntries",
      "runWhen": {
        "matchField": "source",
        "equals": "web-server"
      },
      "configuration": {
        "entries": [
          {"key": "tier", "value": "frontend"}
        ]
      }
    }
  ]'

ステップ 2: Drop Events プロセッサの追加

DEBUG レベルのログエントリをパイプラインから除外する Drop Events プロセッサを追加します。

Bash Drop Events プロセッサで不要なログを除外 
aws logs update-pipeline \
  --pipeline-name "conditional-processing-pipeline" \
  --processors '[
    {
      "type": "AddEntries",
      "runWhen": {
        "matchField": "source",
        "equals": "web-server"
      },
      "configuration": {
        "entries": [
          {"key": "tier", "value": "frontend"}
        ]
      }
    },
    {
      "type": "DropEvents",
      "configuration": {
        "condition": {
          "matchField": "level",
          "equals": "DEBUG"
        }
      }
    }
  ]'

ステップ 3: コンソールでの設定確認

CloudWatch コンソールの Pipelines セクションからも条件付き処理の設定が可能です。各プロセッサの設定画面で "Run when" 条件を追加し、エントリレベルの条件を個別のアクションに対して設定できます。

条件付き処理の設定例 - JSON

JSON パイプライン設定例 
{
  "PipelineName": "my-log-pipeline",
  "Processors": [
    {
      "Type": "AddEntries",
      "RunWhen": {
        "MatchField": "source",
        "Equals": "application"
      },
      "Configuration": {
        "Entries": [
          {
            "Key": "environment",
            "Value": "production"
          }
        ]
      }
    },
    {
      "Type": "DropEvents",
      "Configuration": {
        "Condition": {
          "MatchField": "level",
          "Equals": "DEBUG"
        }
      }
    }
  ]
}

💡 メリットと制約事項

✅ メリット

ビジネス面

💰 Drop Events プロセッサにより不要なログを除外し、ストレージと分析コストを削減
📈 単一パイプラインで条件ベースの柔軟な処理が可能、複数パイプライン管理が不要に
🆓 GA 全リージョンで追加料金なしで利用可能

技術面

🎯 プロセッサレベルとエントリレベルの 2 つの粒度できめ細かなログ変換制御が可能
🧩 条件分岐を単一パイプラインで処理し、アーキテクチャを簡素化
🔧 Add Entries、Grok、Rename Key など 21 種類のプロセッサで条件付き処理が利用可能

⚠️ 制約事項・注意点

  • 条件式の種類や複雑さに制限がある可能性 (公式ドキュメントでの確認を推奨)
  • Drop Events でドロップされたログは復元不可、条件設定に注意が必要
  • CloudWatch Pipelines が GA されていないリージョンでは利用不可
  • 条件設定ミスで意図しないログが除外される可能性、本番適用前にテスト環境での検証を推奨
  • 複雑な条件を多数設定した場合のパフォーマンスへの影響を事前に評価する必要がある
  • 既存パイプラインへの追加時は現在の処理フローへの影響を確認すること

🎯 ユースケース

🗑️ ユースケース 1: 本番環境のデバッグログ除外

シナリオ: アプリケーションが大量の DEBUG レベルログを出力しており、本番環境ではこれらが不要。ログストレージコストが増大している。

実装: Drop Events プロセッサで level = DEBUG のログをドロップ。

✅ DEBUG レベルのログがパイプラインで除外され、ログストレージコストの大幅な削減が期待できる。

🏢 ユースケース 2: マルチテナント環境での条件付きログ加工

シナリオ: SaaS アプリケーションでテナントごとに異なるログ加工ルールを適用したい。特定テナントのログにのみ追加フィールドを付与し、別テナントにはフィールド名変更を適用する。

実装: AddEntries で tenant_id = tenant-A にフィールド追加、RenameKey で tenant_id = tenant-B にフィールド名変更。

✅ 単一パイプラインでテナントごとの要件に対応でき、パイプライン管理が大幅に簡素化される。

🔒 ユースケース 3: セキュリティログの選択的処理

シナリオ: セキュリティ関連のログのみに Grok パターンを適用して構造化し、それ以外はそのまま通過。ヘルスチェックのログは不要なので除外したい。

実装: Grok プロセッサに log_type = security の run when 条件を設定。Drop Events で request_path = /health を除外。

✅ セキュリティログのみが構造化されて分析しやすくなり、ヘルスチェックログの除外によりノイズが削減される。
