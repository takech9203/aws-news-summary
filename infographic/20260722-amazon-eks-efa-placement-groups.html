EKS で EFA とプレイスメントグループをサポート

EKS Auto Mode / Karpenter のノードプール設定で、高性能ネットワークと配置戦略を宣言的に構成
リリース日
2026-07-22

📋 概要

Amazon EKS は、EKS Auto Mode とオープンソースの Karpenter の両方で、2 つの EC2 機能をサポートしました。1 つ目は Elastic Fabric Adapter (EFA) のネットワークデバイス設定、2 つ目は EC2 プレイスメントグループです。ワークロードをより高いパフォーマンスと可用性に向けてチューニングできます。

EFA は、EC2 インスタンス間で低レイテンシ・高帯域幅の通信を実現するネットワークインターフェイスです。今回のアップデートにより、EFA 対応インスタンスのネットワークインターフェイスを EFA 専用または標準の ENI として構成できます。プレイスメントグループでは、cluster / spread / partition の 3 戦略でインスタンスを配置し、パフォーマンス・可用性・障害分離を目的に応じて最適化できます。

これらの設定はいずれも EKS Auto Mode または Karpenter のノードプール設定内で直接構成できるため、これまで必要だった追加の運用上の回避策が不要になります。分散トレーニングジョブのスループット最大化や、重要な本番サービスの障害影響範囲 (ブラストレディウス) の最小化といったユースケースに適しています。

cluster / spread / partition

🔄 アップデート前後の比較

😰 Before（課題）

  • EKS Auto Mode / Karpenter のノードプール設定で EFA ネットワークインターフェイスをネイティブに構成できなかった
  • プレイスメントグループを利用するには追加の運用上の回避策が必要だった
  • 分散トレーニングなどの高パフォーマンスワークロードや、障害分離が重要なワークロードのチューニングが難しかった

😊 After（改善）

  • ノードプール設定内で EFA を直接構成できるようになった
  • cluster / spread / partition の 3 戦略を選択できるようになった
  • EFA 専用インターフェイスは IP アドレスを消費しないため、VPC 内の IP 使用量を精密に管理できる

⭐ 主要機能

🚀 EFA (Elastic Fabric Adapter) ネットワークデバイス設定

  • EFA 対応インスタンス上で、ネットワークインターフェイスを EFA 専用または標準の ENI として構成できる
  • 動的 (dynamic) および静的 (static) の両方のキャパシティノードプールで動作する
  • EFA 専用インターフェイスは IP アドレスを消費しないため、フル帯域幅の相互接続を維持しつつ VPC 内の IP 使用量を精密に管理できる

📍 EC2 プレイスメントグループのサポート

  • cluster、spread、partition の 3 つの配置戦略を用いてインスタンスを起動できる
  • 設定は EKS Auto Mode または Karpenter のノードプール設定内で直接行える
  • プレイスメントグループを利用するための追加の運用上の回避策が不要になる

🎯 パフォーマンスと可用性の最適化

  • 分散トレーニングジョブのスループット最大化に有効
  • 重要な本番サービスの障害影響範囲 (ブラストレディウス) の最小化に有効
  • パフォーマンス、可用性、障害分離を目的に応じて選択的に最適化できる

🛠️ 技術仕様

📐 プレイスメントグループの配置戦略

cluster

単一のアベイラビリティーゾーン内でインスタンスを近接配置し、低レイテンシと高スループットを実現。分散トレーニングや HPC 向け。

spread

インスタンスを個別のハードウェアに分散配置し、同時障害のリスクを低減。少数の重要なインスタンス向け。

partition

インスタンスを論理的なパーティションに分割し、パーティション間でハードウェアを分離。大規模分散システム向け。

適用・プロビジョニング

  • ステップ 1: EKS Auto Mode の NodeClass または Karpenter の EC2NodeClass で、ネットワークインターフェイスの構成を指定する。EFA 専用として構成すれば IP アドレスを消費せず高帯域幅の相互接続を利用できる
  • ステップ 2: 同じく NodeClass 内で配置戦略 (cluster / spread / partition) を指定する。ワークロードの特性に応じて選択することでパフォーマンスや障害分離を最適化できる
  • ステップ 3: 設定した NodeClass をノードプールに関連付けて適用する。以降、EKS Auto Mode または Karpenter が需要に応じて指定した構成の EC2 ノードを自動プロビジョニングする

詳細な設定項目は EKS Auto Mode ユーザーガイドおよび Karpenter のドキュメントを参照してください。

💡 メリット

💼 ビジネス面

✓運用負荷の軽減: 追加の運用上の回避策が不要になり、運用がシンプルになる
✓コスト効率の向上: EFA 専用インターフェイスが IP アドレスを消費せず、VPC の IP 空間を効率的に活用
✓信頼性向上: spread / partition 戦略で障害影響範囲を最小化し、重要サービスの可用性を高める

🔧 技術面

✓高パフォーマンス通信: EFA により分散トレーニングや HPC で低レイテンシ・高帯域幅のノード間通信を実現
✓柔軟なノード構成: 動的・静的の両方のノードプールで EFA を構成でき、幅広いワークロードに対応
✓宣言的な設定: NodeClass の設定として EFA とプレイスメントグループを宣言的に管理できる

⚠️ デメリット・制約事項

🚧 制限事項

!EFA は EFA 対応の EC2 インスタンスタイプでのみ利用可能
!cluster 戦略は単一の AZ に限定されるため、AZ 障害には注意が必要
!プレイスメントグループには EC2 の一般的な制約 (戦略ごとのインスタンス数やインスタンスタイプの制限など) が適用される

🤔 考慮すべき点

!ワークロードの特性 (スループット重視か障害分離重視か) に応じて適切な戦略を選択する必要がある
!EFA 専用インターフェイスと標準 ENI の使い分けを、通信要件と IP 管理要件の両面から検討する

🎯 ユースケース

1. 分散機械学習トレーニング

シナリオ: 複数の GPU ノードを用いた大規模な分散トレーニングジョブで、ノード間通信がボトルネックになっている。
効果: cluster プレイスメントグループと EFA を組み合わせ、低レイテンシ・高帯域幅通信を実現してトレーニングのスループットを最大化

2. 重要な本番サービスの障害分離

シナリオ: ミッションクリティカルな本番サービスを EKS 上で運用しており、ハードウェア障害による同時ダウンを避けたい。
効果: spread または partition プレイスメントグループでインスタンスを異なるハードウェアに分散配置し、障害影響範囲を最小化

3. IP アドレスが逼迫した VPC での HPC ワークロード

シナリオ: IP アドレス空間が限られた VPC 内で、高帯域幅通信が必要な HPC ワークロードを実行したい。
効果: EFA 専用インターフェイスは IP アドレスを消費しないため、IP 使用量を抑えながらフル帯域幅の相互接続を利用できる

💰 料金 & 🌍 利用可能リージョン

本機能自体に追加料金はありません。EFA およびプレイスメントグループは EC2 の標準機能として提供されており、追加料金なしで利用できます。利用した EC2 インスタンスや EKS クラスターの通常料金が適用されます。

提供リージョンは、Amazon EKS が利用可能なすべての AWS リージョンです。

詳細は Amazon EKS の料金ページおよび Amazon EC2 の料金ページを参照してください。

📌 まとめ

今回のアップデートにより、EKS Auto Mode と Karpenter の両方で EFA とプレイスメントグループを宣言的に構成でき、これまで必要だった運用上の回避策が不要になりました。分散トレーニングや HPC のパフォーマンス最適化、重要な本番サービスの障害分離を検討しているユーザーは、ワークロードの特性に応じて EFA 設定とプレイスメントグループ戦略の適用を検討することを推奨します。
