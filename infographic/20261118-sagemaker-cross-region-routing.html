Amazon SageMaker AI

🔀 クロスリージョン推論ルーティング

単一の API 呼び出しで、複数リージョン・複数アカウントのエンドポイントへ自動ルーティング
📅 リリース日: 2026 年 11 月 18 日

📝 概要

Amazon SageMaker AI がクロスリージョン推論ルーティングをサポートしました。 新しいリージョナルリソース推論ルーターを作成し、複数のリージョンやアカウントにデプロイした既存のリアルタイムエンドポイント、非同期エンドポイント、推論コンポーネントを登録すると、アプリケーションは単一の API を呼び出すだけで、正常かつキャパシティに余裕がある宛先にリクエストが自動的にルーティングされます。

GPU などのアクセラレーテッドインスタンスが単一リージョンでキャパシティ上限に達した場合でも、推論アプリケーションの可用性を維持できます。ルーターは自身のリージョンのエンドポイントを優先し、エラーやスロットリングが増加すると他リージョンの正常な宛先へ段階的にトラフィックを移動し、回復すると段階的に戻します。既存のエンドポイント、モデル、コンテナへの変更は不要です。

❌ アップデート前の課題
  • 単一リージョンでアクセラレーテッドインスタンスがキャパシティ不足になると、推論リクエストがスロットリングされ可用性が低下
  • 複数リージョンにデプロイしても、リージョン選択・ヘルスチェック・リトライロジックを独自に構築・運用する必要があった
  • 別アカウントのエンドポイントキャパシティを安全に共有する標準的な仕組みがなかった
✅ アップデート後の改善
  • 推論ルーターに既存エンドポイントを登録するだけで、単一 API によるマルチリージョン・マルチアカウントルーティングが可能に
  • エラー・スロットリング増加に応じた自動トラフィックシフトと回復後の自動復帰で、独自フェイルオーバー実装が不要に
  • エンドポイントポリシーと CrossRegionTrafficConfig で、所有者がアクセス許可とローカルキャパシティ確保を制御可能に

アプリケーションは推論ルーターの単一 API を呼び出すだけで、ルーターがローカルリージョンのエンドポイントを優先しつつ、過負荷やエラー発生時には別リージョン・別アカウントの正常なエンドポイントへトラフィックを自動的に振り分けます。

⚙️ 主要機能

1️⃣ 推論ルーターによる単一 API での複数宛先ルーティング
  • ルーターに 1 つ以上のルーティングターゲット (モデル単位) を追加し、各ターゲットに宛先 (エンドポイントまたは推論コンポーネント) を登録
  • 宛先は同一パーティション内の任意のリージョン、同一アカウントまたは別アカウントのリソースを指定可能
  • リアルタイム推論は InvokeInferenceRouter、非同期推論は InvokeInferenceRouterAsync で呼び出し
  • 既存のエンドポイント、モデル、コンテナ、オートスケーリング設定への変更は不要
2️⃣ ヘルスベースの自動トラフィックシフト
  • 宛先のヘルスは 5xx エラー、スロットリング、タイムアウトの発生状況から測定 (ルーター経由以外のリクエストも含む)
  • ローカル宛先のヘルス低下時は、低下度合いに応じてトラフィックの一部を他リージョンの正常な宛先へ段階的に移動し、回復すると段階的に戻す
  • モデルが実行されなかった失敗 (スロットリングなど) は別の宛先で 1 回リトライ
  • 成功している遅いレスポンスや 4xx エラーではトラフィックは移動しない
3️⃣ エンドポイント所有者による制御
  • エンドポイントポリシーにより、どのクロスアカウントルーターがアクセスできるかを制御
  • CrossRegionTrafficConfig で他リージョンのルーターからのリクエストレートに上限を設定し、ローカルリージョン向けキャパシティを確保
  • 上限は InService インスタンス数に応じて自動的に増減
4️⃣ 可観測性
  • レスポンスヘッダーで処理した宛先 (X-Amzn-SageMaker-Invoked-Routed-Resource-Arn) と選択理由 (X-Amzn-SageMaker-Invoked-Routing-Reason) を確認可能
  • ルーティング理由は local-preferred、capacity-available、failover、only-healthy の 4 種類
  • CloudWatch メトリクスでトラフィック分布や宛先のステータス (destination.status) を追跡可能

🛡️ クロスリージョントラフィック上限の設定例

Bash エンドポイント設定でクロスリージョン上限を指定 
aws sagemaker create-endpoint-config \
    --endpoint-config-name my-endpoint-config \
    --production-variants file://production-variants.json \
    --cross-region-traffic-config MaxInvocationsPerSecondPerInstance=50,MaxCrossRegionPercentPerEndpoint=25

MaxInvocationsPerSecondPerInstance は 1 インスタンスが処理できる秒間呼び出し数、MaxCrossRegionPercentPerEndpoint はそのうち他リージョンのルーターが使用できる割合です。上記の例では、2 インスタンス稼働時に他リージョンからのリクエストを秒間 25 リクエストに制限します。上限を超えたリクエストは ThrottlingException となり、ルーターが別の宛先で 1 回リトライします。

🛠️ 設定方法

📌 前提条件

✓同一モデルを複数リージョン (または複数アカウント) の SageMaker AI エンドポイントにデプロイ済みであること
✓ルーティングターゲット内のすべての宛先が、同じモデル・同じリクエスト/レスポンス形式であること
✓ルーターの作成・呼び出しに必要な IAM 権限が付与されていること
1
推論ルーターの作成
Bash ルーター作成とルーティングターゲット登録 
aws sagemaker create-inference-router \
    --inference-router-name my-router \
    --routing-targets file://routing-targets.json

ローカルリージョンに推論ルーターを作成し、ルーティングターゲット (モデルごとの宛先リスト) を登録します。宛先には同一パーティション内の任意のリージョン・アカウントのエンドポイントや推論コンポーネントを指定できます。

2
ルーター経由での推論リクエスト
Bash InvokeInferenceRouter の呼び出し 
aws sagemaker-inference-router-runtime invoke-inference-router \
    --inference-router-name my-router \
    --routing-target-name my-model \
    --content-type application/json \
    --body fileb://input.json \
    output.json

アプリケーションはエンドポイントの代わりにルーターを呼び出します。管理は sagemaker クライアント、呼び出しは sagemaker-inference-router-runtime という別のランタイムサービスを使用する点に注意してください。

3
ルーティング結果の確認とモニタリング

レスポンスヘッダーの X-Amzn-SageMaker-Invoked-Routed-Resource-Arn でどの宛先が処理したか、X-Amzn-SageMaker-Invoked-Routing-Reason でルーティング理由を確認します。CloudWatch のルーターメトリクスでトラフィック分布と宛先のヘルス (destination.status) を継続的にモニタリングします。

⚖️ メリットと制約事項

💼 ビジネス面のメリット

✓可用性の向上: 単一リージョンのキャパシティ不足や障害時にも他リージョンで推論を継続でき、サービス停止リスクを低減
✓追加料金なし: ルーティング自体は無料で、既存のエンドポイント料金のみで利用可能
✓キャパシティ共有: 別アカウントの共有エンドポイントを活用し、組織全体で GPU リソースを有効活用

🔧 技術面のメリット

✓実装の簡素化: 独自のリージョン選択・ヘルスチェック・リトライロジックの構築が不要
✓既存リソースへの無変更: エンドポイント、モデル、コンテナ、オートスケーリング設定を変更せずに導入可能
✓きめ細かな制御: エンドポイントポリシーと CrossRegionTrafficConfig で所有者側の制御が可能

🚧 制限事項

✗ルーター自体は単一リージョンで稼働するため、ルーターのリージョン障害時は他リージョンの宛先が正常でも呼び出しが失敗
✗レスポンスストリーミングは利用不可
✗TargetVariant、TargetModel、InferenceComponentName、ステートフルセッション (SessionId) は利用不可
✗ルーティングの重み付けやヘルスしきい値のカスタマイズ、ローカルリージョン以外の優先設定は不可
✗ランタイムエンドポイントは HTTP/1.1 のみ対応 (AWS SDK・CLI 利用時は影響なし)
✗リアルタイムのモデル応答時間は 60 秒固定で、アカウント単位のタイムアウト引き上げは適用されない

💡 考慮すべき点

⚠リクエスト単位でリージョンを制限できないため、データレジデンシー要件がある場合は許可されたリージョンの宛先のみを登録
⚠ルーターはキャパシティを追加しないため、スタンバイ側には処理可能なキャパシティとオートスケーリング設定が必要
⚠成功している遅いレスポンスではトラフィックは移動しないため、スロットリング前にスケールアウトする設定を推奨
⚠宛先のモード (リアルタイム/非同期) はルーター作成・更新時のみチェックされるため、モード変更時はルーティングターゲットの見直しが必要

🎯 ユースケース

🚀 ユースケース 1: GPU キャパシティ不足時のオーバーフロー処理

シナリオ: us-west-2 の LLM 推論エンドポイントがトラフィックスパイク時に GPU インスタンスを追加できず、スロットリングが発生している。

  1. us-east-1 に同一モデルのスタンバイエンドポイントをデプロイ (最低 1 インスタンス + オートスケーリング)
  2. us-west-2 に推論ルーターを作成し、両エンドポイントを宛先として登録
  3. アプリケーションの呼び出し先をルーターに変更

✅ 効果: ローカルエンドポイントがスロットリングを返し始めると、超過分のトラフィックが us-east-1 へ自動的に移動し、ユーザーへのエラー応答を回避できる。

🤝 ユースケース 2: 別アカウントとの推論キャパシティ共有

シナリオ: 組織内の複数アカウントで同一の基盤モデルを運用しており、アカウント間で GPU キャパシティを融通したい。

  1. 共有する側のアカウントでエンドポイントポリシーを設定し、許可するルーターを指定
  2. 共有するエンドポイントに CrossRegionTrafficConfig を設定し、自リージョン向けキャパシティを確保
  3. 利用する側のアカウントでルーターに共有エンドポイントを宛先として追加

✅ 効果: エンドポイント所有者がアクセス制御と上限を維持したまま、組織全体で GPU リソースを有効活用できる。

⏱️ ユースケース 3: 長時間推論の非同期フェイルオーバー

シナリオ: 処理に数分かかる非同期推論ジョブを、リージョン障害やキャパシティ不足時にも確実に処理したい。

  1. 複数リージョンに非同期エンドポイントをデプロイ (スタンバイはゼロインスタンスまでスケールイン可能)
  2. InvokeInferenceRouterAsync でルーター経由のジョブ投入に切り替え
  3. MaxTimeInBacklogSeconds をスタンバイのスケールアウト時間より長く設定

✅ 効果: バックログ滞留時間が上限を超えるとジョブが別の宛先へ移動し、コストを抑えつつ非同期処理の完了を担保できる。

💰 料金

クロスリージョン推論ルーティング自体に追加料金はありません。リクエストを処理するエンドポイントおよび推論コンポーネントに対して、標準の Amazon SageMaker AI 料金が発生します (ルーター経由か直接呼び出しかを問わない)。宛先が別アカウントの場合、そのエンドポイントの料金は所有アカウントに課金されます。ルーターが発行する CloudWatch メトリクスとそのクエリには、標準の CloudWatch 料金が適用されます。

🌍 利用可能リージョン

⚡ リアルタイム推論ルーティング

32 の商用 AWS リージョンで利用可能

⏳ 非同期推論ルーティング

25 の AWS リージョンで利用可能 (アジアパシフィック (ニュージーランド、ジャカルタ、ハイデラバード、メルボルン)、欧州 (ミラノ)、イスラエル (テルアビブ)、カナダ西部 (カルガリー) では利用不可)

宛先となるエンドポイントは、ルーターと同一パーティション内であれば、ルーターを作成できないリージョンにも配置できます。最新のリージョン一覧は SageMaker AI endpoints and quotas を参照してください。

📌 まとめ

クロスリージョン推論ルーティングにより、SageMaker AI の推論アプリケーションは単一リージョンの GPU キャパシティ不足や障害の影響を受けにくくなり、独自のフェイルオーバー実装が不要になります。追加料金なしで既存エンドポイントに変更を加えずに導入できるため、アクセラレーテッドインスタンスで本番推論を運用しているチームは、スタンバイリージョンのキャパシティ計画とあわせて導入を検討することを推奨します。
