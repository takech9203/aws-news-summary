📋 概要

Amazon EKS がクラスター作成および設定 API に対して 7 つの新しい IAM 条件キーをサポートしました。IAM ポリシーおよび Service Control Policies (SCPs) を通じたガバナンス制御が強化され、マルチアカウント環境における EKS クラスターの構成を一元的に管理できるようになります。

エンドポイントのアクセス制御、暗号化設定、Kubernetes バージョンの制限、削除保護の強制、コントロールプレーンのスケーリングティア指定、ゾーナルシフトの有効化といった幅広い構成要素をポリシーベースでプロアクティブに制御できます。

❌ アップデート前の課題
  • EKS クラスターの構成を IAM ポリシーで細かく制御する手段が限定的だった
  • マルチアカウント環境でクラスター構成の標準化には手動プロセスやデプロイ後の AWS Config ルールなどリアクティブな仕組みに依存
  • SCP でクラスター作成自体の許可/拒否は可能だったが、個別設定パラメータに対する条件付き制御ができなかった
✅ アップデート後の改善
  • 7 つの新しい条件キーにより、クラスター作成時・設定変更時の構成パラメータを IAM ポリシーレベルで制御可能
  • SCP と組み合わせ、組織全体のクラスター構成ガバナンスをプロアクティブに強制可能
  • 手動確認やデプロイ後のチェックが不要になり、ポリシー違反のクラスターが作成される前にブロック可能

⚙️ 主要機能: 7 つの IAM 条件キー

🔒 エンドポイントアクセス制御
クラスター API エンドポイントのパブリック/プライベートアクセスを条件として制御。組み合わせにより、プライベート専用エンドポイントの強制が可能。
eks:endpointPublicAccess eks:endpointPrivateAccess
🔑 暗号化設定の強制
Kubernetes シークレットの暗号化に使用する KMS キーの ARN を条件として指定。カスタマーマネージド KMS キーの使用を強制可能。
eks:encryptionConfigProviderKeyArns
📌 Kubernetes バージョンの制限
使用可能な Kubernetes バージョンを条件として制限。組織で承認済みのバージョンのみにクラスター作成・アップグレードを限定可能。
eks:kubernetesVersion
🛡️ 削除保護の強制
クラスターの削除保護設定を条件として制御。本番環境ワークロード向けクラスターの誤削除を防止。
eks:deletionProtection
📊 コントロールプレーンスケーリングティア
コントロールプレーンのスケーリングティアを条件として指定。ワークロード要件に応じた適切なティアの使用を強制可能。
eks:controlPlaneScalingTier
🌐 ゾーナルシフトの強制
ゾーナルシフト機能の有効/無効を条件として制御。高可用性が求められるワークロードに対してゾーナルシフトの有効化を強制可能。
eks:zonalShiftEnabled

条件キーの一覧

条件キー 型 対象 API 説明
eks:endpointPublicAccess Bool CreateCluster, UpdateClusterConfig パブリック API エンドポイントの許可/拒否
eks:endpointPrivateAccess Bool CreateCluster, UpdateClusterConfig プライベート API エンドポイントの許可/拒否
eks:encryptionConfigProviderKeyArns ARN CreateCluster, AssociateEncryptionConfig シークレット暗号化用 KMS キー ARN
eks:kubernetesVersion String CreateCluster, UpdateClusterVersion Kubernetes バージョン
eks:deletionProtection String CreateCluster, UpdateClusterConfig 削除保護の有効/無効
eks:controlPlaneScalingTier String CreateCluster, UpdateClusterConfig コントロールプレーンスケーリングティア
eks:zonalShiftEnabled Bool CreateCluster, UpdateClusterConfig ゾーナルシフトの有効/無効

対象 API アクション

API 説明

UpdateClusterConfig 既存クラスターの設定変更
UpdateClusterVersion クラスターの Kubernetes バージョン更新
AssociateEncryptionConfig クラスターへの暗号化設定の関連付け

🔧 設定方法

前提条件

✓ AWS Organizations が有効化されていること (SCP を使用する場合)
✓ IAM ポリシーの作成・編集権限があること
✓ EKS クラスターの管理権限があること
1 プライベートエンドポイントを強制する SCP の作成
パブリックエンドポイントが有効なクラスターの作成・設定変更を拒否し、プライベート専用エンドポイントのみを許可します。
JSON SCP: プライベートエンドポイント強制 
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "DenyPublicEKSEndpoint",
            "Effect": "Deny",
            "Action": [
                "eks:CreateCluster",
                "eks:UpdateClusterConfig"
            ],
            "Resource": "*",
            "Condition": {
                "Bool": {
                    "eks:endpointPublicAccess": "true"
                }
            }
        },
        {
            "Sid": "RequirePrivateEKSEndpoint",
            "Effect": "Deny",
            "Action": [
                "eks:CreateCluster",
                "eks:UpdateClusterConfig"
            ],
            "Resource": "*",
            "Condition": {
                "Bool": {
                    "eks:endpointPrivateAccess": "false"
                }
            }
        }
    ]
}
2 カスタマーマネージド KMS キーを強制する SCP の作成
カスタマーマネージド KMS キーが指定されていないクラスターの作成および暗号化設定の関連付けを拒否します。
JSON SCP: KMS 暗号化強制 
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "RequireCustomerManagedKMSKey",
            "Effect": "Deny",
            "Action": [
                "eks:CreateCluster",
                "eks:AssociateEncryptionConfig"
            ],
            "Resource": "*",
            "Condition": {
                "ForAllValues:ArnNotLike": {
                    "eks:encryptionConfigProviderKeyArns": "arn:aws:kms:*:*:key/*"
                }
            }
        }
    ]
}
3 Kubernetes バージョンと削除保護を強制する SCP の作成
承認済みの Kubernetes バージョン以外でのクラスター作成・バージョン更新を拒否し、削除保護が有効でないクラスターの作成を拒否します。
JSON SCP: バージョン制限 + 削除保護 
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "RestrictKubernetesVersion",
            "Effect": "Deny",
            "Action": [
                "eks:CreateCluster",
                "eks:UpdateClusterVersion"
            ],
            "Resource": "*",
            "Condition": {
                "StringNotEquals": {
                    "eks:kubernetesVersion": [
                        "1.31",
                        "1.32"
                    ]
                }
            }
        },
        {
            "Sid": "RequireDeletionProtection",
            "Effect": "Deny",
            "Action": [
                "eks:CreateCluster",
                "eks:UpdateClusterConfig"
            ],
            "Resource": "*",
            "Condition": {
                "StringNotEquals": {
                    "eks:deletionProtection": "ENABLED"
                }
            }
        }
    ]
}
4 SCP を Organizations の OU にアタッチ
作成した SCP を AWS Organizations の組織単位にアタッチすることで、OU 配下のすべてのアカウントに対してポリシーが適用されます。
Bash AWS CLI: SCP 作成とアタッチ 
# SCP を作成
aws organizations create-policy \
  --name "EKS-Governance-Policy" \
  --description "Enforce EKS cluster governance with IAM condition keys" \
  --type SERVICE_CONTROL_POLICY \
  --content file://eks-governance-scp.json

# SCP を OU にアタッチ
aws organizations attach-policy \
  --policy-id p-xxxxxxxxxxxx \
  --target-id ou-xxxx-xxxxxxxx

💡 ユースケース

1 🏦 金融機関のセキュアクラスター強制
シナリオ: 金融機関が複数の AWS アカウントで EKS クラスターを運用しており、すべてのクラスターでプライベートエンドポイント、カスタマーマネージド KMS キーによるシークレット暗号化、削除保護を必須とするセキュリティポリシーがある。
効果: 組織全体のすべてのアカウントで、セキュリティ要件を満たさない EKS クラスターの作成が自動的にブロックされ、コンプライアンス違反を未然に防止できる。
2 📌 標準化された Kubernetes バージョン管理
シナリオ: 大規模な組織でプラットフォームチームが、すべての開発チームが使用する Kubernetes バージョンを組織承認済みのバージョンに制限し、サポート切れのバージョンでのクラスター作成を防止したい。
効果: 組織で承認されたバージョンのみでクラスターが作成・更新されるため、セキュリティパッチの適用状況やサポートライフサイクルの一元管理が容易になる。
3 🌐 本番環境の高可用性ガードレール
シナリオ: 本番環境の OU に属するアカウントでは、すべての EKS クラスターにゾーナルシフトの有効化と削除保護を強制し、障害時の可用性と誤操作防止を確保したい。
効果: 本番環境のクラスターには必ずゾーナルシフトと削除保護が有効化されるため、AZ 障害時の自動フェイルオーバーと誤削除防止のガードレールが確立される。

✅ ビジネス面のメリット

✓ コンプライアンスの自動化: IAM ポリシーレベルでクラスター構成を強制し、手動レビューやデプロイ後の監査への依存を排除
✓ マルチアカウントガバナンス: SCP と組み合わせ、組織全体に一貫したクラスター構成ポリシーを適用
✓ 運用リスクの軽減: 削除保護やパブリックエンドポイント制限により人的ミスを予防

✅ 技術面のメリット

✓ プロアクティブなポリシー適用: クラスター作成時点で構成違反をブロックし、後からの修正コストが不要
✓ きめ細かいアクセス制御: 7 つの条件キーにより多角的な構成要素を個別に制御可能
✓ 既存 IAM との統合: 新しいツールやサービスの導入不要で、既存の仕組みをそのまま活用

⚠️ 制限事項・考慮すべき点

⚠️ 条件キーは対象 API に対してのみ適用され、既存クラスターの構成を自動修正する機能はない。既にデプロイ済みのクラスターには遡及適用されない。
⚠️ SCP の最大文字数制限 (5,120 文字) があるため、多数の条件キーを含む複雑なポリシーでは分割が必要になる場合がある。
⚠️ 複数の条件キーを組み合わせる場合、ポリシーの論理構造を慎重に設計する必要がある。条件キーの値が API リクエストに含まれない場合の挙動を理解した上でポリシーを設計すること。
⚠️ 既存クラスターの構成適合性を確認するには、AWS Config のカスタムルールや EKS API の DescribeCluster を使用した別途の監査が必要。

📝 まとめ

Amazon EKS が 7 つの新しい IAM 条件キーをサポートし、クラスター作成・設定 API に対するガバナンス制御が大幅に強化されました。エンドポイントアクセス、暗号化、Kubernetes バージョン、削除保護、コントロールプレーンスケーリング、ゾーナルシフトといった構成要素を IAM ポリシーおよび SCP レベルでプロアクティブに制御できるようになったことで、マルチアカウント環境でのセキュリティとコンプライアンスの自動化が実現します。
