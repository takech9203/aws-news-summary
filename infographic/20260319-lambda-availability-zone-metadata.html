Availability Zone メタデータのサポート

AWS Lambda
2026 年 3 月 19 日

📋 概要

AWS Lambda が実行環境内で Availability Zone メタデータを提供する新しいエンドポイントをサポートしました。Lambda 関数が実行されている AZ の AZ ID (例: use1-az1) を取得でき、AZ を考慮したルーティング判断が可能になります。

すべての Lambda ランタイム (カスタムランタイムやコンテナイメージを含む) でサポートされ、SnapStart やプロビジョンドコンカレンシーでも動作します。追加料金なしですべての商用 AWS リージョンで利用可能です。

❌ Before

  • Lambda 関数がどの AZ で実行されているか確認する手段がなかった
  • クロス AZ 通信によるレイテンシー増加を回避できなかった
  • AZ 固有の障害をシミュレートするフォールトインジェクションテストが困難だった

✅ After

  • メタデータエンドポイントから AZ ID を取得し、実行中の AZ を正確に特定可能
  • 同一 AZ のエンドポイントを優先するルーティングでクロス AZ レイテンシーを削減
  • AZ 固有のフォールトインジェクションテストが実現可能に

🔧 主要機能

📋 AZ メタデータエンドポイント

Lambda 実行環境内で新しいメタデータエンドポイントを提供。AZ ID (例: use1-az1) を取得可能で、AZ ID はアカウント間で一貫した物理的な AZ の識別子です。

🔀 AZ 対応ルーティング

同一 AZ 内のエンドポイントを優先する AZ アウェアなルーティング判断が可能。クロス AZ レイテンシーの削減に貢献し、ダウンストリームサービスとの通信を最適化します。

💥 AZ 固有のフォールトインジェクションテスト

特定の AZ に対する障害注入テストが実装可能。AWS Fault Injection Service (FIS) と組み合わせた AZ レベルの障害シミュレーションで、カオスエンジニアリングに活用できます。

🌐 幅広いランタイムサポート

すべての Lambda ランタイムで利用可能。カスタムランタイム、コンテナイメージ、SnapStart、プロビジョンドコンカレンシーとの互換性があります。

📐 技術仕様

※ メタデータは Lambda 実行環境内のローカルエンドポイントから取得するため、既存の Lambda API に対する変更は不要です。

💻 実装例

Powertools for AWS Lambda を使用した AZ メタデータ取得

Python Powertools メタデータユーティリティ 
from aws_lambda_powertools.utilities.metadata import get_availability_zone

def lambda_handler(event, context):
    az_id = get_availability_zone()
    print(f"Current AZ: {az_id}")  # 例: use1-az1

    # AZ ID に基づいてダウンストリームエンドポイントを選択
    endpoint = select_same_az_endpoint(az_id)
    response = call_downstream_service(endpoint)
    return response

メタデータエンドポイントの直接呼び出し

Python 直接 HTTP アクセス 
import urllib.request
import os

def get_az_id():
    """Lambda メタデータエンドポイントから AZ ID を取得"""
    metadata_url = f"http://localhost:9001/2024-11-28/az-id"
    req = urllib.request.Request(metadata_url)
    with urllib.request.urlopen(req) as response:
        return response.read().decode("utf-8")

AZ 対応ルーティングの実装

Python 同一 AZ エンドポイント優先ルーティング 
import os
from aws_lambda_powertools.utilities.metadata import get_availability_zone

# AZ ごとのエンドポイントマッピング
AZ_ENDPOINTS = {
    "use1-az1": "https://service-az1.internal.example.com",
    "use1-az2": "https://service-az2.internal.example.com",
    "use1-az4": "https://service-az4.internal.example.com",
}
DEFAULT_ENDPOINT = "https://service.internal.example.com"

def lambda_handler(event, context):
    az_id = get_availability_zone()

    # 同一 AZ のエンドポイントを優先
    endpoint = AZ_ENDPOINTS.get(az_id, DEFAULT_ENDPOINT)

    # ダウンストリームサービスを呼び出し
    response = call_service(endpoint)
    return response

🎯 ユースケース

1. 同一 AZ 優先ルーティングによるレイテンシー最適化

マイクロサービスアーキテクチャにおいて、Lambda 関数から Amazon ElastiCache や Amazon RDS などのダウンストリームサービスにアクセスする際、同一 AZ のエンドポイントを優先して低レイテンシーを実現します。

→ クロス AZ 通信を回避し、ネットワークレイテンシーを数ミリ秒削減。高頻度呼び出しアプリケーションで大きなパフォーマンス改善が期待できます。

2. AZ 固有のフォールトインジェクションテスト

AWS Fault Injection Service (FIS) と組み合わせて、特定の AZ で動作する Lambda 関数の障害挙動をテスト。環境変数で対象 AZ を指定し、その AZ でのみエラーを発生させることが可能です。

→ AZ レベルの障害シミュレーションにより、マルチ AZ 構成の耐障害性を事前に検証し、本番環境での障害対応力を向上できます。

3. AZ ごとのパフォーマンスモニタリング

AZ ID をカスタムメトリクスに含め、AZ ごとのレイテンシーやエラー率を監視してパフォーマンスの偏りを検出します。Powertools の Logger や Metrics と組み合わせて実装できます。

→ AZ ごとのパフォーマンスを可視化し、特定の AZ でのレイテンシー増加やエラー率の上昇を早期に検出できます。

✅ メリット

ビジネス面

  • 同一 AZ ルーティングによるレイテンシー削減でユーザー体験を向上
  • クロス AZ データ転送削減によるコスト最適化
  • AZ 固有のフォールトインジェクションテストで耐障害性を事前検証

技術面

  • サーバーレスでも AZ アウェアアーキテクチャが設計可能
  • AZ レベルのカオスエンジニアリングが実現
  • AZ ID をログ/メトリクスに含めて可観測性を向上
  • 追加コストなしで利用可能

⚠️ 制限事項・考慮点

  • AZ ID は Lambda 実行環境の起動時に決定され、実行中に変更されることはない
  • AZ 対応ルーティングの実装は開発者が自ら行う必要がある (自動最適化ではない)
  • ダウンストリームサービスが AZ ごとにエンドポイントを分離していない場合、AZ ルーティングのメリットを活かせない
  • 特定の AZ 障害時のフォールバックロジックも合わせて実装が必要
  • AZ Name ではなく AZ ID を使用すること (AZ Name はアカウントごとにマッピングが異なる)
  • プロビジョンドコンカレンシー使用時は、特定の AZ に偏る可能性があるため監視が必要
