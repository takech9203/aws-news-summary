Amazon EBS

💾 EBS Volume Clones がクロスアカウントコピーに対応

📅 2026 年 9 月 9 日リリース ｜ Amazon Elastic Block Store ｜ 再暗号化対応のアカウント間ボリュームコピー

📋 概要

Amazon EBS Volume Clones が AWS アカウントをまたいだボリュームコピーに対応しました。 コピー時にターゲットアカウントの KMS キーで再暗号化できるため、本番環境と開発環境をアカウント単位で分離している組織が、アカウント境界を越えて安全にデータをコピーできます。 非暗号化ボリュームおよびカスタマーマネージドキーで暗号化されたボリュームを含む、すべてのボリュームタイプでサポートされます。

❌ Before: アップデート前の課題

  • Volume Clones (CopyVolumes API) は同一アカウント内に限定。アカウント間の受け渡しはスナップショットの作成・共有・復元という多段階の手順が必要
  • 本番アカウントの最新データを開発アカウントに展開するまでに時間と運用負荷がかかっていた
  • 環境ごとの KMS キー分離には、データコピーとキー付け替えを組み合わせた独自ワークフローの構築が必要

✅ After: アップデート後の改善

  • AWS RAM で共有するだけで、ターゲットアカウントから直接 CopyVolumes によるボリュームコピーを作成可能
  • コピー時にターゲット側の KMS キーを指定して再暗号化でき、本番と非本番のキー分離を維持したままデータを受け渡せる
  • コピーは作成後すぐに available 状態となり、初期化中でもシングルミリ秒レイテンシーで即座にアクセス可能

ソースアカウントが AWS RAM でボリュームを共有し、ターゲットアカウントが同一アベイラビリティーゾーン内にコピーを作成、ターゲット側の KMS キーで再暗号化する流れ

⚡ 主要機能

🤝 1. AWS RAM によるボリューム共有
  • 個別のアカウント ID、組織単位 (OU)、または AWS Organizations の組織全体に共有可能
  • マネージド権限は 2 種類: メタデータ参照のみの AWSRAMDefaultPermissionEBSVolume (デフォルト) と、コピー作成を許可する AWSRAMPermissionEBSVolumeCopyAccess
  • ec2:Volume リソースタイプへのカスタマーマネージド権限の作成にも対応
  • 共有先ができるのは参照とコピー作成のみ。アタッチ・変更・削除・スナップショット作成は不可
🔑 2. 再暗号化を伴うクロスアカウントコピー
  • 共有ボリュームに対して CopyVolumes API (CLI: copy-volumes) を実行し、同一 AZ 内にコピーを作成
  • デフォルトでターゲットアカウントの EBS デフォルト暗号化キーを使用。KmsKeyId で任意のカスタマーマネージドキーも指定可能
  • ソース側キーが共有されていればそのキーも選択可 (デフォルトでソース側キーが再利用されることはない)
  • コピー時にボリュームタイプ、サイズ、IOPS、スループットの変更も可能
🚀 3. 即時アクセスとバックグラウンド初期化
  • クラッシュコンシステントなポイントインタイムコピーで、作成後すぐに available 状態になり EC2 にアタッチ可能
  • データブロックはバックグラウンドでコピーされ、初期化中もシングルミリ秒レイテンシーでアクセス可能
  • 初期化中のベースライン性能は、3,000 IOPS / 125 MiB/s、ソースのプロビジョンド性能、コピーのプロビジョンド性能のうち最小値
  • コピー操作はソースボリュームの性能に影響しない
📊 4. モニタリング
  • 初期化の進捗は describe-volume-status または Amazon EventBridge で監視
  • コピー完了時にはボリューム所有者と共有先の両アカウントに sharedVolumeCopy イベントを配信
  • CopyVolumes 呼び出しは双方のアカウントの CloudTrail に記録され、監査証跡が残る

🛠️ 設定方法

✅ 前提条件

✓ソースボリュームが非暗号化、またはカスタマーマネージドキーで暗号化されていること (aws/ebs で暗号化されたボリュームは共有不可)
✓カスタマーマネージドキーの場合、キーポリシーでターゲットアカウントにキーを共有していること
✓ターゲットアカウントがソースと同じアベイラビリティーゾーン (AZ ID で確認) にコピーを作成できること
1
ソースアカウントでボリュームを共有する
BashAWS RAM リソース共有の作成
aws ram create-resource-share \
  --name prod-volume-share \
  --resource-arns arn:aws:ec2:us-east-1:111111111111:volume/vol-1234567890abcdef0 \
  --principals 222222222222 \
  --permission-arns arn:aws:ram::aws:permission/AWSRAMPermissionEBSVolumeCopyAccess \
  --region us-east-1

コピー作成を許可するには AWSRAMPermissionEBSVolumeCopyAccess の指定が必要。組織外のアカウントに共有した場合は招待の承諾が必要です。

2
ターゲットアカウントで共有ボリュームを確認する
Bash共有ボリュームの一覧表示
aws ec2 describe-volumes \
  --filters Name=owner-id,Values=111111111111 \
  --region us-east-1

コンソールでは [Volumes] 画面の [Shared with me] フィルターでも確認できます。

3
ターゲットアカウントでボリュームをコピーする
Bashターゲット側 KMS キーで再暗号化してコピー
aws ec2 copy-volumes \
  --source-volume-id vol-1234567890abcdef0 \
  --volume-type gp3 \
  --kms-key-id arn:aws:kms:us-east-1:222222222222:key/abcd1234-a123-456a-a12b-a123b4cd56ef \
  --region us-east-1

--kms-key-id を省略するとターゲットアカウントのデフォルト EBS 暗号化キーが使用されます。コピーは短時間で available になります。

4
初期化の進捗を監視する
Bash初期化ステータスの確認
aws ec2 describe-volume-status \
  --volume-ids vol-0abcdef1234567890 \
  --region us-east-1

EventBridge の EBS Volume Notification イベント (sharedVolumeCopy) でコピー完了や失敗を自動検知できます。

💡 メリット

📈 ビジネス面

✓開発サイクルの高速化: 本番データの新しいコピーを開発アカウントに数ステップで展開でき、テスト環境のデータリフレッシュが迅速に
✓アカウント分離によるガバナンス維持: マルチアカウント戦略を崩さずに、必要なデータだけを安全に受け渡し
✓コンプライアンス対応: 環境ごとの KMS キー分離要件を満たしつつ、CloudTrail による双方向の監査証跡も残る

⚙️ 技術面

✓スナップショット経由の手順が不要: 作成・共有・復元の多段階ワークフローを共有とコピーの 2 ステップに簡素化
✓即時アクセス: 初期化完了を待たずにアタッチでき、シングルミリ秒レイテンシーでアクセス可能
✓ソースへの影響なし: 本番ワークロードを稼働させたままコピー可能
✓柔軟な構成変更: コピー時にタイプ・サイズ・IOPS・スループットを変更し、開発向けにコスト最適化

⚠️ デメリット・制約事項

🚫 制限事項

✗コピーはソースと同じ AZ に作成する必要がある (クロス AZ・クロスリージョン不可)
✗AWS マネージドキー (aws/ebs) で暗号化されたボリュームは共有・コピー不可
✗共有ボリュームへの進行中コピーは共有先アカウント全体で同時 1 つまで
✗1 ソースから同時コピーは 1 つ、リージョンあたり進行中コピーは最大 5 つ (クォータ引き上げ可)
✗Outposts 上および Wavelength Zones のボリュームはコピー不可
✗ソースボリュームのタグはコピーに引き継がれない
✗共有先は共有ボリュームのアタッチ・変更・削除・スナップショット作成が不可

🤔 考慮すべき点

⚠コピーはクラッシュコンシステント。アプリケーションコンシステントが必要なら書き込み一時停止や I/O フリーズ (fsfreeze、VSS など) が必要
⚠AZ 名はアカウントごとにマッピングが異なるため、AZ ID (use1-az1 など) で同一ロケーションを確認
⚠初期化中のベースライン性能は最小 3,000 IOPS / 125 MiB/s。高性能が必要ならソースとコピー双方のプロビジョンド性能を考慮
⚠リソース共有からボリュームを削除しても、進行中のコピー操作はキャンセルされない
⚠本番データを開発アカウントにコピーする際は、個人情報のマスキングなどデータ取り扱いポリシーへの準拠を別途検討

🎯 ユースケース

💽 1. 本番データベースの開発環境への展開

本番アカウントで稼働する PostgreSQL データベースの EBS ボリュームを、分離された開発アカウントにコピーし、開発者が最新の本番相当データでテストを行う。

BashDB ボリュームの共有と再暗号化コピー
# ソースアカウント: DB ボリュームを開発アカウントに共有
aws ram create-resource-share \
  --name db-volume-share \
  --resource-arns arn:aws:ec2:ap-northeast-1:111111111111:volume/vol-0db0123456789abcd \
  --principals 222222222222 \
  --permission-arns arn:aws:ram::aws:permission/AWSRAMPermissionEBSVolumeCopyAccess

# ターゲットアカウント: 開発用 KMS キーで再暗号化してコピー
aws ec2 copy-volumes \
  --source-volume-id vol-0db0123456789abcd \
  --kms-key-id alias/dev-ebs-key
✅ 効果: スナップショットの作成・共有・復元を経由せずに本番データを展開。コピーは即座にアタッチ可能で、テスト開始までの待ち時間を短縮。
🔐 2. 環境ごとの暗号化キー分離の徹底

セキュリティポリシーで本番用と非本番用の KMS キー分離が義務付けられており、非本番環境への持ち出し時は必ず非本番キーで再暗号化する。

Bash非本番キーを指定してコピー
# ターゲットアカウントで非本番用カスタマーマネージドキーを指定してコピー
aws ec2 copy-volumes \
  --source-volume-id vol-0prod123456789abc \
  --kms-key-id arn:aws:kms:ap-northeast-1:222222222222:key/nonprod-key-id
✅ 効果: ソース側キーはデフォルトで再利用されないため、キー分離ポリシーを自然に強制。本番キーへのアクセス権を非本番アカウントに広く付与する必要がない。
🔄 3. コピー完了を起点とした環境構築の自動化

毎週の開発環境リフレッシュで、ボリュームコピーの完了を検知して自動的に EC2 へのアタッチとアプリケーション起動を行う。

JSONEventBridge イベントパターン
{
  "source": ["aws.ec2"],
  "detail-type": ["EBS Volume Notification"],
  "detail": {
    "event": ["sharedVolumeCopy"],
    "result": ["completed"]
  }
}
✅ 効果: EventBridge ルールで sharedVolumeCopy イベントを捕捉し、Lambda で後続処理を自動化。イベントは両アカウントに配信され、双方で完了を追跡可能。

🔗 関連サービス・機能

🤝 AWS Resource Access Manager (AWS RAM)

ボリュームをアカウント間で共有するための基盤。マネージド権限 AWSRAMPermissionEBSVolumeCopyAccess でコピー作成を許可。

🔑 AWS Key Management Service (AWS KMS)

コピー時の再暗号化に使用。クロスアカウントでのキー共有やターゲット側キーの指定に関わる。

📸 Amazon EBS スナップショット

従来のクロスアカウントデータ共有手段。クロスリージョンコピーや長期保管が必要な場合は引き続きスナップショットが適する。

📡 Amazon EventBridge / AWS CloudTrail

コピー完了イベントの通知と API 呼び出しの監査に使用。

📝 まとめ

Amazon EBS Volume Clones のクロスアカウントコピー対応により、スナップショットを経由せずに本番アカウントから開発アカウントへボリュームを直接コピーし、ターゲット側の KMS キーで再暗号化できるようになりました。 マルチアカウント戦略でのテストデータ展開やキー分離要件を持つ組織にとって、運用を大きく簡素化するアップデートです。

🎯 推奨アクション: まずは AWS RAM でのボリューム共有と copy-volumes コマンドを開発環境で試し、同一 AZ 制約や AZ ID のマッピングを確認した上でワークフローへの組み込みを検討しましょう。
