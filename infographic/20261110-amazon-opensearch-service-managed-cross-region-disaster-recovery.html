Amazon OpenSearch Service 📅 2026 年 11 月 10 日

🛡️ マネージドクロスリージョンディザスタリカバリ

単一の API 呼び出しで 2 リージョンのドメインをペアリングし、マネージドな DR を実現

📌 概要

Amazon OpenSearch Service が、マネージド型のクロスリージョンディザスタリカバリ (DR) 機能を発表しました。 単一の API 呼び出し、またはコンソールの数ステップで 2 つの AWS リージョンのドメインをペアリングし、 アクティブ/パッシブモデルの継続的な非同期レプリケーションを構成できます。 接続はサービス側が管理し、VPC ピアリングなどのネットワーク設定は不要。レプリケーションデータは転送中に暗号化されます。

😣 アップデート前の課題

  • ❌ クロスクラスターレプリケーションやスナップショット復旧を自前で設計・構築・保守
  • ❌ フェイルオーバー/フェイルバック手順が複雑で、運用負荷と人為的ミスのリスクが高い
  • ❌ レプリケーションの健全性やラグの監視の仕組みを独自に用意する必要

😊 アップデート後の改善

  • ✅ 単一の API またはコンソール数ステップで別リージョンのドメインとペアリング
  • ✅ RPO 1 分未満、RTO 20 分未満のマネージドな目標値を提供
  • ✅ 計画時はデータ損失ゼロのスイッチオーバーでロールを交換
  • ✅ CloudWatch メトリクスで健全性とラグを標準監視

プライマリドメインの変更がセカンダリドメインへ非同期にレプリケーションされ、セカンダリ側が CloudWatch にレプリケーションメトリクスを発行します。 計画時はスイッチオーバー、障害時はフェイルオーバーによってセカンダリをプライマリへ昇格できます。

⚙️ 主要機能

🔗 1. シンプルなドメインペアリング
  • AddReplicationPeer API またはコンソールの数ステップで DR を構成
  • --dry-run オプションで、関係を作成せずに前提条件の検証のみ実行可能
  • 接続はサービス管理で VPC ピアリング不要、転送中は暗号化
🔄 2. 継続的な非同期レプリケーション
  • DR 設定時に既存の全インデックスを初期コピーし、その後は変更を非同期レプリケーション
  • 対象: インデックス、ドキュメント、インデックス設定、エイリアス、データストリーム
  • 対象外: テンプレート、インジェストパイプライン、ISM ポリシー、ロール、クラスター設定 → IaC での同期を推奨
🔁 3. 計画的スイッチオーバー
  • 保留中の変更を全てレプリケーション後、データ損失ゼロでロールを交換
  • スイッチオーバー後は旧プライマリがセカンダリとなり、逆方向にレプリケーション継続
  • 切替中は短時間、両ドメインとも書き込み不可のため、アプリ側でリトライ設定が必要
🚨 4. 障害時のフェイルオーバー
  • FailoverReplication でセカンダリを一方的に昇格
  • データ損失はフェイルオーバー時点のレプリケーションラグの範囲に限定
  • 手動実行が基本。自動化には CloudWatch アラーム連携の仕組みを独自構築
  • フェイルオーバー後は空のセカンダリと再ペアリングして保護を回復
📊 5. CloudWatch によるレプリケーション監視
  • セカンダリドメインが 1 分ごとに DR メトリクスを発行
  • ラグ時間、未適用の変更数、初期コピー中・劣化・失敗したインデックス数を監視可能

🛠️ 設定方法

✅ 前提条件

✓両ドメインが OpenSearch 3.7 以降の同一バージョンで稼働
✓両ドメインが同一 AWS アカウント内の異なるリージョンに存在
✓両ドメインできめ細かなアクセスコントロールとノード間暗号化が有効
✓セカンダリドメインが空 (システムインデックス以外のインデックスを含まない)
✓セカンダリドメインがプライマリと同等以上のストレージ容量を持つ
1
前提条件の検証 (dry-run)
BashAddReplicationPeer を dry-run で実行
aws opensearch add-replication-peer \
  --domain-name my-primary-domain \
  --peer-domain-arn arn:aws:es:us-west-2:123456789012:domain/my-secondary-domain \
  --region us-east-1 \
  --dry-run

レプリケーション関係を作成せずに、2 つのドメインがペアリング可能かどうかの前提条件を検証します。

2
レプリケーション関係の作成
Bashプライマリのリージョンで AddReplicationPeer を実行
aws opensearch add-replication-peer \
  --domain-name my-primary-domain \
  --peer-domain-arn arn:aws:es:us-west-2:123456789012:domain/my-secondary-domain \
  --region us-east-1

レプリケーション関係は非同期に作成され、既存インデックスの初期コピーが開始されます。

3
レプリケーションステータスの確認
BashDescribeDomainReplication でステータス確認
aws opensearch describe-domain-replication \
  --domain-name my-primary-domain \
  --region us-east-1

ロール (PRIMARY / SECONDARY) とステータスを確認します。ACTIVE になればレプリケーションが稼働中です。初期コピーの完了は DisasterRecoveryBootstrappingIndices が 0 に戻ることで確認できます。

4
スイッチオーバーまたはフェイルオーバーの実行
Bashセカンダリのリージョンで実行
# 計画的スイッチオーバー (セカンダリのリージョンで実行)
aws opensearch switchover-replication \
  --domain-name my-secondary-domain \
  --peer-domain-arn arn:aws:es:us-east-1:123456789012:domain/my-primary-domain \
  --region us-west-2

# 障害時フェイルオーバー (データ損失の許容を明示)
aws opensearch failover-replication \
  --domain-name my-secondary-domain \
  --peer-domain-arn arn:aws:es:us-east-1:123456789012:domain/my-primary-domain \
  --allow-data-loss \
  --region us-west-2

いずれも昇格させたいセカンダリドメインのリージョンで実行します。フェイルオーバーはデータ損失の可能性があるため --allow-data-loss が必須です。切り替え後は、アプリケーションの書き込み先を新しいプライマリへ変更します。

💡 メリット

💼 ビジネス面

✓事業継続性の確保: RPO 1 分未満、RTO 20 分未満のマネージドな目標値で BCP 要件を満たしやすい
✓運用コストの削減: 自前のレプリケーション構築・保守が不要になり、DR 体制の工数を大幅削減
✓追加料金なし: セカンダリドメインとリージョン間データ転送の標準料金のみで利用可能

🔧 技術面

✓ネットワーク設定不要: 接続はサービス管理、レプリケーションデータは転送中に暗号化
✓データ損失ゼロのスイッチオーバー: 計画メンテナンスや DR 訓練を安全に実施
✓標準化された監視: CloudWatch でラグや健全性を監視し、アラームによる自動化の起点に
✓読み取りキャパシティの活用: セカンダリも読み取りに利用でき、待機系を有効活用

⚠️ デメリット・制約事項

🚫 制限事項

✗両ドメインが OpenSearch 3.7 以降の同一バージョンである必要 (バージョンが異なる間はスイッチオーバー不可)
✗同一 AWS アカウント内のみ。クロスアカウント構成は非サポート
✗1 つのドメインが持てるレプリケーションピアは 1 つのみ
✗UltraWarm、コールドストレージ、OR1/OR2 インスタンス、ログ分析向け最適化エンジン、自動セマンティックエンリッチメントを使用するドメインは非サポート
✗セカンダリドメインは DR 設定時に空である必要
✗クローズされたインデックスは DR で保護されず、再オープン時にフルコピーが必要

🤔 考慮すべき点

⚠フェイルオーバーは手動。自動化には CloudWatch アラーム連携の独自の仕組みが必要
⚠切替後のエンドポイント変更はユーザー側の責任 (サービスはリダイレクトしない)
⚠テンプレート、パイプライン、ISM ポリシー、ロールなどはレプリケーションされないため IaC で事前作成 (CompareDomainConfiguration で差分検出可能)
⚠フェイルオーバー後、旧プライマリは自動再同期されず、保護回復には空のセカンダリとの再ペアリングとフルコピーが必要
⚠クローンベースアップグレードを使用する場合は、事前にレプリケーション関係の削除が必要
⚠セカンダリの長期間の停止後は、影響を受けたインデックスの再ブートストラップが必要になる場合がある

🎯 ユースケース

🛒 1. ミッションクリティカルな検索基盤のリージョン障害対策

シナリオ: E コマースサイトの商品検索基盤を OpenSearch Service で運用しており、リージョン障害時にも検索サービスを継続する必要がある。

Bash東京と大阪のドメインをペアリング
aws opensearch add-replication-peer \
  --domain-name ec-search-primary \
  --peer-domain-arn arn:aws:es:ap-northeast-3:123456789012:domain/ec-search-secondary \
  --region ap-northeast-1

効果: リージョン障害時にフェイルオーバーで大阪リージョンへ切り替え、RTO 20 分未満で検索サービスを復旧。データ損失はレプリケーションラグ (RPO 1 分未満) の範囲に限定される。

🏦 2. 定期的な DR 訓練とリージョンローテーション

シナリオ: 金融系システムのコンプライアンス要件として、定期的な DR 訓練の実施と復旧手順の実効性確認が求められている。

Bashデータ損失ゼロのスイッチオーバー
aws opensearch switchover-replication \
  --domain-name dr-secondary \
  --peer-domain-arn arn:aws:es:us-east-1:123456789012:domain/dr-primary \
  --region us-west-2

効果: データ損失ゼロの計画的スイッチオーバーにより、本番データを失うリスクなしに DR 手順を定期的にリハーサルできる。訓練後は再度スイッチオーバーして元の構成に戻せる。

📊 3. CloudWatch アラームによるレプリケーション監視の自動化

シナリオ: レプリケーションラグの増大や失敗インデックスの発生を早期に検知し、運用チームへ通知したい。

Bashレプリケーションラグ時間のアラーム作成
aws cloudwatch put-metric-alarm \
  --alarm-name opensearch-dr-lag-alarm \
  --namespace AWS/ES \
  --metric-name DisasterRecoveryReplicationLagTime \
  --statistic Maximum \
  --period 60 \
  --threshold 60000 \
  --comparison-operator GreaterThanThreshold \
  --evaluation-periods 5 \
  --alarm-actions arn:aws:sns:us-west-2:123456789012:dr-alerts

効果: レプリケーションラグが閾値を超えた場合に SNS 経由で通知を受け取り、RPO 要件の逸脱を早期に検知できる。フェイルオーバー判断の起点としても活用可能。

💰 料金・利用可能リージョン

💵 料金

ディザスタリカバリ機能自体に追加料金はありません。以下の標準料金が適用されます。

✓セカンダリドメインのインスタンス・ストレージに対する OpenSearch Service の標準料金
✓リージョン間でレプリケーションするデータに対する標準の AWS データ転送料金

詳細は 料金ページ を参照。

🌍 利用可能リージョン

Amazon OpenSearch Service が利用可能なすべての AWS 商用リージョンで利用できます。

対象リージョンの一覧は AWS リージョン別サービス表 を参照。

📝 まとめ

Amazon OpenSearch Service のマネージドクロスリージョン DR により、これまで自前で構築・運用する必要があったリージョン間のレプリケーションとフェイルオーバーが、 追加料金なしのマネージド機能として利用できるようになりました。 RPO 1 分未満・RTO 20 分未満という明確な目標値が提供されるため、ミッションクリティカルな検索・分析ワークロードの BCP 設計を大幅に簡素化できます。

利用には OpenSearch 3.7 以降が必要なため、まずは対象ドメインのバージョンアップ計画と、 レプリケーションされないリソース (テンプレート、パイプライン、ロールなど) の IaC 管理を検討することを推奨します。
