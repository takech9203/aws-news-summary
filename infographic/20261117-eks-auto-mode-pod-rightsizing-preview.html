Amazon EKSプレビュー

☸️ EKS Auto Mode リソース最適化による
Pod の自動ライトサイジング

📅 リリース日: 2026 年 11 月 17 日 | サービス: Amazon Elastic Kubernetes Service

📋 概要

EKS Auto Mode の新機能リソース最適化 (resource optimization)がプレビューリリース。実行中の Pod の実際の使用量に基づいて、CPU とメモリのリクエスト値を自動的にライトサイジングします。同じワークロードをより少ない / 小さい EC2 インスタンスで実行でき、手動チューニングなし・追加料金なしでコンピューティングコストを削減できます。

有効化は ClusterResourceOptimizationPolicy を作成するだけ。デフォルトの Recommend モードで推奨値を確認し、準備ができたら Apply モードに切り替えると、Pod を再作成せずインプレースでリサイズ。Pod テンプレートは一切変更されないため、Argo CD や Flux などの GitOps ツールでドリフトが発生しません。

❌ アップデート前の課題
  • CPU / メモリのリクエスト値はデプロイ時のまま見直されず、過剰な値のまま放置されがち
  • 適正化には使用量の計測、Pod テンプレート編集、再デプロイといった手動チューニングが必要
  • VPA などで自動調整すると、マニフェスト変更が GitOps ツールのドリフトとして検出される懸念
  • 過剰なリクエスト値により、多すぎる / 大きすぎる EC2 インスタンスが稼働しコスト増大
✅ アップデート後の改善
  • 実使用量に基づく CPU / メモリリクエストの推奨値がワークロードごとに自動生成
  • Apply モードでは Pod resize サブリソースにより再作成なしでインプレースリサイズ
  • Pod テンプレートは変更されないため GitOps ドリフトが発生しない
  • OOM kill 発生時はメモリ推奨値を引き上げ、Java ヒープ等の要件を下回らないよう調整
  • 追加料金なしで、より少ない / 小さいインスタンスに集約

ポリシーを作成すると、選択されたワークロードごとに ResourceOptimization オブジェクトが自動作成され、約 12 時間の使用量履歴に基づいて推奨値が生成されます。Apply モードでは Pod テンプレートを変更せず、実行中の Pod をインプレースでリサイズします。

⚙️ 主要機能

📜 1. ポリシーベースの有効化 (ClusterResourceOptimizationPolicy)
  • クラスタースコープの Kubernetes オブジェクトを kubectl や GitOps ツールで作成するだけ (EKS API の設定は不要)
  • namespaceSelector と workloadSelector で対象を柔軟に選択
  • 複数ポリシーが同じワークロードを選択した場合はフィールドごとに結合、より具体的なポリシーが優先
  • 空の spec はシステム名前空間を除く全 Deployment / StatefulSet を Recommend モードで選択
🔀 2. 2 つの動作モード (Recommend / Apply)
💡 Recommend
推奨値の生成のみ
Pod は変更しない
→
⚡ Apply
推奨値に合わせて
Pod をリサイズ
  • モードを切り替えても収集済みの使用量履歴はリセットされず、再収集は不要
🔁 3. インプレースリサイズと GitOps 親和性
  • Kubernetes の Pod resize サブリソースを使用し、Pod を再作成せずにリサイズ
  • Pod テンプレートは編集しないため、Argo CD や Flux はドリフトを検出せず、リバートも発生しない
  • スケールアウトやロールアウトで作成される新しい Pod は推奨サイズで起動
⚖️ 4. Balanced 最適化プロファイル
  • CPU: 使用量の 95 パーセンタイルがリクエスト値の約 87% になるようにサイジング
  • メモリ: 95 パーセンタイルがリクエスト値の約 70% になるようにサイジング (OOM 対策で CPU より大きいヘッドルーム)
  • 推奨値は宣言された最小リクエストの 1/2 から最大リミットの 2 倍までの範囲内
  • Java サービスではメモリ推奨値が Java ヒープを下回らないよう維持、OOM kill 後はメモリを引き上げ
🤝 5. オートスケーラーとの共存
  • HPA や KEDA がスケーリング基準とするリソースは変更しない
  • VPA が既に管理しているワークロードは除外できる
  • optimization.eks.amazonaws.com/enabled: "false" アノテーションで個別にオプトアウト可能

🔬 技術仕様

要件とスコープ

項目詳細
クラスターKubernetes 1.36 以降の EKS Auto Mode クラスター (既存クラスターも対象、クラスター更新や EKS API 呼び出しは不要)
対象ワークロードDeployment、StatefulSet
対象リソースCPU、メモリ (GPU、エフェメラルストレージ、レプリカ数は対象外)
除外名前空間kube-system、kube-public、kube-node-lease は選択しても管理対象外
推奨値の生成コンテナごとに約 12 時間の使用量履歴が必要
最適化プロファイルプレビューでは Balanced のみ
料金追加料金なし
🔎 API 変更履歴: 今回のアップデートに関連する EKS API の変更はありません。リソース最適化は ClusterResourceOptimizationPolicy という Kubernetes カスタムリソース (apiVersion: eks.amazonaws.com/v1beta1) で管理され、EKS API の設定は存在しません。

ClusterResourceOptimizationPolicy の例

YAML 特定チームのワークロードを Apply モードで管理 
apiVersion: eks.amazonaws.com/v1beta1
kind: ClusterResourceOptimizationPolicy
metadata:
  name: team-search
spec:
  namespaceSelector:
    matchLabels:
      team: search
  workloadSelector:
    matchLabels:
      tier: stateless
  mode: Apply

team: search ラベルを持つ名前空間のうち、tier: stateless ラベルを持つワークロードのみを Apply モードで管理するポリシーの例です。

🛠️ 設定方法

前提条件

✓Kubernetes バージョン 1.36 以降で稼働する EKS Auto Mode クラスター
✓クラスターと通信できるように設定された kubectl
✓クラスタースコープのリソースを作成できる権限
1
デフォルト設定でリソース最適化を有効化
Bash空の spec でポリシーを作成
cat <<EOF > ro-default-policy.yaml
apiVersion: eks.amazonaws.com/v1beta1
kind: ClusterResourceOptimizationPolicy
metadata:
  name: default
spec: {}
EOF

kubectl apply -f ro-default-policy.yaml

システム名前空間を除く全 Deployment / StatefulSet が Recommend モードと Balanced プロファイルで選択されます。この時点では Pod は一切変更されません。

2
ポリシーの状態と推奨値を確認
Bashcrop / ro は短縮名
# ポリシーの状態を確認
kubectl get crop

# ワークロードごとの ResourceOptimization オブジェクトを確認
kubectl get ro --all-namespaces

READY が True であればセレクターは有効、SELECTED は選択中のワークロード数。推奨値は約 12 時間の使用量履歴の収集後に表示されます。

3
Apply モードに切り替えてリサイズを開始
Bashモードの切り替え
kubectl patch crop default --type merge -p '{"spec":{"mode":"Apply"}}'

モード切り替え時に使用量履歴はリセットされないため、既に推奨値があるワークロードは即座にリサイズ対象となります。

4
必要に応じて個別ワークロードをオプトアウト
Bashオプトアウトと値の復元
# ワークロードを管理対象から除外
kubectl annotate deployment my-app -n my-namespace optimization.eks.amazonaws.com/enabled="false"

# 適用済みの値を Pod テンプレートの値に戻す場合
kubectl rollout restart deployment my-app -n my-namespace

適用済みの値は自動では戻らないため、Pod テンプレートの値に戻すにはロールアウト再起動が必要です。GitOps 管理の場合はリポジトリ内のマニフェストにアノテーションを追加してください。

💪 メリット

💼 ビジネス面

✓コンピューティングコストの削減: 過剰なリクエスト値が実使用量に合わせて適正化され、より少ない / 小さい EC2 インスタンスで実行可能
✓追加料金なし: リソース最適化自体に費用は発生せず、導入の障壁が低い
✓運用工数の削減: 放置されがちなリクエスト値の見直しが自動化され、手動チューニングが不要

🔧 技術面

✓GitOps とのドリフトレスな統合: Pod テンプレートを変更しないため、Argo CD や Flux がドリフトを検出しない
✓無停止のリサイズ: Pod resize サブリソースによるインプレースリサイズで Pod の再作成を伴わない
✓安全性を考慮した推奨値: メモリには CPU より大きいヘッドルーム、Java ヒープの維持や OOM kill 後のメモリ引き上げ
✓段階的な導入が可能: Recommend モードで影響なく確認してから、ポリシー単位・ワークロード単位で Apply に移行

⚠️ デメリット・制約事項

制限事項

✗プレビューリリースであり、仕様は変更される可能性がある
✗Kubernetes 1.36 以降の EKS Auto Mode クラスターのみで利用可能 (Auto Mode 以外は利用不可)
✗対象は Deployment と StatefulSet のみ、CPU とメモリのみサイジング (GPU、エフェメラルストレージ、レプリカ数は対象外)
✗kube-system、kube-public、kube-node-lease 名前空間は管理されない
✗最適化プロファイルはプレビューでは Balanced のみ
✗利用可能リージョンは 7 リージョンに限定

考慮すべき点

⚠自動ロールバックなし: 適用した推奨値がワークロードを劣化させても自動では元に戻らない。問題発生時はオプトアウトまたは Recommend モードへの切り替えが必要
⚠適用済みの値は残存する: ポリシー削除やモード変更をしても、実行中の Pod には最後に適用された値が残る。戻すには kubectl rollout restart などの再起動が必要
⚠コスト削減額のレポートなし: プレビューでは削減額の推定値は表示されないため、計測には AWS Cost Explorer などを使用
⚠コンソールは読み取り専用: EKS コンソールに専用ページはなく、Kubernetes リソースビューアーで読み取り専用の確認のみ
⚠最初の推奨値の生成には約 12 時間の使用量履歴が必要。オプトアウトすると履歴が削除され、再有効化時は約 12 時間の再収集が必要

🎯 ユースケース

☕ ユースケース 1: Argo CD 管理下の Java サービス群の一括ライトサイジング

シナリオ: プラットフォームチームが Argo CD で多数の Java サービスを管理しており、各チームのテンプレートを編集せずに全アプリケーション名前空間をライトサイジングしたい。

YAML全名前空間に Apply モードを適用
apiVersion: eks.amazonaws.com/v1beta1
kind: ClusterResourceOptimizationPolicy
metadata:
  name: default
spec:
  mode: Apply

効果: テンプレート編集や GitOps ドリフトなしで全名前空間をライトサイジング。メモリ推奨値は各 Java ヒープより上に維持され、OOM kill 発生後はメモリを引き上げるため、Java ワークロードでも安全に適用できる。

🛡️ ユースケース 2: 本番名前空間を除外した段階的導入

シナリオ: まず本番以外の環境で推奨値を適用し、本番の payments-prod 名前空間は対象外にしたい。

YAMLNotIn で特定の名前空間を除外
apiVersion: eks.amazonaws.com/v1beta1
kind: ClusterResourceOptimizationPolicy
metadata:
  name: all-but-payments
spec:
  namespaceSelector:
    matchExpressions:
      - key: kubernetes.io/metadata.name
        operator: NotIn
        values: [payments-prod]

効果: Kubernetes が全名前空間に自動設定する kubernetes.io/metadata.name ラベルを利用し、ラベル付け作業なしで特定の名前空間を除外。本番環境への影響を避けながら段階的に導入できる。

🔍 ユースケース 3: 特定チームのステートレスワークロードのみ自動適用

シナリオ: 検索チームのステートレスなワークロードだけ自動リサイズを有効にし、その他のワークロードは推奨値の確認にとどめたい。

YAMLセレクターで対象を絞り込み
apiVersion: eks.amazonaws.com/v1beta1
kind: ClusterResourceOptimizationPolicy
metadata:
  name: team-search
spec:
  namespaceSelector:
    matchLabels:
      team: search
  workloadSelector:
    matchLabels:
      tier: stateless
  mode: Apply

効果: より具体的なポリシーが優先されるルールにより、デフォルトポリシー (Recommend) と共存しながら、対象を絞った Apply モードの適用が可能。HPA や KEDA のスケーリング基準リソースは変更されないため、既存のオートスケーリング構成とも共存できる。

💰 料金

リソース最適化は追加料金なしで利用できます。EKS Auto Mode 自体の料金 (管理対象インスタンスに対する Auto Mode 料金と EC2 インスタンス料金) は従来どおり発生します。

ライトサイジングにより必要な EC2 インスタンスの数やサイズが削減されるため、コンピューティングコストの削減が期待できます。プレビューでは削減額の推定値は提供されないため、効果測定には AWS Cost Explorer などを使用してください。

🔗 関連サービス・機能

EKS Auto Mode: 本機能の前提となる EKS のフルマネージドな実行モード。コンピューティング、ネットワーク、ストレージのプロビジョニングと管理を自動化する
Horizontal Pod Autoscaler (HPA) / KEDA: 水平スケーリングの仕組み。リソース最適化はスケーリング基準とするリソースを変更しないため共存できる
Vertical Pod Autoscaler (VPA): 垂直スケーリングの仕組み。VPA が既に管理しているワークロードはリソース最適化から除外できる
AWS Cost Explorer: ライトサイジングによるコスト削減効果の計測に使用できる

📝 まとめ

EKS Auto Mode のリソース最適化は、デプロイ後に放置されがちな CPU / メモリリクエストの適正化を、GitOps ドリフトや Pod 再作成なしで自動化する機能です。追加料金なしで利用でき、まず Recommend モードで推奨値を確認してから Apply モードに移行する段階的な導入が可能です。

Kubernetes 1.36 以降の EKS Auto Mode クラスターを運用しているチームは、まずデフォルトポリシーを作成して推奨値を確認し、コスト削減の余地を把握することをお勧めします。
