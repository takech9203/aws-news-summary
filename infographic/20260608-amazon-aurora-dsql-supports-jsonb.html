📋 概要

Amazon Aurora DSQL が PostgreSQL の JSONB データ型をネイティブサポートしました。バイナリ形式で JSON データを格納し、従来の JSON 型と比較して高速なクエリ処理とインデックス作成が可能です。既存の PostgreSQL JSONB 依存コードを変更なしで Aurora DSQL に移行できます。

❌ Before

  • JSON (テキスト形式) のみサポート
  • JSONB 依存 ORM の移行に修正が必要
  • クエリ時に毎回パース処理が必要
  • GIN インデックスによる JSON 内検索不可

✅ After

  • JSONB ネイティブサポート (バイナリ形式)
  • 既存コードを変更なしで移行可能
  • デフォルト圧縮で効率的なストレージ
  • 全 JSONB 関数・演算子がサポート

⚡ 主要機能

📦 PostgreSQL JSONB データ型のネイティブサポート
PostgreSQL 標準の JSONB 型をカラム定義で使用可能。バイナリ分解形式でデータを格納し、クエリ時のパースが不要。重複キーの自動除去、キーのソート済み格納による効率的なアクセスを実現。
🗜️ デフォルト圧縮によるストレージ最適化
INSERT および UPDATE 操作時に自動的に圧縮を適用。1 MiB の制限は圧縮後サイズに適用されるため、圧縮前はそれ以上のサイズを格納可能。STORAGE キーワードで圧縮無効化も可能。
🛠️ 完全な JSON 関数・演算子サポート
PostgreSQL セクション 9.16 のすべての JSON 関数・演算子に対応。jsonb_populate_record、jsonb_populate_recordset などのレコード操作関数もサポート。ただし CREATE TYPE によるカスタム複合型は未サポート。

🔧 設定方法・コードサンプル

ステップ 1: JSONB カラムを含むテーブルの作成

SQL テーブル作成 
CREATE TABLE api_events (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    event_type VARCHAR(100) NOT NULL,
    payload JSONB NOT NULL,
    created_at TIMESTAMP DEFAULT NOW()
);

ステップ 2: JSONB データの挿入

SQL データ挿入 
INSERT INTO api_events (event_type, payload)
VALUES (
    'user.signup',
    '{"user_id": "u-12345", "email": "user@example.com",
      "plan": "enterprise",
      "metadata": {"source": "web", "campaign": "q2-launch"}}'::jsonb
);

ステップ 3: JSONB 演算子を使用したクエリ

SQL JSONB クエリ例 
-- JSONB フィールドの抽出
SELECT
    event_type,
    payload->>'user_id' AS user_id,
    payload->>'email' AS email,
    payload->'metadata'->>'source' AS source
FROM api_events
WHERE event_type = 'user.signup';

-- 包含演算子 (@>) によるフィルタリング
SELECT *
FROM api_events
WHERE payload @> '{"plan": "enterprise"}'::jsonb;

-- キー存在チェック (?) 演算子
SELECT *
FROM api_events
WHERE payload ? 'metadata';

ステップ 4: 圧縮の無効化 (オプション)

SQL 圧縮無効化 
CREATE TABLE raw_events (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    event_data JSONB STORAGE PLAIN NOT NULL
);

ステップ 5: 既存テーブルへの JSONB カラム追加

SQL ALTER TABLE 
ALTER TABLE existing_table
ADD COLUMN metadata JSONB;

⚖️ メリット・デメリット

✅ メリット

  • 移行コスト削減: Django、Rails、Spring Boot 等のアプリを修正なしで移行可能
  • ストレージ最適化: デフォルト圧縮で大容量データを効率的に保存
  • 開発生産性向上: NoSQL データベースの追加運用が不要に
  • 高速クエリ: バイナリ形式でパース処理が不要
  • 豊富な演算子: @>, ?, ?|, ?& による柔軟なフィルタリング
  • PostgreSQL エコシステム互換: ORM、マイグレーションツールがそのまま動作

⚠️ 制限事項・注意点

  • GIN インデックス未サポート (大規模データセットでの検索性能に制限)
  • CREATE TYPE によるカスタム複合型は未サポート
  • 圧縮後 1 MiB を超えるデータは格納不可
  • 高頻度フィルタリングには正規化を検討
  • 大量 JSONB データのトランザクションでレイテンシー影響の可能性

🎯 ユースケース

🔌 ユースケース 1: マイクロサービスの API ペイロード監査

シナリオ: マイクロサービスアーキテクチャで API リクエスト/レスポンスのペイロードを監査目的で保存し、高速な検索を行う。

効果: JSONB の包含演算子 (@>) により構造化されたエラー情報を高速にフィルタリング。圧縮により大量の API ペイロードのストレージコストを抑制。

SQL API 監査ログ検索 
SELECT service_name, endpoint,
       response_payload->>'error_code' AS error_code
FROM api_audit_log
WHERE response_payload @> '{"error_code": "RATE_LIMIT_EXCEEDED"}'::jsonb
  AND created_at > NOW() - INTERVAL '1 hour';

⚙️ ユースケース 2: マルチテナント設定管理

シナリオ: SaaS アプリケーションで、テナントごとに異なる設定を JSONB で柔軟に管理し、特定の機能フラグを持つテナントを素早く特定する。

効果: JSONB 演算子でネストされた設定構造内の特定のフラグやキーを効率的に検索。スキーマ変更なしに新しい設定項目を追加可能。

SQL テナント設定検索 
-- SSO が有効なエンタープライズテナントを検索
SELECT tenant_name, config->'limits' AS limits
FROM tenant_config
WHERE config @> '{"features": {"sso": true}}'::jsonb
  AND plan = 'enterprise';

📋 ユースケース 3: イベント駆動アーキテクチャのイベントストア

シナリオ: イベントソーシングパターンで、構造が異なる多様なドメインイベントを単一テーブルに格納し、特定の条件でイベントを検索する。

効果: イベントの構造が異なっていても JSONB で柔軟に格納でき、包含演算子で条件に合致するイベントを効率的に検索可能。圧縮によりストレージを最適化。

SQL イベントストア検索 
SELECT aggregate_id, event_type, event_data
FROM domain_events
WHERE event_data @> '{"status": "cancelled", "reason": "payment_failed"}'::jsonb
  AND occurred_at > NOW() - INTERVAL '7 days';
