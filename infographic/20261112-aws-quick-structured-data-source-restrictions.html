🔐 構造化データソースの制限によるきめ細かなガバナンス強化

📅 リリース日: 2026 年 11 月 12 日 | カスタム権限による構造化データソースコネクタの制限 (Structured Data Source Restrictions)

📝 概要

AWS Quick は、カスタム権限 (Custom Permissions) プロファイルを通じて、構造化データソースコネクタ単位でのきめ細かな制限機能の一般提供を開始しました。管理者は、ユーザーがどの種類のデータソースを作成・更新・共有できるかを、コネクタごとに個別に制御できます。

本機能は AWS Quick Enterprise edition の管理者向けに提供され、管理コンソール UI、API、AWS CLI のいずれからも設定可能です。例えば、Amazon Redshift データソースの作成は許可しつつ、ファイルアップロードによるデータソース作成はブロックする、といった柔軟な制御により、セルフサービス分析とデータガバナンスの両立を実現します。

❌ Before: アップデート前の課題
  • データソースの制限は「すべての作成・更新の禁止」「すべての共有の禁止」といった一括制御のみで、コネクタの種類ごとに制御を分けられなかった
  • 承認済みデータウェアハウス (例: Amazon Redshift) への接続は許可しつつ、統制外のデータ持ち込み (例: ファイルアップロード) のみを禁止する要件を実現しにくかった
  • ガバナンスのためにデータソース作成を全面禁止すると、セルフサービス分析の利便性が大きく損なわれていた
✅ After: アップデート後の改善
  • コネクタ単位 (例: Snowflake、RedshiftManual、GoogleBigQuery) で、作成 (Create)・更新 (Update)・共有 (Share) の 3 つの権限を個別に制限可能に
  • 特定コネクタの共有のみをブロックするなど、一括制限よりも精緻なガバナンスポリシーを定義可能に
  • UI に加えて API・AWS CLI でも管理でき、ガバナンス設定の自動化・コード化 (IaC) が容易に

管理者が定義したカスタム権限プロファイルに基づき、ユーザーのデータソース操作がコネクタ単位で評価され、許可または拒否されます。権限はユーザー → ロール → アカウントの順で評価され、より具体的なレベルの設定が優先されます。

⚙️ 主要機能

1️⃣ コネクタ単位のデータソース権限制御
  • 各データソースコネクタに対して、作成 (Create)・更新 (Update)・共有 (Share) の 3 つの権限を個別に制限可能
  • 例: Amazon Redshift データソースの作成は許可し、Snowflake データソースの作成は禁止する
  • コネクタ全体 (作成・更新・共有のすべて) をまとめて制限することも可能
2️⃣ UI・API・AWS CLI による設定
  • Quick 管理コンソールの [Capabilities & features] > [Connectors] グループの [Data sources] 配下で、コネクタごとに設定可能
  • create-custom-permissions などの API / CLI 操作で、Create{{Connector}}DataSource のようなケイパビリティ名を指定してプロファイルを定義可能
  • 管理コンソールの Check permissions 機能で、どのプロファイルがどのレベル (ユーザー、ロール、アカウント) で適用されているかを確認可能
3️⃣ 複数レベルでの適用と優先順位
  • カスタム権限プロファイルはアカウント、ロール (Admin、Author、Reader)、ユーザーの各レベルで割り当て可能
  • ユーザーレベル → ロールレベル → アカウントレベルの順に評価され、最も具体的なレベルの設定が優先される
  • カスタム権限はスコープダウンポリシーであり、ロールが持つデフォルト権限を超える権限の付与はできない

🔧 技術仕様

📛 データソースコネクタのケイパビリティ名

API / CLI でコネクタ単位の権限を設定する際は、以下のケイパビリティ名を使用します。{{Connector}} には Snowflake、RedshiftManual、GoogleBigQuery などのコネクタ名が入ります。

権限ケイパビリティ名
コネクタのすべての権限{{Connector}}DataSource
作成Create{{Connector}}DataSource
更新Update{{Connector}}DataSource
共有Share{{Connector}}DataSource

🔗 全コネクタ共通の制限との関係

設定項目動作
Creating or updating all data sourcesすべてのコネクタのデータソース作成・更新を一括で禁止
Sharing data sourcesすべてのコネクタのデータソース共有を一括で禁止
コネクタ単位の権限一括制限を設定した場合、該当操作はすべてのコネクタで制限される。制限していないコネクタ権限は許可されたまま
⚠️ 親ケイパビリティを DENY にすると、その配下の子機能も拒否されます。親が DENY の状態で子機能を ALLOW にしても子機能は制限されたままとなるため、特定の子機能のみを許可したい場合は、親を許可したまま制限したい子機能のみを DENY にします。

🔑 必要な IAM 権限

カスタム権限プロファイルの管理には、Quick 管理者であることに加えて quicksight:CreateCustomPermissions、quicksight:UpdateCustomPermissions、quicksight:ListCustomPermissionAssignments などの IAM 権限が必要です。

✓カスタム権限関連の IAM 権限 (quicksight:CreateCustomPermissions など) が付与されていること

ステップ 1: カスタム権限プロファイルの作成

Bash プロファイル作成 
aws quicksight create-custom-permissions \
  --aws-account-id 123456789012 \
  --custom-permissions-name RestrictSnowflake \
  --capabilities '{"CreateSnowflakeDataSource": "DENY", "ShareSnowflakeDataSource": "DENY"}'

Snowflake データソースの作成と共有を禁止するカスタム権限プロファイル RestrictSnowflake を作成します。--capabilities にコネクタ単位のケイパビリティ名と DENY を指定することで、対象操作を制限します。

ステップ 2: プロファイルのユーザーまたはロールへの割り当て

Bash ユーザーへの割り当て 
aws quicksight update-user-custom-permission \
  --aws-account-id 123456789012 \
  --namespace default \
  --user-name analyst-user \
  --custom-permissions-name RestrictSnowflake

作成したプロファイルを特定のユーザーに割り当てます。ロール単位 (Admin、Author、Reader) やアカウント単位での割り当ても可能で、ユーザーレベルの設定が最も優先されます。

ステップ 3: 適用状況の確認

Quick 管理コンソールの Check permissions 機能を使用して、対象ユーザーにどのプロファイルがどのレベル (ユーザー、ロール、アカウント) で適用されているかを確認します。設定後は、実際に対象ユーザーでデータソース作成画面を開き、制限が意図どおりに反映されていることを検証します。

💡 メリット

💼 ビジネス面
✓ガバナンスとセルフサービスの両立: 承認済みデータソースへの接続は許可しつつ、統制外のデータ持ち込みのみを禁止し、ガバナンス要件を満たしながらセルフサービス分析を推進
✓コンプライアンス対応の強化: 機密データを扱うコネクタの共有を禁止するなど、組織のデータ取り扱いポリシーを Quick 上で直接強制
✓段階的な統制の導入: 全面禁止ではなくコネクタ単位での制限が可能なため、業務影響を最小限に抑えながらガバナンスを強化
🔧 技術面
✓きめ細かな権限設計: 作成・更新・共有の 3 つの権限を独立して設定でき、一括制限よりも精緻なポリシーを実装可能
✓自動化への対応: API / AWS CLI でプロファイルを管理でき、ガバナンス設定のコード化や CI/CD パイプラインへの組み込みが可能
✓柔軟な適用範囲: アカウント、ロール、ユーザーの各レベルで割り当てられ、優先順位に基づいて最適な粒度で統制を適用

⚠️ デメリット・制約事項

🚧 制限事項
✗Enterprise edition でのみ利用可能
✗カスタム権限はスコープダウンポリシーであり、ユーザーのデフォルトロールを超える権限の付与は不可 (例: Reader に編集権限を与えることは不可)
✗親ケイパビリティを DENY にした状態で子機能を ALLOW に設定してもエラーにならず、子機能は制限されたままとなるため、適用後にコンソールで結果の確認が必要
🤔 考慮すべき点
⚠️権限はユーザー → ロール → アカウントの順で評価され、最初に一致したレベルが優先される。ユーザーレベルで許可プロファイルを割り当てると、アカウントレベルの Deny by Default プロファイルが適用されないため、割り当てレベルの設計に注意が必要
⚠️共有を禁止しても、すでに共有済みのデータソースには引き続きアクセス可能なケースがあるため、既存の共有状態の棚卸しも併せて実施することが望ましい

🎯 ユースケース

📊 ユースケース 1: 承認済みデータウェアハウスへの接続のみを許可

シナリオ: 全社のデータ分析基盤として Amazon Redshift を標準化しており、ユーザーが個人のファイルを直接アップロードして分析することを禁止したい。

JSON capabilities 設定例 
{
  "CreateFileDataSource": "DENY",
  "UpdateFileDataSource": "DENY",
  "ShareFileDataSource": "DENY"
}

効果: ユーザーは承認済みの Redshift データソースを自由に作成して分析できる一方、統制外のファイルアップロードによるデータ持ち込みを防止できる。

❄️ ユースケース 2: 特定コネクタのデータソース共有を禁止

シナリオ: Snowflake 上に機密性の高いデータが存在し、データソースの作成は特定チームに許可するが、他ユーザーへの共有による意図しないアクセス拡大を防ぎたい。

Bash 共有のみ禁止するプロファイル 
aws quicksight create-custom-permissions \
  --aws-account-id 123456789012 \
  --custom-permissions-name NoSnowflakeShare \
  --capabilities '{"ShareSnowflakeDataSource": "DENY"}'

効果: 分析チームは Snowflake データソースを作成・更新できるが、共有操作のみがブロックされ、アクセス範囲の無秩序な拡大を防止できる。

👥 ユースケース 3: ロール単位での段階的なガバナンス適用

シナリオ: Author ロール全体には厳格な制限を適用しつつ、データエンジニアリングチームの特定ユーザーにはより広い権限を許可したい。

実装例:

  • 1. Author ロールに制限プロファイル (複数コネクタの作成を DENY) を割り当て
  • 2. データエンジニアの個別ユーザーに許可プロファイルを割り当て
  • 3. ユーザーレベル → ロールレベルの優先順位により、個別ユーザーには広い権限が適用される

効果: 権限評価の優先順位を活用して、組織全体の統制と特定チームの柔軟性を両立できる。

🔗 関連サービス・機能

  • Amazon QuickSight API: カスタム権限プロファイルの管理には quicksight 名前空間の API (CreateCustomPermissions など) を使用する
  • Amazon Redshift / Snowflake / Google BigQuery などのデータソース: コネクタ単位の制限対象となる構造化データソース
  • AWS IAM: カスタム権限の管理操作自体は IAM 権限 (quicksight:CreateCustomPermissions など) で制御される
  • AWS Quick ナレッジベースコネクタ / アクションコネクタ: データソースと同様に、ナレッジベースやアクションについてもコネクタ単位の制限が可能

📌 まとめ

AWS Quick のカスタム権限がコネクタ単位の構造化データソース制限に対応したことで、組織はセルフサービス分析の利便性を維持しながら、データガバナンス要件をより精緻に強制できるようになりました。

✓ Enterprise edition を利用している組織は、現在のデータソース利用状況を棚卸しし、承認済みコネクタのみを許可するプロファイル設計から導入を検討することを推奨します。
