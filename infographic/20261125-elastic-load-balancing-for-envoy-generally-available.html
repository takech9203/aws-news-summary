⚖️ ELB for Envoy の一般提供開始

オープンソース Envoy のフル機能を AWS マネージドインフラストラクチャで
📅 リリース日: 2026 年 11 月 25 日

📋 概要

ELB for Envoy は、Elastic Load Balancing ファミリーの新しいロードバランサータイプです。オープンソースの Envoy プロキシを AWS 管理のインフラストラクチャ上で実行するマネージドサービスで、ユーザーは Envoy のブートストラップ設定 (YAML) を提供するだけで、プロビジョニング、スケーリング、OS パッチ適用、複数 AZ にまたがる高可用性の維持を AWS に任せられます。

各プロキシは AWS Nitro System によるハードウェア分離を備えた専用 EC2 インスタンス上で動作し、万一のゼロデイ脆弱性の影響も自身のロードバランサー内に封じ込められます。既存の Envoy 設定、拡張機能、制御プレーンを変更なしでそのまま持ち込める点が大きな特徴です。

🔄 Before / After

❌ アップデート前の課題
  • Envoy のバージョンアップグレード、CVE 対応、OS パッチ適用をプラットフォームチームが自ら実施する必要があった
  • 複数 AZ にまたがるキャパシティ管理とスケーリングを自前で設計・運用する必要があった
  • ALB や NLB では Envoy のフル機能セット (カスタムフィルター、xDS による動的設定など) を利用できず、高度なトラフィック制御には自己管理の Envoy フリートが必要だった
✅ アップデート後の改善
  • 既存の Envoy 設定、拡張機能、制御プレーンを変更なしで AWS 管理のインフラストラクチャに移行可能に
  • CVE 監視、Envoy バイナリ更新、OS パッチ適用が自動化され、運用負荷を大幅に軽減
  • ACM による TLS 終端、AWS WAF によるトラフィック検査、CloudWatch によるモニタリングを最小限の設定で利用可能に
  • Envoy Gateway 利用の Kubernetes クラスターで、Gateway API リソースを変更せずにデータプレーンのみ AWS 管理へ移行可能に

ELB for Envoy プロキシはユーザーの VPC 内の専用 EC2 インスタンス上で動作し、セキュリティグループで保護されます。設定は静的なブートストラップ YAML のほか、既存の制御プレーンや Envoy Gateway から xDS 経由で動的に配信でき、スケーリングやパッチ適用は AWS が担当します。

⭐ 主要機能

🔒 1. 専用インフラストラクチャによる分離
  • 各プロキシは AWS Nitro System のハードウェア分離を備えた専用 EC2 インスタンス上で実行
  • シングルテナントアーキテクチャにより、ゼロデイ脆弱性の影響を自身のロードバランサー内に封じ込め
  • プロキシはユーザーの VPC 内で動作し、セキュリティグループ、IAM 権限、VPC 暗号化によるネットワーク制御を維持
🩹 2. 自動メンテナンスと拡張バージョンサポート
  • AWS が CVE を監視し、Envoy バイナリと OS のパッチを自動適用
  • 各 Envoy バージョンはアップストリームの 1 年に対して 2 年間サポート
  • アップグレード時にトラフィックの劣化を検知すると自動ロールバック
  • バージョンのサポート終了が近づくと AWS Health Dashboard で通知
📦 3. 既存 Envoy 資産の持ち込み
  • ブートストラップ設定ファイル (YAML) と補助ファイルをまとめた設定アーカイブ (ZIP) を提供して利用
  • 既存の制御プレーンから xDS プロトコル経由で動的に設定を配信可能
  • Lua スクリプト、WebAssembly (Wasm) フィルター、外部処理 (External Processing) をサポート
🧩 4. AWS サービスとの統合
  • ACM の証明書を関連付けて TLS を終端
  • AWS WAF の Web ACL を関連付けてトラフィックを検査
  • メトリクスは CloudWatch へ、Envoy ログは CloudWatch Logs へ発行
  • 設定はデフォルトで AWS 所有キーで暗号化、KMS カスタマーマネージドキーも選択可能
☸️ 5. Kubernetes との連携
  • ELB for Envoy リモートインフラストラクチャプロバイダー (GitHub で公開) を Envoy Gateway と併用可能
  • プロバイダーは Envoy Gateway の Pod 内でサイドカーとして動作し、ELBProxyConfiguration が付与された Gateway ごとにプロキシをプロビジョニング
  • 制御プレーンはクラスター内に残し、データプレーンのみ AWS 管理へ移行。Gateway API リソースの変更は不要

ステップ 1: Envoy 設定を準備する

YAML bootstrap.yaml の例 (既存の Envoy 設定をそのまま利用可能) 
static_resources:
  listeners:
    - name: http_listener
      # リスナー定義
  clusters:
    - name: backend
      # クラスター定義

既存の Envoy ブートストラップ設定を用意します。補助ファイルがある場合は ZIP 形式の設定アーカイブにまとめます。動的設定を使う場合は、自身の制御プレーンから xDS で配信するように構成します。

ステップ 2: プロキシを作成する

Bash AWS CLI でのプロキシ作成 
# 利用可能な Envoy バージョンを確認
aws elb-proxy list-proxy-versions

# プロキシを作成 (引数の詳細は API リファレンスを参照)
aws elb-proxy create-proxy ...

AWS CLI の aws elb-proxy コマンド、または Amazon EC2 コンソールの [プロキシ] から作成します。作成後、プロキシには VPC 内の IP アドレスを指す一意の DNS 名が付与されます。

ステップ 3: ACM 証明書と AWS WAF を関連付ける

Bash ACM 証明書の関連付け 
# ACM 証明書の関連付け
aws elb-proxy associate-certificate ...

TLS を終端する場合は ACM 証明書をプロキシに関連付け、リスナー設定から参照します。トラフィック検査が必要な場合は AWS WAF の Web ACL を関連付けます。

ステップ 4: Kubernetes で利用する場合

Envoy Gateway を利用しているクラスターでは、ELB for Envoy リモートインフラストラクチャプロバイダーを Envoy Gateway の Pod にサイドカーとしてインストールし、対象の Gateway に ELBProxyConfiguration を付与します。プロバイダーがプロキシをプロビジョニングし、プロキシの DNS 名を Gateway のアドレスとして公開します。

💡 メリット・デメリット

📈 ビジネス面のメリット

✓運用コストの削減: Envoy のアップグレード、CVE 対応、パッチ適用、キャパシティ管理を AWS に委任し、プラットフォームチームの運用負荷を大幅に削減
✓移行リスクの低減: 既存の Envoy 設定、拡張機能、制御プレーンを変更なしで持ち込めるため、アプリケーションやルーティングロジックの書き換えが不要
✓長期サポート: 各 Envoy バージョンがアップストリームの 2 倍の 2 年間サポートされ、アップグレード計画に余裕が生まれる

⚙️ 技術面のメリット

✓セキュリティの強化: Nitro System によるハードウェア分離とシングルテナントアーキテクチャで、脆弱性の影響範囲を限定
✓プログラマブルなデータプレーン: WebAssembly、Lua、外部処理により、カスタム認証やリクエスト変換などの高度なロジックを実装可能
✓AWS ネイティブ統合: ACM、AWS WAF、CloudWatch、KMS、セキュリティグループと最小限の設定で統合
✓安全なアップグレード: トラフィック劣化を検知すると自動ロールバックするため、バージョン更新時のリスクが低い

🚧 制限事項

✗Lua スクリプトは制限された標準ライブラリセットで実行される
✗WebAssembly は V8 ランタイムのみをサポート
✗異なるアベイラビリティゾーンにある 2 つ以上のサブネットが必要
✗提供リージョンは 14 リージョンに限定 (2026 年 11 月時点)

⚠️ 考慮すべき点

⚠標準的な負荷分散の用途には、引き続き ALB や NLB が推奨される。ELB for Envoy は Envoy のフル機能セットとプログラマブルなデータプレーンが必要な場合の選択肢
⚠Envoy 設定の正しさの確認、デバッグ、パフォーマンスチューニングはユーザーの責任範囲
⚠独自のフィルターや拡張機能の内容によって vCPU やメモリの使用量が増え、課金対象の LCU ディメンションが変動する可能性がある
⚠Kubernetes 向けリモートインフラストラクチャプロバイダーの API は v1alpha1 であり、早期段階にある

☸️ ユースケース 1: 自己管理 Envoy フリートからの移行

シナリオ: 100 台を超える自己管理 Envoy プロキシを Kubernetes の Ingress として運用しており、アップグレードとパッチ適用の負荷が課題になっている。

Text実装例
1. Envoy Gateway を利用中のクラスターに ELB for Envoy
   リモートインフラストラクチャプロバイダーをインストール
2. 対象の Gateway に ELBProxyConfiguration を付与
3. Gateway API リソースは変更せず、データプレーンのみ
   AWS 管理のプロキシへ移行
✅ 効果: ルーティングロジックの制御をクラスター内に残したまま、データプレーンの運用 (スケーリング、パッチ、高可用性) を AWS に委任できる。
🔑 ユースケース 2: カスタム認証とリクエスト変換

シナリオ: 独自の認証プロトコルやリクエスト変換ロジックが必要で、ALB の標準機能では要件を満たせない。

Text実装例
1. Rust または Go で WebAssembly フィルターを実装、
   もしくは Lua スクリプトや外部処理を利用
2. Envoy ブートストラップ設定にフィルターを組み込み
3. 設定アーカイブとともにプロキシを作成
✅ 効果: マネージドサービスの運用性を維持しながら、Envoy のプログラマブルなデータプレーンで独自のトラフィック処理を実現できる。
🎛️ ユースケース 3: 独自制御プレーンによる動的トラフィック制御

シナリオ: サービスメッシュや独自の制御プレーンから xDS でルーティング設定を動的に配信しており、データプレーンの運用だけを手放したい。

Text実装例
1. ブートストラップ設定に既存の制御プレーンへの
   xDS 接続を定義
2. ELB for Envoy プロキシを作成
3. 制御プレーンからルートやクラスターを動的に配信
✅ 効果: 制御プレーンへの投資を活かしたまま、プロキシ本体のスケーリングとメンテナンスを AWS に任せられる。

🔗 関連サービス・機能

  • Application Load Balancer / Network Load Balancer: 標準的な負荷分散の用途にはこれらが推奨される。ELB for Envoy は同じ Elastic Load Balancing ファミリーの新しいタイプとして位置づけられる
  • AWS Certificate Manager: プロキシに証明書を関連付けて TLS を終端できる
  • AWS WAF: Web ACL をプロキシに関連付けてトラフィックを検査できる (ELB PROXY リソースタイプが追加)
  • Amazon CloudWatch / CloudWatch Logs: プロキシのメトリクスと Envoy ログの収集先
  • AWS KMS: プロキシ設定の暗号化にカスタマーマネージドキーを利用できる
  • Envoy Gateway: Kubernetes の Gateway API 実装。リモートインフラストラクチャプロバイダー経由で ELB for Envoy と連携できる

📝 まとめ

ELB for Envoy は、オープンソース Envoy のフル機能とプログラマブルなデータプレーンを、AWS のマネージドインフラストラクチャ上で利用できる新しいロードバランサータイプです。

自己管理の Envoy フリートを運用しているチームにとって、設定を変更せずに運用負荷を大幅に削減できる有力な移行先となります。東京リージョンでも利用可能なため、まずは開発環境で既存の Envoy 設定を持ち込み、Envoy Gateway との連携や ACM、AWS WAF との統合を検証することを推奨します。
