保存済みクエリのパラメータサポート

クエリテンプレートにパラメータを定義し、実行時に値を渡して再利用可能に

📅 2026 年 4 月 13 日

📋 概要

Amazon CloudWatch Logs Insights の保存済みクエリがパラメータをサポートするようになりました。プレースホルダーを含む再利用可能なクエリテンプレートを作成し、実行時に値を渡すことが可能になります。

1 つのクエリに最大 20 個のパラメータを定義でき、各パラメータにはオプションでデフォルト値を設定できます。$QueryName() 構文で呼び出し、共通のクエリテンプレートを異なる条件で繰り返し実行できます。

⚡ 主要機能

📝 パラメータ付き保存済みクエリ

  • 保存済みクエリにプレースホルダーとしてパラメータを定義可能
  • 1 つのクエリあたり最大 20 個のパラメータをサポート
  • ログレベル、サービス名、時間間隔など任意の値をパラメータ化できる

📋 デフォルト値のサポート

  • 各パラメータにオプションでデフォルト値を設定可能
  • デフォルト値が設定されたパラメータは呼び出し時に省略可能
  • よく使う値をデフォルトに設定し、必要な場合のみ上書きする運用が可能

💲 $ プレフィックスによるクエリ呼び出し構文

  • クエリ名の前に $ を付けて実行する直感的な構文を採用
  • $QueryName(param1="value1", param2="value2") の形式で呼び出し
  • 関数呼び出しに似た構文で、開発者にとって馴染みやすい

クエリテンプレートの構文例

Logs Insights ErrorsByService テンプレート 
# パラメータ付き保存済みクエリの定義例
# クエリ名: ErrorsByService
# パラメータ: logLevel (デフォルト: "ERROR"), serviceName (デフォルトなし)

fields @timestamp, @message, @logStream
| filter @message like /(?i){logLevel}/
| filter @logStream like /(?i){serviceName}/
| sort @timestamp desc
| limit 100

🚀 設定方法

前提条件

  • ✅ AWS アカウントで CloudWatch Logs Insights が利用可能であること
  • ✅ 保存済みクエリの作成・実行に必要な IAM 権限が付与されていること
  • ✅ 対象のロググループにログデータが存在すること
1 パラメータ付き保存済みクエリの作成
Bash AWS CLI でクエリを作成 
# パラメータ付き保存済みクエリを作成
aws logs put-query-definition \
  --name "ErrorsByService" \
  --log-group-names "/aws/lambda/my-service" "/aws/ecs/my-cluster" \
  --query-string 'fields @timestamp, @message, @logStream
| filter @message like /(?i){logLevel}/
| filter @logStream like /(?i){serviceName}/
| sort @timestamp desc
| limit 100'

{logLevel} と {serviceName} がパラメータとして定義されます。

2 パラメータ付きクエリの実行

CloudWatch コンソールのクエリエディタで、$ プレフィックスを使用してクエリを呼び出します。

Logs Insights クエリ実行例 
$ErrorsByService(logLevel="ERROR", serviceName="OrderEntry")
3 異なるパラメータでの再実行
Logs Insights パラメータ変更例 
# WARN レベルのログを別のサービスで検索
$ErrorsByService(logLevel="WARN", serviceName="PaymentService")

# デフォルト値がある場合はパラメータを省略可能
$ErrorsByService(serviceName="UserAuth")

必要な IAM 権限

JSON IAM ポリシー例 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "logs:PutQueryDefinition",
        "logs:DescribeQueryDefinitions",
        "logs:DeleteQueryDefinition",
        "logs:StartQuery",
        "logs:GetQueryResults"
      ],
      "Resource": "*"
    }
  ]
}

logs:PutQueryDefinition でクエリの作成・更新、logs:StartQuery で実行を許可しています。

⚠️ デメリット・制約事項

制限事項

  • ⚠️ 1 つのクエリあたりのパラメータ数は最大 20 個に制限
  • ⚠️ パラメータ値は文字列として渡されるため、複雑なデータ型の直接的な指定には非対応
  • ⚠️ 既存の保存済みクエリをパラメータ付きに変換するには、クエリの再定義が必要

考慮すべき点

  • 💡 パラメータ名の命名規則をチーム内で統一し、可読性と再利用性を維持することを推奨
  • 💡 頻繁に使用する値をデフォルトに設定することで、日常的な利用の効率が向上
  • 💡 パラメータ値はクエリ結果に直接影響するため、値の妥当性をユーザー側で確認する必要あり

🎯 ユースケース

🔍 ユースケース 1: DevOps チームによるマルチサービス障害調査

マイクロサービスアーキテクチャを運用する DevOps チームが、複数のサービスにまたがる障害調査を効率的に実施。サービスごとに個別のクエリを作成する代わりに、パラメータ付きテンプレートで統一的な調査を行う。

Logs Insights ServiceHealthCheck テンプレート 
# 保存済みクエリテンプレート: ServiceHealthCheck
fields @timestamp, @message, @logStream
| filter @message like /(?i){logLevel}/
| filter @logStream like /(?i){serviceName}/
| stats count(*) as errorCount by bin(30m)
| sort errorCount desc

# 実行例: 各サービスの ERROR を順番に確認
$ServiceHealthCheck(logLevel="ERROR", serviceName="OrderService")
$ServiceHealthCheck(logLevel="ERROR", serviceName="PaymentService")
$ServiceHealthCheck(logLevel="ERROR", serviceName="InventoryService")
1 つのテンプレートで全サービスの障害調査が可能になり、調査時間を短縮。クエリの構文が統一されるため、結果の比較も容易。

🔒 ユースケース 2: セキュリティチームによるログレベル別分析

セキュリティチームが、異なるログレベルやイベントタイプごとにログを分析。パラメータ付きクエリにより、分析条件を柔軟に切り替えながら調査を進める。

Logs Insights SecurityEventAnalysis テンプレート 
# 保存済みクエリテンプレート: SecurityEventAnalysis
fields @timestamp, @message, sourceIPAddress, eventName
| filter @message like /(?i){eventType}/
| filter sourceIPAddress like "{ipRange}"
| sort @timestamp desc
| limit {resultLimit}

# 実行例: 不正アクセスの疑いがある IP 帯域を調査
$SecurityEventAnalysis(eventType="UnauthorizedAccess", ipRange="192.168", resultLimit="500")
$SecurityEventAnalysis(eventType="AccessDenied", ipRange="10.0", resultLimit="200")
イベントタイプや IP レンジの条件を変更するだけで多角的な分析が可能になり、セキュリティインシデントの早期発見と対応が効率化。

📈 ユースケース 3: 開発チームによる環境別パフォーマンス分析

開発チームが本番環境、ステージング環境、開発環境のパフォーマンスログを比較分析。環境ごとに異なるロググループを持つが、分析クエリのロジックは共通。

Logs Insights LatencyAnalysis テンプレート 
# 保存済みクエリテンプレート: LatencyAnalysis
fields @timestamp, @message, @duration
| filter @message like /(?i){endpoint}/
| filter @duration > {thresholdMs}
| stats avg(@duration) as avgLatency, max(@duration) as maxLatency,
        count(*) as requestCount by bin(5m)
| sort avgLatency desc

# 実行例: 各環境の API レイテンシーを比較
$LatencyAnalysis(endpoint="/api/orders", thresholdMs="1000")
$LatencyAnalysis(endpoint="/api/payments", thresholdMs="500")
同一のクエリテンプレートで環境間のパフォーマンス比較が容易になり、環境差異に起因する問題の特定が迅速化。
