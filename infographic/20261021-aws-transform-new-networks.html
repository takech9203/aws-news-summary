🔄 AWS Transform
新規ネットワーク構築とセキュリティグループのモダナイズ

AWS Transform 📅 2026 年 10 月 21 日 NEW
新規 AWS ネットワークの設計・構築、および既存 VPC へのセキュリティポスチャ適用

📌 概要

AWS Transform for migrations に、ネットワークを AWS に移行するための 2 つの新しいアプローチが追加されました。従来の「既存ネットワークの移行とモダナイズ」に加えて、新規 AWS ネットワークをゼロから設計・構築するアプローチと、オンプレミスのアクセスルールをセキュリティグループに変換して既存 VPC に適用するアプローチが利用可能になりました。

変換の過程で古くなったルール (stale rules) を検出して最適化を推奨し、生成されたセキュリティグループはネットワークスタックの再デプロイなしで既存の VPC にそのままデプロイできます。VMware 環境などからの大規模移行を計画している組織や、ランディングゾーン構築済みでセキュリティルールのみを移行したい組織が主な対象です。

❌ Before: アップデート前の課題

  • 既存のソースネットワーク構成を変換する方式のみで、ソース構成ファイルを前提としないネットワーク設計はできなかった
  • 複雑化・陳腐化したネットワーク定義をそのまま持ち込むか、AWS ネットワークを手動で設計する必要があった
  • VPC 構築済み環境では、ファイアウォールルールをセキュリティグループとして手動で再作成する必要があり、時間と設定ミスのリスクがあった

✅ After: アップデート後の改善

  • ソース構成ファイルなしで、AWS ベストプラクティスに沿った新規ネットワークを対話形式で設計・構築できる
  • 古いルールの検出と最適化の推奨により、セキュリティポスチャをモダナイズできる
  • 既存 VPC に対して、ネットワークスタックを再デプロイすることなくセキュリティグループのみを追加デプロイできる

AWS Transform が提供する 3 つのネットワーク移行アプローチの全体像。今回のアップデートで、新規ネットワーク設計 (中央) と既存 VPC へのセキュリティポスチャ適用 (右) が追加されました。

⚡ 主要機能

🆕 1. 新規 AWS ネットワークの設計 (Design a new AWS network)

  • ソース構成ファイルを使わず、移行するアプリケーションの情報からネットワークを設計
  • AI エージェントとの対話形式で、トポロジー選択、ネットワーク定義、レビュー、タグ設定、デプロイまでをガイド
  • アプリケーション名、環境 (本番・ステージング・開発など)、サーバー台数を伝えると、環境ごとに VPC を自動設計
  • CIDR 範囲は指定可能で、未指定の場合は重複しない範囲を自動割り当て
  • VPC サイズは Small (最大 250 アドレス)、Medium (最大 1,000)、Large (最大 4,000)、XL (最大 16,000) から選択
  • ビジュアルとチャットでレビューし、自然言語の Direct Edits で変更可能。変更は検証され、競合が事前に検出される

🛡️ 2. 既存 VPC へのセキュリティポスチャ適用 (Apply security posture to existing VPCs)

  • ソースのファイアウォールルールからセキュリティグループを生成し、既存 VPC に関連付け
  • 対応ソースファイル: VMware NSX、Cisco ACI、Palo Alto Networks、Fortinet FortiGate、modelizeIT、AWS Transform discovery tool。その他の形式は自動変換を試行
  • 対象 VPC はタグ (CreatedFor: AWSTransform など) で指定し、タグ付けした VPC のみが移行スコープに含まれる
  • ソースサブネットと既存 VPC を CIDR でマッチングするカバレッジ分析を実行。Re-IP の場合は CIDR マッピングを対話形式で指定可能
  • VPC トポロジー (Isolated / Connected) に応じて、CIDR ベースまたはセキュリティグループ参照ベースのルールを生成
  • セキュリティグループのみをデプロイするため、既存のネットワークスタックの再デプロイは不要

🔍 3. 古いルールの検出とモダナイズ

  • アクセスルールの変換時に、古くなったルール (stale rules) を検出し、最適化を推奨
  • CIDR マッピング指定時は、影響を受けるルールを複製し、オンプレミス側を指すルールには説明に [ONPREM] プレフィックスを付与。移行中はオンプレミスと AWS の双方のワークロードと通信可能
  • カットオーバー完了後に [ONPREM] プレフィックス付きルールを削除することで、クリーンなセキュリティポスチャに移行

🔧 技術仕様

🌐 新規ネットワーク設計のトポロジー

トポロジー説明
Hub and Spokeアプリケーション間で通信が必要な場合に選択。AWS Transit Gateway が VPC を接続し、VPC 間トラフィックを中央ハブ経由でルーティング
Isolated VPCsアプリケーションが独立して動作し、相互接続が不要な場合に選択

🔐 セキュリティポスチャ適用のルール生成方式

VPC トポロジールール生成方式
IsolatedCIDR 範囲ベースのルールを生成
Connectedセキュリティグループ参照ベースのルールを生成 (Transit Gateway 利用時は SecurityGroupReferencingSupport の有効化が必要)

🚀 デプロイ方式

方式詳細
AWS Transform マネージドデプロイ承認後、AWS Transform が代理でデプロイを実行
セルフデプロイIaC として出力し、自身でデプロイ。出力形式は CloudFormation、AWS CDK、HashiCorp Terraform、Landing Zone Accelerator (LZA) に対応

⚙️ 設定方法

📋 前提条件

✓AWS Transform のワークスペースが設定済みであること
✓マルチアカウント構成の場合、ネットワーク移行開始前にクロスアカウントアクセスの設定が完了していること
✓セキュリティポスチャ適用の場合、ファイアウォールルールを含むソースネットワークファイルが必要 (RVTools はファイアウォールルールを含まないため非対応)

🛠️ 手順 (既存 VPC へのセキュリティポスチャ適用の例)

1

ソースネットワークファイルのアップロード

User Uploads からファイル名を指定するか、チャット内でファイルを直接アップロード。VMware NSX、Cisco ACI、Palo Alto Networks、Fortinet FortiGate などのエクスポートファイルに対応。

2

既存 VPC のタグ付け

タグ付けページで対象 VPC を選択。選択した VPC には以下のタグが適用され、移行スコープに含まれます。タグ付けした VPC のみが対象となり、それ以外のリソースは変更されません。

Text VPC に適用されるタグ 
Key: CreatedFor   Value: AWSTransform
Key: ATWorkspace  Value: {workspace-id}
3

ソースサブネットと既存 VPC のマッチング

カバレッジ分析の結果を確認し、未カバーのサブネットがあれば CIDR マッピングをチャットで指定。可能な限り広い範囲 (/16 など) でマッピングすると一括でカバーされます。マッピングは同じプレフィックス長同士である必要があります。

Text CIDR マッピングの指定例 
Map 10.68.0.0/16 to 172.31.0.0/16
4

トポロジー指定、レビュー、デプロイ

既存 VPC が Isolated か Connected かを指定し、生成されたセキュリティグループを Human-in-the-loop レビューで確認。確認後、マネージドデプロイまたはセルフデプロイ (CloudFormation / CDK / Terraform / LZA) でデプロイ。カットオーバー完了後は [ONPREM] プレフィックス付きルールを削除します。

💡 メリット・制約事項

📈 ビジネス面のメリット

✓移行期間の短縮: 手動設計と比較して、大幅に短い時間で本番利用可能なネットワーク基盤を準備
✓技術的負債の解消: レガシーなネットワーク定義を持ち込まず、クリーンな状態で移行を開始
✓専門知識への依存低減: 深いネットワーク専門知識がなくても、ベストプラクティスに沿った設計が可能

🔬 技術面のメリット

✓セキュリティポスチャのモダナイズ: 古いルールの検出と最適化の推奨で、不要なルールを引き継がない
✓既存環境への非破壊的な適用: セキュリティグループのみを追加デプロイ
✓IaC 出力による統制: CloudFormation / CDK / Terraform / LZA で既存の変更管理プロセスに組み込める
✓移行期間中の接続性確保: [ONPREM] 複製ルールで移行済み・未移行ワークロード双方と通信を維持

⚠️ 制限事項

✗セキュリティポスチャ適用フローでは RVTools ファイルは利用不可 (ファイアウォールルールを含まないため)
✗CIDR マッピングは同じプレフィックス長同士のみ対応 (/24 から /20 のような異なる長さは不可)
✗マッピングされた CIDR 範囲外のルール CIDR は移行されない
✗セキュリティポスチャ適用フローでは Reachability Analyzer は実行されず、デプロイ済みリソースの自動ロールバックもない
✗Connected トポロジー選択時、実際に VPC 間の接続性がないとセキュリティグループ参照ルールのデプロイが失敗する

📝 考慮すべき点

⚠Transit Gateway 経由のセキュリティグループ参照には、Transit Gateway と各 VPC アタッチメントで SecurityGroupReferencingSupport の有効化が必要
⚠マルチアカウント移行では、各ターゲットアカウントにサインインして VPC のタグ付けを個別に行う必要がある
⚠カットオーバー後の [ONPREM] ルール削除は手動のクリーンアップ作業として計画に含める

🎯 ユースケース

1️⃣ クリーンスタートでの VMware 移行

シナリオ: 長年運用してきた VMware 環境のネットワーク定義が複雑化しており、移行を機に AWS ベストプラクティスに沿ったネットワークを再設計したい。

Text 実装例 
1. AWS Transform で「Design a new AWS network」を選択
2. アプリケーション名、環境、サーバー台数をチャットで入力
3. Hub and Spoke トポロジーを選択し、Transit Gateway 経由の接続構成を生成
4. ビジュアルレビューで CIDR や構成を確認し、マネージドデプロイで構築
✅ 効果: レガシー設計を持ち込まず、ベストプラクティスに沿ったネットワークを短時間で構築し、技術的負債をリセットできる。

2️⃣ ランディングゾーン構築済み環境へのファイアウォールルール移行

シナリオ: Landing Zone Accelerator で VPC やサブネットは構築済みだが、オンプレミスの Palo Alto Networks ファイアウォールのルールをセキュリティグループとして再現する作業が残っている。

Text 実装例 
1. 「Apply security posture to existing VPCs」を選択
2. Palo Alto Networks のエクスポートファイルをアップロード
3. 対象 VPC にタグを付与し、CIDR カバレッジ分析を確認
4. 生成されたセキュリティグループをレビューし、LZA 形式で出力して既存パイプラインでデプロイ
✅ 効果: 手動でのルール再作成と比較して時間を短縮し、変換時の古いルール検出により精度と一貫性も向上する。

3️⃣ Re-IP を伴う段階的移行での接続性維持

シナリオ: 移行に合わせてサーバーの IP アドレス体系を変更 (Re-IP) するが、移行期間中はオンプレミスに残るワークロードとの通信も維持したい。

Text 実装例 
1. セキュリティポスチャ適用フローで CIDR マッピングを指定
   例: Map 10.68.0.0/16 to 172.31.0.0/16
2. AWS Transform が各ルールを複製し、[ONPREM] プレフィックス付きルールで
   オンプレミス側アドレス空間への通信も許可
3. カットオーバー完了後、[ONPREM] ルールを削除
✅ 効果: 移行済み・未移行ワークロードの双方と通信を維持しながら段階的に移行し、完了後はクリーンなルールセットに収束できる。

🌍 利用可能リージョン

AWS のすべての商用リージョンおよび AWS GovCloud (US) リージョンへの移行がサポートされています。サポート対象リージョンの一覧は AWS Transform ユーザーガイドを参照してください。

📝 まとめ

AWS Transform for migrations に、新規 AWS ネットワークのゼロからの設計・構築と、既存 VPC へのセキュリティポスチャ適用という 2 つのアプローチが追加されました。レガシーなネットワーク定義を持ち込まないクリーンスタートと、古いルールの検出・最適化によるセキュリティグループのモダナイズが可能になり、移行の初期段階におけるネットワーク設計の負担が大きく軽減されます。

VMware 環境などからの移行を計画している場合は、既存ネットワークの移行・新規設計・セキュリティポスチャ適用のどのアプローチが自社の状況に適しているかを検討することを推奨します。
