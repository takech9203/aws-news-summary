Amazon ECS Action Logs

デプロイとデーモン操作の "見えなかった中間ステップ" を可視化する新しいオブザーバビリティ機能
リリース日
2026-07-21

📋 概要

Amazon ECS が サービスデプロイメントと Managed Daemon の更新中に、お客様に代わって実行するアクションをタイムスタンプ付きで詳細に記録。各ログにはイベント名・ログレベル (INFO / WARN / ERROR)・リソース ARN・ステータス理由が含まれ、MTTR (平均解決時間) の短縮を支援します。

従来はサーバー側で処理される操作が多く、お客様はリソースの開始状態と終了状態しか観察できませんでした。Action Logs は、コンテナイメージのダウンロード、ロードバランサーへの登録、セキュリティグループの設定といった中間ステップを可視化し、AWS Support に問い合わせることなく自己解決を可能にします。クラスターレベルでオプトインし、配信先は CloudWatch Logs / S3 / Kinesis Data Firehose から選択できます。

🔄 アップデート前後の比較

😰 Before（課題）

  • 中間ステップが見えず、開始状態と終了状態しか観察できなかった
  • 原因究明のために AWS Support への問い合わせが必要になる場合があった
  • 失敗タスクのメタデータが標準で 1 時間しか保持されず、事後の詳細分析が困難だった

😊 After（改善）

  • 状態遷移の間に ECS が実行するアクション（プロビジョニング、ネットワーク設定、リソース登録）を可視化
  • AWS Support なしでデプロイ失敗やインフラ問題を自己解決
  • 失敗メタデータを標準の 1 時間を超えて保持し、自分のペースで詳細確認

🏗️ アーキテクチャ図

デプロイとデーモン更新中のアクションを CloudWatch Ingestion Hub 経由で構造化 JSON ログとして生成し、選択した配信先へ fire-and-forget 方式で配信。CloudWatch Logs のログには Amazon Q がアクセスし、デプロイ問題を自動検出します。

⭐ 主要機能

🔍 サービスアクションの可視化

  • 状態遷移の間に ECS が実行する、これまで見えなかったアクションを表示
  • インフラのプロビジョニング、ネットワーク設定、リソース登録を含む
  • コンテナイメージのダウンロード、ロードバランサーへの登録、セキュリティグループの設定などを記録

📝 記録対象の操作

  • サービスデプロイメント: 状態遷移、ロールバック、ライフサイクルフックの実行
  • Managed Daemon のライフサイクル: 作成、更新、削除、インスタンスのドレイン操作

🤖 Amazon Q との統合

  • 提供開始時点で ECS コンソールの Amazon Q が Action Logs と統合
  • サーキットブレーカーによるロールバックや不安定なサービスリビジョンなどを自動検出
  • コンソール内で根本原因分析、リソースレベルの比較、修復手順を提供

🕐 拡張された失敗メタデータ

  • 失敗タスクのメタデータを標準の 1 時間の保持期間を超えて保持
  • 詳細な失敗情報を任意のタイミングで確認可能

🛠️ 技術仕様

📐 ログスキーマ

フィールド詳細
timestampイベント発生時刻 (Unix ミリ秒)
logLevel重要度レベル: INFO / WARN / ERROR
accountAWS アカウント ID
regionイベントが発生した AWS リージョン
resourceArnオプトインスコープを表すクラスター ARN
actionSourceIdサブリソース識別子 (サービス ARN やデーモン ARN など)
eventNameアクション識別子 (例: DAEMON_DEPLOYMENT_IN_PROGRESS)
detail追加コンテキストを含むイベント固有の JSON ペイロード

🚚 配信先の構成

配信先詳細
CloudWatch Logsロググループ /aws/vendedlogs/ecs/action-logs/{resourceId} に保存。サブリソースごとに個別のログストリームを作成
Amazon S3アカウント、リージョン、5 分間の時間ウィンドウでパーティション分割。gzip で圧縮
Amazon Data Firehose改行区切りの JSON レコードとしてニアリアルタイムで配信

⚡ 配信方式: fire-and-forget

Action Logs は fire-and-forget 方式で発行され、ログ発行が ECS のリソース操作をブロック・劣化させることはありません。一時的な配信障害が発生しても、ECS はワークロード処理を中断せず継続します。

🔐 必要な IAM 権限

JSONIAM ポリシー
{
    "Effect": "Allow",
    "Action": [
        "logs:PutDeliverySource",
        "logs:PutDeliveryDestination",
        "logs:CreateDelivery",
        "logs:GetDelivery",
        "ecs:AllowVendedLogDeliveryForResource"
    ],
    "Resource": "*"
}

⚙️ 設定方法

✅ 前提条件

✓IAM アイデンティティに Action Logs 有効化に必要な権限があること
✓配信先のロググループに delivery.logs.amazonaws.com の書き込みを許可するリソースポリシーが設定されていること
✓Amazon Q 統合を利用する場合は ECS コンソールへのアクセス権があること

📋 設定手順

1

配信ソースの登録

Bashput-delivery-source
aws logs put-delivery-source \
    --name my-ecs-action-logs \
    --resource-arn arn:aws:ecs:{{region}}:{{account-id}}:cluster/{{cluster-name}} \
    --log-type EcsActionLogs

対象の ECS クラスターを配信ソースとして登録し、ログタイプに EcsActionLogs を指定します。

2

配信先の構成

Bashput-delivery-destination
aws logs put-delivery-destination \
    --name my-ecs-logs-destination \
    --output-format json \
    --delivery-destination-configuration '{"destinationResourceArn": "arn:aws:logs:{{region}}:{{account-id}}:log-group:/aws/vendedlogs/ecs/action-logs/{{cluster-name}}"}'

ログの配信先 (この例では CloudWatch Logs のロググループ) を構成します。

3

配信の作成

Bashcreate-delivery
aws logs create-delivery \
    --delivery-source-name my-ecs-action-logs \
    --delivery-destination-arn arn:aws:logs:{{region}}:{{account-id}}:delivery-destination:my-ecs-logs-destination

配信ソースと配信先を関連付けて Action Logs を有効化。コンソールから有効化する場合は、クラスター詳細ページの [設定] タブ → [Action logs] → [追加] を選択。CloudWatch Logs はデフォルトで 7 日間の保持期間になります。

💡 メリット

💼 ビジネス面

✓MTTR の短縮: 失敗原因を迅速に特定し復旧時間を削減
✓サポートコストの削減: 自己解決により運用の自律性が向上
✓信頼性の向上: Amazon Q の自動検出でデプロイ安定性を継続監視

🔧 技術面

✓完全な操作の可視化: 中間ステップまで含めて動作を追跡
✓柔軟な配信先: CloudWatch Logs / S3 / Firehose から選択
✓ワークロードへの無影響: fire-and-forget でリソース操作を妨げない

⚠️ デメリット・制約事項

🚧 制限事項

!有料機能であり、CloudWatch の標準 vended logs 料金が適用される
!記録対象はサービスデプロイと Managed Daemon のライフサイクル操作に限定
!オプトインはクラスターレベルで行う必要がある

🤔 考慮すべき点

!ログ量に応じて取り込み・ストレージコストが発生 → 保持期間の設定を検討
!コンソール有効化時のデフォルト保持は 7 日間。必要に応じて調整
!一時的な配信障害時にはログが失われる可能性がある (fire-and-forget)

🎯 ユースケース

1. デプロイメント失敗の根本原因分析

シナリオ: 新リビジョンのデプロイ中にサーキットブレーカーが作動しロールバックが発生。従来は開始/終了状態しか見えず原因特定が困難だった。
実装: ① クラスターで Action Logs を有効化 → ② Amazon Q がロールバックを自動検出 → ③ eventName とステータス理由から失敗ステップを特定
効果: コンソール内で根本原因分析と修復手順を確認でき、迅速に問題を解決

2. 失敗タスクの事後分析

シナリオ: 断続的なタスク起動失敗を調査したいが、標準のタスクメタデータは 1 時間で消えてしまう。
実装: Action Logs を S3 に配信して拡張メタデータを長期保持。Amazon Athena や CloudWatch Logs Insights で失敗パターンを分析。
効果: 保持期間の制約を受けず、失敗情報を任意のタイミングで詳細分析

3. マルチアカウント環境での集中監視

シナリオ: 複数の ECS クラスターを運用しており、デプロイアクションを一元的に監視したい。
実装: 各クラスターの Action Logs を Kinesis Data Firehose 経由で中央の分析基盤にニアリアルタイム集約。
効果: 複数クラスターのデプロイ状況をニアリアルタイムで横断的に可視化

💰 料金

Action Logs は有料機能であり、CloudWatch の標準 vended logs 料金が適用されます。クラスターが生成するログ量に基づき、取り込みとストレージに課金され、配信先 (CloudWatch Logs / S3 / Data Firehose) それぞれの標準料金が適用されます。コンソールから有効化した場合、CloudWatch Logs はデフォルトで 7 日間の保持期間を使用します。

📌 まとめ

Amazon ECS Action Logs は、これまで見えなかったデプロイとデーモン操作の中間ステップを可視化し、AWS Support への問い合わせなしに自己解決を可能にする重要なオブザーバビリティ機能です。Amazon Q との統合で問題の自動検出と修復手順の提示が受けられます。まずは開発環境のクラスターで有効化し、デプロイの可視性とトラブルシューティング体験の向上を確認することを推奨します。
