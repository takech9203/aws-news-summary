AWS Lambda

⚡ Lambda Managed Instances で GPU インスタンスをサポート

📅 リリース日: 2026 年 11 月 18 日 | Event Functions で EC2 G シリーズ GPU が利用可能に

📝 概要

AWS Lambda が、Lambda Managed Instances 上の Event Functions で GPU インスタンス (EC2 G シリーズ) をサポートしました。AI 推論、メディア処理、3D レンダリング、科学技術計算、金融シミュレーションといった GPU ワークロードを、GPU ドライバーやスケーリングインフラの管理なし にサーバーレスモデルで実行できます。

200 以上の AWS イベントソースと統合でき、GPU 使用率・CPU 使用率・同時実行数に基づいて自動スケール。vLLM、SGLang、PyTorch を事前構成した GPU ベースイメージ により、LLM 推論サーバーを最小限の設定でデプロイできます。

❌ Before: アップデート前の課題

  • Lambda は GPU 非対応。GPU 推論には EC2、ECS/EKS、SageMaker AI などで インフラを自前で構築・運用
  • GPU ドライバー、CUDA、推論フレームワークのセットアップとバージョン管理が必要
  • イベントソース統合やオートスケーリングのロジックを個別に実装
  • GPU キャパシティ不足時のフォールバック戦略を自前で設計

✅ After: アップデート後の改善

  • Event Functions として GPU ワークロードを実行。GPU/CPU 使用率と同時実行数で自動スケール
  • vLLM 等の事前構成イメージで モデル ID を指定するだけ で推論サーバーをデプロイ
  • 複数世代の G シリーズを指定可能。最新世代を優先し、不足時は 旧世代へ自動フォールバック
  • SOCI 遅延読み込みと S3 ストリーミングで 大きなイメージでも高速起動

Event Function はキャパシティプロバイダーで指定した複数世代の G シリーズ GPU インスタンス上で実行され、GPU/CPU 使用率と同時実行数に基づいて自動スケールします。コンテナイメージは SOCI 遅延読み込み、モデルウェイトは S3 ストリーミングにより高速に起動します。

🚀 主要機能

🎮 1. GPU インスタンス EC2 G シリーズのサポート

  • キャパシティプロバイダーの AllowedInstanceTypes に g5、g6、g6e など複数世代を指定可能
  • 利用可能な最新世代を優先的に選択し、キャパシティ不足時は旧世代へ自動フォールバック
  • AcceleratorConfig.AcceleratorMemorySize で必要な GPU メモリ (3〜48 GB) を指定すると、要件を満たす最小の GPU に配置

🔀 2. 実行環境ごとの複数同時実行

  • 1 つの実行環境で最大 48 の同時リクエストを処理可能 (PerExecutionEnvironmentMaxConcurrency、デフォルト 4)
  • vLLM が同一 GPU 上で複数リクエストをバッチ処理し、単一のモデルコピーを共有して GPU 使用率を最大化
  • GPU 使用率、CPU 使用率、同時実行数に基づく自動スケーリング

📦 3. 事前構成済み GPU ベースイメージ

  • vLLM、SGLang、PyTorch を含むベースイメージを提供 (例: public.ecr.aws/lambda/deep-learning-containers/vllm:cuda-v1)
  • vLLM イメージでは推論コードの実装が不要。環境変数 MODEL_ID に Hugging Face リポジトリや S3 ロケーションを指定するだけでデプロイ可能
  • OpenAI 互換の API ペイロード (chat completions / text completions) に対応

⚡ 4. 高速起動の仕組み

  • Seekable OCI (SOCI) 遅延読み込みにより、最大 32 GB のコンテナイメージでも必要な部分から起動
  • モデルウェイトを同一リージョンの S3 に配置し VLLM_LOAD_FORMAT=runai_streamer を設定するとウェイトをメモリへ直接ストリーミング
  • バージョン発行時にプロビジョニング、ウェイトのダウンロード、エンジンのウォームアップが完了し、最初の呼び出しがコールドスタートを待たない

⚙️ 設定方法

📋 前提条件

✓EC2 のサービスクォータ「Running On-Demand G and VT instances」の引き上げ (新規アカウントは 0 の場合がある)
✓コンテナイメージを格納する Amazon ECR リポジトリ
✓キャパシティプロバイダー用の VPC (サブネット、セキュリティグループ) と IAM ロール
1

キャパシティプロバイダーの作成

BashAWS CLI
aws lambda create-capacity-provider \
  --cli-input-json file://capacity-provider.json

AllowedInstanceTypes に複数世代の G シリーズを指定すると、Lambda が利用可能なものを自動選択し、キャパシティ不足時のフォールバックが有効になります。

2

コンテナイメージのビルドとプッシュ

BashDocker
docker build -t lmi-gpu-inference .
docker tag lmi-gpu-inference:latest \
  123456789012.dkr.ecr.us-east-1.amazonaws.com/lmi-gpu-inference:latest
docker push 123456789012.dkr.ecr.us-east-1.amazonaws.com/lmi-gpu-inference:latest

vLLM ベースイメージ (public.ecr.aws/lambda/deep-learning-containers/vllm:cuda-v1) をベースにビルドし、ECR にプッシュします。vLLM イメージを使う場合、推論コードの実装は不要です。

3

関数の作成

BashAWS CLI
aws lambda create-function \
  --function-name lmi-gpu-inference \
  --package-type Image \
  --code ImageUri=123456789012.dkr.ecr.us-east-1.amazonaws.com/lmi-gpu-inference:latest \
  --role arn:aws:iam::123456789012:role/LambdaExecutionRole \
  --memory-size 16384 \
  --timeout 900 \
  --accelerator-config AcceleratorMemorySize=16 \
  --capacity-provider-config '{
    "LambdaManagedInstancesCapacityProviderConfig": {
      "CapacityProviderArn": "arn:aws:lambda:us-east-1:123456789012:capacity-provider:gpu-capacity-provider",
      "ExecutionEnvironmentMemoryGiBPerVCpu": 4,
      "PerExecutionEnvironmentMaxConcurrency": 4
    }
  }' \
  --environment 'Variables={MODEL_ID=s3://my-bucket/models/my-model/}'

AcceleratorConfig で必要な GPU メモリ (この例では 16 GB) を指定。MODEL_ID にはモデルウェイトの場所 (Hugging Face リポジトリまたは S3) を指定します。

4

バージョンの発行と呼び出し

BashAWS CLI
aws lambda publish-version --function-name lmi-gpu-inference

GPU 対応の Event Functions は 発行済みバージョンから実行 します。発行時にプロビジョニング、モデルウェイトのダウンロード、エンジンのウォームアップが行われるため、最初の呼び出しがコールドスタートの影響を受けません。呼び出しは OpenAI 互換のペイロード (messages または prompt) で行えます。

⚖️ メリットと制約事項

💼 ビジネス面のメリット

✓インフラ運用コストの削減: GPU クラスターの構築・運用、ドライバー管理が不要
✓GPU コストの最適化: 複数の同時呼び出しが単一 GPU とモデルコピーを共有し、関数集約で GPU 使用率を最大化
✓市場投入までの時間短縮: 事前構成済みイメージとイベントソース統合で AI 推論機能を短期間で組み込み可能

🔧 技術面のメリット

✓自動スケーリング: GPU/CPU 使用率、同時実行数に基づくスケーリングを Lambda が管理
✓キャパシティの耐障害性: 複数世代指定による自動フォールバックで継続稼働
✓高速起動: SOCI 遅延読み込み、S3 ウェイトストリーミング、発行時ウォームアップ
✓イミュータブルなバージョン: MODEL_ID 変更と新バージョン発行のみでモデル切り替え。再ビルド不要、並行稼働可能

🚫 制限事項

✗パッケージ形式はコンテナイメージのみ (ZIP デプロイは不可)
✗GPU 対応の Event Functions は発行済みバージョンからの実行が必要
✗アクセラレーターメモリは 3〜48 GB の範囲 (単一 GPU 相当)。マルチ GPU 構成には非対応
✗Lambda Managed Instances と EC2 G シリーズの両方が利用可能なリージョンが必要

⚠️ 考慮すべき点

⚠EC2 クォータ「Running On-Demand G and VT instances」の事前引き上げが必要 (新規アカウントは 0 の場合がある)
⚠課金は EC2 インスタンスベース。アイドル時間を含めたコスト試算が必要
⚠課金停止には関数削除後にキャパシティプロバイダーの削除が必要
⚠AcceleratorMemorySize は最小要件の指定。配置先によってはより大きい GPU が割り当てられる場合がある

💡 ユースケース

🤖 1. イベント駆動の LLM 推論 API

シナリオ: 自社アプリケーションにオープンウェイト LLM による推論 API を組み込みたいが、GPU インフラの運用チームを持たない。

BashOpenAI 互換ペイロードで呼び出し
# vLLM ベースイメージを使用し、MODEL_ID に S3 のモデルウェイトを指定
# VLLM_LOAD_FORMAT=runai_streamer でウェイトをストリーミング読み込み
aws lambda invoke \
  --function-name lmi-gpu-inference:1 \
  --payload '{"messages":[{"role":"user","content":"こんにちは"}]}' \
  response.json

✅ 効果: OpenAI 互換 API として LLM 推論を提供でき、GPU ドライバーやスケーリングの管理が不要。複数リクエストのバッチ処理により GPU あたりのスループットを最大化できる。

🎬 2. S3 イベント起点のメディア処理

シナリオ: S3 にアップロードされた動画や画像に対して、GPU を使ったトランスコードや画像解析を自動実行したい。

BashS3 イベント通知の設定
# S3 イベント通知を Event Function に接続
aws s3api put-bucket-notification-configuration \
  --bucket my-media-bucket \
  --notification-configuration '{
    "LambdaFunctionConfigurations": [{
      "LambdaFunctionArn": "arn:aws:lambda:us-east-1:123456789012:function:gpu-media-processor:1",
      "Events": ["s3:ObjectCreated:*"]
    }]
  }'

✅ 効果: アップロードをトリガーに GPU 処理が自動実行され、負荷に応じてスケール。最大 90 分のタイムアウトにより長時間のトランスコードにも対応できる。

📊 3. バッチの科学技術計算・金融シミュレーション

シナリオ: 日次で実行する金融リスクシミュレーションやレンダリングジョブを、ジョブ量に応じた GPU キャパシティで実行したい。

BashEventBridge スケジューラから定期起動
# EventBridge スケジューラから Event Function を定期起動
aws scheduler create-schedule \
  --name daily-risk-simulation \
  --schedule-expression "cron(0 1 * * ? *)" \
  --target '{"Arn":"arn:aws:lambda:us-east-1:123456789012:function:risk-sim:1","RoleArn":"arn:aws:iam::123456789012:role/SchedulerRole"}' \
  --flexible-time-window '{"Mode":"OFF"}'

✅ 効果: ジョブ実行時のみ GPU インスタンスがスケールし、複数世代フォールバックによりキャパシティ不足時も安定して実行できる。

🌍 利用可能リージョン

Lambda Managed Instances と EC2 G シリーズインスタンスの両方が利用可能な、すべての AWS 商用リージョン で利用できます。

設定は AWS マネジメントコンソール、AWS CLI、SDK、AWS CloudFormation、AWS CDK、AWS SAM のほか、Agent Toolkit for AWS の Lambda Managed Instances スキルを通じて Kiro、Claude Code、Codex などのコーディングアシスタントからも可能です。

📌 まとめ

AWS Lambda の GPU サポートにより、AI 推論をはじめとする GPU ワークロードを イベント駆動かつサーバーレスの運用モデル で実行できるようになりました。vLLM などの事前構成済みベースイメージと OpenAI 互換 API により、LLM 推論サーバーの構築は大幅に簡素化されます。

GPU 推論基盤を自前運用しているチームや、これから LLM 推論をアプリケーションへ組み込むチームは、EC2 クォータの引き上げを行ったうえで 小規模な PoC から評価を始める ことを推奨します。
