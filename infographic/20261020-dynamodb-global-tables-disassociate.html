Amazon DynamoDB

✂️ グローバルテーブルのレプリカ切り離し
(Disassociate) サポート

📅 リリース日: 2026 年 10 月 20 日 | 機能: グローバルテーブルからのレプリカ切り離し

📌 概要

Amazon DynamoDB グローバルテーブルで、テーブルやデータを削除することなくレプリカを切り離すことが可能になりました。 切り離されたテーブルは、同じアカウント・同じリージョンの単一リージョンテーブルとして、 テーブル名と ARN を保持したまま継続利用できます。代替テーブルの作成やデータのコピーは不要です。

対象は、マルチリージョン結果整合性 (MREC) を使用する同一アカウントおよびマルチアカウントのグローバルテーブル (バージョン 2019.11.21) で、すべての AWS リージョンで利用できます。

❌ アップデート前の課題

  • レプリカを除外するには削除するしかなく、そのリージョンのテーブルとデータは失われた
  • データを残したい場合は、代替テーブルを作成してデータをエクスポート / コピーする作業が必要だった
  • マルチアカウントの共有グローバルテーブルから特定のアカウントだけが離脱し、既存データを引き継いで独立運用する手段がなかった

✅ アップデート後の改善

  • レプリカを削除せずにレプリケーションのみを停止し、既存テーブルを単一リージョンテーブルとして利用可能に
  • テーブル名・ARN・データに加え、インデックス、Streams、TTL、バックアップ、暗号化などの設定が維持され、移行作業が不要に
  • 切り離し保護がデフォルトで有効化されており、誤操作による意図しない切り離しを防止

⚙️ 主要機能

✂️ 1. レプリカの切り離し (Disassociate)

  • UpdateTable API の ReplicaUpdates 配列に新しい Disassociate アクションを指定して実行
  • 切り離されたレプリカは、同じアカウント・リージョンの単一リージョンテーブルになり、テーブル名と ARN を保持
  • インデックス、DynamoDB Streams、TTL、バックアップ、暗号化、課金モード、テーブルクラスなどの設定は維持 (レプリケーション固有の設定とメトリクスは適用されなくなる)
  • レプリカが 3 つ以上の場合、切り離したレプリカのみが単一リージョンテーブル化。レプリカが 2 つの場合は両方が単一リージョンテーブルに (どちらのテーブルもデータも削除されない)

🛡️ 2. 切り離し保護 (Disassociation Protection)

  • 各レプリカでデフォルトで有効になっており、誤操作による切り離しを防止
  • 切り離し実行前に保護を無効化して更新完了を待つ必要がある (保護を無効化してもレプリケーションは停止しない)
  • 削除保護 (deletion protection) とは独立した設定

🔄 3. レプリケーション停止境界による整合性確保

  • 切り離しリクエスト受付時に、レプリケーション停止境界 (replication stop boundary) となる時点を設定
  • 離脱レプリカへの直接書き込みのうち、境界までのすべての書き込みが残りの全レプリカに配信されるまで待機
  • 配信が完了できない場合、切り離しは完了せず全レプリカが元のグローバルテーブルに残る (安全側に倒れる設計)
  • 切り離しの最中および完了後も、テーブルは読み取り / 書き込みを継続して処理可能 (無停止)

🏢 4. マルチアカウントグローバルテーブルのサポート

  • 各アカウントは自分が所有するレプリカのみを切り離し可能
  • 共有グローバルテーブルからの離脱後も、既存データを保持したまま独立運用が可能

API 変更履歴

日付サービス変更内容
2026/10/20 Amazon DynamoDB 6 updated api methods - UpdateTable の ReplicaUpdates に Disassociate アクションを追加。CreateTable、DeleteTable、DescribeTable、RestoreTableFromBackup、RestoreTableToPointInTime、UpdateTable のレスポンスに DisassociationProtectionEnabled を追加

必要な IAM 権限

切り離しには、対象レプリカのテーブル ARN に対して dynamodb:UpdateTable と dynamodb:DisassociateTableReplica の両方が必要です。 dynamodb:DisassociateTableReplica は IAM 権限であり、独立した API オペレーションではありません。 保護状態の確認と完了のモニタリングには dynamodb:DescribeTable が必要です。

JSON IAM ポリシー例 
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "dynamodb:UpdateTable",
                "dynamodb:DisassociateTableReplica",
                "dynamodb:DescribeTable"
            ],
            "Resource": "arn:aws:dynamodb:us-west-2:111122223333:table/Music"
        }
    ]
}

📝 設定方法

前提条件

✓MREC を使用する Global Tables version 2019.11.21 (Current) のグローバルテーブルであること
✓対象レプリカが ACTIVE で、すべてのレプリカが到達可能であること
✓必要な IAM 権限とレプリケーションに必要な暗号化キーへのアクセスが維持されていること
✓他のレプリカライフサイクル操作 (レプリカ作成や別の切り離し) が実行中でないこと

ステップ 1: 切り離し保護を無効化する

対象レプリカのリージョンで、デフォルトで有効になっている切り離し保護を無効化します。レプリカを所有するアカウントの認証情報で実行します。

Bash切り離し保護の無効化
aws dynamodb update-table \
    --table-name Music \
    --region us-west-2 \
    --no-disassociation-protection-enabled

ステップ 2: 保護の無効化とテーブル状態を確認する

TableStatus が ACTIVE かつ DisassociationProtectionEnabled が false になるまで繰り返し確認します。フィールドが存在しない、または true の場合は次に進まないでください。

Bash状態確認
aws dynamodb describe-table \
    --table-name Music \
    --region us-west-2 \
    --query 'Table.{TableStatus:TableStatus,DisassociationProtectionEnabled:DisassociationProtectionEnabled,Replicas:Replicas}'

ステップ 3: Disassociate アクションを実行する

ReplicaUpdates に Disassociate アクションを 1 つ指定して切り離しをリクエストします。ローカルリージョンを指定し、DisassociationMode に WAIT_FOR_REPLICATION を明示的に設定します。レスポンスが成功しても、操作自体は非同期で継続します。

Bash切り離しの実行
aws dynamodb update-table \
    --table-name Music \
    --region us-west-2 \
    --replica-updates '[{"Disassociate":{"RegionName":"us-west-2","DisassociationMode":"WAIT_FOR_REPLICATION"}}]'

ステップ 4: 完了を確認する

TableStatus が ACTIVE であること、および Replicas にピアレプリカが残っていないことの両方を確認します。

Bash完了確認
aws dynamodb describe-table \
    --table-name Music \
    --region us-west-2 \
    --query 'Table.{TableStatus:TableStatus,Replicas:Replicas}'
⚠️ ACTIVE だけでは成功の確認になりません。切り離しがロールバックした場合も ACTIVE に戻るため、必ずレプリカメンバーシップを確認します。残りのレプリカ側からも、更新後のメンバーシップを確認することが推奨されます。

ステップ 5: CloudFormation で管理している場合

AWS::DynamoDB::GlobalTable リソースで管理しているレプリカは、TableType プロパティを使用して切り離します。以下の 2 段階のスタック更新を、レプリカのアカウントとリージョンで実行します。

  1. Replicas 内の対象リージョンのエントリで DisassociationProtectionEnabled を false に設定し、TableType を GlobalTableReplica に設定して更新する
  2. TableType を Regional に変更し、Replicas にスタックのリージョンのみを残して更新する (マルチアカウントの場合は GlobalTableSourceArn を削除し、継承していたテーブル設定を明示的に宣言する)
⚠️ TableType を Regional に変更せずにレプリカエントリを削除すると、通常のスタック更新と同様にレプリカが削除されるため注意が必要です。

💡 メリット

ビジネス面

✓移行コストの削減: リージョン移行やアカウント移行の完了後、代替テーブルの作成やデータコピーなしでレプリケーション構成を解消でき、移行プロジェクトの工数とリスクを削減
✓コスト最適化: 不要になったリージョンへのレプリケートされた書き込み課金を停止しつつ、監査やコンプライアンス要件のためにデータを保持
✓組織の独立性: マルチアカウント共有グローバルテーブルに参加している組織やチームが、既存データを引き継いだまま独立したテーブル運用に移行可能

技術面

✓データ整合性の担保: レプリケーション停止境界により、離脱レプリカへの書き込みが残りのレプリカに配信されてから切り離しが完了するため、データロスを抑えた離脱が可能
✓設定の完全な維持: テーブル名、ARN、インデックス、Streams、TTL、バックアップ、暗号化などが維持され、アプリケーション側の変更を最小化
✓安全性の確保: デフォルト有効の切り離し保護と 2 段階の操作により、誤操作による意図しないレプリケーション停止を防止
✓無停止での切り離し: 切り離しの最中もテーブルは読み取り / 書き込みを継続して処理可能

⚠️ デメリット・制約事項

制限事項

✗マルチリージョン強整合性 (MRSC) のグローバルテーブルでは利用不可
✗Global Tables version 2017.11.29 (Legacy) では利用不可
✗切り離しは取り消し (undo) 不可。同じテーブルを元のグローバルテーブルに再接続することもできない
✗過去 24 時間以内に新規レプリカ追加のソースになったレプリカは切り離し不可
✗グローバルテーブルごとにレプリカライフサイクル操作は同時に 1 つのみで、他の操作の完了を待つ必要がある
✗いずれかのレプリカが INACCESSIBLE_ENCRYPTION_CREDENTIALS、REPLICATION_NOT_AUTHORIZED、ARCHIVING、ARCHIVED の場合は実行がブロックされる

考慮すべき点

⚠MREC は非同期レプリケーションのため、切り離されたテーブルには他リージョンの最新の書き込みが含まれていない可能性がある
⚠同じリージョンに代替レプリカを作成する場合は、スタンドアロンテーブルに残したい変更を残りのグローバルテーブルへ反映してから、スタンドアロンテーブルを削除して新しいレプリカを追加する必要がある (新しいレプリカは残りのグローバルテーブルからデータをコピーする)
⚠TableStatus が ACTIVE に戻っただけでは成功とは限らないため、必ずレプリカメンバーシップを確認する
⚠受け付けられた操作も、暗号化キーへのアクセス喪失などにより後からロールバックされる場合がある。その場合は ReplicaStatus と ReplicaStatusDescription を確認して原因を解消する

🎯 ユースケース

🏢 ユースケース 1: マルチアカウント共有グローバルテーブルからの離脱

シナリオ: 複数の事業部が別々の AWS アカウントでマルチアカウントグローバルテーブルを共有していたが、組織再編により一部の事業部がデータを引き継いで独立運用することになった。

Bash離脱するアカウントの認証情報で、自アカウントのレプリカのみを切り離す
aws dynamodb update-table \
    --table-name SharedCatalog \
    --region ap-northeast-1 \
    --no-disassociation-protection-enabled

aws dynamodb update-table \
    --table-name SharedCatalog \
    --region ap-northeast-1 \
    --replica-updates '[{"Disassociate":{"RegionName":"ap-northeast-1","DisassociationMode":"WAIT_FOR_REPLICATION"}}]'

✅ 効果: データコピーや代替テーブルの構築なしで、離脱時点のデータを保持した単一リージョンテーブルとして独立運用を開始できる。

🌏 ユースケース 2: リージョン移行後のレプリケーション解消

シナリオ: ワークロードを us-west-2 から us-east-1 へ移行するために一時的にグローバルテーブルを構成し、移行完了後は旧リージョンのテーブルを監査用に保持しつつレプリケーションを停止したい。

Bash移行先リージョン側を確認した後、旧リージョンのレプリカを切り離す
aws dynamodb update-table \
    --table-name Orders \
    --region us-west-2 \
    --replica-updates '[{"Disassociate":{"RegionName":"us-west-2","DisassociationMode":"WAIT_FOR_REPLICATION"}}]'

✅ 効果: 旧リージョンのテーブルを削除せずにレプリケートされた書き込みの課金を停止し、監査・検証用のデータとして保持できる。

📜 ユースケース 3: CloudFormation 管理下のレプリカの計画的な単一リージョン化

シナリオ: IaC で管理しているグローバルテーブルについて、特定リージョンの利用縮小に伴い、そのリージョンのレプリカをデータを保持したまま単一リージョンテーブルへ移行したい。

YAML2 段階のスタック更新
# 更新 1: 切り離し保護の無効化
Resources:
  GlobalTable:
    Type: AWS::DynamoDB::GlobalTable
    DeletionPolicy: Retain
    Properties:
      TableName: GT-CFN-Table
      TableType: GlobalTableReplica
      Replicas:
        - Region: us-east-1
          DisassociationProtectionEnabled: false
        - Region: us-east-2

# 更新 2: TableType を Regional に変更して切り離し
# Replicas にはスタックのリージョンのみを残す

✅ 効果: スタックが切り離し後も同じテーブルを単一リージョンテーブルとして管理し続け、テーブルやデータは削除されない。

💰 料金

レプリカの切り離し操作自体に追加料金は発表されていません。切り離し後のテーブルは単一リージョンテーブルとして課金されるため、 グローバルテーブルのレプリケートされた書き込み (replicated writes) に関する課金は発生しなくなります。

状態課金
切り離し前 (レプリカ)グローバルテーブルのレプリケートされた書き込み課金を含む
切り離し後 (単一リージョンテーブル)通常の単一リージョンテーブルとしての読み取り / 書き込み・ストレージ課金のみ

詳細は Amazon DynamoDB の料金ページ を参照してください。

📝 まとめ

DynamoDB グローバルテーブルのレプリカ切り離し機能により、これまで「削除」しか選択肢がなかったレプリカのライフサイクルに、 データと設定を保持したまま単一リージョンテーブル化するという新しい選択肢が加わりました。 リージョン移行やマルチアカウント構成からの離脱、コスト最適化を検討しているチームは、 切り離し保護の挙動と「取り消し不可」という制約を理解した上で、本機能の活用を検討することを推奨します。
