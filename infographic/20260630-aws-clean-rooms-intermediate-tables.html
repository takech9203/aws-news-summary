AWS Clean Rooms

🔐 SQL 中間テーブルのサポート

複数ステップの分析ワークフローを、プライバシー境界内で効率化

2026-06-30
リリース日

📌 概要

AWS Clean Rooms が SQL クエリ向けの中間テーブル (Intermediate Tables) をサポートしました。SQL クエリの結果をコラボレーション内の中間テーブルに書き込み、その後の分析で再利用できます。

複雑な結合の再利用から、ダウンストリーム分析向けの共有 ID マッピングテーブルの構築まで、複数ステップの分析ワークフローを実現します。これらの処理はすべて コラボレーションのプライバシー境界内 で完結し、中間テーブルのデータは AWS マネージドストレージに保存され、外部にエクスポートされることはありません。

⛔ アップデート前の課題
  • 複雑な結合や ID マッピングの計算を分析ごとに毎回実行する必要があった
  • 同じ中間結果を再利用できず、繰り返し計算でコストとクエリ実行時間が増加
  • リーチ・フリークエンシー・アトリビューション間で中間データを共有する仕組みがなかった
➡️
✅ アップデート後の改善
  • SQL クエリ結果を中間テーブルとして保存し、後続分析で再利用可能に
  • 複雑な結合や共有 ID マッピングを一度だけ計算し、複数分析で活用
  • プライバシー境界を維持したまま複数ステップのワークフローを構築可能に

ベーステーブルを結合して中間テーブルを生成し、複数のダウンストリーム分析で再利用するフロー。中間テーブルは POPULATE_SUCCESS 状態になった後に分析から参照できます。

⚙️ 主要機能

1. 中間テーブルへの SQL クエリ結果の保存
  • SQL クエリの結果をコラボレーションスコープの中間テーブルに書き込める
  • データは AWS マネージドストレージに保存され、コラボレーション外部にはエクスポートされない
  • 中間テーブルは分析ランナーが作成し、所有・管理する
2. 後続分析での再利用
  • 設定済みテーブルと同様に SQL クエリや PySpark ジョブから名前で参照できる
  • 複雑な結合や共有 ID マッピングを一度計算し、複数の分析で再利用できる
  • 中間テーブルを別の中間テーブルのベースとして利用するネスト構成も可能
3. プライバシー制御の継承と遅延適用 (Deferred Enforcement)
  • 中間テーブルは、生成元のベーステーブルからプライバシー制御を継承する
  • 一部の制御は populate 時には評価されず、後続分析で参照された時点で適用される (遅延適用)
  • First-party / Multi-party の分類により、制御の適用方法が決まる

🔄 中間テーブルのライフサイクル

分析で参照する前に、まずデータを populate (生成) しカスタム分析ルールをアタッチする必要があります。ステータスが POPULATE_SUCCESS になっている必要があります。

CREATEDリソースは存在するが、データはまだ生成されていない
POPULATE_STARTEDpopulate 操作が進行中
POPULATE_SUCCESSデータが正常に生成され、分析から参照可能

BASE_TABLE_REMOVEDpopulate に使用したベーステーブルが削除された状態。分析で利用不可

💰 予算 (Budgets) の扱い

アクセス予算: populate 時 (ベーステーブルへの分析実行) と中間テーブルへのアクセス時の両方で減算される。キャッシュデータへのアクセスもベーステーブル利用としてカウントされる (ネストの推移的依存も含む)。
差分プライバシー予算: populate 時にベーステーブルの差分プライバシーが有効な場合は予算が減算されノイズが注入される。中間テーブルに設定した場合、利用時に単一予算オーナーのイプシロンが減算される。

⚖️ メリットとデメリット・制約事項

👍 ビジネス面のメリット

  • コスト削減: 複雑な結合や ID マッピングを一度だけ実行し再利用
  • 協働の高度化: 共有 ID マッピングを基盤に複数当事者が一貫した分析を実施
  • プライバシー保護の維持: 基礎データを開示・コピーせず境界内で複数ステップ分析

🚀 技術面のメリット

  • パフォーマンス最適化: 中間結果のキャッシュで後続クエリ実行時間を短縮
  • ワークフローの簡素化: 設定済みテーブルと同じ方法で SQL/PySpark から参照、ネスト構成も可能
  • きめ細かな制御: 遅延適用により参照時点で最も制限的な制御を適用

⚠️ 制限事項

  • 参照には事前に populate し POPULATE_SUCCESS である必要がある
  • ベーステーブル削除時は BASE_TABLE_REMOVED となり利用不可
  • バージョンには保持期間 (デフォルト 30 日)。期限切れ後は再 populate が必要

🔎 考慮すべき点

  • ストレージは削除するまで標準料金で課金される
  • アクセス予算は populate 時と利用時の両方で減算 (二重消費を考慮)
  • 差分プライバシーでは新データセット扱い。populate のトランスフォーメーションでユーザー数を増幅した場合、元母集団への影響は追跡されない

💡 ユースケース

1. 広告のリーチ・フリークエンシー・アトリビューション分析
シナリオ: パブリッシャーと広告主がファーストパーティデータを結合し、共通の ID マッピングテーブルを構築する。
効果: ID マッピングを中間テーブルとして各分析で再利用し、結合処理の重複を排除してコストとパフォーマンスを最適化。
2. 複雑な結合の再利用
シナリオ: 複数テーブルを結合する重い処理を含む分析を、条件を変えて何度も実行する。
効果: 結合結果を中間テーブルに保存し、後続分析では結合済みデータを参照するだけで済み、実行時間とコストを削減。
3. 段階的なデータ加工パイプライン
シナリオ: 生データをクレンジング・集計し、その結果を別の集計に渡す多段階パイプラインを構築する。
効果: 各段階の結果を中間テーブルとして保持しネスト構成で渡すことで、プライバシー境界を維持したまま複数ステップを実現。

💵 料金・リージョン・関連サービス

💵 料金

中間テーブルのストレージは削除するまで標準料金で課金。populate 操作および中間テーブルへのアクセスは、ベーステーブルへの分析実行・利用としてアクセス予算や差分プライバシー予算を消費します。

📝 まとめ

SQL 中間テーブルのサポートにより、AWS Clean Rooms は プライバシー境界を維持したまま複雑な複数ステップ分析 を効率的に実行できるようになりました。複雑な結合や共有 ID マッピングを一度計算して再利用することで、コスト削減とパフォーマンス最適化を実現します。広告分析など繰り返しの中間処理を伴うコラボレーションでは、保持期間 (デフォルト 30 日)、ストレージ課金、予算消費の挙動を考慮しながら導入を検討することを推奨します。
