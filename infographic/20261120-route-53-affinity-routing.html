Amazon Route 53

🌐 アベイラビリティーゾーン (AZ) アフィニティルーティング

リリース日: 2026 年 11 月 20 日 | 新しいルーティングポリシー

📌 概要

Amazon Route 53 が AZ アフィニティルーティングをサポート。VPC 内のクライアントからの DNS クエリに対して、クエリ元と同じ AZ 内のリソースを応答として返すことができます。トラフィックを AZ 内に留めることで、レイテンシーの削減と AZ 間データ転送コストの削減を実現します。

❌ アップデート前の課題

  • レイテンシーベースやジオプロキシミティでは AZ 単位の粒度でトラフィックを制御できなかった
  • AZ をまたぐ通信により AZ 間データ転送コストと追加レイテンシーが発生
  • AZ 単位のルーティングにはアプリ側で独自のエンドポイント選択ロジックが必要だった

✅ アップデート後の改善

  • DNS レベルでクエリ元と同じ AZ のリソースへ自動ルーティングし、トラフィックを AZ 内に維持
  • Zone Group → Region → Partition → Global の順でフォールバックし可用性を確保
  • ヘルスチェックとの組み合わせで AZ 障害時も自動切替

VPC 内のクライアントが DNS クエリを実行すると、Route 53 VPC Resolver がクエリ元の AZ 情報を Route 53 に伝え、Route 53 は同一 AZ のリソースを指すレコードを応答します。該当レコードが存在しない場合や異常な場合は、他のロケーションのレコードにフォールバックします。

Route 53 は最も具体的なロケーションから順に正常なレコードを探して応答します。レコードを作成していないレベルはスキップされます。

⚡ 主要機能

🎯 AZ 単位の DNS ルーティング

  • クエリ元の AZ と同じ AZ のリソースを指すレコードを応答
  • AZ の指定には AZ 名 (us-east-1a など) ではなく AZ ID (use1-az1 など) を使用
  • AZ 名はアカウントごとに異なる AZ にマッピングされるため、AZ ID により一貫した指定が可能

🪜 5 段階のロケーションタイプとフォールバック

  • Availability Zone → Zone Group → Region → Partition → Global の順にフォールバック
  • すべてのロケーションタイプのレコードを作成する必要はなく、存在しないレベルはスキップ
  • Global レコードは VPC 外からのクエリに応答するため、常に作成することが推奨

🩺 ヘルスチェックとの統合

  • 各レコードにヘルスチェックを関連付け可能 (エイリアスレコードは Evaluate Target Health を有効化)
  • エンドポイントが異常な場合、次のロケーションのレコードで応答
  • ヘルスチェックのない非エイリアスレコードは常に正常とみなされ、フォールバックが発生しない点に注意

🌍 パブリック・プライベート両ホストゾーンに対応

  • パブリックホストゾーンとプライベートホストゾーンの両方で利用可能
  • VPC Resolver 経由のクエリのみ AZ 情報が伝わり、それ以外のクエリは Global レコードにのみマッチ
  • コンソール、API、AWS CLI、AWS SDK、AWS CloudFormation から設定可能

🔧 技術仕様

ステップ 1: AZ ID と Zone Group の確認

Bash AZ ID と Zone Group の一覧表示 
aws ec2 describe-availability-zones \
    --region us-east-1 \
    --filters Name=zone-type,Values=availability-zone \
    --query "AvailabilityZones[].[ZoneId,GroupName]" \
    --output text

zone-type フィルタにより、AZ アフィニティルーティングが対応していない Local Zones や Wavelength Zones を除外します。

ステップ 2: AZ アフィニティレコードの作成

Bash AWS CLI でレコードを作成 
aws route53 change-resource-record-sets \
    --hosted-zone-id Z1234567890ABC \
    --change-batch '{
      "Changes": [{
        "Action": "CREATE",
        "ResourceRecordSet": {
          "Name": "api.example.internal",
          "Type": "A",
          "SetIdentifier": "az-use1-az1",
          "AZAffinity": {
            "LocationType": "AvailabilityZone",
            "LocationId": "use1-az1"
          },
          "TTL": 60,
          "ResourceRecords": [{"Value": "10.0.1.10"}]
        }
      }]
    }'

同じ名前・同じタイプのレコードを、ルーティングしたいロケーションごとに作成します。AZ レベルのレコードに加えて、Region レベルや Global レベルのフォールバック用レコードも作成します。

ステップ 3: 動作確認

Route 53 コンソールの DNS チェックツールと TestDNSAnswer API は AZ アフィニティレコードに対応していません。レコードを作成した各 AZ 内の EC2 インスタンスから dig などのコマンドを実行し、VPC Resolver (VPC のデフォルト DNS サーバー) に対してクエリを送信して動作を確認します。Route 53 のネームサーバーに直接クエリを送信しないよう注意してください。

💡 メリット

💼 ビジネス面

✓コスト削減: トラフィックを AZ 内に維持し、AZ 間データ転送コストを削減
✓ユーザー体験の向上: レイテンシー削減によりアプリケーションの応答性能が向上
✓運用負荷の軽減: 独自エンドポイント選択ロジックが不要になり、DNS レベルで一元管理

⚙️ 技術面

✓AZ 単位の粒度のルーティング: 従来のポリシーでは実現できなかった AZ 単位のトラフィック制御
✓自動フォールバック: AZ 障害時にも広いロケーションの順で自動切替
✓セルベースアーキテクチャとの親和性: DNS だけで AZ ローカルなルーティングを実現

⚠️ デメリット・制約事項

🚫 制限事項

✗Local Zones、Wavelength Zones、AWS Outposts はロケーションタイプとしてサポートされない
✗Traffic Flow (トラフィックポリシー) では AZ アフィニティルーティングを利用できない
✗Route 53 コンソールの DNS チェックツールと TestDNSAnswer API は AZ アフィニティレコードに対応していない
✗ロケーション ID は大文字小文字が区別されるため、use1-az1、global のように小文字で指定する必要がある

🤔 考慮すべき点

⚠️AZ 情報が伝わるのは Route 53 VPC Resolver 経由のクエリのみ。インターネットからのクエリや Route 53 ネームサーバーへの直接クエリは Global レコードにのみマッチ
⚠️Global レコードを作成していない場合、マッチするレコードがないクエリには応答が返らない (NODATA) ため、Global レコードの作成を推奨
⚠️ヘルスチェックを関連付けていない非エイリアスレコードは常に正常とみなされ、フォールバックが機能しない
⚠️マッチするレコードがすべて異常な場合は、異常であっても最も具体的なレコードで応答される
⚠️応答するレコードを選択する機能でありアクセス制御ではないため、レコード値の秘匿目的には使用できない

🎯 ユースケース

1️⃣ マイクロサービス間通信の AZ ローカル化

シナリオ: 複数 AZ に展開したマイクロサービス間の内部通信で、AZ 間データ転送コストとレイテンシーを削減したい。

実装例: プライベートホストゾーンに internal-api.example.internal の AZ アフィニティレコードを AZ ごとに作成。use1-az1 → 10.0.1.10 (AZ use1-az1 の内部 ALB)、use1-az2 → 10.0.2.10 (AZ use1-az2 の内部 ALB)、Region us-east-1 のフォールバック用レコードを追加し、各レコードにヘルスチェックを関連付け。

💡 効果: サービス間通信が同一 AZ 内で完結し、AZ 間データ転送コストの削減とレイテンシーの短縮を実現。AZ 障害時はリージョンレコードに自動フォールバック。

2️⃣ セルベースアーキテクチャの障害分離

シナリオ: AZ ごとに独立したセルを構成し、障害の影響範囲を AZ 単位に限定したい。

実装例: 各 AZ のセルを指す AZ アフィニティレコードを作成し、ヘルスチェックを関連付ける。正常時は各クライアントが自身の AZ のセルのみと通信し、障害時はヘルスチェック失敗により他ロケーションへフォールバック。

💡 効果: 正常時は AZ をまたぐ依存関係を排除して障害分離を強化しつつ、AZ 障害時には自動的に他のセルへ切り替えて可用性を維持。

3️⃣ ハイブリッド公開エンドポイントの最適化

シナリオ: 同一の DNS 名を VPC 内クライアントとインターネットクライアントの両方が利用するが、VPC 内からのアクセスは AZ ローカルに最適化したい。

実装例: パブリックホストゾーンに api.example.com のレコードを作成。AZ レコードは各 AZ のエンドポイント (VPC 内クライアント向け)、Global レコードはインターネット向けの公開エンドポイント。

💡 効果: VPC 内からのクエリは同一 AZ のエンドポイントに、インターネットからのクエリは Global レコードに自動的に振り分けられ、単一の DNS 名で両方のアクセス経路を最適化。

🔗 関連サービス・機能

→Amazon Route 53 Resolver (VPC Resolver): VPC 内からのクエリ元 AZ 情報を Route 53 に伝達し、AZ アフィニティルーティングを実現する基盤
→Route 53 ヘルスチェック: AZ アフィニティレコードと関連付けることで、異常時のフォールバックを実現
→Amazon EC2: describe-availability-zones API で AZ ID と Zone Group を確認。インスタンスメタデータ placement/availability-zone-id からも AZ ID を取得可能
→Elastic Load Balancing: AZ ごとの内部 ALB / NLB を AZ アフィニティレコードのルーティング先として利用可能

📋 まとめ

Route 53 の AZ アフィニティルーティングにより、DNS レベルでトラフィックをクライアントと同一の AZ 内に維持できるようになり、レイテンシーと AZ 間データ転送コストの削減が可能になりました。マイクロサービス間通信やセルベースアーキテクチャを採用している場合は、本機能の適用によるコスト・パフォーマンス改善の効果を検証することを推奨します。

✓導入時はヘルスチェックの関連付けを忘れずに行う
✓Global レコードの作成で VPC 外クエリへの応答を確保する
