最小集計しきい値サポート

📅 リリース日: 2026 年 8 月 13 日 ｜ 機能: Minimum Aggregation Thresholds & Comparison Controls

📌 概要

AWS Clean Rooms のカスタム分析ルール (Custom analysis rule) が最小集計しきい値をサポート。クエリ結果のすべての行が指定した数以上の異なるデータ主体 (例: ユーザー ID) を表すことを保証し、個人や少人数グループの情報漏洩リスクを自動的に防止できます。

データ提供者はアイデンティティ列と最小アイデンティティ数を設定し、出力列ごとのしきい値上書きや、比較コントロール (Comparison Controls) による列の利用制限も可能。広告測定、メディアプランニング、オーディエンス分析などのデータコラボレーションで、プライバシー保護とクエリの柔軟性を両立する重要な機能強化です。

😰 アップデート前の課題
✗カスタム SQL に集計しきい値保護を適用するには、事前承認済みの分析テンプレートと手動コードレビューが必要
✗データ提供者はパートナーのクエリを 1 つずつレビューする運用負荷を負担
✗アドホッククエリを許可すると、少人数グループを特定する結果が返るリスクを制御できない
😊 アップデート後の改善
✓事前構造化クエリや承認ワークフローなしで、カスタム分析ルールに直接しきい値を設定可能
✓各行が最低 N 人の異なるデータ主体を表すことを自動保証、しきい値未満の行は自動抑制
✓列ごとのしきい値上書きと比較コントロールで、きめ細かなプライバシー制御を実現

💡 データ提供者がカスタム分析ルールに最小集計しきい値を設定すると、クエリ実行者のアドホッククエリに対して AWS Clean Rooms が自動的にしきい値を適用し、条件を満たさない行を結果から抑制します。

⚡ 主要機能

1️⃣ 最小集計しきい値 (Aggregation Thresholds)
  • アイデンティティ列 (identityColumns) と最小アイデンティティ数 (minimumIdentityCount) を指定し、各結果行が最低 N 人の異なるデータ主体を表すことを保証
  • minimumIdentityCount は 2〜100,000 の範囲で設定可能
  • アイデンティティ列は string、varchar、char 型である必要がある
  • 集計タイプは COUNT_DISTINCT (異なる値のカウント)
2️⃣ 出力列ごとのしきい値の上書き (Output Column Thresholds)
  • 出力列の機密性レベルに応じて、列ごとに異なる minimumIdentityCount を適用可能
  • 例: 低機密の campaign_id にはしきい値 5、高機密の postal_code や income_bracket にはしきい値 100 を適用
  • 上書き値に 0 を指定すると、その列を最小集計の対象から除外できる
3️⃣ 集計関数内のネスト式の制御 (Allowed Aggregate Expression Type)
  • デフォルトは COLUMNS_ONLY で、集計関数内には列のみ許可 (例: SUM(cost))。プライバシー強化構成として推奨
  • 信頼できるパートナーとの場合は ANY_EXPRESSION で SUM(cost * quantity) のような式も利用可能 (再識別リスク増のため、プライバシー・法務・コンプライアンスチームへの相談が必要)
4️⃣ 比較コントロール (Comparison Controls)
  • allowedLiteralComparisonColumns: リテラル値との比較 (例: WHERE state = 'New York') を許可する列を指定
  • allowedColumnComparisonColumns: 列間比較によるテーブル結合 (例: JOIN ... ON t.user_id = partner.user_id) を許可する列を指定
  • 郵便番号や年齢層などカーディナリティの低い準識別子列による意図しない絞り込みリスクを軽減
  • 最小集計しきい値との併用が推奨構成

💻 カスタム分析ルールの設定例

JSON カスタム分析ルール設定 
{
  "aggregationThresholds": [
    {
      "identityColumns": [
        "user_id"
      ],
      "minimumIdentityCount": 100,
      "type": "COUNT_DISTINCT",
      "allowedAggregateExpressionType": "COLUMNS_ONLY",
      "outputColumnThresholds": [
        {
          "outputColumnName": "campaign_id",
          "minimumIdentityCount": 5
        }
      ]
    }
  ],
  "comparisonControls": {
    "allowedLiteralComparisonColumns": [
      "campaign_id",
      "event_date"
    ],
    "allowedColumnComparisonColumns": [
      "user_id"
    ]
  },
  "allowedAnalyses": [
    "ANY_QUERY"
  ],
  "allowedAnalysisProviders": [
    "444455556666"
  ]
}

💡 この例では、すべての結果行が最低 100 人の異なるユーザーを表すことを要求しつつ、低機密の campaign_id 列にはしきい値 5 を適用し、campaign_id と event_date でのリテラルフィルタリングと user_id での結合を許可しています。

🛠️ 設定方法

✅ 前提条件

✓AWS Clean Rooms のコラボレーションが作成済みであること
✓設定済みテーブル (Configured Table) が作成済みであること
✓アイデンティティ列が string、varchar、char 型であること

📝 手順

1
カスタム分析ルールの設定を開始
AWS Clean Rooms コンソールの [Tables] で対象の設定済みテーブルを選択し、[Configure analysis rule] から分析ルールタイプで [Custom] を選択。[Review each new analysis] または [Allow any analysis by specific collaborators] を選択
2
最小集計しきい値を設定
[Enforce aggregation thresholds?] に [Yes] を選択し、アイデンティティ列と最小アイデンティティ数 (2〜100,000) を指定。[Allow nested expressions in aggregate functions?] はデフォルトの [No] を維持 (プライバシー強化構成)。オプションで [Add column override] により列ごとのしきい値上書きを追加
3
比較コントロールを設定 (推奨)
[Custom list] を選択して明示的に制限する構成が推奨。リテラル比較を許可する列と、列間比較 (結合) を許可する列をそれぞれ選択し、設定をレビュー後 [Configure analysis rule] を選択。設定済みテーブルをコラボレーションに関連付ける

✓列単位のきめ細かな制御: 機密性レベルに応じた柔軟なポリシー設計
✓多層防御: しきい値 + 比較コントロール + 出力禁止列の組み合わせ
⚠️ 制約事項・考慮点
制限事項
✗差分プライバシー (Differential Privacy) とは併用不可
✗アイデンティティ列は string / varchar / char 型に限定
✗minimumIdentityCount は 2〜100,000 (列ごとの上書きでは 0 による除外も可能)
考慮すべき点
⚠しきい値単独では準識別子列 (郵便番号、年齢層など) による絞り込みを防げないため、比較コントロールとの併用を推奨

⚠抑制された行の存在を考慮して分析結果を解釈する必要がある

🎯 ユースケース

📰 ユースケース 1: パブリッシャーと広告主のメディアプランニング

シナリオ: パブリッシャー (データ提供者) が広告主とメディアプランニングのコラボレーションを実施。広告主にアドホッククエリを許可しつつ、共通ユーザーが 1,000 人未満の小規模な地方郵便番号の結果は自動的に除外したい。

JSON 実装例 
{
  "aggregationThresholds": [
    {
      "identityColumns": ["user_id"],
      "minimumIdentityCount": 1000,
      "type": "COUNT_DISTINCT",
      "allowedAggregateExpressionType": "COLUMNS_ONLY"
    }
  ],
  "allowedAnalyses": ["ANY_QUERY"],
  "allowedAnalysisProviders": ["444455556666"]
}
✅ 効果: 広告主は事前承認なしで自由にメディアプランニング分析を実行でき、パブリッシャーは小規模グループの情報漏洩リスクをサービス側の保証で排除できる。
📊 ユースケース 2: キャンペーンリーチ測定

シナリオ: パブリッシャーの impressions テーブル (user_id、campaign_id、event_date) に対し、広告主がキャンペーンの日次リーチ (異なるユーザー数) を測定する。

SQL 日次リーチ測定クエリ 
SELECT event_date, COUNT(DISTINCT user_id) AS reach
FROM impressions
WHERE event_date >= '2026-01-01' AND campaign_id = 'Holiday Promotion'
GROUP BY event_date;
✅ 効果: 最小集計しきい値 100 の設定により、100 人以上の異なるユーザーに裏付けられた日付の行のみが返却され、閲覧者が少なかった日の行は自動的に抑制される。個人や少人数グループの情報を明かすことなく日次リーチを把握できる。
🎚️ ユースケース 3: 機密性レベルに応じた列ごとのしきい値設計

シナリオ: データ提供者のテーブルに、機密性の低い campaign_id と機密性の高い postal_code や income_bracket が混在。列ごとに適切な保護レベルを設定したい。

JSON 列ごとのしきい値上書き 
{
  "aggregationThresholds": [
    {
      "identityColumns": ["user_id"],
      "minimumIdentityCount": 100,
      "type": "COUNT_DISTINCT",
      "allowedAggregateExpressionType": "COLUMNS_ONLY",
      "outputColumnThresholds": [
        {
          "outputColumnName": "campaign_id",
          "minimumIdentityCount": 5
        }
      ]
    }
  ]
}
✅ 効果: デフォルトしきい値 100 で高機密列を保護しつつ、低機密の campaign_id はしきい値 5 に緩和することで、プライバシー保護と分析の有用性のバランスを列単位で最適化できる。

従来の事前承認方式。特定のクエリのみを許可したい場合は引き続き有効な選択肢。

🧮 AWS Clean Rooms Differential Privacy

数学的に厳密なプライバシー保護フレームワーク。ただし最小集計しきい値および比較コントロールとは併用不可。

構造化されたクエリのみを許可する既存の分析ルールタイプ。集計分析ルールにも同様の集計制約の概念があり、今回のアップデートでカスタム分析ルールでも同等の保護が利用可能に。

🆔 AWS Entity Resolution

コラボレーション前の ID 解決に利用でき、アイデンティティ列の品質向上に寄与。

✓データコラボレーション運用チームは、比較コントロールとの併用を推奨構成として、既存のカスタム分析ルールへのしきい値追加を検討
