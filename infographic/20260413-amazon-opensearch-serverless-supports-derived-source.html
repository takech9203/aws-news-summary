Derived Source によるストレージ最適化

_source フィールドをオンザフライで再構築し、ストレージ消費量を大幅に削減
2026 年 4 月 13 日

📋 概要

Amazon OpenSearch Serverless において Derived Source のサポートが発表されました。Derived Source は、インデックス内に _source フィールドの個別コピーを保持する代わりに、既にインデックスに格納されている値からオンザフライで _source フィールドを再構築する機能です。

これにより、ドキュメントのソースデータを二重に保持する必要がなくなり、特に多数のインデックス済みフィールドを含む時系列データやログ分析コレクションにおいて大きなストレージ削減効果が期待できます。

🔄 Before / After

❌ Before - アップデート前
  • ドキュメントをインデックスする際に元の _source フィールドを個別に保存する必要があり、インデックス済みフィールドとの間でデータの重複が発生
  • 時系列データやログ分析など多数のフィールドを持つドキュメントでは、_source の保持がストレージ消費量の大きな割合を占めていた
  • _source を無効化するとハイライトや _reindex などの機能が利用できなくなるトレードオフがあった
✅ After - アップデート後
  • Derived Source を有効にすることで、_source フィールドの個別保存が不要になり、ストレージ消費量を大幅に削減可能
  • 必要時にインデックスの値から動的に再構築するため、検索結果の取得やハイライトなどの機能はそのまま利用可能
  • インデックスの作成時またはマッピング更新時に設定でき、既存ワークフローへの影響を最小限に抑えた導入が可能

⚡ 主要機能

🔄 Derived Source による _source フィールドの動的再構築
  • インデックスに格納されている値から _source フィールドをオンザフライで再構築
  • 元のドキュメントの個別コピーを保持する必要がなくなり、ストレージの重複を排除
  • 検索結果の返却時に _source が必要な場合にのみ再構築処理が実行される
⚙️ インデックスレベルでの柔軟な設定
  • インデックスの作成時にマッピング設定で Derived Source を有効化可能
  • 既存インデックスのマッピング更新時にも設定を変更可能
  • コレクション内でインデックスごとに異なる設定を適用できるため、ワークロードに応じた最適化が可能
🔗 既存機能との互換性
  • _source フィールドの無効化とは異なり、検索結果の取得、ハイライト、スクリプトフィールドなどの _source 依存機能がそのまま利用可能
  • クエリや集計の動作に影響を与えずにストレージ最適化を実現
  • 既存のアプリケーションコードの変更は不要

🛠️ 設定方法

前提条件: Amazon OpenSearch Serverless コレクションが作成済みであること、適切な IAM ポリシーでアクセスが許可されていること、データアクセスポリシーが設定済みであること。
1
Derived Source を有効にしたインデックスの作成

_source の mode を derived に設定することで、ドキュメントのソースデータをインデックスの値から動的に再構築するようになります。

Bash Derived Source 有効化 
curl -X PUT "https://<collection-endpoint>/my-logs-index" \
  -H "Content-Type: application/json" \
  -d '{
    "mappings": {
      "_source": {
        "mode": "derived"
      },
      "properties": {
        "@timestamp": { "type": "date" },
        "message": { "type": "text" },
        "level": { "type": "keyword" },
        "service": { "type": "keyword" },
        "trace_id": { "type": "keyword" },
        "duration_ms": { "type": "long" }
      }
    }
  }'
2
既存インデックスのマッピング更新

既存のインデックスのマッピングを更新して Derived Source を有効にします。更新後に取り込まれるドキュメントから適用されます。

Bash 既存インデックスの更新 
curl -X PUT "https://<collection-endpoint>/my-existing-index/_mapping" \
  -H "Content-Type: application/json" \
  -d '{
    "_source": {
      "mode": "derived"
    }
  }'
3
インデックス設定の確認

マッピング設定を表示し、_source の mode が derived と表示されることを確認します。

Bash 設定確認 
curl -X GET "https://<collection-endpoint>/my-logs-index/_mapping?pretty"

ドキュメントを取り込み、検索結果に _source フィールドが正しく含まれることを確認します。

⚠️ デメリット・制約事項

制限事項

🔸 _source の再構築にはインデックスの値を読み取る処理が必要なため、従来の直接読み取りと比較してわずかなクエリレイテンシーのオーバーヘッドが発生する可能性がある
🔸 インデックスに格納されていないフィールド (例: enabled: false や index: false のみのフィールド) は再構築時に復元できない場合がある
🔸 テキスト分析によってトークン化されたフィールドは、元のフィールド値と完全に一致する再構築が保証されない場合がある

考慮すべき点

パフォーマンス: _source の頻繁な取得が必要なワークロードでは、再構築のオーバーヘッドがクエリパフォーマンスに影響する可能性があるため、事前のベンチマークテストを推奨
フィールド設定: 全てのフィールドが適切にインデックスされていることを確認する必要がある。_source から値を取得していたフィールドが index: false に設定されている場合、Derived Source 有効時に値が取得できなくなる可能性がある
最適化の組み合わせ: 先日リリースされた Zstandard 圧縮コーデックと組み合わせることで、さらなるストレージ最適化が期待できる

🌡️ ユースケース 2: IoT 時系列データの効率的な保存
数万台の IoT デバイスからのセンサーデータを時系列コレクションに格納している。各デバイスから 1 分間隔でデータが送信され、デバイス ID、タイムスタンプ、複数のセンサー値で構成される。データ量の増加に伴いストレージコストが課題になっている。

🔒 ユースケース 3: セキュリティログの長期保持
コンプライアンス要件により、セキュリティイベントログを長期間保持する必要がある。大量のセキュリティログを Amazon OpenSearch Serverless に格納し、必要に応じて検索・分析を行うが、アクセス頻度は低い。
