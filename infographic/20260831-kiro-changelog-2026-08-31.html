🌿 リポジトリ選択時のブランチ指定

Pick a Branch When You Pick a Repository ｜ リリース日: 2026 年 8 月 31 日

📌 概要

Kiro Web のセッション開始時に、リポジトリセレクター内で作業対象のブランチを指定できるようになりました。GitHub または GitLab のリポジトリを選択する際にブランチを選ぶと、エージェントがそのブランチをクローンし、その内容を起点として作業を進めます。

フィーチャーブランチやリリースブランチなど、デフォルトブランチ以外を直接指定して AI エージェントに作業を依頼できるため、ブランチ戦略を運用しているチームに有用なアップデートです。

❌ Before: アップデート前の課題
  • ✗セッションは常にデフォルトブランチ (main など) から開始する必要があった
  • ✗進行中のフィーチャーブランチやリリースブランチを前提とした作業を直接依頼できなかった
  • ✗デフォルト以外のブランチを扱うには、開始後に切り替えの追加指示や手順が必要だった
✅ After: アップデート後の改善
  • ✓リポジトリ選択と同時に、セッションの起点となるブランチを指定できる
  • ✓エージェントが指定ブランチをクローンし、その内容を前提に作業を積み上げられる
  • ✓GitHub と GitLab のどちらでも同じ操作でブランチを指定できる

セッション開始時にリポジトリとブランチをセレクター内で選択し、エージェントが指定ブランチをクローンして作業を開始するフロー

⚙️ 主要機能

1️⃣ リポジトリセレクター内でのブランチ選択

→ GitHub / GitLab のリポジトリ選択時に、同じセレクター内で作業対象のブランチを選択可能

→ デフォルトブランチから開始する必要がなくなり、任意のブランチを起点にできる

→ リポジトリ選択とブランチ選択が 1 つの操作フローにまとまり、セッション開始前に作業起点が確定

2️⃣ 指定ブランチのクローンと作業の継続

→ エージェントは選択されたブランチをクローンし、そのブランチの内容を前提に作業を積み上げる

→ 進行中のフィーチャーブランチに対する追加実装や修正をエージェントに直接依頼できる

3️⃣ GitHub と GitLab の両方に対応

→ どちらのリポジトリでも同じ操作でブランチを指定可能

→ 複数の Git ホスティングサービスを併用する環境でも一貫した体験で利用できる

🛠️ 設定方法

✅ 前提条件

  • →Kiro Web を利用できるアカウントを持っていること
  • →GitHub または GitLab のリポジトリを Kiro に接続済みであること
  • →作業対象のブランチがリモートリポジトリに存在すること

セッション用のリポジトリを選択する際、リポジトリセレクター内で作業を開始したいブランチを選択します。デフォルトブランチ以外のフィーチャーブランチやリリースブランチも指定できます。エージェントが指定ブランチをクローンした状態でセッションが開始されるため、そのブランチの内容を前提としたタスクをそのまま依頼できます。

💡 メリット

💼 ビジネス面
  • ✓開発サイクルの短縮: 進行中のブランチへの作業を直接依頼でき、余分な手順や待ち時間を削減
  • ✓ブランチ戦略との整合: GitFlow やリリースブランチ運用を崩さずに AI エージェントを組み込める
  • ✓チームコラボレーションの円滑化: レビュー中や開発中のブランチをそのまま起点にできる
🔧 技術面
  • ✓正確な作業コンテキスト: 指定ブランチの最新内容をクローンするため、デフォルトブランチとの差分に起因する不整合を回避
  • ✓操作の簡素化: セッション開始後のブランチ切り替え指示が不要
  • ✓マルチプラットフォーム対応: GitHub と GitLab で同じ操作性、手順差異なし

⚠️ デメリット・制約事項

🚧 制限事項

  • ⚠️本機能は Kiro Web のセッションに関するアップデートであり、Changelog には IDE や CLI に関する記載はありません
  • ⚠️対応する Git ホスティングサービスとして記載されているのは GitHub と GitLab です

🤔 考慮すべき点

  • 💭意図したブランチを選択しているか、セッション開始前に確認することが望ましい
  • 💭作業対象のブランチが古い場合、リモートの最新状態を反映してから開始すると、作業結果と実際のコードベースの乖離を防げる

🎯 ユースケース

🧩 ユースケース 1: フィーチャーブランチでの追加実装

シナリオ: feature/user-auth ブランチで認証機能を実装中で、残りのタスクをエージェントに依頼したい

実装例: セッション作成時にセレクターで feature/user-auth を指定し、「テストコードの追加とエラーハンドリングの実装」を依頼

✅ 効果: 進行中の実装内容を前提に作業を積み上げるため、デフォルトブランチとの差分を意識せずに開発を継続できる
🚀 ユースケース 2: リリースブランチへのバグ修正

シナリオ: リリース準備中の release/2.0 ブランチのバグを、main の新機能開発と切り離して修正したい

実装例: release/2.0 ブランチを選択し、バグの内容と再現手順を伝えて修正を依頼、リリースブランチ向けマージリクエストとしてレビュー

✅ 効果: リリースブランチの内容だけを起点とした修正が可能になり、main ブランチの未リリース変更が混入するリスクを回避
🦊 ユースケース 3: GitLab 上の長期ブランチのリファクタリング

シナリオ: GitLab で運用中の長期開発ブランチ develop を、デフォルトブランチに影響を与えずにリファクタリングしたい

実装例: GitLab リポジトリと develop ブランチを指定し、対象モジュールと方針を指示、develop ブランチ上の変更としてレビュー・マージ

✅ 効果: GitHub と同じ操作で GitLab のブランチを起点にでき、既存のブランチ運用を変えずにエージェントの支援を受けられる

📝 まとめ

Kiro Web のセッション開始時に、GitHub または GitLab リポジトリのブランチをリポジトリセレクター内で直接指定できるようになり、デフォルトブランチ以外を起点とした AI エージェントへの作業依頼が容易になりました。

🚀 フィーチャーブランチやリリースブランチを運用しているチームは、次回のセッション作成時にブランチ選択を活用し、進行中の作業への支援をエージェントに依頼することを推奨します。
