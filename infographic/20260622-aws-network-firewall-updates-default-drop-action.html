🛡️ AWS Network Firewall
デフォルトドロップアクションの変更

AWS Network Firewall
📅 リリース日: 2026 年 6 月 22 日
⚙️ 新規ポリシーのデフォルト動作変更

📌 概要

AWS Network Firewall は、新規に作成されるすべてのファイアウォールポリシーのデフォルトステートフルアクションを Application drop established (server-directed only) に変更しました。 従来のデフォルトであった bidirectional (双方向) 設定を置き換えるもので、新規ポリシー作成時に追加操作は不要です。

従来の双方向設定では、サーバーからクライアントへの正当な TCP パケット (ウィンドウ更新、キープアライブ、リセットなど) を意図せずドロップし、診断が困難な断続的な接続障害を引き起こす可能性がありました。 新デフォルトの「server-directed only」により、クライアント方向への正当なフロー制御パケットがドロップされなくなり、接続の信頼性が向上します。

⚠️ Before (bidirectional)
  • サーバー → クライアントの正当な TCP パケットを意図せずドロップする可能性
  • 断続的な接続失敗が発生
  • 間欠障害のため根本原因の特定が困難
→
✅ After (server-directed only)
  • サーバー方向のトラフィックのみがドロップ対象
  • クライアント方向の正当なフロー制御パケットは保護され接続信頼性が向上
  • 追加設定なしで安全なデフォルトの恩恵を享受

🗺️ アーキテクチャ図

新デフォルトでは、ステートフルエンジンはサーバー方向 (server-directed) のトラフィックのみをドロップ評価の対象とし、 サーバーからクライアントへのウィンドウ更新やキープアライブなどのフロー制御パケットはドロップされません。

⚡ 主要機能

1️⃣ デフォルトステートフルアクションの変更
✓新規作成されるすべてのファイアウォールポリシーのデフォルトが「Application drop established (server-directed only)」に変更
✓従来の「Application drop established (bidirectional)」(旧称: Application layer drop established) を置き換え
✓既存ポリシーの設定は変更されず、新規ポリシーにのみ適用
2️⃣ サーバー方向のみの評価 (server-directed only)
✓established 接続に対してクライアント → サーバー方向のトラフィックのみをドロップ対象とする
✓サーバー → クライアントの正当な TCP フロー制御パケット (ウィンドウ更新、キープアライブ、リセット) はドロップされない
✓これにより断続的な接続失敗を回避
3️⃣ PQC フラグメント化 TLS ハンドシェイクへの対応
✓ポスト量子暗号 (PQC) のフラグメント化された TLS ハンドシェイクで双方向設定が必要な既存環境はドキュメントを参照
✓双方向設定を継続する、または TCP ドロップルールに to_server フラグを追加する選択肢がある

📊 技術仕様: デフォルトアクションの比較

項目従来のデフォルト新しいデフォルト
アクション名Application drop established (bidirectional)Application drop established (server-directed only)
旧称Application layer drop established-

📖 ステートフルアクションの用語

用語説明
establishedTCP ハンドシェイク (SYN / SYN-ACK / ACK) を完了し確立された接続上のトラフィック
server-directedクライアントからサーバーへ向かう方向のトラフィックを評価対象とする
bidirectionalクライアントとサーバーの双方向のトラフィックを評価対象とする
フロー制御パケットウィンドウ更新、キープアライブ、リセットなど TCP 接続の維持に必要なパケット
🔧 API 変更履歴: 本アップデートは新規ファイアウォールポリシーのデフォルト動作の変更であり、API メソッドの追加や変更は確認されていません。

🛠️ 設定方法

前提条件

✓AWS Network Firewall が利用可能なリージョンであること
✓ファイアウォールポリシーを作成・管理する権限を持つ IAM ユーザーまたはロール
✓Suricata 互換ルールの評価順序に関する基本的な理解

手順

ステップ 1: 新規ポリシーの作成
追加操作なしでデフォルトのステートフルアクションが「server-directed only」となります。特別な設定は不要です。
ステップ 2: 既存環境で双方向設定が必要かの確認
PQC のフラグメント化された TLS ハンドシェイクをサポートするために双方向設定が必要な場合は公式ドキュメントを参照。双方向設定を維持するか to_server フラグを追加します。
ステップ 3: 評価順序の管理
Suricata 互換ルールの評価順序を適切に管理することで意図したトラフィック制御を実現します。
Suricata to_server フラグでサーバー方向のみを対象とする例 
# established 接続のうちサーバーへ向かう方向の TCP のみをドロップ対象とする
drop tcp any any -> any any (flow:to_server, established; sid:1; rev:1;)

上記ルールは established 状態の接続のうち、サーバーへ向かう (to_server) 方向の TCP トラフィックのみをドロップ対象とします。 これによりサーバーからクライアントへのフロー制御パケットはドロップされません。

⚠️ デメリット・制約事項

制限事項

✗本変更は新規作成されるポリシーにのみ適用され、既存ポリシーの設定は変更されない
✗PQC のフラグメント化された TLS ハンドシェイクで双方向設定が必要な環境では追加の設定確認が必要

考慮すべき点

💡既存環境で双方向設定に依存している場合は、デフォルト変更の影響を理解した上で運用する
💡双方向設定が必要なケースでは、AWS 公式ドキュメントに従って適切に設定を行う

💡 ユースケース

① 一般的な VPC ネットワーク保護
シナリオ: VPC 内のワークロードに新規ファイアウォールポリシーを作成しステートフルなトラフィック制御を行う
実装: 新規ファイアウォールポリシーを作成 → デフォルトで server-directed only が適用
▶ 効果: 追加設定なしで正当なフロー制御パケットがドロップされず接続の信頼性を確保
② 断続的な接続障害の解消
シナリオ: 従来の双方向設定により長時間接続でウィンドウ更新やキープアライブがドロップされ断続的な切断が発生
実装: 新規ポリシーへ移行、または既存ポリシーを server-directed only に変更
▶ 効果: フロー制御パケットがドロップされなくなり長時間接続の安定性が向上
③ PQC フラグメント化 TLS ハンドシェイクのサポート
シナリオ: PQC を利用しフラグメント化された TLS ハンドシェイクをサポートするために双方向の評価が必要
実装: bidirectional 設定を維持、または TCP ドロップルールに flow:to_server フラグを追加
▶ 効果: PQC のフラグメント化 TLS ハンドシェイクをサポートしつつ正当なフロー制御パケットのブロックを回避

📝 まとめ

今回のアップデートにより、AWS Network Firewall の新規ファイアウォールポリシーは、より安全な server-directed only をデフォルトのステートフルアクションとして採用します。 これにより、サーバーからクライアントへの正当なフロー制御パケットのドロップに起因する断続的な接続障害を回避できます。 新規ポリシーでは追加操作なしでこのメリットを得られますが、PQC のフラグメント化された TLS ハンドシェイクをサポートするために 双方向設定が必要な既存環境については、公式ドキュメントを参照して適切に設定を確認することを推奨します。
