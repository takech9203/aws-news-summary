Amazon CloudWatch

📡 CloudWatch Observability EKS アドオンが
テレメトリフィルタリングに対応

🗓️ リリース日: 2026 年 11 月 20 日 | 機能: OpenTelemetry フィルター (otelFilters) によるクラスター全体のテレメトリフィルタリング

📋 概要

Amazon CloudWatch Observability EKS アドオンが、テレメトリフィルタリングに対応しました。名前空間、メトリクス名、Pod / ノードラベルに対するクラスター全体の include / exclude リストを定義することで、利用していないテレメトリの取り込みを送信前に停止し、取り込みコストを削減できます。

CloudWatch の OpenTelemetry テレメトリは取り込み量 (GB) に応じて課金されるため、フィルタリングがそのままコスト削減につながります。フィルターはアドオン設定の otelFilters として定義され、要件が変化しても 1 回のアドオン設定更新だけで変更できます。

❌ アップデート前の課題
  • 監視していない名前空間や未使用メトリクスにも取り込み料金が発生
  • 最大 150 のラベル付与により、高カーディナリティラベルがデータ量を増加
  • 取り込み量の制御には、アプリ側の計装変更やコレクター設定の個別調整が必要
✅ アップデート後の改善
  • 名前空間、メトリクス名、Pod / ノードラベルの include / exclude をクラスター全体で定義し、不要なテレメトリを送信前に破棄
  • 取り込み課金の対象データ量が減少し、コストを直接削減
  • 1 回のアドオン設定更新でフィルターを変更でき、要件変化に追随しやすい

CloudWatch エージェントが収集した各ソースのテレメトリは、otelFilters で定義した include / exclude リストで評価され、除外対象は CloudWatch へ送信される前に破棄されるため、取り込み課金の対象になりません。

⚙️ 主要機能

1️⃣ 名前空間フィルター (otelFilters.namespaces)
  • 除外した名前空間の Pod / コンテナテレメトリを破棄
  • OTel Container Insights のメトリクスとログ、OTLP 受信のメトリクス・トレース・ログ、ServiceMonitor / PodMonitor スクレイピングに適用
  • ノードレベルメトリクス、ホストログ、Karpenter や KEDA などコントロールプレーンコンポーネントには適用されず、Kubernetes 名前空間を持たないレコードは常に通過
  • GPU、AWS Trainium / Inferentia、EFA のデバイスメトリクスは破棄されない。除外対象の名前空間の Pod がデバイスを使用している場合、デバイスメトリクスは保持され、Pod・名前空間・コンテナ属性のみ除去
2️⃣ メトリクス名フィルター (otelFilters.metricNames)
  • CloudWatch へ送信される時点のメトリクス名に大文字小文字を区別してマッチング
  • OTel Container Insights のメトリクス、OTLP 受信のメトリクス (スパンメトリクス含む)、ServiceMonitor / PodMonitor スクレイピングに適用。ログには適用されない
  • 空でない include リストを指定すると、リストにあるメトリクスのみが保持され、スパンメトリクスを含む他のすべてのメトリクスが破棄される
  • include リストに up を含めない場合、スクレイプ対象の up メトリクスも破棄される点に注意
3️⃣ Pod / ノードラベルフィルター (otelFilters.podLabels / nodeLabels)
  • エージェントが k8s.pod.label.* / k8s.node.label.* 属性として付与するラベルを制御
  • include (収集するラベル)、exclude (収集後に除去)、recommendedExclusions (高カーディナリティラベルの組み込み除外リスト、デフォルト true) の 3 つの設定
  • 組み込み除外リストには、トポロジー、ホスト名、インスタンスタイプのラベル、Karpenter / EKS Auto Mode のインスタンスラベル、pod-template-hash などのコントローラーリビジョンマーカーを含む
  • 優先順位は exclude > 名前指定の include エントリ > 組み込みリスト。組み込みリストの特定ラベルだけ残したい場合は include に名前を指定
4️⃣ シンプルなマッチングルール
  • エントリは完全一致の名前、prod-* のようなプレフィックス + *、または * 単独のいずれか
  • 空の include リスト、または * を含む include リストはすべてを含める
  • exclude が include より優先され、マッチングは大文字小文字を区別

🔬 技術仕様

📌 フィルターの適用範囲

フィルター適用対象
otelFilters.namespacesOTel Container Insights のメトリクス / ログ、OTLP 受信のメトリクス / トレース / ログ、ServiceMonitor / PodMonitor スクレイピング
otelFilters.metricNamesOTel Container Insights のメトリクス、OTLP 受信のメトリクス (スパンメトリクス含む)、ServiceMonitor / PodMonitor スクレイピング (ログは対象外)
otelFilters.podLabels / otelFilters.nodeLabelsOTel Container Insights のメトリクス / ログ、OTLP 受信のメトリクス / トレース / ログ、ServiceMonitor / PodMonitor スクレイピング

📌 マッチングルール

項目詳細
エントリ形式完全一致の名前、プレフィックス + * (例: prod-*)、または * 単独
空の includeすべてを含める (* を含む場合も同様)
優先順位exclude が include より優先
大文字小文字区別する (dcgm_fi_dev_gpu_util は DCGM_FI_DEV_GPU_UTIL にマッチしない)
ラベルフィルターの優先順位exclude > 名前指定の include エントリ > recommendedExclusions の組み込みリスト

📌 設定例

JSON otelFilters 設定例 
{
  "otelFilters": {
    "namespaces": {
      "exclude": [
        "kube-system",
        "test-*"
      ]
    },
    "metricNames": {
      "exclude": [
        "container_network_*"
      ]
    },
    "podLabels": {
      "include": [
        "app",
        "team"
      ]
    },
    "nodeLabels": {
      "include": [
        "node.kubernetes.io/instance-type",
        "topology.kubernetes.io/zone"
      ]
    }
  }
}

kube-system 名前空間と test- で始まる名前空間のテレメトリを破棄し、container_network_* メトリクスを除外し、Pod ラベルは app と team、ノードラベルは指定した 2 つのみを収集する設定です。

🛠️ 設定方法

✅ 前提条件

✓Amazon CloudWatch Observability EKS アドオンまたは Helm チャートのバージョン 8.0.0 以降
✓OTel Container Insights、OTLP 取り込み、ServiceMonitor / PodMonitor スクレイピングのいずれかを利用していること
✓アドオン設定を更新するための IAM 権限 (eks:UpdateAddon など)
1
アドオンのバージョンを確認
Bash アドオンバージョンの確認 
aws eks describe-addon \
  --cluster-name my-cluster \
  --addon-name amazon-cloudwatch-observability \
  --query addon.addonVersion --output text

8.0.0 未満の場合は aws eks update-addon の --addon-version でバージョン 8.0.0 以降に更新します。

2
otelFilters を含むアドオン設定を適用
Bash アドオン設定の更新 
aws eks update-addon \
  --cluster-name my-cluster \
  --addon-name amazon-cloudwatch-observability \
  --configuration-values '{
    "otelFilters": {
      "namespaces": {
        "exclude": ["kube-system", "test-*"]
      },
      "metricNames": {
        "exclude": ["container_network_*"]
      }
    }
  }'

--configuration-values はアドオン設定全体を置き換えるため、既存の設定値がある場合はマージした JSON を指定します。フィルターを変更すると、影響を受けるエージェント Pod が再起動されます。

3
取り込み量の変化を確認

CloudWatch の請求メトリクスや Cost Explorer で、フィルター適用前後の取り込み量 (GB) を比較します。除外しすぎた場合は、include / exclude リストを調整して再度アドオン設定を更新します。ダッシュボードやアラームが参照しているメトリクス・ラベルを誤って除外していないかも確認します。

💡 メリット

💼 ビジネス面

✓取り込みコストの直接削減: OpenTelemetry テレメトリは取り込み量 (GB) 課金のため、不要なテレメトリの破棄がそのままコスト削減になる
✓運用の一元化: アプリケーションごとの計装変更ではなく、クラスター全体のアドオン設定 1 か所でコスト制御を実施できる
✓変化への追随が容易: クラスターの要件が変わっても、1 回のアドオン設定更新でフィルターを変更できる

🔧 技術面

✓複数ソースへの一貫した適用: OTel Container Insights、OTLP 取り込み、ServiceMonitor / PodMonitor スクレイピングのすべてに同じフィルターが適用される
✓ラベルのカーディナリティ制御: recommendedExclusions により高カーディナリティラベルがデフォルトで除外され、保存・クエリ対象のデータ量を抑制できる
✓シンプルなルール体系: 完全一致とプレフィックスワイルドカードのみの明快なマッチングルールで、意図しないフィルタリングを避けやすい

⚠️ デメリット・制約事項

🚧 制限事項

✗EKS アドオンおよび Helm チャートのバージョン 8.0.0 以降が必要
✗マッチングは大文字小文字を区別し、プレフィックス + * と * 単独以外のパターン (正規表現など) は使用できない
✗名前空間フィルターはノードレベルメトリクス、ホストログ、コントロールプレーンコンポーネントのメトリクスには適用されない
✗GPU / Trainium / Inferentia / EFA のデバイスメトリクスは名前空間フィルターでは破棄されない (Pod・名前空間・コンテナ属性のみ除去)
✗メトリクス名フィルターはログには適用されない

🤔 考慮すべき点

⚠️フィルターを変更すると影響を受けるエージェント Pod が再起動される (エージェントは起動時にのみ設定を読み込むため)
⚠️metricNames に空でない include リストを指定すると、スパンメトリクスを含むリスト外のすべてのメトリクスが破棄される。スクレイプ失敗検知に使う up メトリクスも include に含めないと破棄される
⚠️エージェントは topology.kubernetes.io/zone など一部のラベルを内部処理用に常に読み取り、フィルターで除外されている場合は使用後に除去する
⚠️ダッシュボード、アラーム、PromQL クエリが参照しているメトリクスやラベルを除外すると、データ欠落によりアラームが意図しない状態になる可能性があるため、適用前に影響範囲の確認が必要

🎯 ユースケース

📁 ユースケース 1: 非本番名前空間のテレメトリ除外

シナリオ: 開発・検証用の名前空間が多数存在するが、CloudWatch で実際に監視しているのは本番の名前空間のみで、非本番分の取り込みコストを削減したい。

JSON実装例
{
  "otelFilters": {
    "namespaces": {
      "exclude": ["dev-*", "staging-*", "test-*"]
    }
  }
}

効果: 非本番名前空間の Pod / コンテナテレメトリが送信前に破棄され、取り込み量と料金を削減できる。本番の監視には影響しない。

📉 ユースケース 2: 高カーディナリティメトリクスの破棄

シナリオ: cAdvisor のネットワーク系メトリクスなど、系列数が多いわりにダッシュボードやアラームで使用していないメトリクスが取り込み量を押し上げている。

JSON実装例
{
  "otelFilters": {
    "metricNames": {
      "exclude": ["container_network_*", "node_scrape_*"]
    }
  }
}

効果: 使用していない高カーディナリティメトリクスを名前 (プレフィックス) 指定で破棄し、取り込み量を削減できる。必要になったら設定更新だけで復元できる。

🏷️ ユースケース 3: グルーピングに使うラベルのみの収集

シナリオ: メトリクスに最大 150 のラベルが付与されるが、PromQL でのグルーピングに使うのは app と team のみで、残りのラベルはデータ量を増やしているだけになっている。

JSON実装例
{
  "otelFilters": {
    "podLabels": {
      "include": ["app", "team"]
    },
    "nodeLabels": {
      "include": ["topology.kubernetes.io/zone"]
    }
  }
}

効果: 必要なラベルのみが k8s.pod.label.* / k8s.node.label.* 属性として付与され、各データポイントのサイズが減少して保存・クエリ対象のデータ量を抑制できる。

💰 料金

テレメトリフィルタリング機能自体に追加料金はありません。アドオン経由で送信されるテレメトリは Amazon EKS の OpenTelemetry 取り込みレートである USD 0.08/GB で課金されるため、フィルタリングによる取り込み量の削減がそのまま料金の削減になります。

使用量月額料金 (概算)

📝 まとめ

CloudWatch Observability EKS アドオンのバージョン 8.0.0 以降では、otelFilters による名前空間、メトリクス名、Pod / ノードラベルのクラスター全体フィルタリングで、利用していないテレメトリの取り込みを送信前に停止できるようになりました。OpenTelemetry テレメトリは取り込み量課金のため、不要データの破棄が直接的なコスト削減につながります。OTel Container Insights やカスタムテレメトリ取り込みを利用しているチームは、非本番名前空間と未使用メトリクス・ラベルの棚卸しから始め、アドオン設定更新によるフィルター適用を検討することを推奨します。
