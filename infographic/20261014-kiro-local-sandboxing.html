🔒 Kiro ローカルサンドボックス機能
Local Command Sandbox

Kiro 📅 リリース日: 2026 年 10 月 14 日 🌍 グローバル

📋 概要

Kiro IDE および Kiro CLI に、エージェントが実行するシェルコマンドを OS カーネルレベルで制限する「ローカルコマンドサンドボックス」機能が追加されました。エージェント自体はネイティブに動作したまま、エージェントが実行するコマンドのみがサンドボックス内で実行されます。

プラットフォームサンドボックス技術
🍎 macOSSeatbelt (sandbox-exec 経由)
🐧 Linuxbubblewrap
🪟 WindowsAppContainer

書き込みはプロジェクトディレクトリと一時領域に限定され、~/.ssh や ~/.aws などの認証情報パスへの読み取りはカーネルレベルで拒否、ネットワークアクセスはドメインベースのローカルプロキシを経由します。クラウドに出せないコード (データレジデンシー要件)、VPN 内の localhost サービス、Xcode を必要とする iOS ビルドなど、ローカル実行が必須の作業に OS レベルの保護を提供します。

❌ アップデート前の課題

✗エージェントのコマンドはユーザー権限をそのまま引き継ぎ、ファイルシステムとネットワークへフルアクセス
✗安全性は「人間の注意力」頼み。長時間タスクや並列セッションで承認疲れ (approval fatigue) が発生
✗read_file ツールは ~/.aws や ~/.ssh を拒否しても、シェル経由のスクリプトで回避可能だった
✗悪意がなくても、1 つの誤ったツールコールや意図の取り違えがインシデントにつながるリスク

✅ アップデート後の改善

✓コマンドとその子プロセスが OS カーネルが強制するサンドボックス内で実行される
✓~/.ssh/id_rsa などの読み取りは、ツール経由でもシェルワンライナーでもスクリプトでも一律カーネルレベルで拒否
✓ネットワークはローカルプロキシでドメイン単位にフィルタリングされ、承認済みサービスのみ到達可能
✓既存の Workspace Trust モデルと permissions.yaml をそのまま利用でき、新たな権限システムの学習は不要

エージェント本体はサンドボックスの外で動作し、エージェントが実行するコマンドのみが OS カーネルの制限下で実行されます。1 つのトラストポリシーが、ツールコール時と OS のシステムコール時の 2 段階で強制されます。

⚡ 主要機能

1️⃣ OS カーネルによるコマンド制限

  • エージェントが実行するシェルコマンドとすべての子プロセスがサンドボックス内で実行
  • macOS は Seatbelt (sandbox-exec 経由)、Linux は bubblewrap、Windows は AppContainer を使用
  • 書き込みはプロジェクトディレクトリと一時領域に限定、主要な認証情報パスの読み取りはカーネルで拒否
  • サンドボックスは承認後のコマンドの実行範囲を制限するもの。コマンド承認フロー自体は従来どおり動作

2️⃣ ドメインベースのネットワークフィルタリング

  • ネットワークアクセスはローカルプロキシを強制経由し、ドメイン単位でフィルタリング (クラウドサンドボックスと同じモデル)
  • networkAccess 設定で 3 つのモードから選択: DEFAULT_BLOCKED (デフォルト) / COMMON_DEPENDENCIES / DEFAULT_ALLOWED
  • permissions.yaml の sandbox_network ルールで特定ホストの許可・拒否を細かく制御可能

3️⃣ エージェント本体はサンドボックス外に維持

  • セッションを再起動せずにサンドボックスのオン・オフ切り替えやポリシー変更が可能
  • モデル呼び出しや Kiro バックエンド接続用の認証情報はサンドボックスに入らないため、内部プロセスが暴走しても悪用不可
  • ローカル MCP サーバーはホストネイティブプロセスとして変更なしで動作。mcpSandboxing 設定でサンドボックス経由に切り替えも可能
  • コンテナ・イメージ・VM は不要な制限付き子プロセスとして実装。最初のコマンド実行前の起動待ちが発生しない

4️⃣ 既存の Workspace Trust モデルとの統合

  • 新しい権限システムではなく、既存の fs_read、fs_write、ネットワークのケーパビリティルールを OS カーネルでも強制
  • 同じトラストポリシーが 2 回強制される: ツールコール要求時 + OS のシステムコールチェック時
  • 既存スコープ (管理者、ユーザー、ワークスペース、エージェント、セッション) がすべて自動的に適用

🔧 技術仕様

💻 プラットフォーム要件

プラットフォームサンドボックス技術要件
macOS Seatbelt (sandbox-exec 経由) 追加インストール不要
Linux bubblewrap (bwrap) bwrap を PATH に配置。COMMON_DEPENDENCIES およびホスト許可付き DEFAULT_BLOCKED には socat も必要
Windows AppContainer 初回のみ管理者セットアップが必要 (IDE はプロンプト表示、CLI では /sandbox setup)。DEFAULT_BLOCKED はセットアップ前でも動作

⚙️ sandbox.json の設定キー

キー必須値デフォルト
enabledはいtrue、false-
networkAccessいいえDEFAULT_BLOCKED、COMMON_DEPENDENCIES、DEFAULT_ALLOWEDDEFAULT_BLOCKED
mcpSandboxingいいえtrue、falsefalse

🌐 ネットワークモード

モード外部ネットワークアクセス
DEFAULT_BLOCKEDブロック。sandbox_network ルールで許可されたホストのみ到達可能 (デフォルト)
COMMON_DEPENDENCIES一般的なパッケージ・ソース・ビルド・コンテナサービスに到達可能。その他はルールで許可しない限りブロック
DEFAULT_ALLOWEDオープン。任意のホストに到達可能。ネットワークフィルタリングが不要な場合のみ使用

📦 サンドボックスの適用範囲

対象サンドボックス内か
エージェントが実行するターミナルコマンドとその子プロセス✅ 内
stdio MCP サーバープロセス (mcpSandboxing: true の場合)✅ 内
エージェントハーネスとモデルとの会話⬜ 外
組み込みファイルツール (権限ルールは引き続き適用)⬜ 外
リモート HTTP / SSE MCP サーバー⬜ 外

🛠️ 設定方法

✅ 前提条件

✓Kiro IDE 1.3 以降、または Kiro CLI 2.31 以降 (ローカル V3 セッション)
✓Linux の場合は bubblewrap (必要に応じて socat) のインストール
✓Windows の場合は初回の管理者セットアップ
1サンドボックスを有効化する

グローバルデフォルトとして ~/.kiro/settings/sandbox.json、またはプロジェクト単位のオーバーライドとして <project-root>/.kiro/settings/sandbox.json を作成します。

JSON ~/.kiro/settings/sandbox.json 
{
  "enabled": true,
  "networkAccess": "COMMON_DEPENDENCIES"
}
💡 ファイル編集なしでも有効化可能: Kiro CLI はローカルセッション (kiro-cli chat --v3) で /sandbox on を実行、Kiro IDE はコマンドパレットから Kiro: Open User Sandbox Config (JSON) を実行します。有効化されるとステータスバーに「Command sandbox: Active」と表示されます。
2permissions.yaml でポリシーを調整する
YAML ~/.kiro/settings/permissions.yaml 
rules:
  - capability: sandbox_network
    match: ['packages.internal.example.com']
    effect: allow
  # ワイルドカードルールより前に配置する
  - capability: sandbox_network
    match: ['uploads.example-corp.net']
    effect: deny
  - capability: sandbox_network
    match: ['*.example-corp.net']
    effect: allow
⚠️ sandbox_network ルールは記述順に評価され、最初にマッチしたルールが適用されます (他のケーパビリティと異なり deny が常に優先されるわけではないため、具体的なホストを広いワイルドカードより前に記述)。fs_read と fs_write のルールは、サンドボックス化されたコマンドが参照・書き込みできるパスにも適用されます。
3必要に応じて stdio MCP サーバーをラップする
JSON sandbox.json (mcpSandboxing 有効化) 
{
  "enabled": true,
  "networkAccess": "DEFAULT_BLOCKED",
  "mcpSandboxing": true
}

mcpSandboxing: true で stdio MCP サーバープロセスがシェルコマンドと同じサンドボックス内で起動されます。リモート HTTP / SSE MCP サーバーは影響を受けません。設定変更時にはローカル MCP サーバーが再起動されます (約 1 分かかる場合があります)。

💡 メリット

💼 ビジネス面

  • セキュリティインシデントリスクの低減: 誤ったツールコールや意図の取り違えがインシデントになるリスクを OS レベルの境界で抑制
  • データレジデンシー要件への対応: コードをクラウドに出せない環境でも、ローカル実行のまま保護を適用
  • 開発者の生産性向上: 承認疲れを軽減し、並列実行や長時間タスクでの人間の注意力への依存度を低減

⚙️ 技術面

  • 多層防御の実現: ツールコール権限チェック + OS システムコールレベルの二重強制で、シェルやスクリプト経由の回避を防止
  • 軽量な実装: コンテナ・イメージ・VM 不要の制限付き子プロセス。起動オーバーヘッドなし、セッション中にオン・オフ可能
  • 既存ポリシーの再利用: permissions.yaml と Workspace Trust、各スコープを自動的に引き継ぎ
  • 改ざん防止: グローバルポリシー有効時、プロジェクトファイルは制限強化方向のみ変更可能。クローンしたリポジトリによるネットワーク開放や無効化は不可

⚠️ デメリット・制約事項

🚧 制限事項

⚠デフォルトでは無効であり、明示的な有効化が必要
⚠Kiro IDE 1.3 以降、Kiro CLI 2.31 以降のローカル V3 セッションでのみ利用可能
⚠Linux では bubblewrap (および socat) の手動インストール、Windows では初回の管理者セットアップが必要
⚠プラットフォームのバックエンドが見つからない場合は「Unavailable」となり、コマンドは OS レベルの分離なしで実行される
⚠リモート HTTP / SSE MCP サーバーのネットワークトラフィックはサンドボックスのルールに従わない
⚠クラウドセッションには適用されない (クラウドセッションはマネージドクラウドサンドボックスを使用)

🤔 考慮すべき点

⚠サンドボックスは完全な分離を保証するものではない。提案されたコマンドのレビューと、実行禁止操作の deny ルール維持は引き続き必要
⚠コマンド承認を置き換えるものではなく、承認されたコマンドの実行範囲を制限する位置付け
⚠sandbox_network ルールは先勝ち評価のため、記述順序に注意
⚠sandbox_network は all メタケーパビリティに含まれないため、capability: all, effect: allow でもネットワークアクセスは開放されない

🎯 ユースケース

📁 ユースケース 1: データレジデンシー要件下での長時間リファクタリング

シナリオ: 規制によりソースコードを社外やクラウドに出せない組織で、エージェントに大規模なリファクタリングやビルド・テストのループを任せたい。

JSONsandbox.json
{
  "enabled": true,
  "networkAccess": "COMMON_DEPENDENCIES"
}

効果コードはローカルに保ったまま、書き込みはプロジェクトディレクトリに限定され、認証情報パスへのアクセスはカーネルで拒否。パッケージレジストリなどビルドに必要なサービスには到達できるため、長時間タスクを任せても実行範囲が OS レベルで制限される。

🏢 ユースケース 2: 社内ネットワーク内のサービスを使う開発

シナリオ: VPN 内の社内パッケージレジストリを利用しつつ、社外への不要なデータ送信は防ぎたい。

YAML~/.kiro/settings/permissions.yaml
rules:
  - capability: sandbox_network
    match: ['packages.internal.example.com']
    effect: allow

効果DEFAULT_BLOCKED モードと組み合わせることで、サンドボックス化されたコマンドは明示的に許可した社内レジストリのみに到達でき、その他の宛先への通信はブロック。クラウドサンドボックスでは到達できない VPN 内リソースを使った開発を、ネットワーク制御付きで実行できる。

📦 ユースケース 3: 依存関係アップグレード時のサプライチェーンリスク低減

シナリオ: 依存パッケージのアップグレードでは、インストールスクリプトなど信頼できないコードが実行される可能性があり、認証情報の窃取や外部への不正送信を防ぎたい。

JSONsandbox.json
{
  "enabled": true,
  "networkAccess": "DEFAULT_BLOCKED",
  "mcpSandboxing": true
}

効果パッケージのインストールスクリプトを含むすべての子プロセスがサンドボックス内で実行され、~/.ssh や ~/.aws の読み取りは拒否、許可されていないドメインへの通信もブロック。stdio MCP サーバーも同じ境界内で動作させることで、保護範囲をさらに広げられる。

グローバル (Kiro IDE 1.3 以降および Kiro CLI 2.31 以降のローカル V3 セッションで利用可能)

🔗 関連サービス・機能

☁️ Kiro クラウドサンドボックス

IDE、CLI、Web で利用できる分離されたクラウド実行環境。ローカルサンドボックスは、クラウドに出せない作業に対して同様の保護をローカルで提供する補完関係にある。

📋 Kiro Workspace Trust / permissions.yaml

既存のツール認可ポリシー。ローカルサンドボックスは同じ fs_read、fs_write、sandbox_network ルールを OS カーネルレベルでも強制する。

🔌 MCP (Model Context Protocol)

ローカル stdio MCP サーバーは mcpSandboxing 設定でサンドボックス内にラップ可能。リモート HTTP / SSE サーバーは対象外。

📝 まとめ

Kiro のローカルサンドボックスは、エージェントが実行するコマンドを OS カーネルレベルで制限することで、ツールコール権限チェックだけでは防げなかったシェルやスクリプト経由の回避を塞ぎ、人間の注意力に依存しない多層防御を実現する重要なアップデートです。既存の permissions.yaml ポリシーをそのまま再利用でき、コンテナや VM の起動オーバーヘッドもないため、導入コストは低く抑えられています。Kiro IDE 1.3 以降または Kiro CLI 2.31 以降にアップデートし、まずは sandbox.json で enabled: true を設定してデフォルトポリシーから試すことを推奨します。
