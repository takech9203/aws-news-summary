📅 リリース日: 2026 年 11 月 23 日
組織全体の API と AI エンドポイントをインストール不要・経路変更不要で自動検出し、ガバナンスとドキュメント化を一元化する新機能

📋 概要

API Portal は、単一の AWS アカウントまたは AWS Organizations の組織全体を対象に、Amazon API Gateway、Application Load Balancer、Amazon CloudFront の背後で稼働する API と AI エンドポイントを検出し、ガバナンスとドキュメント化を一元的に実現する機能です。

AWS 側のトラフィックログとサービス設定レコードから継続的に更新されるインベントリを構築するため、エージェントのインストール、ログの転送、トラフィック経路の変更は一切不要です。検出は読み取り専用で、既存の API に変更を加えません。MCP サーバー、A2A サーバー、LLM エンドポイントといった AI 向けエンドポイントも識別でき、生成 AI 時代の API ガバナンスに対応します。

❌ アップデート前の課題

  • 組織全体の API 把握には各チームへのヒアリングや手動カタログ登録が必要で、シャドー API や放置 API を見落とすリスク
  • 棚卸しにサードパーティツール導入、ログ転送基盤構築、プロキシ経由への経路変更などの追加作業が必要
  • MCP サーバーや LLM エンドポイントなどの AI 向けエンドポイントを体系的に識別・管理する仕組みがない
  • 認証、スロットリング、AWS WAF 保護などのセキュリティ対策の適用状況を横断的に確認できない

✅ アップデート後の改善

  • AWS 側のトラフィックログと設定レコードから、組織全体の API インベントリが自動的かつ継続的に構築
  • インストール・ログ転送・経路変更が不要になり、有効化するだけで検出開始
  • MCP / A2A / LLM を含む AI エンドポイントをインベントリ上で識別可能に
  • マネージド API のセキュリティポスチャー評価が可能になり、AWS WAF API Security との組み合わせで脅威も API 単位で確認
  • マネージド API を製品単位でグループ化し、ドキュメントポータルとして公開可能に

API Portal は、API Gateway、ALB、CloudFront の AWS 側トラフィックログとサービス設定レコードから API インベントリを継続的に構築します。検出された API はシャドー API として登録され、昇格したマネージド API に対してセキュリティポスチャー評価とドキュメントポータルへの公開が可能になります。

⚙️ 主要機能

🔍 1. API ディスカバリ

  • API Gateway REST API、ALB、CloudFront の背後にあるすべての API のインベントリを構築し、継続的に更新
  • カタログ未登録のままトラフィックを受けている API も検出
  • AWS 側のトラフィックログと設定レコードが情報源のため、インストール・ログ転送・経路変更が不要
  • 検出は読み取り専用で、既存の API リソースを変更しない

🗂️ 2. 分類とガバナンス

  • 検出されたすべての API は、まず「シャドー API」として扱われる
  • ガバナンス対象としたい API を「マネージド API」に昇格
  • トラフィックが途絶えた「ゾンビ API」や所有者不在の「オーファン API」にフラグを立てる
  • API をパブリック / プライベートとしてラベル付け可能

🤖 3. AI エンドポイント識別

  • MCP サーバー、A2A サーバー、LLM バックエンドの API を、トラフィックで観測されたプロトコルから任意で識別
  • 生成 AI エージェントやツールの増加に伴う「見えない AI エンドポイント」の把握に有効

🛡️ 4. セキュリティポスチャー評価

  • マネージド API を認証、リクエスト検証、スロットリング、TLS バージョン、AWS WAF 保護などのベストプラクティスに照らして評価し、所見をレポート
  • AWS WAF API Security を使用している場合、検出されたセキュリティイベント (脅威) をマネージド API 単位で表示

📘 5. ドキュメントポータル

  • マネージド API を製品 (Product) としてグループ化し、API 定義から生成されるリファレンスページと独自ドキュメントを組み合わせて公開
  • 社内チーム向け、外部パートナー向けのいずれにも対応
  • カスタムブランディング、Amazon Cognito によるアクセス制御、インタラクティブな「Try it」ページをサポート
  • 既存の API Gateway Portals は従来どおり動作 (Documentation Portals セクションから管理)

🔬 技術仕様・検出の仕組み

📐 API Portal における API の定義

API Portal は、フロントドアリソース上の「HTTP メソッド + URI パス」の組み合わせ (例: GET /v1/payments) を 1 つの API として定義します。API Gateway の RestApi リソースとは異なる粒度であり、API Gateway、ALB、CloudFront の API を同じ形式で表現し、OpenAPI Specification と整合させるための設計です。1 つの RestApi はインベントリ上では複数の行として表示されるのが一般的です。

🔎 検出の仕組み

ソースサービス検出方法備考
🔌 API Gateway 設定 (AWS Config 設定項目) とトラフィックの両方 REST API のみ対象。明示的なメソッドとリテラルパスはトラフィックがなくても検出される
⚖️ Application Load Balancer 観測されたトラフィックのみ リクエストを受けていないエンドポイントはインベントリに表示されない
🌐 CloudFront 観測されたトラフィックのみ グローバルサービスのため、us-east-1 リージョンでのみ検出される
⏱️ 検出は継続的に実行されますが即時ではなく、新しい API は通常数時間以内に表示されます。初めて検出を有効化した場合は最大 24 時間を見込む必要があります。

🔗 サービスリンクロールと AWS Config レコーダー

API Portal は、サービスリンクロール AWSServiceRoleForAPIPortal を使用して AWS Organizations の階層を読み取り、検出に使用する AWS Config 設定レコーダーを管理します。検出を有効化すると、このロールが自動作成されます (組織全体の検出では管理アカウントに必要)。検出用のサービスリンク AWS Config 設定レコーダーは必要なリソースタイプのみを記録し、AWS Config の料金は発生しません。

⚠️ 制限事項・考慮すべき点

🚫 制限事項

✗API Gateway は REST API のみが検出対象。HTTP API と WebSocket API は検出されず、ドキュメントポータルにも追加できない
✗REST API の設定ベース検出はリテラルパス上の明示的なメソッドのみが対象。ANY メソッドや /{proxy+} のようなグリーディパスは、実際にトラフィックを受けた具体的なメソッドとパスとして初めて表示される
✗ALB と CloudFront はトラフィックのみから検出されるため、トラフィックがほとんどないエンドポイントは表示されない
✗CloudFront はグローバルサービスのため、CloudFront を前段とする API は us-east-1 リージョンでのみ検出される
✗API Gateway Portals と API Portal のドキュメントポータルは別リソースであり、ローンチ時点で両者間の移行機能はない

🤔 考慮すべき点

⚠検出は即時ではなく、新しい API の表示まで数時間、初回有効化後は最大 24 時間かかる場合がある
⚠API を削除またはトラフィックを停止しても、インベントリの行は約 30 日間残る。検出設定を削除してもインベントリ行が早く消えるわけではない
⚠1 つの API が複数のフロントドアから到達可能な場合 (例: CloudFront の背後の API Gateway REST API)、フロントドアごとに 1 行ずつ表示される
⚠組織全体の検出には管理アカウントまたは委任管理者アカウントでの操作と信頼されたアクセスの有効化が必要なため、組織管理者との調整が必要

🎯 ユースケース

👻 ユースケース 1: 組織全体のシャドー API の棚卸し

シナリオ: 複数の事業部がそれぞれ AWS アカウントで API を運用しており、全社でどの API が稼働しているか誰も正確に把握できていない。セキュリティ監査で API の棚卸しが求められている。

Text 実装例 
1. 管理アカウントで API Portal の信頼されたアクセスを有効化
2. 委任管理者アカウントから組織全体の API ディスカバリを有効化
3. 最大 24 時間後、インベントリで全アカウントのシャドー API を確認
4. 所有チームを特定し、ガバナンス対象の API をマネージド API に昇格

💪 効果: エージェント導入やログ転送の構築なしに、組織全体の API 資産を網羅的に把握でき、未登録 API や放置された API のリスクを早期に発見できる。

🤖 ユースケース 2: AI エンドポイントのガバナンス

シナリオ: 社内の各チームが MCP サーバーや LLM を利用した API を次々に構築しており、セキュリティチームがどこにどのような AI エンドポイントが存在するかを把握できていない。

Text 実装例 
1. API Portal で AI エンドポイント識別を有効化
2. インベントリで MCP サーバー、A2A サーバー、LLM エンドポイントを確認
3. 対象をマネージド API に昇格し、認証や AWS WAF 保護の有無を評価
4. AWS WAF API Security を併用し、検出された脅威を API 単位で監視

💪 効果: 生成 AI 関連のエンドポイントを体系的に可視化し、認証や WAF 保護が不足している AI エンドポイントへ優先的に対策を講じられる。

🤝 ユースケース 3: パートナー向け API ドキュメントポータルの公開

シナリオ: 外部パートナーに提供している API のドキュメントを手動で管理しており、仕様変更のたびに更新漏れが発生している。パートナーのオンボーディングにも時間がかかっている。

Text 実装例 
1. パートナー向けのマネージド API を製品としてグループ化
2. API 定義から生成されるリファレンスページに独自ドキュメントを追加
3. Amazon Cognito ユーザープールでアクセス制御を設定
4. カスタムブランディングとカスタムドメインを設定してポータルを公開

💪 効果: API 定義に基づく正確なリファレンスとインタラクティブな「Try it」ページにより、パートナーのオンボーディングを迅速化し、ドキュメントの更新漏れを防止できる。

📜 AWS Certificate Manager

ドキュメントポータルのカスタムドメイン名に使用。証明書は us-east-1 リージョンに必要

📌 まとめ

API Portal は、組織全体の API と AI エンドポイントを「インストール不要・経路変更不要」で可視化し、シャドー API の発見からセキュリティポスチャー評価、ドキュメント公開までを一元化する、API ガバナンスの基盤となる機能です。

複数アカウントで API を運用している組織や、MCP サーバーなどの AI エンドポイントが増えている組織は、まず検出を有効化してインベントリを確認し、重要な API をマネージド API に昇格してセキュリティ所見のレビューから始めることを推奨します。
