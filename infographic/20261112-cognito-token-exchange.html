🔐 Amazon Cognito

OAuth 2.0 トークン交換のサポート

リリース日: 2026 年 11 月 12 日
RFC 8693 / GetDerivedToken API
🤖 AI エージェント 🔌 MCP サーバー 🧩 マイクロサービス委任 📜 RFC 8693 準拠 🛡️ 最小権限

📝 概要

Amazon Cognito が RFC 8693 で定義される OAuth 2.0 トークン交換をサポートしました。 ユーザーに代わって動作するサービスや AI エージェントが、ユーザーの既存トークンを、 特定のダウンストリームサービス向けにスコープを絞り込んだ新しいトークンに交換できます。 交換は新しい GetDerivedToken API、または既存トークンエンドポイントの トークン交換グラント経由で実行できます。

発行トークンは元のトークンより狭いスコープを持ち、単一オーディエンスにバインドされ、 リフレッシュトークンを伴いません。アクタートークンを含めると act クレームが付与され、 ダウンストリームサービスは「ユーザー本人のリクエスト」と「エージェントによる代理リクエスト」を区別できます。

❌ Before: アップデート前の課題

  • ユーザーの元トークンをそのまま転送し、必要以上に広いスコープや異なるオーディエンス向けのトークンが渡っていた
  • 独自のカスタムトークン発行システムを構築・維持する必要があった
  • ユーザー本人のリクエストと仲介者によるリクエストを区別する標準的な手段がなかった

✅ After: アップデート後の改善

  • 特定サービス向けにスコープを絞り、単一オーディエンスにバインドした短命トークンに交換可能
  • act クレームで仲介者を識別でき、監査ログや仲介者固有のポリシー適用が可能
  • RFC 8693 準拠の標準的な方法でトークン委任を実現、カスタム基盤が不要に

中間サービスがユーザーのトークン (SubjectToken) と自身のトークン (ActorToken) を Cognito に提示し、 ダウンストリーム API 専用にスコープを絞った新しいトークンを取得する委任 (Delegation) フローです。

⚙️ 主要機能

🔄 1. GetDerivedToken API によるトークン交換

  • 既存のトークン (SubjectToken) を提示し、特定のダウンストリームサービス向けの新しいトークンを取得
  • AWS SDK から直接、またはトークンエンドポイント (/oauth2/token) のトークン交換グラント (urn:ietf:params:oauth:grant-type:token-exchange) 経由で実行可能
  • トークンエンドポイント経由はユーザープールドメインが必要。SDK 経由はドメイン不要

🎭 2. 2 つのセマンティクス: Impersonation と Delegation

👤 Impersonation なりすまし

ActorToken を含めない場合、ユーザーが直接操作したかのようなトークンが発行される (act クレームなし)

許可設定: ALLOW_TOKEN_EXCHANGE_IMPERSONATION

🤝 Delegation 委任

ActorToken を含めると、発行トークンに act クレームが付与され、仲介者を識別できる

許可設定: ALLOW_TOKEN_EXCHANGE_DELEGATION

🛡️ 3. ダウンスコープのみのセキュリティモデル

  • 発行スコープは「リクエストしたスコープ」「SubjectToken のスコープ」「アプリクライアントが許可されたスコープ」の積集合。元のトークンにないスコープは絶対に追加されない
  • リフレッシュトークンは発行されず、交換されたトークンは短命で自動的に失効
  • SubjectToken の署名・有効期限・失効 (グローバルサインアウト等) を検証。対象ユーザーは有効かつ確認済みであること
  • Audience / Resource はユーザープールに登録済みのリソースサーバーに対して検証

🌐 4. 外部 IdP トークンのサポート

  • SubjectToken / ActorToken に、登録済み外部 IdP (OIDC または SAML 2.0) のトークンも使用可能
  • 外部 IdP トークン使用時はプロバイダー名 (SubjectTokenProviderName / ActorTokenProviderName) を指定
  • 外部 IdP ユーザーは事前にユーザープール内のリンク済みユーザーとして存在が必要 (交換で新規ユーザーは作成されない)

⚡ 5. Pre Token Generation Lambda トリガーとの統合

  • 交換時に TokenGeneration_TokenExchange という triggerSource で Lambda トリガーが起動
  • 発行トークンのクレームやスコープの追加・抑制・上書き、交換の拒否が可能

🔬 技術仕様

GetDerivedToken API の主要パラメータ

パラメータ必須説明
ClientId必須トークン交換をリクエストするアプリクライアントの ID
ClientSecret条件付きシークレットを持つアプリクライアントの場合に必須
SubjectToken必須交換対象のユーザートークン
SubjectTokenType必須ACCESS_TOKEN / ID_TOKEN / SAML2
ActorToken任意仲介者を示すトークン。指定すると act クレームが付与される
ActorTokenType条件付きActorToken 指定時に必須。ACCESS_TOKEN / ID_TOKEN / SAML2
Audiences任意発行トークンの対象サービスの論理名 (最大 1 件、Resources と同時指定不可)
Resources任意ユーザープール内のリソースサーバー識別子 (最大 1 件、Audiences と同時指定不可)
Scopes任意発行トークンにリクエストするスコープ。未指定の場合は SubjectToken と同じスコープ
RequestedTokenType任意ACCESS_TOKEN または ID_TOKEN (SAML アサーションは発行不可)

API 変更履歴

本アップデートで Amazon Cognito Identity Provider (cognito-idp) に GetDerivedToken API が追加されています。 なお、レポート作成時点 (2026 年 11 月 13 日) では awsapichanges.com のフィードに該当エントリは未掲載です。

委任交換で発行されるアクセストークンのペイロード例

JSON act クレーム付きアクセストークン 
{
    "sub": "a1b2c3d4-5678-90ab-cdef-EXAMPLE11111",
    "token_use": "access",
    "scope": "solar-system-data/asteroids.add",
    "aud": "solar-system-data",
    "act": {
        "sub": "service-a-client-id"
    },
    "exp": 1735689600,
    "iat": 1735686000
}

act クレームの sub に仲介サービスのクライアント ID が記録され、 ダウンストリームサービスは仲介者を識別できます。

🛠️ 設定方法

前提条件

✓ユーザープールが Essentials または Plus 機能プランであること
✓アプリクライアントの ExplicitAuthFlows に、利用するセマンティクスに応じた認証フロー (ALLOW_TOKEN_EXCHANGE_IMPERSONATION / ALLOW_TOKEN_EXCHANGE_DELEGATION) が設定されていること
✓Audiences / Resources に指定する値がユーザープールに登録済みのリソースサーバーに対応していること
✓トークンエンドポイント経由で交換する場合は、ユーザープールにドメインが設定されていること
✓アカウントでトークン交換が有効であること (無効の場合は OperationNotEnabledException が返る)

ステップ 1: アプリクライアントでトークン交換フローを有効化

Bash AWS CLI - 認証フローの追加 
aws cognito-idp update-user-pool-client \
  --user-pool-id us-east-1_EXAMPLE \
  --client-id 1example23456789 \
  --explicit-auth-flows ALLOW_TOKEN_EXCHANGE_DELEGATION ALLOW_REFRESH_TOKEN_AUTH

委任セマンティクスでのトークン交換を許可します。Impersonation を利用する場合は ALLOW_TOKEN_EXCHANGE_IMPERSONATION を指定します。

ステップ 2: GetDerivedToken API でトークンを交換

Bash AWS CLI - トークン交換の実行 
aws cognito-idp get-derived-token \
  --client-id 1example23456789 \
  --client-secret exampleClientSecret123EXAMPLE \
  --subject-token eyJra456defEXAMPLE \
  --subject-token-type ACCESS_TOKEN \
  --actor-token eyJra789ghiEXAMPLE \
  --actor-token-type ACCESS_TOKEN \
  --audiences solar-system-data \
  --scopes solar-system-data/asteroids.add

ユーザーのアクセストークン (SubjectToken) と仲介サービスのトークン (ActorToken) を提示し、 リソースサーバー solar-system-data 向けにスコープを絞った新しいトークンを取得します。

ステップ 3: トークンエンドポイント経由での交換 (代替手段)

Bash RFC 8693 トークン交換グラント 
curl -X POST https://example-domain.auth.us-west-2.amazoncognito.com/oauth2/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -H "Authorization: Basic $(echo -n 'client_id:client_secret' | base64)" \
  -d "grant_type=urn:ietf:params:oauth:grant-type:token-exchange" \
  -d "subject_token=eyJra456defEXAMPLE" \
  -d "subject_token_type=urn:ietf:params:oauth:token-type:access_token" \
  -d "audience=solar-system-data" \
  -d "scope=solar-system-data/asteroids.add"

RFC 8693 標準のトークン交換グラントを使用します。委任の場合は actor_token と actor_token_type パラメータを追加します。

💡 メリット

💼 ビジネス面

✓エージェント型アーキテクチャへの対応: AI エージェントや MCP サーバーがユーザーに代わって行動する際の標準的な認可基盤を、マネージドサービスとして利用できる
✓開発・運用コストの削減: カスタムトークン発行システムの構築・維持が不要になり、認可基盤の開発工数を削減できる
✓監査・コンプライアンスの強化: act クレームにより「誰が誰に代わって操作したか」を監査ログに記録でき、説明責任を果たしやすくなる

🔧 技術面

✓最小権限の原則の徹底: ダウンスコープのみ許可される設計により、交換後のトークンが元のトークンより広い権限を持つことがない
✓トークン漏えいリスクの低減: 単一オーディエンスバインド + リフレッシュトークンなしの短命トークンのため、漏えい時の影響範囲が限定される
✓標準準拠: RFC 8693 準拠のため、OAuth 2.0 エコシステムの他のコンポーネントとの相互運用性が高い
✓柔軟なカスタマイズ: Pre Token Generation Lambda トリガー (TokenGeneration_TokenExchange) で交換時のクレームやスコープを制御できる

⚠️ デメリット・制約事項

制限事項

✗Essentials または Plus 機能プランのユーザープールでのみ利用可能 (Lite プランは対象外)
✗発行できるトークンは Cognito のアクセストークンまたは ID トークンのみで、SAML アサーションは発行できない
✗Audiences と Resources は同時に指定できず、それぞれ最大 1 件まで
✗RFC 8693 の may_act クレーム (事前にどのアクターが代理可能かを宣言するクレーム) は現時点で発行・評価されない
✗外部 IdP トークン使用時は、対象ユーザーが事前にユーザープールのリンク済みユーザーとして存在している必要がある

考慮すべき点

⚠️リフレッシュトークンが発行されないため、有効期限切れを考慮したトークンキャッシュ戦略の設計が必要
⚠️Lite プラン利用中の場合、Essentials 以上へのプラン変更が必要となり、MAU 課金が発生する
⚠️アプリクライアントごとに Impersonation / Delegation のどちらを許可するか、セキュリティ要件に基づいた設計が必要 (Impersonation では仲介者を識別できない点に注意)

🎯 ユースケース

🤖 ユースケース 1: MCP サーバーによるバックエンド API 呼び出し

シナリオ: AI エージェントの MCP サーバーが、ユーザーのトークンを受け取り、ユーザーに代わってバックエンド API を呼び出す。バックエンド側では、エージェント経由のリクエストであることを識別して専用のポリシーを適用したい。

JSON GetDerivedToken リクエスト例 
{
    "ClientId": "mcp-server-client-id",
    "SubjectToken": "<ユーザーのアクセストークン>",
    "SubjectTokenType": "ACCESS_TOKEN",
    "ActorToken": "<MCP サーバーのトークン>",
    "ActorTokenType": "ACCESS_TOKEN",
    "Audiences": [ "backend-api" ],
    "Scopes": [ "backend-api/data.read" ]
}

効果: バックエンド API は act クレームで MCP サーバーを識別でき、エージェント経由のアクセスに対して読み取り専用ポリシーの適用や監査記録が可能になる。

🧩 ユースケース 2: マイクロサービス間のサービス間委任

シナリオ: フロントエンドからリクエストを受けた注文サービスが、決済サービスを呼び出す。決済サービスには決済に必要な最小限のスコープだけを持つトークンを渡したい。

Bash 決済専用トークンへの交換 
aws cognito-idp get-derived-token \
  --client-id order-service-client \
  --subject-token "<ユーザーのアクセストークン>" \
  --subject-token-type ACCESS_TOKEN \
  --resources payment-api \
  --scopes payment-api/charge.create

効果: 決済サービスには決済専用にスコープを絞ったトークンのみが渡り、ユーザーの元トークンが持つ他の権限 (注文履歴の閲覧など) が不要に伝播しない。

🌐 ユースケース 3: 外部 IdP ユーザーのトークンのダウンスコープ

シナリオ: 企業の SAML IdP で認証したユーザーのアサーションを、社内 API 呼び出し用の Cognito アクセストークンに交換する。

JSON SAML アサーションからの交換 
{
    "ClientId": "internal-app-client-id",
    "SubjectToken": "<SAML 2.0 アサーション>",
    "SubjectTokenType": "SAML2",
    "SubjectTokenProviderName": "CorporateSAML",
    "Audiences": [ "internal-api" ]
}

効果: 登録済み外部 IdP のトークンを Cognito の標準トークンに変換でき、ダウンストリームサービスは Cognito トークンの検証ロジックだけで統一的に認可できる。

📌 まとめ

Amazon Cognito の OAuth 2.0 トークン交換サポートにより、AI エージェントやマイクロサービスがユーザーに代わって ダウンストリームサービスを呼び出す際の認可を、RFC 8693 準拠の標準的な方法で実現できるようになりました。 エージェント型アーキテクチャやサービス間委任を設計している場合は、Essentials / Plus プランのユーザープールで アプリクライアントのトークン交換フローを有効化し、GetDerivedToken API の検証から始めることを推奨します。
