📌 概要

Amazon OpenSearch Service の新エンジン (Optimized エンジン、ログ分析最適化エンジン) が、 分散結合 (Distributed Joins)、高カーディナリティ集計、 OpenSearch query DSL をサポートしました。 エンジニアや AI エージェントは、PPL または SQL を使用して、ペタバイト規模のデータに対し、 エラーログとトレースの関連付けやテレメトリへのメタデータ付加を 1 つのクエリで実行できます。

エンジンは集計と結合をデータノード全体に分散して実行し、ルーティングキーにより関連ドキュメントを同一シャードに保持して結合を高速化します。 query DSL のサポートにより、既存のアプリケーション、アラート、インテグレーションを書き換えることなく移行できます。

❌ Before (アップデート前)
  • オブザーバビリティデータが複数インデックスに分散し、インシデント対応時の相関付けが困難
  • 結合分析には事前に 1 つのインデックスへコピー (非正規化) が必要
  • 数百万件規模のホスト / ユーザー / テナントにまたがる影響範囲の測定が困難
  • PPL と SQL が中心で、query DSL を使う既存アプリやアラートをそのまま移行できない
✅ After (アップデート後)
  • PPL / SQL でエラーログとトレースの結合やメタデータ付加を 1 クエリで実行
  • 結合・集計をデータノード全体に分散、事前の非正規化が不要に
  • 高カーディナリティ集計で数百万件規模のインシデント影響を測定可能
  • ルーティングキーで関連ドキュメントを同一シャードに保持し、結合を高速化
  • query DSL サポートで既存アプリ・アラート・連携が書き換えなしで動作

⚙️ query DSL の実行モード

モード内容
⚡ 高速化 (Accelerated)クエリ内のすべての句と集計が高速化対象リストに含まれる場合、ベクトル化実行エンジンで実行され、PPL や SQL と同等のパフォーマンスメリットを得られる
🛟 サポート (Supported)高速化対象外の句や集計を含む場合、Optimized エンジンのストレージ上で標準の OpenSearch クエリ実行が行われる。結果は同一だが高速化はされない

高速化対象: term 系クエリ (term、terms、range、prefix、wildcard、regexp など)、 must / should / filter を使用する bool クエリ、 bucket 集計 (terms、histogram、date_histogram など)、 metric 集計 (min、max、avg、sum、percentiles、cardinality など)

📝 設定例: 高速化対象となる query DSL リクエスト

JSON サービス別エラー集計と p99 レイテンシー算出 
GET logs/_search
{
  "size": 0,
  "query": {
    "bool": {
      "filter": [
        { "range": { "@timestamp": { "gte": "now-1h" } } },
        { "range": { "status_code": { "gte": 500 } } },
        { "term":  { "env": "prod" } }
      ]
    }
  },
  "aggs": {
    "by_service": {
      "terms": { "field": "service.name", "size": 10 },
      "aggs": {
        "p99_latency": { "percentiles": { "field": "latency_ms", "percents": [99] } }
      }
    }
  }
}

過去 1 時間のステータスコード 500 以上のログをサービス別に集計し、各サービスのレイテンシー 99 パーセンタイルを算出します。 高速化対象のクエリと集計のみで構成され、size: 0 を指定しているため、ベクトル化実行エンジンで高速に実行されます。

⚠️ デメリット・制約事項

🚫 制限事項

✗query DSL サポートには OpenSearch 3.9 が必要 (Optimized エンジン自体は OpenSearch 3.5 以降)
✗nested クエリ、has_child / has_parent などの親子結合、地理空間クエリ、percolate、must_not を含む bool クエリ、keyword フィールドによるソートは非サポート
✗geo_point、knn_vector、join、percolator などのフィールドタイプは非サポート。これらを含むマッピングはインデックス作成時に拒否される
✗_count、_update_by_query、_delete_by_query、_reindex、スクロール API は非サポート (ページングにはポイントインタイムと search_after を使用)
✗PPL の expand、xyseries などの一部コマンドは、プライマリシャードが 1 つのインデックスでのみサポート

🤔 考慮すべき点

⚠️query DSL は高速化対象リスト内のクエリと集計で構成された場合のみ高速化され、対象外の句を含むと標準実行になる (実行モードは自動選択で、ユーザーは指定不可)
⚠️ソート指定のないリクエストは関連度スコア順となり高速化されないため、フィールドソートの指定または size: 0 の設定を推奨
⚠️高速化クエリでは _source 内の日付フィールドが標準書式で返却されるなど、一般エンジンと一部挙動が異なる
⚠️関連度ランキング、ベクトル検索、地理空間検索、頻繁なドキュメント更新が中心のワークロードには、引き続き General Purpose エンジンを推奨

🎯 ユースケース

🔍 ユースケース 1: エラーログとトレースの結合によるインシデント調査

シナリオ: 本番環境で 503 エラーが急増しており、どのサービスのどのトレースが原因かを特定したい。ログとトレースは別々のインデックスに格納されている。

SQLエラーログとトレースの結合
SELECT l.trace_id, t.service_name, t.duration_ms, l.message
FROM error_logs l
INNER JOIN traces t ON l.trace_id = t.trace_id
WHERE l.status_code = 503
ORDER BY t.duration_ms DESC
LIMIT 100

効果: 事前の非正規化なしに 1 クエリで結合でき、原因となるサービスと処理時間の長いトレースを即座に特定できる。

🏷️ ユースケース 2: サービス所有者メタデータによるテレメトリの拡充

シナリオ: 障害発生時に、影響を受けているサービスの所有チームと直近のデプロイ情報を即座に把握し、エスカレーション先を特定したい。

PPLlookup によるメタデータ付加
source=error_logs
| where status_code >= 500
| lookup service_catalog service_name
| stats count() as errors by service_name, owner_team, last_deploy_version
| sort - errors

効果: PPL の lookup コマンドでエラーログにサービスカタログの所有者情報とデプロイメタデータを付加し、エスカレーション先の特定とデプロイ起因の切り分けを 1 クエリで実行できる。

📈 ユースケース 3: 高カーディナリティ集計によるインシデント影響範囲の測定

シナリオ: マルチテナント SaaS でインシデントが発生し、数百万のユーザーとテナントのうち、実際に影響を受けた数を正確に把握したい。

PPLdistinct_count による影響範囲測定
source=app_logs
| where status_code >= 500 and @timestamp >= '2026-11-24 00:00:00'
| stats distinct_count(user_id) as affected_users,
        distinct_count(tenant_id) as affected_tenants by service.name
| sort - affected_users

効果: 集計がデータノード全体に分散実行されるため、数百万件規模の異なるユーザー・テナントにまたがる影響範囲の測定をペタバイト規模のログに対して実行できる。
