バルクプットアイテム機能

Amazon DynamoDB 一般提供開始 GA Bulk put items

📌 概要

Amazon S3 上のデータを既存の DynamoDB テーブルに直接書き込むフルマネージド機能「bulk put items」が一般提供開始。入力ファイルの S3 ロケーションを指定するだけで、読み取り・書き込み・リトライ・例外処理・結果レポート出力までを DynamoDB が自動処理します。

書き込みは分離された専用システムキャパシティで実行されるため、テーブルの読み取り・書き込みキャパシティを一切消費せず、稼働中のワークロードに影響しません。通常のリクエスト単位の書き込みより低コストで、書き込まれたアイテムは即座に読み取り可能です。

従来の「Import from Amazon S3」が新規テーブル作成のみ対応だったのに対し、bulk put items は既存テーブルへの書き込みに対応。日次データリフレッシュ、大規模カタログのエンリッチメント、バックフィル、移行を行う開発者・データエンジニアが主な対象です。

❌ Before: アップデート前の課題
  • S3 のデータを既存テーブルに書き込むには AWS Glue や Lambda などのカスタムパイプライン構築が必要
  • アプリケーショントラフィックと競合しないよう、キャパシティ管理やレート制限付きカスタムライターの実装が必要
  • 「Import from Amazon S3」は新規テーブルのみ対応。稼働中テーブルへの投入は再構築や切り替えが必要
✅ After: アップデート後の改善
  • S3 ロケーション指定だけで既存テーブルへの大規模ロードをフルマネージドで実行
  • 分離キャパシティで実行され、テーブルキャパシティを消費せずアラームや Auto Scaling に影響なし
  • アイテムごとの条件式で挿入専用・バージョンガード付きの安全な書き込みが可能
  • Standard / Accelerated の 2 ティアからコストと完了時間で選択可能

⚡ 主要機能

1️⃣ 既存テーブルへのフルマネージドなバルクロード
  • 入力ファイルの S3 ロケーション、対象テーブル、出力レポート用 S3 ロケーションを指定するだけで実行可能
  • S3 オブジェクトの読み取り、各アイテムの書き込み、リトライと例外処理、レポート出力まで自動処理
  • 非同期ジョブとして実行され、書き込まれたアイテムは即座に読み取り可能
  • 別アカウントの S3 バケットを入力・出力に使用するクロスアカウント構成にも対応
2️⃣ テーブルキャパシティを消費しない分離された書き込みパス
  • バルク書き込みはテーブルの読み取り・書き込みキャパシティを一切消費しない
  • ConsumedWriteCapacityUnits メトリクスや Contributor Insights にはカウントされず、既存の CloudWatch アラームや Auto Scaling 設定はそのまま機能
  • GSI / LSI も分離キャパシティで自動更新
3️⃣ アイテムごとの条件式サポート
  • 各レコードに PutItem と同じ構文の条件式 ConditionExpression を指定可能
  • attribute_not_exists による挿入専用の書き込みや、バージョン属性の比較による新しいデータのみの書き込みを強制可能
  • 条件式がないレコードは無条件で書き込まれ、同じキーの既存アイテムを上書き
  • 条件チェックでスキップされたアイテムは失敗扱いではなく、レポートに記録
4️⃣ 2 つのパフォーマンスティア
  • Standard (デフォルト): 低コスト。完了時間に柔軟性がある低優先度のワークロード向け
  • Accelerated: 高スループットで完了を早める。移行や RTO 要件のある復旧、固定時間枠での定期ロード向け
5️⃣ 運用性と監視
  • StartBulkPutItems は即座にオペレーション ARN を返却し、クライアントトークンにより再試行は冪等
  • DescribeBulkOperation で処理済み / 失敗アイテム数、処理済みバイト数を確認可能
  • MaxWriteRequestUnits で書き込みレートに上限を設定し、Streams の下流コンシューマーを保護
  • ListBulkOperations は 90 日間の履歴を保持し、全 API コールは CloudTrail に記録

API 変更履歴 (2026/11/04)

dynamodb に 4 つの新 API メソッドが追加されました。

🚀 StartBulkPutItems
🔍 DescribeBulkOperation
📋 ListBulkOperations
🛑 CancelBulkOperation

入力ファイルの例 (DynamoDB JSON)

JSON Lines 無条件 / 挿入専用 / バージョンガードを 1 ファイルに混在可能 
{"Item": {"Artist": {"S": "No One You Know"}, "SongTitle": {"S": "Call Me Today"}}}
{"Item": {"Artist": {"S": "Acme Band"}, "SongTitle": {"S": "Happy Day"}, "Origin": {"S": "import"}}, "ConditionExpression": "attribute_not_exists(Artist)"}
{"Item": {"Artist": {"S": "The Ternaries"}, "SongTitle": {"S": "Blue"}, "Version": {"N": "12"}}, "ConditionExpression": "#v < :v", "ExpressionAttributeNames": {"#v": "Version"}, "ExpressionAttributeValues": {":v": {"N": "12"}}}

1 行目は無条件の書き込み、2 行目は挿入専用 (既存アイテムを上書きしない)、3 行目はバージョンガード付きの書き込みです。

必要な IAM 権限

アクションスコープ説明
dynamodb:StartBulkOperationbulk-operation/*オペレーションの開始
dynamodb:BulkPutItems対象テーブルオペレーション中のテーブルへの書き込み
dynamodb:DescribeBulkOperationオペレーション ARNオペレーションの監視
dynamodb:CancelBulkOperationオペレーション ARNオペレーションのキャンセル
dynamodb:ListBulkOperationsbulk-operation/*オペレーションの一覧表示

上記に加えて、入力バケットの読み取り (s3:GetObject、s3:ListBucket)、出力バケットへの書き込み (s3:PutObject、s3:AbortMultipartUpload)、KMS 暗号化を使用する場合は kms:Decrypt と kms:GenerateDataKey が必要です。オペレーション実行中も権限が再チェックされるため、完了まで権限を維持する必要があります。

🛠️ 設定方法

前提条件

✓対象の DynamoDB テーブルが ACTIVE 状態であること (セカンダリインデックス作成中、グローバルテーブルへの移行中、バックアップからの復元中は開始不可)
✓入力データが行区切りの DynamoDB JSON または Amazon Ion 形式で S3 に配置されていること
✓呼び出し元の IAM プリンシパルに DynamoDB、S3、KMS 権限が付与されていること
1
入力ファイルを S3 に配置
BashAWS CLI
aws s3 cp items.jsonl s3://my-import-bucket/daily/items.jsonl

行区切りの DynamoDB JSON 形式の入力ファイルをアップロード。gzip または zstd で圧縮すると転送サイズを削減できます。

2
バルクプットオペレーションを開始
BashAWS CLI
aws dynamodb start-bulk-put-items \
    --table-name arn:aws:dynamodb:us-east-1:123456789012:table/MusicCollection \
    --input-s3-configuration '{"S3Bucket":"my-import-bucket","S3KeyPrefix":"daily/","InputFormat":"DYNAMODB_JSON"}' \
    --output-s3-configuration '{"S3Bucket":"my-report-bucket","S3KeyPrefix":"reports/","OutputType":["ERROR","CONDITION_CHECK_FAILURE"]}' \
    --performance-tier ACCELERATED

コマンドは即座にオペレーション ARN を返却。クライアントトークンにより再試行しても重複起動しません。

3
進捗を監視
BashAWS CLI
aws dynamodb describe-bulk-operation \
    --bulk-operation-arn <オペレーション ARN>

処理済みアイテム数、失敗アイテム数、処理済みバイト数、ステータスを確認。開始直後の数分はプロビジョニングのためカウンターがゼロのまま進むことがあります。

4
結果レポートを確認
BashAWS CLI
aws s3 ls s3://my-report-bucket/reports/

書き込めなかったアイテム (ERROR) や条件チェックでスキップされたアイテム (CONDITION_CHECK_FAILURE) を確認。条件チェック失敗のレコードには newImage と oldImage の両方が含まれ、正確な再インポートファイルを作成できます。

💡 メリット

💼 ビジネス面

✓運用コストの削減: カスタム取り込みパイプラインの構築・保守が不要になり、開発リソースを本来の業務に集中できる
✓書き込みコストの削減: 通常のリクエスト単位の書き込みよりも低い価格で大量データを書き込める
✓ダウンタイムなしのデータ投入: 稼働中のサービングテーブルに影響を与えずに数百 GB 規模のデータを投入できる

⚙️ 技術面

✓ワークロードの完全な分離: テーブルキャパシティを消費しないため、既存のアラーム、Auto Scaling、アプリケーション性能に影響しない
✓条件式による安全な書き込み: 挿入専用やバージョンガードにより、再実行可能 (べき等) なインポートを実現
✓フルマネージドな信頼性: リトライ、例外処理、失敗レポートを DynamoDB が処理し、GSI / LSI や Streams への伝播も自動化

⚠️ デメリット・制約事項

制限事項

✗グローバルテーブル非対応: グローバルテーブルの一部であるテーブルには実行不可。実行中のテーブルへのレプリカ追加も不可。グローバルテーブルには BatchWriteItem または PutItem を使用
✗ベクトルインデックス付きテーブルは Standard ティアのみ: Accelerated ティア指定はバリデーションエラー
✗キャンセル時のロールバックなし: キャンセルしても書き込み済みアイテムはテーブルに残る
✗テーブル状態の要件: セカンダリインデックス作成中、グローバルテーブルへの移行中、バックアップからの復元中は開始不可
✗入力オブジェクト数、オブジェクトサイズ、合計入力サイズ、同時実行数にはクォータあり

考慮すべき点

⚠️DAX をバイパスする: DAX にキャッシュされたアイテムは TTL が切れるまで古いままになる
⚠️Streams コンシューマーのサイジング: 全バルク書き込みがストリームレコードを生成。保持期間は 24 時間のため、MaxWriteRequestUnits で書き込みレートに上限を設けることを推奨
⚠️内部フェイルオーバー時の再書き込み: 一部レコードが 2 回書き込まれる可能性あり。同じキーに書き込むアプリケーションがある場合は全レコードにバージョンガード条件を付与すべき
⚠️条件チェック失敗も課金対象: テーブルに到達して条件チェックに失敗したアイテムは課金される (バリデーション拒否は課金されない)
⚠️少量データには不向き: 開始直後のプロビジョニングに時間がかかるため、少数アイテムには PutItem / BatchWriteItem が適切
⚠️クロスリージョンバケットのコスト: データ転送料金が発生し、そのリージョンの障害時にオペレーションが停滞する可能性あり

🎯 ユースケース

🤖 ユースケース 1: ML 推論データの日次リフレッシュ

シナリオ: 機械学習パイプラインが毎日生成する数百 GB の推論結果を、稼働中のサービングテーブルに無停止で反映したい。

Bash実装例
aws dynamodb start-bulk-put-items \
    --table-name arn:aws:dynamodb:ap-northeast-1:123456789012:table/InferenceServing \
    --input-s3-configuration '{"S3Bucket":"ml-output-bucket","S3KeyPrefix":"daily-inference/2026-11-05/","InputFormat":"DYNAMODB_JSON","InputCompressionType":"GZIP"}' \
    --output-s3-configuration '{"S3Bucket":"import-reports","S3KeyPrefix":"inference/","OutputType":["ERROR"]}' \
    --performance-tier STANDARD

✅ 効果: テーブル再構築やレート制限付きカスタムライターが不要になり、サービングトラフィックに影響を与えずに日次リフレッシュを完了できる。

🛒 ユースケース 2: 大規模カタログのエンリッチメント・バックフィル

シナリオ: EC サイトの数百万 SKU に新しい属性 (例: サステナビリティスコア) を追加したい。既存の商品データは上書きせず、属性のみを安全に投入したい。

JSON挿入専用の条件式
{"Item": {"SKU": {"S": "PROD-001"}, "EcoScore": {"N": "85"}, "Source": {"S": "backfill"}}, "ConditionExpression": "attribute_not_exists(EcoScore)"}

✅ 効果: 条件式により既にスコアを持つ商品はスキップされ、再実行しても安全なべき等のバックフィルを実現。スキップされたアイテムはレポートで確認可能。

🔄 ユースケース 3: バージョンガード付きの移行

シナリオ: 旧システムからエクスポートしたデータを移行中、新アプリケーションが既に書き込みを開始している。古いエクスポートデータが新しい書き込みを上書きしないようにしたい。

JSONバージョンガードの条件式
{"Item": {"UserId": {"S": "U-1001"}, "Profile": {"S": "..."}, "Version": {"N": "42"}}, "ConditionExpression": "attribute_not_exists(#v) OR #v < :v", "ExpressionAttributeNames": {"#v": "Version"}, "ExpressionAttributeValues": {":v": {"N": "42"}}}

✅ 効果: バージョン比較により新しいアプリケーション書き込みが保護され、Accelerated ティアを使えば 1 億件規模でも 1 時間未満で移行を完了できる。

💰 料金

バルク書き込みは、通常のリクエスト単位の書き込み (PutItem / BatchWriteItem) よりも低い価格で課金されます。テーブル本体に加えて、GSI / LSI への書き込みバイト数も個別に計測され、使用量に含まれます。ベクトルインデックスのバイト数はテーブルやセカンダリインデックスとは別に計測されます。

課金に関する注意点
  • バリデーションで拒否されたアイテム (テーブル書き込み前) は課金されない
  • テーブルに到達して条件チェックに失敗したアイテムは課金される
  • クロスリージョンの S3 バケットを使用する場合、データ転送料金が別途発生

具体的な料金は Amazon DynamoDB 料金ページを参照してください。

🔗 関連サービス・機能

🪣 Amazon S3

入力データのソースおよび結果レポートの出力先。クロスアカウント・クロスリージョンバケットにも対応。

📥 DynamoDB Import from Amazon S3

S3 から新規テーブルを作成する既存機能。bulk put items は既存テーブルへの書き込みという点で補完関係にある。

🌊 DynamoDB Streams / Amazon Kinesis Data Streams

バルク書き込みも通常の書き込みと同様にストリームに配信され、zero-ETL 統合を含む下流コンシューマーに伝播する。

🔐 AWS KMS

暗号化されたテーブル、入力データ、出力レポートに対応。

📜 AWS CloudTrail

StartBulkOperation イベントとしてオペレーション開始が記録される。

📝 まとめ

bulk put items は、S3 から既存 DynamoDB テーブルへの大規模データロードという長年の課題を、カスタムパイプラインなしで解決するフルマネージド機能です。テーブルキャパシティを消費しない分離された書き込みパスと、アイテムごとの条件式による安全な書き込みが大きな特長です。

日次リフレッシュ、バックフィル、移行などで S3 とのデータ連携を行っているワークロードでは、既存のカスタム取り込み処理からの置き換えを検討することを推奨します。グローバルテーブルには非対応である点と、DynamoDB Streams の下流コンシューマーのサイジングには注意が必要です。
