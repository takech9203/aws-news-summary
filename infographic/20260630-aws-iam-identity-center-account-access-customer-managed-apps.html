🗝️ AWS IAM Identity Center

カスタマー管理アプリケーションによるプログラムによる AWS アカウントアクセス

外部 IdP で認証済みのユーザーが、追加サインインなしでプログラムによる方法で AWS アカウントへアクセス
リリース日
2026-06-30

📌 概要

AWS IAM Identity Center は、カスタマー管理アプリケーションがユーザーに代わって プログラムによる方法で AWS アカウントへアクセスできる機能を発表しました。 ユーザーに割り当てられたアカウントとロールの検出、および AWS アクセスに必要な一時認証情報の取得が可能になります。

外部 ID プロバイダー (IdP) を 信頼されたトークン発行者 (TTI) として設定済みの場合、 IdP ですでにサインインしているユーザーは別途の認証フローを経ることなく、割り当てられた AWS アカウントにアクセスし、 承認されたロールの一時的なセキュリティ認証情報を取得できます。これにより、IdP サインイン後の 冗長なサインインプロンプトが排除されます。

💡 本機能は IAM Identity Center の組織インスタンスで利用でき、管理者は各カスタマー管理アプリケーションに対して 明示的に AWS アカウントアクセスを有効化する必要があります。

😓 アップデート前の課題

  • 外部 IdP で認証済みでも、AWS アカウントアクセスには別途の認証フローが必要
  • プログラムによる方法で AWS アカウントとロールを検出し、一時認証情報を取得する標準的な仕組みがなかった
  • IdP サインインに加え、冗長なサインインプロンプトがユーザー体験を損なっていた

🎉 アップデート後の改善

  • IdP 発行の JWT トークンを IAM Identity Center トークンと交換し、プログラムによる方法で AWS アクセスが可能に
  • 割り当てられたアカウントとロールを検出し、一時的な AWS 認証情報を取得できる
  • 追加のサインインプロンプトが不要になり、シングルサインオン体験を実現

⚙️ 主要機能

🔑 1. JWT ベアラートークンによるトークン交換

  • 外部 IdP から受け取った署名付き JWT トークンを CreateTokenWithIAM API に渡し、IAM Identity Center トークンと交換
  • グラントタイプ: urn:ietf:params:oauth:grant-type:jwt-bearer
  • この呼び出しには Signature Version 4 (SigV4) 認証が必要

🔍 2. アカウントとロールの検出

  • 取得した IDC トークンで ListAccounts および ListAccountRoles を呼び出す
  • ユーザーに割り当てられた AWS アカウントとロールをプログラムによる方法で検出

🎫 3. 一時認証情報の取得

  • GetRoleCredentials API で、承認されたロールの一時的な AWS セキュリティ認証情報を取得
  • 取得した認証情報でユーザーに代わって AWS リソースへアクセス

♻️ 4. リフレッシュトークンによる再認証の省略

  • リフレッシュトークングラントを有効化していれば、CreateTokenWithIAM はリフレッシュトークンも返す
  • refresh_token グラントで呼び出すことで、JWT 交換を繰り返さずに新しいアクセストークンを取得

📝 設定方法

前提条件

  • JWT をサポートする、IDC に設定済みのカスタマー管理アプリケーション (バックエンドサーバーコンポーネントが必須。SPA などのブラウザベースアプリやパブリッククライアントは非対応)
  • アプリケーションにアタッチされた信頼されたトークン発行者 (TTI)
  • AWS Organizations の管理アカウント、または IDC の委任管理者アカウントへのアクセス権

ステップ 1: マネジメントコンソールで有効化

  • 管理アカウントまたは委任管理者で AWS マネジメントコンソールにサインイン
  • IAM Identity Center コンソールを開く → [Applications]
  • [Customer managed] タブを選択 → 対象アプリケーション名を選択
  • [AWS account access] セクションで [Enable AWS account access] をオン

ステップ 2: AWS CLI で有効化 (プログラムによる方法)

Bashput-application-access-scope
aws sso-admin put-application-access-scope \
  --application-arn arn:aws:sso::123456789012:application/ssoins-1234567890abcdef/apl-1234567890abcdef \
  --scope "sso:account:access"

指定したアプリケーションに sso:account:access スコープを付与します。管理アカウントまたは委任管理者アカウントから実行する必要があります。

✅ メリット

💼 ビジネス面

  • シームレスなユーザー体験: 冗長な再認証が不要になり SSO 体験が向上
  • 一元的なガバナンス: 管理者のみが有効化でき、アクセスを集中管理
  • 既存の ID 基盤の活用: 既存の外部 IdP を TTI としてそのまま利用

🔬 技術面

  • 標準的なプロトコル: OAuth 2.0 の JWT ベアラーグラントを使用
  • 一時認証情報による安全性: 長期キー不使用で漏洩リスクを低減
  • リフレッシュトークン対応: 交換を繰り返さずトークンを更新

⚠️ デメリット・制約事項

制限事項

  • IDC の組織インスタンスでのみ利用可能 (アカウントインスタンスは非対応)
  • バックエンドを持つアプリのみ対象。SPA などブラウザベースアプリ・パブリッククライアントは非対応
  • sso:account:access を有効化できるのは管理アカウント管理者または委任管理者のみ
  • 有効化されたアプリは、ユーザーが利用可能なすべてのアカウントとロールにアクセス可能。特定の制限はできない

考慮すべき点

  • スコープがユーザーの全アクセス権限に及ぶため、有効化前にアクセスレベルを十分に理解する
  • アクセストークン・リフレッシュトークンはバックエンドに保持し、クライアントサイドに公開しない
  • トークンや認証情報をログ・エラーメッセージ・デバッグ出力に記録しない
  • トークンを URL クエリで渡さず、アクセストークンには x-amz-sso_bearer_token ヘッダーを使用
  • AWS CloudTrail で API 呼び出しを監視することが推奨

🎯 ユースケース

① 社内開発者ポータルからの AWS アクセス

シナリオ: 自社開発の開発者ポータルから、各開発者の権限に応じた AWS アカウントのリソースを表示・操作したい。

① 社内 IdP でサインイン → ② JWT を CreateTokenWithIAM で交換 → ③ ListAccounts/ListAccountRoles で表示 → ④ GetRoleCredentials で操作実行

効果: 開発者は AWS への追加サインインなしに、自身の権限範囲でリソースを操作できる

② SaaS 型運用ツールからのマルチアカウント管理

シナリオ: 自社構築の運用ダッシュボードから、ユーザーごとに割り当てられた複数の AWS アカウントを横断管理したい。

① 外部 IdP でサインイン → ② トークン交換でアクセストークン取得 → ③ ListAccounts で全アカウント列挙 → ④ 各アカウントの一時認証情報を取得して集約

効果: 権限セット割り当てに基づき、アクセス可能なアカウントのみを安全に横断管理できる

③ 長時間稼働するバックエンド処理での認証維持

シナリオ: ユーザーに代わって定期的に AWS リソースへアクセスするバックエンド処理を、再サインインなしで継続したい。

① 初回に CreateTokenWithIAM でリフレッシュトークン取得 → ② 失効時は refresh_token グラントで更新 → ③ 更新トークンで GetRoleCredentials を再取得

効果: JWT 交換を繰り返すことなく、アクセストークンを更新して処理を継続できる

🔗 関連サービス・機能

  • AWS Organizations: 組織インスタンスの管理アカウント / 委任管理者から本機能を有効化
  • 外部 ID プロバイダー (IdP): 信頼されたトークン発行者 (TTI) として設定し、ユーザー認証と JWT 発行を担う

  • AWS Security Token Service (STS): 取得した一時認証情報による AWS リソースアクセスの基盤

🏁 まとめ

このアップデートにより、外部 IdP で認証済みのユーザーが、カスタマー管理アプリケーションを通じて 追加のサインインなしにプログラムによる方法で AWS アカウントへアクセスできるようになりました。 OAuth 2.0 の JWT ベアラーグラントと一時認証情報を組み合わせた標準的な仕組みにより、 シームレスなユーザー体験とセキュリティを両立できます。 自社開発の開発者ポータルや運用ツールから AWS アクセスを提供している組織は、 TTI の設定と sso:account:access スコープの有効化を検討するとよいでしょう。
