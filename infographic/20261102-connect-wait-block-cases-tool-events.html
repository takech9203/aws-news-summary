Amazon Connect Customer 📅 2026 年 11 月 2 日

⏸️ Wait ブロックが Cases / External Tool イベントに対応

ケースフィールドの条件一致や外部ツール呼び出しの完了を待ってフローを自動再開 — ポーリング実装なしでイベント駆動の待機を実現

📝 概要

Amazon Connect Customer のカスタマーエクスペリエンスフローで使用する Wait ブロックが、新たに Cases イベントと External Tool イベントをサポートしました。 これまでイベントベース待機は非同期 Lambda 呼び出しの完了のみが対象でしたが、ケースフィールドが指定条件を満たすまで、 または External Tool の非同期呼び出しが完了するまでフローを一時停止できるようになりました。

たとえば、ケースの返金ステータスフィールドが更新されるまでフローを保留し、更新後に自動的に再開して結果に基づきルーティングできます。 重要な情報が揃うまでコンタクトを先に進めないことで、不要な転送を削減し、顧客とエージェント双方の時間を節約できます。

❌ Before: アップデート前の課題

  • イベントベース待機は Lambda の完了のみ対象で、ケースフィールドの更新を直接待機できなかった
  • ケースの状態変化を待つには、Lambda でポーリング処理を実装するなどの回避策が必要だった
  • バックエンド処理の完了前にコンタクトが先に進み、情報不足による不要な転送が発生していた

✅ After: アップデート後の改善

  • ケースフィールドが指定条件 (文字列、数値、存在チェック、複合条件) を満たすまでフローを待機可能に
  • External Tool の非同期呼び出しの完了をフロー内で直接待機できるように
  • ポーリング用のカスタム Lambda が不要になり、フロー設計だけでイベント駆動の待機を構成可能に

Wait ブロックは従来の Lambda 完了イベントに加えて、ケースフィールドの条件一致と External Tool 呼び出しの完了を待機できるようになりました。イベント発生時にフローが再開され、結果に基づいてルーティングされます。

⚙️ 主要機能

📋 Case fields updated イベントNEW

  • Connect Customer Cases のケースフィールドが定義した条件を満たすまでフローを待機
  • Case ID と「Conditions for Case Fields」を指定して構成
  • 文字列条件、数値条件、存在条件、および And / Or による複合条件をサポート
  • Connect Customer Cases が利用可能なリージョンで使用可能

🔧 External Tool returned イベントNEW

  • External Tool ブロックによる非同期呼び出しの完了を待機
  • External Tool ブロックが利用可能なリージョンで使用可能

⚡ 既存の Lambda returned イベントとの併用

  • 非同期実行モードで呼び出した Lambda の RequestId を指定して完了を待機 (従来機能)
  • 各ブランチは単一のイベントタイプを待機するため、複数のイベントを待つ場合はブランチを分けて構成
  • いずれのイベントも発生しない場合は Timeout (最大 7 日間) で分岐

🔬 技術仕様

Wait ブロックの主なプロパティ

項目詳細
Participant TypeDefault (顧客) または Bot (カスタム参加者)。イベントベース待機は Default のみ
Timeout最大 7 日間。手動設定または動的設定 (秒単位)
Set Event based WaitLambda returned / Case fields updated / External Tool returned の各イベントを待機
Keep running while waiting待機中に Continue ブランチへ一時的にルーティング (プロンプト再生など)
ブランチ名静的テキストのみ、最大 100 文字
対応フロータイプInbound flow、Customer Queue flow
対応チャネルVoice (条件付き)、Chat、Task、Email

Case fields updated の条件タイプ

条件タイプ詳細
文字列条件フィールド名、比較演算子 (Equals / Starts with / Ends with / Contains)、値を指定
数値条件フィールド名、比較演算子 (Equals / Greater than / Less than / Greater than or equal to / Less than or equal to)、値を指定
存在条件フィールドが存在するかどうかを判定
複合条件And または Or で 2 つ以上のサブ条件を結合。ネストは 1 階層まで

🛠️ 設定方法

前提条件

✓Amazon Connect Customer インスタンスが有効化されていること (Cases / External Tool イベントは Connect Customer インスタンスのみ)
✓Case fields updated イベントを使用する場合、Connect Customer Cases が設定済みであること
✓External Tool returned イベントを使用する場合、External Tool ブロックで非同期呼び出しを構成していること

手順

1

Wait ブロックをフローに追加

フローデザイナーで Inbound flow または Customer Queue flow を開き、Wait ブロックを配置します。Participant Type に Default を選択します。

2

イベントベース待機を構成

Wait ブロックの Config タブで Set Event based Wait を有効化し、ブランチ名を入力してイベントタイプを選択します。

  • Case fields updated の場合: Case ID を指定し、Conditions for Case Fields で条件を定義。たとえば、ケースが解決済みかつ返金が実施された場合のみルーティングするには、Compound Condition を選択し、「status Equals resolved」という文字列条件と「refund_amount Greater than 0」という数値条件を And で結合します
  • External Tool returned の場合: 非同期で呼び出した External Tool の完了を待機するよう構成します
3

タイムアウトと待機中の動作を設定

Timeout (最大 7 日間) を設定し、イベントが発生しない場合の Time Expired ブランチの遷移先を構成します。待機中にプロンプト再生などを行う場合は Keep running while waiting を有効化し、Continue ブランチに処理を追加します。なお、Continue ブランチ内に Wait ブロックをネストすることはできません。

⚖️ メリットと制約事項

👍 メリット

ビジネス面

✓不要な転送の削減: 重要な情報が揃ってからコンタクトを進めることで、情報不足による転送やたらい回しを防止
✓顧客体験の向上: 返金処理などの完了を待ってから結果を案内でき、顧客の再問い合わせを削減
✓エージェントの時間節約: 必要な情報が揃った状態でルーティングされ、確認作業が減少

技術面

✓ポーリング実装の排除: ケース更新監視用のカスタム Lambda が不要になり、イベント駆動で待機を実現
✓柔軟な条件定義: 文字列、数値、存在チェック、複合条件をノーコードで定義可能
✓フロー設計の一元化: 待機、再開、ルーティングのロジックをフローデザイナー内で完結

⚠️ 制限事項・考慮すべき点

✗Cases / External Tool イベントは Amazon Connect Customer インスタンスでのみ利用可能
✗イベントベース待機は Participant Type が Default の場合のみ利用可能
✗Wait ブロックのネスト (Continue ブランチ内の Wait ブロック) は不可
✗各ブランチは単一のイベントタイプのみ待機可能。複数のイベントソースを待つ場合はブランチを分ける必要あり
✗ブランチ名は静的テキストのみで最大 100 文字
✗複合条件のネストは 1 階層まで
⚠タイムアウトは最大 7 日間。それ以上かかる処理の待機には別のアーキテクチャが必要
⚠各イベントは Connect Customer Cases / External Tool ブロックの利用可能リージョンに依存
⚠誤った Invocation ID などを指定するとタイムアウトまで待機し続けるため、設定値の検証が重要

💡 ユースケース

1️⃣ 返金処理の完了待ちルーティング

シナリオ: 顧客から返金依頼を受け付け、バックエンドの返金処理が完了するまでフローを保留し、完了後に結果を案内する。

実装例 Case fields updated + 複合条件 
1. ケースを作成し、返金処理を開始
2. Wait ブロックで Case fields updated イベントを構成
   - Case ID: 対象ケースの ID
   - Compound Condition (And):
     - String condition: status Equals resolved
     - Number condition: refund_amount Greater than 0
3. 条件一致後、返金完了を案内するブランチへルーティング
4. Time Expired の場合はエージェントキューへ転送

✅ 効果: 返金ステータスの更新を自動検知してフローを再開でき、顧客の再入電や状況不明なままの転送を削減できる。

2️⃣ 外部システム処理の完了待ち

シナリオ: External Tool で外部の基幹システムに注文変更を非同期で依頼し、処理完了後に結果に基づいて応対を継続する。

実装例 External Tool returned + Keep running while waiting 
1. External Tool ブロックで外部システムを非同期呼び出し
2. Wait ブロックで External Tool returned イベントを構成
3. Keep running while waiting を有効化し、待機中は
   Play prompt ブロックで処理中の案内を再生
4. 呼び出し完了後、結果を判定して成功 / 失敗の案内へ分岐

✅ 効果: 外部システムの応答を待つ間も顧客体験を維持しながら、処理結果が確定してから正確な案内を提供できる。

3️⃣ エスカレーション前の情報収集待ち

シナリオ: 専門チームによるケースフィールドの更新 (調査結果の記入) を待ってから、適切なスキルを持つエージェントへルーティングする。

実装例 Case fields updated + 存在条件 
1. 問い合わせ内容からケースを作成し、調査タスクを起票
2. Wait ブロックで Case fields updated イベントを構成
   - Exists condition: investigation_result フィールドが存在
3. 調査結果が記入されたら、結果に基づき担当キューへルーティング
4. Time Expired の場合はコールバックを案内

✅ 効果: 調査結果が揃った状態でエージェントに接続されるため、エージェント間の転送回数と平均処理時間を削減できる。

💰 料金

Wait ブロックのイベントベース待機自体に追加料金は発生しません。 Amazon Connect Customer の利用料金 (チャネルごとの従量課金)、Connect Customer Cases、および連携する Lambda や外部サービスの料金が通常どおり適用されます。 詳細は Amazon Connect 料金ページ を参照してください。

🔗 関連サービス・機能

📋 Amazon Connect Customer Cases: ケース管理機能。今回のアップデートで、ケースフィールドの更新をフローの再開トリガーとして使用可能になった
🔧 External Tool ブロック: 外部ツールを呼び出すフローブロック。非同期呼び出しの完了を Wait ブロックで待機できるようになった
⚡ AWS Lambda: 従来からサポートされている待機対象。非同期実行モードの Lambda 呼び出し完了を RequestId で待機できる

🎯 まとめ

Amazon Connect Customer の Wait ブロックが Cases イベントと External Tool イベントに対応し、 ケースフィールドの条件一致や外部ツール呼び出しの完了をトリガーとしてフローを再開できるようになりました。 ポーリング用のカスタム実装なしでイベント駆動の待機を構成できるため、返金処理などバックエンド処理の完了を待つシナリオでの不要な転送を削減できます。

Connect Customer Cases や External Tool を利用中の場合は、既存フローの待機ロジックを本機能で置き換えられないか検討することを推奨します。
