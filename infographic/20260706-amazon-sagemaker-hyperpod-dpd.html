Amazon SageMaker HyperPod

Disaggregated Prefill and Decode (DPD)

LLM 推論の 2 フェーズを分離し、安定したレイテンシーと高い goodput を実現

📅 リリース: 2026 年 7 月 6 日

📌 概要

Amazon SageMaker HyperPod が、LLM 推論最適化技術 Disaggregated Prefill and Decode (DPD) をサポート。プレフィル (prefill) とデコード (decode) をそれぞれ専用の GPU プールに分離して実行します。

LLM 推論には特性の異なる 2 つのフェーズがあります。プレフィルは入力プロンプト全体を一括処理する計算バウンドな処理、デコードはトークンを 1 つずつ生成するメモリ帯域幅バウンドな処理です。DPD は両者を別々の GPU グループで実行し、リソースの奪い合いを解消します。両フェーズ間の Key-Value (KV) キャッシュの受け渡しは、Elastic Fabric Adapter (EFA) 上の GPU-Direct RDMA で行われます。

インテリジェントルーターがロングコンテキストのリクエストを分離パスへ自動振り分けし、短いプロンプトはデコーダーへ直接送ることで不要な転送オーバーヘッドを回避。チャットアシスタント、エージェンティックパイプライン、RAG、長文ドキュメント分析といった本番 LLM ワークロードで安定したレイテンシーと予測可能なスループットを実現します。

❌ アップデート前の課題
  • プレフィルとデコードを同一 GPU で同居実行し、1 件のロングコンテキストが他の全リクエストのトークン生成を停滞
  • フェーズ間干渉で高負荷時にトークンごとのレイテンシーが悪化
  • 一方を保護するため他方を過剰プロビジョニングする必要
  • 入出力分布に合わせた独立スケールが不可能
✅ アップデート後の改善
  • 計算バウンドとメモリ帯域幅バウンドを別 GPU プールで実行し干渉を解消
  • 混在トラフィック下でレイテンシーが予測可能になり SLO 下の goodput が向上
  • プレフィルとデコードの容量を独立してスケール可能
  • pdSpec を追加するだけで既存構成から有効化

インテリジェントルーターが入力トークン数を routingThreshold と比較し、閾値以上のロングコンテキストはプレフィルプールを経由させて KV キャッシュを EFA + GPU-Direct RDMA でデコードプールへ転送。閾値未満の短いリクエストはプレフィルを省略してデコーダーへ直接送られます。

⚙️ 主要機能

1️⃣ プレフィルとデコードの物理的な分離
  • LLM 推論の 2 フェーズを専用の GPU プールに分離して実行
  • 計算バウンドなプレフィルとメモリ帯域幅バウンドなデコードがリソースを奪い合わない
  • Inference Operator がルーターのプロビジョニング、LMCache と NIXL を用いた Pod 連携、HyperPod オブザーバビリティ統合を自動オーケストレーション
2️⃣ EFA + GPU-Direct RDMA による KV キャッシュ転送
  • プレフィルで計算した KV キャッシュを EFA 上の GPU-Direct RDMA でデコード側 GPU へ直接転送
  • NIXL チャネルを介して転送され、デコーダー側では再計算が不要
  • Llama 70B (TP=8) の場合、6,000 トークンのプロンプトの KV キャッシュは 1 ランクあたり約 0.23 GB
3️⃣ インテリジェントルーターによる条件付きルーティング
  • 入力トークン数が routingThreshold (デフォルト 4,096) 以上のリクエストのみ分離パスへ
  • 閾値未満の短いプロンプトはプレフィラーをバイパスし転送オーバーヘッドを回避
  • ルーティング戦略: prefixaware (デフォルト) roundrobin
4️⃣ 独立したスケーリングと既存機能との組み合わせ
  • prefillSpec.replicas と decodingSpec.replicas でプレフィルとデコードの容量を独立してスケール
  • KV キャッシュオフローディング (L1 キャッシュ) やインテリジェントルーティングと組み合わせ可能

🔬 技術仕様

DPD が効果を発揮する条件

項目詳細
モデルサイズ70B 以上の大規模 Dense モデル (例: Llama 3.3 70B)
入力長4,000 トークン以上の長い入力
同時実行性秒間 2 リクエスト以上の継続的な同時実行
出力長256 トークン以上の中〜長い出力
💡 入力が短い・同時実行性が低い・小規模モデルのワークロードでは、標準の同居 (colocated) デプロイの方がシンプルで良好に動作します。

サポート対象インスタンスタイプ

DPD には GPU-Direct RDMA をサポートする EFA 対応インスタンスが必要です。

インスタンスタイプ備考
ml.p5.48xlargeパフォーマンス検証済み (Llama 3.3 70B)
ml.p5e.48xlargeEFA 対応
ml.p5en.48xlargeEFA 対応
ml.p6-b200.48xlargeEFA 対応
ml.p6-b300.48xlargeEFA 対応

API 変更履歴

🔧 HyperPod Inference Operator の Kubernetes カスタムリソース (InferenceEndpointConfig) の拡張によって提供されます。AWS SDK/API レベルの新規メソッド追加は伴わないため、awsapichanges.com 上での該当する API 変更はありません。

pdSpec の設定例

YAMLpdSpec 設定例
pdSpec:
  prefillSpec:
    replicas: 1
    resources:
      limits:
        nvidia.com/gpu: "8"
      requests:
        nvidia.com/gpu: "8"
    args:
      - "--gpu-memory-utilization"
      - "0.75"
  decodingSpec:
    replicas: 1
    resources:
      limits:
        nvidia.com/gpu: "8"
      requests:
        nvidia.com/gpu: "8"
  routingThreshold: 4096

🚀 設定方法

前提条件

✓AWS CLI がセットアップされていること
✓kubectl 経由で HyperPod Amazon EKS クラスターにアクセスできること
✓モデルチェックポイントへの読み取りアクセス用 Hugging Face トークン (S3 バケットにある場合は不要)
✓vLLM、LMCache、NVIDIA NIXL、EFA libfabric を含むワーカーイメージ (DLC: vllm:server-hyperpod-cuda-v1.1 / LMCache 0.4.3、vLLM 0.19.0、NIXL 1.0.0)
✓HyperPod Inference Operator バージョン 3.2 以降 (新規 EKS クラスターにはデフォルト導入済み)

ステップ 1: Inference Operator のバージョン確認

Bash
kubectl get deployment hyperpod-inference-operator-controller-manager \
  -n hyperpod-inference-system \
  -o jsonpath='{.spec.template.spec.containers[?(@.name=="manager")].image}{"\n"}'

ステップ 2: pdSpec を含むマニフェストの適用

Bash
kubectl apply -f inference_endpoint_dpd_config.yaml

pdSpec が存在することで、Operator がプレフィル用とデコード用の別々の Deployment を作成し、ルーターと LMCache PD バックエンドを介して連携させます。

ステップ 3: デプロイの検証

Bash
kubectl get pods -A | grep -E "prefill-|decode-|router"

プレフィル / デコード / ルーター Pod が Running であること、プレフィラーが sender、デコーダーが receiver を報告することを確認。デコーダーのログで Retrieved N out of N required tokens が出れば KV キャッシュが NIXL 経由で正しく転送されています。

🎯 メリット

💼 ビジネス面
  • 予測可能なユーザー体験: 混在トラフィックでもトークンごとのレイテンシーが安定
  • SLO 遵守とコスト効率: 厳格な SLO 下の goodput 向上、過剰プロビジョニングを削減
  • 容易な移行: 既存構成に pdSpec を追加するだけで導入障壁が低い
🔧 技術面
  • リソース干渉の解消: 計算バウンドとメモリ帯域幅バウンドを分離
  • 独立スケーリング: 入出力分布に合わせて個別調整
  • 高速な KV キャッシュ転送: EFA + GPU-Direct RDMA で低レイテンシー・高スループット
  • 自動オーケストレーション: Operator がルーターと Pod 配線を自動化

⚠️ デメリット・制約事項

制限事項

▸DPD は 70B 以上の Dense モデルで推奨。小規模モデルや MoE モデルは通常恩恵を受けない
▸現行リリースでは 1 エンドポイントあたり単一のデコードデプロイメントのみサポート (複数対応は将来予定)
▸パフォーマンスは ml.p5.48xlarge 上の Llama 3.3 70B で最大 64 同時リクエストまで検証済み
▸GPU-Direct RDMA をサポートする特定の EFA 対応インスタンスタイプに限定

考慮すべき点

▸入力が短い・同時実行性が低い・小規模モデルでは標準の同居デプロイの方が適している
▸PD_BUFFER_SIZE (デフォルト 8 GiB) を超えるとレイテンシースパイクが発生。16/32 GiB への増加やデコードレプリカのスケールを検討
▸PYTHONHASHSEED を固定しないとキャッシュキーが一致せずキャッシュミスが発生
▸標準の同居デプロイに戻すには pdSpec を含まない新しい InferenceEndpointConfig を適用

💡 ユースケース

📄 ユースケース 1: 長文ドキュメント分析サービス

シナリオ: 数千トークンの契約書や技術文書を Llama 3.3 70B で要約・分析する SaaS。長い入力が多く、複数リクエストが継続的に発生。

YAML
pdSpec:
  prefillSpec:
    replicas: 2
  decodingSpec:
    replicas: 1
  routingThreshold: 4096

効果: プレフィルレプリカを増やしてキュー滞留を解消し、長い入力の TTFT を改善しつつデコードのトークンごとのレイテンシーを安定化。

💬 ユースケース 2: 高並行のチャットアシスタント

シナリオ: 多数のユーザーが同時アクセス。システムプロンプトやチャット履歴が共通するリクエストが多い。

YAML
intelligentRoutingSpec:
  enabled: true
  routingStrategy: prefixaware
kvCacheSpec:
  enableL1Cache: true

効果: prefixaware ルーティングと L1 KV キャッシュで共通プレフィックスのヒット率を最大化。ロングコンテキストが他ユーザーのトークン生成を停滞させる問題も解消。

🔎 ユースケース 3: RAG / エージェンティックパイプライン

シナリオ: 検索結果や複数ツール出力を大量のコンテキストとして LLM に渡す RAG やエージェントワークフロー。入力長のばらつきが大きい。

YAML
pdSpec:
  routingThreshold: 4096
environmentVariables:
  - name: PD_BUFFER_SIZE
    value: "17179869184"

効果: 長いコンテキストのみを DPD パスへ、短いリクエストはデコーダー直行で処理しスループットとレイテンシーのバランスを最適化。バッファを 16 GiB に拡大し同時 KV 転送スパイクにも対応。

🔗 関連サービス・機能

  • Amazon EKS: EKS オーケストレーターを使用する HyperPod クラスター上で動作し、InferenceEndpointConfig で構成
  • Elastic Fabric Adapter (EFA): GPU-Direct RDMA による KV キャッシュ高速転送に使用
  • vLLM / LMCache / NVIDIA NIXL: プレフィル/デコード Pod の推論エンジンと KV キャッシュ連携を担うコンポーネント
  • HyperPod オブザーバビリティ: E2E TTFT、KV Transfer Time、DPD Routing Counts などの固有メトリクスをダッシュボードで可視化

📝 まとめ

DPD は、大規模 LLM の本番推論においてフェーズ間干渉を解消し、安定したレイテンシーと高い goodput を実現する重要な最適化技術です。70B 以上の Dense モデルで長い入力・高い同時実行性を持つワークロードを HyperPod で運用している場合は、既存の InferenceEndpointConfig に pdSpec を追加して DPD を検証し、実際の入出力分布に合わせて routingThreshold やレプリカ数をチューニングすることを推奨します。
