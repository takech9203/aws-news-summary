📋 概要

Amazon EKS Capabilities が Amazon CloudWatch Vended Logs のログ配信ソースとして構成可能に。AWS マネージドインフラストラクチャで稼働するマネージドコントローラーからログを収集し、EKS Capabilities の監視とトラブルシューティングが可能になった。

⚡ 主要機能

1. CloudWatch Vended Logs 配信ソース対応

各 EKS Capability を CloudWatch Vended Logs の配信ソースとして登録可能。PutDeliverySource API で Capability ARN を指定してソースを作成。1 つの Capability から複数宛先への同時配信、複数 Capability から同一宛先への集約配信にも対応。

2. 構造化ログ配信

JSON 形式の構造化ログで配信。ログレベル、メッセージ、コントローラー名、リコンシリエーション識別子などの運用フィールドを含む。AWS 内部メタデータはフィルタリングされ、運用に関連するコンテンツのみが配信される。ACK ログには controllerGroup フィールドが含まれ、サービスコントローラーの識別が可能。

3. Capability ごとの個別ログタイプ

ACK: EKS_CAPABILITY_ACK_LOGS / kro: EKS_CAPABILITY_KRO_LOGS / Argo CD: 5 つの個別ログタイプ (Application, ApplicationSet, CommitServer, RepoServer, Server)。ログタイプごとに独立した配信設定が可能。

4. 3 種類の配信先サポート

✓ CloudWatch Logs: リアルタイムクエリと Logs Insights による分析 ✓ Amazon S3: 長期保存と Athena による分析 ✓ Kinesis Data Firehose: ストリーミング処理と OpenSearch 等への転送

CloudWatch Vended Logs の既存 API を使用してログ配信を設定する。

Step 1: Capability ARN の取得

Bash EKS Capability ARN の取得 
aws eks describe-capability \
  --region us-east-1 \
  --cluster-name my-cluster \
  --capability-name my-ack-capability \
  --query 'capability.capabilityArn' --output text

Step 2: 配信ソースの作成

Bash CloudWatch Vended Logs 配信ソース登録 
aws logs put-delivery-source \
  --name "my-ack-logs-source" \
  --resource-arn "arn:aws:eks:us-east-1:123456789012:capability/my-cluster/ack/my-ack-capability" \
  --log-type "EKS_CAPABILITY_ACK_LOGS"

Step 3: 配信先の作成

Bash 配信先設定 
aws logs put-delivery-destination \
  --name "my-logs-destination" \
  --delivery-destination-configuration \
    "destinationResourceArn=arn:aws:logs:us-east-1:123456789012:log-group:/eks/capabilities/ack:*"

Step 4: 配信の作成

Bash ログ配信開始 
aws logs create-delivery \
  --delivery-source-name "my-ack-logs-source" \
  --delivery-destination-arn "arn:aws:logs:us-east-1:123456789012:delivery-destination:my-logs-destination"

    }
  ]
}

🎯 ユースケース

1. Argo CD デプロイメント障害の調査

GitOps ワークフローで Argo CD による自動デプロイが失敗した際に、Application コントローラーのログを確認して根本原因を特定する。
CloudWatch Logs Insights エラーログ検索クエリ 
fields @timestamp, controller, message, error
| filter level = "error"
| sort @timestamp desc
| limit 50

→ リポジトリ同期エラー、マニフェスト適用エラー、RBAC 関連の問題を迅速に特定し、デプロイメントパイプラインの復旧時間を短縮。

2. ACK リソースリコンシリエーションの監視

ACK で管理している AWS リソースのリコンシリエーションが正常に動作しているか継続的に監視し、ドリフトの検出と修正状況を把握する。
CloudWatch Logs Insights RDS リコンシリエーション監視クエリ 
fields @timestamp, controllerGroup, message
| filter controllerGroup = "rds.services.k8s.aws"
| filter message like /reconcil/
| sort @timestamp desc
| limit 100

→ ACK コントローラーによる AWS リソースの状態管理を可視化し、リコンシリエーション失敗時のアラート設定やダッシュボード作成が可能に。

3. セキュリティ監査とコンプライアンスログの長期保存

マネージドコントローラーの操作ログを S3 に長期保存し、コンプライアンス要件を満たすための監査証跡を維持する。
Bash S3 への監査ログ配信設定 
# S3 バケットへの配信設定
aws logs put-delivery-destination \
  --name "audit-logs-s3" \
  --delivery-destination-configuration \
    "destinationResourceArn=arn:aws:s3:::my-audit-bucket"

aws logs create-delivery \
  --delivery-source-name "my-argocd-server-logs" \
  --delivery-destination-arn "arn:aws:logs:us-east-1:123456789012:delivery-destination:audit-logs-s3"

→ 規制要件に準拠したログ保存を実現し、Amazon Athena でのアドホック分析も可能。保存期間やライフサイクルポリシーは S3 側で柔軟に設定可能。

✅ メリット

ビジネス面

✓障害対応時間の短縮: コントローラーログへの直接アクセスにより MTTR を削減
✓運用コストの削減: AWS サポートへの問い合わせを減らし、セルフサービスでのトラブルシューティングが可能に
✓コンプライアンス対応: マネージドコンポーネントのログを S3 に長期保存し、監査要件に対応可能

技術面

✓構造化ログによる分析容易性: JSON 形式により CloudWatch Logs Insights での高度なクエリが可能
✓柔軟な配信アーキテクチャ: 1:N / N:1 の配信トポロジーを構成可能
✓選択的ログ収集: Argo CD の 5 つのコンポーネントログを個別に制御可能
✓既存の監視基盤との統合: CloudWatch / S3 / Firehose 経由で既存の SIEM と連携可能

⚠️ 制限事項・注意点

⚠️EKS Capabilities が利用可能なリージョンでのみ使用可能
⚠️ログに含まれるのは運用関連情報のみ (AWS 内部メタデータはフィルタリング)
⚠️各クラスターにつき同一タイプの Capability は 1 つのみ作成可能
⚠️ログ配信の遅延は宛先によって異なる場合がある
⚠️大量のリコンシリエーションが発生する環境ではログ量増加によるコスト影響に注意
⚠️クロスアカウント配信には PutDeliveryDestinationPolicy API で追加の IAM ポリシー設定が必要
⚠️ACK は 50 以上のサービスコントローラーのログが単一ログタイプに集約されるため、controllerGroup でのフィルタリングが必要な場合あり
