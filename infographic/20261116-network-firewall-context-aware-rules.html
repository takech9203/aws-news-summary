AWS Network Firewall AWS Transit Gateway 📅 2026 年 11 月 16 日

🛡️ コンテキストアウェアルール対応

Transit Gateway アタッチ型 Network Firewall で、IP アドレスではなくリソース ID でトラフィックを制御

📌 概要

AWS Transit Gateway にアタッチされた AWS Network Firewall で、ファイアウォールポリシーに コンテキストアウェアルールを使用できるようになりました。 IP アドレスの代わりに VPC、サブネット、セキュリティグループ、Transit Gateway アタッチメントの ID (コンテキスト識別子) を参照してトラフィックをマッチングできます。

ルールはリソースの識別子に基づいてマッチングされるため、参照した境界内のすべてのリソースに適用され、 ルール作成後に追加された新しいワークロードも自動的にカバーされます。 送信元としては任意のプロトコルで、宛先としては HTTP、TLS、SSH などの TCP ベースのプロトコルで参照できます。 フローログとアラートログにもコンテキスト識別子が記録され、リソース観点での調査が可能です。

❌ Before: アップデート前の課題

  • ステートフルルールは IP アドレスやポートに基づく記述が必要で、ワークロード追加や IP 変更のたびに IP セットの更新が必要だった
  • サブネットやセキュリティグループなどの論理的な境界で制御するには、CIDR 範囲を手動で管理し続ける運用負荷が発生
  • 動的に変化する環境では IP ベースのルールと実際の構成に乖離が生じ、セキュリティ制御の抜け漏れリスクがあった

✅ After: アップデート後の改善

  • VPC ID、サブネット ID、セキュリティグループ ID、TGW アタッチメント ID を直接ルールに参照でき、リソース識別子ベースの制御が可能に
  • 既存のルールが新規ワークロードを自動的にカバーし、組織の拡大に伴う手動ルール更新が不要に
  • フローログとアラートログにコンテキスト識別子が記録され、リソースの観点でトラフィックを調査可能に

AWS Network Manager のコンテキストストアが Transit Gateway 配下のリソース情報を追跡し、Network Firewall がこれを自動的に同期します。 ファイアウォールポリシー内のコンテキストアウェアルールは、同期されたコンテキスト識別子 (VPC、サブネット、セキュリティグループ、TGW アタッチメントの ID) に基づいてトラフィックをマッチングします。

⚡ 主要機能

🎯 1. コンテキスト識別子によるトラフィックマッチング

  • VPC (vpc-)、サブネット (subnet-)、セキュリティグループ (sg-)、TGW アタッチメント (tgw-attach-) の ID をルールで参照可能
  • IP アドレスやポートの指定に加えて、または代わりにコンテキストを使用できる
  • ルール作成後に追加されたリソースにもルールが自動適用される

↔️ 2. 送信元・宛先の両方で使用可能

  • 送信元のコンテキスト識別子は、すべてのプロトコルのすべてのフローの全パケットで利用可能
  • 宛先は、戻りトラフィックから受信側リソースを学習する仕組みのため、HTTP、TLS、SSH などの TCP ベースのプロトコルで利用可能

📝 3. コンテキストセット ContextSets によるルール記述

  • RuleVariables に ContextSets を定義し、$APP_SUBNETS のような変数名で参照
  • 1 つのコンテキストセットに VPC、セキュリティグループなど異なる種類の ID を混在可能
  • 既存の IPSets や PortSets と同一ルール内で組み合わせ可能

📊 4. ログへのコンテキスト記録

  • フローログとアラートログに各フローのコンテキスト識別子が記録される
  • ルールにマッチしないフローのコンテキストも記録され、リソース観点でのトラフィック調査が可能

🧩 5. 複数のポリシー形式に対応

  • Next Generation Firewall ポリシーのファイアウォールルールグループおよび IPS ルールグループで使用可能
  • Classic ポリシーのステートフルルールグループ (Suricata 互換 RulesString および構造化 StatefulRules) でも使用可能

💻 ルール記述例

コンテキストセットを定義し、アプリケーションサブネットからデータベースサブネットへの HTTPS のみを許可するファイアウォールルールグループの例です。

JSON firewall-rules.json 
{
    "RuleVariables": {
        "ContextSets": {
            "APP_SUBNETS": {
                "Definition": [
                    "subnet-1234567890abcdef0",
                    "subnet-021345abcdef6789a"
                ]
            },
            "DB_SUBNETS": {
                "Definition": [
                    "subnet-0abc123def4567890"
                ]
            }
        }
    },
    "RulesSource": {
        "RulesString": "accept:flow tcp:all $APP_SUBNETS any -> $DB_SUBNETS 443 (sid:1001;)"
    }
}

1

コンテキストストアの作成と Transit Gateway の関連付け

AWS Network Manager コンソールでグローバルネットワークを選択 (または新規作成) し、ファイアウォールがアタッチされている Transit Gateway を登録して Available になるまで待ちます。[コンテキストストア] から [コンテキストストアの作成] で登録済みの Transit Gateway を関連付けます。

関連付けは通常数分で Associated になります。グローバルネットワークごとに作成できるコンテキストストアは 1 つで、Transit Gateway ごとに 1 回の設定で完了します。

2

IAM ロールの作成

ストア所有アカウントで NetworkFirewallContextStoreReadOnly という名前の IAM ロールを作成します。信頼ポリシーで network-firewall.amazonaws.com の AssumeRole を許可し、以下の許可ポリシーをアタッチします。

JSON IAM 許可ポリシー 
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "networkmanager:GetContextStoreAssociation",
                "networkmanager:GetContextVersion",
                "networkmanager:ListContexts",
                "networkmanager:ListContextChanges"
            ],
            "Resource": "*"
        }
    ]
}
⚠️ このロールがないと、ファイアウォールはコンテキストストアと同期できず、コンテキストアウェアルールはどのトラフィックにもマッチしません。ロールはストア所有アカウントごとに 1 回作成すればよく、アカウント内のすべてのコンテキストストアをカバーします。
3

ファイアウォールの同期状態の確認

Network Firewall 側の設定は不要です。ファイアウォールは Transit Gateway に関連付けられたコンテキストストアを自動的に検出します (通常は関連付けから数分以内)。

Bash ファイアウォール詳細の取得 
aws network-firewall describe-firewall --firewall-name example-firewall

レスポンスの Firewall オブジェクトで ContextStoreId と ContextStoreOwnerAccountId が設定されていれば検出完了です。コンソールではファイアウォール詳細ページの [Context store sync state] セクションで確認できます。

4

コンテキストストア内のリソースの確認

Bash 追跡リソース一覧の取得 
aws network-firewall list-resources-in-context-store \
    --context-store-id <context-store-id> \
    --filters Region=ap-northeast-1,ResourceType=Subnet

ルールで参照するコンテキスト ID は、この API が返す ID である必要があります。

5

コンテキストアウェアルールの作成

Bash ルールグループの作成 
aws network-firewall create-rule-group \
    --type FIREWALL --capacity 100 \
    --rule-group-name example-context-firewall-rule-group \
    --firewall-rule-group file://firewall-rules.json \
    --region ap-northeast-1

ContextSets を含むルールグループ定義ファイルからファイアウォールルールグループを作成し、ファイアウォールポリシーに追加するとコンテキストアウェアルールが有効になります。

💡 メリット

💼 ビジネス面

✓運用負荷の削減: 既存のルールが新規ワークロードを自動的にカバーし、組織の成長に伴う手動更新が不要
✓一貫したセキュリティガバナンス: IP アドレスの変化に影響されず、論理的な境界に基づいた制御を維持
✓追加コストなし: コンテキストアウェアルールは追加料金なしで利用可能

⚙️ 技術面

✓意図が明確なルール記述: 「アプリ層から DB 層への HTTPS のみ許可」のように、アーキテクチャの意図をそのまま表現でき、CIDR の読み解きが不要
✓既存のルール変数との統合: IPSets、PortSets と組み合わせ可能で、段階的な移行がしやすい
✓調査性の向上: ログにコンテキスト識別子が記録され、関与したリソースを直接特定できる
✓安全な削除の扱い: リソースを削除してもルールは残りの ID へのマッチングを継続。削除された ID は再利用されないため即時更新は不要

⚠️ デメリット・制約事項

🚧 制限事項

✗Transit Gateway アタッチ型の Network Firewall のみ対応 (VPC 内にエンドポイントを配置する従来の構成では利用不可)
✗宛先位置でのコンテキスト識別子の使用は TCP または TCP ベースのアプリケーションプロトコルに限定 (戻りトラフィックから受信側リソースを学習するため)
✗コンテキストストアの事前設定 (グローバルネットワーク作成、Transit Gateway 登録、ストアの関連付け) が必要
✗グローバルネットワークごとに作成できるコンテキストストアは 1 つで、関連付けできるのは Transit Gateway のみ

🤔 考慮すべき点

⚠ストア所有アカウントに NetworkFirewallContextStoreReadOnly という固定名の IAM ロールが必須。ロールがない場合、ルールはどのトラフィックにもマッチしないため設定漏れに注意
⚠ルールグループ更新時は RuleVariables を含む完全なルールグループオブジェクトを指定する必要がある。変数を省略した更新を行うとコンテキストセットが削除される
⚠コンテキスト ID はポリシーのデプロイ時に解決されるため、ストアが認識しない ID を参照したルールは何にもマッチしない。ListResourcesInContextStore での事前確認を推奨

🎯 ユースケース

🏢 ユースケース 1: アプリケーション層とデータベース層のセグメンテーション

シナリオ: マルチ VPC 環境で、アプリケーションサブネットからのみデータベースサブネットへのアクセスを許可し、その他のアクセスをすべてブロックしたい。

Suricata実装例
accept:flow tcp:all $APP_SUBNETS any -> $DB_SUBNETS [3306,5432] (msg:"Allow application to database subnets"; sid:2004;)
drop:flow tcp:all any any -> $DB_SUBNETS [3306,5432] (msg:"Block all other access to database subnets"; sid:2005;)

効果: サブネット ID に基づくセグメンテーションにより、IP アドレスの管理なしでデータベース層を保護。新しいアプリケーションサブネットを $APP_SUBNETS に追加するだけで制御を拡張できる。

🔒 ユースケース 2: 隔離済みセキュリティグループからのトラフィック監視

シナリオ: インシデント対応で隔離 (検疫) 用セキュリティグループに移したリソースからの全トラフィックを検知・ブロックしたい。

Suricata実装例
drop:flow tcp:all $QUARANTINE_SG any -> $EXTERNAL_NET any (msg:"Block external access from quarantined resources"; sid:3001;)

効果: 隔離対象のリソースをセキュリティグループに追加するだけで、ファイアウォールレベルでの封じ込めが即座に適用される。アラートログにはセキュリティグループ ID が記録されるため、調査も容易になる。

🌐 ユースケース 3: オンプレミス接続からのプロトコル制御

シナリオ: Direct Connect 経由のオンプレミス接続 (Transit Gateway アタッチメント) からの UDP トラフィックをブロックしたい。

Suricata実装例
drop udp $ON_PREM any -> any any (msg:"Block UDP from on-premises attachments"; sid:2006;)

効果: Transit Gateway アタッチメント ID により、トラフィックがネットワークに入ってくる経路に基づいた制御が可能。オンプレミス側の IP アドレス体系を把握・管理する必要がない。

📝 まとめ

AWS Network Firewall のコンテキストアウェアルールにより、IP アドレスではなく VPC、サブネット、セキュリティグループ、Transit Gateway アタッチメントといったリソースの識別子 に基づいたトラフィック制御が可能になりました。既存のルールが新規ワークロードを自動的にカバーするため、 動的に成長する環境でのルール管理の負荷が大幅に軽減されます。

Transit Gateway アタッチ型の Network Firewall を運用している場合は、AWS Network Manager でコンテキストストアを設定し、 IP ベースのルールからの段階的な移行を検討することを推奨します。
