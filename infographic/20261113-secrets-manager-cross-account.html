AWS Secrets Manager

🔐 クロスアカウントレプリケーション対応

📅 リリース日: 2026 年 11 月 13 日

プライマリシークレットの同期コピーを別の AWS アカウントに保持可能に。 クロスアカウントアクセス、バックアップ、災害対策 (DR) に活用できます。

📌 概要

従来のマルチリージョンレプリケーション機能を、アカウント境界を越えて拡張するアップデートです。 プラットフォームチームやセキュリティチームがシークレットを一元的に所有・ローテーションしながら、利用側の各アカウントは常に最新のローカルコピーを取得できます。

レプリカは完全に独立したリソースであり、レプリカアカウントが所有するカスタマーマネージド KMS キーで暗号化され、ローテーションを含むプライマリ側の値の変更時に自動更新されます。 ランサムウェアやアカウント侵害から隔離された専用の復旧用アカウントに重要シークレットのライブコピーを保持する DR 用途にも有効で、必要に応じてスタンドアロンシークレットへ昇格できます。

❌ Before: アップデート前の課題
  • シークレットのアカウント間共有には、クロスアカウントのリソースポリシーと KMS キーポリシーの両方を設定・維持する必要があった
  • 利用側アカウントはプライマリアカウントのシークレットをリモート参照するため、プライマリ側の障害や侵害時にアクセス不能になるリスクがあった
  • 別アカウントへのバックアップコピー保持には、独自の同期の仕組みを構築・運用する必要があった
✅ After: アップデート後の改善
  • 利用側アカウントは自アカウント内のローカルなレプリカを参照でき、KMS キー共有やクロスアカウントシークレットポリシーが不要になった
  • プライマリシークレットの値が変更 (ローテーション含む) されるたびに、レプリカが自動的に更新されるようになった
  • 隔離された復旧用アカウントにライブコピーを保持でき、必要時にスタンドアロンシークレットへ昇格できるようになった

プライマリアカウントのシークレット値が変更されると、Secrets Manager がレプリケーションロールを使用してプライマリ側 KMS キーで復号し、レプリカ側 KMS キーで再暗号化して、レプリカアカウントのシークレットへ自動的に伝播します。利用側アプリケーションは自アカウント内のレプリカをローカルに参照できます。

⚙️ 主要機能

🔄 1. アカウント間のシークレット自動同期
  • プライマリシークレットの値が変更されるたびに、新しい値をレプリカへ自動的に伝播
  • 自動ローテーションによる値の変更もレプリカに反映され、利用側アカウントは常に最新の値を取得できる
  • レプリケーションは非同期かつ結果整合性。DescribeSecret でレプリケーションステータスを確認可能
🤝 2. 双方の合意に基づくセットアップモデル
  • レプリカアカウントの所有者が、プライマリシークレットの ARN を参照するレプリカシークレットを作成
  • プライマリアカウントの所有者が AssociateCrossAccountReplica でレプリカを関連付けるとレプリケーションが開始
  • ReplicaRestriction パラメータで、同一 AWS Organizations 内 (SameOrg) に限定するか制限なし (NoRestriction) かを指定可能
🧩 3. 独立したリソースとしてのレプリカ
  • レプリカは独自のリソースポリシー、KMS キー、ライフサイクルを持つ独立したシークレット
  • レプリカアカウント所有のカスタマーマネージド KMS キーで暗号化 (AWS マネージドキー aws/secretsmanager は使用不可)
  • タグとリソースポリシーは各アカウントが個別に管理 (レプリケーション対象外)
  • レプリケーション停止により、レプリカをスタンドアロンのシークレットに昇格可能
🔑 4. 柔軟な認可モデル
  • 推奨はレプリケーションロール方式。Secrets Manager が IAM ロールを引き受け、プライマリ側 KMS キーの kms:Decrypt とレプリカ側 KMS キーの kms:Encrypt を実行
  • レプリケーションロールを指定しない場合は Forward Access Session (FAS) 方式となり、PutSecretValue 等を呼び出した ID の権限でレプリケーションが実行される

🛠️ 設定方法

前提条件

✓プライマリアカウントとレプリカアカウントの 2 つの AWS アカウント (プライマリとレプリカのシークレットは同一リージョン)
✓レプリカアカウントが所有するカスタマーマネージド KMS キー (レプリカの暗号化用)
✓レプリケーションロール方式を使用する場合、プライマリシークレットもカスタマーマネージド KMS キーで暗号化されていること

手順

1
レプリカアカウントで KMS キーポリシーを設定
JSON レプリカ側 KMS キーポリシーへの追加ステートメント 
{
  "Sid": "AllowPrimaryAccountEncrypt",
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::111122223333:role/SecretsManagerCrossAccountReplicationRole"
  },
  "Action": "kms:Encrypt",
  "Resource": "*",
  "Condition": {
    "StringEquals": {
      "kms:EncryptionContext:SecretARN": "arn:aws:secretsmanager:us-east-2:444455556666:secret:MyReplicaSecret-a1b2c3"
    }
  }
}

レプリカ側 KMS キーのキーポリシーに、プライマリアカウント側のレプリケーションロールからの kms:Encrypt を許可するステートメントを追加します。kms:EncryptionContext:SecretARN 条件により、このキーの利用をレプリカシークレットに限定できます。

2
レプリカアカウントでレプリカシークレットを作成
Bash AWS CLI 
aws secretsmanager create-secret \
  --name MyReplicaSecret \
  --kms-key-id arn:aws:kms:us-east-2:444455556666:key/replica-key-id \
  --cross-account-primary-arn arn:aws:secretsmanager:us-east-2:111122223333:secret:MyPrimarySecret-a1b2c3 \
  --region us-east-2

CreateSecret の新パラメータ CrossAccountPrimaryARN にプライマリシークレットの ARN を指定し、カスタマーマネージド KMS キーを指定してレプリカシークレットを作成します。作成直後のレプリケーションステータスは Pending です。

3
プライマリアカウントでレプリケーションロールを作成
JSON レプリケーションロールの権限ポリシー 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DecryptPrimarySecretKey",
      "Effect": "Allow",
      "Action": "kms:Decrypt",
      "Resource": "arn:aws:kms:us-east-2:111122223333:key/primary-key-id"
    },
    {
      "Sid": "EncryptReplicaSecretKey",
      "Effect": "Allow",
      "Action": "kms:Encrypt",
      "Resource": "arn:aws:kms:us-east-2:444455556666:key/replica-key-id"
    }
  ]
}

secretsmanager.amazonaws.com を信頼する IAM ロールを作成し、プライマリ側 KMS キーの kms:Decrypt とレプリカ側 KMS キーの kms:Encrypt を許可します。信頼ポリシーには aws:SourceAccount と aws:SourceArn 条件を設定し、混乱した代理問題を防止することが推奨されます。プライマリ側 KMS キーのキーポリシーにも、このロールからの kms:Decrypt を許可するステートメントを追加します。

4
プライマリアカウントでレプリカを関連付け
Bash AWS CLI 
aws secretsmanager associate-cross-account-replica \
  --secret-id MyPrimarySecret \
  --cross-account-replica-arn arn:aws:secretsmanager:us-east-2:444455556666:secret:MyReplicaSecret-a1b2c3 \
  --replica-restriction SameOrg \
  --replication-role-arn arn:aws:iam::111122223333:role/SecretsManagerCrossAccountReplicationRole \
  --region us-east-2

プライマリアカウントの所有者が AssociateCrossAccountReplica を呼び出してレプリカを関連付けると、レプリケーションが開始されます。--replica-restriction SameOrg により、同一 AWS Organizations 内のアカウントに限定できます。

5
レプリケーションステータスを確認
Bash AWS CLI 
aws secretsmanager describe-secret \
  --secret-id MyPrimarySecret \
  --region us-east-2

DescribeSecret のレスポンスに追加された CrossAccountReplicas フィールドでレプリケーションステータスを確認します。InSync になれば、レプリカはプライマリと同じ値を保持しています。レプリカアカウント側では CrossAccountPrimary フィールドで確認できます。

💡 メリット

💼 ビジネス面

✓シークレット管理の一元化: プラットフォーム / セキュリティチームが所有とローテーションを一元的に担い、利用側チームは自アカウント内のコピーを参照するだけでよく、組織全体のガバナンスが向上
✓ランサムウェア / アカウント侵害対策: 隔離された復旧用アカウントに重要シークレットのライブコピーを保持でき、プライマリアカウントが侵害されても業務継続に必要な認証情報を確保
✓運用コストの削減: アカウント間のシークレット同期を独自に構築・運用する必要がなくなる

🔧 技術面

✓クロスアカウント設定の簡素化: KMS キー共有やクロスアカウントのシークレットリソースポリシーの設定・維持が不要
✓ローテーションとの自動連携: ローテーションを含む値の変更が自動的にレプリカへ伝播され、利用側は常に最新の値を取得
✓独立した暗号化とアクセス制御: レプリカはレプリカアカウント所有の CMK で暗号化され、リソースポリシーやタグも独立して管理可能
✓昇格可能なレプリカ: 必要時にレプリケーションを解除してスタンドアロンシークレットに昇格でき、DR フェイルオーバーに対応

⚠️ デメリット・制約事項

🚧 制限事項

✗プライマリとレプリカのシークレットは同一リージョンに存在する必要がある (リージョンをまたぐ場合は既存のマルチリージョンレプリケーションと組み合わせる)
✗1 つのプライマリシークレットに対してクロスアカウントレプリカは 1 つのみ作成できる
✗レプリカの暗号化にはカスタマーマネージド KMS キーが必須で、AWS マネージドキー aws/secretsmanager は使用できない
✗レプリケーションロール方式では、プライマリシークレットもカスタマーマネージド KMS キーで暗号化されている必要がある

🤔 考慮すべき点

⚠非同期・結果整合性のため、値の変更直後はレプリカに最新値が反映されていない可能性がある。DescribeSecret でステータスを監視する運用が必要
⚠組織の RCP (リソースコントロールポリシー) や SCP (サービスコントロールポリシー) が KMS 操作をブロックすると、ID ポリシーとキーポリシーで許可されていてもレプリケーションが失敗する
⚠FAS 方式では、プライマリシークレットを更新するすべての ID にレプリカ側 KMS キーへのクロスアカウント kms:Encrypt 権限が必要となるため、多くのケースではレプリケーションロール方式が推奨される
⚠レプリカごとにシークレットの保管料金が発生するため、レプリカ数に応じたコストを考慮する

🎯 ユースケース

1️⃣ プラットフォームチームによるシークレットの一元管理と配布

シナリオ: 中央のセキュリティアカウントでデータベース認証情報を一元管理し、自動ローテーションを実施している。各ワークロードアカウントのアプリケーションが同じ認証情報を利用する必要がある。

Bash 実装例 
# ワークロードアカウント側でレプリカを作成
aws secretsmanager create-secret \
  --name shared/db-credentials \
  --kms-key-id <ワークロードアカウントの CMK> \
  --cross-account-primary-arn <セキュリティアカウントのシークレット ARN>

# セキュリティアカウント側で関連付け
aws secretsmanager associate-cross-account-replica \
  --secret-id shared/db-credentials \
  --cross-account-replica-arn <ワークロードアカウントのレプリカ ARN> \
  --replica-restriction SameOrg \
  --replication-role-arn <レプリケーションロール ARN>

効果: ローテーション後の新しい認証情報が自動的にワークロードアカウントへ伝播され、各アプリケーションはクロスアカウント権限なしでローカルのシークレットを参照するだけでよい。

2️⃣ ランサムウェア対策としての隔離復旧用アカウント

シナリオ: 本番アカウントが侵害された場合に備え、厳格にアクセス制限された復旧用アカウントに重要シークレットのライブコピーを保持したい。

Bash 実装例 
# 復旧用アカウントにレプリカを作成し、本番アカウントから関連付け
# 障害発生時はレプリケーションを解除してスタンドアロンに昇格
aws secretsmanager disassociate-cross-account-replica \
  --secret-id <プライマリシークレット> \
  --cross-account-replica-arn <復旧用アカウントのレプリカ ARN>

効果: 本番アカウントが侵害されても、隔離されたアカウントに最新のシークレットが保持されており、スタンドアロンシークレットへ昇格して復旧作業を迅速に開始できる。

3️⃣ マルチアカウント環境での DR フェイルオーバー

シナリオ: アカウント単位の障害ドメイン分離を採用しており、スタンバイアカウントへのフェイルオーバー時にアプリケーションが同じシークレットを利用する必要がある。

Bash 実装例 
# スタンバイアカウントのレプリカのステータスを定期監視
aws secretsmanager describe-secret \
  --secret-id <レプリカシークレット> \
  --query 'CrossAccountPrimary.ReplicationStatus'

効果: フェイルオーバー時にシークレットを手動で移行する必要がなく、スタンバイアカウント内の InSync 状態のレプリカを即座に利用して RTO を短縮できる。

🔗 関連サービス・機能

🔑 AWS KMSレプリカはレプリカアカウント所有のカスタマーマネージドキーで暗号化される。レプリケーション時には Secrets Manager がプライマリ側キーで復号し、レプリカ側キーで再暗号化する
🌐 マルチリージョンレプリケーション既存のリージョン間レプリケーション機能。今回のアップデートはこれをアカウント境界を越えて拡張するもので、組み合わせることでリージョンとアカウントの両方にまたがる冗長化が可能
🏢 AWS OrganizationsReplicaRestriction の SameOrg 設定により、レプリケーション先を同一組織内のアカウントに限定できる
👤 AWS IAMレプリケーションロール (推奨) または Forward Access Session により、クロスアカウントの KMS 操作を認可する

📝 まとめ

AWS Secrets Manager のクロスアカウントレプリケーションにより、KMS キー共有やクロスアカウントポリシーの複雑な設定なしに、シークレットの一元管理と自動配布、そして侵害から隔離されたバックアップが実現できます。 マルチアカウント環境でシークレットを共有している組織や、ランサムウェア対策・DR 戦略を強化したい組織は、独自の同期の仕組みからの移行とレプリケーションロール方式での導入を検討することを推奨します。
