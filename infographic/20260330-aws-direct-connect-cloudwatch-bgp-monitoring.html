📋 概要

AWS Direct Connect において、仮想インターフェース (VIF) の BGP セッションの状態とルート数を監視するための 3 つの新しい Amazon CloudWatch メトリクスが追加されました。カスタムソリューションを構築したり API をポーリングすることなく、CloudWatch でネイティブに BGP セッションを監視できるようになります。

❌ Before
•BGP 監視にカスタム Lambda 関数や API ポーリングが必要
•オンプレミスの監視ツールに依存し AWS 側と統合されていなかった
•プレフィクスリミット超過の事前検知が困難
•サイレントなルート撤回を検知する仕組みがなかった
✅ After
•CloudWatch メトリクスで BGP セッション状態をネイティブ監視
•プレフィクスリミットへの到達を事前にアラームで通知
•AWS 広告ルート数の監視でサイレントなルート撤回を検知
•カスタム Lambda や監視ツールへの依存を排除し運用を簡素化

🆕 新規 CloudWatch メトリクス

すべて AWS/DX 名前空間で発行されます。

1. VirtualInterfaceBgpStatus
BGP セッションの状態を報告するメトリクス。セッションがダウンした際に即座に検知可能。
🎯 用途: セッション障害の検知、CloudWatch Alarms による自動通知
2. VirtualInterfaceBgpPrefixesAccepted
オンプレミスから受信した BGP プレフィクス (経路情報) の数を追跡。プレフィクスリミットに近づいた際にプロアクティブなアラーム設定が可能。
🎯 用途: プレフィクスリミット超過の予防、idle 状態への移行を事前検知
3. VirtualInterfaceBgpPrefixesAdvertised
AWS からオンプレミスに広告されるルート数を監視。設定変更後のルート広告の検証に活用可能。
🎯 用途: サイレントなルート撤回の検知、設定変更の検証

🛠 設定方法

前提条件

1.AWS Direct Connect 接続と VIF が設定済み
2.CloudWatch メトリクスへの読み取りアクセス権限 (cloudwatch:GetMetricData 等)
3.アラーム設定の場合は Amazon SNS トピックの作成権限
1
BGP メトリクスの確認
メトリクスは自動的に CloudWatch に発行されます。追加の設定は不要です。
Bash メトリクスの確認 
aws cloudwatch list-metrics \
  --namespace "AWS/DX" \
  --metric-name "VirtualInterfaceBgpStatus"
2
BGP セッション状態のアラーム設定
BGP セッションがダウンした際に SNS 通知を送信するアラームを設定します。
Bash セッション状態アラーム 
aws cloudwatch put-metric-alarm \
  --alarm-name "dx-bgp-session-down" \
  --alarm-description "Direct Connect BGP session is down" \
  --namespace "AWS/DX" \
  --metric-name "VirtualInterfaceBgpStatus" \
  --dimensions Name=VirtualInterfaceId,Value=dxvif-xxxxxxxxx \
  --statistic Average \
  --period 60 \
  --threshold 1 \
  --comparison-operator LessThanThreshold \
  --evaluation-periods 2 \
  --alarm-actions arn:aws:sns:ap-northeast-1:123456789012:dx-alerts
3
プレフィクス数のアラーム設定
受信プレフィクス数がしきい値に近づいた際に通知します。リミットの 90% 程度に設定を推奨。
Bash プレフィクス数アラーム 
aws cloudwatch put-metric-alarm \
  --alarm-name "dx-bgp-prefix-limit-warning" \
  --alarm-description "BGP accepted prefixes approaching limit" \
  --namespace "AWS/DX" \
  --metric-name "VirtualInterfaceBgpPrefixesAccepted" \
  --dimensions Name=VirtualInterfaceId,Value=dxvif-xxxxxxxxx \
  --statistic Maximum \
  --period 300 \
  --threshold 90 \
  --comparison-operator GreaterThanOrEqualToThreshold \
  --evaluation-periods 1 \
  --alarm-actions arn:aws:sns:ap-northeast-1:123456789012:dx-alerts
4
CloudWatch ダッシュボードへの追加
3 つの BGP メトリクスを 1 つのダッシュボードに統合し、BGP セッションの健全性を一元的に可視化します。
Bash ダッシュボード作成 
aws cloudwatch put-dashboard \
  --dashboard-name "DirectConnect-BGP-Monitoring" \
  --dashboard-body '{
    "widgets": [
      {
        "type": "metric",
        "properties": {
          "title": "BGP Session Status",
          "metrics": [["AWS/DX", "VirtualInterfaceBgpStatus", "VirtualInterfaceId", "dxvif-xxxxxxxxx"]],
          "period": 60, "stat": "Average"
        }
      },
      {
        "type": "metric",
        "properties": {
          "title": "BGP Prefixes Accepted",
          "metrics": [["AWS/DX", "VirtualInterfaceBgpPrefixesAccepted", "VirtualInterfaceId", "dxvif-xxxxxxxxx"]],
          "period": 300, "stat": "Maximum"
        }
      },
      {
        "type": "metric",
        "properties": {
          "title": "BGP Prefixes Advertised",
          "metrics": [["AWS/DX", "VirtualInterfaceBgpPrefixesAdvertised", "VirtualInterfaceId", "dxvif-xxxxxxxxx"]],
          "period": 300, "stat": "Maximum"
        }
      }
    ]
  }'

⚠ デメリット・制約事項

制限事項

•メトリクスは VIF 単位で発行。多数の VIF を持つ環境ではアラーム設定の管理が複雑になる可能性あり
•メトリクスの粒度 (発行間隔) については公式ドキュメントで確認が必要
•BGP セッションの詳細な状態遷移 (Idle, Connect, Active, OpenSent, OpenConfirm, Established 等) の区別はメトリクス仕様の確認が必要

考慮すべき点

•既存のカスタム Lambda による BGP 監視ソリューションとの併用期間を設け、段階的に移行することを推奨
•CloudWatch メトリクスの保持期間に注意 (1 分間隔: 15 日間、5 分間隔: 63 日間)
•オンプレミス側のルーター監視との相関分析を行う場合は、別途統合の検討が必要

🎯 ユースケース

1. ハイブリッドクラウド接続の統合監視
複数の Direct Connect 接続を持つエンタープライズ環境で、すべての BGP セッションの健全性を一元的に監視するシナリオ。
✅ CloudWatch ダッシュボードで全 Direct Connect 接続の BGP 状態をリアルタイムに把握でき、障害発生時の初動対応時間を短縮
2. プレフィクスリミット超過の予防
オンプレミスのルーティング変更によりプレフィクス数が増加し、BGP セッションが idle 状態になることを防止するシナリオ。
✅ プレフィクスリミット超過を事前に検知し、ルーティングポリシーの調整やリミット引き上げ申請を計画的に実施
3. ルート変更の影響検証
AWS 側のルーティング設定変更 (VPC CIDR の追加や Transit Gateway のルート変更) が、オンプレミスへの広告ルートに正しく反映されているか検証するシナリオ。
✅ 設定変更前後の広告プレフィクス数を比較し、意図した通りにルートが広告されているか定量的に検証
