⚡ AWS Lambda

Lambda Managed Instances のゼロスケール対応

Scale to and from zero — アイドル期間中のインスタンス料金を削減 | 📅 リリース日: 2026 年 11 月 17 日

📝 概要

AWS Lambda は、Lambda Managed Instances (LMI) 上で動作する Event Functions に対して、ゼロへのスケールインとゼロからのスケールアウトをサポートしました。アイドル期間中は Lambda が実行環境を自動的にゼロまでスケールダウンし、リクエストが到着すると再び実行環境を起動します。

LMI は、Lambda のシンプルな運用性を維持しながら、お客様のアカウント内の Amazon EC2 インスタンス上で Lambda 関数を実行できる機能です。今回のアップデートで、トラフィックがない期間が続くと実行環境がゼロまでスケールインされ、対応する Managed Instance も終了されるため、アイドル期間中のインスタンス料金を削減できます。

❌ Before: アップデート前の課題
  • トラフィックがなくても最小数の実行環境を常時稼働させる必要があった
  • アイドル期間中も Managed Instance (EC2) の料金が発生し続けていた
  • 開発・テスト環境や非同期処理など断続的なワークロードではコスト効率が低かった
✅ After: アップデート後の改善
  • MinExecutionEnvironments = 0 でアイドル時に自動でゼロまでスケールイン
  • リクエスト到着で自動的に実行環境が再起動され、手動での再有効化が不要
  • トラフィックのない期間があるワークロードでも LMI をコスト効率よく利用可能

アイドル期間が続くと実行環境がゼロまでスケールインされてインスタンスが終了し、新しい呼び出しが到着すると実行環境が再起動されます。起動完了までの間、呼び出しは HTTP 429 でスロットリングされます。

🔧 主要機能

1️⃣ ゼロへの自動スケールイン
  • MinExecutionEnvironments = 0、MaxExecutionEnvironments ≧ 1 で有効化
  • 一定期間呼び出しがないと、Lambda が最後の実行環境を停止
  • 実行環境がゼロになっても関数バージョンは Active 状態を維持
  • 実行環境が動いていない Managed Instance は終了され、インスタンス料金を削減 (終了完了まで通常数分、その間は課金が継続)
2️⃣ ゼロからの自動スケールアウト
  • ゼロにスケールした関数を呼び出すと、HTTP 429 でスロットリングしつつ実行環境の起動を開始
  • 空きのある Managed Instance がない場合は新しいインスタンスを起動
  • 最初の実行環境の準備完了まで (通常数分) スロットリングが継続、その後は通常どおりスケール
  • AWS SDK はデフォルトでリトライするが、十分なリトライ回数と指数バックオフの設定を推奨
3️⃣ ゼロスケールと非アクティブ化の使い分け
  • Min = 0 かつ Max > 0: ゼロスケール。呼び出しがあれば自動で復帰
  • Min = 0 かつ Max = 0: 非アクティブ化。復帰には PutFunctionScalingConfig の再実行が必要
  • ゼロスケール状態の関数バージョンも、キャパシティプロバイダーごとの関数バージョンクォータにカウントされる点に注意
4️⃣ スケジュールスケーリングとの組み合わせ
  • Amazon EventBridge Scheduler から PutFunctionScalingConfig をユニバーサルターゲットとして呼び出し、時間帯に応じた設定変更が可能
  • 例: 営業時間中は Min = 10 で待機させ、夜間は Min = 0 にしてゼロスケールを許可

📋 技術仕様

スケーリング設定の仕様

項目詳細
設定 APIPutFunctionScalingConfig (コンソール、AWS CLI、AWS SDK、CloudFormation、SAM、CDK から設定可能)
設定値の範囲MinExecutionEnvironments、MaxExecutionEnvironments ともに 0 〜 15,000
ゼロスケールの条件Min = 0 かつ Max > 0
非アクティブ化の条件Min = 0 かつ Max = 0
設定の適用範囲関数の修飾 ARN 単位 ($LATEST.PUBLISHED に設定すると以降のバージョンに継承)
ゼロスケール中の関数状態Active 状態を維持

ゼロにスケールしないケース

ケース説明
最後の実行環境が CPU を使用中バックグラウンドスレッドやポーリングループなど、呼び出し間に処理が動いていると最後の実行環境がスケールインされない場合がある
デプロイ進行中ローリング更新や重み付きエイリアスによるトラフィックシフト中は、各バージョンで最低 1 つの実行環境が維持される。デプロイ完了後にゼロスケール可能になる

⚙️ 設定方法

前提条件

✓Lambda Managed Instances のキャパシティプロバイダーが作成済みであること
✓対象の関数が LMI 上で動作する Event Function であること
✓lambda:PutFunctionScalingConfig を実行できる IAM 権限があること

ステップ 1: ゼロスケールを有効化する

Bash 最小実行環境数を 0 に設定 
aws lambda put-function-scaling-config \
  --function-name my-lmi-function \
  --qualifier '$LATEST.PUBLISHED' \
  --function-scaling-config MinExecutionEnvironments=0,MaxExecutionEnvironments=20 \
  --region us-east-1

最小値と最大値は必ずペアで指定する必要があり、指定しなかった値はデフォルトにリセットされます。

ステップ 2: スケジュールスケーリングを設定する (オプション)

Bash 毎日 22:00 UTC にゼロスケールを許可 
aws scheduler create-schedule \
  --name "AllowScaleToZeroLambdaManagedInstances" \
  --schedule-expression "cron(0 22 * * ? *)" \
  --flexible-time-window '{"Mode": "OFF"}' \
  --target '{
    "Arn": "arn:aws:scheduler:::aws-sdk:lambda:putFunctionScalingConfig",
    "RoleArn": "arn:aws:iam::111122223333:role/eventbridge-scheduler-role",
    "Input": "{\"FunctionName\": \"my-lmi-function\", \"Qualifier\": \"$LATEST.PUBLISHED\", \"FunctionScalingConfig\": {\"MinExecutionEnvironments\": 0, \"MaxExecutionEnvironments\": 20}}"
  }'

実行ロールには lambda:PutFunctionScalingConfig の権限が必要です。

ステップ 3: 動作を確認する

ゼロスケール後に関数を呼び出し、最初の呼び出しが HTTP 429 でスロットリングされた後、数分以内に実行環境が起動して処理が再開されることを確認します。スロットリングの要因を特定するには、ConcurrencyThrottles、CPUThrottles、MemoryThrottles、DiskThrottles などのメトリクスを監視します。

⚖️ メリットと制約事項

💼 ビジネス面のメリット

✓コスト削減: アイドル期間中の Managed Instance が終了され、トラフィックのない時間帯のインスタンス料金を削減
✓開発・テスト環境の最適化: 最小キャパシティの常時確保が不要になり、無駄なコストを排除
✓LMI の適用範囲拡大: 断続的なワークロードにも適用しやすくなり、EC2 の料金面での優位性を活かせる場面が増加

🛠️ 技術面のメリット

✓運用の自動化: 復帰に手動操作が不要で、呼び出しをトリガーに自動でスケールアウト
✓柔軟なスケーリング制御: スケジュールスケーリングと組み合わせて予測可能なトラフィックパターンに対応
✓関数単位の設定: 修飾 ARN 単位で設定でき、同一キャパシティプロバイダー内でワークロードごとに使い分け可能

⚠️ 制限事項

✗ゼロからの復帰時、最初の実行環境の準備完了まで呼び出しは HTTP 429 でスロットリング (通常数分)
✗最後の実行環境が CPU を使用し続けていると、ゼロまでスケールインされない場合がある
✗デプロイ (ローリング更新・重み付きエイリアスのトラフィックシフト) 中はゼロにスケールしない
✗ゼロスケール状態でも関数バージョンクォータにカウントされる
✗インスタンス終了が完了するまでの数分間はインスタンス料金が発生

💡 考慮すべき点

⚠レイテンシーに敏感なワークロードでは最小 1 以上 (AZ 冗長性が必要なら 3 以上) の維持を推奨
⚠同期呼び出しのクライアントには起動時間をカバーするリトライ回数と指数バックオフの設定が必要
⚠トラフィックの到来時刻が予測できる場合は、スケジュールスケーリングで事前に最小値を引き上げるとスロットリングを回避可能

🎯 ユースケース

🧪 ユースケース 1: 開発・テスト環境のコスト最適化

シナリオ: 日中の業務時間帯のみ利用される開発・テスト環境の LMI 関数で、夜間や週末のインスタンス料金を削減したい。

Bash実装例
aws lambda put-function-scaling-config \
  --function-name dev-api-function \
  --qualifier '$LATEST.PUBLISHED' \
  --function-scaling-config MinExecutionEnvironments=0,MaxExecutionEnvironments=5

効果利用がない時間帯は実行環境とインスタンスが自動停止され、利用再開時に自動復帰。環境の起動・停止の運用なしでコストを削減。

📦 ユースケース 2: 非同期バッチ処理

シナリオ: SQS や EventBridge をトリガーとする非同期処理で、ジョブの到着が断続的であり、数分の起動遅延を許容できる。

Bash実装例
aws lambda put-function-scaling-config \
  --function-name batch-processor \
  --qualifier '3' \
  --function-scaling-config MinExecutionEnvironments=0,MaxExecutionEnvironments=50

効果ジョブがない期間のインスタンス料金をゼロに近づけつつ、ジョブ到着時に自動でスケールアウト。非同期呼び出しは Lambda 側でリトライされるため、起動遅延の影響を受けにくい。

🕐 ユースケース 3: 業務時間に合わせたスケジュール制御

シナリオ: 業務時間中は低レイテンシーで応答し、夜間はゼロスケールを許可してコストを削減したい社内ツール。

Bash7:00 UTC に最小値を 10 に引き上げ
aws scheduler create-schedule \
  --name "RaiseMinimumLambdaManagedInstances" \
  --schedule-expression "cron(0 7 * * ? *)" \
  --flexible-time-window '{"Mode": "OFF"}' \
  --target '{
    "Arn": "arn:aws:scheduler:::aws-sdk:lambda:putFunctionScalingConfig",
    "RoleArn": "arn:aws:iam::111122223333:role/eventbridge-scheduler-role",
    "Input": "{\"FunctionName\": \"internal-tool\", \"Qualifier\": \"$LATEST.PUBLISHED\", \"FunctionScalingConfig\": {\"MinExecutionEnvironments\": 10, \"MaxExecutionEnvironments\": 20}}"
  }'

効果業務時間中はウォームな実行環境でスロットリングを回避し、夜間は自動的にゼロスケールしてコストを削減。非アクティブ化と異なり、夜間の突発的な利用にも自動で応答可能。

💰 料金と利用可能リージョン

💵 料金

LMI では、関数の実行に使用される EC2 インスタンスの料金と LMI の管理料金が発生します。今回のアップデートにより、アイドル期間中は不要になった Managed Instance が終了され、トラフィックのない期間のインスタンス料金を削減できます。

なお、インスタンスの終了が完了するまで (通常数分) はインスタンス料金が発生し続けます。詳細は AWS Lambda 料金ページ を参照してください。

🌍 利用可能リージョン

Lambda Managed Instances が利用可能なすべての AWS 商用リージョンで利用できます。

🔗 関連サービス・機能

→Amazon EC2: LMI の実行基盤。EC2 の料金面での優位性と多様なインスタンスタイプを活用
→Amazon EventBridge Scheduler: PutFunctionScalingConfig をスケジュール実行し、時間帯に応じたスケーリング制御を実現
→Amazon CloudWatch: ConcurrencyThrottles、CPUThrottles などのメトリクスでスロットリング要因を監視
→AWS CloudFormation / AWS SAM / AWS CDK: スケーリング設定を IaC として管理

✨ まとめ

LMI のゼロスケール対応により、断続的なワークロードでも最小キャパシティの常時確保が不要になり、LMI のコスト効率が大きく向上しました。開発・テスト環境や非同期処理など、アイドル期間のある LMI ワークロードでは、MinExecutionEnvironments を 0 に設定してコスト削減効果を確認することを推奨します。復帰時のスロットリングを考慮し、同期呼び出しのリトライ設定やスケジュールスケーリングとの併用も検討してください。
