🔗 外部キー制約のサポート

Foreign Key Constraints - 参照整合性をデータベース側で保証
📅 リリース日: 2026 年 8 月 27 日

PostgreSQL 互換のサーバーレス分散 SQL データベース Aurora DSQL が、ついに外部キー制約をサポート。PostgreSQL 互換性における最大級のギャップの 1 つが解消され、移行の再評価に値する大きなマイルストーンです。

📝 概要

新規テーブルと既存テーブルの両方に外部キー制約を定義でき、テーブル間の参照整合性をデータベース側で保証できるようになりました。参照を壊す書き込み操作は Aurora DSQL がブロックします。参照アクション 5 種類に加え、MATCH FULL / MATCH SIMPLE のマッチタイプや遅延可能制約 (DEFERRABLE) もサポートし、PostgreSQL の標準的な外部キー機能に近い形で利用できます。

❌ Before: アップデート前の課題

✗外部キー制約を定義できず、参照整合性の検証ロジックをアプリケーション側で実装する必要があった
✗実装漏れや競合状態により孤児レコード (参照先が存在しない行) が発生するリスク
✗既存 PostgreSQL アプリケーションの移行時にスキーマとロジックの書き換えが必要だった

✅ After: アップデート後の改善

✓CREATE TABLE および既存テーブルへの追加で、外部キー制約をデータベース側で定義・強制
✓5 つの参照アクションで参照先の削除・更新時の挙動を柔軟に制御
✓MATCH FULL / SIMPLE、DEFERRABLE をサポートし、移行時の書き換えが不要に

🏗️ 参照整合性の保証メカニズム (OCC ベース)

Aurora DSQL は楽観的並行性制御 (OCC) に基づき、トランザクション開始時のスナップショット検証とコミット時の競合解決の 2 段階で参照整合性を保証します。ロック待機は発生せず、競合はコミット時にシリアライゼーションエラーとして返されます。

1️⃣ スナップショット検証

各トランザクションは開始時点の一貫したスナップショットに対して実行。参照する行の挿入・更新時は参照先テーブルを、参照先キーの削除・更新時は参照元テーブルを読み取って検証。ロックを取得しないため、他のトランザクションは並行して両テーブルを変更可能。

2️⃣ コミット時の競合解決

開始からコミットまでの並行変更を検出するため、参照先の行に暗黙的に KEY SHARE 句を適用。競合が検出された場合、トランザクションはシリアライゼーションエラー (SQLSTATE 40001、OC000) で失敗する。

⚙️ 主要機能

🔗 外部キー制約の定義

列制約 (REFERENCES) として単一列、テーブル制約 (FOREIGN KEY ... REFERENCES ...) として単一列または複数列の複合外部キーを定義可能。参照先の列リストを省略すると主キーが使用されます。自己参照外部キー (ツリー構造など) や、1 つのテーブルへの複数の外部キー制約 (多対多関係) もサポート。新規・既存テーブルの両方に定義できます。

🧩 マッチタイプと遅延可能制約
  • MATCH SIMPLE (デフォルト): 外部キー列のいずれかが NULL の場合、参照先との一致を要求しない
  • MATCH FULL: 複合外部キーにおいて、全列が NULL または全列が非 NULL であることを要求
  • DEFERRABLE / INITIALLY DEFERRED: 制約チェックをコミット時まで遅延可能。相互参照する行を順序を気にせず同一トランザクション内で挿入できる

🛠️ 設定方法

前提条件

✓Aurora DSQL クラスターが作成済みであること
✓PostgreSQL 互換クライアント (psql など) で接続できること
✓参照先の列が遅延不可の UNIQUE 制約または主キー制約を持つこと
1 参照先テーブルの作成
SQL 参照先となる商品テーブル 
CREATE TABLE products (
    product_no integer PRIMARY KEY,
    name text,
    price numeric
);

外部キーの参照先となる列は主キーまたは UNIQUE 制約を持つ必要があります。

2 外部キー制約付きテーブルの作成
SQL REFERENCES 句で外部キーを定義 
CREATE TABLE orders (
    order_id integer PRIMARY KEY,
    product_no integer REFERENCES products ON DELETE RESTRICT,
    quantity integer
);

参照先の列リストを省略すると主キーが使用されます。ON DELETE RESTRICT により、注文から参照されている商品の削除はエラーになります。

3 複合外部キーや遅延制約の定義
SQL 複合外部キーと遅延可能制約 
-- 複合外部キー (テーブル制約形式)
CREATE TABLE shipments (
    shipment_id integer PRIMARY KEY,
    warehouse_id integer,
    product_no integer,
    FOREIGN KEY (warehouse_id, product_no)
        REFERENCES inventory (warehouse_id, product_no) MATCH FULL
);

-- コミット時まで制約チェックを遅延
CREATE TABLE orders_deferred (
    order_id integer PRIMARY KEY,
    product_no integer REFERENCES products DEFERRABLE INITIALLY DEFERRED,
    quantity integer
);

DEFERRABLE INITIALLY DEFERRED を指定すると制約チェックがコミット時まで遅延され、参照先の行より先に参照元の行を挿入できます。

💡 メリット

💼 ビジネス面

✓データ品質の向上: 孤児レコードによるデータ不整合や業務障害を防止
✓移行障壁の低減: 既存 PostgreSQL アプリをスキーマの書き換えなしに移行しやすく
✓開発コストの削減: アプリ側の整合性チェック実装・維持が不要になり工数を削減

🔧 技術面

✓ロックフリーの整合性保証: ロック待機なしで並行トランザクションのスループットを阻害しない
✓柔軟な参照アクション: CASCADE や SET NULL で親子関係のライフサイクル管理を DB に委譲
✓遅延可能制約: 相互参照する行を同一トランザクション内で任意の順序で挿入可能

⚠️ デメリット・制約事項

🚧 制限事項

•参照先・参照元テーブルへのすべての DML 操作で追加読み取りが発生
•CASCADE / SET NULL / SET DEFAULT の自動変更はトランザクション行数制限にカウントされ、子行が多いと予期しない失敗の可能性
•RESTRICT のチェックは遅延不可 (NO ACTION は遅延可能)
•DEFERRABLE は外部キー制約のみに適用可能
•MATCH PARTIAL は非サポート (PostgreSQL 本体でも未実装)

🤔 考慮すべき点

→競合はシリアライゼーションエラー (SQLSTATE 40001) で返されるため、リトライロジックの実装が必要
→多数の行から参照されるキー列が頻繁に変わるスキーマは競合が多発。頻繁に変更される値は非キー列へ移動を推奨
→子行数が無制限・予測不能な関係では CASCADE より NO ACTION / RESTRICT を推奨
→導入前にワークロードのベンチマークでパフォーマンス特性を検証

🎯 ユースケース

🛒 ユースケース 1: EC サイトの注文管理

シナリオ: 注文テーブルが商品テーブルを参照する EC サイトで、販売中の商品が誤って削除されて注文データが不整合になることを防ぎたい。

SQL
CREATE TABLE orders (
    order_id integer PRIMARY KEY,
    product_no integer REFERENCES products ON DELETE RESTRICT,
    quantity integer
);

✅ 効果: 注文から参照されている商品の削除は DB がエラーでブロック。アプリ側のチェック漏れがあっても孤児レコードが発生しない。

🚚 ユースケース 2: PostgreSQL アプリケーションの Aurora DSQL への移行

シナリオ: 外部キー制約を多用する既存の PostgreSQL アプリケーションを、サーバーレスでマルチリージョン対応の Aurora DSQL へ移行したい。

SQL
-- 既存の PostgreSQL スキーマをほぼそのまま利用可能
CREATE TABLE order_items (
    product_no integer REFERENCES products,
    order_id integer REFERENCES orders,
    quantity integer,
    PRIMARY KEY (product_no, order_id)
);

✅ 効果: 外部キー制約が移行の障壁だったワークロードで、スキーマの書き換えなしに移行を検討可能。競合時のリトライ対応のみ追加すればよい。

📦 ユースケース 3: 相互参照データの一括登録

シナリオ: マスターデータの一括登録において、参照先と参照元の行を順序を気にせず同一トランザクションで挿入したい。

SQL
CREATE TABLE orders (
    order_id integer PRIMARY KEY,
    product_no integer REFERENCES products DEFERRABLE INITIALLY DEFERRED,
    quantity integer
);

BEGIN;
INSERT INTO orders VALUES (1, 100, 2);   -- 参照先より先に挿入可能
INSERT INTO products VALUES (100, 'Widget', 9.99);
COMMIT;  -- コミット時点で制約を検証

✅ 効果: 制約チェックがコミット時まで遅延されるため、挿入順序の制御ロジックが不要になり、バッチ処理やデータロードの実装が簡素化される。

💰 料金・利用可能リージョン

💵 料金

外部キー制約の利用自体に追加料金は発表されていません。Aurora DSQL の標準料金 (DPU ベースのコンピューティング課金とストレージ課金) が適用されます。

⚠️ ただし、参照整合性保証のための追加読み取りにより、外部キー制約を持つテーブルへの書き込みでは DPU 消費が増加する可能性があります。導入前のベンチマーク確認を推奨。

🔄 関連サービス・機能

🐘 Amazon Aurora PostgreSQL

フル機能の PostgreSQL 互換データベース。外部キーを行ロックで強制する従来型の方式であり、Aurora DSQL の OCC ベースの方式との違いを理解して使い分ける。

⚡ Aurora DSQL の並行性制御 (OCC)

外部キー制約の競合解決は Aurora DSQL の楽観的並行性制御の仕組みに基づく。KEY SHARE 句の挙動やリトライ設計の理解が重要。

📏 Aurora DSQL のデータベース制限

CASCADE などの自動変更はトランザクション行数制限の対象となるため、クォータの確認が必要。

外部キー制約は Aurora DSQL の PostgreSQL 互換性における最大級のギャップの 1 つであり、本アップデートによりリレーショナルデータベースの中核機能である参照整合性をデータベース側で保証できるようになりました。
