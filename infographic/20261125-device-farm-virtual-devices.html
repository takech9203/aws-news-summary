☁️ AWS Device Farm

📱 仮想デバイスサポート開始
Android エミュレーター & iOS シミュレーター

📅 リリース日: 2026 年 11 月 25 日

📝 概要

AWS Device Farm が、従来の実機に加えて仮想デバイス (Android エミュレーター / iOS シミュレーター) をサポートしました。 自動テストと手動テスト (リモートアクセス) の両方で利用でき、実機と同じマネージド API、テスト環境、テストフレームワークをそのまま使用できます。

狙いはモバイルアプリテストの「シフトレフト」の実現です。PR やマージ時の高速・高頻度テストは仮想デバイスで、リリース前の高忠実度テストは実機で、という使い分けが単一サービス内で完結します。 切り替えはデバイスタイプの指定を変更するだけで、既存の CI/CD パイプラインやテストコードの変更は不要です。

❌ Before: アップデート前の課題

  • Device Farm は実機のみをサポート。エミュレーター / シミュレーターは自前構築が必要 (iOS シミュレーターには Mac ホストが必須)
  • 全テストを実機で実行すると起動が遅く、デバイスの空き状況に左右され、開発初期テストにはコストが割高
  • 自前のエミュレーター環境と Device Farm でツールチェーンが分断され、テスト資産の二重管理が発生

✅ After: アップデート後の改善

  • エミュレーター / シミュレーターをマネージドサービスとして利用でき、自前インフラの構築・運用が不要に
  • 実機と仮想デバイスで同じ API・テスト環境・フレームワークを共用。デバイスタイプ変更だけで切り替え可能
  • 最新 OS の仮想デバイスは数秒で起動。PR ごとのテストなど高頻度テストを高速・低コストで実行可能

CI/CD パイプラインの段階に応じて、高速・低コストな仮想デバイスと高忠実度な実機を同一の Device Farm API で使い分けるテスト戦略

⚙️ 主要機能

🤖 仮想デバイスによる自動テスト

Android エミュレーターと iOS シミュレーターで自動テストを実行可能。標準 / カスタムテスト環境の両方をサポートし、各プラットフォームで実機と同じテストタイプ (テストフレームワーク) が使用できます。カスタムテスト環境ではテストスペックファイルでテストホストと capabilities を設定します。

🖱️ 仮想デバイスによる手動テスト (リモートアクセス)

リモートアクセスセッションを開始すると、エミュレーター / シミュレーターが実機と同じデバイスリストに表示され、ブラウザから仮想デバイスを操作してインタラクティブに検証できます。

⚡ 高速な起動時間

最新 OS バージョンの仮想デバイスは通常 30 秒未満、その他の OS バージョンも約 1 分で起動。プルリクエストごとのテストなど高頻度の実行に適した応答性です。

🔄 既存ワークフローとの互換性

実機と同じ Device Farm のマネージド API を使用。デバイスプールのルールに DEVICE_TYPE 属性が追加され、実機 / 仮想デバイスを条件で選択可能。デバイスタイプの指定を変更するだけで切り替えられ、パイプラインやテストの変更は不要です。

🔧 技術仕様

仮想デバイスの仕様

項目詳細
対象プラットフォームAndroid (エミュレーター)、iOS (シミュレーター)
テスト種別自動テスト (標準 / カスタムテスト環境)、手動テスト (リモートアクセス)
デバイスタイプ識別デバイス名の末尾が Emulator または Simulator、type フィールドが VIRTUAL
起動時間最新 OS: 通常 30 秒未満、その他の OS: 通常約 1 分
課金方式メーター制 (iOS シミュレーターはメーター制のみ)。Android はアンメーター制スロットでも利用可能
VPC エンドポイント仮想デバイスは VPC エンドポイント (VPCE) 接続をサポートしない

API 変更履歴 (2026/11/20 - 19 updated api methods)

→Device データ型に type フィールド (PHYSICAL / VIRTUAL) が追加
→CreateDevicePool / UpdateDevicePool のルール属性に DEVICE_TYPE が追加
→ListDevices のフィルター属性に DEVICE_TYPE が追加
→GetDevice、GetRun、ScheduleRun、GetRemoteAccessSession など計 19 の API メソッドが更新

デバイスプールのルール例

JSON 仮想 Android デバイスを選択するルール 
{
  "rules": [
    {
      "attribute": "DEVICE_TYPE",
      "operator": "EQUALS",
      "value": "\"VIRTUAL\""
    },
    {
      "attribute": "PLATFORM",
      "operator": "EQUALS",
      "value": "\"ANDROID\""
    }
  ]
}

🛠️ 設定方法

前提条件

✓AWS アカウントと Device Farm プロジェクトが作成済みであること
✓AWS CLI または SDK が設定済みであること (コンソールからの操作も可能)
✓テスト対象のアプリパッケージ (APK / IPA) とテストパッケージが準備済みであること

ステップ 1: 利用可能な仮想デバイスを確認する

Bash DEVICE_TYPE フィルターで仮想デバイスを一覧表示 
aws devicefarm list-devices \
  --region us-west-2 \
  --filters '[{"attribute":"DEVICE_TYPE","operator":"EQUALS","values":["VIRTUAL"]}]'

デバイス名の末尾が Emulator または Simulator のデバイスが仮想デバイスです。

ステップ 2: 仮想デバイスを含むデバイスプールを作成する

Bash Android エミュレーターのみのデバイスプールを作成 
aws devicefarm create-device-pool \
  --region us-west-2 \
  --project-arn <プロジェクトの ARN> \
  --name "virtual-android-pool" \
  --rules '[{"attribute":"DEVICE_TYPE","operator":"EQUALS","value":"\"VIRTUAL\""},{"attribute":"PLATFORM","operator":"EQUALS","value":"\"ANDROID\""}]'

既存のテストはデバイスプールを差し替えるだけで仮想デバイス上で実行できます。

ステップ 3: テストランをスケジュールする

Bash 仮想デバイスプールでテストランを実行 
aws devicefarm schedule-run \
  --region us-west-2 \
  --project-arn <プロジェクトの ARN> \
  --app-arn <アップロード済みアプリの ARN> \
  --device-pool-arn <ステップ 2 で作成したデバイスプールの ARN> \
  --name "pr-smoke-test" \
  --test type=APPIUM_PYTHON,testPackageArn=<テストパッケージの ARN>

API の使い方は実機の場合と同一で、デバイスプールの指定を変えるだけで実機 / 仮想デバイスを切り替えられます。カスタムテスト環境を使用する場合は、テストスペックファイルでテストホストと capabilities を設定します。

💡 メリット

💼 ビジネス面

✓コスト最適化: 高頻度テストを低コストの仮想デバイスで実行し、高価な実機テストをリリース前に集中。Android はアンメーター制スロットで実機・仮想どちらも追加料金なし
✓開発速度の向上: 数秒で起動する仮想デバイスで PR ごとのフィードバックループが短縮され、問題の早期発見 (シフトレフト) を実現
✓運用負荷の削減: Mac ホストの調達やエミュレーター基盤の構築・運用が不要に。チームはテストの作成と改善に集中できる

🔬 技術面

✓単一のツールチェーン: 実機と仮想デバイスで API・テスト環境・フレームワークを共用し、テスト資産の二重管理を解消
✓パイプライン変更不要: デバイスタイプの指定変更だけで切り替えられ、既存の CI/CD やテストコードはそのまま
✓柔軟なデバイス選択: DEVICE_TYPE 属性のルールやフィルターで、テスト段階に応じたデバイス構成をコードで管理

⚠️ デメリット・制約事項

制限事項

✗仮想デバイスは VPC エンドポイント (VPCE) 接続をサポートしない (プライベートネットワーク経由のテストが必要な場合は実機を使用)
✗iOS シミュレーターはメーター制の課金方式のみをサポート (アンメーター制スロットは利用不可)
✗最新 OS 以外の仮想デバイスは起動に約 1 分かかる

考慮すべき点

⚠エミュレーター / シミュレーターは実機のハードウェア特性 (カメラ、センサー、実際のパフォーマンス特性、キャリアネットワークなど) を完全には再現できないため、リグレッションテストやリリース前テストでは引き続き実機の使用が推奨される
⚠どの段階を仮想デバイスに移行するか (例: PR 時のスモークテストのみ仮想化) をチームでテスト戦略として設計する必要がある

🎯 ユースケース

1️⃣ プルリクエストごとのスモークテスト

シナリオ: PR 作成のたびに主要画面の起動確認と基本操作のテストを実行したいが、実機では起動待ちとコストがボトルネック。

YAML CI パイプラインの例 (擬似コード) 
on: pull_request
steps:
  - run: |
      aws devicefarm schedule-run \
        --project-arn $PROJECT_ARN \
        --app-arn $APP_ARN \
        --device-pool-arn $VIRTUAL_POOL_ARN \
        --name "pr-${PR_NUMBER}-smoke" \
        --test type=APPIUM_PYTHON,testPackageArn=$TEST_PKG_ARN

✅ 効果: 数秒で起動する仮想デバイスで PR ごとのテストが高速化され、マージ前に問題を検出。実機スロットを消費しないためコストも抑制。

2️⃣ 段階的なテストパイプラインの構築

シナリオ: マージ後は仮想デバイスで幅広い OS バージョンをカバーし、リリース前は実機で忠実度の高い最終確認を行いたい。

Bash 同じテストパッケージでプールだけを切り替え 
# マージ後: 仮想デバイスプールで実行
aws devicefarm schedule-run --device-pool-arn $VIRTUAL_POOL_ARN ...

# リリース前: 実機デバイスプールで実行 (同じテストパッケージを使用)
aws devicefarm schedule-run --device-pool-arn $PHYSICAL_POOL_ARN ...

✅ 効果: 同じテストパッケージとパイプラインのまま、デバイスプールの指定だけでテスト段階ごとの速度・コスト・忠実度を最適化。

3️⃣ 手動テスト環境の即時払い出し

シナリオ: QA 担当者が不具合再現のために特定 OS バージョンの端末をすぐに操作したいが、手元に該当端末がない。

💰 料金

仮想デバイスは既存のメーター制 (従量課金) の料金モデルで利用できます。

⏱️ メーター制

テスト実行時間 (デバイス分) に応じた従量課金。iOS シミュレーターはメーター制のみをサポート。

♾️ アンメーター制 (Android)

既存のアンメーター制スロットで、実機と Android エミュレーターのどちらも追加料金なしで実行可能。

最新の料金は Device Farm 料金ページ を参照してください。

🌍 利用可能リージョンと関連サービス

利用可能リージョン: AWS Device Farm が提供されているすべての AWS リージョンで利用可能です。詳細は リージョン別サービス一覧 を参照してください。

関連サービス・機能

→AWS CodePipeline / CodeBuild: CI/CD パイプラインから Device Farm のテストランを呼び出し、仮想デバイスによるシフトレフトテストを自動化
→Device Farm リモートアクセス: 仮想デバイスも実機と同じデバイスリストに表示され、ブラウザから手動テストが可能
→Device Farm デスクトップブラウザテスト: モバイルアプリだけでなく Web アプリのクロスブラウザテストにも活用可能

🚀 まとめ

AWS Device Farm の仮想デバイスサポートにより、エミュレーター / シミュレーター基盤の自前運用が不要になり、実機と同じ API とテスト資産のままテストのシフトレフトを実現できます。

まずは PR 時のスモークテストなど高頻度なテスト段階を仮想デバイスに移行し、実機はリグレッションテストやリリース前の最終確認に集中させるテスト戦略の見直しを推奨します。
