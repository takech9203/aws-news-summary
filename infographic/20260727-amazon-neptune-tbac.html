Amazon Neptune

🔐 IAM タグベースアクセスコントロール (TBAC) サポート

📅 リリース日: 2026 年 7 月 27 日 ｜ 対象: データプレーン操作 (neptune-db:*)

📌 概要

Amazon Neptune Database が IAM のタグベースアクセスコントロール (TBAC) をサポートしました。 AWS リソースタグと IAM プリンシパルタグを IAM ポリシーおよびサービスコントロールポリシー (SCP) の条件として使用し、 Neptune のデータプレーン操作へのアクセスを動的に制御できます。

例えば Project=FraudDetection タグを持つプリンシパルは、同じタグを持つクラスターのみに自動的にアクセスが制限されます。 クラスター ARN をポリシーに列挙する必要がなくなり、SAML / OIDC セッションタグによるフェデレーテッド ID ワークフローにも対応します。

❌ Before: アップデート前の課題
  • クラスター単位の制御には IAM ポリシーに個々のクラスター ARN を列挙する必要があり、追加・削除のたびにポリシー更新が必要
  • 共有 VPC 環境では IAM 認証をパスしたプリンシパルによるラテラルアクセスのリスク
  • プロジェクト・部門単位の分離を組織全体で一律に強制する仕組みがなく、個別のポリシー管理に依存
✅ After: アップデート後の改善
  • プリンシパルタグとリソースタグの一致条件で ARN 列挙なしの動的なアクセス境界を定義
  • SCP により OU・アカウント全体にガードレールを適用し、ラテラルアクセスリスクを排除
  • SAML / OIDC セッションタグでフェデレーテッドユーザーにも属性ベースの制御を適用
  • 「どのクラスターに」「どの操作を」「どのクエリ言語で」を一つのポリシーで表現

⚙️ 主要機能

🏷️ 1. タグ一致によるデータプレーンアクセス制御
  • aws:PrincipalTag/{TagKey} と aws:ResourceTag/{TagKey} を neptune-db:* アクションに対して使用可能
  • プリンシパルタグとリソースタグが一致する場合のみアクセスを許可する動的なポリシーを定義
  • クラスターに付与したタグは、ポリシー評価のためにクラスター内の全インスタンスに伝播
🛡️ 2. SCP による組織全体のガードレール
  • OU またはアカウントレベルで Deny ベースの SCP を適用し、タグ不一致時のアクセスを組織全体で一律に拒否
  • Null 条件で必須タグ未付与クラスターへのアクセスを拒否し、タグ付けの徹底を強制
  • 個々のアカウントの Allow ポリシーはそのまま維持でき、SCP がガードレールとして機能
🌐 3. フェデレーテッド ID ワークフロー対応
  • 外部 ID プロバイダーの SAML / OIDC 属性マッピングによるセッションタグをプリンシパルタグとして評価
  • ID プロバイダー側の属性 (所属プロジェクト、部門など) に基づいて Neptune へのアクセスを制御
🧩 4. 既存のアクセス制御機能との組み合わせ
  • neptune-db:ReadDataViaQuery などアクション単位の権限と組み合わせ、読み取り専用アクセスなどを表現
  • neptune-db:QueryLanguage 条件キーと組み合わせ、クエリ言語 (Gremlin、openCypher、SPARQL) も同時に制限

📜 ポリシー例: タグ不一致時の拒否 (SCP / IAM ポリシー共通パターン)

JSON タグ不一致・タグ未付与の拒否ポリシー 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyNeptuneProjectMismatch",
      "Effect": "Deny",
      "Action": "neptune-db:*",
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:ResourceTag/Project": "${aws:PrincipalTag/Project}"
        }
      }
    },
    {
      "Sid": "DenyNeptuneMissingProjectTag",
      "Effect": "Deny",
      "Action": "neptune-db:*",
      "Resource": "*",
      "Condition": {
        "Null": {
          "aws:ResourceTag/Project": "true"
        }
      }
    }
  ]
}

1 つ目のステートメントは Project タグが一致しない場合にすべてのデータプレーン操作を拒否します。 2 つ目は Project タグ未付与のクラスターへのアクセスを拒否し、タグ付けの徹底を強制します。

🛠️ 設定方法

✅ 前提条件

✓Neptune エンジンバージョン 1.2.0.0 以降 を使用していること
✓Neptune DB クラスターで IAM 認証が有効化されていること
✓クラスターと IAM プリンシパルの両方に、ポリシーで評価するタグが付与されていること
1
タグ体系の定義

組織の境界を表すタグキーを設計します。

タグキー用途値の例
Projectアプリケーション / ワークロード識別子FraudDetection、RecommendationEngine
Department事業部門 / コストセンターEngineering、Finance
Environmentデプロイステージproduction、staging、development
2
Neptune DB クラスターへのタグ付け
BashAWS CLI (RDS API 経由)
aws neptune add-tags-to-resource \
  --resource-name arn:aws:rds:us-east-1:123456789012:cluster:my-neptune-cluster \
  --tags Key=Project,Value=FraudDetection Key=Department,Value=Engineering

付与したタグはクラスター内の全インスタンスのデータプレーンポリシー評価に反映されます。

3
IAM プリンシパルへのタグ付け
BashIAM ロールへのタグ付与
aws iam tag-role \
  --role-name NeptuneAppRole \
  --tags Key=Project,Value=FraudDetection Key=Department,Value=Engineering

フェデレーテッドユーザーの場合は、ID プロバイダーの SAML / OIDC 属性マッピングでセッションタグとして渡します。

4
TBAC ポリシーのデプロイ

組織全体で強制する場合は SCP として OU またはアカウントに適用し、特定のプリンシパルのみを対象とする場合は IAM ポリシーとしてアタッチします。

5
タグ整合性の保護
JSONTBAC タグキーの変更を制限するポリシー
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyTagModification",
      "Effect": "Deny",
      "Action": [
        "rds:AddTagsToResource",
        "rds:RemoveTagsFromResource"
      ],
      "Resource": "*",
      "Condition": {
        "ForAnyValue:StringEquals": {
          "aws:TagKeys": ["Project", "Department"]
        }
      }
    }
  ]
}

プリンシパルが自身のタグやリソースタグを変更できると TBAC を迂回できてしまうため、 iam:TagRole、iam:TagUser、rds:AddTagsToResource、rds:RemoveTagsFromResource の権限を SCP や権限境界で制限することが重要です。

💡 メリット

💼 ビジネス面
✓ガバナンスの強化: SCP でプロジェクト・部門・環境単位の分離を組織全体で一律に強制、コンプライアンス対応が容易に
✓運用コストの削減: クラスター追加・削除時の ARN リスト更新が不要になり、大規模環境でのポリシー管理負荷を大幅に軽減
✓マルチテナント環境の安全性向上: 共有 VPC でのラテラルアクセスリスクを排除し、複数チームが同一インフラを安全に共有
🔧 技術面
✓動的なアクセス境界: タグの付与だけで新規クラスターが自動的に制御対象となる、スケーラブルな認可モデル
✓フェデレーション対応: SAML / OIDC セッションタグで ID プロバイダー側の属性を認可判断に直接利用
✓既存機能との親和性: アクション権限や neptune-db:QueryLanguage と同一ポリシー内で組み合わせ可能、既存モデルを置き換えずに強化

⚠️ デメリット・制約事項

🚧 制限事項

✗Neptune エンジンバージョン 1.2.0.0 以降が必要
✗IAM 認証が有効なクラスターでのみ機能 (IAM 認証なしの接続は TBAC ポリシーの評価対象外)
✗タグはクラスターレベルの粒度で適用され、サブグラフや頂点 / エッジレベルのアクセス制御は提供されない

🤔 考慮すべき点

⏱️伝播遅延: IAM ポリシー変更の反映に最大 10 分、クラスタータグ変更の反映に約 5 分かかるため、稼働中クラスターのタグ変更は計画的に
🔒タグの完全性: タグを変更できるプリンシパルは TBAC を迂回できるため、タグ操作権限の保護が必須
🏷️タグ欠落時の挙動: タグがない場合 ${aws:PrincipalTag/Key} は空文字列に解決されるため、Null 条件による拒否などタグ欠落を想定した設計が必要
🧮条件評価のロジック: 同一 Condition ブロック内の複数条件キーは AND 評価。いずれかのタグ不一致で拒否したい場合はタグキーごとに別ステートメントに分ける

🎯 ユースケース

1️⃣ 共有 VPC でのプロジェクト間分離

シナリオ: 複数のプロジェクトチームが同一の共有 VPC 内でそれぞれの Neptune クラスターを運用しており、ネットワーク的には相互に到達可能。プロジェクト間の誤アクセスや不正アクセスを防止したい。

JSON実装例
{
  "Effect": "Deny",
  "Action": "neptune-db:*",
  "Resource": "*",
  "Condition": {
    "StringNotEquals": {
      "aws:ResourceTag/Project": "${aws:PrincipalTag/Project}"
    }
  }
}

効果: Project=FraudDetection タグを持つプリンシパルは同じタグを持つクラスターのみにアクセスでき、他プロジェクトへのラテラルアクセスが排除される。

2️⃣ SCP による組織全体のガードレール

シナリオ: 数十のアカウントに数百の Neptune クラスターが存在する大規模組織で、部門単位のデータ分離を組織ポリシーとして一律に強制したい。個々のアカウントの IAM ポリシー管理には依存したくない。

BashOU レベルに Deny ベースの SCP を適用
aws organizations attach-policy \
  --policy-id p-neptunetbac123 \
  --target-id ou-root-analytics

効果: 各アカウントの Allow ポリシーを変更することなく、タグ不一致およびタグ未付与のクラスターへのアクセスが組織全体で拒否され、ガバナンスが一元化される。

3️⃣ フェデレーテッドユーザーへの属性ベース認可

シナリオ: 社内の ID プロバイダー (SAML / OIDC) で認証したデータサイエンティストに、所属プロジェクトの属性に応じて Neptune クラスターへの読み取り専用アクセスを付与したい。

JSON実装例
{
  "Effect": "Allow",
  "Action": [
    "neptune-db:ReadDataViaQuery",
    "neptune-db:GetQueryStatus"
  ],
  "Resource": "arn:aws:neptune-db:*:*:*/*",
  "Condition": {
    "StringEquals": {
      "aws:ResourceTag/Project": "${aws:PrincipalTag/Project}",
      "neptune-db:QueryLanguage": "OpenCypher"
    }
  }
}

効果: ID プロバイダーのセッションタグに基づき、所属プロジェクトのクラスターに対して openCypher による読み取りクエリのみが許可され、ユーザーごとの個別ポリシー管理が不要になる。

📝 まとめ

Amazon Neptune の TBAC サポートにより、クラスター ARN の列挙に頼らない属性ベースのデータプレーンアクセス制御が可能になり、 大規模・マルチテナント環境でのガバナンスが大幅に強化されました。

✓多数の Neptune クラスターを運用している場合は、タグ体系を整備した上で SCP によるガードレールの導入を検討
✓導入時は IAM 認証の有効化とタグ操作権限の保護が必須
✓タグ変更の伝播遅延 (ポリシー最大 10 分 / タグ約 5 分) に注意して計画的に運用
