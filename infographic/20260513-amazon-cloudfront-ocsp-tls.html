📋 概要

Amazon CloudFront が、ビューワー側の相互 TLS (mTLS) 接続におけるクライアント証明書の OCSP 失効チェック をサポート。接続確立時にクライアント証明書の失効状態をリアルタイムで検証できるようになりました。規制業界やゼロトラストアーキテクチャで一般的に求められる要件を、標準機能として提供します。

❌ Before (従来)

  • CloudFront Functions + KeyValueStore で静的 CRL を管理
  • 静的リストの手動更新が必要でタイムラグが発生
  • 大規模な失効リストの管理が高運用負荷
  • リアルタイムでの証明書失効確認が不可能

✅ After (新機能)

  • OCSP レスポンダー URL でリアルタイム失効チェック
  • 静的な失効リストの管理・更新が不要
  • 最大 30 分キャッシュでパフォーマンスを最適化
  • Connection Function でカスタムロジックを実装可能

⚡ 主要機能

🔍 リアルタイム OCSP 失効チェック

クライアント証明書の AIA 拡張に埋め込まれた OCSP レスポンダー URL を使用して、接続確立時にリアルタイムで失効状態を確認。UseClientCertificateOCSPEndpoint を有効化して利用。

💾 OCSP レスポンスキャッシュ

OCSP レスポンスを最大 30 分間キャッシュ。同一証明書の繰り返しチェックによるレイテンシー増加を防止し、OCSP レスポンダーへの負荷も軽減。

🔧 Connection Function 統合

OCSP チェック結果がコネクション関数のイベントオブジェクトに含まれ、猶予期間の設定、IP ベース例外、独自失効リストとの組み合わせなどカスタムロジックを実装可能。

🔀 Passthrough モード

ViewerMtlsConfig に新たに passthrough モードが追加。mTLS の結果を強制せず Connection Function にすべての判断を委ねる柔軟な構成が可能。

🛠️ 設定方法

前提条件: 既存の CloudFront ディストリビューション、mTLS 用 Trust Store 設定済み、クライアント証明書に OCSP レスポンダー URL が AIA 拡張として埋め込まれていること

Step 1: Trust Store で OCSP チェックを有効化

Bash OCSP チェック有効化 
aws cloudfront update-trust-store \
  --id E1234567890ABC \
  --use-client-certificate-ocsp-endpoint

Step 2: ViewerMtlsConfig を設定

JSON enforce モード設定例 
{
  "ViewerMtlsConfig": {
    "Mode": "enforce",
    "TrustStoreArn": "arn:aws:cloudfront::123456789012:trust-store/my-mtls-trust-store"
  }
}

Step 3: Connection Function でカスタムロジック (オプション)

JavaScript 猶予期間 + IP ベース例外の実装例 
function handler(event) {
  var connection = event.connection;
  var mtls = connection.mtls;

  // OCSP ステータスの確認
  if (mtls.ocspStatus === "revoked") {
    var revokedTime = new Date(mtls.ocspRevokedAt);
    var now = new Date();
    var gracePeriodMs = 24 * 60 * 60 * 1000; // 24 時間

    if (now - revokedTime < gracePeriodMs) {
      return { action: "allow" }; // 猶予期間内
    }
    return { action: "deny", reason: "certificate_revoked" };
  }

  // OCSP レスポンダーに到達できない場合
  if (mtls.ocspStatus === "unknown") {
    var trustedIPs = ["192.0.2.0/24", "198.51.100.0/24"];
    if (isInRange(connection.clientIp, trustedIPs)) {
      return { action: "allow" };
    }
    return { action: "deny", reason: "ocsp_check_failed" };
  }

  return { action: "allow" };
}

⚠️ 制約事項・考慮点

⏱️ OCSP レスポンスのキャッシュ期間は最大 30 分。この間に失効した証明書は即時にブロックされない
📜 クライアント証明書に OCSP レスポンダー URL (AIA 拡張) が埋め込まれている必要がある
🌐 OCSP レスポンダーの可用性に依存。レスポンダーダウン時のフォールバック設計が必要
⏳ OCSP レスポンダーへのクエリにより、初回接続時のレイテンシーがわずかに増加する可能性
🔄 OCSP Stapling とは異なり、CloudFront (サーバー側) が OCSP レスポンダーに問い合わせを実行
📋 CRL ベースから移行する場合、両方を並行運用する移行期間を検討すること

💡 ユースケース

🏦 金融機関の API ゲートウェイ

銀行の API プラットフォームで、パートナー企業のクライアント証明書が失効した場合に即座にアクセスを遮断。enforce モードで厳格に運用。

→ 契約終了・不正アクセス検知時に CA で証明書を失効させるだけで、最大 30 分以内に自動的にアクセスが遮断

🛡️ ゼロトラストアーキテクチャ

デバイス証明書の有効性を継続的に検証しつつ、社内ネットワークからのアクセスには猶予期間を設ける。Connection Function で IP ベースの例外処理を実装。

→ 外部アクセスは即座にブロック、社内ネットワークからはソフトランディング期間を確保

📡 IoT デバイス管理

大量の IoT デバイスが mTLS で接続する環境で、侵害されたデバイスの証明書を失効させて即時遮断。passthrough モードでデバイスタイプごとの柔軟なポリシー適用。

→ 静的 CRL の配信・更新を待たずに、CA で失効させるだけで侵害デバイスを自動遮断
