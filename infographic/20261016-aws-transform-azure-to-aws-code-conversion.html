AWS Transform一般提供開始 GA

🔄 Azure から AWS へのクラウドネイティブコード変換

📅 リリース日: 2026 年 10 月 16 日 | Azure SDK → AWS SDK アプリケーションコード自動変換

📝 概要

AWS Transform で Azure SDK から AWS SDK へのアプリケーションコード変換が一般提供 (GA) になりました。 .NET モダナイゼーションエージェントが Azure サービスを利用するコードを特定し、同等の AWS サービスを利用するコードへ自動変換します。 例えば、Azure Cosmos DB を使用する Azure Functions のサーバーレス関数を、Amazon DynamoDB を使用する AWS Lambda 関数へ変換できます。

✅ 検証
❌ アップデート前の課題
  • Azure SDK (Azure.Storage.Blobs、Microsoft.Azure.Cosmos など) のコードを AWS SDK へ手作業で書き換える必要があった
  • Azure Functions → AWS Lambda の変換には両クラウドの仕様に精通したエンジニアによる設計と実装が必要だった
  • Azure サービスの利用箇所の調査 (アセスメント) 自体に多くの時間がかかっていた
✅ アップデート後の改善
  • Azure SDK を自動検出し、アセスメントレポートとモダナイゼーションプランで変換オプションを提示
  • Azure Functions / Blob Storage / Queue Storage を AWS Lambda / Amazon S3 / Amazon SQS へ自動変換 (Cosmos DB → DynamoDB はプレビュー)
  • 変換結果をエージェントが検証し、変換できないコードは TODO コメント・スタブコード・Next Steps ファイルで明示

AWS Transform の .NET モダナイゼーションエージェントが Azure SDK を検出し、アセスメント、プラン調整、変換・検証のステップを経て、同等の AWS サービスを利用するコードへ変換する流れ

⚙️ 主要機能

🔍 1. Azure SDK の自動検出とアセスメント

提出されたソースコードから Azure SDK の利用箇所を自動検出。検出結果と変換オプションをアセスメントレポートとモダナイゼーションプランとして提示。対象となるモダンな .NET アプリケーションでは、クラウドネイティブコード変換が自動的に実行される。

🎛️ 2. 変換オプションのカスタマイズ

エージェントチャットでの指示、プラン編集、ステアリングドキュメントで変換動作を制御可能。一部または全部の変換のオプトアウト、変数名や命名規則の指定、コメントの詳細度の調整に対応。デフォルトの変換先の変更も可能 (例: Azure Blob Storage のコードを Amazon S3 ではなく Amazon DynamoDB を使うよう指示)。

✅ 3. 変換と検証

特定された Azure サービスコードを同等の AWS SDK 呼び出しへ変換し、変更が変換後のコードに組み込まれていることを検証。変換できないコードは TODO コメント、スタブコード、または生成される Next Steps のマークダウンファイルに明記される。

🛠️ 設定方法

前提条件

✓AWS Transform が利用可能なリージョンでのセットアップ (ワークスペースの作成など)
✓変換対象となる Azure SDK を利用したモダンな .NET アプリケーションのソースコード
✓ソースコードリポジトリへの接続または Amazon S3 経由でのコードのアップロード

手順

1
ジョブの作成とソースコードの提出
.NET モダナイゼーションのジョブを作成し、Azure SDK を利用する .NET アプリケーションのソースコードを提出。エージェントがコードを分析し、Azure SDK の利用箇所を自動検出する。
2
アセスメントレポートとモダナイゼーションプランの確認
検出された Azure サービスと変換オプションを確認。プランの編集やエージェントチャットでの指示により、変換のオプトアウトや変換先の変更などのカスタマイズが可能。
3
モダナイゼーションの実行と結果の確認
エージェントが Azure サービスコードを AWS SDK 呼び出しへ変換し、変更の組み込みを検証。変換できなかった箇所は TODO コメント・スタブコード・Next Steps ファイルで示されるため、内容を確認して残作業を完了させる。

💡 メリット

💼 ビジネス面

✓移行期間の短縮: 最も工数のかかる SDK コードの書き換えを自動化し、移行プロジェクトを加速できる
✓移行コストの削減: 両クラウドの仕様に精通した専門エンジニアによる手作業の書き換え工数を削減できる
✓移行リスクの低減: アセスメントレポートにより変換範囲を事前に把握でき、計画的な移行判断が可能になる

🔬 技術面

✓自動検出と検証: 検出から変換、変換結果の検証までをエージェントが一貫して実行する
✓柔軟なカスタマイズ: チャット指示、プラン編集、ステアリングドキュメントで変換先サービスや命名規則まで制御できる
✓残作業の可視化: 変換できないコードが TODO コメントや Next Steps ファイルで明示され、手作業が必要な箇所を見落としにくい

⚠️ デメリット・制約事項

制限事項

✗変換対象はアプリケーションコードのみで、クラウドインフラストラクチャ (リソース自体やデータ) の移行は対象外
✗サポートされる変換は Azure Functions、Azure Blob Storage、Azure Queue Storage、Azure Cosmos DB (プレビュー) の 4 つのサービスに限定
✗Azure Cosmos DB → Amazon DynamoDB の変換はプレビュー段階であり、本番利用には注意が必要
✗利用可能なリージョンは 8 リージョンに限定される

考慮すべき点

⚠️変換できないコードは TODO コメントやスタブコードとして残るため、変換後に手動での対応と十分なテストが必要
⚠️Cosmos DB と DynamoDB のようにデータモデルや整合性モデルが異なるサービス間の変換では、アプリケーションの動作検証が特に重要
⚠️対象外の Azure サービスを利用している場合は、AWS Transform custom や Kiro などでの対応を別途検討する必要がある

🎯 ユースケース

1️⃣ Azure Functions ベースのサーバーレスアプリケーションの AWS 移行

シナリオ: Azure Functions と Azure Cosmos DB で構築されたサーバーレス API を、全社的なクラウド戦略の変更に伴い AWS へ移行する。

Text実装例
1. AWS Transform にソースコードを提出
2. アセスメントレポートで Azure Functions と Cosmos DB SDK の検出結果を確認
3. モダナイゼーションプランで Lambda + DynamoDB への変換を承認して実行
4. 変換後のコードと Next Steps ファイルを確認し、残作業とテストを実施

✅ 効果: サーバーレス関数とデータアクセス層の書き換えを自動化し、移行工数を大幅に削減できる

2️⃣ マルチクラウド環境の AWS への統合

シナリオ: 買収した企業が Azure 上で運用していた .NET アプリケーション群 (Blob Storage、Queue Storage を利用) を、自社標準の AWS 環境へ統合する。

Text実装例
1. 各アプリケーションを AWS Transform で順次アセスメント
2. Azure.Storage.Blobs → Amazon.S3、Azure.Storage.Queues → Amazon.SQS の変換を実行
3. 社内の命名規則をステアリングドキュメントで指定し、コード品質を統一

✅ 効果: 複数アプリケーションの移行を標準化されたプロセスで進められ、統合後の運用を AWS に一本化できる

3️⃣ 変換先サービスをカスタマイズした移行

シナリオ: Azure Blob Storage を小さな JSON ドキュメントの保存に使用しており、AWS 移行時には Amazon S3 ではなく Amazon DynamoDB へ格納先を変更したい。

Text実装例
1. アセスメント後、エージェントチャットで「Azure Blob Storage のコードは
   Amazon S3 ではなく Amazon DynamoDB を使うように変換」と指示
2. モダナイゼーションプランに反映された変換先を確認して実行

✅ 効果: デフォルトのマッピングに縛られず、移行を機にアーキテクチャの最適化まで同時に実現できる

📌 まとめ

Azure SDK から AWS SDK へのコード変換が AWS Transform で GA となり、Azure 上のクラウドネイティブ .NET アプリケーションを AWS へ移行する際の最大の障壁であったコード書き換えの自動化が可能になりました。

✓まずアセスメントレポートで変換可能範囲を確認し、小規模なアプリケーションから試行することを推奨
⚠️Azure Cosmos DB の変換はプレビューのため、本番適用時は十分な検証を実施
