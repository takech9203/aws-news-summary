☁️ Amazon Application Recovery Controller

🔄 Region switch に 4 つの新機能が追加

SSM Run Command 実行ブロック / Lambda ペイロード / サービスクォータチェック / ターゲットグループヘルス待機
📅 リリース日: 2026 年 10 月 14 日

📋 概要

Amazon Application Recovery Controller (ARC) の Region switch は、リージョン障害発生時にマルチリージョンアプリケーションのフェイルオーバーをオーケストレーションし、制限された復旧時間 (bounded recovery time) を実現する機能です。今回のアップデートで 4 つの新機能が追加され、フェイルオーバーの自動化範囲が広がり、復旧の確実性が向上しました。

1
🖥️ SSM Run Command 実行ブロック
フェイルオーバー中にマネージドインスタンス上でコマンドを実行
2
⚡ Lambda ペイロード対応
カスタムアクション Lambda にペイロードを渡して関数を再利用
3
📊 サービスクォータチェック
リージョン間のクォータパリティを検証し引き上げを自動申請
4
🩺 ターゲットグループヘルス待機
キャパシティがトラフィック処理可能になるまで待機
❌ アップデート前の課題
✗インスタンス上のコマンド実行はプラン外で手動またはカスタム実装が必要
✗Lambda にペイロードを渡せず、復旧プランごとに専用関数が必要
✗復旧失敗の一般的要因であるクォータ差異を事前に検出する仕組みがない
✗プロビジョニングしたキャパシティがトラフィック処理可能かを確認できない
✅ アップデート後の改善
✓SSM Run Command 実行ブロックでフェイルオーバー中に Run Command を実行。プラン評価で対象と IAM 権限を検証
✓ペイロードにより 1 つの Lambda 関数を複数プランで再利用可能
✓クォータパリティを検証し、引き上げリクエストを自動送信
✓ターゲットグループでヘルシーになってから次のステップへ進行

Region switch プランがフェイルオーバーを実行する流れ。事前のプラン評価とクォータパリティチェックで失敗要因を排除し、SSM Run Command や Lambda などの実行ブロックで復旧処理を行い、ターゲットグループヘルス待機でキャパシティの受信可能状態を確認してから切り替えを完了します。

🚀 主要機能の詳細

1️⃣ AWS Systems Manager Run Command 実行ブロック
  • フェイルオーバー中に、マネージドインスタンスや VM に対して Run Command アクションを実行できる実行ブロック
  • OS レベルの設定変更、サービスの起動、スクリプト実行などをフェイルオーバーワークフローに組み込める
  • プラン評価機能により、コマンドドキュメントが有効なインスタンスを対象としているか、IAM 権限が正しく設定されているかを事前に検証
2️⃣ カスタムアクション Lambda 実行ブロックのペイロード対応
  • カスタムアクション Lambda 実行ブロックの呼び出し時に、任意のペイロードを渡せるようになった
  • プランごとに異なるパラメータをペイロードで渡すことで、1 つの Lambda 関数を複数の復旧プランで再利用可能
  • 復旧プランごとに専用関数を作成・保守する運用負荷を削減
3️⃣ サービスクォータチェック
  • プライマリリージョンとスタンバイリージョン間のサービスクォータのパリティ (同等性) を検証
  • クォータが不足している場合は、クォータ引き上げリクエストを自動的に送信
  • 復旧時の一般的な失敗要因であるクォータ不足のリスクを事前に低減
4️⃣ ターゲットグループヘルス待機
  • Amazon ECS サービススケーリングおよび Amazon EC2 Auto Scaling グループ実行ブロックのオプション機能
  • プロビジョニングしたキャパシティがロードバランサーのターゲットグループでヘルシーになり、トラフィックを処理できる状態になるまで待機
  • 「キャパシティは起動したが、まだリクエストを処理できない」状態でのトラフィック切り替えを防止

⚙️ 設定方法

前提条件

✓Amazon Application Recovery Controller の Region switch プランが作成済みであること
✓SSM Run Command 実行ブロックを使用する場合、対象インスタンスが AWS Systems Manager のマネージドインスタンスとして登録されていること
✓各実行ブロックの実行に必要な IAM 権限 (SSM、Lambda、Service Quotas、ECS、EC2 Auto Scaling、Elastic Load Balancing など) が設定されていること

手順

1
Region switch プランに SSM Run Command 実行ブロックを追加

ARC コンソールのプラン編集画面で「AWS Systems Manager Run Command」実行ブロックを追加し、使用するコマンドドキュメントと対象インスタンスを指定します。

2
カスタムアクション Lambda 実行ブロックにペイロードを設定

呼び出し時に渡すペイロードを定義します。プランごとに異なるペイロードを設定することで、同一の Lambda 関数を複数プランで再利用できます。

3
サービスクォータチェックとターゲットグループヘルス待機を有効化

プランの評価設定でサービスクォータチェックを有効にし、クォータパリティを検証します。ECS サービススケーリングまたは EC2 Auto Scaling グループ実行ブロックで「ターゲットグループヘルス待機」を有効にします。

4
プラン評価の結果を確認

プラン評価を実行し、コマンドドキュメントのターゲット、IAM 権限、クォータパリティに関する検出事項を確認して、必要な修正を行います。

💡 メリット

💼 ビジネス面
✓復旧の確実性向上: クォータ不足やキャパシティの準備不足といった典型的な失敗要因を事前に排除
✓RTO の予測可能性: 手動オペレーションの自動化で、制限された復旧時間の達成がより確実に
✓運用コスト削減: Lambda 関数の再利用により、プランごとの実装・保守コストを削減
🔧 技術面
✓自動化範囲の拡大: OS レベルの操作までフェイルオーバーワークフローに組み込める
✓事前検証の強化: プラン評価が SSM ドキュメントの対象や IAM 権限を検証し、実行時エラーを未然に防止
✓安全なトラフィック切り替え: キャパシティが実際にリクエストを処理できる状態になってから切り替え

⚠️ デメリット・制約事項

制限事項

⚠️SSM Run Command 実行ブロックの対象は、AWS Systems Manager のマネージドインスタンスとして登録されたインスタンス・VM に限られる
⚠️ターゲットグループヘルス待機はオプション機能であり、Amazon ECS サービススケーリングおよび Amazon EC2 Auto Scaling グループ実行ブロックが対象

考慮すべき点

💭クォータ引き上げの自動申請は申請の送信を自動化するものであり、承認に時間を要する場合があるため、定期的なプラン評価で事前にパリティを確保しておくことが望ましい
💭ターゲットグループヘルス待機を有効にすると、ヘルスチェック完了までワークフローが待機するため、プラン全体の実行時間への影響を考慮する必要がある
💭各実行ブロックに必要な IAM 権限を適切に設計し、プラン評価で検出された権限不足を解消しておく必要がある

🎯 ユースケース

🖥️ ユースケース 1: EC2 上のレガシーアプリケーションを含むフェイルオーバーの自動化

シナリオ: スタンバイリージョンの EC2 インスタンス上で、フェイルオーバー時にアプリケーションサービスの起動や設定ファイルの切り替えを行う必要がある。

Text実装例
Region switch プランに SSM Run Command 実行ブロックを追加し、
サービス起動スクリプトを含む SSM ドキュメントを
スタンバイリージョンの対象インスタンスに対して実行するよう構成

効果: これまで手動またはカスタム実装が必要だった OS レベルの操作をプランに統合し、フェイルオーバー全体を一貫して自動化できる。

⚡ ユースケース 2: 共通 Lambda 関数による複数プランの標準化

シナリオ: 複数のアプリケーションの復旧プランで、DNS 更新や外部システムへの通知など共通のカスタムアクションを実行したい。

JSONペイロード例
{
  "application": "app-a",
  "action": "notify",
  "endpoint": "https://example.com/webhook"
}

効果: ペイロードでアプリケーション固有のパラメータを渡すことで、1 つの Lambda 関数を全プランで共有でき、保守対象のコードを大幅に削減できる。

📈 ユースケース 3: 大規模スケールアウトを伴う DR のクォータ・ヘルス担保

シナリオ: 平常時は最小構成のスタンバイリージョンを、フェイルオーバー時に大規模にスケールアウトするパイロットライト構成を運用している。

Text実装例
1. サービスクォータチェックを有効化し、プライマリとスタンバイの
   クォータパリティを定期的に検証
2. EC2 Auto Scaling グループ実行ブロックで
   ターゲットグループヘルス待機を有効化

効果: クォータ不足による起動失敗を未然に防ぎ、スケールアウトしたキャパシティがヘルシーになってからトラフィックを切り替えることで、復旧直後のエラー発生を回避できる。

💰 料金・利用可能リージョン

💵 料金

今回の発表に料金に関する記載はありません。Region switch の料金の詳細は Amazon Application Recovery Controller の料金ページを参照してください。なお、実行ブロックから呼び出される AWS Systems Manager、AWS Lambda、Amazon ECS、Amazon EC2 などの各サービスには、それぞれの料金が適用されます。

🌍 利用可能リージョン

すべての商用リージョンおよび AWS GovCloud (US) リージョンで利用可能です。詳細はリージョン対応状況のドキュメントを参照してください。

📝 まとめ

今回のアップデートは、マルチリージョン DR における「本番フェイルオーバー時に初めて露見する失敗要因」であるクォータ不足、キャパシティの準備不足、手動オペレーションの残存を体系的に解消するものです。

✓サービスクォータチェックとターゲットグループヘルス待機を有効化する
✓SSM Run Command 実行ブロックと Lambda ペイロードを活用して復旧プランの自動化範囲を見直す
