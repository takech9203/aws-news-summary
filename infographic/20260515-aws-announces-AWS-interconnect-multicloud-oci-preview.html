📋 概要

AWS は AWS Interconnect - multicloud の Oracle Cloud Infrastructure (OCI) 対応をパブリックプレビューとして発表しました。AWS と OCI 間でシンプルかつ高速なプライベート接続を数分でプロビジョニングできるようになります。

OCI は Google Cloud (GA 済み) に続く 2 番目のクラウドプロバイダーパートナーとなり、Microsoft Azure も 2026 年後半に対応予定です。業界初の専用マルチクラウド接続プロダクトとして、GitHub 上で公開されたオープン仕様 (OpenAPI 3.0 ベースの対称 API) に基づいています。

🔄 Before / After 比較

❌ Before (従来)

  • サードパーティのネットワークプロバイダーと複雑なルーティング設定が必要
  • 物理的な Cross-Connect の注文、BGP ピアリング設定が必須
  • マルチクラウド環境でのネットワーク管理が複雑
  • 接続確立に数週間〜数カ月のリードタイム

✅ After (AWS Interconnect)

  • AWS コンソールから数分で OCI へのプライベート接続を作成
  • 物理ルーター設定、Cross-Connect 注文、BGP 管理が一切不要
  • ビルトイン冗長性と MACsec 暗号化が標準提供
  • 帯域幅を動的に変更可能、需要に応じたスケーリング

⚡ 主要機能

🔌 OCI へのマネージドプライベート接続

AWS と OCI 間に専用帯域幅を備えたプライベート接続を数分でプロビジョニング。パブリックインターネットを経由しないセキュアな通信。AWS マネジメントコンソール、CLI、API から操作可能。

📖 オープン仕様に基づく統合

GitHub 上で公開された OpenAPI 3.0 ベースの対称 API 仕様を使用。OCI がオープン仕様を採用し、AWS と同じ API インターフェースで接続を調整。中央集権的なブローカー不要のピアツーピア連携。

🛡️ ビルトイン最大冗長性

4 接続モデルと ECMP ロードバランシングにより、計画メンテナンス中も少なくとも 1 つのリンクが稼働を維持。2 つ以上の物理的に独立した施設に分散配置。デバイス、Cross-Connect、施設レベルでの単一障害点を排除。

🔒 MACsec 暗号化によるセキュリティ

IEEE 802.1AE MAC Security (MACsec) 暗号化をすべての物理接続で使用。暗号化セッションがアクティブな場合にのみトラフィックを転送。デフォルトで有効、追加設定不要。

📈 エラスティックな帯域幅スケーリング

AWS コンソールから接続を再プロビジョニングすることなく帯域幅を動的に増減。ピークワークロード時のスケールアップとコスト管理のためのスケールダウンが容易。サポートへの問い合わせ不要。

⚙️ 設定方法

前提条件

✓AWS アカウントが有効であること
✓Direct Connect Gateway が作成済みであること
✓Oracle Cloud Infrastructure アカウントおよびテナンシ情報を取得済みであること
✓us-east-1 リージョンにリソースが配置されていること
✓適切な IAM 権限 (interconnect:* アクション) が設定されていること

Step 1: Direct Connect Gateway の準備

Bash Direct Connect Gateway の作成 
# Direct Connect Gateway の作成 (未作成の場合)
aws directconnect create-direct-connect-gateway \
  --direct-connect-gateway-name "multicloud-oci-dxgw" \
  --amazon-side-asn 64512

Step 2: OCI 環境の確認

Bash OCI への接続環境を一覧表示 
# OCI への接続環境を一覧表示
aws interconnect list-environments \
  --provider '{"cloudServiceProvider": "OCI"}' \
  --region us-east-1

Step 3: OCI への接続を作成

Bash OCI への接続を作成 
# OCI への接続を作成
aws interconnect create-connection \
  --description "AWS to OCI - Production Workload" \
  --bandwidth "1Gbps" \
  --attach-point '{"directConnectGateway": "dxgw-xxxxxxxx"}' \
  --environment-id "env-oci-us-east1" \
  --remote-account '{"identifier": "ocid1.tenancy.oc1..example"}' \
  --tags '{"Environment": "Production", "CSP": "OCI"}' \
  --region us-east-1

Step 4: OCI 側での接続承認

Bash アクティベーションキーを取得 
# アクティベーションキーを取得
aws interconnect get-connection \
  --identifier "conn-xxxxxxxx" \
  --region us-east-1

AWS が生成したアクティベーションキーを取得し、OCI コンソールまたは OCI API で接続を承認します。

Step 5: 接続状態の確認

Bash 接続状態を確認 
# 接続状態を確認
aws interconnect get-connection \
  --identifier "conn-xxxxxxxx" \
  --region us-east-1

接続が available 状態になっていることを確認します。ビルトイン冗長性は自動構成されます。CloudWatch メトリクスおよび Network Synthetic Monitor による監視も利用可能です。

💡 ユースケース

🗄️ UC1: Oracle Database on OCI と AWS 分析基盤の統合

Oracle Database を OCI 上の Exadata で稼働させ、蓄積されたデータを AWS の Amazon Redshift や Amazon SageMaker で分析・ML モデル学習に活用。専用帯域幅によりプライベート接続で安全かつ低レイテンシーな大規模データ転送を実現。

🔄 UC2: マルチクラウド DR 構成

ミッションクリティカルなアプリケーションを AWS で稼働させつつ、OCI をディザスタリカバリ先として使用。Oracle Database ワークロードでは OCI の Autonomous Database が DR 先として最適。ビルトイン冗長性で DR レプリケーションの信頼性を確保。

🚀 UC3: 段階的な Oracle ワークロードのクラウド移行

オンプレミスの Oracle ワークロードをクラウドに移行する過程で、Oracle Database は OCI に、アプリケーション層は AWS に配置するハイブリッド構成。移行完了後は帯域幅を動的に調整してコスト最適化。
