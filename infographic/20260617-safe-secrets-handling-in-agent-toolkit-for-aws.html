安全なシークレット処理

🧩 secret safety skill

📌 概要

AWS Secrets Manager は、Agent Toolkit for AWS の aws-core プラグインに、安全にシークレットを扱う新しいスキル (secret safety skill) を追加しました。

Agent Toolkit for AWS は、AI コーディングエージェントに AWS 開発向けのツール、ナレッジ、ガードレールを提供するオープンソースリポジトリです。このスキルにより、シークレットの値をモデルのコンテキストやセッションログに露出させることなく利用できます。Claude Code / Codex / Cursor といった主要なエージェントハーネスに対応します。

❌ アップデート前の課題

  • ✗get-secret-value でシークレットを平文のまま取得できてしまった
  • ✗平文の値がコンテキストウィンドウに取り込まれ、会話履歴・ログ・下流ツール呼び出しに漏えいするリスク
  • ✗不用意な取得を構造的に防ぐ仕組みが存在しなかった

✅ アップデート後の改善

  • ✓実際の値をコンテキストに通さず、エージェントが安全にシークレットを利用できる
  • ✓平文がモデルのコンテキスト・セッションログ・エージェントメモリに残らない
  • ✓get-secret-value などの直接取得をフックで自動ブロック

エージェントはステアリング層のスキルに従い、シークレットを「取得」せず「利用」するコマンドを生成します。asm-exec が実行時に子プロセス内でのみ値を解決し、フックは直接的な取得呼び出しを自動的にブロックします。

⚙️ 主要機能 — 二層の保護

📘 1. secret safety skill によるステアリング (スキルガイダンス)

  • シークレットを平文で取得せず、{{resolve:secretsmanager:...}} 形式の動的参照を使うようエージェントを誘導
  • モデルが生の値を要求・受領しないように促し、開発者の意図を確認したうえで「利用する」コマンドを構築
  • 動的参照と asm-exec を組み合わせ、平文は子プロセス内にのみ存在しコンテキストには入らない

🛡️ 2. PreToolUse フックによる構造的な強制 (実行層の保護)

  • ツール呼び出しの実行前に PreToolUse フックが介入
  • AWS CLI / SDK / MCP ツール / AWS Workload Credentials Provider デーモンへの直接アクセスによる get-secret-value・batch-get-secret-value をブロック
  • 手動設定不要 — プラグイン導入だけで自動的に有効化

⚙️ 3. asm-exec による実行時解決

  • コマンド引数内の {{resolve:...}} 参照を解決してから対象コマンドを実行するラッパースクリプト
  • 値の解決は AWS Workload Credentials Provider (localhost:2773) または SigV4 署名による AWS MCP エンドポイント要求を利用
  • シークレットの値は asm-exec プロセスのメモリと子プロセスの引数内にのみ存在

🔑 必要な IAM 権限

JSONIAM ポリシー例
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "secretsmanager:GetSecretValue",
      "Resource": "arn:aws:secretsmanager:<region>:<account-id>:secret:prod/*"
    }
  ]
}

解決したいシークレットに対して secretsmanager:GetSecretValue 権限が必要です。

🚀 設定方法

前提条件

プラグイン対応の AI コーディングエージェント aws-core プラグインのインストール 解決バックエンド (localhost:2773 / AWS MCP) secretsmanager:GetSecretValue 権限

ステップ 1: aws-core プラグインのインストール

Bashプラグイン導入
# Claude Code の場合
claude plugin add ./plugins/aws-core

# OpenAI Codex の場合
codex plugin add ./plugins/aws-core

secret safety skill とフックは自動的に有効になります。

ステップ 2: asm-exec でシークレットを利用するコマンドを実行

BashPostgreSQL への接続
asm-exec -- psql \
  "host=mydb.example.com \
  user={{resolve:secretsmanager:prod/db-creds:SecretString:username}} \
  password={{resolve:secretsmanager:prod/db-creds:SecretString:password}}" \
  -c "SELECT * FROM users LIMIT 10"

平文のシークレットは子プロセス内にのみ存在し、エージェントのコンテキストには渡りません。

ステップ 3: リージョンをまたぐシークレットの利用

Bash完全な ARN / AWS_REGION の指定
# 完全な ARN を使う場合 (リージョンは自動的に抽出される)
asm-exec -- curl -H "X-Api-Key: {{resolve:secretsmanager:arn:aws:secretsmanager:eu-west-1:123456789012:secret:prod/key-a1b2c3}}" \
  https://eu.api.example.com/data

# AWS_REGION を使う場合
export AWS_REGION=eu-west-1
asm-exec -- curl -H "X-Api-Key: {{resolve:secretsmanager:prod/key}}" \
  https://eu.api.example.com/data

💡 メリット

📈 ビジネス面

  • →情報漏えいリスクの低減: 平文が会話履歴やログに残らず、機密情報の漏えいリスクを抑制
  • →ガバナンスの強化: フックによる構造的な強制で安全な利用を組織ポリシーとして徹底
  • →追加コストなしで導入可能: オープンソースプラグインとして既存ワークフローに組み込み

🔧 技術面

  • →コンテキスト汚染の防止: 値がコンテキストウィンドウに入らず漏えい経路を遮断
  • →ゼロコンフィグでフック有効化: 導入だけで PreToolUse フックが有効、手動設定不要
  • →柔軟なバックエンド: Workload Credentials Provider と AWS MCP の両方に対応し自動フォールバック

⚠️ デメリット・制約事項

制限事項

  • これはベストエフォートの防御であり、セキュリティ境界ではありません。最も一般的な漏えい経路を防ぎますが、すべての回避経路を阻止できるわけではありません
  • フックはセッション開始時に読み込まれます。セッション途中でインストールした場合は再起動が必要
  • field-type は SecretString のみ指定可能

考慮すべき点

  • IAM の最小権限、CloudTrail による監視、VPC エンドポイントポリシーと組み合わせて多層的に運用することを推奨
  • 値は asm-exec プロセスと子プロセスの引数内に存在するため、対象コマンド自体のログ出力に注意
  • 両方の解決バックエンドに到達できない場合は失敗するため、認証情報やリージョン設定の確認が必要

🎯 ユースケース

1. AI エージェントによるデータベース接続

シナリオ: Claude Code でアプリをデバッグし本番 DB へ接続。従来は接続情報を平文でエージェントに渡していた。

Bash
asm-exec -- mysql \
  -h {{resolve:secretsmanager:prod/mysql:SecretString:host}} \
  -u {{resolve:secretsmanager:prod/mysql:SecretString:username}} \
  -p{{resolve:secretsmanager:prod/mysql:SecretString:password}} \
  -e "SHOW TABLES"

効果: 認証情報がコンテキストやログに残らず安全に接続できます。

2. ベアラートークンを用いた外部 API 呼び出し

シナリオ: エージェントが外部 API を呼び出す処理を生成する際、API トークンを安全に扱いたい。

Bash
asm-exec -- curl -H "Authorization: Bearer {{resolve:secretsmanager:prod/api-token}}" \
  https://api.example.com/data

効果: トークンはコンテキストに露出せず、実行時にのみ解決されます。

3. コンテナへのシークレットの受け渡し

シナリオ: ローカルでコンテナを起動する際、DB パスワードを環境変数として渡す必要がある。

Bash
asm-exec -- docker run \
  -e "DB_PASSWORD={{resolve:secretsmanager:prod/db:SecretString:password}}" \
  myapp:latest

効果: 平文をエージェントに保持させずコンテナへ安全に渡せます。

💰 料金・利用可能リージョン

料金

Agent Toolkit for AWS のオープンソースプラグインとして提供され、スキルとフック自体に追加料金は発生しません。シークレット取得には AWS Secrets Manager の通常料金が適用されます。

利用可能リージョン

AWS Secrets Manager が利用可能なすべての AWS リージョンで利用できます。

🔗 関連サービス・機能

  • AWS Secrets Manager: シークレットの保存と管理を担う基盤。{{resolve:...}} 参照で実行時に値を解決
  • AWS Workload Credentials Provider: localhost:2773 で稼働し、ローカルキャッシュ済みの解決バックエンドを提供
  • Agent Toolkit for AWS: AI コーディングエージェントに AWS 開発向けツールとガードレールを提供する本スキルの提供元

📝 まとめ

このアップデートは、AI コーディングエージェントを活用した開発においてシークレットの漏えいという重大なリスクに対処する重要な機能です。ステアリング層とフックによる二層の保護により、平文のシークレットをモデルのコンテキストに通すことなく安全に利用できます。AI エージェントを開発フローに取り入れているチームは、aws-core プラグインを導入し、IAM の最小権限や CloudTrail 監視と組み合わせて多層的なセキュリティ運用を検討することを推奨します。
