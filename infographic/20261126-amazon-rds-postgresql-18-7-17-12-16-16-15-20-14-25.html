Amazon RDS for PostgreSQL

🐘 PostgreSQL 最新マイナーバージョン
18.7 / 17.12 / 16.16 / 15.20 / 14.25 をサポート

📅 リリース日: 2026 年 11 月 26 日 | 約 45 件の CVE に対処するセキュリティ重要リリース

📌 概要

Amazon RDS for PostgreSQL が、PostgreSQL コミュニティが 2026 年 11 月 12 日にリリースした最新マイナーバージョンをサポートしました。約 45 件の CVE への対処と 50 件超のバグ修正を含むセキュリティ色の強いリリースです。AWS は最新マイナーバージョンへのアップグレードを推奨しています。

❌ アップデート前の課題
  • 既存マイナーバージョンに約 45 件の CVE に該当する脆弱性が残存
  • bpchar 列の btree、GIN、pg_trgm GiST などのインデックスが破損し得るバグが未修正
  • hash right semi-join による行の重複、レプリケーション遅延の誤報告など 50 件超のバグが残存
✅ アップデート後の改善
  • 最新マイナーバージョンへのアップグレードで既知の CVE に対処
  • 50 件を超えるバグ修正と安定性改善を取り込み可能
  • AMVU、Upgrade Rollout Policy、Blue/Green デプロイで環境の重要度に応じた安全なアップグレード戦略を実行可能

⚡ 主要機能

1️⃣ 最新マイナーバージョンのサポート
  • PostgreSQL 18.7、17.12、16.16、15.20、14.25 が RDS for PostgreSQL で利用可能
  • コミュニティが 2026 年 11 月 12 日にリリースしたマイナーバージョンに対応
  • 既知の CVE への対処と 50 件超のバグ修正を含む
2️⃣ 自動マイナーバージョンアップグレード AMVU
  • 「Auto minor version upgrade」を有効にすると、メンテナンスウィンドウ中に自動でアップグレード
  • 事前チェック → エンジンのアップグレード → 事後チェックが順に実行される
  • 重大なセキュリティ問題やサポート終了時は、AMVU 無効でも RDS がアップグレードを適用することがある
3️⃣ AWS Organizations Upgrade Rollout Policy による段階的ロールアウト
  • 複数アカウント・複数リソースの AMVU を first (開発)、second (QA、デフォルト)、last (本番) の 3 段階で制御
  • 各フェーズ間にベイクタイム (検証期間) を設け、下位環境で問題がないことを確認してから進行
  • アカウント単位のポリシーまたはリソースタグで順序を定義し、AWS Health 通知と RDS イベント通知でモニタリング
4️⃣ RDS Blue/Green デプロイによるダウンタイム最小化
  • 本番環境 (Blue) のコピーとして Green 環境を作成し、Green 側でアップグレードと検証を実施後にスイッチオーバー
  • エンジンアップグレードに伴うダウンタイムを最小化

🛡️ 今回のコミュニティリリースに含まれる主な修正 (PostgreSQL 18.7 リリースノートより)

分類内容
複合型の同時変更への防御CVE-2026-6460 ほか。複合型をデータ操作と同時に変更した場合の問題に対する広範な防御を導入
権限・ポリシーのバイパス修正ビューに対する INSERT ... ON CONFLICT DO UPDATE の不正な更新 (CVE-2026-16237)、RLS 関連の修正など
メモリ安全性の修正use-after-free、バッファオーバーラン、整数オーバーフローなど多数の修正
SQL インジェクション対策pg_dump、vacuumdb、reindexdb などクライアントツールにおける識別子のクォート不備を修正
インデックス破損の修正bpchar 列の btree、GIN、TOAST テーブル、pg_trgm GiST の各インデックス破損バグを修正 (影響を受けるインデックスは REINDEX を推奨)
その他プランナーの大規模な修正、スタンバイでの並列 pg_dump に関するデータ整合性修正、tzdata 2026f への更新など

⚖️ アップグレード方法の比較

方法特徴適した用途
🔄 AMVUメンテナンスウィンドウ中に自動適用。ダウンタイムあり常に最新のマイナーバージョンを維持したい環境
🏢 Upgrade Rollout Policyfirst / second / last の 3 段階 + ベイクタイムで段階的に適用マルチアカウントで大規模な DB フリートを運用する組織
🔀 Blue/Green デプロイGreen 環境で検証後にスイッチオーバー。ダウンタイムを最小化ダウンタイム要件が厳しい本番環境
⌨️ 手動アップグレードCLI / コンソールから任意のタイミングで適用バージョンとタイミングを厳密に管理したい環境

🛠️ 設定方法

✅ 前提条件

✓RDS for PostgreSQL DB インスタンスが稼働していること
✓Upgrade Rollout Policy を使用する場合、AWS Organizations の組織に参加し、ポリシーが有効化されていること
✓Blue/Green デプロイを使用する場合、対象インスタンスが Blue/Green デプロイの要件を満たしていること

ステップ 1: 利用可能なアップグレードターゲットの確認

Bashアップグレード可能なバージョンと AMVU ターゲットの確認
aws rds describe-db-engine-versions \
    --engine postgres \
    --engine-version 17.11 \
    --query "DBEngineVersions[*].ValidUpgradeTarget[*].{AutoUpgrade:AutoUpgrade,EngineVersion:EngineVersion}" \
    --output table

ステップ 2: 手動でのマイナーバージョンアップグレード

Bash17.12 へのアップグレード (次回メンテナンスウィンドウで適用)
aws rds modify-db-instance \
    --db-instance-identifier mydbinstance \
    --engine-version 17.12 \
    --no-apply-immediately

💡 --no-apply-immediately で次回のメンテナンスウィンドウに適用、--apply-immediately で即時適用。アップグレード中はダウンタイムが発生します。

ステップ 3: 自動マイナーバージョンアップグレードの有効化

BashAMVU の有効化
aws rds modify-db-instance \
    --db-instance-identifier mydbinstance \
    --auto-minor-version-upgrade \
    --apply-immediately

ステップ 4: Upgrade Rollout Policy 用のタグ付け (段階的ロールアウトを使う場合)

Bash環境識別タグの付与
aws rds add-tags-to-resource \
    --resource-name arn:aws:rds:ap-northeast-1:123456789012:db:mydbinstance \
    --tags Key=Environment,Value=Development

💡 ポリシーでこのタグを参照し first / second / last の順序を割り当てます。ポリシーを設定しないリソースは自動的に second の順序になります。

💡 メリットとデメリット・制約事項

📈 ビジネス面のメリット

✓セキュリティリスクの低減: 約 45 件の CVE に対処した最新バージョンへ移行し、脆弱性に起因する事業リスクを低減
✓運用負荷の削減: AMVU と Upgrade Rollout Policy で大規模 DB フリートのアップグレードを自動化・標準化
✓サービス継続性の確保: Blue/Green デプロイでダウンタイムを最小化

⚙️ 技術面のメリット

✓安定性の向上: インデックス破損、行の重複、レプリケーション遅延の誤報告など 50 件超のバグ修正を取り込み
✓段階的な検証: ベイクタイムを挟んだロールアウトで、下位環境で問題を検出してから本番環境へ
✓可観測性: AWS Health 通知と RDS イベント通知 (Amazon EventBridge 連携) で進行状況を追跡

⚠️ 制限事項

✗マイナーバージョンアップグレードにはダウンタイムが発生 (長さはエンジンタイプや DB サイズに依存)
✗アップグレード中はステータスが upgrading となり、変更操作ができない
✗AMVU のターゲットは必ずしも最新マイナーバージョンとは限らない。特定バージョン維持には手動アップグレードが必要
✗Upgrade Rollout Policy の対象は AMVU 有効リソースのみ。ポリシーやタグの変更反映に伝播時間がかかる

🤔 考慮すべき点

⚠PostgreSQL 14 はコミュニティサポート終了 (14.25 が最終)。15 以降へのメジャーバージョンアップグレード計画が必要
⚠bpchar 列の btree、GIN、TOAST テーブル、pg_trgm GiST の各インデックスに破損の可能性。該当インデックスは REINDEX を検討
⚠Aurora PostgreSQL への移行予定がある場合、RDS 側バージョンが Aurora 未サポートだと移行が遅延する可能性。AMVU 無効化を早期に検討
⚠重大なセキュリティ問題やサポート終了時は、AMVU 無効でも RDS がアップグレードを適用する場合がある

🎯 ユースケース

🏢 ユースケース 1: マルチアカウント環境での段階的な一斉アップグレード

シナリオ: AWS Organizations 配下の数十アカウントで数百の RDS for PostgreSQL インスタンスを運用。CVE 対応のアップグレードを開発環境から本番環境へ安全に展開したい。

Bash環境別タグ付けの例
# 開発環境のインスタンスに first 相当のタグを付与
aws rds add-tags-to-resource \
    --resource-name arn:aws:rds:ap-northeast-1:123456789012:db:dev-db \
    --tags Key=Environment,Value=Development

# 本番環境のインスタンスに last 相当のタグを付与
aws rds add-tags-to-resource \
    --resource-name arn:aws:rds:ap-northeast-1:123456789012:db:prod-db \
    --tags Key=Environment,Value=Production

効果開発環境で先行検証し、ベイクタイム中に問題がないことを確認してから QA、本番環境へ進むため、組織全体のアップグレードリスクを最小化。問題検出時は後続環境の AMVU を無効化して展開を停止できる。

🕐 ユースケース 2: ダウンタイム要件が厳しい本番 DB の CVE 対応

シナリオ: 24 時間稼働のサービスを支える本番 DB で、メンテナンスウィンドウの停止時間を確保しづらいが、CVE 対応のため速やかに 17.12 へアップグレードしたい。

BashBlue/Green デプロイの作成
aws rds create-blue-green-deployment \
    --blue-green-deployment-name pg-17-12-upgrade \
    --source arn:aws:rds:ap-northeast-1:123456789012:db:prod-db \
    --target-engine-version 17.12

効果Green 環境でアップグレード後の動作を事前検証し、準備が整った時点でスイッチオーバーすることで、ダウンタイムを最小限に抑えながら CVE に対処できる。

📅 ユースケース 3: PostgreSQL 14 からのメジャーバージョンアップグレード計画

シナリオ: PostgreSQL 14 系のインスタンスを運用しているが、コミュニティサポートが終了し 14.25 が最終リリースとなるため、サポート中のバージョンへの移行を計画する。

Bash最終マイナーバージョンへの更新
# まず最終マイナーバージョン 14.25 へ更新して既知の CVE に対処
aws rds modify-db-instance \
    --db-instance-identifier legacy-db \
    --engine-version 14.25 \
    --no-apply-immediately

# その後、Blue/Green デプロイで 17 系などへのメジャーバージョンアップグレードを計画

効果当面のセキュリティリスクを 14.25 で解消しつつ、Blue/Green デプロイを利用した計画的なメジャーバージョンアップグレードで、以降もセキュリティ修正を受けられる状態を維持できる。

💰 料金と利用可能リージョン

💵 料金

マイナーバージョンアップグレード自体に追加料金はなく、通常の Amazon RDS for PostgreSQL の料金体系 (インスタンス、ストレージ、I/O など) が適用されます。Blue/Green デプロイを使用する場合は、Green 環境の稼働中に追加のインスタンス・ストレージ料金が発生する点に注意してください。
