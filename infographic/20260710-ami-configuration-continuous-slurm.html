Amazon SageMaker HyperPod

🚀 継続的プロビジョニングでの
AMI ベースのノードライフサイクル設定

2026-07-10 リリース日

📌 概要

Amazon SageMaker HyperPod が、継続的プロビジョニング (Continuous Provisioning) を使用する Slurm クラスターで AMI ベースの設定 をサポートしました。継続的プロビジョニングは、キャパシティが利用可能になるにつれてノードをクラスターに追加するモードです。

これまでは、ノードをセットアップするために ライフサイクル設定スクリプト をダウンロード、設定し、Amazon S3 にアップロードする必要がありました。今回のサポートにより、これらのスクリプトを管理することなくクラスターを作成できます。各ノードはクラスターに追加される際に AMI から設定されるため、ジョブのスケジューリングに利用可能になるまでの時間が短縮されます。

❌ アップデート前の課題

  • ライフサイクル設定スクリプトのダウンロード、設定、S3 へのアップロードが必要
  • スクリプトの管理・メンテナンスに運用負荷がかかっていた
  • スクリプト実行のため、ジョブ利用可能になるまで時間がかかっていた
➡️

✅ アップデート後の改善

  • ライフサイクル設定スクリプトなしでクラスターを作成できる
  • Docker、Enroot、Pyxis などの必須ソフトと設定が AMI から自動プロビジョニング
  • 追加時に AMI から設定されるため、ジョブ利用可能までの時間を短縮

キャパシティが利用可能になると継続的プロビジョニングによってノードが追加され、各ノードは AMI から必須ソフトウェアと設定を取得してプロビジョニングされます。ライフサイクル設定スクリプトの管理が不要になります。

⚡ 主要機能

🔄 継続的プロビジョニングでの AMI ベース設定

  • キャパシティが利用可能になるにつれてノードを追加する継続的プロビジョニングモードに対応
  • 各ノードはクラスターに追加される際に AMI から設定される
  • ライフサイクル設定スクリプトの管理が不要

📦 本番環境対応の自動プロビジョニング

  • 必須ソフトウェア: Docker、Enroot、Pyxis
  • 設定内容: Slurm アカウンティング、SSH キー生成、ログローテーション
  • AI/ML トレーニングワークロードをすぐに実行できる状態でノードが提供される

🛠️ 拡張スクリプトによるカスタマイズ

  • OnInitComplete と SourceS3Uri を LifeCycleConfig ブロックで指定して拡張スクリプトを追加可能
  • AMI のベースライン設定に加えて独自の設定を適用できる
  • 完全な制御が必要なユースケース向けにカスタムスクリプトも引き続きサポート

🔧 技術仕様

API 変更履歴

継続的プロビジョニングでの AMI ベース設定を有効にするには、クラスター作成時にインスタンスグループ設定から LifeCycleConfig ブロックを省略します。拡張スクリプトを使用する場合は、LifeCycleConfig ブロック内で OnInitComplete パラメータと SourceS3Uri を指定します。

⚙️ 設定方法

前提条件

✓SageMaker HyperPod が利用可能なリージョンであること
✓Slurm オーケストレーションを使用する HyperPod クラスターを作成すること
✓継続的プロビジョニングモードを使用するクラスター構成であること

手順

① AMI ベース設定で作成 (API)

インスタンスグループ設定から LifeCycleConfig ブロックを省略し、スクリプトの準備・アップロードなしにクラスターを作成。

② AMI ベース設定で作成 (コンソール)

SageMaker AI コンソールの Custom setup の Lifecycle scripts で「None」を選択。

③ 拡張スクリプトの追加 (任意)

OnInitComplete と SourceS3Uri を指定し、組織固有の設定を AMI の上に適用。

💡 メリット

📈 ビジネス面

  • 運用負荷の削減: スクリプトの管理・メンテナンスが不要になり運用コストを削減
  • 市場投入までの時間短縮: セットアップが簡素化され、AI/ML トレーニングを早く開始
  • 一貫性の向上: 標準化された環境でノード間の設定のばらつきを低減

🔩 技術面

  • ノード可用性の高速化: AMI から設定され、ジョブ利用可能までの時間を短縮
  • 本番環境対応: Docker、Enroot、Pyxis が事前構成された状態で提供
  • 柔軟なカスタマイズ: 拡張・カスタムスクリプトで追加設定が可能

⚠️ デメリット・制約事項

制限事項

!継続的プロビジョニングと AMI ベース設定は Slurm オーケストレーションを使用するクラスターが対象
!AMI に含まれるソフトウェアバージョンは AMI により決定されるため、特定バージョンが必要な場合は拡張・カスタムスクリプトでの対応が必要

考慮すべき点

→プロビジョニングを完全に制御したい場合は、従来のカスタムライフサイクル設定スクリプトの使用を検討
→AMI のベースライン設定で不足する要素は、OnInitComplete を用いた拡張スクリプトで補う

🎯 ユースケース

1. 大規模 LLM トレーニングクラスターの迅速な構築

シナリオ: LLM トレーニングチームが、GPU キャパシティが利用可能になり次第ノードを追加したい。スクリプト管理に時間をかけたくない。

効果: 継続的プロビジョニングと AMI ベース設定でノードが自動構成され、キャパシティ確保後すぐにトレーニングジョブを実行できる。

2. 標準化された ML 環境の展開

シナリオ: 複数チームが共通の ML トレーニング環境を必要とし、ノード間で一貫した設定を維持したい。

効果: Docker、Enroot、Pyxis、Slurm アカウンティングなどが標準化された状態で提供され、環境のばらつきを排除できる。

3. 組織固有の設定を追加した環境構築

シナリオ: AMI の標準設定に加えて、社内のモニタリングエージェントやセキュリティ設定を各ノードに適用したい。

効果: OnInitComplete と SourceS3Uri を用いた拡張スクリプトで、AMI のベースライン設定の上に組織固有の設定を追加できる。

💰 料金・利用可能リージョン

💵 本機能自体に追加料金はありません。使用するコンピューティングリソース (インスタンス) およびストレージなどの通常の SageMaker HyperPod 料金が適用されます。
🌎 Amazon SageMaker HyperPod が利用可能なすべての AWS リージョンで利用できます。

📝 まとめ

このアップデートにより、継続的プロビジョニングを使用する SageMaker HyperPod の Slurm クラスターでも、ライフサイクル設定スクリプトの管理なしにノードを構成できるようになりました。運用負荷の削減とノード可用性の高速化により、AI/ML トレーニングワークロードの立ち上げが容易になります。継続的プロビジョニングを利用しているチームは、クラスター作成時に LifeCycleConfig ブロックの省略 (またはコンソールで「None」を選択) を検討することをお勧めします。
