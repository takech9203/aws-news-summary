Amazon SageMaker Unified Studio AWS Glue

📋 概要

Amazon SageMaker Unified Studio が AWS Glue ジョブのクロスサブネットリトライに対応する Glue コネクタの自動プロビジョニング機能をリリース。管理者がドメイン VPC に複数の AZ にまたがるプライベートサブネットを設定するだけで、システムが自動的にすべてのサブネットに対して Glue コネクタをプロビジョニングする。

IP アドレスの枯渇や AZ の劣化といった障害シナリオにおいて、ユーザーの手動介入なしにジョブが継続実行される。

❌ Before

  • Glue ジョブが失敗した場合、手動でネットワーク接続を再構成しリトライする必要
  • IP アドレス枯渇や AZ 障害時にデータパイプラインが停止し SLA 違反リスク
  • 複数サブネットにまたがる Glue コネクタの手動作成・管理の運用負荷

✅ After

  • ドメイン VPC 設定に基づき Glue コネクタが全サブネットに自動プロビジョニング
  • サブネット障害時に自動的に別サブネットへリトライ、ダウンタイム削減
  • 初期 VPC 設定以降はユーザーの介入が不要、運用負荷を大幅低減

🏗️ アーキテクチャ図

管理者がドメイン VPC を複数サブネットで設定すると、SageMaker Unified Studio が各サブネットに Glue コネクタを自動作成する。Glue ジョブ実行時にサブネット障害が発生した場合、別のサブネットへ自動リトライが行われる。

⚡ 主要機能

🔌 Glue コネクタの自動プロビジョニング
  • ドメイン VPC 設定に定義された全プライベートサブネットに対して Glue コネクタを自動作成
  • 新規プロジェクトに対して自動的にコネクタがプロビジョニングされる
  • 手動でのコネクタ作成・管理が不要
🔄 クロスサブネット自動リトライ
  • プライマリサブネットが利用不可になった場合、別サブネットのコネクタを使用して自動リトライ
  • IP アドレス枯渇シナリオに対応
  • AZ 劣化シナリオに対応
🚀 ゼロオペレーション設計
  • 初期 VPC 設定後はユーザーアクションが不要
  • 既存のドメイン VPC 設定フレームワーク内で動作
  • 管理者による追加設定や監視が最小限

🛠️ 設定方法

前提条件

✓Amazon SageMaker Unified Studio ドメインが設定済みであること
✓ドメイン VPC に複数の AZ にまたがるプライベートサブネットが構成されていること
✓ドメイン管理者権限を持つ IAM ロールがあること

ステップ 1: ドメイン VPC の確認

VPC に複数のプライベートサブネットが異なる AZ に配置されていることを確認する。

Bash VPC 内のサブネット一覧を確認 
# VPC 内のサブネット一覧を確認
aws ec2 describe-subnets \
  --filters "Name=vpc-id,Values=vpc-xxxxxxxx" \
  --query "Subnets[].{SubnetId:SubnetId,AZ:AvailabilityZone,CidrBlock:CidrBlock}" \
  --output table

ステップ 2: ドメイン VPC 設定の更新

ドメイン VPC 設定に複数のサブネットを含めて設定する。この設定により Glue コネクタの自動プロビジョニングが有効になる。

Bash SageMaker ドメインの VPC 設定を確認 
# SageMaker ドメインの VPC 設定を確認
aws sagemaker describe-domain \
  --domain-id d-xxxxxxxx \
  --query "DefaultUserSettings.SecurityGroups"

ステップ 3: 新規プロジェクトでの動作確認

新規プロジェクトを作成し、Glue コネクタが各サブネットに自動プロビジョニングされていることを確認する。

Bash Glue コネクション一覧を確認 
# Glue コネクション一覧を確認
aws glue get-connections \
  --filter '{"ConnectionType": "NETWORK"}' \
  --query "ConnectionList[].{Name:Name,Subnet:PhysicalConnectionRequirements.SubnetId}"

✅ メリット

💼 ビジネス面

  • SLA 遵守の向上: サブネット障害時の自動リカバリによりダウンタイム削減
  • 運用コスト削減: 手動でのコネクタ管理やリトライ対応が不要
  • 信頼性の向上: マルチ AZ のレジリエンスが自動的に確保

🔧 技術面

  • 自動フェイルオーバー: IP 枯渇や AZ 劣化を自動検知しシームレスにリトライ
  • インフラ管理の簡素化: Glue コネクタのライフサイクルが自動管理
  • スケーラビリティ: 新規プロジェクト作成時に自動的にマルチサブネット対応

⚠️ 制限事項・考慮点

📌 制限事項

  • 新規プロジェクトに対してのみ適用 (既存プロジェクトへの自動適用は明示なし)
  • ドメイン VPC に複数 AZ のプライベートサブネットが事前構成されている必要あり
  • リトライ対象は Glue ジョブに限定 (他のコンピュートサービスには非適用)

💡 考慮すべき点

  • 複数サブネットにコネクタが自動作成されるため VPC 内のリソース制限 (ENI 数など) に注意
  • 自動リトライの動作ロジック (リトライ回数、タイムアウトなど) は公式ドキュメントで確認推奨

🎯 ユースケース

📊 大規模 ETL パイプラインの高可用性確保

シナリオ: 毎日数百の Glue ジョブが実行される大規模 ETL パイプラインで、特定の AZ で IP アドレスが枯渇しジョブが失敗するケースが頻発

効果: IP アドレス枯渇による Glue ジョブの失敗率が大幅に減少し、SLA 99.9% の達成が容易に

🔄 マルチ AZ データ統合ワークロード

シナリオ: 複数のデータソースからデータを収集・統合する Glue ジョブが、単一 AZ の障害でバッチ処理全体が停止

効果: AZ 障害時のバッチ処理停止がゼロになり、データの鮮度と可用性が向上

🏦 規制対応が必要なデータパイプライン

シナリオ: 金融機関のデータパイプラインで、規制要件として処理の継続性とデータ処理 SLA の遵守が求められている

効果: 障害発生時も自動リカバリにより処理が継続し、規制当局への SLA 遵守報告が容易に
