AWS Secrets Manager 2026 年 4 月 3 日

🔐 コンソールでのカスタム KMS キー
ARN 直接入力サポート

クロスアカウント暗号化ワークフローがコンソールから実行可能に

📋 概要

AWS Secrets Manager のコンソールにおいて、シークレット作成時にカスタムの AWS KMS キーを直接 ARN で指定できるようになった。従来のドロップダウンリストからの選択に加えて、KMS キーの ARN を直接入力できるフィールドが追加され、別の AWS アカウントの KMS キーもコンソールから指定可能になった。

これにより、コンソールの操作性が既存の API や CLI の機能と同等になり、マルチアカウント環境でのシークレット管理ワークフローが大幅に簡素化された。

❌ Before - アップデート前の課題
  • ドロップダウンリストには同一アカウント内の KMS キーのみ表示
  • クロスアカウントの KMS キーは AWS CLI や API を使用する必要があった
  • コンソールと API/CLI の機能に差異があり、運用手順が複雑
✅ After - アップデート後の改善
  • KMS キーの ARN をコンソール上で直接入力可能に
  • 別の AWS アカウントの KMS キーをコンソールから指定可能に
  • コンソールの機能が API/CLI と同等になり一貫した操作体験を提供

⚡ 主要機能

🔑 KMS キー ARN の直接入力

シークレット作成画面で KMS キーの ARN を直接テキスト入力できるフィールドが追加された。従来のドロップダウンリストからの選択も引き続き利用可能。

ARN 形式: arn:aws:kms:<region>:<account-id>:key/<key-id>

🌐 クロスアカウント KMS キーのサポート

別の AWS アカウントに存在する KMS キーの ARN を指定可能。コンソールから直接クロスアカウント暗号化ワークフローを実行でき、API/CLI で既にサポートされていた機能がコンソールにも拡張された。

📋 既存のドロップダウンリストとの併用

同一アカウント内の KMS キーは従来通りドロップダウンリストから選択可能。カスタム入力とドロップダウン選択の両方の方法が利用できる。

🔧 技術仕様

KMS キー指定方法の比較

項目 アップデート前 アップデート後
同一アカウントの KMS キー ドロップダウンリストから選択 ドロップダウン選択 + ARN 直接入力
クロスアカウントの KMS キー API/CLI のみ コンソール + API/CLI
デフォルト KMS キー 選択可能 選択可能

クロスアカウント KMS キー使用の前提条件

項目 詳細
KMS キーポリシー キー所有アカウントでクロスアカウントアクセスを許可するポリシーの設定が必要

📝 設定例

クロスアカウント KMS キーポリシー

キー所有アカウントで設定するクロスアカウントアクセスポリシーの例。

JSON KMS キーポリシー - クロスアカウントアクセス許可 
{
  "Sid": "AllowCrossAccountSecretsManager",
  "Effect": "Allow",
  "Principal": {
    "AWS": "arn:aws:iam::111122223333:root"
  },
  "Action": [
    "kms:Decrypt",
    "kms:GenerateDataKey",
    "kms:DescribeKey",
    "kms:CreateGrant"
  ],
  "Resource": "*",
  "Condition": {
    "StringEquals": {
      "kms:ViaService": "secretsmanager.ap-northeast-1.amazonaws.com"
    }
  }
}

🛠️ 設定方法

前提条件

  • ✓ クロスアカウントで使用する KMS カスタマーマネージドキーが作成済みであること
  • ✓ KMS キーのキーポリシーでクロスアカウントアクセスが許可されていること
  • ✓ シークレット作成アカウントの IAM ユーザー/ロールに KMS キーの使用権限があること

ステップ 1: KMS キーの ARN を確認

KMS キーを所有するアカウント B で、使用する KMS キーの ARN を確認する。

Bash KMS キー ARN の確認 
aws kms describe-key --key-id alias/my-secrets-key \
  --query 'KeyMetadata.Arn' --output text

ステップ 2: コンソールでシークレットを作成

1 AWS Secrets Manager コンソールを開く
2 「新しいシークレットを保存する」を選択
3 シークレットのタイプと値を入力
4 暗号化キーのセクションで、KMS キーの ARN を直接入力フィールドに貼り付ける
5 残りの設定を完了してシークレットを作成

ステップ 3: AWS CLI での同等操作

Bash CLI でのクロスアカウントシークレット作成 
aws secretsmanager create-secret \
  --name "my-cross-account-secret" \
  --secret-string '{"username":"admin","password":"example"}' \
  --kms-key-id "arn:aws:kms:ap-northeast-1:999888777666:key/12345678-abcd-efgh-ijkl-123456789012"
💡 ポイント: 今回のアップデートにより、この CLI 操作と同等のことがコンソールからも可能になった。

⚖️ メリットとデメリット

✅ メリット

ビジネス面

  • → 運用効率の向上: クロスアカウントのシークレット作成がコンソールから直接可能に
  • → 学習コストの削減: CLI や API の知識がなくても実行可能
  • → セキュリティガバナンスの強化: 一元管理された KMS キーの利用が容易に

技術面

  • → コンソールと API の機能パリティ達成
  • → クロスアカウントワークフローの簡素化
  • → ドロップダウンに表示されないキーも ARN で使用可能

⚠️ デメリット・制約事項

制限事項

  • ! AWS マネージドキー (aws/secretsmanager) はクロスアカウント不可
  • ! KMS キーポリシーで明示的にクロスアカウントアクセスを許可する必要あり
  • ! ARN 入力時のバリデーションエラー時はポリシー確認が必要

考慮すべき点

  • ! キー所有アカウントの KMS キー削除でシークレット復号不可に
  • ! KMS キーとシークレットのリージョンが一致している必要あり
  • ! IAM ポリシーと KMS キーポリシーの両方の適切な設定が必要

💡 ユースケース

🏢 ユースケース 1: 中央集権的な暗号化キー管理

シナリオ: セキュリティチームが専用の AWS アカウントで KMS キーを一元管理し、各プロジェクトアカウントの Secrets Manager シークレットをその KMS キーで暗号化する。

🎯 効果: 暗号化キーのライフサイクル管理を一元化でき、コンプライアンス要件への対応が容易になる。

🔄 ユースケース 2: マルチアカウント環境でのアプリケーションシークレット管理

シナリオ: AWS Organizations で管理された複数アカウントにまたがるマイクロサービス環境で、共有データベースの認証情報を統一された KMS キーで暗号化する。

🎯 効果: 複数アカウントで一貫した暗号化ポリシーを適用でき、鍵のローテーション管理も一箇所で行える。

📋 ユースケース 3: 監査・コンプライアンス対応

シナリオ: 金融機関で規制要件に基づき、特定の KMS キーでのみシークレットを暗号化する必要がある環境で、監査チームが管理するキーを各部門のアカウントから利用する。

🎯 効果: コンプライアンス要件を満たす暗号化キーの使用をコンソールレベルで強制でき、監査証跡の管理が容易になる。

🔗 関連サービス・機能

🔑 AWS KMS

シークレットの暗号化に使用するキー管理サービス。カスタマーマネージドキーのクロスアカウント共有が今回の機能の中核。

🏢 AWS Organizations

マルチアカウント環境の管理。組織内のアカウント間での KMS キー共有に活用。

🛡️ AWS IAM

KMS キーへのクロスアカウントアクセス権限の管理。キーポリシーと IAM ポリシーの両方の設定が必要。

📋 AWS CloudTrail

シークレット作成時の KMS キー使用状況の監査ログ記録。
