Amazon Connect Customer

🧪 テスト・シミュレーションでフローアクションの「結果」を検証可能に

📅 リリース日: 2026 年 10 月 26 日 | 🏷️ 機能: フローアクション結果 (アウトカム) のテスト・シミュレーション検証

📝 概要

Amazon Connect Customer のテスト・シミュレーション機能が拡張され、カスタマーエクスペリエンスフロー内のアクションの結果 (アウトカム) を検証できるようになりました。従来はアクションが「開始された」ことの確認のみでしたが、アクション完了時に返されるデータそのものをテストで検証できます。

検証対象は Lambda 関数のレスポンス、Amazon Lex の解決インテントとスロット値、Agentic CX ブロックのコンテキスト変数の 3 種類。テスト失敗時には予期しない結果を返した正確なアクションを特定でき、問題解決が高速化します。

❌ Before: アップデート前の課題

✗アクションが「開始された」ことしか確認できず、返したデータの正しさは検証不可
✗Lambda や Lex が期待と異なる値を返しても成功扱いになり、問題は下流ステップで初めて顕在化
✗テスト失敗時は下流のステップから遡って手動で原因を調査する必要があった

✅ After: アップデート後の改善

✓「Flow Action Completed」イベントの Observe ブロックで、正常完了時の結果データを捕捉
✓Check ブロックで検証 (アサーション) し、Log data アクションでテスト結果に記録
✓本番実行時と同じ JSONPath ($.External.*、$.Lex.*、$.AgenticCX.*) で参照でき、テストと実際の顧客体験が一致
✓失敗アクションをピンポイントで特定でき、遡り調査が不要に

シミュレーション中にフローアクションが正常完了すると、Observe ブロックが完了イベントを捕捉して結果データを取得し、Check ブロックによる検証と Log data アクションによる記録を実行します。

⚙️ 主要機能

👁️ 1. Flow Action Completed イベントの Observe ブロック

フロー内の特定のアクションが「正常に完了した」タイミングを検出する新しいイベントタイプ。従来の「Flow Action Started (Action Triggered)」が開始を検出するのに対し、完了時に生成された結果データをテストで利用可能にします。対象リソースタイプは Lambda 関数、Lex ボット、Agentic CX の 3 種類。

✅ 2. 結果データの検証 (Check ブロック)

捕捉した結果データを期待値と比較検証。例: Lambda が orderStatus = "Shipped" を返したこと、Lex ボットが CheckOrderStatus インテントを期待どおりのスロット値で解決したこと、Agentic CX が期待するコンテキスト変数を設定したことを確認できます。

📝 3. 結果データの記録 (Log data アクション)

JSONPath 参照 (例: $.External.orderStatus) を使用して、アクションの結果値をテスト結果に記録。テスト実行後のレビューやデバッグに活用できます。

🔄 4. 本番と同一の参照方法

観測が成功すると、結果データへの参照は実際のコンタクト実行時とまったく同じ値に解決されます。テストで記述したアサーションが、顧客が実際に体験する動作と一致することを保証します。

🔧 技術仕様

📂 結果データの参照名前空間

アクション名前空間参照例
⚡ Lambda 関数 $.External.<key> または $.LambdaInvocation.ResultData.<key> $.External.orderStatus
🤖 Amazon Lex $.Lex.<path> $.Lex.IntentName、$.Lex.Slots.OrderNumber、$.Lex.IntentConfidence.Score
🧠 Agentic CX $.AgenticCX.ContextVariables.<key>、$.AgenticCX.metadata.<key> $.AgenticCX.ContextVariables.customerTier

👁️ 観測 (Observation) の動作仕様

項目詳細
一致条件アクションが成功ブランチまたはデフォルトブランチで完了した場合のみ一致 (エラーブランチは「完了」とみなされない)
タイムアウト期待イベントが発生しない場合、5 分でタイムアウトしテストは失敗
参照可能になるタイミング該当アクションの Flow Action Completed 観測が一致した後のみ結果データを参照可能
複数回完了時の挙動同じアクションタイプが複数回正常完了した場合、参照は最後に捕捉された結果に解決される
参照可能な値単一の値のみ参照可能 (オブジェクトやリスト全体への参照は空の値に解決される)
イベント発生回数各 Observe ブロックはイベントが 1 回だけ発生することを期待 (変更不可)

🛠️ 設定方法

📋 前提条件

  • ✓ Amazon Connect Customer が利用可能なリージョンでインスタンスを運用していること
  • ✓ 検証対象の Lambda 関数、Lex ボット、または Agentic CX アプリケーションがフローに組み込まれていること
  • ✓ テスト・シミュレーション機能へのアクセス権限があること

🚶 手順

1
Observe ブロックの追加

テスト定義のインタラクショングループに Observe ブロックを追加し、以下を設定します。

  • Event Type: 「Action completed」を選択
  • Resource Type: 「Lambda function」「Lex Bot」「Agentic CX」のいずれかを選択
  • Target resource: ドロップダウンから対象リソースを選択 (または ARN を指定)

対象アクションが正常完了したタイミングで観測が一致し、結果データが捕捉されます。

2
Check ブロックで結果を検証

同じインタラクショングループに Check ブロックを追加します。Lambda の例は以下のとおりです。

  • Namespace: External / Key: orderStatus
  • Condition: Equals / Value: Shipped

Lambda が返した orderStatus の値が Shipped と等しいことを検証します。Lex や Agentic CX も、それぞれの名前空間を使用して同様に設定します。

3
Log data アクションで値を記録

必要に応じて Log data アクションを追加します。Log identifier: "Order status"、Log value: $.External.orderStatus。アクションが返した値をテスト結果に記録し、実行後のレビューに活用できます。

4
インタラクショングループの接続

メニューから「Add connector」を選択し、次の観測を含むインタラクショングループへ接続します。イベントの発生に沿ってテストがチェックポイントを順に進む論理フローが構成されます。

💡 メリット

💼 ビジネス面

✓問題解決の高速化: 失敗アクションを直接特定でき、遡り調査が不要になりトラブルシューティング時間を短縮
✓リリースの信頼性向上: フロー変更がアクションの出力レベルで検証され、自信を持って本番リリース可能
✓顧客体験の品質保証: アサーションが実際のコンタクト時の動作と一致し、顧客に影響が及ぶ前に問題を検出

🔬 技術面

✓出力レベルの検証: 「実行されたか」だけでなく「正しい結果を返したか」を検証でき、テストカバレッジが向上
✓本番同一の参照体系: フロー言語と同じ JSONPath 参照を使用するため、学習コストが低い
✓Agentic AI の検証: Agentic CX のコンテキスト変数を検証でき、AI 主導フローの品質管理が可能に

⚠️ デメリット・制約事項

🚧 制限事項

⚠️Flow Action Completed 観測は成功ブランチでの完了のみ一致。エラーブランチに進んだ場合は「完了」とみなされず、5 分のタイムアウト後にテスト失敗となる
⚠️結果データは単一の値のみ参照可能。オブジェクトやリスト全体への参照 (例: $.Lex.Slots) は空の値に解決される
⚠️同じアクションタイプが複数回完了した場合、参照は最後に捕捉された結果のみに解決される
⚠️各 Observe ブロックのイベント発生回数は「1 回」固定であり、変更できない

🤔 考慮すべき点

💭結果を参照する Check ブロックや Log data アクションは、必ず該当アクションの Flow Action Completed 観測の後に配置すること。観測前に参照すると空の値となりアサーションが失敗する
💭音声テストでは、音声のセグメント分割が発話のポーズや文構造により変動するため、実行ごとに結果が若干異なる場合がある (Message Received イベント使用時)
💭エラーブランチの動作自体を検証したい場合は、本イベントではなく別のテスト設計が必要

🎯 ユースケース

⚡ ユースケース 1: Lambda 関数の注文状況照会の検証

シナリオ: 注文状況を照会する Lambda 関数をフローに組み込んでおり、特定の注文番号に対して正しいステータスが返ることを検証したい。

設定例Lambda レスポンスの検証
1. Observe ブロック: Event Type = Action completed、Resource Type = Lambda function、
   Target resource = getCustomerInfo
2. Check ブロック: Namespace = External、Key = orderStatus、
   Condition = Equals、Value = Shipped
3. Log data アクション: Log identifier = "Order status"、
   Log value = $.External.orderStatus

効果: Lambda のレスポンス内容そのものを検証でき、データ連携の不具合をフロー変更のリリース前に検出できる。

🤖 ユースケース 2: Lex ボットのインテント解決の検証

シナリオ: 顧客の発話から Lex ボットが正しいインテントとスロット値を解決することを、フロー全体のシミュレーションの中で確認したい。

設定例Lex インテント解決の検証
1. Observe ブロック: Event Type = Action completed、Resource Type = Lex Bot、
   Target resource = 対象ボットの ARN とエイリアス
2. Check ブロック: $.Lex.IntentName が CheckOrderStatus と等しいことを検証
3. Check ブロック: $.Lex.Slots.OrderNumber が期待する注文番号と等しいことを検証

効果: ボットの会話設計変更やモデル更新後も、インテント解決の品質をリグレッションテストとして自動検証できる。

🧠 ユースケース 3: Agentic CX インタラクションのコンテキスト変数検証

シナリオ: Agentic CX ブロックによる AI 主導の顧客対応が、後続のフロー分岐で使用するコンテキスト変数を期待どおりに設定することを確認したい。

設定例コンテキスト変数の検証
1. Observe ブロック: Event Type = Action completed、Resource Type = Agentic CX、
   Target resource = Agentic CX ワークスペース、アプリケーション、エイリアス
2. Check ブロック: $.AgenticCX.ContextVariables.customerTier が
   期待する値と等しいことを検証
3. Log data アクション: $.AgenticCX.metadata の個別の値を記録

効果: Agentic AI の出力を定量的に検証でき、AI 主導フローの変更を安心してリリースできる。

🔗 関連サービス・機能

⚡ AWS Lambda

フローから呼び出される Lambda 関数のレスポンスデータが検証対象。$.External.* 名前空間で参照。

🤖 Amazon Lex

フロー内のボットが解決したインテント、スロット値、信頼度スコアが検証対象。$.Lex.* 名前空間で参照。

📞 Amazon Connect フロー

テスト・シミュレーションはフローの実行をシミュレートし、実際のコンタクトと同じ参照体系で結果を検証する。

🧠 Agentic CX

Amazon Connect Customer の AI 主導の顧客対応ブロック。設定するコンテキスト変数とメタデータが検証対象。

📌 まとめ

Amazon Connect Customer のテスト・シミュレーション機能が、アクションの開始確認から結果 (アウトカム) の検証へと拡張され、Lambda レスポンス、Lex インテント、Agentic CX のコンテキスト変数を出力レベルで検証できるようになりました。テスト失敗時の原因特定が大幅に効率化されるため、コンタクトセンターのフロー開発に携わるチームは、Flow Action Completed イベントを活用したリグレッションテストの整備を検討することを推奨します。
