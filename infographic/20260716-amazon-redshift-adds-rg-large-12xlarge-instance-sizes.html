Amazon Redshift

rg.large / rg.12xlarge
インスタンスサイズの追加

リリース日
2026 年 7 月 16 日

📌 概要

Amazon Redshift が、AWS Graviton プロセッサを搭載した RG インスタンスに 2 つの新しいサイズ rg.large と rg.12xlarge の一般提供 (GA) を開始しました。 既存の rg.xlarge / rg.4xlarge と合わせ、RG インスタンスは 4 つのサイズから選択できるようになりました。

小規模な開発環境から大規模な本番ワークロードまで、プロビジョンドクラスターをワークロードに応じて適切なサイズに調整できる柔軟性が高まりました。 新しいサイズは現行トラック「P202」でのみ利用可能で、トレーリングトラック「P201」では引き続き rg.xlarge / rg.4xlarge を利用できます。

😟 アップデート前の課題

  • rg.xlarge (4 vCPU) と rg.4xlarge (16 vCPU) の 2 サイズのみで選択肢が限定的
  • 小規模ワークロード/開発環境向けの低コスト構成を選べない
  • 大規模ワークロード向けに高いノード単位のコンピューティング能力を選べない
  • 規模に応じた細かな適正サイジングが困難

😀 アップデート後の改善

  • rg.large (2 vCPU / 16 GiB) 追加で低コストに利用開始
  • rg.12xlarge (48 vCPU / 384 GiB) 追加で大規模ワークロードに対応
  • 2 → 4 サイズに拡充し適正サイジングの柔軟性が向上
  • スナップショット/リストア、リサイズで RA3 から移行可能

新しい rg.large と rg.12xlarge の追加により、小規模から大規模まで幅広いワークロード規模に対して適正サイズの RG クラスターを選択できます。 いずれのサイズも Redshift Managed Storage を共有し、コンピューティングとストレージを独立してスケールおよび課金できます。

⚙️ 主要機能

🟢 rg.large の追加 (小規模向け) NEW

  • 2 vCPU、16 GiB RAM のエントリーサイズ
  • マルチノード構成で 2〜16 ノードをサポート
  • ノードあたりのマネージドストレージ上限は 8 TB、最大構成で合計 128 TB
  • 開発環境や小規模な本番ワークロードでの低コスト利用に最適

🟠 rg.12xlarge の追加 (大規模向け) NEW

  • 48 vCPU、384 GiB RAM の最大サイズ
  • 2〜128 ノードをサポートし、最大構成で合計 16,384 TB のマネージドストレージ
  • 高いコンピューティング能力を必要とする大規模分析ワークロードに対応

🛤️ トラック要件 (P202)

  • 新しい 2 サイズは現行トラック「P202」でのみ利用可能
  • トレーリングトラック「P201」では引き続き rg.xlarge / rg.4xlarge を利用可能
  • AWS Graviton 搭載で、RA3 比で最大 2.4 倍の性能と vCPU あたり 30% のコスト削減

🔄 RA3 からのマイグレーションパス

  • 既存 RA3 クラスターはスナップショット/リストア、エラスティックリサイズ、クラシックリサイズで RG へ移行可能

rg.large は ra3.large (マルチノード) に、rg.12xlarge は ra3.16xlarge (48 vCPU / 384 GiB) に相当し、 RA3 の全レンジをカバーする構成が RG でも選択可能になりました。

🛠️ 設定方法

前提条件

▸新しいサイズ利用にはクラスターが現行トラック「P202」であること
▸RG インスタンスをサポートする AWS リージョンでクラスターを作成すること
▸VPC 内にクラスターを配置すること (RG ノードタイプは VPC 内で起動)

ステップ 1: 新規クラスターの作成

Bashrg.large で 2 ノードクラスターを P202 で作成
aws redshift create-cluster \
  --cluster-identifier my-rg-cluster \
  --node-type rg.large \
  --number-of-nodes 2 \
  --master-username admin \
  --master-user-password <password> \
  --maintenance-track-name P202

ステップ 2: 既存 RA3 クラスターからのエラスティックリサイズ

Bashrg.12xlarge 4 ノードへエラスティックリサイズ
aws redshift resize-cluster \
  --cluster-identifier my-existing-cluster \
  --node-type rg.12xlarge \
  --number-of-nodes 4 \
  --classic false

ステップ 3: スナップショットからのリストアによる移行

RA3 クラスターのスナップショットを取得し、リストア時に RG ノードタイプを指定して移行します。 エラスティックリサイズが利用できない構成変更の場合は、スナップショット/リストアまたはクラシックリサイズを使用します。

▸
リージョンにより利用可否が異なるため事前確認が必要

🎯 ユースケース

1. 開発/検証環境のコスト削減

シナリオ: 本番は rg.4xlarge を運用中だが、開発・検証環境のコストを抑えたい。

構成例
本番: rg.4xlarge × 4 ノード
開発: rg.large × 2 ノード (新規)

効果: 価格性能比を維持しながら開発コストを大幅に削減。

2. 大規模分析ワークロードへの対応

シナリオ: データ量とクエリ同時実行数が増加し、コンピューティング能力が不足。

構成例
変更前: rg.4xlarge × 16 ノード (256 vCPU)
変更後: rg.12xlarge × 6 ノード (288 vCPU)

効果: より少ないノード数で高いコンピューティング能力を確保し性能向上。

3. RA3 からの段階的移行

シナリオ: ra3.large / ra3.16xlarge を運用中で、価格性能比の高い RG へ移行したい。

対応関係
ra3.large (マルチノード) → rg.large
ra3.16xlarge            → rg.12xlarge

効果: 既存構成に近いスペックを維持したまま移行し、vCPU あたり 30% のコスト削減と性能向上を実現。

💰 料金

RG インスタンスは、オンデマンド料金に加えて 1 年および 3 年のリザーブドインスタンス (前払いなし) の柔軟な料金オプションをサポートします。 料金はリージョン、ノードタイプ、ノード数、リザーブドの有無によって異なります。マネージドストレージはコンピューティングとは独立して使用量に応じて課金されます。

💡 正確な料金は Amazon Redshift の料金ページを参照してください。

📝 まとめ

今回のアップデートにより、Graviton 搭載の RG インスタンスに小規模な rg.large と大規模な rg.12xlarge が加わり、選択肢が 4 サイズに拡充されました。 開発環境から大規模本番ワークロードまで幅広い規模で適正サイジングが可能になり、RA3 の全サイズレンジに対応する移行先が揃いました。 RA3 クラスターを運用しているお客様は、P202 トラックへの切り替えと適切なリサイズ手法を検討し、価格性能比の高い RG インスタンスへの移行を評価することが推奨されます。
