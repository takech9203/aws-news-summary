Amazon EKS

AWS Outposts での EC2 インスタンスストアを利用したローカルクラスターのサポート

📅 リリース日
2026 年 6 月 11 日

📌 概要

AWS は、Amazon EKS のローカルクラスターのサポートを、 Amazon EC2 インスタンスストアからブートする EC2 インスタンスを実行する 第 1 世代・第 2 世代の AWS Outposts ラックに拡張しました。 EC2 インスタンスストアが提供する静的安定性 (static stability) のメリットが、 EKS ローカルクラスターの利用者にも広がります。

ローカルクラスターでは Kubernetes コントロールプレーン全体が Outposts 上で稼働します。 これにより高度なデータレジデンシー要件に対応でき、ファイバー切断や気象イベントなどで クラウドへの接続が切れても、アプリケーションとクラスター操作を継続できます。

❌ アップデート前の課題
  • インスタンスストアからブートする Outposts ラックではローカルクラスターを利用できなかった
  • etcd バックアップやロギングエージェントを利用者自身が管理する必要があった
  • クラウド版 EKS と比べ、機能や運用面の同等性に差があった
✅ アップデート後の改善
  • 第 1 世代・第 2 世代の Outposts ラックでローカルクラスターが利用可能に
  • コントロールプレーンを EKS サービス所有アカウントが管理し、etcd / ロギング管理が不要に
  • EKS アドオン、IRSA、Pod Identity、OIDC、アクセスエントリ、Bottlerocket をサポート

💡 Kubernetes コントロールプレーン全体が Outposts 上で稼働しつつ、その管理は AWS のサービス所有アカウントが行うため、 利用者は etcd バックアップやロギングエージェントの管理から解放されます。

⚡ 主要機能

1️⃣ EC2 インスタンスストアによる静的安定性

  • 第 1 世代・第 2 世代の Outposts ラックで、インスタンスストアからブートするローカルクラスターをサポート
  • インスタンスストア向けの静的安定性のメリットを EKS ローカルクラスターにも拡張
  • クラウドへの一時的なネットワーク切断時もアプリ・クラスター操作を継続可能

2️⃣ マネージドコントロールプレーンによる運用負荷の軽減

  • コントロールプレーンが Amazon EKS のサービス所有アカウントで管理される
  • etcd バックアップやロギングエージェントの管理が不要
  • 新しい Kubernetes / プラットフォームバージョンがクラウド版のリリースに合わせて提供

3️⃣ クラウド版 EKS との機能同等性の向上

  • Amazon EKS アドオンをサポート
  • IAM Roles for Service Accounts (IRSA)、EKS Pod Identity、OIDC 認証、アクセスエントリをサポート
  • ワーカーノードとして Bottlerocket をサポート (Amazon Linux 2023 に加えて)

⚙️ 設定方法

前提条件

✓Outposts ラック (第 1 / 第 2 世代) がインスタンスストアからブートする構成でプロビジョニング済み
✓Outposts がサポートされる商用 AWS リージョンに接続されていること
✓ローカルクラスターを作成するための IAM 権限を保有していること

ステップ 1: ローカルクラスターの作成

Bash eksctl でローカルクラスターを作成 
# eksctl を使用してローカルクラスターを作成する例
eksctl create cluster -f local-cluster-config.yaml

構成ファイルで Outpost ARN やサブネットなどを指定します。詳細は Amazon EKS ユーザーガイドを参照してください。

ステップ 2: ワーカーノードの追加

Bash Bottlerocket / Amazon Linux 2023 のノードグループ追加 
# Bottlerocket または Amazon Linux 2023 のノードグループを追加
eksctl create nodegroup --cluster <cluster-name> --node-ami-family Bottlerocket

更新後のアーキテクチャでは Bottlerocket と Amazon Linux 2023 の両方を選択できます。

ステップ 3: アドオンと認証の構成

EKS アドオン、IRSA、EKS Pod Identity、OIDC 認証、アクセスエントリなどを必要に応じて設定し、 クラウド版 EKS と同様の運用を実現します。

🎯 メリット

💼 ビジネス面

✓データレジデンシー対応: コントロールプレーン全体を Outposts 上で稼働させ要件を満たす
✓可用性の向上: ネットワーク切断時も継続稼働でダウンタイムリスクを軽減
✓運用コスト削減: コントロールプレーン管理が不要で運用負荷とコストを削減

🔩 技術面

✓静的安定性: インスタンスストア基盤の静的安定性を享受
✓マネージドコントロールプレーン: etcd / ロギング管理から解放
✓機能同等性: クラウド版の新バージョンや主要機能を利用可能

⚠️ デメリット・制約事項

制限事項

✕更新後アーキテクチャが対象。EBS からブートする Outposts は従来アーキテクチャを継続使用
✕AWS Outposts ラックをサポートする商用 AWS リージョンでのみ利用可能
✕対象は第 1 世代・第 2 世代の Outposts ラック

考慮すべき点

!EBS ベースから移行する際は、ブート構成 (インスタンスストア) を含めた設計の見直しが必要
!インスタンスストアは揮発性ストレージのため、データ永続化要件はワークロード設計で別途考慮

💡 ユースケース

① 規制対応が必要なオンプレミス Kubernetes 基盤

シナリオ金融や公共分野など、データを特定の拠点内に留める必要がある組織がオンプレミスで Kubernetes ワークロードを実行。

効果EKS クラスター全体を Outposts 上で稼働させ、データレジデンシー要件を満たしながらマネージド運用のメリットを得られる。

② 不安定なネットワーク環境での継続稼働

シナリオ通信障害や気象イベントでクラウド接続が断続的に切れる可能性がある拠点で、ミッションクリティカルなアプリを稼働。

効果ネットワーク切断時も継続稼働でき、静的安定性によりサービス継続性を確保できる。

③ クラウドとオンプレミスで統一した運用

シナリオクラウド上の EKS とオンプレミスの EKS を併用し、共通の運用手順とツールチェーンを利用したい。

効果EKS アドオン、IRSA、Pod Identity、OIDC、Bottlerocket などクラウド版と同等の機能で運用を標準化できる。

💰 料金

Amazon EKS ローカルクラスターおよび AWS Outposts の利用料金が適用されます。 具体的な料金は、AWS Outposts の構成および Amazon EKS の料金体系に依存します。 最新の料金は公式の料金ページを参照してください。

AWS Outposts ラックをサポートするすべての商用 AWS リージョンで、更新後のアーキテクチャが 一般提供 (GA) されています。ローカルクラスターは以下のリージョンで利用可能です。

📝 まとめ

今回のアップデートにより、EC2 インスタンスストアからブートする AWS Outposts ラックでも Amazon EKS ローカルクラスターを利用できるようになり、 静的安定性とマネージドコントロールプレーンによる運用負荷軽減を両立できます。 データレジデンシー要件や不安定なネットワーク環境で Kubernetes を運用する組織は、 更新後アーキテクチャへの移行や新規導入を検討することを推奨します。 クラウド版 EKS との機能同等性も向上しているため、ハイブリッド環境での運用標準化が進めやすくなります。
