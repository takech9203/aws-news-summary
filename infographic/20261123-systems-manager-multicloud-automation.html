⚙️ Automation によるマルチクラウド運用タスクの自動化

📅 リリース日: 2026 年 11 月 23 日 | 機能: Automation のマルチクラウド対応 (Microsoft Azure / Google Cloud)

📝 概要

AWS Systems Manager Automation が、Microsoft Azure および Google Cloud 上のリソースに対する運用タスクの自動化に対応しました。設定ミスの修復やアイドルリソースのクリーンアップといった定型的な運用ワークフロー (ランブック) を、AWS・Azure・Google Cloud をまたいで単一のツールから実行できます。

Automation は Systems Manager Cloud Connector を通じて Web アイデンティティトークンを短期有効な Azure / Google Cloud クレデンシャルに交換するため、AWS 側に他クラウドの認証情報を保存する必要はありません。バッチ単位での段階的なデプロイ、承認待ちによる一時停止、エラーしきい値による自動停止といった安全性の制御機能も、マルチクラウドのランブックで利用できます。

❌ アップデート前の課題

✗クラウドごとに個別の自動化ツール (Azure Automation、Google Cloud Workflows など) を維持する必要があった
✗クラウドごとに認証情報を個別に管理・保管する必要があり、シークレット管理の負担とリスクが大きかった
✗Azure や Google Cloud の API を呼び出すには、カスタムコードの開発と認証処理の実装が必要だった

✅ アップデート後の改善

✓6 つの新しいランブックアクションにより、カスタムコードなしで API 呼び出し・状態検証・完了待機が可能に
✓aws:executeScript に Azure / Google Cloud の Python SDK が同梱され、短期有効クレデンシャルを自動取得。シークレット保存が不要に
✓Azure はサブスクリプション・リージョン・リソースグループ・タグで、Google Cloud はプロジェクト・ゾーン・ラベルでターゲットを柔軟に指定可能に

Automation のランブックは Cloud Connector を経由して短期有効クレデンシャルを取得し、Azure や Google Cloud の API を直接呼び出してリソースを操作します。AWS 側に他クラウドのシークレットを保存する必要はありません。

🚀 主要機能

1️⃣ 6 つの新しいランブックアクション

各アクションは CloudConnector 入力と、使用する SDK パッケージを指定する Package 入力を受け取り、カスタムコードなしで API を呼び出せます。

aws:executeAzureApi aws:assertAzureResourceProperty aws:waitForAzureResourceProperty
aws:executeGcpApi aws:assertGcpResourceProperty aws:waitForGcpResourceProperty
2️⃣ aws:executeScript での Azure / Google Cloud SDK サポート
  • Azure SDK for Python (azure.mgmt.compute など) と Google Cloud クライアントライブラリ (google.cloud.compute_v1 など) が同梱され、ライブラリのインストールが不要
  • Automation が AZURE_ACCESS_TOKEN または GCP_ACCESS_TOKEN 環境変数にアクセストークンを設定するため、スクリプト内でクレデンシャルを保管する必要がない
  • 複数の API 呼び出し、ループ、独自ロジックを 1 ステップにまとめたい場合に有効
3️⃣ 柔軟なターゲット指定とレート制御
  • Azure: サブスクリプション、リージョン、リソースグループ、リソースタイプ、タグでフィルタリング
  • Google Cloud: プロジェクト、ゾーン、アセットタイプ、ラベルでフィルタリング
  • Cloud Connector ターゲットで条件に一致するリソースごとに子オートメーションを実行し、バッチ制御・承認・エラーしきい値による停止が可能
4️⃣ AWS 提供のランブック
  • Azure / Google Cloud の VM に SSM Agent や Amazon Inspector エージェントをインストールする AWS 提供のランブックが利用可能
  • 独自のワークフローをカスタムランブックとして作成することも可能

⚡ 実行方式

実行方式詳細
Cloud Connector ターゲット + レート制御コネクタとフィルタ条件に一致するリソースごとにランブックを実行。多数の VM への一括実行に適する
Parameter Values + レート制御最大 50 台まで VM の ID を直接指定して実行
Simple / Manual 実行Cloud Connector 入力を持つランブックに対し、リソース ID を指定して 1 回実行
API アクション / スクリプトランブックのステップ内で Azure / Google Cloud API を呼び出す。VM への SSM Agent インストールは不要

項目詳細

📜 ランブック例 (Google Cloud VM の起動と状態待機)

YAML runbook.yaml - mainSteps 
mainSteps:
  - name: startInstance
    action: aws:executeGcpApi
    inputs:
      Service: compute
      Api: Instances.Start
      Package: gcp_202610
      CloudConnector: '{{ CloudConnector }}'
      project: '{{ parseInstanceId.Project }}'
      zone: '{{ parseInstanceId.Zone }}'
      instance: '{{ parseInstanceId.InstanceName }}'
  - name: waitForRunning
    action: aws:waitForGcpResourceProperty
    timeoutSeconds: 600
    inputs:
      Service: compute
      Api: Instances.Get
      Package: gcp_202610
      CloudConnector: '{{ CloudConnector }}'
      project: '{{ parseInstanceId.Project }}'
      zone: '{{ parseInstanceId.Zone }}'
      instance: '{{ parseInstanceId.InstanceName }}'
      PropertySelector: $.status
      DesiredValues:
        - RUNNING

🛠️ 設定方法

📌 前提条件

  • Systems Manager Cloud Connector を作成する (Azure 用または Google Cloud 用)
  • コネクタのオートメーション引き受けロールを用意する (ノード管理を有効化した際にデフォルトで作成される)
  • リソース ID を受け取る入力を持つランブックを用意する (リソースタイプ入力、または allowedPattern で ID 形式を許可する String 入力)
1
Cloud Connector の確認

Systems Manager コンソールで Cloud Connector を作成済みであることを確認します。Cloud Connector は作成したリージョンに紐づくため、オートメーションは必ず同じリージョンで開始します。別リージョンからはコネクタを読み取れません。

2
ランブックの作成とクラウドプロバイダーの指定
Bashランブックの登録
aws ssm create-document \
  --name "StartGcpInstance" \
  --document-type "Automation" \
  --document-format YAML \
  --content file://runbook.yaml

ドキュメントのクラウドプロバイダーを Azure または GCP に設定すると、Automation コンソールの「Hybrid and multicloud」フィルタに表示され、Cloud Connector ターゲットが選択可能になります。

3
オートメーションの実行
Bashオートメーションの開始
aws ssm start-automation-execution \
  --document-name "StartGcpInstance" \
  --parameters "AutomationAssumeRole=arn:aws:iam::123456789012:role/AutomationCloudConnectorRole,CloudConnector=cc-0123456789abcdef0"

Cloud Connector ターゲットを使用したレート制御実行では、フィルタ条件に一致するリソースごとに子オートメーションが実行されます。実行結果は Automation コンソールの「Show child automations」で確認できます。

💼 ビジネス面

✓ガバナンスの統一: 設定ミスの修復やポリシー違反リソースの是正を、マルチクラウド全体で統一された手順として標準化

⚙️ 技術面

✓コード不要の API 呼び出し: 6 つの新アクションにより、API 呼び出し・状態検証・完了待機をカスタムコードなしで記述
✓SDK 同梱のスクリプト実行: aws:executeScript で Python SDK をインストール不要で利用でき、複雑なロジックも実装可能
✓安全な大規模実行: バッチ制御、承認による一時停止、エラーしきい値による自動停止で、大規模な変更を安全に展開

⚠️ デメリット・制約事項

🚧 制限事項

⚠Cloud Connector は作成した AWS リージョンに属するため、オートメーションは同じリージョンで開始する必要がある
⚠マルチアカウント・マルチリージョン実行モードでは Cloud Connector ターゲットを使用できない
⚠Parameter Values でのリソース ID 直接指定は最大 50 台まで (それ以上は Cloud Connector ターゲットを使用)
⚠API アクションのレスポンスは最大 358,400 文字 (セレクタ適用前)
⚠Package 入力は PowerShell ランタイムでは未サポート (REST API を Invoke-RestMethod で直接呼び出す)
⚠アクセストークンはリフレッシュ不可で、aws:executeScript ステップの実行時間は最大 600 秒

🤔 考慮すべき点

⚠コネクタのサービスアカウント / アイデンティティに付与された権限の範囲でのみ操作可能。例えば Google Cloud でインスタンスを起動するには compute.instances.start を含むロールの追加付与が必要
⚠Azure のトークンは Azure Resource Manager (管理プレーン) 専用。azure.storage.blob などのデータプレーンライブラリには別のトークンが必要
⚠DefaultAzureCredential や google.auth.default() は使用できず、環境変数のトークンからクレデンシャルを構築する必要がある
⚠長時間実行オペレーションは完了を待たずに返るため、aws:waitFor...ResourceProperty で完了待機を組み合わせる設計が必要

🎯 ユースケース

🌙 ユースケース 1: 営業時間外の開発用 VM の自動停止

シナリオ: Azure と Google Cloud に散在する開発用 VM を、コスト削減のため営業時間外に自動停止したい。

  • 開発用 VM にタグ (Azure) / ラベル (Google Cloud) を付与
  • VM を停止するランブックを作成し、クラウドプロバイダーを設定
  • Cloud Connector ターゲットでタグ / ラベルをフィルタ条件に指定
  • EventBridge スケジューラから夜間に自動実行
✅ 効果: クラウドごとのスクリプトやスケジューラを維持することなく、マルチクラウド全体のアイドルリソースによるコストを削減できる。
🔒 ユースケース 2: セキュリティポリシーに違反するストレージの是正

シナリオ: Google Cloud のストレージバケットや Azure のストレージアカウントで、組織のセキュリティポリシーに違反する設定 (パブリックアクセスなど) を検出し、自動是正したい。

  • aws:executeGcpApi / aws:executeAzureApi で設定を取得
  • aws:assertAzureResourceProperty などで状態を検証
  • 違反時は API 呼び出しで設定を修正し、承認ステップを挟んで段階的に適用
  • エラーしきい値を設定し、想定外の失敗が続いた場合は自動停止
✅ 効果: マルチクラウド全体のコンプライアンス是正を単一のワークフローで安全に自動化できる。
🖥️ ユースケース 3: Azure / Google Cloud VM への管理エージェント一括導入

シナリオ: Azure と Google Cloud の VM を Systems Manager のマネージドノードとして管理し、Amazon Inspector による脆弱性評価も行いたい。

  • AWS 提供のランブック (SSM Agent / Inspector エージェントのインストール) を選択
  • Cloud Connector ターゲットでサブスクリプション / プロジェクト単位に対象を指定
  • レート制御 (バッチサイズ・エラーしきい値) を設定して段階的に展開
✅ 効果: マルチクラウドの VM 群に対する管理基盤の導入を、手作業なしで安全に展開できる。
