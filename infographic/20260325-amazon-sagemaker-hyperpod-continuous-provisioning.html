Amazon SageMaker HyperPod

Slurm クラスター向け継続的プロビジョニング

部分キャパシティでもトレーニングを即時開始 | 2026 年 3 月 25 日

📋 概要

Amazon SageMaker HyperPod が、Slurm オーケストレーションクラスターに対して継続的プロビジョニング機能を提供開始しました。 一部のインスタンスグループのプロビジョニングが完了できない場合でも、クラスター全体がロールバックされることなく、利用可能なインスタンス上でトレーニングジョブを即座に開始できるようになります。

SageMaker HyperPod は、大規模言語モデル (LLM) や基盤モデル (FM) の開発に向けた耐障害性のある AI/ML クラスターをプロビジョニングするサービスです。 CreateCluster API で NodeProvisioningMode を "Continuous" に設定することで有効化されます。

🔄 Before / After

❌ Before
  • いずれかのインスタンスグループが完全にプロビジョニングできない場合、クラスター全体がロールバック
  • キャパシティ不足によりクラスター作成完了まで全トレーニングジョブが待機状態
  • 複数インスタンスグループのスケーリングが逐次的に処理され時間がかかる
  • 失敗したノードの再試行は手動操作が必要
✅ After
  • 一部のインスタンスが利用可能になった時点でトレーニングジョブを開始可能
  • 残りのキャパシティはバックグラウンドで自動的にプロビジョニング継続
  • 優先度ベースのプロビジョニングで Slurm コントローラーが最初に起動
  • 失敗ノードの非同期自動リトライ、並行ノンブロッキングスケーリング

継続的プロビジョニングでは、Slurm コントローラーが最優先で起動され、その後ログインノードとワーカーノードが並列で起動されます。利用可能なノードでトレーニングジョブを即座に開始でき、残りのキャパシティはバックグラウンドで継続的にプロビジョニングされます。

🔧 主要機能

📋 優先度ベースのプロビジョニング
  • Slurm コントローラーノードが最優先で起動される
  • コントローラー起動後、ログインノードとワーカーノードが並列でプロビジョニング
  • クラスターの基盤コンポーネントから順に確実に起動
🔄 バックグラウンド継続プロビジョニング
  • 利用可能なインスタンスでクラスターが部分的に稼働を開始
  • 残りのキャパシティはバックグラウンドで自動的にプロビジョニング継続
  • ユーザーの介入なしに、徐々にクラスターが完全な状態に近づく
♻️ 非同期リトライ機構
  • 起動に失敗したノードは非同期で自動的にリトライ
  • 一時的なキャパシティ不足やプロビジョニングエラーに対する耐障害性が向上
  • 手動での再試行操作が不要
📈 並行ノンブロッキングスケーリング
  • 複数のインスタンスグループにわたるスケーリング操作が並行して実行
  • 1 つのインスタンスグループのスケーリングが他のグループをブロックしない
  • スケーリング全体の所要時間が短縮

📐 技術仕様: プロビジョニングモード比較

項目 従来モード 継続的プロビジョニング
部分プロビジョニング失敗時 クラスター全体がロールバック 利用可能なノードで稼働開始
ジョブ開始タイミング 全ノードのプロビジョニング完了後 利用可能なノードが揃い次第
スケーリング方式 逐次処理 並行ノンブロッキング
失敗ノードのリトライ 手動 非同期自動リトライ
設定パラメータ デフォルト NodeProvisioningMode: Continuous

⚙️ 設定方法

前提条件

  • AWS アカウントに SageMaker HyperPod へのアクセス権限がある
  • Slurm オーケストレーションを使用するクラスター構成が準備されている
  • 必要な IAM ロールとライフサイクルスクリプトが設定済みである

ステップ 1: クラスター構成ファイルの作成

NodeProvisioningMode を Continuous に設定し、インスタンスグループを定義します。

JSON cluster-config.json 
{
  "ClusterName": "my-hyperpod-cluster",
  "InstanceGroups": [
    {
      "InstanceGroupName": "controller-group",
      "InstanceType": "ml.m5.xlarge",
      "InstanceCount": 1,
      "LifeCycleConfig": {
        "SourceS3Uri": "s3://my-bucket/lifecycle-scripts/",
        "OnCreate": "on-create-controller.sh"
      },
      "ExecutionRole": "arn:aws:iam::123456789012:role/HyperPodRole"
    },
    {
      "InstanceGroupName": "worker-group",
      "InstanceType": "ml.p5.48xlarge",
      "InstanceCount": 16,
      "LifeCycleConfig": {
        "SourceS3Uri": "s3://my-bucket/lifecycle-scripts/",
        "OnCreate": "on-create-worker.sh"
      },
      "ExecutionRole": "arn:aws:iam::123456789012:role/HyperPodRole"
    }
  ],
  "NodeProvisioningMode": "Continuous"
}

ステップ 2: クラスターの作成

Bash CreateCluster API の実行 
# 継続的プロビジョニングを有効にしてクラスターを作成
aws sagemaker create-cluster --cli-input-json file://cluster-config.json

ステップ 3: プロビジョニング状況の確認

Bash クラスター状態の確認 
# クラスターの状態を確認
aws sagemaker describe-cluster --cluster-name my-hyperpod-cluster

# ノードグループの詳細を確認
aws sagemaker list-cluster-nodes --cluster-name my-hyperpod-cluster

バックグラウンドでプロビジョニングが継続されている間も、利用可能なノードの状態を監視できます。

🎯 ユースケース

🧠 大規模 LLM トレーニングの迅速な開始
数百台の GPU インスタンスを必要とする大規模 LLM トレーニングで、一部のインスタンスのキャパシティが一時的に不足している状況。128 台中 96 台が先に利用可能になった場合、96 台でトレーニングを開始し、残り 32 台はバックグラウンドでプロビジョニングされる。
✅ 従来は 128 台全てが揃うまでトレーニングを開始できなかったが、利用可能なノードで即座に開始可能に
📊 マルチインスタンスグループの効率的なスケーリング
異なるインスタンスタイプで構成された複数のインスタンスグループ (トレーニングワーカー: ml.p5.48xlarge x64、データ処理: ml.m5.4xlarge x16) を持つクラスターのスケーリング。
✅ トレーニングワーカーとデータ処理ノードが並行してスケーリングされ、一方のグループのプロビジョニング遅延が他方をブロックしない
🌍 キャパシティ変動が大きいリージョンでの運用
人気の GPU インスタンスタイプのキャパシティが変動しやすいリージョンで、安定したクラスター運用を行いたいシナリオ。NodeProvisioningMode を Continuous に設定してクラスターを作成すると、利用可能なキャパシティで部分的に稼働開始される。
✅ キャパシティの変動に対して自動的に適応し、手動での再試行やクラスター再作成が不要に

⚖️ メリットと制約事項

✅ メリット

  • 全ノード完了を待たずにトレーニング開始、タイムライン改善
  • キャパシティ不足でも運用継続、ビジネス中断リスク低減
  • アイドルリソース削減、利用可能リソースの即時活用
  • 部分的なプロビジョニング失敗がクラスター全体に影響しない
  • 失敗ノードの非同期リトライで手動介入不要
  • 並行スケーリングでクラスター拡張時間を短縮

⚠️ 制約・考慮点

  • Slurm オーケストレーションクラスターのみが対象
  • 部分稼働中はジョブの並列度やデータ分散戦略の調整が必要
  • Slurm ジョブスケジューラー設定の最適化が推奨
  • CreateCluster API での設定が必要
  • リトライ動作やタイムアウトの詳細は公式ドキュメントで確認が必要
  • EKS オーケストレーションには現時点で適用されない可能性あり

💰 料金情報

継続的プロビジョニング機能自体に追加料金は発生しません。 通常の SageMaker HyperPod の料金体系が適用され、プロビジョニングされたインスタンスの使用時間に基づいて課金されます。
