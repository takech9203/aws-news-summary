🧠 長期記憶向け 厳密一貫メタデータ
Strictly Consistent Metadata

アプリケーションが把握している正確な値を、LLM 推論を経ずにそのまま長期記憶レコードへ反映。コンプライアンス境界やマルチテナント分離を確実に実現します。

📌 概要

Amazon Bedrock AgentCore Memory は、短期記憶から有用な情報を抽出し、長期記憶レコードとして保存します。これらのレコードに付与されるメタデータは、検索時の整理・フィルタリング・ルーティングに利用されます。今回のアップデートで、メタデータキーに新しい抽出タイプ STRICTLY_CONSISTENT を設定できるようになりました。

従来はメタデータ値が抽出過程で LLM によって推論されていましたが、新機能ではアプリケーションから値を直接付与でき、LLM 推論を経ることなく抽出と統合を通じて指定どおりレコードへ反映されます。さらに、同じ値を持つイベントは一緒に抽出・統合され、イベントのグループ化方法も分離されます。

Before / After

⚠️ アップデート前の課題
  • メタデータ値が抽出時に LLM 推論されるのみで、既知の正確な値をそのまま反映できなかった
  • LLM 推論のばらつきで eng と Engineering のように表記が混在し、フィルタリングが不安定
  • 部門・コンプライアンスレベル・エージェント ID など決定論的に扱うべきキーまで LLM 推論に依存
➡️
✅ アップデート後の改善
  • STRICTLY_CONSISTENT キーは、イベントで指定した値がそのまま変更されずにレコードへ反映
  • LLM 推論によるばらつきを排除し、正確で一貫した値を保証
  • 決定論的キーの値ごとに抽出と統合を分離し、異なる値のレコードが統合中に混ざらない

抽出タイプが STRICTLY_CONSISTENT のキーは LLM 推論を経ずに値がそのまま反映され、決定論的値でグループ化されてから統合される

⚡ 主要機能

1️⃣ STRICTLY_CONSISTENT 抽出タイプ
  • メタデータスキーマで extractionType を STRICTLY_CONSISTENT に設定
  • イベントで指定した値が、抽出と統合を通じて変更されることなくレコードへ反映
  • 当該キーでは LLM が参照されず、推論や競合解決 (conflict resolution) も行われない
  • 省略時のデフォルトは LLM_INFERRED
2️⃣ 抽出と統合の分離 (Isolation)
  • 決定論的な値の組み合わせによってイベントをグループ化
  • 同じ値を共有するイベントは一緒に抽出・統合される
  • 値が異なるイベントは個別処理され、異なる値グループが統合中に混ざらない
  • すべての決定論的キーの値が一致した場合のみ同一グループとして扱われる
3️⃣ 既存の LLM 推論型メタデータとの共存
  • 同一リソース上で STRICTLY_CONSISTENT キーと LLM_INFERRED キーを併用可能
  • 組織分類子は決定論的に、感情・トピックなどは LLM 推論で扱う使い分けが可能
  • 部門単位検索、コンプライアンス境界、マルチテナントのサブフィルタリングに最適

🛠️ 設定方法

前提条件

  • Amazon Bedrock AgentCore へのアクセス権限を持つ AWS アカウント
  • 決定論的キーが STRING 型でメモリの indexedKeys に宣言されていること
  • 対象ストラテジーが semantic、user preference、episodic のいずれかであること
1
インデックスキーとメタデータスキーマを持つメモリを作成

indexedKeys に決定論的キーを STRING 型で宣言。STRICTLY_CONSISTENT キーはインデックスキーに含まれる必要があります。

Bashcreate-memory
aws bedrock-agentcore-control create-memory \
  --name "SupportMemory" \
  --event-expiry-duration 30 \
  --indexed-keys '[
    {"key": "department",       "type": "STRING"},
    {"key": "compliance_level", "type": "STRING"}
  ]' \
  --memory-strategies '[ ... semanticMemoryStrategy with metadataSchema ... ]'
2
メタデータを付与してイベントを送信

付与した department などの決定論的キーの値はそのままレコードへ反映され、同じ値を持つイベント同士が同一グループとして抽出・統合されます。

Pythoncreate_event
agentcore_client.create_event(
    memoryId="mem-support-abc123",
    actorId="customer-123",
    sessionId="session-escalation-001",
    payload=[{"conversational": {"role": "USER",
        "content": {"text": "請求書に重複請求があり、デプロイが止まっています。"}}}],
    metadata={
        "department": {"stringValue": "billing"},
        "priority": {"stringValue": "high"}
    }
)
3
メタデータフィルタで検索

決定論的キーは正確な値が保証されるため、department=billing のフィルタで意図したレコードのみを確実に取得できます。

Bashretrieve-memory-records
aws bedrock-agentcore retrieve-memory-records \
  --memory-id "<memory-id>" \
  --namespace "support/customer-123" \
  --search-criteria '{
    "searchQuery": "billing issues",
    "topK": 10,
    "metadataFilters": [
      {"left": {"metadataKey": "department"}, "operator": "EQUALS_TO",
       "right": {"metadataValue": {"stringValue": "billing"}}}
    ]
  }'

⚠️ デメリット・考慮すべき点

制限事項

✗1 ストラテジーあたりの STRICTLY_CONSISTENT キーは最大 3 つまで
✗キーの型は STRING のみ (STRINGLIST や NUMBER は不可)
✗summary ストラテジーでは利用できない
✗STRICTLY_CONSISTENT キーには extractionConfig を設定できない
✗各キーはメモリの 10 個あるインデックスキー枠を 1 つ消費し、追加後は削除できない

考慮すべき点

⚠️STRICTLY_CONSISTENT キーの設定変更はグループ化を変える。旧設定のレコードは新設定から分離されるため、イベント取り込み前に設計を計画する必要がある
⚠️イベントに決定論的キーの値が含まれない場合、そのキーはグループ化から除外され結果レコードにも記録されない
⚠️Batch API (BatchCreateMemoryRecords / BatchUpdateMemoryRecords) は抽出をバイパスするため効果が及ばない

🎯 ユースケース

① コンプライアンス境界の分離
シナリオ: 医療系エージェントで HIPAA 規制対象と標準の会話を同一メモリで扱いつつ明確に分離したい
実装: compliance_level を STRICTLY_CONSISTENT にし、イベントごとに hipaa / standard を付与
✅ hipaa のレコードが standard と統合中に混ざらず、規制境界を確実に維持
② 部門単位のルーティング
シナリオ: カスタマーサポートで部門ごとに記憶を分離し、クロスコンタミネーションなく部門スコープ検索を実現したい
実装: department を STRICTLY_CONSISTENT にし、billing / engineering を正確に付与
✅ department=billing でフィルタすると、エンジニアリング部門と混ざらず請求関連の事実のみ取得
③ マルチテナントのサブフィルタリング
シナリオ: SaaS 型エージェントで、ネームスペース分離に加えテナント階層などの属性を正確に保持したい
実装: tenant_tier を STRICTLY_CONSISTENT にし、アプリが把握している値をそのまま付与
✅ テナント固有の属性が LLM 推論のばらつきなく保持され、信頼性の高いサブフィルタリングが可能

📝 まとめ

今回のアップデートは、AgentCore Memory において組織分類子などアプリケーションが既に把握している値を、LLM 推論のばらつきなく正確に長期記憶レコードへ反映できるようにする重要な機能です。

コンプライアンス境界やマルチテナント分離が求められるエージェントを構築する場合は、決定論的キーの設計をイベント取り込み前に計画したうえで STRICTLY_CONSISTENT の活用を検討することを推奨します。
