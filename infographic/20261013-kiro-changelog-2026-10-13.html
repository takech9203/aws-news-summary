Kiro IDE 1.3.0 CLI 2.31.0

🛡️ ローカルコマンドサンドボックスとローカル自律モード

📅 リリース日: 2026 年 10 月 13 日 | Kiro (AWS が提供する AI 搭載 IDE / CLI)

📋 概要

Kiro IDE 1.3.0 と Kiro CLI 2.31.0 が同日リリースされ、両製品でローカルコマンドサンドボックスが利用可能になりました。エージェントが実行するシェルコマンドとその子プロセスが OS レベルのサンドボックス内に隔離され、ネットワークアクセスは「ブロック」「開発ホストのみ」「オープン」の 3 段階から選択できます。ローカルの stdio MCP サーバーも同じサンドボックス内で実行できます。

CLI 2.31.0 では、ローカル自律モードがすべての V3 ユーザーに提供されました。/autonomous on を実行すると、Kiro は Default エージェントに切り替わり、先にサンドボックスを有効化したうえで、シェルコマンドごとの承認なしにタスクを進めます。

IDE 1.3.0 ではこのほか、チャットからの /workflow-run による保存済み Workflow 起動、エディタタブのライブセッションステータス、モデルフォールバック通知が追加されました。IDE / CLI 共通で MCP ツール定義のオンデマンドロードが導入され、CLI では KIRO_HOME による V3 設定の一元管理も拡張されています。

❌ アップデート前の課題

  • シェルコマンドの実行範囲を OS レベルで制限する仕組みがなかった
  • CLI の自律的なタスク遂行でもコマンドごとの承認が必要で、長時間タスクでは手間がかかった
  • 保存済み Workflow は Workflows ビューを開かないと起動できなかった
  • タブを開かないと Kiro が作業中か入力待ちかわからなかった
  • モデルフォールバック時に、継続モデル名や適用範囲がわからなかった
  • MCP ツール定義がすべて事前ロードされ、モデルコンテキストを圧迫していた
  • CLI の V3 設定の保存先を切り替えられず、プロファイルを分離しにくかった

✅ アップデート後の改善

  • IDE / CLI の両方で、シェルコマンドと子プロセスを OS サンドボックスに閉じ込め、ネットワークを 3 段階で制御可能に
  • ローカル stdio MCP サーバーも同じサンドボックス内で実行可能に
  • /autonomous on で承認なしのタスク遂行が可能に (サンドボックスが先に有効化)
  • チャットの /workflow-run で保存済み Workflow を起動可能に
  • タブに「作業中」「入力待ち」のライブステータスを表示
  • フォールバック時にモデル名と適用範囲をトランスクリプトに明示
  • MCP ツール定義のオンデマンドロードでコンテキストに余裕
  • KIRO_HOME でプロファイルを分離可能に

ローカルコマンドサンドボックスの構成です。エージェント本体、組み込みファイルツール、リモート MCP サーバーはサンドボックスの外側に留まり、シェルコマンドとその子プロセス、およびローカル stdio MCP サーバーがサンドボックス内で実行されます。ネットワークアクセスは 3 段階のポリシーで制御されます。

🔄 ローカル自律モードの流れ (CLI V3)

sequenceDiagram
    participant U as 👤 ユーザー
    participant K as 🤖 Kiro CLI V3
    participant S as 📦 サンドボックス

    U->>K: /autonomous on を実行
    K->>K: Default エージェントに切り替え
    K->>S: ローカルコマンドサンドボックスを有効化
    U->>K: タスクを依頼
    loop タスク完了まで
        K->>S: シェルコマンドを承認なしで実行
        S-->>K: 実行結果
    end
    K-->>U: タスク結果を報告

/autonomous on を実行すると、Kiro は Default エージェントへの切り替えとサンドボックスの有効化を先に行い、その後はシェルコマンドごとの承認なしでタスクを進めます。

⚡ 主要機能

📦 ローカルコマンドサンドボックス (IDE 1.3.0 / CLI 2.31.0)
  • エージェントが実行するシェルコマンドと子プロセスを OS サンドボックス内に配置し、アクセス可能な範囲を制限
  • アウトバウンドのネットワークアクセスは「ブロック」「一般的な開発ホストのみ」「オープン」の 3 段階から選択
  • ローカルの stdio MCP サーバーも同じサンドボックス内で実行可能
  • エージェント本体、組み込みファイルツール、リモート MCP サーバーは対象外。権限ルールによる承認制御は引き続き有効
  • IDE はステータスバーの「Command sandbox」から設定、CLI は /sandbox コマンドで有効化
  • リスクを低減するが完全な隔離は保証しないため、提案コマンドのレビューは引き続き必要
🤖 ローカル自律モード (CLI 2.31.0、V3 全ユーザーに提供)
  • ローカルの V3 セッションで /autonomous on を実行すると、シェルコマンドごとの承認なしで Kiro がタスクを進める
  • 実行時には Default エージェントに切り替わり、ローカルコマンドサンドボックスを先に有効化
▶️ チャットからの保存済み Workflow 起動 (IDE 1.3.0)
  • チャットで /workflow-run と入力し、レシピを選択して入力を完了すると Workflow の実行を開始できる
  • 実行開始と同時に Kiro が Workflows ビューを新しい実行の画面で開く
💡 エディタタブのライブセッションステータス (IDE 1.3.0)
  • チャットと Workflow ステップのタブに、Kiro が作業中か入力待ちかのステータスを表示
  • セッションがアイドルになると通常のアイコン表示に戻る
🔁 モデルフォールバック通知 (IDE 1.3.0)
  • モデルが拒否した場合や利用できない場合に、応答を継続するモデル名と適用範囲 (1 ターンのみか会話の残り全体か) をトランスクリプトに表示
🧰 MCP ツールのオンデマンドロード (IDE 1.3.0 / CLI 2.31.0 V3)
  • MCP ツール定義を必要なときにのみロードし、モデルコンテキストをより多く本来の作業に使えるようにする
🗂️ KIRO_HOME による V3 設定の一元管理 (CLI 2.31.0)
  • KIRO_HOME に絶対パスを設定すると、V3 のグローバル設定、サインイン、セッション、エージェント状態がその配下に保存される
  • 仕事用と個人用など、複数の Kiro プロファイルを分離して管理可能
  • 既存の MCP サインインは初回に 1 度だけコピーされる
  • 相対パス、ファイルシステムルート、ホームディレクトリまたはその親の場合は ~/.kiro にフォールバック (修正)
🖥️ ヘッドレス実行でのサンドボックス設定の適用 (CLI 2.31.0)
  • enabled: true を含むグローバルまたはプロジェクトの sandbox.json が V3 ヘッドレス実行にも適用される
  • 保護なしで続行する代わりに実行を停止させたい場合は --sandbox フラグを追加

🛠️ 設定方法

前提条件

✓Kiro IDE 1.3.0 以降、または Kiro CLI 2.31.0 以降にアップデートされていること
✓CLI の場合、ローカルの V3 セッションを使用していること (サンドボックスと自律モードは V3 機能)

手順

1
IDE でローカルコマンドサンドボックスを有効化
操作
ステータスバーの「Command sandbox」を選択 → 設定画面でサンドボックスを有効化

IDE のステータスバーから設定を開き、ネットワークアクセスのポリシー (ブロック / 開発ホストのみ / オープン) を選択してサンドボックスを有効化します。設定画面でサンドボックスがアクティブかどうかも確認できます。

2
CLI でローカルコマンドサンドボックスを有効化
Bash
/sandbox

ローカルの V3 セッションで /sandbox を実行すると、エージェントのシェルコマンドと子プロセスが OS サンドボックス内に配置されます。ネットワークアクセスの範囲も選択できます。

3
CLI でローカル自律モードを開始
Bash
/autonomous on

ローカルの V3 セッションで /autonomous on を実行すると、Kiro が Default エージェントに切り替わり、ローカルコマンドサンドボックスを有効化したうえで、シェルコマンドごとの承認なしにタスクを進めます。

4
IDE のチャットから保存済み Workflow を起動
操作
チャットで /workflow-run と入力 → レシピを選択 → 入力を完了して実行を開始

チャットから保存済み Workflow のレシピを選択して実行を開始すると、Kiro が Workflows ビューを新しい実行の画面で開きます。

5
CLI のプロファイルを分離する場合
Bash
export KIRO_HOME=/path/to/kiro-work-profile

KIRO_HOME に絶対パスを設定すると、V3 のグローバル設定、サインイン、セッション、エージェント状態がその配下に保存され、仕事用と個人用などのプロファイルを分離できます。既存の MCP サインインは初回に 1 度だけコピーされます。

🎯 メリット

💼 ビジネス面

  • セキュリティリスクの低減: コマンドの影響範囲を OS レベルで制限でき、AI エージェント導入時の組織的なリスク評価がしやすくなる
  • 生産性の向上: 自律モードで承認が不要になり、長時間タスクでも開発者が張り付く必要がない。サンドボックスが先に有効化されるため安全性と効率を両立
  • ガバナンスの強化: ヘッドレス実行 (CI/CD など) にも sandbox.json で適用でき、--sandbox フラグで保護なしの実行を停止させる運用も可能

⚙️ 技術面

  • 多層防御: 権限ルールによる承認制御に加えて、OS サンドボックスとネットワークポリシーという実行時の制限レイヤーが追加
  • コンテキスト効率の向上: MCP ツール定義のオンデマンドロードにより、多数の MCP サーバー登録時もコンテキストを本来の作業に使える
  • 環境分離: KIRO_HOME による一元管理で、複数プロファイルの切り替えや CI 環境での独立した設定管理が容易に
  • 可視性の向上: ライブステータスとフォールバック通知で、セッション状態と応答モデルを正確に把握できる

⚠️ デメリット・制約事項

制限事項

✗サンドボックスはリスクを低減するが、完全な隔離を保証するものではない。提案されたコマンドのレビューは引き続き必要
✗エージェント本体、組み込みファイルツール、リモート MCP サーバーはサンドボックスの対象外
✗ローカル自律モードとサンドボックスの /sandbox コマンドは CLI の V3 セッションが対象
✗KIRO_HOME は絶対パスで指定する必要がある。相対パス、ファイルシステムルート、ホームディレクトリまたはその親を指定した場合は ~/.kiro にフォールバック

考慮すべき点

⚠ネットワークポリシーを「ブロック」にすると、パッケージのインストールなど外部アクセスを必要とするコマンドが失敗する可能性があるため、ワークフローに応じたポリシー選択が必要
⚠自律モードではコマンドごとの承認がなくなるため、作業対象のリポジトリやタスクの性質を考慮して利用を判断することを推奨
⚠ヘッドレス実行でサンドボックスを必須にしたい場合は、sandbox.json の設定に加えて --sandbox フラグの付与が必要

💡 ユースケース

🔍 ユースケース 1: 信頼度の低いコードベースでの安全なエージェント利用

シナリオ: 外部から取得した OSS リポジトリの調査やビルドをエージェントに任せたいが、未知のスクリプトが実行される可能性があり、ホスト環境への影響を最小化したい。

Bash実装例
# CLI V3 セッションでサンドボックスを有効化し、ネットワークを開発ホストのみに制限
/sandbox

効果: シェルコマンドと子プロセスがサンドボックス内に閉じ込められ、ネットワークアクセスも制限されるため、意図しない外部送信やホスト環境の改変リスクを低減しながらエージェントを活用できる。

⏱️ ユースケース 2: 長時間タスクの自律実行

シナリオ: テストスイート全体の修復やリファクタリングなど、多数のコマンド実行を伴うタスクをエージェントに任せたいが、コマンドごとの承認で作業が中断されるのを避けたい。

Bash実装例
# ローカル V3 セッションで自律モードを有効化
/autonomous on
# タスクを依頼
"テストスイートを実行し、失敗しているテストをすべて修正してください"

効果: サンドボックスが先に有効化されたうえで、承認なしにタスクが進むため、安全性を確保しながら開発者は別の作業に集中できる。

▶️ ユースケース 3: チャットからの定型 Workflow の即時実行

シナリオ: コードレビューやリリース準備などの定型手順を Workflow レシピとして保存しており、チャットでの作業中に素早く起動したい。

操作実装例
チャットで /workflow-run と入力 → レシピを選択 → 必要な入力を完了して実行開始

効果: Workflows ビューに移動することなくチャットから直接 Workflow を起動でき、実行状況はエディタタブのライブステータスで把握できるため、定型作業の着手から完了確認までがスムーズになる。

👥 ユースケース 4: 仕事用と個人用の CLI プロファイル分離

シナリオ: 同じマシンで業務プロジェクトと個人プロジェクトの両方に Kiro CLI を使っており、サインイン情報やエージェント状態を分離したい。

Bash実装例
# 業務用プロファイル
export KIRO_HOME=/home/user/kiro-profiles/work
kiro-cli

# 個人用プロファイル
export KIRO_HOME=/home/user/kiro-profiles/personal
kiro-cli

効果: V3 のグローバル設定、サインイン、セッション、エージェント状態がプロファイルごとに分離され、環境の切り替えによる設定の混在を防げる。

📝 まとめ

Kiro IDE 1.3.0 と CLI 2.31.0 は、エージェント実行コマンドの OS レベルの隔離という安全性の強化と、自律モードによる承認レスのタスク遂行という効率化を同時に実現するリリースです。権限ルールに加えてサンドボックスとネットワークポリシーの多層防御が利用できるため、AI エージェントを日常の開発ワークフローへ組み込む際のリスク管理が大きく前進します。

まずは最新バージョンへ更新し、IDE のステータスバーまたは CLI の /sandbox からサンドボックスを有効化したうえで、長時間タスクでの /autonomous on の活用を検討することを推奨します。
