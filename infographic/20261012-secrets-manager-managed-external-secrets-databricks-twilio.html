📅 2026 年 10 月 12 日リリース | Managed external secrets support for Databricks and Twilio

📝 概要

AWS Secrets Manager のマネージド外部シークレット機能が、新たに Databricks と Twilio に対応。カスタムローテーション Lambda 関数を作成・保守することなく、 コンソールまたは API からサードパーティー認証情報を自動ローテーションできます。

❌ Before: アップデート前の課題
  • サードパーティー認証情報のローテーションには、パートナーごとに固有のカスタム Lambda 関数の開発・保守が必要
  • 設定が難しく、更新後の認証情報の安全な配布も困難で、長期有効な認証情報が放置されがち
  • パートナーごとに異なる API 仕様に合わせた実装と継続的なメンテナンスが運用負荷に
➜
✅ After: アップデート後の改善
  • Databricks の PAT / OAuth クライアントシークレット、Twilio の API キー / Auth Token を Lambda なしで自動ローテーション
  • 置き換え後の PAT は元のトークンのスコープを維持し、最小権限の原則を保てる
  • GetSecretValue で常に最新の認証情報を取得でき、コード変更・配布作業が不要

💡 Secrets Manager がスケジュールに従って Databricks / Twilio の認証情報を直接ローテーションし、アプリケーションは GetSecretValue を通じて常に最新の認証情報を取得します。アカウント内に Lambda 関数はデプロイされません。

⚡ 主要機能

🧱 1. Databricks 認証情報の自動ローテーション
  • ジョブや CI/CD パイプラインが使用するパーソナルアクセストークン PAT をローテーション可能
  • 自動化ワークフローが使用するサービスプリンシパルの OAuth クライアントシークレットもローテーション可能
  • 置き換え後の PAT は元のトークンのスコープを維持し、権限が拡大することはない
📞 2. Twilio 認証情報の自動ローテーション
  • メッセージ送信や発信に使用する API キーと Auth Token をローテーション可能
  • シークレットタイプとして TwilioApiKey、TwilioAuthToken、TwilioMainApiKey が定義
🚫 3. Lambda 不要のマネージドローテーション
  • カスタムローテーション Lambda の作成・保守が不要で、アカウント内に Lambda はデプロイされない
  • コンソールでのシークレット作成時にはローテーションがデフォルトで有効化
  • すべてのローテーション操作やシークレット値の更新は AWS CloudTrail に記録され、完全な監査性を確保
🔄 4. アプリケーション側の変更不要
  • Secrets Manager は常に現在有効な認証情報を返すため、コード変更なしでローテーション後の値を利用可能
  • 細かな権限管理、可観測性、ガバナンス、ディザスタリカバリなど Secrets Manager の全機能をそのまま利用可能

🛠️ 設定方法

✅ 前提条件

✓Databricks または Twilio のアカウントと、ローテーション対象の認証情報 (PAT、OAuth クライアントシークレット、API キー、Auth Token)
✓マネージド外部シークレットがサポートされているリージョンの AWS Secrets Manager
✓Secrets Manager がシークレットのライフサイクルを管理するための IAM ロール (コンソールから自動作成も可能)

📌 手順

1
マネージド外部シークレットの作成

パートナーが定義する形式に従い、認証情報をマネージド外部シークレットとして保存。コンソールではシークレットタイプ (例: DatabricksPAT、TwilioApiKey) を選択し、必要なフィールドを入力。コンソールから作成した場合、自動ローテーションはデフォルトで有効になります。

2
ローテーションの設定 (コンソール)
  1. Secrets Manager コンソールで対象のマネージド外部シークレットを選択
  2. [設定] タブの [ローテーション設定] で [ローテーションを編集] を選択
  3. 自動ローテーションを有効化し、パートナーが要求するローテーションメタデータを入力
  4. ローテーション用の IAM ロールを新規作成または選択
  5. ローテーションスケジュール (例: 30 日ごと) を設定して保存
3
ローテーションの設定 (CLI)
Bash rotate-secret でマネージドローテーションを有効化 
aws secretsmanager rotate-secret \
  --secret-id SampleSecret \
  --external-secret-rotation-role-arn arn:aws:iam::123412341234:role/xyz \
  --rotation-rules AutomaticallyAfterDays=30 \
  --external-secret-rotation-metadata '[{"Key":"example-key","Value":"example-value"}]'

メタデータの必須フィールドはパートナーごとに異なるため、各パートナーのドキュメントに従って設定します。

4
アプリケーションからの利用
Bash 常に最新の認証情報を取得 
aws secretsmanager get-secret-value --secret-id SampleSecret

ローテーション後も同じ呼び出しで新しい値が返されるため、アプリケーション側の変更は不要です。

⚖️ メリットと制約事項

💼 ビジネス面のメリット

✓セキュリティ態勢の強化: 放置されがちだった長期有効な認証情報を定期的に自動ローテーションし、漏えいリスクを低減
✓運用コストの削減: カスタム Lambda の開発・保守が不要になり、エンジニアリングリソースを本来の業務に集中
✓コンプライアンス対応: すべてのローテーション操作が CloudTrail に記録され、監査要件への対応が容易

🔧 技術面のメリット

✓Lambda 不要: ランタイム更新や障害対応が不要
✓スコープの維持: Databricks PAT は元のスコープを維持し、最小権限の原則を保てる
✓アプリケーション変更不要: コード変更や再デプロイが不要

⛔ 制限事項

✗対応する認証情報の種類はパートナーごとに定義されたシークレットタイプに限定
✗シークレット値とメタデータは各パートナーが定義する所定の形式で保存する必要がある
✗マネージド外部シークレットがサポートされているリージョンでのみ利用可能

⚠️ 考慮すべき点

⚠パートナーにスコープされた適切な権限を持つ IAM ロールを Secrets Manager に付与する必要がある
⚠認証情報をキャッシュしているアプリケーションは、ローテーション間隔に応じた TTL 設定を考慮
⚠既存のカスタム Lambda ローテーションからの移行時は、シークレット形式を所定のマネージド外部シークレット形式に合わせる必要がある

🎯 ユースケース

🧱 ユースケース 1: Databricks ジョブ / CI/CD パイプラインの PAT 管理

シナリオ: データエンジニアリングチームが Databricks のジョブ実行や CI/CD パイプラインに PAT を使用しており、トークンが長期間ローテーションされないままになっている。

Bash DatabricksPAT タイプのシークレットにローテーションを設定 
aws secretsmanager rotate-secret \
  --secret-id prod/databricks/ci-cd-pat \
  --external-secret-rotation-role-arn arn:aws:iam::123412341234:role/SecretsManagerDatabricksRotation \
  --rotation-rules AutomaticallyAfterDays=30

効果: PAT が 30 日ごとに自動ローテーションされ、置き換え後も元のスコープが維持されるため、最小権限を保ちながら漏えいリスクを低減できる。

📞 ユースケース 2: Twilio を利用する通知基盤の Auth Token 保護

シナリオ: カスタマーサポート基盤が SMS 通知や音声通話に Twilio を利用しており、Auth Token の手動ローテーションが運用負荷となっている。

Bash アプリケーションは常に最新のトークンを取得 
aws secretsmanager get-secret-value --secret-id prod/twilio/auth-token

効果: Auth Token が自動ローテーションされ、アプリケーションはコード変更なしで常に最新の認証情報を利用できるため、通知基盤を停止せずにセキュリティを強化できる。

🔁 ユースケース 3: カスタムローテーション Lambda からの移行

シナリオ: 複数のサードパーティー認証情報に対して個別のローテーション Lambda を運用しており、ランタイム更新やエラー対応の保守コストが増大している。

💰 料金と利用可能リージョン

💵 料金

マネージド外部シークレットには Secrets Manager の標準料金が適用されます。シークレット 1 件あたりの月額料金と API コール数に応じた料金が発生します。マネージドローテーションでは Lambda 関数をデプロイしないため、カスタムローテーションで発生していた Lambda の実行料金は不要です。

最新の料金は Secrets Manager 料金ページを参照してください。

🌍 利用可能リージョン

AWS Secrets Manager のマネージド外部シークレットがサポートされているすべての AWS リージョンで、Databricks および Twilio のマネージド外部シークレットを利用できます。

🔗 関連サービス・機能

⚡ AWS Lambda

従来のカスタムローテーションで必要だった実行基盤。マネージド外部シークレットでは不要になる

📜 AWS CloudTrail

すべてのローテーション操作、シークレット値の更新、管理操作を記録し、監査性を提供

🛡️ AWS IAM

ローテーション用ロールにより、Secrets Manager がパートナーのシークレットライフサイクルを管理する権限を制御

🔑 AWS KMS

Secrets Manager に保存されるシークレット値の暗号化に使用

💡 まとめ

AWS Secrets Manager のマネージド外部シークレットが Databricks と Twilio に対応し、 カスタム Lambda なしでサードパーティー認証情報を自動ローテーションできる対象が 14 パートナーに拡大しました。 Databricks の PAT や Twilio の Auth Token を手動管理またはカスタム Lambda で運用している場合は、 マネージド外部シークレットへの移行を検討することで、セキュリティ強化と運用負荷の削減を同時に実現できます。
