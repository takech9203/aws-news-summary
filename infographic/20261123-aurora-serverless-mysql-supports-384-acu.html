Amazon Aurora (MySQL 互換エディション)

🗄️ Aurora Serverless for MySQL が最大 384 ACU をサポート

📅 リリース日: 2026 年 11 月 23 日 | 機能: Aurora Serverless の最大キャパシティ拡張

📋 概要

Amazon Aurora MySQL 互換エディションの Aurora Serverless が、最大 384 ACU までのスケーリングをサポートしました。従来の最大値 256 ACU から 50% の引き上げとなり、1 つのデータベースインスタンスで最大 768 GiB のメモリを利用できます。

Aurora Serverless は需要に応じて自動的にスケーリングし、処理完了後はゼロまでスケールダウンするため、消費したキャパシティに対してのみ課金されます。AWS は、アクティビティの急増・長いアイドル時間・予測不能なトラフィックパターンを特徴とするエージェント型 AI ワークロードを主な対象として挙げています。

❌ アップデート前の課題
  • 最大キャパシティが 256 ACU (約 512 GiB メモリ) に制限
  • 256 ACU を超えるピークにはプロビジョンドインスタンスへの移行を検討する必要
  • 大規模メモリが必要なワークロードで、自動スケーリングやスケール to ゼロの利点を享受しにくい
✅ アップデート後の改善
  • 最大 384 ACU (約 768 GiB メモリ) に拡張され、より大規模なワークロードをサーバーレスで実行可能
  • Platform Version 4 上の既存クラスターは設定変更のみでダウンタイムなしで利用可能
  • バーストの大きいエージェント型 AI ワークロードでも、使用した分だけの課金でピーク需要に対応

Aurora Serverless はワークロードの需要に応じて 0 ACU から最大 384 ACU まで自動的にスケーリングし、消費したキャパシティに対してのみ課金されます。

⚡ 主要機能

🚀 最大キャパシティの 384 ACU への拡張

  • 従来の最大値 256 ACU から 50% の引き上げ
  • 各 ACU は約 2 GiB のメモリと、対応する CPU・ネットワークリソースを提供
  • 最大構成で約 768 GiB のメモリを利用可能

💤 スケール to ゼロによるコスト最適化

  • ワークロードの完了後、自動的にキャパシティをゼロまでスケールダウン
  • 消費したキャパシティに対してのみ課金
  • バーストが大きく、アイドル時間が長い、予測不能なトラフィックパターンのワークロードに適合

🔄 ダウンタイムなしでの適用

  • Platform Version 4 上の既存クラスターは、最大キャパシティ設定の変更だけで利用可能
  • 必要に応じてエンジンバージョンを変更
  • 旧プラットフォームのクラスターは、保留中のメンテナンスアクションから Platform Version 4 へアップグレード

🔌 API 変更履歴

本アップデートに直接関連する API 変更は、発表時点の AWS API Changes (直近 7 日間) では確認されていません。最大キャパシティは既存の ServerlessV2ScalingConfiguration の設定値として指定します。

⚙️ 設定方法

✅ 前提条件

✓Aurora MySQL バージョン 3.14 または 8.4.10 を使用していること
✓クラスターが Platform Version 4 上で稼働していること (旧プラットフォームの場合はアップグレードが必要)
✓クラスターを変更できる IAM 権限があること
1新規クラスターで 384 ACU を指定する場合
Bash AWS CLI - クラスター作成 
aws rds create-db-cluster \
  --db-cluster-identifier my-serverless-cluster \
  --engine aurora-mysql \
  --engine-version 8.0.mysql_aurora.3.14.0 \
  --serverless-v2-scaling-configuration MinCapacity=0,MaxCapacity=384 \
  --master-username admin \
  --manage-master-user-password

サポート対象のエンジンバージョンを指定して Aurora クラスターを作成し、Serverless のスケーリング設定で最大キャパシティを 384 ACU に設定します。

2既存クラスターの最大キャパシティを変更する場合
Bash AWS CLI - クラスター変更 (ダウンタイムなし) 
aws rds modify-db-cluster \
  --db-cluster-identifier my-serverless-cluster \
  --serverless-v2-scaling-configuration MinCapacity=0,MaxCapacity=384 \
  --apply-immediately

Platform Version 4 上の既存クラスターの最大キャパシティ設定を 384 ACU に変更します。この変更にダウンタイムは発生しません。

3旧プラットフォームのクラスターをアップグレードする場合
Bash AWS CLI - メンテナンスアクション適用 
# 保留中のメンテナンスアクションを確認
aws rds describe-pending-maintenance-actions

# メンテナンスアクションを即時適用
aws rds apply-pending-maintenance-action \
  --resource-identifier <クラスターの ARN> \
  --apply-action system-update \
  --opt-in-type immediate

旧プラットフォームで稼働しているクラスターに対して、保留中のメンテナンスアクションを確認し、Platform Version 4 へのアップグレードを適用します。

⚖️ メリット・制約事項

💼 ビジネス面のメリット

✓コスト効率の向上: プロビジョンドインスタンスの常時稼働が不要になり、消費分のみの課金で最適化
✓AI ワークロードへの対応: バーストが大きく予測不能なワークロードをキャパシティプランニングなしで運用
✓移行の手間を削減: ACU 上限を理由にプロビジョンド構成へ移行していたワークロードをサーバーレスのまま維持

🛠️ 技術面のメリット

✓スケーリング上限の拡大: 最大 384 ACU (約 768 GiB メモリ) まで自動スケーリング
✓ダウンタイムなしの適用: Platform Version 4 上の既存クラスターは設定変更のみ
✓運用の簡素化: スケール to ゼロとの組み合わせでアイドル時のリソース管理が不要

🚧 制限事項

✗Aurora MySQL バージョン 3.14 および 8.4.10 のみでサポート
✗Platform Version 4 が必須。旧プラットフォームのクラスターはアップグレードが必要
✗本発表は MySQL 互換エディションが対象 (PostgreSQL 互換エディションの上限は別途確認が必要)

💡 考慮すべき点

⚠最大キャパシティを引き上げるとピーク時の時間あたりコストも増加するため、ワークロードに応じた上限設定が必要
⚠リージョンごとの利用可否と料金は Amazon Aurora 料金ページでの確認が必要
⚠旧プラットフォームからのアップグレードはメンテナンスアクションとして計画的に実施

🎯 ユースケース

🧠 ユースケース 1: エージェント型 AI アプリケーションのバックエンド

シナリオ: AI エージェントが必要に応じてデータベースへ大量のクエリを発行するアプリケーション。アクティビティのバースト、長いアイドル時間、予測不能なトラフィックが特徴。

Bash実装例
aws rds modify-db-cluster \
  --db-cluster-identifier ai-agent-backend \
  --serverless-v2-scaling-configuration MinCapacity=0,MaxCapacity=384

効果アイドル時は 0 ACU まで縮小してコストを抑えつつ、バースト時は最大 384 ACU まで自動拡張して応答性能を維持できる。

📊 ユースケース 2: 月次バッチ処理や期末処理などの周期的な重負荷

シナリオ: 通常時は小規模な負荷だが、月末や期末の集計処理で大量のメモリと CPU を必要とするワークロード。

Bash実装例
aws rds modify-db-cluster \
  --db-cluster-identifier monthly-batch-db \
  --serverless-v2-scaling-configuration MinCapacity=1,MaxCapacity=384

効果ピーク処理のためにプロビジョンドの大型インスタンスを常時確保する必要がなくなり、処理時間の短縮とコスト削減を両立できる。

🔀 ユースケース 3: プロビジョンド構成からの統合・移行

シナリオ: 従来は 256 ACU の上限を超えるピークに備えてプロビジョンドインスタンスを使用していたが、平均稼働率が低くコスト効率が悪い。

Bash実装例
aws rds create-db-cluster \
  --db-cluster-identifier migrated-serverless \
  --engine aurora-mysql \
  --engine-version 8.0.mysql_aurora.3.14.0 \
  --serverless-v2-scaling-configuration MinCapacity=0.5,MaxCapacity=384

効果拡大された上限によりピーク需要をサーバーレスでカバーできるようになり、平均稼働率の低いワークロードのコストを削減できる。

💰 料金・利用可能リージョン

💵 料金

消費した ACU 時間 (ACU-hour) に基づく秒単位の課金です。ゼロまでスケールダウンしている間はコンピューティング料金が発生せず、ストレージと I/O には別途料金がかかります。最大キャパシティの引き上げ自体に追加料金はありません。

🌍 利用可能リージョン

公式発表にはリージョンの一覧が記載されていません。利用可能なリージョンは Amazon Aurora 料金ページで確認してください。

📝 まとめ

Aurora Serverless for MySQL の最大キャパシティが 384 ACU (約 768 GiB メモリ) に拡張され、これまでプロビジョンド構成が必要だった大規模なピーク需要もサーバーレスで対応できるようになりました。Platform Version 4 上の既存クラスターはダウンタイムなしで設定変更のみで利用できるため、エージェント型 AI などバーストの大きいワークロードを運用している場合は、最大キャパシティ設定の見直しを推奨します。
