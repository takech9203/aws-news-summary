🛡️ AWS WAF: CloudFront ディストリビューション向け自動 SDK 統合

📅 リリース日: 2026 年 10 月 30 日 | Automatic SDK integration for Amazon CloudFront distributions

📝 概要

AWS WAF が CloudFront ディストリビューション向けの自動 SDK 統合を発表。有効化すると、CloudFront がエッジで HTML レスポンスに AWS WAF JavaScript SDK のスクリプトタグを自動挿入します。アプリケーションコード、ビルドプロセス、デプロイの変更は一切不要です。

SDK は Bot Control (targeted)、Fraud Control ATP (アカウント乗っ取り防止)、Fraud Control ACFP (アカウント作成不正防止) が利用するクライアントサイドシグナルを収集します。これまでは保護対象のすべてのページにスクリプトタグを手動追加する必要がありました。

自動 SDK 統合を有効化した CloudFront Web ACL では、AWS WAF が許可した HTML レスポンスの head 要素直後に SDK スクリプトタグがエッジで挿入され、ブラウザがトークンを取得してクライアントサイドシグナルを送信する流れになります。

⚡ 主要機能

1️⃣ エッジでのスクリプトタグ自動挿入
  • HTTP 200 かつ Content-Type: text/html の非圧縮レスポンスの head 要素直後に挿入
  • 挿入されるタグは手動統合と同じもの。Web ACL の統合 URL (ApplicationIntegrationURL) を参照し、defer 属性付きで読み込み
  • 挿入に失敗した場合はオリジンのレスポンスがそのまま返される (フェイルオープン設計のため、レスポンスがブロックされることはない)
2️⃣ 対象となるマネージドルールグループ
  • Bot Control (AWSManagedRulesBotControlRuleSet): 検査レベルが targeted の場合のみ対象 (common は対象外)
  • Fraud Control ATP (AWSManagedRulesATPRuleSet): アカウント乗っ取り防止
  • Fraud Control ACFP (AWSManagedRulesACFPRuleSet): アカウント作成不正防止
  • アクションを Count にオーバーライドしていても対象となるため、評価段階から SDK を導入できる
3️⃣ 柔軟な有効化オプション
  • コンソールで対象ルールグループを含む新規 CloudFront Web ACL を作成する場合は、デフォルトで有効
  • API や CloudFormation などプログラムで作成する場合は、デフォルトで無効 (明示的な設定が必要)
  • 既存の Web ACL やリリース前に作成された Web ACL は変更されない (必要なときに自分で有効化)

API 設定例

Web ACL の AssociationConfig に ChallengeJavascriptSdkInjection 設定を CLOUDFRONT マップキーで追加します。設定オブジェクトは空です。

JSON AssociationConfig 設定 
"AssociationConfig": {
    "ChallengeJavascriptSdkInjection": {
        "CLOUDFRONT": {}
    }
}

無効化する場合は、この設定を含めずに UpdateWebACL を実行します (設定を省略した更新リクエストは自動 SDK 統合をオフにします)。

🛠️ 設定方法

前提条件

✓CloudFront スコープ (Global) の Web ACL を使用していること
✓Web ACL に対象ルールグループ (Bot Control targeted、ATP、ACFP のいずれか) が含まれていること
✓ページの Content Security Policy で https://*.awswaf.com を許可していること (CSP を使用している場合)

手順

1
コンソールで有効化

CloudFront Web ACL で対象のマネージドルールグループを追加または編集し、「Automatic SDK integration」セクションで「Enable automatic SDK integration」を選択します。Bot Control の場合は、検査レベルと機械学習を設定するパネルと同じ場所に設定があります。

2
CLI / API で有効化する場合
Bash UpdateWebACL で自動 SDK 統合を有効化 
aws wafv2 update-web-acl \
  --scope CLOUDFRONT \
  --region us-east-1 \
  --name my-web-acl \
  --id <web-acl-id> \
  --lock-token <lock-token> \
  --default-action Allow={} \
  --rules file://rules.json \
  --visibility-config SampledRequestsEnabled=true,CloudWatchMetricsEnabled=true,MetricName=my-web-acl \
  --association-config '{"ChallengeJavascriptSdkInjection":{"CLOUDFRONT":{}}}'

UpdateWebACL は設定全体の置き換えとなるため、既存のルールや設定も含めて指定する必要があります。

3
動作確認

プライベートブラウジングウィンドウでページを開き、ページソースにスクリプトタグが挿入されていること、ブラウザが aws-waf-token Cookie を受け取っていることを確認します。HTML をキャッシュしている場合、即時反映にはキャッシュの無効化 (Invalidation) を実行します。タグ挿入を記録するメトリクスやログフィールドは存在しないため、ブラウザでの確認が必要です。

💡 メリット

ビジネス面

✓運用負荷の削減: 多数のアプリケーションへの SDK 統合作業が不要になり、セキュリティチームが Web ACL の設定だけで保護を展開できる
✓保護漏れリスクの低減: クライアント側統合の漏れによる保護の不完全さを防ぎ、Bot Control や Fraud Control の検知精度を安定して確保できる
✓追加コストなし: 自動 SDK 統合自体に追加料金は発生しない

技術面

✓コード変更不要: アプリケーションコード、ビルドプロセス、デプロイを変更せずにクライアント側統合を実現できる
✓安全な導入: ルールグループを Count モードで評価しながら SDK を先行導入でき、挿入はフェイルオープンでレスポンスをブロックしない
✓手動統合との共存: SDK は複数回読み込まれても 1 回だけ実行されるため、既に手動統合済みのアプリケーションで有効化しても問題ない

⚠️ デメリット・制約事項

制限事項

✗CloudFront スコープの Web ACL 専用。ALB や API Gateway などのリージョナルリソースでは利用できない
✗Origin Shield を有効にしたオリジン、オリジンリクエスト / オリジンレスポンスイベントに Lambda@Edge を設定したキャッシュビヘイビア、埋め込み POP ではタグが一貫して挿入されない
✗キャッシュされない高レートのリクエスト (POST や TTL 0 のビヘイビアなど) では、タグが挿入されないレスポンスが発生する場合がある
✗'strict-dynamic' と nonce / ハッシュを使う Content Security Policy には非対応 (挿入タグに nonce が付与されずブラウザにブロックされる)
✗挿入されるのは SDK スクリプトタグのみで、CAPTCHA JavaScript API やモバイル SDK は対象外
✗SDK リクエストを独自ドメイン経由でプロキシする構成は使用されず、挿入タグは awswaf.com を直接参照する

考慮すべき点

⚠有効化すると、保護対象ディストリビューションのすべてのオブジェクト (HTML 以外も含む) をオリジンから非圧縮で取得するようになる。ビューワーへの圧縮配信を継続するには、キャッシュビヘイビアで圧縮を有効化する
⚠Range / If-Range ヘッダーが削除され、常にオブジェクト全体が HTTP 200 で返されるため、動画プレイヤーやダウンロードマネージャーなど部分取得クライアントのデータ転送量が増加する
⚠挿入後は Content-Length が更新され、ETag が弱い検証子に置き換わる。Content-MD5 などのボディ整合性ヘッダーは再計算されない
⚠キャッシュ済みの HTML は保存時点の状態で配信される。即時反映にはキャッシュ無効化が必要で、ブラウザや下流キャッシュに残る古いコピーは無効化できない
⚠SPA など、アプリケーション自身の API 呼び出しにトークンを付与する必要がある場合は、従来どおり SDK を直接統合する方が確実
⚠トークン欠落に対してアクションを取るルールを適用する前に、Count モードで結果を確認することが推奨される
⚠対象ルールグループを Web ACL から削除する (または Bot Control を common に変更する) 場合は、同じ更新で自動 SDK 統合の設定も削除しないと更新が拒否される

🎯 ユースケース

🌐 ユースケース 1: 多数の Web アプリケーションへの Bot 対策の一括展開

シナリオ: 数十の Web サイトを CloudFront で配信している企業が、Bot Control (targeted) を導入したいが、各アプリケーションチームにスクリプトタグの追加を依頼するコストが大きい。

JSON Web ACL 設定例 
{
  "Scope": "CLOUDFRONT",
  "Rules": [
    {
      "Name": "BotControl",
      "Statement": {
        "ManagedRuleGroupStatement": {
          "VendorName": "AWS",
          "Name": "AWSManagedRulesBotControlRuleSet",
          "ManagedRuleGroupConfigs": [
            { "AWSManagedRulesBotControlRuleSet": { "InspectionLevel": "TARGETED" } }
          ]
        }
      }
    }
  ],
  "AssociationConfig": {
    "ChallengeJavascriptSdkInjection": { "CLOUDFRONT": {} }
  }
}
✅ 効果: セキュリティチームが Web ACL の設定だけで全サイトにクライアント側統合を展開でき、各アプリケーションチームの作業が不要になる。
🔐 ユースケース 2: 自社管理外システムが生成するページの保護

シナリオ: SaaS やレガシーな CMS が生成するページを CloudFront で配信しており、ページテンプレートに手を加えられないため、ATP によるログインページの保護でクライアント側シグナルを活用できていなかった。

📊 ユースケース 3: 評価段階からの段階的な導入

シナリオ: ACFP の導入を検討中で、誤検知の影響を避けるため、ルールを Count モードで評価しながら SDK によるシグナル収集を先行して開始したい。

  • Web ACL に AWSManagedRulesACFPRuleSet を追加し、アクションを Count にオーバーライド
  • 自動 SDK 統合を有効化 (Count でも対象ルールグループとして認められる)
  • CloudWatch メトリクスとサンプルリクエストでトークン付きリクエストの挙動を分析
  • 問題がなければルールアクションを有効化して本番適用
✅ 効果: 本番トラフィックへの影響を抑えながら、クライアントサイドシグナルを含む完全な評価データに基づいて導入判断ができる。

💰 料金

自動 SDK 統合の利用に追加料金はかかりません。ただし、前提となる機能には通常の料金が適用されます。

項目料金
自動 SDK 統合追加料金なし
AWS WAF Web ACL / ルール / リクエスト通常の AWS WAF 料金
Bot Control (targeted) / ATP / ACFP各マネージドルールグループのサブスクリプション料金と分析対象リクエスト料金
CloudFront通常のデータ転送・リクエスト料金 (Range ヘッダー削除や非圧縮オリジン取得により転送量が増える場合がある)

詳細は AWS WAF 料金ページ を参照してください。

🌍 利用可能リージョン

CloudFront スコープ (Global) の Web ACL で利用可能です。CloudFront はグローバルサービスのため、CloudFront 用 Web ACL (us-east-1 で管理) を使用するすべてのディストリビューションが対象です。リージョナルリソース用の Web ACL では利用できません。

📌 まとめ

CloudFront 配信のアプリケーションでは、コード変更なしに AWS WAF JavaScript SDK のクライアント側統合を展開できるようになりました。Bot Control (targeted) や ATP / ACFP を利用中、または導入を検討中のチームは、まず Count モードと組み合わせて有効化し、タグ挿入と aws-waf-token Cookie の動作を確認することを推奨します。非圧縮でのオリジン取得や Range リクエストの扱いなど、配信挙動への影響があるため、「考慮すべき点」を事前に確認したうえで有効化してください。
