🧬 AWS HealthOmics

Amazon CloudWatch への
リアルタイムランメトリクス発行

📅 リリース日: 2026 年 9 月 11 日

ワークフロー実行中の CPU / GPU / メモリ / ストレージ / ネットワークの使用状況を、14 種類のメトリクスとしてほぼリアルタイムに CloudWatch へ発行。ボトルネック特定・タスク失敗の事前検知・適正サイズ化を実現します。

📌 概要

AWS HealthOmics が、ワークフロー実行中のリソース使用状況を約 30 秒間隔で Amazon CloudWatch に発行する機能を発表しました。メトリクスは OpenTelemetry (OTel) 互換のメトリクス標準で発行され、PromQL によるクエリ、ダッシュボード、アラーム、サードパーティオブザーバビリティツールとの統合が可能です。

😰 アップデート前の課題

✗実行中のリソース使用状況をリアルタイムに把握する手段がなく、ボトルネックの特定が困難だった
✗メモリやスクラッチストレージの枯渇によるタスク失敗を、事前に検知できなかった
✗リソース使用状況の詳細な調査には、サポートケースの起票が必要になる場合があった
✗実使用量と割り当てリソースの比較が難しく、適正サイズ化の判断材料が不足していた

😊 アップデート後の改善

✓実行中のランとタスクのリソース使用状況を約 30 秒間隔でほぼリアルタイムに可視化
✓CloudWatch アラームで、メモリ・ストレージ枯渇の兆候をタスク失敗前に検知
✓OpenTelemetry 標準での発行により、サードパーティツールとの統合が可能に
✓usage / limit メトリクスの比較で、コンピュートとストレージの適正サイズ化が容易に

HealthOmics のランとタスクが約 30 秒間隔でリソース使用状況メトリクスを CloudWatch に OpenTelemetry 標準で発行し、ユーザーは PromQL クエリでの分析、ダッシュボードでの可視化、アラームによる通知、サードパーティツールとの統合が可能になります。

⚡ 主要機能

📊 14 種類のリアルタイムランメトリクス
  • ラン単位: 共有ファイルシステムの使用量と容量
  • タスク単位: CPU / メモリの使用量と上限、ネットワーク I/O、ファイルシステム I/O とオペレーション数、スクラッチストレージの使用量と上限
  • GPU メトリクス: GPU 使用率、GPU メモリの使用量と上限 (アクセラレーター使用タスクのみ)
  • 多くのメトリクスは 30 秒間隔で発行され、タスクが RUNNING になってから COMPLETED になるまで発行される
📡 OpenTelemetry 互換のメトリクス標準
  • CloudWatch の OTel 互換メトリクス標準 (cloudwatch.aws/omics スコープ) で発行
  • PromQL でクエリ可能で、CloudWatch Query Studio やダッシュボード、アラームで利用できる
  • OTel 互換のサードパーティオブザーバビリティツールとも統合可能
  • ランの ARN、ワークフロー ID、ラン ID、タスク ID などの共通リソースラベルが付与される
🎯 プロアクティブな問題検出と適正サイズ化
  • 実行中に CPU / GPU ボトルネックを特定できる
  • タスクが失敗する前にメモリ不足やスクラッチストレージの枯渇を検出できる
  • usage / limit メトリクスの比較により、コンピュートとストレージの適正サイズ化が可能
🤖 HealthOmics MCP サーバーとの連携
  • HealthOmics Model Context Protocol (MCP) サーバー経由でランメトリクスを取得し、AI モデルの支援を受けながらラン失敗を調査できる
  • Kiro CLI、Claude Code などの MCP 互換エージェントクライアントから利用可能

🛠️ 設定方法

前提条件

  • ✓ AWS HealthOmics のプライベートワークフローまたは共有ワークフローを使用していること
  • ✓ ランのサービスロールに cloudwatch:PutMetricData 権限が付与されていること
  • ✓ 対応リージョンでランを実行すること
1
サービスロールに権限を追加
Bash CloudWatch へのメトリクス書き込み権限を追加 
aws iam put-role-policy \
  --role-name HealthOmicsRunRole \
  --policy-name AllowPutMetricData \
  --policy-document '{
    "Version": "2012-10-17",
    "Statement": [
      {
        "Effect": "Allow",
        "Action": "cloudwatch:PutMetricData",
        "Resource": "*"
      }
    ]
  }'

この権限があると、HealthOmics はデフォルトでランメトリクスを発行します。

2
ランを開始
Bash 権限を付与したサービスロールでランを開始 
aws omics start-run \
  --workflow-id 1122334 \
  --role-arn arn:aws:iam::123456789012:role/HealthOmicsRunRole \
  --output-uri s3://my-bucket/outputs/ \
  --name my-run

タスクが RUNNING 状態になると、約 30 秒後から最初のデータポイントが CloudWatch に発行されます。

3
CloudWatch Query Studio でメトリクスを確認

CloudWatch コンソールで [Query Studio] を選択し、クエリエディタで [PromQL] を選択します。以下のクエリは指定したランの各タスクが使用中の vCPU 数を返します。

PromQL タスクごとの vCPU 使用数を取得 
{"aws.omics.task.cpu.usage", "@resource.aws.omics.run.id"="1234567"}

結果は時系列グラフとして表示され、[Create alarm] からアラームの作成、[Add to dashboard] からダッシュボードへの追加が可能です。

💡 メリットと注意点

✅ ビジネス面のメリット

✓コスト最適化: 実使用量と割り当て量の比較で過剰なリソース割り当てを特定し、適正サイズ化できる
✓運用効率の向上: サポートケースの起票が不要になり、自己解決までの時間が短縮
✓ワークフローの信頼性向上: 枯渇をタスク失敗前に検知し、長時間ジョブのやり直しコストを削減

✅ 技術面のメリット

✓ほぼリアルタイムの可視性: 約 30 秒間隔で実行中ワークフローの状況を把握
✓OpenTelemetry 標準準拠: 既存のサードパーティオブザーバビリティスタックにそのまま統合
✓PromQL による柔軟な分析: ラン ID、タスク ID、GPU ID などのラベルでフィルタリング可能
✓AI エージェントとの連携: MCP サーバー経由で AI 支援によるラン失敗調査が可能

⚠️ 制限事項

•実行時間が 30 秒未満のタスクはメトリクスが記録されない場合がある
•ストレージタイプが DYNAMIC の場合、ファイルシステム使用量は 30 分以上遅延することがあり、30 分未満のランでは利用できない場合がある
•SHARED スクラッチストレージで一時ファイル数が非常に多い場合、使用量メトリクスが取得できないことがある
•サービスロールを所有しランを開始した AWS アカウントでのみ利用可能
•イスラエル (テルアビブ) リージョンでは利用不可

🤔 考慮すべき点

•CloudWatch へのメトリクス取り込み量に応じた料金が発生。不要な場合は権限除外でオプトアウト可能
•cloudwatch:PutMetricData 権限があるとデフォルトで発行される点に注意
•CPU / メモリのメトリクスは測定スコープの違いにより、ランマニフェストの値と異なる場合がある (ランメトリクスの方が実際の消費量に近い)
•発行は RUNNING から COMPLETED までの期間のみで、最初のデータポイントには約 30 秒の遅延がある

🎯 ユースケース

1️⃣ GPU を使用する機械学習ワークフローのボトルネック特定

シナリオ: タンパク質構造予測など GPU を使用するワークフローで、想定より処理時間が長い。GPU が有効活用されているかを実行中に確認したい。

PromQL
{"aws.omics.task.gpu.utilization", "@resource.aws.omics.run.id"="1234567"}

効果: GPU ごとの使用率をリアルタイムに確認し、GPU・データ転送・CPU 処理のどこがボトルネックかを特定。GPU 使用率が低い場合はインスタンスタイプや並列度を見直し、コストと実行時間を最適化できる。

2️⃣ メモリ枯渇によるタスク失敗の事前検知

シナリオ: 大規模なゲノムデータを扱うタスクがメモリ不足で失敗することがあり、長時間実行後の失敗によるやり直しコストが問題になっている。

PromQLQuery Studio でクエリを作成し [Create alarm] でアラームを設定
{"aws.omics.task.memory.usage", "@resource.aws.omics.run.id"="1234567"}
しきい値: aws.omics.task.memory.limit の 90% 相当の値
通知先: Amazon SNS トピック

効果: メモリ使用量が上限に近づいた時点で SNS 経由の通知を受け取り、タスク失敗前の介入や、次回ラン以降のメモリ割り当て増加などの対策を事前に講じられる。

3️⃣ 実使用量に基づくワークフローの適正サイズ化

シナリオ: ワークフロー定義の CPU / メモリ割り当てが経験則で設定されており、過剰割り当てによるコスト増が疑われる。

PromQLusage と limit を比較しダッシュボードで継続モニタリング
{"aws.omics.task.cpu.usage", "@resource.aws.omics.run.id"="1234567"}
{"aws.omics.task.cpu.limit", "@resource.aws.omics.run.id"="1234567"}

効果: タスクごとの実使用量と割り当て量の乖離を定量的に把握し、リソース指定を実態に合わせて削減。過剰割り当ての解消によりラン実行コストを削減できる。

💰 料金

AWS HealthOmics 自体にはランメトリクスの追加料金はありません。メトリクスはお客様のアカウントの Amazon CloudWatch に発行され、取り込まれたメトリクスデータ量に基づいて CloudWatch から直接課金されます。

アクティビティ課金方法
OpenTelemetry メトリクスの発行取り込みデータ量 (GB) ごと。15 か月分の保存を含み、保存やユニークなメトリクス系列数への追加課金はなし
CloudWatch コンソールでの PromQL クエリ実行 (Query Studio、ダッシュボード含む)無料
CloudWatch API での PromQL クエリ実行スキャンしたサンプル 100 万件ごと
PromQL クエリを評価するアラーム標準のアラーム料金に加えて、評価ごとにスキャンしたサンプルのクエリ料金

リージョンごとの具体的な料金は Amazon CloudWatch 料金ページ を参照してください。
