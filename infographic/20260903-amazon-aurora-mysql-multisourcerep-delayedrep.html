Amazon Aurora MySQL 📅 2026 年 9 月 3 日

🔀 マルチソースレプリケーションと
⏰ 遅延レプリケーションのサポート

複数ソースの統合と、誤操作からの迅速な復旧を Aurora MySQL のネイティブ機能で実現

📌 概要

Amazon Aurora MySQL が 2 つの新しいレプリケーション機能をサポートしました。いずれも Aurora MySQL 8.4.8 以降で利用可能です。

🔀 マルチソースレプリケーション
単一の Aurora MySQL クラスターが複数のソースデータベースから同時に binlog レプリケーションを受信。ソースには RDS for MySQL、別の Aurora MySQL クラスター、RDS 外部の MySQL を指定でき、シャードのマージや地域別・部門別データベースの集約によるレポーティング・バックアップの一元化を実現します。
⏰ 遅延レプリケーション
binlog レプリカがソースの変更を意図的に指定時間だけ遅らせて適用。誤った DROP TABLE や DELETE が実行された場合、レプリカに適用される前にレプリケーションを停止して昇格することで、フルリストアなしで迅速に復旧できます。アップグレード時のフォールバック先や過去時点のデータ確認にも活用可能です。

❌ Before: アップデート前の課題
  • 単一ソースからしか binlog レプリケーションを受信できず、複数 DB の統合には AWS DMS や ETL パイプラインが必要
  • シャード横断のレポーティングやバックアップの一元化に追加の中間システムが必要
  • 変更が即時適用されるため、誤操作や論理破損がレプリカにも即座に伝播し、復旧にはフルリストアや PITR が必要
✅ After: アップデート後の改善
  • 最大 15 チャネルを構成し、複数ソースからのデータをリアルタイムに統合
  • チャネルごとに binlog 座標 / GTID 自動ポジショニングを選択でき、チャネル単位のフィルターも設定可能
  • 意図的な適用遅延により、有害な変更の適用前にレプリケーションを停止して昇格する迅速な復旧手段を確保
  • CloudWatch メトリクス ReplicationChannelLag でソースごとの遅延を監視

マルチソースレプリケーションでは、Aurora MySQL クラスターのライターインスタンスがレプリケーションターゲットとなり、ソースごとに独立したチャネルで binlog イベントを受信します。チャネルには遅延レプリケーションを組み合わせることも可能で、統合したデータは Aurora のリードスケーリングを活用してレポーティングに利用できます。

⚙️ 主要機能

1️⃣ マルチソースレプリケーション
  • 単一の Aurora MySQL クラスターが複数の MySQL 互換ソースから同時に binlog レプリケーションを受信可能
  • ソースは RDS for MySQL / 別の Aurora MySQL クラスター / RDS 外部の MySQL に対応
  • 1 つのマルチソースレプリカに最大 15 チャネルを構成可能
  • チャネルごとに binlog ファイル位置ベースまたは GTID 自動ポジショニングを選択可能
  • レプリケーションフィルターをグローバルとチャネル単位の 2 レベルで設定可能 (チャネル単位が優先)
  • ターゲットはクラスターのライターインスタンス。ストアドプロシージャはライターで実行
2️⃣ 遅延レプリケーション
  • トランザクションの適用を指定した最小秒数だけ意図的に遅延
  • mysql.rds_set_source_delay で設定 (上限 259,200 秒 = 72 時間)。チャネル単位は mysql.rds_set_source_delay_for_channel (delay 上限 86,400 秒 = 1 日)
  • rds_start_replication_until / rds_start_replication_until_gtid と組み合わせ、有害な変更の直前までロールフォワードして昇格する DR フローを実現
  • 誤操作対策のほか、アップグレード時のフォールバック先や過去時点のデータ確認にも活用可能
3️⃣ チャネル単位の管理用ストアドプロシージャ
  • rds_set_external_source_for_channel: binlog 座標ベースでチャネルを構成
  • rds_set_external_source_with_auto_position_for_channel: GTID 自動ポジショニング + 任意の遅延で構成
  • rds_set_external_source_with_delay_for_channel: binlog 座標ベース + 遅延指定で構成
  • rds_start_replication_for_channel / rds_stop_replication_for_channel: チャネル単位の開始・停止
  • rds_start_replication_until_for_channel / rds_start_replication_until_gtid_for_channel: 指定位置・指定 GTID までのレプリケーション
  • rds_reset_external_source_for_channel: チャネルの削除 (関連リレーログも削除)
  • rds_skip_repl_error_for_channel / rds_next_source_log_for_channel: チャネル単位のエラー対処
4️⃣ チャネル単位のモニタリング
  • SHOW REPLICA STATUS FOR CHANNEL 'channel_name'\G で I/O・SQL スレッド状態、遅延秒数、エラーを確認
  • CloudWatch メトリクス ReplicationChannelLag でチャネルごとの遅延を 60 秒間隔で監視 (15 日間保持)。しきい値超過時のアラーム設定が可能

📐 リソースプランニング

レプリケーションスレッドの総数は「(replica_parallel_workers + コーディネータースレッド 1) × チャネル数」です。たとえばデフォルトの replica_parallel_workers = 4 で 10 チャネルを構成すると 50 スレッドが割り当てられます。ソースの合計スループットとチャネル数に応じて、db.r6g.2xlarge 以上などの大きめのインスタンスクラスの使用を検討してください。なお、MySQL の仕様上、チャネルごとに異なる並列ワーカー数を設定することはできません。

🛠️ 設定方法

✅ 前提条件

✓Aurora MySQL 8.4.8 以降のクラスターが稼働し、ライターインスタンスの autocommit が 1 に設定されていること
✓各ソースでバイナリログが有効化され、binlog 保持期間が適切に設定されていること
✓各ソースに REPLICATION CLIENT および REPLICATION SLAVE 権限を持つレプリケーションユーザーが作成されていること
✓Aurora ライターインスタンスから各ソースへのネットワーク接続 (セキュリティグループ、VPC ピアリング、VPN など) がソースごとに確保されていること
1
ソースの binlog 位置の確認と初期データのインポート
SQLbinlog 座標の確認
-- 各ソースで現在の binlog ファイルと位置を確認 (MySQL 8.4 以降)
SHOW BINARY LOG STATUS;
-- 結果例: mysql-bin-changelog.000045, Position: 3892
Bash初期データのコピー
# ソースのデータを Aurora MySQL クラスターへコピー
mysqldump --databases orders_db --single-transaction --compress \
  -u admin -p --host=orders-db.xxxxx.us-east-1.rds.amazonaws.com | \
  mysql --host=my-aurora-cluster.cluster-xxxxx.us-east-1.rds.amazonaws.com -u admin -p

各ソースで binlog の座標を記録し、既存データを Aurora クラスターへインポートします。大規模データベースの場合は AWS DMS やスナップショット復元の利用が推奨されています。この作業をソースごとに繰り返します。

2
レプリケーションチャネルの構成と開始
SQLチャネル構成 (binlog 座標ベース)
-- Aurora ライターインスタンスに接続し、チャネルを構成
CALL mysql.rds_set_external_source_for_channel(
  'orders-db.xxxxx.us-east-1.rds.amazonaws.com',
  3306, 'repl_user', 'password',
  'mysql-bin-changelog.000045', 3892, 0, 'orders_channel');

-- チャネルのレプリケーションを開始
CALL mysql.rds_start_replication_for_channel('orders_channel');

GTID を使用する場合は mysql.rds_set_external_source_with_auto_position_for_channel を使用します。ソースごとに一意のチャネル名を指定して繰り返します。

3
遅延レプリケーションの設定 (必要に応じて)
SQL遅延の設定
-- 単一ソースのレプリカに 1 時間 3600 秒の遅延を設定
CALL mysql.rds_stop_replication;
CALL mysql.rds_set_source_delay(3600);
CALL mysql.rds_start_replication;

-- チャネル単位で遅延を設定する場合
CALL mysql.rds_stop_replication_for_channel('orders_channel');
CALL mysql.rds_set_source_delay_for_channel(3600, 'orders_channel');
CALL mysql.rds_start_replication_for_channel('orders_channel');

遅延を設定する前にレプリケーションを停止する必要があります。再開後、ソースの変更は指定した最小秒数が経過するまでレプリカに適用されません。

4
レプリケーション状態の監視
SQL状態確認
-- すべてのチャネルの状態を確認
SHOW REPLICA STATUS\G

-- 特定チャネルの状態を確認
SHOW REPLICA STATUS FOR CHANNEL 'orders_channel'\G

Replica_IO_Running と Replica_SQL_Running が Yes であること、Seconds_Behind_Source が想定範囲内であることを確認します。あわせて CloudWatch メトリクス ReplicationChannelLag にアラームを設定し、継続的に監視することを推奨します。

💡 メリット

💼 ビジネス面

✓データ統合コストの削減: 別途 ETL ツールや中間システムを構築・運用する必要がなくなり、マネージドなレプリケーションだけでシャード統合やマルチテナント集約を実現
✓データ損失リスクの低減: 遅延レプリカにより人的ミスや論理破損からの復旧時間が大幅に短縮され、RTO の改善と事業継続性の向上につながる
✓レポーティングの一元化: 地域別・部門別に分散したデータを 1 つのクラスターに集約し、リードスケーリングを活用した横断的な分析基盤を構築

🔧 技術面

✓柔軟なトポロジ: 最大 15 チャネルを独立して構成・開始・停止でき、binlog 座標と GTID をチャネル単位で使い分け可能
✓きめ細かなフィルタリング: 2 レベルのフィルターでソースごとに複製対象を制御し、書き込み競合を回避
✓フルリストア不要の復旧: 遅延レプリカと rds_start_replication_until / rds_start_replication_until_gtid で有害な変更の直前まで正確にロールフォワードしてから昇格
✓運用性の高い監視: ReplicationChannelLag による自動検知。フェイルオーバー時もチャネル構成は共有ストレージに保持され、新しいライターで自動再開

⚠️ デメリット・制約事項

🚫 制限事項

✗Aurora MySQL 8.4.8 以降でのみ利用可能 (バージョン 3 系および 8.4.7 以前では利用不可)
✗マルチソースレプリカに構成できるチャネルは最大 15
✗競合検出・解決の仕組みはなく、ソース間の変更が競合しないようユーザー側で設計が必要 (ソースごとに異なる DB・テーブルへ書き込む、replicate-do-db などのフィルターを使用する等)
✗DB クラスタースナップショットにはマルチソースチャネルの構成が含まれず、復元後は各チャネルの再構成が必要
✗チャネルごとに異なる並列ワーカー数は設定できない (MySQL の仕様)

🤔 考慮すべき点

⚠スレッド数は「(replica_parallel_workers + 1) × チャネル数」で増加するため、チャネル数と合計スループットに応じたインスタンスクラスの選定が必要
⚠直接書き込みによる競合を防ぐには CALL mysql.rds_set_read_only(1); で読み取り専用モードを有効化することを推奨
⚠遅延時間は、復旧ウィンドウの確保とデータ鮮度のトレードオフを考慮して設定
⚠チャネルの管理操作は一度に 1 チャネルずつ実施し、複数接続からの同時変更を避けることを推奨
⚠ソース側のフェイルオーバーでチャネルが I/O エラー停止する場合があり、rds_start_replication_for_channel での再開や、エラー 1236 発生時の rds_next_source_log_for_channel による対処が必要

🎯 ユースケース

📊 ユースケース 1: シャーディングされたデータベースの統合レポーティング

シナリオ: アプリケーションを複数の RDS for MySQL シャードで運用しており、全シャードを横断した分析・レポーティングと長期バックアップの一元化が必要。

SQLシャードごとのチャネル構成
-- Aurora ライターインスタンスでソースごとにチャネルを構成
CALL mysql.rds_set_external_source_for_channel(
  'shard-a.xxxxx.rds.amazonaws.com', 3306, 'repl_user', 'password',
  'mysql-bin-changelog.000045', 3892, 1, 'channel_shard_a');
CALL mysql.rds_start_replication_for_channel('channel_shard_a');

CALL mysql.rds_set_external_source_for_channel(
  'shard-b.xxxxx.rds.amazonaws.com', 3306, 'repl_user', 'password',
  'mysql-bin-changelog.000012', 1567, 1, 'channel_shard_b');
CALL mysql.rds_start_replication_for_channel('channel_shard_b');
✅ 効果: 複数シャードのデータが単一の Aurora MySQL クラスターへリアルタイムに統合され、ETL パイプラインなしで、リードレプリカを活用した横断レポーティングとバックアップの一元化が実現。
🛡️ ユースケース 2: 遅延レプリカによる誤操作・論理破損対策

シナリオ: 誤った DELETE 文や DROP TABLE、アプリケーション不具合による論理的なデータ破損に備え、フルリストアより高速な復旧手段を確保したい。

SQL遅延レプリカによる復旧フロー
-- レプリカに 1 時間 3600 秒の適用遅延を設定
CALL mysql.rds_stop_replication;
CALL mysql.rds_set_source_delay(3600);
CALL mysql.rds_start_replication;

-- 誤操作が発覚したらレプリケーションを停止
CALL mysql.rds_stop_replication;
-- 有害な変更の直前の GTID まで適用してから停止
CALL mysql.rds_start_replication_until_gtid('3E11FA47-71CA-11E1-9E33-C80AA9429562:23');
-- その後、レプリカを新しいプライマリクラスターへ昇格
✅ 効果: 有害な変更がレプリカに適用される前にレプリケーションを制御し、問題発生直前の状態まで正確にロールフォワードしてから昇格できるため、スナップショットからのフルリストアと比較して復旧時間を大幅に短縮。
💰 ユースケース 3: マルチテナント集約によるコスト最適化

シナリオ: テナントごとに個別の MySQL インスタンスを運用しており、コスト最適化と管理の簡素化のために単一の Aurora クラスターへ集約したい。

SQLテナントごとのチャネル集約
-- チャネル単位のフィルターでテナントごとの複製対象を制御し、
-- 読み取り専用モードで直接書き込みによる競合を防止
CALL mysql.rds_set_read_only(1);

-- テナント A, B, C をそれぞれ独立したチャネルで集約
CALL mysql.rds_start_replication_for_channel('tenant_a_channel');
CALL mysql.rds_start_replication_for_channel('tenant_b_channel');
CALL mysql.rds_start_replication_for_channel('tenant_c_channel');
✅ 効果: 複数のシングルテナントデータベースを 1 つの Aurora クラスターへ段階的に集約でき、インスタンス数の削減によるコスト最適化と運用の簡素化を実現。移行期間中もチャネル単位でレプリケーションを制御でき、テナントごとに切り替えタイミングを調整可能。

💵 料金と利用可能リージョン

💰 料金

マルチソースレプリケーションおよび遅延レプリケーションの利用に追加料金はありません。通常の Aurora の料金 (インスタンス時間、ストレージ、I/O または I/O-Optimized 構成) が適用されます。

複数ソースからのデータ統合によりストレージ使用量とレプリカの負荷が増加するため、チャネル数に応じたインスタンスクラスのコストと、クロスリージョンレプリケーション時のデータ転送料金を考慮してください。詳細は Aurora 料金ページ を参照。

🌍 利用可能リージョン

Aurora MySQL が利用可能なすべての AWS リージョンで提供されています。対応リージョンの詳細は Aurora の利用可能リージョン一覧 を参照してください。

→AWS DMS: 大規模データベースの初期データ移行や、異種データベース間の移行に利用。継続的なレプリケーションの代替手段
→Amazon CloudWatch: チャネル単位のメトリクス ReplicationChannelLag による遅延監視とアラーム設定
→Aurora Global Database: マルチリージョンの耐障害性が必要な場合の選択肢。リージョン間のマネージドレプリケーションを提供

📝 まとめ

マルチソースレプリケーションと遅延レプリケーションは、これまで RDS for MySQL や自己管理の MySQL でしか利用できなかった重要なレプリケーション機能を Aurora MySQL にもたらすアップデートです。シャード統合やレポーティング基盤の構築を外部ツールなしで実現できるほか、遅延レプリカは誤操作対策として費用対効果の高いセーフガードになります。

利用には Aurora MySQL 8.4.8 以降が必要なため、これらの機能を活用したいクラスターはまずバージョンアップグレードの計画から始めることを推奨します。
