Amazon Managed Service for Prometheus

📊 ネイティブヒストグラムのサポート

📅 リリース日
2026 年 6 月 11 日

💡 概要

Amazon Managed Service for Prometheus が、Prometheus の ネイティブヒストグラム (Native Histograms) の取り込み・保存・クエリに対応しました。従来のクラシックヒストグラムよりも 高い精度と低いカーディナリティで、メトリクスの分布を高解像度で取得できます。

ネイティブヒストグラムは指数バケッティングを採用し、データに応じて解像度を自動調整します。 分布全体を単一の時系列に格納することで、アクティブな時系列数を削減し、 histogram_quantile() によるテールレイテンシー分析の精度を高めます。

対象: レイテンシー・リクエスト時間などの分布を監視する DevOps エンジニア、SRE、プラットフォームチーム。 既存のクラシックヒストグラムと並行して段階的に導入できます。

❌ アップデート前の課題

  • バケット境界を事前定義する必要があり、解像度を超える精度のパーセンタイル計算ができない
  • バケット境界ごとに時系列が必要で高カーディナリティ (20 バケットで 22 時系列)
  • アクティブな時系列の増加でコスト・リソース管理の負担が増大
➜

✅ アップデート後の改善

  • 事前定義なしでより正確なパーセンタイル計算が可能
  • 分布全体を単一時系列に格納し時系列数を大幅削減 (22 → 1)
  • 利用されたバケットのみ課金され、空のバケットには課金されずコスト効率が改善

クラシックヒストグラムがバケット境界ごとに複数の時系列を必要とするのに対し、 ネイティブヒストグラムは分布全体を単一時系列に格納し、同一のストレージとクエリエンジンで処理されます。

🔧 主要機能

① 指数バケッティングによる自動解像度調整

データに応じてバケット解像度を自動調整。バケット境界の事前定義が不要で、高解像度の分布を正確にキャプチャします。

② 単一時系列への分布格納

分布全体を 1 つの時系列に格納。バケット境界ごとの時系列作成が不要になり、アクティブな時系列数とカーディナリティを大幅に削減します。

③ 段階的な導入とマイグレーション

既存のクラシックヒストグラムと並行利用が可能。監視を中断することなく、ワークロード単位で独自のペースで移行できます。

④ より正確なテールレイテンシー分析

histogram_quantile() などの関数で精度の高いパーセンタイル計算が可能。p99 などのテールレイテンシー分析精度が向上します。

📐 技術仕様: クラシック vs ネイティブ

項目 📊 クラシックヒストグラム 🎯 ネイティブヒストグラム
バケット境界 事前定義が必要 指数バケッティングで自動調整
時系列の数 バケット数 + 2 (例: 22 時系列) 単一時系列 (1 時系列)
カーディナリティ 高い 低い
パーセンタイル精度 定義したバケット解像度に依存 より高精度
課金対象 各時系列 観測値を含む利用されたバケットのみ

🔍 PromQL クエリ例

PromQL 99 パーセンタイルのレイテンシー計算 
# ネイティブヒストグラムから 99 パーセンタイルのレイテンシーを計算
histogram_quantile(0.99, sum(rate(http_request_duration_seconds[5m])))

ネイティブヒストグラムでは、事前定義したバケット境界に依存せず、指数バケッティングによってより正確な計算結果が得られます。

⚙️ 設定方法

前提条件

  • → Amazon Managed Service for Prometheus のワークスペースが作成済み
  • → ネイティブヒストグラム対応の Prometheus クライアントライブラリを使用
  • → 取り込みエージェント (例: ADOT Collector) がネイティブヒストグラム送信に対応

導入ステップ

STEP 1: アプリケーション側で有効化

Prometheus クライアントライブラリでネイティブヒストグラムを有効化。バージョンと設定が対応していることを確認します。

STEP 2: メトリクスの取り込み

ネイティブヒストグラム形式のメトリクスをワークスペースに送信。クラシックと並行運用でき、既存監視を維持したまま段階導入できます。

STEP 3: クエリと可視化

PromQL の histogram_quantile() でパーセンタイルを計算。Amazon Managed Grafana などで可視化し分布の傾向を分析します。

✅ メリット

💼 ビジネス面

✓コスト効率の向上: 利用されたバケットのみ課金され、空のバケットには課金されないため疎な分布でコストを抑制
✓運用負荷の軽減: 時系列数とカーディナリティが削減され、ワークスペース管理がシンプルに
✓段階的な導入: 監視を中断せず移行でき、移行リスクとダウンタイムを最小化

🛠️ 技術面

✓高精度なパーセンタイル計算: バケット境界の事前定義が不要でテールレイテンシーを正確に分析
✓低カーディナリティ: 分布全体を単一時系列に格納しアクティブな時系列数を大幅削減
✓自動解像度調整: 指数バケッティングでデータに応じて解像度が自動調整され設計の手間が減少

⚠️ デメリット・制約事項

制限事項

!アプリケーション側およびメトリクス取り込みパイプラインがネイティブヒストグラムに対応している必要がある
!既存の可視化やアラート定義をネイティブヒストグラムに合わせて見直す必要がある場合がある

考慮すべき点

!クラシックとネイティブを併用する場合、メトリクスの管理方針を明確にする必要がある
!課金は利用されたバケット数に基づくため、分布の特性に応じてコストを見積もる必要がある

🎯 ユースケース

① API レイテンシーの高精度監視

シナリオ: マイクロサービスで API のレイテンシー分布を高精度で監視し、p99 などのテールレイテンシーを正確に把握したい。

PromQL
histogram_quantile(0.99, sum(rate(api_request_duration_seconds[5m])) by (le, service))

✨ 効果: 事前定義バケットに依存せず正確なテールレイテンシーを取得でき、SLO 達成状況を精度高く評価できます。

② 高カーディナリティ環境のコスト最適化

シナリオ: 多数のサービス・エンドポイントを監視しており、クラシックヒストグラムの時系列数増大がコストとリソースの負担に。

移行イメージ
クラシックヒストグラム (20 バケット): 22 時系列
↓ ネイティブヒストグラムへ移行
ネイティブヒストグラム: 1 時系列

✨ 効果: アクティブな時系列数とカーディナリティが削減され、ワークスペースのコストと管理負荷を低減できます。

③ 段階的なヒストグラム移行

シナリオ: 既存のクラシックヒストグラム監視を運用中で、監視を中断せずネイティブへ移行したい。

移行戦略
ワークロード A: ネイティブヒストグラムを先行導入
ワークロード B: クラシックヒストグラムを継続
→ 検証後にワークロード B も順次移行

✨ 効果: 現在の監視を維持しながらワークロード単位で独自のペースで移行でき、移行リスクを抑えられます。

💰 料金 & 利用可能リージョン

ネイティブヒストグラムは、実際の観測値を含む利用されたバケットのみに基づいて計測・課金されます。 疎な分布における空のバケットには課金されません。詳細は Amazon Managed Service for Prometheus の料金ページを参照してください。

🌍 Amazon Managed Service for Prometheus が提供されているすべての AWS リージョンで利用可能

🔗 関連サービス・機能

📈 Amazon Managed Grafana

メトリクスを可視化し、ネイティブヒストグラムの分布を分析するために利用できます。

🔭 AWS Distro for OpenTelemetry (ADOT)

メトリクスの収集と Amazon Managed Service for Prometheus への送信に利用できます。

📦 Amazon EKS / Amazon ECS

コンテナワークロードのメトリクスを収集し監視する際の主要な対象環境です。

📝 まとめ

ネイティブヒストグラムのサポートにより、Amazon Managed Service for Prometheus は より高精度なパーセンタイル計算と 低カーディナリティでのメトリクス監視を実現します。 DevOps チームや SRE は既存のクラシックヒストグラムと並行して段階導入でき、監視を中断することなく コスト効率と分析精度の両方を向上できます。

👉 まずは検証環境でネイティブヒストグラムを有効化し、既存の監視との比較を行うことを推奨します。
