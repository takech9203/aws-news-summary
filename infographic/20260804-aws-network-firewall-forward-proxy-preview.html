AWS Network FirewallPublic Preview

🛡️ 明示的フォワードプロキシ機能の再導入

no-source-preservation デプロイモード | リリース日: 2026 年 8 月 4 日

📋 概要

AWS Network Firewall の明示的フォワードプロキシ機能が、Network Firewall 本体の機能としてパブリックプレビューで再導入されました。既存のファイアウォールポリシーを新しい no-source-preservation デプロイモードで使用することで、Network Firewall のすべてのフィルタリング機能をそのまま利用しながら、ファイアウォールを明示的プロキシとして動作させることができます。

もともと 2025 年 11 月 25 日に「Network Firewall proxy」がスタンドアロン製品としてプレビュー公開されていましたが、独自のプロキシセキュリティポリシーが既存の透過型ファイアウォールと分離していました。お客様からの機能同等性と統一ポリシーへの要望を受け、Network Firewall 本体の機能として再設計されました。

❌ Before: アップデート前の課題

  • 2025 年 11 月版はスタンドアロン製品で、独自のプロキシセキュリティポリシーを別途管理
  • 透過型とプロキシでポリシーが分離し、同じ制御を二重に定義・運用
  • マネージドルールグループや Geo-IP フィルタリングなど既存機能との同等性がない

✅ After: アップデート後の改善

  • Network Firewall の既存のすべてのフィルタリング機能を明示的プロキシとして利用可能
  • 単一のファイアウォールポリシーを透過型とプロキシの両モードで共有し、管理を一元化
  • マネージドルールグループ、Active Threat Defense、Geo-IP、URL / ドメインカテゴリ、コンテナ属性ベースのルールに対応

アプリケーションはプロキシ環境変数でファイアウォールの FQDN を指定し、VPC エンドポイント経由で CONNECT リクエストを送信します。ファイアウォールは接続を終端してフィルタリングし、許可された通信のみ NAT ゲートウェイの IP アドレスを送信元として宛先へ新規接続を確立します。

⚡ 主要機能

🔀 no-source-preservation デプロイモード

  • ファイアウォール作成時に選択する新しいデプロイモード (作成後の変更は不可)
  • クライアント接続を終端して検査後、アタッチされた NAT ゲートウェイの IP を送信元として宛先への接続を再確立
  • 送信元 IP がマスクされるため「no-source-preservation」と呼ばれる
  • デフォルトの source-preservation モード (透過型) では従来どおり送信元 IP を保持

🔌 明示的プロキシとしての動作

  • クライアントは HTTP CONNECT リクエストをファイアウォールに送信し、ファイアウォールが代理で宛先へ接続
  • ファイアウォールに FQDN が割り当てられ、http_proxy / https_proxy 環境変数などに指定
  • ルートテーブルの変更が不要で、VPC エンドポイント経由でトラフィックが到達
  • プロキシリスナーポートはデフォルトで HTTP 3128 / HTTPS 8443 (変更可能)

🧩 既存フィルタリング機能との完全な統合

  • マネージドルールグループ / Active Threat Defense
  • Geo-IP フィルタリング、URL / ドメインカテゴリフィルタリング
  • Amazon EKS / Amazon ECS 向けコンテナ属性ベースのルール
  • 単一のファイアウォールポリシーを透過型とプロキシの両方で共有可能

🌐 マルチ VPC 対応

  • CreateVpcEndpointAssociation API で任意の VPC に VPC エンドポイントをデプロイし、複数 VPC から同一プロキシを利用可能
  • Network Firewall がプライベートホストゾーンを自動作成し、関連付けた VPC 内でファイアウォールのホスト名を解決

🚀 設定方法

前提条件

✓AWS Network Firewall を利用可能な AWS アカウント (プレビューは米国東部 (オハイオ) リージョンのみ)
✓ファイアウォールをデプロイする VPC と、エンドポイント用サブネット (NAT ゲートウェイとは別サブネット)
✓同じアベイラビリティーゾーンに存在する NAT ゲートウェイ
1

ファイアウォールポリシーの作成

ルールグループを指定してポリシーを作成します。AWS マネージドルールグループやパートナーマネージドルールグループも使用でき、透過型ファイアウォールとプロキシの両方で共有できます。

BashAWS CLI
aws network-firewall create-firewall-policy \
  --firewall-policy-name proxy-policy \
  --firewall-policy '{
    "StatelessDefaultActions": ["aws:forward_to_sfe"],
    "StatelessFragmentDefaultActions": ["aws:forward_to_sfe"],
    "StatefulRuleGroupReferences": [
      {"ResourceArn": "arn:aws:network-firewall:us-east-2:aws-managed:stateful-rulegroup/MalwareDomainsActionOrder"}
    ]
  }' \
  --region us-east-2
2

NAT ゲートウェイの作成 (存在しない場合)

ファイアウォールは NAT ゲートウェイにアタッチされ、その IP アドレスを使用して宛先と通信します。

BashAWS CLI
aws ec2 create-nat-gateway \
  --subnet-id subnet-0123456789abcdef0 \
  --allocation-id eipalloc-0123456789abcdef0 \
  --region us-east-2
3

no-source-preservation モードでファイアウォールを作成

マネジメントコンソールまたは API でデプロイモードとして「No source preservation」を選択し、以下を設定します。

  • アタッチする NAT ゲートウェイを指定 (この NAT ゲートウェイの IP がエグレスに使用される)
  • ファイアウォールエンドポイントの VPC とサブネットを指定 (NAT ゲートウェイと同一 AZ、別サブネット)
  • ステップ 1 のファイアウォールポリシーを関連付け
  • 必要に応じて削除保護、トラフィック分析モード、プロキシリスナーポート、ログ記録を構成

作成後、ステータスが PROVISIONING から READY に遷移すると、プロキシの FQDN (DnsName) が表示されます。

4

ワークロードのプロキシ設定

プロキシ環境変数にファイアウォールの DnsName とリスナーポートを指定します。ルートテーブルの変更は不要です。

Bash環境変数の設定
export http_proxy=http://<firewall-dns-name>:3128
export https_proxy=http://<firewall-dns-name>:8443
5

他の VPC への拡張 (オプション)

VPC エンドポイント関連付けにより、他の VPC のアプリケーションからも同一のプロキシを利用できます。プライベートホストゾーンが自動作成されます。

BashAWS CLI
aws network-firewall create-vpc-endpoint-association \
  --firewall-arn <firewall-arn> \
  --vpc-id vpc-0123456789abcdef0 \
  --subnet-mapping SubnetId=subnet-0123456789abcdef0 \
  --region us-east-2

💡 メリット

💼 ビジネス面

✓セキュリティ統制の一元化: 単一のファイアウォールポリシーで透過型とプロキシの両方を統制でき、二重管理によるコストと設定ミスのリスクを削減
✓データ持ち出し対策の強化: アウトバウンド通信をプロキシで終端・検査し、データ持ち出しやマルウェア注入に対する集中的なセキュリティ制御を実現
✓サードパーティプロキシの代替可能性: マネージドサービスのため、自己管理型プロキシサーバー (Squid など) の構築・運用負荷を軽減

⚙️ 技術面

✓ルーティング設定の簡素化: 明示的プロキシ方式のためルートテーブル変更が不要で、クライアント側のプロキシ設定のみでトラフィックを誘導
✓既存機能の完全活用: マネージドルールグループ、Active Threat Defense、Geo-IP、URL / ドメインカテゴリ、コンテナ属性ベースのルールをプロキシモードでもそのまま利用
✓マルチ VPC 対応: VPC エンドポイント関連付けで複数 VPC から単一プロキシを共有でき、プライベートホストゾーンによる名前解決も自動化

⚠️ デメリット・制約事項

制限事項

✗パブリックプレビューであり、米国東部 (オハイオ) リージョン (us-east-2) のみで利用可能
✗機能と動作はプレビュー期間中に変更される可能性がある
✗デプロイモードはファイアウォール作成時に選択し、作成後に変更できない
✗ステートレスルールエンジンは明示的プロキシトラフィックを検査しない (CONNECT リクエストはステートフルルールエンジンが直接処理)
✗ファイアウォールエンドポイントは、アタッチした NAT ゲートウェイと同じアベイラビリティーゾーンにのみ作成可能

考慮すべき点

⚠クライアント側でプロキシ設定 (環境変数やアプリケーション設定) が必要であり、透過型と異なりワークロード側の変更が発生する
⚠送信元 IP が NAT ゲートウェイの IP に置換されるため、宛先側で送信元 IP に基づく制御を行っている場合は影響確認が必要
⚠AWS はテスト環境での試用を推奨しており、本番環境への適用は GA を待つことが望ましい
⚠既存の透過型 Network Firewall とはデプロイモードが異なるため、プロキシ化には新規ファイアウォールの作成が必要

🎯 ユースケース

1️⃣ アウトバウンド通信の集中統制によるデータ持ち出し対策

シナリオ: 金融機関が、複数 VPC にまたがるワークロードからのインターネットアクセスを単一のプロキシに集約し、許可されたドメインへの通信のみを許可したい。

実装例: 許可ドメインリストのステートフルルールグループを作成 → no-source-preservation モードのファイアウォールにポリシーを関連付け → 各ワークロード VPC に VPC エンドポイント関連付けを作成 → 全ワークロードの https_proxy に FQDN を設定

✅ 効果: すべてのアウトバウンド通信がプロキシで終端・検査され、未許可ドメインへのデータ持ち出しを一元的に遮断できる。

2️⃣ 透過型ファイアウォールとプロキシのポリシー統一

シナリオ: すでに Network Firewall を透過型で運用している企業が、プロキシ対応アプリケーション向けに明示的プロキシも提供したいが、セキュリティポリシーは一本化したい。

実装例: 既存のファイアウォールポリシーをそのまま利用 → no-source-preservation モードの新しいファイアウォールを作成し同一ポリシーを関連付け → プロキシ対応アプリケーションのみプロキシ設定を追加

✅ 効果: 単一ポリシーで両モードを統制でき、ルール変更が両方に即時反映されるため、運用負荷とポリシー乖離のリスクを削減できる。

3️⃣ EKS / ECS ワークロードのコンテナ単位のエグレス制御

シナリオ: Amazon EKS 上のマイクロサービスごとに、アクセス可能な外部 API を制限したい。

実装例: コンテナ属性ベースのルールを含むルールグループを作成 → no-source-preservation モードのファイアウォールにポリシーを関連付け → Pod のプロキシ環境変数に FQDN を設定

✅ 効果: コンテナ属性に基づくきめ細かなエグレス制御をプロキシ経由で適用でき、マイクロサービス単位の最小権限通信を実現できる。

🔗 関連サービス・機能

🌐 Amazon VPC NAT ゲートウェイ

no-source-preservation モードのファイアウォールがアタッチする必須コンポーネント。宛先への通信の送信元 IP として使用される。

🔌 AWS PrivateLink (VPC エンドポイント)

アプリケーション VPC からファイアウォールへトラフィックを送るための接続手段。VPC エンドポイント関連付けで複数 VPC に展開できる。

🛡️ AWS Firewall Manager

AWS Organizations 配下の複数アカウントにわたる Network Firewall の一元管理に利用可能。

📡 Route 53 プライベートホストゾーン

ファイアウォールの FQDN を関連付けた VPC 内で解決するために自動作成される。

📝 まとめ

AWS Network Firewall の明示的フォワードプロキシが、独立製品ではなく Network Firewall 本体の機能として再導入され、既存のすべてのフィルタリング機能と統一ポリシーで利用できるようになりました。透過型ファイアウォールとプロキシのセキュリティ統制を一元化できる点は、アウトバウンド通信の統制やデータ持ち出し対策を強化したい組織にとって大きな価値があります。現時点では米国東部 (オハイオ) リージョン限定のプレビューであり無料で試用できるため、テスト環境での検証を通じて GA に備えることを推奨します。
