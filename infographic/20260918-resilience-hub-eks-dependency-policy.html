🛡️ AWS Resilience Hub (次世代)

EKS ラベルサポート・依存関係インサイト・ポリシー共有の 3 つの新機能

📅 リリース日: 2026 年 9 月 18 日 | 対象: プラットフォームエンジニアリング / SRE チーム

📝 概要

次世代 Resilience Hub は、ワークロードのレジリエンス (回復力) を評価・改善するための中央管理サービスです。今回のアップデートで、Kubernetes 環境やマルチアカウント環境でのレジリエンス管理を強化する 3 つの機能が追加されました。

☸️
EKS ラベルサポート
名前空間内のラベルをサービス入力ソースとして指定し、評価対象を制御
🤖
依存関係インサイト
生成 AI が検出済みの依存関係を分析し、リスクパターンを自動ハイライト
🏢
ポリシー共有
AWS Organizations 経由でレジリエンスポリシーを複数アカウントに共有

❌ アップデート前の課題

✗EKS の分析対象を Kubernetes のラベル規約で絞り込めず、名前空間単位でしか制御できなかった
✗自動検出された依存関係の情報は、リスク特定やパターン把握を人手で分析する必要があった
✗レジリエンスポリシーはアカウントごとに個別作成が必要で、マルチアカウントでの基準統一が困難だった

✅ アップデート後の改善

✓EKS のラベルをサービス入力ソースに指定し、既存のラベル運用に沿って検出・分析対象を制御可能に
✓生成 AI が新しい依存関係、クロスリージョン依存、異常な使用パターンを自動的にハイライト
✓中央チームのポリシーを Organizations の複数アカウントに共有し、利用状況を組織全体で可視化

中央管理アカウントで作成したレジリエンスポリシーを Organizations 経由でメンバーアカウントに共有し、EKS ラベルで絞り込んだリソースの依存関係を生成 AI が分析する流れを示しています。

⚙️ 主要機能

☸️ 1. EKS ラベルによるサービス入力ソース
  • EKS の名前空間内のラベルをサービス入力ソースとして使用可能
  • 既に運用している Kubernetes のラベル付け規約をそのまま活用し、検出・分析対象のリソースを制御
  • チームの EKS ワークロードの整理方法とレジリエンス評価の対象を整合させることが可能
🤖 2. 依存関係インサイト
  • 依存関係の自動検出 (dependency discovery) を有効にしている場合に利用できる生成 AI 機能
  • 検出されたアプリケーションの依存関係を分析し、意味のあるパターンをハイライト
  • 新しい依存関係の出現、クロスリージョン依存、通常と異なる使用状況を自動的に検出
  • API レベルでは CROSS_REGION、NEW_DEPENDENCY、THIRD_PARTY、UNEVEN_USAGE、AWS_SERVICE のカテゴリを定義
🏢 3. AWS Organizations によるレジリエンスポリシー共有
  • 中央チームが作成したポリシー (RTO、RPO、可用性 SLO などの目標値) を組織内の複数アカウントに共有可能
  • ポリシーの利用状況を組織全体で可視化し、採用状況の追跡と一貫した基準の維持が可能
  • ポリシーのアタッチ、デタッチ、共有取り消し、削除などのイベント履歴を追跡可能

🔧 技術仕様

📊 依存関係インサイトのカテゴリ

カテゴリ説明
NEW_DEPENDENCY新しく出現した依存関係
CROSS_REGIONリージョンをまたぐ依存関係
THIRD_PARTYサードパーティサービスへの依存
UNEVEN_USAGE通常と異なる、偏った使用パターン
AWS_SERVICEAWS サービスへの依存

💻 API 使用例

Python 依存関係インサイトとポリシー共有の実装例 
# 依存関係インサイトの生成を開始
response = client.start_dependency_insights(
    serviceArn='arn:aws:resiliencehub:...:service/...'
)

# インサイトを取得
insights = client.get_dependency_insights(
    serviceArn='arn:aws:resiliencehub:...:service/...'
)
# insights['insights'] に CROSS_REGION や NEW_DEPENDENCY などの
# カテゴリ別の分析結果が含まれる

# 組織内共有を有効にしたポリシーを作成
policy = client.create_policy(
    name='corporate-standard-policy',
    availabilitySlo={'target': 99.9},
    multiAz={
        'rtoInMinutes': 60,
        'rpoInMinutes': 15,
        'disasterRecoveryApproach': 'WARM_STANDBY'
    },
    sharingEnabled=True
)

🚀 設定方法

✅ 前提条件

✓次世代 Resilience Hub をセットアップ済みであること
✓依存関係インサイトを使用する場合は、依存関係の自動検出 (dependency discovery) を有効にしていること
✓ポリシー共有を使用する場合は、AWS Organizations が設定済みであること
✓EKS ラベルを使用する場合は、対象の EKS クラスターと名前空間にラベル運用が整備されていること
1
EKS ラベルをサービス入力ソースに設定

Resilience Hub コンソールでサービスの入力ソースとして EKS の名前空間とラベルを指定します。既存の Kubernetes ラベル規約に基づいて、検出・分析対象のリソースを絞り込みます。

2
依存関係インサイトの実行
BashAWS CLI
# 依存関係インサイトの生成を開始
aws resiliencehub start-dependency-insights \
  --service-arn <サービスの ARN>

# 生成されたインサイトを取得
aws resiliencehub get-dependency-insights \
  --service-arn <サービスの ARN>

ステータスが COMPLETED になると、概要とカテゴリ別の分析結果を確認できます。

3
レジリエンスポリシーの組織内共有
BashAWS CLI
# 共有を有効にしたポリシーを作成
aws resiliencehub create-policy \
  --name corporate-standard-policy \
  --availability-slo target=99.9 \
  --sharing-enabled

中央管理アカウントで sharingEnabled を有効にしてポリシーを作成すると、Organizations のメンバーアカウントに共有されます。各アカウントのサービスにアタッチし、利用状況を組織全体で追跡します。

💡 メリットと制約事項

📈 ビジネス面のメリット

✓ガバナンス強化: 中央定義のレジリエンス基準 (RTO / RPO / SLO) を全アカウントに展開し、一貫した体制を維持
✓リスク特定の迅速化: 生成 AI による分析で、人手では見落としがちなリスクパターンを早期発見
✓採用状況の可視化: ポリシー利用状況を追跡し、施策の浸透度を定量的に把握

🔧 技術面のメリット

✓既存運用との整合性: Kubernetes のラベル規約をそのまま活用し、ワークロードの整理方法と評価対象を一致
✓分析の自動化: クロスリージョン依存や新規依存の出現を自動検出し、手動レビューの負荷を軽減
✓監査性の向上: ListPolicyEvents や ListServiceEvents でポリシーの適用・変更履歴を追跡

⚠️ 制限事項

✗依存関係インサイトは、依存関係の自動検出を有効にしている場合のみ利用可能
✗データ不足 (INSUFFICIENT_DATA) や生成 AI の処理失敗 (LLM_GENERATION_FAILED) でエラーになる可能性
✗ポリシー共有は AWS Organizations の利用が前提

🤔 考慮すべき点

⚠生成 AI のインサイトは分析の補助であり、最終判断はチームのレビューと組み合わせることが望ましい
⚠共有ポリシーの削除・共有取り消しは利用中のサービスに影響するため、イベント履歴 (POLICY_SHARING_REVOKED、POLICY_DELETED) の監視が必要
⚠ラベル運用が不統一だと、評価対象の漏れが発生する可能性

🎯 ユースケース

☸️ ユースケース 1: EKS 上のマイクロサービスをチーム単位で評価

シナリオ: 1 つの EKS クラスター上で複数チームがマイクロサービスを運用しており、チームごとにレジリエンス評価を行いたい。

実装例: ① 各チームのワークロードに team=payment などのラベルを付与 → ② サービス入力ソースとして名前空間 + ラベルを指定 → ③ チーム単位で評価対象を絞り込んでアセスメントを実行

✅ 効果: 名前空間全体ではなくチームの担当範囲に限定した評価が可能になり、評価結果とチームの責任範囲が一致する。
🤖 ユースケース 2: 生成 AI による依存関係リスクの早期発見

シナリオ: マイクロサービス間の依存関係が頻繁に変化しており、意図しないクロスリージョン依存や新規依存の混入を早期に検出したい。

実装例: ① 依存関係の自動検出を有効化 → ② StartDependencyInsights を定期的に実行 → ③ CROSS_REGION / NEW_DEPENDENCY カテゴリのインサイトを確認し、意図しない依存関係をレビュー

✅ 効果: リージョン障害時に影響を受けるクロスリージョン依存や、レビューを経ていない新規依存を自動的に把握でき、障害リスクを事前に低減できる。
🏢 ユースケース 3: マルチアカウント環境でのレジリエンス基準の統一

シナリオ: 数十のアカウントを持つ組織で、全社共通の RTO / RPO 目標を各アカウントのワークロードに適用したい。

実装例: ① 中央管理アカウントで sharingEnabled=True のポリシーを作成 → ② Organizations 経由でメンバーアカウントに共有 → ③ 各アカウントのサービスにアタッチ → ④ 組織全体で利用状況をモニタリング

✅ 効果: アカウントごとのポリシー重複作成が不要になり、全社共通のレジリエンス基準を一元管理しながら採用状況を追跡できる。

📌 まとめ

次世代 Resilience Hub に、EKS ラベルによる評価対象の制御、生成 AI による依存関係インサイト、AWS Organizations でのポリシー共有という 3 つの機能が追加され、Kubernetes 環境やマルチアカウント環境でのレジリエンス管理が大きく強化されました。EKS を活用している組織や、複数アカウントでレジリエンス基準の統一に課題を持つ組織は、コンソールから新機能の利用を検討することを推奨します。
