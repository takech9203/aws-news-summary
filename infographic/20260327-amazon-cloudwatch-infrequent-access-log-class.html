📋 概要

CloudWatch Logs の Infrequent Access 取り込みクラスに、データ保護機能、OpenSearch PPL、OpenSearch SQL のサポートが追加されました。

Logs IA はフォレンジック調査やトラブルシューティングなど、頻繁にはクエリされないログをコスト効率よく統合するための取り込みクラスです。

🔄 Before / After

❌ アップデート前
  • Logs Insights のクエリ言語のみ
  • SQL/PPL による柔軟な分析不可
  • データ保護ポリシー適用不可
  • 機密データ含むログは Standard 必須
➔
✅ アップデート後
  • OpenSearch PPL/SQL で高度な分析
  • データ保護ポリシー適用可能
  • 機密データの自動検出・マスキング
  • コストと機能のトレードオフ軽減

⭐ 主要機能

🔒 データ保護機能の Logs IA 対応
➤ Logs IA ロググループにデータ保護ポリシーを適用可能
➤ クレジットカード番号、SSN、メールアドレスなどを自動検出・マスキング
➤ Standard クラスと同様のルールでコンプライアンス対応
📊 OpenSearch PPL サポート
➤ パイプラインベースの直感的なクエリ
➤ source, where, stats, sort をパイプで接続
📊 OpenSearch SQL サポート
➤ 標準 SQL 構文でログデータをクエリ
➤ SELECT, WHERE, GROUP BY, ORDER BY で分析
➤ SQL に慣れた開発者は追加学習コストなし

🛠️ 設定方法

前提条件: AWS アカウント、CloudWatch Logs アクセス権限、logs:PutDataProtectionPolicy 権限

Bash Step 1: Logs IA ロググループ作成 
aws logs create-log-group \
  --log-group-name "/app/my-application" \
  --log-group-class INFREQUENT_ACCESS
Bash Step 2: データ保護ポリシー適用 
aws logs put-data-protection-policy \
  --log-group-identifier "/app/my-application" \
  --policy-document file://data-protection-policy.json
Bash Step 3: OpenSearch SQL クエリ 
aws logs start-query \
  --log-group-names "/app/my-application" \
  --start-time $(date -d '1 hour ago' +%s) \
  --end-time $(date +%s) \
  --query-language SQL \
  --query-string "SELECT @timestamp, @message
    FROM \`/app/my-application\`
    WHERE @message LIKE '%ERROR%'
    ORDER BY @timestamp DESC LIMIT 100"
Bash Step 4: OpenSearch PPL クエリ 
aws logs start-query \
  --log-group-names "/app/my-application" \
  --start-time $(date -d '1 hour ago' +%s) \
  --end-time $(date +%s) \
  --query-language PPL \
  --query-string "source = \`/app/my-application\`
    | where @message like '%ERROR%'
    | stats count() by bin(@timestamp, 5m)
    | sort -count()"

💪 メリット

💼 ビジネス面
💰コスト削減: Logs IA クラスを選択でき、Standard と比較して大幅なコスト削減が可能
📜コンプライアンス対応の簡素化: 機密データの自動検出・マスキングで規制要件対応コストを削減
📦ログ統合の促進: より多くのログを AWS ネイティブで一元管理、サードパーティ依存を低減
⚙️ 技術面
📋クエリ言語の選択肢拡大: Insights + PPL + SQL でチームのスキルセットに合わせた分析
💻既存 SQL スキルの活用: 追加学習なしにログ分析を開始可能
🔒統一的なデータ保護: Standard/IA 横断で一貫したセキュリティポリシーを実現

⚠️ デメリット・制約事項

🚫メトリクスフィルターやサブスクリプションフィルターは引き続き利用不可
🚫ロググループ作成後にログクラスの変更は不可
🚫データ保護の検出パターンは AWS マネージドデータ識別子に限定
💡Logs IA はクエリ時にスキャン料金が発生。頻繁にクエリするログには Standard クラスが適切な場合あり
💡PPL/SQL 構文は Logs Insights と異なるため、既存クエリの移行が必要

💡 ユースケース

🕵️ セキュリティフォレンジック調査

インシデント発生時に過去のアクセスログを SQL で詳細調査。低コスト保存 + 馴染みの SQL で効率的に分析。

📜 コンプライアンス対応のログ管理

規制要件による個人情報保護が必要なログを、Logs IA の低コストで保持しながら自動マスキングでコンプライアンス充足。

📊 運用ログの集約分析

複数マイクロサービスの運用ログを Logs IA に統合し、PPL のパイプライン構文で直感的にエラー傾向を集計。
