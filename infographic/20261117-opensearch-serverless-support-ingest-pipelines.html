Amazon OpenSearch Serverless

🔄 インジェストパイプラインのサポート開始

📅 リリース日: 2026 年 11 月 17 日 🏷️ 機能: Ingest Pipelines

📌 概要

Amazon OpenSearch Serverless がインジェストパイプラインをサポートしました。インジェストパイプラインは、ドキュメントがインデックスされる際にコレクション内部でクリーニング、エンリッチメント、ベクトル化を実行する、順序付けられたプロセッサのシーケンスです。別途前処理用のインフラストラクチャを用意することなく、データ変換をコレクション側で統一的に適用できます。

特にセマンティック検索や AI 検索のワークロードでは、text_chunking による長文の分割や text_embedding などによるインデックス時の埋め込みベクトル生成が可能になり、ベクトル検索基盤の構築が大幅に簡素化されます。

❌ Before: アップデート前の課題
  • データ正規化・エンリッチメントには Lambda や ETL ジョブなどの外部前処理インフラの構築・運用が必要
  • クライアントごとに前処理コードを実装するため、変換ロジックの重複や不整合が発生しやすい
  • 埋め込みベクトルの生成をアプリケーション側で行う必要があり、セマンティック検索の実装が複雑
✅ After: アップデート後の改善
  • コレクション内部でインデックス時にドキュメントの変換・エンリッチメントを実行可能
  • copy、date、lowercase、rename、set、trim などのプロセッサでデータ正規化を宣言的に定義
  • text_chunking、text_embedding などでインデックス時のチャンキングと埋め込み生成が可能
  • 標準の _ingest/pipeline API で管理、_simulate API で適用前テストが可能

従来はアプリケーションと OpenSearch Serverless の間に前処理用の Lambda や ETL が必要でしたが、今回のアップデートにより変換処理をコレクション内部のインジェストパイプラインに集約できます。

⚡ 主要機能

🧹 データ変換プロセッサ
copy date dot_expander join lowercase uppercase remove rename set trim
  • copy: ソースフィールドの値をターゲットフィールドにコピー
  • date: 日付文字列をパースして正規化されたタイムスタンプを書き込み
  • dot_expander: ドットを含むフィールド名をネストされたオブジェクト構造に展開
  • join: 配列フィールドの要素をセパレータで連結して 1 つの文字列に変換
  • remove / rename / set / trim: フィールドの削除、リネーム、静的な値の設定、空白除去
🤖 機械学習プロセッサ (ニューラル検索・セマンティックエンリッチメント)
text_chunking text_embedding text_image_embedding sparse_encoding ml_inference
  • text_chunking: 長いテキストを埋め込みモデルのトークン制限に収まるパッセージに分割
  • text_embedding: セマンティック検索用の密ベクトル埋め込みを生成
  • text_image_embedding: マルチモーダル検索用の結合ベクトル埋め込みを生成
  • sparse_encoding: ニューラルスパース検索用のスパースベクトル表現を生成
  • ml_inference: 接続済みの任意の ML モデルを呼び出し、入出力フィールドのマッピングを定義可能
  • ML プロセッサの利用には、設定済みの機械学習モデル接続が必要
🛠️ パイプラインの管理と適用
  • 標準の OpenSearch REST API (_ingest/pipeline) で作成・更新・取得・一覧・削除が可能
  • _simulate API により、本番適用前にサンプルドキュメントで変換結果をテスト可能
  • index.default_pipeline 設定によるデフォルト適用、または pipeline クエリパラメータによる個別指定が可能

🔐 必要なデータアクセスポリシー権限

パイプライン操作は、collection リソースタイプに対する以下の権限にマッピングされます。

✓aoss:CreateCollectionItems: パイプラインの作成・更新
✓aoss:DescribeCollectionItems: パイプラインの取得・一覧・シミュレート
✓aoss:DeleteCollectionItems: パイプラインの削除
JSON データアクセスポリシー例 
[
    {
        "Description": "Manage pipelines",
        "Rules": [
            {
                "ResourceType": "collection",
                "Resource": ["collection/my-collection"],
                "Permission": [
                    "aoss:CreateCollectionItems",
                    "aoss:DescribeCollectionItems",
                    "aoss:DeleteCollectionItems"
                ]
            }
        ],
        "Principal": [
            "arn:aws:iam::123456789012:role/pipeline-admin-role"
        ]
    }
]

パイプラインの作成
Bash パイプライン作成リクエスト 
PUT _ingest/pipeline/my-pipeline
{
  "description": "Normalizes the category field",
  "processors": [
    { "trim": { "field": "category" } },
    { "lowercase": { "field": "category" } },
    { "rename": { "field": "category", "target_field": "category_normalized" } }
  ]
}

category フィールドの空白除去、小文字化、リネームを順番に実行するパイプラインを作成します。プロセッサは定義された順序で実行されます。

2
パイプラインのシミュレート
Bash 適用前のテスト 
POST _ingest/pipeline/my-pipeline/_simulate
{
  "docs": [
    {
      "_index": "my-index",
      "_id": "1",
      "_source": { "category": "  Home Appliances  " }
    }
  ]
}

本番トラフィックに適用する前に変換結果を確認できます。この例では category_normalized: "home appliances" が返されます。

3
インデックスへの適用
Bash デフォルトパイプラインの設定 
PUT my-index
{
  "settings": {
    "index.default_pipeline": "my-pipeline"
  }
}

このインデックスに送信されるすべてのドキュメントにパイプラインが適用されます。個別適用は POST my-index/_doc?pipeline=my-pipeline のように指定します。クエリパラメータはデフォルトパイプライン設定を上書きし、両者は組み合わされない点に注意してください。

⚖️ メリットと制約事項

👍 メリット

✓インフラコストの削減: 前処理専用の Lambda 関数や ETL ジョブが不要になり、構築・運用コストを削減
✓開発速度の向上: セマンティック検索や RAG 向けのベクトル化パイプラインを宣言的な定義だけで構築
✓データ品質の向上: すべての取り込み経路で同一の変換が適用され、一貫性を保証
✓OpenSearch 標準 API との互換性: マネージドドメインやオープンソース OpenSearch の知識を活用可能
✓事前テストが可能: _simulate API で本番適用前に安全に検証

⚠️ 制約・考慮点

✗利用できるプロセッサは限定されたセットのみ (非サポートプロセッサを含むパイプラインは拒否)
✗script プロセッサおよび Painless スクリプトは利用不可
✗Mustache テンプレートは利用不可、設定値はリテラル値のみ
⚠パイプラインの作成・更新の反映まで最大 15 秒程度の遅延
⚠パイプラインの処理時間はインデックス用 OCU を消費するため、計算負荷の高いパイプラインはキャパシティ消費が増加
⚠自動セマンティックエンリッチメントなどがデフォルトパイプラインを管理している場合、上書きにより機能が実行されなくなる可能性
⚠ML プロセッサのリモートモデル推論はモデルプロバイダーから別途課金

💡 ユースケース

🔍 ユースケース 1: セマンティック検索向けのインデックス時ベクトル化

シナリオ: ドキュメント検索システムで、長文ドキュメントをチャンク分割し、埋め込みベクトルを生成してセマンティック検索を実現したい。

JSON チャンキング + 埋め込み生成パイプライン 
PUT _ingest/pipeline/nlp-ingest-pipeline
{
  "description": "Chunks text and generates embeddings",
  "processors": [
    {
      "text_chunking": {
        "algorithm": { "fixed_token_length": { "token_limit": 384 } },
        "field_map": { "body": "body_chunks" }
      }
    },
    {
      "text_embedding": {
        "model_id": "my-model-id",
        "field_map": { "body_chunks": "body_embedding" }
      }
    }
  ]
}
✨ 効果: アプリケーション側で埋め込み生成コードを実装することなく、インデックス時に自動でチャンキングとベクトル化が行われ、RAG やセマンティック検索の基盤構築が簡素化される。
📊 ユースケース 2: ログ・イベントデータの正規化

シナリオ: 複数のシステムから送信されるログデータのフィールド名や形式が統一されておらず、検索や集計の精度に問題がある。

JSON ログ正規化パイプライン 
PUT _ingest/pipeline/log-normalize
{
  "description": "Normalizes log fields",
  "processors": [
    { "date": { "field": "event_time", "formats": ["ISO8601"], "target_field": "@timestamp" } },
    { "lowercase": { "field": "log_level" } },
    { "rename": { "field": "src_ip", "target_field": "source.ip" } },
    { "remove": { "field": "debug_info" } }
  ]
}
✨ 効果: 送信元システムごとの前処理実装が不要になり、タイムスタンプの正規化、フィールド名の統一、不要フィールドの削除がコレクション側で一元的に行われる。
⚡ ユースケース 3: Lambda 前処理層の置き換え

シナリオ: 現在、データ投入前の整形処理を Lambda 関数で実装しており、その運用・保守の負担を削減したい。

JSON デフォルトパイプラインの設定 
PUT my-index
{
  "settings": {
    "index.default_pipeline": "my-normalize-pipeline"
  }
}
✨ 効果: インデックスのデフォルトパイプラインとして変換処理を設定することで、Lambda 関数の運用が不要になり、どのクライアントから投入してもデータの一貫性が保たれる。

💰 料金

インジェストパイプラインの処理は、コレクションのインデックスリクエストを処理するコンピューティング上で実行されます。パイプラインが消費する処理時間はインデックス用 OpenSearch Compute Unit (OCU) にカウントされ、他のインデックス処理と同じ方法で課金されます。

⚠プロセッサ数が多い、または計算負荷の高いパイプラインは、シンプルなパイプラインよりも多くのインデックスキャパシティを消費
⚠text_embedding などの ML プロセッサが呼び出すリモートモデルの推論は、モデルプロバイダーから別途課金

🌏 利用可能リージョン

Amazon OpenSearch Serverless が利用可能なすべての AWS リージョンで利用できます。詳細は リージョン別の利用可否一覧 を参照してください。

🔗 関連サービス・機能

✓Amazon OpenSearch Service (マネージドドメイン): 以前からインジェストパイプラインが利用可能であり、今回 Serverless でも同等の機能 (サブセット) が利用可能に
✓OpenSearch Serverless ニューラル検索 / ハイブリッド検索: ML プロセッサの利用には ML モデル接続の設定が必要で、ニューラル検索機能と組み合わせて使用
✓AWS Lambda / AWS Glue: これまで前処理に使用していた Lambda 関数や ETL ジョブをインジェストパイプラインに置き換えることで、アーキテクチャを簡素化

🎯 まとめ

Amazon OpenSearch Serverless のインジェストパイプラインサポートにより、データの正規化からインデックス時のベクトル化までをコレクション内で完結でき、前処理インフラの構築・運用が不要になります。

💡 特にセマンティック検索や RAG を構築しているチームは、text_chunking と text_embedding プロセッサの活用を検討する価値があります。まずは _simulate API でパイプラインの動作を検証し、既存の前処理ロジックの置き換えを評価することを推奨します。
