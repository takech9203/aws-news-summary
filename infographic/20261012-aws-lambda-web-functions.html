AWS Lambda

🚀 Lambda Web Functions の発表

📅 リリース日: 2026 年 10 月 12 日 | 新しいサーバーレスコンピューティングプリミティブ

📝 概要

AWS Lambda が新しいサーバーレスコンピューティングプリミティブである Lambda Web Functions を発表しました。 コードがポートをリッスンする標準的な HTTP サーバーとして HTTP リクエストを直接処理し、 Express、Hono、Fastify などの Web フレームワークをアダプタやカスタム設定なしでそのまま利用できます。 料金はアクティブ CPU 時間と保持メモリに対する課金となり、I/O 待ちのアイドル時間には課金されません。 既存の Lambda 関数は Lambda Event Functions に改名されます (名称変更のみ、コード変更・再デプロイ不要)。

❌ Before: アップデート前の課題

  • イベントハンドラモデルに合わせたコード記述が必要で、HTTP フレームワーク利用にはアダプタ (Lambda Web Adapter など) やカスタム設定が必要だった
  • 1 つの実行環境が同時に 1 リクエストしか処理できず、バースト時に多数のコールドスタートが発生していた
  • ウォールクロック時間に基づく課金のため、データベース応答や外部 API 待ちなどのアイドル時間にも課金されていた
  • マルチリージョン展開には、リージョンごとのデプロイとルーティング構成の個別管理が必要だった

✅ After: アップデート後の改善

  • ポートをリッスンする標準的な HTTP サーバーのコードをそのままデプロイでき、アダプタが不要に
  • 1 つのウォーム実行環境が最大 128 の同時リクエストを処理し、コールドスタートを桁違いに削減
  • アクティブ CPU 時間 + 保持メモリに基づく課金で、I/O 待ちの多いワークロードのコストを低減
  • 1 回のデプロイで複数リージョンへ複製し、最も近いリージョンから自動処理するマルチリージョンルーティング
  • ネイティブ HTTP ストリーミングで AI 推論のトークンストリーミングなど段階的レスポンスが容易に

Lambda Web Functions のマルチリージョン構成の例です。1 つのグローバル URL へのリクエストがユーザーに最も近いリージョンへルーティングされ、各リージョンのウォーム実行環境が複数の同時リクエストを処理します。

⚙️ 主要機能

🌐 1. HTTP ネイティブなプログラミングモデル

コードが環境変数 AWS_LAMBDA_HTTP_ENDPOINT で指定されたホストとポートをリッスンし、HTTP リクエストを直接処理。Express、Hono、Fastify、Next.js などの Node.js フレームワークをアダプタなしで利用でき、ローカル実行も標準的な方法で可能です。

⚡ 2. マルチ同時リクエスト処理によるコールドスタート削減

1 つのウォーム実行環境が最大 128 の同時リクエストを処理。トラフィックのバースト時にもウォーム環境を共有するため、コールドスタートの発生を桁違いに削減します。

💰 3. アクティブ CPU 課金モデル

アクティブ CPU 時間と実行環境が保持するメモリに対して課金。データベースクエリや外部 API 呼び出しの待機中はほとんど CPU を消費しないため、I/O 待ちの多いワークロードでコスト効率が向上します。

📡 4. HTTP ストリーミング

ネイティブの HTTP ストリーミングにより結果を段階的に返却可能。AI 推論エンドポイントのトークンストリーミングなどに有効です。

🌍 5. マルチリージョンルーティング

1 回のデプロイコマンドで複数リージョンへコードを複製。グローバル URL (<domain-id>.lambda-web.global.on.aws) により、ユーザーに最も近いリージョンへレイテンシーベース (ベストエフォート) でルーティングします。

🔀 6. リビジョンとエンドポイントによるデプロイ管理

リビジョン (コードの不変スナップショット) とエンドポイント (HTTPS URL) で構成を管理。複数リビジョンへの重み付きトラフィック分割により、カナリアリリースを API 1 回で実現します。

🔗 7. VPC 接続と CloudFront 統合

Amazon VPC 内のリソース (RDS など) へのアクセスをサポート。エンドポイントを CloudFront のオリジンとして利用でき、オリジンアクセスコントロール (OAC) によるプライベートオリジン構成にも対応します。

🏷️ 8. Lambda Event Functions への名称変更

既存の Lambda 関数は Lambda Event Functions に改名。名称変更のみであり、コードの変更や再デプロイは不要です。

💻 コード例

JavaScript 標準的な Express アプリをそのままデプロイ 
import express from 'express';

const app = express();
const [host, port] = process.env.AWS_LAMBDA_HTTP_ENDPOINT.split(':');

app.get('/', (req, res) => {
  res.json({ message: 'Hello from Lambda Web Functions!' });
});

app.listen(port, host, () => {
  console.log(`Server running on port ${port}`);
});

環境変数 AWS_LAMBDA_HTTP_ENDPOINT から提供されるホストとポートでリッスンする標準的な Express アプリケーションです。アダプタやハンドラの記述は不要です。

🔧 設定方法

✅ 前提条件

  • AWS アカウントと AWS CLI の最新バージョン
  • Node.js 24 で動作するアプリケーションコード (Express、Hono など)
  • Lambda Web Functions をデプロイするための IAM 権限
1
Hello World アプリケーションのデプロイ
Bash サンプルアプリのデプロイ 
aws lambda-web deploy --name hello-world --hello-world

関数の作成、リビジョンの発行、エンドポイントのアタッチが行われ、1 分以内に稼働中の HTTPS URL が返却されます。

2
独自アプリケーションのデプロイ
Bash ローカルコードのデプロイ 
aws lambda-web deploy --name my-web-app --code ./my-app

ローカルディレクトリのソースコードをバンドルし、Web Function としてデプロイ。1 つのコマンドで関数作成からエンドポイント発行までが完了します。

3
マルチリージョンへのデプロイ
Bash 複数リージョンへの複製デプロイ 
aws lambda-web deploy --name my-web-app --code ./my-app \
    --regions us-east-1,eu-west-1,ap-northeast-1

指定した複数リージョンにコードを複製してデプロイ。グローバル URL が発行され、ユーザーに最も近いリージョンへ自動的にルーティングされます。

4
カナリアリリースの設定
Bash 重み付きトラフィック分割 
aws lambda-web update-web-function-endpoint \
    --function-name my-web-app --endpoint-name dev \
    --auto-deployment-mode Disabled \
    --revision-weights '[{"revisionId": "<current>", "weight": 90}, {"revisionId": "<new>", "weight": 10}]'

エンドポイントのトラフィックをリビジョン間で重み付けし、新リビジョンへ 10% のトラフィックを流すカナリアリリースを構成します。

👍 メリット

ビジネス面

✓コスト最適化: アクティブ CPU 課金により、I/O 待ちの多い Web アプリや API バックエンドのコストを削減
✓グローバル展開の簡素化: 1 コマンドのマルチリージョンデプロイで低レイテンシーなサービスを容易に提供

技術面

✓コールドスタートの大幅削減: 最大 128 同時リクエストでバーストトラフィックでもウォーム環境を共有
✓ネイティブ HTTP ストリーミング: トークンストリーミングや大きなレスポンスの段階的返却に対応
✓安全なデプロイ: 不変リビジョンと重み付き分割でカナリアリリースやロールバックを API 1 回で実現
✓既存エコシステムとの統合: VPC 接続、CloudFront オリジン + OAC、CloudFormation / SAM / CDK と連携可能

⚠️ 制限事項・考慮点

制限事項

✗起動時点のランタイムは Node.js 24 のみ (Python や Java などは未対応)
✗アーキテクチャは Arm64 のみ
✗利用可能リージョンは起動時点で 5 リージョンに限定
✗レイテンシーベースルーティングはベストエフォート

考慮すべき点

💡複数リクエストの同時処理のため、マルチ同時実行を前提とした実装 (グローバル状態の扱いなど) が必要
💡CPU バウンドなワークロードではコスト特性を事前に検証することを推奨
💡キュー処理や AWS サービストリガーには引き続き Lambda Event Functions が適する
💡Event Functions への改名は名称のみだが、社内ドキュメントや IaC コメントの表記更新を検討

🎯 ユースケース

🤖 ユースケース 1: AI 推論エンドポイントのストリーミング配信

シナリオ: LLM を利用したチャットアプリケーションで、生成されたトークンを順次ユーザーへストリーミング返却したい。モデル応答の待機時間が長く、従来のウォールクロック課金ではコストが高くなっていた。

JavaScript トークンストリーミングの実装例 
app.post('/chat', async (req, res) => {
  res.setHeader('Content-Type', 'text/event-stream');
  const stream = await bedrock.converseStream(params);
  for await (const chunk of stream) {
    res.write(`data: ${JSON.stringify(chunk)}\n\n`);
  }
  res.end();
});

✨ 効果: ネイティブ HTTP ストリーミングでトークンを順次返却でき、モデル応答待ちのアイドル時間には CPU 課金が発生しないため、コストを抑えつつ応答性の高い体験を提供できる。

🖥️ ユースケース 2: Next.js による SSR Web アプリケーションのグローバル展開

シナリオ: Next.js の SSR アプリケーションを日本・米国・欧州のユーザーへ低レイテンシーで提供したい。従来はリージョンごとのデプロイとルーティング構成の管理が負担だった。

Bash 3 リージョンへの一括デプロイ 
aws lambda-web deploy --name my-ssr-app --code ./my-ssr-app \
    --regions ap-northeast-1,us-east-1,eu-west-1

✨ 効果: 1 コマンドで 3 リージョンへデプロイされ、グローバル URL により各ユーザーに最も近いリージョンから SSR レスポンスを返却。CloudFront と組み合わせれば静的アセットのキャッシュも可能。

🔄 ユースケース 3: Express ベースのマイクロサービス移行

シナリオ: コンテナや EC2 で稼働中の Express ベースの API マイクロサービスをサーバーレス化したいが、Lambda のイベントハンドラモデルへの書き換えコストが障壁となっていた。

Bash 既存アプリのデプロイ 
# 既存の Express アプリをほぼそのままデプロイ
aws lambda-web deploy --name orders-api --code ./orders-api

✨ 効果: アダプタやコード書き換えなしで既存アプリケーションを移行でき、VPC 接続により既存の RDS などへもアクセス可能。重み付きルーティングで段階的な移行も安全に実施できる。

💰 料金

Lambda Web Functions では、アクティブ CPU 時間と実行環境が保持するメモリに対して課金されます。

課金ディメンション課金ルール
⚙️ CPUアクティブに CPU を使用した時間に対して課金。データベースクエリや API 呼び出しの待機中はほとんど CPU を消費しないため、課金が最小限に抑えられる
🧠 メモリ実行環境が存在している間、保持しているメモリに対して課金

I/O 待ちの多い SSR、API バックエンド、トークンストリーミング型の AI 推論などのワークロードでは、従来のウォールクロック課金と比較してコンピューティングコストを削減できる可能性があります。 詳細は AWS Lambda 料金ページを参照してください。

🔗 関連サービス・機能

⚡ AWS Lambda (Event Functions)

従来のイベント駆動型 Lambda 関数。今回 Lambda Event Functions に改名 (名称変更のみ)。キュー処理やイベント処理には引き続きこちらが適します。

🌐 Amazon CloudFront

Web Function のエンドポイントをオリジンとして利用可能。OAC により CloudFront 経由のみのアクセスに制限するプライベートオリジン構成に対応します。

🔒 Amazon VPC

Web Functions から VPC 内のリソース (Amazon RDS など) へのアクセスをサポートします。

🧰 AWS SAM / AWS CDK / AWS CloudFormation

Web Functions の IaC によるデプロイと管理に対応します。

🧩 Lambda Web Adapter

従来、HTTP フレームワークを Lambda で動かすために利用されていたアダプタ。Web Functions ではアダプタ自体が不要になります。

🚀 まとめ

Lambda Web Functions は、HTTP サーバーをそのまま動かせるプログラミングモデル、最大 128 同時リクエストによるコールドスタート削減、アクティブ CPU 課金という 3 つの大きな変化をもたらす、Lambda の新しいフォームファクターです。 Web アプリケーション、API バックエンド、AI 推論エンドポイントをサーバーレスで構築する際の第一の選択肢となる可能性があります。

✓東京リージョンでも利用可能。まずは aws lambda-web deploy --hello-world での検証から始めることを推奨
✓既存の Express / Hono / Next.js アプリの移行候補を洗い出し、I/O 待ちの多いワークロードからコスト効果を試算
