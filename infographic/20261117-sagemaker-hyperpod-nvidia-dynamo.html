Amazon SageMaker HyperPod 📅 2026 年 11 月 17 日

🚀 HyperPod Inference が NVIDIA Dynamo をサポート

分離型 (Disaggregated) サービングとマルチノード推論を、分散インフラの自前構築なしで実現

📝 概要

Amazon SageMaker HyperPod Inference が NVIDIA Dynamo をサービングランタイムとしてサポートしました。Dynamo は vLLM、SGLang、TensorRT-LLM などの推論エンジンの上で動作し、複数の GPU やノードにまたがってエンジンを協調させるオープンソースの推論フレームワークです。

これにより、単一インスタンスに収まらない大規模モデルの提供や、長いプロンプトでもトークン生成速度を維持する分離型サービングが可能になります。Dynamo の管理は HyperPod の Inference Operator アドオンが担うため、EFA ネットワーキング、GPU キャパシティ管理、障害ノードの自動交換、エンドポイント登録、オートスケーリング、オブザーバビリティを自前で構築する必要はありません。

😣 Before: アップデート前の課題
  • ✗GPU メモリを超える大規模モデルの提供には分散サービングスタックの自前構築・運用が必要
  • ✗長いプロンプトのプレフィルとデコードが同じ GPU を奪い合い、他リクエストの生成が遅延
  • ✗プレフィルとデコードのリソースを独立してスケールできない
  • ✗KV キャッシュを考慮したルーティングには独自の仕組みが必要
😀 After: アップデート後の改善
  • ✓マルチノードサービングで 1 つのモデルを複数ノードにまたがる単一ワーカーとして提供 (ギャングスケジューリングで一括配置)
  • ✓分離型サービングでプレフィルとデコードを別 GPU プールに分割し、独立してサイジング・スケール
  • ✓kv-aware ルーティングで再計算を削減しスループット向上
  • ✓Dynamo オペレーター、Grove、KAI スケジューラ、EFA 設定、KEDA オートスケーリングを HyperPod が管理

分離型サービングでは、プレフィルとデコードが別々のワーカープールで動作し、KV キャッシュは NIXL を介して EFA 経由で転送されます。インフラ管理やオートスケーリングは HyperPod が担います。

⭐ 主要機能

🧩 1. マルチノードサービング
  • 単一インスタンスに収まらない大規模モデルを、複数ノードにまたがる 1 つのワーカーとして提供
  • nodesPerReplica でノード数を指定し、テンソル並列 (tensorParallelism) やパイプライン並列と組み合わせて GPU をノード間に分割
  • ワーカーのノードはギャングスケジューリングされ、全ノードが揃うまで配置されない (部分的な配置は発生しない)
  • マルチノードワーカーには EFA デバイスを持つインスタンスタイプが必須
✂️ 2. 分離型サービング (Disaggregated Serving)
  • プレフィル (プロンプト処理) とデコード (トークン生成) を別々のワーカープールに分割
  • 各ロールのレプリカ数、並列度、インスタンスタイプ、オートスケーリングを独立設定可能
  • KV キャッシュは NVIDIA Inference Xfer Library (NIXL) で転送、対応インスタンスでは EFA + GPUDirect RDMA を使用
  • 長いプロンプトが他のリクエストのトークン生成を妨げなくなる
🎯 3. KV キャッシュ対応ルーティング
  • Dynamo フロントエンドは OpenAI 互換の HTTP API を公開し、routingMode で方式を選択
  • kv-aware (デフォルト): KV キャッシュの重なりが最大のワーカーへルーティングし、再計算を削減してスループットを向上
  • round-robin / random も選択可能
🛠️ 4. マネージドな Dynamo 運用
  • HyperPod Inference アドオン (v3.0.0-eksbuild.1) が Dynamo オペレーター 1.6.2、Grove、KAI スケジューラを一括インストール・アップグレード
  • AWS Deep Learning Containers が vLLM / SGLang / TensorRT-LLM 向けの Dynamo ランタイムイメージ (EFA 対応版含む) を提供
  • Inference Operator がロードバランサー、TLS 証明書、SageMaker AI エンドポイント登録、KEDA オートスケーリングを管理
  • ノードヘルスの監視と障害ノードの自動交換

🧭 2 つのデプロイアプローチ

項目 InferenceEndpointConfig + dynamoSpec DynamoGraphDeployment (DGD) 直接作成

📜 API 変更履歴

本アップデートは Kubernetes カスタムリソース (InferenceEndpointConfig の dynamoSpec フィールドおよび DynamoGraphDeployment) と EKS アドオンの更新により提供されるため、SageMaker API 自体の直接的な変更はありません。

⚙️ 設定方法

📋 前提条件

✓Amazon EKS でオーケストレーションされた SageMaker HyperPod クラスターが作成済みであること
✓ワーカー用の GPU インスタンスが用意されていること (マルチノードワーカーには EFA デバイス付きインスタンスタイプが必須)
✓アドオンがインストールする Dynamo プラットフォーム (1.6.2) と同一リリースの Dynamo ランタイムイメージを使用すること
1
アドオンで Dynamo を有効化
BashHyperPod Inference アドオンの更新
aws eks update-addon \
    --cluster-name $EKS_CLUSTER_NAME \
    --addon-name amazon-sagemaker-hyperpod-inference \
    --addon-version v3.0.0-eksbuild.1 \
    --configuration-values file://addon-config.json \
    --resolve-conflicts OVERWRITE \
    --region $REGION

設定ファイルに "dynamo": { "enabled": true } を含めることで Dynamo オペレーター、Grove、KAI スケジューラをインストールします。--resolve-conflicts OVERWRITE は既存設定を置き換えるため、現在の設定値を取得してから追記します。コンソールからのインストールでは Dynamo はデフォルトで有効です。

2
dynamoSpec 付きの InferenceEndpointConfig を作成
YAML分離型サービングのエンドポイント定義
apiVersion: inference.sagemaker.aws.amazon.com/v1
kind: InferenceEndpointConfig
metadata:
  name: my-endpoint
  namespace: default
spec:
  modelName: my-endpoint
  endpointName: my-endpoint
  instanceType: ml.p5.48xlarge
  invocationEndpoint: v1/chat/completions
  modelSourceConfig:
    modelSourceType: huggingface
    huggingFaceModel:
      modelId: {{HUGGING_FACE_MODEL_ID}}
      tokenSecretRef:
        name: {{SECRET_NAME}}
        key: token
  dynamoSpec:
    modelServer: vllm
    frontend:
      routingMode: kv-aware
    disaggregation:
      prefill:
        replicas: 1
        tensorParallelism: 4
      decode:
        replicas: 1
        tensorParallelism: 4
  worker:
    image: public.ecr.aws/deep-learning-containers/dynamo:1.6.2-efa-vllm-runtime-v1
    modelInvocationPort:
      containerPort: 8000
    modelVolumeMount:
      name: model-weights
    resources: {}

dynamoSpec で推論エンジン、ルーティングモード、サービングモード (aggregation または disaggregation のどちらか一方) を指定します。GPU 数は tensorParallelism などから Inference Operator が自動算出するため、worker.resources に nvidia.com/gpu を設定しません。モデルは Hugging Face のほか、Amazon S3、Amazon FSx、Kubernetes ボリュームからも読み込めます。

3
マニフェストの適用とデプロイの確認
Bashデプロイ状態の確認
kubectl apply -f endpoint.yaml
kubectl get inferenceendpointconfig my-endpoint -n default \
    -o jsonpath='{.status.state}'

状態が DeploymentComplete になればデプロイ完了です。失敗時は DynamoSpecInvalid や DynamoPodsUnschedulable などの理由が status に記録されます。

4
テストリクエストの送信
BashOpenAI 互換 API でのテスト
kubectl port-forward -n default svc/my-endpoint-frontend 8000:8000
curl http://localhost:8000/v1/chat/completions \
    -H "Content-Type: application/json" \

💼 ビジネス面

✓インフラ構築コストの削減: 分散サービングスタックの自前構築・運用が不要になり、エンジニアリングコストを削減
✓GPU 投資の最大化: kv-aware ルーティングと分離型サービングで GPU 使用効率が向上し、同じスループットをより少ないリソースで実現
✓大規模モデル活用の加速: 単一インスタンスに収まらない最先端の大規模モデルを自己ホストで提供可能

🔧 技術面

✓プレフィル / デコードの独立スケーリング: ワークロード特性に応じて各ロールを個別に最適化
✓高速な KV キャッシュ転送: EFA + GPUDirect RDMA により GPU 間で低レイテンシー転送
✓再計算の削減: kv-aware ルーティングでキャッシュを再利用し、Time to First Token を短縮
✓運用の自動化: アドオンによる一括アップグレード、KEDA オートスケーリング、障害ノードの自動交換

⚠️ デメリット・制約事項

🚫 制限事項

✗EKS オーケストレーションの HyperPod クラスターが対象 (Slurm オーケストレーションは対象外)
✗マルチノードワーカーには EFA デバイス付きインスタンスタイプが必須 (EFA なしでは Inference Operator が設定を拒否)
✗既存の InferenceEndpointConfig への dynamoSpec の追加・削除や、aggregation と disaggregation の切り替えは不可 (リソースの削除・再作成が必要)
✗pdSpec、intelligentRoutingSpec、kvCacheSpec、スケールトゥゼロとの併用は不可 (DynamoSpecInvalid となる)
✗dataParallelism は vLLM の単一ノードワーカーのみサポート、パイプライン並列との併用は不可
✗マルチノードワーカーは本リリースでは HyperPod Task Governance と併用不可
✗SGLang の KV 転送はすべてのインスタンスタイプで TCP

🤔 考慮すべき点

⚠フロントエンドはクラスター内で認証を持たないため、VPC CNI アドオンでネットワークポリシーの適用を有効化し、サービングポートへのアクセスを制限することが推奨される
⚠DGD を直接作成する場合、ロードバランサー、TLS、エンドポイント登録、オートスケーリング、NetworkPolicy の設定は自分で行う必要がある
⚠大規模モデルはダウンロードに時間がかかるため、maxDeployTimeInSeconds を十分に大きく設定しないと DynamoDeployTimeout で失敗する可能性がある
⚠フロントエンドやプラットフォームコンポーネントは GPU 不要のため、ml.c5.4xlarge 以上などの CPU インスタンスグループを追加して GPU ノードのキャパシティを節約するのが望ましい
⚠Dynamo エンドポイントのポッドは Pod Security Standard の baseline を満たすが restricted は満たさない

🎯 ユースケース

🐘 ユースケース 1: 単一インスタンスに収まらない超大規模モデルの提供

シナリオ: 数百 GB 規模の重みを持つ大規模モデルを自己ホストで提供したいが、ml.p5.48xlarge (8 GPU) 1 台では GPU メモリが不足する。

YAMLマルチノード Aggregated サービング
dynamoSpec:
  modelServer: vllm
  aggregation:
    nodesPerReplica: 2
    tensorParallelism: 16

効果: 2 ノード (計 16 GPU) にまたがる単一ワーカーとしてモデルを提供できる。ノードはギャングスケジューリングで一括配置され、EFA 設定は Inference Operator が自動で行う。

📚 ユースケース 2: 長文プロンプトを扱う RAG / ドキュメント分析基盤

シナリオ: 長大なコンテキストを含む RAG アプリケーションで、長いプロンプトのプレフィル処理が他のリクエストのトークン生成を遅延させている。

YAML分離型サービング + kv-aware
dynamoSpec:
  modelServer: vllm
  frontend:
    routingMode: kv-aware
  disaggregation:
    prefill:
      replicas: 2
      tensorParallelism: 4
    decode:
      replicas: 1
      tensorParallelism: 4

効果: プレフィルとデコードが別の GPU プールで動作するため、長文プロンプトの処理が他リクエストの生成速度に影響しない。プレフィル側だけを増強するなど、ワークロードに合わせたサイジングが可能。

💬 ユースケース 3: マルチターン会話でのレイテンシー最適化

シナリオ: チャットアプリケーションで、同じ会話のリクエストが毎回異なるワーカーに割り当てられ、コンテキストの再計算によるレイテンシー増加が発生している。

YAMLkv-aware ルーティング
dynamoSpec:
  modelServer: vllm
  frontend:
    routingMode: kv-aware
  aggregation:
    tensorParallelism: 8

効果: kv-aware ルーティングにより、キャッシュ済みコンテキストとの重なりが最大のワーカーへリクエストが振り分けられ、再計算が削減されて Time to First Token が短縮、全体のスループットも向上する。

💰 料金

本機能自体に追加料金はありません。SageMaker HyperPod の利用料金は、クラスターを構成するインスタンスの稼働時間に基づいて課金されます。分離型サービングや kv-aware ルーティングによる GPU 使用効率の向上により、同等のスループットをより少ないインスタンスで実現できる可能性があります。詳細は Amazon SageMaker の料金ページを参照してください。

📌 まとめ

SageMaker HyperPod Inference が NVIDIA Dynamo をマネージドでサポートし、単一インスタンスに収まらない大規模モデルのマルチノード推論と、プレフィル / デコードを分離した効率的なサービングが、分散インフラを自前で構築することなく利用できるようになりました。

✓大規模 LLM の自己ホスト推論を運用しているチームは、HyperPod Inference アドオン v3.0.0 への更新と dynamoSpec によるデプロイを検討することを推奨
✓導入時は EFA 対応インスタンスの選定と VPC CNI のネットワークポリシー有効化を忘れずに計画
