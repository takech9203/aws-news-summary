🔍 AWS IAM - Access Troubleshooter

📅 2026 年 11 月 17 日リリース
AWS IAM Access Troubleshooter IAM Toolbox API

📝 概要

AWS IAM が、アクセス拒否エラーの背後にある認可コンテキスト全体を可視化する新機能「Access Troubleshooter」を発表。対応サービスの API でリクエストが拒否されると、エラーメッセージに一意の認可 ID (Authorization ID) が含まれ、この ID を使って評価されたポリシー、認可コンテキスト、評価結果の詳細を取得できます。

1 回の API 呼び出しで拒否の根本原因を特定でき、試行錯誤による時間のかかるトラブルシューティングが不要になります。IAM ポリシー、SCP、RCP、Permissions Boundary、セッションポリシーなど複数のポリシータイプを組み合わせて運用する組織に特に有効です。

❌ Before: アップデート前の課題
  • エラーメッセージには拒否したポリシーの ARN しか含まれず、評価された他のポリシーを確認できない
  • リクエスト時の認可コンテキスト (条件コンテキストキーの値など) を確認する手段がない
  • 暗黙的な拒否の場合、どのポリシータイプに Allow を追加すべきか特定が困難
  • ポリシー修正と再実行の試行錯誤を繰り返し、拒否を 1 つずつしか解決できない
✅ After: アップデート後の改善
  • 認可 ID を使い GetRequestAuthorizationDetails API で評価詳細を 1 回で取得
  • 評価されたすべてのポリシー、認可コンテキスト、チェックごとの評価結果を確認可能
  • GetRequestAuthorizationPolicy API で拒否発生時点のポリシードキュメントを取得
  • エラーメッセージ内のリンクから IAM コンソールで認可詳細を直接確認
  • 満たされなかったすべてのチェックが表示され、明示的・暗黙的な拒否を同時に解決

⚙️ 主要機能

🆔 認可 ID によるエラー詳細の参照

対応サービスの API でアクセスが拒否されると、エラーレスポンスに一意の認可 ID と IAM コンソールの認可詳細ページへのリンクが自動的に含まれる。認可詳細は非同期に記録されるため、直後に取得できない場合は少し待って再試行。認可詳細は拒否発生から少なくとも 24 時間保持される。

🔍 GetRequestAuthorizationDetails API

認可 ID を指定して、拒否されたリクエストの認可評価の詳細を取得。リクエストコンテキスト (評価された条件コンテキストキーの値)、アクション / リソースのペアごとの評価結果 (ALLOW、EXPLICIT_DENY、IMPLICIT_DENY)、評価されたすべてのポリシーの一覧を返す。評価はチェック (Check) 単位にグループ化され、SCP、RCP、VPC エンドポイントポリシー、リソースベースポリシー、プリンシパル、Permissions Boundary、セッションの各認可要件の結果を個別に確認できる。

📜 GetRequestAuthorizationPolicy API

認可 ID とポリシー URI を指定して、拒否発生時点に AWS が評価したポリシードキュメントを取得。現在のバージョンではなく評価時点のポリシーを返すため、その後ポリシーが変更されていても拒否の原因を正確に調査できる。

🖥️ IAM コンソールでのトラブルシューティング

エラーメッセージ内のリンクからコンソールを開くと、アクション / リソースのペアごとの評価結果と考慮されたポリシーが表示される。拒否されたペアと原因となったポリシー、該当する Deny ステートメント名まで特定できる。

✅ チェックの仕組み

AWS はリクエスト評価時に、適用されるすべての認可要件 (チェック) を確認し、すべてのチェックが許可した場合のみリクエストを許可します。各チェックの結果は Allow、Implicit deny、Explicit deny、No impact のいずれかです。

チェックタイプ確認すべきポリシータイプ説明

🛠️ 設定方法

📌 前提条件

  • 呼び出し元に iam:GetRequestAuthorizationDetails 権限が付与されていること
  • ポリシードキュメントの取得には iam:GetRequestAuthorizationPolicy 権限が付与されていること
  • 拒否が発生したリージョンと同じリージョンで API を呼び出すこと
  • 拒否されたリクエストに組織が記録されている場合、その組織内のアカウントから呼び出すこと

ステップ 1: 認可 ID の確認

アクセス拒否エラーのレスポンスに含まれる認可 ID (例: EXAMPLE1a2b3c4d5e6f7g8h9i0j) を確認します。コンソールのリンクが含まれる場合は、リンクを開くだけで認可詳細を確認できます。

ステップ 2: 認可詳細の取得

Bash 認可評価の詳細を取得 
aws iam-toolbox get-request-authorization-details \
    --region us-east-1 \
    --authorization-id EXAMPLE1a2b3c4d5e6f7g8h9i0j

evaluatedEffect が EXPLICIT_DENY または IMPLICIT_DENY の評価を確認し、拒否されたチェックの relevantPolicyTypes から確認すべきポリシータイプを特定します。明示的な拒否の場合は、チェックの matchedPolicies から拒否したポリシーとステートメントを特定します。

ステップ 3: 拒否時点のポリシードキュメントの取得

Bash 拒否発生時点のポリシーを取得 
aws iam-toolbox get-request-authorization-policy \
    --region us-east-1 \
    --authorization-id EXAMPLE1a2b3c4d5e6f7g8h9i0j \
    --policy-uri arn:aws:iam::000111222333:policy/InstanceProfilePermissions

認可 ID と、ステップ 2 の policies リストに含まれる uri を指定して、拒否発生時点に評価されたポリシードキュメントを取得します。レスポンスの policyDocument に JSON 形式でポリシー本文が含まれます。

ステップ 4: ポリシーの修正

明示的な拒否の場合は該当する Deny ステートメントを削除または範囲を絞り、暗黙的な拒否の場合は該当するポリシータイプに Allow ステートメントを追加します。修正前に、拒否が意図したものでないか (セッションタグの欠落や想定外のネットワーク経路など、リクエストコンテキスト側に原因がないか) を必ず確認します。

🔧 技術面

✓完全な認可コンテキストの可視化: 評価されたすべてのポリシー、条件コンテキストキーの値、チェックごとの結果を 1 回の API 呼び出しで確認
✓暗黙的な拒否の原因特定: relevantPolicyTypes でどのチェックに Allow が不足しているかを特定し、複数の不足を同時に解決

⚠️ デメリット・制約事項

🚧 制限事項

⚠️認可 ID の付与は保証されない。評価されたポリシーが多すぎる場合、未対応のサービス / API / リクエストタイプ (サービスによる代理リクエストや匿名リクエストなど) の場合は認可 ID が返されない
⚠️対応サービスは段階的に拡大中で、現時点では AWS CodeDeploy、IAM、AWS KMS、AWS STS、AWS Step Functions、Amazon EC2、Amazon ECR、Amazon Kinesis Data Streams、Amazon SQS の一部 API に限られる
⚠️認可詳細の保持期間は少なくとも 24 時間であり、長期保存はされない
⚠️リージョナル API のため、拒否が発生したリージョンと同じリージョンで呼び出す必要がある

🤔 考慮すべき点

💭認可詳細は非同期に記録されるため、拒否直後は取得できない場合がある (Not Found の場合は少し待って再試行する)
💭iam:GetRequestAuthorizationDetails 権限を持つユーザーは、単一アカウントまたは単一組織内のリクエストの認可詳細を参照できるため、権限の付与範囲を適切に設計する必要がある
💭組織をまたぐリクエストでは、自組織に関する詳細のみが返され、他組織のポリシーやコンテキストキーの値は参照できない
💭評価レベルの matchedPolicies フィールドは非推奨となっており、checks を使用する必要がある

🎯 ユースケース

1️⃣ 開発中のアクセス拒否エラーの迅速な解決

シナリオ: 開発者が新しいアプリケーションのデプロイ中に iam:CreateInstanceProfile でアクセス拒否エラーに遭遇。どのポリシーが原因か不明で、従来は管理者に調査を依頼していた。

Bash
aws iam-toolbox get-request-authorization-details \
    --region us-east-1 \
    --authorization-id EXAMPLE1a2b3c4d5e6f7g8h9i0j

効果: 評価結果からインラインポリシーの DenyCreateInstanceProfile ステートメントによる明示的な拒否であることを即座に特定でき、管理者へのエスカレーションなしで該当ステートメントの修正を依頼できる。

2️⃣ SCP / RCP が原因の暗黙的な拒否の切り分け

シナリオ: マルチアカウント環境で、アイデンティティベースポリシーでは許可されているはずの操作が拒否される。SCP、RCP、Permissions Boundary のどれが原因か切り分けに時間がかかっていた。

Bash
aws iam-toolbox get-request-authorization-details \
    --region ap-northeast-1 \
    --authorization-id <認可 ID> \
    --query 'evaluations[].checks[?checkResult!=`ALLOW`]'

効果: チェック単位の結果から、どの組織ターゲット (ルート、OU、アカウント) の SCP が暗黙的な拒否を発生させているかを特定でき、組織レベルのポリシー修正箇所を即座に把握できる。

3️⃣ 拒否発生時点のポリシー内容の監査

シナリオ: 一時的に発生していたアクセス拒否の原因を調査したいが、その後ポリシーが更新されており、現在のポリシーからは原因を再現できない。

Bash
aws iam-toolbox get-request-authorization-policy \
    --region us-east-1 \
    --authorization-id <認可 ID> \
    --policy-uri <ポリシー URI>

効果: 拒否発生時点に評価されたポリシードキュメントを取得でき、現在のポリシーと比較して変更の影響や拒否の原因を正確に監査できる。

🌏 利用可能リージョン

Access Troubleshooter のサポートは、AWS のサービスおよびリージョン全体に段階的に展開されています。GetRequestAuthorizationDetails と GetRequestAuthorizationPolicy はリージョナル API であり、拒否が発生したリージョンと同じリージョンで呼び出す必要があります。対応サービスおよび API の最新情報は公式ドキュメントを参照してください。

SCP や RCP による組織レベルの拒否もチェック単位で可視化され、組織ターゲットごとに評価結果を確認できる。

🔎 IAM Access Analyzer

外部アクセスや未使用アクセスの分析を行うサービス。Access Troubleshooter と組み合わせて権限の最小化と問題解決の両面をカバーできる。

📜 AWS CloudTrail

API 呼び出しの記録を提供する。Access Troubleshooter は CloudTrail では見えない認可評価の内部詳細を提供する。

📌 まとめ

IAM Access Troubleshooter により、これまでブラックボックスだったアクセス拒否時の認可評価の全体像を、認可 ID を使って 1 回の API 呼び出しで確認できるようになりました。SCP や Permissions Boundary を含む複雑なポリシー構成を運用する環境では、権限トラブルの解決時間を大幅に短縮できます。まずは対応サービス (IAM、STS、EC2、SQS など) でアクセス拒否エラーが発生した際に、エラーメッセージの認可 ID と GetRequestAuthorizationDetails API を活用することを推奨します。
