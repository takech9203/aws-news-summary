AWS IoT Core

🌐 HTTP ルールアクション向け専用 IPv6 アドレスレンジ

📅 リリース日: 2026 年 11 月 25 日 ｜ HTTPS エンドポイントへのインバウンドを AWS IoT Core だけに限定

📋 概要

AWS IoT Core のルールエンジンが、HTTP ルールアクションで HTTPS トラフィックを送信する際に、 公開された専用の IPv6 アドレスレンジを使用するようになりました。 API Gateway リソースポリシー、セキュリティグループ、ファイアウォールルールに固定レンジを登録することで、 HTTPS エンドポイントへのインバウンドトラフィックを AWS IoT Core のルールエンジンからのものだけに限定でき、 エンドポイントの攻撃対象領域を大幅に削減できます。

❌ Before: アップデート前の課題
  • 送信元 IP が非公開のため、送信元アドレスによるエンドポイント保護ができなかった
  • HTTPS エンドポイントをパブリックインターネットに広く公開する必要があり、不正アクセスやスキャンのリスクに晒されていた
  • Sigv4 や独自ヘッダーなどの認証に加えた、ネットワークレイヤーの多層防御の手段が限られていた
✅ After: アップデート後の改善
  • リージョンごとに公開された固定 IPv6 レンジ (例: us-east-1 は 2600:1f33:8000::/48) から送信されるように
  • リソースポリシーやセキュリティグループで送信元レンジを許可するだけで、AWS IoT Core 以外からのアクセスを遮断可能
  • レンジはルールエンジンアクション専用で変更されないため、一度設定すれば安定して運用できる

ルールエンジンは専用 IPv6 レンジからのみ HTTPS エンドポイントへデータを送信するため、 エンドポイント側のファイアウォールやリソースポリシーでこのレンジだけを許可すれば、その他の送信元からのアクセスを遮断できます。

⚡ 主要機能

1️⃣ 専用 IPv6 アドレスレンジの公開
  • ルールエンジンの HTTP アクションが使用する IPv6 レンジがリージョンごとに公開
  • 各レンジは /48 の固定 CIDR で、ルールエンジンアクション専用・変更なし
  • 新しいリージョンのレンジは、利用可能になり次第ドキュメントの表に追加
2️⃣ 送信元アドレスによるエンドポイント保護
  • API Gateway リソースポリシーの aws:SourceIp 条件でレンジ外からのアクセスを拒否可能
  • セキュリティグループのインバウンドルールで、該当リージョンのレンジからの TCP 443 番ポートのみ許可可能
  • AWS Network Firewall などのファイアウォールルールにも適用可能
3️⃣ DNS レコードによる IPv6 配信の制御
  • デフォルトは IPv4。エンドポイントのホスト名が AAAA レコードのみを公開している場合に IPv6 で接続
  • AWS IoT Core 側に IP バージョン切り替え設定はなく、エンドポイントの DNS 設定で制御
  • IPv4 の同等レンジは存在しないため、送信元制限にはエンドポイントを IPv6 のみで到達可能にする必要あり

🛠️ 設定方法

✅ 前提条件

✓AWS IoT Core を利用しており、HTTP ルールアクションでデータを HTTPS エンドポイントへ転送している (または転送を計画している)
✓HTTPS エンドポイントの DNS レコード (A / AAAA) を管理できる
✓エンドポイントが IPv6 で到達可能である

📌 手順

1
エンドポイントを IPv6 のみで到達可能にする

A レコードと AAAA レコードの両方を公開した状態で HTTP アクションの宛先 (Topic Rule Destination) を作成し、確認プロセスを完了します。 宛先確認は常に IPv4 で行われるためです。確認完了後に A レコードを削除し、AAAA レコードのみを残します。 これ以降、ルールエンジンは IPv6 で接続します。

2
公開された IPv6 レンジを許可する

利用リージョンのレンジを、エンドポイント側のアクセス制御に追加します。セキュリティグループの例:

Bash 東京リージョンのレンジからの TCP 443 を許可 
aws ec2 authorize-security-group-ingress \
    --group-id sg-0123456789abcdef0 \
    --ip-permissions 'IpProtocol=tcp,FromPort=443,ToPort=443,Ipv6Ranges=[{CidrIpv6=2406:da33:4000::/48,Description="AWS IoT Core rules engine ap-northeast-1"}]'

API Gateway の場合はリソースポリシーで、ファイアウォールの場合はルールグループで同様にレンジを許可します。

3
HTTP ルールアクションを作成または更新する
Bash MQTT トピックのメッセージを HTTPS エンドポイントへ転送 
aws iot create-topic-rule \
    --rule-name ForwardToMyEndpoint \
    --topic-rule-payload '{
        "sql": "SELECT * FROM '\''devices/+/data'\''",
        "ruleDisabled": false,
        "awsIotSqlVersion": "2016-03-23",
        "actions": [
            {
                "http": {
                    "url": "https://api.example.com/telemetry",
                    "confirmationUrl": "https://api.example.com"
                }
            }
        ]
    }'

宛先が確認済みで ENABLED 状態であれば、ルールエンジンは専用 IPv6 レンジからデータを送信します。

⚠️ デメリット・制約事項

🚧 制限事項

✗IPv4 の同等レンジは提供されず、送信元制限にはエンドポイントを IPv6 のみ (AAAA レコードのみ) で到達可能にする必要がある
✗宛先確認 (Destination Confirmation) は常に IPv4 で行われるため、確認時には A レコードを公開して IPv4 で到達可能にする必要がある (確認後に削除)
✗対象は HTTP ルールアクションのみ。その他のルールアクションはデュアルスタック宛先に IPv4 で接続するため、許可すべきレンジは存在しない
✗ドキュメントの表に記載のないリージョンには、ルールエンジンの IPv6 レンジがない

🤔 考慮すべき点

⚠宛先の再確認 (ステータスを IN_PROGRESS に変更して確認リクエストを再送) を行う場合は、事前に A レコードを復元する必要がある
⚠エンドポイント側のインフラ (ロードバランサー、Web サーバー、DNS) が IPv6 に対応している必要がある
⚠リージョンごとにレンジが異なるため、複数リージョンで利用している場合は各リージョンのレンジをすべて許可する必要がある

🎯 ユースケース

1. API Gateway で受けるテレメトリ収集 API の保護

シナリオ: テレメトリデータを HTTP ルールアクション経由で API Gateway の REST API に集約しているが、API がパブリックに公開されており、スキャンや不正リクエストが懸念される。

JSONリソースポリシーの Deny ステートメント
{
    "Effect": "Deny",
    "Principal": "*",
    "Action": "execute-api:Invoke",
    "Resource": "execute-api:/*",
    "Condition": {
        "NotIpAddress": {
            "aws:SourceIp": ["2406:da33:4000::/48"]
        }
    }
}
✅ 効果: 東京リージョンのルールエンジン以外からの API 呼び出しをネットワークレイヤーで拒否し、API の露出を最小化。
2. EC2 上の自社 Web サービスへの直接ルーティング

シナリオ: ALB 配下の EC2 インスタンスで稼働する自社アプリケーションにデバイスデータを転送しており、セキュリティグループで送信元を限定したい。

Bashセキュリティグループのインバウンドルール追加
aws ec2 authorize-security-group-ingress \
    --group-id sg-0123456789abcdef0 \
    --ip-permissions 'IpProtocol=tcp,FromPort=443,ToPort=443,Ipv6Ranges=[{CidrIpv6=2600:1f33:8000::/48}]'
✅ 効果: セキュリティグループだけで AWS IoT Core 以外からの接続を遮断でき、WAF や追加の認証基盤を導入せずに防御レイヤーを追加。
3. オンプレミスシステムやパートナーサービスへの安全なデータ連携

シナリオ: 工場のオンプレミスシステムや外部パートナーの API にデバイスデータを連携しているが、受信側のファイアウォールで許可すべき送信元が明確でなく、広い範囲を開放していた。

Textファイアウォールルール例
ファイアウォールルール:
  許可: 送信元 2a05:d033:8000::/48 (eu-west-1 のルールエンジン)
        宛先 TCP 443
  拒否: その他すべてのインバウンド
✅ 効果: 受信側に伝えるべき送信元レンジが明確になり、パートナー側・オンプレミス側のファイアウォールを最小権限で構成可能。

📝 まとめ

AWS IoT Core の HTTP ルールアクションが専用 IPv6 レンジからトラフィックを送信するようになり、 HTTPS エンドポイントを AWS IoT Core からのアクセスのみに限定できるようになりました。 デバイスデータを外部の Web サービスやオンプレミスに転送している場合は、エンドポイントを AAAA レコードのみの構成に移行し、 リージョンごとの公開レンジを許可リストに追加することで、追加コストなしでエンドポイントの露出を大幅に削減できます。 まずは開発者ガイドのレンジ一覧と宛先確認時の IPv4 要件を確認し、段階的な移行を検討することを推奨します。
