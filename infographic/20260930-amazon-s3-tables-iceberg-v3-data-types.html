Amazon S3 Tables

🧊 Apache Iceberg V3 全データ型サポート

geometry / geography、ナノ秒タイムスタンプ、unknown 型、列デフォルト値が追加 — 📅 リリース日: 2026 年 9 月 30 日

📋 概要

Amazon S3 Tables が Apache Iceberg V3 仕様の全データ型をサポートしました。 空間データを格納する geometry / geography 型、スキーマ進化のプレースホルダーとなる unknown 型、ナノ秒精度タイムスタンプ timestamp(9) / timestamptz(9)、 および 列のデフォルト値が新たに追加され、既存の variant 型・削除ベクトル・行リネージと合わせて V3 のデータ型を網羅的にカバーします。

車両管理や資産マッピングなどの位置情報ワークロード、テレメトリや金融取引のような高精度時刻を扱うワークロードを、 エンコードの工夫なしに単一のデータレイクへ統合できます。S3 Tables の自動メンテナンスは V3 テーブルにも適用されます。

❌ アップデート前の課題

✗位置情報 (点、線、ポリゴン) は WKT 文字列や緯度・経度の double ペアとしてエンコードが必要
✗ナノ秒精度のイベント時刻は整数型にエンコードし、読み取り時に変換が必要
✗エンコード値では位置や時刻で直接フィルタリングできず、変換オーバーヘッドが発生
✗列追加時、既存行への値設定にはバックフィル (データの書き直し) が必要

✅ アップデート後の改善

✓geometry / geography 型で空間データをネイティブ格納、クエリ時に位置で直接フィルタリング
✓timestamp(9) / timestamptz(9) でソース精度のままナノ秒タイムスタンプを記録
✓列デフォルト値により、バックフィルなしで既存行に値が反映
✓unknown 型で型未確定の列を定義でき、移行やスキーマ進化が容易に
✓V3 全データ型のサポートで、V3 への移行判断がシンプルに

位置情報や高精度時刻のデータをエンコードせずに V3 のネイティブデータ型として S3 Tables に格納し、 EMR Spark や AWS Glue ETL などの V3 対応エンジンから直接クエリできます。自動メンテナンスは V3 テーブルにも適用されます。

⚡ 主要機能

🌍 1. 地理空間データ型 (geometry / geography)

→ 点、線、ポリゴンをエンコード文字列や緯度・経度ペアではなく、ネイティブ列として格納

→ geometry はデカルト平面、geography は回転楕円体上の球面座標として座標を扱う。両型とも SRID 0 と SRID 4326 を認識

→ ST_Intersects などの空間述語により、クエリ時に位置で直接フィルタリング可能

⏱️ 2. ナノ秒精度タイムスタンプ (timestamp(9) / timestamptz(9))

→ timestamp(9) はタイムゾーンなし、timestamptz(9) はタイムゾーンありのナノ秒精度タイムスタンプ

→ テレメトリ、センサーフュージョン、金融ワークロードでソース精度のまま時刻を記録でき、整数エンコードと読み取り時の変換が不要に

🏷️ 3. 列のデフォルト値 (column default values)

→ initial-default (列追加前のレコード用) と write-default (書き込み時に列が省略された場合用) を設定可能

→ 値はスキーマメタデータに 1 回だけ保存され、読み取り時に補完されるためバックフィル不要

→ unknown、variant、geometry、geography 型の列は null デフォルトが必須

❓ 4. unknown 型

→ 型が未確定の列を表すプレースホルダー型。必ず optional で、常に null として読み取られ、データファイルには書き込まれない

→ 他のテーブルフォーマットからの移行やスキーマ進化の途中段階で有用。後から具体的な型に進化可能

🔗 5. 既存の V3 サポートとの統合

→ サポート済みの variant 型、削除ベクトル、行リネージと合わせて V3 仕様の全データ型をカバー

→ 自動メンテナンス (コンパクション、スナップショット管理、未参照ファイル削除) が V3 テーブルにも適用され、スケールしてもパフォーマンスとコスト効率を維持

ステップ 1: V3 テーブルを作成する

SQL地理空間列を含む V3 テーブルの作成
CREATE TABLE IF NOT EXISTS myns.vehicle_telemetry (
    vehicle_id     string,
    event_time     timestamp,
    position       geometry(4326),
    service_area   geography(4326),
    firmware       string
)
USING iceberg
TBLPROPERTIES ('format-version' = '3')

format-version テーブルプロパティに 3 を指定して、地理空間列 (geometry / geography) を含む Iceberg V3 テーブルを作成します。SRID 4326 を空間参照系として指定しています。

ステップ 2: 地理空間データを挿入し、位置でフィルタリングする

SQL空間値の挿入と ST_Intersects による位置フィルタ
INSERT INTO myns.vehicle_telemetry VALUES (
    'v-1024',
    TIMESTAMP '2026-09-18 14:22:31.123456',
    ST_SetSrid(ST_GeomFromWKT('POINT (1 2)'), 4326),
    ST_SetSrid(ST_GeogFromWKT('POLYGON ((0 0, 10 0, 10 10, 0 10, 0 0))'), 4326),
    'fw-3.2.1'
);

SELECT vehicle_id, event_time
FROM myns.vehicle_telemetry
WHERE ST_Intersects(
        position,
        ST_SetSrid(ST_GeomFromWKT('POLYGON ((0 0, 10 0, 10 10, 0 10, 0 0))'), 4326)
      );

ST_GeomFromWKT で WKT から空間値を生成して挿入し、ST_Intersects 述語で指定ポリゴンと交差する車両位置をクエリ時に直接フィルタリングします。

ステップ 3: ナノ秒精度タイムスタンプのテーブルを作成する

SQLtimestamptz(9) 列を持つテーブル
CREATE TABLE IF NOT EXISTS myns.trades (
    trade_id     bigint,
    executed_at  timestamptz(9),
    symbol       string,
    price        decimal(18,8)
)
USING iceberg
TBLPROPERTIES ('format-version' = '3')

timestamptz(9) 列により、タイムゾーン付きのナノ秒精度で約定時刻を記録するテーブルを作成します。タイムゾーンが不要な場合は timestamp(9) を使用します。

ステップ 4: デフォルト値付きの列を追加する

SQLバックフィル不要の列追加
ALTER TABLE myns.orders
ADD COLUMN currency string DEFAULT 'USD'

既存テーブルにデフォルト値 USD 付きの currency 列を追加します。列追加前に書き込まれた既存行も null ではなく USD を返し、データファイルの書き直し (バックフィル) は発生しません。

ステップ 5: 既存の V2 テーブルを V3 にアップグレードする (必要な場合)

SQLV2 から V3 へのアトミックなアップグレード
ALTER TABLE myns.existing_table
SET TBLPROPERTIES ('format-version' = '3')

既存の V2 テーブルを、データの書き直しなしでアトミックに V3 へアップグレードします。V3 へのアップグレードは一方向で V2 に戻せないため、テーブルを読み書きするすべてのエンジンが V3 に対応していることを事前に確認してください。

💡 メリット

💼 ビジネス面

→データアーキテクチャの簡素化: エンコード・デコード処理や別システムの維持が不要になり、パイプラインの開発・運用コストを削減
→コンプライアンスとガバナンスの強化: 削除ベクトルや行リネージと組み合わせて、GDPR 対応の削除や行レベルの変更追跡を含むデータレイク全体を V3 に統一
→運用負荷の軽減: 自動メンテナンスが V3 テーブルにも適用され、データ増加時も手動管理なしでパフォーマンスとコスト効率を維持

⚙️ 技術面

→ネイティブ型による性能向上: クエリ時のフィルタリングが直接可能になり、変換オーバーヘッドが解消
→ソース精度の保持: テレメトリや金融データをナノ秒精度のまま格納
→バックフィル不要のスキーマ進化: 大規模テーブルでも低コストで列追加が可能
→移行の柔軟性: unknown 型により、他フォーマットからの段階的な移行やスキーマ設計の先行定義が可能

⚠️ デメリット・制約事項

🚫 制限事項

✗V3 データ型は Parquet データファイル形式のテーブルのみサポート (ORC、Avro は非対応)
✗sort / Z-order コンパクション戦略は variant、geometry、geography、ナノ秒タイムスタンプ型に非対応
✗Amazon Athena (Trino) は V3 テーブルを読み取れないため、Athena 利用ワークロードでは V3 アップグレードに注意
✗unknown、variant、geometry、geography 型の列には非 null のデフォルト値を設定できない
✗variant 型は一部リージョンのみで利用可能 (東京リージョンを含む 15 リージョン)

🤔 考慮すべき点

⚠️ 一方向アップグレード: V2 から V3 へのアップグレードは標準操作ではダウングレード不可。事前にテーブルへアクセスする全エンジンとサードパーティツールの V3 対応を確認すること
⚠️ 既存データは自動変換されない: エンコード済み座標列 (double ペアや WKT 文字列) は V3 アップグレード時に自動変換されず、地理空間型の採用には新しい列の追加とデータ移行が必要
⚠️ 精度の切り捨て: マイクロ秒精度までのエンジンでナノ秒列を読み書きすると値が切り捨てられる。利用エンジンのナノ秒精度対応を事前に確認
⚠️ 測地述語はエンジン依存: geography 型に対する測地空間述語はエンジン依存であり、Amazon EMR と AWS Glue の Apache Spark における空間述語は geometry 型を対象とする

🎯 ユースケース

🚚 ユースケース 1: フリートトラッキングと配送エリア分析

シナリオ: 物流企業が数万台の車両の位置情報を収集し、特定の配送エリア内にいる車両をリアルタイムに特定したい。従来は緯度・経度を double 値のペアで格納し、アプリケーション側で距離計算を行っていた。

SQL対象エリア内の車両を直接フィルタリング
SELECT vehicle_id, event_time
FROM myns.vehicle_telemetry
WHERE ST_Intersects(
        position,
        ST_SetSrid(ST_GeomFromWKT('POLYGON ((139.6 35.5, 139.9 35.5, 139.9 35.8, 139.6 35.8, 139.6 35.5))'), 4326)
      )

✅ 効果: geometry 型と空間述語により、クエリ時に対象エリア内の車両を直接フィルタリング。アプリケーション側の距離計算ロジックが不要になり、分析パイプラインが簡素化される。

💹 ユースケース 2: 金融取引データのナノ秒精度記録

シナリオ: 証券取引システムの約定データを S3 Tables のデータレイクに格納し、取引の正確な順序を保持したまま監査や市場分析に利用したい。従来はナノ秒時刻を bigint にエンコードして格納していた。

SQLtimestamptz(9) による約定データテーブル
CREATE TABLE IF NOT EXISTS myns.trades (
    trade_id     bigint,
    executed_at  timestamptz(9),
    symbol       string,
    price        decimal(18,8)
)
USING iceberg
TBLPROPERTIES ('format-version' = '3')

✅ 効果: ソース精度のまま約定時刻を記録でき、読み取り時の変換処理が不要に。ナノ秒レベルの時刻順序が保持され、監査要件や高頻度取引の分析に対応できる。

📦 ユースケース 3: バックフィルなしの大規模テーブルへの列追加

シナリオ: 数十億行の注文テーブルに通貨コード列を追加したい。従来は既存行に値を設定するために大規模なバックフィルジョブが必要で、コストと時間がかかっていた。

SQLデフォルト値付きの列追加
ALTER TABLE myns.orders
ADD COLUMN currency string DEFAULT 'USD'

✅ 効果: デフォルト値はスキーマメタデータに 1 回だけ保存され、読み取り時に補完されるため、データファイルの書き直しが発生しない。大規模テーブルでも即座に、追加コストなしでスキーマ進化が完了する。

💰 料金

今回の V3 データ型サポートに伴う追加料金はありません。 S3 Tables の標準料金 (ストレージ、リクエスト、自動メンテナンスに伴うモニタリング・コンパクション料金) がそのまま適用されます。 詳細は Amazon S3 の料金ページを参照してください。

🔗 関連サービス・機能

→Amazon EMR: EMR Spark リリース 7.12 以降で V3 テーブルの読み書きに対応。地理空間型の利用には Spark 設定の有効化が必要

📝 まとめ

S3 Tables が Apache Iceberg V3 の全データ型をサポートしたことで、地理空間データやナノ秒精度の時刻データを含むワークロードを、 エンコードの工夫なしに単一のデータレイクへ統合できるようになりました。 削除ベクトル・行リネージ・variant 型と合わせて V3 の主要機能が出揃ったため、更新頻度の高いテーブルや位置情報・テレメトリ系ワークロードでは V3 の採用を検討する価値があります。

ただし V3 へのアップグレードは一方向であり、Amazon Athena が V3 に未対応である点など、 テーブルにアクセスする全エンジンの対応状況を確認した上で移行計画を立てることを推奨します。
