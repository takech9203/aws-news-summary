Kiro IDE 1.4.236

🧩 GitLab からのインストール、Permission Request Hook、MCP の組織サインイン

📅 リリース日: 2026 年 11 月 18 日 | 🛠️ Kiro IDE 1.4.236 アップデート

📌 概要

Kiro IDE 1.4.236 がリリースされ、3 つの主要機能が追加されました。GitLab のパブリック URL を貼り付けるだけでカスタム Power や Skill をインストールできる機能、ツール呼び出しの承認プロンプトにスクリプトが自動応答できる Permission Request Hook、そして組織の ID プロバイダーを通じた MCP サーバーへの 1 回のサインイン共有です。あわせて Pre Tool Use Hook によるツール入力の実行前置換、チャットの表示位置の移動、Memories ビューの改善も含まれています。

❌ アップデート前の課題

  • Power や Skill のインストール元は GitHub の URL のみで、GitLab でホストされたリポジトリから直接インストールできなかった
  • ツール呼び出しの承認プロンプトに人間の応答が必要で、無人セッションでは定型的な承認待ちでエージェントが停止していた
  • HTTP MCP サーバーごとに個別のサインインが必要で、多数の社内 MCP サーバー利用時に認証操作が繰り返し発生していた

✅ アップデート後の改善

  • GitLab のパブリック URL の貼り付けでインストール可能になり、セルフホスト型 GitLab にも設定追加で対応
  • Permission Request Hook のスクリプトが定型的な承認プロンプトに自動応答し、無人セッションの継続実行が可能に
  • Pre Tool Use Hook がツール入力を実行前に置換でき、承認プロンプトには最終的な引数を表示
  • 対象の HTTP MCP サーバー群に対して組織の ID プロバイダー経由の 1 回のサインインを共有可能に

Kiro IDE 1.4.236 に追加された 3 つの機能領域を示しています。GitLab を含むインストール元の拡大、フックによる承認とツール入力の自動化、組織の ID プロバイダーを介した MCP サーバーへの一括サインインで構成されます。

⚡ 主要機能

🦊 1. GitLab からの Powers / Skills インストール
  • GitHub と同じ操作で、GitLab のパブリック URL を貼り付けてカスタム Power のインストールや Skill のインポートができる
  • セルフホスト型 GitLab は、事前に kiroAgent.powers.trustedGitLabHosts 設定にホストを追加する
  • 社内資産を GitLab で管理している組織でも、Power / Skill の配布と再利用がしやすくなる
📜 2. Permission Request Hook によるスクリプト応答
  • Hook エディタで作成すると、Kiro がツール呼び出しの承認を求める直前にコマンドが実行される
  • スクリプトが定型的なプロンプトに応答できるため、誰も監視していないセッションでも処理を継続できる
  • Pre Tool Use Hook は、ツール呼び出しの入力を実行前に置き換えられるようになった
  • 承認プロンプトには最終的な引数が表示され、置換後の実際の実行内容を確認したうえで承認できる
🔐 3. MCP サーバーへの組織サインイン
  • 対象の HTTP MCP サーバーは、サーバーごとの個別サインインの代わりに、組織の ID プロバイダーを通じた 1 回のサインインを共有できる
  • 管理者から提供された ID プロバイダー情報を MCP 設定に追加し、MCP Servers ビューの「Organization sign-in」行で [Sign in] を選択する
  • 同日リリースの Kiro CLI 3.5.0 でも、V3 セッション向けに同様の組織サインインを提供
✨ 4. その他の改善
  • チャットをサイドバーとエディタ領域の間で移動できるようになった
  • Memories ビューから Memory 設定を選択できるようになった

🛠️ 設定方法

前提条件

✓Kiro IDE 1.4.236 以降にアップデートしていること
✓セルフホスト GitLab を利用する場合は、対象ホストを信頼済みとして設定できること
✓MCP 組織サインインを利用する場合は、管理者から組織の ID プロバイダー情報の提供を受けていること

手順

1
GitLab から Power / Skill をインストールする

インストール画面に GitLab のパブリック URL を貼り付けます。セルフホスト型 GitLab の場合は、先に設定へホストを追加します。

JSON セルフホスト GitLab ホストの追加 
{
  "kiroAgent.powers.trustedGitLabHosts": ["gitlab.example.com"]
}

信頼するホスト名を設定に追加することで、そのインスタンスの URL からのインストールが可能になります。

2
Permission Request Hook を作成する

Hook エディタで Permission Request Hook を作成し、承認プロンプトの直前に実行するコマンドを指定します。スクリプトの応答により、定型的なツール呼び出しの承認を自動化できます。

3
MCP の組織サインインを設定する

管理者から提供された ID プロバイダー情報をユーザーの MCP 設定に追加します。その後、MCP Servers ビューの「Organization sign-in」行で [Sign in] を選択すると、対象のサーバー群に対して 1 回のサインインが共有されます。

💎 メリット

💼 ビジネス面

✓GitLab 利用組織への対応: 社内資産を GitLab で管理する組織でも Power / Skill を直接配布でき、導入の障壁が下がる
✓無人運用の実現: 夜間バッチや CI 連携など監視者のいないセッションでもエージェントを継続稼働できる
✓認証運用の簡素化: 一括サインインで、多数の社内 MCP サーバー利用時の認証の手間とサポート負荷を削減できる

⚙️ 技術面

✓インストール元の統一的な扱い: GitHub と GitLab を同じ操作で扱え、セルフホスト環境も設定追加のみで利用できる
✓フックの表現力向上: 入力の置換と最終引数が表示される承認プロンプトの組み合わせで、制御と透明性を両立
✓MCP 認証の一元化: サーバーごとのブラウザサインインフローが不要になり、ID プロバイダーを起点とした一貫した認証が可能

⚠️ デメリット・制約事項

🚧 制限事項

✗GitLab からのインストールはパブリック URL が対象で、セルフホスト型は trustedGitLabHosts への事前登録が必要
✗MCP の組織サインインは対象 (eligible) の HTTP MCP サーバーに限られる
✗組織サインインの利用には、管理者から提供される ID プロバイダー情報が必要

🤔 考慮すべき点

⚠Permission Request Hook で承認を自動化する場合、意図しないツール呼び出しまで許可しないよう、スクリプトの応答条件を慎重に設計する
⚠Pre Tool Use Hook の入力置換を利用する場合、承認プロンプトに表示される最終的な引数を確認する運用を徹底する
⚠信頼する GitLab ホストの追加は許可範囲を広げる操作のため、組織のセキュリティポリシーに沿って管理する

🎯 ユースケース

📦 ユースケース 1: GitLab で管理する社内 Power の配布

シナリオ: 開発標準やコーディング規約を Power としてセルフホスト GitLab で管理している組織が、各開発者の Kiro IDE に配布したい。

Text実装例
1. kiroAgent.powers.trustedGitLabHosts に社内 GitLab のホストを追加
2. 開発者に Power リポジトリの URL を共有
3. 各開発者が URL を貼り付けて Power をインストール
✅ 効果: GitHub への移行やミラーリングを行わずに、既存の GitLab 資産をそのまま Kiro の Power / Skill として配布できる。
🌙 ユースケース 2: 無人セッションでの承認自動化

シナリオ: 長時間実行するリファクタリングタスクを夜間に走らせたいが、定型的なツール呼び出しの承認プロンプトで処理が停止してしまう。

Text実装例
1. Hook エディタで Permission Request Hook を作成
2. 許可してよいツール呼び出しの条件をスクリプトに実装
3. 条件に一致する承認プロンプトにはスクリプトが自動応答
4. 条件外のプロンプトは従来どおり人間の確認に委ねる
✅ 効果: 監視者のいないセッションでも定型的な承認で停止せず、タスクを最後まで実行できる。
🔑 ユースケース 3: 社内 MCP サーバー群への一括サインイン

シナリオ: 社内のナレッジ検索、チケット管理、監視ツールなど複数の HTTP MCP サーバーを利用しており、サーバーごとのサインインが負担になっている。

Text実装例
1. 管理者が組織の ID プロバイダー情報を開発者に配布
2. 開発者がユーザーの MCP 設定に ID プロバイダーを追加
3. MCP Servers ビューの Organization sign-in 行で [Sign in] を選択
4. 対象のサーバー群が 1 回のサインインを共有
✅ 効果: サーバーごとのブラウザ認証フローが不要になり、複数の社内 MCP サーバーをすぐに利用開始できる。

🌍 利用可能リージョン

Kiro はグローバルに利用可能です。

📝 まとめ

Kiro IDE 1.4.236 では、GitLab からの Power / Skill インストール、承認プロンプトに自動応答する Permission Request Hook、組織の ID プロバイダーによる MCP サーバーへの一括サインインが追加されました。GitLab を利用する組織や、無人セッションでのエージェント運用、多数の社内 MCP サーバーを扱う環境において実用性の高いアップデートです。まずは IDE を 1.4.236 以降へ更新し、自組織のワークフローに合わせてフックと MCP 設定を見直すことを推奨します。
