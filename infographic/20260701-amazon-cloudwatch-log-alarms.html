Amazon CloudWatch

📊 ログクエリからのアラーム作成

Alarms from log queries
リリース日
2026-07-01

💡 概要

Amazon CloudWatch は、ログクエリを使ってログデータに直接アラームを作成できる機能を発表しました。ログ分析のワークフローから離れることなく、異常を検知してアラート通知を受け取れます。

ログクエリに対してしきい値を直接指定でき、これまで中間ステップとして必要だったメトリクスフィルターやカスタムメトリクスの作成が不要になります。たとえばサービスごとのエラー率をカウントするクエリを設定すれば、エラーが急増した際にログのコンテキストを含む通知を単一のワークフロー内で受け取れます。

作成されたアラームは、Amazon SNS 通知や Amazon EventBridge 連携を含む標準的な CloudWatch アラームアクションをすべてサポートします。

😓 アップデート前の課題
🔸ログ内のパターンやカウント監視に、まずメトリクスフィルター/カスタムメトリクスの作成が必要
🔸ログ分析画面とアラーム設定画面を行き来する分断されたワークフロー
🔸中間ステップを介するため監視開始まで手間と時間がかかる
➡
✨ アップデート後の改善
✅ログクエリに直接しきい値を指定、中間メトリクスの事前作成が不要
✅ログ分析のワークフロー内でアラームを設定、画面を離れる必要なし
✅異常検知から通知までを単一ワークフローで完結

🔧 主要機能

📝 ログクエリからの直接アラーム作成
  • ログクエリに対してアラームを設定し、しきい値を直接指定できる
  • メトリクスフィルターやカスタムメトリクスを中間ステップとして作成する必要がない
  • ログ分析のワークフロー内で完結する
🔔 ログコンテキストを含む通知
  • しきい値を超過した際に、ログのコンテキストを含むアラーム通知を受け取れる
  • サービスごとのエラー率をカウントするクエリを設定し、急増時に通知を受け取る運用が可能
📣 標準的なアラームアクションのサポート
  • Amazon SNS 通知に対応
  • Amazon EventBridge 連携に対応
  • 既存の CloudWatch アラームアクションと同様に扱える

⚙️ 技術仕様

項目詳細

📌 API 変更履歴: 本レポート作成時点で awsapichanges.com 上の対応する API 変更情報は確認できませんでした。コンソール、AWS CLI、AWS CloudFormation、AWS SDK から利用できます。

🚀 設定方法

前提条件

✓Amazon CloudWatch Logs にログデータが収集されていること
✓監視対象のログに対してクエリを実行できる権限があること
✓アラーム作成および通知先 (Amazon SNS トピックなど) の設定権限があること

手順

1
🔍 ログクエリの作成

ログ分析画面で監視したいログデータに対するクエリを作成。例: サービスごとのエラー率をカウント。

2
📊 しきい値の設定

作成したクエリに対してアラームを構成し、しきい値を直接指定。中間メトリクスの事前作成は不要。

3
📣 アクションの設定

しきい値超過時の通知先を設定。Amazon SNS 通知や EventBridge 連携など標準アクションを利用。

コンソールに加えて、AWS CLI、AWS CloudFormation、AWS SDK を使用したアラーム作成にも対応。Infrastructure as Code での管理も可能です。

💼 ビジネス面

✓異常検知の迅速化: エラー急増などを素早く検知し、インシデント対応の初動を早められる
✓導入の容易さ: 中間メトリクスの設計・作成が不要で導入ハードルが低下

🔩 技術面

✓設定の簡素化: ログクエリに直接しきい値を設定可能
✓既存アクションとの互換性: SNS や EventBridge をそのまま活用
✓多様な設定手段: コンソール、CLI、CloudFormation、SDK に対応

⚠️ デメリット・制約事項

制限事項
✗Middle East (UAE) および Middle East (Bahrain) を除くすべての商用 AWS リージョンで利用可能。上記 2 リージョンでは利用不可
✗クエリ実行やアラーム評価に関する具体的な制約 (対応するクエリ言語や結果形式など) は公式ドキュメントで確認を推奨
考慮すべき点

・ログクエリベースのアラームは、しきい値の判定に適したクエリ設計が重要。クエリの内容や結果形式を事前に確認してください。
・料金は CloudWatch の料金体系に基づきます。

🎯 ユースケース

① エラー率の急増監視

シナリオ: マイクロサービス環境で、サービスごとのエラー発生数をログから集計し、急増した場合にアラート通知を受け取りたい。

実装イメージ
サービスごとのエラー率をカウントするログクエリを作成し、
しきい値を設定してアラームを構成する。
しきい値超過時に Amazon SNS 経由で通知する。
💥 効果: メトリクスフィルターを事前作成することなく、ログから直接エラー急増を検知し迅速に対応。
② 特定パターンの発生監視

シナリオ: アプリケーションログ内の特定のエラーパターンや例外の発生回数を監視し、一定回数を超えたら運用チームに通知したい。

実装イメージ
対象のログパターンを抽出・集計するクエリを作成し、
しきい値を指定してアラームを設定する。
💥 効果: ログ分析の画面を離れずにアラームを設定でき、監視設定の手間を削減。
③ EventBridge による自動対応

シナリオ: ログクエリでしきい値を超過した際に、自動で修復ワークフローやインシデント管理プロセスを起動したい。

実装イメージ
ログクエリベースのアラームアクションに Amazon EventBridge を設定し、
イベントをトリガーに後続の処理 (Lambda 関数の実行など) を起動する。
💥 効果: 異常検知から自動対応までをイベント駆動で連携し、運用の自動化を推進。

📌 まとめ

このアップデートにより、Amazon CloudWatch でログクエリから直接アラームを作成できるようになり、メトリクスフィルターやカスタムメトリクスの中間ステップが不要になりました。ログ分析から監視・通知までを単一のワークフローで完結できるため、運用効率と異常検知の迅速化に貢献します。ログベースの監視を運用しているチームは、既存の監視設定を見直し、この機能への移行を検討することを推奨します。
