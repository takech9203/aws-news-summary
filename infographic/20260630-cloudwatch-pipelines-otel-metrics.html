OpenTelemetry メトリクスの
処理・エンリッチメントに対応

📅 2026-06-30

💡 概要 — 何が変わったのか

CloudWatch pipelines は、テレメトリデータを取り込み・変換し、CloudWatch にルーティングするフルマネージドサービスです。今回のアップデートで、取り込み (インジェスト) 時に OpenTelemetry (OTel) メトリクスを処理・エンリッチできるようになりました。

新しいインフラは不要で、アプリケーションの計装を変更せずに、一致したメトリクスへ透過的に処理を適用します。変更できないソースから送られるメトリクスにも、チーム・コストセンター・環境タグといったビジネスコンテキストを付与できます。処理済みメトリクスは Query Studio で PromQL クエリでき、アラームや異常検出とも互換性があります。

Before / After

❌ アップデート前
•エンリッチ・変換にカスタムの処理レイヤーを自前で構築
•アプリ側の計装をソースで変更する必要があり、変更不可のソースには非対応
•高カーディナリティラベル削減の仕組みを自前で用意
➜
✅ アップデート後
•新インフラなしで変換をインジェストパス上で一元適用
•変更不可のソースにもビジネスコンテキストを付与
•ラベル削除でコスト削減、リネームで命名規則統一をマネージドで実現
🎯 対象読者: 監視・オブザーバビリティを担当するプラットフォームエンジニア / SRE、コスト最適化を進めたい運用チーム

OTLP 経由で取り込まれた OTel メトリクスが、CloudWatch pipelines の Source → Processors → Sink を順に通過し、変換・エンリッチされたうえで CloudWatch に格納される流れを示しています。

⚙️ 主要機能

🏷️ メトリクスのエンリッチメント
  • チーム所有者・コストセンター・環境タグなどのビジネスコンテキストを付与
  • 変更できないソースにも属性を追加
  • アプリケーションの計装変更は不要
✂️ 高カーディナリティラベルの削除
  • カスタムワークロード由来の高カーディナリティラベルを削除
  • 保存メトリクス量を減らしストレージコストを削減
🔤 リネームによる標準化
  • メトリクス名・属性名をリネームし一貫した命名規則を強制
  • インジェストパス上で透過的に適用、一致したメトリクスのみ処理

項目詳細

🎯 ユースケース

1️⃣ 変更できないソースへのビジネスコンテキスト付与

サードパーティ製ソフトウェアや共通基盤から送られる OTel メトリクスに、アプリを改変せずにチームやコストセンターのタグを付与したい。

Processoradd-attributes
team = platform-team
cost_center = 12345
environment = production
✅ 効果: 変更できないソースのメトリクスもビジネス単位で分類・集計できる
2️⃣ 高カーディナリティラベル削除によるコスト最適化

カスタムワークロードが request_id のような高カーディナリティ属性を大量に付与し、ストレージコストが増大している。

Processordelete-attributes
remove = request_id, session_id
✅ 効果: 不要な高カーディナリティラベルを削除し、保存メトリクス量とコストを削減
3️⃣ 命名規則の統一

複数チームがそれぞれ異なる命名規則でメトリクスを送っており、組織全体で統一したい。

Processorrename
from = svc.req.latency
to   = service.request.latency
✅ 効果: メトリクス名・属性名を統一し、クエリやダッシュボードの一貫性を向上

✨ メリット

💼 ビジネス面
✓コスト削減: 高カーディナリティラベル削除で保存量とストレージコストを削減
✓運用コスト低減: カスタム処理レイヤーの構築・運用が不要
✓コスト配賦の明確化: コストセンター/チームタグでビジネス単位に整理
🔧 技術面
✓インフラ不要: 新インフラなしでインジェストパスで変換を適用
✓アプリ非改変: 計装を変更せず変更不可のソースも処理
✓一貫性の確保: リネームで組織全体の命名規則を強制

⚠️ デメリット・制約事項

制限事項

▸メトリクスのインジェストパスは OTLP のみサポート
▸プロセッサーはパイプラインあたり最大 20 個
▸メトリクスパイプラインはアカウントあたり最大 300 個
▸パイプライン定義はカスタマー提供キーで暗号化されないため、パスワード・API キー・PII などの機微情報を含めない

考慮すべき点

▸プロセッサーはメトリクスを変換するため、処理内容によっては元の値と異なる形で保存される点を理解する
▸処理は一致したメトリクスにのみ透過的に適用されるため、マッチ条件の設計を確認する

📝 まとめ

今回のアップデートにより、OTel メトリクスのエンリッチメント・ラベル削除・リネームといった変換を、追加のインフラやアプリ改変なしにインジェストパス上で一元的に適用できるようになりました。特に、変更できないソースへのビジネスコンテキスト付与やコスト最適化を検討しているチームに有用です。

まずは対象リージョンで CloudWatch コンソールから CloudWatch Metrics (OTel) をソースとするメトリクスパイプラインを作成し、既存の OTel メトリクスに対する処理設計を検討することをおすすめします。
