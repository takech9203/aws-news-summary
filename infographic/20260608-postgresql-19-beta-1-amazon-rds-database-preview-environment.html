⚡ 主要機能

🔗 SQL Property Graph Queries (SQL/PGQ)

SQL 標準に準拠したプロパティグラフクエリをネイティブサポート。CREATE PROPERTY GRAPH でグラフスキーマを定義し、グラフパターンマッチングを標準 SQL 内で実行可能。ソーシャルネットワーク分析、不正検知、推薦システムに最適。

📦 REPACK CONCURRENTLY

テーブルのリビルドと未使用ストレージの回収を本番稼働中に実行可能。VACUUM FULL と異なりテーブルロックが不要で、ルーチンメンテナンス中もデータベースへのアクセスを維持。

🔄 ロジカルレプリケーション - シーケンス自動同期

シーケンス値がレプリカに自動的に同期。メジャーバージョンアップグレードのカットオーバー後に手動でシーケンスを調整する作業が不要に。CREATE PUBLICATION ... EXCEPT で特定テーブルを除外したパブリケーションも可能。

⚙️ ロジカルレプリケーション - 動的有効化

wal_level=replica の状態からサーバー再起動なしでロジカルレプリケーションを有効化。新しい読み取り専用パラメータ effective_wal_level で現在有効な WAL レベルを確認可能。

🚀 パフォーマンス改善

外部キーチェック付き INSERT で最大 2 倍の性能向上。パラレル autovacuum、Anti-join 最適化、インクリメンタルソートの拡張適用、Eager aggregation による高速行処理、LISTEN/NOTIFY のスケーラビリティ改善。

👩‍💻 開発者体験の向上

INSERT ... ON CONFLICT DO SELECT ... RETURNING で競合行を返却可能。GROUP BY ALL による自動グルーピング。WAIT FOR LSN で read-your-writes パターンを実現。jsonpath への文字列関数追加、テンポラルクエリの FOR PORTION OF 句サポート。

🔒 セキュリティ強化

SNI サポートによるホスト名別 TLS 証明書の提示。パスワード有効期限警告。MD5 認証の非推奨化警告。RADIUS 認証の削除。

ステップ 3: SQL/PGQ グラフクエリの評価例

SQL プロパティグラフの作成とクエリ 
-- プロパティグラフの作成
CREATE PROPERTY GRAPH social_network
  VERTEX TABLES (
    users KEY (user_id)
      LABEL Person PROPERTIES (name, age)
  )
  EDGE TABLES (
    friendships KEY (friendship_id)
      SOURCE KEY (user_id_1) REFERENCES users (user_id)
      DESTINATION KEY (user_id_2) REFERENCES users (user_id)
      LABEL Knows
  );

-- グラフパターンマッチングクエリ
SELECT p1.name, p2.name
FROM social_network GRAPH_TABLE (
  MATCH (p1:Person)-[:Knows]->(p2:Person)
  WHERE p1.age > 30
  COLUMNS (p1.name, p2.name)
);

💡 ユースケース

🔗 ユースケース 1: ソーシャルグラフ分析の統合

シナリオ: SNS アプリケーションでユーザー間の友達関係や推薦を分析するために、PostgreSQL とは別に Neo4j を運用していた。データ同期のラグやインフラコストが課題。

SQL 友達の友達を探す (2 ホップ) 
SELECT DISTINCT p3.name
FROM social_network GRAPH_TABLE (
  MATCH (p1:Person)-[:Knows]->(p2:Person)-[:Knows]->(p3:Person)
  WHERE p1.name = 'Alice' AND p3.name <> 'Alice'
  COLUMNS (p3.name)
);

効果: グラフ DB の運用コスト削減、データ同期ラグの解消、SQL スキルのみでグラフクエリを記述可能

🔄 ユースケース 2: ゼロダウンタイムメジャーバージョンアップグレード

シナリオ: 大規模 EC サイトの DB を PostgreSQL 18 から 19 にアップグレードする際、ロジカルレプリケーションを使用した Blue/Green デプロイメントを計画。

SQL 動的ロジカルレプリケーション有効化 
-- ロジカルレプリケーションを動的に有効化 (再起動不要)
ALTER SYSTEM SET wal_level = 'logical';
SHOW effective_wal_level;

-- シーケンスも自動同期されるため手動調整が不要
CREATE SUBSCRIPTION upgrade_sub
  CONNECTION 'host=old-primary dbname=mydb'
  PUBLICATION all_tables;

効果: ダウンタイムを数秒レベルに短縮、シーケンス不整合によるエラーリスクを排除

📦 ユースケース 3: 大規模テーブルのオンラインメンテナンス

シナリオ: 数百 GB のログテーブルで UPDATE/DELETE が頻繁に発生し、テーブルの肥大化が進行。VACUUM FULL はテーブルロックが必要なため営業時間中に実行不可。

SQL オンラインメンテナンス 
-- ノンブロッキングでテーブルを再構築
REPACK TABLE access_logs CONCURRENTLY;

-- パラレル autovacuum で大規模テーブルの VACUUM を高速化
ALTER SYSTEM SET autovacuum_max_parallel_workers = 4;
SELECT pg_reload_conf();

効果: メンテナンスウィンドウ不要でテーブルサイズを最適化、I/O パフォーマンスの継続的な維持

✓ パフォーマンス向上: パラレル autovacuum、Eager aggregation、外部キーチェック最適化

⚠️ デメリット・制約事項

制限事項

  • Preview Environment のインスタンスは最大 60 日で自動削除
  • スナップショットは Preview Environment 内でのみ利用可能
  • 本番ワークロードには使用不可 (ベータ版のため)
  • 利用可能リージョンは US East (Ohio) のみ
  • PostgreSQL 19 はベータ版であり仕様変更の可能性あり

考慮すべき点

  • SQL/PGQ の実装はベータ段階でありパフォーマンス特性が最終版と異なる可能性
  • 既存のアプリケーションやエクステンションとの互換性を十分にテストする必要あり
  • JIT がデフォルト無効化 - JIT に依存していたワークロードはパフォーマンス影響を確認
  • RADIUS 認証が削除 - RADIUS 使用環境はアップグレード前に認証方式の変更が必要
