Amazon CloudWatch / AWS X-Ray

📡 OpenTelemetry トレース向け
API キー (ベアラートークン) 認証サポート

📅 リリース日: 2026 年 11 月 3 日 | 対象: AWS X-Ray OTLP トレースエンドポイント

📝 概要

Amazon CloudWatch が、AWS X-Ray の OTLP トレースエンドポイントへの送信で API キーによるベアラートークン認証をサポートしました。 Authorization: Bearer ヘッダーを設定できる任意の OTLP/HTTP クライアントが、 SigV4 署名なしで CloudWatch へトレースを送信できます。

❌ Before: SigV4 署名が必須

  • AWS SDK や AWS クレデンシャルを利用できない環境 (オンプレミス、他社クラウド、CI/CD) からの直接送信が困難
  • 静的な Authorization ヘッダーのみ対応のサードパーティツールから送信不可
  • sigv4auth 拡張の構成と AWS クレデンシャルの配布が必要

✅ After: API キー認証が選択肢に

  • Authorization: Bearer を設定できる任意の OTLP/HTTP クライアントから送信可能
  • オンプレミス、他社クラウド、CI/CD パイプラインからのトレース送信が容易に
  • Transaction Search、Application Signals、CloudWatch Omni など SigV4 と同一機能を利用可能
⚠️ SigV4 は引き続き推奨の認証方式です。ADOT SDK はデフォルトで SigV4 を使用し続けるため、既存環境への変更は不要です。

AWS 外部のワークロードが、IAM ユーザーに発行した X-Ray API キーをベアラートークンとして使用し、SigV4 署名なしで OTLP トレースエンドポイントへトレースを送信する流れを示しています。

⚡ 主要機能

🔑 API キーによるベアラートークン認証

https://xray.{region}.amazonaws.com/v1/traces への送信時に Authorization: Bearer ヘッダーで認証。API キーは IAM ユーザーが所有する xray.amazonaws.com 向けのサービス固有クレデンシャルで、リクエストはその IAM ユーザーの権限で実行されます。 スパン送信 (xray:PutTraceSegments として認可) のみに使用でき、SigV4 が必要な X-Ray API の呼び出しには使用できません。

🌐 幅広い OTLP/HTTP クライアントのサポート

OpenTelemetry Collector では sigv4auth の代わりに bearertokenauth 拡張で構成可能。 OpenTelemetry SDK のエクスポーターや curl など、Authorization ヘッダーを設定できる任意のクライアントが利用可能。 ペイロードは application/x-protobuf と application/json の両方に対応します。

🔄 キーのライフサイクル管理と監査

有効期限は 1 日〜36,600 日で設定可能 (未設定の場合は無期限)。IAM ユーザーごとに 2 つの API キーを保持でき、 ダウンタイムなしのローテーションが可能。AWS CloudTrail のデータイベントに "callWithBearerToken": true が記録され、SigV4 リクエストと区別して監査できます。

🤝 SigV4 との機能同等性

API キー認証でも Transaction Search、Application Signals、CloudWatch Omni を含む同一の CloudWatch 機能を利用可能。 ADOT SDK はデフォルトで SigV4 を使用し続けるため、既存構成の変更は不要です。

🔧 技術仕様

認証方式の比較

項目SigV4 (推奨)API キー (ベアラートークン)
認証方法AWS クレデンシャルによるリクエスト署名Authorization: Bearer ヘッダー
必要なものAWS SDK または sigv4auth 拡張、一時クレデンシャルIAM ユーザーと X-Ray API キー
主な用途AWS 上のワークロード全般オンプレミス、他社クラウド、CI/CD、サードパーティツール
利用可能な CloudWatch 機能Transaction Search、Application Signals、CloudWatch Omni などSigV4 と同一
セキュリティ上の位置づけ最も強力なセキュリティ体制 (推奨)短期クレデンシャルが使えない場合のみ使用

API キーの要件と制限

項目詳細
前提条件Transaction Search の有効化 (OTLP トレースエンドポイントの要件)
通信HTTPS 必須 (HTTP リクエストは拒否される)
対応エンドポイント標準エンドポイント、FIPS エンドポイント、X-Ray のインターフェイス VPC エンドポイント
キー数の上限IAM ユーザーごとに 2 キー (無停止ローテーション用)
有効期限1〜36,600 日で設定可能 (未設定の場合は無期限)
必要な IAM 権限xray:CallWithBearerToken および xray:PutTraceSegments (管理ポリシー AWSXRayAPIKeyAccess を推奨)
エラー応答キーが無効・期限切れ・非アクティブ、または権限不足の場合は HTTP 403、一時的な障害の場合は HTTP 503

IAM ポリシー例

トレース送信用 IAM ユーザーに付与する権限の例です。

JSON IAM ポリシー 
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "XRayTracesWithAPIKey",
            "Effect": "Allow",
            "Action": [
                "xray:CallWithBearerToken",
                "xray:PutTraceSegments"
            ],
            "Resource": "*"
        }
    ]
}

🛠️ 設定方法

前提条件

✓Transaction Search が有効化されていること (OTLP トレースエンドポイントの利用に必須)
✓トレース送信専用の IAM ユーザーを作成できること
✓送信元クライアントが HTTPS で Authorization ヘッダーを設定できること
1
IAM ユーザーの作成と権限付与

トレース送信専用の IAM ユーザー (例: xray-traces-api-key-user) を作成し、 AWS 管理ポリシー AWSXRayAPIKeyAccess、または xray:CallWithBearerToken と xray:PutTraceSegments を許可するカスタマー管理ポリシーをアタッチします。

2
API キーの作成
Bash AWS CLI で X-Ray API キーを作成 
aws iam create-service-specific-credential \
    --user-name xray-traces-api-key-user \
    --service-name xray.amazonaws.com \
    --credential-age-days 30

レスポンスの ServiceCredentialSecret が API キー (ベアラートークン) です。 後から再取得できないため、AWS Secrets Manager などに安全に保管します。

3
OpenTelemetry Collector の構成
YAML bearertokenauth 拡張を使用した構成例 
extensions:
  bearertokenauth:
    filename: "/etc/otel/xray-api-key"

receivers:
  otlp:
    protocols:
      http:
        endpoint: "0.0.0.0:4318"

processors:
  batch:

exporters:
  otlphttp/traces:
    compression: gzip
    traces_endpoint: "https://xray.us-east-1.amazonaws.com/v1/traces"
    auth:
      authenticator: bearertokenauth

service:
  extensions: [bearertokenauth]
  pipelines:
    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [otlphttp/traces]

環境変数から読み込む場合は token: "${env:XRAY_API_KEY}" を使用します。 API キーを構成ファイルやソースコードに直接記載してはいけません。

4
curl による送信テスト
Bash OTLP JSON ペイロードの直接送信 
curl -X POST "https://xray.us-east-1.amazonaws.com/v1/traces" \
     -H "Content-Type: application/json" \
     -H "Authorization: Bearer ${XRAY_API_KEY}" \
     -d @spans.json

認証と疎通を確認するコマンドです。

💡 メリット

📈 ビジネス面

✓ハイブリッド・マルチクラウドの可観測性統合: オンプレミスや他社クラウドからも直接送信でき、可観測性基盤を CloudWatch に一元化
✓サードパーティツールとの連携拡大: 静的ヘッダーのみ対応のツールからも利用でき、ツール選択の自由度が向上
✓導入障壁の低減: AWS SDK の組み込みや SigV4 署名の実装が不要に

⚙️ 技術面

✓シンプルな認証実装: ヘッダー 1 つの設定で認証でき、標準の bearertokenauth 拡張をそのまま利用可能
✓無停止のキーローテーション: IAM ユーザーごとに 2 キーを保持でき、送信を中断せずローテーション
✓ガバナンスと監査: iam:ServiceSpecificCredentialAgeDays で有効期限を強制、CloudTrail の callWithBearerToken で監査

⚠️ デメリット・制約事項

制限事項

✗API キーは OTLP トレースエンドポイントへのスパン送信のみに使用可能。SigV4 が必要な X-Ray API (トレースデータの読み取りなど) には使用不可
✗OTLP トレースエンドポイントの利用には Transaction Search の事前有効化が必要
✗API キーは IAM ユーザーに紐づく長期クレデンシャルの一種。SigV4 と短期クレデンシャルの方が強力なセキュリティ体制を提供するため、AWS は可能な限り SigV4 を推奨
✗ベアラートークン認証が利用可能なリージョンは、ドキュメントに記載された商用リージョンに限られる

考慮すべき点

⚠️API キーは作成時にしか取得できないため、AWS Secrets Manager などでの安全な保管と漏えい対策が必須
⚠️すべてのキーに有効期限を設定し、iam:ServiceSpecificCredentialAgeDays 条件キーで最大キー年齢を強制することを推奨
⚠️アプリケーションや連携ごとに専用の IAM ユーザーを分け、最小権限の原則を適用することを推奨
⚠️漏えいが疑われる場合は、キーの無効化・削除、または xray:CallWithBearerToken の明示的拒否で即座にブロック可能 (反映まで約 5 分)
⚠️CloudTrail のデータイベントはデフォルトで記録されないため、監査には明示的な有効化が必要

🎯 ユースケース

🏢 ユースケース 1: オンプレミスアプリケーションのトレースを CloudWatch に集約

シナリオ: オンプレミスで OpenTelemetry を導入済みだが、AWS クレデンシャルの配布が難しく CloudWatch へ送信できていない。

実装: 専用 IAM ユーザーに AWSXRayAPIKeyAccess をアタッチ → 有効期限付き API キーを作成してシークレット管理基盤に保管 → Collector に bearertokenauth を構成して送信。

効果: クレデンシャル配布なしでトレースを集約し、Transaction Search や Application Signals で AWS 上のワークロードと一元分析。

🔁 ユースケース 2: CI/CD パイプラインのトレーシング

シナリオ: GitHub Actions などのパイプライン実行を可視化したいが、SigV4 署名の仕組み構築が負担。

実装: CI/CD 専用 IAM ユーザーと短い有効期限の API キーを作成 → CI/CD のシークレットに登録 → OTLP/HTTP で Authorization: Bearer ヘッダー付きで送信。

効果: HTTP ヘッダー設定のみでパイプラインの実行状況を可視化し、ビルドやデプロイのボトルネックを分析。

☁️ ユースケース 3: 他社クラウド上のワークロードのマルチクラウド可観測性

シナリオ: 複数クラウドに分散したワークロードのトレースを CloudWatch に統合し、分散トレーシングを一元化したい。

実装: 他社クラウド用の IAM ユーザーと API キーを作成して各クラウドのシークレット管理サービスに保管 → 各 Collector に bearertokenauth を構成 → aws:SourceIp 条件で利用元ネットワークを制限。

効果: クラウドをまたぐエンドツーエンドのトレースを CloudWatch Omni や Transaction Search で分析し、マルチクラウド環境の障害調査時間を短縮。

💰 料金

API キー認証の利用自体に関する追加料金は発表されていません。トレースの取り込みには CloudWatch / X-Ray の既存の料金が適用されます。 また、OTLP トレースエンドポイントの利用には Transaction Search の有効化が必要で、スパンは CloudWatch Logs に送信されるため、関連する料金が発生します。 詳細は Amazon CloudWatch 料金ページ を参照してください。

🌏 利用可能リージョン

X-Ray OTLP トレースエンドポイントが利用可能なすべての AWS 商用リージョンで利用できます。ベアラートークン認証の対応リージョンは以下のとおりです。

東京 大阪 バージニア北部 オハイオ 北カリフォルニア オレゴン ケープタウン 香港 ハイデラバード ジャカルタ マレーシア メルボルン ムンバイ ソウル シンガポール シドニー タイ カナダ中部 カルガリー フランクフルト アイルランド ロンドン ミラノ パリ スペイン ストックホルム チューリッヒ サンパウロ

🔗 関連サービス・機能

  • AWS X-Ray: OTLP トレースエンドポイントを提供する分散トレーシングサービス。API キーは X-Ray のサービス固有クレデンシャルとして発行
  • AWS IAM: API キーの発行・ローテーション・失効を管理。xray:CallWithBearerToken アクションと条件キーでガバナンスを実現
  • CloudWatch Application Signals: 送信されたトレースを活用してアプリケーションのパフォーマンスを監視。API キー認証でも利用可能
  • AWS CloudTrail: callWithBearerToken フィールドを含むデータイベントで API キーの利用状況を監査
  • AWS Secrets Manager: API キーの安全な保管に推奨されるシークレット管理サービス

✅ まとめ

CloudWatch の OTLP トレースエンドポイントが API キーによるベアラートークン認証をサポートしたことで、 オンプレミス、他社クラウド、CI/CD パイプラインなど AWS クレデンシャルを利用しにくい環境からも、 標準的な OpenTelemetry ツールで CloudWatch へトレースを送信できるようになりました。 SigV4 が引き続き推奨であることを踏まえつつ、短期クレデンシャルを利用できない外部ワークロードには、 有効期限付きの API キーと最小権限の IAM ユーザーを組み合わせた導入がおすすめです。
