☁️ Amazon EKS

EKS Auto Mode と Karpenter が
Dynamic Resource Allocation (DRA) をサポート

📅 リリース日: 2026 年 11 月 9 日 | NVIDIA GPU と EFA の属性ベース割り当て・トポロジー整合・Pod 間共有を動的プロビジョニングと組み合わせ可能に

📝 概要

Amazon EKS は、EKS Auto Mode と Karpenter の使用時に、NVIDIA GPU と Elastic Fabric Adapter (EFA) ネットワークデバイスに対する Dynamic Resource Allocation (DRA) をサポートしました。DRA は Kubernetes 1.34 で一般提供された機能で、デバイスプラグインの制限を解消し、属性ベースのデバイス選択、トポロジーを考慮した割り当て、Pod 間でのデバイス共有を可能にします。

ユーザーが ResourceClaim / ResourceClaimTemplate でモデルやアーキテクチャなどの属性を宣言すると、Karpenter が条件に一致する最低コストのインスタンスを自動起動 (スケールフロムゼロ対応) します。EKS Auto Mode では NVIDIA DRA ドライバーと EFA DRA ドライバー (DRANET) がノードランタイムに組み込み済みのため、ドライバーのインストールや管理は不要です。

❌ Before: デバイスプラグインの制限
  • 整数カウント (nvidia.com/gpu など) のみで、GPU モデルやアーキテクチャによるフィルタリング不可
  • コンテナや Pod 間でのデバイス共有ができない
  • GPU と EFA をまたぐ PCIe / NUMA トポロジー割り当てを表現できず、カスタムスケジューラー拡張が必要
  • DRA には既存ノードが必要で、ResourceClaim からのゼロスケールアウトが不可能
✅ After: DRA サポートで実現
  • ResourceClaim の属性を Karpenter が評価し、最低コストの EC2 を自動起動 (スケールフロムゼロ)
  • 共有 ResourceClaim で複数 Pod が同一 GPU を共有可能
  • PCIe アラインされた GPU + EFA のトポロジー整合割り当てが標準機能に
  • Auto Mode は DRA ドライバー組み込み済みで導入・運用不要
  • DRA ノードとデバイスプラグインノードを自動分離し、オーバーサブスクリプションを防止

ユーザーが DeviceClass と ResourceClaim / ResourceClaimTemplate で必要なデバイスを宣言すると、Karpenter が保留中のクレームを評価して条件に一致する最低コストの EC2 インスタンスを起動し、組み込みの DRA ドライバーが GPU と EFA デバイスを Pod に割り当てます。

⚡ 主要機能

🎯 属性ベースのデバイス選択

DRA ドライバーが ResourceSlice でデバイス属性を公開。ResourceClaim で GPU のモデルやアーキテクチャを CEL 式で指定でき、「整数カウントのみ」から宣言的で表現力の高い要求方式に進化。

🔗 トポロジー整合 GPU / EFA 割り当て

同一 PCIe スイッチや NUMA ドメイン上のデバイスの組み合わせを保証。分散トレーニングで GPU と近接する EFA をペアで割り当て、通信性能を最適化。GPU と EFA の両方で DRA が必要。

🤝 Pod 間での GPU 共有

複数の Pod が同じ ResourceClaim を参照して同一 GPU を共有 (同一ノードにスケジュール)。Auto Mode ではタイムスライシング / MIG は利用不可 (必要な場合は Karpenter を使用)。EFA は共有不可。

🚀 Karpenter の DRA 動的プロビジョニング

Karpenter 1.15 以降がインスタンスのデバイスメタデータを同梱し、保留中のクレームを評価してノードを起動。スケールフロムゼロ対応。アルファ機能のため settings.enableDRA: true などで有効化。

🛡️ Auto Mode の組み込みドライバーと安全機構

NVIDIA DRA ドライバーと DRANET が組み込み済みで導入・運用不要。ノードはデバイスタイプごとに DRA / デバイスプラグインの役割を終生維持し、サイレントなオーバーサブスクリプションを防止。DeviceClass はユーザーが作成。

🛠️ 設定方法 (EKS Auto Mode の場合)

前提条件: EKS Auto Mode は Kubernetes 1.36 以降のクラスターが必要。Karpenter の動的プロビジョニングには Karpenter 1.15 以降とフィーチャーゲートの有効化が必要 (静的 NodePool は追加設定なし)。Karpenter / マネージドノードグループ / セルフマネージドノードでは DRA ドライバーのインストールと、同一ノード上での同一デバイスタイプのデバイスプラグインとの共存回避をユーザー自身が管理。
1

DeviceClass の作成

BashNVIDIA GPU 用 DeviceClass
cat <<EOF | kubectl apply -f -
apiVersion: resource.k8s.io/v1
kind: DeviceClass
metadata:
  name: gpu.nvidia.com
spec:
  selectors:
    - cel:
        expression: device.driver == 'gpu.nvidia.com'
EOF

Auto Mode は DRA ドライバーを組み込みで提供しますが、DeviceClass は作成しないため、ユーザー自身が作成します。上流ドライバーの Helm チャートと同じ名前を使用すると、ドライバーを自己管理するクラスターとの間でクレームの可搬性を維持できます。

2

ResourceClaimTemplate の作成

BashPod ごとに GPU を 1 つ割り当て
cat <<EOF | kubectl apply -f -
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: single-gpu
spec:
  spec:
    devices:
      requests:
        - name: gpu
          exactly:
            deviceClassName: gpu.nvidia.com
            allocationMode: ExactCount
            count: 1
EOF

CEL 式のセレクターを追加すると、GPU のモデルやアーキテクチャなどの属性で割り当て対象を絞り込むこともできます。

3

ワークロードから DRA オブジェクトを参照

BashGPU ワークロードの Pod 定義
cat <<EOF | kubectl apply -f -
apiVersion: v1
kind: Pod
metadata:
  name: gpu-workload
spec:
  containers:
    - name: app
      image: nvidia/cuda:13.0.1-base-ubuntu24.04
      command: ["nvidia-smi"]
      resources:
        claims:
          - name: gpu
  resourceClaims:
    - name: gpu
      resourceClaimTemplateName: single-gpu
EOF

Pod の resourceClaims で ResourceClaimTemplate を参照すると、EKS Auto Mode がクレームを満たすインスタンスを起動し、NVIDIA DRA ドライバーを有効化して GPU を割り当てます。

4

Karpenter の場合: フィーチャーゲートの有効化

BashHelm による DRA 有効化
helm upgrade karpenter oci://public.ecr.aws/karpenter/karpenter \
  --namespace kube-system \
  --reset-then-reuse-values \
  --set settings.enableDRA=true

以前のチャートバージョンが settings.ignoreDRARequests を true にデフォルト設定しているため、--reuse-values ではなく --reset-then-reuse-values (Helm 3.14 以降が必要) を使用します。

💡 メリット

💼 ビジネス面

✓コスト最適化: Karpenter が最低コストのインスタンスを自動選択し、スケールフロムゼロにも対応するため、高価な GPU インスタンスの無駄な常時稼働を削減
✓運用負荷の削減: EKS Auto Mode では DRA ドライバーが組み込み済みで、インストール・設定・アップグレードが不要
✓学習時間短縮: PCIe アラインされた GPU と EFA の割り当てにより分散トレーニングの通信効率が向上し、ジョブ完了時間の短縮が期待できる

⚙️ 技術面

✓宣言的で表現力の高いデバイス要求: CEL 式で GPU のモデルやアーキテクチャの属性ベース選択ができ、カスタムスケジューラー拡張が不要
✓トポロジー整合割り当て: 同一 PCIe スイッチ / NUMA ドメイン上の GPU と EFA のペア割り当てを標準機能で実現
✓安全な移行: デバイスタイプごとに DRA ノードとデバイスプラグインノードを自動分離し、サイレントオーバーサブスクリプションを防止
✓デバイス共有: 共有 ResourceClaim により複数 Pod で同一 GPU を安全に共有可能

⚠️ デメリット・制約事項

🚫 制限事項

✗EKS Auto Mode の DRA は Kubernetes 1.36 以降が必要 (それ以前のバージョンではデバイスプラグインを使用)
✗Auto Mode では DRA 経由のタイムスライシングと MIG による GPU 共有は利用不可 (共有 ResourceClaim のみ)。タイムスライシングが必要な場合は Karpenter を使用
✗Auto Mode の DRA 対象は NVIDIA GPU と EFA のみ。Trainium / Inferentia は Neuron デバイスプラグインを使用
✗ComputeDomain を使用する Multi-Node NVLink ワークロードは動的プロビジョニング非対応 (静的キャパシティ、マネージドノードグループ、セルフマネージドノードが必要)
✗g7e インスタンスファミリーは DRA のデバイスメタデータ未提供のため動的プロビジョニング対象外
✗Karpenter の DRA 動的プロビジョニングはアルファ機能でデフォルト無効。メタデータを同梱するインスタンスタイプのみ評価可能
✗AWS GovCloud (US) リージョンと中国リージョンでは利用不可

🤔 考慮すべき点

⚠️Auto Mode のノードはデバイスタイプごとに役割を終生維持するため、デバイスプラグインから DRA への移行にはノードの置き換えが必要 (Capacity Reservation / Capacity Block 利用時はスケールダウン後にスケールアップ)
⚠️settings.enableDRA は NVIDIA と EFA の両ドライバー稼働が前提。片方のみの場合は個別ゲート (draNVIDIAGPU / draEFA) を有効化
⚠️動的プロビジョニング + 静的ネットワークインターフェイス設定 + トポロジー整合割り当ての 3 つの併用は動作未定義 (Pod が Pending のまま残る可能性)。カスタムインターフェイスレイアウトと EFA DRA の併用には静的キャパシティを使用
⚠️EFA の動的プロビジョニングではパブリック IP が割り当てられないため、NAT ゲートウェイ付きプライベートサブネットまたは AWS PrivateLink エンドポイント付きサブネットで実行
⚠️DeviceClass が存在しないクレームは割り当てられず Pod が Pending のままになるため、展開前に DeviceClass の作成を確認
⚠️Karpenter / マネージドノードグループ / セルフマネージドノードでは、同一デバイスタイプの DRA ドライバーとデバイスプラグインの共存回避をユーザー自身が管理

🎯 ユースケース

1️⃣ 分散トレーニングにおけるトポロジー整合割り当て

シナリオ: 大規模言語モデルの分散トレーニングで、ノード間通信に EFA を使用。GPU と EFA が PCIe トポロジー上で離れていると GPUDirect RDMA の性能が低下するため、トポロジーを考慮した割り当てを行いたい。

YAMLGPU と EFA の PCIe 整合割り当て
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: gpu-efa-aligned
spec:
  spec:
    devices:
      requests:
        - name: gpu
          exactly:
            deviceClassName: gpu.nvidia.com
            allocationMode: ExactCount
            count: 1
        - name: efa
          exactly:
            deviceClassName: efa.dra.net
            allocationMode: ExactCount
            count: 1
      constraints:
        - requests: ["gpu", "efa"]
          matchAttribute: "dra.net/pcieRoot"

✅ 効果: 同一 PCIe ルート配下の GPU と EFA がペアで割り当てられ、GPU と NIC 間の通信パスが最短になり、分散トレーニングの通信パフォーマンスが最適化される。

2️⃣ 推論ワークロードでの GPU 共有によるコスト削減

シナリオ: 複数の軽量な推論サービスがそれぞれ GPU 全体を占有しており、GPU 使用率が低く、コストが課題になっている。

YAML共有 ResourceClaim による GPU 共有
apiVersion: resource.k8s.io/v1
kind: ResourceClaim
metadata:
  name: shared-gpu
spec:
  devices:
    requests:
      - name: gpu
        exactly:
          deviceClassName: gpu.nvidia.com
          allocationMode: ExactCount
          count: 1
---
# 複数の推論 Pod が resourceClaimName: shared-gpu を参照

✅ 効果: 複数の推論 Pod が同一 GPU を共有して同じノードにスケジュールされるため、GPU 使用率が向上しインスタンス数を削減できる。

3️⃣ 特定 GPU モデルを指定したスケールフロムゼロ

シナリオ: バッチ推論ジョブで特定の GPU アーキテクチャが必要だが、ジョブ実行時以外は GPU ノードを保持したくない。従来はデバイスプラグインの整数カウントでは GPU モデルを指定できず、NodePool のインスタンスタイプ制限で代替していた。

YAMLCEL 式による GPU モデル指定
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: specific-gpu
spec:
  spec:
    devices:
      requests:
        - name: gpu
          exactly:
            deviceClassName: gpu.nvidia.com
            allocationMode: ExactCount
            count: 1
            selectors:
              - cel:
                  expression: device.attributes["gpu.nvidia.com"].productName.contains("L40S")

✅ 効果: CEL 式で GPU モデルを直接指定でき、Karpenter が条件を満たす最低コストのインスタンスをゼロから起動。ジョブ完了後はノードが削除され、GPU コストをジョブ実行時間に限定できる。

📌 まとめ

EKS Auto Mode と Karpenter が DRA に対応したことで、GPU や EFA を使う機械学習ワークロードにおいて、属性ベースのデバイス選択、Pod 間の GPU 共有、PCIe アラインされたトポロジー整合割り当てと、動的なノードプロビジョニングを組み合わせられるようになりました。

✓EKS Auto Mode はドライバーが組み込み済みのため導入障壁が低く、Kubernetes 1.36 以降のクラスターでの新規 GPU ワークロードには DRA の採用を推奨
✓Karpenter の動的プロビジョニングはアルファ機能のため、フィーチャーゲートの設定と制限事項を確認した上で検証環境から導入することを推奨
