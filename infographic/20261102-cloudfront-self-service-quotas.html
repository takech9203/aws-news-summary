📅 リリース日: 2026 年 11 月 2 日 ｜ サービス: Amazon CloudFront

📋 概要

Amazon CloudFront が AWS Service Quotas と統合され、 28 個の CloudFront クォータを Service Quotas コンソールまたは API から表示、監視、引き上げリクエストできるようになりました。 これまでサポートケースの起票と手動レビューが必要だった上限緩和が、多くのケースで不要になります。 AWS Business Support 以上の契約があれば、公開しきい値内のリクエストは自動承認されます。

28 個 Service Quotas で管理できる CloudFront クォータ数
自動承認 Business Support 以上 + 公開しきい値内のリクエスト
5 分ごと 一部クォータの使用状況メトリクスを CloudWatch に発行

❌ アップデート前の課題

✗クォータ引き上げにはサポートケースの起票が必要で、手動レビューの完了まで待つ必要があった
✗クォータの現在値と使用状況を一元的に確認する手段が限られ、上限到達を事前に検知しにくかった
✗マルチテナント構成や SaaS 環境の拡張時に、引き上げの待ち時間がデプロイのボトルネックになることがあった

✅ アップデート後の改善

✓Service Quotas コンソール / API から 28 個のクォータを表示、監視、引き上げリクエスト可能に
✓Business Support 以上なら公開しきい値内のリクエストは自動承認され、サポートケースが不要に
✓5 分ごとの使用状況メトリクスと CloudWatch アラームで事前検知と計画的な引き上げが可能に

ステップ 1: CloudFront のクォータ一覧を確認する

Bash 適用済みクォータの一覧を取得 
aws service-quotas list-service-quotas \
  --service-code cloudfront \
  --region us-east-1

クォータコード、名前、現在値の一覧を取得します。CloudFront はグローバルサービスのため、us-east-1 リージョンを指定します。

ステップ 2: クォータ引き上げをリクエストする

Bash クォータ引き上げリクエスト 
aws service-quotas request-service-quota-increase \
  --service-code cloudfront \
  --quota-code L-XXXXXXXX \
  --desired-value 1000 \
  --region us-east-1

Business Support 以上を契約しており、希望値が公開しきい値内であれば自動的に承認されます。

ステップ 3: リクエストの状況を確認する

Bash リクエスト履歴とステータスの確認 
aws service-quotas list-requested-service-quota-change-history \
  --service-code cloudfront \
  --region us-east-1

クォータ引き上げリクエストの履歴とステータス (PENDING、APPROVED など) を確認します。

ステップ 4: CloudWatch アラームで使用状況を監視する

Service Quotas コンソールの各クォータ詳細ページから、使用率に対する CloudWatch アラーム (例: 使用率 80% 到達で通知) を作成できます。使用状況メトリクスを発行するクォータが対象です。

💼 ビジネス面

✓リードタイムの短縮: サポートケースの起票と手動レビューの待ち時間がなくなり、サービス拡張のスピードが向上する
✓運用負荷の削減: クォータ引き上げの申請作業が簡素化され、運用チームの工数を削減できる
✓成長への即応性: SaaS やマルチテナント環境でテナント追加時のクォータ制約に迅速に対応できる

🔧 技術面

✓一元的なクォータ管理: 他の AWS サービスと同様に Service Quotas でクォータを統一的に管理できる
✓自動化との親和性: Service Quotas API を使用して、IaC やスクリプトからクォータ引き上げを自動化できる
✓プロアクティブな監視: 5 分間隔の使用状況メトリクスと CloudWatch アラームにより、上限到達前に対処できる

⚠️ デメリット・制約事項

🚧 制限事項

⚠️自動承認を利用するには AWS Business Support 以上のサポートプラン契約が必要
⚠️自動承認されるのは公開しきい値の範囲内のリクエストのみで、それを超える場合はレビューが必要
⚠️Service Quotas に対応するのは 28 個のクォータであり、未対応のクォータは従来どおりサポートケースでの申請が必要
⚠️使用状況メトリクスを CloudWatch に発行するのは一部のクォータに限られる

🤔 考慮すべき点

💭Basic または Developer Support の場合、Service Quotas からリクエストは可能だが自動承認の対象外となる
💭CloudFront はグローバルサービスのため、Service Quotas の操作は us-east-1 リージョンで行う必要がある
💭クォータ引き上げはコスト増加につながるリソース作成を許容するため、IAM によるリクエスト権限の制御などガバナンス上の管理を検討する

🎯 ユースケース

1️⃣ SaaS 事業者のテナント拡大への即応

シナリオ: マルチテナント SaaS を運用しており、テナント追加に伴いディストリビューション数がデフォルト上限の 500 に近づいている。

Bash ディストリビューション数の引き上げ 
aws service-quotas request-service-quota-increase \
  --service-code cloudfront \
  --quota-code <ディストリビューション数のクォータコード> \
  --desired-value 1000 \
  --region us-east-1

効果: Business Support 以上であれば自動承認されるため、サポートケースの待ち時間なしでテナント追加を継続できる。

2️⃣ 多数のカスタムドメインを持つ Web サイトの統合配信

シナリオ: 1 つのディストリビューションで多数のブランドドメインを配信しており、代替ドメイン名数がデフォルトの 100 では不足する。

Bash 代替ドメイン名数の引き上げ 
aws service-quotas request-service-quota-increase \
  --service-code cloudfront \
  --quota-code <代替ドメイン名数のクォータコード> \
  --desired-value 500 \
  --region us-east-1

効果: 代替ドメイン名数を最大 500 まで自動承認で引き上げられ、ディストリビューションを分割せずにドメインを追加できる。

3️⃣ クォータ使用率のプロアクティブな監視

シナリオ: CI/CD パイプラインでディストリビューションやポリシーを動的に作成しており、クォータ上限到達によるデプロイ失敗を防ぎたい。
