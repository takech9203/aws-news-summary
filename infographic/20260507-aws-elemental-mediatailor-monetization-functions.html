AWS Elemental MediaTailor

📺 Monetization Functions

ストリーミング広告マネタイゼーションをサーバーレスで最適化する新機能が一般提供開始

2026-05-07

📋 概要

AWS Elemental MediaTailor が Monetization Functions を一般提供 (GA) として発表。ストリーミングメディアのプレイバックセッション中に、広告判定サーバー (ADS) へのリクエストのカスタマイズやセッションデータの管理を柔軟に行えるようになった。

JSONata 式を使用したデータ変換や、外部データソースからの情報エンリッチメントがサーバーレスで実現される。カスタムミドルウェアの構築・運用が不要に。

🔄 Before / After

❌ Before

  • プレーヤーと ADS の間にカスタムミドルウェアを自前で構築・運用が必要
  • 外部データソース連携のためのインフラ管理が必要
  • セッション初期化時のデータ変換に高い開発コスト
  • ミドルウェア障害がプレイバック全体に影響するリスク

✅ After

  • カスタムインフラなしでライフサイクルフック内で外部 API 呼び出し・データ変換が可能
  • JSONata 式によるインラインデータ変換で開発工数を大幅削減
  • フェイルオープン設計で視聴者体験に影響しない信頼性を確保
  • 3 種類の関数タイプを組み合わせた複雑なワークフロー構築が可能

⚡ 主要機能

3 種類の関数タイプ

🌐 HTTP_REQUEST

外部 API に GET/POST リクエストを送信し、レスポンスデータを広告リクエストに統合する

📝 CUSTOM_OUTPUT

JSONata 式を使用してセッションパラメータのインラインデータ変換を実行する

🔄 SEQUENTIAL_EXECUTOR

複数の関数を順次実行し、条件付き実行 (RunCondition) やタイムアウト制御が可能

🛡️ フェイルオープン設計

✓ 関数がエラーを返した場合、出力を破棄してデフォルト動作を継続

✓ 視聴者のプレイバック体験を最優先で保護

⚙️ 設定方法

前提条件

✓ AWS Elemental MediaTailor のプレイバック設定が作成済み
✓ 外部 API エンドポイントが利用可能 (HTTP_REQUEST タイプ使用時)
✓ IAM ポリシーで mediatailor:PutFunction, GetFunction 等の権限付与済み

Step 1: Monetization Function の作成

Bash AWS CLI - Function 作成 
aws mediatailor put-function \
  --function-id "resolve-identity" \
  --function-type "HTTP_REQUEST" \
  --description "外部 ID プロバイダーで ID 解決" \
  --http-request-configuration '{
    "Runtime": "JSONATA",
    "MethodType": "POST",
    "Url": "https://api.example.com/resolve",
    "RequestTimeoutMilliseconds": 500,
    "Output": {"identity": "$.response.id"}
  }'

Step 2: プレイバック設定への関数マッピング

Bash AWS CLI - Playback Configuration 更新 
aws mediatailor put-playback-configuration \
  --name "my-playback-config" \
  --ad-decision-server-url "https://ads.example.com/vast" \
  --video-content-source-url "https://origin.example.com/content" \
  --function-mapping '{
    "PRE_ADS_REQUEST": "resolve-identity"
  }'

Step 3: ログ設定の有効化

Bash AWS CLI - ログ設定 
aws mediatailor configure-logs-for-playback-configuration \
  --playback-configuration-name "my-playback-config" \
  --percent-enabled 100 \
  --enabled-logging-strategies '["VENDED_LOGS"]' \
  --ads-interaction-log '{
    "PublishOptInEventTypes": ["PRE_ADS_REQUEST_FUNCTION_COMPLETED"]
  }'

技術面

☁️ サーバーレス実行

🛡️ 高信頼性

フェイルオープン設計により、関数障害が視聴者体験に影響しない

🔧 柔軟な制御

SEQUENTIAL_EXECUTOR で条件付き実行やパイプライン構成が可能、複雑なビジネスロジックにも対応

関数実行の成功・失敗を CloudWatch や S3 に記録でき、デバッグやパフォーマンス監視が容易

⚠️ デメリット・制約事項

制限事項

✗ 関数のランタイムは JSONata のみサポート (カスタムコードの実行は不可)
✗ HTTP_REQUEST のタイムアウトは RequestTimeoutMilliseconds で制御、外部 API のレスポンス時間に依存
✗ SEQUENTIAL_EXECUTOR の TimeoutMilliseconds 超過時、残りの関数はスキップ
✗ フェイルオープンのため、関数出力破棄時のフォールバック動作を事前に設計する必要あり

考慮すべき点

💡 外部 API の可用性とレイテンシーが広告リクエストのパフォーマンスに影響する可能性
💡 高トラフィック環境では外部プロバイダーの API レート制限に注意
💡 JSONata 式の複雑さがデバッグの難易度を上げる場合がある
💡 料金はライフサイクルフック呼び出しごとに課金、大規模ライブ配信では高コストの可能性

🎯 ユースケース

🔑 ユースケース 1: プライバシー準拠の ID 解決

シナリオ: ストリーミングサービスが、ハッシュ化されたメールアドレスから LiveRamp のプライバシー準拠 ID エンベロープを解決し、パーソナライズド広告を配信。

効果: カスタムサーバーなしでプライバシー準拠の ID 解決を実現し、広告ターゲティング精度の向上と CPM の増加を期待できる。

📋 ユースケース 2: コンテキストメタデータによる広告エンリッチメント

シナリオ: VOD プラットフォームが、GraceNote から番組ジャンルやコンテンツレーティングなどのメタデータを取得し、広告リクエストに付加してコンテキストターゲティングを実現。

効果: コンテンツのコンテキストに基づいた広告配信により、視聴者体験の向上と広告効果の最大化を実現。

🔬 ユースケース 3: A/B テストによる広告サーバー比較

シナリオ: メディア企業が、複数の広告判定サーバーの収益パフォーマンスを比較するための A/B テストを実施。

効果: 追加のインフラストラクチャなしで広告サーバーの A/B テストを実行し、データに基づいた収益最適化の意思決定が可能に。

💲 料金

Monetization Functions はライフサイクルフック呼び出し (invocation) ごとの従量課金制。関数の数、タイプ、ロジックの複雑さに依存しない。初期費用や最低利用料金は不要。

シナリオ 月額料金 (概算)
50 万視聴者 x 1 セッション + 18 広告ブレーク = 950 万 invocations $950
10 万視聴者 x 1 セッション + 10 広告ブレーク = 110 万 invocations $110
1 万視聴者 x 1 セッション + 5 広告ブレーク = 6 万 invocations $6
課金単位: 1 回の invocation は、1 つのライフサイクルフックにマッピングされた関数群の 1 回の実行に相当。マッピングされた関数の数に関係なく、フック呼び出し 1 回につき 1 invocation として課金。

📌 まとめ

AWS Elemental MediaTailor の Monetization Functions は、ストリーミングメディアのマネタイゼーションにおいて、カスタムインフラストラクチャの構築・運用を不要にする重要なアップデート。JSONata ベースのデータ変換と外部 API 連携をフェイルオープン設計で提供し、視聴者体験を損なうことなく広告収益の最適化を実現する。

ID 解決、コンテキストターゲティング、ヘッダービディングなどのユースケースを持つストリーミング事業者は、早期の評価・導入を推奨。
