⚡ 主要機能

🔍 新コマンド: parse logfmt

logfmt 形式のログ行をキー・バリューペアのマップとして自動パース。ドット記法でフィールドにアクセス可能 (例: lf.level, lf.duration)。Go 言語や Ruby のアプリケーションログで広く使われる形式に対応。

📦 新コマンド: expand

JSON 配列を含むフィールドを個別のログイベントに展開。元のログイベントの他のフィールドは各新レコードに複製され、配列要素ごとの集計や分析が可能に。

🎯 新コマンド: relevantfields

指定条件に対して最も関連性の高いフィールドを自動ランキング。ベースライン全体と条件合致サブセットを比較し、関連度スコア (0-1) を算出。障害原因の迅速な特定に有効。

✂️ 文字列関数: startsWith / endsWith / regex_replace

startsWith: 指定プレフィックスで始まるかを判定。endsWith: 指定サフィックスで終わるかを判定。regex_replace: RE2 正規表現構文による文字列置換。

🔐 エンコード/デコード関数

urlencode / urldecode、base64encode / base64decode でエンコード/デコードをクエリ内で直接実行。エンコードされたペイロードをインラインで変換して分析可能。

🧮 数値・条件関数: round / haversine / case

round(a, d): 数値を指定小数点桁数で丸め。haversine(lat1, lon1, lat2, lon2): 2 点間の大圏距離をキロメートルで計算。case(cond1, val1, ...): 条件分岐ロジック (最大 10 分岐)。

🛠️ 設定方法・クエリ例

前提条件

CloudWatch Logs にログデータが収集済み logs:StartQuery 権限 logs:GetQueryResults 権限 Standard または Infrequent Access ログクラス

parse logfmt によるログパース

CloudWatch Logs Insights logfmt ログのパースとフィルタリング 
parse @message logfmt as lf
| filter lf.level = "error"
| display lf.msg, lf.duration, lf.host

expand による配列展開と集計

CloudWatch Logs Insights JSON 配列の展開と集計 
fields @timestamp, @message
| parse @message "items=*" as items_json
| fields jsonParse(items_json) as items
| expand items
| stats count(*) by items

⚠️ デメリット・制約事項

制限事項

  • relevantfields の @relevanceScore はヒューリスティックな指標であり、因果関係を保証するものではない
  • case 関数は最大 10 分岐に制限されている
  • parse logfmt はマップ型を返すため、dedup、pattern、sort、stats でマップ全体を直接使用できない
  • expand で展開される配列サイズが大きい場合、スキャンデータ量が増加する可能性がある

考慮すべき点

  • regex_replace は RE2 構文を使用。PCRE 固有の機能 (後方参照、先読みなど) は使用不可
  • haversine の入力は度単位の緯度経度。ラジアン変換は不要
  • 新コマンド・関数は Standard ログクラスと Infrequent Access ログクラスの両方で利用可能

💡 ユースケース

🔧 マイクロサービスの logfmt ログ分析

シナリオ: Go 言語で構築されたマイクロサービスが logfmt 形式でログを出力。エラー率とレイテンシの相関を分析したい。

CloudWatch Logs Insights 
parse @message logfmt as lf
| filter lf.level = "error"
| stats count(*) as error_count, avg(lf.duration) as avg_duration by lf.service, bin(5m)
| sort avg_duration desc

効果: 複雑な正規表現が不要。サービスごとのエラー傾向とレイテンシの関係を迅速に把握。

🌐 API Gateway ログのデコードと分析

シナリオ: API Gateway のアクセスログに URL エンコードされたクエリパラメータや Base64 エンコードされたリクエストボディが含まれている。

CloudWatch Logs Insights 
fields @timestamp, urldecode(queryString) as decoded_query, base64decode(requestBody) as decoded_body
| filter startsWith(decoded_query, "action=")
| parse decoded_query "action=*&" as action_type
| stats count(*) by action_type, bin(1h)

効果: エンコードされたデータの外部デコード処理が不要。リアルタイムでリクエストパターンの分析が可能。

🔎 レイテンシ急増の根本原因調査

シナリオ: 本番環境でレイテンシの急増が発生。どのフィールドが最も関連しているかを迅速に特定したい。

CloudWatch Logs Insights 
relevantfields Controller, Region, InstanceType, APIEndpoint where @duration > 3000

効果: 手動で各フィールドを個別にフィルタリングする代わりに、関連度スコアで即座にボトルネックの原因候補を絞り込み。
