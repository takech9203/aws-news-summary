Kiro IDE 1.4.0

🧠 チャットセッションをまたぐ Memory 機能の一般提供開始

📅 リリース日: 2026 年 10 月 19 日 🛠️ サービス: Kiro (IDE 1.4.0) ✨ 機能: Memory Across Chat Sessions

📋 概要

Kiro IDE 1.4.0 のリリースにより、Memory 機能がすべての Kiro IDE ユーザーに提供されました。リポジトリのコマンドや規約、修正指示、デバッグの知見、不採用と判断したアプローチ、ユーザーの作業スタイルといった有用なコンテキストを、チャットセッションをまたいで保持し、関連する場面で Kiro が活用します。

Memory は、コンテキストを組み立ててエージェントを実行する Kiro エージェントハーネスの一部として動作し、「どの情報を保持する価値があるか判断する」「タスクに関連するメモリを見つける」という 2 つの課題を解決します。各メモリはタイトル、説明、内容を持つレコードであり、過去の会話のコピーではありません。

❌ Before: アップデート前の課題
  • セッション終了で規約や修正指示などのコンテキストが引き継がれず、毎回説明し直す必要があった
  • デバッグの知見や不採用アプローチが記録されず、同じ調査を繰り返すおそれがあった
  • 恒常的なルールの引き継ぎは Steering ファイルとして明示的に記述する必要があった
✅ After: アップデート後の改善
  • Kiro が作業から有用なコンテキストを自動的に学習し、後続セッションで想起できる
  • Memory ビューから記憶内容の確認、検索、削除が可能になった
  • チャット上でメモリ操作が可視化され、Kiro Agent: Memory 設定で使用・学習方法を制御できる

エージェントハーネスが現在のセッションから有用なコンテキストを学習してメモリとして保存し、後続のセッションで関連するメモリを想起してタスクに活用する流れを示しています。

⭐ 主要機能

1. 🔄 セッションをまたぐコンテキストの保持 (Memory)
  • リポジトリのコマンドや規約、修正指示、デバッグの知見、不採用アプローチ、作業スタイルなどを記憶
  • 各メモリはタイトル、説明、内容を持つレコードとして保存 (会話のコピーではない)
  • 後続セッションで、作業中のリクエストに関連するメモリを Kiro が自動的に想起
2. 🗂️ Memory ビューによる記憶内容の管理
  • アクティビティバーの Memories アイコンから、グローバルメモリとリポジトリスコープのメモリを一覧
  • タイトル、経過時間、1 行サマリー、タイプ (Preference、Fact など)、適用場所を表示
  • 検索・フィルタリング、エディタタブでの内容確認、右クリックまたはタブからの削除に対応
3. 👁️ チャット上でのメモリ操作の可視化
  • チャットに Memory accessed、Memory created、Memory updated などの折りたたみ可能なエントリを表示
  • タイトルにカーソルを合わせるとタイプとサマリーを確認でき、選択するとメモリを開ける
  • 想起されたメモリはコンテキストを消費し、Context Usage に Memory の行として表示
4. 🔐 Kiro Agent: Memory 設定によるアクセスレベル制御
  • メモリの使用と学習の方法を 4 段階のアクセスレベルで制御
  • Use only を選択すると、既存メモリを変更せずに読み取り専用で使用
  • 信頼していないワークスペースでは、チャットからの追加・変更・削除は不可 (読み取りは可能)
5. 🛠️ その他の改善と修正 (IDE 1.4.0)
  • Markdown Review の検索改善: ドキュメント更新時にマッチを保持、非表示の数式テキストや図のコントロールを無視、マッチ多数のドキュメントにも対応。コメントは対象文章にアンカーされたまま維持
  • サインイン画面が Cancel を無視する問題を修正。Cancel で開始画面に戻り、再試行を妨げない
  • Ubuntu 24.04 以降で .deb パッケージからのインストール後に起動しない問題を修正

🔬 技術仕様

🎚️ Memory のアクセスレベル

アクセスレベル動作
Use and learnメモリを使用し、権限に従って変更できる。メモリの作成・更新を自動的に行う (デフォルト)
Use but don't learnメモリを使用し、ユーザーが依頼した場合のみ権限に従って変更する。自動的な作成・更新は行わない
Use only既存のメモリを使用するが、依頼されても作成・更新・削除は行わない (読み取り専用)
Offメモリを使用せず、変更もしない

⚙️ 設定の適用タイミングとスコープ

項目詳細
設定スコープユーザー設定のみ有効。ワークスペース設定に値を記述しても効果はない
オン / オフ、Use only への切り替え新しいセッションから適用される。「Memory settings updated. The change applies to new sessions.」の通知と Start new session アクションが表示される
Use and learn と Use but don't learn 間の切り替え開いているローカルセッションに即時反映される
ワークスペーストラスト信頼していないワークスペースでは、チャットからのメモリの追加・変更・削除は不可 (読み取りは可能)
メモリの構成要素タイトル、説明、内容。タイプ (Preference、Fact、Other) と場所 (Global またはリポジトリ) を持つ

🚀 設定方法

✅ 前提条件

✓Kiro IDE 1.4.0 以降がインストールされていること
✓Kiro にサインインしていること
✓メモリを変更する場合は、対象のワークスペースを信頼していること

📝 手順

1
Memory ビューを開く

アクティビティバーの Memories アイコンを選択して Memory ビューを開きます。グローバルメモリと、現在のウィンドウで開いているリポジトリにスコープされたメモリが一覧表示されます。

2
アクセスレベルを設定する

Memory ビューの設定ギアから Kiro Agent: Memory 設定を開き、Use and learn (デフォルト)、Use but don't learn、Use only、Off から選択します。オン / オフや Use only への切り替えは新しいセッションから適用されます。

3
記憶内容を確認・管理する

検索ボックスでタイトルやサマリーをフィルタリングし、行を選択してエディタタブで内容を確認します。不要なメモリは右クリックまたはタブの Delete ボタンから削除します (削除前に確認ダイアログが表示されます)。チャットでは Memory accessed などのエントリからセッション中のメモリ操作を確認できます。

💡 メリット

💼 ビジネス面
✓オンボーディングの効率化: リポジトリ固有のコマンドや規約を記憶するため、セッションごとの説明が不要になり、作業の立ち上がりが速くなる
✓作業の継続性向上: コンテキストの再構築に費やす時間が減り、タスクの継続に集中できる
✓ガバナンスの確保: アクセスレベル設定とワークスペーストラストにより、組織のポリシーに応じて学習・変更を制御できる
⚙️ 技術面
✓デバッグ知見の再利用: 「統合テストの前にローカルデータベースのシードが必要」といった知見を記録し、原因調査の繰り返しを回避
✓不採用アプローチの記録: 検討済みで不採用とした方法を記憶し、同じ提案の繰り返しを回避
✓透明性の高い動作: メモリへのアクセス・作成・更新がチャットで可視化され、Context Usage で消費量も確認できる

⚠️ デメリット・制約事項

🚧 制限事項

✗Memory 設定はユーザー設定のみ有効で、ワークスペース設定では制御できない
✗信頼していないワークスペースでは、チャットからメモリを追加・変更・削除できない (読み取りは可能)
✗オン / オフや Use only への切り替えは新しいセッションからの適用となり、既存セッションには反映されない

🤔 考慮すべき点

⚠想起されたメモリはコンテキストを消費するため、Context Usage で使用状況を確認するとよい
⚠常に一貫して適用すべきルールは、Memory ではなく Steering に明示的に記述することが推奨されている
⚠Use only でも Memory ビューからの削除は可能だが、メモリ内容の修正をチャットで依頼できるのは Use and learn または Use but don't learn のときのみ

🎯 ユースケース

📌 ユースケース 1: リポジトリ固有の手順の自動想起

シナリオ: 統合テストがローカルデータベースのシード後にしか成功しないリポジトリで、毎回テスト失敗の原因調査から始まってしまう。

Text実装例
1. デバッグセッション中に Kiro が「シード前は統合テストが失敗する」ことを学習
2. メモリ seed-db-before-integration-tests が作成される
3. 後続セッションでテスト実行を依頼すると、チャットに
   Memory accessed (1) が表示され、シードを先に実行する

効果: 原因の再調査が不要になり、テスト実行までの手戻りが削減される。

📌 ユースケース 2: コーディング規約・修正指示の継続適用

シナリオ: レビューのたびに「このプロジェクトではこの命名規則を使う」「このライブラリは使わない」といった同じ指摘を Kiro に伝え直している。

Text実装例
1. アクセスレベルを Use and learn (デフォルト) のままにする
2. チャットで規約や修正指示を伝えると、Kiro がメモリとして学習
3. Memory ビューで Preference タイプのメモリとして内容を確認

効果: セッションをまたいで修正指示が反映され、同じ指摘の繰り返しが減る。

📌 ユースケース 3: 読み取り専用運用による安定したコンテキスト利用

シナリオ: チームで検証済みの知見だけを Kiro に使わせたいが、日々の作業で意図しないメモリが自動的に追加されることは避けたい。

Text実装例
1. 必要なメモリが蓄積された段階で、Kiro Agent: Memory 設定を
   Use only に変更
2. 新しいセッションから、Kiro は既存メモリを読み取り専用で使用
3. 不要になったメモリは Memory ビューから手動で削除

効果: 検証済みのコンテキストのみを安定して活用でき、メモリの意図しない変更を防止できる。

📝 まとめ

Kiro IDE 1.4.0 で Memory 機能がすべてのユーザーに提供され、リポジトリの規約や修正指示、デバッグの知見をセッションをまたいで活用できるようになりました。

✓デフォルトの Use and learn で自動学習が有効。まずは Memory ビューで記憶内容を確認する
✓チームのポリシーに合わせて Kiro Agent: Memory 設定のアクセスレベルを選択する
✓常に適用すべきルールは引き続き Steering に記述し、Memory と役割を分担させるのが効果的
