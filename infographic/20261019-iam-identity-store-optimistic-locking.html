AWS IAM Identity Center 📅 2026 年 10 月 19 日

🔒 アイデンティティストアがユーザー・グループの楽観的ロックに対応

Revision 値による条件付き更新・削除で、同時変更の競合を API レベルで検出

📝 概要

IAM Identity Center のアイデンティティストアが、ユーザーとグループに対する楽観的ロック (Optimistic Locking) をサポートしました。 最後に読み取った時点から対象が変更されていない場合にのみ、更新や削除のリクエストが成功するように制御できます。

各ユーザー・グループには Revision 値が付与され、SCIM プロビジョニング、Active Directory 同期、コンソール操作など、変更経路を問わず属性変更のたびに更新されます。 条件付きリクエストで Revision が一致しない場合は ConflictException が返され、意図しない上書きを防止できます。 Revision の指定はオプションのため、既存のインテグレーションへの影響はありません。

❌ アップデート前の課題

✗複数の管理者や自動化ツールの同時更新で、後の書き込みが先の変更を暗黙的に上書き
✗SCIM 同期とカスタム自動化が並行する環境で、競合を API レベルで検出する手段がない
✗競合回避にはアプリケーション側で独自の排他制御やロック機構の実装が必要

✅ アップデート後の改善

✓Revision 値を用いた条件付きリクエストで、変更がない場合にのみ更新・削除が成功
✓競合時は ConflictException が返却され、再読み取りとリトライで安全に競合解決
✓Revision はオプションのため、既存ワークフローを変更せず段階的に導入可能

🔄 楽観的ロックの動作シーケンス

複数のクライアントが同一ユーザーを同時に更新しようとした場合の動作です。Revision が一致しないリクエストは ConflictException で拒否され、再読み取り後のリトライにより安全に更新が完了します。

    participant A as 👤 管理者 A
    participant B as 🤖 自動化処理 B
    participant IS as 🗄️ Identity Store API

    A->>IS: DescribeUser
    IS-->>A: ユーザー情報と Revision v1
    B->>IS: DescribeUser
    IS-->>B: ユーザー情報と Revision v1

    A->>IS: UpdateUser に Revision v1 を指定
    IS-->>A: 成功 Revision は v2 に更新

    B->>IS: UpdateUser に Revision v1 を指定
    IS-->>B: ConflictException 競合を検出

    B->>IS: DescribeUser で再読み取り
    IS-->>B: 最新のユーザー情報と Revision v2
    B->>IS: UpdateUser に Revision v2 を指定
    IS-->>B: 成功 Revision は v3 に更新

⚙️ 主要機能

🔢 Revision 値による変更追跡

すべてのユーザーとグループに Revision 値が付与され、属性が変更されるたびに変化します。SCIM プロビジョニング、Active Directory 同期、コンソール操作など、あらゆる変更経路で Revision が更新されます。

🛡️ 条件付き更新・削除リクエスト

UpdateUser、UpdateGroup、DeleteUser、DeleteGroup で Revision を指定可能。指定値が現在の Revision と一致する場合にのみ成功し、不一致の場合は ConflictException が返されます。

📥 Revision の取得手段

Create、Describe、Update、List の各オペレーションが現在の Revision を返却します。更新成功時のレスポンスから新しい Revision を取得し、後続の操作に利用できます。

🔄 後方互換性の維持

Revision の指定はオプションであり、省略した場合は従来どおりの動作となります。既存のインテグレーションやスクリプトは変更なしで動作し続けます。

🛠️ 設定方法

前提条件

  • ✓ AWS IAM Identity Center が有効化されていること
  • ✓ アイデンティティストアの ID (IdentityStoreId) を把握していること
  • ✓ identitystore API を呼び出す IAM 権限 (例: identitystore:DescribeUser、identitystore:UpdateUser) があること

ステップ 1: 現在の Revision を取得する

BashDescribeUser で Revision を取得
aws identitystore describe-user \
  --identity-store-id d-1234567890 \
  --user-id "94482488-3041-7026-18f3-example"

レスポンスに現在の Revision 値が含まれるため、この値を控えておきます。

ステップ 2: Revision を指定して条件付き更新を実行する

BashUpdateUser に Revision を指定
aws identitystore update-user \
  --identity-store-id d-1234567890 \
  --user-id "94482488-3041-7026-18f3-example" \
  --operations '[{"AttributePath": "title", "AttributeValue": "Senior Engineer"}]' \
  --revision "<ステップ 1 で取得した Revision>"

読み取り時点から対象ユーザーが変更されていればリクエストは ConflictException で失敗し、意図しない上書きを防止できます。

💡 メリットと制約事項

✅ メリット

✓データ整合性の向上: 複数チームや自動化処理による変更の相互上書きリスクを排除し、監査性と信頼性を向上
✓運用リスクの低減: 意図しない属性の巻き戻りや削除事故を防止
✓API レベルの競合検出: 独自の排他制御を実装せず標準機能として競合を検出
✓安全なリトライ設計: ConflictException を契機とした冪等で堅牢な自動化を実装可能
✓追加コスト不要: 追加料金なしで導入障壁が低い

⚠️ 制約・考慮点

✗条件付きリクエストは Identity Store API 経由のみ。SCIM エンドポイントでは利用不可
✗グループメンバーシップ操作は Revision を受け付けず、メンバーシップ変更は Revision を変化させない
✗対象は UpdateUser / UpdateGroup / DeleteUser / DeleteGroup に限定
📌 考慮すべき点
• 外部 IdP 連携環境では SCIM 同期や AD 同期でも Revision が変化するため競合が発生しやすく、リトライ処理の実装が重要
• Revision を省略したリクエストは無条件で成功するため、効果を得るにはすべての更新経路で Revision を指定する運用が望ましい
• 競合が頻発するワークロードでは、リトライ回数の上限やバックオフ戦略の設計が必要

🎯 ユースケース

1️⃣ 複数管理者による同時運用での上書き防止

シナリオ: 複数の IT 管理者がコンソールや CLI から同じユーザー情報を更新しており、競合によって属性が意図せず巻き戻る事象が発生している。

Bash更新前に Revision を取得して条件付き更新
# 更新前に必ず最新の Revision を取得
aws identitystore describe-user \
  --identity-store-id d-1234567890 \
  --user-id "<ユーザー ID>"

# 取得した Revision を指定して更新
aws identitystore update-user \
  --identity-store-id d-1234567890 \
  --user-id "<ユーザー ID>" \
  --operations '[{"AttributePath": "displayName", "AttributeValue": "New Name"}]' \
  --revision "<取得した Revision>"
💪 効果: 他の管理者が先に変更していた場合はリクエストが失敗するため、最新状態を確認したうえで更新でき、変更の上書き事故を防止できる。
2️⃣ SCIM 同期と並行する自動化パイプラインの保護

シナリオ: 外部 IdP からの SCIM プロビジョニングが稼働している環境で、社内の自動化パイプラインが追加の属性更新を行っており、同期処理との競合が懸念される。

  • → DescribeUser で属性と Revision を取得
  • → Revision を指定して UpdateUser を実行
  • → ConflictException 発生時は指数バックオフで再読み取りとリトライ
  • → 最大リトライ回数を超えた場合はアラートを送信
💪 効果: SCIM 同期が直前にユーザーを変更していた場合でも、自動化側が古い状態に基づいて上書きすることを防ぎ、両者の変更を安全に共存させられる。
3️⃣ 安全なユーザー・グループ削除の実装

シナリオ: 退職者のオフボーディング処理でユーザーを削除する際、削除判断の根拠とした情報が削除実行時点まで変わっていないことを保証したい。

BashRevision を指定した条件付き削除
# 削除対象の状態と Revision を確認
aws identitystore describe-user \
  --identity-store-id d-1234567890 \
  --user-id "<ユーザー ID>"

# 確認した Revision を指定して削除
aws identitystore delete-user \
  --identity-store-id d-1234567890 \
  --user-id "<ユーザー ID>" \
  --revision "<確認した Revision>"
💪 効果: 確認後にユーザー情報が変更されていた場合は削除が失敗するため、最新状態を再確認してから削除を判断でき、誤削除のリスクを低減できる。

🔗 関連サービス・機能

  • → AWS IAM Identity Center: 本機能が属するサービス。AWS アカウントやアプリケーションへのシングルサインオンとアイデンティティ管理を提供
  • → Identity Store API: ユーザー・グループの作成、参照、更新、削除を行う API。今回のアップデートで条件付きリクエストに対応
  • → SCIM プロビジョニング: 外部 IdP からの同期の仕組み。SCIM による変更も Revision を更新するが、SCIM エンドポイント自体は条件付きリクエスト非対応
  • → AWS Managed Microsoft AD / AD Connector: Active Directory 同期による変更も Revision の更新対象

✨ まとめ

IAM Identity Center のアイデンティティストアが楽観的ロックに対応し、ユーザー・グループの更新・削除における同時変更の競合を API レベルで検出できるようになりました。 Revision の指定はオプションで後方互換性が維持されているため、既存環境への影響なく導入できます。 複数の管理者や自動化処理がアイデンティティ情報を変更している環境では、更新・削除リクエストに Revision を指定し、 ConflictException に対するリトライ処理を組み込むことを推奨します。
