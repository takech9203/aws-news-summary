AWS Glue (Data Catalog)

🔐 Apache Iceberg REST Catalog API で OAuth 2.0 認証をサポート

AWS 認証情報を配布せずに、外部クエリエンジンやパートナーへフェデレーテッドアクセスを提供
📅 リリース日: 2026 年 10 月 26 日 🛠️ 機能: OAuth 2.0 ベアラートークン認証

📋 概要

AWS Glue Data Catalog が、Apache Iceberg REST Catalog (IRC) API において AWS Sign-In を利用した OAuth 2.0 ベアラートークン認証をサポートしました。IRC 仕様は OAuth 2.0 を標準の認証メカニズムとして定義しており、Apache Spark、Trino、Apache Flink などのクエリエンジンがネイティブに実装しています。既存の SigV4 に加えて、業界標準の方法で Glue の Iceberg エンドポイントに認証できます。

認証の仕組みには OAuth 2.0 Token Exchange (RFC 8693) を採用。連携パートナーはエンドユーザーの OIDC ID トークン (JWT) を AWS Sign-In のトークン交換エンドポイントに提示し、Glue サービスにスコープされた短命の OAuth アクセストークンと交換します。アクセス権限は引き続き AWS IAM と AWS Lake Formation によって管理されるため、既存のガバナンスモデルを維持できます。

😣 アップデート前の課題
✗認証は SigV4 のみで、外部エンジンやパートナーに AWS 認証情報 (アクセスキー等) の配布・管理が必要
✗OAuth 2.0 ネイティブ実装のエンジンやサードパーティ製品から接続する際、SigV4 署名のための追加実装が必要
✗パートナーのエンドユーザー単位のフェデレーテッドアクセスを標準的な方法で実現することが困難
😊 アップデート後の改善
✓IRC 仕様準拠の標準 OAuth 2.0 ベアラートークン (Authorization: Bearer ヘッダー) で認証可能に
✓RFC 8693 のトークン交換により、OIDC ID トークンを短命の Glue スコープトークンに交換。AWS 認証情報の配布が不要に
✓IAM ロール + Lake Formation + オプションのセッションポリシーでアクセスを制御し、ガバナンスを維持

連携パートナーがエンドユーザーの OIDC トークンを AWS Sign-In で Glue スコープのアクセストークンに交換し、Glue Iceberg REST エンドポイントに Bearer トークンで認証するフローです。すべてのリクエストで Lake Formation の権限が適用されます。

⚡ 主要機能

🎫 1. OAuth 2.0 ベアラートークン認証
→Glue Iceberg REST エンドポイントが Authorization: Bearer ヘッダーによる OAuth 2.0 アクセストークンを受け付け
→IRC 仕様の標準認証に準拠し、Apache Spark、Trino、Apache Flink などの OAuth ネイティブ実装と互換
→既存の SigV4 認証も引き続き利用可能。AWS SDK や AWS ネイティブ分析エンジンからの接続は従来どおり
🔄 2. OAuth 2.0 Token Exchange (RFC 8693) によるフェデレーション
→エンドユーザーの JWT を地域別トークン交換エンドポイント https://{region}.oauth.signin.aws に提示
→AWS STS が issuer、audience、署名を IAM OIDC プロバイダーに対して検証し、JWT の https://aws.amazon.com/roles クレームで指定された単一の IAM ロールを引き受け
→Glue サービスプリンシパル glue.amazonaws.com にスコープされた短命のアクセストークンを発行
🛡️ 3. IAM と Lake Formation による一貫したアクセス制御
→OAuth 認証は追加の AWS 権限を付与せず、IAM ロールの権限と Lake Formation の権限付与の範囲に制限
→IAM 管理ポリシー ARN を scope パラメータに渡し、セッションポリシーとしてさらに絞り込み可能
→LoadTable 操作で払い出される Amazon S3 認証情報も同じ権限境界内に制限
📝 4. 監査とトークン管理
→トークン交換 (CreateOAuth2Token) とイントロスペクション (IntrospectOAuth2Token) は AWS CloudTrail に記録
→IntrospectOAuth2Token API でトークンのメタデータを検証可能

🎟️ トークン仕様

項目詳細
トークン交換エンドポイントhttps://{region}.oauth.signin.aws/v1/token
grant_typeurn:ietf:params:oauth:grant-type:token-exchange
subject_token_typeurn:ietf:params:oauth:token-type:jwt
resourceglue.amazonaws.com (Glue サービスプリンシパル)
scope (オプション)お客様所有の IAM 管理ポリシー ARN (セッションポリシーとして適用)
アクセストークン有効期間最大 1 時間。リフレッシュトークンは発行されず、期限切れ時は再度トークン交換を実行
セッション時間JWT の https://aws.amazon.com/session_duration クレームで 900〜43,200 秒を指定可能 (ロールの最大セッション時間が上限)

📜 サブジェクトトークン (JWT) の必須クレーム

クレーム用途
iss発行者。お客様アカウントに登録した IAM OIDC プロバイダーと一致する必要がある
subパートナーのエンドユーザーを識別
aud地域別トークン交換エンドポイント URL と一致する必要がある
exp / iat有効期限と発行時刻
https://aws.amazon.com/roles引き受ける IAM ロール ARN (ちょうど 1 つ)
https://aws.amazon.com/role_session_nameロールセッション名 (2〜64 文字)

💻 トークン交換リクエストの例

HTTP トークン交換リクエスト 
POST /v1/token HTTP/1.1
Host: {region}.oauth.signin.aws
Content-Type: application/x-www-form-urlencoded

grant_type=urn%3Aietf%3Aparams%3Aoauth%3Agrant-type%3Atoken-exchange
&subject_token={partner-jwt}
&subject_token_type=urn%3Aietf%3Aparams%3Aoauth%3Atoken-type%3Ajwt
&resource=glue.amazonaws.com
&scope={managed-policy-arn}

レスポンスとして access_token (Bearer 形式、expires_in: 3600) が返却され、以下のように IRC API 呼び出しに使用します。

HTTP IRC API 呼び出し 
GET /iceberg/v1/catalogs/{catalog}/namespaces HTTP/1.1
Host: glue.{region}.amazonaws.com
Authorization: Bearer {oauth-access-token}

⚙️ 設定方法

✅ 前提条件

✓Glue Data Catalog に Apache Iceberg テーブルが存在すること
✓AWS Lake Formation によるアクセス管理が有効であること
✓連携パートナーの JWT 発行者 (issuer) URL が提供されていること

📝 手順

  1. IAM OIDC アイデンティティプロバイダーを作成
    IAM コンソールの [Identity providers] ページで、パートナーの JWT 発行者を信頼する OpenID Connect プロバイダーを作成。プロバイダー URL にはパートナーの JWT 発行者 URL、audience には https://{region}.oauth.signin.aws を指定。
  2. 信頼ポリシー付きの IAM ロールを作成
    信頼ポリシーで sts:AssumeRoleWithWebIdentity を許可し、aud クレームを検証。sts:RoleAuthorizedByIdp 条件により、パートナーのトークンが https://aws.amazon.com/roles クレームで認可した場合のみロールを引き受け可能にする。
  3. Lake Formation 権限をロールに付与
    公開したいデータベース、テーブル、列に必要な権限 (例: 特定テーブルへの SELECT と DESCRIBE) のみを付与。Lake Formation の権限付与がパートナーに見えるデータを制御する主要な境界となる。
  4. AWS Sign-In のトークン発行権限をロールに付与
    signin:CreateOAuth2Token を許可するアイデンティティベースポリシーをアタッチし、Glue スコープのアクセストークンを発行できるようにする。
  5. (オプション) 管理ポリシーでアクセスをさらに絞り込み
    許可する Glue アクションとリソースをスコープする IAM 管理ポリシーを作成し、パートナー接続の scope として設定。実効アクセスはロール権限、このポリシー、Lake Formation 権限付与の積集合になる。
  6. パートナー接続を設定
    パートナーに Glue Iceberg REST エンドポイント、AWS Sign-In トークン交換エンドポイント、ロール ARN、リソーススコープ (設定した場合) を提供。設定後はトークン交換とクエリが透過的に実行される。

🔧 IAM ロールの信頼ポリシー例 (ステップ 2)

JSON 信頼ポリシー 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::{your-account-id}:oidc-provider/{oidc-provider-issuer}"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "{oidc-provider-issuer}:aud": "https://{region}.oauth.signin.aws"
        },
        "Bool": {
          "sts:RoleAuthorizedByIdp": "true"
        }
      }
    }
  ]
}

🔧 トークン発行権限のポリシー例 (ステップ 4)

JSON アイデンティティベースポリシー 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "signin:CreateOAuth2Token",
      "Resource": "arn:aws:signin:{region}:{your-account-id}:service-principal/glue.amazonaws.com"
    }
  ]
}

💡 メリット

💼 ビジネス面
✓AWS 認証情報の配布が不要: アクセスキーを渡す必要がなくなり、漏えいリスクと管理コストを削減
✓パートナーエコシステムとの連携強化: IRC 標準認証への準拠で、Iceberg エコシステムの外部製品からの接続が容易に
✓ガバナンスの一元化: IAM と Lake Formation で一元管理でき、既存の監査・コンプライアンス体制を維持
🔧 技術面
✓標準準拠: RFC 8693 と OIDC に基づき、Apache Spark、Trino、Apache Flink がそのまま利用可能
✓短命トークン: 有効期間は最大 1 時間、リフレッシュトークンなしで漏えい時の影響範囲を限定
✓多層防御: IAM ロール権限 ∩ セッションポリシー ∩ Lake Formation 権限付与でアクセスを制限。LoadTable の S3 認証情報も同じ境界内
✓監査可能性: CloudTrail 記録に加え、ネットワーク条件キー (aws:SourceIp、aws:SourceVpc 等) も評価可能

⚠️ デメリット・制約事項

🚧 制限事項
•アクセストークンの有効期間は最大 1 時間で、リフレッシュトークンは発行されない。期限切れ時はパートナー側で再度トークン交換が必要
•JWT の https://aws.amazon.com/roles クレームに指定できるロール ARN はちょうど 1 つのみ
•scope に指定できるのはお客様アカウント内のお客様所有の管理ポリシーのみ。クロスアカウントのポリシーは不可
•無効なサブジェクトトークン (署名不正、発行者不一致、期限切れ) によるトークン交換の失敗は、対象アカウントの CloudTrail イベントとして記録されない
•Glue Iceberg REST エンドポイントは単一レベルのネームスペースのみをサポート (マルチレベルカタログ階層は catalog パスで表現)
🤔 考慮すべき点
→パートナーの発行者が共有プロバイダーに分類される場合、信頼ポリシーにテナンシーを強制する追加条件が必要 (IAM の OIDC secure-by-default 動作を参照)
→Lake Formation の権限付与がデータ可視性の主要な境界。パートナー用ロールには最小権限の原則に基づき必要最小限の SELECT / DESCRIBE のみを付与することを推奨
→OIDC プロバイダー、IAM ロール、Lake Formation 権限などのリソースは、Iceberg テーブルが存在するリージョンに作成する必要がある

🎯 ユースケース

☁️ ユースケース 1: サードパーティデータクラウドからの Iceberg テーブル参照

シナリオ: 外部のデータクラウドプラットフォームのユーザーが、AWS 上の Glue Data Catalog に登録された Iceberg テーブルを、プラットフォームの認証基盤のまま直接クエリしたい。

1.パートナーの JWT 発行者を IAM OIDC プロバイダーとして登録
2.読み取り専用の IAM ロールを作成し、Lake Formation で対象テーブルに SELECT / DESCRIBE を付与
3.パートナー接続に Glue IRC エンドポイント、トークン交換エンドポイント、ロール ARN を設定
✨ 効果: AWS 認証情報を配布せず、エンドユーザー単位のフェデレーテッドアクセスで単一ストレージコピーのまま安全にデータ共有できる。
🖥️ ユースケース 2: セルフマネージドの OSS クエリエンジンからの接続

シナリオ: AWS 外 (オンプレミスや他クラウド) で運用する Trino や Apache Flink から、IRC 標準の OAuth 認証で Glue Data Catalog の Iceberg テーブルにアクセスしたい。

→uri: https://glue.{region}.amazonaws.com/iceberg
→warehouse: {aws_account_id}
→認証: OAuth 2.0 ベアラートークン (AWS Sign-In のトークン交換で取得)
✨ 効果: SigV4 署名のための AWS SDK 統合や認証情報管理が不要になり、エンジン標準の OAuth 設定だけで接続できる。
🔒 ユースケース 3: セッションポリシーによる限定スコープのデータ提供

シナリオ: 特定のパートナーには一部のデータベース・テーブルのみ参照を許可し、将来のロール権限拡大の影響も受けないようにしたい。

1.許可する Glue アクションとリソースを限定した IAM 管理ポリシーを作成
2.パートナー接続の scope パラメータにポリシー ARN を設定
3.実効権限 = ロール権限 ∩ セッションポリシー ∩ Lake Formation 権限付与
✨ 効果: トークン交換時にセッションポリシーが適用され、多層防御により過剰なアクセスを構造的に防止できる。

📝 まとめ

AWS Glue Data Catalog の Iceberg REST Catalog API が OAuth 2.0 ベアラートークン認証に対応したことで、AWS 認証情報を配布することなく、サードパーティのクエリエンジンやデータプラットフォームに標準的な方法でフェデレーテッドアクセスを付与できるようになりました。

アクセス制御は引き続き IAM と Lake Formation に集約されるため、既存のガバナンスを維持したまま Iceberg エコシステムとの連携を拡大できます。

🚀 次のアクション: 外部パートナーとのデータ共有を検討している場合は、IAM OIDC プロバイダーとロールの設定、Lake Formation の最小権限付与から着手することを推奨します。
