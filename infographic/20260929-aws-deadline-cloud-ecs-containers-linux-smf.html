AWS Deadline Cloud 📅 2026 年 9 月 29 日

🐳 Linux サービスマネージドフリートで
ECS コンテナサポートを提供開始

Amazon ECR のイメージを指定するだけで、独自ソフトウェアを全ワーカーへ自動デプロイ

📋 概要

AWS Deadline Cloud が、Linux ベースのサービスマネージドフリート SMF 上で Amazon ECS の Docker コンテナを使用したジョブ実行をサポートしました。すでにソフトウェアをコンテナイメージとしてパッケージ化しているチームは、イメージを指定するだけで、サービスが全ワーカーインスタンスへ大規模かつ自動的にデプロイします。

レンダリング用の Blender はもちろん、NVIDIA Isaac Sim や MuJoCo といったフィジカル AI ツールなど、コンテナとしてデプロイ可能なあらゆるソフトウェアに対応。コンテナ統合はフリートとキューのレベルで完結するため、ジョブテンプレートの変更は不要です。

❌ Before: アップデート前の課題
  • SMF で独自ソフトウェアを使うには Conda パッケージ化やカスタムセットアップスクリプトが必要だった
  • コンテナイメージ化済みのソフトウェア資産を Deadline Cloud でそのまま活用できなかった
  • コンテナ環境の利用には顧客管理フリート CMF で自前のインフラ運用が必要になるケースがあった
✅ After: アップデート後の改善
  • Amazon ECR のイメージを指定するだけで SMF の全ワーカーにソフトウェアが自動デプロイされる
  • コンテナ統合がフリートとキューのレベルで完結し、ジョブテンプレート側の変更が不要になった
  • ローカルで動作確認したジョブバンドルを変更なしでクラウドのマネージドファームに投入できる

Amazon ECR のコンテナイメージをキュー環境に指定すると、Docker を有効化した Linux サービスマネージドフリートの各ワーカーがイメージを pull し、ジョブセッションごとにコンテナを起動してタスクを実行します。

⚡ 主要機能

🐳 Docker ソフトウェアアドオン (フリート側)
  • 追加設定で「Container support」を有効化すると、各ワーカーにルートレス Docker が自動インストール・構成される
  • GPU フリートでは Container Device Interface (CDI) が自動構成され、特権コンテナアクセスなしで GPU を利用可能
  • フリートロールに AmazonEC2ContainerRegistryReadOnly がアタッチされ、ECR からイメージを pull できる
📬 Docker デフォルトキュー環境 (キュー側)
  • キューの環境タイプとして「Docker」を選択し、Amazon ECR のイメージ URI を指定
  • カスタマイズすることで他のコンテナレジストリプロバイダーへの認証と pull も可能
  • ジョブセッションごとに 1 つのコンテナが起動され、セッション終了時に停止
📦 ジョブテンプレートの可搬性
  • ジョブテンプレートにコンテナコマンドやイメージ参照を含める必要がない
  • Open Job Description CLI でローカル実行できるジョブバンドルを追加変更なしで投入可能
  • セッションディレクトリがコンテナ内の同じパスにマウントされ、埋め込みファイル・ジョブアタッチメント・出力パスがそのまま利用できる
🔒 セキュリティ設計
  • Docker はルートレスモードで実行され、コンテナアクションは非特権の job-user ID で動作
  • コンテナからワーカーへの root アクセスは提供されない

フリートで Docker を有効化
  • Deadline Cloud コンソールでファームを開き、[Fleets] からサービスマネージドフリートを作成または編集
  • オペレーティングシステムとして Linux を選択
  • [Additional configurations] の [Container support] で [Enable Docker] を選択
  • フリートロールを選択または作成 (コンソールが AmazonEC2ContainerRegistryReadOnly ポリシーをアタッチ)
  • 必要に応じて [Persistent storage] を有効化し、Docker レイヤーとアプリケーションキャッシュを保持
2
キューに Docker キュー環境を設定
  • キューを作成または編集し、[Default queue environment] の [Environment type] で [Docker] を選択
  • [Container image URI] に Amazon ECR リポジトリとイメージタグを指定
  • キューロールを選択または作成し、キューを Docker 対応フリートに関連付け
Text Amazon ECR イメージ URI の形式 
{account-id}.dkr.ecr.{region}.amazonaws.com/{repository}:{tag}
3
設定の確認とジョブ投入
  • フリートの [Software add-ons] に Docker が含まれていることを確認
  • キューが Docker デフォルト環境を使用し、指定したイメージ URI が表示されていることを確認
  • キューが Docker 有効な Linux サービスマネージドフリートのみに関連付けられていることを確認
Bash ジョブバンドルの投入 (バンドル側の変更は不要) 
# ジョブバンドルを投入 (ローカルで動作するバンドルをそのまま投入可能)
deadline bundle submit ./my-job-bundle \
  --farm-id farm-xxxxxxxxxxxx \
  --queue-id queue-xxxxxxxxxxxx
⚠️フリート更新は実行中のワーカーを置き換えません。Docker ソフトウェアアドオンを全ワーカーに即時適用するには、フリートをドレインして再起動します。AWS CLI によるフリートとロールの自動セットアップもサポートされています。

💡 メリットと制約事項

💼 ビジネス面のメリット
✓移行の迅速化: 既存のコンテナ化済みワークフローを変更せずマネージドなレンダー / コンピュートファームへ移行でき、導入までの時間を短縮
✓運用負荷の削減: ワーカーへのソフトウェアデプロイをサービスが自動化し、環境構築・保守の工数が減少
✓ワークロードの拡大: レンダリングに加え、NVIDIA Isaac Sim や MuJoCo などフィジカル AI・シミュレーション用途にも同一基盤を活用
⚙️ 技術面のメリット
✓ジョブテンプレートの可搬性: コンテナ統合がフリート / キューレベルで完結し、テンプレートはコンテナ非依存のまま
✓セキュアな実行環境: ルートレス Docker と非特権 job-user により root アクセスなしで実行
✓GPU 対応: CDI により特権コンテナなしで GPU レンダリングや物理シミュレーションに対応
✓キャッシュの永続化: 永続ストレージで Docker レイヤーを保持し、イメージ pull の時間を短縮
🚫 制限事項
✗コンテナサポートは Linux SMF のみで利用可能であり、Windows フリートでは利用できない
✗デフォルトのキュー環境は Amazon ECR プライベートリポジトリからの pull が前提。他のレジストリにはキュー環境のカスタマイズが必要
✗フリート設定の更新は実行中のワーカーに自動適用されず、即時反映にはフリートのドレインと再起動が必要
⚠️ 考慮すべき点
⚠️フリートロールとキューロールの両方に Amazon ECR への読み取りアクセス権限 (AmazonEC2ContainerRegistryReadOnly) が必要
⚠️イメージサイズが大きい場合、初回 pull に時間がかかるため、永続ストレージの有効化やイメージの軽量化を検討
⚠️キューは Docker 有効なフリートのみに関連付ける必要があり、キューフリート関連付けの設計見直しが必要な場合がある

🎯 ユースケース

🎬 ユースケース 1: Blender によるコンテナベースのレンダリングファーム
シナリオ

スタジオが Blender と独自プラグインを含むコンテナイメージを社内で管理しており、これをそのままクラウドレンダリングに利用したい。

実装例
  1. Blender と必要なプラグインを含む Docker イメージをビルドし Amazon ECR に push
  2. Linux SMF で Container support を有効化
  3. キューの Docker 環境にイメージ URI を設定
  4. アーティストは既存のジョブバンドルをそのまま投入
効果

ワーカーごとのソフトウェアセットアップが不要になり、社内で検証済みの環境と同一のコンテナでレンダリングを大規模実行できる。

🤖 ユースケース 2: NVIDIA Isaac Sim によるフィジカル AI シミュレーション
シナリオ

ロボティクス開発チームが NVIDIA Isaac Sim を使った大規模なシミュレーションバッチを実行したい。GPU が必要だが、特権コンテナは避けたい。

実装例
  1. Isaac Sim のコンテナイメージを Amazon ECR に登録
  2. GPU インスタンスを含む Linux SMF で Docker を有効化 (CDI が自動構成)
  3. シミュレーションジョブを Open Job Description のジョブバンドルとして投入
効果

特権アクセスなしで GPU をコンテナから利用でき、セキュリティを保ちながらシミュレーションをスケールできる。

🔄 ユースケース 3: ローカル検証からクラウドへのシームレスな移行
シナリオ

パイプライン開発者が Open Job Description CLI を使ってローカルでジョブを開発・検証し、本番は Deadline Cloud で実行したい。

実装例
Bash ローカル検証からクラウド投入まで 
# ローカルでジョブバンドルを検証
openjd run ./my-job-bundle

# 検証済みバンドルを変更なしで Deadline Cloud に投入
deadline bundle submit ./my-job-bundle
効果

ジョブテンプレートにコンテナ固有の記述が不要なため、ローカルとクラウドで同一のバンドルを使い回せ、開発サイクルが短縮される。

🔗 関連サービス・機能

🪣Amazon ECR: コンテナイメージの保管元。デフォルトのキュー環境はプライベートリポジトリからイメージを pull する
📦Amazon ECS: コンテナイメージのエコシステム。ECS 向けにビルドした Docker イメージをそのまま活用できる
📝Open Job Description (OpenJD): ジョブテンプレートの仕様。ローカル検証済みのジョブバンドルを変更なしで投入できる
💾Deadline Cloud 永続ストレージ: Docker レイヤーやアプリケーションキャッシュをワーカーのライフサイクルをまたいで保持し、起動を高速化する

📝 まとめ

AWS Deadline Cloud の Linux サービスマネージドフリートが Docker コンテナに対応し、Amazon ECR のイメージを指定するだけで独自ソフトウェアを全ワーカーへ自動デプロイできるようになりました。ジョブテンプレートはコンテナ非依存のまま維持されるため、既存のコンテナ資産とローカル検証済みのジョブバンドルを活かして、レンダリングからフィジカル AI シミュレーションまで迅速にマネージドファームへ移行できます。

👉 コンテナ化されたワークフローを持つチームは、フリートの Docker 有効化とキュー環境の設定から試すことを推奨します。
