⚡ Aurora Serverless が最大 384 ACU をサポート

Amazon Aurora PostgreSQL 互換 📅 リリース日: 2026 年 10 月 27 日

📌 概要

Amazon Aurora Serverless が、Aurora PostgreSQL 互換エディションにおいて 最大 384 ACU までのスケーリングをサポートしました。 従来の上限 256 ACU から 50% 増 となり、 データベースインスタンスあたり 最大 768 GiB のメモリ を利用できます。 アイドル時に 0 ACU まで縮退する自動一時停止 (auto-pause) はそのまま利用でき、 バースト的なアクセスを持つエージェント型 AI アプリケーションに好適です。

❌ アップデート前の課題
  • 最大容量は 256 ACU (約 512 GiB メモリ) に制限され、ピーク時にはプロビジョンドへの移行や混合構成の検討が必要
  • メモリ集約型ワークロード (大規模結合、ベクトル検索、大量同時接続) ではサーバーレスの利便性と大容量の両立が困難
  • バースト対策で大型プロビジョンドインスタンスを常時稼働させると、アイドル期間のコストが無駄に
✅ アップデート後の改善
  • 最大 384 ACU (768 GiB メモリ) まで従来比 50% 増の処理能力へシームレスに自動スケール
  • 0 ACU への自動一時停止と組み合わせ、「アイドル時はゼロ、ピーク時は 768 GiB」の幅広いダイナミックレンジを単一構成で実現
  • Platform Version 4 上の既存クラスターはダウンタイムなしの設定変更のみで新上限を利用可能

🔧 主要機能

📈 1. 最大容量の 384 ACU への拡張

Aurora PostgreSQL 互換エディションで最大 384 ACU までスケール可能 (従来は 256 ACU)。 1 ACU は約 2 GiB のメモリ、対応する CPU、ネットワーク帯域で構成され、最大 768 GiB のメモリを利用可能。 スケーリングは最小 0.5 ACU 単位で実行され、現在の容量が大きいほど増分も大きくなり高速にスケール。

💤 2. 0 ACU へのスケールダウンの維持

最大容量が拡張されても、アイドル時に 0 ACU まで自動一時停止 (auto-pause) する機能は引き続き利用可能。 使用したキャパシティに対してのみ課金されるモデルはそのまま。 バースト的なアクティビティと長いアイドル期間を持つエージェント型 AI アプリケーションに好適。

🚀 3. Platform Version 4 による提供

Platform Version は、性能・スケーリング能力・機能の改善を表すクラスターレベルの属性。 Platform Version 4 は Platform Version 3 と比較して最大 30% の性能向上を提供。 新規クラスター、リストア、クローンは、リージョンで利用可能な最新の Platform Version で自動的に起動。

🔄 4. 既存クラスターのダウンタイムなしの移行

Platform Version 4 上の既存クラスターは、最大容量設定 (必要に応じてエンジンバージョンも) を変更するだけで ダウンタイムなしで 384 ACU を利用可能。 古い Platform Version のクラスターは、保留中のメンテナンスアクションの適用、クラスターの停止と再起動、 またはブルー/グリーンデプロイで Platform Version 4 へアップグレード可能。

⚙️ 設定方法

前提条件

✓Aurora PostgreSQL 14.23 / 15.18 / 16.14 / 17.10 / 18.4 以降のエンジンバージョンを使用していること
✓クラスターが Aurora Serverless Platform Version 4 上で稼働していること (古い Platform Version の場合はアップグレードが必要)
✓Platform Version 4 が利用可能なリージョンであること
1
現在の Platform Version を確認する
BashPlatform Version の確認
aws rds describe-db-clusters \
  --db-cluster-identifier my-aurora-cluster \
  --query "DBClusters[0].ServerlessV2PlatformVersion"

ServerlessV2PlatformVersion が 4 でない場合は、メンテナンスアクションの適用、停止と再起動、またはブルー/グリーンデプロイでアップグレードします。

2
保留中のメンテナンスアクションを確認・適用する (古い Platform Version の場合)
Bashメンテナンスアクションの確認と適用
# 保留中のメンテナンスアクションを確認
aws rds describe-pending-maintenance-actions \
  --filters "Name=db-cluster-id,Values=arn:aws:rds:ap-northeast-1:123456789012:cluster:my-aurora-cluster"

# メンテナンスアクションを即時適用
aws rds apply-pending-maintenance-action \
  --resource-identifier arn:aws:rds:ap-northeast-1:123456789012:cluster:my-aurora-cluster \
  --apply-action system-update \
  --opt-in-type immediate
3
最大容量を 384 ACU に変更する
Bashスケーリング設定の変更 (ダウンタイムなし)
aws rds modify-db-cluster \
  --db-cluster-identifier my-aurora-cluster \
  --serverless-v2-scaling-configuration MinCapacity=0,MaxCapacity=384 \
  --apply-immediately

最小容量 0 ACU (自動一時停止有効)、最大容量 384 ACU を設定。Platform Version 4 上の既存クラスターではダウンタイムなしで適用されます。

4
スケーリング動作を監視する
BashCloudWatch メトリクスの取得
aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name ServerlessDatabaseCapacity \
  --dimensions Name=DBClusterIdentifier,Value=my-aurora-cluster \
  --start-time 2026-10-27T00:00:00Z \
  --end-time 2026-10-28T00:00:00Z \
  --period 300 \
  --statistics Average Maximum

ServerlessDatabaseCapacity と ACUUtilization で容量消費の推移を確認し、容量範囲の適正化に活用します。

⚠️ デメリット・制約事項

制限事項

✗384 ACU は Aurora PostgreSQL 互換エディションのみの対応で、Aurora MySQL 互換エディションの上限は引き続き 256 ACU
✗Aurora PostgreSQL 14.23 / 15.18 / 16.14 / 17.10 / 18.4 以降かつ Platform Version 4 が必要で、エンジンバージョンと Platform Version のいずれか低い方の能力でスケーリング範囲が決まる
✗Platform Version 4 は利用可能なリージョンが限定されている

考慮すべき点

⚠古い Platform Version のクラスターは、メンテナンスアクションの適用、停止と再起動、またはブルー/グリーンデプロイによるアップグレードが必要
⚠最大容量を引き上げると max_connections など最大容量に基づくパラメータのデフォルト値が変わる可能性があるため、パラメータグループの動作を事前確認
⚠最大容量までスケールした場合の ACU 時間あたりの課金額も増えるため、ACUUtilization の監視と適切な最大容量の設定が重要

🎯 ユースケース

🤖 1. エージェント型 AI アプリケーションのバックエンド

AI エージェントが自律的にタスクを実行するアプリケーションで、エージェントの活動に応じてデータベースアクセスが突発的に集中し、それ以外の時間はほぼアイドル状態となるシナリオ。

Bash新規クラスター作成例
aws rds create-db-cluster \
  --db-cluster-identifier agentic-ai-db \
  --engine aurora-postgresql \
  --engine-version 17.10 \
  --serverless-v2-scaling-configuration MinCapacity=0,MaxCapacity=384
✅ 効果: アイドル時は 0 ACU まで一時停止してコストを抑えつつ、バースト的な処理時には最大 768 GiB メモリまで自動スケールし、性能とコストを両立。
📊 2. メモリ集約型分析クエリを伴う SaaS アプリケーション

マルチテナント SaaS で通常時のトランザクション負荷は小さいが、月次レポート生成時に大規模な結合や集計クエリが実行され、従来の 256 ACU では処理が遅延していたシナリオ。

Bash既存クラスターの設定変更例
aws rds modify-db-cluster \
  --db-cluster-identifier saas-production-db \
  --serverless-v2-scaling-configuration MinCapacity=8,MaxCapacity=384 \
  --apply-immediately
✅ 効果: レポート生成時のみ 384 ACU まで自動スケールして処理時間を短縮し、通常時は小さい容量で稼働してインフラコストを最適化。
🔄 3. プロビジョンドからサーバーレスへの統合

ピーク容量の要件から一部をプロビジョンドの大型インスタンスで運用していた混合構成クラスターを、運用簡素化のためフルサーバーレス構成へ統合するシナリオ。

Bashサーバーレスリーダーを追加して段階的に移行
aws rds create-db-instance \
  --db-instance-identifier serverless-reader-1 \
  --db-cluster-identifier mixed-config-cluster \
  --db-instance-class db.serverless \
  --engine aurora-postgresql
✅ 効果: 最大容量の拡張により、これまでプロビジョンドインスタンスが必要だったワークロードもサーバーレスでカバーでき、インスタンスクラスの管理やサイジング作業が不要に。

💰 料金

Aurora Serverless の料金は、消費した容量を ACU 時間単位で計測する従量課金です。 最小容量 0 ACU を設定した場合、アイドル時の自動一時停止中はコンピューティング料金が発生しません (ストレージおよび I/O 料金は別途発生)。 最大容量を 384 ACU に引き上げても、実際に消費した容量分のみが課金対象となります。

詳細: Amazon Aurora 料金ページ

🔗 関連サービス・機能

💤 Aurora Serverless 自動一時停止 (Scaling to Zero)

最小容量 0 ACU の設定により、アイドル時にコンピューティングを完全に停止してコストを削減する機能。本アップデート後も引き続き利用可能。

📊 Amazon CloudWatch

ServerlessDatabaseCapacity と ACUUtilization メトリクスにより、容量消費の推移を監視し、容量範囲の適正化に活用。

🔵🟢 Amazon RDS ブルー/グリーンデプロイ

古い Platform Version から Platform Version 4 への移行手段の 1 つとして利用可能。

🌐 Aurora Global Database

セカンダリクラスターにサーバーレス容量を使用でき、災害対策構成でもスケールダウンによるコスト削減が可能。

📝 まとめ

Aurora Serverless の最大容量が Aurora PostgreSQL 互換エディションで 384 ACU (最大 768 GiB メモリ) に拡張され、 0 ACU への自動一時停止と組み合わせた幅広いダイナミックレンジを単一のサーバーレス構成で実現できるようになりました。 バースト的なアクセスパターンを持つエージェント型 AI アプリケーションや、ピーク時のみ大容量が必要なワークロードでは、 プロビジョンド構成からの移行を検討する価値があります。
