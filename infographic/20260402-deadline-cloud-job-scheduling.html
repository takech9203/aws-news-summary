🔄 概要: Before / After

AWS Deadline Cloud において、キューごとにジョブスケジューリングモードを設定できる機能が追加されました。映像制作やアニメーション、VFX などのレンダリングワークロードにおいて、チームの作業効率を大幅に向上させます。

❌ アップデート前の課題
  • すべてのワーカーが最も優先度の高い最初に送信されたジョブに集中し、後続ジョブの処理開始が遅延
  • アーティストが新しいジョブを送信しても、先行ジョブ完了までフィードバックを得られない
  • ジョブの特性に基づいたワーカー分配の最適化ができない
  • 複数アーティストが同じキューを共有する環境で、公平なリソース配分が困難
✅ アップデート後の改善
  • 3 つのスケジューリングモードからワークロードに適した方式を選択可能
  • Priority Balanced モードで同一優先度のジョブ間でワーカーを均等に分配
  • Weighted Balanced モードで優先度、エラー数、送信時刻、タスク数に基づく重み付けスケジューリング
  • アーティストがジョブ送信直後にフィードバックを得られ、イテレーション速度が向上

🚀 主要機能

1️⃣ Priority FIFO モード

従来のデフォルトスケジューリング方式。利用可能なすべてのワーカーを、最も優先度が高く最初に送信されたジョブに割り当てます。そのジョブが完了すると次のジョブにワーカーが移動します。個々のジョブの最速完了を重視するワークロードに適しています。

2️⃣ Priority Balanced モード

最も高い優先度レベルのすべてのジョブにワーカーを均等に分配します。同一優先度のジョブ間で公平なリソース配分を実現。renderingTaskBuffer パラメータでレンダリングタスクのバッファサイズを設定可能。複数のアーティストが同時にフィードバックを必要とする環境に適しています。

3️⃣ Weighted Balanced モード

複数の設定可能なパラメータに基づいてジョブに重みを付けてワーカーを分配します。priorityWeight、errorWeight、submissionTimeWeight、renderingTaskWeight の 4 つの重みパラメータを調整可能。maxPriorityOverride で特定ジョブを常に最優先、minPriorityOverride で常に最後にスケジュールできます。

schedulingConfiguration パラメータ

JSON schedulingConfiguration - union 型 
{
  "schedulingConfiguration": {
    "priorityFifo": {},
    "priorityBalanced": {
      "renderingTaskBuffer": 123
    },
    "weightedBalanced": {
      "priorityWeight": 1.0,
      "errorWeight": 0.5,
      "submissionTimeWeight": 0.3,
      "renderingTaskWeight": 0.2,
      "renderingTaskBuffer": 100,
      "maxPriorityOverride": {
        "alwaysScheduleFirst": {}
      },
      "minPriorityOverride": {
        "alwaysScheduleLast": {}
      }
    }
  }
}

schedulingConfiguration は union 型で、3 つのモードのうちいずれか 1 つを指定します。weightedBalanced では各重みパラメータを double 型で指定し、ジョブの優先度スコアの計算に使用されます。

IAM 権限

スケジューリングモードの設定には、既存の deadline:CreateQueue および deadline:UpdateQueue の IAM アクション権限が必要です。新しい IAM アクションの追加はありません。

⚙️ 設定方法

前提条件

  • AWS Deadline Cloud のファーム (Farm) が作成済みであること
  • deadline:CreateQueue または deadline:UpdateQueue の IAM 権限を持つユーザーまたはロール
  • AWS CLI v2 の最新バージョン

Step 1: Priority Balanced モードでキューを作成

Bash キュー作成 
aws deadline create-queue \
  --farm-id farm-xxxxxxxxxxxxxxxxx \
  --display-name "VFX-Rendering-Queue" \
  --scheduling-configuration '{
    "priorityBalanced": {
      "renderingTaskBuffer": 50
    }
  }'

Step 2: 既存キューのスケジューリングモードを変更

Bash Weighted Balanced モードに変更 
aws deadline update-queue \
  --farm-id farm-xxxxxxxxxxxxxxxxx \
  --queue-id queue-xxxxxxxxxxxxxxxxx \
  --scheduling-configuration '{
    "weightedBalanced": {
      "priorityWeight": 1.0,
      "errorWeight": 0.5,
      "submissionTimeWeight": 0.3,
      "renderingTaskWeight": 0.2,
      "renderingTaskBuffer": 100
    }
  }'

Step 3: キューのスケジューリング設定を確認

Bash 設定確認 
aws deadline get-queue \
  --farm-id farm-xxxxxxxxxxxxxxxxx \
  --queue-id queue-xxxxxxxxxxxxxxxxx \
  --query "schedulingConfiguration"

💡 ユースケース

🎨 ユースケース 1: VFX スタジオでの複数アーティスト環境

シナリオ: VFX スタジオで複数のアーティストが同じキューを使用してレンダリングジョブを送信している。各アーティストが素早くプレビュー結果を確認したい。

Bash Priority Balanced モード 
aws deadline update-queue \
  --farm-id farm-xxxxxxxxxxxxxxxxx \
  --queue-id queue-xxxxxxxxxxxxxxxxx \
  --scheduling-configuration '{
    "priorityBalanced": {
      "renderingTaskBuffer": 30
    }
  }'
✅ 同一優先度のジョブにワーカーが均等に分配されるため、全アーティストが並行してレンダリング結果のフィードバックを受けられる。先行ジョブの完了を待つ必要がなくなり、チーム全体の作業効率が向上。

🏭 ユースケース 2: 大規模プロダクション環境での最適化

シナリオ: アニメーション制作会社で、優先度の異なる複数のプロジェクトが混在。締切の近い本番レンダリング、テストレンダリング、プレビュー生成などが同時に実行される。

Bash Weighted Balanced モード 
aws deadline update-queue \
  --farm-id farm-xxxxxxxxxxxxxxxxx \
  --queue-id queue-xxxxxxxxxxxxxxxxx \
  --scheduling-configuration '{
    "weightedBalanced": {
      "priorityWeight": 2.0,
      "errorWeight": 1.0,
      "submissionTimeWeight": 0.5,
      "renderingTaskWeight": 0.3,
      "renderingTaskBuffer": 100,
      "maxPriorityOverride": {
        "alwaysScheduleFirst": {}
      }
    }
  }'
✅ 優先度の高いジョブにより多くのワーカーが割り当てられつつ、低優先度のジョブにも一定のワーカーが分配される。errorWeight によりエラーの多いジョブの優先度が調整され、maxPriorityOverride で緊急ジョブを最優先で処理可能。

⚡ ユースケース 3: 単一プロジェクトの最速完了

シナリオ: 納期が迫っているプロジェクトで、1 つのジョブをできるだけ早く完了させる必要がある。

Bash Priority FIFO モード 
aws deadline update-queue \
  --farm-id farm-xxxxxxxxxxxxxxxxx \
  --queue-id queue-xxxxxxxxxxxxxxxxx \
  --scheduling-configuration '{
    "priorityFifo": {}
  }'
✅ 従来のデフォルト動作と同じく、最も優先度の高い最初に送信されたジョブにすべてのワーカーが集中するため、個々のジョブの完了時間が最短に。

✅ メリット

💼 ビジネス面

  • ジョブ送信後すぐにレンダリング結果のフィードバックを得られ、イテレーションサイクルが短縮
  • 複数のアーティストやプロジェクトが同じキューを共有する場合に、公平なワーカー分配が可能
  • ワークロードの特性に応じてスケジューリング方式を切り替え、納期やリソース効率を最適化

🔧 技術面

  • Weighted Balanced モードの 4 つの重みパラメータでスケジューリングロジックを詳細にチューニング
  • maxPriorityOverride と minPriorityOverride で特定ジョブのスケジューリング順序を強制制御
  • 既存の CreateQueue、GetQueue、UpdateQueue API にパラメータ追加で後方互換性を維持
  • キューごとに異なるスケジューリングモードを設定可能

⚠️ デメリット・制約事項

制限事項

  • schedulingConfiguration は union 型のため、3 つのモードのうち同時に 1 つしか設定できない
  • Weighted Balanced モードの重みパラメータの最適値はワークロードに依存するため、チューニングが必要
  • スケジューリングモードの変更は実行中のジョブへの影響について、公式ドキュメントでの確認が必要

考慮すべき点

  • Priority FIFO から他のモードに変更すると、個々のジョブの完了時間は長くなる可能性がある
  • Weighted Balanced モードの重みパラメータは、実際のワークロードでテストしながら段階的に調整することを推奨
  • renderingTaskBuffer の値が小さすぎるとスケジューリング効率が低下し、大きすぎるとメモリ使用量が増加する可能性あり
