🔐 ポスト量子 TLS 鍵交換 PQ-TLS のサポート

量子コンピュータ時代に備えるデータベース接続の暗号化 — ssl_groups パラメータで ML-KEM ハイブリッド鍵交換を利用可能に
📅 リリース日: 2026 年 10 月 29 日
🗄️ 対象: Aurora PostgreSQL 18 以降
💰 追加料金なし

📌 概要

Aurora PostgreSQL 18 以降で、クラスターパラメータ ssl_groups を変更することで、NIST 標準化済みのポスト量子鍵カプセル化アルゴリズム ML-KEM を組み合わせたハイブリッド鍵交換グループ (X25519MLKEM768、SecP256r1MLKEM768) を選択できるようになりました。

将来の量子コンピュータによる解読に備えて現在の暗号化通信を記録しておく 「Harvest Now, Decrypt Later (今収集して後で解読する)」攻撃への対策として重要です。AWS は CloudFront、KMS、S3、Secrets Manager などで ML-KEM を展開済みであり、今回のアップデートでお客様が所有するデータベースリソースにもポスト量子暗号が拡大しました。

❌ Before: アップデート前の課題
  • TLS 鍵交換は古典的な楕円曲線アルゴリズム (X25519、prime256v1 など) のみで、量子コンピュータによる解読リスクに対応できなかった
  • 「Harvest Now, Decrypt Later」攻撃に対して、長期保存が必要な機密データの通信を保護する手段がなかった
  • TLS 鍵交換の名前付きグループをデータベース側で制御する手段がなかった
✅ After: アップデート後の改善
  • ssl_groups の変更で ML-KEM ハイブリッド鍵交換グループを含む許可リストから暗号グループを選択可能に
  • セキュリティ要件に合わせて、サーバーが受け入れる鍵交換グループと優先順位を制御可能に
  • 動的パラメータのため、DB クラスターの再起動なしで適用可能

クライアントと Aurora PostgreSQL の間の TLS 1.3 ハンドシェイクにおいて、ssl_groups パラメータで設定した優先順位に基づきハイブリッド鍵交換グループがネゴシエートされる流れを示しています。

⚡ 主要機能

1️⃣ ポスト量子ハイブリッド鍵交換グループのサポート
✓古典的な楕円曲線暗号 (X25519 または P-256) と NIST FIPS 203 で標準化された ML-KEM-768 を組み合わせたハイブリッド方式
✓X25519MLKEM768 と SecP256r1MLKEM768 の 2 つのハイブリッドグループを許可リストから選択可能
✓ML-KEM に万一問題が見つかった場合でも古典暗号による安全性が維持される
2️⃣ ssl_groups クラスターパラメータによる柔軟な制御
✓TLS 鍵交換に使用する名前付きグループをコロン区切りのリストで指定
✓リストの順序がサーバー側の優先順位となり、クライアントも対応する最初のグループが接続に使用される
✓動的パラメータのため、変更時に DB クラスターの再起動が不要
3️⃣ セキュリティ要件に応じた構成の強制
✓ssl_groups は名前付きグループを使用する鍵交換にのみ適用され、RSA 鍵交換を使用する TLS 1.2 暗号スイートでは無視される
✓指定グループのみを使用させるには rds.force_ssl を有効化し、ssl_min_protocol_version を TLSv1.3 に設定するか、TLS 1.2 向けに ssl_ciphers を ECDHE ベースに制限
⚠ML-KEM グループは TLS 1.3 が必須

🛠️ 設定方法

前提条件

✓Aurora PostgreSQL 18 以降の DB クラスターを使用していること
✓カスタム DB クラスターパラメータグループを作成し、DB クラスターに関連付けていること (デフォルトのパラメータグループは変更不可)
✓ML-KEM グループを使用する場合、クライアント側のライブラリ (OpenSSL など) が TLS 1.3 およびハイブリッドポスト量子鍵交換に対応していること
1
カスタム DB クラスターパラメータグループの作成
BashAWS CLI
aws rds create-db-cluster-parameter-group \
    --db-cluster-parameter-group-name my-aurora-pg18-pqtls \
    --db-parameter-group-family aurora-postgresql18 \
    --description "Aurora PostgreSQL 18 with PQ-TLS key exchange"

既存のカスタムパラメータグループがある場合、このステップは不要です。

2
ssl_groups パラメータの変更
BashAWS CLI
aws rds modify-db-cluster-parameter-group \
    --db-cluster-parameter-group-name my-aurora-pg18-pqtls \
    --parameters "ParameterName=ssl_groups,ParameterValue='X25519MLKEM768:X25519:prime256v1',ApplyMethod=immediate"

ハイブリッドポスト量子グループ X25519MLKEM768 を最優先に設定。動的パラメータのため ApplyMethod=immediate で再起動なしに適用されます。

3
ML-KEM の使用を強制する場合の追加設定
BashAWS CLI
aws rds modify-db-cluster-parameter-group \
    --db-cluster-parameter-group-name my-aurora-pg18-pqtls \
    --parameters \
    "ParameterName=rds.force_ssl,ParameterValue=1,ApplyMethod=immediate" \
    "ParameterName=ssl_min_protocol_version,ParameterValue=TLSv1.3,ApplyMethod=immediate"

SSL/TLS 接続を必須化し、最小プロトコルバージョンを TLS 1.3 に設定。ML-KEM グループは TLS 1.3 が必須のため、指定したポスト量子グループの使用を確実にできます。TLS 1.3 に対応していないクライアントは接続できなくなる点に注意してください。

4
接続の確認
SQLsslinfo 拡張機能で暗号化状態を確認
-- sslinfo 拡張機能で接続の暗号化状態を確認
CREATE EXTENSION IF NOT EXISTS sslinfo;
SELECT ssl_is_used(), ssl_cipher();

データベースに接続後、SSL/TLS が使用されていることとネゴシエートされた暗号スイートを確認します。

⚖️ メリットと制約事項

👍 メリット
  • 長期的なデータ機密性の確保: 「Harvest Now, Decrypt Later」攻撃対策により、10 年以上の機密性が求められる金融・医療・個人情報のデータ通信を保護
  • コンプライアンス対応の先行: CISA、NIST などが推奨するポスト量子暗号移行に早期対応
  • 追加コストなし: パラメータ変更のみで利用でき、追加料金は発生しない
  • ハイブリッド方式による安全性: 古典暗号と ML-KEM のどちらか一方が破られても機密性を維持
  • 再起動不要の動的パラメータ: 本番環境でもダウンタイムなしで段階的に導入可能
  • 柔軟な優先順位制御: PQ 対応クライアントと非対応クライアントが混在する移行期間にも対応
⚠️ 制約事項・考慮点
  • Aurora PostgreSQL 18 以降でのみ利用可能 (Aurora MySQL 互換エディションは対象外)
  • ML-KEM グループの使用には TLS 1.3 が必須
  • ssl_groups は RSA 鍵交換を使用する TLS 1.2 暗号スイートでは無視される
  • クライアント側ライブラリ (OpenSSL、libpq、JDBC ドライバーなど) の PQ 対応が必要で、未対応クライアントとの互換性を考慮したグループリスト設計が必要
  • ssl_min_protocol_version を TLSv1.3 にすると TLS 1.3 非対応クライアントが接続不可になるため、事前のクライアント棚卸しが必要
  • ML-KEM の公開鍵と暗号文は古典暗号より大きく、ハンドシェイク時のデータ量がわずかに増加 (接続確立後のクエリ性能への影響はない)

🏦 ユースケース 1: 金融機関における長期機密データの通信保護

シナリオ: 顧客の取引データを Aurora PostgreSQL で管理し、規制により 10 年以上の機密性保持が求められている。将来の量子コンピュータによる解読リスクに今から備えたい。

BashPQ グループのみを許可し TLS 1.3 を強制
aws rds modify-db-cluster-parameter-group \
    --db-cluster-parameter-group-name finance-aurora-pg18 \
    --parameters \
    "ParameterName=ssl_groups,ParameterValue='X25519MLKEM768:SecP256r1MLKEM768',ApplyMethod=immediate" \
    "ParameterName=rds.force_ssl,ParameterValue=1,ApplyMethod=immediate" \
    "ParameterName=ssl_min_protocol_version,ParameterValue=TLSv1.3,ApplyMethod=immediate"

効果: すべてのデータベース接続が量子耐性のある鍵交換で保護され、「Harvest Now, Decrypt Later」攻撃のリスクを低減できる。

🔄 ユースケース 2: 段階的なポスト量子暗号への移行

シナリオ: PQ 対応クライアントと非対応クライアントが混在する環境で、接続互換性を維持しながら段階的に移行したい。

Bash古典グループをフォールバックとして残す
aws rds modify-db-cluster-parameter-group \
    --db-cluster-parameter-group-name myapp-aurora-pg18 \
    --parameters "ParameterName=ssl_groups,ParameterValue='X25519MLKEM768:X25519:prime256v1',ApplyMethod=immediate"

効果: PQ 対応クライアントは自動的に X25519MLKEM768 で接続し、未対応クライアントは従来の X25519 などにフォールバック。ダウンタイムなしで移行を進め、移行完了後に古典グループを削除すれば完全移行できる。

🏛️ ユースケース 3: 公共機関におけるポスト量子暗号移行計画の実行

シナリオ: 政府機関のシステムで、CISA や NIST のガイダンスに沿った暗号インベントリの整備と移行計画を進めており、データベース層の対応を開始したい。

SQL移行前のインベントリ作成
-- 接続ごとの暗号利用状況を確認し、移行前のインベントリを作成
CREATE EXTENSION IF NOT EXISTS sslinfo;
SELECT ssl_is_used(), ssl_version(), ssl_cipher();

効果: 現状の TLS 利用状況を把握した上で計画的に切り替えを実施でき、暗号移行計画のマイルストーンとしてデータベース層の量子耐性化を達成できる。
