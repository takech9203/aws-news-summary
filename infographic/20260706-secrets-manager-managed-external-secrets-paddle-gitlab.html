マネージド外部シークレットサポート

📅 リリース日
2026 年 7 月 6 日

📌 概要

AWS Secrets Manager のマネージド外部シークレット機能に、Paddle API キーおよび GitLab アクセストークンのサポートが追加されました。サードパーティサービスの認証情報を Secrets Manager から直接自動ローテーションでき、カスタム Lambda 関数の作成・維持が不要になります。

マネージド外部シークレットは、サードパーティアプリケーションの認証情報を各パートナーが定義した事前定義フォーマットで保存し、自動的にローテーションする機能です。Paddle はネイティブのローテーション API と設定可能な猶予期間で中断なくキーを移行し、GitLab は Personal / Group / Project の 3 種類のトークンをアトミックなローテーションメカニズムでローテーションします。

今回のアップデートで、既存パートナーに Paddle と GitLab が加わりました。

🔴 アップデート前の課題
  • Paddle API キーや GitLab アクセストークンのローテーションにカスタム Lambda 関数の開発・維持が必要だった
  • サードパーティごとに異なるローテーションロジックを実装する必要があった
  • トークン更新時のダウンタイムを防ぐための猶予期間管理を独自に実装する必要があった
🟢 アップデート後の改善
  • Lambda 関数不要でマネージドローテーションが自動的に実行される
  • Paddle では設定可能な猶予期間により中断なくキーを移行できる
  • GitLab ではアトミックなローテーションにより新旧トークンの一貫性が保証される

⚙️ 主要機能

💳 Paddle API キーのマネージドローテーション

  • シークレットタイプ PaddleApiKey として単一シークレットアーキテクチャで管理 (管理用シークレット不要)
  • Paddle のネイティブローテーション API を使用し、API キーが自身をローテーション
  • 設定可能な猶予期間 (gracePeriodSeconds: 0-86400 秒、デフォルト 300 秒) で旧キーを段階的に無効化
  • 新キーは AWSPENDING として保存され、/check/whoami で検証後に AWSCURRENT へ昇格

🦊 GitLab アクセストークンのマネージドローテーション

  • シークレットタイプ GitLabAccessToken として 3 種類のトークンをサポート
  • Personal Access Token: projectId と groupId の両方が未指定の場合
  • Project Access Token: projectId を指定した場合 / Group Access Token: groupId を指定した場合
  • Token Rotate API により新トークンの作成と旧トークンの無効化をアトミックに実行
  • 単一シークレット (自己ローテーション) と 2 シークレット (管理者アシスト) の両アーキテクチャに対応

🚫 Lambda 不要のマネージドローテーション

  • カスタム Lambda 関数の作成・デプロイ・管理が一切不要
  • コンソールでシークレット作成時にローテーションが自動的に有効化
  • AWS CloudTrail による全操作の完全な監査証跡

🔧 技術仕様

サポートされるシークレットタイプ

パートナーシークレットタイプ用途
PaddlePaddleApiKeyPaddle API キーの自動ローテーション
GitLabGitLabAccessTokenPersonal / Group / Project アクセストークンの自動ローテーション

Paddle: シークレット値とローテーションメタデータ

JSONシークレット値
{
  "api_key": "{{Paddle API キー値}}"
}

api_key は pdl_live_、pdl_test_、pdl_sdbx_ で始まり、apikey_ とキー本体が続きます。このフィールドがローテーション対象です。

パラメータ説明デフォルト範囲
gracePeriodSecondsローテーション後に旧 API キーが有効なままとなる秒数。0 で即時失効3000-86400

💡 猶予期間のカウントダウンは、新しいキーが初めて正常に使用された時点で開始されます。

GitLab: シークレット値とローテーションメタデータ

JSONシークレット値
{
  "token": "{{GitLab アクセストークン値}}",
  "tokenId": "{{数値のトークン ID}}",
  "gitlabUrl": "{{GitLab インスタンス URL}}",
  "projectId": "{{プロジェクト ID (オプション)}}",
  "groupId": "{{グループ ID (オプション)}}"
}
フィールド / パラメータ説明
tokenGitLab アクセストークン値 (glpat- で始まる)。ローテーション対象
tokenId数値のトークン ID。ローテーションごとに新トークンの ID に更新
gitlabUrlGitLab インスタンスの URL。HTTPS 必須
projectId (任意)数値のプロジェクト ID。Project アクセストークンの場合のみ指定
groupId (任意)数値のグループ ID。Group アクセストークンの場合のみ指定
adminSecretArn (任意)api スコープの管理用 GitLabAccessToken シークレット ARN。省略時は自己ローテーション
daysToExpiry (任意)新トークンの有効期限までの日数 (1-365)。省略時はインスタンスのデフォルトを継承

🔑 自己ローテーションには api または self_rotate スコープが必要。管理者アシストでは Project トークンに Maintainer ロール、Group トークンに Owner ロールを持つ管理用トークンが必要です。

API 変更履歴

awsapichanges.com で確認された範囲では専用の API 変更は検出されませんでした。既存の CreateSecret API および RotateSecret API のシークレットタイプパラメータに、新しい値 (PaddleApiKey、GitLabAccessToken) が追加される形で実装されています。

IAM 権限設定 (Paddle ローテーションポリシー例)

JSONローテーション用 IAM ポリシー
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowRotationAccess",
      "Action": [
        "secretsmanager:DescribeSecret",
        "secretsmanager:GetSecretValue",
        "secretsmanager:PutSecretValue",
        "secretsmanager:UpdateSecretVersionStage"
      ],
      "Resource": "*",
      "Effect": "Allow",
      "Condition": {
        "StringEquals": {
          "secretsmanager:resource/Type": "PaddleApiKey"
        }
      }
    }
  ]
}
JSON信頼ポリシー
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "SecretsManagerPrincipalAccess",
      "Effect": "Allow",
      "Principal": { "Service": "secretsmanager.amazonaws.com" },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": { "aws:SourceAccount": "111122223333" },
        "ArnLike": {

      }

}

GitLab の管理者アシストローテーションを使用する場合、管理用シークレット (同じく GitLabAccessToken タイプ) の ARN にスコープしたステートメントをロールポリシーに明示的に追加する必要があります。

🛠️ 設定方法

前提条件

✓AWS Secrets Manager へのアクセス権限を持つ IAM ロールまたはユーザー
✓Paddle: Paddle ダッシュボードで「rotatable」オプションを有効化して作成した API キー
✓GitLab: 自己ローテーションには api / self_rotate スコープ、管理者アシストには対象トークンをローテーションできる管理用トークン
1

Paddle API キーシークレットの作成とローテーション設定

BashAWS CLI
# シークレット作成
aws secretsmanager create-secret \
  --name "paddle/api-key" \
  --secret-string '{"api_key": "pdl_live_apikey_your-key-content"}' \
  --secret-type PaddleApiKey

# ローテーション設定 (30 日ごと、猶予期間 300 秒)
aws secretsmanager rotate-secret \
  --secret-id "paddle/api-key" \
  --rotation-rules '{"AutomaticallyAfterDays": 30}' \
  --rotation-metadata '{"gracePeriodSeconds": "300"}' \
  --role-arn "arn:aws:iam::111122223333:role/SecretsManagerRotationRole"

管理用シークレットは不要で、API キーが自身をローテーションします。

2

GitLab Project アクセストークンシークレットの作成とローテーション設定

BashAWS CLI
# シークレット作成 (projectId を指定 → Project アクセストークン)
aws secretsmanager create-secret \
  --name "gitlab/project-token" \
  --secret-string '{
    "token": "glpat-your-token-value",
    "tokenId": "12345",
    "gitlabUrl": "https://gitlab.com",
    "projectId": "67890"
  }' \
  --secret-type GitLabAccessToken

# ローテーション設定 (自己ローテーション、有効期限 30 日)
aws secretsmanager rotate-secret \
  --secret-id "gitlab/project-token" \
  --rotation-rules '{"AutomaticallyAfterDays": 25}' \
  --rotation-metadata '{"daysToExpiry": "30"}' \
  --role-arn "arn:aws:iam::111122223333:role/SecretsManagerRotationRole"

projectId を指定することで Project アクセストークンとして認識されます。

3

GitLab 管理者アシストローテーションの設定 (オプション)

BashAWS CLI
# 管理用トークン (api スコープ) のシークレットを作成
aws secretsmanager create-secret \
  --name "gitlab/admin-token" \
  --secret-string '{
    "token": "glpat-admin-token-value",
    "tokenId": "10000",
    "gitlabUrl": "https://gitlab.com"
  }' \
  --secret-type GitLabAccessToken

# 対象トークンのローテーションに管理用シークレットを指定
aws secretsmanager rotate-secret \
  --secret-id "gitlab/group-token" \
  --rotation-rules '{"AutomaticallyAfterDays": 25}' \
  --rotation-metadata '{
    "adminSecretArn": "arn:aws:secretsmanager:us-east-1:111122223333:secret:gitlab/admin-token-AbCdEf",
    "daysToExpiry": "30"
  }' \
  --role-arn "arn:aws:iam::111122223333:role/SecretsManagerRotationRole"

対象トークン自体にローテーション権限がない場合、api スコープの管理用トークンを adminSecretArn で指定できます。ロールポリシーに管理用シークレット ARN へのアクセスを明示的に付与する必要があります。

⚠️ デメリット・制約事項

制限事項
✗Paddle API キーは「rotatable」オプション有効化で作成したものに限定 (不可のキーはエラーで拒否)
✗GitLab の gitlabUrl は HTTPS を使用する必要がある
✗管理者アシストには Project トークンに Maintainer、Group トークンに Owner ロールの管理用トークンが必要
考慮すべき点
!Paddle の猶予期間は新キーが初めて使用された時点で開始。使用されないと旧キーが長く有効なまま
!GitLab の daysToExpiry はローテーション間隔より長い値に設定する必要がある
!キャッシュライブラリ利用時は次回リフレッシュ時に新トークンを自動取得

🎯 ユースケース

1. SaaS 決済プラットフォームの API キー管理

Paddle を決済プロバイダーとして利用する SaaS 企業。本番環境の API キーをアプリから利用しており、セキュリティポリシーで定期的なキーローテーションが求められている。

30 日ごとのローテーション、猶予期間を 600 秒に設定 (gracePeriodSeconds: "600")。

効果: 600 秒の猶予期間により、稼働中の決済処理が新旧キーの切り替えで中断されることなく、セキュリティ要件を満たしたローテーションを実現。

2. CI/CD パイプラインの GitLab プロジェクトトークン管理

GitLab を利用する開発チームが、CI/CD パイプラインや外部連携で Project アクセストークンを使用。有効期限管理と定期ローテーションを自動化したい。

60 日ごとにローテーション、新トークンの有効期限を 90 日に設定 (daysToExpiry: "90")。

効果: トークンの有効期限切れによるパイプライン障害を防ぎ、アトミックローテーションで新旧トークンの一貫性を保証。

3. 中央管理トークンによる複数 GitLab グループトークンのローテーション

多数の GitLab グループを運用する組織が、各グループの Group アクセストークンを中央の管理用トークンで一括ローテーションしたい。個々のトークンに自己ローテーション権限を付与したくない。

Owner ロールを持つ中央の管理用トークンを adminSecretArn で参照してローテーション。

効果: 各グループトークンに広範な権限を付与せず、中央の管理用トークンでローテーションを一元管理。最小権限の原則を維持しつつ運用を効率化。

📝 まとめ

マネージド外部シークレットに Paddle と GitLab が追加されたことで、決済プラットフォームや DevOps ツールチェーンの認証情報のライフサイクル管理がさらに簡素化されました。Paddle の設定可能な猶予期間と GitLab のアトミックローテーションにより、中断なくセキュアなローテーションを実現できます。Paddle や GitLab を利用している組織は、既存の認証情報管理をマネージド外部シークレットに移行することが推奨されます。
