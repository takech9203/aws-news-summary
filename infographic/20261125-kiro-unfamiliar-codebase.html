👻 未知のコードベースでコーディングエージェントを活用する手法

トレース → 特性テスト → 変更境界 → 証拠と影響範囲に応じた自律性設定

📝 概要

Kiro チーム (Customer Success の Suruchi Saxena 氏、Burhan Khalid 氏) が、自分が書いていない未知のコードベースでコーディングエージェントを安全に活用する体系的な手法を解説。3 年前から存在し 200 ファイル以上のリポジトリで最初のチケット (請求書の支払い失敗時にメールを送信する機能の追加) に取り組むシナリオを題材に、エージェントにコードを書かせる前に「検証可能な証拠」を作らせるワークフローを提示しています。

中核となる主張: エージェントは人間より高速に検索できるものの、「どの詳細が重要か」は速度だけでは分からない。`legacy` とマークされた関数が本番トラフィックの大半を処理していたり、奇妙に見えるテストアサーションが顧客の依存する動作を保護していたりしますが、通常それらは文書化されていません。

本記事は新機能のリリースではなく、Kiro の既存機能 (スキル、ステアリング、フック、メモリ、ワークフロー、クラウドセッション) を組み合わせた実践手法 (technique) の解説で、IDE、CLI、Web のすべての Kiro 利用形態に適用できます。

❌ Before: 従来の課題
  • 暗黙の要件や長年の設計判断が人の頭の中にしか存在せず、エージェントは正しく見えるコードでも暗黙のルールを壊す可能性
  • リポジトリ全体の説明を求めても README の言い換えが返るだけで、チケットの背後にある問いには答えられない
  • 作業時間の約 58% がプログラム理解に費やされる (2018 年調査)。METR 2025 年研究では既知リポジトリの熟練開発者が AI ツールで 19% 遅くなったと報告
✅ After: 本手法による改善
  • トレースと特性テストを先行させ、エージェントの「信念」をコードに対して検証。レビュー可能な証拠に基づき自律性を段階的に委譲
  • 変更境界 (Goal / Change / Preserve / Validate) の事前文書化で、テストがグリーンのままのスコープ外変更を抑制
  • 「証拠」と「影響範囲」の 2 軸でタスクごとの監督レベルを決める実践的な判断基準を獲得

トレースと特性テストで変更境界を確立してから実装を開始するワークフロー。コードパスマップと矛盾する動作が見つかった場合は、前のステージに戻って証拠を更新します。

⚙️ 主要なステップ

1
🗺️ 重要なコードパスをトレースする
  • チケットの 1 段階上のレベルから開始し、「請求イベントと顧客通知を所有するパッケージはどれか」「公開エントリポイントはどこか」を質問
  • すべての主張にファイル引用 (citation) を必須とし、この段階では変更提案を禁止。人間が実ファイルを開いて検証できる
  • 同じパスを使う既存機能 (例: すでにメールを送信している invoice.paid イベント) にトレースを絞り込む
  • 自分が答えを知っているケースを説明させ、エージェントが本番のコードパスを実際に追ったのか、パターンマッチでストーリーを作ったのかを確認
2
🧪 トレースを特性テストに変換する
  • トレースは「エージェントが信じていること」の記録。特性テストはその信念をコードに対して検証し、一見間違って見える部分も含め現在の動作を捕捉
  • テスト結果とコードパスマップの差分を最初にレビュー。差分はマップの誤りか、文書化されていないルール (バグか、誰かが依存する契約か)
  • 「観察したこと」と「推論したこと」の分離を要求。推論には追加のテストまたはオーナーの回答が必要
  • 安定インターフェースでテストできないパスは隠れた副作用のサインであり、変更リスクが高いため自律性の委譲を減らす
3
📏 変更境界を定義する
  • 特性テストが保護するのは「動作」であって「スコープ」ではない。全テストをグリーンに保ったまま型のリネームや無関係ファイルの変更が起こり得る
  • コードを依頼する前に Goal / Change / Preserve / Validate を Markdown で明文化
  • 「既存テストを実装に合わせて書き換えない」ルールが重要。グリーンに最適化するエージェントは意図をエンコードしたアサーションを平気で書き換える
  • エージェントは人間の約 2 倍の頻度で防御的エラーハンドリングを追加する傾向。制約がないと会話が長くなるほど元の意図から逸脱
  • バグの場合は Kiro の Bugfix Spec が現在の動作・期待される動作・変更しない動作を分割し、境界を自動生成
4
🎚️ 証拠と影響範囲に応じて自律性を設定する
  • 証拠 (evidence): 検証のために構築したもの (トレース、特性テスト、失敗する再現テスト)。薄い場合はテスト追加かオーナー確認を先に
  • 影響範囲 (reach): 誤った変更の波及先。共有イベントスキーマや DB マイグレーションの誤りは、編集していない呼び出し元や保存済みデータまで波及
  • 完全なインベントリを備えた大規模な機械的変更の方が、誰もトレースしていない共有コードの 1 行編集より委譲が安全なことが多い
5
♻️ 有用な証拠を保持し、Kiro の機能で再利用する
  • PR を開く前に、意図した動作を保護する特性テストは残し、探索用テストは破棄。チケット専用ステアリングは出荷後に削除
  • フック (hooks) でファイル保存のたびに影響を受けるテストを自動実行
  • プロンプトと境界テンプレートを Kiro スキルとしてパッケージ化。オープンな Agent Skills 標準準拠で Kiro Crew でも動作
  • リポジトリ規約はステアリング / AGENTS.md に、小さな発見はメモリ機能に記録

💬 プロンプト例と境界テンプレート

🗺️ コードパスのトレース

Prompt 既存イベントがメールになるまでの呼び出しパスを引用付きで示させる 
Trace how an existing `invoice.paid` event becomes an email.

Show the call path from event ingestion to delivery and cite the files you read.
List the tests for routing, preferences, retries, and templates.
Mark external calls and shared types. Skip unrelated implementations.

Then explain what happens when a payment retry succeeds on the second attempt.
I know that behavior and will use it to check your code-path map.

最後に「自分が答えを知っている挙動」の説明を要求することで、エージェントが実際のコードを追ったかを検証します。

📏 変更境界テンプレート

Markdown Goal / Change / Preserve / Validate の 4 セクション 
## Goal

Send an email for `invoice.payment_failed` events.

## Change

- Reuse the existing billing-event consumer and notification pipeline.
- Add the minimum template and routing code for the new event.
- Add tests for preferences, retries, and delivery records.

## Preserve

- Public event and notification interfaces.
- Existing retry behavior for every billing event.
- Current package boundaries and dependency direction.

## Validate

- Run affected tests, type checks, and linting.
- Do not modify an existing test to make the implementation pass.
- Report required changes outside this scope before making them.

目的・変更・維持・検証の 4 セクションで変更境界を明文化し、スコープ外の変更は実施前に報告させます。

🛠️ 設定方法 (実践手順)

📋 前提条件

✓Kiro (IDE、CLI、または Web) を利用できること
✓対象モジュールに実行可能なテストが存在すること
✓エージェントのスコープを対象モジュールに限定できること

ステップ 1: パッケージレベルの地図を作る

Prompt変更提案を禁止し、引用付きで責務を特定
Read the repository-level architecture documents, package manifests, and build files.
Identify the packages involved in billing events and customer notifications.
For each package, state its responsibility and its public entry points.
Cite the files that support each conclusion. Do not propose changes yet.

ステップ 2: 特性テストを作成する

Prompt本番コードを変更せず、未変更コードに対して実行
Add characterization tests for the current `invoice.paid` notification path.

Cover recipient selection, preference checks, template selection, and retries.
Do not change production code.

Run the tests against the unmodified code.
Report anything that differs from your code-path map.

ステップ 3: バグの場合は安定インターフェースで再現する

Prompt修正の前に失敗する再現テストを作成
Write a failing test that sends the same `invoice.payment_failed` event twice
through the public consumer interface and asserts that one email is sent.

Do not fix anything yet. Report which component should have deduplicated
the event and what evidence supports that conclusion.

安定インターフェースで再現を書けば、修正によってテストが壊れることを防げます。

ステップ 4: 大きなタスクは Kiro ワークフローとして実行する

1 セッションに収まらないチケットでは、スキルのステップを Kiro ワークフローとして実行します。ワークフローはトークン消費と引き換えに各ステップで新しいセッションを得られます。バンドルされている investigate レシピは、バックグラウンドで読み取り専用の調査を行い、引用付きレポートを返します。長いテストループはクラウドセッションで実行できます。

👍 メリット

💼 ビジネス面

✓オンボーディングコストの削減: 暗黙知の学習をトレースと特性テストで加速し、属人化された知識を検証可能なテストとして資産化
✓変更リスクの低減: 動作を壊す「正しく見えるコード」の混入を、実装前の証拠作成とレビューで抑止
✓自動化の段階的拡大: 証拠と影響範囲に基づく明確な委譲基準でリスクに応じて自律性を拡大。Kiro Crew チームは時間の約 20% を自動化インフラに投資

⚙️ 技術面

✓検証可能性: ファイル引用の必須化により、エージェントの要約や主張を人間が実ファイルで確認可能
✓観察と推論の分離: 追加のテストやオーナー確認が必要な箇所を特定できる
✓再利用可能なパッケージ化: Agent Skills 標準準拠のスキルとして保存でき、Kiro 本体と Kiro Crew の両方で動作。フック、ステアリング、AGENTS.md、メモリと組み合わせて継続活用

⚠️ デメリット・制約事項

🚧 制限事項

✗オーナーにしか答えられない質問が残る。モジュール間の設計差異の「理由」(Chesterton's fence 問題) は、歴史を知る人間にしか答えられない
✗ユニットテストで観測できない実行順序や副作用はエージェントも見逃す。重要な場合はオーナーの回答をステアリングに記録し、最寄りの安定インターフェースで統合テストを追加
✗セキュリティバグや競合状態を含む変更は、良い証拠があっても監督下に置き続ける必要がある

🤔 考慮すべき点

⚠公開 API、マイグレーション、セキュリティ、並行性に関わる変更の最終判断はシステムのオーナーが行うべき。計画段階でオーナーレビューを依頼
⚠小さなチケットではトレースとテストの先行作成は手間に感じられるが、自動化されたソフトウェアデリバリーへの布石として位置づけられる
⚠ワークフロー実行は各ステップで新しいセッションを使うため、トークン消費が増える

2️⃣ 本番バグの原因特定と修正

シナリオ: 請求プロバイダーのイベント再送により、支払い失敗メールが顧客に 2 通届くようになった。

公開コンシューマーインターフェース経由で同一イベントを 2 回送信し「メールは 1 通」をアサートする失敗テストを先に作成。修正前に、重複排除を担うべきコンポーネントと証拠を報告させる。

効果: トレース段階で重複排除が「推論」としてフラグ済みのため調査箇所が明確。安定インターフェースでの再現テストにより、修正後もテストが有効であり続ける。

3️⃣ 手法のチーム資産化

シナリオ: この手法が自チームのリポジトリで有効だったため、チーム全体で再利用できるようにする。

  • → トレース用プロンプトと境界テンプレートを Kiro スキルとしてパッケージ化
  • → リポジトリ規約をステアリング / AGENTS.md に記録
  • → フックで保存時に影響テストを自動実行
  • → 大きなチケットは workflow + investigate レシピで調査を自動化

効果: Agent Skills 標準準拠のため Kiro Crew でも同じスキルが動作し、個人の手法がチーム・組織の自動化資産になる。
