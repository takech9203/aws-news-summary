RDS マルチ AZ 構成において、プライマリからスタンバイへの同期レプリケーションが ENA Express (SRD) を経由。マルチパスルーティングと輻輳制御で高帯域幅かつ低レイテンシーなレプリケーションを実現。

⚡ 主要機能

🔀 SRD プロトコルによるレプリケーション最適化

AWS Scalable Reliable Datagram (SRD) プロトコルを RDS マルチ AZ レプリケーションに適用。単一フロー帯域幅が最大 25 Gbps に向上し、トラフィックを複数のネットワークパスに動的に分散。

🛡️ 高度な輻輳制御

リアルタイムでネットワーク輻輳を検知し、トラフィックを代替パスにルーティング。レイテンシー変動を低減し、書き込みレイテンシーの予測可能性が向上。

📈 書き込みパフォーマンスの向上

書き込み集中型ワークロードでの書き込みスループットが向上。同期レプリケーションのオーバーヘッドが軽減され、書き込みレイテンシーが低減。

🔧 マネージドサービスとしての透過的な適用

RDS が自動的に ENA Express を活用 (手動設定不要)。既存インスタンスへの適用にはスタートストップまたはコンピュートスケーリングが必要。アプリケーション側の変更は一切不要。

🛠️ 設定方法

前提条件

✓ Amazon RDS マルチ AZ 構成のインスタンスであること
✓ 対象エンジン (MariaDB, MySQL, PostgreSQL, Db2, Oracle) を使用
✓ ENA Express 対応のリージョンで運用

Step 1: マルチ AZ 構成の確認

Bash 現在の構成確認 
aws rds describe-db-instances \
  --db-instance-identifier my-db-instance \
  --query "DBInstances[].{DBInstanceId:DBInstanceIdentifier,MultiAZ:MultiAZ,Engine:Engine,DBInstanceClass:DBInstanceClass}"

Step 2: ENA Express の有効化 (既存インスタンス)

方法 A: スタートストップによる適用

Bash インスタンス停止 / 再開 
# インスタンスを停止
aws rds stop-db-instance \
  --db-instance-identifier my-db-instance

# インスタンスを開始
aws rds start-db-instance \
  --db-instance-identifier my-db-instance

方法 B: コンピュートスケーリングによる適用

Bash インスタンスクラス変更 
aws rds modify-db-instance \
  --db-instance-identifier my-db-instance \
  --db-instance-class db.m6i.2xlarge \
  --apply-immediately

Step 3: パフォーマンス監視

Bash WriteLatency メトリクス確認 
aws cloudwatch get-metric-statistics \
  --namespace AWS/RDS \
  --metric-name WriteLatency \
  --dimensions Name=DBInstanceIdentifier,Value=my-db-instance \
  --start-time 2026-05-26T00:00:00Z \
  --end-time 2026-05-27T00:00:00Z \
  --period 300 \
  --statistics Average
💡 ヒント: ENA Express の適用はインフラレベルで行われるため、RDS API での明示的な確認パラメータはない。CloudWatch メトリクスで書き込みレイテンシーの改善を監視することを推奨。

  • 軽量な書き込みワークロードでは改善効果が限定的な場合あり

💡 ユースケース

🛒 高頻度トランザクション処理システム

EC サイトや金融系アプリケーションで、ピーク時に大量の書き込みトランザクションが発生。マルチ AZ のレプリケーション遅延が書き込みレイテンシーに影響していた。

✅ 効果: SRD のマルチパスルーティングによりレプリケーションレイテンシーの変動が低減され、ピーク時でも安定した書き込みレイテンシーを実現。P99 レイテンシーが改善。

📦 バッチ書き込みを伴うデータウェアハウスのソース DB

ETL 処理やバッチジョブが定期的に大量のデータを書き込む OLTP データベース。バッチ書き込み中にレプリケーションが遅延し、フェイルオーバー時にデータ損失のリスクがあった。

✅ 効果: 最大 25 Gbps のレプリケーション帯域幅により、バッチ書き込み中でもスタンバイとの同期を高速維持。RPO が事実上ゼロに近い状態を維持。

📡 IoT データ収集基盤の書き込み集中型 DB

数万台の IoT デバイスからセンサーデータを受信し、RDS PostgreSQL に書き込む基盤。データ量増加に伴い、同期レプリケーションがボトルネックとなり書き込みスループットが頭打ちに。

✅ 効果: ENA Express による高帯域幅レプリケーションで同期レプリケーションのオーバーヘッドが軽減。IoT デバイス数の増加に対するスケーラビリティが改善。
