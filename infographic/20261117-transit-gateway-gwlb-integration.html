AWS Transit Gateway Gateway Load Balancer 📅 2026 年 11 月 17 日

🔀 Transit Gateway × Gateway Load Balancer ネイティブ統合

ネットワーク機能アタッチメントで、インスペクション VPC 不要の集中型トラフィック検査を実現

📌 概要

AWS Transit Gateway が Gateway Load Balancer タイプのネットワーク機能アタッチメント をサポートしました。 ファイアウォールなどのセキュリティアプライアンスをフロントする GWLB の VPC エンドポイントサービスに、Transit Gateway を直接接続できます。 Transit Gateway が選択した AZ に GWLB エンドポイントを自動作成・管理するため、従来必要だったインスペクション VPC の構築が不要になります。 さらにコンテキスト共有により、ファイアウォールが VPC やセキュリティグループなどのリソースコンテキストを使ったセグメンテーションポリシーを適用できます。

❌ アップデート前の課題

✗専用のインスペクション VPC を作成し、AZ ごとにエンドポイント用サブネットと GWLB エンドポイントを手動構築
✗アプライアンスモードの有効化やルートテーブル設計が複雑で、設定ミスによる非対称ルーティングのリスク
✗ファイアウォールは IP アドレスベースの情報しか参照できず、AWS リソースの文脈に基づくポリシー適用が困難

✅ アップデート後の改善

✓GWLB の VPC エンドポイントサービスを直接指定でき、インスペクション VPC・専用サブネット・ルートテーブルが不要に
✓最大 16 AZ に GWLB エンドポイントを自動作成・管理。AZ の追加・削除もアタッチメント変更操作だけで完結
✓コンテキスト共有により、アタッチメント・VPC・サブネット・セキュリティグループを使ったセグメンテーションポリシーが可能
✓別アカウントのエンドポイントサービス (FWaaS 含む) もサポートし、クロスアカウント運用が容易に

従来はインスペクション VPC 内にサブネット、GWLB エンドポイント、ルートテーブルを手動で構築する必要がありましたが、新しいネットワーク機能アタッチメントでは Transit Gateway がエンドポイントサービスへの接続を直接管理します。

⚙️ 主要機能

🧩 GWLB タイプのネットワーク機能アタッチメント

  • アタッチメントタイプ「Network Function」が追加され、GWLB の VPC エンドポイントサービスを直接指定して接続
  • 選択した AZ ごとに 1 つの GWLB エンドポイントを Transit Gateway が自動作成・管理
  • 作成時に最大 16 の AZ を指定可能。承認制のサービスでは pendingAcceptance 状態で承認を待機

🏢 クロスアカウント対応

  • GWLB エンドポイントサービスは Transit Gateway と別の AWS アカウントに配置可能
  • 新しい許可タイプ transit-gateway-attachment で Transit Gateway 所有者のアカウント (ルート ARN) に接続を許可
  • 自社展開のファイアウォールのほか、ファイアウォール・アズ・ア・サービス (FWaaS) にも適用可能

🔖 セキュリティサービスとのコンテキスト共有

  • ファイアウォールへ送信するトラフィックに、アタッチメント・VPC・サブネット・セキュリティグループのリソースコンテキストを付加
  • IP アドレスに加えてコンテキストを参照した、リソース単位のセグメンテーションポリシーを適用可能
  • 同日の API 更新で AWS Network Manager にコンテキスト共有 API (12 メソッド)、AWS Network Firewall にコンテキスト対応ステートフルルールグループが追加

🚀 運用のシンプル化

  • AZ の追加・削除はアタッチメントの変更操作のみで完結。AZ 追加時はエンドポイントが自動作成
  • 変更中は modifying 状態、非サポート AZ 指定時は rollingBack を経て元の構成に自動復旧
  • アタッチメント削除時には、作成された GWLB エンドポイントも自動的に削除

主な新規 API

  • CreateTransitGatewayNetworkFunctionAttachment: GWLB エンドポイントサービスへのアタッチメントを作成
  • ModifyTransitGatewayNetworkFunctionAttachment: アベイラビリティゾーンの追加・削除
  • DescribeTransitGatewayNetworkFunctionAttachments: アタッチメントの一覧・フィルタリング
  • DeleteTransitGatewayNetworkFunctionAttachment: アタッチメントの削除

また、ModifyVpcEndpointServicePermissions に PermissionType パラメータ (vpc-endpoint または transit-gateway-attachment) が追加され、 AcceptVpcEndpointConnections / RejectVpcEndpointConnections が TransitGatewayAttachmentIds を受け付けるようになりました。

🛠️ 設定方法

前提条件

  • 正常なアプライアンスターゲットを持つ GWLB と、それをフロントする VPC エンドポイントサービスが作成済みであること
  • Transit Gateway の暗号化サポート (Encryption Support) が無効であること
  • アタッチメントを作成するプリンシパルに ec2:DescribeVpcEndpointServices の権限があること
  • クロスアカウント構成の場合、エンドポイントサービス所有者が Transit Gateway 所有者のアカウントに接続を許可していること
1

エンドポイントサービス側で接続を許可する (クロスアカウントの場合)

BashAWS CLI
aws ec2 modify-vpc-endpoint-service-permissions \
  --service-id vpce-svc-0123456789abcdef0 \
  --permission-type transit-gateway-attachment \
  --add-allowed-principals arn:aws:iam::111122223333:root

transit-gateway-attachment 許可タイプで Transit Gateway 所有者のアカウント (ルート ARN) に接続を許可します。この許可タイプは AWS アカウントプリンシパルのみをサポートします。

2

ネットワーク機能アタッチメントを作成する

BashAWS CLI
aws ec2 create-transit-gateway-network-function-attachment \
  --transit-gateway-id tgw-0123456789abcdef0 \
  --service-name com.amazonaws.vpce.ap-northeast-1.vpce-svc-0123456789abcdef0 \
  --availability-zone-ids apne1-az1 apne1-az2

指定した各 AZ に GWLB エンドポイントが自動作成されます。承認制のサービスでは、所有者が承認するまで pendingAcceptance 状態になります。

3

ルートテーブルを設定して検査対象トラフィックを転送する

BashAWS CLI
aws ec2 create-transit-gateway-route \
  --transit-gateway-route-table-id tgw-rtb-0123456789abcdef0 \
  --destination-cidr-block 0.0.0.0/0 \
  --transit-gateway-attachment-id tgw-attach-0123456789abcdef0

検査対象トラフィックがアタッチメントを経由するよう静的ルートを追加します。ルートテーブルの関連付けと静的ルートをサポートしますが、ルート伝播はサポートしません。

4

アタッチメントの状態を確認する

BashAWS CLI
aws ec2 describe-transit-gateway-network-function-attachments \
  --filters "Name=transit-gateway-id,Values=tgw-0123456789abcdef0"

アタッチメントが available 状態になっていることを確認します。service-name や state などのフィルタも利用できます。

✓FWaaS 活用の加速: 別アカウントのエンドポイントサービスにも接続でき、サードパーティ FWaaS や共有ファイアウォールを導入しやすい

🔧 技術面

✓構成の簡素化: アタッチメント作成だけで GWLB エンドポイントが自動プロビジョニングされ、非対称ルーティングのリスクを低減
✓AZ 単位の柔軟な拡張: 変更操作で AZ を追加・削除でき、障害時は自動ロールバックで元の構成に復旧
✓コンテキストベースのポリシー: アタッチメント、VPC、サブネット、セキュリティグループの情報を参照した精緻なルール設計が可能

⚠️ デメリット・制約事項

🚫 制限事項

✗Transit Gateway の暗号化サポートが有効 (enabled、enabling、disabling) の場合は作成不可
✗ルート伝播は非サポート。静的ルートのみ利用可能
✗AZ use1-az3 は非サポート
✗中東 (バーレーン) および中東 (UAE) リージョンでは利用不可
✗クロスアカウント許可はアカウントのルート ARN のみ。IAM ユーザー・ロール・組織単位は指定不可

📝 考慮すべき点

⚠指定する各 AZ は、Transit Gateway とエンドポイントサービスの両方でサポートされている必要がある
⚠アタッチメント削除前にルートを削除・置換しないと、ルートが blackhole 状態になりトラフィックが破棄される
⚠Transit Gateway アタッチメントのクォータに計上されるため、大規模環境では事前にクォータを確認する
⚠AWS Network Firewall を利用する場合は、Network Firewall タイプという別方式があり、GWLB タイプとは作成・管理方法が異なる

🎯 ユースケース

1️⃣ サードパーティファイアウォールによる集中型 East-West トラフィック検査

シナリオ: 複数の VPC を Transit Gateway で接続している企業が、VPC 間通信をサードパーティのファイアウォールアプライアンスで集中検査したい。

実装例: ファイアウォールをターゲットとする GWLB とエンドポイントサービスを作成 → GWLB タイプのネットワーク機能アタッチメントを複数 AZ で作成 → 各 VPC アタッチメントのルートテーブルで他 VPC 宛てルートをアタッチメントに向ける → 検査後のトラフィックを宛先 VPC へ転送するルートテーブルを関連付け。

✅ 効果: インスペクション VPC の構築・管理なしで VPC 間トラフィックの集中検査を実現。AZ 追加もアタッチメント変更のみで対応可能。

2️⃣ 別アカウントのセキュリティチームが運用する共有ファイアウォール基盤

シナリオ: セキュリティ専門チームが専用アカウントでファイアウォール基盤 (GWLB + アプライアンス) を運用し、各事業部門の Transit Gateway から接続させたい。

実装例: セキュリティアカウントで承認制のエンドポイントサービスを作成 → transit-gateway-attachment 許可を各事業部門アカウントに付与 → 各部門が自アカウントの Transit Gateway にアタッチメントを作成 → セキュリティチームが接続リクエストを承認。

✅ 効果: セキュリティ基盤の運用を一元化しつつ、各部門は自律的に接続を構成可能。承認フローで接続のガバナンスも確保。

3️⃣ リソースコンテキストを活用したセグメンテーションポリシー

シナリオ: 本番 VPC と開発 VPC の間の通信を、IP アドレスではなく VPC やセキュリティグループといったリソース単位で制御したい。

実装例: GWLB タイプのアタッチメントを作成しコンテキスト共有を活用 → ファイアウォール側で Transit Gateway が付加する VPC ID やセキュリティグループなどのコンテキストを参照するルールを定義 → 本番 VPC から開発 VPC への通信をリソースコンテキストに基づいて許可・拒否。

✅ 効果: CIDR 変更や IP アドレスの変動に影響されない、意図が明確なセグメンテーションポリシーを実装可能。

🌍 利用可能リージョン

AWS Transit Gateway と Gateway Load Balancer の両方が利用可能なすべての商用 AWS リージョンで利用できます。 ただし、中東 (バーレーン) および中東 (UAE) リージョンは除きます。 また、AWS GovCloud (US-East) / (US-West) リージョンでも利用可能です。

🔗 関連サービス・機能

⚖️ Gateway Load Balancer

  • ファイアウォールなどのサードパーティ仮想アプライアンスを透過的に展開・スケールするロードバランサー。本機能の接続先となるエンドポイントサービスを提供

  • ネットワーク機能アタッチメントのもう 1 つのタイプとして直接接続でき、コンテキスト対応ステートフルルールグループでリソースコンテキストを参照可能

  • GWLB エンドポイントサービスの基盤技術で、クロスアカウント接続の許可管理 (transit-gateway-attachment 許可タイプ) を担う

📝 まとめ

今回のアップデートにより、Transit Gateway と Gateway Load Balancer の統合に必要だったインスペクション VPC やエンドポイント用サブネットの構築が不要になり、集中型ネットワークセキュリティの導入が大幅に簡素化されました。 リソースコンテキスト共有により、IP アドレスに依存しないセグメンテーションポリシーも実現できます。 現在 GWLB ベースの集中検査アーキテクチャを運用している場合は、ネットワーク機能アタッチメントへの移行による構成の簡素化を検討することを推奨します。
