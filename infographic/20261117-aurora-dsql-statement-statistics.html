Amazon Aurora DSQL

📊 Database Insights での SQL ステートメント統計

リリース日: 2026 年 11 月 17 日 | 機能: SQL ステートメント統計 (Statement Statistics)

📝 概要

Amazon Aurora DSQL が、クラスターで実行される各 SQL ステートメントの統計を記録し、Amazon CloudWatch の OpenTelemetry (OTel) メトリクスとして発行する機能を提供開始。 CloudWatch Database Insights で各ステートメントの実行回数、実行時間、スキャン / 返却 / 変更した行数、使用した DPU (Distributed Processing Unit) を可視化できます。

ステートメント統計はサンプリングなしの完全計測で、成功したすべてのステートメントを記録。最も時間がかかる / 頻繁に実行される / コストがかかるステートメントを正確に特定できます。追加の Aurora DSQL 料金は不要です。

Aurora DSQL がステートメントごとの統計を OTel メトリクスとして CloudWatch に発行し、正規化 SQL テキストを CloudWatch Logs に書き込みます。収集されたデータは Database Insights、PromQL、Log Analytics の 3 つの方法で分析できます。

⚡ 主要機能

1️⃣ 全ステートメントの統計記録

成功したすべての SELECT、INSERT、UPDATE、DELETE をサンプリングなしで計測。BEGIN、COMMIT、SET などのユーティリティステートメントや DDL はカウント対象外。アプリケーションが直接送信するトップレベルのステートメントのみをカウントし、コミット時にトランザクションが失敗した場合も、実行されたステートメントはカウントされます。

2️⃣ 正規化 SQL テキストとクエリ ID

SQL コメントを除去し、リテラル値を $0 などのプレースホルダーに置換して正規化。リテラル値だけが異なるステートメントは同じ正規化テキストとクエリ ID を共有します。正規化 SQL テキスト (最大 32 KiB) は CloudWatch Logs の /aws/dsql/normalized-sql-text ロググループに書き込まれます。

3️⃣ CloudWatch Database Insights での可視化

Fleet Health ビューから Aurora DSQL クラスターを選択し、Top SQL でステートメントごとの統計を確認。Calls/s、Rows/s、平均実行時間、呼び出しあたりの DPU、コンピュート時間とストレージ時間、スキャン行数と返却行数のチャートを表示し、コードを書かずに問題のあるステートメントを特定できます。

4️⃣ PromQL によるプログラマティックなクエリ

CloudWatch Query Studio で PromQL を使用してメトリクスを直接分析。sum_over_time と sum by を組み合わせた集計が基本パターンで、モニタリングツールとの統合やランキング分析に活用できます。

⚙️ データ集計の仕組み

  • Aurora DSQL は 1 分ごとのウィンドウで 1 つ以上のデータポイントを CloudWatch に送信
  • 各データポイントは前回のデータポイント以降の作業量のみを保持 (累積値ではなく差分値)
  • クラスター、クエリ ID、IAM アイデンティティ、アプリケーション名の組み合わせごとに個別の時系列を保持
  • 差分値のため、PromQL では rate() や increase() ではなく sum_over_time を使用

🛠️ 設定方法

📋 前提条件

  • Aurora DSQL クラスターが利用可能であること
  • 設定変更には dsql:CreateCluster または dsql:UpdateCluster 権限、設定確認には dsql:GetCluster 権限が必要
  • PromQL クエリには cloudwatch:GetMetricData と cloudwatch:ListMetrics 権限が必要
1
既存クラスターでステートメント統計を有効化
BashAWS CLI で STATEMENT_STATISTICS を有効化
aws dsql update-cluster \
  --identifier your_cluster_id \
  --metric-groups '[{"metricGroup":"STATEMENT_STATISTICS"}]' \
  --region us-east-1

コンソールの場合は、クラスターの [Monitoring] タブにある [Advanced monitoring] から設定できます。新規クラスター作成時は create-cluster コマンドに同じ --metric-groups オプションを指定します。

2
設定の確認
Bashメトリクスグループ設定の取得
aws dsql get-cluster \
  --identifier your_cluster_id \
  --query 'metricGroups[].metricGroup' --output text \
  --region us-east-1

有効化されている場合は STATEMENT_STATISTICS が出力され、無効の場合は空の出力になります。

3
Database Insights で統計を確認

CloudWatch コンソールで [Database Insights] を開き、[Fleet Health] ビューの [Database resources] から Aurora DSQL クラスターの DB Identifier を選択。[Top SQL] でステートメントを選択し、クエリ ID、正規化 SQL テキスト、統計チャートを確認します。

4
PromQL でメトリクスをクエリ
PromQL合計時間の上位 10 ステートメントをランキング
topk(10,
  sum by ("db.query.id") (
    sum_over_time({
      "aws.dsql.query.time",
      "@resource.aws.dsql.cluster_id"="your_cluster_id"
    }[1h])
  )
)

CloudWatch Query Studio の PromQL で、過去 1 時間に合計時間が最も長かった上位 10 ステートメントをランキング。メトリクス名を aws.dsql.query.calls や DPU 系メトリクスに変えると、実行回数やコストでのランキングも可能です。

⚖️ メリットと制約事項

✅ ビジネス面のメリット

  • コストの可視化: ステートメントごとの DPU 使用量 (コンピュート / 読み取り / 書き込み) を確認でき、コストドライバーとなるクエリを特定して最適化の優先順位を付けられる
  • 追加料金なしの Aurora DSQL 機能: Aurora DSQL 側の追加料金は不要で、標準の CloudWatch 料金のみで利用できる
  • 運用工数の削減: アプリケーション側での計測実装なしに、クエリレベルの分析基盤を数分で有効化できる

✅ 技術面のメリット

  • サンプリングなしの完全計測: 低頻度だが高コストなクエリも見逃さない
  • OTel 標準メトリクス: PromQL を使った既存のオブザーバビリティツールとの統合が容易
  • 多角的な分析ラベル: クエリ ID に加えて IAM ロール ARN やアプリケーション名で分析でき、マルチテナント環境での切り分けが可能
  • チューニングの判断材料: スキャン行数と返却行数の比較により、インデックス追加が必要なクエリを特定できる

⚠️ 制限事項

  • デフォルトでは無効であり、クラスターごとに有効化が必要 (マルチリージョンクラスターでは各リージョンで個別に有効化)
  • 正規化 SQL テキストはステートメントあたり最大 32 KiB まで保存
  • PromQL クエリの時間範囲は最大 24 時間、1 クエリで返される時系列は最大 500 件
  • ユーティリティステートメントや DDL、ネストされたステートメントは計測対象外
  • 現時点で利用可能なメトリクスグループは STATEMENT_STATISTICS のみ

💭 考慮すべき点

  • CloudWatch メトリクスと Logs の標準料金が発生。クエリの種類が非常に多いワークロードでは時系列数とログ量に応じたコスト見積もりが必要
  • リトライされたトランザクション内のステートメントは再度カウントされ、呼び出し回数が実際のリクエスト数より多く見える場合がある
  • 無効化後も、オープン中の接続からの統計は数分間、正規化 SQL テキストは最大 1 日間到着する可能性がある
  • Aurora DSQL がロググループを新規作成する場合、保持期間は 545 日に設定される (変更可能)

💡 ユースケース

🐢 ユースケース 1: スロークエリの特定とチューニング

シナリオ: Aurora DSQL 上のアプリケーションでレイテンシーが悪化しており、原因となるクエリを特定したい。

実装: Database Insights の Top SQL で平均実行時間の長いステートメントを確認し、「Scanned rows per call」と「Returned rows per call」を比較。スキャン行数が返却行数を大きく上回る場合はインデックス追加を検討する。

効果: アプリケーション側の計測実装なしに、フルスキャンに近い動作をしているクエリを特定し、インデックス設計の改善につなげられる。

💰 ユースケース 2: DPU コストドライバーの分析

シナリオ: Aurora DSQL の DPU 料金が想定より高く、どのクエリがコストを押し上げているかを調査したい。

PromQLコンピュート DPU の上位 10 ステートメント
topk(10,
  sum by ("db.query.id") (
    sum_over_time({
      "aws.dsql.query.compute_dpu",
      "@resource.aws.dsql.cluster_id"="your_cluster_id"
    }[1h])
  )
)

効果: コンピュート / 読み取り / 書き込みの DPU 使用量をステートメント単位で把握し、最もコストの高いクエリから優先的に最適化できる。

🏢 ユースケース 3: マルチテナント環境でのワークロード切り分け

シナリオ: 複数のアプリケーションが同一クラスターを共有しており、どのアプリケーションがどのクエリを実行しているかを把握したい。

実装: 接続パラメータで application.name を設定し、PromQL で sum by ("application.name") または sum by ("aws.dsql.session.role.arn") を使用して集計する。

効果: アプリケーション名や IAM アイデンティティごとにクエリ負荷を切り分け、特定のテナントやサービスに起因する負荷増加を迅速に特定できる。

💵 料金 / 🌍 利用可能リージョン

💵 料金

Aurora DSQL 側の追加料金はありません。標準の CloudWatch メトリクスおよび CloudWatch Logs の料金が適用されます。

  • OTel メトリクス: CloudWatch のメトリクス料金に基づく (時系列数に依存)
  • 正規化 SQL テキスト: CloudWatch Logs の取り込みおよび保存料金に基づく

詳細は CloudWatch 料金ページ を参照してください。

🌍 利用可能リージョン

Aurora DSQL が利用可能なすべての AWS リージョンで利用できます。最新のリージョン一覧は AWS リージョン別サービス一覧 を参照してください。

🎯 まとめ

Aurora DSQL のステートメント統計により、サンプリングなしの完全な計測に基づくクエリレベルのパフォーマンス分析と DPU コスト分析が可能になりました。 Aurora DSQL を本番運用しているユーザーは、UpdateCluster で STATEMENT_STATISTICS メトリクスグループを有効化し、Database Insights の Top SQL から高負荷・高コストなステートメントの確認を始めることを推奨します。
