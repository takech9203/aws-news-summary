Amazon Bedrock Guardrails

🛡️ エージェント型 AI 向け
新 API「InvokeGuardrailChecks」

2026-06-16 サービスアップデート

📌 概要

Amazon Bedrock Guardrails が、エージェント型 AI アプリケーション向けの新 API InvokeGuardrailChecks API を発表しました。 ガードレールリソースを作成することなく、個別のセーフガードをワークフローの 任意のポイントで適用できるリソースレスな API です。

エージェント型アプリは「計画 → ツール呼び出し → 出力処理」といった反復ループで動作し、 各ステップが異なるリスクレベルを持ちます。新 API は検出専用モードで動作し、 ガードレール ID やバージョン管理が不要なため、各リクエストで適用するセーフガードを直接指定できます。 返却される数値の重大度スコアと信頼度スコアを使い、ブロック・通過・再試行・ログ記録を カスタムしきい値で判断できます。

❌ アップデート前の課題

  • ガードレールリソースを事前に作成し、ID とバージョンを管理する必要があった
  • 単一の画一的な設定では、リスクの異なる各ステップへ柔軟に対応しにくかった
  • 特定のセーフガードのみを個別適用する、リクエスト単位の細かい制御が困難だった

✅ アップデート後の改善

  • リソースの作成や ID・バージョンの管理が不要に
  • 各ステップで適用するセーフガードをリクエスト単位で指定可能に
  • 重大度・信頼度スコアに基づき、ブロック/通過/再試行/ログをカスタムしきい値で判断可能に

⭐ 主要機能

🧩 リソースレスな検出専用 API

  • ガードレールリソースを事前作成せずにセーフガードを適用
  • 追跡すべきガードレール ID やバージョン管理が不要
  • 検出専用モードで動作し、適用するセーフガードを各リクエストで直接指定

📊 スコアベースのきめ細かい制御

  • 数値の重大度スコアと信頼度スコアを返却
  • カスタムしきい値を設定して判断ロジックを構築
  • ブロック・通過・再試行・ログ記録を自社のニーズに応じて判断

🛡️ 3 種類のセーフガードの個別適用

🚫

コンテンツフィルター

ヘイト、暴力、性的表現、侮辱、不正行為などの有害コンテンツを検出

🎯

プロンプト攻撃検出

ジェイルブレイク、プロンプトインジェクション、プロンプトリークを個別チェック

🔐

機密情報フィルター

サポートされている PII エンティティタイプを検出

🔧 技術仕様

セーフガードの種類

セーフガード検出対象
コンテンツフィルターヘイト、暴力、性的表現、侮辱、不正行為などの有害コンテンツ
プロンプト攻撃検出ジェイルブレイク、プロンプトインジェクション、プロンプトリーク (各攻撃ベクトルを個別に呼び出し可能)
機密情報フィルターサポートされている PII エンティティタイプ

プロンプト攻撃検出は独立したセーフガードとして提供され、各攻撃ベクトルを個別に呼び出せます。

💡 メリット

ビジネス面

✓責任ある AI の実現: 各ステップで適切なセーフガードを適用し、有害コンテンツ・プロンプト攻撃・機密情報漏えいのリスクを低減
✓導入の容易さ: リソースの作成や管理が不要で、既存アプリへ迅速に組み込める
✓柔軟な運用: スコアベースの判断でユースケースに応じて厳格度を調整

技術面

✓運用負荷の軽減: ID やバージョンの管理が不要になり設定管理が簡素化
✓きめ細かい制御: リクエスト単位でセーフガードを指定し、ステップごとのリスクに対応
✓柔軟な判断ロジック: 重大度・信頼度スコアで独自ロジックを実装

⚠️ デメリット・制約事項

制限事項

!検出専用モードのため、API は検出結果を返すのみ。ブロックなどの後続処理はアプリケーション側で実装が必要
!現時点では利用可能なリージョンが限定されている

考慮すべき点

!各ステップで API を呼び出すため、ループ全体での呼び出し回数・レイテンシー・コストを考慮する必要がある
!重大度・信頼度スコアの適切なしきい値設計が、検出精度と利便性のバランスに影響する

🎯 ユースケース

1. エージェントループの各ステップでのリスク制御

シナリオ: 計画・ツール呼び出し・出力処理を繰り返すアプリで、ステップごとに異なるリスクへ対応したい。

実装イメージ
各ステップで InvokeGuardrailChecks API を呼び出し、
そのステップに必要なセーフガード
（例: ツール呼び出し前はプロンプト攻撃検出）のみを指定する

→ ステップごとに最小限のセーフガードを適用し、安全性と効率を両立

2. プロンプトインジェクション攻撃の独立した検出

シナリオ: 外部入力を扱うエージェントで、攻撃を入力処理段階で個別に検出したい。

実装イメージ
ユーザー入力の処理前に、プロンプト攻撃検出のセーフガードのみを
指定して InvokeGuardrailChecks API を呼び出す

→ 攻撃ベクトルを独立して検出し、攻撃判定時は処理を中断できる

3. 機密情報の漏えい防止

シナリオ: モデル出力に PII が含まれていないか確認してからエンドユーザーへ応答したい。

実装イメージ
出力処理ステップで機密情報フィルターを指定して
InvokeGuardrailChecks API を呼び出し、重大度スコアに基づいて
PII を含む応答をブロックまたはマスキングする

→ 機密情報の意図しない漏えいを防ぎ、コンプライアンス対応を強化

📝 まとめ

InvokeGuardrailChecks API は、ガードレールリソースの管理を不要にし、エージェント型 AI の各ステップに セーフガードをリクエスト単位で適用できる重要なアップデートです。 各ステップのリスクレベルを評価し、コンテンツフィルター・プロンプト攻撃検出・機密情報フィルターを 適切に組み込むことで、責任ある AI の実現を強化することが推奨されます。
