⚡ ElastiCache Serverless for Valkey
ゼロダウンタイムオンライン移行

Amazon ElastiCache 📅 リリース日: 2026 年 10 月 20 日
EC2 上のセルフマネージド Valkey / Redis OSS クラスターから、クライアントにエラーを一切返さずに ElastiCache Serverless for Valkey へオンライン移行できるようになりました。

📝 概要

ここでの「ゼロダウンタイム」とは、ElastiCache SLA と同じ方法で可用性を測定した場合に、移行中クライアントへエラーを一切返さないことを意味します。カットオーバー中もアプリケーションは読み書きを継続でき、サードパーティのレプリケーションツールやメンテナンスウィンドウは不要です。

移行は 3 つの API 駆動フェーズで制御し、アプリケーションは ElastiCache が提供する移行エンドポイント (= サーバーレスキャッシュの標準エンドポイント) に接続するだけ。カットオーバー後も接続先の変更は不要です。

❌ Before: アップデート前の課題

  • スナップショットからのリストアなどオフライン手段が中心で、切り替え時にダウンタイムが発生
  • ダウンタイム回避にはサードパーティのレプリケーションツールや独自のデュアルライト実装が必要
  • カットオーバー時に接続先エンドポイントの切り替えと書き込み停止期間の調整が必要

✅ After: アップデート後の改善

  • EC2 上の Valkey 7.2〜8.1 / Redis OSS 4.0〜7.2 (クラスターモード) からエラーゼロで移行
  • 移行エンドポイント経由でトラフィックを流したまま同期とカットオーバーが完了。サードパーティツール不要
  • 古い Redis OSS 4.0 から Valkey 9.0 へ直接移行可能
  • カットオーバーは手動または自動から選択可能

🔧 主要機能

🛡️ ゼロダウンタイムのオンライン移行
ElastiCache SLA と同じ方法で可用性を測定し、移行中にクライアントへエラーを返しません。カットオーバー中も読み書きを継続でき、サードパーティのレプリケーションツールやメンテナンスウィンドウは不要です。
🔀 3 ステップの移行フロー
1️⃣ 移行の準備 PrepareMigration 要件検証とインフラの
プロビジョニング
→
2️⃣ データ同期の開始 StartMigration 全シャードの
継続的レプリケーション
→
3️⃣ カットオーバー完了 CompleteMigration 手動 (デフォルト)
または自動
各ステップの遷移はキャッシュの Events タブにイベントとして記録され、失敗時には理由が表示されます。
🔌 移行エンドポイント
サーバーレスキャッシュの標準エンドポイントがそのまま移行エンドポイントになるため、カットオーバー後の接続先変更が不要。移行中は ElastiCache がリクエストをソースキャッシュへプロキシします。データ同期は途中で停止 (StopMigration) でき、その間もソースキャッシュ経由で提供が継続されます。
🔐 セキュアなソース接続
TLS による転送時暗号化と認証でソースに接続 (SourceTlsMode: none / verify-ca)。ソースの認証情報は AWS Secrets Manager のシークレットから読み取ります。
📚 幅広いバージョンサポート
ソースは EC2 上のクラスターモードの Redis OSS 4.0〜7.2、Valkey 7.2〜8.1。ターゲットは Valkey 7.2 / 8.1 / 9.0。古い Redis OSS から Valkey 9.0 へ直接移行できます。ソースバージョンはターゲットバージョン以下である必要があります。

移行の要件

項目詳細
ソースエンジンValkey 7.2〜8.1 または Redis OSS 4.0〜7.2 (クラスターモード必須)

⚙️ 設定方法

前提条件

✓ソースが EC2 上のクラスターモードの Valkey 7.2〜8.1 または Redis OSS 4.0〜7.2 であり、PSYNC / REPLCONF が有効であること
✓ターゲットの ElastiCache Serverless for Valkey キャッシュを事前に作成し、空かつパブリックエンドポイントなし (IPv4) であること
✓ターゲットキャッシュの VPC からソースへプライベートに到達でき、ソースのセキュリティグループが ElastiCache からのインバウンドを許可していること
✓ソースが認証を要求する場合、認証情報を AWS Secrets Manager に保存し、ElastiCache に読み取り権限を付与していること
✓ソースのプライマリノードに、移行中のフルシンク (プロセスフォーク) と本番トラフィックを同時にさばく CPU / メモリの余裕があること

ステップ 1: 移行の準備

Bash prepare-migration 
aws elasticache prepare-migration \
  --serverless-cache-name my-serverless-cache \
  --customer-node-endpoint-list "Address=10.0.1.10,Port=6379" \
  --source-authentication-configuration 'SecretManagerConfig={SecretArn=arn:aws:secretsmanager:ap-northeast-1:123456789012:secret:valkey-auth}' \
  --source-tls-configuration 'SourceTlsMode=verify-ca'

ソースキャッシュを移行要件に対して検証し、移行インフラをプロビジョニングして移行エンドポイントを返します。要件を満たさない場合は準備ステップが失敗し、理由を示すイベントがキャッシュに記録されて、移行はロールバックされます。

ステップ 2: アプリケーションの切り替えとデータ同期の開始

Bash start-migration 
aws elasticache start-migration \
  --serverless-cache-name my-serverless-cache \
  --auto-cutover

アプリケーションの接続先を移行エンドポイントに切り替えて、トラフィックが流れていることを確認したうえでデータ同期を開始します。--auto-cutover を指定すると、データ同期の完了後に自動でカットオーバーされます (デフォルトは手動)。ElastiCache はアプリケーションが切り替わったかを検知できないため、同期開始前に切り替えを完了させる必要があります。

ステップ 3: 移行状態の確認とカットオーバーの完了

Bash describe-serverless-caches / complete-migration 
# 移行状態と移行エンドポイントの確認
aws elasticache describe-serverless-caches \
  --serverless-cache-name my-serverless-cache \
  --query 'ServerlessCaches[0].Migration'

# 手動カットオーバーの場合
aws elasticache complete-migration \
  --serverless-cache-name my-serverless-cache

Migration オブジェクト (Status、MigrationEndpoint、CutoverMode) を確認し、手動カットオーバーの場合は complete-migration を実行します。ElastiCache は次の完全同期ウィンドウでターゲットキャッシュへ切り替え、アプリケーションは同じエンドポイントのまま ElastiCache Serverless から提供されるようになります。

💡 メリット

💼 ビジネス面

✓ダウンタイムなしの移行: メンテナンスウィンドウの調整やサービス停止の告知が不要になり、移行プロジェクトのハードルが大幅に低下
✓運用コストの削減: セルフマネージド運用 (パッチ適用、スケーリング、障害対応) から自動スケーリングする Serverless へ移行し運用負荷を削減
✓180 日間の無料移行期間: アカウントごとに最初の移行準備から 180 日間は移行機能を無料で利用可能

🔬 技術面

✓アプリケーション変更が最小限: 移行エンドポイントは標準エンドポイントそのもので、カットオーバー後の接続先変更が不要
✓バージョンアップグレードの同時実行: Redis OSS 4.0 などから Valkey 9.0 へ直接移行でき、移行とアップグレードを 1 回で完了
✓可観測性: 各フェーズの遷移がイベントとして記録され、標準メトリクス (BytesUsedForCache、CurrItems、NetworkBytesIn など) で進行状況を確認可能
✓セキュアな接続: TLS による転送時暗号化と Secrets Manager による認証情報管理に対応

⚠️ デメリット・制約事項

制限事項

✗ソースは EC2 上のクラスターモードのセルフマネージドキャッシュに限定。クラスターモード無効のソース、ElastiCache マネージドキャッシュ、Amazon MemoryDB はソース不可
✗ソース規模はノードあたり最大 32 GB、最大 166 シャードまで
✗移行中はパイプライン非サポート。コマンドが直列化されバッチ処理のレイテンシーが増加 (コネクションプールの拡大を検討)
✗移行中はリーダーエンドポイントを使用不可。トラフィックは移行エンドポイントに送る必要がある
✗移行エラーは永続的なものとして報告され、エラー発生後は移行を再開できない。終了には強制完了 (Force) が必要
✗カットオーバー後のロールバックはない。ソースに戻すにはアプリケーショントラフィックを自分で戻す必要がある
✗1 つのキャッシュは同時に 1 つの移行のターゲットにしかなれない

考慮すべき点

⚠️移行エンドポイント経由のトラフィックには ElastiCache Serverless のコマンドサポートが適用される。FLUSH、CLUSTER 系、Pub/Sub 系コマンドの利用を事前に確認する
⚠️移行中にソースへ直接書き込むとターゲットとの不整合が発生し、移行エラーになる。すべてのトラフィックを移行エンドポイント経由にする
⚠️ロード済みスクリプトはレプリケートされないため、移行エンドポイント経由で SCRIPT LOAD を再実行する。Pub/Sub のサブスクリプションはカットオーバー時に切断され、再接続が必要
⚠️データ同期を停止 (StopMigration) しても課金は止まらない。移行と課金を終了するのは CompleteMigration
⚠️移行スループットはソースのシャード数に比例。少数シャードに高トラフィックが集中する構成では低トラフィック時間帯の移行を計画する
⚠️ネットワーク経路、ソースの TLS 証明書、Secrets Manager の認証情報は移行完了まで変更しない。準備ステップが作成するセキュリティグループも削除しない

🎯 ユースケース

1️⃣ EC2 セルフマネージド Redis OSS からのマネージド移行

EC2 上で Redis OSS 7.0 のクラスターを自前運用しており、パッチ適用やスケーリングの運用負荷を削減するため ElastiCache Serverless for Valkey へ移行したい。ただし 24 時間 365 日稼働の EC サイトのセッションストアであり、ダウンタイムは許容できない。

Bash実装例
# 1. 空のターゲットキャッシュを作成
aws elasticache create-serverless-cache \
  --serverless-cache-name session-store \
  --engine valkey --major-engine-version 8

# 2. 移行を準備し、移行エンドポイントを取得
aws elasticache prepare-migration \
  --serverless-cache-name session-store \
  --customer-node-endpoint-list "Address=10.0.1.10,Port=6379" \
  --source-authentication-configuration 'SecretManagerConfig={SecretArn=arn:aws:secretsmanager:ap-northeast-1:123456789012:secret:redis-auth}'

# 3. アプリを移行エンドポイントへ切り替え後、同期開始 (手動カットオーバー)
aws elasticache start-migration --serverless-cache-name session-store
✨ 効果: セッションを失うことなく、エラーゼロでマネージドサービスへ移行できる。移行後は自動スケーリングにより容量管理が不要になる。
2️⃣ 古い Redis OSS から Valkey 9.0 への直接アップグレード移行

EC2 上に Redis OSS 4.0 のレガシークラスターが残っており、段階的なバージョンアップを繰り返す手間をかけずに最新の Valkey 9.0 環境へ一気に移行したい。

Bash実装例
# ターゲットとして Valkey 9.0 のサーバーレスキャッシュを作成
aws elasticache create-serverless-cache \
  --serverless-cache-name legacy-modernize \
  --engine valkey --major-engine-version 9

# 以降、prepare-migration、start-migration、complete-migration を実行
✨ 効果: Redis OSS 4.0 から Valkey 9.0 へ中間バージョンを経由せずに直接移行でき、アップグレード作業を 1 回のオンライン移行に集約できる。
3️⃣ 自動カットオーバーによる省力化移行

複数のキャッシュクラスターを順次移行する計画で、各クラスターの同期完了を待ってカットオーバー操作を行う人的コストを削減したい。

Bash実装例
# AutoCutover を有効にして同期開始。同期完了後に自動で切り替わる
aws elasticache start-migration \
  --serverless-cache-name cache-01 \
  --auto-cutover

# 進行状況はイベントとメトリクスで監視
aws elasticache describe-events --source-type serverless-cache
✨ 効果: データ同期が完了した次の完全同期ウィンドウで自動的にカットオーバーされるため、オペレーターの待機が不要になる。完了はキャッシュ詳細ページのバナーとイベントで確認できる。

💰 料金

移行機能は、AWS アカウントごとに最初の移行準備から 180 日間は無料で利用できます。無料期間の終了後は、移行がアクティブな間、移行ノードのノード時間単位で課金されます。

⚠️ ターゲットの ElastiCache Serverless キャッシュ自体は、無料期間中であっても標準のデータストレージ (GB-時間) と ECPU のレートで別途課金されます。データ同期を停止しても移行インフラの課金は継続されるため、移行を終了する場合は CompleteMigration を実行してください。

詳細は ElastiCache 料金ページ を参照してください。

📌 まとめ

ElastiCache Serverless for Valkey へのオンライン移行は、セルフマネージド環境からマネージドなサーバーレス環境への移行における最大の障壁であったダウンタイムとツール整備の問題を解消する重要なアップデートです。

✓180 日間の無料移行期間内に、前提条件 (クラスターモード、バージョン、ネットワーク到達性) を確認して移行を計画する
✓まずは検証環境で移行フローを試す
✓パイプライン利用時のレイテンシー増加やコマンド互換性への影響を確認してから本番移行に進む
