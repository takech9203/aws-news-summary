AWS HealthOmics

🧬 キャンセルされたワークフロー実行のキャッシュサポート

完了済みタスク出力を自動保存し、キャンセル地点から再開可能に

📅 2026-05-11

📋 概要

AWS HealthOmics が、キャンセルされたワークフロー実行の完了済みタスク出力をキャッシュする機能をサポート。ワークフローがキャンセルされた場合でも、既に完了しているタスクの出力が顧客の S3 バケットに自動保存され、再実行時にキャンセル地点から処理を再開できるようになった。

AWS HealthOmics は HIPAA 対応のフルマネージドバイオインフォマティクスワークフローサービスであり、ヘルスケアおよびライフサイエンス分野で大規模な科学的発見を加速するために活用されている。

❌ Before (アップデート前)

  • キャンセル時に完了済みタスクの出力が保存されない
  • 再実行時にすべてのタスクを最初から実行し直す必要あり
  • 長時間タスクの再計算によるコスト増大
  • 中間ファイルの確認ができず、デバッグが困難

✅ After (アップデート後)

  • 完了済みタスクの出力が S3 バケットに自動保存
  • 再実行時にキャンセル地点から処理を再開
  • 未完了タスクのみが実行されコスト削減
  • 中間ファイルを検査してデバッグが効率化

🔧 主要機能

💾 キャンセル済み実行の完了タスク出力キャッシュ

  • キャッシュ有効時にワークフローがキャンセルされると、完了済みタスクの出力が自動保存
  • 保存先は顧客が指定した S3 バケット
  • 追加の設定変更なしで既存のキャッシュ設定が適用

⏩ キャンセル地点からの再開

  • 再実行時に cacheId を指定することで、前回のキャンセル地点から処理を再開
  • 完了済みタスクは再計算されず、キャッシュ出力が再利用
  • 未完了タスクのみが新たに実行される

🔍 中間ファイルの検査

  • キャッシュされた中間ファイルをデバッグ目的で検査可能
  • ワークフロー開発時の反復的なデバッグサイクルを効率化
  • タスク単位での出力確認が可能

⚙️ 技術仕様

キャッシュ動作の設定

項目 詳細
cacheBehavior CACHE_ON_FAILURE または CACHE_ALWAYS
保存先 顧客指定の S3 バケット (outputUri)
対応ワークフロー言語 Nextflow, WDL, CWL
キャッシュ対象 キャンセル時点で完了していたタスクの出力

キャッシュ設定パラメータ

JSON キャッシュ設定例 
{
  "cacheId": "string",
  "cacheBehavior": "CACHE_ALWAYS",
  "outputUri": "s3://my-bucket/workflow-outputs/",
  "retentionMode": "RETAIN"
}

🛠️ 設定方法

前提条件: AWS HealthOmics が利用可能なリージョンの AWS アカウント、ワークフロー実行用の IAM ロール、キャッシュ出力保存用の S3 バケットが必要。

Bash Step 1: キャッシュ用の Run Cache を作成 
aws omics create-run-cache \
  --cache-s3-uri s3://my-bucket/run-cache/ \
  --name "my-workflow-cache"
Bash Step 2: キャッシュ有効でワークフローを実行 
aws omics start-run \
  --workflow-id "1234567" \
  --role-arn "arn:aws:iam::123456789012:role/OmicsRole" \
  --output-uri "s3://my-bucket/outputs/" \
  --cache-id "cache-id-from-step1" \
  --cache-behavior "CACHE_ALWAYS" \
  --parameters file://params.json
Bash Step 3: キャンセル後の再実行 (同じ cache-id を指定) 
aws omics start-run \
  --workflow-id "1234567" \
  --role-arn "arn:aws:iam::123456789012:role/OmicsRole" \
  --output-uri "s3://my-bucket/outputs/" \
  --cache-id "cache-id-from-step1" \
  --cache-behavior "CACHE_ALWAYS" \
  --parameters file://params.json

⚠️ 制約事項・考慮点

🚫 制限事項

  • キャッシュ動作を有効にしていない既存の実行には遡って適用されない
  • キャッシュ出力は S3 に保存されるため、ストレージコストが発生
  • キャッシュの有効性はタスクの入力パラメータに依存。入力変更時はキャッシュ無効

💡 考慮すべき点

  • S3 バケットのライフサイクルポリシーを設定し、不要なキャッシュのストレージコストを管理
  • 大規模なゲノムデータセットの中間出力はサイズが大きくなる可能性があるため、ストレージ容量を事前に計画

🎯 ユースケース

🧬 ユースケース 1: ゲノム解析パイプラインのデバッグ

新しいゲノム変異解析パイプラインの開発中に後段タスクでエラーが発生。全体 8 時間のパイプラインで、エラーは 6 時間目のタスクで発生。

Bash 初回実行 + エラー修正後の再実行 
# 初回実行 (キャッシュ有効)
aws omics start-run \
  --workflow-id "variant-calling-wf" \
  --cache-id "dev-cache-001" \
  --cache-behavior "CACHE_ALWAYS" \
  --parameters '{"sample": "NA12878", "reference": "hg38"}'

# エラー確認後にキャンセルし、修正版を再実行
# 最初の 6 時間分のタスクはスキップされる

✅ 効果: 8 時間のパイプラインで 6 時間分の計算を節約し、デバッグサイクルを 2 時間に短縮

💳 ユースケース 2: コスト管理によるワークフロー中断と再開

大規模な WGS (全ゲノムシーケンシング) 解析を実行中に、予算上限に達したため一時的にワークフローをキャンセルする必要がある。

Bash 予算管理によるキャンセルと再実行 
# 予算上限到達時にキャンセル
aws omics cancel-run --id "run-12345"

# 次月の予算が割り当てられた後に再実行
aws omics start-run \
  --workflow-id "wgs-pipeline" \
  --cache-id "budget-managed-cache" \
  --cache-behavior "CACHE_ALWAYS" \
  --parameters file://wgs-params.json

✅ 効果: 予算管理と計算効率を両立し、完了ステップのコストを重複して支払う必要がない

📊 ユースケース 3: マルチサンプル解析での段階的実行

CWL ワークフローで 100 サンプルのバッチ解析を実行中に、優先度の高いジョブが入ったためワークフローをキャンセル。後で残りのサンプルを処理。

Bash 優先ジョブのためのキャンセルと再開 
# 優先ジョブのためにキャンセル
aws omics cancel-run --id "batch-run-001"

# 優先ジョブ完了後に再開 - 処理済みサンプルはスキップ
aws omics start-run \
  --workflow-id "multi-sample-analysis" \
  --cache-id "batch-cache-001" \
  --cache-behavior "CACHE_ALWAYS" \
  --parameters file://batch-params.json

✅ 効果: リソースの優先度管理が柔軟になり、処理済みタスクの再実行コストを回避
