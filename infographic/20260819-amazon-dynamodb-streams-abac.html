🔐 DynamoDB Streams が属性ベースアクセス制御 ABAC をサポート

📅 リリース日: 2026 年 8 月 19 日 | タグベースの IAM 条件でストリームへのアクセスをスケーラブルに制御

📌 概要

Amazon DynamoDB Streams が 属性ベースアクセス制御 (ABAC) をサポートしました。 ストリームリソースに直接タグを付与し、IAM ポリシーの条件として使用することで、 GetRecords などのストリーム操作へのアクセスをタグベースで許可/拒否できます。 ストリームのタグは親テーブルのタグとは独立して管理され、環境分離・チーム分離・コンプライアンス統制を、 大量の個別 IAM ポリシーを作らずに実現できます。

⚙️ 主要機能

🏷️ 1. ストリームへの独立したタグ付与
  • ストリーム 1 つあたり最大 50 個のタグ、合計最大 10 KB
  • 親テーブルのタグを継承せず、独立して管理
  • tag-resource、untag-resource、list-tags-of-resource の CLI/SDK 操作をストリーム ARN に対して実行可能
🔑 2. タグベースの IAM 条件キーによるアクセス制御
  • aws:ResourceTag/tag-key: ストリームのタグに基づいて許可/拒否
  • aws:RequestTag/tag-key: タグ付与リクエスト時のタグ値を制御
  • aws:TagKeys: 使用できるタグキーを制限
  • GetRecords などの読み取り API、TagResource / UntagResource などのタグ操作 API に適用
🌍 3. アカウント単位・リージョン単位の有効化
  • 新規アカウントの多くではデフォルトで有効、既存アカウントではデフォルト無効 (監査後に有効化)
  • DynamoDB コンソールの Settings ページから現在のリージョンに対して有効化
  • 有効化には dynamodb:UpdateAbacStatus、状態確認には dynamodb:GetAbacStatus 権限が必要
  • 有効化後 7 日以内 であればオプトアウト可能

📜 IAM ポリシー例

environment タグの値が production のストリームに対してのみ GetRecords を許可する例です。

JSON タグ条件付き IAM ポリシー 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "dynamodb:GetRecords"
      ],
      "Resource": "arn:aws:dynamodb:*:*:table/*/stream/*",
      "Condition": {
        "StringEquals": {
          "aws:ResourceTag/environment": "production"
        }
      }
    }
  ]
}

🛠️ 設定方法

✅ 前提条件

  • DynamoDB Streams が有効なテーブルが存在すること
  • dynamodb:UpdateAbacStatus および dynamodb:GetAbacStatus 権限を持つこと
  • 既存アカウントの場合、有効化前に既存の IAM ポリシーを監査すること
1
🔍 既存ポリシーの監査

ストリーム ARN への aws:ResourceTag 条件、タグ操作アクションへの aws:RequestTag / aws:TagKeys 条件、ワイルドカード ARN とタグ条件の組み合わせを確認します。ABAC が無効な間はタグがないものとして評価されるため、有効化で認可の挙動が変わる可能性があります。

2
🚀 Streams ABAC の有効化

DynamoDB コンソールで対象リージョンを選択し、[Settings] ページの [Attribute-based access control for Streams] カードで [Enable] を選択します。ステータス更新は非同期・結果整合性で反映されます。有効化後 7 日以内であれば [Disable] から無効化できます。

3
🏷️ ストリームへのタグ付与
Bash AWS CLI でストリームにタグを付与 
aws dynamodb tag-resource \
  --resource-arn arn:aws:dynamodb:ap-northeast-1:123456789012:table/MyTable/stream/2026-08-19T00:00:00.000 \
  --tags Key=environment,Value=production

タグの確認は list-tags-of-resource、削除は untag-resource を使用します。親テーブル削除後もストリームは 24 時間存続し、その間は CLI/SDK でタグ操作が可能です (コンソールと CloudFormation からは不可)。

4
📜 タグ条件付き IAM ポリシーの適用

aws:ResourceTag 条件を含む IAM ポリシーを作成し、対象のユーザーやロールにアタッチします。タグが一致するストリームに対してのみ操作が許可されます。

⚖️ メリットと制約事項

💼 ビジネス面のメリット

✓管理コストの削減: タグベースの共通ポリシーで大規模環境のアクセス管理を効率化
✓コンプライアンス強化: タグでアクセス境界を明確化し、監査要件への対応が容易に
✓追加費用なし: ABAC の利用に追加料金は発生しない

🔧 技術面のメリット

✓スケーラブルな認可: 新規ストリームもタグ付与だけで既存ポリシーが自動適用
✓テーブルと独立した制御: 書き込み権限と読み取り権限を別々のきめ細かさで設計可能
✓一貫した ABAC 戦略: テーブル ABAC や他の AWS サービスと同じ条件キーで統一

⚠️ 制限事項

•タグは最大 50 個 / 合計 10 KB まで
•テーブル ABAC とストリーム ABAC は別設定で、それぞれ有効化が必要
•既存アカウントはデフォルト無効 (オプトイン必須)
•オプトアウトは有効化後 7 日以内のみ
•親テーブル削除後のタグ操作は CLI/SDK のみ

🤔 考慮すべき点

•有効化により既存ポリシーの認可結果が変化する可能性があり、事前監査を強く推奨
•ストリームはテーブルのタグを継承しないため、明示的なタグ付与が必要
•CloudFormation 管理時はサービスロールにストリームへのタグ操作権限が必要
•ABAC ステータス更新とタグ評価は結果整合性 (反映に数分かかる場合あり)

💡 ユースケース

🏭 ユースケース 1: 本番環境と開発環境のアクセス分離

シナリオ: 同一アカウント内に本番用と開発用のテーブル/ストリームが混在。開発者には開発環境のストリームのみ読み取りを許可したい。

JSON 開発環境ストリームのみ許可 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "dynamodb:GetRecords",
        "dynamodb:GetShardIterator",
        "dynamodb:DescribeStream"
      ],
      "Resource": "arn:aws:dynamodb:*:*:table/*/stream/*",
      "Condition": {
        "StringEquals": {
          "aws:ResourceTag/environment": "development"
        }
      }
    }
  ]
}

効果: ARN の列挙なしにタグだけで環境分離を実現。新しい開発用ストリームが追加されてもポリシー変更は不要。

👥 ユースケース 2: チーム単位のストリームアクセス分離

シナリオ: 複数チームが共有するアカウントで、各チームが所有するストリームのみ、そのチームの Lambda 実行ロールから消費できるようにしたい。

JSON プリンシパルタグとリソースタグの一致条件 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "dynamodb:GetRecords"
      ],
      "Resource": "arn:aws:dynamodb:*:*:table/*/stream/*",
      "Condition": {
        "StringEquals": {
          "aws:ResourceTag/team": "${aws:PrincipalTag/team}"
        }
      }
    }
  ]
}

効果: 1 つの共通ポリシーで全チームのアクセス分離を実現。チーム追加時のポリシー作成が不要。

🛡️ ユースケース 3: タグ改ざんの防止によるガバナンス強化

シナリオ: アクセス制御に使用する environment タグが、権限のないユーザーによって変更・削除されることを防ぎたい。

JSON 重要タグキーの変更を拒否 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Deny",
      "Action": [
        "dynamodb:TagResource",
        "dynamodb:UntagResource"
      ],
      "Resource": "arn:aws:dynamodb:*:*:table/*/stream/*",
      "Condition": {
        "ForAnyValue:StringEquals": {
          "aws:TagKeys": "environment"
        }
      }
    }
  ]
}

効果: aws:TagKeys 条件により、アクセス制御用の重要なタグキーの変更を管理者以外に禁止し、ABAC の信頼性を担保。

🔗 関連サービス・機能

🔐 AWS IAM

ABAC の条件キー (aws:ResourceTag、aws:RequestTag、aws:TagKeys) を IAM ポリシーで評価し、タグベースの認可を実現。

📋 Amazon DynamoDB (テーブルの ABAC)

テーブルは先行して ABAC をサポート済み。今回のアップデートでストリームにも同じ認可戦略を拡張可能に。

⚡ AWS Lambda

DynamoDB Streams の代表的なコンシューマー。Lambda 実行ロールにタグ条件付きポリシーを適用してイベントソースへのアクセスを制御。

🧱 AWS CloudFormation

ストリームのタグを IaC で管理する場合、サービスロールにストリームへのタグ操作権限 (TagResource / UntagResource / ListTagsOfResource) が必要。

DynamoDB Streams の ABAC サポートにより、タグベースのスケーラブルなアクセス制御をストリームにも適用でき、 マルチ環境・マルチチーム構成での IAM ポリシー管理が大幅に簡素化されます。 既存アカウントではデフォルト無効のため、まず既存ポリシーのタグ条件を監査 し、 影響を確認した上でリージョンごとに有効化することを推奨します。 追加料金は不要であり、環境分離やコンプライアンス要件を持つ組織は早期の導入検討が有効です。
