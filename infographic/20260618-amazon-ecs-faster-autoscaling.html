高速サービスオートスケーリング

高解像度メトリクスでスケールアウトを最大 4.2 倍高速化
📅 リリース日2026-06-18

📌 概要

Amazon ECS のサービスオートスケーリングが、負荷変化により迅速に反応できるようになりました。高解像度 (20 秒) メトリクスとメトリクス発行の最適化により、トラフィックの急増に対してスケールアウトの判断と新しいタスクのプロビジョニングが大幅に高速化されます。

反応速度が向上することで、お客様はベースラインキャパシティを削減し、コンピューティングコストを抑えながら信頼性を維持できます。本機能は CPU 使用率・メモリ使用率に基づくターゲット追跡スケーリングポリシーで 20 秒解像度をサポートし、スパイク状トラフィックを処理するすべての ECS ユーザーが対象です。

🔄 Before / After

❌ アップデート前の課題
  • メトリクス解像度がデフォルト 60 秒で、負荷急増の検知が遅い
  • スケールアウトのトリガーまで 6 分以上 (363 秒) を要した
  • 遅延を見越して余分なベースラインキャパシティが必要でコスト増
➡️
✅ アップデート後の改善
  • 20 秒の高解像度メトリクスで判断を 4.2 倍高速化
  • 新タスクのプロビジョニングを E2E で 3.5 倍高速化
  • 過剰なベースラインが不要になりコンピューティングコスト削減

🚀 主要機能

1️⃣ 高解像度 (20 秒) メトリクスのサポート

  • 従来のデフォルト 60 秒解像度に加えて、20 秒の高解像度メトリクスを選択可能
  • CPU 使用率およびメモリ使用率のメトリクスが対象
  • 60 秒解像度も引き続き利用可能で、ワークロードに応じて選択できる

2️⃣ メトリクス発行の最適化

  • 発行パイプラインを最適化し、負荷変化からスケーリングアクションまでの遅延を短縮
  • スケールアウトのトリガー時間が 363 秒 → 86 秒 (76% 短縮)
  • 新タスクの E2E プロビジョニング時間が 386 秒 → 109 秒 (72% 短縮)

3️⃣ ターゲット追跡スケーリングポリシーとの統合

  • CPU/メモリ使用率ベースのターゲット追跡ポリシーで 20 秒解像度をサポート
  • 高解像度対応の事前定義メトリクスを指定することで迅速なスケーリングを実現
  • 予測スケーリングやスケジュールスケーリングなど既存ポリシーと併用可能

📋 設定方法

✅ 前提条件

✓Amazon ECS のサービスが稼働していること (Fargate、ECS Managed Instances、または EC2 起動タイプ)
✓Application Auto Scaling を利用するための適切な IAM 権限を持っていること
✓CPU/メモリ使用率に基づくスケーリングを行う構成であること

1高解像度メトリクスを有効にする

サービスの作成時または更新時に 20 秒解像度のメトリクスを有効化します。これにより CPU/メモリ使用率が 20 秒間隔で CloudWatch に発行されます。

BashAWS CLI
# サービス作成または更新時に 20 秒の高解像度メトリクスを有効化する
aws ecs update-service \
  --cluster my-cluster \
  --service my-service \
  --enable-high-resolution-metrics

2スケーラブルターゲットを登録する

ECS サービスのタスク数 (DesiredCount) をスケーリング対象として登録し、最小・最大キャパシティを指定します。

BashAWS CLI
# ECS サービスをスケーラブルターゲットとして登録する
aws application-autoscaling register-scalable-target \
  --service-namespace ecs \
  --resource-id service/my-cluster/my-service \
  --scalable-dimension ecs:service:DesiredCount \
  --min-capacity 2 \
  --max-capacity 20

3ターゲット追跡ポリシーを設定する

CPU 使用率を対象としたターゲット追跡ポリシーを適用します。config.json には目標値とクールダウン設定を記述します。コンソール、CLI、CloudFormation、各種 SDK から設定できます。

BashAWS CLI
# 高解像度メトリクスに対応したターゲット追跡ポリシーを適用する
aws application-autoscaling put-scaling-policy \
  --service-namespace ecs \
  --resource-id service/my-cluster/my-service \
  --scalable-dimension ecs:service:DesiredCount \
  --policy-name cpu-target-tracking \
  --policy-type TargetTrackingScaling \
  --target-tracking-scaling-policy-configuration file://config.json

⚖️ メリットと制約事項

👍 メリット

✓コスト削減: 反応が速くなり、過剰なベースラインキャパシティを削減できる
✓UX 向上: トラフィック急増に素早く対応し、レスポンス遅延やエラーを抑制
✓信頼性維持: 低コスト化と同時に急激な負荷変動への対応力を保てる
✓高速化: トリガー最大 4.2 倍、プロビジョニング最大 3.5 倍
✓柔軟性: 20 秒と 60 秒を選択でき、既存ポリシーとも併用可能

⚠️ 制約・考慮点

!20 秒の高解像度メトリクスには CloudWatch 標準料金が適用され追加コストが発生
!対象は CPU/メモリ使用率に基づくターゲット追跡ポリシーに限定
!ベンチマーク値は AWS 社内測定で、改善幅はワークロード・構成により異なる
!頻繁なスケーリングを避けるためクールダウン設定を適切に調整する
!急速なスケールインによる可用性低下を防ぐため最小キャパシティを慎重に設定

💡 ユースケース

1. スパイク型トラフィックを処理する API

シナリオ: イベントやキャンペーンで短時間に急激にリクエストが増加する API。従来は 60 秒解像度のため対応が遅れていた。

実装: CPU 使用率のターゲット追跡ポリシー (目標値 60%) + 20 秒高解像度メトリクス

✅ 効果: 負荷急増を素早く検知し、約 86 秒でスケールアウトを開始。エラー率やレイテンシの悪化を防ぐ。

2. コスト最適化を狙うバックエンドワークロード

シナリオ: 通常は低負荷だが断続的に負荷が高まるサービス。これまでは遅延を見越して余分なタスクを常時稼働していた。

実装: 最小キャパシティを引き下げ + 20 秒高解像度メトリクスによる高速スケールアウト

✅ 効果: ベースラインのタスク数を削減してコストを下げつつ、負荷増加時に迅速にキャパシティを追加。

3. メモリ集約型の処理ワークロード

シナリオ: バッチ処理やデータ変換などメモリ使用率が急上昇するワークロード。メモリ枯渇によるタスク停止を避けたい。

実装: メモリ使用率のターゲット追跡ポリシー + 20 秒高解像度メトリクス

✅ 効果: メモリ使用率の上昇を 20 秒間隔で検知し、迅速にタスクを増やしメモリ起因の障害リスクを低減。

💰 料金

高解像度 (20 秒) メトリクスの利用には CloudWatch の標準料金が適用されます。高解像度メトリクスは標準解像度とは異なる料金体系のため、利用前に Amazon CloudWatch の料金ページで確認することを推奨します。ECS サービスオートスケーリング機能自体には追加料金は発生しません。

🎯 まとめ

このアップデートは、ECS サービスオートスケーリングが 20 秒の高解像度メトリクスをサポートすることで、スケールアウトを最大 4.2 倍高速化する重要な機能強化です。スパイク型トラフィックを扱う本番ワークロードでは、可用性を高めながらベースラインキャパシティを削減してコストを最適化できます。CloudWatch の追加料金とのバランスを評価したうえで、ターゲット追跡ポリシーへの高解像度メトリクスの適用を検討することを推奨します。
