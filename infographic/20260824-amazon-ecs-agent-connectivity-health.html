Amazon ECS

🩺 エージェント接続障害のあるコンテナインスタンスの自動検出・修復

📅 2026 年 8 月 24 日リリース ｜ 新ヘルスチェックタイプ AGENT_CONNECTIVITY と障害インスタンスの自動修復

📋 概要

Amazon ECS が、ECS エージェントとコントロールプレーン間の接続状態を継続監視し、接続障害 (impaired) 状態のコンテナインスタンスを自動検出・自動修復する機能を発表。EBS ボリューム劣化、ホストの熱イベント、ネットワーク障害などインフラ起因の「サイレント障害」を、手動介入なしで検知・復旧できるようになりました。

AGENT_CONNECTIVITY
新しいヘルスチェックタイプが追加
3 つの環境対応
Fargate / Managed Instances / EC2
追加料金なし
ECS 標準機能として提供

❌ Before: アップデート前の課題

✗インフライベントによる接続断を標準機能では即座に検知できず、ワークロード障害が見過ごされる可能性
✗切断検知には agentConnected のポーリングなどカスタム監視の構築が必要
✗タスクドレイン、代替キャパシティ確保、登録解除を手動または自作の自動化で実施

✅ After: アップデート後の改善

✓接続を継続監視し、しきい値を超えた切断でインスタンスを自動的に impaired としてマーク
✓AGENT_CONNECTIVITY イベントが EventBridge 経由で全コンピューティングオプションに配信
✓Managed Instances / Fargate ではドレイン → 代替起動 → 登録解除が完全自動化
✓ECS on EC2 ではヘルスイベントをトリガーに独自の置き換えワークフローを構築可能

⚡ 主要機能

1. 🔍 エージェント接続の継続監視

ECS がエージェントとコントロールプレーン間の接続状態を継続監視。切断がしきい値を超えるとインスタンスを impaired 状態としてマーク。EBS ボリューム劣化、熱イベント、ネットワーク障害などインフラ起因の切断を検知可能。

2. 🩺 新ヘルスチェックタイプ AGENT_CONNECTIVITY

AWS Fargate、Amazon ECS Managed Instances、Amazon ECS on EC2 のすべてのコンピューティングオプションで利用可能。describe-container-instances の CONTAINER_INSTANCE_HEALTH オプションや EventBridge の「ECS Container Instance Health Change」イベントで確認できる。

3. 🔧 障害インスタンスの自動修復 (Managed Instances / Fargate)

障害検知後、実行中タスクの自動ドレイン → 代替キャパシティの起動 → 障害インスタンスの登録解除までを手動介入なしで完了し、アプリケーションの可用性を自動的に維持。

4. 🛠️ ECS on EC2 でのカスタムワークフロー構築

AGENT_CONNECTIVITY ヘルスイベントを利用して独自のインスタンス置き換えワークフローを構築可能。EventBridge ルールと Lambda や Systems Manager Automation を組み合わせた自動復旧を実装できる。

🔬 技術仕様

項目詳細
ヘルスチェックタイプAGENT_CONNECTIVITY (今回追加)
既存のヘルスチェックタイプCONTAINER_RUNTIME (EC2)、ACCELERATED_COMPUTE (Managed Instances)、DAEMON (Managed Instances)
overallStatus の値OK、IMPAIRED、INSUFFICIENT_DATA、INITIALIZING
ステータス優先順位IMPAIRED > INSUFFICIENT_DATA > INITIALIZING > OK (最も深刻なステータスが優先)
対象コンピューティングAWS Fargate、Amazon ECS Managed Instances、Amazon ECS on EC2
自動修復の対象Amazon ECS Managed Instances、AWS Fargate
イベント配信EventBridge (detail-type: ECS Container Instance Health Change)
必要なエージェントバージョンヘルス監視には ECS エージェント 1.57.0 以降 (EC2 の場合)
必要な AWS CLI バージョンv1.22.3 以降または v2.3.6 以降

🛠️ 設定方法

📌 前提条件

✓Amazon ECS クラスターが作成済み (Fargate、ECS Managed Instances、または ECS on EC2)
✓ECS on EC2 の場合、ECS コンテナエージェントのバージョンが 1.57.0 以降
✓AWS CLI バージョン 1.22.3 以降または 2.3.6 以降がインストール済み
1
コンテナインスタンスのヘルスステータスを確認する
Bashヘルスステータスの確認
aws ecs describe-container-instances \
    --cluster my-cluster \
    --container-instances 47279cd2cadb41cbaef2dcEXAMPLE \
    --include CONTAINER_INSTANCE_HEALTH

CONTAINER_INSTANCE_HEALTH オプションを付与すると、healthStatus 内の overallStatus と AGENT_CONNECTIVITY を含む個別ヘルスチェックの details 配列を確認できます。

2
EventBridge ルールでヘルス変更イベントを受信する
BashEventBridge ルールの作成
aws events put-rule \
    --name ecs-agent-connectivity-health \
    --event-pattern '{
        "source": ["aws.ecs"],
        "detail-type": ["ECS Container Instance Health Change"],
        "detail": {
            "healthChecks": {
                "type": ["AGENT_CONNECTIVITY"],
                "status": ["IMPAIRED"]
            }
        }
    }'

AGENT_CONNECTIVITY タイプのヘルスチェックが IMPAIRED になったイベントのみをフィルタリングし、通知や自動化のトリガーにできます。

3
ターゲットを設定して通知または自動復旧を実行する
Bashターゲットの設定
aws events put-targets \
    --rule ecs-agent-connectivity-health \
    --targets "Id"="1","Arn"="arn:aws:sns:ap-northeast-1:123456789012:ecs-health-alerts"

SNS トピックや Lambda 関数をターゲットとして設定。Managed Instances / Fargate では修復は ECS が自動実行するため通知用途が中心となり、ECS on EC2 では Lambda などで独自の置き換えワークフローを起動できます。

💼 ビジネス面

✓可用性の向上: サイレントなワークロード障害が自動検知・自動修復され、サービス停止時間を最小化
✓運用コストの削減: 独自ツール開発やオンコール対応による手動復旧作業が不要に
✓追加料金なし: 既存の ECS ワークロードにそのまま適用可能

⚙️ 技術面

✓全コンピューティングオプション対応: Fargate / Managed Instances / EC2 すべてで利用可能
✓完全自動の修復フロー: ドレイン、代替起動、登録解除までを自動化
✓既存ヘルス監視との統合: CONTAINER_RUNTIME などと同じ仕組みで統一的に監視

⚠️ デメリット・制約事項

🚧 制限事項

✗自動修復が提供されるのは ECS Managed Instances と AWS Fargate のみ。ECS on EC2 では独自ワークフローの構築が必要
✗切断から impaired 判定までにはしきい値 (一定時間の切断継続) があり、瞬時には検知されない
✗EC2 起動タイプでの利用には ECS エージェント 1.57.0 以降が必要

🤔 考慮すべき点

⚠ECS on EC2 での自動置き換えには、EventBridge + Lambda / Auto Scaling / SSM Automation を組み合わせたワークフローの設計・テストが必要
⚠自動ドレインによるタスク再配置が発生するため、graceful shutdown (stopTimeout や SIGTERM ハンドリング) の実装確認を推奨
⚠単一タスク稼働のワークロードでは、ドレイン中の可用性確保のため desired count やデプロイ設定の見直しを検討

2. 🔄 ECS on EC2 での独自インスタンス置き換えワークフロー

シナリオ: Auto Scaling グループで運用する ECS on EC2 クラスターで、接続障害インスタンスを自動的に入れ替えたい。

Text実装フロー
1. EventBridge ルールで AGENT_CONNECTIVITY / IMPAIRED イベントを捕捉
2. Lambda 関数で該当インスタンスを DRAINING 状態に変更
   (aws ecs update-container-instances-state --status DRAINING)
3. タスクのドレイン完了後、Auto Scaling グループの
   terminate-instance-in-auto-scaling-group で該当インスタンスを終了
4. Auto Scaling グループが代替インスタンスを自動起動

効果: EC2 起動タイプでも Managed Instances に近い自動復旧を実現し、障害インスタンスの滞留を防止。
