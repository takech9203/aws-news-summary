Amazon SageMaker HyperPod

🚀 EKS オーケストレーションクラスターで
高ポッド密度をサポート

ノードあたりのポッド密度向上で GPU / CPU / メモリを使い切る ｜ 📅 リリース日: 2026 年 11 月 18 日

📋 概要

Amazon SageMaker HyperPod が、EKS オーケストレーションクラスターにおいてノードあたりのポッド密度向上をサポートしました。モニタリング、ロギング、セキュリティ用のシステム DaemonSet と並行して、アプリケーション用のポッドをより多く配置でき、ノードの GPU、CPU、メモリの使用率を高めることで、同じワークロードをより少ないインスタンス数で実行できます。

ポッドのスケジュール数が増えると Amazon VPC CNI が自動的にネットワークキャパシティを追加し、Karpenter オートスケーリングも高いポッドキャパシティに対応します。大規模な基盤モデルのトレーニングや推論、特に 1 つの GPU インスタンス上で複数のモデルレプリカやノートブック環境を稼働させたいユーザーに有用です。

❌ アップデート前の課題
  • ポッド数上限により、GPU / CPU / メモリに余裕があってもポッドを追加配置できなかった
  • システム DaemonSet がポッド数の枠を消費し、アプリケーション用の枠が圧迫されていた
  • MIG で GPU を多数のスライスに分割しても、すべてのスライスを個別のポッドで活用できない場合があった
  • 同じ量のワークロードを処理するために、より多くのインスタンスが必要だった
✅ アップデート後の改善
  • ポッド密度が向上し、各インスタンスの GPU、CPU、メモリの使用率を高められる
  • ポッド数の増加に応じて VPC CNI が自動的にネットワークキャパシティを追加
  • Karpenter が高ポッドキャパシティに対応し、スケールアウト時の新ノードも多くのポッドを処理
  • 同じワークロードをより少ないインスタンス数で実行でき、コスト効率が改善

アップデート前はポッド数上限によりノードのリソースを使い切れませんでしたが、アップデート後はより多くのポッドを配置でき、VPC CNI によるネットワーク容量の自動追加と Karpenter のオートスケーリングがこれを支えます。

⚡ 主要機能

1️⃣ ノードあたりのポッド密度向上
  • EKS オーケストレーションの HyperPod クラスターで、各ノードにより多くのポッドをスケジュール可能
  • モニタリング、ロギング、セキュリティ用のシステム DaemonSet と共存しながら、アプリケーション用のポッド枠を確保
  • GPU、CPU、メモリの使用率が向上し、同じワークロードをより少ないインスタンスで実行可能
2️⃣ Amazon VPC CNI によるネットワーク容量の自動追加
  • ポッドのスケジュール数が増えると、Amazon VPC CNI が自動的にノードへネットワークキャパシティを追加
  • ユーザーが手動でネットワークインターフェイスを管理する必要がない
3️⃣ Karpenter オートスケーリングとの連携
  • Karpenter によるオートスケーリングが高ポッドキャパシティに対応
  • クラスターのスケールアウト時に、新しく起動するノードもより多くのポッドを受け入れ可能

🎯 ユースケース

1. 小規模 GPU インスタンスでのマルチモデル推論

シナリオ: ml.g5 や ml.g6 などの小規模な GPU インスタンスで、複数のモデルレプリカや複数の異なるモデルを提供したい。

YAML 推論用 Deployment で 1 ノードに複数レプリカを配置 
# 推論用 Deployment のレプリカ数を増やし、1 ノードに複数レプリカを配置
apiVersion: apps/v1
kind: Deployment
metadata:
  name: model-inference
spec:
  replicas: 8
  template:
    spec:
      containers:
        - name: inference
          resources:
            requests:
              cpu: "2"
              memory: 8Gi
✅ 効果: 各 GPU インスタンスからより多くのモデルレプリカを提供でき、推論基盤のインスタンス数を削減できる。
2. MIG による GPU パーティショニングの完全活用

シナリオ: ml.p5en.48xlarge で Multi-Instance GPU (MIG) により GPU を多数のスライスに分割し、各スライスで独立したワークロードを実行したい。

YAML MIG スライスを要求するポッド定義の例 
# MIG スライスを要求するポッド定義の例
resources:
  limits:
    nvidia.com/mig-1g.10gb: 1
✅ 効果: ポッド数上限に妨げられることなく、すべての MIG スライスをそれぞれ独自のポッドで活用でき、GPU リソースを余すことなく利用できる。
3. データサイエンスチームの開発環境集約

シナリオ: 多数のデータサイエンティストが利用するノートブックや IDE 環境を、少ないノードに集約してホストしたい。

YAML ノートブック環境ポッドのリソース要求の例 
# ノートブック環境ポッドのリソース要求を適切に設定して高密度に配置
resources:
  requests:
    cpu: "1"
    memory: 4Gi
✅ 効果: 各ノードにより多くの開発環境をホストでき、チーム全体のインフラコストを削減しながら開発者の環境を迅速に提供できる。
