🛡️ Amazon GuardDuty

Runtime Monitoring 向け
オプション脅威検出ルール

環境固有の侵害兆候をマネージドルールで検出 (Custom Detection Rules) ｜ リリース日: 2026 年 10 月 19 日

📌 概要

Amazon GuardDuty が、Runtime Monitoring 向けのオプション脅威検出ルールのサポートを発表。 50 を超える事前構築済みルールを任意に有効化することで、「ある環境では日常的な操作だが、別の環境では侵害の兆候となる」 プロセス・ファイル・ネットワークアクティビティ (例: sudoers ファイルの変更、監査ログの無効化) をランタイムレベルで検出できます。

従来の GuardDuty 検出結果が「どの環境でも疑わしいアクティビティ」を対象とするのに対し、本機能は 「特定の環境でのみ疑わしいアクティビティ」を補完的にカバーします。 各ルールはドライランモードで事前評価でき、誤検知の多いルールを本番検出に入れる前に見極められます。

❌ Before: アップデート前の課題
  • Runtime Monitoring の検出は「どの環境でも疑わしい」アクティビティに限定され、環境固有の想定外操作 (sudoers 変更、監査ログ無効化など) は検出対象外
  • 環境固有のランタイム検出にはサードパーティ製 EDR や独自のエージェント・ログ分析基盤の構築・運用が必要
  • 新しい検出ロジック投入時に誤検知量を事前に見積もる手段がなく、アラート疲れのリスク
✅ After: アップデート後の改善
  • 50 超の事前構築済みルールから「発生しないはず」のアクティビティに対応するルールを選択して有効化
  • EC2、EKS、ECS (EC2/Fargate) のランタイムアクティビティを追加ツールなしに GuardDuty だけで検出
  • ドライランモードで CloudWatch メトリクスによりシグナル量を事前評価してからライブ検出へ移行
  • 委任された GuardDuty 管理者アカウントからメンバーアカウントへルールを一括適用

Runtime Monitoring のエージェントが収集したランタイムアクティビティを、有効化したオプション検出ルールが評価します。 ドライランモードでは CloudWatch メトリクスのみを出力し、ライブモードでは検出結果を生成して EventBridge や Security Hub に連携します。

⚙️ 主要機能

📚 50 超の事前構築済み検出ルール
  • GuardDuty が構築・保守するマネージドルールのライブラリから、必要なルールを選択して有効化
  • sudoers ファイルの変更や監査ログの無効化など、環境によっては侵害の兆候となるプロセス・ファイル・ネットワークアクティビティを検出
  • 各ルールは MITRE ATT&CK や AWS Threat Technique Catalog の脅威テクニック語彙で説明され、名前・重要度・データソース・戦術・テクニック・サービスでフィルタリング可能
🎯 MITRE ATT&CK 戦術にマッピングされた 13 の検出結果タイプ

以下の戦術をカバーします。

永続化 Persistence 権限昇格 Privilege Escalation 実行 Execution 防御回避 Defense Evasion 探索 Discovery 持ち出し Exfiltration コマンド & コントロール C2

今回新たに 4 つの検出結果タイプを追加。

CommandAndControl:Runtime/SuspiciousCommand
CredentialAccess:Runtime/SensitiveFileRead
Discovery:Runtime/SensitiveFileRead
Exfiltration:Runtime/SuspiciousCommand
🧪 ドライランモードによる事前評価
  • ドライランモードで有効化すると、検出結果を生成せずに CloudWatch メトリクスのみを出力
  • 本番検出を有効化する前にシグナル量とルールの挙動を評価でき、アラート疲れを防止
  • ドライランの関連付けは作成から 14 日で自動的に期限切れとなり、ルールは無効状態に戻る (ライブモードに期限はない)
🏢 マルチアカウント環境での一元管理
  • 委任された GuardDuty 管理者アカウントが、組織設定 (Organization Configuration) を使ってメンバーアカウントへルールを一括適用
  • 包含リスト・除外リストで適用対象アカウントを制御でき、後から組織に参加したアカウントにも自動適用

🔧 技術仕様

機能の構成要素

項目詳細
ルール (Rule)GuardDuty が所有・保守する事前構築済み検出。1 ルールが 1 つの脅威テクニックを対象
関連付け (Association)ルールとアカウントのリンク。実行モード (ライブ / ドライラン) を記録。関連付けのないルールは評価されない
ライブモードルールがマッチすると検出結果を生成。EventBridge、Security Hub、S3 (設定時) へエクスポート
ドライランモード検出結果を生成せず CloudWatch メトリクスのみ出力。14 日で自動期限切れ
対象リソースEC2 インスタンス、EKS、ECS (EC2 / Fargate)。プラットフォームごとに最小エージェントバージョン要件あり
検出対象ランタイムのプロセス・ファイル・ネットワークアクティビティ

ルールのステータス

ステータス説明
Liveライブモードで関連付けられており、検出結果を生成
Dry runドライランモードで関連付けられており、CloudWatch メトリクスのみ出力
Disabled関連付けがなく、評価されない

ステップ 1: 利用可能なルールの一覧表示

Bash AWS CLI - ルール一覧の取得 
aws guardduty list-custom-detection-rules \
    --filters Name=dataSource,Values=RuntimeMonitoring

データソースが Runtime Monitoring のルールに絞り込みます。重要度 (severity) や MITRE ATT&CK の戦術 (tactic) でのフィルタリングも可能です。コンソールの場合はナビゲーションペインから [Custom Detection Rules] を選択します。

ステップ 2: ドライランモードでルールを有効化

Bash AWS CLI - ドライランで関連付け 
aws guardduty create-custom-detection-rule-association \
    --rule-id <rule-id> \
    --mode DRY_RUN

この状態ではルールがイベントにマッチしても検出結果は生成されず、CloudWatch メトリクスのみが出力されるため、シグナル量を安全に評価できます。ドライランの関連付けは 14 日で期限切れになる点に注意してください。

ステップ 3: ライブモードへ切り替え

Bash AWS CLI - ライブモードに更新 
aws guardduty update-custom-detection-rule-association \
    --rule-id <rule-id> \
    --mode LIVE

誤検知が許容範囲であれば、関連付けをライブモードに更新して本番の脅威検出を開始します。以降、ルールがマッチすると GuardDuty の検出結果が生成され、EventBridge や Security Hub に連携されます。不要になったルールは delete-custom-detection-rule-association で無効化できます。

📈 ビジネス面

✓追加ツール不要のランタイム防御強化: 環境固有の侵害兆候の検出をサードパーティ EDR なしで実現でき、ツール導入・運用コストを削減
✓アラート疲れの防止: ドライランモードで事前にシグナル量を評価でき、誤検知の多いルールによる運用負荷の増大を回避
✓コンプライアンス・監査対応: 監査ログの無効化や機密ファイルの読み取りといった内部統制上重要なアクティビティを継続的に監視

🔧 技術面

✓マネージドルール: ルールは GuardDuty が構築・保守するため、検出ロジックの作成やメンテナンスが不要
✓MITRE ATT&CK との整合: 既存の脅威分析フレームワークやセキュリティ運用プロセスに統合しやすい
✓幅広いカバレッジ: EC2、EKS、ECS (EC2 / Fargate) を単一の仕組みで横断的に監視
✓組織全体への一括展開: 委任管理者アカウントから組織設定でルールを適用でき、大規模環境でもスケール

⚠️ デメリット・制約事項

🚧 制限事項

✗ルールはオプトイン方式であり、関連付けを作成しない限り評価されない (デフォルトでは無効)
✗ドライランの関連付けは 14 日で自動期限切れ。再評価には新しい関連付けの作成が必要
✗ドライランのメトリクスはルールがイベントにマッチした場合のみ出力され、マッチしないルールの動作確認はできない
✗ルールごとにプラットフォーム別の最小エージェントバージョン要件があり、古いエージェントでは検出できない場合がある

🤔 考慮すべき点

⚠環境によっては正常な運用操作を検出するため、自社の運用実態に合わせたルール選定が重要
⚠ライブモード有効化の前に、ドライランで誤検知量を評価するワークフローを運用プロセスに組み込むことを推奨
⚠Runtime Monitoring の有効化とエージェント導入が前提。未導入の環境では先にエージェント展開の計画が必要

🎯 ユースケース

1️⃣ 本番サーバーにおける権限昇格の兆候検出

シナリオ: 本番環境の EC2 インスタンスでは sudoers ファイルの変更は発生しないはずだが、開発環境では日常的に発生する。本番アカウントのみでこの操作を侵害兆候として検出したい。

Bash 本番アカウントでドライラン評価後、ライブ化 
# 本番アカウントで sudoers 変更検出ルールをドライラン評価後、ライブ化
aws guardduty create-custom-detection-rule-association \
    --rule-id <sudoers-rule-id> \
    --mode LIVE

効果: 本番環境での想定外の権限昇格操作を即座に検出し、インシデント対応を早期に開始できる。開発アカウントではルールを無効のままにすることで誤検知を回避できる。

2️⃣ コンテナ環境での防御回避の検出

シナリオ: EKS / ECS 上のコンテナワークロードで、攻撃者が痕跡を消すために監査ログを無効化する操作を検出したい。

Bash 防御回避戦術のルールを一括有効化 
# 防御回避の戦術に該当するルールを抽出して一括有効化
for RULE in $(aws guardduty list-custom-detection-rules \
    --filters Name=tactic,Values="Defense Evasion" \
    --query 'Rules[].RuleId' --output text); do
  aws guardduty create-custom-detection-rule-association \
      --rule-id "$RULE" --mode DRY_RUN
done

効果: MITRE ATT&CK の防御回避戦術に対応する検出を一括導入し、コンテナ環境における攻撃の初期段階を可視化できる。

3️⃣ 組織全体へのルール一括展開

シナリオ: AWS Organizations 配下の数十アカウントに対し、セキュリティチームが選定したランタイム検出ルールを一括適用し、新規参加アカウントにも自動適用したい。

実装: GuardDuty 委任管理者アカウントで組織設定を作成し、包含リスト / 除外リストで対象アカウントを指定。GuardDuty が各アカウントの関連付けを自動作成し、後から組織に参加したアカウントにも適用される。

効果: アカウントごとの個別設定が不要になり、組織全体で一貫したランタイム脅威検出ポリシーを維持できる。

📝 まとめ

Amazon GuardDuty の Runtime Monitoring に、環境固有の侵害兆候を検出する 50 超のオプションルールが追加され、 EC2 / EKS / ECS にわたるランタイム防御を追加ツールなしで強化できるようになりました。 ドライランモードで誤検知の量を事前評価できるため、まずは自社環境で「発生しないはず」の操作に対応するルールを ドライランで有効化し、評価結果をもとにライブモードへ移行することを推奨します。
