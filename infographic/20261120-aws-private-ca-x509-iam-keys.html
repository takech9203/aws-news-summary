AWS Private Certificate Authority

🔐 X.509 IAM 条件キーのサポート

証明書の「中身」を IAM ポリシーで制御できるように

📅 2026 年 11 月 20 日
AWS What's New

📋 概要

AWS Private CA が、発行しようとしている証明書の内容を記述する IAM 条件キーをサポートしました。サブジェクト、SAN、公開鍵、署名アルゴリズム、有効期間、Key Usage、Extended Key Usage、Basic Constraints といった X.509 証明書の属性に基づいて、証明書リクエストを許可または拒否する IAM ポリシーを記述できます。

IssueCertificate API が呼び出されると、AWS Private CA は CSR、証明書テンプレート、API パススルー値から署名前の証明書 (TBS 証明書) を構築し、その属性に対してポリシーを評価します。非準拠のリクエストは署名前に拒否され、AccessDeniedException が返されます。条件キーの値は最終的な証明書から取得されるため、属性の入力元を変えてもポリシーを回避できません。

1 つのプライベート CA を複数のチームやアカウント間で共有しながら、各チームが発行できる証明書をポリシーで細かく制御できるようになります。マルチアカウント環境で PKI を集中管理する組織や、証明書発行のガバナンスを強化したいセキュリティチームに特に有用です。

❌ Before: 証明書の内容は制御できない
  • IAM で制御できるのは「誰が」「どの CA に」「どのテンプレートで」まで。ドメイン名や有効期間など証明書の中身は制御不可
  • チームごとに発行可能な証明書を分離するには、チームごとに別々の CA が必要で、月額料金と運用負荷が増加
  • あるいは証明書リクエストを検証する独自の認可レイヤー (申請ワークフローやプロキシ) の構築・維持が必要
✅ After: 証明書の内容そのものをポリシーで制御
  • 1 つの CA を共有しつつ、アカウントごとに発行可能な DNS 名を自身のサブドメインに限定できる
  • 有効期間の上限や、組織全体で必須とするキーアルゴリズム・キーサイズをポリシーで強制できる
  • CA 証明書 (下位 CA) の発行を PKI チームのみに限定するなど、役割に応じた発行権限の分離が可能
  • SCP、RCP、VPC エンドポイントポリシー、AWS RAM 許可でも利用でき、組織全体へ一括適用できる

署名前に構築された TBS 証明書の属性に対して IAM ポリシーが評価され、非準拠のリクエストは証明書が発行される前に拒否されます。

⚙️ 主要機能

1️⃣ 証明書内容に基づくポリシー評価
✓acm-pca:IssueCertificate アクションの実行時に、発行予定の証明書 (TBS 証明書) の属性に対してポリシーを評価
✓条件キーは「最終的にどのような証明書になるか」を表すため、CSR・テンプレート・API パススルーのどこで属性を指定しても回避不能
✓非準拠のリクエストには AccessDeniedException が返され、証明書は発行されない
2️⃣ 幅広い証明書属性のカバレッジ
✓サブジェクト: CN、C、O、OU、空サブジェクトの判定
✓SAN: DNS 名、IP アドレス、URI (SPIFFE ID など)、メールアドレス、ディレクトリ名、OtherName、エントリ数、critical フラグ
✓鍵と署名: 鍵アルゴリズム (RSA、EC、SM2、ML-DSA)、鍵サイズ、楕円曲線、CA の署名アルゴリズム
✓有効期間: notBefore、notAfter、日数・時間単位の期間
✓拡張領域: Key Usage、Extended Key Usage、Basic Constraints (CA フラグ、pathLen)
3️⃣ 多様なポリシータイプのサポート
アイデンティティベースポリシー SCP RCP VPC エンドポイントポリシー AWS RAM カスタマーマネージド許可

AWS RAM のカスタマーマネージド許可は、クロスアカウントで CA を共有する場合の発行制御に有効です。

🔬 技術仕様: 主な条件キー

すべての条件キーは acm-pca: プレフィックスを使用し、署名前の TBS 証明書を記述します。証明書に該当しない属性のキーはリクエストコンテキストに存在しません (例: RSA 鍵の場合 acm-pca:x509Key/curve は存在しない)。

カテゴリ条件キーの例型説明
サブジェクトx509Subject/CNArrayOfStringサブジェクトのコモンネーム
サブジェクトx509Subject/C / O / OUArrayOfString国 (2 文字コード)、組織、組織単位
サブジェクトx509Subject/emptyBoolサブジェクト DN が空かどうか (常に存在)
SANx509SAN/DNSArrayOfStringDNS 名エントリ (小文字、末尾ドットなし)
SANx509SAN/IPArrayOfIPAddressIP アドレスエントリ
SANx509SAN/URIArrayOfStringURI エントリ (SPIFFE ワークロード ID など)
SANx509SAN/countNumericSAN エントリの総数
SANx509SAN/OtherName/${OID}ArrayOfStringOtherName エントリ (例: Microsoft UPN は 1.3.6.1.4.1.311.20.2.3)
鍵x509Key/algorithmString公開鍵アルゴリズム: RSA、EC、SM2、ML-DSA-44/65/87
鍵x509Key/sizeNumeric鍵サイズ (ビット)。RSA はモジュラス長、EC は曲線のフィールドサイズ
鍵x509Key/curveStringEC / SM2 鍵の曲線名 (例: prime256v1、secp384r1)
署名x509Signature/algorithmStringCA の署名アルゴリズム (例: ecdsa-with-SHA384)
有効期間x509Validity/durationDaysNumeric有効期間の日数 (切り捨て)
有効期間x509Validity/notBefore / notAfterDate有効期間の開始 / 終了 (UTC)
拡張x509Ext/KeyUsageArrayOfStringRFC 5280 の名称によるキー使用法 (digitalSignature など)
拡張x509Ext/ExtendedKeyUsageArrayOfString拡張キー使用法 (serverAuth、clientAuth、codeSigning、OID など)
拡張x509Ext/BasicConstraints/CABoolCA 証明書かどうか
拡張x509Ext/BasicConstraints/pathLenNumericCA 証明書のパス長制約

条件キーの完全な一覧は ユーザーガイド を参照してください。

📜 ポリシー例: 有効期間を 90 日以内に制限

JSON 有効期間 90 日超の証明書発行を拒否 
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "DenyLongLivedCertificates",
            "Effect": "Deny",
            "Action": "acm-pca:IssueCertificate",
            "Resource": "*",
            "Condition": {
                "NumericGreaterThan": {
                    "acm-pca:x509Validity/durationDays": "90"
                }
            }
        }
    ]
}

🛠️ 設定方法

前提条件

✓AWS Private CA でプライベート CA が作成済みであること
✓IAM ポリシー、SCP、RCP などを編集する権限があること
✓本番適用前に非本番アカウントでポリシーをテストできる環境があること

手順

1
制御したい証明書属性と条件キーを決定する

ユーザーガイドの条件キーリファレンスを確認し、組織のポリシー要件 (許可するドメイン、鍵アルゴリズム、有効期間の上限など) を条件キーにマッピングします。

2
ポリシーを作成してテスト用プリンシパルにアタッチする
Bash インラインポリシーのアタッチ 
aws iam put-role-policy \
  --role-name CertificateIssuerRole \
  --policy-name RestrictCertificateContents \
  --policy-document file://certificate-policy.json

作成したポリシードキュメントをテスト用の IAM ロールにインラインポリシーとしてアタッチします。SCP や RCP として組織全体に適用する場合は AWS Organizations で設定します。

3
準拠・非準拠のリクエストで動作を検証する
Bash 非準拠リクエストの拒否確認 (有効期間 100 日) 
aws acm-pca issue-certificate \
  --certificate-authority-arn arn:aws:acm-pca:ap-northeast-1:123456789012:certificate-authority/example \
  --csr fileb://test.csr \
  --signing-algorithm SHA256WITHECDSA \
  --validity Value=100,Type=DAYS

ポリシーに違反する証明書リクエスト (この例では有効期間 100 日) を実行し、AccessDeniedException で拒否されることを確認します。準拠するリクエストが正常に発行されることも併せて確認します。

4
影響範囲を確認してから本番環境へ展開する

新しい Deny ステートメントは、AWS サービスやコネクタがユーザーに代わって行う証明書リクエストも拒否する可能性があります。ユーザーガイドの「Before you deploy a policy」を確認し、非本番アカウントでテストしてから段階的に適用します。

✓多層的な適用: アイデンティティベースポリシー、SCP、RCP、VPC エンドポイントポリシー、AWS RAM 許可の複数レイヤーで適用可能

⚠️ デメリット・制約事項

制限事項

✗X.509 条件キーは acm-pca:IssueCertificate アクションでのみ利用可能。acm-pca:RevokeCertificate や acm-pca:GetCertificate など他のアクションのステートメントで使用すると、キーが存在しないため意図しない評価結果になる
✗証明書に該当しない属性のキーはリクエストコンテキストに存在しないため、Null 条件や ForAllValues の評価挙動を正しく理解してポリシーを設計する必要がある
✗acm-pca:x509Subject/CN は証明書に記載されたとおりに評価され、小文字化されない (大文字小文字を区別しない比較には StringEqualsIgnoreCase などが必要)

考慮すべき点

⚠️新しい Deny ステートメントは、AWS サービスやコネクタ (AWS Certificate Manager との連携など) が代理で行う証明書リクエストも拒否する可能性がある。本番適用前に非本番アカウントでのテストが推奨される
⚠️Allow ステートメントで ForAllValues を使う場合、対象キーの値が存在しない証明書も条件を満たすため、Null 条件や acm-pca:x509SAN/count と組み合わせて抜け道を塞ぐ設計が必要
⚠️SAN の OtherName エントリは OID ごとに個別のキーとなるため、単一の条件ですべての OtherName タイプをカバーすることはできない

🎯 ユースケース

1. 共有 CA でアカウントごとにサブドメインを制限

シナリオ: 組織の PKI チームが 1 つのプライベート CA を AWS RAM で各アカウントに共有し、各アカウントは自身のサブドメインの証明書のみ発行できるようにしたい。

JSON 承認済みドメイン以外の DNS 名を拒否 
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "DenyUnapprovedDomains",
            "Effect": "Deny",
            "Action": "acm-pca:IssueCertificate",
            "Resource": "*",
            "Condition": {
                "ForAnyValue:StringNotLike": {
                    "acm-pca:x509SAN/DNS": ["team-a.example.com", "*.team-a.example.com"]
                }
            }
        }
    ]
}
✅ 効果: チームごとに CA を分けることなく、他チームのドメイン名を含む証明書の発行を防止できる。
2. 組織全体で鍵強度と有効期間の標準を強制

シナリオ: セキュリティチームが、組織内のすべての証明書に対して RSA 2048 ビット以上または承認済み EC 曲線の使用と、90 日以内の有効期間を義務付けたい。

JSON 弱い RSA 鍵と長期有効期間を拒否 
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "DenyShortRSAKeys",
            "Effect": "Deny",
            "Action": "acm-pca:IssueCertificate",
            "Resource": "*",
            "Condition": {
                "StringEquals": { "acm-pca:x509Key/algorithm": "RSA" },
                "NumericLessThan": { "acm-pca:x509Key/size": "2048" }
            }
        },
        {
            "Sid": "DenyLongLivedCertificates",
            "Effect": "Deny",
            "Action": "acm-pca:IssueCertificate",
            "Resource": "*",
            "Condition": {
                "NumericGreaterThan": { "acm-pca:x509Validity/durationDays": "90" }
            }
        }
    ]
}
✅ 効果: SCP として組織全体に適用することで、どのアカウント・どのツールから発行しても組織標準を満たさない証明書は発行されない。
3. CA 証明書の発行を PKI チームに限定

シナリオ: 下位 CA 証明書の発行は PKI チームのみに許可し、一般の開発者ロールにはエンドエンティティ証明書のみ発行させたい。

JSON エンドエンティティ専用ロールによる CA 証明書発行を拒否 
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Sid": "DenyCACertificatesForEndEntityRoles",
            "Effect": "Deny",
            "Action": "acm-pca:IssueCertificate",
            "Resource": "*",
            "Condition": {
                "Bool": { "acm-pca:x509Ext/BasicConstraints/CA": "true" },
                "StringEquals": { "aws:PrincipalTag/CertificateType": "EndEntityOnly" }
            }
        }
    ]
}
✅ 効果: プリンシパルタグと組み合わせることで、アカウントごとに個別のポリシーを用意せずに役割別の発行権限を実現できる。

💰 料金・利用可能リージョン

💵 料金

この機能は追加料金なしで利用できます。AWS Private CA 自体の料金 (CA の月額料金と証明書発行料金) は通常どおり適用されます。詳細は AWS Private CA 料金ページ を参照してください。

🌏 利用可能リージョン

AWS Private CA が利用可能なすべての AWS リージョンで利用できます (東京・大阪リージョンを含む)。

🔗 関連サービス・機能

🔑 AWS IAM

条件キーを利用するポリシー評価の基盤。アイデンティティベースポリシーで個別のロール・ユーザーを制御。

🏢 AWS Organizations (SCP / RCP)

組織・OU 単位で証明書発行のガードレールを一括適用。

🤝 AWS RAM

プライベート CA のクロスアカウント共有。カスタマーマネージド許可に条件キーを組み込むことで、共有先の発行内容を制御。

📜 AWS Certificate Manager (ACM)

Private CA と連携して証明書を発行・管理するサービス。Deny ポリシーが ACM 経由の発行に影響しないか事前確認が必要。

📝 まとめ

AWS Private CA の X.509 IAM 条件キーにより、証明書の「中身」に対するガバナンスを IAM ポリシーだけで実現できるようになりました。チームごとの CA 分割や独自の認可レイヤーが不要になるため、マルチアカウントで PKI を運用している組織は、まず非本番環境でポリシーを検証し、SCP / RCP による組織全体のガードレールとしての適用を検討することを推奨します。
