🔐 AWS Secrets Manager Agent
プリフェッチと IAM ロール引き受け機能

AWS Secrets Manager
2026 年 5 月 18 日

📋 概要

AWS Secrets Manager Agent に 起動時のシークレットプリフェッチ機能 と IAM ロール引き受け機能 の 2 つの新機能が追加された。プリフェッチ機能により Agent 起動時にシークレットをバッチ取得・キャッシュが可能となり、アプリケーションの起動レイテンシーが削減される。IAM ロール引き受け機能によりクロスアカウントのシークレット取得が実現される。

BatchGet 一括取得で起動高速化
20 同時引き受け可能ロール数
TOML 宣言的な設定ファイル

Before / After

❌ Before

  • 個別に GetSecretValue API を順次呼び出し、起動レイテンシー大
  • クロスアカウント取得に独自のロール引き受けロジックが必要
  • シークレットごとに異なる IAM ロールの使い分けを自前で構築
  • 起動時プリロードロジックのカスタム実装が運用負荷に

✅ After

  • BatchGetSecretValue API で一括取得、レイテンシーとコスト最適化
  • TOML 設定ファイルに宣言的記述で自動取得実現
  • roleArn パラメータでシークレットごとに異なるロール引き受け可能
  • カスタムプリロードロジック不要、運用オーバーヘッド大幅削減

⚡ 主要機能

🚀 プリフェッチ機能

  • Agent 起動時に指定シークレットをバックグラウンドで自動取得
  • BatchGetSecretValue API による効率的なバッチ取得
  • 明示的なシークレット ID/ARN 指定またはタグベースの自動検出に対応
  • Agent はプリフェッチ完了を待たずに即座にリクエスト受付を開始
  • cache_buffer_ratio によるキャッシュ使用率の制御が可能

👤 IAM ロール引き受け機能

  • プリフェッチ設定または HTTP リクエストで roleArn を指定可能
  • AWS STS AssumeRole によるクロスアカウントシークレット取得
  • シークレットごとに異なるロールの指定が可能
  • ロールごとに独立したキャッシュクライアントを維持
  • 最大 20 ロールの同時引き受けに対応

🎯 フリート起動時のジッター制御

  • max_jitter_seconds パラメータにより複数 Agent の同時起動時の API 呼び出し集中を防止
  • 0 から 10 秒の範囲でランダム遅延を設定可能
  • 大規模フリートでの Secrets Manager API スロットリング回避に有効

🔧 技術仕様

設定パラメータ

パラメータ 説明 範囲 デフォルト
cache_buffer_ratio プリフェッチ時のキャッシュ使用率上限 0.1 - 1.0 0.8
max_jitter_seconds プリフェッチ開始前のランダム遅延 0 - 10 秒 0
max_roles 同時引き受け可能なロール数 1 - 20 20
cache_size キャッシュ最大エントリ数 1 - 1000 1000
ttl_seconds キャッシュ TTL 0 - 3600 秒 300

必要な IAM 権限

操作 必要な権限
基本的なシークレット取得 secretsmanager:GetSecretValue, secretsmanager:DescribeSecret
プリフェッチ secretsmanager:BatchGetSecretValue
タグベース検出 secretsmanager:ListSecrets
クロスアカウントアクセス sts:AssumeRole

エラーレスポンス

ステータスコード 説明
400 roleArn フォーマット不正、または最大ロール数到達
403 STS AssumeRole 呼び出し失敗

⚙️ 設定方法

前提条件: Secrets Manager Agent のビルド済みバイナリ、対象シークレットへのアクセス権限、クロスアカウント利用の場合はターゲットロールの信頼ポリシー設定が必要。

Step 1: プリフェッチ設定ファイルの作成

TOML config.toml 
# config.toml
log_level = "INFO"
http_port = 2773
ttl_seconds = 300
cache_size = 1000
max_roles = 20

[prefetch]
cache_buffer_ratio = 0.6
max_jitter_seconds = 5
secrets = [
    { secret_id = "arn:aws:secretsmanager:ap-northeast-1:123456789012:secret:AppSecret-AbCdEf" },
    { secret_id = "DatabasePassword" },
    { secret_id = "cross-account-secret", role_arn = "arn:aws:iam::987654321098:role/SecretAccessRole" },
]
filter_tags = [
    { key = "Environment" },
    { key = "Team", role_arn = "arn:aws:iam::987654321098:role/SecretAccessRole" },
]

Step 2: IAM ポリシーの設定

JSON IAM Policy 
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Action": [
                "secretsmanager:GetSecretValue",
                "secretsmanager:DescribeSecret",
                "secretsmanager:BatchGetSecretValue",
                "secretsmanager:ListSecrets"
            ],
            "Resource": "*"
        },
        {
            "Effect": "Allow",
            "Action": "sts:AssumeRole",
            "Resource": "arn:aws:iam::987654321098:role/SecretAccessRole"
        }
    ]
}

Step 3: ターゲットロールの信頼ポリシー設定

JSON Trust Policy 
{
    "Version": "2012-10-17",
    "Statement": [
        {
            "Effect": "Allow",
            "Principal": {
                "AWS": "arn:aws:iam::123456789012:role/SecretsManagerAgentRole"
            },
            "Action": "sts:AssumeRole"
        }
    ]
}

Step 4: Agent の起動

Bash Agent 起動コマンド 
./aws_secretsmanager_agent --config config.toml

Step 5: アプリケーションからのシークレット取得

Bash シークレット取得リクエスト 
# ローカルシークレットの取得
curl -H "X-Aws-Parameters-Secrets-Token: $(

✅ メリット

💼 ビジネス面

  • 起動時間の短縮: バッチ取得で起動レイテンシーを大幅削減
  • コスト最適化: BatchGetSecretValue で API コール数削減
  • 運用効率の向上: カスタムプリロードロジックの開発・保守が不要

🔧 技術面

  • セキュリティ強化: ロールベースのアクセスで最小権限の原則を実現
  • マルチアカウント対応: 宣言的にクロスアカウント構成を管理
  • フリートスケーリング: ジッター設定で API スロットリング回避
  • 非ブロッキング設計: プリフェッチはバックグラウンド実行

⚠️ デメリット・制約事項

🚧 制限事項

  • 同時引き受け可能なロール数は最大 20。上限到達後は Agent の再起動まで新規ロールのリクエストが拒否される
  • プリフェッチはキャッシュ無効化をサポートしない。ローテーションが TTL 内に発生した場合、古い値が返される可能性
  • cache_buffer_ratio の上限に達した場合、残りのシークレットはプリフェッチされない
  • Agent はシークレットの読み取りのみ対応。書き込み・更新はできない

💡 考慮すべき点

  • プリフェッチ設定の変更には Agent の再起動が必要
  • ロールキャッシュはエビクションされないため、動的にロールが追加されるワークロードでは max_roles の設計が重要
  • SSRF トークンにアクセスできるすべてのプロセスがキャッシュされたシークレットを取得できるため、ホストのセキュリティ境界の設計が重要

🎯 ユースケース

🚀 ユースケース 1: マイクロサービスの高速起動

Kubernetes 上で稼働するマイクロサービスが起動時に 20 個のデータベース接続情報や API キーを必要としている。従来は順次取得で起動に数秒かかっていた。

TOML プリフェッチ設定例 
[prefetch]
cache_buffer_ratio = 0.8
secrets = [
    { secret_id = "db-primary-credentials" },
    { secret_id = "db-replica-credentials" },
    { secret_id = "redis-auth-token" },
    { secret_id = "api-key-payment-service" },
    { secret_id = "api-key-notification-service" },
]
filter_tags = [
    { key = "service", value = "order-service" },
]
✅ BatchGetSecretValue による一括取得で起動レイテンシーを大幅に削減。ECS タスクや Kubernetes Pod のヘルスチェック通過までの時間が短縮される。

🏢 ユースケース 2: マルチアカウント SaaS アーキテクチャ

SaaS プロバイダーが顧客ごとに別 AWS アカウントでシークレットを管理しており、中央のアプリケーションアカウントから各顧客アカウントのシークレットにアクセスする必要がある。

TOML マルチテナント設定例 
[prefetch]
secrets = [
    { secret_id = "tenant-a-db-creds", role_arn = "arn:aws:iam::111111111111:role/SecretReader" },
    { secret_id = "tenant-b-db-creds", role_arn = "arn:aws:iam::222222222222:role/SecretReader" },
    { secret_id = "tenant-c-db-creds", role_arn = "arn:aws:iam::333333333333:role/SecretReader" },
]
✅ テナントごとのカスタムロール引き受けロジックが不要になり、設定ファイルのみでマルチテナントのシークレットアクセスを管理。IAM ロールの分離によりテナント間のセキュリティ境界を維持。

🏷️ ユースケース 3: 環境タグベースの自動シークレット検出

開発環境・ステージング環境・本番環境で同じアプリケーションをデプロイしており、環境ごとのシークレットをタグで管理している。

TOML タグベース検出設定例 
[prefetch]
cache_buffer_ratio = 0.6
max_jitter_seconds = 3
filter_tags = [
    { key = "Environment" },
    { key = "Application" },
]
✅ 新しいシークレットを追加する際、適切なタグを付与するだけで自動的にプリフェッチ対象に含まれる。デプロイパイプラインの変更が不要になり、シークレット管理のスケーラビリティが向上。

💰 料金

Secrets Manager Agent 自体は無料のオープンソースコンポーネント。料金は Secrets Manager の API 呼び出しとシークレット保管に対して発生する。

項目 料金
シークレット保管 $0.40/シークレット/月
API コール (GetSecretValue, BatchGetSecretValue) $0.05/10,000 件
API コール (ListSecrets) $0.05/10,000 件
💡 プリフェッチにより BatchGetSecretValue を使用することで、個別の GetSecretValue 呼び出しと比較して API コール数が削減され、特に起動頻度の高いワークロードでコスト効率が向上する。
