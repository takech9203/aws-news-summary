Configurable Deployment Circuit Breaker Settings — 自動ロールバックをより細かく制御
リリース日
2026-07-01

📌 概要

Amazon ECS は、サービスデプロイをいつ失敗とみなし自動的にロールバックするかを、より細かく制御できるようになりました。 デプロイサーキットブレーカーの設定を、アプリケーションの起動動作・デプロイのニーズ・タスク障害への許容度に合わせてカスタマイズできます。

障害しきい値を 「固定のタスク障害数」 または 「希望タスク数に対する割合」 で設定でき、 さらに障害のカウント方法も選択可能に。開発環境では素早くロールバック、本番環境では起動時の一時障害を許容するといった、環境ごとの最適な運用が実現します。

❌ Before（従来）
•障害しきい値がサービス側で固定的に決定され、アプリ特性に合わせた調整ができなかった
•起動時に一時的な障害が想定されるアプリでも、その特性を考慮したロールバック設定ができなかった
•開発環境と本番環境で異なるロールバック感度を使い分けるのが難しかった
➜
✅ After（今回）
•障害しきい値を固定のタスク障害数、または希望タスク数に対する割合で指定できる
•障害カウント方法を連続（consecutive）／累積（cumulative）モデルから選択できる
•環境やアプリケーションごとにロールバックの感度を最適化できる

🔄 動作フロー（アーキテクチャ図）

タスクの起動と正常性確認を繰り返しながら障害数をカウントし、設定したしきい値に到達すると直近の成功デプロイへ自動ロールバックします。

⭐ 主要機能

📊 しきい値の指定方法の選択
✓固定のタスク障害数を指定し、その数に達した時点でロールバックを実行
✓サービスの希望タスク数に対する割合でしきい値を指定
✓割合指定により、サービスのスケールに応じた相対的なしきい値設定が可能
🔢 障害カウントモデルの選択
✓連続（consecutive）モデル: 正常なタスクが起動するとカウンターがリセットされる
✓累積（cumulative）モデル: デプロイ全体を通じて障害数が加算され続ける
✓アプリの起動特性に応じて、より適切なカウント方式を選択
🎯 環境やアプリごとの最適化
✓開発・テスト環境では低いしきい値で素早いロールバックを実現
✓起動時に想定される障害があるアプリには、より高い許容度を設定
✓新規・既存の ECS サービスの両方に対して設定可能

🔧 技術仕様

デプロイサーキットブレーカーの設定項目

項目詳細
しきい値の指定方法固定のタスク障害数、または希望タスク数に対する割合
カウントモデル連続（consecutive）モデル、または累積（cumulative）モデル
適用対象新規および既存の ECS サービス
ロールバック動作しきい値到達時に直近の成功デプロイへ自動ロールバック

連続モデル と 累積モデル の違い

連続 consecutive

カウント動作: 正常なタスクが起動するとカウンターがリセットされる

適したケース: 起動時に一時的な障害が発生してから安定するアプリケーション

累積 cumulative

カウント動作: デプロイ全体を通じて障害数が加算され続ける

適したケース: 障害の総数を厳格に管理したいケース

設定例（有効化設定）

JSON deploymentConfiguration 
{
  "deploymentConfiguration": {
    "deploymentCircuitBreaker": {
      "enable": true,
      "rollback": true
    }
  }
}

上記は既存の有効化設定の例です。しきい値やカウントモデルの詳細なパラメータ名は、ECS デプロイサーキットブレーカーのドキュメントを参照してください。

⚙️ 設定方法

前提条件: ECS サービスが作成済み（または新規作成）／デプロイサーキットブレーカーを有効化／Console・CLI・SDK・CloudFormation・CDK・Terraform のいずれかが利用可能。

1
対象サービスとデプロイ要件の確認
アプリの起動特性（一時障害の有無）、開発／本番の区別を整理し、適切なしきい値とカウントモデルを決定します。
2
デプロイサーキットブレーカー設定の適用
現在の設定を確認し、create-service / update-service でしきい値・カウントモデルを適用します。
3
デプロイの実行と挙動の確認
しきい値到達時に想定どおりロールバックが動作するかを検証。開発環境で確認してから本番環境へ展開することを推奨します。
Bash サービス設定の確認例 
# ECS サービスの設定を確認する例
aws ecs describe-services \
  --cluster my-cluster \
  --services my-service

💡 ユースケース

1. 開発環境での高速ロールバック

開発・テスト環境で、デプロイに問題があった場合に素早くロールバックし開発サイクルを短縮したい。

しきい値: 固定のタスク障害数（低い値） カウント: 累積 cumulative
効果: 少数の障害でも即座にロールバックが発生し、問題のあるデプロイに開発チームが早期に気づける。
2. 起動時に一時的な障害があるアプリケーション

起動直後に一時的な障害が発生し、その後安定するアプリで、正常起動を待ってから判断したい。

しきい値: 希望タスク数に対する割合 カウント: 連続 consecutive
効果: 正常なタスクが起動するたびにカウンターがリセットされ、一時的な起動障害による不要なロールバックを回避。
3. 大規模サービスでのスケールに応じたしきい値

希望タスク数が変動する大規模サービスで、常に一定の割合の障害を許容範囲としたい。

しきい値: 希望タスク数に対する割合 カウント: 累積 cumulative
効果: スケールに応じてしきい値が相対的に調整され、タスク数が変わっても一貫したロールバック基準を維持。

🎁 メリット

💼 ビジネス面
✓リリースリスクの低減: 問題のあるデプロイを早期に検出し自動ロールバック
✓運用効率の向上: 手動でのロールバック判断が不要になり運用負荷を軽減
✓サービス品質の維持: 本番環境での障害の影響範囲を最小化
🔩 技術面
✓柔軟なしきい値設定: 固定数と割合の 2 通りでスケールに応じた設定
✓アプリ特性への適合: 連続／累積モデルで起動挙動に合わせた制御
✓幅広いツール対応: Console・CLI・SDK・CloudFormation・CDK・Terraform

⚠️ デメリット・制約事項

🚫 制限事項
▲デプロイサーキットブレーカーを有効化していないサービスでは、しきい値設定は機能しない
▲設定が不適切だと、意図しないロールバックや、逆にロールバックの遅延が発生する可能性がある
🧭 考慮すべき点
▲起動特性を正しく把握したうえで、連続／累積モデルのどちらを選ぶか慎重に検討
▲割合指定の場合、希望タスク数の変更に伴いロールバック発生条件も変化する点に注意

💰 料金・利用可能リージョン

💰 料金

本機能はデプロイサーキットブレーカーの設定オプションの拡張であり、この機能自体に追加料金は発生しません。ECS の利用料金は起動タイプ（AWS Fargate または Amazon EC2）に応じた通常の料金体系に従います。

🌐 利用可能リージョン

Amazon ECS が利用可能なすべての AWS リージョンで利用できます。

🔗 関連サービス・機能

  • ▸AWS Fargate: サーバーレスでコンテナを実行する起動タイプ。本機能と組み合わせて利用可能。
  • ▸AWS CloudFormation / CDK / Terraform: Infrastructure as Code でサーキットブレーカー設定を管理。
  • ▸Amazon CloudWatch: デプロイやタスクの状態を監視し、ロールバック発生状況を可視化。

📝 まとめ

デプロイサーキットブレーカーを、しきい値の指定方法（固定数／割合）とカウントモデル（連続／累積）の観点でカスタマイズ可能に。

開発環境から本番環境まで、また多様な起動特性を持つアプリケーションに対して最適な自動ロールバック挙動を設定できます。 ECS でコンテナサービスを運用しているチームは、対象サービスの特性を確認し、環境ごとに適切なサーキットブレーカー設定を見直すことを推奨します。
