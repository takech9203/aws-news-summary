Amazon RDS for SQL Server

🗄️ 1 インスタンスあたり最大 500 データベースをサポート

📅 リリース日: 2026 年 11 月 24 日 | データベース数上限が 100 → 500 に拡大

📋 概要

Amazon RDS for SQL Server が、1 つの DB インスタンスあたり最大 500 データベースをサポートするようになりました。従来の上限 100 から 5 倍に拡大され、4 vCPU 以上の DB インスタンス (xlarge 以上、バースト可能インスタンスクラスを除く) で、RDS がサポートするすべての SQL Server バージョンにて利用できます。

テナントごとにデータベースを分離する SaaS プロバイダーやマルチテナントアプリケーションの運用者にとって特に有益で、データベースの集約により管理の簡素化、監視・パッチ適用対象の削減、SQL Server ライセンスコストとインフラコストの低減が期待できます。

❌ Before: 上限 100 データベース

  • インスタンス数の増加に伴い、監視・パッチ適用・バックアップ管理などの運用負荷が増大
  • インスタンスごとに SQL Server ライセンス費用とインフラ費用が発生し、コスト増につながっていた
✅ After: 上限 500 データベース
  • 従来 5 台前後に分散していたデータベース群を 1 台に集約可能に
  • 監視・パッチ適用の対象インスタンス数が減り、運用管理が簡素化
  • インスタンス集約により SQL Server ライセンスコストとインフラコストを削減

従来は 500 データベースを運用するために 5 台の DB インスタンスが必要でしたが、今回のアップデートにより xlarge 以上の 1 台の DB インスタンスに集約できます。

⚡ 主要機能

📈 1. データベース数上限の 5 倍への拡大
✓1 DB インスタンスあたりの上限が 100 から 500 に拡大
✓RDS がサポートするすべての SQL Server バージョンで利用可能
✓追加の設定や有効化作業は不要、対象構成であれば新しい上限が自動適用
🧩 2. 幅広いエディションとデプロイ構成のサポート
✓Single-AZ: Enterprise、Enterprise Developer、Standard、Standard Developer、Web の各エディションでサポート
✓Multi-AZ: Always On 可用性グループを使用する Enterprise / Enterprise Developer エディションと、Web エディションでサポート
🎯 3. 対象インスタンスクラスの明確な要件
✓4 vCPU 以上の DB インスタンス (xlarge 以上) が対象
✗バースト可能インスタンスクラス (db.t 系) は対象外
⚠️対象外の構成には従来の上限が引き続き適用される

🛠️ 設定方法

✅ 前提条件

✓DB インスタンスが xlarge 以上 (4 vCPU 以上、バースト可能インスタンスクラス以外) であること
✓利用するエディションとデプロイ構成 (Single-AZ / Multi-AZ) が新しい上限の対象であること
✓Multi-AZ で 500 DB を利用する場合は、Always On 可用性グループを使用する Enterprise / Enterprise Developer エディション、または Web エディションであること
1
現在のインスタンスクラスとエンジン情報を確認する
Bash インスタンス情報の確認 
aws rds describe-db-instances \
  --db-instance-identifier my-sqlserver-instance \
  --query "DBInstances[0].{Class:DBInstanceClass,Engine:Engine,MultiAZ:MultiAZ}"

インスタンスクラス、エンジン (エディション)、Multi-AZ 設定を確認します。インスタンスクラスが xlarge 以上であれば新しい上限の対象です。

2
必要に応じてインスタンスクラスを変更する
Bash xlarge 以上への変更 
aws rds modify-db-instance \
  --db-instance-identifier my-sqlserver-instance \
  --db-instance-class db.m6i.xlarge \
  --apply-immediately

large 以下またはバースト可能インスタンスクラスの場合に、xlarge 以上へ変更します。変更時には再起動が発生するため、メンテナンスウィンドウの利用も検討してください。

3
データベースを作成して集約する
SQL データベースの作成 
-- SQL Server クライアントから接続してデータベースを作成
CREATE DATABASE tenant_101;
CREATE DATABASE tenant_102;
-- 最大 500 データベースまで作成可能

対象構成のインスタンスでは、追加設定なしで最大 500 データベースまで作成できます。既存の複数インスタンスからの集約には、ネイティブバックアップ / リストア機能などを使用してデータベースを移行します。

💡 メリット

💼 ビジネス面

✓ライセンスコストの削減: DB インスタンス数を減らすことで、SQL Server ライセンス費用を抑えられる
✓インフラストラクチャコストの削減: インスタンス集約により、コンピューティングリソースの総量と費用を最適化できる
✓SaaS ビジネスのスケーラビリティ向上: テナントごとの DB 分離モデルを維持したまま、1 インスタンスあたり 5 倍のテナントを収容できる

⚙️ 技術面

✓運用管理の簡素化: 監視、パッチ適用、バックアップなどの運用対象インスタンス数が削減される
✓追加設定が不要: 対象構成であれば自動的に新しい上限が適用され、有効化作業や移行作業は発生しない
✓幅広い構成のサポート: Single-AZ は主要 5 エディション、Multi-AZ も Always On 可用性グループ構成などでサポート

⚠️ デメリット・制約事項

🚫 制限事項

✗xlarge 未満のインスタンスおよびバースト可能インスタンスクラスでは、従来の上限が引き続き適用される
✗Database Mirroring を使用した Multi-AZ 構成は新しい上限の対象外
✗Standard エディションの Multi-AZ 構成は新しい上限の対象外

🤔 考慮すべき点

⚠️集約により 1 インスタンス障害時の影響範囲 (ブラストラディウス) が大きくなるため、Multi-AZ 構成やバックアップ戦略の見直しが重要
⚠️多数のデータベースを集約する場合、CPU、メモリ、IOPS などのリソース競合を考慮したインスタンスサイズとストレージ設定が必要
⚠️テナント間のパフォーマンス干渉 (ノイジーネイバー問題) への対策として、リソース使用状況の監視を強化することが望ましい

🎯 ユースケース

🏢 ユースケース 1: SaaS プロバイダーのテナント DB 集約

シナリオ: テナントごとに独立したデータベースを提供する SaaS プロバイダーが、400 テナントを 4 台の DB インスタンスで運用している。

1.集約先となる xlarge 以上のインスタンスを準備 (例: db.m6i.2xlarge)
2.ネイティブバックアップ / リストアで各テナント DB を集約先へ移行
3.アプリケーションの接続文字列を集約先インスタンスへ更新
4.旧インスタンスを削除
✨ 効果: 4 台のインスタンスを 1 台に集約し、ライセンス費用・インフラ費用・運用負荷を削減。さらに 100 テナント分の増加余地を確保。
🗂️ ユースケース 2: 部門別データベースの統合管理

シナリオ: 企業内で部門ごと・アプリケーションごとに小規模な SQL Server データベースが乱立し、複数の RDS インスタンスに分散している。

1.現在の各インスタンスのデータベース数とリソース使用率を棚卸し
2.統合先インスタンス (Enterprise エディション、Multi-AZ、Always On 可用性グループ) を設計
3.部門 DB を段階的に統合先へ移行し、監視を一元化
✨ 効果: パッチ適用やバックアップ管理の対象が一元化され、ガバナンスと運用効率が向上。
🧪 ユースケース 3: 開発・テスト環境の集約

シナリオ: 開発者ごと・ブランチごとにテスト用データベースを払い出しており、上限 100 に達するたびにインスタンスを追加していた。

1.開発用インスタンスを xlarge 以上 (Developer エディション) に統一
2.CI/CD パイプラインから 1 インスタンス上にテスト DB を動的に作成・削除
3.不要になった追加インスタンスを削減
✨ 効果: 開発・テスト環境のインスタンス数を削減し、コストを抑えながら最大 500 の一時 DB を柔軟に払い出し可能。

💰 料金

今回のアップデートによる追加料金はありません。上限の拡大は対象構成の DB インスタンスに自動的に適用され、料金は従来どおりインスタンスクラス、ストレージ、ライセンスモデル (ライセンス込み / BYOL) などに基づく Amazon RDS for SQL Server の標準料金体系が適用されます。

むしろ、複数インスタンスを 1 台に集約することで、インスタンス費用とライセンス費用の削減が期待できます。たとえば 500 データベースの運用に従来 5 台のインスタンスが必要だった場合、適切なサイズの 1 台に集約することで総コストを下げられる可能性があります。詳細は Amazon RDS for SQL Server の料金ページ を参照してください。

🌍 利用可能リージョン

Amazon RDS for SQL Server が利用可能なすべての AWS リージョンで利用できます。

🔗 関連サービス・機能

🛡️ Amazon RDS Multi-AZ 配置

Always On 可用性グループを使用する Multi-AZ 構成では、Enterprise / Enterprise Developer エディションで 500 データベースをサポート。集約後の可用性確保に重要。

📊 Amazon CloudWatch / Performance Insights

多数のデータベースを集約したインスタンスのリソース使用状況やパフォーマンスの監視に活用。

💾 RDS ネイティブバックアップ / リストア

既存インスタンスから集約先インスタンスへのデータベース移行手段として利用可能。

📝 まとめ

Amazon RDS for SQL Server の 1 インスタンスあたりのデータベース数上限が 100 から 500 に拡大され、SaaS プロバイダーやマルチテナントアプリケーションのデータベース集約が大幅に容易になりました。追加料金や設定作業は不要で、xlarge 以上の対象構成であれば自動的に適用されます。

複数の SQL Server インスタンスを運用している場合は、集約によるライセンス・インフラコスト削減と運用簡素化の効果を試算し、Multi-AZ 構成や監視体制とあわせて集約計画を検討することをお勧めします。
