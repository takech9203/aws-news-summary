☁️ AWS Parallel Computing Service

💰 Split Cost Allocation Data 対応で
Slurm ジョブ単位のコスト可視化を実現

📅 リリース日: 2026 年 11 月 23 日 | 🏷️ 分割コスト配分データによるジョブレベルのコスト分析

📋 概要

AWS Parallel Computing Service (PCS) が、AWS Cost and Usage Reports (CUR) における Split Cost Allocation Data (分割コスト配分データ) に対応しました。 PCS クラスター上で実行される Slurm ジョブ単位での詳細なコスト可視化が可能になり、 ジョブごとのコスト分析、最適化、チャージバック (費用の按分請求) を実現できます。

Slurm ジョブが分割対象のサブリソース、EC2 インスタンスが親リソースとなり、各ジョブがインスタンス上で要求した CPU、メモリ、GPU リソースに基づいてジョブレベルのコストが生成されます。 HPC クラスターを複数チームで共有する研究機関や製造業など、利用部門ごとに正確なコスト配分を求める組織にとって重要な機能強化です。

❌ Before: アップデート前の課題
  • CUR では EC2 インスタンスレベルのコストしか把握できず、同一インスタンス上の複数 Slurm ジョブへのコスト配分ができなかった
  • チームやプロジェクト単位のチャージバックには、Slurm アカウンティングデータと AWS 請求データを突き合わせる独自の仕組みが必要だった
  • アイドル状態のコアやノードなど、未使用キャパシティのコストを定量的に把握することが困難だった
✅ After: アップデート後の改善
  • Slurm ジョブが要求した CPU、メモリ、GPU に基づき、ジョブ単位のコストが CUR に自動記録されるようになった
  • ジョブ、ユーザー、Slurm アカウント、キュー、コンピュートノードグループ、ノード、クラスターの各単位で集計し、チャージバックが可能になった
  • 未配分キャパシティを特定でき、クラスターの適正サイジングと非効率の削減に活用できるようになった

共有 EC2 インスタンス上で実行される各 Slurm ジョブの要求リソース (CPU、メモリ、GPU) に基づき、 インスタンスのコストがジョブ単位の明細行として CUR に分割記録され、チームごとのチャージバックや未使用コストの分析に利用できます。

⚡ 主要機能

1️⃣ ジョブレベルのコスト可視化

各 Slurm ジョブが要求した EC2 の CPU、メモリ、GPU リソースに基づいてコストを配分。 インスタンスの償却コストとジョブのリソース要求割合からジョブ単位のコストを算出し、 ジョブ、ユーザー、Slurm アカウント、キュー、コンピュートノードグループ、ノード、クラスターの各単位で集計できます。

2️⃣ コスト配分タグの自動有効化

オプトインすると、PCS が Slurm ジョブの属性をコスト配分タグとして自動的に有効化。 タグはデフォルトで有効化され、CUR での分析にそのまま利用可能 (過去に無効化したタグキーがある場合はその設定が維持される)。

3️⃣ 未使用キャパシティの特定

どのジョブにも配分されなかったコスト (アイドルコアや作業待ちのノードなど) を未使用コストとして記録。 クラスターの適正サイジングや非効率の削減に活用できます。

4️⃣ GPU を含むアクセラレーテッドコンピューティング対応

ジョブが gpu ジェネリックリソース (GRES) として要求した GPU のコストを配分。 GPU 搭載インスタンスではアクセラレーター、CPU、メモリの 3 種類の使用レコードを時間単位で生成します。

🔧 技術仕様

🏷️ 自動有効化されるコスト配分タグ

タグキー内容
aws:pcs:cluster-nameAWS PCS クラスターの ID
aws:pcs:slurm-accountジョブを実行した Slurm アカウント (組織、グループ、プロジェクトなど。AWS アカウントではない)
aws:pcs:slurm-job-idSlurm ジョブ ID
aws:pcs:usernameジョブを送信したユーザー
aws:pcs:queueジョブを実行したキュー (Slurm パーティション)
aws:pcs:compute-node-groupインスタンスを提供したコンピュートノードグループ
aws:pcs:node-nameジョブを実行した Slurm ノード名

📈 コストデータの挙動

項目詳細
コスト算出基準ジョブが要求したリソースに基づく (splitLineItem/ActualUsage 列は PCS では空)
サスペンド時間ジョブのサスペンド中の時間は課金対象外
対象期間2026 年 11 月 17 日以降の使用分をカバー (それ以前から実行中のジョブは同日から課金記録)
最小ジョブ時間最小ジョブ実行時間の制限なし
明細行の増加量ジョブごと・インスタンスごとに 1 時間あたり 2 レコード (GPU 等のアクセラレーテッドインスタンスでは 3 レコード) を追加

🧮 CUR 明細行数の見積もり式

Text 1 日あたりの明細行数の見積もり 
# 通常のインスタンスの場合 (1 日あたり)
(ジョブ数 × ジョブあたり平均インスタンス数 × 平均ジョブ実行時間 × 2) × 24

# アクセラレーテッドコンピューティングインスタンスの場合 (1 日あたり)
(ジョブ数 × ジョブあたり平均インスタンス数 × 平均ジョブ実行時間 × 3) × 24

🛠️ 設定方法

✅ 前提条件

✓AWS PCS クラスターが Slurm バージョン 25.11 以降で稼働していること
✓AWS Billing and Cost Management へのアクセス権限があること
✓CUR (レガシー CUR または CUR 2.0 エクスポート) を利用できること

📝 手順

1
Split Cost Allocation Data へのオプトイン

Billing and Cost Management コンソールの [Cost Management preferences] で、AWS PCS の Split Cost Allocation Data を有効化します。

2
CUR への分割コスト配分データの追加

新規または既存の CUR レポート (またはデータエクスポート) の設定で、Split Cost Allocation Data を含めるように構成します。 これにより、ジョブ単位の分割明細行がレポートに出力されるようになります。

3
レポートの確認と分析

出力された CUR で splitLineItem 列と aws:pcs:* タグを使用してジョブ単位のコストを分析します。 Amazon Athena や Amazon QuickSight と組み合わせることで、チームやプロジェクト単位のダッシュボードを構築できます。

💡 メリット

📊 ビジネス面

✓正確なチャージバック: 共有 HPC クラスターのコストを、実際のリソース要求量に基づいてチームやプロジェクトに公平に配分できる
✓コスト最適化の推進: 未使用キャパシティのコストが定量化されるため、クラスターの適正サイジングの判断材料になる
✓説明責任の向上: ユーザーや Slurm アカウント単位でコストを可視化することで、利用部門のコスト意識を高められる

⚙️ 技術面

✓独自ツールが不要: Slurm アカウンティングと AWS 請求データを突き合わせる独自のコスト配分システムを構築・運用する必要がなくなる
✓タグの自動有効化: オプトインするだけで 7 種類の Slurm ジョブ属性タグが自動的に有効化され、追加の設定なしで分析に利用できる
✓GPU コストの配分: gpu GRES として要求された GPU のコストもジョブ単位で配分され、AI/ML や計算集約型ワークロードのコスト追跡が可能

⚠️ デメリット・制約事項

🚫 制限事項

以下の状況では、該当インスタンスのその時間帯の分割コスト配分データは生成されず、 EC2 インスタンスのコストがジョブ単位に分割されずにそのまま CUR に記録されます。

✗ジョブ実行中にコンピュートノードグループの MemSpecLimit、CpuSpecList、RealMemory を変更した場合
✗サスペンドされたジョブが、他のジョブが使用中の CPU 上で再開された場合
✗OverSubscribe=YES の Slurm パーティションで --oversubscribe オプションを使用したジョブがインスタンスの保有量を超えるリソースを要求した場合 (オーバーサブスクリプションは OverSubscribe=FORCE のパーティションのみサポート)

以下の GPU 構成では分割コスト配分データ自体は生成されますが、GPU コストは未使用コストとして記録されます。

✗Multi-Instance GPU (MIG) は未サポート: いずれかの GPU で MIG が有効なインスタンスでは、そのインスタンスの全 GPU コストが未使用コストとして表示される
✗GPU 共有は未サポート: Slurm の shard や mps リソースで共有される GPU は未使用コストとして表示される

🤔 考慮すべき点

⚠️Slurm 25.11 以降が必須のため、既存クラスターではスケジューラーのバージョンアップが必要になる場合がある
⚠️コストは実際の使用量ではなく要求量ベースで配分されるため、ジョブのリソース要求が過大な場合はそのままコストに反映される (リソース要求の適正化が重要)
⚠️ジョブ数が多い大規模クラスターでは CUR の明細行数が大幅に増加するため、Athena などでのクエリコストやデータ量に留意が必要
⚠️AWS GovCloud (US) リージョンでは利用不可

🎯 ユースケース

🏢 ユースケース 1: 研究部門ごとのチャージバック

シナリオ: 複数の研究チームが共有する PCS クラスターで、各チームの実際のリソース消費に応じてコストを配分したい。

SQL Athena での CUR クエリ例: Slurm アカウント別の月次コスト集計 
SELECT
  resource_tags['aws:pcs:slurm-account'] AS slurm_account,
  SUM(CAST(split_line_item_split_cost AS DOUBLE)) AS allocated_cost
FROM cur_table
WHERE bill_billing_period_start_date = DATE '2026-12-01'
  AND split_line_item_split_cost IS NOT NULL
GROUP BY resource_tags['aws:pcs:slurm-account']
ORDER BY allocated_cost DESC;
✅ 効果: Slurm アカウント (研究チーム) 単位の正確なコストを自動的に算出でき、手作業による按分計算が不要になる。
🤖 ユースケース 2: GPU ワークロードのコスト追跡

シナリオ: AI/ML トレーニングジョブが GPU インスタンスをどの程度効率的に使用しているかを把握し、高額な GPU コストを最適化したい。

Bash ジョブ送信時に GPU を GRES として明示的に要求 
# 分割コスト配分の対象にするには gpu GRES としての要求が必要
sbatch --gres=gpu:4 --partition=gpu-queue train_model.sh
✅ 効果: ジョブ単位の GPU コストと未使用 GPU コストが可視化され、GPU 要求数の適正化やキュー設計の見直しに役立つ。
📐 ユースケース 3: クラスターの適正サイジング

シナリオ: 静的なコンピュートノードグループを運用しており、アイドルリソースによる無駄なコストを削減したい。

SQL Athena での CUR クエリ例: ノードグループ別の未使用コスト集計 
SELECT
  resource_tags['aws:pcs:compute-node-group'] AS node_group,
  SUM(CAST(split_line_item_unused_cost AS DOUBLE)) AS unused_cost
FROM cur_table
WHERE bill_billing_period_start_date = DATE '2026-12-01'
GROUP BY resource_tags['aws:pcs:compute-node-group']
ORDER BY unused_cost DESC;
✅ 効果: 未使用コストが大きいノードグループを特定し、スケーリング設定やインスタンスサイズの見直しによってクラスター全体の費用対効果を改善できる。

💵 料金と利用可能リージョン

💰 料金

公式発表に Split Cost Allocation Data の有効化に伴う追加料金の記載はありません。 CUR 自体の利用では、レポートを保存する Amazon S3 のストレージ料金が発生します。

⚠️ 分割コスト配分データを有効にするとジョブ数に応じて CUR の明細行数が増加するため、 Athena クエリなど下流の分析コストへの影響を考慮してください。

🌍 利用可能リージョン

✓AWS PCS が利用可能なすべての AWS 商用リージョンで利用可能
✗AWS GovCloud (US) リージョンは対象外

🔗 関連サービス・機能

📋 AWS Cost and Usage Reports (CUR)

分割コスト配分データの出力先。レガシー CUR と CUR 2.0 エクスポートの両方に対応。

🐳 Amazon ECS / Amazon EKS

同じ Split Cost Allocation Data の仕組みで、タスク単位・ポッド単位のコスト配分に対応済み。PCS はこれに続く対応。

📊 Amazon Athena / Amazon QuickSight

CUR データのクエリと可視化に利用し、チャージバックレポートやダッシュボードを構築可能。

💳 AWS Billing and Cost Management

Cost Management preferences からのオプトインと、コスト配分タグの管理を実施。

📝 まとめ

AWS PCS の Split Cost Allocation Data 対応により、共有 HPC クラスターのコストを Slurm ジョブ単位で可視化し、チームやプロジェクトへの正確なチャージバックと 未使用キャパシティの特定が可能になりました。

複数部門で PCS クラスターを共有している組織は、Slurm 25.11 以降へのアップグレードを確認のうえ、 Cost Management preferences でのオプトインと CUR への分割コスト配分データの追加を検討することを推奨します。
