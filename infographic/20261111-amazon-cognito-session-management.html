🔐 ユーザープールセッション管理

User Pool Session Management — セッションの可視化・個別失効・上限制御がマネージド API に
📅 リリース日: 2026 年 11 月 11 日

Amazon Cognito がユーザープールのセッション管理機能をサポート。全デバイス・全アプリクライアントにわたる SSO セッションとトークンセッションを一覧表示し、任意のセッションをオンデマンドで失効できるようになりました。従来 1 時間固定だった SSO セッションの再利用期間も、アプリクライアントごとに設定可能になります。

📌 概要 — Before / After

Cognito ユーザープールには 2 種類のセッションがあります。マネージドログイン経由のサインインで作成され、他のアプリクライアントへの再認証なしのアクセスを可能にする SSO セッションと、アプリクライアントへのサインインとトークン発行時に作成される トークンセッションです。

❌ アップデート前の課題

✗どのデバイス・アプリクライアントでアクティブなセッションを保持しているか確認する手段がなかった
✗特定セッションのみの失効は不可。GlobalSignOut による全セッション一括サインアウトか RevokeToken に限られていた
✗SSO セッションの再利用期間が 1 時間に固定で、アプリクライアントごとに調整できなかった
✗ユーザーごとのアクティブセッション数を制限する仕組みがなかった

✅ アップデート後の改善

✓ListUserSessions / AdminListUserSessions で全デバイス・全アプリクライアントのアクティブセッションを一覧表示
✓RevokeUserSession / AdminRevokeUserSession でセッション ID 指定の個別失効。リンクされたセッションへのカスケード失効も選択可能
✓SSO セッション再利用期間をアプリクライアントごとに 0 分〜129,600 分 (90 日) で設定可能
✓ユーザーごとのトークンセッション数上限を設定可能 (デフォルト 20、最大 100)

マネージドログインで作成された SSO セッションを起点に、アプリクライアントごとのトークンセッションが作成されます。ユーザーと管理者はセッション管理 API を通じて、これらのセッションの一覧表示と失効を実行できます。

⚡ 主要機能

📋 1. セッションの一覧表示

ListUserSessions (ユーザー自身、アクセストークンで認可) / AdminListUserSessions (管理者、IAM 認証情報)。全アプリクライアントにわたるセッションを最大 125 件の単一ページで返却。アクティブなセッションのみ返され、失効済み・期限切れは含まれない。

🚫 2. セッションの失効

RevokeUserSession / AdminRevokeUserSession でセッション ID 指定の失効。RevokeAssociatedSessions パラメータ (NONE / LINKED) でカスケード失効を制御。トークンセッションに LINKED を指定すると親の SSO セッションも失効、SSO セッションに指定すると配下のトークンセッションも失効。セッション追跡が有効なら GlobalSignOut / AdminUserGlobalSignOut は全セッションを自動失効。

⏱️ 3. SSO セッション再利用期間のアプリクライアントごとの設定

SetUserPoolClientSessionConfiguration で SSOSession.MaxValidityMinutes を 0 分〜129,600 分 (90 日) で設定 (デフォルト 60 分)。0 を指定すると SSO セッションを再利用せず常に再サインインを要求。適用されるのは現在サインインしているアプリクライアントの設定値。

🔢 4. アクティブセッション数の上限設定

SetUserPoolSessionConfiguration の TokenSession.MaxPerUser でプールレベルの上限を設定 (デフォルト 20、最大 100)。上限到達後のサインインは拒否されず、最も長く未使用のセッションが自動失効 (TERMINATE_LEAST_RECENTLY_USED 方式)。SSO セッションはユーザーごとに最大 10 で固定。

🪪 5. sid クレームの追加

セッション追跡を有効にすると、ID トークンとアクセストークンに sid クレーム (セッション識別子) が追加される。OpenID Connect 標準のセッション ID クレーム名に準拠し、同一セッション内のトークン更新・ローテーションを通じて不変。

ステップ 1: セッション追跡の有効化

Bashプールレベルでセッション追跡を有効化
aws cognito-idp set-user-pool-session-configuration \
  --user-pool-id us-east-1_aBcDeFgHi \
  --user-session-tracking ENABLED \
  --token-session '{"MaxPerUser": 20}'

セッション追跡はデフォルトで無効のため、明示的なオプトインが必要です。トークンセッション数の上限を 20 に設定しています。

ステップ 2: アプリクライアントごとの SSO セッション有効期間の設定

BashSSO セッション再利用期間を 30 日に設定
aws cognito-idp set-user-pool-client-session-configuration \
  --user-pool-id us-east-1_aBcDeFgHi \
  --client-id 1example23456789 \
  --sso-session '{"MaxValidityMinutes": 43200}'

指定したアプリクライアントが SSO セッションを再利用できる期間を 43,200 分 (30 日) に設定します。この期間内は再サインインなしで新しいトークンを取得できます。

ステップ 3: セッションの一覧表示と失効

Bash管理者によるセッション一覧の取得とカスケード失効
# 管理者としてユーザーのセッションを一覧表示
aws cognito-idp admin-list-user-sessions \
  --user-pool-id us-east-1_aBcDeFgHi \
  --username example-user

# 特定のセッションをリンクされたセッションごと失効
aws cognito-idp admin-revoke-user-session \
  --user-pool-id us-east-1_aBcDeFgHi \
  --username example-user \
  --session-id sso1234567890abcdefghijklmnop \
  --revoke-associated-sessions LINKED

1 つ目のコマンドで全アクティブセッションを取得し、2 つ目のコマンドで SSO セッションとその配下のトークンセッションをまとめて失効します。

⚖️ メリットと制約事項

💼 ビジネス面のメリット

✓セキュリティインシデントへの迅速な対応: 特定のデバイスやアプリのセッションだけを選択的に失効でき、ユーザー全体への影響を最小化
✓エンドユーザー体験の向上: 「ログイン中のデバイス一覧」「他のデバイスからサインアウト」を自社アプリに実装可能
✓コンプライアンス対応: セッション可視化と同時接続数の制御でセキュリティ要件に対応しやすく

🔩 技術面のメリット

✓独自実装の削減: セッションストアの自前構築が不要に
✓柔軟な SSO 制御: 再利用期間を 0 分 (常に再認証) から 90 日まで調整可能
✓標準準拠の sid クレーム: アプリ側でのセッション相関が容易に
✓CloudFormation 対応: セッション設定を IaC として管理可能

⚠️ 制限事項

✗Essentials または Plus プランが必要。Lite プランでは利用不可、セッション追跡を有効にしたまま Lite へのダウングレードも不可
✗セッション一覧は最大 125 セッションの単一ページで返却
✗SSO セッションの上限はユーザーごとに 10 で固定、変更不可
✗SSO セッションは最終の新規認証から 90 日で必ず失効し、サイレントな再利用では延長されない
✗マシンツーマシン (クライアントクレデンシャル) のトークンはセッションとして追跡されない

💡 考慮すべき点

→セッション追跡はデフォルト無効。プールレベルでの明示的な有効化が必要
→Pre Token Generation トリガーで独自の sid クレームを追加している場合は競合するため、トリガーから削除が必要
→上限を現在のセッション数より低く変更しても即時には失効されず、次回サインイン時に LRU 方式で失効
→マルチリージョンユーザープールでは上限はリージョンごとに適用され、カウントは結果整合性。ほぼ同時のサインインで一時的に上限を超える可能性

🎯 ユースケース

📱 1. エンドユーザー向けのデバイス管理画面

シナリオ: コンシューマー向けアプリで、ユーザー自身がログイン中のデバイスを確認し、身に覚えのないセッションをサインアウトできる画面を提供したい。

実装例
1. アプリから ListUserSessions をアクセストークンで呼び出し、セッション一覧を取得
2. DeviceType、LastLocation、LastActiveDate を画面に表示
3. ユーザーが選択したセッションに対して RevokeUserSession を
   RevokeAssociatedSessions=LINKED で呼び出し
💡 効果: ユーザー自身による不正アクセスの発見と対処が可能になり、サポート問い合わせの削減とセキュリティ向上につながる。

🛡️ 2. 管理者による侵害アカウントへの対応

シナリオ: セキュリティチームが不審なサインインを検知し、該当ユーザーの特定デバイスのセッションのみを強制終了したい。

実装例
1. AdminListUserSessions で該当ユーザーの全セッションを取得
2. LastIPAddress や LastLocation から不審なセッションを特定
3. AdminRevokeUserSession で該当セッションを失効
4. 全デバイスからのサインアウトが必要な場合は AdminUserGlobalSignOut を実行
💡 効果: 正常なセッションを維持したまま侵害が疑われるセッションのみを失効でき、ユーザーへの影響を最小限に抑えたインシデント対応が可能になる。

🔑 3. アプリクライアントごとの再認証ポリシー

シナリオ: 同一ユーザープール内で、一般向けポータルは 30 日間の SSO セッション再利用を許可し、決済管理などの機密性の高いアプリでは毎回再認証を要求したい。

実装例
# 一般向けポータル: 30 日間の再利用を許可
SetUserPoolClientSessionConfiguration
  ClientId: portal-client, SSOSession.MaxValidityMinutes: 43200

# 決済管理アプリ: 常に再認証を要求
SetUserPoolClientSessionConfiguration
  ClientId: payment-client, SSOSession.MaxValidityMinutes: 0
💡 効果: アプリケーションの機密度に応じた再認証ポリシーを単一のユーザープールで実現でき、利便性とセキュリティを両立できる。

📦 Cognito 機能プラン Lite / Essentials / Plus

セッション管理の利用には Essentials 以上のプランが必要。

独自の sid クレームを追加している場合はセッション追跡と競合するため注意が必要。

📝 まとめ

Amazon Cognito のセッション管理機能により、これまで自前実装が必要だったセッションの可視化・個別失効・同時セッション数制限がマネージドな API として利用できるようになりました。SSO セッションの再利用期間もアプリクライアントごとに調整可能になり、利便性とセキュリティのバランスを柔軟に設計できます。

Essentials または Plus プランのユーザープールを運用している場合は、セッション追跡の有効化と、デバイス管理画面やインシデント対応フローへの組み込みを検討することを推奨します。
