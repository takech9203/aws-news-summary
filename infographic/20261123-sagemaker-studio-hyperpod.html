Amazon SageMaker Studio SageMaker HyperPod 📅 2026 年 11 月 23 日

🖥️ SageMaker Studio が HyperPod クラスター向けジョブ送信・モデルデプロイに対応

kubectl 不要。Studio の UI から分散トレーニングジョブの送信、モデルデプロイ、ワークロードモニタリングが可能に

📋 概要

Amazon SageMaker Studio が、EKS オーケストレーションの SageMaker HyperPod クラスター向けのネイティブな開発者エクスペリエンスを提供するようになりました。データサイエンティストは、分散トレーニングジョブの送信、モデルのデプロイ、ワークロードのビジュアルなモニタリングを Studio の UI から直接実行できます。

SageMaker HyperPod は基盤モデルの大規模な分散トレーニングやファインチューニングのための専用インフラストラクチャですが、これまでは kubectl の知識や Kubernetes マニフェストの記述が必要でした。今回のアップデートにより、Kubernetes の専門知識がなくても HyperPod のワークロードを管理できるようになります。

❌ Before: アップデート前の課題

  • ジョブ実行に kubectl の操作スキルと Kubernetes マニフェスト (YAML) の記述が必要
  • コンピュート設定を毎回手動で入力する必要があり、ジョブ送信の手間が大きい
  • メトリクスやログの確認に複数ツールを行き来し、問題の診断に時間がかかる

✅ After: アップデート後の改善

  • ライブ YAML プレビュー付きのシングルページフォームから分散 PyTorch / Ray ジョブを送信
  • JumpStart、Amazon S3、Amazon FSx からのモデルデプロイが Studio の UI で完結
  • 再利用可能なリソースプリセットで手動のコンピュート入力が不要に
  • メトリクスとログが詳細ページに統合され、その場で問題を診断可能

SageMaker Studio のフォームから HyperPod クラスターへジョブ送信・モデルデプロイを行い、Prometheus と CloudWatch によるメトリクス・ログを Studio の詳細ページで確認できる構成

⚡ 主要機能

🏋️ 1. 分散トレーニングジョブの送信

  • 分散 PyTorch ジョブおよび Ray ジョブを Studio の UI から送信可能
  • ライブ YAML プレビュー付きのシングルページフォームで設定内容を確認しながら作成
  • kubectl や Kubernetes マニフェストの手書きが不要

🚀 2. モデルデプロイ

  • SageMaker JumpStart、Amazon S3、Amazon FSx をソースとしたモデルデプロイに対応
  • トレーニングと同様にシングルページフォームで設定が完結

⚙️ 3. コンピュート設定 (再利用可能なリソースプリセット)

  • コンピュートリソースの設定をプリセットとして保存・再利用できる
  • ジョブ送信のたびに手動でコンピュート情報を入力する必要がなくなる

📊 4. 統合されたオブザーバビリティ

  • メトリクスとログがジョブやデプロイの詳細ページに表示される
  • HyperPod Observability と Amazon Managed Service for Prometheus が基盤
  • Kubernetes のコンディション・イベント、CloudWatch ログ、埋め込みメトリクスをその場で確認でき、ツールを切り替えずに診断が可能

📋 5. タスクガバナンスの統合キュービュー

  • トレーニングと推論をまたいだ保留中タスクを一元的に表示
  • タスクの優先度クラスを Studio から調整可能

🛠️ 設定方法

前提条件

✓EKS オーケストレーションの SageMaker HyperPod クラスターが作成済みであること
✓Amazon SageMaker Studio のドメインとユーザープロファイルが設定済みであること
✓メトリクス・ログ表示を利用する場合、HyperPod Observability が有効化されていること

手順

1
SageMaker Studio にアクセスする

SageMaker コンソールから Studio を起動し、HyperPod クラスターのビューに移動。EKS オーケストレーションのクラスターが一覧に表示される。

2
トレーニングジョブを送信する

シングルページフォームで分散 PyTorch または Ray ジョブの設定を入力。保存済みのコンピュート設定 (プリセット) を選択でき、ライブ YAML プレビューで生成されるマニフェストを確認しながら送信。

3
モデルをデプロイする

JumpStart、Amazon S3、Amazon FSx のいずれかをモデルソースとして選択し、フォームからデプロイを実行。

4
ワークロードをモニタリングする

詳細ページで Kubernetes のコンディション・イベント、CloudWatch ログ、メトリクスを確認。統合キュービューで保留中タスクを確認し、必要に応じて優先度クラスを調整。

💡 メリット

💼 ビジネス面

✓生産性の向上: Kubernetes の学習コストなしに HyperPod を活用でき、モデル開発のリードタイムを短縮
✓チームの裾野拡大: kubectl を扱えないメンバーも大規模な分散トレーニング基盤を利用可能に
✓運用負荷の軽減: プラットフォームチームが個別のジョブ送信手順を整備する負担が減少

⚙️ 技術面

✓YAML プレビューによる透明性: 生成される YAML をリアルタイムで確認でき、高度なカスタマイズへの橋渡しに
✓リソースプリセットの再利用: コンピュート設定を標準化し、設定ミスを防止
✓統合された診断体験: Kubernetes イベント、CloudWatch ログ、Prometheus メトリクスを 1 つの画面で確認

⚠️ デメリット・制約事項

制限事項

✗EKS オーケストレーションの HyperPod クラスターのみが対象 (Slurm オーケストレーションのクラスターは対象外)
✗トレーニングジョブは分散 PyTorch と Ray に対応。その他のフレームワークはフォームからの送信対象として言及されていない

考慮すべき点

⚠️メトリクス・ログの統合表示には HyperPod Observability と Amazon Managed Service for Prometheus の構成が前提
⚠️高度な Kubernetes 設定が必要なワークロードでは、引き続き kubectl やマニフェストによる直接操作が必要になる場合がある

🎯 ユースケース

🧪 ユースケース 1: データサイエンティストによる基盤モデルのファインチューニング

シナリオ: Kubernetes の経験がないデータサイエンティストが、HyperPod クラスター上で LLM のファインチューニングを実行したい。

Text実装例
1. Studio の HyperPod ビューでトレーニングジョブ作成フォームを開く
2. 分散 PyTorch を選択し、コンテナイメージとスクリプトを指定
3. 保存済みのコンピュート設定プリセット (例: GPU ノード 8 台) を選択
4. ライブ YAML プレビューを確認してジョブを送信
✅ 効果: kubectl やマニフェスト作成なしで分散トレーニングを開始でき、開発着手までの時間を大幅に短縮できる。

🚀 ユースケース 2: JumpStart モデルの HyperPod クラスターへのデプロイ

シナリオ: 評価済みの公開基盤モデルを、自社の HyperPod クラスター上の推論環境として迅速に展開したい。

Text実装例
1. Studio のデプロイフォームでモデルソースに JumpStart を選択
2. デプロイ先の HyperPod クラスターとコンピュート設定を指定
3. フォームからデプロイを実行し、詳細ページでステータスとログを確認
✅ 効果: モデル取得からデプロイ、モニタリングまでを Studio 内で完結でき、推論環境の立ち上げが迅速になる。

📋 ユースケース 3: タスクガバナンスによるクラスターリソースの優先度管理

シナリオ: 複数チームが共有する HyperPod クラスターで、緊急度の高いトレーニングジョブを優先的に実行したい。

Text実装例
1. Studio の統合キュービューでトレーニングと推論をまたぐ保留中タスクを確認
2. 緊急度の高いタスクの優先度クラスを引き上げる
3. キューの消化状況を詳細ページのメトリクスで監視
✅ 効果: クラスター管理者に依頼することなく、ビジネス優先度に応じたリソース配分の調整が可能になる。

🔗 関連サービス・機能

→Amazon SageMaker HyperPod: 基盤モデルの大規模な分散トレーニング・ファインチューニング向けの専用インフラストラクチャ。本アップデートの操作対象

📝 まとめ

本アップデートにより、SageMaker HyperPod の強力な分散トレーニング・推論基盤を、Kubernetes の専門知識なしに SageMaker Studio から活用できるようになりました。kubectl 中心の運用がデータサイエンティストの障壁となっていた組織にとって、導入ハードルを大きく下げる重要な改善です。EKS オーケストレーションの HyperPod クラスターを運用しているチームは、Studio からのジョブ送信とモニタリング体験をぜひ試してみてください。
