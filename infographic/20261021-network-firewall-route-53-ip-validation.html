AWS Network Firewall Amazon Route 53 📅 2026 年 10 月 21 日

🔥 AWS Network Firewall が Route 53 Resolved IP Validation をサポート

宛先 IP の「出所」を DNS 解決結果で検証 — SSH / SFTP を含む全プロトコルにドメインベースのエグレス制御を拡張

📋 概要

AWS Network Firewall が、接続先 IP アドレスの「出所」を検証する新機能 Route 53 Resolved IP Validation (解決済み IP 検証) をサポートしました。 接続の宛先 IP アドレスが VPC の Amazon Route 53 VPC Resolver を通じて正規に DNS 解決されたものであることを検証し、 従来 HTTP/HTTPS に限定されていたドメインベースのトラフィックフィルタリングを、SFTP や SSH などを含む すべてのアウトバウンドトラフィックに拡張します。

従来のドメインリストルールはクライアントが「主張する」ホスト名 (TLS の SNI や HTTP の Host ヘッダー) に依存していたため、 SNI スプーフィングや DNS 解決を経ない直接 IP 接続によるルールバイパスという セキュリティギャップが存在していました。本機能は Route 53 Resolver DNS Firewall と連携した多層防御でこのギャップを解消します。 金融、ヘルスケア、公共部門などの厳格なエグレス制御や、DLP / C2 通信対策に重要なアップデートです。

全プロトコル
SSH / SFTP を含む全アウトバウンド通信にドメイン制御を拡張
追加料金なし
既存の Network Firewall + DNS Firewall 構成で利用可能

❌ Before: アップデート前の課題
  • ドメインフィルタリングは SNI / HTTP Host ヘッダーに依存し、SSH や SFTP などの非 HTTP/HTTPS プロトコルはドメイン名で制御できなかった
  • 許可済みドメインを SNI や Host ヘッダーに偽装して別 IP へ接続する SNI スプーフィングを防げなかった
  • DNS 解決を行わない直接 IP 指定の通信は許可リストをバイパスでき、C2 通信やデータ持ち出しのリスクが残っていた
✅ After: アップデート後の改善
  • 宛先 IP が Route 53 VPC Resolver で解決されたものかをポリシーレベルで検証し、直接 IP 接続を ALERT / DROP / REJECT で制御可能に
  • AWS_ROUTE_53_RESOLVED_DOMAIN ターゲットタイプや aws_route_53_resolved_domain Suricata キーワードで「どのドメインとして解決されたか」に基づくルールを記述可能に
  • 検証は IP レイヤーで実行されるため全プロトコルに適用され、SNI と解決済み IP の両方が一致する場合のみ許可する SNI スプーフィング対策も可能に

クライアントの DNS クエリは Route 53 VPC Resolver と DNS Firewall ルールグループを経由して解決され、その解決結果 (ドメインと IP の対応) が記録されます。 その後のアウトバウンド接続時に、Network Firewall が宛先 IP アドレスを解決済み IP と照合し、DNS 解決を経ていない宛先への接続を設定したアクション (ALERT / DROP / REJECT) で制御します。

⚙️ 主要機能

1️⃣ ポリシーレベルの Resolved IP Validation

ファイアウォールポリシーの設定として有効化し、宛先 IP が「いずれかのドメイン」として Route 53 VPC Resolver で解決されたものかを検証 (ドメイン非依存のチェック)。 検証失敗時のアクションは ALERT (ログに記録して通過) / DROP (サイレントにブロック) / REJECT (TCP リセット返送、TCP のみ) から選択。 検証対象の送信元 IP 範囲 (SourceIPRanges) や検証を免除する宛先 IP 範囲 (BypassDestinationValidationIPRanges) をそれぞれ最大 100 エントリまで指定できます。

2️⃣ ルールレベルの resolved-domain ルール

ポリシーレベルの検証を前提に、「特定のドメイン」として解決された IP への接続を許可 / 拒否するルールを記述可能。 ドメインリストのターゲットタイプ AWS_ROUTE_53_RESOLVED_DOMAIN、Suricata 互換ルールの aws_route_53_resolved_domain キーワード、 標準ステートフルルールのルールオプションの 3 通りで設定できます。検証は IP レイヤーで行われるため、プロトコルを問わず全アウトバウンドトラフィックに適用されます。

3️⃣ SNI スプーフィング対策

許可リストで AWS_ROUTE_53_RESOLVED_DOMAIN を TLS_SNI や HTTP_HOST と併用すると、 「SNI / Host ヘッダーがドメインに一致する」かつ「宛先 IP がそのドメインとして解決されている」の両条件を満たす場合のみトラフィックが許可されます。 Host ヘッダーに許可済みドメインを偽装しても、そのドメインとして解決されていない IP への接続は許可されません。

4️⃣ DNS 解決キャッシュと TTL の扱い

Network Firewall は DNS レコードの TTL より長く解決結果をキャッシュに保持するため、短い TTL だけが原因で接続が失敗することはありません。 キャッシュ期限切れ後もトラフィックが続く場合の動作は DNSExpiryExceptionPolicy (CONTINUE / DROP / REJECT) で制御できます。

5️⃣ Route 53 Resolver DNS Firewall との連携

検証に使用する DNS 解決情報は、ポリシーに指定した Route 53 Resolver DNS Firewall ルールグループに関連付けられた VPC の解決結果に基づきます。 DNS Firewall によるドメインクエリのフィルタリングと組み合わせることで、DNS レイヤーからネットワークレイヤーまでの一貫したドメインベースセキュリティを実現できます。

🔬 技術仕様

📐 ポリシーレベル設定 (Route53ResolvedIPValidation)

設定項目必須詳細
Action必須 検証失敗時のアクション。ALERT / DROP / REJECT。ALERT はロギングの有効化が必要。REJECT は TCP のみで、非 TCP トラフィックは DROP される
DNSFirewallRuleGroupId必須 検証に使用する Route 53 Resolver DNS Firewall ルールグループの ID (rslvr-frg- で始まる形式)。このルールグループに関連付けられた VPC の DNS 解決結果が検証に使用される
DNSExpiryExceptionPolicy必須 キャッシュ内の解決結果が期限切れになった IP へのトラフィックの扱い。CONTINUE (有効とみなす) / DROP / REJECT
SourceIPRanges任意 検証対象とする送信元 IP アドレス / CIDR 範囲 (最大 100 エントリ)。未指定時はファイアウォールの VPC CIDR 範囲が対象
BypassDestinationValidationIPRanges任意 ポリシーレベル検証を免除する宛先 IP アドレス / CIDR 範囲 (最大 100 エントリ)

📝 ルールレベルの記述方法

方法記述内容
ドメインリスト ターゲットタイプに AWS_ROUTE_53_RESOLVED_DOMAIN を追加 (TLS_SNI / HTTP_HOST と併用可)
Suricata 互換ルール aws_route_53_resolved_domain:"example.com"; キーワードを使用。ワイルドカードは先頭ドット (.example.com) で表現し、カンマ区切りで複数ドメインを指定可能
標準ステートフルルール ルールオプションにキーワード aws_route_53_resolved_domain とドメイン名を追加

💻 Suricata ルールの例

Suricata resolved-domain ルールの記述例 
# example.com として解決された IP へのトラフィックを全プロトコルでドロップ
drop ip $HOME_NET any -> $EXTERNAL_NET any (aws_route_53_resolved_domain:"example.com"; flow:to_server, established; sid:1;)

# example.com とそのサブドメインとして解決された IP への通信を許可
pass ip $HOME_NET any -> $EXTERNAL_NET any (aws_route_53_resolved_domain:".example.com"; flow:to_server, established; sid:2;)

# SNI と解決済み IP の両方が一致する場合のみ許可 (SNI スプーフィング対策)
pass tls $HOME_NET any -> $EXTERNAL_NET any (tls.sni; content:"example.com"; nocase; startswith; endswith; aws_route_53_resolved_domain:"example.com"; flow:to_server, established; sid:5;)

🛠️ 設定方法

✅ 前提条件

✓AWS Network Firewall がデプロイされ、アウトバウンドトラフィックがファイアウォールエンドポイントを経由するようにルートテーブルが構成されていること
✓Route 53 Resolver DNS Firewall ルールグループが作成され、保護対象の VPC に関連付けられていること
✓VPC 内のクライアントが DNS 解決に Route 53 VPC Resolver (AmazonProvidedDNS) を使用していること
✓ALERT アクションを使用する場合は、ファイアウォールのロギングが有効化されていること
1
DNS Firewall ルールグループの作成と VPC への関連付け
Bash AWS CLI 
# DNS Firewall ルールグループを作成
aws route53resolver create-firewall-rule-group \
  --name "nfw-resolved-ip-validation" \
  --region ap-northeast-1

# ルールグループを保護対象 VPC に関連付け
aws route53resolver associate-firewall-rule-group \
  --firewall-rule-group-id rslvr-frg-0123456789abcdef0 \
  --vpc-id vpc-0123456789abcdef0 \
  --priority 101 \
  --name "nfw-validation-association" \
  --region ap-northeast-1

このルールグループに関連付けられた VPC の DNS 解決結果が、Resolved IP Validation の照合に使用されます。

2
ファイアウォールポリシーで Resolved IP Validation を有効化
Bash AWS CLI 
# 既存のファイアウォールポリシーを更新して Resolved IP Validation を追加
aws network-firewall update-firewall-policy \
  --update-token <update-token> \
  --firewall-policy-name my-firewall-policy \
  --firewall-policy '{
    "StatelessDefaultActions": ["aws:forward_to_sfe"],
    "StatelessFragmentDefaultActions": ["aws:forward_to_sfe"],
    "Route53ResolvedIPValidation": {
      "Action": "DROP",
      "DNSFirewallRuleGroupId": "rslvr-frg-0123456789abcdef0",
      "DNSExpiryExceptionPolicy": "CONTINUE"
    }
  }' \
  --region ap-northeast-1

この例では、Route 53 VPC Resolver で解決されていない宛先 IP への接続をサイレントにドロップし、キャッシュ期限切れの解決結果は有効として扱います。 DNS Firewall ルールグループの関連付けは非同期で処理されるため、ポリシーが ACTIVE 状態に戻るまで追加の変更はできません。

3
特定ドメインを対象とする resolved-domain ルールの追加
Bash AWS CLI 
# AWS_ROUTE_53_RESOLVED_DOMAIN ターゲットタイプを使用したドメインリストルールグループを作成
aws network-firewall create-rule-group \
  --rule-group-name allowed-domains-all-protocols \
  --type STATEFUL \
  --capacity 100 \
  --rule-group '{
    "RulesSource": {
      "RulesSourceList": {
        "Targets": [".example.com", "sftp.example.org"],
        "TargetTypes": ["TLS_SNI", "HTTP_HOST", "AWS_ROUTE_53_RESOLVED_DOMAIN"],
        "GeneratedRulesType": "ALLOWLIST"
      }
    }
  }' \
  --region ap-northeast-1

許可リストで TLS_SNI / HTTP_HOST と併用した場合、SNI / Host ヘッダーの一致と解決済み IP の一致の両方を満たすトラフィックのみが許可され、 SNI スプーフィングを防止できます。作成したルールグループはステップ 2 のポリシーに関連付けて使用します。

💡 メリット

💼 ビジネス面

✓追加コストなしのセキュリティ強化: 追加料金なしで利用でき、既存の Network Firewall と Route 53 Resolver DNS Firewall の構成にセキュリティレイヤーを追加できる
✓コンプライアンス対応の強化: アウトバウンド通信の宛先を「DNS で正規に解決されたドメイン」に限定する統制を実装でき、金融や公共部門などの厳格なエグレス制御要件に対応しやすくなる
✓サードパーティプロキシの削減: SSH / SFTP などの非 Web プロトコルに対するドメインベース制御のために別途プロキシ製品を導入する必要性が減り、運用コストを削減できる

🔧 技術面

✓全プロトコルへのドメインフィルタリング拡張: 検証が IP レイヤーで行われるため、SNI や Host ヘッダーを持たないプロトコルを含む全アウトバウンドトラフィックにドメインベースの制御を適用できる
✓SNI スプーフィングの防止: クライアントが主張するドメイン名と、宛先 IP が実際に解決されたドメインの両方を照合することで、ヘッダー偽装によるルールバイパスを防止できる
✓柔軟な適用範囲の制御: 送信元 IP 範囲による検証対象の絞り込みや、バイパス宛先 IP 範囲による例外設定により、段階的な導入や特定ワークロードへの限定適用が可能
✓段階的な導入が可能: まず ALERT アクションで影響を可視化し、問題がないことを確認してから DROP / REJECT に切り替える運用ができる

⚠️ デメリット・制約事項

🚫 制限事項

✗ルールレベルの resolved-domain ルール (AWS_ROUTE_53_RESOLVED_DOMAIN / aws_route_53_resolved_domain) は、ポリシーレベルの Resolved IP Validation 設定が有効な場合にのみ機能する
✗REJECT の TCP リセットは TCP トラフィックにのみ適用され、非 TCP トラフィックはドロップされる。ドメインリストで Reject と AWS_ROUTE_53_RESOLVED_DOMAIN を併用すると生成ルールが TCP のみに限定されるため、全プロトコルをブロックするには Deny を使用する必要がある
✗SourceIPRanges と BypassDestinationValidationIPRanges はそれぞれ最大 100 エントリまで
✗AWS_ROUTE_53_RESOLVED_DOMAIN のみをターゲットタイプとする許可リストは加算的に動作し、一致しないトラフィックをドロップするデフォルトルールは追加されない。非一致トラフィックもドロップするには TLS_SNI / HTTP_HOST を併用する必要がある
✗Suricata キーワード aws_route_53_resolved_domain は 1 ルールにつき 1 回のみ使用でき、ワイルドカードはアスタリスクではなく先頭ドットで記述する

🤔 考慮すべき点

⚠クライアントが Route 53 VPC Resolver 以外の DNS サーバー (外部 DNS、独自 DNS) を使用している場合、解決結果が記録されないため正規の通信でも検証に失敗する。導入前に VPC 内の DNS 構成の確認が必要
⚠IP アドレスを直接指定して接続する正規のワークロード (ヘルスチェック、レガシーアプリケーションなど) がある場合は、BypassDestinationValidationIPRanges への登録が必要
⚠DNS Firewall ルールグループの変更は非同期で処理され、処理中はポリシーの Resolved IP Validation 設定に対する追加変更が拒否される
⚠ポリシーから Resolved IP Validation を削除すると DNS Firewall ルールグループとの関連付けが解除され、resolved-domain ルールを含めて機能全体が停止する

🎯 ユースケース

📁 ユースケース 1: SSH / SFTP を含む全プロトコルのエグレス制御

シナリオ: データ分析基盤の VPC から、外部パートナーの SFTP サーバー sftp.partner.example へのファイル転送のみを許可し、 それ以外の外部宛先へのアウトバウンド通信をすべてブロックしたい。従来の SNI ベースのドメインフィルタリングでは SFTP を制御できなかった。

Suricata 実装例 
# ポリシーレベル: DNS 解決を経ない宛先への接続を DROP
# ルールレベル: 許可対象ドメインとして解決された IP への通信のみ許可
pass ip $HOME_NET any -> $EXTERNAL_NET any (aws_route_53_resolved_domain:"sftp.partner.example"; flow:to_server, established; sid:100;)
drop ip $HOME_NET any -> $EXTERNAL_NET any (flow:to_server, established; sid:999;)
効果: SFTP のようなドメイン名をトラフィックに含まないプロトコルでも、DNS 解決に基づくドメイン単位の許可制御が可能になり、 許可していない宛先へのファイル持ち出し経路を遮断できる。
🛡️ ユースケース 2: SNI スプーフィングによるデータ漏洩の防止

シナリオ: アウトバウンド HTTPS を許可リスト方式で制御しているが、侵害されたインスタンスが SNI に許可済みドメインを偽装して 攻撃者のサーバーへデータを送信するリスクに対処したい。

JSON 実装例 
{
  "RulesSource": {
    "RulesSourceList": {
      "Targets": [".example.com"],
      "TargetTypes": ["TLS_SNI", "AWS_ROUTE_53_RESOLVED_DOMAIN"],
      "GeneratedRulesType": "ALLOWLIST"
    }
  }
}
効果: SNI が許可ドメインに一致していても、宛先 IP がそのドメインとして Route 53 VPC Resolver で解決されたものでなければ接続が許可されず、 SNI 偽装によるデータ漏洩を防止できる。
🔍 ユースケース 3: マルウェアの C2 通信対策としての直接 IP 接続の検出

シナリオ: マルウェアの多くは DNS 解決を行わずにハードコードされた IP アドレスへ C2 通信を行う。 まず影響を可視化してから、段階的にブロックへ移行したい。

JSON 実装例 
{
  "Route53ResolvedIPValidation": {
    "Action": "ALERT",
    "DNSFirewallRuleGroupId": "rslvr-frg-0123456789abcdef0",
    "DNSExpiryExceptionPolicy": "CONTINUE"
  }
}
効果: DNS 解決を経ていない宛先への接続がフローログに記録され、不審な直接 IP 通信を検出できる。 影響範囲を確認した後に Action を DROP へ変更することで、C2 通信経路を安全に遮断できる。

💰 料金

Route 53 Resolved IP Validation は追加料金なしで利用できます。 AWS Network Firewall 本体 (エンドポイント時間料金と処理データ量に基づく料金) および Route 53 Resolver DNS Firewall の標準料金は別途適用されます。 ロギングを有効にする場合は、ログ配信先 (CloudWatch Logs、S3、Kinesis Data Firehose) に応じた料金が発生します。

🔗 関連サービス・機能

🛡️ Amazon Route 53 Resolver DNS Firewall

本機能の前提となるサービス。DNS クエリ自体のフィルタリングを担い、本機能で使用する解決済み IP 情報の基盤となる。併用により DNS レイヤーとネットワークレイヤーの一貫した防御を実現。

🔍 Amazon Route 53 Resolver (VPC Resolver)

VPC 内の DNS 解決を担うリゾルバー。クライアントがこのリゾルバーを使用していることが検証の前提条件。

🔐 AWS Network Firewall TLS インスペクション

SNI 検査を超えた TLS トラフィックの復号検査が必要な場合の補完機能。

🏢 AWS Firewall Manager

AWS Organizations 配下の複数アカウントに対して、本機能を含むファイアウォールポリシーを一元的に展開・管理可能。

📝 まとめ

Route 53 Resolved IP Validation により、AWS Network Firewall のドメインベースフィルタリングが SNI / Host ヘッダー依存の制約を脱し、 SSH や SFTP を含む全プロトコルに拡張されるとともに、 SNI スプーフィングや直接 IP 接続によるルールバイパスという長年のセキュリティギャップが解消されました。

追加料金なしで利用できるため、Network Firewall でエグレス制御を行っている環境では、 まず ALERT アクションで影響を可視化したうえで、DROP / REJECT による強制への 段階的な移行を検討することを推奨します。
