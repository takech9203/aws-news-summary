AWS What's New

📋 概要

Amazon Bedrock AgentCore Identity の Credential Provider で、AWS Secrets Manager の既存シークレット ARN を直接参照できるようになった。組織固有のガバナンスポリシーに基づいてシークレットを完全に管理した上で、AgentCore Identity と連携できる。

❌ Before

  • サービスマネージドシークレットのみ
  • リソースタグの付与不可
  • CMK による暗号化不可
  • 組織ガバナンスコントロールの適用不可
  • 厳格なコンプライアンス要件への非対応

✅ After

  • 既存シークレット ARN を直接参照可能
  • CMK 暗号化、タグ付け自由
  • 自動ローテーション設定可能
  • リソースポリシーによるアクセス制御
  • シークレットの完全なオーナーシップ

⚡ 主要機能

🔗 既存シークレット ARN の直接参照

Credential Provider 構成時に secretId パラメータで既存の Secrets Manager シークレット ARN を指定可能。apiKeySecretSource または clientSecretSource を EXTERNAL に設定することで外部シークレット参照モードを有効化。JSON キーの指定により、1 つのシークレット内の特定のフィールドを参照可能。

🔌 対応する Credential Provider タイプ

API キー: API キーシークレットの外部参照

OAuth2: クライアントシークレットの外部参照 (Google、GitHub、Slack、Salesforce、Microsoft、Atlassian、LinkedIn 等)

Payment: 決済関連シークレットの外部参照 (Coinbase CDP、Stripe Privy)

🔀 シークレットソースの選択制

MANAGED: 従来のサービスマネージドシークレット (引き続き利用可能)

EXTERNAL: 顧客管理の既存シークレットを ARN で参照

🛠️ 設定方法

前提条件

✓AWS Secrets Manager にシークレットが作成済みであること
✓AgentCore Identity が secretsmanager:GetSecretValue 権限を持つこと
✓CMK 暗号化の場合、kms:Decrypt 権限を持つこと

Step 1: シークレット作成

Bash Secrets Manager でシークレットを作成 
aws secretsmanager create-secret \
  --name "agentcore/my-oauth-client-secret" \
  --description "OAuth2 client secret for AgentCore Identity" \
  --secret-string '{"clientSecret": "your-secret-value"}' \
  --kms-key-id "arn:aws:kms:us-east-1:123456789012:key/your-cmk-key-id" \
  --tags '[{"Key": "Environment", "Value": "Production"}, {"Key": "Team", "Value": "AI-Platform"}]'

Step 2: Credential Provider を構成

Bash EXTERNAL モードで Credential Provider を作成 
aws bedrock-agentcore-control create-api-key-credential-provider \
  --name "my-external-api-key-provider" \
  --api-key-secret-source "EXTERNAL" \
  --api-key-secret-config '{
    "secretId": "arn:aws:secretsmanager:us-east-1:123456789012:secret:agentcore/my-api-key-AbCdEf",
    "jsonKey": "apiKey"
  }'

Step 3: リソースポリシーを設定

Bash AgentCore Identity のアクセスを許可 
aws secretsmanager put-resource-policy \
  --secret-id "agentcore/my-oauth-client-secret" \
  --resource-policy '{
    "Version": "2012-10-17",
    "Statement": [
      {
        "Effect": "Allow",
        "Principal": {
          "Service": "bedrock-agentcore.amazonaws.com"
        },
        "Action": "secretsmanager:GetSecretValue",
        "Resource": "*"
      }
    ]
  }'

IAM ポリシー設定例

JSON 必要な IAM 権限 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["secretsmanager:GetSecretValue"],
      "Resource": "arn:aws:secretsmanager:us-east-1:123456789012:secret:my-agent-secret-*"
    },
    {
      "Effect": "Allow",
      "Action": ["kms:Decrypt"],
      "Resource": "arn:aws:kms:us-east-1:123456789012:key/your-cmk-key-id"
    }
  ]
}

⚖️ メリット・デメリット

✅ メリット

  • コンプライアンス対応: 組織ポリシーに完全準拠したシークレット管理
  • 監査対応強化: リソースタグ + CloudTrail による一元追跡
  • 運用コスト削減: 既存のワークフローをそのまま活用
  • 暗号化制御: CMK によるキーローテーション・無効化を自社管理
  • 自動ローテーション: Secrets Manager のローテーション機能を活用
  • 組織ポリシー統合: SCP やリソースポリシーによるアクセス制御

⚠️ 制約・考慮点

  • AgentCore Identity 用の IAM 権限設定が追加で必要
  • ローテーション戦略の設計が必要
  • EXTERNAL モードではシークレットの可用性責任が顧客側に
  • MANAGED から EXTERNAL への移行にはシークレット再作成が必要
  • クロスアカウント参照にはリソースポリシーと KMS キーポリシーの両方が必要

💡 ユースケース

🏦 金融機関のコンプライアンス対応

AI エージェント構築時に、全シークレットに対して CMK 暗号化、タグ分類、90 日ごとの自動ローテーションを義務付けている金融機関。EXTERNAL モードにより、組織のセキュリティ監査要件を満たしながら AgentCore Identity を活用した認証を実現。

🏢 マルチアカウント環境での一元管理

セキュリティアカウントでシークレットを一元管理し、複数のワークロードアカウントの AgentCore Identity から参照。シークレットの一元管理によりセキュリティガバナンスを維持しつつ、複数アカウントでの AI エージェント展開を実現。

🔗 OAuth2 連携の SaaS 統合

複数の SaaS (Salesforce、GitHub、Slack) と連携する AI エージェントを構築する際、各サービスのクライアントシークレットを既存のシークレット管理基盤で統一管理。既存のローテーション・監視基盤を活用し、SaaS 連携のセキュリティを組織標準で統一。
