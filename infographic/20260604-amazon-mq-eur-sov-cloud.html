🐇 Amazon MQ for RabbitMQ
AWS European Sovereign Cloud での提供開始

2026 年 6 月 4 日
AWS European Sovereign Cloud (Germany)

📋 概要

Amazon MQ for RabbitMQ が AWS European Sovereign Cloud (Germany) リージョンで利用可能になりました。欧州におけるデータレジデンシー要件を持つ顧客が、EU 域内に完全にデータを保持しながらマネージドメッセージブローカーサービスを利用できます。

RabbitMQ 4.2 エンジンと Graviton3 ベースの m7g インスタンス (m7g.medium ~ m7g.16xlarge) をサポートし、既存の RabbitMQ ワークロードをアプリケーションコードの書き換えなしに移行可能です。

Graviton3 m7g インスタンスシリーズ

0 行 コード変更で移行可能

🔄 Before / After

❌ Before (アップデート前)

  • Sovereign Cloud でマネージドメッセージブローカーを利用不可
  • 自己管理型の RabbitMQ クラスターを構築・運用する必要あり
  • EU 域内にデータを保持しつつ高可用性を維持する運用負荷が高い

✅ After (アップデート後)

  • Sovereign Cloud 内で Amazon MQ for RabbitMQ をネイティブにデプロイ可能
  • 他の AWS リージョンと同等の RabbitMQ 機能を EU 域内で利用可能
  • フルマネージドで自動パッチ適用、メンテナンス、高可用性を提供

🏗️ アーキテクチャ図

⚡ 主要機能

🐇 RabbitMQ 4.2 エンジンのサポート
最新の RabbitMQ 4.2 エンジンを利用可能。標準的な AMQP プロトコルと RabbitMQ API に完全対応し、既存の RabbitMQ アプリケーションコードをそのまま移行できます。
💪 Graviton3 ベース m7g インスタンス
m7g.medium から m7g.16xlarge までの幅広いインスタンスサイズを提供。AWS Graviton3 プロセッサによる優れたコストパフォーマンスとワークロード規模に応じた柔軟なスケーリングを実現。
🔧 フルマネージド運用
ブローカーのプロビジョニング、パッチ適用、メンテナンスを AWS が自動管理。高可用性クラスター構成による耐障害性とセキュリティアップデートの自動適用。

ステップ 1: RabbitMQ ブローカーの作成

Bash AWS CLI - ブローカー作成 
aws mq create-broker \
    --broker-name "eu-sovereign-rabbitmq" \
    --engine-type RABBITMQ \
    --engine-version "4.2" \
    --host-instance-type "mq.m7g.large" \
    --deployment-mode CLUSTER_MULTI_AZ \
    --users '[{"Username": "admin", "Password": "SecurePassword123!"}]' \
    --subnet-ids "subnet-xxxxxxxx" "subnet-yyyyyyyy" "subnet-zzzzzzzz" \
    --security-groups "sg-xxxxxxxxx"

ステップ 3: アプリケーションからの接続

Python pika を使用した接続例 
import pika

# Amazon MQ RabbitMQ エンドポイントに接続
credentials = pika.PlainCredentials('admin', 'SecurePassword123!')
parameters = pika.ConnectionParameters(
    host='b-xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx.mq.eu-sovereign-1.amazonaws.com',
    port=5671,
    virtual_host='/',
    credentials=credentials,
    ssl_options=pika.SSLOptions()
)

connection = pika.BlockingConnection(parameters)
channel = connection.channel()

# キューの宣言とメッセージ送信
channel.queue_declare(queue='eu-sovereign-queue', durable=True)
channel.basic_publish(
    exchange='',
    routing_key='eu-sovereign-queue',
    body='Hello from EU Sovereign Cloud!'
)

✅ メリット

ビジネス面

✓データ主権の確保: すべてのメッセージデータと運用が EU 域内に保持され、GDPR や各国のデータ保護規制に準拠
✓コンプライアンス対応の簡素化: 規制の厳しい業界や政府機関が、データ主権を維持しながらマネージドメッセージングサービスを利用可能
✓運用コストの削減: 自己管理型 RabbitMQ クラスターの構築・運用が不要になり、管理コストを大幅に削減

技術面

✓既存コードの再利用: 標準 AMQP プロトコルと RabbitMQ API をサポートし、コード変更なしで移行可能
✓高可用性: 3 ノードクラスター構成と複数 AZ デプロイメントにより可用性を確保
✓Graviton3 による高効率: m7g インスタンスにより、優れたコストパフォーマンスと低消費電力を実現

⚠️ 制約事項・考慮点

制限事項

✗RabbitMQ エンジンのみが対象。ActiveMQ の European Sovereign Cloud 対応は未発表
✗AWS European Sovereign Cloud へのアクセスには適格な顧客としての要件を満たす必要あり
✗他の商用リージョンと比較して連携サービスが限定的な場合あり

考慮すべき点

⚡European Sovereign Cloud リージョンの料金は標準商用リージョンと異なる可能性あり
⚡商用リージョンからの移行には VPC 構成やネットワーク設計の見直しが必要
⚡クロスリージョンレプリケーション利用時はデータ主権要件との整合性を確認

🎯 ユースケース

🏦 欧州金融機関のイベント駆動アーキテクチャ

EU の金融規制 (DORA、MiFID II) に準拠しながら、取引処理システム間の非同期メッセージングを実装。取引データを EU 域内に保持しつつ、高スループットかつ低レイテンシーの非同期メッセージングにより、リアルタイム取引処理を実現。

🏛️ 欧州公共部門のマイクロサービス連携

データ主権を厳格に遵守しながら、市民向けデジタルサービスのバックエンドをマイクロサービスアーキテクチャで構築。市民データが EU 域外に流出するリスクを排除し、スケーラブルなイベント駆動アーキテクチャで迅速なサービス提供を実現。

🏥 ヘルスケア業界の医療データ連携

GDPR と各国の医療データ保護規制に準拠しながら、病院間のデータ連携や医療機器からのデータ収集を非同期処理。患者データを EU 域内に保持しつつ、信頼性の高いデータ連携を実現。
