AWS CloudFormation

🛠️ Force Rollback でスタック更新ロールバックを簡素化

📅 リリース日: 2026 年 10 月 22 日 | 機能: Force Rollback (強制ロールバック)

📋 概要

AWS CloudFormation が、スタック更新のロールバック操作を簡素化する新機能 Force Rollback (強制ロールバック) を発表しました。 一部のリソースが自動ロールバックできずスタックが UPDATE_ROLLBACK_FAILED 状態になった場合でも、 --force-rollback オプションを指定するだけで失敗リソースを自動的にスキップし、 単一の操作でロールバックを完了できます。

スキップされたリソースは記録され、ドリフト対応変更セットと組み合わせて差分を確認してから安全に再デプロイできます。 AWS CLI、SDK、AWS CDK、AI エージェントなど、すべての CloudFormation ワークフローで利用可能です。

❌ Before: 手動での復旧作業

✗ロールバックに失敗したリソースを 1 つずつ手動で特定
✗--resources-to-skip に失敗リソースの論理 ID をすべて列挙して再試行
✗ネストスタックは {NestedStackName}.{ResourceLogicalID} 形式で個別に調査・指定が必要
✗復旧手順が多く、障害対応時の MTTR が長期化

✅ After: 単一操作で自動復旧

✓--force-rollback の指定だけで失敗リソースを自動スキップし、1 回でロールバック完了
✓ネストスタック全階層で失敗リソースの特定・列挙が不要
✓スキップしたリソースは Resource skipped during UpdateRollback として記録
✓ドリフト対応変更セットで差分を確認してから再デプロイ可能

スタック更新が失敗しロールバックも失敗した場合の復旧フローです。従来は失敗リソースの手動特定が必要でしたが、Force Rollback により単一操作で UPDATE_ROLLBACK_COMPLETE 状態まで復旧できます。

⚡ 主要機能

1️⃣ 単一操作でのロールバック完了

  • continue-update-rollback コマンドに --force-rollback オプションを追加するだけで実行可能
  • ロールバックに失敗した (UPDATE_FAILED 状態の) リソースを CloudFormation が自動的にスキップ
  • スキップされたリソースのステータスは UPDATE_COMPLETE になり、理由に Resource skipped during UpdateRollback と記録
  • スキップ対象はロールバック失敗リソースのみ。フォワード更新で失敗したリソースはスキップされない

2️⃣ ネストされたスタックへの対応

  • ネストスタックを含む全階層で、失敗リソースを自動的にスキップ
  • 従来必要だった {NestedStackName}.{ResourceLogicalID} 形式でのリソース指定が不要
  • 多階層構成でも、ルートスタックに対する 1 回の操作で全体を復旧可能

3️⃣ スキップされたリソースの記録と確認

  • ロールバック完了時に、スタックのステータス理由にリソースがスキップされたことが報告される
  • ドリフト検出では NOT_CHECKED と報告されるため、DetectStackResourceDrift で個別に差分を確認可能
  • ドリフト対応変更セットで、実際のリソース状態・前回デプロイ状態・desired state の 3 方向比較が可能

4️⃣ すべてのワークフローで利用可能

  • AWS CLI、SDK、AWS CDK、AI エージェントなど、CloudFormation を利用するすべてのワークフローで使用可能

🔧 技術仕様: Force Rollback の動作

項目詳細
対象の状態UPDATE_ROLLBACK_FAILED 状態のスタック
スキップ対象ロールバック中に UPDATE_FAILED となったリソース (ネストスタック内を含む)
スキップ対象外フォワード更新中に失敗したリソース
スキップ後のステータスUPDATE_COMPLETE (理由: Resource skipped during UpdateRollback)
完了後のスタック状態UPDATE_ROLLBACK_COMPLETE
ドリフト検出での扱いスキップされたリソースは NOT_CHECKED と報告される
排他制約--force-rollback と --resources-to-skip は同一リクエストで併用不可
Bash 強制ロールバックの実行 
# 強制ロールバックの実行
aws cloudformation continue-update-rollback \
    --stack-name MyStack \
    --force-rollback

UPDATE_ROLLBACK_FAILED 状態のスタックに対して強制ロールバックを実行するコマンドです。失敗リソースを自動スキップし、スタックを UPDATE_ROLLBACK_COMPLETE 状態に戻します。

📝 設定方法

✅ 前提条件

✓スタックが UPDATE_ROLLBACK_FAILED 状態であること
✓AWS CLI または SDK が利用可能であること (コンソールからも操作可能)
✓cloudformation:ContinueUpdateRollback の IAM 権限があること
1

スタックの状態を確認

Bashステータス確認
aws cloudformation describe-stacks \
    --stack-name MyStack \
    --query "Stacks[0].StackStatus"

現在のステータスが UPDATE_ROLLBACK_FAILED であることを確認します。

2

強制ロールバックを実行

BashForce Rollback 実行
aws cloudformation continue-update-rollback \
    --stack-name MyStack \
    --force-rollback

失敗リソースを自動スキップしてロールバックを完了します。ネストスタックがある場合も、ルートスタックへの 1 回の実行で全階層が対象になります。

3

スキップされたリソースを確認

Bashスタックイベントの確認
aws cloudformation describe-stack-events \
    --stack-name MyStack \
    --query "StackEvents[?ResourceStatusReason=='Resource skipped during UpdateRollback']"

スキップされたリソースはテンプレートと実際の状態が不整合になっている可能性があるため、必ず確認します。

4

ドリフト対応変更セットで差分を確認して再デプロイ

Bashドリフト対応変更セットの作成
aws cloudformation create-change-set \
    --stack-name MyStack \
    --change-set-name my-drift-aware-changeset \
    --template-body file://updated-template.yaml \
    --deployment-mode REVERT_DRIFT

実際のリソース状態とテンプレートの 3 方向比較により、スキップされたリソースを含む構成差分を確認してから、安全に次のデプロイを実行できます。

💡 メリット

💼 ビジネス面

✓復旧時間の短縮: 失敗リソースの手動特定と列挙が不要になり、障害発生時の MTTR を大幅に短縮
✓運用負荷の軽減: 複雑なネストスタック構成でも 1 回の操作で復旧でき、オンコール対応の負担が軽減
✓追加コストなし: すべてのリージョンで追加料金なしで利用可能

⚙️ 技術面

✓自動化との親和性: CLI、SDK、CDK、AI エージェントから利用でき、自動復旧パイプラインに組み込みやすい
✓ネストスタック全階層への対応: 形式指定の調査が不要になり、オペレーションミスを防止
✓可視性の確保: スキップされたリソースが記録され、差分を確認してから再デプロイ可能

⚠️ デメリット・制約事項

🚧 制限事項

⚠--force-rollback と --resources-to-skip は同一リクエストで併用できない (特定リソースのみスキップしたい場合は従来どおり --resources-to-skip を使用)
⚠スキップ対象はロールバック中に失敗したリソースのみで、フォワード更新中に失敗したリソースはスキップされない
⚠ドリフト検出では NOT_CHECKED と報告されるため、差分確認には DetectStackResourceDrift やドリフト対応変更セットが必要

🔍 考慮すべき点

⚠ロールバック完了後、スキップされたリソースはスタックテンプレートと不整合な状態になる。次の更新前に整合させないと、以降のスタック更新が失敗し、スタックが復旧不能になる可能性がある
⚠強制ロールバックは「エラーを修正できない場合」の手段。まずはロールバック失敗の原因調査と修正を検討することが推奨される

🎯 ユースケース

1. 外部変更されたリソースを含むスタックの復旧

シナリオ: スタック管理下のデータベースインスタンスが CloudFormation の外部で削除され、更新のロールバックが UPDATE_ROLLBACK_FAILED で停止した。

Bash
aws cloudformation continue-update-rollback \
    --stack-name ProductionStack \
    --force-rollback

効果: 削除済みリソースを手動特定せずにロールバックを完了し、デプロイ可能な状態に復旧。ドリフト対応変更セットで状態を確認し、テンプレートを修正して再デプロイできる。

2. 多階層ネストスタックの一括復旧

シナリオ: ルートスタック配下に複数のネストスタックを持つ大規模インフラで更新が失敗し、スタック階層全体が UPDATE_ROLLBACK_FAILED 状態になった。

Bash
aws cloudformation continue-update-rollback \
    --stack-name WebInfra \
    --force-rollback

効果: ネストスタック名や論理 ID を調査・列挙することなく、ルートスタックへの 1 回の操作で階層全体のロールバックを完了できる。

3. CI/CD パイプラインでの自動復旧

シナリオ: CDK ベースの CI/CD パイプラインでデプロイが失敗した際、スタックが UPDATE_ROLLBACK_FAILED のままだと後続のデプロイがすべてブロックされる。

Bashパイプラインの復旧ステップに組み込む例
STATUS=$(aws cloudformation describe-stacks \
    --stack-name MyAppStack \
    --query "Stacks[0].StackStatus" --output text)

if [ "$STATUS" = "UPDATE_ROLLBACK_FAILED" ]; then
    aws cloudformation continue-update-rollback \
        --stack-name MyAppStack \
        --force-rollback
fi

効果: 人手の介入なしにスタックを自動復旧し、パイプラインの停止時間を最小化。スキップされたリソースは記録されるため、後から確認・解決できる。

💰 料金・利用可能リージョン

💵 料金

Force Rollback は追加料金なしで利用できます。CloudFormation 自体の料金体系 (AWS リソースタイプへの操作は無料、サードパーティリソースタイプのハンドラーオペレーションに課金) に変更はありません。

🌍 利用可能リージョン

すべての AWS リージョンで利用可能です。

🔗 関連サービス・機能

ドリフト対応変更セット (Drift-aware Change Sets): 実際のリソース状態・前回デプロイ状態・desired state の 3 方向比較を提供。強制ロールバック後にスキップされたリソースの差分確認と解消に活用できる。
AWS CDK: CDK によるデプロイが失敗した場合の復旧でも Force Rollback を利用できる。
CloudFormation ドリフト検出: スキップされたリソースは NOT_CHECKED となるため、DetectStackResourceDrift による個別の差分確認と組み合わせて使用する。

📌 まとめ

CloudFormation の Force Rollback により、これまで手動でのリソース特定と列挙が必要だった UPDATE_ROLLBACK_FAILED 状態からの復旧を、単一の操作で完了できるようになりました。 ネストスタックを含む複雑な構成や CI/CD パイプラインでの自動復旧に特に有効です。 スキップされたリソースはテンプレートと不整合になるため、再デプロイ前に ドリフト対応変更セットで差分を確認するワークフローを整備することを推奨します。
