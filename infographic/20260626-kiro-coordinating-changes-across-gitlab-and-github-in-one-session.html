🦊🐙 GitLab と GitHub をまたぐ変更を
1 セッションで調整

Kiro Kiro Web プレビュー
2026-06-26
リリース日

📌 概要

Kiro Web が新たに GitLab をサポート。これまでの GitHub サポートと併せ、両方のリポジトリを同一セッションに追加し、1 つの変更を自然言語で記述するだけで、両プロバイダーにまたがって変更を適用できます。

コードを GitLab と GitHub に分散させているチームは少なくありません。公開 SDK を GitHub に置き、それが呼ぶ非公開サービスを GitLab に置くケースや、買収による組織分割、フロントエンドとバックエンドで別ツールに落ち着いたケースなどです。理由は何であれ、1 つの変更が両方にまたがった瞬間にコストが発生します。

今回のアップデートにより、1 つの論理的な変更を 2 つのコンテキストで別々の PR と MR として手作業で管理する必要がなくなります。Kiro が両リポジトリをまとめて推論し、両者の不整合 (ドリフト) を防ぎます。GitLab には マージリクエスト (MR)、GitHub には プルリクエスト (PR) がそれぞれ作成されます。

🔄 アップデートによる変化

❌ Before
  • GitLab と GitHub にまたがる 1 つの変更を、2 つの別々のタスクとして手作業で対応
  • 片方への反映漏れで両者がドリフト (整合性の崩れ) するリスク
  • Kiro Web は GitHub のみ対応、GitLab リポジトリを扱えなかった
➡
✅ After
  • GitLab と GitHub の両リポジトリを 1 セッションに追加可能
  • 1 つのプロンプトで両プロバイダーへ一貫して変更を適用
  • GitLab に MR、GitHub に PR を自動作成し、手作業の管理が不要に

💡 開発者が 1 つのプロンプトで変更を記述すると、Kiro が隔離サンドボックス内で両リポジトリをまとめて推論し、GitLab には MR、GitHub には PR を作成します。

⭐ 主要機能

1. Kiro Web の GitLab サポート

  • これまでの GitHub サポートに加えて、GitLab のリポジトリを扱えるように
  • GitLab と GitHub の両方を接続した状態で 1 つのセッションを開始
  • GitLab 側の変更にはマージリクエスト (MR) が作成される

2. クロスプロバイダーの同時調整

  • GitLab の user-service と GitHub の user-sdk を同一セッションに追加
  • 2 つの無関係なタスクではなく、両リポジトリをまとめて推論
  • 1 つの変更要件 (例: email フィールド追加) を整合性を保ったまま両方へ反映

3. 自律的な変更適用とブランチ作成

  • 隔離されたサンドボックス内で両リポジトリを探索し、必要な変更を判断・適用
  • 各リポジトリにフィーチャーブランチを作成し、明確なメッセージでコミット
  • 完了後、GitLab に MR、GitHub に PR を作成し、説明と変更アプローチを添付

🛠️ 設定方法

前提条件

  • ✅Pro、Pro+、または Power の Kiro サブスクリプションを契約していること
  • ✅Kiro Web (app.kiro.dev) にサインインできること
  • ✅GitLab と GitHub の両方のアカウントを Kiro Web に接続していること

手順

1

両プロバイダーを接続

GitLab と GitHub の両プロバイダーを Kiro Web に接続し、両方のリポジトリをセッションに追加できる状態にする。

2

リポジトリを追加

新しいセッションを開始し、GitLab の user-service と GitHub の user-sdk をアタッチする。

3

プロンプトを記述

変更を自然言語で記述。Kiro が両リポジトリをまとめて推論し、変更適用後に MR と PR を作成する。

Prompt 1 つのプロンプトで両プロバイダーへ反映 
Add an email field to the user response in the service, and expose it through the SDK.

このプロンプトは、サービス側 (GitLab) のユーザーレスポンスに email フィールドを追加し、SDK 側 (GitHub) を通じて公開するという、1 つの変更を両リポジトリへ反映するよう指示しています。

📈 メリット

💼 ビジネス面

  • プロバイダー分割の維持: 公開と非公開、チーム間分担といった意図的な分割を保ったまま作業
  • レビュープロセスの不変性: レビューとマージは各プロバイダー上で従来どおり実施
  • 作業漏れリスクの低減: 手作業の管理を Kiro が肩代わりし、反映漏れによる不整合を防止

🔧 技術面

  • 統合された推論: 両リポジトリをまとめて推論し、変更がエンドツーエンドで一貫
  • 隔離サンドボックスでの実行: 探索と変更を行い、明確なコミットメッセージでブランチを作成
  • 整合性の確保: 1 つの論理的変更を 2 つのプロバイダーへ一貫適用し、ドリフトを防止

⚠️ デメリット・制約事項

制限事項

  • 🔸Kiro Web はプレビュー段階であり、提供内容が変更される可能性がある
  • 🔸利用には Pro、Pro+、または Power のサブスクリプションが必要
  • 🔸本機能は Kiro Web で提供され、対応プロバイダーは GitLab と GitHub

考慮すべき点

  • 👀作成された MR と PR は、各プロバイダー上で内容をレビューしてからマージする必要がある
  • 👀自律的に変更が適用されるため、生成されたコミット内容とブランチの確認が推奨される

🎯 ユースケース

1. 公開 SDK と非公開サービスの同時更新

シナリオ: 公開 SDK を GitHub に、その SDK が呼び出す非公開サービスを GitLab に置くチームが、ユーザーレスポンスに新フィールドを追加したい。

効果: サービス側 (GitLab) と SDK 側 (GitHub) の変更が 1 セッションで整合性を保って適用され、それぞれ MR と PR が作成される。

2. 買収後の組織横断的な変更

シナリオ: 買収により組織の半分が GitLab、もう半分が GitHub に分かれ、両環境にまたがる共通の変更を適用したい。

効果: プロバイダー分割を維持したまま 1 つの変更を両環境へ一貫反映でき、手作業の調整コストを削減。

3. フロントエンドとバックエンドの連動変更

シナリオ: フロントエンドとバックエンドのチームが異なるプロバイダーを使用し、API 仕様の変更を両コードベースへ同時反映したい。

効果: 連動する変更が片側のみに反映される事態を防ぎ、両コードベースの整合性を維持。

📝 まとめ

このアップデートにより、Kiro Web は GitLab をサポートし、GitLab と GitHub にまたがる 1 つの変更を 1 セッションで一貫して適用できるようになりました。意図的なプロバイダー分割を維持しつつ、クロスリポジトリの手作業による管理から解放される点が大きな価値です。

複数プロバイダーにコードが分散しているチームは、Pro、Pro+、Power のサブスクリプションで app.kiro.dev のプレビューを試し、両プロバイダーをまたぐ変更を体験することをお勧めします。
