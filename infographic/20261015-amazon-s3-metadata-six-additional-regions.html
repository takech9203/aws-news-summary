S3 Metadata が 6 つの AWS リージョンで追加提供開始

📅 リリース日: 2026 年 10 月 15 日 | 機能: Amazon S3 Metadata (リージョン拡大)

📋 概要

Amazon S3 Metadata が新たに 6 つの AWS リージョンで利用可能になりました。 S3 Metadata は、S3 オブジェクトのメタデータを自動的に収集し、ほぼリアルタイムで更新される クエリ可能な Apache Iceberg テーブルとして提供する機能です。 新規・既存オブジェクトの両方に対応し、ビジネス分析やリアルタイム推論アプリケーションで S3 データをキュレーション・特定・活用できます。

さらに Annotations (アノテーション) 機能により、オブジェクトごとに最大 1 GB の JSON、XML、YAML 形式の ビジネスコンテキストを直接付与し、アノテーションテーブルを通じて大規模にクエリできます。

❌ Before: アップデート前の課題
  • 新興リージョンでは S3 Metadata を利用できず、S3 Inventory や独自のメタデータ管理システムの構築が必要
  • データレジデンシー要件がある場合、S3 Metadata によるデータ発見の仕組みを導入できなかった
  • 特定条件のデータを探すために LIST オペレーションの繰り返しやカスタムインデックスの維持が必要
→
✅ After: アップデート後の改善
  • 追加 6 リージョンでもメタデータを自動収集し SQL でクエリ可能に
  • アノテーションテーブルでビジネスコンテキストを大規模にクエリ可能に
  • データレジデンシー要件のあるワークロードでも、リージョン内で完結するメタデータ管理と検索が可能に

S3 汎用バケットへのオブジェクト操作が S3 Metadata によって自動的に Apache Iceberg 形式のメタデータテーブルへ反映され、 Amazon Athena などの分析サービスから SQL でクエリできる構成です。

⚡ 主要機能

🌏 1. 6 リージョンへの提供拡大
  • アジアパシフィック (ハイデラバード・マレーシア・ニュージーランド・台北・タイ)、メキシコ (中部) で利用可能に
  • 今回の拡大により合計 38 の AWS リージョンで一般提供
  • データレジデンシー要件のあるリージョンでもメタデータ駆動のデータ発見が可能
🔄 2. 自動メタデータ収集とクエリ
  • 新規オブジェクトと既存オブジェクトの両方に対してメタデータを自動収集
  • ほぼリアルタイムで更新され、読み取り専用のフルマネージド Apache Iceberg テーブルに保存
  • システム定義メタデータ (作成日時、ストレージクラスなど)、カスタムメタデータ (タグなど)、イベントメタデータ (更新・削除イベントとリクエスト元アカウントなど) を記録
🏷️ 3. Annotations によるビジネスコンテキストの付与
  • JSON、XML、YAML 形式でオブジェクトごとに最大 1 GB のアノテーションを付与可能
  • アノテーションテーブルを有効化することで、内容を大規模に SQL でクエリ可能
  • アノテーションキーや内容に基づくオブジェクトの発見・取得、オブジェクト間での相関分析が可能

🔧 技術仕様

📊 S3 Metadata のテーブル構成

テーブル必須/任意内容
📓 ジャーナルテーブル必須 設定作成後の変更イベント (アップロード、更新、削除など) をほぼリアルタイムで記録
📦 ライブインベントリテーブル任意 バケット内の全オブジェクトとバージョンの最新状態を提供。有効化時にバックフィル処理が実行される
🏷️ アノテーションテーブル任意 オブジェクトに付与された最新のアノテーションを記録し、内容を直接クエリ可能にする

🗄️ テーブルの保存と管理

項目詳細
保存先AWS マネージド S3 テーブルバケット (aws-s3 という名前、アカウント・リージョンごとに 1 つ)
テーブル形式Apache Iceberg (読み取り専用)
暗号化デフォルトで SSE-S3。テーブル作成時に SSE-KMS (カスタマーマネージドキー) を選択可能
メンテナンスコンパクションや未参照ファイルの削除を Amazon S3 が自動実行
レコード有効期限ジャーナルテーブルはレコード有効期限を設定可能 (最低 7 日間の保持が必要)
インベントリ更新バックフィル完了後、オブジェクトの更新は通常 1 時間以内に反映
クエリ方法Amazon Athena、Amazon EMR、Amazon Redshift のほか、Apache Spark、Apache Trino など Iceberg 対応エンジン

ステップ 1: メタデータテーブル設定の作成

Bash AWS CLI でメタデータテーブル設定を作成 
aws s3api create-bucket-metadata-configuration \
  --bucket amzn-s3-demo-bucket \
  --metadata-configuration '{
    "JournalTableConfiguration": {
      "RecordExpiration": {
        "Expiration": "ENABLED",
        "Days": 30
      }
    },
    "InventoryTableConfiguration": {
      "ConfigurationState": "ENABLED"
    }
  }'

ジャーナルテーブル (レコード有効期限 30 日) とライブインベントリテーブルを有効化します。インベントリテーブルは有効化後にバックフィル処理が実行されます。

ステップ 2: 設定の確認

Bash 設定内容とステータスの確認 
aws s3api get-bucket-metadata-configuration \
  --bucket amzn-s3-demo-bucket

インベントリテーブルのステータスが Backfilling から Active に変わるとクエリ可能になります。

ステップ 3: Athena でメタデータをクエリ

SQL 直近 1 日にアップロードされたオブジェクトを確認 
-- 直近 1 日にアップロードされたオブジェクトを確認
SELECT key, size, storage_class, last_modified_date
FROM "b_amzn_s3_demo_bucket"."journal"
WHERE record_type = 'CREATE'
  AND record_timestamp > (current_timestamp - interval '1' day)
ORDER BY record_timestamp DESC;

LIST オペレーションを繰り返すことなく、SQL だけで変更履歴を把握できます。

💼 ビジネス面

✓データ発見の高速化: 大量のオブジェクトから必要なデータを SQL で即座に特定でき、分析や AI/ML ワークロードのデータ準備時間を短縮
✓データレジデンシー対応: アジアパシフィックの新興リージョンやメキシコでデータを保持する要件があっても、リージョン内でメタデータ管理を完結
✓運用コスト削減: 独自のメタデータ管理システムやカスタムインデックスの構築・維持が不要

⚙️ 技術面

✓フルマネージドな Iceberg テーブル: コンパクションなどのメンテナンスを Amazon S3 が自動実行し、運用負荷なしで最適なクエリ性能を維持
✓ほぼリアルタイムの更新: オブジェクトの変更がほぼリアルタイムでジャーナルテーブルに反映され、鮮度の高いメタデータに基づいた処理が可能
✓豊富なクエリエコシステム: Athena、EMR、Redshift に加え、Apache Spark や Apache Trino など Iceberg 対応エンジンからクエリ可能

⚠️ デメリット・制約事項

🚫 制限事項

✗ジャーナルテーブルは、メタデータテーブル設定を作成した後に発生した変更イベントのみを記録 (作成前のイベントは記録されない)
✗メタデータテーブルは読み取り専用であり、Amazon S3 以外の IAM プリンシパルによる変更はできない (削除は可能)
✗ジャーナルテーブルのレコード有効期限は最低 7 日間の保持が必要
✗利用可能なリージョンは 38 リージョンであり、すべての AWS リージョンでは利用できない

🤔 考慮すべき点

⚠ライブインベントリテーブルの有効化時にはバックフィル処理に対する課金が発生し、オブジェクト数によっては完了まで数時間かかる場合がある (最低 15 分)
⚠10 億オブジェクトを超えるバケットでは、ライブインベントリテーブルに月額料金が発生
⚠インベントリテーブルへの更新反映は通常 1 時間以内であり、ジャーナルテーブルと比較すると鮮度が低い点を考慮した使い分けが必要

🎯 ユースケース

🤖 ユースケース 1: AI/ML トレーニングデータのキュレーション

シナリオ: ハイデラバードリージョンに保存した大量の画像データから、特定のアノテーションが付与されたオブジェクトのみをモデルトレーニングに使用したい。

SQL検証済みラベル付きオブジェクトの抽出
SELECT o.key, o.size
FROM "b_training_data_bucket"."annotation" a
JOIN "b_training_data_bucket"."inventory" o
  ON a.key = o.key
WHERE a.annotation_key = 'label'
  AND a.annotation_content LIKE '%"verified": true%';
✅ 効果: 検証済みラベルを持つオブジェクトのみを SQL で抽出でき、トレーニングデータの準備時間を大幅に短縮できる。
🔒 ユースケース 2: セキュリティ・コンプライアンス監査

シナリオ: メキシコ (中部) リージョンのバケットで、SSE-KMS で暗号化されていないオブジェクトを定期的に検出したい。

SQL暗号化ポリシー非準拠オブジェクトの検出
SELECT key, encryption_status, storage_class
FROM "b_compliance_bucket"."inventory"
WHERE encryption_status != 'SSE-KMS';
✅ 効果: バケット全体をスキャンするカスタムスクリプトを実行することなく、暗号化ポリシーに準拠していないオブジェクトを即座に特定できる。
🔄 ユースケース 3: データ変更の追跡とパイプライン連携

シナリオ: タイリージョンのデータレイクで、新規に到着したデータのみを下流の ETL パイプラインで処理したい。

SQL新規到着データの増分抽出
SELECT key, record_timestamp
FROM "b_datalake_bucket"."journal"
WHERE record_type = 'CREATE'
  AND record_timestamp > TIMESTAMP '2026-10-15 00:00:00'
ORDER BY record_timestamp;
✅ 効果: S3 イベント通知の個別処理や LIST オペレーションの繰り返しが不要になり、増分処理パイプラインをシンプルに実装できる。

💰 料金

S3 Metadata の料金は、以下に対して発生します。

  • 📓 ジャーナルテーブルへの更新: オブジェクト数ベースの課金
  • 🗄️ メタデータテーブルのストレージ: テーブルの保存容量に対する課金
  • 📦 ライブインベントリテーブル: 有効化時のバックフィル処理に対する課金。10 億オブジェクトを超えるバケットでは月額料金が発生

詳細は Amazon S3 の料金ページ を参照してください。

📝 まとめ

Amazon S3 Metadata が 6 リージョンに拡大し、合計 38 リージョンで利用可能になりました。 アジアパシフィックの新興リージョンやメキシコでデータレジデンシー要件を持つワークロードでも、 自動収集されたメタデータとアノテーションを SQL でクエリするデータ発見の仕組みを導入できます。

💡 該当リージョンで S3 を利用している場合は、メタデータテーブル設定を有効化し、 データ分析や AI/ML ワークロードのデータ準備の効率化を検討することを推奨します。
