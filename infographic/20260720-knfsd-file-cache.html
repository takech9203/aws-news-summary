KNFSD File Cache (AWS Solutions Guidance) プレビュー

スケーラブルな高速 NFS キャッシュを AWS 上に展開

📅 2026 年 7 月 20 日

📌 概要

AWS は、スケーラブルで高速な NFS (Network File System) キャッシュを AWS 上に展開するためのオープンソースソリューション 「KNFSD File Cache」のプレビュー提供を開始しました。KNFSD は kernel NFS daemon の略称で、 Apache-2.0 ライセンスのもと GitHub 上に公開されています。

KNFSD File Cache は、1 つ以上のソース NFS サーバーからエクスポートをマウントし、AWS 内の NFS クライアントに対して再エクスポートする キャッシングプロキシとして動作します。ソースはオンプレミス、別の AZ / リージョン、 あるいは AWS Interconnect 経由の別クラウド (マルチクラウド) に配置できます。頻繁に読み取られるデータをメモリとローカル NVMe にキャッシュすることで、 ファイルは高レイテンシーリンクを一度だけ通過し、その後はローカル VPC 速度でコンピュートフリートに提供されます。

🔄 アップデートによる変化

⚠️ Before - 課題
  • ❗ 高レイテンシーリンクを介した繰り返し読み取りがボトルネックに
  • ❗ バーストワークロードでソースファイラーへの負荷や WAN 帯域消費が課題
  • ❗ 高速キャッシュ層を独自構築するには設計・デプロイ・監視をゼロから整備が必要
➡
✅ After - 改善
  • ✓ メモリ + ローカル NVMe にキャッシュしローカル VPC 速度でデータ提供
  • ✓ Packer による AMI ビルドと Terraform モジュールで迅速にデプロイ
  • ✓ 70 以上のメトリクスを備えた CloudWatch ダッシュボードで詳細監視
💡 対象ワークロードは VFX レンダリング、シミュレーション、金融サービス、ヘルスケア / ライフサイエンス、半導体設計 (EDA)、気象予測、エネルギーといった読み取り負荷の高いバースト型コンピュートワークロードです。フロントに立てる対象はオンプレミスのファイラー、FSx for OpenZFS / FSx for NetApp ONTAP、および NFS v3 / v4.1 / v4.2 準拠のあらゆるファイラーです。

KNFSD File Cache がソース NFS サーバーとコンピュートフリートの間に立ち、頻繁に読み取られるデータをメモリ (L1) とローカル NVMe (L2) の 2 層でキャッシュすることで、高レイテンシーリンクの通過を最小化する構成を示しています。

⚡ 主要機能

🐧 標準 Linux カーネル技術による NFS 再エクスポート
  • nfs-kernel-server が NFS の再エクスポートを担当し、ソースを元のファイラーのように提供
  • FS-Cache (cachefilesd) が永続的なディスクキャッシュを提供
  • バイト範囲の読み書き、同期 / 非同期書き込み、write-through / write-around モードを完全サポート
🗂️ 2 層キャッシュアーキテクチャ
  • L1: Linux ブロックキャッシュ (RAM) による超低レイテンシーアクセス
  • L2: FS-Cache (ローカル NVMe) による高スループット・再起動をまたぐ永続化・テラバイト級容量
  • まず L1、次に L2 を確認し、完全なミス時のみソースファイラーから取得
🚀 柔軟なデプロイと自動スケーリング
  • Packer でキャッシュ AMI をビルドし、付属の Terraform モジュールでクラスターをデプロイ
  • AMD / Intel / AWS Graviton インスタンス上の EC2 Auto Scaling グループで稼働
  • クライアントトラフィックは DNS ラウンドロビンまたは Network Load Balancer で分散
📈 豊富な監視機能
  • CloudWatch ダッシュボードが OpenTelemetry ベースのエージェント経由で 70 以上のメトリクスを公開
  • Prometheus や Grafana などサードパーティツールへのメトリクス発行にも対応

🔧 技術仕様

2 層キャッシュの構成

レイヤー技術メディア特性
L1Linux ブロックキャッシュRAM超低レイテンシー、インスタンスメモリで上限が決まる
L2FS-Cache (cachefilesd)ローカル NVMe高スループット、再起動をまたいで永続化、テラバイト級容量

ファンアウトアーキテクチャ (オプション)

高レイテンシー / 低帯域リンク向けに、2 段構成のファンアウトアーキテクチャを利用できます。

ティア役割
ティア 1ソースファイラーとの通信をすべて担当する高メモリプロキシ。各ファイルが WAN を一度だけ通過することを保証
ティア 2ローカル VPC で多数のクライアントに提供する小型プロキシのクラスター。キャッシュのハイドレーションを維持しながらスケール

📝 自動スケーリングの考え方: スケーリングは CPU ではなくインスタンスあたりのアクティブな NFS 接続数というカスタム CloudWatch メトリクスに基づきます。CPU はプロキシ負荷を十分に反映しないためです。スケールダウンはウォームキャッシュの破棄やアクティブ NFS マウントの切断につながるため、意図的にスケールアップのみとし、スケールダウンは利用者独自のスケジュールで手動実行します。

🛠️ 設定方法

前提条件

必要なもの

  • VPC のサブネットが用意されていること
  • ソース NFS サーバー (オンプレミス、FSx、他クラウドなど) のエクスポートにアクセスできること

接続要件

  • オンプレミスや別クラウドをソースとする場合、AWS Site-to-Site VPN、AWS Direct Connect、または AWS Interconnect による接続が確立されていること

手順

1
AMI のビルド
Bash Packer でキャッシュ AMI をビルド 
# Packer でキャッシュ AMI をビルド
packer build knfsd.pkr.hcl

NFS 再エクスポートと FS-Cache を有効化したチューニング済みカーネル、メトリクスエージェント、HTTP ヘルスチェックエージェント、スモークテストを含む Ubuntu AMI を x86 (Intel/AMD) と ARM64 (AWS Graviton) 向けに生成します。

2
Terraform によるクラスターのデプロイ
Bash Terraform モジュールでデプロイ 
# Terraform モジュールでキャッシュクラスターをデプロイ
terraform init
terraform apply

Auto Scaling グループ、セキュリティグループ、ヘルスチェック、DNS レコード、オプションのロードバランサー、FSID データベースを含むクラスターをデプロイします。必要な入力は VPC サブネット、ビルド済み AMI、ソース NFS エクスポートのみです。

3
クライアントからのマウント

クライアントは特別なドライバーを必要とせず、通常の NFS 共有と同様にキャッシュをマウントします。トラフィックは DNS ラウンドロビンまたは Network Load Balancer 経由で各キャッシュノードに分散されます。

⚖️ メリットと考慮点

💼 ビジネス面のメリット

  • ライセンスコスト不要: オープンソース (Apache-2.0)、消費した AWS リソース料金のみ
  • データ移行の回避: データを移行・複製せず既存 NFS ストレージを AWS に拡張
  • コスト効率: キャッシュが KNFSD 層に永続化されるため下流コンピュートを EC2 スポットで実行可能

🔬 技術面のメリット

  • 標準技術ベース: 独自エージェント不要、あらゆる NFSv3/v4 クライアントを変更なしで利用
  • 高いスループット: ローカル VPC 速度で提供し高レイテンシーリンクの通過を最小化
  • 詳細な可観測性: 70 以上のメトリクスと事前構築済みダッシュボードでキャッシュヒット率を監視

🚧 制限事項

  • 現時点ではプレビュー提供であり、本番利用には十分な検証が必要
  • 読み取り負荷の高いワークロードが主対象で、書き込み中心には最適化されていない
  • スケールダウンはウォームキャッシュの破棄を伴うため自動化されておらず手動実施が必要

🔍 考慮すべき点

  • キャッシュ容量はインスタンスのメモリと NVMe サイズに依存するため、タイプ選定が重要
  • 最新のインスタンスタイプと料金は EC2 の公式ドキュメントで確認すること
  • AWS マネージドサービスではなく、利用者が運用管理を行うソリューション

🎯 ユースケース

1️⃣ メディア / エンターテインメントのレンダーファーム
シナリオ: オンプレミスのファイラーに保存された大量のアセットを、AWS 上の VFX レンダリングフリートから読み取る。
効果: アセットが WAN を一度だけ通過し、以降はローカル VPC 速度で多数のレンダリングノードに提供されるため、レンダリング時間を短縮できる。
2️⃣ HPC シミュレーションと EDA
シナリオ: 金融サービスのシミュレーションや半導体設計 (EDA) で、共通の入力データセットを多数のコンピュートインスタンスが繰り返し読み取る。
効果: キャッシュヒットにより読み取りレイテンシーを削減し、EC2 スポットインスタンスと組み合わせてコスト効率よく大規模な並列処理を実行できる。
3️⃣ マルチリージョン / マルチクラウドのデータアクセス
シナリオ: 別リージョンや別クラウドに配置された中央 NFS ソースに対し、AWS 上のコンピュートからアクセスする。
効果: データをローカルにキャッシュすることで中央ソースへのレイテンシーを排除し、データの複製なしにマルチリージョン / マルチクラウド構成を実現できる。

💰 料金と利用可能リージョン

💵 料金

オープンソースソリューションのためライセンスコストは不要。消費した AWS リソース (EC2、EBS/NVMe、データ転送、CloudWatch など) の料金のみを支払います。参考値として im4gn.16xlarge は 10〜12 GB/s のスループットを提供し、i3en.24xlarge と同等性能をオンデマンド料金でおよそ半分のコストで実現。集約スループットのコストは 100 Gb/s あたり 1 時間 6 ドル未満とされています。

🌍 利用可能リージョン

プレビューとして、すべての AWS リージョンで利用可能です。

📝 まとめ

KNFSD File Cache は、既存の NFS ストレージを AWS に拡張し、読み取り負荷の高いバースト型コンピュートワークロードを高速化する オープンソースソリューションです。標準の Linux カーネル技術をベースにライセンスコストなしで導入でき、 Packer と Terraform による自動デプロイと 70 以上のメトリクスによる監視を備えています。VFX レンダリング、HPC、EDA、金融シミュレーションなどで オンプレミスや別クラウドのファイラーへのアクセスに課題を抱えている場合は、まずプレビュー環境でキャッシュヒット率などの効果を検証することを推奨します。
