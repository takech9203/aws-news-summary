BFPO & SCOP

📌 概要

AWS Batch が、コンピューティング環境におけるインスタンスタイプの優先順位をより細かく制御できる 2 つの新しい割り当て戦略を発表しました。

ワークロード固有のパフォーマンス特性に基づいて、インスタンスタイプの選択順序をユーザー自身が手動で定義できます。AWS Batch API (CreateComputeEnvironment / UpdateComputeEnvironment) およびマネジメントコンソールの両方から利用でき、AWS Batch が利用可能なすべての AWS リージョンでサポートされます。

🔄 Before / After

❌ アップデート前の課題

  • オンデマンド環境の BEST_FIT_PROGRESSIVE では vCPU あたりコストが優先され、特定タイプを先頭に置けなかった
  • スポット環境では容量・価格に基づく自動選択のみで、ユーザー定義の優先順位を反映できなかった
  • ワークロード固有の特性 (CPU アーキテクチャ・ネットワーク性能) に最適化したタイプを優先する手段がなかった

✅ アップデート後の改善

  • instanceTypes リストに記載した順序でインスタンスタイプが選択される
  • 最適なタイプを優先しつつ、フォールバックの順序も制御できる
  • スポット環境では容量を最優先しつつ、ベストエフォートでユーザー定義の優先順位を尊重できる

BFPO は順序を厳密に尊重し、SCOP は容量を優先しつつベストエフォートで順序を尊重します。

🔧 主要機能

📋 Best Fit Progressive Ordered (BFPO)

BEST_FIT_PROGRESSIVE_ORDERED
  • オンデマンドインスタンス (EC2) コンピューティングリソース専用
  • instanceTypes リストに記載された順序でインスタンスタイプを選択
  • ファミリー指定時、ファミリー内サイズは BEST_FIT_PROGRESSIVE ロジックで展開 (最適サイズ優先、大きいサイズはフォールバック)
  • ジョブのリソース要件を満たせないインスタンスタイプはスキップ

📋 Spot Capacity Optimized Prioritized (SCOP)

SPOT_CAPACITY_OPTIMIZED_PRIORITIZED
  • スポットインスタンスコンピューティングリソース専用
  • 容量を最優先に最適化しつつ、ユーザー定義の優先順位をベストエフォートで尊重
  • 容量プールが同程度に利用可能な場合は優先順位が尊重される
  • 容量が制約されている場合は、中断可能性を最小化するため最も利用可能なプールから選択

🔀 ファミリーと明示的タイプの混在

  • instanceTypes にはファミリー (例: m7a) と明示的タイプ (例: m7a.4xlarge) を混在できる
  • 同じファミリーのファミリー名と明示的タイプ両方がある場合、明示的タイプはリストの位置に配置され、ファミリー展開から除外される
  • 例: ["m7a.4xlarge", "m7a", "m6a"] では m7a.4xlarge が常に最初に配置される

📊 技術仕様: 割り当て戦略の比較

割り当て戦略対象環境順序の扱い
BEST_FIT (デフォルト)オンデマンド/スポット最低コストを優先 (順序指定なし)
BEST_FIT_PROGRESSIVEオンデマンドvCPU あたりコストが低いものを優先
BEST_FIT_PROGRESSIVE_ORDERED新規オンデマンド指定順序を厳密に尊重
SPOT_CAPACITY_OPTIMIZEDスポット中断されにくいものを優先
SPOT_PRICE_CAPACITY_OPTIMIZEDスポット価格と容量を最適化
SPOT_CAPACITY_OPTIMIZED_PRIORITIZED新規スポット容量を優先しつつベストエフォートで順序を尊重

📜 API 変更履歴

日付サービス変更内容
2026/06/18batch3 updated api methods - 順序付き割り当て戦略のサポートを追加

対象 API メソッドは CreateComputeEnvironment、UpdateComputeEnvironment、DescribeComputeEnvironments の 3 つで、いずれも computeResources.allocationStrategy パラメータに新しい列挙値が追加されました。

ステップ 1: 割り当て戦略の選択

オンデマンド環境では BEST_FIT_PROGRESSIVE_ORDERED、スポット環境では SPOT_CAPACITY_OPTIMIZED_PRIORITIZED を選択します。

ステップ 2: コンピューティング環境の作成

Bashcreate-compute-environment
aws batch create-compute-environment \
  --compute-environment-name ordered-ondemand-env \
  --type MANAGED \
  --state ENABLED \
  --compute-resources '{
    "type": "EC2",
    "allocationStrategy": "BEST_FIT_PROGRESSIVE_ORDERED",
    "minvCpus": 0,
    "maxvCpus": 256,
    "instanceTypes": ["m7a.4xlarge", "m7a", "m6a"],
    "subnets": ["subnet-xxxxxxxx"],
    "instanceRole": "ecsInstanceRole"
  }'

ステップ 3: 既存環境の更新

Bashupdate-compute-environment
aws batch update-compute-environment \
  --compute-environment ordered-ondemand-env \
  --compute-resources '{
    "allocationStrategy": "BEST_FIT_PROGRESSIVE_ORDERED",
    "instanceTypes": ["c7a", "c6a"]
  }'

UpdateComputeEnvironment API でも新しい割り当て戦略を指定できます。

💡 メリット

📈 ビジネス面

  • パフォーマンス最適化: 最適なインスタンスタイプを優先し処理性能を向上
  • コスト管理の柔軟性: コストとパフォーマンスのバランスを調整
  • 既存ワークフローとの統合: API とコンソール両対応で組み込みやすい

⚙️ 技術面

  • 明示的な順序制御: リスト順がそのまま選択優先順位に反映 (BFPO)
  • スポット容量との両立: 容量優先で中断リスクを抑制 (SCOP)
  • 柔軟な指定方法: ファミリーと明示的タイプを混在指定可能

⚠️ デメリット・制約事項

制限事項

✗BFPO はオンデマンド (EC2) 専用、SCOP はスポット専用で相互に使用不可
✗Fargate リソースには適用できない
✗高度な戦略であり、順序設定を誤ると非効率な結果を招く可能性がある

考慮すべき点

⚡大きなタイプを先頭に置くと、小さなジョブで過剰プロビジョニングになる可能性
⚡小さなタイプを先頭に置くと、maxvCpus 到達前に EC2 のインスタンス数上限に達する可能性
⚡SCOP の優先順位はベストエフォート。容量制約時は最も利用可能なプールが選択される
⚡BEST_FIT 以外でオンデマンドを使う場合、容量要件のため maxvCpus を超えることがある (最大 1 インスタンス分まで)

🎯 ユースケース

1. 特定の CPU アーキテクチャを優先する HPC ワークロード

シナリオ: 特定世代の CPU で最適化された HPC アプリを実行し、その世代のタイプを優先的に使用したい。

JSON
{
  "allocationStrategy": "BEST_FIT_PROGRESSIVE_ORDERED",
  "instanceTypes": ["c7a", "c6a", "c5"]
}

効果: 最新世代の c7a を優先しつつ、不足時は c6a、c5 へフォールバックし、性能維持と安定スケーリングを両立。

2. コスト効率の高いスポットインスタンスの優先利用

シナリオ: バッチ処理をスポットで実行し、特定タイプを優先しつつスポット中断リスクを最小化したい。

JSON
{
  "allocationStrategy": "SPOT_CAPACITY_OPTIMIZED_PRIORITIZED",
  "instanceTypes": ["m7a", "m6a", "m5"]
}

効果: 容量を最優先で確保しつつ、同程度に利用可能なら優先度の高い m7a を選択し、中断リスクを抑制。

3. 特定タイプの固定とファミリーのフォールバック併用

シナリオ: 特定サイズを最優先で使用しつつ、不足時には同ファミリーや別ファミリーへフォールバックさせたい。

JSON
{
  "allocationStrategy": "BEST_FIT_PROGRESSIVE_ORDERED",
  "instanceTypes": ["m7a.4xlarge", "m7a", "m6a"]
}

効果: m7a.4xlarge を常に最優先で配置し、不足時は m7a 他サイズ、さらに m6a へフォールバックする柔軟な構成。

💰 料金・リージョン・関連サービス

💴 料金

この機能自体に追加料金はありません。AWS Batch の利用に料金はかからず、ジョブ実行に使用した AWS リソース (EC2 インスタンスなど) に対してのみ料金が発生します。料金は使用するインスタンスタイプ (オンデマンド/スポット) に応じて変動します。

🌍 利用可能リージョン

AWS Batch が利用可能なすべての AWS リージョンで利用できます。

🔗 関連サービス・機能

  • Amazon EC2: コンピューティングリソースとして利用され、本機能で選択順序を制御する対象
  • Amazon EC2 スポットインスタンス: SCOP 戦略の対象リソース
  • Amazon ECS / Amazon EKS: AWS Batch のジョブ実行基盤となるコンテナオーケストレーション

✅ まとめ

今回のアップデートにより、AWS Batch でインスタンスタイプの選択順序を明示的に制御できるようになりました。ワークロード固有のパフォーマンス特性に基づいてインスタンスタイプを優先したいユーザーにとって、BFPO (オンデマンド) と SCOP (スポット) は強力な選択肢となります。既存環境でも UpdateComputeEnvironment で適用できるため、現在の割り当て戦略を見直し、ワークロードに最適なインスタンスタイプ順序の設定を検討することをお勧めします。
