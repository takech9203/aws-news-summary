Amazon ECS 📅 2026 年 10 月 28 日

🚀 ECS Managed Instances
クロスインスタンス統合と Spot 統合

フリート全体を横断したタスク再配置で、使用率を最大化しコストを自動削減

📝 概要

Amazon ECS Managed Instances に、インフラストラクチャ最適化を強化する 2 つの新機能 が追加されました。 「クロスインスタンス統合」は複数の低使用率インスタンスのタスクをまとめて評価し、より少ないインスタンスへ再配置 (パッキング) します。 「Spot 統合」は同じアプローチを Spot キャパシティにも適用し、代替キャパシティの確保を確認してから元のインスタンスを回収します。

フリートを継続的にモニタリングし、start-before-stop (先に起動してから停止する) 方式のグレースフルなタスク置換により、アプリケーションの可用性を維持しながらアイドルキャパシティを回収します。

⚠️ Before: アップデート前の課題

  • インスタンスごとに個別に最適化を評価していたため、複数インスタンスにまたがる再配置機会を活用できなかった
  • 利用可能なインスタンスタイプの範囲が狭い場合、個別評価による最適化の効果が限定的だった
  • Spot インスタンスは低使用率でも統合による回収が行われなかった

✅ After: アップデート後の改善

  • 複数インスタンスのタスクを同時に評価し、より少ないインスタンスへパッキングして使用率を大幅に向上
  • Spot キャパシティも代替キャパシティの存在を確認したうえで安全に統合
  • 追加料金なしで、既存・新規のすべてのキャパシティプロバイダーに自動適用

複数の低使用率インスタンスにまたがるタスクを同時に評価し、代替キャパシティを先に起動してからタスクを移行する start-before-stop 方式で、可用性を維持しながらフリートをより少ないインスタンスへ統合する流れ

⚙️ 主要機能

1️⃣ クロスインスタンス統合 (cross-instance consolidation)

✓ 複数の低使用率インスタンスで実行中のタスクをまとめて評価し、より少ないインスタンスへパッキング

✓ 従来のインスタンス単位の評価と異なり、フリート全体を横断した再配置が可能

✓ インスタンスタイプの選択範囲が狭いキャパシティプロバイダーでも高い統合効果を発揮

2️⃣ Spot 統合 (Spot consolidation)

✓ 低使用率の Spot インスタンスも統合の対象に (2026 年 10 月 26 日以降)

✓ Spot をドレインする前に代替キャパシティを起動し、置換タスクが RUNNING 状態になるのを待ってから元のインスタンスを回収

✓ サービスの最小・最大タスク数制限とタスク保護設定を尊重し、コスト最適化と可用性のバランスを維持

3️⃣ 安全なタスク置換メカニズム

✓ 低使用率インスタンスを DRAINING 状態にし、タスクをより効率的なインスタンスへ移行

✓ 全タスクの移行完了後、DEREGISTERING 状態に遷移して EC2 インスタンスを安全に終了

✓ サービスタスクを実行するインスタンスが対象 (スタンドアロンタスクは対象外)

4️⃣ 自動適用

✓ 既存・新規のすべての ECS Managed Instances キャパシティプロバイダーに追加設定なしで自動適用

✓ 追加料金は発生しない

🔬 技術仕様

インフラストラクチャ最適化の種類

最適化の種類動作
アイドルインスタンス検出実行中タスクがないインスタンスを検出し、DEREGISTERING 状態にして EC2 インスタンスを終了
低使用率インスタンス検出タスク分散を分析し、複数インスタンスのタスクをより少ないインスタンスへ統合 (今回のアップデートでクロスインスタンス評価に強化)
Spot 統合低使用率の Spot インスタンスを、代替キャパシティ確保後に回収 (2026 年 10 月 26 日以降)

ScaleInAfter 設定

最適化アクションのタイミングは、キャパシティプロバイダー設定の ScaleInAfter で制御できます。

設定値動作
0〜3600 (秒)インスタンスがアイドルまたは低使用率になってから最適化を開始するまでの遅延時間
-1インフラストラクチャ最適化を無効化
未指定ECS Managed Instances がデフォルト設定に基づいて最適なタイミングを自動判断
💡 待機期間中に新しいタスクが起動した場合、アイドルインスタンスの終了はキャンセルされます。低使用率インスタンスは、待機期間中のタスク起動・停止によりタイマーがリセットされ、新しい待機期間の満了後に再評価されます。

🛠️ 設定方法

前提条件

✓Amazon ECS クラスターで Managed Instances キャパシティプロバイダーを使用していること
✓統合の対象はサービスタスクを実行するインスタンス (スタンドアロンタスクは対象外)
✓特別な有効化手順は不要 (既存・新規のキャパシティプロバイダーに自動適用)

ステップ 1: キャパシティプロバイダーの確認

Bash キャパシティプロバイダーの設定確認 
aws ecs describe-capacity-providers \
  --capacity-providers my-managed-instances-cp \
  --region ap-northeast-1

クロスインスタンス統合と Spot 統合は自動的に適用されるため、追加の有効化操作は不要です。

ステップ 2: ScaleInAfter による最適化タイミングの調整 (オプション)

Bash 最適化開始までの待機時間を 600 秒に設定 
aws ecs update-capacity-provider \
  --name my-managed-instances-cp \
  --managed-instances-provider '{
    "infrastructureOptimization": {
      "scaleInAfter": 600
    }
  }' \
  --region ap-northeast-1

ワークロードの変動が大きい場合は長めに設定することで、不要な統合と再スケールアウトの繰り返しを抑制できます。-1 を指定すると最適化を無効化できます。

ステップ 3: 統合動作のモニタリング

Bash DRAINING 状態のインスタンスを確認 
aws ecs list-container-instances \
  --cluster my-cluster \
  --status DRAINING \
  --region ap-northeast-1

統合処理中のインスタンスは DRAINING 状態となり、タスク移行完了後に DEREGISTERING 状態へ遷移して EC2 インスタンスが終了されます。CloudWatch の使用率メトリクスとあわせて、統合によるフリートの変化を確認できます。

💡 メリットと制約事項

✅ ビジネス面のメリット

✓インフラコストの削減: フリート全体のインスタンス数を削減 (AWS テストでは 19 台から 13 台へ約 32% 削減)
✓追加コストなし: 両機能とも追加料金なしで利用でき、既存環境にも自動適用
✓運用負荷の軽減: ビンパッキングやインスタンス入れ替えの複雑な最適化判断を AWS に委任

✅ 技術面のメリット

✓使用率の大幅な向上: CPU / メモリ使用率を 90% 近くまで高められる
✓可用性を維持した統合: start-before-stop 方式でサービス断が発生しにくい
✓Spot でも安全な最適化: 代替キャパシティの存在を確認してから回収

⚠️ 制限事項

✗統合の対象はサービスタスクを実行するインスタンスのみ (スタンドアロンタスクは対象外)
✗ECS Managed Instances 専用 (自己管理の EC2 キャパシティプロバイダーや Fargate には適用されない)
✗ScaleInAfter の設定範囲は 0〜3600 秒 (または -1 で無効化)

🤔 考慮すべき点

⚠統合時にタスクの再配置が発生するため、起動に時間がかかるタスクや状態を持つタスクでは置換の影響を考慮する
⚠デプロイ設定が適切でない場合は統合の効果が限定される可能性がある
⚠統合を避けたいワークロードでは ScaleInAfter に -1 を設定して無効化できる

🎯 ユースケース

1️⃣ インスタンスタイプを限定したキャパシティプロバイダーのコスト最適化

シナリオ: ライセンスや性能要件により特定のインスタンスファミリー (例: c9g) のみを使用しており、従来のインスタンス単位の最適化では効果が限定的だった。

実装: キャパシティプロバイダー設定で c9g ファミリーに限定 → クロスインスタンス統合が自動適用され、複数の低使用率インスタンスのタスクを少数のインスタンスへ再配置。

💰 効果: インスタンスタイプの選択範囲が狭くても、フリート横断の評価により高い使用率とコスト削減を実現
2️⃣ Spot キャパシティを活用したバッチ・開発環境のコスト削減

シナリオ: 開発環境や中断耐性のあるサービスを Spot インスタンスで運用しており、低使用率の Spot インスタンスが残り続けてコストが無駄になっていた。

実装: Managed Instances キャパシティプロバイダーで Spot を使用 → Spot 統合が代替キャパシティを先に起動し、置換タスクの RUNNING 確認後に元の Spot インスタンスを回収。

💰 効果: Spot の割引メリットを享受しながら、低使用率インスタンスの自動回収でさらにコストを削減。可用性は start-before-stop 方式で維持
3️⃣ トラフィック変動の大きい Web サービスのフリート効率化

シナリオ: 日中のピーク後にタスク数が減少し、夜間に低使用率のインスタンスが多数残る Web サービスを運用している。

実装: ScaleInAfter を 600 秒に設定 → タスク減少後 10 分間の安定を確認してから統合を開始し、夜間のフリートを自動的に縮小。

💰 効果: スケールインの繰り返しによるタスク置換の頻発を抑えつつ、オフピーク時間帯のインフラコストを自動的に削減

💰 料金と利用可能リージョン

💵 料金

クロスインスタンス統合および Spot 統合は追加料金なしで利用できます。ECS Managed Instances の通常料金 (使用する EC2 インスタンスの料金および Managed Instances の管理料金) のみが適用されます。統合によりインスタンス数が削減されるため、実質的なコスト削減効果が期待できます。

🌍 利用可能リージョン

ECS Managed Instances が利用可能なすべての AWS リージョンで利用できます (公式発表では「all AWS Regions」と記載)。既存および新規のすべての ECS Managed Instances キャパシティプロバイダーに自動的に適用されます。

📌 まとめ

ECS Managed Instances のクロスインスタンス統合と Spot 統合により、フリート全体を横断したタスクの再配置が自動化され、追加料金なしで大幅な使用率向上とコスト削減が期待できます。 既存のキャパシティプロバイダーにも自動適用されるため、まずは CloudWatch メトリクスでフリートの使用率変化を確認し、必要に応じて ScaleInAfter でタイミングを調整することを推奨します。
