Amazon SageMaker HyperPod

🕵️ Slurm クラスターでのハングジョブ検出と復旧

📅 リリース日: 2026 年 11 月 23 日 ｜ 機能: Hung Job Detection (ハングしたトレーニングジョブの検出と復旧)

📝 概要

Amazon SageMaker HyperPod が、Slurm オーケストレーションクラスター上でハング (進捗停止) したトレーニングジョブの検出に対応しました。 進捗が止まったジョブを数分以内に特定して Amazon CloudWatch にイベントを書き込み、オプションでジョブをキャンセルして Slurm のジョブキューに戻します。 ジョブは GPU をアイドル状態で占有し続ける代わりに、最後のチェックポイントから再開できます。

検出エージェントは各ノード上で動作し、ジョブの出力 (stdout)、GPU アクティビティ、ユーザー定義のログパターン (トレーニングステップのメッセージや NCCL エラーなど) を監視します。 環境変数 HYPERPOD_HANG_RULES でルールファイルを指定するだけで有効化でき、トレーニングスクリプトやコンテナの変更は不要です。

❌ Before: 手動運用に依存
  • NCCL タイムアウトやデッドロックでハングしても、GPU を保持したまま Slurm 上は「実行中」と報告され続けた
  • 誰かが手動で気付くまで、高価な GPU がアイドル状態で占有され続けた
  • 既存の auto-resume はハードウェア障害で終了したジョブが対象で、終了せずにハングするジョブはカバー外
✅ After: 検出から復旧まで自動化
  • 出力、GPU アクティビティ、ログパターンに基づき、ハングを数分以内に自動検出
  • 検出イベントを CloudWatch に記録し、オプションで自動キャンセル + requeue が可能
  • 環境変数の指定だけで有効化。コードやコンテナの変更なしに主要フレームワークで利用可能

⚙️ 主要機能

🔍 1. デフォルト検出 (出力と GPU アクティビティの監視)
  • ルールファイルに {"enabled": true} のみを記述すると、stdout と GPU アクティビティを監視するデフォルト検出を使用
  • GPU がメモリを保持したままアイドル状態で、出力が長時間停止している場合にハングと判定 (ランデブーハングを捕捉)
  • GPU の状態にかかわらず、出力がさらに長い期間停止した場合もハングと判定
📐 2. カスタム検出ルール (ログパターン監視)
  • RE2 正規表現 (最大 256 文字) でログパターンを定義し、ステップやエポックの進捗を追跡
  • timeout_minutes 内にパターンがマッチしない場合にハングと判定
  • fault_on_match で NCCL エラーなどの出現時に即座にハングと判定
  • stop_pattern、start_timeout_minutes、metric_evaluation_data_points などの調整が可能
  • 1 ファイルに最大 20 ルール、サイズは最大 1 MB
🔔 3. 検出時のアクションと CloudWatch 連携
  • action_policy.action に notify (デフォルト、記録のみ) または cancel (キャンセルも実行) を指定
  • Slurm はデフォルトでキャンセルされたジョブを requeue し、最後のチェックポイントから再開可能 (#SBATCH --no-requeue で停止のみも可)
  • イベントは HANG_DETECTED、HANG_ACTION_TAKEN、CONFIG_ERROR として CloudWatch に記録
🧩 4. フレームワーク非依存のシンプルな有効化
  • 環境変数 HYPERPOD_HANG_RULES にルールファイルのパスを指定するだけでジョブ単位に有効化
  • トレーニングスクリプトやコンテナの変更は不要。PyTorch、TensorFlow、JAX、カスタムスクリプトに対応
  • srun --no-hang-detection で特定のジョブステップのみ無効化も可能

🔬 技術仕様

📄 ルールファイルのフィールド

フィールド必須説明
enabledはいtrue で検出を有効化。false または未指定の場合は監視されない
monitoring.log_fileいいえ監視対象のログファイル。デフォルトは Slurm の出力ファイル (--output または slurm-{job-id}.out)
rulesいいえ最大 20 ルール。有効な log_pattern ルールはデフォルト検出を置き換える
action_policy.actionいいえnotify (デフォルト) はイベント記録のみ。cancel はジョブもキャンセル

📐 ルールのフィールド

フィールド必須説明
nameはいルール名。イベントに表示される
typeはいlog_pattern のみサポート
enabledいいえデフォルトは false。true で有効化
log_patternはいRE2 正規表現。最大 256 文字
timeout_minutes条件付きパターンが未マッチのまま許容される時間 (fault_on_match が true の場合は不要)
fault_on_matchいいえtrue の場合、マッチした時点でハングと判定。エラーパターン向け
stop_patternいいえマッチするとルールを無効化するパターン (例: Training complete)
start_timeout_minutesいいえジョブ開始から最初のマッチまでの最大時間。起動時のハングを捕捉
metric_evaluation_data_pointsいいえハング判定に必要な 10 秒間隔の連続失敗チェック回数。デフォルトは 1

📈 CloudWatch 検出イベント

項目詳細
ロググループ/aws/sagemaker/Clusters/{cluster-name}/{cluster-id}
ログストリームSageMakerHangJobDetectionEvents/{controller-instance-group-name}/{controller-instance-id}
イベントタイプHANG_DETECTED (ハング検出)、HANG_ACTION_TAKEN (キャンセル実行)、CONFIG_ERROR (ルールファイル不正)
JSON HANG_DETECTED イベントの例 
{
  "event_type": "HANG_DETECTED",
  "job_id": "12345",
  "step_id": "0",
  "node": "ip-172-22-230-3",
  "evidence": "stdout stale for 18 min and GPU idle with memory allocated",
  "layer": "signal_evaluator",
  "detected_at": "2026-04-22T00:58:47Z",
  "job_action": "notify",
  "config_source": "per_job_env_var"
}

layer フィールドはデフォルト検出 (signal_evaluator) とカスタムルール (pattern_evaluator) のどちらが発火したかを示します。

🛠️ 設定方法

📋 前提条件

✓SageMaker HyperPod の Slurm オーケストレーションクラスターを利用していること
✓既存クラスターの場合、クラスターソフトウェアを最新の AMI に更新していること (更新しない場合、ハングジョブ検出は利用不可)
✓マルチノードジョブの場合、ルールファイルを全コンピュートノードから読み取り可能な共有ストレージ (Amazon FSx for Lustre など) に配置すること
1
ルールファイルを作成する
Bash最小構成のルールファイル
echo '{"enabled": true}' > /fsx/my-project/rules.json

共有ストレージ上に検出を有効化するルールファイルを作成します。この最小構成では、ジョブの出力と GPU アクティビティを監視するデフォルト検出が使用され、ハング検出時にはイベントの記録のみが行われます。

2
ジョブ投入時に環境変数を設定する
Bashsbatch スクリプト
#SBATCH --export=ALL,HYPERPOD_HANG_RULES=/fsx/my-project/rules.json

HYPERPOD_HANG_RULES 環境変数にルールファイルのパスを指定します。この環境変数を設定したジョブのみが監視対象となります。多数のジョブに適用する場合は、シェルプロファイルやサイト共通のプロファイルスクリプトでも設定できます。

3
カスタムルールと自動キャンセルを設定する (推奨)
JSON進捗監視 + NCCL エラー即時検出 + 自動キャンセル
{
  "enabled": true,
  "rules": [
    {
      "name": "epoch_progress",
      "type": "log_pattern",
      "enabled": true,
      "log_pattern": "Epoch \\d+/\\d+ complete",
      "timeout_minutes": 45
    },
    {
      "name": "nccl_error",
      "type": "log_pattern",
      "enabled": true,
      "log_pattern": "NCCL error|NCCL WARN",
      "fault_on_match": true
    }
  ],
  "action_policy": {
    "action": "cancel"
  }
}

エポック完了のログが 45 分間出力されない場合、または NCCL エラーが出現した時点でハングと判定し、自動キャンセルする設定例です。キャンセルされたジョブは Slurm によって requeue され、最後のチェックポイントから再開されます。GPU がビジーのまま進捗しないジョブはデフォルト検出では捕捉できないため、進捗を追跡する log_pattern ルールを少なくとも 1 つ追加することが推奨されています。

4
検出イベントを確認する
BashCloudWatch Logs のフィルタリング
aws logs filter-log-events \
  --log-group-name /aws/sagemaker/Clusters/{cluster-name}/{cluster-id} \
  --log-stream-name-prefix SageMakerHangJobDetectionEvents/ \
  --filter-pattern '{ $.job_id = "12345" }'

CONFIG_ERROR は sbatch や squeue、ジョブ出力には表示されないため、新しいルールファイルは短いジョブでテストし、本番ジョブで使用する前にログストリームを確認してください。

💡 メリット

💼 ビジネス面

✓GPU コストの削減: ハングしたジョブが高価な GPU をアイドル状態で占有し続ける時間を数分以内の検出で最小化し、クラスターの投資対効果を向上
✓運用負荷の軽減: 進捗停止の手動監視が不要になり、オンコール対応や定期的なジョブ状態確認の工数を削減
✓トレーニング完了までの時間短縮: ハングからの自動復旧により、人が気付くまでの待ち時間なしでチェックポイントから再開可能

🔧 技術面

✓非侵襲的な導入: 環境変数の設定のみで有効化でき、トレーニングコードやコンテナイメージの変更が不要
✓フレームワーク非依存: PyTorch、TensorFlow、JAX、カスタムスクリプトなど、あらゆるワークロードで利用可能
✓柔軟な検出ルール: デフォルト検出に加え、RE2 正規表現によるログパターン監視、即時検出、誤検知低減など細かな調整が可能
✓可観測性との統合: 検出イベントが CloudWatch Logs に集約され、既存のモニタリングやアラートの仕組みと連携しやすい

⚠️ デメリット・制約事項

🚫 制限事項

✗デフォルト検出は、GPU がビジーのまま進捗しないジョブ (ループに陥ったジョブなど) を捕捉できない。ステップやエポックを追跡する log_pattern ルールの追加が推奨される
✗デフォルト検出は持続的な非アクティブ期間を待つため、検出は即時ではない。短いカスタムタイムアウトは検出を速くするが、チェックポイント保存などの正常な停止を誤検知する可能性がある
✗パターンは RE2 構文のみ対応。後方参照や先読み / 後読みを使用したパターンはコンパイルされず、そのルールはスキップされる
✗ルールファイルは最大 20 ルール、最大 1 MB。超過したファイルは拒否され、ジョブは監視されない
✗既存クラスターでは、最新の AMI へのクラスターソフトウェア更新が必要

🤔 考慮すべき点

⚠カスタムルールはそのジョブのデフォルト検出を置き換えるため、パターンがマッチし続ける限り GPU がアイドルでもハングと判定されない
⚠エージェントはルールファイルの所有者や書き込み権限を検証しない。ルールファイルとそのディレクトリは所有者のみ書き込み可能に設定する (chmod 600 または共有時は chmod 644)
⚠ルールファイルの変更を確実に反映するには、ジョブをキャンセルして再投入する必要がある
⚠ハングジョブ検出は、ハードウェア障害で終了したジョブを再起動する auto-resume とは独立した機能である

🎯 ユースケース

🌐 ユースケース 1: 大規模分散トレーニングでの NCCL タイムアウト対策

シナリオ: 数百 GPU を使用する LLM の事前トレーニングで、ノード間通信の問題により NCCL タイムアウトが発生し、全ノードがバリアで待機したままジョブがハングする。

JSONNCCL エラーの即時検出 + 自動キャンセル
{
  "enabled": true,
  "rules": [
    {
      "name": "nccl_error",
      "type": "log_pattern",
      "enabled": true,
      "log_pattern": "NCCL error|NCCL WARN",
      "fault_on_match": true
    }
  ],
  "action_policy": { "action": "cancel" }
}

効果NCCL エラーの出現と同時にジョブがキャンセル・requeue され、タイムアウトを待たずに最後のチェックポイントから再開。大規模クラスターのアイドル時間を大幅に削減。

📊 ユースケース 2: トレーニング進捗の停滞監視

シナリオ: データパイプラインの停止やデッドロックにより、GPU はビジーに見えるがトレーニングステップが進まない状態を検出したい。

JSONステップ進捗の監視ルール
{
  "enabled": true,
  "rules": [
    {
      "name": "step_progress",
      "type": "log_pattern",
      "enabled": true,
      "log_pattern": "step \\d+ loss",
      "timeout_minutes": 30,
      "start_timeout_minutes": 60,
      "metric_evaluation_data_points": 3,
      "stop_pattern": "Training complete"
    }
  ],
  "action_policy": { "action": "cancel" }
}

効果ステップログが 30 分間出力されない場合にハングと判定。デフォルト検出では捕捉できない「GPU ビジーのまま進捗停止」のケースもカバーし、起動時のハングや誤検知にも対応。

🪜 ユースケース 3: 通知のみで段階的に導入する

シナリオ: 自動キャンセルによる誤検知のリスクを避けつつ、まずはハング発生状況を可視化して運用判断の材料にしたい。

Bashnotify のみの最小構成で全ジョブに適用
# notify のみの最小構成でルールファイルを作成
echo '{"enabled": true}' > /fsx/team/rules.json
chmod 644 /fsx/team/rules.json

# サイト共通のプロファイルで全ジョブに適用
export HYPERPOD_HANG_RULES=/fsx/team/rules.json

効果デフォルトの notify アクションにより、ジョブへの影響なしに CloudWatch へハング検出イベントが記録される。検出精度を確認した後、action: cancel へ段階的に移行することで安全に自動復旧を導入できる。

🔗 関連サービス・機能

🔄 Amazon SageMaker HyperPod auto-resume

ハードウェア障害で終了したジョブを自動再起動する機能。終了せずにハングするジョブを対象とする今回の機能とは独立しており、組み合わせることで耐障害性が向上。

📈 Amazon CloudWatch Logs

ハング検出イベント (HANG_DETECTED など) の記録先。メトリクスフィルターやアラームと組み合わせて通知を自動化可能。

🗄️ Amazon FSx for Lustre

マルチノードジョブでルールファイルを全ノードから参照するための共有ストレージとして利用。

🧭 Slurm

SageMaker HyperPod がサポートするワークロードオーケストレーター。キャンセルされたジョブのデフォルトの requeue 動作により、チェックポイントからの再開を実現。

📌 まとめ

SageMaker HyperPod の Slurm クラスターで、NCCL タイムアウトやデッドロックなどによりハングしたトレーニングジョブを数分以内に自動検出し、キャンセル・再キューイングまで自動化できるようになりました。 環境変数の設定のみで導入でき、コード変更が不要なため、大規模 GPU クラスターを運用するチームはまず notify モードで検出状況を可視化し、進捗を追跡する log_pattern ルールを整備した上で自動キャンセルへ移行することを推奨します。
