IAM ロールの自動セットアップが一般提供開始

AWS IAM role manager 📅 リリース日: 2026 年 8 月 12 日

📌 概要

AWS サービスが必要とする IAM ロールを自動的にセットアップする新機能「role manager」が GA。対応サービスをコンソールでセットアップする際、AWS 管理の role template からデフォルトロールが自動作成され、合致する既存ロールがあれば再利用されます。

  • コンソールワークフロー内で AWS 管理テンプレートからロールを自動作成、追加の IAM 設定なしで構築開始

対応サービスのコンソールでリソースを作成すると、role manager が AcquireRole API を通じて AWS 管理テンプレートを適用し、ロールの新規作成または既存ロールの再利用を自動的に行います。作成は CloudTrail に記録され、権限の絞り込みには IAM Access Analyzer を活用できます。

⚡ 主要機能

🆕 1. IAM ロールの自動作成
  • 対応サービスのコンソールでリソースをセットアップすると、必要なデフォルトロールがユーザーに代わって自動作成される
  • 例: Lambda 関数をコンソールで作成すると、ワークフロー用テンプレートが適用され実行ロールがデフォルトで作成される
  • 従来どおり既存ロールの選択や手動作成も可能
📋 2. AWS 管理の role template
  • 信頼ポリシー、インライン/マネージドポリシー、アクセス許可境界、タグ、最大セッション時間などを定義
  • 特定タスク向けテンプレートは、そのタスクに必要なアクションのみを許可
  • オープンエンドな用途 (例: Lambda) では PowerUserAccess のような広い権限を付与しつつ、信頼ポリシーは対象サービスのみに限定
  • テンプレート内容は GetRoleTemplateVersion API でいつでも確認可能
♻️ 3. 既存ロールの再利用
  • 必要な権限に合致するロールが既に存在する場合、新規作成せずに再利用
  • 同じタスク用ロールの重複蓄積を防止
  • 再利用時に必要な権限は iam:GetRole と iam:GetRoleTemplateVersion のみ
👁️ 4. 完全な可視性とコントロール
  • アカウント単位のオプション設定で、いつでも有効化・無効化できる
  • 作成されたロールは標準の IAM ロールとして表示・編集・削除が可能、作成元テンプレートを記録
  • ロール作成は AWS CloudTrail に記録され監査できる
  • 無効化しても作成済みロールは削除されず、既存リソースへの影響なし

🔌 新規 API

API種別説明
AcquireRole新規指定した role template からロールを作成する。テンプレートにパラメータが定義されている場合は置換値を指定可能
GetRoleTemplateVersion新規role template のバージョン情報 (信頼ポリシー、ポリシー、タグ、最大セッション時間など) を取得する
PutAccountProperties新規role manager などアカウント全体の IAM 機能を制御するアカウントプロパティを Namespace/PropertyName 形式で設定する
GetAccountProperties新規現在のアカウントプロパティを取得する

このほか、GetRole / ListRoles / CreateRole など 10 の既存 API が更新され、ロールの作成元テンプレートを示す SourceRoleTemplate (テンプレート ARN とマイナーバージョン) がレスポンスに追加されています。

🛠️ 設定方法

✅ 前提条件

✓有効化・無効化には iam:PutAccountProperties 権限が必要 (AWS 管理ポリシー IAMFullAccess に含まれる)
✓ロールの自動作成は操作するユーザー自身の IAM 権限で実行 (再利用のみの場合は iam:GetRole と iam:GetRoleTemplateVersion のみ)
✓AWS GovCloud (US) リージョンおよび中国リージョン以外の AWS リージョンであること

📝 手順

1
role manager を有効化する

IAM コンソール → Account settings → role manager セクションで Enable を選択。同じページで現在の有効・無効の状態も確認できます。

2
アカウント設定を CLI で確認する
Bashアカウントプロパティの確認
aws iam get-account-properties

Namespace/PropertyName 形式のキーと値のペアで、role manager を含むアカウント全体の IAM 機能の設定状態を確認します。

3
対応サービスのコンソールでリソースを作成する

例: Lambda コンソールで関数を作成すると、AWS 管理テンプレートが適用され、実行ロールが自動作成または既存ロールが再利用されます。追加の操作は不要です。

4
作成されたロールを確認する
Bash作成元テンプレートの確認
aws iam get-role --role-name <ロール名>

レスポンスの SourceRoleTemplate フィールドで作成元テンプレートの ARN とマイナーバージョンを確認。あわせて AWS CloudTrail でロール作成イベントを監査できます。

5
権限を絞り込む

本番稼働に向けては role manager を無効化し、IAM Access Analyzer の未使用アクセス分析で各ロールを必要最小限の権限に絞り込みます。無効化から 90 日間は未使用アクセス分析を無料で利用可能です。

💡 メリット

💼 ビジネス面
  • 構築開始までの時間短縮: IAM ロールの手動設定という中断要因がなくなり、構築そのものに集中できる
  • 学習コストの低減: IAM の詳細な知識がなくても、AWS のベストプラクティスに基づく構成で安全に開始できる
  • ガバナンスとの両立: アカウント単位の切り替えと AWS Organizations の SCP による組織的な制御が可能
⚙️ 技術面
  • ロールの乱立防止: 既存ロールの再利用により、同じ用途のロールの重複蓄積を防止
  • 透明性と監査性: 作成元テンプレートの記録と CloudTrail 記録で識別・監査が容易
  • 最小権限化への道筋: IAM Access Analyzer との組み合わせで「まず動くロール → 利用実績に基づき絞り込み」を実現

⚠️ デメリット・制約事項

🚧 制限事項

✗ローンチ時点で対応するのは 6 つのサービスコンソールのみ (今後拡大予定)
✗AWS GovCloud (US) リージョンおよび中国リージョンでは利用不可
✗コンソールのセットアップワークフローが対象で、CLI や IaC でのリソース作成には適用されない

🤔 考慮すべき点

⚠️オープンエンドなワークフロー (例: Lambda の実行ロール) では PowerUserAccess のような広い権限が付与されるため、本番環境では権限を絞り込んでから稼働させることを推奨
⚠️作成されたロールを編集すると role manager の管理対象から外れ、通常のカスタマー管理ロールとして扱われる
⚠️無効化しても作成済みのロールは削除されないため、不要なロールの棚卸しは別途必要
⚠️推奨運用: サンドボックス・開発アカウントでは有効化、本番アカウントでは無効化して権限を厳格化

🎯 ユースケース

🚀 ユースケース 1: 開発・検証環境での迅速なプロトタイピング

シナリオ: Lambda 関数と EventBridge ルールを組み合わせたイベント駆動アプリケーションを素早く構築したい。IAM ロールの設計に時間をかけず、まず動くものを作りたい。

手順実装例
1. 開発アカウントの IAM コンソール > Account settings で role manager を有効化
2. Lambda コンソールで関数を作成 → 実行ロールが自動作成される
3. EventBridge コンソールでルールを作成し SQS / SNS をターゲットに設定
   → ターゲット呼び出し用ロールが自動作成される

効果: ロール作成のための画面遷移や信頼ポリシーの設定が不要になり、構築フローが中断されずにプロトタイピングを完了できる。

🔒 ユースケース 2: 本番移行前の最小権限化

シナリオ: role manager で作成したロールを使って開発したワークロードを本番に移行するにあたり、最小権限の原則を満たす必要がある。

手順実装例
1. IAM コンソールで role manager を無効化
2. GetRole / ListRoles の SourceRoleTemplate で自動作成されたロールを特定
3. IAM Access Analyzer の未使用アクセス分析 (無効化後 90 日間無料) で
   実際に使用されたアクションを確認
4. 推奨されるスコープダウンポリシーを適用して権限を絞り込み

効果: 実際の利用実績に基づいてロールを必要最小限の権限に精緻化でき、開発スピードとセキュリティを両立できる。

🏢 ユースケース 3: 組織全体でのガバナンス制御

シナリオ: マルチアカウント環境で、開発系アカウントでは role manager の利用を許可し、本番系アカウントでは利用を禁止したい。

JSONSCP の例
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Deny",
      "Action": "iam:PutAccountProperties",
      "Resource": "*"
    }
  ]
}

効果: AWS Organizations のサービスコントロールポリシー (SCP) を本番系 OU に適用することで、メンバーアカウントによる role manager の有効化を組織的に制御できる。

💰 料金・利用可能リージョン

✓料金: IAM および role manager は追加料金なしで利用可能
✓特典: role manager 無効化後の権限絞り込みを支援するため、IAM Access Analyzer の未使用アクセス分析 (通常は有料) を無効化から 90 日間無料で利用可能
✓リージョン: AWS GovCloud (US) リージョンと中国リージョンを除く、すべての AWS リージョンで利用可能

🔗 関連サービス・機能

🔎 IAM Access Analyzer
  • 未使用アクセス分析により、role manager で作成したロールを実際の利用状況に基づいて最小権限に絞り込める
📝 AWS CloudTrail
  • role manager によるロール作成イベントを記録し、いつどのようにロールが作成されたかを監査できる
🏢 AWS Organizations (SCP)
  • iam:PutAccountProperties を制御することで、メンバーアカウントでの role manager の有効化可否を組織的に管理できる
⚡ AWS Lambda / 🔔 Amazon EventBridge
  • ローンチ時点の代表的な対応サービス。実行ロールやターゲット呼び出しロールの自動セットアップに対応

📝 まとめ

role manager は、AWS での構築の出発点となる IAM ロールのセットアップを自動化し、「まず動くものを作り、その後に権限を絞り込む」という現実的なワークフローを公式にサポートするアップデートです。

💡 推奨される使い分け: 開発・サンドボックスアカウントでは有効化して構築スピードを高め、本番アカウントでは無効化して IAM Access Analyzer による最小権限化を徹底する、という運用から始めることを推奨します。
