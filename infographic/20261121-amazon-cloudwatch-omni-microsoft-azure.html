☁️ Amazon CloudWatch (CloudWatch Omni)

📊 CloudWatch Omni が Microsoft Azure のプラットフォームログ・メトリクス・トレースに対応

📅 リリース日: 2026 年 11 月 21 日 | 機能: Azure プラットフォームテレメトリ (リソースログ・メトリクス・トレース・VNet フローログ) の収集

📝 概要

Amazon CloudWatch Omni が、Microsoft Azure のプラットフォームテレメトリの収集に対応しました。Azure のリソースログ、Azure Monitor プラットフォームメトリクス、仮想ネットワーク (VNet) フローログ、Application Insights のトレースを CloudWatch に直接取り込み、AWS と Azure にまたがるワークロードを単一の場所で監視できます。

セットアップでは Microsoft Entra ID テナントを AWS アカウントとリージョンに一度接続し、収集するテレメトリタイプ、サブスクリプション、Azure リージョン、リソースタイプ、タグを選択します。Azure 側にエージェントのインストールは不要で、認証にはワークロードアイデンティティフェデレーションを使用するため、Azure のシークレットやキーを AWS 側に保存しません。マルチクラウド環境を運用する中央運用チーム、DevOps チーム、SRE チームが主な対象です。

📋 リソースログ

各リソースの診断設定 (allLogs カテゴリグループ) が同一リージョンの Event Hub に送信し、パイプラインが継続的に読み取り

📈 プラットフォームメトリクス

Azure Monitor の Metrics Batch API から最小タイムグレイン (通常 1 分) で読み取り。Azure 側のリソース作成は不要

🧭 トレース

Application Insights の AppRequests / AppDependencies レコードがスパンに変換され X-Ray に送信

🌐 VNet フローログ

フローログが同一リージョンのストレージアカウントに書き込まれ、パイプラインが 1 時間ごとに新しいファイルを読み取り

❌ アップデート前の課題

✗AWS と Azure の両方でワークロードを運用する組織は、別々の監視ツールやカスタムパイプラインを構築する必要があった
✗Azure のプラットフォームテレメトリを CloudWatch に取り込む公式の仕組みがなく、CloudWatch エージェントで取得できるアプリケーションテレメトリに限られていた
✗インシデント調査の際に Azure ポータルと AWS コンソールを行き来する必要があり、クロスクラウドのトレーシングが困難だった

✅ アップデート後の改善

✓Azure リソースログ、Azure Monitor プラットフォームメトリクス、VNet フローログ、Application Insights のトレースを CloudWatch に直接取り込めるように
✓Azure 側にソフトウェアをインストールせず、Entra ID テナントの接続とスコープ選択だけでテレメトリ収集を開始可能に
✓Omni スペース上で AWS と Azure のテレメトリを横断分析でき、別々の監視ツールやカスタムパイプラインが不要に

Azure 側では Bicep テンプレートが Event Hubs やストレージアカウントなどの収集リソースを自動作成し、テレメトリパイプラインがワークロードアイデンティティフェデレーションで認証して Azure から読み取り、CloudWatch Logs・CloudWatch Metrics・X-Ray に書き込みます。取り込まれたテレメトリは CloudWatch Omni スペースに表示されます。

⚡ 主要機能

1️⃣ 4 種類の Azure プラットフォームテレメトリの収集
  • リソースログ: 診断設定 (allLogs カテゴリグループ) が同一リージョンの Event Hub にログを送信し、パイプラインが継続的に読み取る
  • プラットフォームメトリクス: Azure Monitor の Metrics Batch API から各メトリクスの最小タイムグレイン (通常 1 分) で読み取る。Azure 側のリソース作成は不要
  • トレース: Application Insights (microsoft.insights/components) の AppRequests / AppDependencies レコードがスパンに変換され X-Ray に送信
  • VNet フローログ: フローログが同一リージョンのストレージアカウントに書き込まれ、パイプラインが 1 時間ごとに新しいファイルを読み取る
2️⃣ エージェントレス・シークレットレスの接続

Azure 側にソフトウェアのインストールは不要。認証はワークロードアイデンティティフェデレーションを使用し、Azure のシークレットやキーを保存しません。CloudWatch は接続ロール (IAM ロール) を引き受けて IAM からトークンを取得し、Microsoft Entra ID で AWS CloudWatch Ingestion アプリケーションのアクセストークンと交換します。

3️⃣ 柔軟なテレメトリスコープ

収集対象をテレメトリタイプ、サブスクリプション (全部または最大 1,000 件)、Azure リージョン、リソースタイプ、タグフィルターで細かく指定可能。リソース ID の直接指定にも対応。スコープから生成される Bicep テンプレートが Event Hubs 名前空間、ストレージアカウント、Azure Policy 割り当てを自動作成し、既存リソースには修復タスクで診断設定を適用します。

4️⃣ トポロジーとリソースタグによるエンリッチメント (オプション)

AWS Config コネクタで Azure リソースを検出し、アプリケーションマップに Azure リソースを表示可能。Azure のリソースタグをログとメトリクスに付加するテレメトリエンリッチメントにも対応します。

5️⃣ コンソールと AWS CLI の両方で設定可能

Omni Web UI の 3 ステップウィザード、または AWS CLI (aws observabilityadmin の connector コマンド) とセットアップスクリプトで構成できます。

🛠️ 設定方法

✅ 前提条件

  • トレースを収集する場合、対象の AWS アカウント・リージョンで Transaction Search が有効化されていること
  • aws observabilityadmin の connector コマンドを含むバージョンの AWS CLI
  • Microsoft Entra ID 側でアプリケーション登録権限 (Cloud Application Administrator など) と、テナントルート管理グループでのロール割り当て権限 (Owner など) を持つこと
  • Bash、curl、jq、および Azure CLI 2.47.0 以降と Bicep (Azure Cloud Shell にはすべて揃っている)
1
接続の作成

セットアップスクリプトが、AWS 側でアウトバウンド Web アイデンティティフェデレーションの有効化と接続ロールの作成、Entra ID 側で AWS CloudWatch Ingestion アプリケーションの登録とロール割り当て、接続 (コネクタ) の作成を順に実行します。Azure シークレットは保存されません。

Bash接続セットアップ
bash cloudwatch-azure-connection-setup.sh \
    --aws-region us-east-1 \
    --aws-role-name CloudWatchConnector \
    --connection-name my-azure-tenant
2
テレメトリスコープの定義

収集するテレメトリタイプ、サブスクリプション、リージョン、リソースタイプを記述した JSON (前述の例を参照) を接続に保存します。

Bashスコープの保存
aws observabilityadmin put-connector-telemetry-manifest \
    --connector-identifier <connector-arn> \
    --manifest file://scope.json
3
Azure リソースのデプロイ

スコープから生成された Bicep テンプレートを取得し、Azure 側にデプロイします。Event Hubs 名前空間、フローログ用ストレージアカウント、診断設定を追加する Azure Policy が作成され、既存リソースには修復タスクで診断設定が適用されます。

BashBicep テンプレートの取得とデプロイ
aws observabilityadmin get-connector-telemetry-setup \
    --connector-identifier <connector-arn> \
    --format BICEP > setup.json

bash cloudwatch-azure-telemetry-deploy.sh \
    --client-id <appId> \
    --tenant-id <tenant-id> \
    --connector-id <connector-id> \
    --location eastus \
    --template-file azure-setup/main.bicep
4
ライターロールとテレメトリパイプラインの作成

パイプラインの書き込み先となるロググループを作成し、接続をソース、ライターロールと CloudWatch Logs・Metrics・X-Ray をシンクとするテレメトリパイプラインを作成します。ステータスが ACTIVE になると取り込みが開始され、テレメトリが Omni スペースに表示されます。

Bashパイプラインの作成
aws logs create-log-group --log-group-name /az/my-azure-tenant-telemetry

aws observabilityadmin create-telemetry-pipeline \
    --name my-azure-tenant-telemetry \
    --configuration "$(jq -n --rawfile body pipeline.yaml '{Body: $body}')"

💡 なお、Omni Web UI の Settings から Azure をクラウドプロバイダーとして選択すれば、上記の一連の手順を 3 ステップウィザードで実行できます。

💡 メリット

💼 ビジネス面

✓監視ツールの統合: AWS と Azure で別々の監視ツールやサードパーティ製品を維持する必要がなくなり、ライセンスコストと運用負荷を削減
✓インシデント対応の迅速化: Azure ホストのサービスから AWS の依存関係までコンソールを切り替えずにトレースでき、MTTR の短縮につながる
✓カスタムパイプラインの廃止: Azure テレメトリを AWS に転送する自前の連携処理の開発・保守が不要に

⚙️ 技術面

✓エージェントレス収集: Azure 側にソフトウェアをインストールせず、既に記録されているテレメトリをそのまま取り込める
✓シークレットレス認証: ワークロードアイデンティティフェデレーションにより、キーのローテーションや漏えいリスクを排除
✓Infrastructure as Code: 収集リソースは生成された Bicep テンプレートで作成され、セットアップスクリプトは冪等で再実行可能
✓タグエンリッチメントとトポロジー: Azure リソースタグをテレメトリに付加し、アプリケーションマップに Azure リソースを表示可能

⚠️ デメリット・制約事項

🚫 制限事項

✗Azure 仮想マシン内部やアプリケーションコードからのテレメトリは対象外 (CloudWatch エージェントによる収集が別途必要)
✗global ロケーションのリソース (Azure Front Door など) は収集不可
✗タグフィルターは完全一致のみで、ワイルドカードや除外条件は使用不可
✗メトリクスはリソースの 1 メトリクスあたり 1,000 系列が上限で、超過分は収集されない
✗VNet フローログの読み取りは 1 時間ごとで、リアルタイム性は低い

🤔 考慮すべき点

⚠Azure 側の Event Hubs とストレージには Azure の料金が発生。CloudWatch 側で接続を削除しても Azure リソースは残り、削除するまで課金が継続
⚠Azure プラットフォームメトリクスはアカウントの新規メトリクス系列の上限にカウントされるため、リソースの多いテナントの初回接続時は上限超過に注意
⚠セットアップにはテナントルート管理グループでの Owner 相当の強い権限が必要で、Azure 側の管理者との調整が必要
⚠配信は at-least-once であり、リトライされたウィンドウが二重にカウントされる可能性がある

🎯 ユースケース

1. マルチクラウド環境の一元監視

シナリオ: 買収などにより AWS と Azure の両方でワークロードを運用している企業で、中央の SRE チームが環境全体を単一のダッシュボードで監視したい。

  • Omni Web UI で Entra ID テナントを AWS アカウントに接続
  • テレメトリスコープで全サブスクリプションの主要リソースタイプを指定
  • Omni スペースで AWS と Azure のメトリクス・ログを横断分析
✅ 効果: 別々の監視ツールを行き来することなく、両クラウドの状態を単一の場所で把握できる。
2. クロスクラウドの分散トレーシング

シナリオ: フロントエンドが Azure App Service、バックエンド API とデータベースが AWS にある構成で、遅いリクエストの原因を特定したい。

  • Transaction Search を有効化
  • Application Insights を含むスコープでリソースログ収集を設定 (AppRequests と AppDependencies がスパンに変換される)
  • Omni でリクエストを Azure サービスから AWS の依存関係まで追跡
✅ 効果: インシデント対応中にコンソールを切り替えることなく、Azure 起点のリクエストを AWS 側までエンドツーエンドでトレースできる。
3. Azure ネットワークトラフィックの監査

シナリオ: セキュリティチームが Azure VNet のトラフィックを AWS 側の既存のログ分析基盤と同じ場所で監査したい。

  • テレメトリスコープで FlowLogs タイプと対象 VNet を指定
  • フローログが CloudWatch Logs のロググループに取り込まれる
  • CloudWatch Logs Insights で AWS の VPC Flow Logs と合わせて分析
✅ 効果: 両クラウドのネットワークフローログを同一基盤で分析でき、監査・調査のワークフローを統一できる。

📌 まとめ

CloudWatch Omni が Azure のプラットフォームテレメトリ収集に対応したことで、AWS と Azure にまたがる環境をエージェントレス・シークレットレスで一元監視できるようになり、マルチクラウド運用における監視ツールの分断という大きな課題が解消されます。マルチクラウド環境を運用しているチームは、まず Omni Web UI のウィザードで小さなスコープから接続を試し、Azure 側の Event Hubs 等のコスト影響を確認しながら段階的に対象を広げることを推奨します。
