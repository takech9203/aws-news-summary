📋 概要

Amazon EBS の Elastic Volumes 機能が強化され、AWS European Sovereign Cloud (ドイツ) リージョンにおいて、1 つのボリュームに対してローリング 24 時間ウィンドウ内で最大 4 回のボリューム変更が可能になりました。ボリュームのサイズ拡張、タイプ変更、パフォーマンス調整を、ボリュームをデタッチしたりインスタンスを再起動したりすることなく実行できます。

この拡張は自動的に利用可能であり、既存のワークフローを変更する必要はありません。

❌ Before
-24 時間あたりの変更回数に制限があり連続的な調整が困難
-ワークロードの急変動に対して迅速なボリューム調整ができず
-段階的なスケーリングやチューニングの柔軟性が不足
✅ After
+24 時間以内に最大 4 回まで変更可能
+前回の変更完了後すぐに次の変更を開始可能
+既存ワークフローの変更なしで自動適用

⚡ 主要機能

🔄 24 時間あたり最大 4 回のボリューム変更
  • ローリング 24 時間ウィンドウ内で 1 つのボリュームに対して最大 4 回の変更が可能
  • 前回の変更が completed 状態になれば、すぐに次の変更を開始可能
  • 制限超過時は、次の変更可能タイミングを示すエラーメッセージが表示
📐 対応する変更操作
  • ボリュームサイズの拡張 (縮小は不可)
  • ボリュームタイプの変更 (例: gp2 から gp3)
  • IOPS やスループットなどのパフォーマンスパラメータの調整
🔧 無停止での変更
  • ボリュームのデタッチやインスタンスの再起動が不要
  • アプリケーションは稼働を継続、パフォーマンスへの影響は最小限
  • ボリュームが in-use または available 状態であれば変更可能

前提条件

  • AWS European Sovereign Cloud (ドイツ) リージョンへのアクセスが有効であること
  • 対象の EBS ボリュームが in-use または available 状態であること
  • 前回のボリューム変更が completed 状態であること

ステップ 1: ボリュームの現在の状態を確認

Bash ボリュームの詳細を確認

  --query 'Volumes[0].{VolumeId:VolumeId,Size:Size,VolumeType:VolumeType,Iops:Iops,Throughput:Throughput,State:State}'

ステップ 2: ボリューム変更の実行

Bash サイズ、タイプ、IOPS、スループットを同時に変更 
# サイズ、タイプ、IOPS、スループットを同時に変更
# これらは 1 回の変更操作としてカウントされます
aws ec2 modify-volume \
  --volume-id vol-xxxxxxxxxxxxxxxxx \
  --size 500 \
  --volume-type gp3 \
  --iops 6000 \
  --throughput 250

🎯 ユースケース

🏦 ユースケース 1: 欧州のデータ主権要件に対応した段階的ストレージ拡張
ドイツを拠点とする金融機関が、欧州のデータ主権要件を満たしながら、月末の決算処理に伴うデータ増加に対応するためストレージを段階的に拡張する。
Bash 段階的なストレージ最適化 
# 1 回目: ボリュームサイズを 500 GiB → 750 GiB に拡張
aws ec2 modify-volume --volume-id vol-xxx --size 750

# 2 回目: IOPS を 3000 → 6000 に引き上げ
aws ec2 modify-volume --volume-id vol-xxx --iops 6000

# 3 回目: 処理完了後、スループットを最適化
aws ec2 modify-volume --volume-id vol-xxx --throughput 400
💡 効果: データ主権を維持しながら、24 時間以内に 3 段階のストレージ最適化を無停止で実行
🚀 ユースケース 2: ワークロードスパイクへの緊急対応
European Sovereign Cloud で運用している SaaS アプリケーションが予期しないトラフィック急増に直面し、データベースのストレージ性能を緊急に引き上げる必要がある。
Bash 緊急パフォーマンス引き上げ 
# 1 回目: gp3 → io2 に変更して高 IOPS を確保
aws ec2 modify-volume \
  --volume-id vol-xxx \
  --volume-type io2 \
  --iops 32000

# 2 回目: 状況に応じてさらに IOPS を引き上げ
aws ec2 modify-volume \
  --volume-id vol-xxx \
  --iops 64000
💡 効果: アプリケーション無停止で緊急のパフォーマンス要件に段階的に対応
🧪 ユースケース 3: 開発環境のボリューム構成テスト
European Sovereign Cloud の開発環境で、本番環境のストレージ構成を検証するために、異なるボリューム設定を短時間で試したい。
Bash 4 パターンの構成テスト 
# 1 回目: gp3 ベースライン性能
aws ec2 modify-volume --volume-id vol-xxx --volume-type gp3 --iops 3000

# 2 回目: gp3 高 IOPS
aws ec2 modify-volume --volume-id vol-xxx --iops 10000

# 3 回目: io2 に変更
aws ec2 modify-volume --volume-id vol-xxx --volume-type io2 --iops 32000

# 4 回目: io2 最大 IOPS
aws ec2 modify-volume --volume-id vol-xxx --iops 64000
💡 効果: 24 時間以内に最大 4 パターンの構成をテストし、最適な構成を迅速に特定

⚖️ メリットとデメリット

✓ メリット

ビジネス面

  • データ主権を確保しながら柔軟なストレージ管理
  • 24 時間以内に最大 4 回の変更で迅速対応
  • ダウンタイム排除でビジネス継続性を維持

技術面

  • 複数回の変更で段階的な最適化が可能
  • 既存ワークフローの変更が不要
  • 追加設定やオプトイン不要で即座に利用可能

✗ デメリット / 制約

  • 24 時間あたり 4 回を超える変更は不可
  • ボリュームサイズの縮小はサポートされない
  • 変更リクエスト送信後のキャンセル不可
  • マルチアタッチ有効な io2 ではタイプ変更不可
  • マルチアタッチ有効な io1 ではタイプ、サイズ、Provisioned IOPS の変更不可

考慮すべき点

  • 変更完了に数分~数時間 (1 TiB で最大約 6 時間)
  • 未初期化ボリュームでは変更時間が延長される可能性
  • ルートボリュームを st1/sc1 に変更することは不可

💰 料金情報

💡 ポイント: Elastic Volumes のボリューム変更操作自体には追加料金は発生しません。変更後の新しいボリューム構成に基づく料金が、変更開始時点から適用されます。
ボリュームタイプ 課金項目
gp3 ストレージ容量 (GiB/月) + ベースライン超過分の IOPS + ベースライン超過分のスループット
io2 ストレージ容量 (GiB/月) + プロビジョニング IOPS
gp2 ストレージ容量 (GiB/月)
