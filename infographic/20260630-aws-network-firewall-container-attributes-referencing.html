📌 概要

AWS Network Firewall が、コンテナ属性ベースのルールに対応しました。Amazon EKS / Amazon ECS 上のコンテナ化ワークロード (生成 AI アプリを含む) のネットワークセキュリティを、IP アドレスに依存せず Namespace や Cluster Name、Labels といったネイティブなコンテナ構成要素で記述できます。

対象ユーザーは、セキュリティエンジニア、DevSecOps 担当者、プラットフォームチームです。動的で急速に変化するコンテナ環境に対して、エンタープライズグレードのセキュリティコントロールを提供します。

😰 アップデート前の課題
❌ ポッドのスケールや再起動のたびに IP ベースのルールが破綻
❌ 動的なコンテナ環境への静的ルール適用が困難
❌ 複数クラスターにまたがる一元管理が煩雑
➜
🎉 アップデート後の改善
✅ Namespace / Cluster / Labels などの属性でルール記述
✅ 複雑な IP ベースのルール管理が不要に
✅ コンテナのスケールに合わせてルールが自動適応

コンテナのメタデータ (Namespace や Labels など) に基づいてトラフィックを識別し、AWS Network Firewall が各種フィルタリングを適用する流れ

⚙️ 主要機能

1️⃣ コンテナ属性ベースのルール定義
  • Amazon EKS: Namespace、Cluster Name、Labels でルールを記述
  • Amazon ECS: Cluster Name、Container Instance Attributes でルールを記述
  • IP ではなくネイティブなコンテナ構成要素を参照し、スケールや再起動に自動適応
2️⃣ 多様な検査・フィルタリング機能との連携
  • TLS 復号による暗号化トラフィックのディープパケットインスペクション (DPI)
  • FQDN ベースフィルタリングで、特定ポッドを承認済みドメインのみに制限
  • URL カテゴリフィルタリング (Malicious、Phishing、Malware など 50 種類以上)
  • GeoIP フィルタリングによる地理的な IP アドレス制限
3️⃣ 一元的なマルチクラスターセキュリティ
  • AWS Network Firewall / Amazon EKS / Amazon ECS のネイティブ統合
  • 複数クラスターにまたがるセキュリティを一元管理
  • ビジネス要件および規制コンプライアンスへの対応を支援

検査・フィルタリング方式

方式説明
TLS 復号暗号化トラフィックのディープパケットインスペクションを実施
FQDN フィルタリング特定のポッドを承認済みドメインのみに制限
URL カテゴリaws_url_category キーワードで完全な URL を評価 (HTTPS は TLS インスペクションが必要)
ドメインカテゴリaws_domain_category キーワードで TLS SNI や HTTP Host からドメインを評価 (TLS インスペクション不要)
GeoIPgeoip キーワードで地理的な IP アドレスを制限

URL / ドメインカテゴリフィルタリングの利用例

Suricata互換ルールの例
# 悪意のあるドメインへのアクセスをブロックする例
drop tls $HOME_NET any -> $EXTERNAL_NET any (aws_domain_category:Malicious; sid:1;)

# 特定カテゴリの URL をブロックする例 (HTTPS の場合は TLS インスペクションが必要)
drop http $HOME_NET any -> $EXTERNAL_NET any (aws_url_category:Phishing,Malware; sid:2;)

🚀 設定方法

前提条件

✓ Amazon EKS または Amazon ECS 上で稼働するコンテナワークロードが存在すること
✓ AWS Network Firewall が対象 VPC にデプロイされていること
✓ HTTPS の URL カテゴリフィルタリングを行う場合は TLS インスペクションが有効化されていること

💡 ユースケース

🤖 ユースケース 1: 生成 AI アプリケーションのアウトバウンド制御

Amazon EKS 上の生成 AI ポッドを、承認済みの AI/ML API エンドポイントのみと通信するように制限。

SuricataLabel ベースの制御
# ai=true ラベルを持つポッドを対象に、承認済みドメインのみへのアクセスを許可
pass tls (labels: ai=true) $HOME_NET any -> approved-ai-domains any (sid:10;)
drop tls (labels: ai=true) $HOME_NET any -> $EXTERNAL_NET any (sid:11;)
📈 効果: データ漏洩リスクを低減し、承認外ドメインへの通信を防止
🧱 ユースケース 2: Namespace 単位のトラフィック分離

開発用と本番用の Namespace で異なるネットワークポリシーを適用し、環境間のトラフィックを分離。

SuricataNamespace ベースの制御
# production Namespace は特定のドメインカテゴリをブロック
drop tls (namespace: production) $HOME_NET any -> $EXTERNAL_NET any (aws_domain_category:Malicious,Phishing; sid:20;)
📈 効果: 環境ごとに適切なセキュリティレベルを適用し、本番環境の保護を強化
🌐 ユースケース 3: 複数クラスターの一元的なセキュリティ管理

複数の Amazon EKS / ECS クラスターに対して、共通のセキュリティポリシーを一元的に適用。

SuricataCluster ベースの GeoIP 制御
# 複数クラスターを Cluster Name で識別し、共通の GeoIP フィルタを適用
drop tls (cluster: prod-cluster-1) $HOME_NET any -> $EXTERNAL_NET any (geoip:dst,CN,RU; sid:30;)
📈 効果: クラスターが増えても一貫したポリシーを維持し、コンプライアンス対応が容易に

⚖️ メリットと制約事項

✅ メリット
💰 運用負荷の軽減: IP ベースのルール手動更新が不要になり運用コスト削減
📋 コンプライアンス対応: 一元的なマルチクラスターセキュリティで規制要件に対応
🆓 追加費用なし: Network Firewall の一部として利用可能
🔄 動的環境への自動適応: スケールや再起動に合わせてルールが自動更新
🔗 ネイティブ統合: NFW / EKS / ECS 統合で設定を簡素化
🛡️ 多層防御: TLS 復号や URL カテゴリなど複数方式を組み合わせ可能
⚠️ 制約・考慮点
🔐 HTTPS の URL カテゴリフィルタリングには TLS インスペクションが必須
🚧 URL / ドメインカテゴリと GeoIP は同一ルール内で併用不可 (別ルールが必要)
⏱️ URL / ドメインカテゴリはカテゴリ検索が追加され、レイテンシー増加の可能性
📜 TLS インスペクション有効化には証明書管理などの追加設定が必要
🌍 利用可能リージョンは AWS Capabilities by Region ページで事前確認が必要

💴 料金と利用可能リージョン

💰 料金
  • コンテナ属性ベースのインスペクションは 追加費用なし
  • AWS Network Firewall の標準料金 (エンドポイント時間 + トラフィック処理量) が適用
  • TLS インスペクションや URL カテゴリフィルタリングなど既存機能はそれぞれの標準料金が適用
🌍 利用可能リージョン
  • 完全な一覧は AWS Capabilities by Region ページで確認可能
  • ご利用予定のリージョンでの提供状況を事前に確認すること
