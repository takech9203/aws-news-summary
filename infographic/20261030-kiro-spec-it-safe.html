🛡️ Kiro 仕様ハードニング
Specification Hardening - セキュリティ要件のシフトレフト

Kiro Power 📅 2026 年 10 月 30 日 🔬 リサーチプロトタイプ

📋 概要

Kiro のスペック駆動開発 (SDD) ワークフローにセキュリティ要件を組み込む Kiro Power が公開されました。 多くの仕様は「何をすべきか」という機能要件のみを記述し、「悪用にどう耐えるか」には言及していません。 仕様ハードニングは、機能要件の完成後・プランニング前に 1 ステップを追加し、EARS 形式の要件から弱点タイプを検出して、 CWE に基づく追跡・テスト可能なセキュリティ制約を仕様に自動追記します。

提案は CWE 弱点クラスとセキュリティ義務をマッピングしたキュレーション済みライブラリに基づき、 モデルの推測ではなく既知の弱点を根拠とします。コード生成前の「アップストリームの制御ポイント」であり、 SAST / DAST / 依存関係スキャン / 人間によるレビューを置き換えるものではありません。

仕様ハードニングは Specify → Plan → Execute フローに 1 つのハードニングステップを挿入し、 コード生成前の早期制御ポイントとして機能します。 3 段階パイプラインは決定論的で、その後のエージェントによるセマンティックレビューが追加の制約を補完します。

⚡ 主要機能

📚 1. CWE-to-spec マッピングライブラリ
  • 仕様で表現可能な CWE 弱点クラスを再利用可能なセキュリティ義務にマッピングした決定論的な TypeScript ライブラリ / CLI
  • 8 ドメイン (インジェクション、認証、認可、データ露出、暗号化、入力検証、セキュリティ設定ミス、ビジネスロジック) × 60 件の CWE マッピング
  • 選定と検出パターンは MITRE CWE、OWASP Top 10:2021、Amazon Q Developer Detector Library (旧 CodeGuru) に主に基づく
  • 各マッピングに OWASP カテゴリと手動割り当ての重大度を付与
🔍 2. 3 段階のハードニングパイプライン
  • トリガー検出: 部分文字列キーワード (database、upload、session など) と正規表現の 2 つの字句的シグナルでスコアリングし、しきい値 (デフォルト 0.3) を超えた CWE をフラグ
  • カバレッジチェック: 仕様がすでに必要なプリミティブ (パラメータ化クエリ、所有権チェックなど) を記述済みか確認し、未カバーのギャップのみを提案対象に
  • 制約提案: 不足制約を EARS 項目として挿入。各行に提案 ID と [SECURITY: …] タグが付き、diff としてレビュー可能
👤 3. セマンティックレビューパス
  • 字句マッチングで検出できない認可チェックの欠落などを、Kiro Power ではエージェントが、CLI では開発者がレビュー
  • しきい値未満の弱い認可マッチは候補として提示し、確認されたギャップをドメイン固有の制約として追加
  • レビューで追加された句は EC の代わりに SEM プレフィックスを使用 (例: SEM-862-1)
🔄 4. インクリメンタルな再実行とバージョン管理との統合
  • エンジンは行の追加のみを行い、要件の変更・分割・並べ替えは行わない。厳密な EARS 形式でない要件は書き換えず報告
  • 隠しレビューマーカーにより、再実行時は新規・変更された要件のみをハードニングし、レビュアーが削除した制約は再提案しない
  • requirements.md をその場で編集するため、バージョン管理とコードレビューのフローに自然に統合

🎯 対象とする弱点クラスの例

CWE弱点トリガー条件必須 EARS 制約の例
CWE-89SQL インジェクション外部入力を使用してデータベースにクエリするすべてのクエリをパラメータ化 / プリペアドステートメントで実行し、文字列連結を禁止
CWE-862認可の欠落プリンシパルが所有するリソースを返却または変更するリクエスト元プリンシパルがリソースを所有するか明示的な許可を持つことを検証
CWE-306認証の欠落エンドポイントまたはリソースを公開する処理前に有効な認証済みセッションまたは署名付きトークンを要求
CWE-79クロスサイトスクリプティングユーザー提供コンテンツをブラウザに描画するすべての出力をコンテキストに応じてエンコードし、多層防御として CSP ヘッダーを追加
CWE-522不十分な資格情報保護パスワードを保存または検証する強力な適応型関数でパスワードをハッシュ化 (平文や可逆形式は禁止)
CWE-434無制限のファイルアップロードファイルアップロードを受け付けるMIME 許可リストに対してマジックバイトを検証し、サイズ上限を設定し、Web ルート外に保存
CWE-639IDOR / BOLA呼び出し元指定の識別子でオブジェクトを取得するオブジェクトの所有テナントが認証済み呼び出し元と一致することを返却前に検証

※ 表の制約は代表的な言い換えであり、すべてのアーキテクチャを網羅する完全な制御ではありません。

🚀 設定方法

前提条件

  • Kiro IDE がインストールされていること (Kiro Power として使用する場合)
  • Node.js / npm が利用可能であること (CLI として使用する場合)
  • スペック駆動開発ワークフローで EARS 形式の requirements.md が作成済みであること

手順

1
Kiro Power のインストール
GitHub の sample-kiro-spec-security-hardening リポジトリから仕様ハードニング Power を Kiro IDE にインストール。
2
仕様のハードニング
機能要件の確定後、Kiro に「harden my specs」と依頼。harden-spec スキルがエンジンのビルド・実行、セマンティックレビュー、サマリー提示を実施。
3
CLI での実行 (代替手段)
cwe-to-spec-mapping-library/ ディレクトリで初回ビルド後、コンパイル済み CLI を仕様ファイルに対して実行。
Bash CLI での実行 
# cwe-to-spec-mapping-library/ ディレクトリで初回ビルド
npm install

# コンパイル済み CLI を仕様ファイルまたは specs ディレクトリに対して実行 (絶対パスを使用)
# --semantic-candidates フラグで、弱い認可マッチをレビュー用に表示 (ファイルには書き込まない)
4
diff のレビュー
エンジンは行の追加のみを行うが、必ず git diff をレビュー。3 つ以上の要件で提案された句は「Security Baseline (Cross-Cutting)」セクションに 1 回だけ移動されるヒューリスティックがあるため、diff での確認が推奨される。

⚖️ メリットと制約事項

✅ メリット

✓シフトレフト: コード作成前にセキュリティ義務を明示し、後工程の手戻りと修正コストを削減
✓監査可能性: ハードニング済み仕様がリポジトリに残り、各義務の根拠を後から監査可能
✓決定論的で再現可能: 提案の根拠がモデルの推測ではなく既知の CWE に基づく
✓追跡・テスト可能: 提案 ID と [SECURITY: …] タグ付きの EARS 形式で仕様に組み込み
✓既存フローと統合: その場編集と行追加のみでバージョン管理・コードレビューに自然に適合
✓アーキテクチャ改善: 要件を中心に据えたクリーンな設計と 3 プロジェクトタイプ対応

⚠️ 制約事項・考慮点

⚠マッチングは字句的であり、文言が明示しない弱点は見逃す可能性がある
⚠データフロー / コードレベル分析が必要な弱点、ランタイム・インフラ・依存関係の弱点は対象外
⚠SAST、DAST、依存関係スキャン、人間によるレビューの代替にはならない
⚠カバレッジチェックはファイル全体への字句チェックのため、別要件の制御が提案を抑制する場合がある
⚠CLI は構造化レポートを保存しない (プログラマティック API では取得可能)
⚠リサーチプロトタイプの位置付け。ハードニング後も git diff の確認と開発者判断、セキュリティレビューが必須
⚠脅威モデリング、Kiro ステアリングファイル、安全なデフォルトを持つフレームワーク、下流のセキュリティテストとの併用が推奨

💡 ユースケース

🏥 1. 新規開発でのセキュア・バイ・デザイン (グリーンフィールド)

シナリオ: デジタルヘルススタートアップが、医師が患者名で臨床ノートを検索する患者ポータルを新規開発。機能要件は検索機能のみを記述し、認証やクエリの安全性には言及していない。

Textハードニングの流れ
1. EARS 形式で機能要件を作成
2. Kiro に「harden my specs」と依頼
3. エンジンが CWE-89 (SQL インジェクション) と CWE-306 (認証の欠落) を検出し、
   7 つのセキュリティ制約を要件に追記
   - 1.1-1.2: パラメータ化クエリ (CWE-89)
   - 1.3-1.4: 入力検証 (CWE-89)
   - 1.5-1.7: 認証 (CWE-306)
4. レビューパスで 1.8 (データ最小化、CWE-200) と
   1.9 (診療関係に基づく認可、CWE-862) を追加
5. ハードニング済み仕様からエージェントがコードを生成

効果: SQL インジェクションや認証チェック欠落を含むコードが生成されるリスクをコード作成前に排除。しきい値未満の認可ギャップもセマンティック候補として提示され、ドメイン固有の制約として確定できる。

🔄 2. 既存プロジェクトへの要件追加 (ブラウンフィールド)

シナリオ: 既存アプリケーションに要件を追加・変更する際、変更部分のみにセキュリティ制約を適用したい。

  • 仕様ハードニングを再実行すると、隠しレビューマーカーにより新規・変更された要件のみがハードニングされる
  • 追加された SEC- 制約が機能変更と並ぶレビュー可能な diff として表示される
  • 提案された義務を既存システムの実際の挙動と照合する

効果: 変更が修正対象の範囲内に収まり、レビュー済み要件には影響しない。義務と実装の相違を確認することで、コードのギャップまたは適応すべき制約を発見できる。

🏛️ 3. レガシーシステムのスペック駆動モダナイゼーション

シナリオ: レガシーシステムを書き換える際、元のシステムのセキュリティギャップを引き継がずにモダナイズしたい。

📝 まとめ

仕様ハードニングは、セキュリティ要件を仕様そのものに組み込むことで、AI コーディングエージェントが推測ではなく 明示的な義務に対してコードを構築できるようにする、SDD 時代のシフトレフトの新しいアプローチです。 60 件の CWE マッピングに基づく決定論的なエンジンとセマンティックレビューの組み合わせにより、 一般的な弱点クラスの見落としを仕様段階で削減できます。

🔬 導入時のポイント
SDD を採用しているチームは、GitHub のサンプルリポジトリから Kiro Power を導入し、「完了の定義」に仕様セキュリティレビューを追加することを検討してください。 ただし本機能はリサーチプロトタイプであり、SAST / DAST / 人間によるレビューなどの下流のセキュリティ対策と組み合わせて利用することが前提となります。
