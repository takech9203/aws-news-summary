AWS Glue

⚙️ zero-ETL 統合のターゲットテーブルプロパティ
オーナーシップ管理と競合検出

📅 リリース日: 2026 年 9 月 14 日 | 対象: AWS Glue zero-ETL 統合

📌 概要

AWS Glue zero-ETL 統合が、ターゲットテーブルプロパティの競合検出と統合オーナーシップの追跡に対応しました。 生成されるターゲットテーブルプロパティが所有元の統合に関連付けられ、2 つの統合が意図せず同じターゲットテーブルを指して一方がもう一方のデータを上書きする事態を仕組みとして防止できます。

競合検出はコンソール、CLI、API のいずれの操作でも一貫して適用され、コンソールでは統合作成ワークフローの「Output settings」ステップで作成前に競合を検出・解決できます。ターゲットは Amazon S3 Tables と Amazon SageMaker Lakehouse カタログの両方に対応します。

❌ アップデート前の課題

  • 複数の統合が同じターゲットテーブルを指しても検出されず、データ上書きのリスクがあった
  • テーブルプロパティの所有統合を追跡する仕組みがなく、統合が増えるほど構成ミスの発見が困難
  • 複数チーム・複数アカウントでは、運用ルールや手動確認で重複を防ぐ必要があった

✅ アップデート後の改善

  • テーブルプロパティが所有元の統合に関連付けられ、オーナーシップを明確に追跡
  • 同じ組み合わせへの 2 つ目の統合を検出してブロックし、意図しない上書きを防止
  • 「Output settings」ステップで作成前に競合を可視化・解決
  • 新 API ListIntegrationTableProperties でプログラムから所有関係を確認可能

複数の zero-ETL 統合が同じターゲットリソースとソーステーブルの組み合わせを指定した場合、AWS Glue がオーナーシップを確認して競合を検出し、後から作成される統合をブロックする流れ

🔧 主要機能

🔑 競合検出の識別キー ターゲットテーブルプロパティは ターゲットリソース ARN + ソーステーブル名 の組み合わせで識別され、各組み合わせは同時に 1 つの統合のみが所有できます。

1️⃣ 統合オーナーシップの追跡

  • ターゲットリソースは、汎用 S3 ターゲットの場合は AWS Glue データベース、Amazon S3 Tables ターゲットの場合は S3 Tables カタログ
  • ソーステーブルのターゲットプロパティは 1 つの統合のみが所有可能

2️⃣ 競合の検出とブロック

  • 同じソーステーブルを同じターゲットリソースに書き込む 2 つ目の統合の作成を防止
  • 競合発生時は所有元の統合を提示し、別ターゲットの選択または既存統合の変更で解決
  • コンソール、CLI、API のいずれの操作経路でも同じルールを適用

3️⃣ コンソールでの競合の可視化

  • 統合作成ワークフローの「Output settings」ステップで作成前に検出
  • マルチテーブルソース (SaaS など) は「Action required」「Notes」の 2 列で各テーブルの状態を表示
  • シングルテーブルソース (DynamoDB など) はインラインアラートで表示

4️⃣ 検出対象となる競合条件

  • 別の統合が既に同じソーステーブルを選択中のターゲットリソースに書き込んでいる
  • 出力テーブル名が、選択中のターゲットリソース上で別のソーステーブル用に登録済み
  • 複数のソーステーブルが同じ出力テーブル名にマッピングされている
  • 出力テーブル名が無効 (小文字・数字・アンダースコアのみ、255 文字以内。S3 Tables ではアンダースコア始まり不可)
  • 出力設定への同時変更 (この条件のみブロックせず、最新設定への更新か現状続行かを選択可能)

ターゲットテーブルプロパティの設定例

Bash ターゲットテーブルプロパティの登録 
aws glue create-integration-table-properties \
  --resource-arn arn:aws:glue:us-east-1:123456789012:database/my-database \
  --table-name my-source-table \
  --target-table-config '{
      "UnnestSpec": "TOPLEVEL",
      "PartitionSpec": [
          {
              "FieldName": "created_at",
              "FunctionSpec": "day"
          }
      ],
      "TargetTableName": "my_target_table"
  }' \
  --region us-east-1

このプロパティは作成した統合に所有され、他の統合からの重複利用が競合として検出されます。

2
ターゲットテーブルプロパティの設定と競合確認
Bashテーブルプロパティの登録
aws glue create-integration-table-properties \
  --resource-arn arn:aws:glue:us-east-1:123456789012:catalog/s3tablescatalog/my-table-bucket \
  --table-name my-source-table \
  --target-table-config '{"TargetTableName": "my_target_table"}' \
  --region us-east-1

同じ組み合わせが既に別の統合に所有されている場合、AWS Glue が競合を検出します。コンソールでは「Output settings」ステップで同じ内容を設定でき、競合があれば「Action required」列またはインラインアラートで通知されます。

3
統合の作成
Bashzero-ETL 統合の作成
aws glue create-integration \
  --integration-name my-integration \
  --source-arn arn:aws:dynamodb:us-east-1:123456789012:table/my-source-table \
  --target-arn arn:aws:glue:us-east-1:123456789012:catalog/s3tablescatalog/my-table-bucket \
  --region us-east-1

登録済みのターゲットテーブルプロパティは、この統合に関連付けられて所有されます。競合が検出された場合は、別のターゲットリソースを選択するか、所有元の統合からソーステーブルを除外して解決します。

💡 メリット

📈 ビジネス面

✓データ破損リスクの低減: 統合同士の意図しない上書きを仕組みとして防止し、分析基盤のデータ信頼性が向上
✓チーム間ガバナンスの強化: 共有カタログでも所有関係が明確になり、運用ルールへの依存を削減
✓障害調査コストの削減: 書き込み元の統合が追跡可能になり、データ不整合の原因特定が容易に

⚙️ 技術面

✓作成前の競合検出: 「Output settings」で作成後の手戻りを防止
✓一貫した適用: コンソール・CLI・API のどの経路でも保護が有効
✓プログラムによる確認: ListIntegrationTableProperties と IntegrationArn で所有関係を監査可能
✓非ブロッキングな同時変更検出: 他ユーザーの同時変更は警告のみで作業を中断しない

⚠️ デメリット・制約事項

制限事項

✗1 つのターゲットリソースとソーステーブルの組み合わせは 1 統合のみが所有できるため、同じテーブルを同じターゲットに複数統合で書き込む構成は不可
✗別の統合に既に所有されているソーステーブルは、競合を解決するまで自分の統合ではレプリケーションされない
✗出力テーブル名には命名制約がある (小文字・数字・アンダースコアのみ、255 文字以内。S3 Tables カタログターゲットではアンダースコア始まり不可)
✗zero-ETL 統合のターゲットは作成後に変更できない

考慮すべき点

⚡意図的に同一ターゲットへ重複書き込みしている既存構成は、統合変更時に競合として検出される可能性があるため見直しが必要
⚡クロスアカウントのターゲットでは、ターゲットテーブルプロパティの設定を統合作成前に完了しておく必要がある
⚡統合作成後にテーブルプロパティを変更すると、既存設定と競合する変更 (パーティション列の変更など) ではフルリシンクが発生する可能性がある

🎯 ユースケース

1. 複数チームが共有する S3 Tables カタログの保護

シナリオ: 全社共通の Amazon S3 Tables カタログに、各事業部チームがそれぞれ DynamoDB テーブルから zero-ETL 統合でデータを取り込む。チーム間の調整不足で同じターゲットテーブルに複数統合が書き込むリスクがある。

実装: 各チームが Output settings で出力テーブル名を指定 → 他チームの統合が所有する組み合わせはコンソールが所有元を提示してブロック → 別の出力テーブル名やネームスペースを選択して解決。

効果: 事前のチーム間調整に頼らず、プラットフォーム側の仕組みとしてターゲットの重複を防止し、共有カタログのデータ整合性を保てる。

2. SaaS マルチテーブルソースの出力マッピング検証

シナリオ: SaaS アプリケーションをソースに数十のテーブルを SageMaker Lakehouse に同期。テーブル数が多く、出力テーブル名の重複や命名規則違反が発生しやすい。

実装: Output settings で全ソーステーブルの一覧を確認 → 「Action required」「Notes」列で名前の重複・無効な名前・他統合との競合を特定 → フラグ付きテーブルのみ修正して作成を続行。

効果: 多数のテーブルマッピングを作成前に一括検証でき、作成後に判明する構成ミスと修正作業を削減できる。

3. IaC パイプラインでの統合構成の監査

シナリオ: zero-ETL 統合を CLI / API ベースの IaC パイプラインで管理し、デプロイ前に所有状況を自動チェックしたい。

BashCI での所有統合の監査
# ターゲットリソース上のテーブルプロパティと所有統合を一覧
aws glue list-integration-table-properties \
  --resource-arn arn:aws:glue:us-east-1:123456789012:catalog/s3tablescatalog/my-table-bucket

# 出力の IntegrationArn を確認し、デプロイ対象の統合と
# 競合しないことを CI で検証

効果: 所有関係をプログラムから監査でき、CI/CD パイプラインの段階で競合を検出して安全にデプロイできる。

🔗 関連サービス・機能

🪣 Amazon S3 Tables

zero-ETL 統合のターゲットの 1 つ。S3 Tables カタログがターゲットリソースとして競合検出の識別キーになる。

🏠 Amazon SageMaker Lakehouse

zero-ETL 統合のターゲットとなるレイクハウスアーキテクチャ。汎用 S3 バケット、S3 Tables、Redshift Managed Storage をストレージとして利用可能。

⚡ Amazon DynamoDB

zero-ETL 統合の代表的なシングルテーブルソース。コンソールではインラインアラートで競合が通知される。

🔒 AWS Lake Formation

S3 Tables カタログや SageMaker Lakehouse カタログの権限管理を担う。

📝 まとめ

AWS Glue zero-ETL 統合のターゲットテーブルプロパティにオーナーシップ追跡と競合検出が追加され、複数の統合が意図せず同じターゲットテーブルへ書き込むリスクを仕組みとして防止できるようになりました。複数チームや多数の統合を運用する環境では、共有カタログのデータ整合性を高める重要な保護機能です。
