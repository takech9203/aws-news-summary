AWS Cloud WAN

🌐 AWS Cloud WAN が Flow Logs をサポート

📅 リリース日: 2026 年 11 月 11 日
機能: Cloud WAN Flow Logs

グローバルネットワーク全体の IP トラフィックを、Cloud WAN のアカウントから離れることなく一元的に可視化。コアネットワーク上のアタッチメント間のエンドツーエンドのフローを、トラフィック経路外でキャプチャするため、スループットやレイテンシーへの影響はゼロです。

📋 概要

Cloud WAN Flow Logs は、コアネットワーク上のアタッチメント間のエンドツーエンドのフローをキャプチャします。フローログレコードは、トラフィックがコアネットワークに入る (ingress)、またはコアネットワークから出る (egress) 各アタッチメントで記録されます。接続性やパフォーマンスのトラブルシューティング、キャパシティプランニング、異常トラフィックの検出、セキュリティ・コンプライアンス目的の記録保持に活用でき、マルチアカウント・マルチリージョンのネットワーク管理者に特に価値の高いアップデートです。

❌ Before: アップデート前の課題
  • 多数の VPC、アカウント、リージョンにまたがる VPC Flow Logs を個別に収集して突き合わせる必要があった
  • ログへのアクセスを VPC 所有者など他のチームに依存し、コアネットワーク所有者が自律的に調査できなかった
  • オンプレミス接続を含むコアネットワーク上のフローを、一貫した形式で横断的に分析する手段がなかった
✅ After: アップデート後の改善
  • VPC 間、リージョン間、Direct Connect・Site-to-Site VPN・SD-WAN 経由のオンプレミスとのトラフィックを 1 つの統合ビューで確認可能に
  • コアネットワーク全体 / コアネットワークエッジ / アタッチメントという柔軟な単位で有効化可能に
  • CloudWatch Logs、Amazon S3、Amazon Data Firehose の 3 種類の配信先に発行可能に

コアネットワークの各アタッチメントで ingress / egress のフローログレコードが記録され、CloudWatch Logs、Amazon S3、Amazon Data Firehose のいずれかに発行されます。

⚙️ 主要機能

🔭 グローバルネットワークの一元的な可視化
  • VPC 間、リージョン間、オンプレミス (Direct Connect、Site-to-Site VPN、SD-WAN 経由) とのトラフィックを統合的に把握
  • 個々の VPC Flow Logs の収集・結合作業が不要になり、他チームへの依存も解消
  • IP アドレス、ポート、プロトコル、トラフィック量、パケットロスカウンターに加え、セグメント・リージョン・サービス挿入ホップ・アタッチメント詳細などの Cloud WAN 固有メタデータを含む
🎚️ 柔軟な有効化スコープ
  • コアネットワーク全体 / 単一のコアネットワークエッジ / 個別のアタッチメントのいずれの単位でも有効化可能
  • サブスクリプションにタグを付与でき、目的や所有者による整理が可能
  • トラフィック経路外で収集されるため、作成・削除によるネットワークパフォーマンスへの影響なし
📤 3 種類の配信先
  • Amazon CloudWatch Logs: CloudWatch Logs Insights によるクエリやアラーム連携に最適
  • Amazon S3: 長期保管や Amazon Athena などによる分析に最適 (プレーンテキストまたは Parquet 形式)
  • Amazon Data Firehose: リアルタイムに近いストリーミング連携や外部 SIEM への転送に最適
🧩 カスタムフォーマット対応
  • デフォルトフォーマットは 1:1 NAT フィールド (src-nat-addr、dst-nat-addr) を除くバージョン 2〜13 の全フィールドを含む
  • カスタムフォーマットで必要なフィールドのみを任意の順序で出力でき、後続の抽出処理を削減可能

1
対象リソースと配信先の決定

フローログ作成対象 (コアネットワーク全体、コアネットワークエッジ、またはアタッチメント) と発行先 (CloudWatch Logs、Amazon S3、Amazon Data Firehose) を決定します。配信先ごとに必要な IAM 設定が異なるため、事前にユーザーガイドで確認します。

2
フローログサブスクリプションの作成

AWS Management Console、AWS CLI、または API を使用して、Cloud WAN のホームリージョンで作成します。作成時にデフォルトフォーマットまたはカスタムフォーマットを選択。作成直後は PROVISIONING 状態となり、初回作成時はコアネットワークが一時的に UPDATING 状態になります。

3
ログ配信の確認と分析

サブスクリプションが ACTIVE 状態になった後、数分程度でログ配信が開始されます。CloudWatch Logs Insights でのクエリ、Amazon Athena による S3 上の Parquet データの分析、Firehose 経由での外部分析基盤への連携など、配信先に応じた方法で分析します。

💪 メリット

💼 ビジネス面

✓運用負荷の削減: 複数アカウント・複数リージョンの VPC Flow Logs の収集・結合作業や、他チームへのログアクセス依頼が不要になり、ネットワーク運用の効率が向上
✓コンプライアンス対応: グローバルネットワーク全体の通信記録を一貫した形式で保持でき、セキュリティ監査や要件対応が容易に
✓追加コストなしで利用可能: Cloud WAN 側の追加料金は発生せず、配信先の標準料金のみで利用できる

🔧 技術面

✓パフォーマンスへの影響なし: トラフィック経路外で収集されるため、スループットやレイテンシーに影響を与えずに有効化・無効化できる
✓豊富なメタデータ: セグメント名、リージョン、アタッチメント、サービス挿入ホップなど Cloud WAN 固有の情報により、トラブルシューティングや経路分析が容易に
✓パケットロスの可視化: ルート未指定、ブラックホール、MTU 超過、TTL 失効といった原因別カウンターにより、接続性問題の切り分けが迅速に

⚠️ デメリット・制約事項

制限事項

✗サブスクリプションは 1 アカウントあたり、リソースごとに最大 250 件まで
✗Tunnel-less Connect (TLC) アタッチメントは非対応。TLC アタッチメントを通過するフローは基盤となるトランスポート (VPC) アタッチメント側に記録されるため、トランスポートアタッチメントでフローログを作成する必要がある
✗Route Table アタッチメントは非対応。これを通過するフローは基盤となるピアリング接続側に記録される
✗サブスクリプションは Cloud WAN のホームリージョンでのみ作成可能

考慮すべき点

⚠フローログはリアルタイムのログストリームではなく、配信開始まで数分かかる場合がある
⚠初回のサブスクリプション作成時にはコアネットワークが一時的に UPDATING 状態になり、ACTIVE 後もログ配信開始まで数分を要する
⚠セグメント ID は初期伝播中に一時的に古い値になる場合がある
⚠内部エラーやログ伝播遅延により、フローがエンドツーエンドで相関されず、log-status が INCOMPLETEDATA となる場合がある
⚠フローログの削除では既存のログデータは削除されないため、不要なログは CloudWatch Logs や Amazon S3 側で別途削除が必要

🎯 ユースケース

1️⃣ グローバルネットワークの接続性トラブルシューティング

シナリオ: 東京リージョンの VPC からバージニア北部リージョンの VPC への通信が断続的に失敗しており、原因を特定したい。

実装例CloudWatch Logs での調査
1. コアネットワーク全体でフローログを有効化し、CloudWatch Logs に発行
2. CloudWatch Logs Insights で該当の送信元・宛先 IP のフローを抽出
3. packets-lost-no-route や packets-lost-blackhole などの
   原因別パケットロスカウンターを確認し、ルーティング設定を修正

💡 効果: 複数リージョンの VPC Flow Logs を突き合わせることなく、コアネットワーク上のどこでパケットが失われているかを迅速に特定できる。

2️⃣ 帯域幅トレンドに基づくキャパシティプランニング

シナリオ: オンプレミスと AWS 間のトラフィックが増加傾向にあり、Direct Connect の増強時期を計画したい。

実装例S3 + Athena での分析
1. Direct Connect 関連のアタッチメントでフローログを有効化し、
   Parquet 形式で Amazon S3 に発行
2. Amazon Athena で bytes フィールドを期間・アタッチメント別に集計
3. 過去の帯域幅トレンドから将来の必要帯域を予測

💡 効果: 実測データに基づいた精度の高いキャパシティプランニングが可能になり、帯域不足による障害や過剰投資を回避できる。

3️⃣ セキュリティ監視と異常トラフィックの検出

シナリオ: グローバルネットワーク上でセグメント間の想定外の通信や異常なトラフィックパターンを検出したい。

実装例Firehose + SIEM 連携
1. コアネットワーク全体でフローログを有効化し、
   Amazon Data Firehose 経由で SIEM に連携
2. src-segment-name と dst-segment-name を用いて
   セグメント間通信のベースラインを作成
3. ベースラインから逸脱する通信を検出した際にアラートを発報

💡 効果: Cloud WAN メタデータを活用したセグメント単位の監視により、ネットワーク全体のセキュリティ態勢を強化し、インシデントの早期検出につながる。

💰 料金

Cloud WAN Flow Logs 自体に追加料金は発生しません。配信先ごとの標準料金 (Vended Logs のデータ取り込み・保存料金など) が適用されます。

配信先課金の考え方
Amazon CloudWatch LogsVended Logs のデータ取り込みおよび保存料金
Amazon S3Vended Logs の配信料金およびストレージ料金
Amazon Data FirehoseFirehose のデータ取り込み料金

詳細は Amazon CloudWatch 料金ページ の Paid tier にある Logs の Vended Logs を参照してください。

🗺️ 利用可能リージョン

AWS Cloud WAN が利用可能なすべての AWS リージョンで利用できます。なお、フローログサブスクリプションの作成は Cloud WAN のホームリージョンでのみ可能です。

🔗 関連サービス・機能

VPC Flow Logs: VPC 内の ENI 単位で IP トラフィックをキャプチャする機能。Cloud WAN Flow Logs はコアネットワーク上のアタッチメント間フローを対象とする点で補完関係にある
Amazon CloudWatch Logs: フローログの配信先の 1 つ。CloudWatch Logs Insights によるクエリやメトリクスフィルターと組み合わせた監視が可能
Amazon S3: フローログの長期保管先。Parquet 形式で出力すれば Amazon Athena による効率的な分析が可能
Amazon Data Firehose: フローログをストリーミングで外部の分析基盤や SIEM に連携する際に使用
AWS Transit Gateway Flow Logs: Transit Gateway 向けの同様のフローログ機能。Cloud WAN への移行時にも一貫した可観測性を維持できる

📝 まとめ

AWS Cloud WAN の Flow Logs サポートにより、これまで多数の VPC Flow Logs を突き合わせる必要があったグローバルネットワークのトラフィック可視化が、コアネットワーク所有者の単一ビューで完結するようになりました。Cloud WAN 側の追加料金なしで利用でき、ネットワークパフォーマンスへの影響もないため、Cloud WAN を利用中のネットワーク管理者はまずコアネットワーク全体で有効化し、トラブルシューティングやセキュリティ監視への活用を検討することを推奨します。
