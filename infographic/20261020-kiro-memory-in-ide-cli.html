🧠 Kiro - Kiro IDE と CLI におけるメモリ機能の導入

Memory in Kiro IDE and CLI — セッションをまたいでコンテキストを引き継ぎ、使い込むほどユーザーの好みに沿って動作
Kiro 📅 2026 年 10 月 20 日 🖥️ IDE 1.4.0 以降 / ⌨️ CLI 2.29.0 以降 🔒 デフォルトで無効 (オフ)

📋 概要

Kiro IDE と Kiro CLI にメモリ機能が導入されました。Kiro は、ユーザーの好みの作業スタイル、リポジトリ固有のコマンドや規約、過去の修正指示、デバッグで得られた知見、すでに検討から除外したアプローチなどを記憶し、再び関連する場面でコンテキストを自動的に引き継ぎます。コンテキストの再説明や同じ修正指示の繰り返しが減り、使い込むほど Kiro がユーザーの好みに沿って動作するようになります。

メモリは過去の会話の再生ではなく、後の作業に役立つ具体的なコンテキストを保持する仕組みで、理解の変化に応じて記憶内容を更新 (refine) できます。記憶はローカルマシンに保存され、同一マシン上の IDE と CLI の間で共有されます。各メモリはグローバルまたはリポジトリ単位のスコープで適用されます。

なお、今回のローンチではメモリ機能はデフォルトで無効 (オフ) です。既存メモリの利用可否と、メモリの作成・更新可否をユーザー自身が制御できます。

❌ Before: アップデート前の課題
  • セッションが変わるたびに、作業の進め方の好みやリポジトリ固有の事情を Kiro に再説明する必要があった
  • 一度行った修正指示 (例: 特定のロジックの配置場所) を、新しいセッションで繰り返し伝える必要があった
  • デバッグで得た知見や、すでに検討から除外したアプローチが、セッション終了とともに失われていた
  • Steering ルールやプロジェクトドキュメントは事前に明文化できるコンテキストには有効だが、作業中に自然に生まれるコンテキストは記録されないまま失われがちだった
✅ After: アップデート後の改善
  • 作業中に現れたコンテキストを Kiro が自動的に記憶として捕捉し、以降のセッションに引き継げるようになった
  • 同一マシン上の Kiro IDE と CLI の間で記憶が共有され、どちらのクライアントからも同じコンテキストを利用できるようになった
  • グローバル / リポジトリ単位のスコープにより、汎用的な好みとコードベース固有の知識を区別して管理できるようになった
  • IDE の Memories ビューや CLI の /memories コマンドで、Kiro が何を記憶しているかを確認・検索・削除できるようになった

🚀 主要機能

1️⃣ 作業中に生まれるコンテキストの記憶

ロジックの配置場所に関する修正指示、デバッグ中に判明した手順 (例: ローカルサービスの起動が統合テストの前提)、変更へのアプローチ方法の好みなどを、作業の流れの中で Kiro が自動的に捕捉します。Steering ルールが「事前に明文化して一貫適用したいコンテキスト」向けであるのに対し、メモリは「作業中に現れ、放っておくと記録されないコンテキスト」向けという位置づけです。過去の会話の再生ではなく、後の作業に役立つ具体的なコンテキストのみを保持し、理解の変化に応じて記憶を更新できます。

2️⃣ ローカル保存と IDE / CLI 間の共有

記憶はユーザーのローカルマシンに保存され、同一マシン上の Kiro IDE と CLI で共有されます。一方のクライアントで獲得したコンテキストをもう一方でも利用できます。各メモリはグローバルまたは特定リポジトリのスコープを持ち、汎用的な好みとコードベース固有のコンテキストを区別できます。

3️⃣ 記憶の可視化と制御

IDE では、Kiro がメモリにアクセス・作成・更新・削除した際にチャット上に表示され、記憶の利用や変更を確認できます。アクティビティバーの Memories ビューから、記憶の一覧表示・検索、適用スコープの確認、個別エントリの閲覧、不要な記憶の削除が可能です。CLI では、呼び出された記憶がチャット内に Memory エントリとして表示され、/memories コマンドで保存済みメモリの検索・プレビュー・表示ができます。

4️⃣ デフォルトオフとアクセス制御

今回のローンチではメモリ機能はデフォルトで無効です。IDE と CLI の両方で「既存メモリを利用できるか」「メモリを作成・更新できるか」を個別に制御できます (IDE の Kiro Agent: Memory 設定には、記憶を変更せず利用のみ行う Use only などの選択肢があります)。呼び出された記憶は Kiro が利用可能なコンテキストの一部となるため、メモリの利用によりコンテキスト使用量が増加する可能性があります。

⚙️ 設定方法

前提条件

→Kiro IDE 1.4.0 以降、または Kiro CLI 2.29.0 以降がインストールされていること
→Kiro CLI で利用する場合は、ローカル V3 セッションを使用していること
→メモリはデフォルトで無効のため、利用には明示的な有効化が必要であること

手順

1
Kiro IDE でメモリを有効化する

アクティビティバーから Memories ビューを開き、設定から Use and learn を選択します。これにより、Kiro が既存のメモリを利用し、作業中に自動的にメモリを作成・更新できるようになります。有効化後は通常どおり Kiro と作業するだけで、記憶が蓄積されていきます。

2
Kiro CLI でメモリを有効化する
Bash CLI のチャット内でメモリの確認・設定を行う 
# CLI のチャット内でメモリの確認・設定を行う
/memories

/memories コマンドで保存済みメモリの確認やアクセス設定を行います。read & write アクセスを設定すると自動メモリ更新を有効化でき、Kiro が作業中にメモリを作成・更新できるようになります。設定変更は新しい CLI セッションから有効になります。

3
記憶の確認と管理

IDE: Memories ビューに戻れば、いつでも記憶の内容を確認し、不要な記憶を削除したり、メモリの動作設定を変更したりできます。

CLI: /memories で保存済みメモリの検索・プレビュー・表示ができます。

👍 メリット

💼 ビジネス面

✓再説明コストの削減: セッションごとのコンテキスト再説明や修正指示の繰り返しが不要になり、開発者が本来の作業に集中できる
✓利用期間に応じた価値向上: Kiro を使い込むほどユーザーの好みやプロジェクト固有の知識が蓄積され、支援の精度が高まる
✓知見の喪失防止: デバッグ中に得た知見や検討済みのアプローチがセッション終了で失われず、同じ試行錯誤の繰り返しを防げる

🔧 技術面

✓IDE / CLI 間のシームレスな共有: 同一マシン上であれば、IDE で獲得したコンテキストを CLI でも活用でき、クライアントをまたいだ一貫した動作が得られる
✓スコープによる適切な適用: グローバルとリポジトリ単位のスコープにより、汎用的な好みと特定コードベース固有の知識が混ざらない
✓透明性と制御性: チャット上での記憶アクセス表示、Memories ビュー、/memories コマンドにより、Kiro が何を記憶し利用しているかを常に確認・管理できる
✓Steering ルールとの補完関係: 事前に明文化するルールと、作業中に自然発生するコンテキストの両方をカバーできる

⚠️ デメリット・制約事項

制限事項

✗メモリはデフォルトで無効のため、利用には IDE または CLI での明示的な有効化が必要
✗Kiro CLI ではローカル V3 セッションでのみ利用可能
✗記憶はローカルマシンに保存されるため、別のマシンとの間では共有されない
✗CLI でのメモリアクセス設定の変更は、新しいセッションを開始するまで反映されない

考慮すべき点

→呼び出された記憶は Kiro のコンテキストに含まれるため、メモリの利用によりコンテキスト使用量が増加する可能性がある
→不要・不正確になった記憶が蓄積されると意図しない動作につながる可能性があるため、Memories ビューや /memories で定期的に内容を確認し、不要な記憶を削除することが望ましい
→事前に明文化して一貫適用したいコンテキストには、引き続き Steering ルールやプロジェクトドキュメントの利用が適している

💡 ユースケース

1. リポジトリ固有の規約・手順の自動適用

シナリオ: 特定のリポジトリでは、統合テストの実行前にローカルの依存サービスを起動する必要があり、また特定の種類のロジックは決まったディレクトリに配置する規約がある。

実装例: IDE の Memories ビューで Use and learn を有効化 → 作業中に「このロジックは services 層に置いて」と修正指示 → デバッグ中に「ローカルサービス起動後にテストが通る」ことが判明 → Kiro がこれらをリポジトリスコープのメモリとして記憶。

✅ 効果: 次回以降のセッションで、Kiro が自動的に規約に沿った配置や正しいテスト手順を適用し、同じ指摘を繰り返す必要がなくなる。
2. IDE と CLI をまたいだ作業スタイルの共有

シナリオ: 日中は Kiro IDE でコードレビューや実装を行い、定型作業やスクリプト実行は Kiro CLI で行う開発者が、どちらのクライアントでも同じ作業スタイル (コミットメッセージの書き方、変更アプローチの好みなど) を適用したい。

実装例: IDE 側で Use and learn を有効化し、作業中に好みを記憶させる → CLI 側で /memories から read & write アクセスを設定 → 同一マシン上でメモリが共有され、CLI でも IDE で獲得したグローバルスコープの記憶が利用される。

✅ 効果: クライアントを切り替えても一貫した支援が受けられ、環境ごとの再設定や再説明が不要になる。
3. 検討済みアプローチの記録による手戻り防止

シナリオ: パフォーマンス改善の作業で、いくつかのアプローチを試した結果、特定の方式は副作用があるため採用しないと判断した。数週間後に別のセッションで同様の改善作業を行う。

実装例: メモリ有効化済みの状態で、除外したアプローチとその理由を Kiro との対話の中で明確にする → Kiro が「すでに検討から除外したアプローチ」として記憶 → 後日のセッションで同じ領域の改善を依頼すると、Kiro が除外済みアプローチを避けた提案を行う。

✅ 効果: 過去に否定した方式を Kiro が再提案することがなくなり、検討の手戻りを防止できる。

🌍 利用可能リージョン

🎯 まとめ

Kiro IDE と CLI へのメモリ機能の導入により、作業中に生まれるコンテキストがセッションをまたいで引き継がれ、Kiro は使い込むほど開発者の好みやプロジェクト固有の知識に沿った支援ができるようになります。メモリはデフォルトで無効かつローカル保存であり、何を記憶させるか・学習を続けるかをユーザーが完全に制御できる設計です。Kiro IDE 1.4.0 以降または Kiro CLI 2.29.0 以降を利用している場合は、Memories ビューまたは /memories コマンドからメモリを有効化し、再説明の手間を減らす効果を試すことを推奨します。
