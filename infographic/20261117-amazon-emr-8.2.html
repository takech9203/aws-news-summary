⚙️ Amazon EMR 8.2 リリース

📅 2026 年 11 月 17 日 | EMR on EC2 / EMR on EKS / EMR Serverless | 長期サポート (LTS) リリース

📋 概要

Amazon EMR 8.2 が一般提供開始されました。EMR on EC2、EMR on EKS、EMR Serverless の 3 つのデプロイメントオプションすべてに新機能をもたらし、 Apache Spark 4.1.3、Apache Iceberg 1.11.0、Delta Lake 4.2.0 へのアップグレードを含みます。 本リリースは長期サポート (LTS) リリースに指定され、2029 年 11 月 17 日まで標準サポートが提供されます。

中心テーマは「セキュアでガバナンスの効いた大規模分析の容易化」です。 S3 条件付き書き込みによる Delta Lake 同時書き込み (DynamoDB ログストア不要)、Iceberg マテリアライズドビューの増分リフレッシュ、 信頼されたアイデンティティ伝搬 (Trusted Identity Propagation) など、データ基盤のガバナンスと運用効率を大きく向上させる機能が含まれています。

❌ アップデート前の課題

✗複数クラスターからの Delta Lake 同時書き込みには DynamoDB ベースのログストアを別途構成・運用する必要があった
✗マテリアライズドビューはリフレッシュのたびにソーステーブル全体を再計算する必要があり、コストが高かった
✗ジョブは実行ロールの権限で動作するため、Lake Formation や S3 へのアクセスを「元のユーザー」として認可・監査することが難しかった
✗Lake Formation FGAC 環境ではカスタム UDF や一部の Iceberg 操作、Spark SQL 機能に制限があった
✗高同時実行数のもとではユーザープロビジョニングに大きなレイテンシーが発生することがあった

✅ アップデート後の改善

✓S3 条件付き書き込みにより、DynamoDB ログストアなしで複数クラスターから同一 Delta Lake テーブルへ同時書き込み可能に
✓Iceberg v3 テーブル上のマテリアライズドビュー (射影、フィルター、内部結合、SUM / COUNT 集計) が変更分のみを増分リフレッシュ
✓信頼されたアイデンティティ伝搬により、Lake Formation や S3 Access Grants まで元のユーザーとして認可・監査可能に
✓FGAC がマテリアライズドビュー、ガバナンス付き UDF、追加 Iceberg 操作、HyperLogLog 関数などをカバー
✓Secret Agent 改善でプロビジョニングレイテンシーを最大 97% 削減。EMR Serverless スケーリングプロファイル、Spark Operator v2 も追加

EMR 8.2 では、3 つのデプロイメントオプションすべてから、エンドユーザーのアイデンティティを Lake Formation や Amazon S3 まで伝搬し、 元のユーザーとして認可・監査できます。また、S3 条件付き書き込みにより複数クラスターからの同時 Delta Lake 書き込みが可能になります。

🚀 主要機能

1️⃣ Apache Spark 4.1.3 へのアップグレードと LTS 指定
  • Apache Spark 4.1.3、Apache Iceberg 1.11.0、Delta Lake 4.2.0、Apache Hudi 1.1.1 を同梱
  • Apache ORC 2.2.2、AWS SDK for Java v2 2.55.8 などの依存関係も更新
  • GPU ワークロード向けに NVIDIA cuDF plugin for Apache Spark 26.08.1 をサポート
  • LTS リリースに指定され、2029 年 11 月 17 日まで標準サポート
2️⃣ 複数クラスターからの同時 Delta Lake 書き込み (全デプロイメントオプション)
  • S3 条件付き書き込みを利用し、DynamoDB ベースのログストアなしで同一 Delta Lake テーブルへ複数の Spark ジョブ / クラスターから同時書き込みが可能
  • 2 つのライターが同時にコミットした場合、一方のみが成功し、他方は標準的な Delta コミット競合を受け取ってリトライ可能
3️⃣ Iceberg マテリアライズドビューの強化 (Glue Data Catalog)
  • 増分リフレッシュ: Iceberg v3 テーブル上の集計なしビュー (射影、フィルター、内部結合) はデフォルトで増分リフレッシュ、必要時にはフルリフレッシュへフォールバック。Hive Parquet ベーステーブルも追記のみの変更で対応
  • FGAC 対応: FGAC 有効クラスターでビューの作成・リフレッシュが可能。行フィルターと列マスクはビュー定義者のポリシーに基づき適用
  • Spark Declarative Pipelines 対応: パイプライン定義のビューを Glue Iceberg マテリアライズドビューとして保存。変更がなければリフレッシュをスキップ
  • スキーマ進化: CREATE OR REPLACE によるスキーマ進化をサポート
4️⃣ 信頼されたアイデンティティ伝搬 (Trusted Identity Propagation)
  • ステップおよび対話型セッション (Spark Connect / Livy) が IAM Identity Center の信頼されたアイデンティティコンテキストをランタイムロールセッションに伝搬
  • Lake Formation や S3 Access Grants が「元のユーザー」としてアクセスを認可・監査可能
  • 永続的な Spark History Server では、完了したアプリケーションの所有者として各ユーザーを表示
  • EMR on EKS でも IAM フェデレーションユーザー向けにバッチジョブ・対話型セッションの両方でサポート
  • ワークロード完了後、一時 OS ユーザーと HDFS ホームディレクトリ、認証情報を自動クリーンアップ (デフォルト有効)
5️⃣ Lake Formation FGAC の対象範囲拡大
  • ガバナンス付きカスタム UDF: 管理者承認済みのカスタムコードアーティファクトとしてパッケージ化された UDF を FGAC クラスターから呼び出し可能。未承認関数を呼び出すクエリは拒否
  • 追加の Iceberg 操作: ALTER TABLE ... SET LOCATION、WRITE ORDERED BY、WRITE DISTRIBUTED BY、add_files / register_table プロシージャに対応
  • Spark SQL 機能の拡大: uuid()、variant 式、列デフォルト値、HyperLogLog スケッチ関数、型付き Dataset、Hudi 増分 / 変更データクエリなどが FGAC 環境で利用可能に
6️⃣ OpenLineage ベースのリネージ取得
  • glue-openlineage-spark ライブラリにより、Spark ジョブから OpenLineage 互換のリネージを自動取得して Glue Data Catalog またはカスタムトランスポートへ発行
  • リネージには入出力データセット・カラム、スキーマ、ユーザーアイデンティティなどを含む
  • 従来の datazone-openlineage-spark ライブラリを置き換え
7️⃣ EMR on EC2 固有の機能強化
  • マルチプライマリクラスターでの Spark Connect: emr-spark-8.2.0 以降でサポート
  • Secret Agent の改善: ノード間接続の再利用、CPU キャップのデフォルト撤廃、デッドロック修正などにより、ユーザープロビジョニングレイテンシーを最大 97% 削減
  • EMRFS から S3A への移行支援: オプトインパラメータ fs.s3a.emrfs.compatibility.folder.marker.as.dir と fs.s3a.emrfs.compatibility.marker.empty を追加
8️⃣ EMR Serverless 固有の機能強化
  • スケーリングプロファイル: spark.emr-serverless.scalingProfile に performance-optimized / balanced / cost-optimized を指定してエグゼキューターのスケール速度を選択可能 (デフォルトは balanced)
  • Lake Formation ガバナンス付き Glue UDF: 行フィルター式を含め、Lake Formation がガバナンスする Glue UDF を実行可能
9️⃣ EMR on EKS 固有の機能強化
  • Spark Operator バージョン 2: オープンソース Spark Operator 2.5.0 ベースにアップグレード。イメージタグ未指定時は Helm チャートが最新のパッチ適用済みイメージを使用
  • FGAC ユーザーエグゼキューターへのノードセレクター適用: 従来適用されなかったノードセレクターがユーザーエグゼキューターにも適用されるよう修正

🛠️ 設定方法

✅ 前提条件

✓Amazon EMR を利用できる AWS アカウントと適切な IAM 権限
✓Lake Formation FGAC や信頼されたアイデンティティ伝搬を使用する場合は、AWS Lake Formation および IAM Identity Center の設定
✓マテリアライズドビューの増分リフレッシュを最大限活用する場合は、Iceberg v3 テーブルの利用

ステップ 1: EMR 8.2 クラスターの作成 (EMR on EC2)

Bash AWS CLI でクラスター作成 
aws emr create-cluster \
  --name "emr-spark-8.2-cluster" \
  --release-label emr-spark-8.2.0 \
  --applications Name=Spark Name=Livy \
  --instance-type m7g.xlarge \
  --instance-count 3 \
  --use-default-roles

リリースラベル emr-spark-8.2.0 を指定して EMR on EC2 クラスターを作成します。Spark と Livy をインストールし、デフォルトの IAM ロールを使用します。

ステップ 2: EMR Serverless アプリケーションでスケーリングプロファイルを設定

Bash スケーリングプロファイルの指定 
aws emr-serverless create-application \
  --name "spark-8.2-app" \
  --release-label emr-spark-8.2.0 \
  --type SPARK \
  --runtime-configuration '[
    {
      "classification": "spark-defaults",
      "properties": {
        "spark.emr-serverless.scalingProfile": "cost-optimized"
      }
    }
  ]'

EMR Serverless アプリケーションを作成し、アプリケーションデフォルトとしてコスト最適化のスケーリングプロファイルを設定します。ジョブ単位で Spark プロパティを上書きすることも可能です。

ステップ 3: Iceberg マテリアライズドビューの作成と増分リフレッシュ

SQL マテリアライズドビューの作成と増分リフレッシュ 
-- マテリアライズドビューの作成 (集計を含む例)
CREATE MATERIALIZED VIEW glue_catalog.analytics.daily_sales_mv AS
SELECT order_date, region, SUM(amount) AS total_amount, COUNT(*) AS order_count
FROM glue_catalog.sales.orders
WHERE status = 'COMPLETED'
GROUP BY order_date, region;

-- 増分リフレッシュの実行 (変更分のみを反映)
REFRESH MATERIALIZED VIEW glue_catalog.analytics.daily_sales_mv;

Glue Data Catalog 上に Iceberg マテリアライズドビューを作成します。Iceberg v3 ベーステーブルでは、射影・フィルター・内部結合・SUM / COUNT 集計を含むビューが変更分のみを増分リフレッシュします。

💼 ビジネス面

✓ガバナンスとコンプライアンスの強化: データアクセスを実行ロールではなく元のユーザー単位で認可・監査でき、監査要件への対応が容易に
✓運用コストの削減: Delta Lake 同時書き込みに DynamoDB ログストアが不要になり、追加コンポーネントの構築・運用・コストが削減
✓計算コストの最適化: 増分リフレッシュによりソーステーブル全体の再計算が不要になり、計算コストと処理時間を削減
✓長期的な安定運用: LTS として 2029 年 11 月まで標準サポートが提供され、計画的なバージョン管理が可能

⚙️ 技術面

✓アーキテクチャの簡素化: S3 条件付き書き込みベースの Delta Lake コミットにより、マルチクラスター書き込み構成がシンプルに
✓FGAC 環境での表現力向上: ガバナンス付き UDF、追加 Iceberg 操作、拡大された Spark SQL 機能により、セキュリティを維持したまま高度な処理を実装可能
✓スケーラビリティの向上: Secret Agent の改善により高同時実行環境でのレイテンシーが最大 97% 削減

⚠️ デメリット・制約事項

🚧 制限事項

⚠️集計なしマテリアライズドビューのデフォルト増分リフレッシュは Iceberg v3 テーブルが対象 (Hive Parquet ベーステーブルは追記のみの変更に限定)
⚠️Spark Declarative Pipelines のビューを Glue Iceberg マテリアライズドビューとして保存するにはオプトイン設定が必要 (オプトイン後に作成されたビューのみ適用)
⚠️ガバナンス付き UDF の利用には実行ロールへの lakeformation:GetTemporaryGlueFunctionCredentials 権限付与が必要
⚠️Delta Lake 同時書き込みでは、コミット競合時に一方のライターがリトライ処理を実装する必要がある

🔍 考慮すべき点

⚠️Spark 4.1.3 へのメジャーバージョンアップを伴うため、既存ジョブの互換性検証を推奨 (特に EMR 7.x 以前からの移行時)
⚠️glue-openlineage-spark は従来の datazone-openlineage-spark を置き換えるため、既存のリネージ設定の確認が必要
⚠️一時 OS ユーザークリーンアップはデフォルト有効のため、完了後のユーザー環境に依存する運用がある場合は emr.secretagent.users.teardown.enabled を確認
⚠️EMR Serverless のスケーリングプロファイルは、独自に設定した Spark 動的割り当て設定が優先される

🎯 ユースケース

1. マルチクラスターからの Delta Lake テーブル同時更新

シナリオ: 複数の部門がそれぞれの EMR クラスターから共通の Delta Lake テーブルにデータを書き込むデータ基盤。従来は DynamoDB ログストアの構築と運用が必要だった。

Python 同時書き込みの実装例 
# 各クラスターから同一テーブルへ同時書き込み (特別なログストア設定は不要)
df.write.format("delta") \
    .mode("append") \
    .save("s3://my-datalake/tables/shared_events/")
# コミット競合が発生した場合は Delta の標準的な競合例外を受け取りリトライ
✅ 効果: DynamoDB ログストアの構築・運用が不要になり、アーキテクチャが簡素化されるとともに運用コストが削減される。
2. SQL によるパイプラインステージの事前計算と増分リフレッシュ

シナリオ: 日次で大量データを集計する ETL パイプラインで、毎回ソーステーブル全体を再計算しており、処理時間とコストが課題になっている。

SQL パイプラインステージの事前計算 
CREATE MATERIALIZED VIEW glue_catalog.mart.region_revenue_mv AS
SELECT region, product_category, SUM(revenue) AS total_revenue
FROM glue_catalog.raw.transactions t
JOIN glue_catalog.raw.products p ON t.product_id = p.product_id
GROUP BY region, product_category;

REFRESH MATERIALIZED VIEW glue_catalog.mart.region_revenue_mv;
✅ 効果: 各ステージが変更分のみを増分リフレッシュするため、再計算コストと処理時間が大幅に削減される。
3. エンドユーザー単位のアクセス制御と監査

シナリオ: 複数のデータアナリストが対話型セッション (Spark Connect / Livy) から機密データを分析する環境で、ロール単位ではなくユーザー単位でのアクセス制御と監査証跡が求められている。

💰 料金

Amazon EMR 8.2 の利用自体に追加料金はありません。通常の Amazon EMR 料金体系が適用されます。

EMR on EC2: EC2 インスタンス料金 + EMR 料金 (インスタンスタイプごとの秒単位課金)
EMR on EKS: vCPU およびメモリリソースに基づく秒単位課金 + EKS クラスター料金
EMR Serverless: ワーカーが使用した vCPU、メモリ、ストレージに基づく秒単位課金 (cost-optimized スケーリングプロファイルの活用でコスト最適化が可能)

詳細は Amazon EMR 料金ページ を参照してください。

🌏 利用可能リージョン

Amazon EMR 8.2 は、Amazon EMR が利用可能なすべての AWS リージョンで利用できます (🗾 東京・大阪リージョンを含む)。

📝 まとめ

Amazon EMR 8.2 は、Spark 4.1.3 / Iceberg 1.11.0 / Delta Lake 4.2.0 を同梱する LTS リリースであり、 S3 条件付き書き込みによる Delta Lake 同時書き込み、Iceberg マテリアライズドビューの増分リフレッシュ、 信頼されたアイデンティティ伝搬など、ガバナンスと効率性を両立する機能が多数追加されました。

データレイクのガバナンス強化や ETL パイプラインのコスト最適化を検討している場合は、EMR 8.2 への移行検証を推奨します。 LTS リリースのため、2029 年 11 月までの長期的な運用計画にも適しています。
