🔒 NLB TLS リスナーサポート

Network Load Balancer 環境で TLS リスナーをマネージド設定として構成可能に

AWS Elastic Beanstalk
2026 年 5 月 6 日

📋 概要

AWS Elastic Beanstalk が Network Load Balancer (NLB) 環境で TLS リスナーをサポート。Elastic Beanstalk のコンソールまたは CLI から直接 TLS リスナーの設定が可能になり、NLB レベルでの TLS 終端を構成できるようになった。SSL 証明書とセキュリティポリシーを指定して、ロードバランサーで暗号化接続を処理し、復号済みトラフィックをインスタンスに転送する構成が実現する。

❌ Before

  • NLB 環境ではマネージド設定として TLS リスナーを構成できなかった
  • NLB で TLS 終端を行うには Elastic Beanstalk 外で手動設定が必要
  • TLS 設定を環境設定と一元管理できず運用の複雑さが増加

✅ After

  • コンソールまたは CLI から NLB の TLS リスナーを直接設定可能
  • SSL 証明書とセキュリティポリシーを Elastic Beanstalk の設定として管理
  • NLB レベルでの TLS 終端がマネージド設定として統合、運用簡素化

🏗️ アーキテクチャ図

Elastic Beanstalk 環境内の NLB に TLS リスナーを設定し、HTTPS トラフィックを NLB で復号してバックエンドインスタンスには平文で転送するアーキテクチャ。

⚡ 主要機能

🔒 TLS リスナーの設定
NLB 環境で TLS リスナーを追加可能。ポート番号とプロトコルを指定して設定し、複数のリスナーを同時に構成可能。
📜 SSL 証明書の指定
AWS Certificate Manager で管理された証明書を使用可能。TLS リスナーに証明書を関連付けて TLS 終端を実現。証明書の更新も ACM 経由で管理。
🛡️ セキュリティポリシーの設定
TLS プロトコルバージョンと暗号スイートを制御するセキュリティポリシーを選択可能。AWS 提供の事前定義ポリシーからセキュリティ要件に応じて選択。

📝 設定方法

前提条件

  • Elastic Beanstalk 環境が Network Load Balancer を使用するよう設定されていること
  • AWS Certificate Manager (ACM) で有効な SSL/TLS 証明書が発行済みであること
  • 適切な IAM 権限が付与されていること

Step 1: ACM で SSL 証明書を準備

Bash ACM 証明書リクエスト 
# ACM で証明書をリクエスト
aws acm request-certificate \
  --domain-name "example.com" \
  --validation-method DNS \
  --subject-alternative-names "*.example.com"

Step 2: .ebextensions で TLS リスナーを構成

YAML .ebextensions/nlb-tls.config 
# .ebextensions/nlb-tls.config
option_settings:
  aws:elbv2:listener:443:
    ListenerEnabled: true
    Protocol: TLS
    SSLCertificateArns: arn:aws:acm:region:account-id:certificate/certificate-id
    SSLPolicy: ELBSecurityPolicy-TLS13-1-2-2021-06

Step 3: 環境をデプロイ

Bash Elastic Beanstalk CLI デプロイ 
# Elastic Beanstalk CLI でデプロイ
eb deploy

Step 4: コンソールから設定する場合

⚖️ メリットと制約事項

👍 メリット

  • 運用コスト削減: マネージド設定で個別設定の手間を排除
  • コンプライアンス対応簡素化: ロードバランサーレベルで暗号化を統一適用
  • デプロイ効率化: 環境設定と TLS 設定を同時にデプロイ
  • TLS オフロード: NLB で TLS 終端しインスタンスの CPU 負荷軽減
  • 一元管理: Infrastructure as Code として TLS 設定を管理
  • セキュリティポリシーの柔軟性: AWS 最新ポリシーで暗号化強度を制御

⚠️ 制約事項・注意点

  • NLB 環境のみが対象 (ALB とは設定方法が異なる)
  • エンドツーエンド暗号化には別途バックエンドの再暗号化が必要
  • セキュリティポリシーは AWS 事前定義のものから選択
  • ACM 証明書は NLB と同じリージョンに存在する必要あり
  • TLS リスナー追加で NLB の処理オーバーヘッドが若干増加の可能性
  • TCP パススルーから切替時にバックエンドアプリの構成変更が必要な場合あり

💡 ユースケース

🌐 Web アプリケーションの HTTPS 対応
Elastic Beanstalk で運用している Web アプリケーションに HTTPS を導入したいが、各インスタンスでの証明書管理を避けたい場合。NLB で TLS を終端し、バックエンドは平文通信のみ処理する構成。
➤ NLB で TLS 終端し、証明書管理の複雑さを排除しつつ HTTPS を実現
⚡ マイクロサービス間の安全な通信
TCP ベースの高パフォーマンスが必要なマイクロサービスで、サービス間通信を暗号化する必要がある場合。カスタムポート 8443 で TLS リスナーを構成。
➤ NLB レイヤー 4 の高パフォーマンスを維持しつつ TLS 暗号化を実現。ALB 比でレイテンシー最小化
📋 コンプライアンス要件への対応
PCI DSS や HIPAA などの規制要件により、転送中のデータ暗号化が必須。最新の TLS バージョンとセキュリティポリシーを適用する必要がある場合。
➤ TLS 1.3 優先のセキュリティポリシーで規制準拠の暗号化通信をマネージド設定として実現

AWS Elastic Beanstalk で NLB 環境における TLS リスナーがマネージド設定として利用可能になった。NLB を使用する環境でも Elastic Beanstalk の管理体験の中で TLS 終端を簡単に構成でき、高パフォーマンスな TCP/TLS 通信が必要でありながら HTTPS によるセキュアな接続も求められるワークロードにおいて、運用の簡素化とセキュリティの両立を実現するアップデートである。
