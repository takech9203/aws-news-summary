Amazon ECS

ECS Managed Daemons
タスク間の可視性と通信をサポート

PID / IPC ネームスペース共有 (pidMode / ipcMode)
🗓️ 2026 年 6 月 10 日

📌 概要

Amazon ECS Managed Daemons が、タスク間の可視性と通信をサポートするようになりました。これにより、ECS Managed Instances 上で、アプリケーションのプロセスや共有 IPC リソースへのアクセスを必要とするトレーシング・プロファイリング・セキュリティの各エージェントを、デーモンとして展開できます。

デーモンのタスク定義に 2 つの新しい設定を追加できます。pidMode はデーモンがインスタンス上のすべてのプロセスを参照できるかを制御し、ipcMode は他のコンテナと IPC ネームスペースを共有するかを制御します。いずれかを shared にすると対応するネームスペースへのアクセスが付与され、デフォルトの none ではデーモンは分離された状態を維持します。

ECS は Managed Instance ごとに 1 つのデーモンタスクを正確に配置し、アプリケーションタスクよりも先にデーモンを起動します。プラットフォームチームはエージェントをアプリケーションとは独立して展開・アップデートでき、一貫したカバレッジを実現できます。

❌ Before（アップデート前の課題）
  • プロセス認識型・IPC 依存型エージェントを、各アプリタスク定義にサイドカーとして埋め込む必要があった
  • アプリとエージェントのライフサイクルが密結合。エージェント更新のたびにアプリの再デプロイが必要
  • プロセス / IPC リソースが分離され、ホストレベルの可視性を持つ監視・セキュリティ展開が困難
➡️
✅ After（改善）
  • pidMode: shared でデーモンがインスタンス上の全プロセスを参照可能に
  • ipcMode: shared で共有メモリ・メッセージキュー等の IPC を共有可能に
  • エージェントをデーモンとして一元展開し、アプリと独立して更新できる

pidMode / ipcMode を shared に設定したデーモンは、host を指定したアプリケーションタスクのプロセスや IPC リソースにアクセスできます。デフォルト設定のタスク (Task C) は分離されたままです。

⚙️ 主要機能

🔢 1. pidMode による PID ネームスペース共有
  • デーモンの PID ネームスペースモードを制御するタスク定義パラメータ
  • 有効値は none または shared、デフォルトは none
  • shared 指定でデーモンはホストの PID ネームスペースに参加。pidMode: "host" の非デーモンタスクや pidMode: "shared" の他デーモンからアクセス可能に
  • プロセスの監視やシグナル送信といったユースケースを実現
📨 2. ipcMode による IPC ネームスペース共有
  • デーモンの IPC ネームスペースモードを制御するタスク定義パラメータ
  • 有効値は none または shared、デフォルトは none
  • shared 指定でホストの IPC ネームスペースに参加。ipcMode: "host" の非デーモンタスクや他デーモンからアクセス可能に
  • 共有メモリセグメントやメッセージキューといった IPC リソースへのアクセスを実現
📍 3. デーモンの配置と起動順序
  • ECS は Managed Instance ごとに 1 つのデーモンタスクを正確に配置
  • アプリケーションタスクよりも先にデーモンを起動し、一貫したカバレッジを提供
  • エージェントをアプリケーションとは独立して展開・アップデートできる

🔧 技術仕様

📋 タスク定義パラメータ

項目詳細
pidModePID ネームスペースモード。型は String、任意指定。有効値は none / shared、デフォルトは none
ipcModeIPC ネームスペースモード。型は String、任意指定。有効値は none / shared、デフォルトは none
対象ECS Managed Instances 上で動作するデーモンタスク定義（専用の register-daemon-task-definition で登録）
設定手段AWS マネジメントコンソール、AWS CLI、AWS CloudFormation、AWS SDK

🔗 ネームスペース共有の対応関係

非デーモンタスクがデーモンと同じネームスペースを共有するには、タスク側で host を指定する必要があります。

pidMode: "shared" + pidMode: "host" → デーモンがタスクのプロセスを参照し、プロセス監視やシグナル送信が可能
ipcMode: "shared" + ipcMode: "host" → デーモンがタスクの共有メモリセグメントやメッセージキューにアクセス可能

🚀 設定方法

✅ 前提条件

✓ECS Managed Instances のキャパシティプロバイダーが構成されていること
✓デーモンタスク定義を登録・管理する権限を持つ IAM ロールが用意されていること
✓プロセス認識型または IPC 依存型のエージェントコンテナイメージが Amazon ECR などのレジストリに用意されていること

📝 手順

ステップ 1: デーモンタスク定義の作成

BashAWS CLI
aws ecs register-daemon-task-definition --cli-input-json file://daemon-taskdef.json

pidMode または ipcMode を shared に設定したデーモンタスク定義を、JSON ファイルをもとに登録します。

ステップ 2: アプリケーションタスク側の設定

JSONアプリタスク定義（host 指定）
{
    "family": "my-app-task",
    "pidMode": "host",
    "ipcMode": "host",
    "containerDefinitions": [
        { "name": "app", "image": "my-app:latest", "essential": true }
    ]
}

デーモンとネームスペースを共有させたいアプリタスクには pidMode / ipcMode に host を指定します。

ステップ 3: デーモンの展開

デーモンを ECS Managed Instances のキャパシティプロバイダーに関連付けて新規作成またはアップデートします。ECS が Managed Instance ごとに 1 つのデーモンタスクを配置し、アプリケーションタスクよりも先に起動します。

⚠️ デメリット・制約事項

🚧 制限事項

✗ネームスペース共有には、デーモン側 (shared) とアプリタスク側 (host) の両方で設定が必要
✗デーモンタスク定義は専用リソース。Amazon EBS、EFS、FSx for Windows File Server、Docker ボリューム、エフェメラルストレージは非サポート（バインドマウントのみ対応）
✗すべてのデーモンタスクが単一のネットワークネームスペースを共有するため、同一インスタンス上のデーモンは同じポートにバインドできない

🧭 考慮すべき点

▲PID / IPC 共有はデーモンに広範なアクセスを付与するため、最小権限の原則に沿った設計が望ましい
▲カーネルレベルのアクセスが必要な場合は privileged モードや linuxParameters.capabilities（例: SYS_PTRACE, NET_ADMIN）と組み合わせて検討

🎯 ユースケース

1. ホスト全体のセキュリティ監視

シナリオ: ランタイムセキュリティエージェントを各 Managed Instance に展開し、インスタンス上の全アプリプロセスを監視したい。

JSONsecurity-daemon
{
    "family": "security-daemon",
    "pidMode": "shared",
    "containerDefinitions": [
        { "name": "security-agent", "image": "my-security-agent:latest", "essential": true,
          "linuxParameters": { "capabilities": { "add": ["SYS_PTRACE"] } } }
    ]
}
✨ 効果: サイドカーを埋め込むことなく、インスタンス全体のプロセスを一元的に監視できる。
2. プロファイリングとトレーシング

シナリオ: パフォーマンスプロファイリングエージェントでアプリのプロセスを参照し、CPU / メモリ使用状況を継続収集したい。

JSONprofiler-daemon
{
    "family": "profiler-daemon",
    "pidMode": "shared",
    "containerDefinitions": [
        { "name": "profiler", "image": "my-profiler:latest", "essential": true }
    ]
}
✨ 効果: アプリ側は pidMode: "host" を指定するだけでプロファイリング対象となり、アプリコードの変更が不要。
3. IPC 依存型エージェントの集約

シナリオ: 共有メモリやメッセージキューでアプリと連携するオブザーバビリティエージェントを、インスタンスごとに 1 つだけ動作させたい。

JSONobservability-daemon
{
    "family": "observability-daemon",
    "ipcMode": "shared",
    "containerDefinitions": [
        { "name": "obs-agent", "image": "my-obs-agent:latest", "essential": true }
    ]
}
✨ 効果: IPC リソースを共有するエージェントをデーモンとして集約し、アプリタスクの肥大化を防げる。

📝 まとめ

今回のアップデートにより、トレーシング・プロファイリング・セキュリティといったプロセス認識型・IPC 依存型のエージェントを、サイドカーではなく ECS デーモンとして展開できるようになりました。pidMode と ipcMode を shared に設定し、アプリ側で host を指定するだけで、インスタンス全体の一貫した可視性を実現できます。

エージェントの運用を簡素化したいプラットフォームチームは、既存のサイドカー構成をデーモン方式へ移行できないか検討することをお勧めします。
