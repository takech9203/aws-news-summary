🚨 Amazon CloudWatch Omni
PagerDuty 統合

Amazon CloudWatch Omni 📅 リリース日: 2026 年 11 月 25 日

アラートから PagerDuty インシデントを自動作成し、既存のインシデント管理ワークフローに直接組み込み

📝 概要

Amazon CloudWatch Omni が PagerDuty との統合に対応しました。CloudWatch Omni は、AI エージェント、アプリケーション、インフラストラクチャを横断して監視できる、オープンスタンダードに基づいたフルマネージドの AI 搭載オブザーバビリティ体験です。

PagerDuty に送信されたアラートは、既存のオンコールスケジュールとエスカレーションポリシーに従ってルーティングされ、各アラートには重要度、影響サービス、Omni 内の関連データへのリンクが含まれます。手動での通知手順を排除し、平均復旧時間 (MTTR) の短縮に貢献します。

❌ Before: アップデート前の課題
  • アラートを PagerDuty インシデントに変換するには、手動での通知や独自の中継実装が必要だった
  • アラート発生から担当者への通知までに手動のステップが介在し、対応開始が遅れていた
  • PagerDuty のオンコールスケジュールやエスカレーションポリシーと連動させる標準的な仕組みがなかった
✅ After: アップデート後の改善
  • アラートから PagerDuty インシデントが自動的に作成されるようになった
  • 既存のオンコールスケジュールとエスカレーションポリシーをそのまま活用し、適切な担当者へ確実に通知できる
  • 重要度、影響サービス、関連データへのリンクが含まれ、対応者が診断コンテキストを即座に確認できる

CloudWatch Omni のアラートが発火すると、アクセスプロファイルによる権限チェックを経て、PagerDuty Events API v2 経由でイベントが送信され、PagerDuty 側のサービスとエスカレーションポリシーに従ってオンコール担当者に通知されます。

⚡ 主要機能

1️⃣ PagerDuty インシデントの自動作成
  • アラートが発火すると、PagerDuty Events API v2 のイベントが自動送信される
  • アラートの状態 (Critical / Warning / No data / OK) に応じて trigger または resolve イベントが送信される
  • 重要度、影響サービス、Omni 内の関連データへのリンクがイベントに含まれる
2️⃣ 既存のインシデント管理ワークフローとの連動
  • PagerDuty 側の既存のオンコールスケジュールとエスカレーションポリシーをそのまま利用できる
  • アラートの通知先として、連携済みの PagerDuty サービスを個別に選択できる
  • 連携時に追加した PagerDuty サービスのみが通知先の候補として表示される
3️⃣ インシデントの重複排除と自動解決
  • デフォルトではアラートの ARN を重複排除キーとして共有し、アラートごとに 1 件のインシデントが開かれる
  • 後続の Critical イベントはインシデントの重要度を引き上げ、OK イベントはインシデントを解決する
  • 通知ルールの追加設定で、独自の重複排除キーや class、group、component フィールドを指定できる
4️⃣ アクセスプロファイルによる通知制御
  • アラートのアクセスプロファイルにインテグレーションへの権限付与 (grant) が必要
  • 権限は通知設定の保存時と配信のたびにチェックされ、権限を取り消すと既存アラートの通知も停止する
  • 権限付与は特定の PagerDuty サービス ID に限定することも可能

🔐 アクセスプロファイルの権限付与の例

アラートの通知を許可するには、アクセスプロファイルに cloudwatch:InvokeIntegration の権限付与が必要です。以下は 2 つの PagerDuty サービスに限定した権限付与の例です。

JSON アクセスプロファイルの権限付与 
{
  "name": "pagerduty-alert-integration",
  "permission": "CUSTOM",
  "scopedActions": [
    {
      "actions": ["cloudwatch:InvokeIntegration"],
      "resources": [
        {
          "resourceType": "Integration",
          "resourceArns": ["arn:aws:cloudwatch:{{region}}:{{account-id}}:integration/{{integration-id}}"]
        }
      ],
      "contextConditions": { "serviceIds": ["{{PABC123}}", "{{PDEF456}}"] }
    }
  ]
}
⚠️contextConditions を省略すると、PagerDuty アカウント内のすべてのサービスが許可されます
⚠️1 つの scopedActions エントリで制限できるのは channelNames または serviceIds のいずれか一方のみです。Slack と PagerDuty は別々のエントリで権限付与します

🛠️ 設定方法

✅ 前提条件

✓CloudWatch Omni のスペースが作成済みであること
✓PagerDuty アカウントを保有しており、Admin またはアカウントオーナーがアプリをインストールできること
✓統合を管理するメンバーに、インテグレーションの作成・更新・削除アクションの権限付与があること

📌 設定手順

1
PagerDuty に Amazon CloudWatch Omni アプリをインストールする
[Settings] → [Integrations] の [PagerDuty] カードでサービスリージョン (US または EU) を選択し、[Install the app in PagerDuty] から PagerDuty の Admin またはアカウントオーナーとしてインストール。アカウントごとに 1 回で、スペース内の誰でも接続可能に。Admin でない場合はインストールリンクを Admin に送付。
2
PagerDuty アカウントを接続する
[PagerDuty] カードで [Enable] を選択し、PagerDuty にサインインしてアプリを承認。完了すると [Connected] と表示され、アカウント、サービスリージョン、インテグレーションの ARN を確認できる。
3
通知先となる PagerDuty サービスを追加する
[Add services] で対象サービスを選択すると、各サービスにアプリのインテグレーションが追加される。接続しただけではサービスは追加されず、この手順で追加したサービスのみが通知先に指定可能。サービスは後からいつでも追加できる。
4
アラートの通知先に PagerDuty サービスを設定する
アラートの通知先 (destinations) で PagerDuty サービスを選択。アクセスプロファイルに権限付与がないと保存が拒否されるため、[Grant permission] から権限付与を追加して再保存。新しい権限付与の有効化には数分かかる場合がある。自動解決させたい場合は、通知ルールのアラート状態に OK を含める。

💡 メリット

💼 ビジネス面

✓MTTR の短縮: 手動の通知ステップを排除し、アラート発生から担当者への通知までを自動化
✓既存投資の活用: 構築済みのオンコールスケジュールやエスカレーションポリシーをそのまま活用でき、運用プロセスの再構築が不要
✓一貫したインシデントワークフロー: すべてのアラートが同じプロセスを通るため、対応品質のばらつきを低減

⚙️ 技術面

✓豊富な診断コンテキスト: 重要度、影響サービス、関連データへのリンクが含まれ、即座に調査を開始できる
✓インテリジェントな重複排除: アラート単位の集約、重要度の自動引き上げ、OK 時の自動解決でライフサイクルを自動管理
✓最小権限の設計: PagerDuty への権限は読み取り専用スコープのみ。アラートごと・サービスごとに通知を細かく制御可能

⚠️ デメリット・制約事項

🚫 制限事項

✗1 リージョン内で 1 AWS アカウントにつき接続できる PagerDuty アカウントは 1 つのみ (別アカウントに接続するには一度無効化して再接続が必要)
✗通知先に指定できるのは、[Add services] で明示的に追加した PagerDuty サービスのみ
✗1 つの scopedActions エントリで channelNames と serviceIds の両方を制限することはできない
✗CloudWatch Omni 自体の利用可能リージョンに依存する

🤔 考慮すべき点

⚠️権限付与は配信のたびにチェックされるため、権限を取り消すと稼働中のアラート通知も停止する。インシデントが開かれない場合は、まずプロファイルを確認
⚠️統合を無効化しても、インテグレーションへの権限付与や PagerDuty サービス側のアプリインテグレーションは削除されない
⚠️インシデントの自動解決を利用するには、通知ルールのアラート状態に OK を含める必要がある
⚠️新しい権限付与が有効になるまで数分かかる場合がある

🎯 ユースケース

🌏 ユースケース 1: 24 時間 365 日のオンコール体制との連動

シナリオ: グローバル展開企業が PagerDuty のフォローザサン型オンコールスケジュールを運用しており、CloudWatch Omni で検知した重大なアラートを時間帯に応じた担当者へ自動的にエスカレーションしたい。

実装例
  1. PagerDuty に Amazon CloudWatch Omni アプリをインストール
  2. CloudWatch Omni のスペースで PagerDuty を接続し、本番サービスを追加
  3. 重要メトリクスのアラートの通知先に該当 PagerDuty サービスを設定
  4. アラート状態に Critical / Warning / OK を含め、自動解決も有効化
✨ 効果: 深夜や休日でも既存のエスカレーションポリシーに従って適切な担当者に自動で通知され、人手による連絡の遅延や漏れがなくなる。
🔕 ユースケース 2: アラートの重複によるノイズの抑制

シナリオ: 同一の障害で状態変化が繰り返されるたびにインシデントが乱立し、対応者が本質的な問題に集中できない。

実装例
  1. デフォルトの重複排除キー (アラートの ARN) を利用し、アラートごとに 1 インシデントへ集約
  2. 必要に応じて通知ルールの PagerDuty 追加設定で独自の重複排除キーを指定し、複数アラートを 1 つのインシデントにまとめる
  3. class / group / component フィールドを設定し、PagerDuty のイベントルールで分類
✨ 効果: インシデントの乱立を防ぎ、重要度の自動引き上げと OK イベントによる自動解決でインシデント管理の運用負荷を削減できる。
👥 ユースケース 3: チームごとの通知権限の分離

シナリオ: 複数チームが同じ CloudWatch Omni スペースを共有しており、各チームのアラートが自チーム担当の PagerDuty サービスのみに通知されるよう統制したい。

実装例
JSON チーム A 専用の権限付与 
{
  "name": "team-a-pagerduty",
  "permission": "CUSTOM",
  "scopedActions": [
    {
      "actions": ["cloudwatch:InvokeIntegration"],
      "resources": [
        {
          "resourceType": "Integration",
          "resourceArns": ["arn:aws:cloudwatch:ap-northeast-1:123456789012:integration/example-id"]
        }
      ],
      "contextConditions": { "serviceIds": ["PABC123"] }
    }
  ]
}
✨ 効果: 権限付与を PagerDuty サービス ID 単位で制限することで、チーム間の誤通知を防ぎ、ガバナンスを維持したままスペースを共有できる。

📌 まとめ

CloudWatch Omni と PagerDuty の統合により、アラートから担当者への通知までが完全に自動化され、既存のオンコール体制をそのまま活かしたインシデント対応が可能になりました。

PagerDuty を利用中で CloudWatch Omni を導入している、または検討しているチームは、まず PagerDuty アプリのインストールと通知先サービスの追加を行い、重要なアラートの通知先として設定することを推奨します。
