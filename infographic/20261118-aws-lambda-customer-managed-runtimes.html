⚡ カスタマーマネージドランタイム
Customer-managed Runtimes

📅 リリース日: 2026 年 11 月 18 日 | ランタイムを関数から独立したスタンドアロンリソースとして一元管理

📝 概要

AWS Lambda がカスタマーマネージドランタイムのサポートを発表。ランタイムを関数から完全に独立したスタンドアロンリソースとして作成・管理でき、プラットフォームチームがランタイムの内容、更新、アクセス制御、ライフサイクルを一元管理できます。ランタイムは OCI コンテナイメージとして Amazon ECR にパッケージ化し、既存の Docker や CI/CD ツールと組み合わせて利用できます。

ランタイム発行者が一度更新すれば、Lambda が実行環境をリサイクルするタイミングで各関数が自動的に更新を取り込むため、関数ごとの再デプロイや大規模なロールアウト調整が不要になります。

💡 本機能は Lambda Event Functions を対象とし、プラットフォームチーム、SaaS/PaaS プロバイダー、サードパーティのランタイム発行者、変更管理ポリシーに基づくランタイムパッチ管理が必要な組織に適しています。なお、従来の「カスタムランタイム」(デプロイパッケージやレイヤーにランタイムを含める方式) は「bring your own language (BYOL)」に名称変更されました。
❌ Before: アップデート前の課題
🔴共有コンポーネント (SDK、証明書、監視ツールなど) を Layers やコンテナイメージで配布すると、変更のたびに全関数の再デプロイが必要
🔴コンテナイメージ利用時は、ランタイムのセキュリティパッチ適用にもイメージの再ビルドと再デプロイが必要
🔴マネージドランタイムは AWS が内容・更新時期・非推奨化を管理するため、組織の変更管理ポリシーに合わせた制御が不可
🔴Lambda 未サポート言語 (PHP など) では、関数開発者自身がランタイムの管理責任を負う必要があった
✅ After: アップデート後の改善
🟢ランタイムをスタンドアロンリソースとして一元管理し、ランタイム管理と関数デプロイを完全に分離
🟢発行者が更新を一度公開すれば、関数は再デプロイなしで次回コールドスタート時に自動的に新バージョンへ移行
🟢リソースベースポリシーで特定アカウント、AWS Organizations の組織/OU、パブリックに共有可能
🟢段階的ロールアウト、一元的なヘルスメトリクス監視、迅速なロールバックが可能
🟢関数開発者は従来どおり .zip デプロイで、マネージドランタイムと同じ開発体験を維持

ランタイム発行者が ECR 上のコンテナイメージからランタイムバージョンを作成し、エイリアスを更新すると、エイリアスを参照する関数は次回コールドスタート時に自動的に新しいランタイムバージョンへ移行します。

🔧 主要機能

1️⃣ ランタイム管理と関数管理の分離
  • ランタイムを関数から独立したスタンドアロンリソースとして作成・管理
  • 「ランタイム発行者」と「ランタイム利用者」の 2 つの役割を明確に分離 (同一チームが両方を担うことも、アカウントをまたぐことも可能)
  • 発行者はランタイムの内容・更新・アクセス制御・ライフサイクルを管理し、利用者はアプリケーション開発に専念
2️⃣ 3 階層のリソースモデル
📘 Runtime

ランタイム全体を表す最上位リソース。名前、ARN、説明、ライセンス情報を保持し、リソースベースポリシーでアクセスを制御

→
🔒 Runtime Version

ランタイムの内容 (実行環境のファイルシステム) を表すイミュータブルなリソース。Amazon ECR 上のコンテナイメージを指す

←
🏷️ Runtime Alias

ランタイムバージョンへの名前付きポインタ。関数はエイリアス経由でランタイムを利用する

3️⃣ 自動的な更新ロールアウト
  • 発行者がエイリアスを新バージョンに向けると、デフォルトで関数は次回コールドスタート時に自動移行
  • 環境ごとの段階的ロールアウト、ヘルスメトリクスの監視、ロールバックが可能
  • 利用者は Function update モードや Manual モードで更新タイミングを制御可能 (既存のランタイム管理コントロールを利用)
4️⃣ クロスアカウント共有
  • リソースベースポリシーで特定の AWS アカウント、AWS Organizations の組織または OU、あるいはパブリックに共有可能
  • 組織全体で承認済みコンポーネントを標準化できる
5️⃣ 既存ツールとの互換性
  • ランタイムイメージは OCI コンテナイメージとして ECR に格納し、既存の Docker / CI/CD ツールで構築可能
  • Lambda ランタイムベースイメージから構築することも、スクラッチから構築することも可能
  • AWS CLI、AWS SDK、CloudFormation、AWS CDK で管理可能

ランタイム名2〜128 文字。小文字、数字、_、.、- のみ。作成後の変更不可
イメージ形式OCI コンテナイメージ (Amazon ECR に格納)

リージョン性リージョナルリソース。利用するリージョンごとに作成が必要

🛠️ 設定方法

✅ 前提条件

  • ランタイムイメージを格納する Amazon ECR リポジトリ
  • ランタイム、ランタイムバージョン、ランタイムエイリアスを管理する IAM 権限
  • ランタイムインターフェースクライアント (RIC) を含むランタイムイメージ (Lambda ベースイメージまたはスクラッチから構築)
1
ランタイムイメージをビルドして ECR にプッシュ
Bashイメージのビルドとプッシュ
docker build -t companyphp8:v1 .
docker tag companyphp8:v1 123456789012.dkr.ecr.us-east-1.amazonaws.com/companyphp8:v1
docker push 123456789012.dkr.ecr.us-east-1.amazonaws.com/companyphp8:v1

Lambda ランタイムベースイメージまたはスクラッチからランタイムイメージをビルドし、Amazon ECR リポジトリにプッシュします。イメージには RIC を含める必要があります。

2
ランタイムを作成
BashLambda Core API でランタイムを作成
aws lambda-core create-runtime \
  --name companyphp8 \
  --description "PHP 8 runtime with company-approved extensions" \
  --license-info "PHP License v3.01." \
  --tags Team=platform,Project=runtimes

Lambda Core API でランタイム (最上位リソース) を作成します。名前、説明、ライセンス情報、タグを指定でき、出力に含まれる ARN をアクセス制御や関数設定で使用します。

3
ランタイムバージョンとエイリアスを作成
Bashランタイムの確認と一覧表示
# ランタイムの確認
aws lambda-core get-runtime --runtime-name companyphp8

# アカウント内のランタイム一覧
aws lambda-core list-runtimes

ECR 上のイメージからランタイムバージョンを作成し、そのバージョンを指すランタイムエイリアス (例: prod) を作成します。ランタイムは作成直後にはバージョンもエイリアスも持たないため、関数から利用するにはこのステップが必須です。

4
関数でランタイムエイリアスを参照

関数の設定で、python3.14 のような Lambda マネージドランタイム識別子の代わりにカスタマーマネージドランタイムのエイリアスを指定します。関数コードは従来どおり .zip ファイルでデプロイします。クロスアカウントで共有する場合は、ランタイムにリソースベースポリシーを設定します。

👍 メリット

💼 ビジネス面
✓ガバナンスの強化: プラットフォームチームが組織全体のランタイム内容と更新を一元管理し、承認済みコンポーネントを標準化
✓コンプライアンス対応: 変更管理ポリシーに合わせた更新スケジューリングや段階的ロールアウトが可能。公開 EOL スケジュールを超えたランタイムの延長利用も可能
✓運用コスト削減: 共有コンポーネント更新時の関数ごとの再デプロイ作業や大規模なロールアウト調整が不要に
🔧 技術面
✓再デプロイ不要の更新: エイリアス更新だけで、関数は次回コールドスタート時に自動的に新バージョンを取り込み
✓開発体験の維持: .zip デプロイと自動ランタイム更新というマネージドランタイムと同じ体験を維持
✓既存ツールとの互換性: OCI コンテナイメージベースのため、Docker、CI/CD、CloudFormation、CDK がそのまま利用可能
✓任意の言語のサポート: PHP などマネージドランタイム未提供の言語でも、組織やサードパーティがランタイムを公開可能

⚠️ デメリット・制約事項

🚫 制限事項

✗Lambda Event Functions 専用。Lambda Web Functions では利用不可
✗Lambda SnapStart および Lambda@Edge は利用不可
✗ランタイムリソースを AWS KMS カスタマーマネージドキーで暗号化できない (関数側の KMS キーやコード署名のサポートには影響なし)
✗ランタイムイメージにコード署名を使用できない
✗AWS SAM ではランタイムの公開・更新ができない (関数定義では利用可能)
✗ランタイムはリージョナルリソースのため、利用するリージョンごとに作成が必要

🤔 考慮すべき点

⚠️発行者への信頼が必須: 発行者はランタイム更新を通じて関数の実行環境に任意のコードをプッシュでき、そのコードは関数の実行ロールの権限で動作。信頼できる発行者のランタイムのみ利用すること。サードパーティ製ランタイムや重要なアプリケーションでは、イメージを自アカウントの ECR にコピーして独自ランタイムを作成する方法も検討
⚠️パッチ適用責任の移転: OS ライブラリや言語ランタイムを含むすべてのコンポーネントのセキュリティパッチは発行者の責任
⚠️後方互換性の維持: 発行者は既存の関数と後方互換性のある更新を維持する責任がある
⚠️削除時の影響: 発行者がエイリアスやバージョンを削除すると、依存する関数は Inactive 状態になり、コールドスタートが必要な呼び出しは失敗
⚠️イメージの保持: ランタイムバージョンが存在する間、発行者は対応するコンテナイメージを ECR に保持し続ける必要がある
⚠️一部の機能 (Lambda Managed Instances、レスポンスストリーミングなど) はランタイム側の実装が必要なため、発行者のドキュメントで対応状況を確認

🎯 ユースケース

🏢 ユースケース 1: エンタープライズプラットフォームチームによる標準ランタイムの配布

シナリオ: 大企業のプラットフォームチームが、セキュリティエージェント、監視ツール、社内 SDK を組み込んだ標準ランタイムを全社のアプリケーションチームに提供する。

実装例:

Text実装フロー
1. 承認済みコンポーネントを含むランタイムイメージをビルドし ECR にプッシュ
2. ランタイムを作成し、AWS Organizations の組織単位でリソースベースポリシーを設定
3. 各アプリケーションチームは関数設定でランタイムエイリアスを参照
4. ツール更新時はプラットフォームチームが新バージョンを作成しエイリアスを更新
✅ 効果: 数百〜数千の関数に対して、再デプロイなしで一斉にセキュリティツールを更新できる。
🐘 ユースケース 2: Lambda 未対応言語のランタイム提供

シナリオ: 組織またはサードパーティが、Lambda のマネージドランタイムが提供されていない PHP 8 のランタイムを公開し、複数チームが利用する。

実装例:

BashPHP 8 ランタイムの作成
aws lambda-core create-runtime \
  --name companyphp8 \
  --description "PHP 8 runtime with company-approved extensions"
# バージョンとエイリアスを作成後、各関数はエイリアスを参照して .zip でデプロイ
✅ 効果: 従来の BYOL (旧カスタムランタイム) と異なり、PHP ランタイムの更新を一元管理でき、各関数の再デプロイが不要になる。
🏦 ユースケース 3: 変更管理ポリシーに基づくランタイムパッチ制御

シナリオ: 金融機関などの規制業種で、ランタイム更新を組織の変更管理プロセスに沿ってステージング環境から本番環境へ段階的に適用する。

実装例:

Text段階的ロールアウト
1. ステージング用エイリアス staging を新バージョンへ更新し検証
2. ヘルスメトリクスを監視して問題がないことを確認
3. 本番用エイリアス prod を更新し、問題発生時はエイリアスを旧バージョンへ戻す
✅ 効果: 環境ごとのエイリアス運用により、コンプライアンス要件を満たす制御されたロールアウトと迅速なロールバックを実現できる。

💰 料金

カスタマーマネージドランタイム自体に追加料金はありません。

✓カスタマーマネージドランタイムを使用する関数の料金は、Lambda マネージドランタイムを使用する関数と同じ標準 Lambda 料金
✓ランタイムバージョンごとの料金は発生しない
⚠️発行者はランタイムバージョンが存在する間、対応するコンテナイメージを Amazon ECR に保持する必要があり、標準の Amazon ECR ストレージ料金が適用される

従来の実行環境カスタマイズ手法。カスタマーマネージドランタイムはこれらの課題 (関数ごとの再デプロイ) を解消する位置付け

💡 まとめ

カスタマーマネージドランタイムは、ランタイム管理を関数デプロイから完全に分離し、プラットフォームチームによる一元的なランタイムガバナンスを実現する重要なアップデートです。Lambda Layers やコンテナイメージで共有コンポーネントを配布している組織は、関数ごとの再デプロイが不要になる本機能への移行を検討する価値があります。

🚀 推奨アクション: まずは開発環境でランタイムの作成からエイリアス経由の関数設定までのワークフローを検証し、組織の変更管理プロセスに合わせたロールアウト戦略を設計することを推奨します。
