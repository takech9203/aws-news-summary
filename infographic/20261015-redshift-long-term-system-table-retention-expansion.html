🗄️ システムテーブル長期保存
S3 Tables ネイティブ統合の対応リージョン拡大

📅 リリース日: 2026 年 10 月 15 日 | GovCloud (US) を含む 4 リージョンが新たに対応

📌 概要

Amazon Redshift のシステムテーブルデータを Amazon S3 Tables とのネイティブ統合により長期保存する機能が、 アジアパシフィック (ニュージーランド)、カナダ西部 (カルガリー)、AWS GovCloud (US-East / US-West) の 4 リージョンに拡大されました。

有効化すると、AWS がシステムテーブルデータを Apache Iceberg 形式で S3 Tables に自動書き込みし、パーティショニング、コンパクション、保持期間の管理まで実施。 従来 7 日間に制限されていた保持期間を、コンプライアンス・監査・オブザーバビリティの要件に合わせて自由に延長できます。 特に GovCloud 対応は、厳格なコンプライアンス要件を持つ政府機関や規制業界にとって重要です。

❌ Before: アップデート前の課題
  • システムテーブルはウェアハウス内で 7 日間しか保持されず、長期の監査・コンプライアンス要件を満たせない

  • エクスポート処理が本番ワークロードとリソース競合する可能性

✅ After: アップデート後の改善
  • NZ、カルガリー、GovCloud (US-East / US-West) でも利用可能に
  • 7 日の制限を超えて要件に応じた期間 (無期限も可) で保持可能
  • 書き込み・パーティショニング・コンパクションを AWS が自動管理し、カスタム ETL が不要
  • 複数ウェアハウスのデータを単一の場所に集約しフリート全体を横断分析
  • AWS Agent Toolkit で自然言語によるインサイト取得が可能

Redshift が完了済みのシステムテーブルレコードをバッチで S3 Tables に自動配信し、AWS Glue Data Catalog との統合を経て、Redshift、Athena、DuckDB などの Iceberg 互換エンジンから長期保存データをクエリできます。

⚡ 主要機能

⏳ 7 日間を超えるシステムテーブルデータの保持
SYS_* ビューはウェアハウス内では 7 日間のみ保持。本機能を有効化すると完了済みレコードが S3 Tables に Apache Iceberg 形式で自動配信されます。保持期間は S3 Tables のレコード有効期限ポリシーで設定し、未設定の場合は無期限に保持されます。
🤖 サービスマネージドなデータ配信とテーブル管理
S3 テーブルバケット (aws-redshift)、名前空間、テーブルの作成からスキーマ進化、コンパクション、スナップショット管理まで AWS が自動実行。配信は本番ワークロードと分離され、各レコードは Exactly-once で配信されるため再有効化しても重複しません。
🧩 2 つのデプロイメントモデル
  • ウェアハウス個別: ウェアハウスごとに専用の S3 テーブルセットへ書き込み、物理的に分離
  • 統合 (consolidated): 同一アカウント・リージョン内の複数ウェアハウスを共有テーブルに集約し、warehouse_namespace_arn や warehouse_name 列で区別。フリート全体の横断分析が可能
🔓 オープンフォーマットによるマルチエンジンクエリ
Apache Iceberg 形式のため Redshift、Amazon Athena、DuckDB など任意の互換エンジンでクエリ可能。Glue Data Catalog 統合により IAM / Lake Formation で細かなアクセス制御ができ、AWS Agent Toolkit のスキルで自然言語によるパフォーマンスインサイト取得にも対応します。
🌏 追加リージョンへの拡大
アジアパシフィック (ニュージーランド)、カナダ西部 (カルガリー)、AWS GovCloud (US-East)、AWS GovCloud (US-West) で新たに利用可能に。GovCloud 対応により政府機関や規制業界の厳格な監査要件にも対応しやすくなりました。

追加されるメタデータ列

各 S3 テーブルには、元の SYS_* ビューの全列に加えて以下のメタデータ列が追加されます。

列名型説明
warehouse_account_idstringソースデータウェアハウスを所有する AWS アカウント
warehouse_region_namestringソースデータウェアハウスのリージョン
warehouse_namespace_arnstring名前空間の ARN (リネームや再作成でも不変の一意識別子)
warehouse_namestringクラスター名またはワークグループ名
s3_tables_ingestion_timetimestampRedshift が行を S3 Tables にコミットした時刻 (UTC)

有効化に必要な権限

JSON IAM ポリシー (有効化を実行するプリンシパル) 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": [
        "redshift:EnableLogging",
        "s3tables:CreateTableBucket",
        "s3tables:PutTableBucketEncryption",
        "s3tables:PutTableBucketPolicy"
      ],
      "Resource": "*"
    }
  ]
}

Redshift Serverless の場合は redshift:EnableLogging の代わりに redshift-serverless:UpdateNamespace が必要です。 バケット作成後の名前空間とテーブルの作成は、Redshift と S3 Tables 間のサービス信頼関係により行われます。

ステップ 1: 有効化 (Provisioned クラスター)

Bash ログ出力先タイプ s3table を指定して有効化 
aws redshift enable-logging \
    --cluster-identifier my-redshift-cluster \
    --log-destination-type s3table \
    --log-exports all \
    --s3-table-granularity account

--log-exports には all または SYS_* ビュー名のリストを指定し、 --s3-table-granularity で cluster (個別) または account (統合) を選択します。 実行するとアカウント内に aws-redshift という S3 テーブルバケットが作成され、配信が開始されます。

ステップ 2: 有効化 (Redshift Serverless)

Bash 名前空間単位で設定 
aws redshift-serverless update-namespace \
    --namespace-name my-namespace \
    --log-destination-type s3table \
    --s3-table-action Enable \
    --s3-table-names all \
    --s3-table-granularity namespace

ステップ 3: 配信ステータスの確認

Bash 有効化されたテーブル、名前空間、最終取り込み時刻を確認 
# Provisioned クラスターの場合
aws redshift describe-logging-status \
    --cluster-identifier my-redshift-cluster

# Serverless の場合
aws redshift-serverless get-namespace \
    --namespace-name my-namespace

ステップ 4: Glue Data Catalog 統合と保持期間の設定

S3 テーブルバケットを AWS Glue Data Catalog と統合すると、Redshift では外部スキーマの作成 (CREATE EXTERNAL SCHEMA ... FROM DATA CATALOG)、Athena ではそのままの SQL でクエリできるようになります。保持期間は S3 Tables のレコード有効期限ポリシーをテーブル単位で設定します (例: 365 日)。

💡 メリット

💼 ビジネス面

✓コンプライアンス・監査要件への対応: クエリ履歴、接続ログ、変更履歴を数か月から数年単位で保持可能。GovCloud 対応により政府機関や規制業界でも利用可能
✓運用コストの削減: カスタム ETL パイプラインの構築・保守が不要になり、エンジニアリングリソースを本来の業務に集中
✓ログ配信は追加料金なし: 配信自体は無料。課金は S3 Tables のストレージとメンテナンス、クエリエンジンの利用分のみ

⚙️ 技術面

✓本番ワークロードへの影響なし: 配信はバックグラウンドで実行され、リソース競合が発生しない。Serverless ではワークグループを起動状態に保つこともない
✓オープンフォーマットの柔軟性: Redshift、Athena、DuckDB、Spark など任意の Iceberg 互換エンジンで分析でき、ベンダーロックインがない
✓フリート全体の一元的オブザーバビリティ: 統合モデルにより複数ウェアハウスを単一テーブルで横断分析
✓監査証跡の完全性: 配信済みデータはイミュータブルで、管理者でも改変・削除ができず、監査証跡として信頼性が高い

⚠️ デメリット・制約事項

🚫 制限事項

✗単一アカウント・単一リージョン内でのみ動作。クロスリージョン・クロスアカウント分析はクエリ時の結合または Glue Data Catalog のクロスアカウント共有で対応
✗1 つのウェアハウスで同時に使用できるデプロイメントパターンは 1 つのみ
✗パターン切り替え、再有効化、テーブル再追加では過去データのバックフィルは行われない
✗配信済みデータはイミュータブルで、個別行の変更・削除は不可
✗S3 テーブルを削除すると保存データは完全に失われ、再有効化しても復元されない
✗配信は固定頻度のバッチベースでリアルタイムではない。進行中のクエリなど未完了のアクティビティは配信されない
✗暗号化キーはテーブル作成後に変更不可。変更には統合の無効化とテーブル削除 (データ完全削除) が必要

🤔 考慮すべき点

⚠SYS_QUERY_TEXT などはクエリ内のリテラル値 (機密情報を含む可能性) を保持するため、機密性を評価して対象テーブルとモデルを選択
⚠保持期間を設定しないと無期限に保持されるため、要件を満たす最小限の保持期間を設定してストレージコストを管理
⚠大量の履歴データをクエリする際は warehouse_name や s3_tables_ingestion_time などのメタデータ列でフィルタリングしてスキャン量を削減
⚠KMS カスタマーマネージドキー使用時は、systemtables.redshift.amazonaws.com と maintenance.s3tables.amazonaws.com のサービスプリンシパルにキー使用を許可するキーポリシーが必要

🎯 ユースケース

1️⃣ GovCloud 環境での長期監査証跡の保持

シナリオ: AWS GovCloud (US) で Redshift を運用する政府機関が、規制要件により全クエリと接続の履歴を 1 年以上保持する必要がある。

Bash 監査対象ビューを個別粒度で有効化 
aws redshift enable-logging \
    --cluster-identifier gov-dwh-cluster \
    --log-destination-type s3table \
    --log-exports sys_query_history sys_query_text sys_connection_log sys_userlog \
    --s3-table-granularity cluster

S3 Tables 側でレコード有効期限を 400 日に設定する。

効果: カスタム ETL なしで監査証跡を自動保存。データはイミュータブルなため、監査人に対して改変されていない証跡として提示できる。

2️⃣ 複数ウェアハウスの横断的なパフォーマンス分析

シナリオ: 同一アカウント・リージョン内で複数の Serverless ワークグループと Provisioned クラスターを運用し、フリート全体のクエリパフォーマンスのトレンドを一元的に分析したい。

SQL 統合モデル (account 粒度) で有効化後、Athena から横断クエリ 
SELECT warehouse_name,
       DATE_TRUNC('week', start_time) AS week,
       AVG(elapsed_time) / 1000000.0 AS avg_elapsed_sec,
       COUNT(*) AS query_count
FROM "aws-redshift"."sys_query_history"
WHERE start_time > CURRENT_DATE - INTERVAL '90' DAY
GROUP BY 1, 2
ORDER BY 1, 2;

効果: 7 日を超える期間のトレンドをウェアハウス横断で可視化でき、キャパシティプランニングやワークロード変更前後の影響比較に活用できる。

3️⃣ 過去インシデントの根本原因分析

シナリオ: 3 週間前に発生したパフォーマンス劣化の根本原因を分析したいが、クラスター内のシステムテーブルには直近 7 日分しか残っていない。

SQL Redshift から外部スキーマ経由で過去のクエリ詳細を分析 
CREATE EXTERNAL SCHEMA sys_history
FROM DATA CATALOG DATABASE 'aws_redshift_namespace'
IAM_ROLE 'arn:aws:iam::123456789012:role/RedshiftS3TablesRole';

SELECT query_id, start_time, elapsed_time, queue_time, status
FROM sys_history.sys_query_history
WHERE start_time BETWEEN '2026-09-20' AND '2026-09-27'
ORDER BY elapsed_time DESC
LIMIT 50;

効果: 保存期間の制限なく過去のインシデントを調査でき、ポストモーテムや再発防止策の立案に必要なデータを確保できる。

💰 料金

Redshift から S3 Tables へのシステムテーブルデータの書き込み (ログ配信) 自体は無料です。課金対象は以下のとおりです。

✓保存データに対する S3 Tables の標準的なストレージ料金とメンテナンス料金
✓データの読み取りに使用するクエリエンジン (Redshift、Athena など) の料金

詳細は Amazon S3 の料金ページ を参照してください。保持期間をコンプライアンス要件を満たす最小限に設定することで、ストレージコストを最適化できます。

Amazon Redshift のシステムテーブルを S3 Tables に長期保存する機能が、アジアパシフィック (ニュージーランド)、カナダ西部 (カルガリー)、AWS GovCloud (US-East / US-West) に拡大されました。 7 日間の保持制限をカスタム ETL なしで克服でき、特に GovCloud 対応により厳格な監査・コンプライアンス要件を持つ組織でも利用しやすくなりました。 該当リージョンで Redshift を運用し、監査証跡の長期保持や横断的なオブザーバビリティが必要な場合は、本機能の有効化を検討することを推奨します。
