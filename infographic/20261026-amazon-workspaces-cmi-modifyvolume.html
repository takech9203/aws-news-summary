Amazon WorkSpaces Core

🖥️ Managed Instances が ModifyVolume API をサポート

📅 2026 年 10 月 26 日リリース ｜ 稼働中のままボリューム構成をインプレース変更

📋 概要

Amazon WorkSpaces Core Managed Instances が ModifyVolume API をサポートしました。 ボリュームのデタッチやインスタンスの再起動を行うことなく、マネージドインスタンスにアタッチされたボリュームの サイズ・ボリュームタイプ・IOPS・スループット をインプレース (稼働中のまま) で変更できます。

これまではストレージ構成の変更にインスタンスの再構築が必要でしたが、今回のアップデートにより、ユーザーのデスクトップ環境を停止せずにストレージ要件の変化へ柔軟に対応できます。WorkSpaces Core Managed Instances を利用する VDI 管理者や、パートナーソリューションを構築するパートナーに有用です。

❌ Before: 再構築が必要
  • ストレージ容量・性能の変更にはインスタンスの再構築が必要
  • 再構築に伴い、ユーザーのデスクトップ環境にダウンタイムが発生し、運用負荷が高い
  • データ増加やワークロードの高負荷化に迅速に追従できない
✅ After: インプレース変更
  • デタッチ・再起動なしでボリューム構成をオンライン変更
  • 最大 16,384 GiB まで拡張、タイプ変更、gp3/io1/io2 の IOPS 調整、gp3 のスループット変更が可能
  • ClientToken による冪等性、EC2 の DescribeVolumesModifications で進捗追跡

従来はストレージ変更にインスタンスの再構築が必要でしたが、今回のアップデートにより ModifyVolume API を呼び出すだけで、稼働中のインスタンスにアタッチされたボリュームをオンラインで変更し、EC2 の DescribeVolumesModifications で進捗を追跡できます。

⚡ 主要機能

📏 ボリュームサイズのインプレース拡張
  • デタッチ・再起動なしで最大 16,384 GiB まで拡張可能
  • サイズは拡張のみ可能で、縮小はできない (現在のサイズ以上を指定)
🔄 ボリュームタイプの変更
  • サポートされる EBS ボリュームタイプ間での切り替えが可能
  • 指定可能な値は standard | io1 | io2 | gp2 | sc1 | st1 | gp3
  • 一部の組み合わせは非サポートのため EBS ユーザーガイドの制限事項を確認
🚀 IOPS / スループットの調整
  • gp3、io1、io2 ボリュームの IOPS を調整可能
  • gp3 ボリュームのスループット (MiB/s) を変更可能
  • 指定しなかったパラメータは現在の値が維持される
🔁 冪等性と進捗追跡
  • ClientToken による冪等性サポートで重複したボリューム変更を防止
  • 進捗は Amazon EC2 の DescribeVolumesModifications 操作で直接追跡可能

🔧 技術仕様

📥 ModifyVolume API リクエストパラメータ

パラメータ型必須説明
VolumeIdStringはい変更対象のボリューム ID (パターン: vol-[0-9a-zA-Z]{1,63})
SizeInGBIntegerいいえ目標サイズ (GiB)。1〜16,384。現在のサイズ以上を指定
VolumeTypeStringいいえ目標 EBS ボリュームタイプ (standard/io1/io2/gp2/sc1/st1/gp3)
IopsIntegerいいえ目標 IOPS。gp3/io1/io2 のみ有効
ThroughputIntegerいいえ目標スループット (MiB/s)。gp3 のみ有効
ClientTokenStringいいえ冪等性トークン (1〜64 文字)

少なくとも 1 つの変更パラメータ (SizeInGB、VolumeType、Iops、Throughput のいずれか) の指定が必要です。同一ボリュームに対する前回の変更が完了するまで、次の変更は実行できません。

⚠️ 主なエラー

エラーHTTP説明
ValidationException400入力パラメータが不正
ConflictException409リソースの現在の状態と競合
VolumeModificationRateExceededException429前回の変更が進行中、または 24 時間以内の変更回数上限 (4 回) に到達
ResourceNotFoundException404対象リソースが見つからない
ThrottlingException429リクエストレート超過

🛠️ 設定方法

✅ 前提条件

✓Amazon WorkSpaces Core Managed Instances が利用可能であること
✓変更対象のボリューム ID (vol-xxxx) を把握していること
✓workspaces-instances:ModifyVolume を実行できる IAM 権限があること
1
ボリュームの変更を実行
Bash ModifyVolume API の呼び出し 
aws workspaces-instances modify-volume \
  --volume-id vol-0123456789abcdef0 \
  --size-in-gb 500 \
  --volume-type gp3 \
  --iops 6000 \
  --throughput 500 \
  --client-token my-idempotency-token-001

サイズを 500 GiB、タイプを gp3、IOPS を 6,000、スループットを 500 MiB/s に変更。--client-token により同じリクエストの重複実行を防止します。

2
変更の進捗を確認
Bash EC2 API で進捗追跡 
aws ec2 describe-volumes-modifications \
  --volume-ids vol-0123456789abcdef0

進捗 (modifying、optimizing、completed など) を確認します。

3
ファイルシステムの拡張

サイズ拡張後は OS 側でパーティションとファイルシステムの拡張が必要です。Linux では growpart と resize2fs/xfs_growfs、Windows ではディスクの管理または diskpart を使用します。詳細は Amazon EBS ユーザーガイド を参照してください。

💡 メリット

💼 ビジネス面

✓ダウンタイムの削減: 再構築が不要になり、デスクトップ環境を停止せずにストレージを変更。業務影響を最小化
✓運用コストの削減: イメージ管理、再デプロイ、ユーザー調整などの作業が不要に
✓コスト最適化: 必要なタイミングで必要な分だけ容量・性能を引き上げる運用が可能

⚙️ 技術面

✓インプレース変更: デタッチ・再起動が不要で、稼働中のまま構成変更が完了
✓冪等性の確保: ClientToken でリトライ時の重複変更を防止
✓既存運用フローとの親和性: 進捗追跡は既存の EC2 API をそのまま利用でき、EBS Elastic Volumes と同様の運用モデル

🚧 デメリット・制約事項

⛔ 制限事項

✗ボリュームサイズは拡張のみ可能で、縮小はできない
✗変更は変更先ボリュームタイプの上限内である必要があり、一部のタイプ間変更は非サポート (EBS の制限事項)
✗前回の変更完了まで次の変更は不可。ローリング 24 時間あたり 4 回の変更回数上限
✗IOPS 指定は gp3/io1/io2 のみ、スループット指定は gp3 のみ有効

🤔 考慮すべき点

⚠サイズ拡張後は OS 側でパーティションとファイルシステムの拡張作業が別途必要
⚠変更後は EBS 料金が新しい構成に基づいて課金されるため、コスト影響の事前見積もりが必要
⚠パートナーソリューション経由で利用する場合は、パートナー側の対応状況を確認

🎯 ユースケース

📈 ユースケース 1: ユーザーデータ増加に伴うディスク容量の拡張

シナリオ: 開発者向け仮想デスクトップでリポジトリやビルド成果物が増加し、ディスク空き容量が逼迫。業務時間中のダウンタイムは許容できない。

Bash容量を 1,000 GiB に拡張
aws workspaces-instances modify-volume \
  --volume-id vol-0123456789abcdef0 \
  --size-in-gb 1000

効果: ユーザーが作業を継続したまま容量を 1,000 GiB に拡張でき、再構築やデータ移行が不要になる。

💰 ユースケース 2: gp2 から gp3 への移行によるコスト最適化

シナリオ: 既存のマネージドインスタンスが gp2 ボリュームを使用しており、gp3 への移行でコスト効率とベースライン性能の改善を図りたい。

Bashgp3 へのオンライン移行
aws workspaces-instances modify-volume \
  --volume-id vol-0123456789abcdef0 \
  --volume-type gp3 \
  --iops 3000 \
  --throughput 250

効果: 稼働中のまま gp3 へ移行し、IOPS とスループットを独立して設定できるため、性能要件に合わせたコスト最適化が実現できる。

🚀 ユースケース 3: 高負荷ワークロード向けの一時的な性能引き上げ

シナリオ: CAD や動画編集など I/O 集約型のワークロードを扱う期間だけ、特定ユーザーのデスクトップのストレージ性能を引き上げたい。

Bash繁忙期の IOPS / スループット引き上げ
# 繁忙期: IOPS とスループットを引き上げ
aws workspaces-instances modify-volume \
  --volume-id vol-0123456789abcdef0 \
  --iops 10000 \
  --throughput 700 \
  --client-token peak-season-2026

効果: 再構築なしで必要な期間だけ性能を引き上げられる。冪等性トークンにより、自動化スクリプトのリトライ時にも重複変更を防げる。

💲 料金・利用可能リージョン

💳 料金

ModifyVolume API の呼び出し自体に追加料金は発生しません。変更後のボリューム構成 (サイズ、タイプ、IOPS、スループット) に応じて、Amazon EBS および WorkSpaces Core Managed Instances の料金が適用されます。容量や性能を引き上げた場合は、その分のストレージ料金が増加する点に注意してください。

詳細: WorkSpaces Core 料金 ／ EBS 料金

🌍 利用可能リージョン

Amazon WorkSpaces Core Managed Instances が利用可能なすべての AWS リージョンで利用できます。

💾 Amazon EBS Elastic Volumes

本機能の基盤となる EBS のオンラインボリューム変更機能。変更可能な組み合わせや制限事項は EBS 側の仕様に準拠する。

🔍 Amazon EC2 DescribeVolumesModifications

ボリューム変更の進捗追跡に使用する EC2 API。

🤝 Amazon WorkSpaces Core パートナーソリューション

Citrix、Omnissa、Workspot などのパートナー VDI 管理ソリューション。パートナー経由でも本機能を利用可能 (提供開始後)。

📝 まとめ

Amazon WorkSpaces Core Managed Instances の ModifyVolume API サポートにより、これまで再構築が必要だったストレージ構成の変更を、ダウンタイムなしのインプレース操作で実行できるようになりました。VDI 環境のストレージ運用を大幅に簡素化できるアップデートであり、WorkSpaces Core Managed Instances を利用中の場合は、既存の再構築ベースの運用手順を本 API を活用したフローへ見直すことを推奨します。
