🧊 Apache Iceberg テーブル向け
マルチステートメントトランザクション・競合解決・タイムトラベル

リリース日: 2026 年 11 月 16 日 | データウェアハウス同等のトランザクションセマンティクスをレイクハウスへ

📌 概要

Amazon Redshift が Apache Iceberg テーブルに対する 3 つの新機能をサポートしました。これにより、データウェアハウスと同等のトランザクションセマンティクスを備えた本番規模の書き込みワークロードを Iceberg テーブル上で実行できます。

🔄 マルチステートメント
トランザクション
BEGIN ... COMMIT
⚖️ 自動競合解決
同時書き込みを自動リベース
⏰ タイムトラベル
AS OF TIMESTAMP

対象ユーザー: バッチジョブの開発者、ストリーミングと定期ジョブを同一テーブルに書き込むデータエンジニア、過去のテーブル状態を参照したいアナリスト・監査担当者、AI エージェントなど、Iceberg ベースのレイクハウスを運用する幅広いユーザー。

❌ Before (アップデート前)
  • 複数の書き込みが個別コミットされ、途中失敗で中途半端な状態がテーブルに残り、外部からも見えてしまった
  • Iceberg の OCC がテーブルバージョン単位で競合検出するため、異なるパーティションへの書き込みでも後発コミットが失敗 (例: 1 時間の削除ジョブが、ストリーミング挿入 1 件で失敗)
  • 過去時点の参照にはテーブルのコピー保持などの運用上の工夫が必要
✅ After (アップデート後)
  • BEGIN ... COMMIT 内の複数ステートメントが単一の Iceberg スナップショットとしてアトミックに公開、失敗時はクリーンにロールバック
  • データレベルで重複しない同時書き込みは自動リベースしてコミット。アプリケーション側のリトライが不要に
  • AS OF TIMESTAMP で追加コピーなしにレポート再現・変更監査・誤書き込みからの復旧が可能

⚡ 主要機能

1️⃣ マルチステートメントトランザクション
  • 複数の DML を BEGIN ... COMMIT にまとめ、単一のアトミックな Iceberg スナップショットとして公開 (新しい構文は不要)
  • 各ステートメントは直前の未コミットメタデータの上に構築され、1 つの保留中スナップショットとして蓄積
  • 外部からは「バッチ適用前」か「適用後」のみが見え、中間状態は決して見えない
  • 失敗または ROLLBACK 時は何も公開されず、テーブルは変更されない
  • トランザクション内で自身の未コミット書き込みを読み取り可能 (write-audit-publish パターンに対応)
  • 書き込み対象は 1 トランザクションにつき 1 つの Iceberg テーブル。読み取りはデータベースをまたいで可能
2️⃣ 自動競合解決
  • 競合した書き込みが実際にデータレベルで重複しているかをチェックし、独立していれば最新バージョンに自動リベースしてコミット (git rebase に類似)
  • 再スキャン・再実行・リトライロジックが不要。設定やクラスタリングキー、再パーティショニングも不要
  • チェックは軽量な順に 3 段階: 操作レベル (片方が追加のみなら解決) → パーティションレベル → ファイルレベル
  • 独立性を証明できない場合は安全側に倒してリトライさせる設計 (正しさを同時実行性より優先)
  • Iceberg の write.*.isolation-level に準拠したスナップショット分離で Spark、Amazon EMR、Amazon Athena と整合
3️⃣ タイムトラベルクエリ
  • FROM、JOIN、USING 句のテーブル名の後に AS OF TIMESTAMP を追加して過去時点のスナップショットを読み取り
  • タイムスタンプはリテラルまたは式 (CURRENT_TIMESTAMP - INTERVAL '1 day' など) で指定
  • 読み取り専用でテーブルや履歴は変更されない。クエリ可能な期間はスナップショット保持設定に依存
  • レポートの再現、変更の監査、誤った書き込みからの復旧に活用可能

⏰ タイムトラベルの構文

SQL AS OF TIMESTAMP 構文 
SELECT ...
FROM iceberg_table
     AS OF TIMESTAMP { 'timestamp_literal' | ( timestamp_expression ) }
     [ [ AS ] alias ]

AS OF TIMESTAMP 句は直後のテーブル参照にのみ適用され、クエリ内の他のテーブルは現在の状態で読み取られます。時点はクエリ実行前に一度だけ決定されます。

🛠️ 設定方法

✅ 前提条件

✓Amazon Redshift プロビジョンドクラスター (RA3) または Redshift Serverless (マルチステートメントトランザクションは Patch 206 以降)
✓AWS Glue Data Catalog または Amazon S3 Tables に Iceberg テーブルが登録され、外部スキーマまたは awsdatacatalog 経由で参照可能
⚠孤立ファイルクリーンアップの有効化を推奨 (中断されたトランザクションが未参照ファイルを残すため。S3 Tables はデフォルト有効、Glue Data Catalog は孤立ファイル削除オプティマイザーの有効化が必要)

ステップ 1: マルチステートメントトランザクションで複数の書き込みをまとめる

SQL write-audit-publish パターン 
BEGIN;

-- POS 売上データをマージ
MERGE INTO iceberg_schema.sales USING iceberg_schema.pos_sales p ON ...;

-- 取り消しされた売上を削除
DELETE FROM iceberg_schema.sales
  WHERE sale_id IN (SELECT sale_id FROM iceberg_schema.pos_voids);

-- 監査チェック: 未コミットの変更をトランザクション内で確認
SELECT sum(amount), sum(CASE WHEN amount < 0 THEN 1 ELSE 0 END)
FROM iceberg_schema.sales WHERE sale_date = '2026-10-06';

COMMIT; -- チェックに問題があれば ROLLBACK

MERGE と DELETE が単一の Iceberg スナップショットとして公開されます。コミット前の SELECT は自身の未コミット変更を読み取れるため、検証してから公開できます。問題があれば ROLLBACK で何も公開せずに取り消せます。

ステップ 2: タイムトラベルクエリで過去の状態を参照する

SQL 1 日前と現在の比較 
-- 1 日前と現在の行数を比較
SELECT 'current' AS period, COUNT(*) AS order_count
FROM iceberg_schema.orders
UNION ALL
SELECT '1 day ago', COUNT(*)
FROM iceberg_schema.orders AS OF TIMESTAMP (CURRENT_TIMESTAMP - INTERVAL '1 day');

AS OF TIMESTAMP 句を付けたテーブル参照のみが過去時点のスナップショットを読み取り、他のテーブル参照は現在の状態を読み取ります。

ステップ 3: 誤った書き込みから復旧する

SQL 1 時間前の状態へ復元 
BEGIN;

DELETE FROM iceberg_schema.orders WHERE customer_id = 42;

INSERT INTO iceberg_schema.orders
SELECT * FROM iceberg_schema.orders
     AS OF TIMESTAMP (CURRENT_TIMESTAMP - INTERVAL '1 hour')
WHERE customer_id = 42;

COMMIT;

顧客 42 の行を一度削除し、1 時間前のスナップショットから再挿入してその時点の状態に正確に復元します。どちらかのステートメントが失敗した場合は何もコミットされません。

💡 メリット

💼 ビジネス面

✓パイプラインの信頼性向上: バッチ処理が all-or-nothing でコミットされ、途中失敗による不整合データが下流のレポートや分析に影響しない
✓運用コストの削減: 競合リトライロジックの実装・運用や、監査用のテーブルコピー保持が不要になり、開発・運用の負担が軽減
✓監査・コンプライアンス対応: タイムトラベルで過去時点の状態を正確に再現でき、監査対応やレポートの再現性が向上

⚙️ 技術面

✓スループットの向上: 従来 OCC で 16 並列書き込み時に約 94% が失敗していたワークロードが拒否ゼロとなり、完了コミット数が 12 倍に
✓コミットオーバーヘッドの削減: 25 ステートメントのバッチで INSERT 約 14.77%、DELETE 約 11.29% の短縮。32 並列時の正規化スループットは 4 ステートメントのトランザクションで約 10.37 倍 (自動コミットは約 2.89 倍)
✓エコシステムとの整合性: スナップショット分離の動作が Spark、Amazon EMR、Amazon Athena と整合し、マルチエンジン構成でも一貫した動作

⚠️ デメリット・制約事項

🚫 制限事項

✗書き込めるのは 1 トランザクションにつき 1 つの Iceberg テーブルのみ。2 つ目のテーブルへの書き込みはトランザクションを中断させる
✗トランザクション内で Iceberg DDL (CREATE / ALTER / DROP TABLE など) は拒否。動作変更であり、以前はトランザクション内の単一 DDL が成功していた
✗ストアドプロシージャ内からの Iceberg 書き込みはトランザクションで利用不可
✗同一ファイルを変更する書き込み同士、および ALTER が絡む競合は自動解決されず再実行が必要
✗タイムトラベルは AWS Glue Data Catalog の Iceberg テーブルのみ対応。AWS Lake Formation 管理テーブル (s3tablescatalog を含む) やデータ共有経由のテーブルは非対応
✗参照スナップショットのスキーマに struct / array / map などの複合データ型の列が含まれる場合、タイムトラベルは利用不可
✗タイムトラベルはスナップショット ID 指定 (AS OF VERSION) に非対応で、タイムスタンプ指定のみ

🤔 考慮すべき点

⚠中断されたトランザクションは未参照ファイルを残すため、孤立ファイルクリーンアップの有効化を推奨 (Glue Data Catalog のオプティマイザーは有効化後に作成されたファイルのみクリーンアップ)
⚠テーブルバージョンは BEGIN 時点ではなく各テーブルの初回読み取り時点で固定されるため、後から初めて読むテーブルには他セッションのコミットが反映される可能性
⚠遡れる期間はスナップショット保持設定に依存。保持しすぎるとクエリプランニングやストレージに影響するため、必要な期間のみ保持し、長期履歴はテーブル自体にタイムスタンプ列などで保持することを推奨
⚠個々のステートメントがすでにデータ量の多い処理である場合、コミットオーバーヘッドの割合が小さく、トランザクション化による性能向上は限定的

🎯 ユースケース

1. 日次バッチの write-audit-publish パターン 🏪

シナリオ: 小売業で POS データを夜間バッチで売上テーブルにマージし、取り消しデータを削除した上で、整合性チェックに合格した場合のみ公開したい。

SQL
BEGIN;
MERGE INTO iceberg_schema.sales USING iceberg_schema.pos_sales p ON ...;
DELETE FROM iceberg_schema.sales
  WHERE sale_id IN (SELECT sale_id FROM iceberg_schema.pos_voids);
SELECT sum(amount) FROM iceberg_schema.sales WHERE sale_date = '2026-10-06';
-- チェック結果に応じて COMMIT または ROLLBACK
COMMIT;

効果下流の利用者には検証済みの完全な状態のみが見え、途中失敗時もテーブルは変更前のままクリーンに保たれる。

2. ストリーミング挿入とコンプライアンス削除の同時実行 🌊

シナリオ: IoT データをストリーミング挿入し続けるテーブルに対し、GDPR などに基づく長時間の削除ジョブを定期実行したい。従来は削除ジョブ実行中に挿入が 1 件コミットされるだけで削除ジョブ全体が失敗していた。

SQL
-- セッション A: ストリーミング挿入 (継続実行)
INSERT INTO iceberg_schema.events SELECT * FROM staging_events;

-- セッション B: 定期削除ジョブ (同時実行)
DELETE FROM iceberg_schema.events
  WHERE user_id IN (SELECT user_id FROM deletion_requests);

効果挿入は追加のみの操作であるため常に自動解決され、削除ジョブも変更が重複しない限り失敗しない。リトライロジックの実装が不要になり、ジョブの完了時間が予測可能になる。

3. 誤削除からの復旧とレポートの再現 🔄

シナリオ: 誤った DELETE で注文データの一部が消えてしまった。また、月末締めのレポートを後日同じ結果で再実行したい。

SQL
-- 誤削除からの復旧: 1 時間前のスナップショットから復元
INSERT INTO iceberg_schema.orders
SELECT * FROM iceberg_schema.orders
     AS OF TIMESTAMP (CURRENT_TIMESTAMP - INTERVAL '1 hour')
WHERE status = 'pending';

-- 月末締め時点のレポート再現
SELECT order_date, SUM(amount) AS revenue
FROM iceberg_schema.orders AS OF TIMESTAMP '2026-11-01 02:00:00 UTC'
WHERE order_date = '2026-10-31'
GROUP BY order_date;

効果テーブルのコピーやバックアップからのリストアなしに、SQL だけで誤操作からの復旧と締め時点のレポート再現が可能になる。

💰 料金・利用可能リージョン

💵 料金

これらの機能に追加料金はありません。Iceberg テーブルへの書き込み・クエリに使用する Amazon Redshift プロビジョンドクラスターまたは Redshift Serverless の通常の料金が適用されます。なお、タイムトラベル用にスナップショットを保持すると、そのスナップショットのみが参照するデータファイルが Amazon S3 に残るため、ストレージコストに影響する点に留意してください。

🌍 利用可能リージョン

Iceberg テーブルへの書き込みまたはクエリをサポートする Amazon Redshift プロビジョンドクラスター (RA3) および Redshift Serverless が利用できる、すべての AWS 商用リージョンで利用可能です。

🔗 関連サービス・機能

→AWS Glue Data Catalog: Iceberg テーブルのカタログとして使用。スナップショット保持・コンパクション・孤立ファイル削除の各オプティマイザーによるテーブルメンテナンスを提供
→Amazon S3 Tables: Iceberg 専用の組み込みマネージドテーブルストレージ。トランザクションの書き込み先として利用可能で、未参照ファイル削除がデフォルトで有効
→Amazon Athena / Amazon EMR (Spark): 同一の Iceberg テーブルを共有する他の分析エンジン。競合解決のスナップショット分離の動作がこれらのエンジンと整合
→Amazon Redshift マテリアライズドビュー: Iceberg マテリアライズドビューはトランザクション内での REFRESH やタイムトラベルクエリの対象

📝 まとめ

今回のアップデートにより、Amazon Redshift は Apache Iceberg テーブルに対してデータウェアハウス同等のトランザクションセマンティクスを提供し、レイクハウスでの本番書き込みワークロードの運用を大幅に簡素化します。Iceberg テーブルへの書き込みで競合リトライや部分失敗に悩まされていた場合は、Patch 206 以降への更新と孤立ファイルクリーンアップの有効化を確認した上で、マルチステートメントトランザクションの導入を検討することを推奨します。
