Amazon SageMaker Unified Studio

カスタム Designation (カスタム権限セット) のサポート

組織のペルソナに合わせた名前付き権限セットをプロジェクトメンバーに割り当て可能に
📅 リリース日: 2026 年 10 月 29 日
🛠️ 機能: Custom designations

📝 概要

Amazon SageMaker Unified Studio がカスタム Designation (名前付き権限セット) をサポートしました。 ドメイン管理者が Catalog、Subscriptions、Connections、Notebooks、Data Agent などのカテゴリから権限を選択して独自の役割を定義し、プロジェクトメンバーに割り当てられます。 Designation はドメインレベルで一度定義すれば全プロジェクトで再利用でき、「Data Steward」「Analyst」といった組織のペルソナに対応した権限分離を単一プロジェクト内で実現できます。

❌ Before: アップデート前の課題
  • 割り当て可能なロールは Owner と Contributor の 2 種類のみで、権限はほぼ同一
  • 職務分掌の実現には、ペルソナごとに別々のプロジェクトを作成して権限を分離する必要があった
  • 「承認はできるが編集はできない」「閲覧とクエリのみ」といった組織独自の役割を表現できなかった
✅ After: アップデート後の改善
  • 名前付き権限セットをドメインレベルで定義し、ドメイン内の任意のプロジェクトで再利用可能に
  • 異なる役割のメンバーが差別化された権限で同一プロジェクトを共有でき、追加プロジェクトが不要に
  • アクション実行時に Designation が評価される単一の権限モデルで職務分掌を実現

ドメイン管理者がドメインレベルでカスタム Designation を定義し、プロジェクトオーナーが各メンバーに割り当てます。メンバーがポータルまたは API からアクションを実行すると、割り当てられた Designation が評価され、許可または拒否が決定されます。

⚙️ 主要機能

1️⃣ カスタム Designation の作成
  • 管理ポータルの [Designations] メニューから名前付き権限セットを作成
  • Catalog、Project、Subscriptions、Connections、Notebooks、Data Agent などのカテゴリから権限を視覚的に選択
  • 既存の Designation の複製 (Duplicate) によるカスタマイズも可能
  • 誤削除を防ぐ削除保護 (Allow delete チェックボックス) を設定可能
2️⃣ ドメインレベルでの一元管理とプロジェクト横断の再利用
  • 一度定義すれば、そのドメイン内の任意のプロジェクトで割り当て可能
  • 各メンバー (IAM ロール、IAM ユーザー、SSO ユーザー、SSO グループ) に 1 つの Designation を割り当て
  • グループ経由で追加の Designation を継承した場合は権限の和集合が適用
3️⃣ 実行時の権限評価による職務分掌
  • ポータルまたは API からのアクション実行時に Designation を評価し、許可/拒否を決定
  • 権限定義には Cedar ポリシー言語を使用
  • IAM と Designation の 2 層認可 (IAM の明示的 Deny は常に優先)
  • 既存の IAM ポリシーを変更せずに利用可能
4️⃣ マネージド Designation との併用
  • 編集・削除できない 2 つのマネージド Designation (Owner、Contributor) を引き続き提供
  • マネージド Designation は一般的なプロジェクトロールのベースライン権限セットを提供

💻 CLI での作成例

Bash AWS CLI によるカスタム Designation の作成 
aws datazone create-designation \
    --domain-identifier "dzd_example1234" \
    --name "Data Engineer" \
    --delete-protection \
    --description "Can manage data sources and create assets" \
    --policy 'permit(principal, action in [DataZone::Action::"CreateDataSource", DataZone::Action::"UpdateDataSource", DataZone::Action::"CreateAsset"], resource);'

Amazon DataZone の create-designation コマンドで、Cedar ポリシーにより許可するアクションを指定してカスタム Designation を作成します。削除保護を無効にする場合は --no-deletion-protection フラグを使用します。

🔧 設定方法

✅ 前提条件

✓ドメインレベルで Administrator designation を保有していること
✓対象のドメインが V2 ドメインであること (V1 ドメインはカスタム Designation 非対応)
✓関連アカウントから操作する場合、AWS RAM マネージド許可が所定の最小バージョンを満たしていること (例: AWSRAMPermissionAmazonDataZoneDomainFullAccessWithPortalAccess v8 以上)

ステップ 1: カスタム Designation の作成
  • ドメイン管理ポータルにサインインし、[Designations] → [Create designation] を選択
  • 名前 (ドメイン内で一意、最大 64 文字) と説明を入力
  • 削除を許可する場合は [Allow delete] を選択 (デフォルトでは削除保護が有効)
  • 視覚的な権限セレクタで、含める権限をカテゴリから選択して [Create] を選択
  • 既存の Designation から [Duplicate designation] で権限が事前選択された状態で複製作成も可能
ステップ 2: プロジェクトメンバーへの割り当て
  • プロジェクトオーナーが、メンバー管理画面で各メンバー (IAM ロール、IAM ユーザー、SSO ユーザー、SSO グループ) に Designation を割り当て
  • 各メンバーには直接割り当てで 1 つの Designation を設定
  • グループ経由で追加の Designation を継承した場合は権限の和集合が適用
ステップ 3: 動作確認
  • 割り当てたメンバーでポータルにサインイン
  • 許可したアクション (例: アセットの公開、サブスクリプションの承認) が実行できることを確認
  • 許可していないアクションが拒否されることを確認

💡 メリット

💼 ビジネス面

✓職務分掌の実現: 承認者と作業者を同一プロジェクト内で権限分離でき、データガバナンスやコンプライアンス要件に対応しやすい
✓ペルソナに合わせた権限設計: Data Steward、Analyst など実際の役割に対応した権限セットを定義でき、権限管理の意図が明確になる
✓プロジェクト乱立の抑止: 権限分離のためだけの別プロジェクトが不要になり、プロジェクト数と管理コストを削減

🛠️ 技術面

✓IAM ポリシー変更が不要: 既存の IAM ポリシーを変更せずにプロジェクトレベルの細粒度アクセス制御を追加
✓ドメインレベルでの一元管理: 一度定義すれば全プロジェクトで再利用でき、一貫した権限適用が可能
✓2 層認可による多層防御: IAM と Designation の両方で許可された場合のみ成功し、IAM の Deny が常に優先されるため安全性が高い

⚠️ デメリット・制約事項

🚫 制限事項

✗カスタム Designation は V2 ドメインのみ対応 (V1 ドメインでは利用不可)
✗ドメインの管理プロジェクト (Admin project) では作成・割り当て不可
✗選択できるのは事前定義された権限セットのみで、対象外の API アクションは追加できない
✗Data Agent アクションは必須で、カスタム Designation から除外できない
✗DataSource API は IAM のみで認可され、Designation による Cedar 認可は非対応
✗作成数はデフォルトでドメインあたり 10 個まで (上限緩和で最大 100 個)

🤔 考慮すべき点

⚠カスタム Designation のメンバーは Contributor と同じプロジェクト通知を受け取るため、実行できないイベントの通知受信やオーナー向け通知の未受信が発生しうる
⚠Amazon QuickSight ブループリント使用時は、権限設定に関わらず QuickSight フォルダへの Viewer アクセスのみ (Contributor 権限は QuickSight 管理者による個別付与が必要)
⚠新しい Query Editor はノートブック基盤のため、ノートブック権限の設定は Querybook にも適用される
⚠関連アカウントから操作する場合は AWS RAM マネージド許可のバージョン要件に注意

🎯 ユースケース

🧑‍⚖️ ユースケース 1: データスチュワードによるガバナンス運用

シナリオ: データガバナンスチームのスチュワードが、データ自体の編集は行わずに、サブスクリプションリクエストの承認とアセットの公開のみを担当する。

実装例: Designation 名「Data Steward」/ 権限は Subscriptions カテゴリの承認権限と Catalog カテゴリの公開権限 / ガバナンスチームの SSO グループに割り当て

効果: 承認権限と編集権限を分離した職務分掌を単一プロジェクト内で実現し、監査要件に対応できる。

🧑‍💻 ユースケース 2: アナリスト向けの閲覧・分析限定アクセス

シナリオ: ビジネスアナリストにはデータのクエリとノートブックの実行のみを許可し、接続やカタログの変更は禁止したい。

実装例: Designation 名「Analyst」/ 権限は Notebooks カテゴリの実行権限とクエリ実行に必要な権限のみ / アナリストの SSO ユーザーまたはグループに割り当て

効果: アナリストが分析に必要な操作のみ実行でき、意図しない設定変更やカタログ汚染を防止できる。

🤖 ユースケース 3: 自動化パイプライン用の最小権限ロール

シナリオ: CI/CD やデータパイプラインの自動化で使用する IAM ロールに、パイプライン実行に必要な最小限のプロジェクト権限のみを付与する。

Bash 自動化パイプライン用 Designation の作成 
aws datazone create-designation \
    --domain-identifier "dzd_example1234" \
    --name "Pipeline Automation" \
    --delete-protection \
    --description "Automated pipeline minimal permissions" \
    --policy 'permit(principal, action in [DataZone::Action::"CreateDataSource", DataZone::Action::"UpdateDataSource"], resource);'

効果: 人間のユーザーと自動化ロールが同一プロジェクトを共有しつつ、自動化ロールには最小権限の原則を適用できる。

🔗 関連サービス・機能

→Amazon DataZone: Designation の権限は Amazon DataZone API アクションとして定義され、CLI では aws datazone create-designation で作成
→AWS IAM: IAM が AWS API 境界での呼び出し可否を、Designation がプロジェクト内のアクション可否を評価する 2 層認可を構成
→AWS IAM Identity Center: SSO ユーザーおよび SSO グループへの Designation 割り当てに利用
→Cedar: Designation の権限定義に使用されるオープンソースのポリシー言語
→Amazon QuickSight: QuickSight ブループリント使用時、カスタム Designation のメンバーには Viewer アクセスが付与される

📌 まとめ

カスタム Designation により、Owner と Contributor の 2 択だった権限モデルから脱却し、組織のペルソナに合わせた細粒度のプロジェクト権限を単一プロジェクト内で実現できるようになりました。 複数の役割が 1 つのプロジェクトを共有する環境や、職務分掌が求められるガバナンス要件のある環境では、まず Data Steward や Analyst などの代表的なペルソナのカスタム Designation を定義し、既存プロジェクトへの適用を検討することを推奨します。
