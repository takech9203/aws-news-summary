🛡️ AWS Security Agent (AWS Continuum)

予算コントロールと Finding 再検証 のサポート

AI ペネトレーションテストに「コスト上限」と「修正確認の高速化」が登場
📅 リリース日: 2026 年 8 月 19 日
⚙️ 機能: 最大タスク時間制限 / Finding 再検証

📝 概要

AWS Security Agent は、AI エージェントが Web アプリケーションの脆弱性を自律的にテストするオンデマンドのペネトレーションテストサービスです。課金は並列タスク全体の累積タスク時間に基づきます。今回のアップデートで 2 つの新機能が追加されました。

💰 予算コントロール (最大タスク時間制限)

テストごとに最大タスク時間の上限を設定。プリセット (20 / 30 時間)、カスタム、無制限から選択でき、上限がそのままコスト上限として機能します。上限到達時もテストは正常に停止し、発見済み Finding はすべて保持されます。

🔁 Finding 再検証 (Revalidation)

修正デプロイ後、フルテストを再実行せずに選択した Finding だけを再テスト。結果は Active または Resolved で返され、元の Finding にリンクされた履歴で追跡できます。

❌ アップデート前の課題

  • テストコストに上限を設定する組み込みの方法がなく、大規模アプリではタスク時間の消費 (= コスト) を事前に制御できなかった
  • 修正の有効性確認にはペネトレーションテスト全体の再実行が必要だった
  • フルテスト再実行は時間とコストを余分に消費し、修復サイクルの高速化を妨げていた

✅ アップデート後の改善

  • 最大タスク時間制限でテストごとのコスト上限を設定可能 (最小 20 時間)
  • 上限到達時も正常停止し、Finding は全保持のまま Completed で完了
  • 特定 Finding のみの再検証でフルテスト再実行が不要に
  • Active / Resolved のステータスと再検証履歴で修復状況を時系列で追跡

最大タスク時間制限付きのペネトレーションテストから Finding の修正・再検証までのワークフロー。再検証は独立したジョブとして実行され、選択した Finding のみを対象に Active / Resolved を判定します。

⚡ 主要機能

1️⃣ 予算コントロール (最大タスク時間制限)

  • テスト作成時に Max task hours セクションで上限を設定可能
  • プリセット値 (20 / 30 時間など)、カスタム値 (最小 20 時間)、または No limit から選択
  • タスク時間は並列タスクを含む累積作業時間で、実際の経過時間 (wall-clock time) とは異なる
  • タスク時間 = 課金単位のため、上限設定がそのままコスト上限として機能
  • 上限到達時は正常停止し、発見済み Finding を全保持したまま Completed で完了

2️⃣ Finding 再検証 (Revalidation)

  • 完了したテスト実行から 1 つ以上の Finding を選択して再検証を実行
  • 選択された Finding の検証ステップのみを再実行 (新規脆弱性の探索は行わない)
  • 結果は Active (再現できた = 悪用可能) / Resolved (再現不可 = 修正確認) の 2 種類
  • 独立ジョブとして実行され、元の Finding は変更されない
  • 実行履歴に「Revalidation」タイプとして表示され、フルテストと区別可能

3️⃣ 再検証履歴のトレーサビリティ

  • 再検証ジョブから「Original finding」で元の Finding を参照可能
  • Finding 側から「Revalidation jobs」で過去の再検証履歴と結果を一覧可能
  • 修復の試行から解決までの経緯を時系列で追跡できる

🛠️ 設定方法

📋 前提条件

✓AWS Security Agent Web アプリケーションへのアクセス権があること
✓検証済みドメインが少なくとも 1 つ存在すること (テスト対象は検証済みドメインのみ)
✓AWS Security Agent 用の適切な権限を持つ IAM ロールが設定されていること
✓(再検証の場合) 少なくとも 1 つの Finding を持つ完了済みテストと、対象 Agent Space へのアクセス権

ステップ 1: 最大タスク時間制限を設定してテストを作成

  1. AWS Security Agent Web アプリケーションにログイン
  2. Penetration tests セクションから Create a penetration test を選択
  3. テスト名、対象ドメイン、スコープ、IAM ロールなどを設定
  4. Max task hours セクションで上限を選択 — プリセット (20 / 30 時間など)、No limit、または Custom (最小 20 時間)
  5. Create and execute を選択してテストを開始

💡 大規模アプリや網羅的な結果を得たい場合は、30 時間以上などの高めの上限が推奨されています。課金は実使用分のみのため、高い上限を設定してもテストが追加時間を必要としない限りコストは増加しません。

ステップ 2: 修正デプロイ後に Finding を再検証

  1. 修正を元のテスト対象と同じ環境にデプロイ (修正の反映が正確な結果の前提)
  2. 対象の Finding を含むペネトレーションテスト実行を開く
  3. Finding パネルで Multiselect findings for revalidation を選択
  4. 再検証したい Finding のチェックボックスを選択
  5. Revalidate findings を選択して再検証を実行

ステップ 3: 結果の確認と履歴の追跡

  1. 再検証ジョブの結果で各 Finding のステータス (Active / Resolved) を確認
  2. Active の場合は追加の修復を行い、Resolved になるまで再検証を繰り返す
  3. 再検証ジョブから Original finding、Finding から Revalidation jobs をたどり修復経緯を確認

⚠️ アプリケーションに広範な変更を加えた場合は、個別再検証ではなくフルのペネトレーションテストの実行が推奨されています。

💡 メリット

📈 ビジネス面

  • コストの予見性向上: タスク時間 = 課金単位に上限を設定でき、予算超過のリスクを排除
  • 修復サイクルの高速化: フルテスト再実行を待たずに修正の有効性を確認でき、修復からクローズまでのリードタイムが短縮
  • 監査対応の強化: 再検証履歴により、発見から解決までの証跡を提示できる

⚙️ 技術面

  • Graceful な停止動作: 上限到達時も Finding が失われず Completed で完了。部分的な結果でも有効活用可能
  • フォーカスした再テスト: 選択した Finding の検証ステップのみを再実行するため、フルテストより高速かつ低コスト
  • 元の Finding の不変性: 再検証は独立ジョブとして実行され、テスト結果の履歴が保全される

⚠️ デメリット・制約事項

制限事項

✗最大タスク時間制限の最小値は 20 時間。それより小さい上限は設定不可
✗再検証は選択した Finding のみを再テストし、新しい脆弱性の発見や他の箇所のテストは行わない
✗再検証には、完了済みテストの認証設定で到達可能なターゲットアプリケーションが必要
✗What's New では利用可能リージョンが明記されていない

考慮すべき点

⚠タスク時間は並列タスクを含む累積作業時間であり、実際の経過時間とは異なる点を理解して上限を設定する
⚠上限を低くしすぎるとテストが途中停止しカバレッジが不完全になる可能性 (課金は実使用分のみのため高めの上限が推奨)
⚠正確な再検証結果には、修正が元のテスト対象と同じ環境にデプロイ済みであることが必要
⚠広範な変更を加えた場合は、個別再検証ではなくフルテストの再実行が適切

🎯 ユースケース

1. 予算上限付きの定期ペネトレーションテスト

シナリオ: セキュリティチームが四半期ごとに本番 Web アプリのテストを実施。部門予算の制約からテストごとのコスト上限を保証する必要がある。

手順予算上限付きテスト
1. テスト作成時に Max task hours でプリセットの 30 時間を選択
2. Create and execute でテストを開始
3. 上限到達時は Completed となり、発見済み Finding をレビュー
4. カバレッジが不足していれば、次回のテストで上限を引き上げて再実行

✅ 効果: テストあたりのコスト上限が保証され、予算計画が立てやすくなる。上限到達時も Finding は保持されるため、部分的な結果からでも修復作業を開始できる。

2. 修正デプロイ後の迅速な修復確認

シナリオ: DevSecOps エンジニアが SQL インジェクションの Finding を修正しデプロイ。フルテストを再実行せずに修正の有効性を確認したい。

手順Finding 再検証
1. 修正をテスト対象環境にデプロイ
2. 完了済みテスト実行を開き、Multiselect findings for revalidation を選択
3. 該当する Finding を選択して Revalidate findings を実行
4. 結果が Resolved であれば修復完了、Active であれば追加修正して再検証

✅ 効果: フルテスト再実行に比べて大幅に短い時間とコストで修正を検証でき、修復サイクルが高速化する。

3. 修復状況の継続的なトラッキングと報告

シナリオ: セキュリティ管理者が、複数の脆弱性の修復進捗を経営層や監査人に報告する必要がある。

手順修復トラッキング
1. 各修復試行の後に該当 Finding の再検証を実行
2. Finding の Revalidation jobs で再検証の履歴と結果を確認
3. Active から Resolved への遷移を修復完了のエビデンスとして報告資料に反映

✅ 効果: 元の Finding にリンクされた再検証履歴により、脆弱性ごとの修復経緯を客観的なエビデンスとして提示できる。

💰 料金と利用可能リージョン

💵 料金

  • 並列テストタスク全体で消費された累積タスク時間に基づいて課金
  • 課金は実際に使用されたタスク時間のみに基づく
  • 上限を高く設定しても、追加時間を必要としない限りコストは増加しない
  • 具体的な単価は AWS Security Agent の料金ページを参照

📌 まとめ

予算コントロールと Finding 再検証は、AI エージェントによるペネトレーションテストを本番運用に組み込むうえで重要な「コストの予見性」と「修復確認の効率化」という 2 つの課題を解決するアップデートです。タスク時間の上限設定により予算超過のリスクなくテストを実行でき、再検証により修復サイクルを大幅に短縮できます。

AWS Security Agent を利用中、または導入を検討しているチームは、まず既存テストへの最大タスク時間制限の設定と、修正デプロイ後の再検証ワークフローの組み込みから始めることが推奨されます。
