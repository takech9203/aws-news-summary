🛡️ AWS Nitro Sandboxes

EKS Pod、ECS タスク、軽量 VM にハードウェア分離境界を 1 行で適用
📅 リリース日: 2026 年 11 月 9 日

📋 概要

AWS Nitro Sandboxes は、Nitro Hypervisor が管理する軽量 VM として、EKS Pod、ECS タスク、AI エージェントなどのワークロードをハードウェア分離された専用 VM 内で実行できる新機能です。単一の EC2 インスタンスを複数のワークロードで安全に共有しながら、EC2 インスタンス間と同等の分離境界を実現します。

❌ Before: アップデート前の課題
  • コンテナや Pod は同一ノードで Linux カーネルを共有し、コンテナエスケープやカーネル脆弱性の影響が他ワークロードへ波及するリスク
  • VM レベルの分離には専用 EC2 インスタンスか、オーバーヘッドの大きいネスト仮想化が必要で非効率
  • LLM 生成コードなど信頼できないコードに、ハードウェア分離をコンテナ単位で手軽に適用する手段がなかった
✅ After: アップデート後の改善
  • EKS Pod、ECS タスク、軽量 VM それぞれに Nitro Hypervisor が強制するハードウェア分離境界を付与
  • 単一 EC2 インスタンスを安全に共有し、使用率向上とコスト削減を両立
  • 暗号学的 Attestation により、完全性を証明したワークロードにのみシークレットを解放 (KMS キーポリシー条件)
  • 1 行の変更で有効化。Pod Identity、VPC CNI、EBS/EFS/S3、CloudWatch はそのまま動作

単一の EC2 親インスタンス上で、各 Pod、タスク、エージェントがそれぞれ専用の Nitro Sandbox (軽量 VM) 内で動作し、Nitro Hypervisor がサンドボックス間および親インスタンスとの間のハードウェア分離を強制します。Confidential モードでは Attestation の測定値を AWS KMS キーポリシーで検証し、整合性を証明したサンドボックスにのみシークレットを解放できます。

⚡ 主要機能

🛡️ Nitro Hypervisor によるハードウェア分離
  • 各サンドボックスは親インスタンスと並行して動作する第 1 レベルのハードウェア仮想化ゲスト (ネスト仮想化やエミュレーションを使用しない)
  • 親が vCPU、メモリ、I/O を提供し、Nitro System が分離境界を強制。サンドボックス内のコードは他のサンドボックスや親にアクセス不可
  • AWS が維持・パッチ適用する最小化ハイパーバイザーが信頼モデルの基盤。自組織のオペレーターからもワークロードを分離可能
  • Intel、AMD、AWS Graviton プロセッサで動作
🔐 Confidential モードと Direct モード
  • Confidential (デフォルト): サンドボックスのメモリを親の外に移動し、親から読み取り不可。NSM による Attestation を提供。シークレットを扱うワークロードに推奨
  • Direct: 親がメモリを共有し Attestation なし。構成がシンプルで I/O スループットが高い。親とサンドボックスを同一の信頼できる主体が運用する場合に使用
  • モードは作成時に選択し、実行中の変更は不可
🔑 暗号学的 Attestation によるシークレット保護
  • 起動時に内容を NSM に測定し、改変されていないコードの実行を証明
  • KMS キーポリシーの kms:RecipientAttestation:PCR 条件で、測定値が期待値と一致するサンドボックスにのみデータキーを解放。親は測定値を偽造できない
☸️ EKS の Isolated / Confidential Pod
  • Pod spec の runtimeClassName に isolated-sandbox または confidential-sandbox を設定するだけで Pod 単位にオプトイン
  • シム (containerd-shim-nitro-sandbox-v2) が Pod 用 Firecracker microVM を起動し、サンドボックス内の専用 containerd がコンテナを管理
  • Cedar ポリシーでコンテナ受け入れ、exec、ログストリーミングなどを制御 (ポリシーは Attestation レジスタに測定)
  • OCI 準拠のイメージ暗号化 (KMS で復号) と AWS Signer による署名検証をサポート
  • Pod Identity、VPC CNI、EBS/EFS CSI、CloudWatch などの EKS ネイティブ機能がそのまま動作
  • sandbox.amazonaws.com/network-isolated: "true" アノテーションで、生成コードのネットワークアクセスを遮断可能
📋 ECS Managed Instances の Isolated / Confidential タスク
  • ECS Managed Instances の信頼実行機能として提供。各タスクが専用の軽量 VM 内で動作
  • AWS Fargate と同様の分離保証を実現しつつ、インスタンスタイプ選択、ビンパッキング、キャパシティ予約の柔軟性を維持
🖥️ EC2 での直接利用 (セルフマネージド)
  • 独自の AMI、オーケストレーション、VMM で直接制御可能。Amazon Linux と Firecracker をネイティブサポート、QEMU などへのパッチも提供
  • Firecracker は Nitro Enclaves ドライバーを使い、標準の virtio-pci デバイスモデルのサンドボックスを作成・起動
  • ゲストは通常の virtio-pci デバイスを認識するため、サンドボックス固有のコードは不要

Nitro Sandboxes の主な仕様

項目詳細
分離方式Nitro Hypervisor による第 1 レベルのハードウェア仮想化 (ネスト仮想化ではない)
モードConfidential (デフォルト、Attestation あり) / Direct (Attestation なし、高 I/O スループット)

GPU パススルー現時点では利用不可
サイズ変更実行中の vCPU / メモリ変更は不可 (終了して再作成)

KMS キーポリシーでの Attestation 条件の例

JSON KMS キーポリシー条件 
{
  "Effect": "Allow",
  "Principal": { "AWS": "arn:aws:iam::123456789012:role/sandbox-workload-role" },
  "Action": "kms:Decrypt",
  "Resource": "*",
  "Condition": {
    "StringEqualsIgnoreCase": {
      "kms:RecipientAttestation:PCR0": "<期待する PCR0 測定値>"
    }
  }
}

PCR (Platform Configuration Register) の測定値が期待値と一致するサンドボックスにのみ復号を許可します。Confidential モードの機密性保証を完結させるには、この検証の構成が必須です。

📌 API 変更履歴: 本アップデートは EKS の RuntimeClass、ECS Managed Instances のタスク設定、EC2 の既存の Enclave オプションを通じて提供されており、awsapichanges.com では対応する API 変更エントリは確認できませんでした (2026 年 11 月 10 日時点)。

🚀 設定方法

前提条件

✓Nitro Sandboxes をサポートするインスタンスタイプ (AWS Nitro Enclaves 対応タイプ) を使用
✓EKS: Isolated / Confidential Pod に対応したクラスターとノード設定
✓ECS: Amazon ECS Managed Instances を使用
✓EC2 直接利用: Enclave オプションを有効化し、ゲストイメージと VMM (Firecracker 推奨) を準備

ステップ 1: EKS Pod でサンドボックスを有効化

YAML Pod spec に 1 行追加 
apiVersion: v1
kind: Pod
metadata:
  name: sandboxed-pod
spec:
  runtimeClassName: isolated-sandbox  # または confidential-sandbox
  containers:
    - name: app
      image: 123456789012.dkr.ecr.ap-northeast-1.amazonaws.com/app:latest

runtimeClassName を 1 行追加するだけで、この Pod が専用の Nitro Sandbox 内で起動します。設定のない Pod は従来どおりデフォルトのコンテナランタイムで動作します。

ステップ 2: EC2 で直接利用する場合のインスタンス起動

Bash Enclave オプションを有効化して起動 
aws ec2 run-instances \
  --image-id ami-xxxxxxxxxxxxxxxxx \
  --instance-type m7i.xlarge \
  --enclave-options Enabled=true

ステップ 3: Firecracker でサンドボックスを起動

JSON sandbox.json - 空の enclave オブジェクトで Nitro Sandbox 化 
{
    "boot-source": { "kernel_image_path": "sandbox-image" },
    "machine-config": { "vcpu_count": 2, "mem_size_mib": 2048 },
    "drives": [
        { "drive_id": "rootfs", "path_on_host": "rootfs.ext4",
          "is_root_device": true, "is_read_only": false }
    ],
    "network-interfaces": [
        { "iface_id": "eth0", "host_dev_name": "tap0" }
    ],
    "enclave": {}
}
Bash Firecracker 起動 
firecracker --config-file sandbox.json

空の "enclave": {} で Confidential モード (デフォルト)。Direct モードは "enclave": { "direct_mode": true } を設定します。

ステップ 4: Attestation によるシークレット解放の構成

Confidential モードのワークロードがシークレットを受け取る前に、KMS キーポリシーの kms:RecipientAttestation:PCR<PCR_ID> 条件で Attestation ドキュメントを検証するように構成します。サンドボックスが kms:Decrypt を呼び出すと、測定値が一致する場合にのみキーが解放されます。

💡 メリットと制約事項

✅ ビジネス面のメリット

✓コスト効率と分離の両立: 専用インスタンス不要で VM 相当の分離を実現し、インスタンス共有で使用率向上とコスト削減
✓追加料金なし: 既存の EC2 インスタンス料金の範囲内で分離を強化
✓規制対応の強化: Attestation + KMS で、完全性を証明してからシークレットを受け取る構成を実現

✅ 技術面のメリット

✓導入の容易さ: 1 行の変更で有効化。既存の EKS / ECS 機能がそのまま動作
✓ネイティブに近いパフォーマンス: エミュレーションやネスト仮想化のオーバーヘッドなし
✓自組織の運用者からの保護: Confidential モードでは親からメモリを読み取れない
✓ゲスト側の変更不要: 標準の virtio-pci デバイスモデルを提供

⚠️ 制限事項

✗Nitro Enclaves 対応インスタンスタイプのみ (最小サイズや metal は対象外が多い)
✗GPU パススルーは現時点で利用不可
✗合計 vCPU はインスタンスの 5 倍まで。メモリはオーバーコミットされない
✗実行中の vCPU / メモリ変更不可。デバイスのホットアンプラグ不可
✗ブロックデバイスは同時に 1 サンドボックスのみアタッチ可能
✗Confidential モードでは virtio-rng を利用不可 (ゲスト自身のエントロピーソースを使用)
✗Firecracker 以外の VMM での Attestation / Confidential モードにはパッチ適用が必要

⚠️ 考慮すべき点

⚠親のネットワークスタックは共有リソース。conntrack や DNS の枯渇対策としてサンドボックスごとの上限 / レート制限が必要
⚠分離はセキュリティ境界でありパフォーマンス予約ではない。vCPU はタイムシェアされるため密度とサイジングの設計が必要
⚠KMS キーポリシーで PCR 検証を構成しないと、機密性保証が不完全になる
⚠ネットワーク分離アノテーションは vsock 経由のゲスト側ポート到達を遮断しない
⚠責任共有モデル: AWS は Nitro Hypervisor / 境界 / ゲストイメージ、顧客はコンテナイメージ / Cedar ポリシー / KMS キーポリシー / アプリコードに責任

🎯 ユースケース

🤖 1. AI エージェントの LLM 生成コードの安全な実行

シナリオ: LLM が生成した信頼できないコードを実行しつつ、他のエージェントセッションや基盤自体への影響を遮断したい。

実装: セッションごとの Pod に runtimeClassName: isolated-sandbox を設定。ネットワーク不要なコード実行 Pod には network-isolated アノテーションを付与し、単一 EC2 インスタンスに多数のセッションをビンパッキング。

💡 効果: 生成コードが暴走や悪意ある挙動を示しても他セッションや親インスタンスに影響せず、インスタンス共有でコストも削減。

🏢 2. マルチテナント SaaS のテナント間分離

シナリオ: 同一クラスターで実行するテナントワークロード間の、コンテナエスケープやカーネル脆弱性によるデータ漏えいリスクを排除したい。

実装: EKS では isolated-sandbox、ECS では Managed Instances の Isolated タスクを適用。既存の Pod Identity、VPC CNI、ストレージ構成は維持し、テナント専用インスタンス構成から共有インスタンス構成へ移行。

💡 効果: Fargate 相当の分離保証を得ながら、インスタンスタイプ選択とビンパッキングによるコスト効率を維持。

🏦 3. 規制対象ワークロードの Attestation 付き実行

シナリオ: 金融・医療などで、ノード運用者からもデータを保護し、改変されていないコードだけがシークレットにアクセスできることを証明したい。

実装: confidential-sandbox を設定し、コンテナイメージを OCI 仕様で暗号化 + AWS Signer で署名。KMS キーポリシーに PCR 条件を設定し、Cedar ポリシーでイメージダイジェストや引数、マウントを固定。

💡 効果: 内部者リスクを含む脅威モデルに対応した、監査可能な実行環境を実現。

💰 料金と利用可能リージョン

💵 料金

Nitro Sandboxes は追加料金なし。通常の EC2 インスタンス、EKS クラスター、ECS の利用料金のみが発生します。親インスタンスの vCPU とメモリをサンドボックスに割り当てる方式のため、インスタンスサイズの設計がコストに直結します。

🌍 利用可能リージョン

すべての AWS 商用リージョンで、Nitro ベースのほとんどの EC2 インスタンス (Nitro Enclaves 対応インスタンスタイプ) において利用可能です。

📝 まとめ

AWS Nitro Sandboxes により、EKS Pod、ECS タスク、軽量 VM のそれぞれに Nitro Hypervisor が強制するハードウェア分離境界を、追加料金なし・1 行の変更で適用できるようになりました。LLM 生成コードの実行やマルチテナント環境など、これまで専用インスタンスやネスト仮想化が必要だったシナリオで、分離性とコスト効率を両立できる重要なアップデートです。AI エージェント基盤やマルチテナントワークロードを運用している場合は、対応インスタンスタイプと vCPU / メモリのサイジング制約を確認したうえで、Isolated モードからの導入を検討してください。
