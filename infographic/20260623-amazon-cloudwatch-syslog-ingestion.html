Amazon CloudWatch Logs

☁️ マネージド syslog 取り込み

エージェントレスで syslog を直接 CloudWatch Logs へ
📅 リリース日
2026 年 6 月 23 日

📌 概要

Amazon CloudWatch Logs が マネージド syslog 取り込み に対応しました。ファイアウォール、ルーター、スイッチ、Linux サーバーなどから送信される syslog メッセージを、エージェントのインストールや管理なし で直接 CloudWatch Logs に取り込めます。

ネットワーク機器やサーバーは、お客様の VPC エンドポイントへ TCP / TCP+TLS / UDP で syslog を送信します。トラフィックは AWS PrivateLink 経由で CloudWatch Logs の syslog サービスにトンネリングされ、サービスがメッセージを自動解析してロググループに書き込みます。RFC 5424 / RFC 3164 / Cisco FTD/ASA に対応し、facility・severity・hostname・appName といった構造化フィールドを自動抽出します。

❌ アップデート前の課題

  • syslog 取り込みに収集エージェントや中継サーバー、独自のログ転送基盤の構築・運用が必要
  • ファイアウォールやスイッチなど、エージェントを入れられない機器には追加の仕組みが必要
  • facility や severity を取り出すためにカスタム解析パイプラインを用意する必要

✅ アップデート後の改善

  • エージェントを一切インストールせず syslog を直接 CloudWatch Logs に送信
  • VPC エンドポイント宛てに送るだけで取り込みが完結し、中継基盤が不要
  • 主要フォーマットを自動検出し構造化フィールドを自動抽出、カスタム解析が不要

⚙️ 主要機能

1. エージェントレスでの syslog 取り込み
  • ファイアウォール、ルーター、スイッチ、Linux サーバー、ネットワークアプライアンスから直接取り込み
  • 収集エージェントのインストールや管理が不要
  • VPC 内ソースは VPC エンドポイントへ直接、AWS 外ソースは VPN / AWS Direct Connect 経由で到達
2. 複数プロトコルとプライベート接続への対応
  • TCP+TLS、TCP プレーンテキスト、UDP に対応
  • トラフィックは AWS PrivateLink でネットワーク的に分離された経路を転送
  • TLS は NLB で終端し、Amazon Trust Services 発行の AWS マネージド証明書を使用 (クライアント側の証明書設定は不要)
3. 複数フォーマットの自動検出と構造化フィールドの自動抽出
  • RFC 5424 / RFC 3164 / Cisco FTD/ASA を自動検出して解析
  • facility・severity・hostname・appName などを自動抽出
  • メッセージは生フォーマットのまま保存、抽出フィールドは Logs Insights でクエリ可能
4. 新しい API による設定管理
  • PutSyslogConfiguration / ListSyslogConfigurations / DeleteSyslogConfiguration の 3 つの新 API
  • ロググループと VPC エンドポイントの組み合わせで取り込み設定を管理

🔧 技術仕様

対応プロトコルとポート

プロトコルポート備考
TCP + TLS6514転送中に暗号化。コンプライアンス要件がある場合に推奨
TCP プレーンテキスト1514AWS PrivateLink 上のプレーンテキスト (ネットワーク分離)
UDP514ベストエフォート配信
💡TLS (6514) は NLB で終端され、Amazon Trust Services 発行の AWS マネージド証明書を使用。クライアントは追加設定なしに信頼します。UDP はメッセージ損失の可能性があるため、信頼性が必要な場合は TCP を推奨。

対応 syslog フォーマット

フォーマット概要
RFC 5424新しいフォーマット。構造化データ、ISO 8601 タイムスタンプ、明示的なアプリ名とプロセス ID を含む
RFC 3164BSD syslog (レガシー)。BSD タイムスタンプと TAG フィールド。ファイアウォールやルーターで広く使用
Cisco FTD/ASACisco FTD / ASA で使用。%FTD- または %ASA- タグで識別

抽出される主なフィールド (RFC 5424)

フィールド説明
facility / facilityCodeログカテゴリ名と数値コード (0-23)
severity / severityCode重要度レベル名と数値コード (0-7)
timestampISO 8601 形式のメッセージタイムスタンプ
hostname送信元デバイスのホスト名
appNameアプリケーション名
procId / msgIdプロセス ID とメッセージ識別子
structuredDataRFC 5424 構造化データ要素 (キーバリューメタデータ)
messageメッセージ本文
📝RFC 3164 では BSD タイムスタンプを ISO 8601 へ変換し TAG から appName / procId を抽出。Cisco FTD/ASA では device、deviceId、severityLevel、messageId、subsystem などを抽出します。

⚠️メッセージ配信の注意: syslog はアプリ層の ACK がなく、ロググループへの配信はベストエフォート。ロググループ削除、リソースポリシー誤設定、クォータ超過などで配信できない場合はメッセージが破棄され再送できません。SyslogMessagesDropped メトリクス (Reason ディメンション) で破棄を監視してください。

🎯 メリット

💼 ビジネス面

  • 運用コスト削減: 収集エージェントや中継基盤の構築・運用が不要
  • セキュリティ可視性向上: ファイアウォール等の syslog を一元集約し調査・監査に活用
  • 導入の迅速化: エージェント展開なしで多様なソースから短期間で収集開始

🔧 技術面

  • エージェントレス: インストール・更新・管理が不要
  • プライベート転送: AWS PrivateLink で分離経路、TCP+TLS で暗号化
  • 自動解析: 複数フォーマット検出と構造化抽出で Logs Insights クエリが即可能

⚠️ デメリット・制約事項

制限事項

  • 中東 (UAE)、中東 (バーレーン)、イスラエル (テルアビブ) では利用不可
  • メッセージサイズは TCP 最大 64 KB、UDP 最大 8 KB
  • 取り込みスループットはアカウントの PutLogEvents クォータを共有

考慮すべき点

  • ベストエフォート配信。配信失敗時は破棄され再送不可。SyslogMessagesDropped 監視が重要
  • UDP は損失の可能性。信頼性が必要なら TCP を使用
  • コンプライアンス要件があれば TCP+TLS (6514) を推奨

💰 料金・利用可能リージョン

料金

syslog 取り込みは CloudWatch Logs の取り込みとして扱われ、取り込みデータ量に応じた標準料金 が適用されます。スループットはアカウントの PutLogEvents クォータを共有。正確な料金はリージョンと取り込み量に基づき料金ページで確認してください。

利用可能リージョン

中東 (UAE)、中東 (バーレーン)、イスラエル (テルアビブ) を 除く、すべての商用 AWS リージョンで利用可能です。

🔗 関連サービス・機能

  • AWS PrivateLink: VPC エンドポイントから syslog サービスへ分離経路でトラフィックを転送
  • Amazon CloudWatch Logs Insights: 自動抽出された構造化フィールド (severity、hostname など) にクエリ
  • AWS Direct Connect / Site-to-Site VPN: AWS 外の syslog ソースが VPCEP に到達するための接続経路
  • Amazon CloudWatch メトリクス: SyslogMessagesDropped で配信失敗を監視

📝 まとめ

マネージド syslog 取り込みは、ファイアウォールやネットワーク機器、Linux サーバーの syslog を エージェントレスかつプライベートな経路 で集約し、構造化フィールドを自動抽出する機能です。エージェント管理やカスタム解析パイプラインの運用負担を大きく削減できます。まずは対象機器の syslog 送信先を VPC エンドポイントへ向け、PutSyslogConfiguration で設定して取り込みを検証し、あわせて SyslogMessagesDropped メトリクスの監視を設定して配信失敗を早期に検知できる体制を整えることを推奨します。
