Amazon CloudWatch

📊 メトリクスセントラライゼーション

複数アカウント・複数リージョンのメトリクスを単一の宛先アカウントへ自動集約
リリース日
2026 年 6 月 15 日
一般提供 (GA)

🎯 概要

AWS は、Amazon CloudWatch Metrics Centralization の一般提供を発表しました。複数のアカウントおよび複数のリージョンに分散している CloudWatch メトリクスを、単一の宛先アカウントに自動的に複製 (集約) できます。

AWS Organizations を通じて集約ルールを定義することで、ソースアカウント・ソースリージョンからメトリクスを宛先アカウントへ自動複製。中央の運用チームは集約データの完全な所有権を得て、クエリ・アラーム・コンプライアンス・ガバナンスに活用できます。

集約されたメトリクスは CloudWatch メトリクスと OpenTelemetry メトリクスの両方に対応し、Metrics Insights・ダッシュボード・アラーム・Metric Math・異常検出・Metric Streams・PromQL と完全に互換性があります。

⛔ アップデート前の課題
  • メトリクスが各アカウント・リージョンに分散し、統合的な可視化が困難
  • 参照にはロールの引き受けやアカウント切り替えが必要で、データの完全な所有権を持てない
  • メトリクスを単一の場所に保持・管理する仕組みが不足し、コンプライアンス対応が難しい
✅ アップデート後の改善
  • 集約ルールを定義するだけで、宛先アカウントへメトリクスが自動複製
  • 中央運用チームが完全な所有権を持ち、クエリ・アラーム・ガバナンスを一元実施
  • CloudWatch / OpenTelemetry 両方を集約し、既存機能とそのまま連携

ソースアカウントとリージョンのメトリクスが、AWS Organizations の集約ルールに基づいて宛先アカウントへ自動複製され、中央運用チームが統合的に分析できる構成を示しています。

⚙️ 主要機能

1️⃣ AWS Organizations による集約ルールの定義
  • 管理アカウントまたは委任管理者アカウントで集約ルールを作成
  • ソースとなるアカウント・OU・リージョンと、宛先となるアカウント・リージョンを定義
  • 信頼されたアクセス (trusted access) を利用するため AWS Organizations が必須
2️⃣ メトリクスの自動複製とメタデータ付与
  • ソースアカウントに到達したメトリクスが宛先アカウントへ自動コピー
  • ソースのアカウント ID とリージョンがメタデータとして付与され、出所を識別可能
  • データは実際に宛先へ移動 (コピー) されるため、中央チームが完全な所有権を持つ
3️⃣ 幅広いメトリクスタイプと既存機能との互換性
  • CloudWatch メトリクスと OpenTelemetry (OTLP) メトリクスの両方に対応
  • PutMetricData によるカスタムメトリクス、Embedded Metric Format (EMF) もサポート
  • Metrics Insights・ダッシュボード・アラーム・Metric Math・異常検出・Metric Streams・PromQL と完全互換

🚀 設定方法

前提条件: AWS Organizations を有効化 / CloudWatch に対する信頼されたアクセスを有効化 / 管理アカウントまたは委任管理者アカウントで集約ルールを作成する権限を保有。

1
信頼されたアクセスの有効化

管理アカウントで CloudWatch に対する信頼されたアクセスを有効化し、Organizations 全体での集約ルール適用を可能にします。

2
集約ルールの作成

管理 / 委任管理者アカウントで、ソースのアカウント・OU・リージョンと宛先を指定したルールを作成。対象範囲のメトリクスが自動複製されます。

3
集約済みメトリクスの活用

宛先アカウントで Metrics Insights・ダッシュボード・アラーム・異常検出などに活用。メタデータで出所ごとにフィルタリング可能。

💡 メリット

📈 ビジネス面
  • ガバナンス強化: 中央チームが完全な所有権を持ち、組織全体の統制とコンプライアンス対応が容易
  • 運用効率の向上: アカウント切り替えやロール引き受けが不要
  • 既存資産の活用: 既存の CloudWatch 機能をそのまま利用でき学習コストが少ない
⚡ 技術面
  • 自動複製: ルール定義だけで自動複製され、手動収集が不要
  • 幅広い互換性: CloudWatch / OpenTelemetry に対応し PromQL・Metric Math とも連携
  • メタデータ識別: ソースのアカウント ID・リージョン付与で出所を明確化

⚠️ デメリット・制約事項

🚧 制限事項
  • 利用には AWS Organizations が必須
  • 利用可能リージョンが限定されている
  • 最初のコピーは無料、オプションのバックアップリージョン (2 つ目のコピー) は有料
🤔 考慮すべき点
  • データが実際に宛先へ移動 (コピー) されるため、保存場所とアクセス制御を設計時に考慮
  • 集約対象の範囲を適切に設計し、不要なデータの複製を避けることが重要

📌 ユースケース

① 組織全体の統合運用監視

シナリオ: 数十のアカウントと複数リージョンで本番ワークロードを運用する企業が、中央 SRE チームで全体を一元監視したい。

効果: 全アカウント・全リージョンのメトリクスを中央に集約し、単一のダッシュボードで組織全体の健全性を把握。

② コンプライアンスとガバナンスの一元管理

シナリオ: 規制業界の組織が、運用メトリクスを中央で保持し監査やコンプライアンス要件に対応する必要がある。

効果: 完全な所有権により、組織ポリシーに基づく保持・アクセス制御・監査対応を一元的に実施。

③ クロスリージョン障害分析

シナリオ: マルチリージョン構成のアプリで、リージョンをまたいだパフォーマンス劣化や障害の相関分析を行いたい。

効果: 複数リージョンのメトリクスを集約し、Metric Math や異常検出でリージョン横断の相関分析を実施。

🔗 関連サービス・機能

  • AWS Organizations: 集約ルールの定義と信頼されたアクセスに利用する基盤サービス (本機能の利用には必須)
  • CloudWatch Logs Centralization: 同様の仕組みでログをクロスアカウント・クロスリージョンに集約。組み合わせて利用可能
  • CloudWatch クロスアカウントオブザーバビリティ: 単一リージョン内でメトリクス・ログ・トレースを共有する補完機能
  • OpenTelemetry: OTLP メトリクスに対応し、ベンダーニュートラルな計装と組み合わせて集約

📝 まとめ

CloudWatch Metrics Centralization は、マルチアカウント・マルチリージョン環境のメトリクスを単一の宛先アカウントへ自動集約し、中央チームによる統合監視とガバナンスを実現する重要なアップデートです。AWS Organizations を利用している組織では、集約ルールを定義することで運用の可視性とコンプライアンス対応を大幅に強化できます。

まずは 対象範囲を絞った集約ルールで効果を検証し、段階的に展開することを推奨します。
