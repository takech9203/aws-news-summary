AWS Certificate Manager (ACM)

🔐 ACME プロトコルによる
パブリック証明書の自動発行

📅 リリース日
2026 年 7 月 6 日

📌 概要

AWS Certificate Manager (ACM) が ACME (Automated Certificate Management Environment) プロトコル に対応しました。フルマネージドの ACME サーバーエンドポイントをプロビジョニングし、Amazon Trust Services から有効期間 45 日のパブリック TLS 証明書を発行できます。Certbot、cert-manager、acme.sh など ACMEv2 互換クライアントであれば利用可能です。

ACME は RFC 8555 で定義されたインターネット標準プロトコルです。オンプレミスサーバー、Kubernetes クラスター、ハイブリッド環境など、お客様が管理するインフラに対して、公的に信頼される証明書を業界標準の方法で発行できます。

このアップデートは、CA/Browser Forum が 2029 年初頭までに最大有効期間を 47 日に短縮する業界動向に対応するものです。有効期間の短縮により手動管理が現実的でなくなるなか、ACME による自動更新の重要性が増しています。

🔴 アップデート前の課題
  • 自動発行には AWS SDK に依存する RequestCertificate API が必要で、標準 ACME クライアントを利用できなかった
  • お客様管理インフラ (オンプレ、Kubernetes、ハイブリッド) での証明書ライフサイクル自動化が難しかった
  • 秘密鍵を自社システム内で保持したい場合の運用手段が限られていた
  • 発行委任時に DNS 認証情報の配布が必要でガバナンス統制が難しかった
🟢 アップデート後の改善
  • Certbot、cert-manager、acme.sh など標準クライアントで発行・更新を自動化
  • 秘密鍵は ACME クライアント側で生成・保持され、ACM は一切参照しない
  • 管理者が事前にドメイン検証すれば、チームは DNS 認証情報なしで証明書をリクエスト可能
  • ドメインスコープ/ワイルドカードポリシーによる一元ガバナンスと CloudTrail・CloudWatch での可視化

⚙️ 主要機能

🔌 1. マネージド ACME エンドポイント

  • お客様専用の一意な URL を持つ RFC 8555 準拠のマネージド ACME サーバーをプロビジョニング
  • ディレクトリ URL 形式: https://acm-acme-enroll.{region}.api.aws/{endpoint-id}/directory
  • PublicCertificateAuthority を指定して Amazon Trust Services からの公的信頼証明書を有効化
  • 許可する鍵アルゴリズム (ECDSA P-256、RSA 2048、ECDSA P-384) を制限可能

✅ 2. 事前承認方式のドメイン検証

  • PKI 管理者が事前にドメインを検証する永続的なリソースとして構成
  • 標準 ACM DNS 検証と同じ CNAME レコード方式で継続的な検証を ACM に委任
  • ドメインスコープを ExactDomain / Subdomains / Wildcards の 3 つの独立設定で制御
  • アプリケーション所有者はドメイン検証を自ら行わず証明書をリクエスト可能

🔑 3. 外部アカウントバインディング (EAB) による委任

  • ACME クライアントがアカウント登録する際の認証情報を発行
  • 各 EAB は IAM ロールに関連付けられ、acm:RequestCertificate / acm:RevokeCertificate 権限で制御
  • Key ID と MAC キーを生成し、ACME クライアントの kid と hmacKey として使用
  • EAB に有効期限 (MINUTES / HOURS / DAYS) を任意で設定可能

📊 4. 監査と可視化

  • すべての発行・失効操作が AWS CloudTrail に記録
  • AWS/CertificateManager 名前空間に CertificateIssuanceSuccess / CertificateIssuanceFailed メトリクスを発行
  • ACM コンソールの Monitoring タブや Certificates ダッシュボードで発行状況を確認
  • AWS Organizations の Service Control Policy (SCP) が発行時に適用

🔬 技術仕様

ACME 証明書の特性

項目詳細
発行元 CAAmazon Trust Services (公的に信頼される Web PKI 証明書)
有効期間45 日 (標準の ACM パブリック証明書より短い)
秘密鍵ACME クライアント側で生成・保持され、ACM は参照しない
更新ACME クライアントが有効期限前に新しい証明書をリクエスト (ACM マネージド更新は非対応)
失効ACME エンドポイントの revoke-cert URL を通じてクライアントが実行
削除有効期限切れ後、ACM が 1 年で自動削除 (DeleteCertificate でも削除可能)
鍵ペア出所CertificateKeyPairOrigin が ACME として識別される

ACME で利用できない ACM API

ACME で発行した証明書に対しては以下の API はサポートされません。ライフサイクルは ACME クライアントが管理します。

ExportCertificate RevokeCertificate RenewCertificate ResendValidationEmail

🛠️ 設定方法

前提条件

✓ACME エンドポイントを作成・管理する PKI 管理者の IAM 権限
✓証明書発行を許可する IAM ロール (acm:RequestCertificate 権限と信頼ポリシー)。EAB 作成者には iam:PassRole が必要
✓検証対象ドメインの DNS レコードを操作できる権限 (Route 53 利用時はホストゾーン ID)
1

ACME エンドポイントの作成

PKI 管理者が事前承認方式 (PRE_APPROVED) のマネージド ACME エンドポイントを作成します。レスポンスの AcmeEndpointArn を後続操作で使用し、describe-acme-endpoint でディレクトリ URL を取得します。

BashAWS CLI
aws acm create-acme-endpoint \
    --authorization-behavior PRE_APPROVED \
    --contact REQUIRED \
    --certificate-authority '{
        "PublicCertificateAuthority": {
            "AllowedKeyAlgorithms": ["RSA_2048", "EC_prime256v1", "EC_secp384r1"]
        }
    }'
2

ドメイン検証の事前承認

対象ドメインを事前承認し、発行を許可する範囲を指定します。Route 53 のホストゾーン ID を指定すると CNAME が自動プロビジョニングされます。ステータスが VALID になれば発行に利用可能。CNAME が 72 時間以内に確認されない場合は INVALID (TIMED_OUT) に遷移します。

BashAWS CLI
aws acm create-acme-domain-validation \
    --acme-endpoint-arn arn:aws:acm:region:111122223333:acme-endpoint/00000000-0000-0000-0000-000000000000 \
    --domain-name example.com \
    --prevalidation-options '{
        "DnsPrevalidation": {
            "DomainScope": {
                "ExactDomain": "ENABLED",
                "Subdomains": "ENABLED",
                "Wildcards": "DISABLED"
            },
            "HostedZoneId": "Z1234567890"
        }
    }'
3

外部アカウントバインディング (EAB) の作成と配布

発行権限を持つ IAM ロールに紐づく EAB を作成し、get-acme-external-account-binding-credentials で Key ID と MAC キーを取得します。MAC キーは秘密情報として扱い、認可した ACME クライアントにのみ安全に配布します。

BashAWS CLI
aws acm create-acme-external-account-binding \
    --acme-endpoint-arn arn:aws:acm:region:111122223333:acme-endpoint/00000000-0000-0000-0000-000000000000 \
    --role-arn arn:aws:iam::111122223333:role/AcmeIssuanceRole \
    --expiration '{"Value": 7, "Type": "DAYS"}'

aws acm get-acme-external-account-binding-credentials \
    --acme-external-account-binding-arn arn:aws:acm:region:111122223333:acme-endpoint/00000000-0000-0000-0000-000000000000/acme-external-account-binding/22222222-2222-2222-2222-222222222222
4

ACME クライアントでの証明書リクエスト

アプリケーション所有者は、受け取ったディレクトリ URL、Key ID、MAC キーを ACME クライアント (例: Certbot) に設定してアカウントを登録し、事前承認済みドメインの証明書をリクエストします。発行された証明書は標準の ARN を持ち、ACM の証明書インベントリに表示されます。

💡 メリット

📈 ビジネス面
✓業界標準への準拠: CA/Browser Forum の有効期間短縮 (2029 年までに 47 日) に先行対応し、自動更新で運用負荷を抑制
✓ガバナンスの一元化: ドメインスコープやワイルドカードポリシーで統制しつつチームへ安全に委任
✓ベンダーロックイン回避: Certbot や cert-manager をそのまま活用でき、AWS SDK 依存なく自動化
🔧 技術面
✓秘密鍵の非開示: 秘密鍵はクライアント側でのみ生成・保持され、コンプライアンス要件を満たしやすい
✓既存 IAM 統制の再利用: EAB に紐づく IAM ロールで発行・失効、標準 ACM と同じポリシー・条件キー・SCP が適用
✓可観測性: CloudTrail 監査ログと CloudWatch メトリクス、ACM コンソールで発行状況を包括把握

⚠️ デメリット・制約事項

🚫 制限事項
✗ELB、CloudFront、API Gateway などの AWS 統合サービスにバインドできない
✗ACM マネージド更新は適用されず、更新は ACME クライアントが担う
✗ExportCertificate / RevokeCertificate / RenewCertificate / ResendValidationEmail は利用不可
✗ドメイン検証の CNAME はエンドポイントごとに個別に必要
🤔 考慮すべき点
!有効期間 45 日と短いため、確実な自動更新の運用設計が前提
!失効情報確認に OCSP / CRL (http://*.amazontrust.com) への通信が必要な場合あり
!EAB を失効・削除しても既存 ACME アカウントは発行継続。停止には RevokeAcmeAccount などが必要
!CAA レコードで Amazon の発行が拒否されないよう DNS 設定を事前確認

🎯 ユースケース

1. Kubernetes クラスターの証明書自動化

シナリオ: 自社管理の Kubernetes クラスターで稼働するサービスに、公的に信頼される TLS 証明書を自動発行・更新したい。
1. PKI 管理者が ACME エンドポイントと example.com のドメイン検証 (サブドメイン許可) を作成
2. cert-manager 用 IAM ロールと EAB を作成し、Key ID / MAC キーを Kubernetes Secret として配布
3. cert-manager の ACME Issuer にディレクトリ URL と EAB を設定
効果: cert-manager が 45 日有効の証明書を自動発行・更新し、DNS 認証情報をクラスターに渡さず運用できる。

2. オンプレミスサーバーでの秘密鍵保持

シナリオ: 規制要件により秘密鍵を第三者に預けられないオンプレミスの Web サーバーで、パブリック証明書を利用したい。
1. サーバー上の Certbot に ACME ディレクトリ URL と EAB 認証情報を設定
2. 事前承認済みドメインに対して certbot で証明書をリクエスト
3. 秘密鍵はサーバー内で生成・保持し、TLS 終端をサーバー上で実施
効果: 秘密鍵を ACM に渡すことなく、公的に信頼される証明書を取得しコンプライアンス要件を満たせる。

3. 複数チームへの発行委任

シナリオ: 中央の PKI チームがドメインを一元管理しつつ、各アプリケーションチームに証明書発行を委任したい。
1. PKI 管理者がドメインスコープを絞った検証 (ワイルドカード禁止など) を構成
2. チームごとに権限を分離した IAM ロールと EAB を発行 (有効期限付き)
3. 各チームは割り当てられた範囲内でのみ証明書を発行
効果: ドメインごとの発行範囲とポリシーを統制しながら、DNS 認証情報を配布せず発行をセルフサービス化できる。

🔗 関連サービス・機能

  • Amazon Trust Services: 公的に信頼される証明書の認証局
  • ACM (RequestCertificate): AWS 統合サービス向けやマネージド更新が必要な場合の従来方式
  • AWS CloudTrail: 発行・失効操作を監査ログとして記録
  • Amazon CloudWatch: CertificateIssuanceSuccess / CertificateIssuanceFailed メトリクスで監視
  • AWS IAM / AWS Organizations: EAB に紐づくロールと SCP により発行操作を統制
  • cert-manager / Certbot / acme.sh: ライフサイクルを自動化する ACMEv2 互換クライアント

📝 まとめ

ACM の ACME プロトコルサポートは、公的に信頼される証明書のライフサイクルを業界標準ツールで自動化しつつ、PKI 管理者による一元的なガバナンスを実現する重要なアップデートです。CA/Browser Forum による有効期間短縮が迫るなか、オンプレミス・Kubernetes・ハイブリッド環境を運用するお客様は、まずマネージド ACME エンドポイントとドメイン検証を作成し、Certbot や cert-manager での自動更新運用を検証することが推奨されます。
