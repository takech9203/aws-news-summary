Amazon S3 Mountpoint v1.24.0

🪣 Mountpoint for Amazon S3
メモリ使用量コントロール

📅 リリース日: 2026 年 8 月 26 日 | 機能: Memory Usage Controls (--memory-target)

📌 概要

Mountpoint for Amazon S3 がメモリ使用量の上限を制御する機能をサポートしました。 --memory-target で明示的にターゲットを指定する方法と、実行環境 (cgroup のメモリ制限) に基づいて 自動的に安全なデフォルト値を決定する方法の 2 種類が利用できます。 Amazon EKS 上ではコンテナに割り当てられたメモリ量を自動検出し、その範囲内で動作します。

メモリ逼迫時には、I/O の減速、不要バッファの解放、プリフェッチの縮小により、ターゲット内に収まるように動作します。 これにより ML トレーニングや分析ジョブなど、メモリ集約型アプリケーションとの安全な同居が可能になります。

❌ Before: アップデート前の課題
  • メモリ使用量が使用パターンに応じて増加し、上限を設定する手段がなかった
  • メモリ集約型アプリと同居させると、メモリ競合によるパフォーマンス低下や OOM のリスクがあった
  • メモリ制限が厳しいコンテナ環境 (Kubernetes / EKS の Pod など) では、Pod の強制終了を考慮した運用が必要だった
✅ After: アップデート後の改善
  • --memory-target 引数で総メモリ使用量のターゲットを明示的に設定可能に
  • cgroup のメモリ制限に基づく自動検出で、コンテナのメモリバジェット内で安全に動作
  • 逼迫時は I/O 減速・バッファ解放・プリフェッチ縮小でターゲット内に収まり、他アプリのメモリを確保できる

Mountpoint は明示的な指定または cgroup 制限の自動検出によりメモリターゲットを決定し、その予算内で読み取りプリフェッチと書き込みバッファを管理します。 これにより、同一ホスト上のメモリ集約型アプリケーションとの安全な同居が可能になります。

⚡ 主要機能

1️⃣ 明示的なメモリターゲット設定 (--memory-target)
  • 総メモリ使用量のターゲットを MiB 単位で指定できる (最小 512 MiB)
  • 読み取り時のプリフェッチバッファと、書き込み時のアップロードパート保持の両方をカバー
  • ターゲットは保証されたハードリミットではなく、バッファ管理により収まるように動作する目標値
2️⃣ 実行環境に基づく自動検出
  • 未指定時は総メモリ量 (cgroup 制限がある場合はその制限値) の 95% がデフォルトのターゲット
  • Amazon EKS などのコンテナ環境では、コンテナに割り当てられたメモリバジェットを自動検出
  • v1.24.0 では、親スライスから継承された cgroup メモリ制限の検出も修正
3️⃣ メモリ逼迫時の適応動作
  • 逼迫時には I/O 減速・不要バッファの解放・プリフェッチウィンドウの縮小を実施
  • オーバーヘッド (メタデータやファイルハンドル) 用に max(128 MiB, memory_target / 8) を予約し、残りをデータバッファ予算として使用
  • 同時に書き込みオープンできるファイル数がターゲットから導出される上限に制限される (v1.24.0 の破壊的変更)

✍️ 書き込みオープン可能ファイル数の上限

メモリターゲットと書き込みパートサイズから、同時に書き込みオープンできるファイル数の上限が決まります。 上限に達すると、書き込み用の open() は ENOMEM で失敗します。

数式 書き込みオープン上限の計算 
上限 = (memory_target - オーバーヘッド - read_part_size) / write_part_size
メモリターゲットパートサイズ書き込みオープン可能ファイル数
512 MiB8 MiB (デフォルト)47
4 GiB8 MiB (デフォルト)447

上限を引き上げるには、--memory-target を増やすか --write-part-size を減らします。 Mountpoint は起動時にこの上限をログに出力します。

⌨️ 関連する CLI 引数

引数説明
--memory-target総メモリ使用量のターゲット (MiB 単位、最小 512 MiB)
--read-part-size並列読み取りのパートサイズ (デフォルト 8 MiB)
--write-part-size並列書き込みのパートサイズ (デフォルト 8 MiB)

--read-part-size はデータバッファ予算内に収まる必要があります。--memory-target を明示的に指定した場合、 大きすぎるパートサイズは起動時に拒否されます。デフォルトターゲット使用時は、警告とともに自動的に縮小されます。

🛠️ 設定方法

📋 前提条件

✓Mountpoint for Amazon S3 v1.24.0 以降がインストールされていること (GitHub の最新リリースにアップグレード)
✓マウント対象の S3 バケットへの適切な IAM 権限があること
✓コンテナ環境で自動検出を利用する場合、cgroup によるメモリ制限が設定されていること
1
最新バージョンへのアップグレード

現在のバージョンを確認し、v1.24.0 以降でない場合は最新リリースをインストールします。

Bash バージョン確認とインストール (x86_64 Linux の例) 
# 現在のバージョンを確認
mount-s3 --version

# 最新版をダウンロードしてインストール
wget https://s3.amazonaws.com/mountpoint-s3-release/latest/x86_64/mount-s3.rpm
sudo yum install -y ./mount-s3.rpm
2
メモリターゲットを指定してマウント

総メモリ使用量のターゲットを 1024 MiB に設定してマウントします。読み取りプリフェッチと書き込みバッファがこの予算内で管理されます。

Bash 明示的なメモリターゲット指定 
# メモリ使用量のターゲットを 1024 MiB に設定してマウント
mount-s3 --memory-target 1024 amzn-s3-demo-bucket /mnt/s3
3
自動検出に任せる場合

未指定の場合、総メモリ量 (コンテナでは cgroup のメモリ制限値) の 95% を自動的にターゲットとして使用します。EKS の Pod など、メモリ制限が設定されたコンテナ内ではその制限値が自動検出されます。

Bash 自動検出によるマウント 
# 引数を指定せずにマウント (環境の 95% を自動的にターゲットに設定)
mount-s3 amzn-s3-demo-bucket /mnt/s3

💡 メリット

💼 ビジネス面

✓インフラコストの最適化: メモリ集約型ワークロードと同一ホストに安全に同居でき、インスタンスの集約度を高めてコスト削減
✓安定性の向上: OOM による強制終了リスクが低減し、ML トレーニングなど長時間処理の中断を防止
✓運用負荷の軽減: 自動検出により環境ごとのチューニングが不要になり、運用がシンプルに

⚙️ 技術面

✓予測可能なメモリフットプリント: 予算内に収まるため、キャパシティプランニングが容易
✓コンテナネイティブな動作: cgroup 制限の自動検出により Kubernetes / EKS の limits.memory と自然に整合
✓グレースフルな縮退: 逼迫時にはクラッシュではなく、I/O 減速とプリフェッチ縮小で動作を継続

⚠️ デメリット・制約事項

🚫 制限事項

✗メモリターゲットの最小値は 512 MiB であり、それ未満には設定できない
✗ターゲットは保証されたハードリミットではなく、瞬間的に超える可能性がある
✗v1.24.0 以降、同時書き込みオープン数が上限に制限され、超過時は open() が ENOMEM で失敗する (破壊的変更)

🤔 考慮すべき点

⚠ターゲットを小さくしすぎると、プリフェッチ縮小や I/O 減速によりスループットが低下する可能性
⚠多数ファイルの同時書き込みでは、--memory-target の引き上げや --write-part-size の縮小が必要になる場合がある
⚠--read-part-size を大きく設定する場合、データバッファ予算内に収まるかを確認する必要がある

🎯 ユースケース

🧠 ユースケース 1: EKS 上の ML トレーニングジョブとの同居

シナリオ: Amazon EKS 上で S3 のトレーニングデータを Mountpoint 経由で読み込む ML トレーニング Pod を実行。Pod にはメモリ制限があり、トレーニングプロセス自体が大量のメモリを消費する。

YAML Pod のメモリ制限 (Mountpoint はこの制限を自動検出) 
resources:
  limits:
    memory: "16Gi"

効果: コンテナのメモリバジェットを自動検出して予算内で動作するため、OOM による Pod の強制終了を防ぎながらトレーニングを継続できます。

📊 ユースケース 2: 分析ジョブ実行ホストでの明示的なメモリ割り当て

シナリオ: EC2 インスタンス上で Spark などの分析ジョブと Mountpoint を同居させる。分析ジョブに大部分のメモリを割り当てたい。

Bash Mountpoint に 2 GiB のみ割り当て 
mount-s3 --memory-target 2048 amzn-s3-demo-bucket /mnt/data

効果: Mountpoint のメモリ使用量が 2 GiB 程度に抑えられ、分析ジョブが必要とするメモリを確実に確保できます。

📝 ユースケース 3: 多数ファイルの同時書き込みワークロード

シナリオ: ログ集約やバッチ出力など、多数のファイルを同時に S3 へ書き込むワークロードで、書き込みオープン数の上限を確保したい。

Bash メモリターゲット 4 GiB (デフォルトの 8 MiB パートで約 447 ファイルまで同時書き込み可能) 
mount-s3 --memory-target 4096 amzn-s3-demo-bucket /mnt/output

効果: メモリターゲットに応じた書き込みオープン上限を把握した上で運用でき、ENOMEM エラーを回避しながら安定した書き込みが可能になります。

💰 料金 / 🌍 利用可能リージョン

💰 料金

Mountpoint for Amazon S3 はオープンソースのファイルクライアントであり、追加料金なしで利用できます。 S3 の通常の API リクエスト料金 (GET、PUT、LIST など)、ストレージ料金、データ転送料金が適用されます。

🌍 利用可能リージョン

すべての AWS リージョンで利用可能です。 メモリ使用量コントロール機能を利用するには、GitHub から最新リリース (v1.24.0 以降) にアップグレードしてください。
