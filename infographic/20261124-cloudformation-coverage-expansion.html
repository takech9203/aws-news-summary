🧱 206 の新リソースタイプ追加によるリソースカバレッジの包括化

📅 リリース日: 2026 年 11 月 24 日

📋 概要

AWS CloudFormation が 88 サービスにわたる 206 の新リソースタイプのサポートを発表しました。Amazon SageMaker Hub、Amazon Bedrock AgentCore PolicyEngine、Amazon EC2 Snapshot などが含まれ、CloudFormation カバレッジの主要なギャップを解消します。

今回のローンチは AI を活用した新しい内部フレームワークによって実現され、リソースタイプのオンボーディングコストを大幅に削減。IaC (Infrastructure as Code) でカバーできないリソースが残るという長年の課題に、構造的な解決アプローチが示されました。さらに AWS Cloud Control API も全新規タイプに対応し、99 サービス・224 の読み取り専用リソースタイプによる既存リソースの検出・調査も提供されます。

❌ アップデート前の課題

✗一部リソースは CloudFormation 非対応で、コンソールや CLI で個別に作成・管理が必要だった
✗IaC でカバーできないリソースが混在し、構成ドリフトや手作業ミスのリスクが増大、再現性が損なわれていた
✗新サービスのリソースタイプ追加に時間がかかり、IaC への完全な標準化の障壁となっていた

✅ アップデート後の改善

✓88 サービス・206 タイプが CloudFormation テンプレートで宣言的に管理可能に
✓Cloud Control API の統一 CRUDL 操作に対応し、Terraform や Pulumi などサードパーティツールにも恩恵
✓AI 駆動フレームワークでオンボーディングコストが削減され、今後の継続的なカバレッジ拡大が期待できる
✓224 の読み取り専用タイプで既存リソースの検出・調査 (インベントリ把握) が簡素化

AI 駆動の内部フレームワークによってオンボーディングされた新リソースタイプは、CloudFormation テンプレートと Cloud Control API の両方から利用できます。読み取り専用タイプは Cloud Control API 経由で既存リソースの検出・調査に活用できます。

⚡ 主要機能

🆕 1. 206 の新リソースタイプのサポート

  • 88 のサービスにわたり、206 のリソースタイプが CloudFormation テンプレートで新たに利用可能
  • 発表で挙げられた例: Amazon SageMaker Hub、Amazon Bedrock AgentCore PolicyEngine、Amazon EC2 Snapshot
  • CloudFormation カバレッジの主要なギャップを解消し、IaC への標準化を推進

🤖 2. AI 駆動の内部フレームワークによるオンボーディング

  • 新しい AI 活用フレームワークにより、リソースタイプを CloudFormation に対応させる際のコストを大幅に削減
  • 今回の 206 タイプ追加はこのフレームワークによって実現され、今後の継続的なカバレッジ拡大の基盤となる

🔧 3. Cloud Control API の完全対応

  • CloudFormation がサポートするすべての新リソースタイプを Cloud Control API でも利用可能
  • 統一的な Create / Read / Update / Delete / List (CRUDL) 操作でリソースを管理できる

👁️ 4. 224 の読み取り専用リソースタイプ

  • Cloud Control API では、99 サービスにわたる 224 の読み取り専用リソースタイプを追加で提供
  • 既存リソースの検出 (List) と調査 (Read) を簡素化し、インベントリ管理や監査に活用できる

📝 リソースタイプ定義の例: AWS::EC2::Snapshot

新たにサポートされた AWS::EC2::Snapshot の構文です (公式テンプレートリファレンスより)。

YAML AWS::EC2::Snapshot の構文 
Type: AWS::EC2::Snapshot
Properties:
  Description: String        # スナップショットの説明 (任意、変更時は置換)
  VolumeId: String           # 対象 EBS ボリュームの ID (必須、変更時は置換)
  Tags:                      # タグ (任意、中断なしで更新可能)
    - Key: String
      Value: String

Fn::GetAtt で SnapshotId、Arn、Encrypted、State、StorageTier、VolumeSize などの属性を取得できます。

🛠️ 設定方法

✅ 前提条件

  • AWS アカウントと、対象リソースを操作できる IAM 権限
  • AWS CLI または CloudFormation コンソールへのアクセス
  • 利用したいリソースタイプが リソースおよびプロパティタイプのリファレンス に掲載されていることの確認
1

新リソースタイプを含むテンプレートを作成

YAML template.yaml 
AWSTemplateFormatVersion: "2010-09-09"
Resources:
  MySnapshot:
    Type: AWS::EC2::Snapshot
    Properties:
      VolumeId: vol-0123456789abcdef0
      Description: Managed by CloudFormation
Outputs:
  SnapshotId:
    Value: !GetAtt MySnapshot.SnapshotId

既存 EBS ボリュームのスナップショットを IaC として定義し、スナップショット ID を出力します。

2

スタックをデプロイ

Bash CloudFormation スタックのデプロイ 
aws cloudformation deploy \
  --template-file template.yaml \
  --stack-name ebs-snapshot-stack

スナップショットの作成・更新・削除がスタックのライフサイクルで管理されるようになります。

3

Cloud Control API で同じリソースタイプを操作 (任意)

Bash Cloud Control API での操作 
# リソースの一覧を取得
aws cloudcontrol list-resources --type-name AWS::EC2::Snapshot

# 特定リソースの詳細を取得
aws cloudcontrol get-resource \
  --type-name AWS::EC2::Snapshot \
  --identifier snap-0123456789abcdef0

統一的な CRUDL 操作で同じリソースタイプを一覧表示・取得できます。CloudFormation がサポートするすべての新リソースタイプが Cloud Control API でも利用できます。

✓エコシステムへの波及: Cloud Control API 基盤のサードパーティ IaC ツールでも同じリソースを扱える

⚠️ デメリット・制約事項

🚧 制限事項

⚠読み取り専用の 224 タイプは検出・調査 (Read / List) 用で、作成・更新・削除には利用できない
⚠各リソースタイプは、基盤となるサービスが提供されているリージョンでのみ利用可能
⚠AI 駆動の内部フレームワークは AWS 内部の仕組みで、ユーザーが直接利用・制御することはできない

🤔 考慮すべき点

→既存の手動管理リソースの移行には、CloudFormation のリソースインポート機能の利用を検討する
→リソースタイプごとにプロパティや更新時の動作 (置換の有無など) が異なるため、テンプレートリファレンスで事前確認を推奨
→206 タイプの具体的な一覧は、リソースおよびプロパティタイプのリファレンスで確認が必要

🎯 ユースケース

📸 ユースケース 1: EBS スナップショットのコード管理

シナリオ: データ移行やゴールデンイメージ作成の際に、EBS スナップショットの作成を手順書ベースの手作業で行っており、作業の再現性と追跡性に課題がある。

YAML 実装例 
Resources:
  MigrationSnapshot:
    Type: AWS::EC2::Snapshot
    Properties:
      VolumeId: !Ref SourceVolume
      Description: Pre-migration snapshot
      Tags:
        - Key: Purpose
          Value: migration
✅ 効果: スナップショット作成がテンプレートとして定義され、レビュー・バージョン管理・再実行が可能に。スタック削除時のクリーンアップも自動化できる。

🤖 ユースケース 2: 生成 AI ワークロードの IaC 化

シナリオ: Amazon Bedrock AgentCore や Amazon SageMaker を活用した生成 AI 基盤を構築しており、ポリシーエンジンやモデルハブなどの周辺リソースだけが手動管理として残っている。

シナリオ: セキュリティチームが複数アカウントにまたがる既存リソースの棚卸しを行いたいが、サービスごとに異なる API を呼び分けるスクリプトの維持負担が大きい。

Bash 統一 API でのリソース列挙 
# 読み取り専用タイプを含む統一 API でリソースを列挙

aws cloudcontrol get-resource \
  --type-name <リソースタイプ名> --identifier <識別子>
✅ 効果: 99 サービス・224 の読み取り専用タイプを含む統一インターフェースでリソースを検出・調査でき、インベントリスクリプトの実装・保守コストを削減できる。
