🧬 AWS HealthOmics
Nextflow ワークフロー向けリソースフォールバック順序

AWS HealthOmics 📅 リリース日: 2026 年 10 月 14 日

📝 概要

AWS HealthOmics が、Nextflow ワークフローのタスクに対する「リソースフォールバック」ディレクティブ omicsResourceFallbackOrder のサポートを発表しました。 優先する アクセラレーター GPU タイプを順序付きリストとして定義でき、 最終フォールバック先として CPU インスタンスも指定可能です。

優先アクセラレーターのキャパシティが確保できない場合、HealthOmics はランを再送信することなく、 フォールバック順序に従って次のリソースプロファイルへ自動的に移行します。 各プロファイルには個別のタイムアウトを設定でき、アクセラレーターを検索する時間を制御できます。 本機能は 2026 年 9 月に WDL 向けに提供開始されたディレクティブを Nextflow に拡張するものです。

❌ アップデート前の課題

✗単一のアクセラレータータイプしか指定できず、キャパシティ不足時は INSTANCE_RESERVATION_FAILED でタスクが失敗
✗ラン失敗のたびに、原因診断・ワークフロー定義修正・ラン再送信という手動対応が必要
✗人気の高い GPU (例: NVIDIA L40S) のキャパシティ変動により、本番パイプラインの安定稼働が困難

✅ アップデート後の改善

✓アクセラレーターの優先順位リストを定義でき、キャパシティ不足時には再送信なしで次の候補へ自動移行
✓プロファイルごとに待機タイムアウト omicsResourceWaitTimeoutInMin を設定可能
✓最終フォールバックとして CPU プロファイルを含め、インスタンス確保の可能性を最大化
✓環境変数 AWS_HEALTHOMICS_RESOURCE_TYPE で GPU 用と CPU 用のコマンドを分岐可能

HealthOmics はフォールバック順序の先頭プロファイルからキャパシティの確保を試行し、 タイムアウトに達すると次のプロファイルへ自動的に移行します。 すべてのプロファイルが失敗した場合のみタスクが失敗します。

⚙️ 主要機能

1️⃣ 順序付きリソースプロファイルの定義

アクセラレーターおよび CPU のリソースプロファイルを優先順に最大 10 件まで定義。 各プロファイルには acceleratorType、acceleratorCount、 cpus、memory、 omicsResourceWaitTimeoutInMin の 5 フィールドを個別に設定可能。 container や errorStrategy などの他のディレクティブは全プロファイルで共有。

2️⃣ プロファイルごとの待機タイムアウト制御

デフォルトは単一 GPU 20 分、マルチ GPU バンドル 30 分。短いタイムアウトはフォールバックを素早く進め、 長いタイムアウトは優先アクセラレーターの確保確率を高める。タイムアウト時はタスク失敗ではなく次のプロファイルへ移行。

3️⃣ CPU プロファイルへの最終フォールバック

acceleratorType を省略したプロファイルは CPU プロファイルとして扱われ、 リストの最後に 1 つだけ配置可能。CPU プロファイルにはキャパシティ制約がないため、 インスタンス確保の可能性が大幅に向上。

4️⃣ 実行時のリソースタイプ判別

タスクコンテナに環境変数 AWS_HEALTHOMICS_RESOURCE_TYPE が設定される (値の例: nvidia-l40s、cpu)。 GPU 用と CPU 用でコードパスが異なる場合に、スクリプト内でコマンドを分岐できる。

5️⃣ 柔軟な設定場所

process 定義内のディレクティブ、または nextflow.config の process スコープ (トップレベル、withName、withLabel セレクター) で設定可能。 適用優先度は config のセレクター > process 定義内 > config のトップレベル。

🔬 技術仕様

📋 プロファイルのフィールド仕様 (Nextflow)

フィールド型省略時のデフォルト備考
acceleratorType String 省略すると CPU プロファイル サポートされる 7 種類のアクセラレータータイプのいずれか。空文字列は不可
acceleratorCount Integer - acceleratorType とセットで指定必須。最大 4
cpus Integer / Float / String process の cpus、未設定なら GPU インスタンスタイプのデフォルト 最大 192 vCPU
memory String / Nextflow メモリ値 process の memory、未設定なら GPU インスタンスタイプのデフォルト 単位は B、KB、MB、GB、TB (GiB、MiB は不可)。最大 1,536 GiB
omicsResourceWaitTimeoutInMin Integer 単一 GPU: 20 分、マルチ GPU バンドル: 30 分 上限なし。CPU プロファイルには不要

✅ 検証ルール (主要なもの)

項目内容
排他制約omicsResourceFallbackOrder 使用時は、トップレベルの acceleratorType などの個別リソースディレクティブとの併用は警告対象
プロファイル数1 タスクあたり最大 10 プロファイル。空リスト・空プロファイルは不可
CPU プロファイル最大 1 つ、かつリストの最後に配置する必要がある
リージョン非対応ワークフローのリージョンで未サポートのアクセラレータータイプはスケジューリング時にスキップされ、ランタイムログに警告が出力される
全プロファイル失敗時タスクは ALL_PROFILES_INSTANCE_RESERVATION_FAILED で失敗。errorStrategy と maxRetries に従ってリトライされ、リトライは先頭プロファイルから再開
リトライとの関係OOM やサービスエラーによるリトライは、確保済みの現在のプロファイル内で実行され、次のプロファイルには進まない

💻 Nextflow での設定例

Groovy process 定義内でのフォールバック設定 
process ALIGN {
    container 'my-registry/align-multi-arch:latest'
    errorStrategy 'retry'
    maxRetries 2

    omicsResourceFallbackOrder([
        [acceleratorType: 'nvidia-l40s', acceleratorCount: 1, cpus: 8, memory: '32 GB',
         omicsResourceWaitTimeoutInMin: 45],
        [acceleratorType: 'nvidia-l4', acceleratorCount: 1, cpus: 8, memory: '32 GB'],
        [cpus: 32, memory: '128 GB']
    ])

    script:
    """
    # 割り当てられたリソースタイプに応じてコマンドを分岐
    if [ "\$AWS_HEALTHOMICS_RESOURCE_TYPE" = "cpu" ]; then
      sentieon bwa mem -t \$(nproc) ${reference} ${fastq}
    else
      pbrun fq2bam --ref ${reference} --in-fq ${fastq}
    fi
    """
}

最初に nvidia-l40s を最大 45 分間待機して確保を試行し、次に nvidia-l4 (デフォルトタイムアウト)、最後に CPU のみのプロファイル (32 vCPU、128 GB) へフォールバックします。

ステップ 1: ワークフロー定義にディレクティブを追加

process 定義内にメソッド呼び出し形式 (括弧付き) で記述するか、 nextflow.config で代入形式 (=) により設定します。

Groovy nextflow.config でのラベル単位の設定 
process {
    withLabel: 'gpu_align' {
        omicsResourceFallbackOrder = [
            [acceleratorType: 'nvidia-l40s', acceleratorCount: 1, cpus: 8, memory: '32 GB'],
            [cpus: 32, memory: '128 GB']
        ]
    }
}

ステップ 2: ワークフローを作成または更新

Bash HealthOmics ワークフローの作成 
aws omics create-workflow \
  --name "my-nextflow-workflow" \
  --engine NEXTFLOW \
  --definition-zip fileb://workflow.zip

Nextflow の場合、検証ルール違反はワークフロー作成を拒否せず、ステータスメッセージに報告され、不正な値はタスク実行時に失敗します。

ステップ 3: ランを開始して動作を確認

Bash ランの開始 
aws omics start-run \

  --role-arn <role-arn> \

💡 メリット

💼 ビジネス面

✓本番パイプラインの安定稼働: GPU キャパシティの変動に起因するラン失敗が減り、臨床・研究パイプラインの SLA 遵守が容易になる
✓運用コストの削減: 失敗したランの診断と再送信という手動オペレーションが不要になり、研究者やバイオインフォマティシャンが本来の業務に集中できる
✓スループットの向上: キャパシティ待ちで停滞せず代替リソースで処理を継続でき、解析全体の所要時間を短縮できる

🔧 技術面

✓宣言的なフォールバック制御: ワークフロー定義のみで優先順位とタイムアウトを制御でき、外部のリトライ機構やカスタムスクリプトが不要
✓プロファイルごとの細かな制御: アクセラレーターごとに待機時間、vCPU、メモリを個別に調整できる
✓環境変数によるコード分岐: AWS_HEALTHOMICS_RESOURCE_TYPE により、単一のワークフロー定義で GPU / CPU 両対応のタスクを実装できる

⚠️ デメリット・制約事項

🚧 制限事項

  • 1 タスクあたりのプロファイル数は最大 10 件
  • CPU プロファイルは最大 1 つで、リストの最後に配置する必要がある
  • memory の単位は B、KB、MB、GB、TB のみで、GiB や MiB は使用できない (WDL とは異なる)
  • インスタンスタイプ名 (例: omics.g6e.4xlarge) をリソース値として指定することはできない
  • CWL ワークフローは未対応 (サポート予定)
  • マルチインスタンスファミリーにまたがるバンドルタイプ (例: nvidia-t4-a10g-l4) のフォールバック順序内での使用は非推奨

🤔 考慮すべき点

  • GPU から CPU へフォールバックする場合、コンテナイメージが両方のコードパスのツールを含む必要がある (マルチアーキテクチャイメージの準備が必要)
  • ${task.cpus} と ${task.memory} はプロセスレベルの値を示し、実際に実行されたプロファイルのリソース値ではない点に注意が必要
  • プロファイルで省略したフィールドは前のプロファイルの値を継承せず、ドキュメント記載のデフォルト値が適用される
  • タイムアウトを短くしすぎると優先アクセラレーターを確保できる確率が下がる。推奨最小値 (単一 GPU: 20 分、マルチ GPU: 30 分) 未満の値は警告の対象となる
  • フォールバック先のリソースによって処理時間と課金額が変動するため、CPU フォールバック時の実行時間を事前に検証しておくことが望ましい

🎯 ユースケース

🧪 ユースケース 1: 高性能 GPU 優先のアライメント処理

シナリオ: NVIDIA Parabricks を使用したゲノムアライメントで、最新の L40S GPU を優先しつつ、キャパシティ不足時には L4 GPU で処理を継続したい。

Groovy実装例
omicsResourceFallbackOrder([
    [acceleratorType: 'nvidia-l40s', acceleratorCount: 1, cpus: 8, memory: '32 GB',
     omicsResourceWaitTimeoutInMin: 60],
    [acceleratorType: 'nvidia-l4', acceleratorCount: 1, cpus: 8, memory: '32 GB',
     omicsResourceWaitTimeoutInMin: 20]
])
✨ 効果: 優先 GPU には長めの待機時間を設定して確保確率を高めつつ、確保できない場合も代替 GPU で自動的に処理を継続でき、ランの失敗と再送信を回避できる。
🧬 ユースケース 2: GPU / CPU 両対応ツールによる確実な実行

シナリオ: GPU 版 (Parabricks) と CPU 版 (Sentieon) の両方のツールを持つ変異検出パイプラインで、GPU 不足時にも必ず処理を完了させたい。

Groovy実装例
process VARIANT_CALL {
    container 'my-registry/variant-multi:latest'

    omicsResourceFallbackOrder([
        [acceleratorType: 'nvidia-l4', acceleratorCount: 1, cpus: 8, memory: '32 GB'],
        [cpus: 48, memory: '192 GB']
    ])

    script:
    """
    if [ "\$AWS_HEALTHOMICS_RESOURCE_TYPE" = "cpu" ]; then
      run-cpu-variant-caller --threads \$(nproc)
    else
      run-gpu-variant-caller
    fi
    """
}
✨ 効果: CPU プロファイルにはキャパシティ制約がないため、タスクが確実にインスタンスを確保でき、締め切りのある解析ジョブを時間内に完了できる。
⚙️ ユースケース 3: config ファイルによるラベル単位の一括設定

シナリオ: nf-core 由来のワークフローで、ソースコードを変更せずに GPU タスク全体へフォールバック設定を適用したい。

Groovynextflow.config
// nextflow.config
process {
    withLabel: 'gpu' {
        omicsResourceFallbackOrder = [
            [acceleratorType: 'nvidia-l40s', acceleratorCount: 1, cpus: 8, memory: '32 GB'],
            [acceleratorType: 'nvidia-l4', acceleratorCount: 1, cpus: 8, memory: '32 GB'],
            [cpus: 32, memory: '128 GB']
        ]
    }
}
✨ 効果: ワークフロー本体を変更せずに config ファイルのみでフォールバック戦略を適用でき、コミュニティパイプラインの保守性を維持したまま HealthOmics 上での実行信頼性を高められる。

💰 料金

リソースフォールバック機能自体に追加料金はありません。 AWS HealthOmics のワークフロー実行では、タスクが実際に使用したコンピューティングリソース (インスタンスタイプ) と ラン保存容量に基づいて課金されます。フォールバックにより実際に確保されたプロファイル (GPU または CPU インスタンス) に応じた料金が適用されるため、フォールバック先によってタスク単価と実行時間が変動する点に留意してください。

詳細は AWS HealthOmics の料金ページを参照してください。

🔗 関連サービス・機能

🧬 AWS HealthOmics ワークフロー (WDL)

本ディレクティブは 2026 年 9 月に WDL 向けに先行提供されており、今回 Nextflow に拡張された。WDL では cpu / GiB 表記を使用するなど構文に差異がある。

🎮 HealthOmics タスクアクセラレーター

📊 Amazon CloudWatch Logs

アクセラレーターのスキップやフォールバックの発生をランタイムログで確認できる。

📌 まとめ

Nextflow ワークフローでも omicsResourceFallbackOrder ディレクティブが利用可能になり、 GPU キャパシティ不足によるラン失敗を自動フォールバックで回避できるようになりました。 GPU を使用する本番パイプラインを HealthOmics で運用しているチームは、優先アクセラレーターの順序と待機タイムアウトを定義し、 可能であれば CPU プロファイルを最終フォールバックとして追加することを推奨します。 GPU / CPU 両対応のマルチアーキテクチャコンテナイメージと環境変数 AWS_HEALTHOMICS_RESOURCE_TYPE による分岐を組み合わせることで、実行信頼性を大きく高められます。
