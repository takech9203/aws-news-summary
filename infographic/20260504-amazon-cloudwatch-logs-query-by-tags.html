Amazon CloudWatch Logs

CloudWatch Logs Insights - タグによるロググループクエリ

タグベースでロググループを動的に選択し、横断的なログ分析を実現

2026-05-04

📋 概要

Amazon CloudWatch Logs Insights のクエリ言語が拡張され、ロググループに付与されたタグ (キーバリューペア) を使用してクエリを実行できるようになりました。これにより、ロググループ名を個別に指定することなく、共通のタグを持つロググループ全体に対してログ分析を実行できます。

タグはロググループに割り当てるキーバリューペアで、Environment: Production、Application: PaymentService のような形でリソースを分類するために使用されます。

BEFORE - アップデート前の課題

  • クエリ実行時にロググループ名を個別に明示的に指定する必要があった
  • ロググループ増加のたびにクエリ対象リストを手動更新する運用負荷
  • 横断分析には対象ロググループの事前把握と列挙が必要だった

AFTER - アップデート後の改善

  • タグ指定だけで共通タグを持つ全ロググループに対してクエリ実行可能
  • タグの追加/削除でクエリ結果が自動更新、手動メンテナンス不要
  • 環境の成長に伴う運用オーバーヘッドが大幅に削減

🏗️ アーキテクチャ図

タグ Environment: Production を指定してクエリを実行すると、該当タグを持つすべてのロググループが自動的にクエリ対象となり、統合された結果が返されます。

⚡ 主要機能

🏷️ タグベースのロググループ選択

  • ロググループに付与されたタグのキーと値を条件としてクエリ対象を指定可能
  • 複数のタグ条件を組み合わせたフィルタリングに対応
  • 既存のロググループ名指定、データソース指定、ファセット指定と併用可能

🔄 動的なクエリ対象の更新

  • ロググループにタグが追加されると、次回クエリ実行時から自動的に対象に含まれる
  • タグが削除されると、そのロググループはクエリ対象から自動的に除外される
  • クエリ定義の変更なしに、環境の変化に追従

🔗 既存のクエリ手法との統合

以下の 4 つの指定方法を組み合わせて柔軟にクエリ対象を選択:

  • ロググループ名による指定 (従来方式)
  • データソースによる指定
  • ファセットによる指定
  • タグによる指定 (今回追加)

🔧 技術仕様

クエリ対象指定方法の比較

指定方法 説明 ユースケース
ロググループ名 個別のロググループ名を明示的に指定 特定のロググループのみを対象とする場合
データソース データソースの種類で指定 特定のデータソース種別のログ分析
ファセット ファセット属性で指定 属性ベースのフィルタリング
タグ キーバリューペアで指定 環境、アプリケーション、チーム単位の横断分析

logs:StartQuery
logs:GetQueryResults
logs:ListLogGroups
tag:GetResources

📝 設定方法

ステップ 1: ロググループにタグを付与

Bash タグの付与 
aws logs tag-resource \
  --resource-arn arn:aws:logs:ap-northeast-1:123456789012:log-group:/aws/lambda/my-function \
  --tags Environment=Production,Application=PaymentService,Owner=TeamA

ステップ 2: タグを使用してクエリを実行

Bash タグベースクエリの実行 
aws logs start-query \
  --log-group-tags '[{"key":"Environment","values":["Production"]}]' \
  --start-time $(date -d '1 hour ago' +%s) \
  --end-time $(date +%s) \
  --query-string 'fields @timestamp, @message | filter @message like /ERROR/ | sort @timestamp desc | limit 20'

ステップ 3: クエリ結果を取得

Bash 結果の取得 
aws logs get-query-results \
  --query-id "12345678-1234-1234-1234-123456789012"

🎯 ユースケース

1. 本番環境の横断的なエラー監視

本番環境で稼働する全マイクロサービスのエラーログを一括で監視したい。サービスは頻繁に追加・廃止される。

CloudWatch Logs Insights 
fields @timestamp, @message, @logStream
| filter @message like /ERROR|CRITICAL/
| sort @timestamp desc
| limit 100

新しいマイクロサービスが追加されても Environment: Production タグを付与するだけでモニタリング対象に自動追加

2. チーム別のログ分析

各開発チームが担当するサービスのログを、チームメンバーが簡単に横断検索したい。

CloudWatch Logs Insights 
fields @timestamp, @message, @logStream
| filter @message like /latency/
| stats avg(latency) as avg_latency by bin(5m)

チームが新しいサービスをデプロイする際に Owner タグを設定するだけで既存ダッシュボードに自動的に含まれる

3. コスト配分単位でのログ分析

AWS のコスト配分タグと連動し、プロジェクト単位でのログ使用量やエラー傾向を分析したい。

CloudWatch Logs Insights 
fields @timestamp, @message
| stats count(*) as log_count by bin(1h)

コスト配分レポートと同じタグ体系でログ分析が可能になり、プロジェクト単位でのログコスト最適化を支援

✅ メリット

💼 ビジネス面

  • 運用コストの削減: クエリ定義の手動更新作業が不要に
  • 環境拡大への自動対応: タグ付与だけで既存クエリが新しいロググループを含む
  • チーム間コラボレーション改善: チーム名タグでの横断分析が容易に

🔧 技術面

  • クエリ管理の簡素化: ロググループ名のハードコーディングが不要
  • 動的なスコーピング: IaC との親和性が高い
  • 柔軟なフィルタリング: 多次元でのログ分類と横断分析が可能

⚠️ 制約事項・注意点

  • タグ変更がクエリ結果に反映されるタイミングの詳細は公式ドキュメントでの確認が必要
  • ロググループに付与できるタグの上限は 50 個 (既存の CloudWatch Logs 制限)
  • タグのキーは最大 128 文字、値は最大 256 文字
  • タグベースクエリを効果的に活用するには、組織全体で一貫したタグ付け戦略の策定が必要
  • タグが未設定のロググループはタグベースクエリの対象外 (既存ロググループへのタグ付与作業が発生する可能性)
  • tag:GetResources の API コール制限に注意 (大量のロググループがある場合)
