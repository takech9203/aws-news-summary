Amazon API Gateway

🔐 REST API のネイティブ JWT オーソライザー

OIDC / OAuth 2.0 の JWT をコードなしでゲートウェイ内検証 📅 2026 年 11 月 17 日

📝 概要

Amazon API Gateway の REST API で、JSON Web Token (JWT) をゲートウェイ内で直接検証する新しいオーソライザータイプ「JWT オーソライザー」が利用可能になりました。OpenID Connect (OIDC) または OAuth 2.0 に対応した任意の ID プロバイダー (Amazon Cognito ユーザープールを含む) が発行するトークンを、コードを書かずに設定だけで検証できます。

これまで REST API で Amazon Cognito 以外の ID プロバイダーのトークンを検証するには Lambda オーソライザーの実装と運用が必要でした。今回のアップデートにより、マシン間 (M2M) API、モバイル / Web バックエンド、複数の ID プロバイダーのトークンを受け入れるマルチテナント API の認可を簡素化できます。

😓 Before: アップデート前の課題
✗Cognito 以外の OIDC / OAuth 2.0 IdP のトークン検証には Lambda オーソライザーの実装・運用が必要
✗署名検証・有効期限チェックなどの定型ロジックを自前で開発し、ライブラリ更新やキーローテーションにも対応し続ける必要
✗Lambda オーソライザー呼び出しに伴うレイテンシーとコストが発生
🎉 After: アップデート後の改善
✓トークン検証をコードではなく設定として定義でき、Lambda オーソライザーの開発・運用が不要
✓複数の発行者・オーディエンス・署名アルゴリズム・追加クレームを宣言的に設定し、API Gateway がリクエストごとに検証
✓1 つのオーソライザーを複数メソッドで共有しつつ、メソッドごとに異なる認可スコープを要求可能

    participant G as 🔌 API Gateway JWT オーソライザー
    participant I as 🔑 ID プロバイダー OIDC

    C->>I: 認証してトークンを取得

    Note over G: 署名・発行者・オーディエンス

    I-->>G: 署名キー

クライアントが ID プロバイダーから取得した JWT を API Gateway がゲートウェイ内で直接検証し、検証に成功したリクエストのみバックエンドに転送するフローです。Lambda オーソライザーを介さずにトークン検証が完結します。

⚡ 主要機能

🛡️ ゲートウェイ内でのネイティブ JWT 検証

設定したヘッダー (アイデンティティソース) からトークンを読み取り、リクエストごとに検証を実行。トークンの iss クレームに一致する発行者設定を検索し、未設定の発行者からのトークンは拒否。OIDC ディスカバリードキュメント経由で公開署名キーを取得して署名を検証します。

🔧 柔軟な検証ルールの設定

複数の発行者を 1 つのオーソライザーに定義し、発行者ごとに受け入れるオーディエンス (aud クレーム) を指定可能。許可する署名アルゴリズムを defaultAlgorithms で指定し、追加クレーム (additionalClaims) でクレーム名・期待値・必須かどうかを条件として設定できます。

🎯 メソッドごとのスコープ制御

1 つのオーソライザーを多数のメソッドにアタッチし、メソッドごとに異なる認可スコープを要求可能。トークンの scope または scp クレームに、メソッドが要求するスコープの少なくとも 1 つが含まれるかを検証します。

🔗 クレームのバックエンド連携

検証済みトークンのクレームを $context.authorizer.claims としてバックエンド統合に引き渡し可能です。

🔍 検証フローの詳細

ドキュメントによると、API Gateway は以下の手順でリクエストを認可します。

  1. アイデンティティソースとして設定したリクエストヘッダーからトークンを読み取る
  2. トークンの iss クレームに一致する発行者設定を特定する
  3. 発行者の OIDC ディスカバリードキュメントから取得した公開署名キーで署名を検証する
  4. aud クレーム (Cognito アクセストークンの場合は client_id) を設定済みオーディエンスと照合し、exp、nbf、iat を現在時刻と照合する (60 秒のクロックスキューを許容)
  5. 発行者に設定した追加クレームルールを評価する
  6. メソッドがスコープを要求する場合、scope または scp クレームを検証する

🛠️ 設定方法

✅ 前提条件

  1. 既存の REST API (リージョナル、エッジ最適化、プライベートのいずれか)
  2. OIDC / OAuth 2.0 準拠の ID プロバイダー (発行者 URL、オーディエンスを把握していること)
  3. ID プロバイダーの OIDC ディスカバリードキュメント (/.well-known/openid-configuration) とキーセットがパブリックインターネットから到達可能であること

ステップ 1: JWT オーソライザーを作成する

Bash AWS CLI でオーソライザーを作成 
aws apigateway create-authorizer \
  --rest-api-id abcde12345 \
  --name my-jwt-authorizer \
  --type JWT \
  --identity-source method.request.header.Authorization \
  --jwt-configuration '{
    "issuers": [
      {
        "issuer": "https://idp.example.com",
        "audiences": ["my-api"]
      }
    ],
    "defaultAlgorithms": ["RS256"]
  }'

identity-source でトークンを読み取るヘッダーを指定し、jwt-configuration で信頼する発行者、受け入れるオーディエンス、許可する署名アルゴリズムを宣言します。

ステップ 2: メソッドにオーソライザーをアタッチする

マネジメントコンソールまたは API でメソッドの認可設定に作成した JWT オーソライザーを指定します。必要に応じてメソッドごとに認可スコープを設定すると、トークンの scope / scp クレームにそのスコープが含まれているかどうかが検証されます。

ステップ 3: デプロイして動作を確認する

Bash ステージへのデプロイ 
aws apigateway create-deployment \
  --rest-api-id abcde12345 \
  --stage-name prod

有効なトークンでは 2xx、トークン欠落・不正では 401、スコープ不足では 403 が返ることを確認します。

💡 メリット

💼 ビジネス面

✓運用負荷の削減: トークン検証用の Lambda オーソライザーのコード開発、ライブラリ更新、監視が不要になり、運用コストを削減
✓導入スピードの向上: 設定のみで外部 ID プロバイダーとの連携を実現でき、API の公開までの期間を短縮
✓マルチテナント対応の簡素化: 複数の ID プロバイダーのトークンを 1 つのオーソライザーで受け入れられ、テナントごとに異なる IdP を使う SaaS アーキテクチャに適合

⚙️ 技術面

✓宣言的なセキュリティ設定: 発行者、オーディエンス、署名アルゴリズム、追加クレームを設定として管理でき、IaC による統制が容易
✓堅牢な検証: 署名、発行者、オーディエンス、有効期限、クレーム、スコープをマネージドに検証し、HMAC 系アルゴリズムや alg: none のトークンを拒否
✓メソッド単位の細かな認可: 1 つのオーソライザーを共有しつつ、メソッドごとに異なるスコープを要求可能

⚠️ デメリット・制約事項

🚧 制限事項

✗対応する署名アルゴリズムは RS256 / RS384 / RS512 / ES256 / ES384 / ES512 のみで、HS256 などの共有鍵 (HMAC) 方式は利用できない
✗ID プロバイダーの OIDC ディスカバリードキュメントとキーセットは、プライベート API の場合でもパブリックインターネットから到達可能である必要がある
✗JWT オーソライザーで評価できない独自の認可ロジック (外部データベース参照など) が必要な場合は、引き続き Lambda オーソライザーが必要

🤔 考慮すべき点

⚠Cognito ユーザープールのみを使用し、プール内の任意のアプリクライアントのトークンを受け入れたい場合は、クライアント ID を列挙せずに済む既存の Cognito ユーザープールオーソライザーも選択肢
⚠既存の Lambda オーソライザーから移行する場合は、カスタムロジックが JWT オーソライザーの設定 (オーディエンス、追加クレーム、スコープ) で表現できるかを事前に確認
⚠トークンの時刻検証には 60 秒のクロックスキューが許容される点を踏まえてテストを設計

🎯 ユースケース

1️⃣ マシン間 (M2M) API の認可

シナリオ: 社内マイクロサービスやパートナーシステムが、OAuth 2.0 のクライアントクレデンシャルフローで取得したアクセストークンを使って REST API を呼び出す。

JSON実装例
{
  "issuers": [
    {
      "issuer": "https://auth.example.com",
      "audiences": ["orders-api"]
    }
  ],
  "defaultAlgorithms": ["RS256"]
}
✨ 効果: Lambda オーソライザーを実装せずにサービス間認可を実現でき、トークン検証の実装差異による脆弱性リスクを低減できる。
2️⃣ 複数 ID プロバイダーを受け入れるマルチテナント API

シナリオ: SaaS プロバイダーが、テナントごとに異なる OIDC プロバイダー (Amazon Cognito、外部 IdP など) が発行するトークンを 1 つの API で受け入れる。

JSON実装例
{
  "issuers": [
    {
      "issuer": "https://cognito-idp.ap-northeast-1.amazonaws.com/{user-pool-id}",
      "audiences": ["tenant-a-client"]
    },
    {
      "issuer": "https://idp.tenant-b.example.com",
      "audiences": ["tenant-b-api"],
      "additionalClaims": [
        { "claimName": "tenant", "format": "SINGLE_STRING", "required": true, "expectedValues": ["tenant-b"] }
      ]
    }
  ],
  "defaultAlgorithms": ["RS256", "ES256"]
}
✨ 効果: 発行者ごとの検証ルールを 1 つのオーソライザーに集約し、テナント追加時も設定変更だけで対応できる。
3️⃣ メソッドごとのスコープによる権限分離

シナリオ: モバイル / Web バックエンドで、読み取り系メソッドには orders/read、書き込み系メソッドには orders/write スコープを要求する。

📖 GET /orders
orders/read
✏️ POST /orders
orders/write
✨ 効果: 同一のオーソライザーを共有しながらメソッド単位で最小権限を実現でき、トークンのスコープ不足は 403 で拒否される。

🔗 関連サービス・機能

👥 Amazon Cognito

ユーザープールは OIDC 発行者として JWT オーソライザーで利用可能。プール内の任意のアプリクライアントを受け入れる場合は Cognito ユーザープールオーソライザーも選択肢。

🔌 API Gateway HTTP API

HTTP API では以前から JWT オーソライザーをサポートしており、今回のアップデートで REST API でも同等の機能が利用可能に。

⚡ AWS Lambda (Lambda オーソライザー)

JWT で表現できないカスタム認可ロジックが必要な場合に引き続き使用。

🛡️ AWS WAF

JWT オーソライザーによる認可と組み合わせて、REST API の多層防御を構成可能。

📌 まとめ

REST API で外部 OIDC / OAuth 2.0 プロバイダーのトークン検証がネイティブにサポートされ、Lambda オーソライザーの開発・運用なしで JWT ベースの認可を実現できるようになりました。トークン検証のみを目的とした Lambda オーソライザーを運用している場合は、JWT オーソライザーへの移行によりコードの保守コストと Lambda 呼び出しコストの削減が期待できます。まずは開発環境の REST API で発行者・オーディエンス・スコープの設定を検証することを推奨します。
