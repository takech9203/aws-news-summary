リソース構成におけるプライベートドメイン名ターゲットのサポート

📅 2026-05-04

📑 概要

Amazon VPC Lattice のリソース構成で、ネットワーク内のプライベートなドメイン名ターゲットがサポートされるようになった。プライベート FQDN のリソース構成を定義し、AWS RAM を通じて他のアカウントと共有することで、パブリック DNS エントリなしでセキュアなクロスアカウントアクセスが可能に。

❌ Before

  • 共有可能なドメイン名ターゲットはパブリックに解決可能なものに限定
  • プライベート DNS 環境では FQDN を他アカウントと共有不可
  • クロスアカウントアクセスに複雑なネットワーク構成が必要

✅ After

  • プライベート FQDN をリソース構成として定義・共有可能
  • DNS 解決プロパティを IN_VPC に設定するだけで有効化
  • Route 53 Private Hosted Zone やカスタム DNS と連携可能

⚡ 主要機能

🔒 プライベートドメイン名ターゲットの共有

  • プライベート FQDN をリソース構成として定義可能
  • AWS RAM を通じて他のアカウントとセキュアに共有
  • パブリック DNS エントリが不要

🌐 IN_VPC DNS 解決モード

  • リソースゲートウェイに resourceConfigDnsResolution プロパティを追加
  • IN_VPC 設定で VPC の DNS を使用してプライベート FQDN を解決
  • Route 53 Private Hosted Zone およびカスタム DNS サーバーと互換

🔗 シームレスなクロスアカウント接続

  • コンシューマー側は既存のサービスネットワーク経由でアクセス
  • プロバイダー側の DNS インフラ変更不要
  • ネットワーク分離を維持しながら安全なアクセスを実現

🔧 技術仕様

リソースゲートウェイの DNS 解決設定

項目 詳細
プロパティ名 resourceConfigDnsResolution
設定値 IN_VPC または PUBLIC
デフォルト値 PUBLIC
適用対象 リソースゲートウェイ
対象ターゲットタイプ ドメイン名 (FQDN) ターゲット

Bash Step 1: リソースゲートウェイの作成 (IN_VPC DNS 解決を有効化) 
aws vpc-lattice create-resource-gateway \
  --name my-private-dns-gateway \
  --vpc-identifier vpc-0123456789abcdef0 \
  --subnet-ids subnet-0123456789abcdef0 subnet-0123456789abcdef1 \
  --security-group-ids sg-0123456789abcdef0 \
  --ip-address-type IPV4 \
  --resource-config-dns-resolution IN_VPC
Bash Step 2: リソース構成の作成 
aws vpc-lattice create-resource-configuration \
  --name my-private-app \
  --type SINGLE \
  --resource-gateway-identifier rgw-0123456789abcdef0 \
  --resource-configuration-definition \
    '{"dnsResource": {"domainName": "app.internal.example.com", "ipAddressType": "IPV4"}}' \
  --port-ranges '[{"fromPort": 443, "toPort": 443}]'
Bash Step 3: AWS RAM でリソース構成を共有 
aws ram create-resource-share \
  --name my-private-resource-share \
  --resource-arns arn:aws:vpc-lattice:us-east-1:111111111111:resourceconfiguration/rcfg-0123456789abcdef0 \
  --principals 222222222222

🎯 ユースケース

💻 共有サービスアカウントのプライベートアプリ共有

共有サービスアカウントにホストされている内部 API (プライベート DNS で管理) を複数の開発アカウントからアクセスしたい場合。

✅ 効果: VPN やピアリングなしに共有サービスの内部 API にアクセスできる

🏭 オンプレミス連携リソースのクロスアカウント公開

オンプレミスの DNS サーバーで管理されているアプリケーション (Direct Connect 経由で到達可能) を、他の AWS アカウントから利用可能にしたい場合。

✅ 効果: 複雑なネットワーク構成なしに他のアカウントからセキュアにアクセスできる

🔬 マイクロサービスのプライベートサービスディスカバリ

Route 53 プライベートホストゾーンでサービスディスカバリを行っているマイクロサービス群を、異なるチームのアカウントから利用させたい場合。

✅ 効果: サービスメッシュを導入せずに、プライベート DNS ベースのサービスディスカバリをクロスアカウントで活用できる

⚖️ メリット・制約事項

🟢 メリット

  • マルチアカウント戦略の促進 - クロスアカウント共有が容易に
  • 運用コスト削減 - VPN やピアリング設定不要
  • 追加料金なし - 既存の VPC Lattice 料金内で使用可能
  • DNS インフラ変更不要 - 既存の Private Hosted Zone をそのまま活用
  • セキュリティ維持 - パブリック DNS への情報露出なし
  • シンプルな設定 - 1 プロパティの設定で有効化

🔴 制約・考慮点

  • VPC の DNS 設定で対象 FQDN が解決可能である必要あり
  • TCP プロトコルのみサポート (現時点)
  • リソース構成のカスタムドメイン名は作成後に変更不可
  • DNS サーバーの可用性がリソースアクセスに直接影響
  • AWS RAM の権限設定とサービスネットワーク関連付けが必要
  • 既存のリソースゲートウェイの更新にはアップデート操作が必要
