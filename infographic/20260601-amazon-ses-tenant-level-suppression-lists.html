📧 テナントレベル抑制リスト

Tenant-Level Suppression Lists - マルチテナント環境のメール配信を独立管理

2026-06-01

📋 概要

Amazon SES がテナントレベルの抑制リストをサポート。マルチテナント環境でテナントごとに独立した抑制リストを維持し、クロステナント汚染を防止します。

1:1 テナントと抑制リストのマッピング
API TenantName パラメータで制御
0 追加アカウント分離の必要性

❌ Before - 従来の課題

  • 全テナントが単一の抑制リストを共有
  • テナント A のバウンスがテナント B に影響
  • テナント間分離にはアカウント分離が必要
  • 1 つの顧客のメール問題が全顧客に波及

✅ After - 改善後

  • 各テナントが独立した抑制リストを保持
  • バウンス/苦情が該当テナントにのみ影響
  • 単一アカウントで安全にマルチテナント管理
  • API で TenantName を指定するだけで利用可能

⚡ 主要機能

🔒 テナントレベルの抑制分離

各テナントが独立した抑制リストを保持。テナント間でバウンスや苦情が相互に影響しません。1 つのテナントに対して 1 つの抑制リストが 1:1 でマッピングされます。

⚙️ 設定可能な抑制動作

SuppressionScope: TENANT または ACCOUNT を選択。SuppressedReasons: BOUNCE、COMPLAINT、または両方を選択可能。PutTenantSuppressionAttributes API で設定します。

🤖 自動記録と管理

SES がバウンスと苦情を自動的に適切なテナントのリストに記録。ハードバウンスはテナント + グローバル抑制リストに、苦情はテナント抑制リストにのみ追加。「not-spam」フィードバック時に苦情エントリを自動削除します。

🔧 Configuration Set によるオーバーライド

Configuration Set の SuppressionOptions に SuppressionScope フィールドを追加。スコープのみ、理由のみ、または両方を個別にオーバーライド可能。テナントのデフォルト設定を変更せずに特定の送信ワークフローを制御できます。

🛠️ 設定方法

前提条件: SES マルチテナンシーが構成済み / SES アカウントが本番環境アクセスを持つ / 適切な IAM 権限が設定済み

ステップ 1: テナントの抑制属性を設定

Bash テナント抑制属性の設定 
aws sesv2 put-tenant-suppression-attributes \
  --tenant-name "customer-a" \
  --suppression-attributes '{
    "SuppressionScope": "TENANT",
    "SuppressedReasons": ["BOUNCE", "COMPLAINT"]
  }'

ステップ 2: 抑制リストにアドレスを手動追加

Bash アドレスの手動追加 
aws sesv2 put-suppressed-destination \
  --email-address "bounced@example.com" \
  --reason "BOUNCE" \
  --tenant-name "customer-a"

ステップ 3: 抑制リストを確認

Bash 抑制リストの確認 
aws sesv2 list-suppressed-destinations \
  --tenant-name "customer-a"

ステップ 4: 抑制アドレスを削除

Bash アドレスの削除 
aws sesv2 delete-suppressed-destination \
  --email-address "bounced@example.com" \
  --tenant-name "customer-a"

ステップ 5: 抑制設定をクリア

Bash 設定のクリア 
aws sesv2 put-tenant-suppression-attributes \
  --tenant-name "customer-a" \
  --suppression-attributes '{
    "SuppressionScope": null,
    "SuppressedReasons": null
  }'

✅ メリット

ビジネス面

✓ 顧客間影響の排除: マルチテナント SaaS 環境で、1 つの顧客のメール問題が他の顧客に影響しない
✓ アカウント統合の実現: テナント分離のためにアカウントを分ける必要がなくなり、運用コストが削減
✓ メール配信品質の向上: 各テナントが独立した配信レピュテーションを維持でき、全体的な配信率が向上

技術面

✓ きめ細かい制御: テナント単位、Configuration Set 単位での抑制動作カスタマイズが可能
✓ 後方互換性: TenantName パラメータを省略すれば既存の動作が維持され、移行リスクが低い
✓ 自動化対応: API ベースの管理により、プログラマティックな抑制リスト運用が可能
✓ イベント追跡: ses:tenant-name タグにより、どのテナントのイベントかを容易に識別可能

⚠️ デメリット・制約事項

制限事項

✗ SES マルチテナンシーが必須 (未構成アカウントでは利用不可)
✗ テナントあたり 1 つの抑制リストのみ
✗ 抑制リストはリージョン固有 (クロスリージョン共有不可)
✗ メールアドレスは大文字小文字を区別して保存 (完全一致が必要)
✗ Gmail は苦情データを SES に送信しないため、Gmail アドレスは苦情による自動追加の対象外
✗ サンドボックス環境では PutSuppressedDestination を呼び出せない
✗ テナント削除時に全抑制リストエントリも削除される

考慮すべき点

  • テナント抑制リストで抑制されたメッセージも日次送信クォータにカウントされる
  • スコープが TENANT の場合、アカウントレベルの抑制リストはチェックされない
  • SuppressionScope と SuppressedReasons は必ずセットで指定するか、両方を null に設定する必要がある

💡 ユースケース

🏢 SaaS プロバイダーのマルチテナントメール送信

SaaS プラットフォームが複数の顧客企業に代わってメールを送信する場合に、ある顧客のバウンス問題が他の顧客に影響するのを防止。各顧客テナントに TENANT スコープを設定し、独立した配信品質を維持。

📬 トランザクションメールとマーケティングメールの分離

1 つのアカウントからトランザクションメール (注文確認など) とマーケティングメール (ニュースレター) を送信する場合に、マーケティングメールへの苦情がトランザクションメールに影響するのを防止。トランザクション用テナントには BOUNCE のみ、マーケティング用には BOUNCE + COMPLAINT を設定。

🎨 代理店のマルチブランドキャンペーン管理

マーケティング代理店が複数のブランドのメールキャンペーンを管理する場合に、ブランドごとに独立した抑制管理を実現。各ブランドのテナントを作成し、独立した配信レピュテーションを管理。
