Amazon ECS

ECS Service Connect
ゾーン対応ルーティング

Zone-Aware Routing で クロス AZ コストとレイテンシーを削減
リリース日
2026 年 7 月 23 日

📌 概要

Amazon ECS は、ECS Service Connect に ゾーン対応ルーティング を追加しました。サービス間通信を、リクエスト元タスクと 同じアベイラビリティーゾーン (AZ) 内のエンドポイントへ優先的にルーティングし、AZ をまたぐデータ転送 (クロス AZ トラフィック) の コストとレイテンシーの両方を削減します。

従来、耐障害性のためにアプリケーションを複数 AZ に分散すると、サービス間通信が AZ をまたいで発生し、クロス AZ データ転送コストと追加レイテンシーが避けられませんでした。この機能は、こうした 「コストと耐障害性のトレードオフ」 を解消します。

すべての新規・既存サービスで デフォルト有効。追加インフラやコード変更は不要で、既存サービスは 1 回の再デプロイのみ。追加料金なしで利用できます。

🔄 Before / After

😰 アップデート前の課題
  • 複数 AZ 分散でサービス間通信が AZ をまたぎ、クロス AZ データ転送コストが発生
  • AZ をまたぐ通信でサービス間レイテンシーが増加
  • コスト削減と耐障害性がトレードオフの関係
➡
😊 アップデート後の改善
  • 同一 AZ 内エンドポイントを優先し、クロス AZ データ転送コストを削減
  • 同一 AZ 内通信の優先でサービス間レイテンシーを低減
  • ローカル異常時は正常な AZ へ自動再分散し、コストと可用性を両立

⚙️ 主要機能

🎯 同一 AZ 優先ルーティング

リクエスト元と同じ AZ 内のエンドポイントへ優先的にトラフィックをルーティング。AZ をまたぐデータ転送を削減し、コストとレイテンシーを低減します。

⚖️ 動的なトラフィックウェイト調整

エンドポイントのスケールに応じてトラフィックウェイトを動的に調整。対象サービス間で負荷を均等に保ちます。

🔀 異常時の自動フェイルオーバー

ローカルエンドポイントが異常、または容量しきい値を下回ると、正常な AZ へ自動的に再分散。可用性を維持しながらコスト最適化を実現します。

🚀 デフォルト有効 & ゼロコード変更

全サービスでデフォルト有効。追加インフラやコード変更は不要。既存サービスは 1 回の再デプロイのみで有効化されます。

🛠️ 設定方法

前提条件: ECS のクラスターとサービスが構成済み / サービス間通信で Service Connect が有効 / 複数 AZ にタスクが分散配置されていること。

ステップ 1: 既存サービスの再デプロイ

Bash ゾーン対応ルーティングを有効化 
aws ecs update-service \
  --cluster my-cluster \
  --service my-service \
  --force-new-deployment

--force-new-deployment で既存タスクを新しいタスクに置き換えると、新しいルーティング動作が適用されます。新規サービスはデフォルトで有効です。

ステップ 2: ルーティング動作の確認

Bash VPC Flow Logs を有効化 (AZ メタデータを含む) 
aws ec2 create-flow-logs \
  --resource-type VPC \
  --resource-ids vpc-xxxxxxxx \
  --traffic-type ALL \
  --log-destination-type cloud-watch-logs \
  --log-group-name /vpc/flowlogs

AZ メタデータを含む VPC Flow Logs で、トラフィックが同一 AZ 内で処理されているかを検証できます。

⚖️ メリットと考慮点

✅ メリット

  • コスト削減: 同一 AZ 内通信の優先でクロス AZ データ転送コストを削減
  • 追加料金なし: 既存構成をそのまま活用してコスト最適化
  • 導入が容易: コード変更・新インフラ不要、1 回の再デプロイのみ
  • レイテンシー低減: 同一 AZ 内通信でネットワーク遅延を削減
  • 可用性の維持: 異常時の自動フェイルオーバー
  • 動的な負荷分散: スケールに応じてウェイトを自動調整

⚠️ 制約・考慮点

  • 対象は Service Connect が有効なサービス間通信
  • 既存サービスは有効化に 1 回の再デプロイが必要
  • 単一 AZ に偏った構成ではフェイルオーバーの恩恵は限定的
  • 各 AZ に十分なエンドポイントを配置するとコスト削減効果が最大化
  • ローカル不足時は他 AZ へ再分散し、期待した削減が得られない場合がある
  • 効果は VPC Flow Logs の AZ メタデータで検証することを推奨

💡 ユースケース

1️⃣ マイクロサービス間通信のコスト最適化

複数のマイクロサービスを複数 AZ に分散配置。頻繁なサービス間通信でクロス AZ データ転送コストが増大していた。

➡ Service Connect を有効化し各サービスを再デプロイ、VPC Flow Logs でクロス AZ トラフィックの減少を確認。

効果: 同一 AZ 内通信が優先され、クロス AZ データ転送コストを削減。

2️⃣ レイテンシーに敏感なアプリケーション

低レイテンシーが求められるサービス間 API 呼び出しが多く、AZ をまたぐ通信の遅延が性能に影響していた。

➡ ゾーン対応ルーティングを有効化し、各 AZ に十分なエンドポイントを配置して同一 AZ 内通信を優先。

効果: AZ をまたぐ通信が減り、サービス間レイテンシーが改善。

3️⃣ コストと可用性を両立する本番環境

本番環境で高可用性を維持しつつ、データ転送コストも最適化したい。

➡ 各 AZ に冗長なエンドポイントを配置。通常時は同一 AZ を優先、ローカル異常時は正常な AZ へ自動フェイルオーバー。

効果: 通常時はコストを最適化しつつ、異常時には可用性を維持。

💰 料金 & 利用可能リージョン

料金: ゾーン対応ルーティングは 追加料金なし で利用可能。ECS および Service Connect の既存料金体系がそのまま適用され、同一 AZ 内通信の優先により AZ をまたぐデータ転送料金の削減効果が期待できます。

利用可能リージョン

🌍 すべての AWS 商用リージョン 🏛️ AWS GovCloud (US)

🔗 関連サービス・機能

Amazon ECS Service Connect サービス間通信を簡素化するマネージド機能。ゾーン対応ルーティングはその拡張機能として提供。
Amazon VPC Flow Logs AZ メタデータを含めることで、ルーティングのトラフィックパターンを監視・検証できる。
AWS Availability Zones 複数 AZ にまたがる分散構成が、コスト最適化とフェイルオーバーの前提となる。

📝 まとめ

ECS Service Connect のゾーン対応ルーティングは、コストと耐障害性のトレードオフを解消する重要なアップデートです。追加料金なし・コード変更なしで導入でき、既存サービスは 1 回の再デプロイのみで有効化できます。複数 AZ に分散配置したマイクロサービス環境では、クロス AZ データ転送コストとレイテンシーの削減効果が期待できるため、既存サービスの再デプロイを計画し、VPC Flow Logs で効果を検証することを推奨します。
