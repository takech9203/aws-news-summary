Amazon EC2

📊 EC2 Capacity Manager
サポータビリティチェックとキャパシティ充足メトリクス

リリース日: 2026 年 11 月 4 日 | AWS Unified Operations に含まれる新機能

💡 概要

EC2 Capacity Manager に 2 つの新機能が追加され、スケールアップの「事前計画」と「事後測定」の両面をデータドリブンにカバーできるようになりました。対象は、ミッションクリティカルなワークロードを大規模運用するエンタープライズのインフラ担当者や SRE チームです。

🔍

サポータビリティチェック

事前計画: どこで実行すべきか

インスタンスを起動・予約せずに、インスタンスタイプ × AZ の組み合わせごとにキャパシティ提供可能性を High / Medium / Low と総合スコアで評価。

📈

キャパシティ充足メトリクス

事後測定: どれだけ提供されたか

リクエストしたキャパシティに対する実際の提供割合を、AWS Organizations 全体・アカウント・リージョン・タグ単位で計測。

High十分なキャパシティあり
Medium余裕は少ないが収まる
Low不足

❌ Before: アップデート前の課題

  • インスタンスタイプ × AZ の組み合わせを事前評価する手段がなく、実際に起動を試すかキャパシティ予約を作成して確認する必要があった
  • リクエストしたキャパシティの充足状況を組織・アカウント・リージョン・ワークロード横断で定量的に把握できなかった
  • ダイバーシフィケーション (多様化) の効果をデータで検証できなかった

✅ After: アップデート後の改善

  • 起動・予約なしで組み合わせごとの提供可能性を High / Medium / Low で事前評価
  • リクエスト vCPU 数、充足 vCPU 数、充足率、平均組み合わせ数を組織・アカウント・リージョン・タグ単位で追跡
  • 組み合わせごとの内訳分析で、Auto Scaling 混合インスタンスポリシー、EC2 フリート、Karpenter の設定改善につなげられる

🔧 主要機能

1️⃣ サポータビリティチェック (Supportability Checks)

  • インスタンスを起動・予約することなく、各インスタンスタイプと AZ の組み合わせのキャパシティ提供可能性を評価
  • マーケットタイプ (オンデマンド / スポット)、必要キャパシティ量、対象 AZ、インスタンスタイプ (または vCPU / メモリ範囲などの属性ベース要件) を指定
  • 各組み合わせに High / Medium / Low のレーティングと総合スコアを返却
  • コンソールの Supportability タブ、または get-capacity-manager-supportability-scores API で実行

2️⃣ キャパシティ充足メトリクス (Capacity Fulfillment Metrics)

  • リクエストレベルの 4 つのメトリクス: リクエスト vCPU 数、充足 vCPU 数、リクエスト充足率 (vCPU 加重)、リクエストあたりの平均「インスタンスタイプ × AZ」組み合わせ数
  • 組み合わせ数が 1 を超える値は、ダイバーシフィケーション (柔軟性) が機能していることを示す
  • AWS Organizations 全体、アカウント、リージョン、タグ付けされたワークロード単位でフィルタリング可能
  • コンソールの Fulfillment タブ、または get-capacity-manager-metric-data API で取得 (スポットメトリクスには Spot プレフィックス)

3️⃣ 組み合わせごとのブレークダウン分析

  • View breakdown オプションで、InstAzFulfillmentRate メトリクスによる組み合わせ単位の充足率を表示
  • AZ ディメンションに加えて、インスタンスタイプまたはインスタンスファミリーの指定が必要
  • 組み合わせ単位の充足率はリクエスト全体より低くなる傾向 (代替の組み合わせがギャップを埋めるため)

📋 技術仕様

🔍 サポータビリティチェックの仕様

項目詳細
評価レーティングHigh / Medium / Low + 総合スコア
指定パラメータマーケットタイプ、キャパシティ量、AZ、インスタンスタイプまたは属性ベース要件
AZ 数の上限1 回のチェックで最大 10 AZ (複数リージョンにまたがる指定も可能)
組み合わせ数の上限1 回のチェックで最大 100 組み合わせ
スコアの性質ガイダンスであり、キャパシティの保証ではない (保証にはキャパシティ予約を使用)
実行タイミングの推奨起動ごとではなく計画時に実行 (クロスリージョン依存とクォータ枯渇を回避)

📈 充足メトリクスの仕様

メトリクス説明
リクエスト vCPU 数キャパシティリクエストで要求された vCPU の総数
充足 vCPU 数実際に提供された vCPU の総数
リクエスト充足率vCPU 加重のリクエスト充足割合
平均組み合わせ数リクエストあたりのインスタンスタイプ × AZ 組み合わせ数 (1 超で柔軟性あり)
InstAzFulfillmentRate組み合わせ単位の充足率 (AZ ディメンション + インスタンスタイプ / ファミリーが必要)

⚙️ 設定方法

📌 前提条件

✓AWS Unified Operations サポートプランに加入していること
✓EC2 Capacity Manager を有効化していること (組織レベルまたは単一アカウント)
✓タグ単位で分析する場合は、モニタリング対象のタグキーを有効化していること (aws:eks:cluster-name など一部のタグは有効化不要)

ステップ 1: Capacity Manager の有効化とタグの設定

Bash 有効化 
# Capacity Manager のコンソールから有効化 (組織レベルまたはアカウント単位)
# 必要に応じてモニタリング対象のタグキーを有効化する

有効化すると組織またはアカウントのキャパシティデータの収集が開始され、タグキーを有効化するとワークロード単位でのフィルタリングが可能になります。

ステップ 2: 充足メトリクスの確認

Bash 充足メトリクスの取得 
# 充足メトリクスを取得
aws ec2 get-capacity-manager-metric-data \
  --region us-east-1 \
  # リージョン、アカウント、タグでフィルタリングし、
  # 充足率や組み合わせ数のメトリクスを指定して取得

コンソールでは Fulfillment タブから同じ情報を確認でき、View breakdown でインスタンスタイプ × AZ ごとの内訳を表示できます。

ステップ 3: サポータビリティチェックの実行

Bash サポータビリティスコアの取得 
# サポータビリティスコアを取得
aws ec2 get-capacity-manager-supportability-scores \
  --region us-east-1 \
  # マーケットタイプ、必要キャパシティ量、対象 AZ、
  # インスタンスタイプ (または属性ベース要件) を指定

スコアの高い組み合わせを Auto Scaling の混合インスタンスポリシーや EC2 フリートの設定に反映します。

✅ メリット

💼 ビジネス面

✓スケールアップの成功率向上: 大規模イベントやピーク需要の前に、キャパシティを獲得できる可能性が高い構成を事前に特定でき、機会損失のリスクを低減
✓キャパシティ戦略の定量評価: 充足率という客観的な指標により、戦略の有効性を経営層やステークホルダーに説明しやすくなる
✓過剰予約の抑制: 事前評価により不要なキャパシティ予約 (使用有無にかかわらず課金) を減らし、弱い AZ のみベースライン予約を行う最適化が可能

🔧 技術面

✓起動不要の事前評価: インスタンスを起動・予約せずに評価でき、検証コストとクォータ消費を回避
✓組織横断の可視性: AWS Organizations 全体、アカウント、リージョン、タグ単位で充足状況を一元的に把握
✓ダイバーシフィケーションの効果測定: 平均組み合わせ数メトリクスで多様化の効果をデータで確認し、Auto Scaling や Karpenter の設定改善につなげられる

⚠️ デメリット・制約事項

🚧 制限事項

✗両機能の利用には AWS Unified Operations サポートプランへの加入が必要
✗サポータビリティチェックは 1 回あたり最大 10 AZ、最大 100 組み合わせまで
✗サポータビリティスコアはあくまでガイダンスであり保証ではない (確実な確保にはオンデマンドキャパシティ予約が必要)
✗組み合わせ単位のブレークダウン (InstAzFulfillmentRate) には AZ ディメンションとインスタンスタイプまたはファミリーの指定が必要

🤔 考慮すべき点

⚠チェックは起動のたびではなく計画時に実行することが推奨される (クロスリージョン依存の回避とクォータ枯渇の防止)
⚠組み合わせ単位の充足率はリクエスト全体より低く見えるのが正常であり、数値の解釈に注意が必要
⚠弱い AZ へのキャパシティ予約は使用の有無にかかわらず課金されるため、サイズを慎重に設計する必要がある

🎯 ユースケース

🛒 ユースケース 1: 大規模イベント前のキャパシティ計画

シナリオ: EC サイトがセールイベントに向けて数千 vCPU 規模のスケールアップを計画しており、どのインスタンスタイプと AZ の組み合わせを Auto Scaling グループに設定すべきか判断したい。

  1. 候補となるインスタンスタイプ群 (例: m7i, m7a, m6i) と対象 AZ を指定してサポータビリティチェックを実行
  2. High レーティングの組み合わせを混合インスタンスポリシーに設定
  3. Low レーティングの AZ にはオンデマンドキャパシティ予約でベースライン分のみ確保

💪 効果: 起動失敗のリスクを事前に低減し、イベント当日のスケールアップ成功率を向上。不要なキャパシティ予約も抑制。

⚡ ユースケース 2: スポットワークロードの充足率モニタリング

シナリオ: バッチ処理基盤をスポットインスタンスで運用しており、リクエストしたキャパシティがどの程度充足されているかを継続的に監視したい。

  1. Capacity Manager の Fulfillment タブで Spot プレフィックス付きメトリクスを確認
  2. タグキーを有効化し、ワークロード単位で充足率をフィルタリング
  3. View breakdown で組み合わせごとの充足率を分析し、充足率の低い組み合わせを特定

💪 効果: 充足率の低下を早期に検知し、インスタンスタイプの追加やダイバーシフィケーション強化などの対策を打てる。

☸️ ユースケース 3: Kubernetes クラスターのノード戦略改善

シナリオ: Amazon EKS で Karpenter を使用してノードをプロビジョニングしており、ノードプールのインスタンスタイプ選定を改善したい。

  1. aws:eks:cluster-name タグ (有効化不要) でクラスター単位の充足メトリクスを確認
  2. 平均組み合わせ数メトリクスで柔軟性の度合いを評価
  3. サポータビリティチェックの結果をもとに Karpenter の NodePool の requirements を調整

💪 効果: データに基づいてノードプールの柔軟性を高め、ポッドのスケジューリング遅延やキャパシティ不足を削減。

📝 まとめ

EC2 Capacity Manager のサポータビリティチェックと充足メトリクスにより、キャパシティ計画の「事前評価」と「事後測定」の両方をデータドリブンに行えるようになりました。AWS Unified Operations を利用する大規模環境では、スケールアップ前のサポータビリティチェックを変更管理プロセスに組み込み、充足メトリクスで継続的に柔軟性の改善を検証することを推奨します。
