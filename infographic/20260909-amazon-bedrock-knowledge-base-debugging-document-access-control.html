Amazon Bedrock Knowledge Bases

🔍 ドキュメントレベルアクセス制御のデバッグ機能

📅 2026 年 9 月 9 日リリース ｜ 新 API CheckIngestedDocumentAcl / GetIngestedDocumentAcl とコンソールサポート

📌 概要

Amazon Bedrock Managed Knowledge Base に、ドキュメントレベルのアクセス制御 (ACL) をデバッグするための 2 つの新 API とコンソールサポートが追加されました。 ACL 対応データソースを利用する場合に、ドキュメントへのアクセス権限の問題を サポートケースなしでセルフサービス診断できます。

❌ Before: アップデート前の課題
  • ドキュメントが表示されない原因が ACL 設定ミスか、取り込み失敗か、検索精度かを判別する手段がなかった
  • 取り込み済みドキュメントの ACL を確認する API が存在しなかった
  • 権限問題の解決に AWS サポートへの問い合わせが必要なケースがあった
✅ After: アップデート後の改善
  • CheckIngestedDocumentAcl で特定ユーザーのアクセス可否をその場で検証
  • GetIngestedDocumentAcl で ACL 全体を取得し、権限監査や設定ミスの特定が可能
  • コンソールからも同等の操作ができ、サポートケースなしで自己解決

管理者はコンソールまたは API を通じて、取り込み済みドキュメントに付与された ACL を照会し、特定ユーザーのアクセス可否を検証できます。

⚙️ 主要機能

✅ CheckIngestedDocumentAcl API
  • 特定のユーザーが特定の取り込み済みドキュメントにアクセスできるかを検証
  • ドキュメント ID とユーザーコンテキスト (ユーザー ID、オプションでグループメンバーシップ) を指定して呼び出す
  • レスポンスの hasAccess (Boolean) でアクセス可否を即座に判定
  • 取り込み後にドキュメントレベルのアクセス制御が期待どおりに機能しているかの検証に使用
📋 GetIngestedDocumentAcl API
  • 特定のドキュメントに対して取り込まれた ACL 全体を取得
  • 許可リスト (allowList) と拒否リスト (denyList) の両方が返され、ユーザー・グループ単位の条件や条件間の関係 (memberRelation) を確認可能
  • 権限設定の監査や、アクセス制御の設定ミスの特定に使用
🖥️ コンソールの Document Access Control セクション
  • データソース詳細ページに新しく追加されたセクション
  • ドキュメント ID とユーザーのメールアドレスを入力してアクセス可否を確認
  • ドキュメント ID のみを入力して、ドキュメントの ACL 全体を取得

🛠️ 設定方法

前提条件

✓Amazon Bedrock Managed Knowledge Base が作成済みであること
✓ACL 対応データソースが接続され、ドキュメントが取り込み済みであること
✓呼び出し元の IAM プリンシパルに bedrock:CheckIngestedDocumentAcl および bedrock:GetIngestedDocumentAcl 権限が付与されていること

手順

1
ユーザーのアクセス可否を検証する
Bash CheckIngestedDocumentAcl の呼び出し 
aws bedrock-agent-runtime check-ingested-document-acl \
  --knowledge-base-id KB12345678 \
  --data-source-id DS12345678 \
  --document-id "doc-001" \
  --user-context '{"userId": "user@example.com", "userGroups": [{"id": "engineering", "type": "KNOWLEDGE_BASE"}]}'

ドキュメント doc-001 に対して、ユーザー user@example.com (グループ engineering に所属) がアクセスできるかを検証します。レスポンスの hasAccess が true であればアクセス可能、false であればアクセス不可です。

2
ドキュメントの ACL 全体を取得する
Bash GetIngestedDocumentAcl の呼び出し 
aws bedrock-agent-runtime get-ingested-document-acl \
  --knowledge-base-id KB12345678 \
  --data-source-id DS12345678 \
  --document-id "doc-001"

ドキュメント doc-001 に取り込まれた ACL 全体 (許可リストと拒否リスト) を取得します。ステップ 1 でアクセス不可と判定された場合に、どの条件が原因かをこの出力から特定します。

3
コンソールから確認する

① Amazon Bedrock コンソールで対象のナレッジベースを開く

② データソース詳細ページの「Document Access Control」セクションに移動する

③ ドキュメント ID とユーザーのメールアドレスを入力してアクセス可否を確認する、またはドキュメント ID のみを入力して ACL 全体を取得する

💡 メリット

💼 ビジネス面
✓問題解決の迅速化: サポートケースなしで権限問題をセルフサービス診断・解決し、RAG アプリケーションの障害対応時間を短縮
✓コンプライアンス対応の強化: ドキュメント単位の権限を監査でき、機密情報へのアクセス制御が意図どおりに機能していることを証明しやすい
✓運用コストの削減: 権限トラブルの調査工数と AWS サポートとのやり取りを削減
🔧 技術面
✓原因の切り分けが容易: ACL 設定ミスか、それ以外の問題 (取り込み失敗、検索精度など) かを明確に切り分け
✓API とコンソールの両対応: 自動化された監査スクリプトには API、アドホックな調査にはコンソールを使い分け
✓ACL の内部状態を可視化: 取り込み時に生成された allowList / denyList を確認でき、ソースシステム側の権限設定と突き合わせ可能

⚠️ デメリット・制約事項

制限事項

✗ACL 対応データソースを使用している場合にのみ有効な機能
✗対象は取り込み済み (ingested) のドキュメントであり、取り込み前のソースシステム側の権限をリアルタイムに照会するものではない
✗発表時点では利用可能リージョンが明記されていないため、利用前に対象リージョンでの提供状況の確認が必要

考慮すべき点

⚠ACL 情報自体が機密情報となり得るため、bedrock:CheckIngestedDocumentAcl と bedrock:GetIngestedDocumentAcl の IAM 権限の付与先は最小限にすべき
⚠ソースシステム側で権限を変更した場合、次回の同期 (sync) が完了するまで取り込み済み ACL には反映されない

🎯 ユースケース

1️⃣ 検索結果にドキュメントが表示されない問題のトラブルシューティング

シナリオ: 社内 RAG チャットボットで、あるユーザーから「自分の部署のドキュメントが回答に反映されない」と報告があった。原因が権限設定なのか検索精度なのかを切り分けたい。

Bash 対象ユーザーのアクセス可否を確認 
aws bedrock-agent-runtime check-ingested-document-acl \
  --knowledge-base-id KB12345678 \
  --data-source-id DS12345678 \
  --document-id "dept-doc-042" \
  --user-context '{"userId": "taro@example.com"}'

効果: hasAccess が false であれば ACL の設定ミス、true であれば検索精度など別の原因と即座に切り分けられ、調査時間を大幅に短縮できる。

2️⃣ ドキュメントレベル権限の定期監査

シナリオ: 機密ドキュメントを含むナレッジベースについて、意図しないユーザーやグループに権限が付与されていないかを定期的に監査したい。

Bash 機密ドキュメントの ACL を監査ログに記録 
aws bedrock-agent-runtime get-ingested-document-acl \
  --knowledge-base-id KB12345678 \
  --data-source-id DS12345678 \
  --document-id "confidential-doc-001" > acl_audit_$(date +%Y%m%d).json

効果: 許可リスト・拒否リストの内容を定期的に記録・レビューすることで、権限の設定ミスや不要な権限付与を早期に検出できる。

3️⃣ データソース同期後の ACL 反映確認

シナリオ: ソースシステム側でドキュメントの共有範囲を変更した後、データソースの同期を実行した。変更が Knowledge Base 側の ACL に正しく反映されたかを確認したい。

Bash 新しく権限を付与したユーザーで検証 
aws bedrock-agent-runtime check-ingested-document-acl \
  --knowledge-base-id KB12345678 \
  --data-source-id DS12345678 \
  --document-id "shared-doc-010" \
  --user-context '{"userId": "new-member@example.com", "userGroups": [{"id": "project-a", "type": "KNOWLEDGE_BASE"}]}'

効果: 権限変更のリリース作業に検証ステップを組み込むことで、エンドユーザーからの問い合わせを未然に防止できる。

📝 まとめ

Amazon Bedrock Managed Knowledge Base の ACL 対応データソースにおける権限トラブルを、 サポートケースなしでセルフサービスで診断できる重要なアップデートです。 ドキュメントレベルアクセス制御を利用した RAG アプリケーションを運用しているチームは、 トラブルシューティング手順と定期監査プロセスに CheckIngestedDocumentAcl と GetIngestedDocumentAcl の活用を組み込むことを推奨します。

💡 権限変更のリリース作業や定期監査に、これらの API による検証ステップを組み込むことで、エンドユーザーからの問い合わせを未然に防止できます。
