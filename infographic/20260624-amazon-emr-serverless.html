Amazon EMR Serverless

⚙️ アプリケーション再起動なしの
ライブ構成更新

📅 2026年6月24日
Live Configuration Updates

📌 概要

Amazon EMR Serverless で、アプリケーションを停止・再起動せずに 最大キャパシティ や カスタムイメージ設定 などの主要な構成を更新できるようになりました。

更新後に投入された新しいワークロードは自動的に新設定を使用し、既存のワークロードは元の構成のまま中断されずに継続します。変更の影響が予測しやすく、運用上の安全性が向上します。対象は主にデータエンジニアや分析プラットフォームの運用担当者で、すべての Amazon EMR リリースで利用可能です。

😓 Before（これまで）
  • 構成変更のためにアプリケーションの停止が必要
  • メンテナンスウィンドウの調整とジョブ投入の一時ブロックが必要
  • スケーリング上限やイメージ更新を実行中ジョブを止めずに行えなかった
➡
🚀 After（今回のアップデート）
  • 最大キャパシティ・カスタムイメージをアプリ停止なしで更新
  • メンテナンスウィンドウ調整やジョブ停止が不要に
  • 新規ワークロードは新設定、既存は元構成という予測可能な挙動

構成更新後、新規に投入されたワークロードは新しい設定を自動的に使用し、すでに実行中の既存ワークロードは元の構成のまま中断なく継続します。

✨ 主要機能

① アプリケーション稼働中の構成更新

  • アプリケーションを停止・再起動せずに主要な構成を更新できる
  • 最大キャパシティ（maximum capacity）の調整に対応
  • カスタムイメージ設定（custom image settings）の更新に対応

② 新旧ワークロードの分離された挙動

  • 更新後に投入された新規ワークロードは新しい設定を自動的に使用
  • すでに実行中の既存ワークロードは元の構成のまま中断されずに継続
  • 構成変更が実行中ジョブに予期しない影響を与えることを防ぐ

③ 運用調整の不要化

  • メンテナンスウィンドウの事前調整が不要
  • 構成変更時にジョブ投入を一時ブロックする必要がない
  • スケーリング上限調整やイメージ更新をいつでも実施可能

🔧 技術仕様

更新可能な主要構成

項目詳細
最大キャパシティアプリケーションが使用できる vCPU、メモリ、ディスクの上限値。スケーリング境界の調整に使用
カスタムイメージ設定ジョブ実行に使用するカスタムコンテナイメージの設定。更新済みイメージのデプロイに使用
新規ワークロードへの反映更新後に投入されたジョブが自動的に新しい設定を使用
既存ワークロードへの影響実行中のジョブは元の構成のまま継続し、中断されない
📝 API: 構成更新には emr-serverless の UpdateApplication API を使用します。awsapichanges.com への該当エントリはレポート作成時点では確認できませんでした。

⌨️ 設定方法

前提条件

✓既存の Amazon EMR Serverless アプリケーションが作成済みであること
✓emr-serverless:UpdateApplication を実行する権限を持つ IAM ロール／ユーザーであること
✓AWS CLI または SDK が利用可能な環境であること

ステップ 1: 現在のアプリケーション構成を確認する

Bashget-application
aws emr-serverless get-application \
  --application-id <application-id>

ステップ 2: 最大キャパシティを更新する

Bashupdate-application（capacity）
aws emr-serverless update-application \
  --application-id <application-id> \
  --maximum-capacity '{"cpu": "400 vCPU", "memory": "3000 GB", "disk": "20000 GB"}'

アプリケーションを停止せずに最大キャパシティ（スケーリング境界）を更新。更新後に投入される新規ジョブから新しい上限値が適用されます。

ステップ 3: カスタムイメージ設定を更新する

Bashupdate-application（image）
aws emr-serverless update-application \
  --application-id <application-id> \
  --image-configuration '{"imageUri": "<account-id>.dkr.ecr.<region>.amazonaws.com/<repository>:<new-tag>"}'

更新済みのカスタムコンテナイメージをデプロイ。実行中の既存ジョブは元のイメージのまま継続し、更新後の新規ジョブが新しいイメージを使用します。

💡 メリット

📈 ビジネス面

✓ダウンタイムの排除: 分析ワークロードの中断によるビジネス影響を回避
✓運用負荷の軽減: メンテナンスウィンドウ調整やジョブ停止が不要に
✓俊敏性の向上: 需要変化やセキュリティ更新に迅速に対応

⚙️ 技術面

✓無停止運用: 長時間実行ジョブの完遂を妨げない
✓予測可能な挙動: 新規のみに新設定が適用され影響範囲を把握しやすい
✓広範な対応: すべての EMR リリース／対応リージョンで利用可

⚠️ デメリット・制約事項

制限事項

▲更新可能な構成は最大キャパシティやカスタムイメージ設定などの主要構成に限定される
▲既存の実行中ワークロードには新構成が反映されず、適用には新規ジョブの投入が必要
▲一部の構成項目には従来の制約が適用される可能性があり、最新の公式ドキュメントで確認が必要

考慮すべき点

▲新旧ワークロードが異なる構成で並行実行される期間が発生するため、運用監視で双方の挙動を考慮する
▲カスタムイメージ更新時は、新イメージと既存ジョブの互換性を事前検証することが望ましい

🎯 ユースケース

1. ピーク時間帯のスケーリング上限引き上げ

シナリオ: 月次バッチ処理のピーク時間帯に向けて一時的に最大キャパシティを引き上げたい。従来は停止が必要だったが、稼働中のジョブを止めたくない。

Bash
aws emr-serverless update-application \
  --application-id <application-id> \
  --maximum-capacity '{"cpu": "800 vCPU", "memory": "6000 GB"}'
✅ 効果: ジョブを中断せずにスケーリング上限を引き上げ、ピーク処理を高速化。

2. セキュリティパッチを含むカスタムイメージの即時デプロイ

シナリオ: カスタムイメージにセキュリティパッチを適用したいが、長時間実行中の分析ジョブを完了させたい。

Bash
aws emr-serverless update-application \
  --application-id <application-id> \
  --image-configuration '{"imageUri": "<account-id>.dkr.ecr.<region>.amazonaws.com/emr-custom:patched"}'
✅ 効果: 実行中ジョブは元イメージで完遂しつつ、以降の新規ジョブにパッチ適用済みイメージを適用。

3. コスト最適化のためのキャパシティ縮小

シナリオ: 業務閑散期に向けて最大キャパシティを縮小し、想定外のコスト増を抑制したい。

Bash
aws emr-serverless update-application \
  --application-id <application-id> \
  --maximum-capacity '{"cpu": "100 vCPU", "memory": "750 GB"}'
✅ 効果: ジョブ投入を止めずにスケーリング上限を縮小し、リソース消費とコストを抑制。

💰 料金

本アップデートは構成の更新方法に関する機能拡張であり、ライブ構成更新の利用自体に追加料金は発生しません。Amazon EMR Serverless の料金は、ジョブ実行中に消費した vCPU、メモリ、ストレージのリソース使用量に基づいて課金されます。

🌍 利用可能リージョン

🌐 Amazon EMR Serverless が利用可能なすべての AWS リージョンで使用できます。また、すべての Amazon EMR リリースに対応しています。

🔗 関連サービス・機能

  • Amazon EMR — ビッグデータ処理のためのマネージドプラットフォーム。EMR Serverless はサーバーレスでの実行オプションを提供
  • Amazon ECR — カスタムイメージ機能で使用するコンテナイメージのレジストリ。更新済みイメージの保管・配布に利用
  • AWS IAM — emr-serverless:UpdateApplication などの操作権限を制御

📝 まとめ

このアップデートにより、Amazon EMR Serverless のアプリケーション構成をダウンタイムなしで変更でき、運用調整の負担が大幅に軽減されます。新規ワークロードのみに新設定が適用される明確な挙動により、変更の影響を安全に管理できます。スケーリング上限の調整やカスタムイメージの更新を運用ルーチンに取り入れ、無停止での柔軟なキャパシティ管理とイメージ更新を活用することを推奨します。
