Lessons learned from one million evaluations — コーディングエージェント評価 (Evals) 運用のエンジニアリング知見

💡 概要

Kiro チームは、エージェント開発の過程で実施してきた 100 万回を超える評価 (Evals) から得られた教訓をまとめたエンジニアリングブログ記事を公開しました。固定されたベンチマークセットを合否 (pass/fail) のみで採点する評価アプローチの限界と、顧客価値を正しく測定するために構築した仕組みが解説されています。

🚨 出発点となった実体験

新モデル追加時、Terminal Bench 2.1 のパス率は期待どおりだったのに、社内テストユーザーからは「体験が悪い」という声が。調査の結果、ツール説明 (tool description) が原因でツール呼び出しの 40% が無効な入力で失敗していたことが判明。モデルはリトライでタスクを完了できたためパス率は正常に見えたが、その間にトークン消費と遅延が増大し、顧客価値は低下していました。

❌ 従来の評価アプローチの課題
  • ベンチマークの飽和: 性能向上で固定セットのパス率が上限に近づき、残る差分はノイズに。シグナルが得られない
  • pass/fail シグナルの不十分さ: どのように解決したかが見えず、トークン消費・遅延・コード品質が隠れる
  • 顧客体験との乖離: 公開ベンチマークは入手可能性や知名度で選ばれがちで、実際の顧客ユースケースを反映しない
✅ Kiro が構築したアプローチ
  • 静的セットから動的ベンチマークへ: 社内利用状況を集計・分類し、実態に合わせてシナリオを継続補充するバージョン管理されたスイート
  • 合否から段階的な判定へ: pass/fail + 出力シグナル + LLM-as-judge の 3 層の粒度で測定
  • ライブシグナルによる信頼構築: アンケート・満足度評価・ユーザーの声でベンチマーク自体を継続検証

ユーザーのフィードバックをライブシグナルとして収集し、オフラインベンチマークとの一致を検証した上で改善を出荷する 4 ステップのループ

🔍 記事の主要なポイント

1️⃣ ベンチマーク飽和の実例と教訓

Terminal Bench 2.1 の飽和を認識しつつも「大きなリグレッションは検出できる」と想定。実際にはツール呼び出しの 40% が失敗してもパス率は正常に見え、リトライの裏でトークン・遅延・顧客価値が悪化していました。

2️⃣ 評価がエージェント開発に不可欠な理由

プロンプト、ツール説明、モデル自体への小さな変更が予期しない形で挙動を変える可能性があります。サブエージェントの使い方、AGENTS.md に何を書くべきか、ツール数の上限、メモリの有効性、スキルとカスタム MCP ツールのどちらを重視すべきかなど、経験豊富なエンジニアでも意見が分かれるトレードオフの判断には信頼できる評価結果が必要です。

3️⃣ 動的ベンチマークスイートの構築

社内 Amazon ユーザーの利用状況を集計カテゴリとして測定し、シナリオに同じカテゴリでラベル付け。シナリオは「自作シナリオ」「他の Amazon チームのシナリオ」「公開ベンチマーク」の 3 ソースから補充し、実利用に比べて不足するカテゴリを優先的に追加します。

4️⃣ 3 層の粒度による採点
第 1 層
✅ pass/fail
タスクの合否。性能の複合的な指標として最初に確認する第一指標
第 2 層
⚡ 出力シグナル
遅延、トークン使用量、場合によってはコード複雑度や生成成果物のサイズ。顧客体験に影響する定量指標を追跡
第 3 層
🤖 LLM-as-judge
トラジェクトリ評価により、コード品質や応答トーンなど決定的な測定が難しいシグナルを評価
5️⃣ ライブシグナルによる評価システム自体の検証

Jeff Bezos 氏の「データと逸話が食い違うときは、たいてい逸話が正しい」という言葉を指針に採用。アンケート、集計された満足度評価、ユーザーとの対話から得られる逸話を活用し、外部顧客へのアンケートと対話により社内ユーザーと同様の体験であることを確認しています。

6️⃣ 実際の測定結果

コンタミネーション (学習データ混入) リスクを避けるための複数のプライベートベンチマークに加え、Terminal Bench 4.0、Deep SWE、SWE Marathon などで測定。ツール失敗率のデータでツール説明の不整合問題を修正し、効率性データにより機能改善・ハーネスのバグ修正・顧客のコスト削減に直結する効率改善など数十件の変更を実施しました。

✨ メリット

💼 ビジネス面

✓顧客価値に直結する測定: パス率だけでは見えないトークンコスト、遅延、コード品質を測定し、顧客が実際に体感する価値の改善につなげられる
✓効率改善によるコスト削減: トークン効率の改善は顧客のコスト削減に直接つながる変更として実際に出荷されている
✓意思決定の信頼性向上: トレードオフの判断を経験や勘ではなく、信頼できる評価結果に基づいて行える

🔧 技術面

✓リグレッションの早期検出: ツール失敗率などの詳細メトリクスにより、パス率に表れない品質低下を検出できる
✓改善オプションの再テスト: 複数の改善案を再テストして最も効果的なものを選択できる
✓評価システム自体の継続的検証: ライブシグナルとの突き合わせで、ベンチマークが顧客体験から乖離していないかを常に確認できる

⚠️ デメリット・制約事項

🚧 制限事項

✗本記事は機能リリースではなくエンジニアリング知見の共有であり、ユーザーが直接利用できる新機能は含まれない
✗紹介されている評価の仕組みは Kiro 内部のものであり、評価スイート自体は公開されていない
✗MCP サーバーやステアリングファイルなどの複雑な顧客構成はまだカバーされていない (今後の研究課題)

🤔 考慮すべき点

⚠適切なシナリオの選定は難しく、成功に見えるシグナル (マージ済み・高評価のプルリクエスト) が誤ったシナリオである場合がある
⚠カテゴリ・ドメイン・言語で一致していても、飽和やカテゴリ粒度の不足により顧客体験を反映しない可能性が残る

🎯 ユースケース

1. 自社エージェント製品の評価設計

シナリオ: 社内でコーディングエージェントや LLM アプリケーションを開発しており、評価基盤の設計方針を検討している。

適用方法: pass/fail に加えて、遅延・トークン使用量などの出力シグナルと LLM-as-judge による品質評価の 3 層構造を採用し、実際のユーザー利用カテゴリに合わせてシナリオを補充する。

効果: ベンチマーク飽和によるシグナル喪失を防ぎ、顧客体験に直結する指標でリグレッションを早期検出できる。

2. 新モデル導入時の品質検証

シナリオ: エージェント製品に新しい基盤モデルを追加する際、既存ベンチマークのパス率だけで品質を判断している。

適用方法: パス率に加えてツール呼び出しの失敗率、トークン効率、遅延を測定し、社内テストユーザーの逸話的フィードバックと突き合わせる。

効果: パス率が正常でもツール説明との相性問題などで顧客体験が悪化しているケースを、リリース前に検出できる。

3. ベンチマークシナリオのキュレーション

シナリオ: 実際の開発タスク (プルリクエストなど) をベンチマークシナリオとして採用したい。

適用方法: マージ済み・高評価という表面的なシグナルだけでなく、リポジトリ履歴を確認し、後続コミットでバグ修正が行われていないかを検証する。

効果: 誤った「正解」を基準とするベンチマークの混入を防ぎ、評価の信頼性を維持できる。

🔭 今後の研究課題

📚 ベンチマークキュレーションのスケール

マージされ 5 つ星評価を得た社内プルリクエストをベンチマーク候補としたところ、次のコミットでそのプルリクエストが混入させたバグが修正されていた事例を紹介。このような「成功に見えて誤ったシナリオ」を検出しながらスイートを更新し続ける仕組みの研究。

🧩 複雑な顧客構成での評価

MCP サーバー、ステアリングファイル、冗長なスキル、コメントの多いコードベースなど、複雑な顧客構成における Kiro の性能評価。

📝 まとめ

100 万回を超える評価の実践から得られた「ベンチマーク飽和」「pass/fail シグナルの限界」「顧客体験との乖離」という 3 つの課題と、それに対する動的ベンチマーク、3 層採点、ライブシグナル検証という解決アプローチを示したエンジニアリング知見です。コーディングエージェントや LLM アプリケーションを開発・評価するチームは、自社の評価基盤設計の参考として本記事と関連記事 (Continuous Prompt Evaluation) の確認を推奨します。
