統合オブザーバビリティ体験

📝 概要

Amazon OpenSearch Service において統合オブザーバビリティ体験が提供開始。Amazon Managed Service for Prometheus とのネイティブ統合および包括的なエージェントトレーシング機能を導入。

😥 Before

  • プレミアムオブザーバビリティプラットフォームの高額なコスト負担
  • メトリクス、ログ、トレースが異なるツールに分散
  • Prometheus メトリクス取り込み時のデータ重複でストレージコスト増大
  • LLM エージェント実行フローを可視化する統合的な手段がない

😊 After

  • 単一 UI からメトリクス、ログ、トレース、エージェントトレーシングを統合確認
  • ライブクエリでデータ複製なしに PromQL で直接クエリ
  • RED メトリクスベースのアプリケーション監視
  • OpenTelemetry GenAI 規約で LLM エージェント実行フローを追跡

🌟 主要機能

1 Prometheus ネイティブ統合

  • 📈OpenSearch UI から直接 PromQL 構文で Prometheus メトリクスをクエリ
  • 🔄ライブクエリアーキテクチャでデータ重複なしにリアルタイム参照
  • 📊ログ・トレースと同一ワークスペースで並行確認
  • 🔗サービスダッシュボードに Prometheus メトリクスをオーバーレイ表示

2 RED メトリクス監視

📊 Rate
リクエスト頻度
🚨 Errors
エラー率
⏱️ Duration
レイテンシー

3 つの指標を統合的に可視化し、遅いトレースからログへの相関分析をワンクリックで実行

3 AI エージェントトレーシング

  • 🤖OpenTelemetry GenAI セマンティック規約に準拠
  • 🔍プロンプト送信、モデル推論、ツール呼び出しを可視化
  • ⚡各ステップのレイテンシーやエラーを特定
  • 🔧複雑なエージェントワークフローのデバッグに対応

⚙️ 設定方法

📌 前提条件

1️⃣OpenSearch Service ドメインが対応リージョンで稼働
2️⃣Managed Service for Prometheus ワークスペースが設定済み

Step 1: Prometheus データソース接続

YAML OpenTelemetry Collector 設定例 
receivers:
  otlp:
    protocols:
      grpc:
        endpoint: 0.0.0.0:4317
      http:
        endpoint: 0.0.0.0:4318

exporters:
  prometheusremotewrite:
    endpoint: "https://aps-workspaces.<region>.amazonaws.com/workspaces/<workspace-id>/api/v1/remote_write"
    auth:
      authenticator: sigv4auth
  otlp/opensearch:
    endpoint: "https://<opensearch-domain-endpoint>"

extensions:
  sigv4auth:
    region: "<region>"
    service: "aps"

service:
  extensions: [sigv4auth]
  pipelines:
    metrics:
      receivers: [otlp]
      exporters: [prometheusremotewrite]
    traces:
      receivers: [otlp]
      exporters: [otlp/opensearch]

Step 2: AI エージェントトレーシング計装

Python OpenTelemetry GenAI 計装例 
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor
from opentelemetry.exporter.otlp.proto.grpc.trace_exporter import OTLPSpanExporter

provider = TracerProvider()
processor = BatchSpanProcessor(
    OTLPSpanExporter(endpoint="http://localhost:4317")
)
provider.add_span_processor(processor)
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("llm-agent")

# LLM エージェント実行のトレーシング
with tracer.start_as_current_span("agent.workflow") as workflow_span:
    workflow_span.set_attribute("gen_ai.system", "openai")

    with tracer.start_as_current_span("gen_ai.chat") as chat_span:
        chat_span.set_attribute("gen_ai.request.model", "gpt-4")
        chat_span.set_attribute("gen_ai.usage.prompt_tokens", 150)
        chat_span.set_attribute("gen_ai.usage.completion_tokens", 50)

    with tracer.start_as_current_span("agent.tool_call") as tool_span:
        tool_span.set_attribute("gen_ai.tool.name", "search_documents")
        tool_span.set_attribute("gen_ai.tool.status", "success")

✅ メリット

📈 ビジネス面

💰大幅なコスト削減: ライブクエリでデータ重複不要、プレミアムプラットフォーム比で大幅削減
🚀運用効率の向上: 単一 UI で確認、複数ツール間のコンテキストスイッチング不要
🤖AI エージェント可視化: LLM 実行フローの詳細トレースで品質管理・デバッグが容易に

🔧 技術面

📈PromQL ネイティブサポート: 既存クエリ資産をそのまま活用、学習コスト最小
🌐OpenTelemetry 標準準拠: ベンダーロックイン回避
🔗統合相関分析: トレース → ログのドリルダウン、メトリクスオーバーレイ
📐スケーラブル: ライブクエリでストレージコスト抑制

⚠️ デメリット・制約事項

制限事項

🌍利用可能リージョンは 20 リージョンに限定
📡ライブクエリは Amazon Managed Service for Prometheus が前提 (セルフホスト型は対象外)
🤖AI トレーシングは OpenTelemetry GenAI 規約準拠の計装が必要 (独自形式は非対応)

考慮すべき点

⏱️ライブクエリではネットワークレイテンシーによる若干の遅延の可能性
🔄既存ツールからの移行にはダッシュボード再構築・アラート再設定が必要
💻AI トレーシング計装には OpenTelemetry SDK 組み込みの開発工数
🔧RED メトリクスの効果最大化にはサービスメッシュや計装が前提

💡 ユースケース

🔧 UC1: マイクロサービスの統合障害調査

RED メトリクスで異常を検知し、同一画面でトレースを確認。遅延原因のスパンを特定 → ログにドリルダウンして MTTR を大幅短縮

🤖 UC2: LLM エージェントのパフォーマンス最適化

カスタマーサポートエージェントの応答速度低下を調査。各ステップ (ナレッジベース検索、LLM 推論、ツール呼び出し) のレイテンシーを個別計測しボトルネックを特定

💰 UC3: オブザーバビリティスタック統合

Prometheus にメトリクス保持 + OpenSearch UI からライブクエリ参照、ログ・トレースは OpenSearch に集約。データ重複排除でコスト削減、プレミアムライセンスも不要に

📝 まとめ

Amazon OpenSearch Service の統合オブザーバビリティ体験は、メトリクス、ログ、トレース、AI エージェントトレーシングを単一のインターフェースに統合する重要なアップデートです。Amazon Managed Service for Prometheus とのネイティブ統合によりデータ複製なしに PromQL でメトリクスを参照でき、プレミアムオブザーバビリティプラットフォームと比較して大幅なコスト削減が期待できます。特に、生成 AI アプリケーションの運用監視を検討しているチームは、OpenTelemetry GenAI セマンティック規約に基づくエージェントトレーシング機能を活用し、LLM エージェントの実行フローの可視化と最適化に取り組むことを推奨します。
