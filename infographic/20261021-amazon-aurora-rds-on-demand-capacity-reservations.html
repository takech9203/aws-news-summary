🗄️ On-Demand Capacity Reservations

DB インスタンスのコンピュートキャパシティを AZ 単位で事前予約し、InsufficientCapacity エラーを防止

📝 概要

Amazon Aurora および Amazon RDS が On-Demand Capacity Reservations (ODCR) をサポートしました。 リージョン内の 1 つ以上のアベイラビリティーゾーン (AZ) で、DB インスタンス用のコンピュートキャパシティを必要な期間だけ予約できます。 これにより、create / restore / scale-compute / start の各操作が InsufficientCapacity エラーで失敗することを防げます。

予約方式は「即時利用」(コミットメント不要、いつでもキャンセル可能) と「将来日付のスケジュール」(5〜120 日先に開始、最低コミットメント期間あり) の 2 つから選択できます。 移行、製品ローンチ、季節的なピーク (年末商戦など)、高可用性構成、災害対策 (DR) といったビジネスクリティカルなイベントの前に、確実にキャパシティを確保したいユーザーに有用です。

❌ Before: アップデート前の課題
  • Aurora / RDS にキャパシティ予約の仕組みがなく、作成・復元・スケーリング・起動時に AZ のキャパシティ不足で操作が失敗するリスクがあった
  • 大規模移行やセール期間などのピークイベント前に、キャパシティを事前確保する手段がなかった
  • DR 戦略でフェイルオーバー先やリストア先のキャパシティが確保できる保証がなかった
  • Reserved DB Instances / Database Savings Plans は料金割引のみで、物理的なキャパシティは予約されない
✅ After: アップデート後の改善
  • 特定の DB インスタンスクラス・エンジン・AZ の組み合わせでキャパシティを事前予約し、操作の失敗を防止
  • 即時利用の予約はコミットメント不要で、不要になったらいつでもキャンセル可能
  • 将来のイベントに備えて 5〜120 日先に開始する予約をスケジュール可能
  • Reserved DB Instances / Savings Plans の割引が予約上のインスタンスにも自動適用され、キャパシティ確保と割引を両立

管理者が複数 AZ にキャパシティ予約を作成し、DB インスタンス作成時に予約 ID (dbcr-) または予約名を指定して予約キャパシティへ配置する流れです。 Multi-AZ 構成では、プライマリとスタンバイがそれぞれの AZ の予約キャパシティを消費します。

⚙️ 主要機能

1️⃣ コンピュートキャパシティの予約
  • DB インスタンスクラス (例: db.r7g.large)、データベースエンジン (例: RDS for PostgreSQL)、1 つ以上の AZ、AZ ごとの予約数の組み合わせでキャパシティを保持
  • 複数のライセンスモデルを持つエンジン (Oracle など) では license-included / bring-your-own-license のいずれかを指定
  • 予約は dbcr- プレフィックス付きの ID と、作成時に付与する名前で識別
  • create / restore / scale-compute / start 操作がキャパシティ不足で失敗することを防止
2️⃣ ターゲット型の予約消費
  • 予約の ID または名前を明示的に指定した場合のみ予約を消費する「ターゲット型」
  • 予約を作成しただけでは、予約を指定しない他の DB インスタンスの配置には影響しない
  • DB インスタンスのエンジン、インスタンスクラス、ライセンスモデル、AZ が予約と一致し、その AZ に空きキャパシティがあることが必要
3️⃣ Multi-AZ 配置のサポート
  • 2 つ以上の AZ を指定すると、各 AZ に同じキャパシティが予約される
  • Multi-AZ DB インスタンスでは、プライマリとスタンバイの両方の AZ に空きキャパシティが必要
4️⃣ 2 つの予約方式
  • 即時利用: 作成と同時にキャパシティが予約され課金が開始。コミットメント不要で、いつでもキャンセル可能
  • 将来日付のスケジュール: 開始日を 5〜120 日先に設定し、最低コミットメント期間 (14 日、X ファミリーは 12 週間) を指定。開始日までは課金されない

🛠️ 設定方法

✅ 前提条件

✓Amazon Aurora または Amazon RDS を利用できる AWS アカウント
✓予約キャパシティは On-Demand DB インスタンスのアカウントクォータの範囲内であること (既存インスタンス数 + 未使用予約キャパシティがクォータにカウントされる)
✓AWS CLI を使用する場合は、ODCR 対応バージョンへの更新

ステップ 1: キャパシティ予約の作成 (即時利用)

Bash 即時利用の予約を作成 
aws rds create-db-capacity-reservation \
    --db-capacity-reservation-name my-multi-az-reservation \
    --engine postgres \
    --db-instance-class db.r7g.large \
    --availability-zones us-east-1a us-east-1b \
    --capacity-per-availability-zone 2

RDS for PostgreSQL の db.r7g.large 用に、us-east-1a と us-east-1b の 2 つの AZ にそれぞれ 2 インスタンス分のキャパシティを即時予約します。レスポンスで dbcr- プレフィックス付きの予約 ID が返され、状態が active になると利用可能です。課金は作成と同時に開始されます。

ステップ 2: 将来日付の予約の作成 (スケジュール)

Bash 将来日付のスケジュール予約を作成 
aws rds create-db-capacity-reservation \
    --db-capacity-reservation-name peak-reservation \
    --engine postgres \
    --db-instance-class db.r7g.large \
    --availability-zones us-east-1a \
    --capacity-per-availability-zone 16 \
    --start-date 2026-11-01T00:00:00Z \
    --commitment-duration 1209600

--start-date で開始日 (5〜120 日先)、--commitment-duration でコミットメント期間を秒単位 (1209600 秒 = 14 日) で指定します。予約は assessing 状態で作成され、受理されると scheduled になり、開始日に active へ移行します。開始日までは課金されません。

ステップ 3: 予約を指定して DB インスタンスを作成

Bash 予約キャパシティ内に DB インスタンスを作成 
aws rds create-db-instance \
    --db-instance-identifier my-db-instance \
    --engine postgres \
    --db-instance-class db.r7g.large \
    --availability-zone us-east-1a \
    --allocated-storage 100 \
    --master-username admin \
    --manage-master-user-password \
    --db-capacity-reservation-identifier my-multi-az-reservation

--db-capacity-reservation-identifier に予約名または dbcr- ID を指定します。同じパラメータは restore-db-instance-from-db-snapshot、restore-db-instance-to-point-in-time、restore-db-instance-from-s3、create-db-instance-read-replica、modify-db-instance、start-db-instance でも使用できます。

ステップ 4: 予約の利用状況の確認

Bash 予約の状態と空きキャパシティを確認 
aws rds describe-db-capacity-reservations

予約の状態、AZ ごとの空きキャパシティ (AvailableCapacityPerAvailabilityZoneList)、コミットメント情報などを確認できます。DB インスタンスが予約に配置されると、該当 AZ の AvailableCapacity が減少します。

💡 メリット

💼 ビジネス面

✓ビジネスクリティカルなイベントの確実な実行: 移行、製品ローンチ、年末商戦などのピークイベント前にキャパシティを確保し、当日のキャパシティ不足リスクを排除できる
✓柔軟なコミットメント: 即時利用の予約はコミットメント不要でいつでもキャンセルでき、必要な期間だけキャパシティを確保できる
✓既存割引との併用: Reserved DB Instances や Database Savings Plans の割引が自動適用されるため、キャパシティ確保のために割引を諦める必要がない

🔩 技術面

✓運用操作の失敗防止: create / restore / scale-compute / start 操作が InsufficientCapacity で失敗しなくなり、DR のリストアやフェイルオーバー計画の信頼性が向上する
✓Multi-AZ 対応: 複数 AZ に同一キャパシティを予約でき、プライマリとスタンバイの両方の配置を保証できる
✓ターゲット型による影響の局所化: 予約を明示的に指定したインスタンスのみが予約を消費するため、既存ワークロードの配置に影響を与えない

⚠️ デメリット・制約事項

🚫 制限事項

✗1 つの予約は 1 つの DB インスタンスクラス、1 つのエンジン、(複数ある場合は) 1 つのライセンスモデルのみをカバー。異なる組み合わせには複数の予約が必要
✗予約は単一リージョン内の指定した AZ に限定され、他の AZ のインスタンスは予約を利用できない
✗RDS Custom (custom-oracle-*、custom-sqlserver-* エンジン) はサポート対象外
✗コンピュートキャパシティのみが予約対象で、ストレージ、I/O などは予約されない
✗将来日付の予約には、インスタンスファミリー (C / M / T / R / X)、世代 (M / R は第 7 世代以降)、最低規模 (AZ あたり 32 vCPU 以上)、最低コミットメント期間 (14 日、X ファミリーは 12 週間) の制約がある
✗予約キャパシティは同一アカウント内のマッチングする DB インスタンスにのみ適用される

🤔 考慮すべき点

⚠予約中はインスタンスの稼働有無にかかわらず、未使用分もオンデマンド料金相当で課金される。不要になった予約は速やかにキャンセルしないとコストが発生し続ける
⚠予約キャパシティは AZ あたりのキャパシティ x AZ 数でアカウントの On-Demand DB インスタンスクォータを消費する (例: 3 AZ x 3 インスタンスで 9 クォータ)
⚠DB インスタンスを停止しても予約のコストは変わらず、停止したインスタンス分は未使用予約として課金される
⚠既存インスタンスを設定変更なしで予約に移すには、インスタンス変更 (クラス / Multi-AZ / ライセンスモデルの変更を伴う) または停止後に予約を指定して起動する操作が必要
⚠将来日付の予約が delayed 状態になった場合、AWS は改訂された提供日を提示しない

🎯 ユースケース

🚚 ユースケース 1: オンプレミスから Aurora / RDS への大規模移行

シナリオ: 数十台の Oracle / PostgreSQL データベースを計画的に RDS へ移行する。移行当日にターゲットの AZ でキャパシティ不足が発生すると、移行ウィンドウを逃してしまう。

Bash 移行の 2 週間前に移行先 AZ のキャパシティをスケジュール予約 
aws rds create-db-capacity-reservation \
    --db-capacity-reservation-name migration-wave1 \
    --engine oracle-se2 \
    --db-instance-class db.r7i.large \
    --availability-zones ap-northeast-1a \
    --capacity-per-availability-zone 20 \
    --license-model bring-your-own-license \
    --start-date 2026-11-10T00:00:00Z \
    --commitment-duration 1209600
✨ 効果: 移行当日に必要なキャパシティが保証され、移行プロジェクトのスケジュールリスクを低減できる。
🛒 ユースケース 2: 年末商戦などの季節的ピークへの備え

シナリオ: EC サイトが第 4 四半期のセールイベントに向けて、リードレプリカの追加やインスタンスクラスのスケールアップを計画している。ピーク直前のスケール操作がキャパシティ不足で失敗する事態を避けたい。

Bash ピーク前に予約し、ピーク時に予約を指定してスケールアップ 
# ピーク前にスケールアップ先クラスのキャパシティを予約
aws rds create-db-capacity-reservation \
    --db-capacity-reservation-name q4-peak \
    --engine postgres \
    --db-instance-class db.r7g.4xlarge \
    --availability-zones us-east-1a us-east-1b \
    --capacity-per-availability-zone 4

# ピーク時に予約を指定してスケールアップ
aws rds modify-db-instance \
    --db-instance-identifier prod-db \
    --db-instance-class db.r7g.4xlarge \
    --db-capacity-reservation-identifier q4-peak \
    --apply-immediately
✨ 効果: ピーク時のスケール操作が確実に成功し、イベント終了後は予約をキャンセルして余分なコストを抑えられる。
🛡️ ユースケース 3: 災害対策 DR のリストア先キャパシティ確保

シナリオ: DR 計画として、障害発生時にスナップショットからのリストアやポイントインタイムリカバリを想定している。大規模障害時には同一 AZ への需要が集中し、リストアがキャパシティ不足で失敗する可能性がある。

Bash DR 用の予約を常時保持し、障害時に予約を指定してリストア 
# DR 用の予約を常時保持 (Multi-AZ 用に 2 AZ)
aws rds create-db-capacity-reservation \
    --db-capacity-reservation-name dr-reservation \
    --engine postgres \
    --db-instance-class db.r7g.2xlarge \
    --availability-zones us-west-2a us-west-2b \
    --capacity-per-availability-zone 2

# 障害時に予約を指定してリストア
aws rds restore-db-instance-from-db-snapshot \
    --db-instance-identifier dr-restored \
    --db-snapshot-identifier prod-snapshot \
    --db-instance-class db.r7g.2xlarge \
    --availability-zone us-west-2a \
    --db-capacity-reservation-identifier dr-reservation
✨ 効果: 障害時のリストアが確実に成功し、RTO (目標復旧時間) の達成確度が向上する。Reserved DB Instances の割引を組み合わせれば、予約の維持コストも軽減できる。

💰 料金

キャパシティ予約は、予約期間中、DB インスタンスの稼働有無にかかわらず該当 DB インスタンスクラスのオンデマンド料金相当で課金されます。前払い料金はありません。

✓予約にマッチする DB インスタンスが稼働している間は、インスタンスの料金のみが課金され、その分の予約には追加料金が発生しない
✓未使用の予約キャパシティは「未使用予約」として請求書に表示される
✓課金は秒単位 (最低 60 秒) で計算される
✓予約はコンピュートキャパシティのみが対象で、ストレージ、I/O、バックアップストレージは通常どおり課金される
✓Reserved DB Instances / Database Savings Plans の割引は、マッチする使用分に自動適用される

💵 料金例

米国東部 (オハイオ) リージョンで db.m7g.large (オンデマンド料金 $0.168/時間と仮定) を 1 ユニット予約した場合の例です。

時間帯予約と DB インスタンスの状態課金 (概算)
1 時間目予約はアクティブ、未使用未使用予約として $0.168
2〜5 時間目DB インスタンスが予約内で稼働DB インスタンス料金 $0.168/時間のみ (予約の追加料金なし)
6 時間目予約をキャンセル、インスタンスは予約外で稼働オンデマンドの DB インスタンス料金 $0.168

詳細は Amazon RDS の料金ページ を参照してください。

🌍 利用可能リージョン

すべての AWS 商用リージョンで、Amazon Aurora と Amazon RDS の両方に対して利用可能です。

🔗 関連サービス・機能

Reserved DB Instances: 1 年 / 3 年コミットメントによる料金割引。キャパシティ予約と併用すると、割引とキャパシティ確保の両方を実現できる
Database Savings Plans: 1 年コミットメントによる柔軟な料金割引。キャパシティ予約上の使用分にも自動適用される
Amazon EC2 On-Demand Capacity Reservations: EC2 で先行して提供されている同種の機能。今回のアップデートで同様の概念が Aurora / RDS にも拡張された
Amazon RDS Multi-AZ 配置: 複数 AZ への予約により、プライマリとスタンバイの両方の配置を保証できる

📌 まとめ

Aurora / RDS の On-Demand Capacity Reservations により、移行・ローンチ・季節ピーク・DR といった重要イベントで DB インスタンス操作がキャパシティ不足で失敗するリスクを排除できるようになりました。 即時利用はコミットメント不要で手軽に始められるため、まずは DR のリストア先やピークイベント前のスケールアップ先など、キャパシティ不足の影響が大きいシナリオでの活用を検討することを推奨します。

未使用分もオンデマンド料金相当で課金されるため、Reserved DB Instances / Database Savings Plans との併用と、不要になった予約の速やかなキャンセルを運用に組み込むことが重要です。
