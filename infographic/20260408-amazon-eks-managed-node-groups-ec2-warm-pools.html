Amazon EKS (Elastic Kubernetes Service)

マネージドノードグループの EC2 Auto Scaling ウォームプールサポート

事前初期化済みインスタンスでスケールアウトレイテンシーを大幅短縮
2026 年 4 月 8 日

📋 概要

Amazon EKS マネージドノードグループが EC2 Auto Scaling ウォームプールをサポートしました。ウォームプールとは、事前に初期化された EC2 インスタンスを待機状態で保持する仕組みで、スケールアウト時のノードプロビジョニングレイテンシーを大幅に短縮できます。

バーストトラフィックパターンを持つアプリケーション、時間に敏感なワークロード、複雑な初期化スクリプトやソフトウェア依存関係によりインスタンスの起動に時間がかかる環境に最適です。

🔄 Before / After

❌ アップデート前の課題
  • スケールアウト時に OS 初期化、ユーザーデータ実行、ソフトウェア設定を全て実行する必要がありノード追加に数分以上
  • バーストトラフィック対応のため常に余剰キャパシティを Running 状態で保持しコスト増大
  • 複雑な初期化処理を持つワークロードでスケールアウトのレイテンシーが特に深刻
✅ アップデート後の改善
  • 事前初期化済みインスタンスをウォームプールに保持しスケールアウトレイテンシーを大幅短縮
  • Stopped 状態でインスタンスを保持し Running 状態より低コストでウォームキャパシティを維持
  • Cluster Autoscaler との連携が追加設定なしで動作しシームレスに統合

🔀 インスタンス状態の選択

ウォームプール内のインスタンスは Stopped または Running の 2 つの状態から選択できます。コストとレイテンシーのバランスに応じて選択してください。

🛑 Stopped 状態
  • → インスタンスを停止状態で保持
  • → 低コスト: EBS ボリューム料金のみ
  • → アクティブへの移行に再起動時間が必要
  • → コスト重視のシナリオに最適
▶️ Running 状態
  • → インスタンスを実行状態で保持
  • → 高コスト: 通常の EC2 インスタンス料金
  • → アクティブへの移行が最速
  • → レイテンシー重視のシナリオに最適

🚀 主要機能

🔥 ウォームプールによる事前初期化

OS の初期化、ユーザーデータの実行、ソフトウェアの設定が完了済みのインスタンスをプールに保持。需要増加時にコールドスタートシーケンスをスキップして高速にスケールアウトし、プロビジョニングレイテンシーを大幅に短縮。

♻️ スケールイン時の再利用

スケールイン時にインスタンスを終了せずウォームプールに戻す再利用ポリシーを設定可能。インスタンスの再初期化コストを削減し、リソースの効率的な循環を実現。

🔗 Cluster Autoscaler との統合

追加設定なしで Cluster Autoscaler と連携。既存のスケーリングポリシーやメトリクスをそのまま利用可能で、シームレスにウォームプールを活用できます。

🛠️ 複数の管理ツール対応

EKS API、AWS CLI、EKS コンソール、CloudFormation から設定可能。既存の IaC ワークフローに統合して管理できます。

📐 技術仕様

項目 詳細
インスタンス状態Stopped (低コスト、移行に時間) または Running (高コスト、高速移行)

ウォームプール設定例

JSON ウォームプール設定パラメータ 
{
  "nodegroupName": "my-nodegroup",
  "scalingConfig": {
    "minSize": 2,
    "maxSize": 10,
    "desiredSize": 3
  },
  "warmPoolConfig": {
    "poolState": "Stopped",
    "maxGroupPreparedCapacity": 3,
    "instanceReusePolicy": {
      "reuseOnScaleIn": true
    }
  }
}

ステップ 1: 既存のノードグループにウォームプールを有効化

Bash マネージドノードグループにウォームプールを設定 
# AWS CLI を使用してマネージドノードグループにウォームプールを設定
aws eks update-nodegroup-config \
    --cluster-name my-cluster \
    --nodegroup-name my-nodegroup \
    --scaling-config minSize=2,maxSize=10,desiredSize=3 \
    --region us-west-2

ステップ 2: ウォームプールの状態を確認

Bash ノードグループの詳細を確認 
# ノードグループの設定とウォームプールの状態を確認
aws eks describe-nodegroup \
    --cluster-name my-cluster \
    --nodegroup-name my-nodegroup \
    --region us-west-2

⚖️ メリット・デメリット

✅ ビジネス面のメリット

  • バーストトラフィック時のスケールアウトレイテンシーを短縮しエンドユーザー体験を向上
  • Stopped 状態のインスタンスで常時 Running より低コストにウォームキャパシティを維持
  • Cluster Autoscaler との自動連携で追加の運用負荷なし

✅ 技術面のメリット

  • 事前初期化済みインスタンスによりコールドスタートの待ち時間を排除
  • Stopped と Running の 2 つの状態からコストとレイテンシーのバランスに応じて選択可能
  • スケールイン時のインスタンス再利用でリソースの効率的な循環を実現

⚠️ 制限事項・考慮点

  • ウォームプール内のインスタンスにも EC2 の料金が発生 (Stopped 状態でも EBS ボリューム料金が発生)
  • 中国リージョンでは利用不可
  • ウォームプールのサイズ管理を適切に行わないと不要なコストが発生する可能性あり
  • Stopped 状態から Running 状態への移行にはインスタンスの再起動時間がかかるため完全にゼロレイテンシーではない
  • Running 状態でウォームプールを維持すると通常の EC2 インスタンス料金が発生するためコストメリットを慎重に評価する必要あり

🎯 ユースケース

🛒 ユースケース 1: E コマースのフラッシュセール対応
E コマースサイトで定期的にフラッシュセールを実施しており、セール開始時に急激なトラフィック増加が発生。通常のスケールアウトでは新しいノードのプロビジョニングに数分かかり、セール開始直後にリクエストが処理しきれない。
Bash フラッシュセール用ノードグループ設定 
# Stopped 状態で 5 台の事前初期化済みインスタンスを保持
aws eks update-nodegroup-config \
    --cluster-name ecommerce-cluster \
    --nodegroup-name flash-sale-nodes \
    --region ap-northeast-1
→ セール開始時に事前初期化済みのインスタンスが即座にアクティブになり、コールドスタートによるレイテンシーを排除してスムーズなスケールアウトを実現
🤖 ユースケース 2: バッチ処理ワークロードの高速起動
機械学習のトレーニングジョブを定期的に実行しており、GPU インスタンスの初期化に CUDA ドライバやライブラリのインストールが必要で、コールドスタートに 10 分以上かかる。
Bash GPU ノードグループ設定 
# Running 状態で最速の移行を実現
aws eks update-nodegroup-config \
    --cluster-name ml-cluster \
    --nodegroup-name gpu-nodes \
    --region us-east-1
→ 事前に CUDA 環境が構築済みのインスタンスがウォームプールに待機しているため、トレーニングジョブの開始待ち時間を大幅に短縮
🕐 ユースケース 3: 営業時間に連動したスケーリング
SaaS アプリケーションで営業時間帯にトラフィックが増加し夜間は低下するパターン。毎朝のスケールアウト時に複雑な初期化処理が必要で、ユーザーの業務開始時に遅延が発生。
Bash SaaS アプリケーション用設定 
# スケールイン時にインスタンスをウォームプールに保持
aws eks update-nodegroup-config \
    --cluster-name saas-cluster \
    --nodegroup-name app-nodes \
    --region eu-west-1
→ 夜間のスケールイン時にインスタンスをウォームプールに戻し、翌朝のスケールアウト時に再利用することで毎日の初期化コストを削減し業務開始時の遅延を解消

💰 料金

ℹ️ ウォームプール機能自体に追加料金はかかりません。ウォームプール内のインスタンスに対して EC2 関連の料金が発生します。
インスタンス状態 月額料金 (概算)
Stopped 状態 (m5.xlarge x 3 台、各 50GB EBS)EBS ボリューム料金のみ: 約 $15/月
Running 状態 (m5.xlarge x 3 台)通常の EC2 料金: 約 $420/月
アクティブインスタンス (m5.xlarge x 5 台)通常の EC2 + EKS 料金

補足

  • EKS コントロールプレーン: クラスターあたり $0.10/時間
  • Stopped インスタンス: EBS ボリュームの料金のみ (インスタンス料金は停止中は非課金)
  • Running インスタンス: 通常の EC2 インスタンス料金が適用

🌍 利用可能リージョン

Amazon EKS が利用可能な全ての AWS リージョンで提供されています。ただし、中国リージョンは除きます。
