Amazon MSK

🔐 MSK Replicator が外部 Apache Kafka からの
mTLS 認証をサポート

📅 リリース: 2026 年 6 月 22 日

📌 概要

Amazon MSK Replicator が、外部 Apache Kafka クラスターから Amazon MSK Express ブローカーへのデータレプリケーションにおいて、 相互 TLS (mTLS) 認証をサポートしました。 ここでいう外部クラスターには、オンプレミス環境、AWS 上の自己管理型クラスター、他クラウドプロバイダー上のクラスターが含まれます。

MSK Replicator は Kafka クラスター間のデータレプリケーションを自動化するフルマネージド機能です。 これまで外部 Apache Kafka への接続でサポートされていた認証方式は SASL/SCRAM のみでしたが、 今回のアップデートで mTLS によるクライアント認証を必須とするクラスターも レプリケーション元として利用できるようになりました。

⚠️ アップデート前の課題
  • 外部 Kafka への接続は SASL/SCRAM のみ対応。mTLS 必須クラスターは利用不可
  • mTLS クラスターからの移行には認証方式の変更や独自基盤の構築が必要
  • 証明書ベースの相互認証を求める環境ではマネージドなレプリケーション手段を選べなかった
✅ アップデート後の改善
  • 認証方式を変更せず mTLS クラスターから MSK Express へレプリケーション可能
  • 移行・DR・ハイブリッド/マルチクラウド配信がマネージド機能だけで実現
  • トピック名維持・無限ループ自動回避・オフセット双方向同期を mTLS 環境でも享受

mTLS で構成された外部 Apache Kafka から、MSK Replicator が Secrets Manager に保管したクライアント証明書を使って接続し、 MSK Express ブローカーへデータをレプリケーションする構成です。

⚡ 主要機能

🔐 mTLS 認証によるレプリケーション元接続
  • 従来の SASL/SCRAM に加えて mTLS (相互 TLS) をサポート
  • クライアントとサーバーが互いに証明書を提示し、証明書ベースの相互認証が必須のクラスターにも対応
  • クライアント証明書と秘密鍵は AWS Secrets Manager に保管し、レプリケーター作成時に Secret の ARN を指定
🏷️ 元のトピック名維持と無限ループ自動回避
  • 元の Kafka トピック名をそのまま維持でき、移行先でのトピック名変更が不要
  • 双方向レプリケーション構成でも無限レプリケーションループを自動回避
🔄 コンシューマーグループオフセットの双方向同期
  • オフセットを双方向に同期し、プロデューサーとコンシューマーを順序に依存せず独立して移動可能
  • シームレスなアプリケーションのカットオーバー (切り替え) を実現
⚙️ フルマネージドな運用
  • レプリケーションに必要なリソースを自動的にスケール。容量の監視やスケーリングは不要
  • カスタムコードの記述、独自インフラの管理、クロスリージョンネットワーキングの設定が不要

🔧 技術仕様

認証方式の比較

認証方式レプリケーション元 (外部 Kafka)概要
SASL/SCRAM ✅ サポート (従来から) ユーザー名とパスワードによる認証。認証情報を Secrets Manager に保管
mTLS 🆕 サポート (今回追加) クライアント証明書と秘密鍵による相互 TLS 認証。証明書を Secrets Manager に保管

🛠️ 設定方法

前提条件

  • レプリケーション元の Apache Kafka クラスターが mTLS 認証で構成されていること (Kafka 2.8.1 以上が推奨)
  • 外部クラスターと AWS 間にネットワーク接続 (Direct Connect、Site-to-Site VPN、VPC ピアリング、Transit Gateway など) が確立されていること
  • ターゲットとなる MSK Express ブローカーのクラスター (IAM 認証有効) が作成済みであること
  • クライアント証明書・秘密鍵を保管した Secrets Manager の Secret、および SSL ハンドシェイク用のルート CA 証明書が用意されていること
  • レプリケーター実行用の IAM ロール (kafka.amazonaws.com を信頼) が作成済みであること

レプリケーター作成

ステップ 1: 認証情報を Secrets Manager に保管

Bashcreate-secret
aws secretsmanager create-secret \
  --name AmazonMSK_external_kafka_mtls \
  --secret-string file://mtls-client-credentials.json

外部 Kafka への mTLS 接続に使うクライアント証明書・秘密鍵を Secret として登録します。MSK Replicator はこの Secret を参照して相互認証を行います。

ステップ 2: クラスター定義ファイルで mTLS を指定

JSONkafka-clusters.json
{
  "ApacheKafkaCluster": {
    "ApacheKafkaClusterId": "your-source-cluster-id",
    "BootstrapBrokerString": "broker1:9094,broker2:9094"
  },
  "VpcConfig": {
    "SecurityGroupIds": ["sg-xxxxxxxx"],
    "SubnetIds": ["subnet-xxxxxxxx", "subnet-yyyyyyyy"]
  },
  "ClientAuthentication": {
    "MTLS": {
      "SecretArn": "arn:aws:secretsmanager:region:account-id:secret:AmazonMSK_external_kafka_mtls"
    }
  },
  "EncryptionInTransit": {
    "EncryptionType": "TLS",
    "RootCaCertificate": "arn:aws:secretsmanager:region:account-id:secret:root-ca-secret"
  }
}

MTLS.SecretArn にステップ 1 で作成した Secret の ARN を指定します。

ステップ 3: レプリケーターを作成

Bashcreate-replicator
aws kafka create-replicator \
  --replicator-name external-kafka-to-express \
  --kafka-clusters file://kafka-clusters.json \
  --replication-info-list file://replication-info.json \
  --service-execution-role-arn arn:aws:iam::account-id:role/MSKReplicatorRole \
  --log-delivery file://log-delivery.json

元のトピック名を維持する場合は、replication-info.json 内の TopicReplication.TopicNameConfiguration.Type を IDENTICAL に設定します。

💡 メリット

ビジネス面

✓セキュリティ要件への適合: 証明書ベースの相互認証が必須のポリシー下でもマネージド機能でレプリケーションを実現
✓移行コストの削減: 既存 mTLS クラスターの認証方式を変更せず移行でき、工数とリスクを低減
✓事業継続性の向上: MSK Express ベースのクラスターをフェイルオーバー/バックアップ先とした DR 構成を構築可能

技術面

✓運用負荷の低減: カスタムのレプリケーション基盤やオープンソースツールの構築・運用が不要
✓シームレスなカットオーバー: オフセット双方向同期により、任意の順序でプロデューサー/コンシューマーを移行
✓アプリケーション変更の最小化: 元のトピック名を維持でき、移行先でのトピック名変更が不要

⚠️ デメリット・制約事項

制限事項

✗mTLS 認証によるレプリケーションは、ターゲットが MSK Express ブローカーの場合にサポート
✗本機能は MSK Express ブローカーが利用可能な AWS リージョンに限定
✗MSK クラスター間のレプリケーションでは、元とターゲットが同一 AWS アカウントにある必要がある (外部 Kafka とは要件が異なる)

考慮すべき点

⚠️外部クラスターと AWS 間のネットワーク接続を別途構成し、IP ルーティングと DNS 解決を検証する必要がある
⚠️mTLS 用クライアント証明書には有効期限があるため、証明書のローテーションと Secrets Manager の更新運用を計画する
⚠️MessageLag、ReplicationLatency などを CloudWatch メトリクスで監視し、カットオーバーのタイミングを判断する

💰 料金と利用可能リージョン

料金: MSK Replicator はレプリケーションされたデータ量 (GB 単位) に基づく料金と、対象クラスターの基盤リソース関連料金が発生します。 mTLS 認証のサポート自体に追加料金はありません。証明書を保管する Secrets Manager、ログを配信する CloudWatch Logs などにはそれぞれの料金が適用されます。
利用可能リージョン: 本機能は Amazon MSK Express ブローカーが利用可能なすべての AWS リージョンでサポートされます。最新の対応リージョンは公式ドキュメントを参照してください。

🔗 関連サービス・機能

  • Amazon MSK Express ブローカー: レプリケーションのターゲットとなる、運用負荷を軽減した MSK のブローカータイプ
  • AWS Secrets Manager: mTLS 用のクライアント証明書・秘密鍵、ルート CA 証明書を安全に保管
  • Amazon CloudWatch: レプリケーションのログ配信、および MessageLag、ReplicationLatency などのメトリクス監視
  • AWS Direct Connect / Site-to-Site VPN / Transit Gateway: 外部 Kafka クラスターと AWS 間のネットワーク接続

📝 まとめ

今回のアップデートにより、mTLS 認証を必須とする外部 Apache Kafka クラスターからも、 マネージドな MSK Replicator を使って MSK Express ブローカーへデータをレプリケーションできるようになりました。 証明書ベースの相互認証が求められる環境での移行・災害復旧・ハイブリッド/マルチクラウド配信が大幅に容易になります。

mTLS クラスターからの MSK 移行を検討している場合は、Secrets Manager への証明書登録とネットワーク接続の準備から着手し、 AWS Blog のウォークスルーを参照して構成を進めることを推奨します。
