Amazon Managed Service for Prometheus Amazon MSK Amazon CloudWatch

📈 マネージドコレクターが Amazon MSK コンシューマーグループメトリクスの収集に対応

🗓️ リリース日: 2026 年 10 月 30 日 | Kafka エクスポーターの自前運用なしでコンシューマーラグを監視

📝 概要

Amazon Managed Service for Prometheus のマネージドコレクター (スクレイパー) が、Amazon MSK クラスターからの Kafka エクスポーターメトリクスとコンシューマーグループラグメトリクスの収集をサポートしました。マネージドコレクターがマネージド Kafka エクスポーターを実行し、コンシューマーラグ、コミット済みオフセット、コンシューマーグループのメンバー数などを自動収集します。

収集先には Prometheus ワークスペースと Amazon CloudWatch の両方を指定可能。コレクターは IAM 認証でクラスターに接続し、アクセス許可は MSK クラスターポリシーで付与します。Open Monitoring 経由の JMX / Node Exporter メトリクスを補完する位置づけで、コンシューマーグループメトリクスの収集に Open Monitoring は不要です。

😣 Before: アップデート前の課題

  • コンシューマーラグを Prometheus 形式で取得するには kafka_exporter などを EC2 / EKS 上で自前にデプロイ・運用する必要があった
  • エクスポーターのパッチ適用、スケーリング、可用性確保などの運用負荷が発生
  • マネージドコレクターで収集できるのは Open Monitoring 経由の JMX / Node Exporter メトリクスに限られ、コンシューマーグループ単位のラグ監視には追加の仕組みが必要

😊 After: アップデート後の改善

  • マネージドコレクターがマネージド Kafka エクスポーターを実行し、エクスポーターのインストール・運用が不要に
  • コンシューマーラグ、コミット済みオフセット、メンバー数を自動収集
  • Prometheus ワークスペースに加えて CloudWatch も配信先に選択でき、PromQL で分析可能
  • topicFilter と consumerGroupFilter で収集対象を正規表現で絞り込み可能

マネージドコレクターがサービスリンクロールと MSK クラスターポリシーに基づく IAM 認証でクラスターに接続し、コンシューマーグループメトリクスを収集して Amazon Managed Service for Prometheus ワークスペースまたは Amazon CloudWatch に配信する構成です。

⚡ 主要機能

🤖 マネージド Kafka エクスポーターによる自動収集

  • マネージドコレクターがエクスポーターを実行するため、ユーザー側でのインストール・運用が不要
  • コンシューマーラグ、コミット済みオフセット、コンシューマーグループメンバー数を収集
  • スクレイプ設定に job_name: kafka-exporter のジョブを含めることで有効化。スクレイプターゲットの指定は不要で、コレクターが自動的に接続を構成

🔐 IAM 認証と MSK クラスターポリシーによるアクセス制御

  • コレクターはサービスリンクロールを使用し、IAM 認証 (ポート 9098) で MSK ブローカーに接続
  • MSK クラスターポリシーで kafka-cluster:Connect、kafka-cluster:DescribeTopic、kafka-cluster:DescribeGroup を付与
  • ポリシー追加後は自動的に収集が開始され、スクレイパーの更新は不要

🎯 トピックとコンシューマーグループのフィルタリング

  • create-scraper / update-scraper の exporters フィールドに kafkaConfiguration を指定し、topicFilter と consumerGroupFilter を正規表現 (^ で始まり $ で終わる、最大 256 文字) で設定可能
  • フィルターを省略するとすべてのトピック・コンシューマーグループが対象
  • metric_relabel_configs で収集するメトリクスをさらに絞り込み可能

📊 2 つの配信先をサポート

  • Amazon Managed Service for Prometheus ワークスペース (ampConfiguration)
  • Amazon CloudWatch (cloudWatchConfiguration)。CloudWatch 側では Query Studio から PromQL でクエリ可能

🔬 技術仕様

📏 収集されるコンシューマーグループメトリクス

⏳
kafka_consumergroup_lag
コンシューマーグループのラグ (未処理メッセージ数)
📍
kafka_consumergroup_current_offset
コミット済みオフセット (コミットがない場合は -1)
👥
kafka_consumergroup_members
コンシューマーグループのメンバー数

付与されるラベルには clusterArn (relabel で付与推奨)、consumergroup、topic、partition が含まれます。エクスポーターはトピック・パーティションのオフセットなどの追加メトリクスも送信できますが、一部は Open Monitoring や MSK 標準の CloudWatch メトリクスと重複するため、必要なものだけを metric_relabel_configs で keep する構成が推奨されています。

🛠️ 設定方法

📋 前提条件

Apache Kafka 3.6.0 以降の Amazon MSK Provisioned クラスター (Standard ブローカー、IAM 認証有効) がスクレイパーと同一アカウント・リージョンに存在すること
クラスターの VPC に異なる AZ の 2 つ以上のサブネットがあり、DNS が有効で、クラスターのセキュリティグループがスクレイパー用セキュリティグループからのポート 9098 の TCP 通信を許可していること
操作するユーザーに kafka:DescribeClusterV2、kafka:GetBootstrapBrokers、kafka-cluster:Connect、kafka-cluster:DescribeTopic、kafka:GetClusterPolicy、kafka:PutClusterPolicy などの権限があること
配信先がワークスペースの場合、スクレイパーと同一リージョンの Amazon Managed Service for Prometheus ワークスペースがあること。AWS CLI は kafkaConfiguration をサポートするバージョンであること
1

スクレイプ設定の作成

YAML msk-consumer.yaml 
global:
  scrape_interval: 30s
scrape_configs:
  - job_name: kafka-exporter
    relabel_configs:
      - target_label: clusterArn
        replacement: 'arn:aws:kafka:us-west-2:111122223333:cluster/my-cluster/cluster-id'
    metric_relabel_configs:
      - source_labels: [__name__]
        regex: kafka_consumergroup_(current_offset|members|lag)
        action: keep

ジョブ名は必ず kafka-exporter とする必要があり、含まれていない設定は拒否されます。relabel_configs で clusterArn ラベルを付与してクラスターを識別し、metric_relabel_configs でラグ・オフセット・メンバー数の 3 メトリクスのみを残しています。

2

スクレイパーの作成

Bash create-scraper 
aws amp create-scraper \
  --region us-west-2 \
  --alias msk-consumer-metrics \
  --source '{"vpcConfiguration":{"subnetIds":["subnet-id-1","subnet-id-2"],"securityGroupIds":["sg-id"]}}' \
  --exporters '[{"kafkaConfiguration":{"clusterArn":"arn:aws:kafka:us-west-2:111122223333:cluster/my-cluster/cluster-id","topicFilter":"^orders.*$","consumerGroupFilter":"^payments.*$"}}]' \
  --cli-binary-format base64 \
  --scrape-configuration "configurationBlob=$(base64 < msk-consumer.yaml | tr -d '\n')" \
  --destination '{"ampConfiguration":{"workspaceArn":"arn:aws:aps:us-west-2:111122223333:workspace/workspace-id"}}'

exporters の kafkaConfiguration で対象クラスターの ARN と、トピック・コンシューマーグループのフィルターを指定します。CloudWatch を配信先にする場合は --destination に {"cloudWatchConfiguration":{"datasetArn":"arn:aws:cloudwatch:us-west-2:111122223333:dataset/default"}} を指定します。作成後、aws amp describe-scraper でステータスが ACTIVE になるまで待ちます。

3

クラスターポリシーによるアクセス許可の付与

Bash クラスターポリシーの適用 
# スクレイパーのサービスリンクロール ARN を取得
aws amp describe-scraper \
  --region us-west-2 \
  --scraper-id scraper-id \
  --query scraper.roleArn --output text

# クラスターポリシーを適用
aws kafka put-cluster-policy \
  --region us-west-2 \
  --cluster-arn arn:aws:kafka:us-west-2:111122223333:cluster/my-cluster/cluster-id \
  --policy file://policy.json

スクレイパーのサービスリンクロール ARN を確認し、kafka-cluster:Connect、kafka-cluster:DescribeTopic、kafka-cluster:DescribeGroup を許可するクラスターポリシーを適用します。既存のポリシーがある場合は put-cluster-policy がポリシー全体を置き換えるため、既存のステートメントとマージして --current-version を指定します。ポリシー追加後、収集は自動的に開始されます。

4

メトリクスの確認

PromQL メトリクスの確認クエリ 
kafka_consumergroup_lag{clusterArn="arn:aws:kafka:us-west-2:111122223333:cluster/my-cluster/cluster-id"}

最初のメトリクスが表示されるまで数分かかる場合があります。メトリクスが表示されない場合は、クラスターポリシー、consumerGroupFilter の一致、ポート 9098 への接続性を確認します。

💡 メリット

💼 ビジネス面

運用コストの削減: Kafka エクスポーターの自前運用 (デプロイ、パッチ、スケーリング) が不要になり、監視基盤の運用負荷を削減
ストリーミング処理の品質向上: コンシューマーラグを継続的に監視し、処理遅延やボトルネックを早期に検出してビジネスへの影響を最小化
可観測性の統合: 既存の Prometheus / CloudWatch ベースの監視基盤に Kafka コンシューマーメトリクスを統合でき、ツールの分散を回避

⚙️ 技術面

フルマネージドな収集: コレクターがメトリクスの検出と収集を自動処理し、スクレイプターゲットの指定も不要
IAM ベースのセキュアな接続: サービスリンクロールとクラスターポリシーによるきめ細かなアクセス制御。認証情報の管理が不要
柔軟なフィルタリング: フィルターと metric_relabel_configs の 2 段階で収集対象を制御し、取り込みコストを最適化
JMX / Node Exporter メトリクスとの補完: 既存の Open Monitoring 連携と同じスクレイパーにジョブを追加でき、一元的に収集可能

⚠️ デメリット・制約事項

🚫 制限事項

Amazon MSK Serverless クラスターは非対応 (クラスターポリシーで kafka-cluster アクションを受け付けないため)。Serverless では MSK が CloudWatch に送信する標準メトリクスを使用
IAM 認証が有効になっていないクラスターは非対応
スクレイパーと異なるアカウントまたはリージョンのクラスターは非対応
Apache Kafka 3.6.0 以降の Provisioned クラスター (Standard ブローカー) のみ対応
1 つのスクレイパーに設定できるエクスポーターは 1 つのみ
フィルターは ^ で始まり $ で終わる正規表現で、最大 256 文字

🤔 考慮すべき点

スクレイプ設定に job_name: kafka-exporter のジョブが必須。含まれない設定は拒否される
スクレイパーが ACTIVE でも、クラスターポリシーを付与するまで Kafka メトリクスは収集されない。作成・更新リクエストの成功はクラスターへのアクセス可否を保証しない
クラスターポリシーのプリンシパルにアカウントルートやワイルドカード入りロール ARN は使用できない
スクレイパーを再作成するとサービスリンクロールの ARN が変わるため、クラスターポリシーの更新が必要
収集するメトリクスを増やすほど取り込むシリーズ数が増加し、コストに影響する
トピックやコンシューマーグループが非常に多いクラスターでは、フィルターを絞り込まないと収集に失敗する場合がある
収集を停止するにはクラスターポリシーの削除だけでは不十分で、先にエクスポーターの削除またはスクレイパーの削除が必要

🎯 ユースケース

1️⃣ ストリーミングアプリケーションのコンシューマーラグ監視とアラート

シナリオ: EC2 や ECS 上で動作するコンシューマーアプリケーションの処理遅延を検出したい。ラグが増加し続けている場合に通知を受け取り、処理のボトルネックに早期に対応する。

PromQL ラグベースのアラート例 
# コンシューマーグループごとのラグ合計が 10,000 を超えたらアラート
sum by (consumergroup) (kafka_consumergroup_lag{clusterArn="arn:aws:kafka:..."}) > 10000

効果: エクスポーターを運用することなくラグベースのアラートを構築でき、メッセージ処理の遅延によるデータ鮮度の劣化を早期に検出できる。

2️⃣ コンシューマーのスケーリング判断

シナリオ: コンシューマーグループのメンバー数とラグの関係を可視化し、コンシューマーの増減やパーティション数の見直しを判断する。

PromQL Grafana ダッシュボードでの可視化例 
# メンバー数とパーティションごとのラグを Grafana ダッシュボードで可視化
kafka_consumergroup_members{clusterArn="arn:aws:kafka:..."}
sum by (topic, partition) (kafka_consumergroup_lag{clusterArn="arn:aws:kafka:..."})

効果: 特定パーティションへのラグの偏りやメンバー数の不足をデータに基づいて把握し、スケーリングやリバランスの判断を客観的に行える。

3️⃣ CloudWatch への直接配信による監視の一元化

シナリオ: Prometheus ワークスペースを運用せず、CloudWatch を標準の監視基盤としている組織が、MSK のコンシューマーグループメトリクスも CloudWatch で監視したい。

Bash CloudWatch を配信先に指定 
aws amp create-scraper \
  --alias msk-consumer-metrics \
  --source '{"vpcConfiguration":{...}}' \
  --exporters '[{"kafkaConfiguration":{"clusterArn":"arn:aws:kafka:..."}}]' \
  --scrape-configuration "configurationBlob=..." \
  --destination '{"cloudWatchConfiguration":{"datasetArn":"arn:aws:cloudwatch:us-west-2:111122223333:dataset/default"}}'

効果: CloudWatch Query Studio の PromQL でコンシューマーグループメトリクスを分析でき、既存の CloudWatch アラーム・ダッシュボード運用に統合できる。

💰 料金・利用可能リージョン

💵 料金

マネージドコレクターと取り込みメトリクスの料金は、配信先に応じて Amazon Managed Service for Prometheus または Amazon CloudWatch の料金体系に従います。収集するメトリクス (シリーズ数) を増やすほど取り込み量が増加するため、metric_relabel_configs やフィルターで必要なメトリクスに絞り込むことがコスト最適化につながります。最新の料金は各サービスの料金ページを参照してください。

マネージド Prometheus コレクターが一般提供されているすべての AWS リージョンで利用可能です。詳細は AWS リージョン別サービス一覧を参照してください。

🔗 関連サービス・機能

📈 Amazon Managed Service for Prometheus

メトリクスの配信先となるマネージド Prometheus 互換サービス。マネージドコレクター (スクレイパー) 機能の提供元。

📊 Amazon CloudWatch

もう 1 つの配信先。Query Studio による PromQL クエリと既存のアラーム・ダッシュボードとの統合が可能。

📨 Amazon MSK

監視対象となるマネージド Apache Kafka サービス。Open Monitoring による JMX / Node Exporter メトリクスや標準の CloudWatch メトリクスも提供。

📉 Amazon Managed Grafana

Prometheus ワークスペースのメトリクスを可視化するダッシュボードとして活用可能。

✅ まとめ

マネージド Prometheus コレクターが Amazon MSK のコンシューマーグループメトリクスに対応したことで、Kafka エクスポーターの自前運用なしにコンシューマーラグの監視が可能になりました。ストリーミングアプリケーションを MSK で運用しているチームは、既存のスクレイパーへの kafka-exporter ジョブの追加とクラスターポリシーの設定だけで導入できるため、まずは重要なコンシューマーグループを対象に試すことを推奨します。Serverless クラスターや IAM 認証が無効なクラスターは対象外である点に注意してください。
