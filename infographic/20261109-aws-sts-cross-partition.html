AWS STS AWS IAM Security

🔐 AWS STS クロスパーティションフェデレーション

あるパーティションの IAM アイデンティティで、別パーティションの一時認証情報を取得
📅 リリース日: 2026 年 11 月 9 日

📋 概要

AWS Security Token Service (AWS STS) がクロスパーティションフェデレーションをサポート。 パーティション (商用、GovCloud、中国、欧州ソブリンクラウドなどのリージョングループ) は独立した IAM インスタンスを持つ強固な分離境界ですが、 ワークロードが自パーティションの STS から短命トークン (JWT) を取得し、 既存の GetWebIdentityToken / AssumeRoleWithWebIdentity API で 別パーティションの一時認証情報と交換できるようになりました。

主な対象は、複数パーティションにまたがってワークロードを運用し、セキュリティ・コンプライアンスレポートの統合や運用ツールの一元化を必要とする組織です。

❌ Before: アップデート前の課題
  • 各パーティションは独立した IAM を持ち、AssumeRole によるパーティション間の直接のロール引き受けは不可
  • リソースポリシーで他パーティションのプリンシパルを参照できない
  • 自動失効しない IAM ユーザーのアクセスキーなど長期認証情報に依存し、保存・ローテーションの管理負担とセキュリティリスクを抱えていた
✅ After: アップデート後の改善
  • 短命トークンを別パーティションの一時認証情報と交換でき、長期認証情報の保存が不要に
  • 全段階で一時認証情報を使用でき、IAM のベストプラクティスに準拠
  • 独自の PKI や OpenID Provider のホスティング不要のフルマネージドなトークン基盤
  • 両パーティションの CloudTrail でトークンの発行と使用を相関させて監査可能

🏗️ アーキテクチャ: トークン交換フロー

sequenceDiagram
    participant W as ⚙️ ワークロード ソースパーティション
    participant S1 as 🔐 AWS STS ソースパーティション
    participant S2 as 🔐 AWS STS 宛先パーティション
    participant R as 🪣 宛先パーティションのリソース

    W->>S1: 1. GetWebIdentityToken を呼び出し
    S1-->>W: 2. 短命の署名付き JWT を発行
    W->>S2: 3. AssumeRoleWithWebIdentity で JWT とロール ARN を提示
    S2->>S1: 4. ソースアカウントの JWKS エンドポイントから検証キーを取得
    S2->>S2: 5. 署名検証とロールの信頼ポリシー評価
    S2-->>W: 6. 一時認証情報を返却
    W->>R: 7. 一時認証情報でリソースにアクセス

ソースパーティションの AWS STS が発行した短命 JWT を、宛先パーティションの AWS STS が OIDC フェデレーションの仕組みで検証し、一時認証情報と交換する 2 段階のフローです。

⚡ 主要機能

🔄 1. 既存 API による 2 段階のトークン交換
  • ソースパーティションで sts:GetWebIdentityToken を呼び出し、短命の暗号署名付き JWT を取得
  • JWT にはアカウント ID、プリンシパル ARN、ソースリージョンなど AWS アイデンティティを表明するクレームを含む
  • 宛先パーティションの STS エンドポイントで sts:AssumeRoleWithWebIdentity を呼び出し、一時認証情報と交換
  • AssumeRoleWithWebIdentity の呼び出しに AWS 認証情報は不要 (JWT 自体が認証に使用される)
🛡️ 2. 発行元アイデンティティに基づくアクセス制御
  • 宛先ロールの信頼ポリシーで、ソースのアカウント ID、組織 ID、ソースリージョン、プリンシパルなどを条件指定
  • IAM ポリシー条件で、許可するオーディエンス、トークンの有効期間、署名アルゴリズムを制限可能
  • 既存の IAM ロール・ポリシーの仕組みをそのまま利用し、組織全体のガバナンスを適用
📊 3. クロスパーティションの監査証跡
  • 宛先パーティションの CloudTrail イベントにソースプリンシパルの ARN とトークン ID が含まれる
  • ソース側の GetWebIdentityToken イベントと相関させ、両パーティションにまたがるエンドツーエンドの監査が可能
  • 発行済みの一時認証情報のセッション失効にも対応

🔬 技術仕様

項目詳細
使用 APIsts:GetWebIdentityToken (ソース側)、sts:AssumeRoleWithWebIdentity (宛先側)
トークン形式短命の暗号署名付き JWT (JSON Web Token)
トークンのクレームアカウント ID、プリンシパル ARN、ソースリージョンなど
検証方式宛先 STS がソースアカウントの Issuer URL の JWKS エンドポイントから公開検証キーを取得し署名を検証
オーディエンスGetWebIdentityToken 呼び出し時に 1 つだけ指定 (複数指定したトークンは交換不可)
対象パーティションaws (商用)、aws-cn (中国)、aws-us-gov (GovCloud)、aws-eusc (欧州ソブリンクラウド)
制約宛先ロールはトークン発行元と異なるパーティションに存在する必要がある。同一パーティション内は AssumeRole を使用

📜 API 変更履歴

今回のアップデートは既存の GetWebIdentityToken および AssumeRoleWithWebIdentity API を利用するもので、 awsapichanges.com では本アップデートに対応する新規の API 変更は確認できませんでした (2026 年 11 月 10 日時点)。

🔏 信頼ポリシーによる制御

宛先パーティションのロールの信頼ポリシーでは、ソースアカウントの Issuer URL で作成した OIDC アイデンティティプロバイダーを信頼し、 aud や sub クレームを条件として使用します。トークン生成側では以下のポリシーで sts:GetWebIdentityToken を許可します。

JSON トークン生成を許可する IAM ポリシー 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "sts:GetWebIdentityToken",
      "Resource": "*"
    }
  ]
}

🛠️ 設定方法

✅ 前提条件

✓ソースパーティションと宛先パーティションのそれぞれに AWS アカウントがあること
✓ソース側で iam:EnableOutboundWebIdentityFederation と sts:GetWebIdentityToken の権限があること
✓宛先側で iam:CreateOpenIDConnectProvider の権限と、信頼ポリシーを持つロールの作成権限があること
1
ソースアカウントでアウトバウンド ID フェデレーションを有効化
Bash アカウント単位で 1 回のみ実行 
aws iam enable-outbound-web-identity-federation

有効化するとアカウント固有の Issuer URL を取得できます。

2
宛先アカウントで OIDC アイデンティティプロバイダーとロールを作成

ソースアカウントの Issuer URL を使用して OIDC アイデンティティプロバイダーを作成します。 クライアント ID リストには GetWebIdentityToken で使用するオーディエンスを含めます。 次に、この OIDC プロバイダーを信頼し sts:AssumeRoleWithWebIdentity を許可する信頼ポリシーを持つ IAM ロールを作成します。

3
トークンを取得して一時認証情報と交換
Bash JWT の取得と一時認証情報への交換 
# ソースパーティションで短命 JWT を取得
TOKEN=$(aws sts get-web-identity-token \
  --region us-east-1 \
  --endpoint-url https://sts.us-east-1.amazonaws.com \
  --audience "your-audience" \
  --signing-algorithm ES384 \
  --duration-seconds 300 \
  --query WebIdentityToken --output text)

# 宛先パーティションで一時認証情報と交換
aws sts assume-role-with-web-identity \
  --region cn-north-1 \
  --role-arn arn:aws-cn:iam::111122223333:role/DestinationWorkloadRole \
  --role-session-name cross-partition-session \
  --web-identity-token "$TOKEN" \
  --no-sign-request

AssumeRoleWithWebIdentity の呼び出しは JWT で認証されるため、 AWS 認証情報による署名は不要です (--no-sign-request)。

💡 メリット

💼 ビジネス面
✓セキュリティ態勢の向上: 長期認証情報を排除し、認証情報漏えいのリスクを低減
✓ガバナンスの一元化: どのアイデンティティがどのロールにアクセスできるかを制御し、組織全体で一貫したガバナンスを適用
✓コンプライアンス対応の効率化: パーティションをまたぐセキュリティ・コンプライアンスレポートの統合が容易に
⚙️ 技術面
✓運用負担の軽減: 長期認証情報の保存・ローテーション管理や、独自 PKI・OpenID Provider のホスティングが不要
✓既存の仕組みの活用: 既存の STS API と IAM ロール・ポリシーをそのまま利用可能
✓監査性の向上: 両パーティションの CloudTrail で相関させたエンドツーエンドの監査が可能

⚠️ デメリット・制約事項

🚧 制限事項

✗宛先ロールはトークン発行元と異なるパーティションに存在する必要があり、JWT を同一パーティション内の OIDC フェデレーションに使用することはできない (同一パーティション内は AssumeRole を使用)
✗GetWebIdentityToken 呼び出し時にオーディエンスを 1 つだけ指定する必要がある (複数指定したトークンは交換不可)
✗アウトバウンド ID フェデレーションの有効化や、宛先アカウントでの OIDC プロバイダー・ロールの作成など、事前のセットアップが必要

🤔 考慮すべき点

⚠パーティションは規制・コンプライアンス上の分離境界のため、FedRAMP、ITAR、DoD CC SRG、GDPR などの要件に適合するかをコンプライアンスチームに確認することが推奨されている
⚠信頼ポリシーでは aud や sub クレームに加え、組織 ID やソースリージョンなどの条件でアクセスを絞り込むことがベストプラクティス
⚠すでに PKI を運用している場合は、IAM Roles Anywhere もクロスパーティションアクセスの選択肢となる

🎯 ユースケース

📊 1. セキュリティ・コンプライアンスレポートの統合

シナリオ: 商用パーティションと AWS GovCloud (US) の両方でワークロードを運用する組織が、セキュリティ監査情報を商用パーティションの中央アカウントに集約したい。

実装例: GovCloud 上のレポート収集ワークロードがクロスパーティションフェデレーションで商用パーティションの集約用ロールを引き受け、監査データを中央の S3 バケットに書き込む。信頼ポリシーでソースの組織 ID とアカウント ID を条件に指定し、アクセス元を限定する。

効果: IAM ユーザーのアクセスキーを配布することなく、パーティションをまたいだレポート集約を一時認証情報のみで実現できる。

🧰 2. 運用ツールの一元化

シナリオ: 中央の運用チームが商用パーティションで運用ツールを稼働させており、GovCloud や中国リージョンの環境に対しても同じツールから運用タスクを実行したい。

実装例: 商用パーティションの運用ツール (EC2 や Lambda 上で実行) が、実行ロールの権限で GetWebIdentityToken を呼び出し、各パーティションの運用用ロールの一時認証情報と交換する。EC2 や Lambda ではインスタンスプロファイルや実行ロールが自動的に使用されるため、手動のロール引き受けは不要。

効果: パーティションごとに長期認証情報を管理することなく、単一の運用ツール基盤から複数パーティションを安全に運用できる。

🪣 3. GovCloud から商用パーティションの S3 へのデータアクセス

シナリオ: AWS GovCloud (US) の us-gov-west-1 で稼働するワークロードが、商用パーティションの us-east-1 にある S3 バケットのデータにアクセスする必要がある。

📝 まとめ

パーティションをまたぐワークロードで長年の課題であった長期認証情報への依存を、 既存の STS API を使用した短命トークンの交換で解消できる重要なアップデートです。

✓複数パーティションで環境を運用している組織は、IAM ユーザーのアクセスキーによるクロスパーティションアクセスを本機能へ移行することを検討
✓導入にあたっては、規制・コンプライアンス要件への適合をコンプライアンスチームに確認することが推奨されている
