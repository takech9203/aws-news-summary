Amazon ElastiCache

🧠 セルフホスト LLM 推論向け分散 KV キャッシング

📅 リリース日: 2026 年 11 月 18 日 | Distributed KV Caching for Self-Hosted LLMs (ElastiCache for Valkey)

📝 概要

Amazon ElastiCache for Valkey が、セルフホスト LLM 推論向けのフルマネージド分散 KV キャッシングの一般提供を開始しました。 GPU ローカルキャッシュをフリート共有の L2 キャッシュティアで拡張し、どのサーバーからでも KV ステートを数日間にわたって再利用できます。

これにより、AI エージェントやチャットアプリケーションが繰り返し送信する長大なコンテキストのプリフィル再計算を解消し、 推論コストを最大 40% 削減、最初のトークンが生成されるまでの時間 (TTFT) を最大 80% 短縮します。 vLLM、SGLang、TensorRT-LLM にオープンソースの LMCache コネクタ経由で設定変更のみ (コード変更不要) で接続できます。

🔄 Before / After

❌ アップデート前の課題
  • L0 キャッシュ (GPU メモリ、HBM3e で最大約 288 GB) はモデル重みと全リクエストで共有され、長い会話の KV ステートはすぐに追い出されていた
  • L1 キャッシュ (ホストメモリ / ローカル NVMe) は単一サーバー専用で、別サーバーにルーティングされたリクエストは利用不可
  • 数時間〜数日後の再訪セッションはキャッシュから消失し、プロンプト全体のプリフィルを再計算 (コーディングエージェントではプロンプトトークンの 95% 以上が処理済みプレフィックスの再送)
  • GPU サーバー障害やスケールインでローカルキャッシュが完全に失われ、復旧後もレイテンシが悪化
✅ アップデート後の改善
  • フリート全体で共有する L2 キャッシュティアにより、どのサーバーに着信しても過去のコンテキストの KV ステートを数ミリ秒で取得
  • 推論コストを最大 40% 削減、TTFT を最大 80% 短縮 (ワークロードによっては最大 93%)
  • RDMA over EFA で OS ネットワークスタックと TCP/IP をバイパスし、ノードあたり最大 220 Gbps で GPU ホストメモリと直接データ転送
  • サーバー障害時も残存サーバーが共有キャッシュから KV ステートを読み出し、性能劣化を緩和・復旧を高速化

推論エンジンはリクエストごとに L0 (GPU メモリ)、L1 (ホストメモリ / NVMe) の順にローカルキャッシュを確認し、ミスした場合のみ L2 (ElastiCache for Valkey) から RDMA over EFA 経由で KV ステートを読み出します。新しく計算した KV ステートは LMCache コネクタが L2 ティアに書き込み、フリート内の任意の GPU が再利用できます。

⚙️ 主要機能

🗄️ 共有 L2 KV キャッシュティア

  • GPU ローカルの L0 / L1 キャッシュを補完する、フリート全体で共有される L2 ティアを提供
  • KV ステートがサーバー境界・セッション・障害をまたいで数日間維持される
  • ペタバイト級までスケール可能なストレージを提供し、同一 AZ 内のすべての GPU が同じ L2 キャッシュを読み取り可能

⚡ RDMA over EFA による高速データ転送

  • Elastic Fabric Adapter (EFA) 上の RDMA により、ElastiCache ノードのメモリと GPU ホストのメモリ間で直接データを転送
  • OS ネットワークスタック、TCP/IP、中間コピーをバイパスし、ノードあたり最大 220 Gbps のスループットを実現
  • DRAM 上のブロックへのキャッシュ応答はサブミリ秒 (8 MB オブジェクトの Get で P50 477 µs、1 GB の取得で約 42 ms)

📚 DRAM と NVMe の自動データティアリング

  • 新たに導入された Valkey のラージオブジェクトサポートを使用し、KV ブロックを DRAM と NVMe に格納
  • 最もホットな KV ブロックは DRAM から読み書きし、コールドなブロックはノードローカルの NVMe に自動的にティアリング
  • ユーザーは ElastiCache for Valkey のエンドポイントとやり取りするだけでよく、ティアリングは透過的に動作

🔌 LMCache コネクタによる主要推論エンジン対応

  • vLLM、SGLang、TensorRT-LLM をオープンソースの LMCache コネクタ経由で接続可能
  • 設定変更のみで導入でき、アプリケーションコードの変更は不要
  • オープンウェイト、ファインチューニング済み、カスタムモデルに対応し、フル・スパース・ハイブリッドなどのアテンション設計をサポート

📊 KVTrace による事前効果見積もり

  • オープンソースの KVTrace ツールにより、デプロイ前に自分のトラフィックでコスト削減と TTFT 改善を無料で見積もり可能
  • vLLM / SGLang が発行するキャッシュイベントを利用し、分散 KV キャッシュが解消できたはずの再計算をレポート
  • ハッシュ化されたプロンプトデータのみを使用するためプライバシーを保護し、推論エンジンや GPU クラスターの変更は不要

ステップ 1: KVTrace で効果を事前見積もり (推奨)

Bash KVTrace によるシミュレーション 
# KVTrace を GitHub から取得 (PyPI にはない)
git clone https://github.com/aws-samples/amazon-elasticache-samples.git
cd amazon-elasticache-samples/kvtrace
pip install .

# vLLM の KV キャッシュイベントを有効化
vllm serve <model> --enable-prefix-caching \
  --kv-events-config '{"enable_kv_cache_events": true, "publisher": "zmq", "endpoint": "tcp://127.0.0.1:5557", "replay_endpoint": "tcp://127.0.0.1:5558", "topic": "kv-events"}'

# 各 GPU サーバーでトラフィックを記録
kvtrace record --endpoint-mode bind --endpoint tcp://127.0.0.1:5557 \
  --replay-endpoint tcp://127.0.0.1:5558 \
  --model <model-label> --metrics-url http://127.0.0.1:8000/metrics --out traces/

# キャッシュサイズをシミュレートしてレポートを作成
kvtrace simulate traces/ --model-config config.json --tp 8 -o sim.json
kvtrace report sim.json -o report.html \
  --gpu-cost-per-hour <GPU 時間単価> --gpus-per-replica 8

vLLM が発行するキャッシュイベントを記録し、分散 KV キャッシュ導入時の期待キャッシュヒット率・コスト削減・TTFT 改善と推奨クラスターサイズをオフラインでシミュレートします。本番クラスターの変更は不要で、ハッシュ化されたデータのみを扱います。

ステップ 2: ElastiCache for Valkey クラスターの作成

Bash GPU フリートと同一 AZ にクラスターを作成 
aws elasticache create-replication-group \
  --replication-group-id llm-kv-cache \
  --replication-group-description "Distributed KV cache for LLM inference" \
  --engine valkey \
  --cache-node-type cache.i8ge.48xlarge \
  --preferred-cache-cluster-azs <GPU フリートと同じ AZ>

同一 AZ への配置は、RDMA over EFA による低レイテンシ通信の要件です。

ステップ 3: 推論エンジンへのエンドポイント追加

LMCache の Valkey コネクタ設定に、作成した ElastiCache for Valkey クラスターのエンドポイントを追加します。 vLLM、SGLang、TensorRT-LLM のいずれも設定変更のみで接続でき、アプリケーションコードの変更は不要です。

💡 メリットと制約事項

📈 ビジネス面のメリット

✓推論コストの大幅削減: プリフィル再計算の代わりにキャッシュから KV ステートを取得し、100 万トークンあたりのコストを最大 40% 削減 (ElastiCache ノード費用考慮後)
✓ユーザー体験の向上: TTFT を最大 80% 短縮。Multiverse Computing 社の事例では、同じ GPU で 50% 多いリクエストを処理し、ピーク時の TTFT 中央値を 95% 削減
✓GPU 投資の最大活用: ルーティング最適化への依存を減らし、フリート全体の GPU を有効活用。トラフィックスパイク時の増設判断を緩和

🔧 技術面のメリット

✓コード変更不要の導入: LMCache コネクタによる設定変更のみで vLLM / SGLang / TensorRT-LLM に統合可能
✓障害・スケーリング耐性: ローカルキャッシュ喪失時も共有ティアから KV ステートを読み出して性能を維持。復帰サーバーも 60 秒以内に初期性能に回復 (テスト環境)
✓事前検証が可能: KVTrace により、デプロイ前に自社トラフィックでの効果とクラスターサイズを無料で見積もり可能
✓フルマネージド: DRAM / NVMe ティアリングやスケーリングは ElastiCache が管理し、ユーザーはエンドポイントを利用するだけ

⚠️ 制限事項

✗ノードタイプは cache.i8ge.48xlarge に限定され、GPU フリートと同一アベイラビリティーゾーンへの配置が必要
✗提供リージョンは米国、欧州、アジアパシフィックの 13 リージョン (発表時点。具体名はドキュメントで確認)
✗RDMA over EFA を使用するため、EFA に対応した GPU インスタンス構成が前提
✗キャッシュは容量確保のために古い KV ステートを追い出すため、保持期間は無期限ではない (数日単位)

🤔 考慮すべき点

⚠️KV ステートが GPU メモリに収まる小規模デプロイ、再利用のない単発 LLM 呼び出し (分類、翻訳、モデレーションなど)、短いプロンプトから長い出力を生成するワークロードでは効果が小さい
⚠️モデルごとに「カットオーバーポイント」(キャッシュ取得が再計算より速くなるプロンプト長) が存在。テストした全モデルで 10K トークン未満 (スパースモデルで 512 トークン未満、ハイブリッドモデルで 1,000〜7,600 トークン)。レイテンシ重視の場合は自ワークロードでの測定とカットオーバー超のプロンプトのみのキャッシュが推奨
⚠️cache.i8ge.48xlarge は大型ノードのため、ノード費用を上回るコスト削減が得られるか KVTrace で事前確認が重要
⚠️ベンチマーク値 (最大 40% コスト削減、最大 80% TTFT 短縮) はワークロード特性とキャッシュヒット率に依存

🎯 ユースケース

1️⃣ AI コーディングアシスタント

シナリオ: 開発者が同じコードベースに対して何十ターンも対話を続ける AI コーディングアシスタントを、複数の GPU サーバーでセルフホスト。プロンプトは 100K トークンを超え、95% 以上が過去に処理済みのプレフィックスの再送。

実装例: KVTrace でトレースを記録して効果を見積もり、GPU フリートと同一 AZ に cache.i8ge.48xlarge クラスターを作成し、vLLM の LMCache 設定に Valkey エンドポイントを追加。

💡 効果: AWS のテストでは、コーディングエージェントワークロードで同一負荷時に最大 1.98 倍のスループットを達成。長いプロンプトほどプリフィル再計算の削減効果が大きい。

2️⃣ 数時間〜数日の会話履歴を持つサポートエージェント

シナリオ: カスタマーサポート AI が長時間の会話履歴を保持し、ユーザーが数時間後や翌日に戻ってくる。従来はローカルキャッシュから KV ステートが消失し、履歴全体のプリフィルを再計算していた。

実装例: 分散 KV キャッシュを L2 ティアとして追加し、KV ステートを数日間保持。どの GPU サーバーにルーティングされても過去の文脈を再利用。

💡 効果: 再訪ユーザーへの応答で TTFT が大幅に短縮され (テストでは最大 80%)、GPU は新規リクエストの処理に集中できる。

3️⃣ 共有ドキュメントに対する大規模 QA

シナリオ: 多数のユーザーが同じ契約書やマニュアルに対して質問するドキュメント QA サービス。共有システムプロンプトと共通ドキュメントのプリフィルが全サーバーで重複計算されている。

実装例: 共通ドキュメントの KV ステートを L2 ティアで共有し、全 GPU サーバーがプリフィル済みの状態を再利用。

💡 効果: AWS のテストでは、サーバーあたりの処理リクエスト数が 2 倍になり、インタラクティビティ SLO (P90 TTFT 5 秒未満) を維持しながら 100 万出力トークンあたりのコストを 40% 削減。

💰 料金と利用可能リージョン

ElastiCache for Valkey のノード料金体系に基づき、cache.i8ge.48xlarge ノードの稼働時間に応じて課金されます。 分散 KV キャッシング機能自体の追加料金は発表されていません。KVTrace ツールは無料で利用できます。

AWS の公表値である「コスト最大 40% 削減」は、ElastiCache ノードの費用を支払った後のネットの削減率です。

🌍 利用可能リージョン: 米国、欧州、アジアパシフィックの 13 の AWS リージョン (2026 年 11 月 18 日時点)。具体的なリージョンは ElastiCache ドキュメントで確認してください。

📌 まとめ

Amazon ElastiCache for Valkey の分散 KV キャッシングは、セルフホスト LLM 推論の最大のボトルネックであるプリフィル再計算を、フリート共有の L2 キャッシュティアで解消する画期的なアップデートです。 コード変更なしの設定のみで vLLM / SGLang / TensorRT-LLM に導入でき、コスト最大 40% 削減と TTFT 最大 80% 短縮が期待できます。 長いコンテキストを扱う AI エージェントやドキュメント QA をセルフホストしている場合は、まず無料の KVTrace ツールで自社トラフィックでの効果を見積もることを推奨します。
