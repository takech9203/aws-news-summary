🧠 AWS Neuron 2.33 リリース

ネイティブ PyTorch サポート「TorchNeuron」、ヘルス監視「Neuron Observer」ほか包括的アップデート
📅 リリース日: 2026 年 10 月 21 日 | 対象: AWS Trainium / Inferentia 向け SDK

📌 概要

AWS は、AWS Trainium / Inferentia 向け SDK である AWS Neuron 2.33 を発表しました。 ネイティブ PyTorch バックエンド TorchNeuron (パブリックベータ) と、 Trainium のヘルス問題を 1 秒未満で検出する Neuron Observer (パブリックベータ) を柱に、 vLLM プラグインの更新、新しい Neuron DLAMI / DLC、Neuron Explorer の強化、NKI の大幅な拡張を含む、 開発者体験と運用性の両面にわたる大型リリースです。

対象ユーザーは、Trainium / Inferentia 上でトレーニングや推論を行う ML エンジニア、AI 研究者、 および大規模な Trainium クラスターを運用するインフラチームです。

😣 Before: アップデート前の課題

  • Trainium 上で標準 PyTorch API によるネイティブな eager 実行ができず、GPU と同等の開発体験を得にくかった
  • デバイスのヘルス問題の検出と影響ノード / デバイスの特定に時間がかかり、大規模クラスターの運用負荷が高かった
  • eager モードの OOM エラー調査で、メモリ割り当てを Python ソース行レベルで追跡する手段が限られていた
  • NKI カーネル記述には Python 言語機能の制約があり、ジェネレータやクラス継承が使えなかった

😀 After: アップデート後の改善

  • TorchNeuron により、標準 PyTorch API のモデルを Trn2 / Trn3 上で eager モードまたは torch.compile で実行可能に
  • Neuron Observer がヘルス問題を 1 秒未満で検出し、影響を受けたノードやデバイスを特定可能に
  • Neuron Explorer が torch.profiler に対応し、メモリ割り当てを Python ソース行に帰属させて OOM デバッグが可能に
  • NKI で Python 言語全体が利用可能になり、25 の新しい実験的カーネルが追加

Neuron 2.33 では、標準 PyTorch コードや vLLM サービングが TorchNeuron バックエンドを経由して Trn2 / Trn3 インスタンス上で実行されます。Neuron Observer がデバイスのヘルスを監視し、 Neuron Explorer と NKI が開発・最適化を支援します。

🚀 主要機能

🧩 1. TorchNeuron パブリックベータ

  • AWS Trainium 向けのネイティブ PyTorch バックエンド
  • 標準 PyTorch API で書かれたモデルを Trn2 / Trn3 上で eager モードまたは torch.compile で実行可能

📡 2. Neuron Observer パブリックベータ

  • Trainium のヘルス問題を 1 秒未満で検出するモニタリングツール
  • 影響を受けたノードやデバイスを特定し、大規模クラスターでの障害切り分けを迅速化
  • バージョン 0.2.0 として Neuron 2.33 に同梱

🔌 3. vLLM プラグインの更新

  • vLLM Neuron プラグインを vLLM 0.29.0 に更新
  • Wan2.2 動画生成向けの vLLM Omni Neuron プラグインを新規追加
  • 両プラグインとも TorchNeuron 経由のネイティブ PyTorch コンパイルをサポート

💿 4. 新しい Neuron DLAMI / DLC

  • TorchNeuron、PyTorch 2.14、TorchTitan をバンドルした新しい Deep Learning AMI / Container を提供
  • 環境構築の手間なく TorchNeuron ベースの開発を開始可能

🔍 5. Neuron Explorer の強化

  • torch.profiler でキャプチャしたプロファイルを開けるように
  • PyTorch メモリスナップショットの割り当てを Python ソース行に帰属可能
  • eager モードでの OOM エラーのデバッグを支援

🔧 6. NKI (Neuron Kernel Interface) の拡張

  • カーネルのメタプログラミングに Python 言語全体 (ジェネレータ、クラス継承を含む) が利用可能に
  • NKI Library に 25 の新しい実験的カーネルを追加 (DeepSeek-V3.2、Qwen3.5、Kimi Delta Attention 向けなど)

⚙️ 設定方法

前提条件

✓AWS アカウントを保有していること
✓Amazon EC2 Trn2 / Trn3 (TorchNeuron 利用時) など、Neuron 対応インスタンスを利用できること
✓既存環境を更新する場合は、Neuron 2.33 のリリースノートで変更点を確認していること

手順

1

新しい Neuron DLAMI でインスタンスを起動

Bash SSM パラメータから AMI ID を取得 
# Neuron DLAMI 2.33 の AMI ID を SSM パラメータから取得する例
aws ssm get-parameter \
  --name /aws/service/neuron/dlami/pytorch/latest/image_id \
  --query "Parameter.Value" --output text

取得した AMI を指定して Trn2 / Trn3 インスタンスを起動すると、TorchNeuron、PyTorch 2.14、TorchTitan がセットアップ済みの環境を利用できます。

2

既存環境の Neuron SDK を 2.33 に更新

Bash pip による Neuron パッケージの更新例 
# 例: pip で Neuron 関連パッケージを更新 (Ubuntu は Neuron リポジトリ設定済みが前提)
python -m pip install --upgrade \
  --extra-index-url https://pip.repos.neuron.amazonaws.com \
  neuronx-cc torch-neuronx

コンポーネントごとの正確なインストール手順は公式セットアップガイドを参照してください。

3

新機能の利用

TorchNeuron による eager / torch.compile 実行、Neuron Observer によるヘルス監視、 Neuron Explorer での torch.profiler プロファイル分析など、各機能のドキュメントに従って利用を開始します。 vLLM で推論サービングを行う場合は、vLLM 0.29.0 対応の vLLM Neuron プラグインを使用します。

💡 メリット

💼 ビジネス面

✓移行障壁の低減: 標準 PyTorch API がそのまま動作し、GPU から Trainium への移行コストが低下。コスト効率の高い AI 基盤を採用しやすくなる
✓クラスター運用コストの削減: 1 秒未満のヘルス問題検出で、大規模トレーニングの停止時間と障害調査の工数を削減
✓最新モデルへの迅速な対応: DeepSeek-V3.2 や Qwen3.5 向けカーネル、Wan2.2 動画生成対応など、最新オープンモデルを Trainium 上で活用しやすい

🔧 技術面

✓ネイティブな PyTorch 開発体験: eager モードと torch.compile の両方をサポートし、GPU と同様の開発・デバッグフローを実現
✓デバッグ能力の向上: メモリ割り当ての Python ソース行への帰属により、eager モードの OOM エラーの原因特定が容易に
✓カーネル開発の柔軟性: NKI で Python 言語全体が使え、ジェネレータやクラス継承を活用した再利用性の高いカーネル実装が可能

⚠️ デメリット・制約事項

🚧 制限事項

✗TorchNeuron と Neuron Observer はパブリックベータであり、本番環境での利用には慎重な検証が必要
✗TorchNeuron の対応インスタンスは Trn2 / Trn3 に限定
✗NKI Library の 25 の新カーネルは実験的な位置付けであり、仕様変更の可能性がある

🤔 考慮すべき点

⚠SDK 更新時は Compiler / Runtime / Driver などコンポーネント間のバージョン整合性をリリースノートで確認する
⚠既存の PyTorch NeuronX (XLA ベース) と TorchNeuron (ネイティブ) は実行方式が異なるため、移行時には性能と互換性の検証を推奨
⚠ベータ期間中は API や挙動が変更される可能性があるため、リリースノートと GitHub の更新を継続的に確認する

🎯 ユースケース

📡 ユースケース 1: 大規模 Trainium クラスターの運用監視

シナリオ: 数百ノード規模の Trn2 クラスターで基盤モデルをトレーニングしており、デバイス障害時の切り分けに時間がかかりジョブの再開が遅れている。

実装: Neuron Observer をクラスターに導入し、Trainium デバイスのヘルス問題を 1 秒未満で検出。影響を受けたノード / デバイスを特定し、該当ノードを交換してジョブを再開。

✅ 効果: 障害の検出と切り分けが高速化され、大規模トレーニングジョブの停止時間を最小化できる。

🚀 ユースケース 2: vLLM による最新モデルの推論サービング

シナリオ: vLLM で LLM 推論基盤を運用しており、推論コスト削減のために Trainium への移行を検討。あわせて Wan2.2 による動画生成ワークロードも計画している。

実装: vLLM Neuron プラグイン (vLLM 0.29.0 対応) で Trn2 / Trn3 上に LLM をサービング。動画生成には vLLM Omni Neuron プラグインで Wan2.2 を実行。いずれも TorchNeuron 経由のネイティブ PyTorch コンパイルを利用。

✅ 効果: 使い慣れた vLLM のインターフェースのまま、テキスト生成と動画生成の両方を Trainium 上でコスト効率よく運用できる。

🔍 ユースケース 3: eager モードでのメモリ問題のデバッグ

シナリオ: TorchNeuron の eager モードで新しいモデルを開発中に OOM エラーが発生し、どのコードがメモリを消費しているか特定できない。

実装: torch.profiler でプロファイルと PyTorch メモリスナップショットを記録 → Neuron Explorer で開く → メモリ割り当てを Python ソース行に帰属させ、大量消費箇所を特定。

✅ 効果: メモリ消費の原因となるコード行を直接特定でき、OOM エラーの解決までの時間を大幅に短縮できる。

🌍 利用可能リージョン

発表内に利用可能リージョンの明記はありません。Amazon EC2 Trn2 / Trn3 など、Neuron 対応インスタンスが利用可能なリージョンでの利用が前提となります。
