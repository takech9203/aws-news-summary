Amazon Redshift

🗄️ SUPER データ型の文字列上限を
1,600 万バイトに拡張

📅 リリース日: 2026 年 11 月 6 日 | 機能: SUPER データ型における最大 16,000,000 バイトの文字列サポート

📝 概要

Amazon Redshift は、SUPER データ型に格納できる個々の文字列の上限を、従来の 65,535 バイトから 16,000,000 バイト (約 16 MB) に拡張しました。 データベースパラメータ enable_large_strings_opt_in によるオプトイン方式で有効化し、 JSON、PARQUET、TEXT、CSV の各ソースファイルからの取り込みと ELT 処理の両方に適用されます。

契約書や長文の利用規約のような大きなテキストドキュメントをそのまま Redshift に取り込み、PartiQL で探索したり SQL で分析したりできます。 JSON_PARSE、CONCAT、LISTAGG などの文字列関数も最大 1,600 万バイトの文字列を入出力として扱えるようになりました。

❌ アップデート前の課題

✗SUPER 内の個々の文字列は 65,535 バイトに制限され、超過データはロードエラーや切り詰めの原因に
✗大きな文字列を含む JSON は、ロード前に分割・圧縮・切り詰めなどの複雑な事前変換が必要
✗LISTAGG や CONCAT の処理結果も 65,535 バイトが上限で、大量の値を連結する集計が困難

✅ アップデート後の改善

✓SUPER データ型に最大 16,000,000 バイトの個々の文字列を格納可能
✓JSON、PARQUET、TEXT、CSV から事前変換なしで直接取り込み可能
✓JSON_PARSE、CONCAT、LISTAGG が最大 1,600 万バイトの文字列を入出力可能
✓インメモリ処理により切り詰めやディスクスピルによるクエリ遅延を回避

💡 オプトインパラメータを有効化すると、S3 上の各種フォーマットのファイルから最大 16 MB の文字列を含むデータを SUPER カラムに直接ロードし、文字列関数や PartiQL で処理できます。

⚡ 主要機能

📏 SUPER データ型の文字列上限拡張

  • SUPER データ型に格納できる個々の文字列が 65,535 バイト → 16,000,000 バイトに拡張
  • JSON、PARQUET、TEXT、CSV ソースファイルからの取り込みに対応
  • ELT 処理での大きな文字列の生成・格納にも対応

🧠 インメモリ文字列関数の拡張

  • JSON_PARSE、CONCAT、LISTAGG などの文字列関数が最大 1,600 万バイトの文字列を入出力可能
  • インメモリ処理により、従来発生し得た切り詰めやディスクスピルを回避
  • 式コンテキスト (CAST 式、ビュー、UDF、ストアドプロシージャ) では VARCHAR(MAX) が VARCHAR(16000000) として解決

🔐 オプトイン方式による安全な有効化

  • データベースパラメータ enable_large_strings_opt_in で制御 (デフォルトは未設定で既存動作を維持)
  • プロビジョンドクラスターではパラメータ適用に再起動が必要
  • SELECT is_large_string_enabled(); で現在の状態を確認可能

🔧 技術仕様

項目詳細

🛠️ 設定方法

📋 前提条件

  • Amazon Redshift プロビジョンドクラスターまたは Redshift Serverless ワークグループ (パッチ 206 以降)
  • パラメータグループまたはワークグループ設定を変更できる IAM 権限
  • S3 からの COPY を行う場合は、適切な権限を持つ IAM ロール
1

パラメータの有効化

Bash パラメータグループで有効化 + 再起動 
# プロビジョンドクラスターの場合: パラメータグループで有効化
aws redshift modify-cluster-parameter-group \
  --parameter-group-name my-parameter-group \
  --parameters "ParameterName=enable_large_strings_opt_in,ParameterValue=Yes"

# パラメータを適用するためクラスターを再起動
aws redshift reboot-cluster --cluster-identifier my-cluster

Redshift Serverless の場合はワークグループの設定で同パラメータを設定します。

2

有効化状態の確認

SQL 状態確認 
SELECT is_large_string_enabled();
3

大きな文字列を含むデータのロードとクエリ

SQL COPY とクエリの例 
-- SUPER カラムを持つテーブルを作成
CREATE TABLE orders (data SUPER);

-- S3 上の JSON ファイルをシュレッドせずにロード
COPY orders FROM 's3://<your-bucket>/orders.json'
IAM_ROLE 'arn:aws:iam::123456789012:role/MyRedshiftRole'
FORMAT JSON 'noshred';

-- camelCase キーを引用符なしで参照するための設定
SET enable_case_sensitive_super_attribute TO true;

-- VARCHAR にキャストして文字列関数を適用
SELECT lower(data.customerId::VARCHAR) AS customer_id FROM orders;

COPY コマンドで JSON ドキュメント全体を 1 つの SUPER 値としてロードし、PartiQL でネストされた属性にアクセスします。文字列関数を適用する際は、SUPER を VARCHAR にキャストすることで文字列全体をインメモリで処理します。

💡 メリット

💼 ビジネス面

✓データパイプラインの簡素化: 大きな文字列の分割や切り詰めといった事前変換処理が不要になり、ETL / ELT パイプラインの開発・運用コストを削減
✓分析対象データの拡大: 契約書や利用規約などの長文テキストドキュメントをそのまま取り込み、SQL でクエリ可能な資産として活用
✓移行の容易化: 大きな文字列を扱う他のデータウェアハウスからの移行時に、データ構造の再設計を削減

⚙️ 技術面

✓大きな JSON ドキュメントの直接ロード: 最大 16 MB の JSON を noshred オプションでそのまま SUPER カラムに格納し、PartiQL でネスト構造を探索
✓文字列関数の上限拡張: LISTAGG による大量の値の連結結果 (65,535 バイト超) も切り詰めなしに生成し、SUPER カラムに保存
✓インメモリ処理による性能改善: 切り詰めやディスクスピルを回避し、クエリレイテンシへの悪影響を抑制

⚠️ デメリット・制約事項

🚧 制限事項

✗テーブルカラムとして定義する VARCHAR(MAX) は引き続き 65,535 バイトが上限。16 MB の上限が適用されるのはインメモリ操作 (CAST、ビュー、UDF、ストアドプロシージャ) のみ
✗機能の有効化前に作成したビューは 65,535 バイトの上限のまま (16 MB を利用するにはビューの再作成が必要)
✗一度 enable_large_strings_opt_in を Yes または No に設定すると、デフォルト (未設定) の状態には戻せない
✗プロビジョンドクラスターではパラメータ適用にクラスターの再起動が必要

🤔 考慮すべき点

オプトイン機能: 既存クラスターの動作は自動では変わらない。利用には明示的なパラメータ設定が必要
バージョン要件: パッチ 206 以降が必要なため、事前にクラスター / ワークグループのバージョンを確認する
キャストの併用: SUPER カラムに文字列関数を直接適用するとエラーになる場合があるため、VARCHAR へのキャストを組み合わせる
ビュー作成時の設定: ビューは作成時の大文字小文字の区別設定を保持するため、SET enable_case_sensitive_super_attribute などの設定はビュー作成前に実行する

🎯 ユースケース

📦 ユースケース 1: 大きな JSON ドキュメントの直接取り込みと分析

シナリオ: EC サイトの注文データが、注文明細や履歴を含む数 MB 規模のネストされた JSON ドキュメントとして S3 に出力されている。従来は 65,535 バイトの制限により分割処理が必要だった。

SQLJSON の直接ロード
CREATE TABLE orders (data SUPER);

COPY orders FROM 's3://my-bucket/orders.json'
IAM_ROLE 'arn:aws:iam::123456789012:role/MyRedshiftRole'
FORMAT JSON 'noshred';

SET enable_case_sensitive_super_attribute TO true;
SELECT data.orderId::VARCHAR, data.totalAmount FROM orders;

効果: 事前の分割・変換処理なしで JSON ドキュメント全体を 1 行としてロードし、PartiQL でネストされた属性を直接クエリできる。

📜 ユースケース 2: 契約書・利用規約など長文テキストの SQL 分析

シナリオ: 法務部門が管理する契約書や利用規約の全文テキスト (数百 KB〜数 MB) をデータウェアハウスに集約し、キーワード検索や条項の抽出を SQL で行いたい。

SQL長文テキストのキーワード検索
CREATE TABLE contracts (contract_id INT, body SUPER);

-- 16 MB までの本文を SUPER に格納し、文字列関数で処理
SELECT contract_id,
       POSITION('解約条項' IN body::VARCHAR) AS clause_pos
FROM contracts;

効果: 長文ドキュメントを外部ストレージと分析基盤に分けて管理する必要がなくなり、テキスト全文を SQL でクエリ可能な形で一元管理できる。

🔗 ユースケース 3: LISTAGG による大規模な文字列集約

シナリオ: 顧客ごとの行動ログを 1 つの文字列に連結してレポートや機械学習の特徴量として利用したいが、従来は連結結果が 65,535 バイトを超えるとエラーになっていた。

SQL大規模な文字列集約
-- 連結結果が 65,535 バイトを超えても処理可能
CREATE TABLE customer_events_agg AS
SELECT customer_id,
       JSON_PARSE('"' || LISTAGG(event_detail, ',') || '"') AS events_super
FROM customer_events
GROUP BY customer_id;

効果: 100 万文字を超えるような大規模な連結結果も切り詰めなしに生成し、SUPER カラムとして保存・再利用できる。

📌 まとめ

Amazon Redshift の SUPER データ型が最大 16,000,000 バイトの文字列をサポートし、 大きな JSON ドキュメントや長文テキストを事前変換なしで直接取り込めるようになりました。 オプトイン方式のため既存環境への影響はなく、enable_large_strings_opt_in パラメータの設定だけで利用を開始できます。

65,535 バイトの制限が原因で前処理パイプラインを運用しているワークロードでは、 パッチ 206 以降への更新と本パラメータの有効化を検討することを推奨します。
