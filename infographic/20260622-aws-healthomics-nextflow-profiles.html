AWS HealthOmics

🧬 Nextflow プロファイルのサポート

2026年6月22日
機能: Nextflow profiles

📌 概要

AWS HealthOmics が Nextflow プロファイル (Nextflow profiles) のサポートを開始しました。 実行時 (run time) に事前定義された実行設定を有効化でき、ワークフローのソースコードを変更せずに実行設定を簡単に切り替えられます。

AWS HealthOmics は HIPAA 適格なフルマネージドのバイオインフォマティクスワークフローサービスです。 今回のアップデートで、リソース制限や実行オプションといったプラットフォーム固有の設定を、ワークフローの中核ロジックからきれいに分離できます。 特に nf-core ワークフローを使うお客様にとって価値が大きく、同梱の組み込みプロファイルや機関固有のプロファイルをそのまま有効化できます。

⚠️ アップデート前の課題

  • 開発・本番で設定を使い分けるにはワークフロー定義の編集や複数定義の管理が必要だった
  • プラットフォーム固有の設定が中核ロジックと混在していた
  • nf-core 同梱プロファイルを HealthOmics でそのまま活用できなかった
  • 手動編集によるヒューマンエラーが発生しやすかった

✅ アップデート後の改善

  • engineSettings の profile キー指定だけで設定を切り替え
  • プラットフォーム固有の設定を中核ロジックから明確に分離
  • nf-core の組み込み・機関固有プロファイルをそのまま有効化
  • 別々の定義を作らずに開発設定と本番設定を切り替え

ユーザーは StartRun 時に engineSettings.profile でプロファイル名を渡し、 HealthOmics はワークフロー定義内の profiles ブロックから該当する設定を選択して、 Nextflow エンジンに -profile フラグとして適用します。

🚀 主要機能

① 実行時のプロファイル選択

  • StartRun API の engineSettings マップに profile キーを指定して 1 つ以上のプロファイルを有効化
  • HealthOmics は内部的に Nextflow エンジンへ -profile フラグを渡す
  • すべての HealthOmics サポート対象 Nextflow バージョンで利用可能

② 複数プロファイルの合成と優先順位

  • カンマ区切り (例: "test,docker") で複数指定が可能
  • 競合する設定は後に指定したプロファイルが上書き (上記例では docker が優先)
  • Nextflow バージョン 26 未満では、コマンドライン順ではなく設定ファイルの定義順に適用

③ nf-core ワークフローとの親和性

  • nf-core 同梱の組み込みプロファイル・機関固有プロファイルをそのまま有効化
  • パラメータ、プロセスディレクティブ、includeConfig 文、マニフェストの上書き (manifest.nextflowVersion 含む) を含められる

④ デフォルトプロファイルの挙動

  • 未指定時、standard が定義されていれば standard を使用
  • standard がなければトップレベルのデフォルト設定を使用
  • 明示的に指定した実行パラメータは、プロファイル定義の値よりも優先される

⚙️ 技術仕様

engineSettings の主要キー

キー値の例動作バージョンサポート
profileカンマ区切りのプロファイル名1 つ以上の Nextflow 設定プロファイルを有効化すべての Nextflow バージョン
engineVersion"24.10.8", "25.10.0", "26.04.0"実行に使用する Nextflow バージョンを固定すべての Nextflow バージョン
syntaxVersion"v1", "v2"構文パーサーを選択v26.04.0 以降。v25.10.0 以前は "v1" のみ
outputFormat"json", "text", "none"標準出力サマリーの形式を指定v26.04.0 以降
agentMode"true", "false", "0", "1"Nextflow エージェントモードを制御v26.04.0 以降

nextflow.config でのプロファイル定義

Groovynextflow.config の profiles ブロック
profiles {
    standard {
        process.cpus = 2
        process.memory = '4 GB'
    }

    production {
        process.cpus = 16
        process.memory = '64 GB'
        params.input = 's3://bucket/production-data.bam'
    }
}

🛠️ 設定方法

前提条件

  • AWS HealthOmics で Nextflow エンジンのプライベートワークフローを利用していること
  • ワークフロー定義 zip の nextflow.config 内に profiles ブロックが定義されていること (外部ソースからの取得は非サポート)
  • StartRun 用の IAM サービスロールと出力先 S3 バケットが用意されていること

ステップ 1: 単一プロファイルを指定して実行

Bashproduction プロファイルで実行
aws omics start-run \
  --workflow-id {{workflow-id}} \
  --role-arn {{role-arn}} \
  --output-uri s3://{{bucket-name}}/{{prefix}}/ \
  --engine-settings '{"profile": "production"}'

HealthOmics が Nextflow エンジンへ -profile production を適用。ワークフロー定義を一切変更せず本番用設定で実行できます。

ステップ 2: 複数プロファイルを合成して実行

Bashtest の後に docker を適用 (docker 優先)
aws omics start-run \
  --workflow-id {{workflow-id}} \
  --role-arn {{role-arn}} \
  --output-uri s3://{{bucket-name}}/{{prefix}}/ \
  --engine-settings '{"profile": "test,docker"}'

適用されたエンジン設定は GetRun のレスポンスにある engineSettings フィールドで確認できます。

💡 メリット

📈 ビジネス面

  • 開発から本番への移行を高速化: 別々の定義維持が不要、スケールアップ時間を削減
  • ヒューマンエラーの削減: 手動ファイル編集が不要に
  • ワークフローの移植性向上: nf-core パイプラインを同梱プロファイルごと持ち込める

🔧 技術面

  • 関心の分離: プラットフォーム固有設定を中核ロジックから分離
  • 柔軟な設定合成: 複数プロファイルを優先順位を制御しながら組み合わせ
  • 既存資産の活用: nf-core の組み込み・機関固有プロファイルを再利用

⚠️ デメリット・制約事項

制限事項

  • プロファイルはワークフロー定義 zip 内に定義が必要。外部ソースからの取得は非サポート
  • 存在しないプロファイル名を指定すると検証エラー (validation error) を返す
  • syntaxVersion、outputFormat、agentMode は Nextflow v26.04.0 以降のみ有効 (それ以前は無視)

考慮すべき点

  • バージョン 26 未満ではプロファイルの適用順序が定義順になるため、複数プロファイルの上書き挙動に注意
  • manifest.nextflowVersion でバージョンを固定し、実行間で適用挙動を一貫させることを推奨
  • 明示的に指定した実行パラメータはプロファイル値より優先されるため、意図しない上書きに注意

🎯 ユースケース

1. 開発環境と本番環境の切り替え

同一のゲノム解析パイプラインを、開発時は小さなテストデータと低リソースで、本番時は大規模データと高リソースで実行したい。
Bash
# 開発実行 (低リソース・テストデータ)
aws omics start-run --workflow-id {{workflow-id}} \
  --role-arn {{role-arn}} --output-uri s3://{{bucket}}/dev/ \
  --engine-settings '{"profile": "standard"}'

# 本番実行 (高リソース・本番データ)
aws omics start-run --workflow-id {{workflow-id}} \
  --role-arn {{role-arn}} --output-uri s3://{{bucket}}/prod/ \
  --engine-settings '{"profile": "production"}'
✅ 効果: 1 つのワークフロー定義を使い回しながら、実行時の指定だけで環境を切り替え可能。

2. nf-core パイプラインの同梱プロファイル活用

nf-core/rnaseq などのコミュニティパイプラインを実行し、同梱のテストプロファイルとコンテナプロファイルを組み合わせたい。
Bash
aws omics start-run --workflow-id {{workflow-id}} \
  --role-arn {{role-arn}} --output-uri s3://{{bucket}}/nfcore/ \
  --engine-settings '{"profile": "test,docker"}'
✅ 効果: パイプラインを改変せずに、コミュニティ標準のプロファイルをそのまま適用できる。

3. 機関固有プロファイルによる標準化

研究機関内の複数チームが共通ワークフローを使う際に、機関固有のリソースポリシーやリトライ戦略を共通プロファイルとして適用したい。
Bash
aws omics start-run --workflow-id {{workflow-id}} \
  --role-arn {{role-arn}} --output-uri s3://{{bucket}}/team-a/ \
  --engine-settings '{"profile": "institution"}'
✅ 効果: 機関共通の設定を 1 つのプロファイルに集約し、実行時指定だけで標準化できる。

💰 料金

Nextflow プロファイルのサポート自体に追加料金はありません。 ワークフロー実行は従来どおり、使用したコンピュートリソース (vCPU、メモリ、GPU) の使用時間と実行ストレージ使用量に基づいて課金されます。 プロファイルでリソース設定 (CPU、メモリなど) を変更した場合、その設定に応じた実行コストが発生します。

🔗 関連サービス・機能

  • AWS HealthOmics ワークフロー: プライベートワークフローおよび nf-core ベースのワークフローの実行制御に利用
  • Amazon S3: 入力データ取得と出力結果の保存。プロファイルで入力パスを切り替える際にも S3 URI を指定
  • AWS IAM: StartRun のサービスロールにより、HealthOmics の S3 などへのアクセス権限を制御
  • エフェメラルストレージ (scratch storage): 同日追加の /tmp ローカルエフェメラルストレージマウントと組み合わせ、I/O 集約タスクを最適化

📝 まとめ

AWS HealthOmics の Nextflow プロファイルサポートにより、ワークフロー定義を変更せず実行時に設定を切り替えられるようになり、 開発から本番への移行やコミュニティパイプラインの活用が大幅に容易になりました。

プラットフォーム固有の設定を中核ロジックから分離したい場合や、nf-core ワークフローを運用しているお客様は、まず nextflow.config に用途別の profiles ブロックを定義し、 StartRun の engineSettings で指定するところから始めることを推奨します。
