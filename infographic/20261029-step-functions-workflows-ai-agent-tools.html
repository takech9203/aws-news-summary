AWS Step Functions Amazon Bedrock AgentCore Gateway

⚙️ Step Functions ワークフローを
AI エージェントのツールとして利用可能に

📅 リリース日: 2026 年 10 月 29 日 | AgentCore Gateway Step Functions コネクタ

📋 概要

AWS Step Functions のワークフローを、Amazon Bedrock AgentCore Gateway を通じて AI エージェントのツールとして公開できるようになりました。エージェントは「いつ・どの入力で」実行するかを判断し、Step Functions は定義どおりに各ステップを実行します。

組み込みコネクタ (connectorId: "states") でゲートウェイターゲットを作成するだけで、エージェントは MCP (Model Context Protocol) 経由でツールを検出・呼び出しできます。既存の Standard / Express ワークフローを変更せずそのまま公開でき、Lambda 関数や独自 MCP サーバーの実装は不要です。

😣 Before: アップデート前の課題

  • エージェントからワークフローを呼び出すには Lambda や独自 MCP サーバーを実装し、ツール定義を自分で記述する必要があった
  • エージェントに広い AWS API 権限を与えると、意図しない実行や手順スキップを防ぐ仕組みを自前で構築する必要があった
  • 業務プロセスの実行順序をエージェントに委ねると、ポリシーどおりの手順実行や監査証跡の確保が難しかった

😊 After: アップデート後の改善

  • ゲートウェイターゲットを作成するだけで、既存ステートマシンを変更せず MCP ツールとして公開可能
  • stateMachineArn を「ピン留め」でき、エージェントは対象ワークフローを変更・上書き不可 (試みると拒否)
  • DescribeExecution や GetExecutionHistory、StopExecution で運用アシスタント用途にも活用可能
  • コールバックパターン (.waitForTaskToken) でワークフローからエージェントへタスクを依頼する双方向連携も実現

AI エージェントは AgentCore Gateway の MCP エンドポイント経由でツールを検出・呼び出し、ゲートウェイがピン留めされたステートマシンに対して Step Functions API を実行します。エージェントは対象ステートマシンを変更できず、実行手順はワークフロー定義が保証します。

🚀 主要機能

🧩 組み込み Step Functions コネクタによるツール公開
  • ターゲット作成時に connectorId: "states" を指定し、公開する操作を選択するだけでツール化
  • ツールスキーマ生成、パラメータ統制、エンドポイント解決、Step Functions への認証はゲートウェイが自動処理
  • Lambda 関数や独自 MCP サーバーの実装、ツール定義の記述は不要
  • 既存の Standard / Express ステートマシンを変更せずそのまま公開可能
🔧 10 種類の操作をツールとして提供
  • ステートマシン操作 (ピン留め対象): StartExecution、StartSyncExecution、ListExecutions、DescribeStateMachine
  • 実行・タスクトークン操作: DescribeExecution、StopExecution、GetExecutionHistory、SendTaskSuccess、SendTaskFailure、SendTaskHeartbeat
  • ツール名は <ターゲット名>___<操作名> の形式でエージェントに公開
📌 ピン留めによるガバナンス
  • ターゲット作成時に stateMachineArn を固定し、エージェントからは見えない (スキーマから除外)
  • エージェントが stateMachineArn を渡そうとするとゲートウェイがリクエストを拒否
  • 1 操作につき 1 ピン留め。複数のステートマシンを公開する場合はターゲットを分けて作成
🔄 コールバックパターンによる双方向連携
  • Standard ワークフローの .waitForTaskToken タスクで一時停止し、タスクトークンをエージェント側アプリケーションへ
  • 作業完了後に SendTaskSuccess / SendTaskFailure で再開、長時間タスクは SendTaskHeartbeat で生存通知
  • Standard ワークフローは最長 1 年間実行でき、エージェントのセッション終了後も処理を継続可能

🔐 ゲートウェイサービスロールの IAM ポリシー例 (最小権限)

JSON 公開するステートマシンと実行のみにスコープした例 
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "StateMachineOperations",
      "Effect": "Allow",
      "Action": [
        "states:StartExecution",
        "states:ListExecutions",
        "states:DescribeStateMachine"
      ],
      "Resource": "arn:aws:states:us-east-1:123456789012:stateMachine:AgentHelloWorld"
    },
    {
      "Sid": "ExecutionOperations",
      "Effect": "Allow",
      "Action": [
        "states:DescribeExecution",
        "states:GetExecutionHistory",
        "states:StopExecution"
      ],
      "Resource": "arn:aws:states:us-east-1:123456789012:execution:AgentHelloWorld:*"
    }
  ]
}
⚠️ 実行 ARN はステートマシン ARN と異なるリソースタイプのため、ステートメントを分ける必要があります。SendTaskSuccess、SendTaskFailure、SendTaskHeartbeat は IAM のリソースレベル権限に対応していないため "*" で許可する必要があり、タスクトークンが唯一の制御手段となります。

🛠️ 設定方法

✅ 前提条件

✓AWS CLI バージョン 2 が設定済みであること
✓IAM ロール、Step Functions ステートマシン、AgentCore ゲートウェイを作成できる権限があること
✓ゲートウェイを呼び出す ID に bedrock-agentcore:InvokeGateway 権限があること
✓すべてのリソースを同一リージョンに作成すること (ゲートウェイは自身と同じリージョンの Step Functions エンドポイントを呼び出すため)
1ゲートウェイの作成
Bash MCP プロトコル + IAM 認証のゲートウェイを作成 
aws bedrock-agentcore-control create-gateway \
  --name "step-functions-gateway" \
  --protocol-type MCP \
  --authorizer-type AWS_IAM \
  --role-arn "arn:aws:iam::123456789012:role/AgentCoreGatewayToStepFunctions" \
  --region us-east-1

レスポンスに含まれる gatewayId と gatewayUrl を控え、ステータスが READY になるまで待ちます。ロールには前述の Step Functions 権限を付与しておきます。

2Step Functions コネクタターゲットの追加
Bash StartExecution にステートマシン ARN をピン留め 
aws bedrock-agentcore-control create-gateway-target \
  --gateway-identifier "GATEWAY_ID" \
  --name "hello" \
  --target-configuration '{
    "mcp": {
      "connector": {
        "source": { "connectorId": "states" },
        "configurations": [
          {
            "name": "StartExecution",
            "parameterValues": {
              "stateMachineArn": "arn:aws:states:us-east-1:123456789012:stateMachine:AgentHelloWorld"
            }
          },
          { "name": "DescribeExecution" },
          { "name": "GetExecutionHistory" },
          { "name": "StopExecution" }
        ]
      }
    }
  }' \
  --credential-provider-configurations '[{"credentialProviderType": "GATEWAY_IAM_ROLE"}]' \
  --region us-east-1
⚠️ configurations に列挙した操作のみがツールとして公開されます。ピン留め可能な操作で parameterValues.stateMachineArn を省略するとターゲット作成は成功するものの、ツール呼び出しはすべて失敗する点に注意してください。
3エージェントからのツール呼び出し
Bash MCP tools/call でピン留めされたステートマシンを実行 
awscurl --service bedrock-agentcore --region us-east-1 \
  -X POST "GATEWAY_URL" \
  -H "Content-Type: application/json" \
  -d '{
    "jsonrpc": "2.0",
    "id": 1,
    "method": "tools/call",
    "params": {
      "name": "hello___StartExecution",
      "arguments": { "input": "{\"orderId\": \"12345\"}" }
    }
  }'

エージェントが渡すのは input のみで、レスポンスには新しい実行の executionArn が含まれます。その後 hello___DescribeExecution に ARN を渡してステータスを確認し、includedData に ALL_DATA を指定すると入出力も取得できます。実際の運用では Strands Agents や LangGraph などのエージェントフレームワークからゲートウェイに接続します。

💡 メリット

💼 ビジネス面

✓業務プロセスの一貫性保証: 適格性チェック、マネージャー承認、入金処理などのステップが必ずポリシーどおりの順序で実行される
✓監査対応の強化: Standard ワークフローは各ステップを実行履歴に記録し、AI エージェント関与の処理でも監査証跡を確保
✓開発コストの削減: Lambda や MCP サーバーの開発・運用が不要になり、既存ワークフロー資産をそのまま活用

⚙️ 技術面

✓決定論的実行と柔軟性の両立: エージェントは「いつ・どの入力で」を判断し、「どのステップをどの順序で」はステートマシン定義が決定
✓多層的なガバナンス: ピン留めによる対象固定と、IAM ポリシーによる実行 ARN 単位の制御を組み合わせ可能
✓長時間・非同期処理への対応: Standard は最長 1 年間実行可能で、コールバックによりセッション終了後も処理継続
✓運用の可視性: 「昨夜失敗した注文処理はどれか」といった問い合わせに ListExecutions や GetExecutionHistory で回答可能

⚠️ デメリット・制約事項

🚧 制限事項

✗ピン留めは 1 操作につき 1 つのステートマシンのみ。複数公開するにはステートマシンごとにターゲットを作成する必要がある
✗StartSyncExecution は Express のみ、ListExecutions・DescribeExecution・GetExecutionHistory・StopExecution は Standard のみ対応するなど、ワークフロータイプによる操作の制約がある
✗コールバックパターン (.waitForTaskToken) は Standard ワークフローのみ対応 (Express は非対応)
✗ゲートウェイは自身と同じリージョンの Step Functions のみ呼び出せる (クロスリージョン不可)

🤔 考慮すべき点

⚠️SendTaskSuccess、SendTaskFailure、SendTaskHeartbeat は IAM で特定の実行に制限できず、有効なタスクトークンを持つエージェントは誰でもタスクを完了できる。タスクトークンはシークレットとして扱うこと
⚠️1 つのゲートウェイのすべてのターゲットはサービスロールを共有する。ワークフローごとに異なる IAM 境界が必要な場合はゲートウェイを分ける
⚠️実行 ARN ベースの 6 操作はピン留めの対象外のため、サービスロールの IAM ポリシーを可能な限り狭くスコープすることが重要

🎯 ユースケース

💬 ユースケース 1: 会話からの業務ワークフロー起動

シナリオ: カスタマーサポートエージェントが顧客との会話から返金を判断し、返金ワークフローを起動。適格性チェック、マネージャー承認、入金の各ステップは必ずポリシーどおりに実行される。

JSONMCP ツール呼び出し
{
  "method": "tools/call",
  "params": {
    "name": "refund___StartExecution",
    "arguments": { "input": "{\"customerId\": \"C-1001\", \"orderId\": \"O-2345\", \"amount\": 5000}" }
  }
}

効果エージェントの柔軟な判断と承認済みプロセスの確実な実行を両立し、ポリシー逸脱のリスクを排除できる。

🔍 ユースケース 2: 運用アシスタント

シナリオ: 運用担当者が「昨夜失敗した注文処理の実行はどれ? どのステップで失敗した?」とエージェントに質問し、エージェントが実行の一覧と失敗箇所を調査して報告する。

JSON失敗した実行の一覧取得
{
  "method": "tools/call",
  "params": {
    "name": "orders___ListExecutions",
    "arguments": { "statusFilter": "FAILED" }
  }
}

続けて GetExecutionHistory で各実行のイベント履歴を取得し、失敗したステートと error・cause を特定します。

効果障害調査の一次切り分けを自然言語で実行でき、運用対応の初動を高速化。必要なら StopExecution で問題のある実行を停止可能。

🤝 ユースケース 3: ヒューマンインザループ / エージェントへのタスク委任

シナリオ: Standard ワークフローが .waitForTaskToken タスクで一時停止し、Amazon SQS 経由でタスクトークンと作業内容をエージェント側アプリケーションに渡す。エージェントは調査や文書作成などの作業を完了後、結果を返してワークフローを再開させる。

JSONタスク完了の通知
{
  "method": "tools/call",
  "params": {
    "name": "orders___SendTaskSuccess",
    "arguments": {
      "taskToken": "AQCEAAAAKgAAAAMAAAAA...",
      "output": "{\"approved\": true}"
    }
  }
}

効果ワークフロー主導でエージェントに作業を委任でき、長時間の処理やエージェントセッションをまたぐ業務プロセスを実現できる。

💰 料金・利用可能リージョン

💵 料金

追加料金なし。Step Functions と AgentCore Gateway それぞれの標準料金が適用されます。

  • Step Functions: Standard は状態遷移数、Express はリクエスト数と実行時間に基づく課金
  • AgentCore Gateway: ツール呼び出しなどに基づく課金
🌍 利用可能リージョン

Amazon Bedrock AgentCore Gateway が利用可能なすべての AWS リージョンで利用できます。

  • ゲートウェイは自身と同じリージョンの Step Functions エンドポイントを呼び出します

🔗 関連サービス・機能

🚪 Amazon Bedrock AgentCore Gateway

本機能の中核。エージェントとツールを MCP で接続するマネージドゲートウェイで、Lambda、API、Knowledge Bases など他のターゲットタイプも提供。

🔌 Model Context Protocol (MCP)

エージェントがツールを検出 (tools/list)・呼び出し (tools/call) するための標準プロトコル。

🔄 Step Functions の AgentCore 統合 (逆方向)

Step Functions の Task ステートから AgentCore 上のエージェントを呼び出すことも可能で、本機能と組み合わせて双方向のエージェント・ワークフロー連携を構築できます。

🧰 Agent Toolkit for AWS

Kiro などの AI コーディングアシスタントで Step Functions ワークフローの構築を支援するツールキット。

📝 まとめ

Step Functions ワークフローが AgentCore Gateway 経由で AI エージェントのツールとして公開できるようになり、エージェントの柔軟な判断と決定論的な業務プロセス実行を安全に組み合わせられるようになりました。コードを書かずに既存のステートマシンをそのまま活用でき、ピン留めと IAM による多層的なガバナンスも備えています。

🚀 推奨アクション: まずチュートリアルで Standard ワークフローのツール化を試し、サービスロールの最小権限設計とタスクトークンの取り扱いを確認することを推奨します。
