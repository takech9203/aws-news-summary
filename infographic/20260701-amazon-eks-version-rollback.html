Amazon EKS

☸️ Kubernetes バージョンロールバック

リリース日: 2026 年 7 月 1 日
Amazon Elastic Kubernetes Service

📌 概要

Amazon EKS が Kubernetes バージョンのロールバック に対応しました。 インプレースアップグレードの実施後 7 日以内 であれば、クラスターのコントロールプレーンを 1 つ前のマイナーバージョン (N から N-1) に戻せます。 アップグレード後にアプリの非互換性、非推奨 API の利用、想定外の動作などが発生した場合に、 既知の正常な状態へ復元する安全策を提供します。

ロールバックは コンソール / AWS CLI / AWS SDK から開始でき、実行前に 「ロールバック準備状況インサイト」が API 互換性・バージョンスキュー・アドオン互換性・クラスター健全性を自動チェックします。 ロールバック中も etcd データ・ワークロード・永続ボリュームはすべて保持 されます。 Amazon EKS が利用可能なすべての AWS リージョンで追加費用なしで利用できます。

❌ アップデート前の課題
  • 問題が判明しても前バージョンへ戻す仕組みがなく、切り戻しにクラスター再作成や複雑な手動対応が必要
  • 本番の実負荷で検証し、問題があれば戻すという安全策を組み込みにくい
  • EKS Auto Mode でコントロールプレーンとノードのバージョン整合が煩雑
✅ アップデート後の改善
  • 完了後 7 日以内なら console / CLI / SDK から N-1 へロールバック可能
  • ロールバック準備状況インサイトで互換性問題を事前に自動チェック
  • Auto Mode はノードのロールバックを自動管理し中断制御も尊重

⚙️ 主要機能

🕐 7 日間のロールバックウィンドウ
  • インプレースアップグレード完了後 7 日以内に開始可能
  • 7 日を過ぎると利用不可
  • 戻せるのは 1 マイナーバージョン (N → N-1) のみ。1.31→1.32→1.33 の場合、戻せるのは 1.32 まで
🔍 ロールバック準備状況インサイト
  • ROLLBACK_READINESS カテゴリで自動評価
  • API 互換性 / 健全性 / kubelet・kube-proxy のスキュー / アドオン互換性をチェック
  • Auto Mode では中断バジェット・PDB・do-not-disrupt も追加チェック
  • 24 時間ごと更新、[Refresh] や start-insights-refresh で手動更新可
🤖 EKS Auto Mode の自動ノードロールバック
  • コントロールプレーンを戻す前にノードのロールバックを自動管理
  • 中断バジェット・PDB・do-not-disrupt を尊重 (--force でも上書き不可)
  • ノードロールバック中は ACTIVE、CP 開始時に UPDATING へ
💾 データとワークロードの保持
  • 戻るのは API サーバー / CP コンポーネント・設定 / プラットフォームバージョン
  • etcd データ・Pod・Deployment・Service・永続ボリューム・アドオンは保持

🔧 技術仕様: ロールバックで戻るもの / 戻らないもの

項目ロールバックの対象
Kubernetes API サーバーのバージョン戻される
コントロールプレーンのコンポーネントと設定戻される
プラットフォームバージョン戻される (前バージョンの最新プラットフォームへ)
EKS Auto Mode ワーカーノード自動的に戻される
etcd データ / クラスターの状態戻されない (保持)
お客様のワークロード (Pod、Deployment 等)戻されない (稼働継続)
EKS アドオン戻されない (別途管理)
永続ボリュームとデータ戻されない (保持)
マネージドノードグループ (MNG)戻されない (UpdateNodegroupVersion で別途)
セルフマネージド / ハイブリッドノード戻されない (ユーザー責任)

✅ 前提条件のチェック項目

項目詳細
7 日間のウィンドウアップグレード完了から 7 日以内に開始する必要がある
アップグレード済みクラスターインプレースアップグレードを経たクラスターのみ対象。現行バージョンで作成されたクラスターは対象外
1 バージョンのみN から N-1 への 1 マイナーバージョンのみ
サポート対象バージョン現在サポートされている EKS バージョンが対象
拡張サポートポリシー拡張サポート中バージョンへ戻す場合、事前にポリシーを EXTENDED に変更
クラスターステータスACTIVE であり、他の更新が進行中でないこと

インサイトのステータスと挙動

ステータス意味ロールバックへの影響
PASSING問題なしロールバック可能
WARNING潜在的な問題あり (ブロックしない)ロールバック可能 (助言のみ)
ERRORブロッキングの問題あり解決までブロック、または --force で回避
UNKNOWN判定不可解決までブロック、または --force で回避

🛠️ 設定方法 (4 ステップ)

1
ロールバック準備状況インサイトの確認

ROLLBACK_READINESS カテゴリのインサイトを取得し、ERROR / WARNING がないか確認します。詳細は aws eks describe-insight --id <insight-id> で取得可能です。

Bashインサイト確認
aws eks list-insights \
  --cluster-name my-cluster \
  --region us-west-2 \
  --filter '{"categories": ["ROLLBACK_READINESS"]}'
2
ワーカーノードの準備 (マネージドノードグループの場合)

バージョンスキューポリシーにより、ノードは CP より新しいバージョンを実行できません。MNG を先に前バージョンへ。Auto Mode ではこの操作は不要で自動処理されます。

BashMNG を先に戻す
aws eks update-nodegroup-version \
  --cluster-name my-cluster \
  --nodegroup-name my-nodegroup \
  --kubernetes-version 1.30 \
  --region us-west-2
3
コントロールプレーンのロールバック実行

既存の update-cluster-version に N-1 を指定。レスポンスの type が VersionRollback、status が InProgress になります。ERROR のまま強制する場合は --force（全チェックが回避され自己責任）。

BashCP ロールバック
aws eks update-cluster-version \
  --name my-cluster \
  --kubernetes-version 1.30 \
  --region us-west-2
4
ロールバックの進捗監視

ステータスは InProgress → Successful または Failed へ遷移。Successful になれば完了です。

Bash進捗確認
aws eks describe-update \
  --name my-cluster \
  --region us-west-2 \
  --update-id <update-id>

🎯 メリット

💼 ビジネス面

  • アップグレードリスクの低減: 本番の実負荷で検証し、問題があれば戻せるため踏み切りやすい
  • ダウンタイムと復旧コストの抑制: クラスター再作成に頼らず切り戻せる
  • 追加費用なし: EKS 利用可能な全リージョンで無料

🔧 技術面

  • データとワークロードの保持: etcd・Pod・永続ボリュームを保持したまま CP のみ戻す
  • 事前チェックの自動化: インサイトが API・アドオン互換性を自動評価しリスクを可視化
  • Auto Mode の自動化: ノードのロールバックを自動管理し中断制御も尊重

⚠️ デメリット・制約事項

制限事項

  • ロールバックは完了から 7 日以内、かつ 1 マイナーバージョンのみ
  • 現行バージョンで新規作成したクラスターは対象外
  • Fargate ノードは非対応。CP は戻せるが、稼働中の Fargate Pod は kubelet スキューインサイトが ERROR に
  • MNG・セルフマネージド・ハイブリッドノード・アドオンは自動で戻らず別途対応

考慮すべき点

  • インサイトはベストエフォートかつポイントインタイム評価。チェック後の変更は検出されない
  • --force は 7 日ウィンドウや作成バージョンチェックは回避しない。非互換リソースは etcd に残り自動削除されない
  • 標準サポート→拡張サポートへ戻すと拡張サポート料金が発生
  • アプリ・依存関係の互換検証は責任共有モデルによりお客様の責任

💡 ユースケース

1. 本番アップグレード後の非互換検出時の切り戻し

シナリオ マイナーバージョンアップグレード後、非推奨 API を利用していたコントローラーが動作不良を起こした。

Bash
aws eks list-insights --cluster-name prod-cluster \
  --filter '{"categories": ["ROLLBACK_READINESS"]}' --region ap-northeast-1
aws eks update-cluster-version --name prod-cluster \
  --kubernetes-version 1.31 --region ap-northeast-1

効果 クラスター再作成なしに前バージョンへ戻し、ワークロードと etcd を保持したまま正常な状態へ復旧。

2. EKS Auto Mode クラスターでの安全なアップグレード検証

シナリオ Auto Mode を使う本番クラスターで、アップグレード後の性能を数日間検証したい。

Bash
# 検証後に問題が判明した場合、ノードは自動でロールバックされる
aws eks update-cluster-version --name automode-cluster \
  --kubernetes-version 1.31 --region ap-northeast-1

効果 中断バジェットや PDB を尊重しながらノードが自動で戻り、その後 CP が戻る。運用負荷を抑えつつ安全に検証。

3. アドオン互換性の事前確認とダウングレード

シナリオ ロールバック前に、稼働中の VPC CNI アドオンが前バージョンと非互換であることをインサイトで検出。

Bash
aws eks update-addon --cluster-name my-cluster \
  --addon-name vpc-cni --addon-version v1.12.0-eksbuild.2 \
  --region ap-northeast-1

効果 CP ロールバック前にアドオンを互換バージョンへ調整し、ロールバック後の不具合を防止。

💰 料金 & 🌏 利用可能リージョン

💰 料金

バージョンロールバック機能自体は 追加費用なし。ただし標準サポート→拡張サポート中バージョンへ戻した場合は 拡張サポート料金 が発生。クラスターとワーカーノードの通常 EKS 料金は引き続き適用されます。

🌏 リージョン

Amazon EKS が利用可能な すべての AWS リージョン で利用できます。

🔗 関連サービス・機能

  • EKS Auto Mode: ノードのロールバックを自動管理。中断制御を尊重しながらノードを先に戻す
  • EKS クラスターインサイト: ROLLBACK_READINESS カテゴリで準備状況を評価。アップグレード前チェックにも利用
  • マネージドノードグループ: ロールバック時に UpdateNodegroupVersion で別途バージョンを戻す必要あり
  • AWS CloudFormation: スタックのロールバックはクラスターのバージョンロールバックを自動トリガーしない点に注意
📝 まとめ: アップグレード完了から 7 日以内なら etcd・ワークロードを保持したまま CP を 1 つ前へ戻せます。ロールバック準備状況インサイトの確認手順を運用フローに組み込み、Fargate・アドオン・MNG の制約を事前に把握しておくことを推奨します。
