☁️ Amazon CloudFront

オリジンへの接続における HTTP/2 サポート

📅 リリース日: 2026 年 11 月 23 日 🔧 機能: Origin HTTP version (オリジン接続の HTTP/2 サポート)

📝 概要

Amazon CloudFront が、カスタムオリジンおよび VPC オリジンへの接続において HTTP/2 をサポートしました。HTTP/2 の多重化 (マルチプレキシング) により、 より少ない接続数で多数のリクエストをオリジンに送信できます。

オリジンが処理する接続数と TLS ハンドシェイク数を削減するため、バックエンド API を呼び出すモバイル / Web アプリケーションや、 MCP サーバーを呼び出す AI エージェントのような API 中心のワークロードで特に効果を発揮します。 オリジン側の変更は不要で、HTTP/2 非対応のオリジンには自動的に HTTP/1.1 にフォールバックします。

接続数を削減
単一接続で複数リクエストを多重化
追加料金なし
既存のデータ転送 / リクエスト料金のみ
オリジン変更不要
非対応時は HTTP/1.1 に自動フォールバック
❌ Before: アップデート前の課題
  • オリジン接続は HTTP/1.1 のみで、1 接続あたり同時に 1 リクエストのみ
  • 同時リクエスト増加に比例して接続数と TLS ハンドシェイク数が増加し、オリジン負荷が上昇
  • トラフィックスパイク時に新規接続確立のレイテンシーが発生し、応答時間が悪化
✅ After: アップデート後の改善
  • HTTP/2 の多重化により、少ない接続数で多数のリクエストを送信可能
  • 接続数と TLS ハンドシェイク数が削減され、オリジンのリソース消費を軽減
  • スパイク時も既存接続を再利用し、接続確立レイテンシーを回避して応答を高速化
  • extended CONNECT 対応オリジンへは HTTP/2 経由の WebSocket 接続も可能

従来の HTTP/1.1 ではリクエストごとに個別の接続が必要でしたが、HTTP/2 では単一の接続上で複数のリクエストを多重化できるため、 オリジンが処理する接続数と TLS ハンドシェイク数が削減されます。

⚡ 主要機能

1️⃣ オリジン接続の HTTP/2 多重化
カスタムオリジンおよび VPC オリジンへの接続で HTTP/2 を選択可能。同一接続上で複数のリクエストを並行して送信でき、 接続数と TLS ハンドシェイク数を削減。オリジンの CPU / メモリ消費の軽減と、スパイク時の応答高速化に寄与します。
2️⃣ 自動フォールバック
CloudFront は TLS 接続確立時 (ALPN) に HTTP/2 をオリジンに提示。オリジンが HTTP/2 を受け入れない場合は 自動的に HTTP/1.1 を使用するため、オリジン側の事前変更なしで安全に有効化できます。
3️⃣ HTTP/2 経由の WebSocket サポート
extended CONNECT をサポートするオリジンに対して、HTTP/2 接続上で WebSocket を利用可能。 リアルタイム通信を行うアプリケーションでも接続集約の恩恵を受けられます。

🔧 技術仕様

Origin HTTP version 設定

項目詳細
設定名Origin HTTP version (API: OriginHttpVersion)
設定対象カスタムオリジン、VPC オリジン (CustomOriginConfig / VpcOriginConfig)
有効な値http1.1 (デフォルト)、http2
プロトコル要件HTTPS 接続のみで HTTP/2 を使用
TLS 要件オリジンの最小 SSL プロトコルが TLSv1.2 以上であること
フォールバックオリジンが HTTP/2 非対応の場合は HTTP/1.1 を自動使用
VPC オリジンの扱いHTTP バージョンはディストリビューション側で指定 (同じ VPC オリジンを使う複数ディストリビューションで異なるバージョンを設定可能)

⚠️ HTTP/2 が使用されず HTTP/1.1 になるケース

http2 を選択していても、以下の場合は HTTP/1.1 が使用されます。

⚠️オリジンの Protocol 設定が HTTP only の場合
⚠️Protocol 設定が Match viewer で、ビューワーリクエストが HTTP の場合
⚠️最小オリジン SSL プロトコルが TLSv1.2 より古い場合 (SSLv3、TLSv1、TLSv1.1 が含まれる場合)
⚠️オリジンリクエスト / オリジンレスポンスイベントの Lambda@Edge 関数があるキャッシュビヘイビアの場合 (HTTP/1.1 が使用されることがある)

🛠️ 設定方法

前提条件

✓CloudFront ディストリビューションにカスタムオリジンまたは VPC オリジンが設定されていること
✓オリジンへの接続が HTTPS であること (Protocol が HTTPS only、または Match viewer かつビューワーが HTTPS)
✓最小オリジン SSL プロトコルが TLSv1.2 以上に設定されていること

手順

1
現在のディストリビューション設定を取得
BashAWS CLI
aws cloudfront get-distribution-config \
  --id EXAMPLEDISTID \
  --output json > dist-config.json
対象ディストリビューションの現在の設定と ETag を取得し、取得した JSON を編集して更新に使用します。
2
Origin HTTP version を HTTP/2 に変更
BashAWS CLI
# dist-config.json 内の対象オリジンの CustomOriginConfig に
# "OriginHttpVersion": "http2" を設定し、ETag を指定して更新
aws cloudfront update-distribution \
  --id EXAMPLEDISTID \
  --distribution-config file://dist-config.json \
  --if-match E2EXAMPLEETAG
マネジメントコンソールの場合は、オリジンの編集画面で [Origin HTTP version] に HTTP/2 を選択します。 更新時に OriginHttpVersion を省略した場合は HTTP/1.1 が使用される点に注意してください。
3
動作確認
オリジンサーバーのアクセスログやメトリクスで、接続数や TLS ハンドシェイク数の変化を確認します。 ALB や NGINX などのオリジンでは、アクセスログのプロトコルフィールドで HTTP/2 の使用を確認できます。 オリジンが HTTP/2 非対応でも自動的に HTTP/1.1 にフォールバックするため通信は継続されます。

⚖️ メリットと制約事項

💼 ビジネス面のメリット

✓応答時間の改善: スパイク時も既存接続を再利用し、エンドユーザー体験が向上
✓オリジンコストの最適化: 接続数と TLS ハンドシェイク数の減少でリソース消費を抑制
✓追加コストなし: HTTP/2 接続の利用に追加料金は発生しない

🔬 技術面のメリット

✓接続の多重化: 単一接続上で複数リクエストを並行処理、API 中心のワークロードで効率向上
✓安全な有効化: ALPN 自動ネゴシエーションと HTTP/1.1 自動フォールバック
✓WebSocket 対応: extended CONNECT 対応オリジンで HTTP/2 上の WebSocket が利用可能

🚧 制限事項

✗HTTP/2 は HTTPS 接続でのみ使用される (HTTP only や Match viewer の HTTP リクエストでは HTTP/1.1)
✗最小オリジン SSL プロトコルが TLSv1.2 より古いと、すべてのオリジン接続で HTTP/1.1 を使用
✗Amazon S3 オリジン (REST API エンドポイント) は対象外 (カスタム / VPC オリジンのみ)
✗オリジンリクエスト / レスポンスイベントの Lambda@Edge があるビヘイビアでは HTTP/1.1 になることがある

🤔 考慮すべき点

⚠️デフォルトは HTTP/1.1 のため、既存ディストリビューションでは明示的な設定変更が必要
⚠️更新時に OriginHttpVersion を省略すると HTTP/1.1 になるため、IaC テンプレートの更新漏れに注意
⚠️オリジン側の HTTP/2 同時ストリーム数の設定 (例: http2_max_concurrent_streams) を確認しておくことが望ましい

🎯 ユースケース

🤖 1. AI エージェントから MCP サーバーへの大量同時呼び出し
AI エージェントが CloudFront 経由で MCP サーバーに対して多数のツール呼び出しを同時に実行。 従来はリクエストごとに接続が必要で、スパイク時にオリジンの接続処理がボトルネックになっていた。
設定例
CloudFront ディストリビューション
  オリジン: MCP サーバー (ALB / VPC オリジン)
  Protocol: HTTPS only
  Minimum origin SSL protocol: TLSv1.2
  Origin HTTP version: HTTP/2
効果: 多数の同時ツール呼び出しを少数の共有接続で多重化し、接続確立のレイテンシーを排除。 エージェントの応答速度が向上し、オリジンの負荷が軽減される。
📱 2. モバイル / Web アプリのバックエンド API 高速化
モバイルアプリや SPA が CloudFront 経由でバックエンド API を呼び出しており、画面表示時に多数の API リクエストが並行して発生する。
設定例
CloudFront ディストリビューション
  オリジン: api.example.com (カスタムオリジン)
  Origin HTTP version: HTTP/2
  Keep-alive timeout: 60 秒 (接続再利用を促進)
効果: エッジからオリジンへのリクエストが多重化され、TLS ハンドシェイク回数が減少。 API サーバーの CPU 使用率が下がり、ピーク時のレスポンスタイムが安定する。
💬 3. HTTP/2 上の WebSocket によるリアルタイム通信
チャットや通知などリアルタイム機能を提供するアプリケーションで、CloudFront 経由の WebSocket 接続をオリジン側でも効率的に集約したい。
設定例
CloudFront ディストリビューション
  オリジン: extended CONNECT 対応の WebSocket サーバー
  Origin HTTP version: HTTP/2
効果: extended CONNECT をサポートするオリジンに対して HTTP/2 上で WebSocket 接続を確立でき、 通常の HTTP リクエストと合わせて接続を効率化できる。

💰 料金と利用可能リージョン

💵 料金
オリジンへの HTTP/2 接続の利用に追加料金は発生しません。 既存の CloudFront のデータ転送およびリクエスト料金のみが適用されます。
🌍 利用可能リージョン
すべての CloudFront エッジロケーションで利用可能です。

🔗 関連サービス・機能

🔒 CloudFront VPC オリジン
VPC 内のプライベートなオリジンに対しても HTTP/2 接続を利用可能。HTTP バージョンはディストリビューションごとに指定する。
⚖️ Application Load Balancer
HTTP/2 をサポートするオリジンの代表例。CloudFront からの接続集約と組み合わせることで効率的な構成を実現できる。
⚡ Lambda@Edge
オリジンリクエスト / オリジンレスポンスイベントの関数があるキャッシュビヘイビアでは HTTP/1.1 が使用されることがあるため、設計時に考慮が必要。
🛡️ CloudFront Origin Shield
オリジン負荷軽減という点で目的が近く、HTTP/2 オリジン接続と併用することでオリジン保護をさらに強化できる。

💡 まとめ

CloudFront からオリジンへの接続で HTTP/2 が利用可能になり、接続の多重化によって オリジンの接続数と TLS ハンドシェイク数を削減できるようになりました。 オリジン側の変更なしで有効化でき、非対応オリジンには自動的に HTTP/1.1 でフォールバックするため、導入リスクは小さい機能です。
