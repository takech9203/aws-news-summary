🧠 Amazon OpenSearch Memory の一般提供開始

AI エージェントに永続的な長期記憶を追加するサーバーレス機能 | リリース日: 2026 年 11 月 18 日

📋 概要

Amazon OpenSearch Memory が 一般提供 (GA) となりました。エージェントとのやり取りを 検索可能なイベントとして保存し、そこから構造化されたメモリを自動的に導出して、 セッションをまたいで関連するコンテキストを取得できる Amazon OpenSearch Service の新しいサーバーレス機能です。

エージェントは過去の意思決定、以前のやり取り、ユーザーの好みなどを、会話履歴全体をモデルに再送信することなく想起できます。 対象は、チャットボットやエージェントアプリケーションを構築する開発者、複数セッションにわたるパーソナライズ体験を提供したい組織です。

❌ Before: 独自実装が必要
  • 会話履歴全体を毎回プロンプトに含める必要があり、入力トークン数とコストが増大
  • メモリの抽出・埋め込み・インデックス作成・統合・検索の各システムを個別に構築・運用
  • メモリ基盤のインフラのプロビジョニングと容量管理が必要
✅ After: フルマネージド化
  • イベントを書き込むだけで、メモリの抽出から検索までのライフサイクル全体をマネージドに処理
  • クラスター構築・インスタンス選択・インデックス作成が不要。抽出と検索の容量は自動スケール
  • キーワード・セマンティック・ハイブリッド検索で必要なコンテキストだけを効率的に取得

エージェントは各ターンのやり取りをイベントとして Space に書き込み、サービスがバックグラウンドで Amazon Bedrock のモデルを使用してメモリを抽出・統合します。 エージェントは応答生成前にハイブリッド検索で関連メモリを取得します。

⚡ 主要機能

📝 1. イベントの保存と即時検索
  • エージェントとのやり取りを原文のまま (verbatim) イベントとして保存
  • 書き込み後すぐに読み取り可能で、数秒以内に検索可能になる
  • セッション ID によって単一の会話のイベントをグループ化できる
💡 2. メモリの自動導出と統合 (Consolidation)
  • イベントから事実・好み・要約などの構造化されたメモリを非同期に導出
  • 新しい情報の到着時に、既存メモリと比較して追加・更新・スキップを自動判断し、常に最新の状態を維持
  • 抽出されたメモリには sourceEventIds が含まれ、元のイベントまで追跡可能
🔍 3. 柔軟な検索方式
  • キーワード (レキシカル) 検索、セマンティック検索、ハイブリッド検索をサポート
  • match クエリと neural クエリを組み合わせたハイブリッド検索で高い検索精度を実現
🔒 4. セキュリティとアクセス制御
  • メモリストアごとに AWS IAM によるアクセス制御が可能
  • アクター (エンドユーザー) とセッションによるスコープ設定でデータを分離
  • IAM 条件キーでエージェントがアクセスできるアクターを制限可能
  • AWS KMS による暗号化 (カスタマーマネージドキーは作成時のみ指定可能)、CloudTrail ログ記録、CloudWatch メトリクスに対応
☁️ 5. サーバーレスで運用負荷ゼロ
  • クラスターのプロビジョニング、インスタンスタイプの選択、インデックスの作成が不要
  • 抽出と検索の容量は自動的にスケールする

ステップ 1: Space の作成

Pythonメモリストア Space の作成
import boto3

client = boto3.client("opensearch-memory")

response = client.create_space(
    name="agent-memory-space",
    memoryStrategies=[
        {"type": "SEMANTIC"},
        {"type": "SUMMARY"},
    ],
    eventExpiryDuration={"days": 90},
    memoryExpiryDuration={"days": 365},
)

セマンティック戦略と要約戦略を設定し、イベント保持期間を 90 日、メモリ有効期限を 365 日に設定。必要に応じて KMS キーや抽出用モデルも指定できます。

ステップ 2: イベントの書き込み

Python会話ターンごとのイベント保存
client.create_event(
    spaceId=space_id,
    actorId="user-123",
    sessionId="session-456",
    payload={"role": "USER", "content": "来月の東京出張では窓側の席を希望します"},
)

会話の各ターンの後に、アクター ID とセッション ID を付けてイベントを書き込みます。サービスがバックグラウンドでメモリを抽出・統合します。

ステップ 3: メモリの検索

Pythonハイブリッド検索でメモリを取得
response = client.search_memories(
    spaceId=space_id,
    actorId="user-123",
    query="座席の好み",
)

応答生成前にアクター単位でスコープされたハイブリッド検索を実行し、関連するメモリを取得してプロンプトに含めます。

⚙️ 技術面

✓フルマネージドなメモリライフサイクル: 抽出、埋め込み、インデックス作成、統合、検索までを一貫してマネージドに処理
✓自動スケーリング: サーバーレスで容量管理が不要
✓トレーサビリティ: sourceEventIds で導出元のイベントまで追跡可能

⚠️ デメリット・制約事項

🚧 制限事項

✗利用可能リージョンは現時点で 5 リージョンに限定される
✗カスタマーマネージド KMS キーは Space 作成時のみ指定可能で、後から変更できない
✗BatchGetEvent は 1 回の呼び出しで最大 10 件まで
✗Python SDK の利用には Boto3 1.44.4 以上、Python 3.10 以上が必要

🤔 考慮すべき点

⚠メモリ抽出は非同期 (バックグラウンド) で実行されるため、新規ユーザーのメモリは即座には検索結果に現れない場合がある
⚠エージェントが書き込んだメモリは永続化されて将来のプロンプトに影響するため、writtenBy などのメタデータでタグ付けし、監査可能にすることが推奨されている
⚠既存の独自メモリ実装からの移行では、データモデル (Space、イベント、メモリ、アクター) への対応付けを設計する必要がある

✨ 効果: 過去のセッションの文脈を踏まえた応答により、解決までの時間を短縮し、顧客満足度を向上できる。

📝 まとめ

Amazon OpenSearch Memory の一般提供開始により、AI エージェントへの長期記憶の追加が、 独自のメモリ基盤を構築することなくサーバーレスで実現できるようになりました。 ベンチマークでは全履歴送信比で約 12 分の 1 のトークン消費で高い精度を維持しており、 コスト効率の高いエージェント構築に有効です。

🚀 エージェントアプリケーションを運用中、または構築予定のチームは、東京リージョンでも利用可能なため、 まずは Space を作成してイベント保存とメモリ検索の動作を検証することを推奨します。
