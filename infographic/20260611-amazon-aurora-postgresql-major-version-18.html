Amazon Aurora PostgreSQL-Compatible Edition

🐘 PostgreSQL メジャーバージョン 18 サポート

リリース日
2026-06-11

📌 概要

Amazon Aurora PostgreSQL-Compatible Edition が PostgreSQL 18 (18.3 から) をサポート。最新のクエリパフォーマンス改善とデータベース管理機能を、Aurora の運用性・スケーラビリティとともに利用できます。

本リリースには、大規模な整数集合に対して高速かつメモリ効率の高い集合演算を行う新拡張機能 pg_roaringbitmap が含まれます。さらに B-tree スキップスキャン、アップグレード時のオプティマイザ統計情報の保持、論理レプリケーションの並列ストリーミングなど、運用面で重要な改善が導入されました。

主な対象はデータベース管理者・アプリケーション開発者・データエンジニアです。

🔴 アップデート前の課題

  • アップグレード後にオプティマイザ統計情報が失われ、ANALYZE 完了までクエリパフォーマンスが不安定
  • 複合 B-tree インデックスは先頭列に条件がないと活用しづらく、追加インデックスが必要
  • 大規模なオーディエンスセグメンテーションをアプリケーション層で処理し効率が低下
  • 論理レプリケーションで大規模トランザクション時にレプリケーション遅延が発生しやすい

🟢 アップデート後の改善

  • アップグレード後も統計情報を保持し、直後から一貫したクエリパフォーマンス
  • B-tree スキップスキャンで先頭列に条件がなくても複合インデックスを活用、保守オーバーヘッド削減
  • pg_roaringbitmap で大規模集合演算を DB 内で高速・省メモリに実行
  • 大規模トランザクションの並列ストリーミングでレプリケーション遅延を削減

3 つのアップグレード方式 (Blue/Green デプロイメント、インプレースアップグレード、スナップショットからの復元) のいずれかで Aurora PostgreSQL 18.3 へ移行でき、移行後は統計情報の保持や B-tree スキップスキャンなどの新機能を利用できます。

⭐ 主要機能

🔍 B-tree スキップスキャン
  • 複合 B-tree インデックスで、先頭列に等価条件がない場合や後続列のみに有用な条件がある場合でもインデックスを活用
  • 各検索パターンごとに追加インデックスを作成する必要性が減少
  • インデックスのストレージ消費と保守オーバーヘッドを削減しつつクエリパフォーマンスを向上
📊 メジャーバージョンアップグレード時のオプティマイザ統計情報の保持
  • PostgreSQL 18 では pg_upgrade が統計情報を保持するように改善
  • アップグレード直後に ANALYZE を再実行する必要がなく、一貫したパフォーマンスをすぐに得られる
  • 注意: 拡張統計情報 (extended statistics) は保持されない
🔁 論理レプリケーションの大規模トランザクション並列ストリーミング
  • 大規模トランザクションを並列に適用し、レプリケーション遅延を削減
  • ダウンストリームシステムをより最新の状態に維持
  • CREATE SUBSCRIPTION のストリーミングのデフォルトが parallel に変更
🧮 pg_roaringbitmap 拡張機能のサポート
  • 大規模整数集合に対する高速・省メモリな集合演算 (積集合・和集合・差集合など)
  • オーディエンスセグメンテーション、タグベースフィルタリング、権限チェックを DB 内で直接処理
  • アプリケーション層での処理を回避し効率を向上

pg_roaringbitmap の使用例

SQL集合演算でセグメントの積集合を算出
-- 拡張機能の有効化
CREATE EXTENSION roaringbitmap;

-- roaringbitmap 型の列を持つテーブルの作成
CREATE TABLE audience_segments (
    segment_id   integer PRIMARY KEY,
    user_bitmap  roaringbitmap
);

-- 2 つのセグメントの積集合 (両方に属するユーザー数) を計算
SELECT rb_cardinality(
    rb_and(
        (SELECT user_bitmap FROM audience_segments WHERE segment_id = 1),
        (SELECT user_bitmap FROM audience_segments WHERE segment_id = 2)
    )
);

pg_roaringbitmap を有効化し、2 つのオーディエンスセグメントの積集合に含まれるユーザー数を集合演算で算出する例です。

⚙️ 設定方法 (Blue/Green での移行手順)

前提条件

✓アップグレード対象の Aurora PostgreSQL DB クラスターが稼働していること
✓アップグレード前にスナップショットを取得し、バックアップを確保していること
✓アプリケーションが PostgreSQL 18 の非互換変更 (仮想生成列のデフォルト化、MD5 パスワードの非推奨化など) に対応していること

手順

1
アップグレード前の互換性確認
Bash現在のエンジンバージョンを確認
# 現在の DB クラスターのエンジンバージョンを確認
aws rds describe-db-clusters \
    --db-cluster-identifier my-aurora-cluster \
    --query 'DBClusters[0].EngineVersion'
2
Blue/Green デプロイメントの作成
BashGreen 環境を 18.3 で構成
# Blue/Green デプロイメントを作成し、Green 環境を 18.3 で構成
aws rds create-blue-green-deployment \
    --blue-green-deployment-name aurora-pg18-upgrade \
    --source arn:aws:rds:ap-northeast-1:123456789012:cluster:my-aurora-cluster \
    --target-engine-version 18.3

本番環境 (Blue) に影響を与えずに PostgreSQL 18.3 の Green 環境を準備。十分に検証してから切り替えることでダウンタイムとリスクを最小化できます。

3
切り替えの実行
BashGreen 環境へ切り替え
# 検証完了後、Green 環境へ切り替え
aws rds switchover-blue-green-deployment \
    --blue-green-deployment-identifier bgd-xxxxxxxxxxxx

インプレースアップグレードやスナップショット復元を選ぶ場合は、それぞれ modify-db-cluster / restore-db-cluster-from-snapshot を使用します。

✅ メリット

ビジネス面

✓パフォーマンス安定化: 統計情報保持により、アップグレード直後から安定し移行リスクを低減
✓運用コスト削減: B-tree スキップスキャンで冗長なインデックスを削減し、ストレージコストと保守工数を抑制
✓開発生産性の向上: pg_roaringbitmap で集合演算を DB 内で完結、アプリ実装負荷を軽減

技術面

✓クエリパフォーマンス向上: B-tree スキップスキャンや非同期 I/O など最新の最適化を活用
✓レプリケーション遅延の削減: 大規模トランザクションの並列ストリーミングで鮮度を維持
✓柔軟なアップグレード手段: 3 方式から最適なものを選択可能

⚠️ デメリット・制約事項

制限事項

✗拡張統計情報 (extended statistics) はメジャーバージョンアップグレード時に保持されない
✗PostgreSQL 18 には非互換変更が含まれる (生成列のデフォルト仮想化、MD5 パスワードの非推奨化、initdb のデータチェックサムデフォルト有効化など)
✗pg_roaringbitmap は新しい拡張機能のため、既存アプリへの組み込みには設計と検証が必要

考慮すべき点

⚠️ メジャーバージョンアップグレードは非互換変更を伴うため、テスト環境で十分に検証してから本番へ適用することを推奨。
⚠️ 仮想生成列がデフォルトになるため、書き込み時に値を保存する従来の挙動が必要な場合は STORED キーワードを明示的に指定する。

💡 ユースケース

1. 大規模オーディエンスセグメンテーション

シナリオ: マーケティングプラットフォームで数百万人のユーザー ID を複数セグメントに分類し、積集合や和集合をリアルタイムに算出したい。

SQL
-- 複数セグメントの和集合に含まれるユニークユーザー数を算出
SELECT rb_cardinality(
    rb_or_cardinality_agg(user_bitmap)
)
FROM audience_segments
WHERE segment_id IN (10, 11, 12);
効果: 集合演算を DB 内で完結させ、アプリ層への大量データ転送を回避。応答時間とメモリ使用量を削減。
2. メジャーバージョンアップグレードの安定化

シナリオ: ミッションクリティカルな Aurora PostgreSQL を、パフォーマンスを劣化させずに最新メジャーバージョンへ移行したい。

Bash
# Blue/Green デプロイメントで 18.3 へ移行
aws rds create-blue-green-deployment \
    --blue-green-deployment-name prod-pg18 \
    --source arn:aws:rds:ap-northeast-1:123456789012:cluster:prod-cluster \
    --target-engine-version 18.3
効果: 統計情報が保持され、切り替え直後から安定したクエリパフォーマンスを維持。ANALYZE 完了を待つ必要がない。
3. インデックス効率化によるコスト削減

シナリオ: 多様な検索パターンに対応するため多数の複合インデックスを作成しており、ストレージと保守コストが増大している。

SQL
-- 先頭列 region に条件がないクエリでも、複合インデックスを活用可能
-- CREATE INDEX idx_orders ON orders (region, order_date);
EXPLAIN ANALYZE
SELECT * FROM orders WHERE order_date >= '2026-06-01';
効果: B-tree スキップスキャンで既存の複合インデックスを再利用。追加インデックスを削減してコストと保守オーバーヘッドを低減。

🎯 まとめ

Aurora PostgreSQL 18.3 のサポートにより、B-tree スキップスキャンや統計情報の保持といった最新のパフォーマンス・運用改善と、pg_roaringbitmap による高度な集合演算をマネージド環境で活用できるようになりました。

メジャーバージョンアップグレードは非互換変更を伴うため、まずはテスト環境で互換性を検証し、Blue/Green デプロイメントを活用して安全に移行することを推奨します。
