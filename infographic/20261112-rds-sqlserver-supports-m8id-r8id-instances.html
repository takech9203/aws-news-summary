Amazon RDS for SQL Server

🗄️ M8id / R8id インスタンスのサポート開始

📅 リリース日: 2026 年 11 月 12 日 | カスタム Intel Xeon 6 + ローカル NVMe SSD で tempdb を高速化

📌 概要

Amazon RDS for SQL Server が db.m8id / db.r8id インスタンスのサポートを開始しました。 AWS でのみ利用可能なカスタム Intel Xeon 6 プロセッサとローカル NVMe SSD インスタンスストアを搭載し、 インスタンスタイプを変更するだけで tempdb が自動的にローカル NVMe SSD に配置され、 EBS より低い読み取り / 書き込みレイテンシーを実現します。データベース本体は引き続き EBS 上に保持されるため耐久性は維持されます。

  • インスタンスストア付きの最新世代の選択肢が限られ、tempdb 高速化は M5d / R5d (最大 96 vCPU) や x2iedn / x2m に限定

  • 頻繁に変化する tempdb のブロックがスナップショットサイズを増大させ、バックアップストレージの消費が大きくなるケースも
✅ After: アップデート後の改善
  • 最大 384 vCPU / 3 TiB メモリ / 22.8 TB ローカル NVMe SSD の大規模スペックを選択可能
  • インスタンスタイプの変更だけで tempdb が自動的にローカル NVMe へ配置され、低レイテンシーな tempdb I/O を実現
  • スナップショットに tempdb が含まれず、サイズ縮小で無料バックアップ枠の消費を抑制

db.m8id / db.r8id では tempdb のデータ / ログファイルがローカル NVMe インスタンスストアに自動配置され、データベース本体のファイルは EBS 上に保持されます。スナップショットには tempdb が含まれないためサイズが小さくなります。

⚡ 主要機能

🧠 1. カスタム Intel Xeon 6 プロセッサ搭載の最新世代インスタンス
  • AWS でのみ利用可能なカスタム Intel Xeon 6 プロセッサを搭載
  • 最大 384 vCPU、3 TiB のメモリを提供
  • M5d / R5d と比較して vCPU とメモリが 4 倍に拡大
🚀 2. ローカル NVMe SSD インスタンスストアによる tempdb の高速化
  • 最大 22.8 TB のローカル NVMe SSD ストレージ (M5d / R5d 比 6 倍以上)
  • DB インスタンスの作成時または変更時に、tempdb のデータ / ログファイルが自動的にインスタンスストア (T:\rdsdbdata\DATA) に配置
  • EBS ストレージと比較して低い読み取り / 書き込みレイテンシーを実現
  • データベース本体のデータファイルとログファイルはインスタンスストアには配置されない
📦 3. バックアップストレージの効率化
  • tempdb がインスタンスストア上にあるため、DB スナップショットに一時ファイルが含まれない
  • スナップショットサイズが小さくなり、無料バックアップ枠の消費を抑制

🛠️ 設定方法

✅ 前提条件

✓利用可能リージョン (東京を含む 13 リージョン) で RDS for SQL Server を運用していること
✓インスタンスクラス変更に伴う再起動の影響を考慮したメンテナンス計画があること
✓tempdb のワークロードがインスタンスストアの容量に収まることを確認していること

ステップ 1: 現在のインスタンスクラスの確認

Bash現在のインスタンスクラスを確認
aws rds describe-db-instances \
  --db-instance-identifier my-sqlserver-instance \
  --query "DBInstances[0].[DBInstanceClass,Engine,EngineVersion]"

ステップ 2: 利用可能な db.m8id / db.r8id サイズの確認

Bash注文可能な db.r8id クラスの一覧を取得
aws rds describe-orderable-db-instance-options \
  --engine sqlserver-ee \
  --query "OrderableDBInstanceOptions[?contains(DBInstanceClass, 'db.r8id')].[DBInstanceClass,EngineVersion]" \
  --region ap-northeast-1

ステップ 3: インスタンスクラスの変更

Bashdb.r8id.4xlarge へ変更 (次のメンテナンスウィンドウで適用)
aws rds modify-db-instance \
  --db-instance-identifier my-sqlserver-instance \
  --db-instance-class db.r8id.4xlarge \
  --no-apply-immediately

--no-apply-immediately を指定すると次のメンテナンスウィンドウで適用されます。即時適用する場合は --apply-immediately を指定しますが、再起動が発生します。変更後、tempdb のデータ / ログファイルは自動的にインスタンスストアへ配置されます。

💡 メリット

💼 ビジネス面
✓バックアップコストの削減: スナップショットに tempdb が含まれず、サイズと無料バックアップ枠の消費を抑制
✓スケールアップによる統合: 複数の中規模インスタンスを大規模インスタンスへ統合し、SQL Server ライセンスや運用の効率化を検討可能
✓移行の容易さ: インスタンスクラスの変更のみで tempdb の高速化が有効になり、アプリケーションの変更は不要
⚙️ 技術面
✓tempdb の低レイテンシー化: ローカル NVMe SSD への自動配置により、EBS と比較して低い読み取り / 書き込みレイテンシーを実現
✓大容量の一時領域: 最大 22.8 TB のローカルストレージで大規模なソートや一時テーブルに対応
✓柔軟な構成: 容量不足時は EBS ボリューム上に追加の tempdb ファイルを作成する混在構成も可能

⚠️ デメリット・制約事項

🚫 制限事項

✗インスタンスストアに配置されるのは tempdb のみで、データベース本体のデータ / ログファイルは配置されない
✗インスタンスストアの容量を使い切ると tempdb のトランザクションログフルやファイルグループフルのエラーが発生する可能性がある
✗利用可能リージョンは発表時点で 13 リージョンに限定される

🤔 考慮すべき点

⚠️インスタンスクラス変更時には再起動が発生するため、メンテナンスウィンドウを活用した計画的な移行が必要
⚠️ALTER DATABASE [tempdb] MODIFY FILE で tempdb ファイルを再配置して再起動すると、元のボリュームに孤立ファイルが残り容量を消費する場合がある (削除には AWS サポートへの連絡が必要)
⚠️インスタンスストアを使用しない構成へ戻す場合は、インスタンスストア非対応のインスタンスクラス (db.m5、db.r5 など) へ変更する

🎯 ユースケース

🌙 ユースケース 1: tempdb I/O がボトルネックのバッチ処理の高速化

シナリオ: 夜間バッチで大量のソートや一時テーブルを使用しており、tempdb への EBS I/O レイテンシーが処理時間を長期化させている。

Bashバッチ用インスタンスを db.m8id.8xlarge へ変更
aws rds modify-db-instance \
  --db-instance-identifier my-batch-sqlserver \
  --db-instance-class db.m8id.8xlarge \
  --no-apply-immediately

効果: tempdb がローカル NVMe SSD に配置され、ソートやハッシュ結合などの tempdb 集約的な処理のレイテンシーが低減し、バッチ処理時間の短縮が期待できます。

📈 ユースケース 2: M5d / R5d からの世代更新とスケールアップ

シナリオ: db.r5d.24xlarge (最大サイズ) で運用しているが、ワークロードの成長により CPU とメモリが不足しつつある。

Bashdb.r8id.48xlarge へ即時変更
aws rds modify-db-instance \
  --db-instance-identifier my-core-sqlserver \
  --db-instance-class db.r8id.48xlarge \
  --apply-immediately

効果: M5d / R5d 比で 4 倍の vCPU / メモリにより、シャーディングやアプリケーション分割を行わずにスケールアップで対応でき、tempdb 用ローカルストレージも 6 倍以上に拡大します。

📸 ユースケース 3: スナップショットサイズの削減によるバックアップ最適化

シナリオ: tempdb の変更ブロックが多いワークロードで、EBS のみのインスタンスではスナップショットサイズが大きく、バックアップストレージのコストが増加している。

Bash変更後のスナップショットサイズを確認
# インスタンスストア対応クラスへ変更後、スナップショットサイズを確認
aws rds describe-db-snapshots \
  --db-instance-identifier my-sqlserver-instance \
  --query "DBSnapshots[*].[DBSnapshotIdentifier,AllocatedStorage,SnapshotCreateTime]"

効果: tempdb がスナップショットに含まれなくなるため、スナップショットサイズが小さくなり、無料バックアップ枠の消費とバックアップコストを抑制できます。
