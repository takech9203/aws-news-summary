AWS IAM Identity Center Amazon EventBridge

🔔 Identity Store の変更通知が EventBridge に対応

📅 リリース日: 2026 年 10 月 28 日 | ユーザー・グループ・メンバーシップの変更をリアルタイムイベントで配信

📌 概要

AWS IAM Identity Center の Identity Store が、ユーザー、グループ、グループメンバーシップ、Identity Store 自体の作成・更新・削除時に、Amazon EventBridge へリアルタイムイベントを配信する機能をサポートしました。 ID のライフサイクルイベントに自動対応でき、セキュリティ・コンプライアンスプロセスを強化できます。

❌ Before: アップデート前の課題
  • Identity Store API を定期的にポーリングして差分を比較する必要があった
  • CloudTrail で API 呼び出しは追跡できたが、「ID データに何が起きたか」をイベント単位で把握する手段がなかった
  • オンボーディング / オフボーディングのリアルタイム自動化が困難だった
✅ After: イベント駆動型の ID 管理
  • ID の作成・更新・削除がリアルタイムイベントとして EventBridge のデフォルトイベントバスに配信
  • EventBridge ルールで Lambda、SNS、SQS などをターゲットに指定し、自動対応ワークフローを構築可能
  • ポーリング不要、変更発生と同時に処理を開始できる

Identity Store で発生した ID の変更が EventBridge のデフォルトイベントバスにリアルタイム配信され、ルールにマッチしたイベントが Lambda や SNS などのターゲットに送信される流れ

⚙️ 主要機能

📨 リアルタイム変更イベントの配信

ユーザー、グループ、グループメンバーシップ、Identity Store 自体の作成・更新・削除時にイベントを配信。IAM Identity Center インスタンスが有効化されている AWS アカウントのデフォルトイベントバスに自動配信 (組織インスタンスは管理アカウント、アカウントインスタンスは有効化したメンバーアカウント)。イベントソースはすべて aws.identitystore、イベント名は detail-type フィールドに格納。

🗂️ 11 種類のイベントタイプ
👤 User
Created / Updated / Deleted
ユーザーの作成・属性更新・削除
👥 Group
Created / Updated / Deleted
グループの作成・属性更新・削除
🔗 GroupMembership
Created / Deleted
グループへのユーザー追加・削除
🏪 IdentityStore
Created / Updated / Deleted
Identity Store 自体の作成・設定更新・削除
🌍 マルチリージョンレプリケーション対応

IAM Identity Center インスタンスを追加リージョンにレプリケートしている場合、各追加リージョンのデフォルトイベントバスでもイベントを受信可能。インスタンスの各有効化リージョンでイベントが送信される。

🔬 技術仕様

項目詳細
イベントソースaws.identitystore
配信先IAM Identity Center インスタンスが有効なアカウント・リージョンのデフォルトイベントバス
含まれる情報Identity Store の ID、インスタンスの ARN、変更されたユーザー / グループ / メンバーシップの ID と ARN、変更リクエストの ID、変更時刻、送信リージョン
含まれない情報ユーザー名やメールアドレスなどの属性値、Updated イベントにおける変更内容の詳細
配信保証少なくとも 1 回 (at-least-once)。重複受信や順序の入れ替わりの可能性あり
遡及配信なし (ルール作成後の変更のみが対象。バックフィルやリプレイは行われない)

💡 属性の現在値が必要な場合は、DescribeUser / DescribeGroup / DescribeGroupMembership の各 Identity Store API を呼び出して取得します。

📋 イベントパターンの例 (全イベントにマッチ)

JSON すべての Identity Store 変更イベント 
{
  "source": ["aws.identitystore"],
  "detail-type": [
    "User Created", "User Updated", "User Deleted",
    "Group Created", "Group Updated", "Group Deleted",
    "GroupMembership Created", "GroupMembership Deleted",
    "IdentityStore Created", "IdentityStore Updated", "IdentityStore Deleted"
  ]
}

⚠️ CloudTrail 経由の API 呼び出しイベントも同じイベントソース aws.identitystore で配信されるため、detail-type にイベント名を明示することで変更通知イベントのみを受信できます。

🛠️ 設定方法

✅ 前提条件

✓IAM Identity Center インスタンスが有効化されている AWS アカウントとリージョンを確認済み (ルールはそこに作成)
✓events:PutRule や events:PutTargets など、EventBridge ルールとターゲットを作成する権限
✓イベント受信先のターゲット (Lambda 関数、SNS トピック、SQS キューなど) を用意済み
1
イベントパターンの作成

受信したいイベントを選択するパターンをファイルに保存。この例では下流アプリケーションのアクセス削除を想定し、ユーザー削除とグループからのユーザー削除のみにマッチさせます。

Bashidentity-events.json
cat > identity-events.json << 'EOF'
{
  "source": ["aws.identitystore"],
  "detail-type": ["User Deleted", "GroupMembership Deleted"]
}
EOF
2
EventBridge ルールの作成

デフォルトイベントバス上にルールを作成。リージョンには IAM Identity Center インスタンスが有効化されているリージョンを指定します。

BashAWS CLI
aws events put-rule \
  --name identity-change-events \
  --event-pattern file://identity-events.json \
  --region us-east-1
3
ターゲットの追加

この例では Amazon SNS トピックにイベントを送信。CLI でルールを作成する場合は、ターゲットのリソースベースポリシーなどで EventBridge からの送信許可が必要です。

BashAWS CLI
aws events put-targets \
  --rule identity-change-events \
  --targets "Id"="1","Arn"="arn:aws:sns:us-east-1:111122223333:identity-change-topic" \
  --region us-east-1
4
ルールのテスト

ルール作成後約 1 分待ってから、ユーザーをグループに追加するなどの変更を行い、ターゲットが GroupMembership Created イベントを受信することを確認。テスト時は CloudWatch Logs ロググループを 2 つ目のターゲットとして追加すると便利です。

💪 メリット

💼 ビジネス面

✓オンボーディング / オフボーディングの自動化: グループへの追加・削除をトリガーにリソース作成やアクセス削除を自動実行し、大規模な従業員管理の運用負荷を削減
✓コンプライアンス対応の強化: ID の変更をリアルタイムに SIEM へ連携し、監査証跡の即時性と網羅性が向上
✓追加コストなし: 標準の Amazon EventBridge 利用料金以外の追加料金なし

🔧 技術面

✓イベント駆動アーキテクチャへの統合: ポーリング方式から脱却し、Lambda / SNS / SQS と組み合わせたイベント駆動の ID 管理ワークフローを構築可能
✓変更単位のイベント: CloudTrail の API 呼び出し記録と異なり「ID データへの変更」そのものがイベントになるため、変更対応ロジックをシンプルに実装可能
✓マルチリージョン対応: レプリケートした各リージョンでもイベントを受信でき、リージョン分散ワークロードに対応

⚠️ デメリット・制約事項

🚧 制限事項

✗配信は少なくとも 1 回 (at-least-once)。同一イベントの複数回受信や、変更発生順と異なる順序での受信の可能性あり
✗配信は前方のみ (forward-looking)。ルール作成以前の変更のバックフィルやリプレイは行われず、ルールにマッチしないイベントも保存されない
✗イベントにユーザーやグループの属性 (名前、メールアドレスなど) は含まれず、Updated イベントにも変更内容の詳細は含まれない

🤔 考慮すべき点

⚡同じイベントを 2 回処理しても副作用がないよう、冪等性を考慮したワークフロー設計が必要
⚡配信時間は保証されないため、下流システムの正確性維持には Identity Store API との定期的な突合を推奨
⚡インスタンス削除時は IdentityStore Deleted イベントの後、内部のユーザー・グループ・メンバーシップの削除イベントが時間差で順次届く
⚡イベント通知と CloudTrail イベントは 1 対 1 に対応しない。変更対応はイベント通知、API 呼び出し元の監査は CloudTrail と使い分ける

🎯 ユースケース

1️⃣ オフボーディング時のアクセス自動削除

シナリオ: 退職者や異動者がグループから削除された際に、下流の SaaS アプリケーションや社内システムのアクセス権を即座に削除したい。

JSONイベントパターン
{
  "source": ["aws.identitystore"],
  "detail-type": ["User Deleted", "GroupMembership Deleted"]
}

このパターンのルールから Lambda 関数をトリガーし、イベントに含まれるユーザー ID をもとに下流アプリケーションのアクセスを削除する。

✅ 効果: アクセス削除の遅延による不正アクセスリスクを低減し、オフボーディングプロセスを完全自動化
2️⃣ SIEM へのリアルタイム連携によるセキュリティ監査

シナリオ: セキュリティチームが、ユーザープロビジョニングやグループ変更のアクティビティをリアルタイムに監視し、不審な変更を即座に検知したい。

JSONイベントパターン
{
  "source": ["aws.identitystore"],
  "detail-type": [
    "User Created", "Group Updated", "GroupMembership Created"
  ]
}

ルールのターゲットに Amazon Data Firehose や Lambda を指定し、SIEM システムにイベントを転送する。

✅ 効果: 特権グループへの予期しないメンバー追加などを即時に検知し、インシデント対応までの時間を短縮
3️⃣ 新入社員オンボーディングの自動化

シナリオ: 新入社員が特定の部門グループに追加されたタイミングで、業務アプリケーションのアカウント作成や初期リソースのプロビジョニングを自動実行したい。

JSONイベントパターン
{
  "source": ["aws.identitystore"],
  "detail-type": ["GroupMembership Created"]
}

イベント受信後、Lambda 関数で DescribeGroupMembership と DescribeUser を呼び出してユーザー属性を取得し、Step Functions でオンボーディングワークフローを起動する。

✅ 効果: 手動のアカウント発行作業が不要になり、入社初日から必要なリソースを利用可能に

💰 料金・利用可能リージョン

💵 料金

変更通知自体に追加料金はありません。標準の Amazon EventBridge 利用料金のみが適用されます。

🌐 利用可能リージョン

IAM Identity Center が利用可能なすべての AWS リージョンで利用可能。イベントはインスタンスの各有効化リージョンで送信されます。詳細は AWS capabilities by Region を参照。

🔗 関連サービス・機能

  • Amazon EventBridge: 変更イベントの受信基盤。ルールとターゲットを定義してイベント駆動ワークフローを構築
  • AWS Lambda: イベントをトリガーとした自動化処理の実行基盤
  • Amazon SNS / Amazon SQS: 通知配信やイベントのキューイングに利用できるターゲット
  • AWS CloudTrail: Identity Store API 呼び出しの監査ログ。変更対応はイベント通知、呼び出し元の監査は CloudTrail と使い分ける
  • Identity Store API: DescribeUser / DescribeGroup / DescribeGroupMembership で変更後の現在の属性を取得

📝 まとめ

Identity Store の EventBridge 変更通知対応により、ポーリング不要のイベント駆動型 ID 管理が実現可能になりました。 オンボーディング / オフボーディングの自動化や SIEM 連携によるセキュリティ監視を強化したい組織は、まず aws.identitystore をソースとする EventBridge ルールを作成し、重要なイベント (特に User Deleted や GroupMembership の変更) への自動対応から導入を始めることを推奨します。
