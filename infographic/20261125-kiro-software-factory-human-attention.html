🏭 人間の注意力を中心に据えた
ソフトウェアファクトリーの構築

📅 2026 年 11 月 25 日 ｜ 運用手法「Manual」をオープンソース公開

📝 概要

Kiro チームが、自分たち自身のソフトウェアファクトリーの構築方法をブログで公開しました。ソフトウェアファクトリーとは、タスクボード上の作業項目をリリース済みの変更へと変換する仕組みで、トリアージから設計、実装、リリース、モニタリングまでをエージェントが自律的に進め、人間は意思決定が必要な場面でのみ関与します。

中心的な主張は「エージェントに任せられる量の上限は人間の注意力 (attention) で決まる」という点です。エージェントがコードを書く速度は人間がレビューする速度を上回るため、Kiro チームは「人間の注意力をどこに、どのように使うか」を中心にファクトリーを設計しました。あわせて、運用方法をプロンプトとスキルのセットとしてまとめた「Manual」を GitHub リポジトリ kirodotdev-labs/sample-kiro-factory-manual でオープンソースとして公開しました。

😰 Before: アップデート前の課題
  • エージェントの速度にレビューが追いつかず、レビューが滞留するか流し読みになるかの二択
  • レビューに必要なコードベース理解やチームプラクティスの知識を、レビューエージェントだけではカバーしきれない
  • メンバーごとにセットアップが異なり、チーム全体で頼れる統一された品質基準がない
  • タスクを 1 件ずつ手渡して進捗を見守る運転作業に多くの時間が取られる
🎉 After: ファクトリーと Manual による改善
  • Discover から Learn までの 7 つのステップをワーカーが自律実行し、人間は重要な意思決定のみに集中
  • 各ステップが検証ループで自己チェックし、検証可能なアウトプットを残すためレビュー負荷が低下
  • 人間のすべての修正を Learn が読み取り、ファクトリー自体がチーム全体から学習
  • Manual がオープンソース公開され、Kiro CLI と GitHub リポジトリがあればどのチームでも試せる

6 つのステップが閉じたループを構成し、Learn が外側からすべてのステップのスキルを改善します。人間は、元に戻しにくい意思決定とマージ前のレビューでのみ関与します。

⚡ 主要機能

1️⃣ ライフサイクル全体を分担する 7 つのステップ
ステップ役割
🔍 Discover新しい作業をタスクボードに起票する
🩺 Triageコードを読んで問題を特定し、誰の判断が必要かを決める
📝 Design必要な場合はスペックを作成し、チームが求める場合は人間が承認する
⚙️ Implementテスト付きで実装し、レビューコメントや CI への対応まで自分で行う
🚀 Release変更をユーザーに届けるリリース作業を管理する
📈 Monitor変更の効果を確認し、問題があればフォローアップを起票する
🧠 Learnすべてのステップが使うスキルを改善する
2️⃣ スケジュール実行される自律ワーカー

各ステップには専用のワーカー (エージェント) があり、チーム共有のホスト上でスケジュール実行。誰かがセッションを開始しなくても前のステップが残した作業項目を自動的に拾って処理します。ワーカーは実行間で状態を保持しないため、必要な情報はすべてボード項目やプルリクエスト上に残されます。

3️⃣ 各ステップの検証ループと検証可能なアウトプット

各ステップは成果物の候補を作成し、ビルド、テスト、レビューエージェント、チームで合意したプラクティスなど、チームが信頼するシグナルと照合します。基準を満たさなければ再試行し、堅実な収束が見込めない場合は停止します。

元に戻しにくい選択のみ人間に確認 (永続化データ、公開インターフェース、セキュリティ動作の変更など)。プルリクエストには何をなぜ変えたか、検討した代替案、各チェックの結果をまとめたページが添付され、人間はコード全行ではなくこのページを読んでレビューできます。

4️⃣ チーム全体からの学習

ボード項目やプルリクエスト上で人間が行った修正を Learn ステップがすべて読み取り、既存スキルへの変更を提案します。個人がメモリーやカスタムスキルに記録する方式と異なり、誰かが教訓に気づいて書き留める必要がありません。

5️⃣ Manual のオープンソース公開

ファクトリーの運用方法をプロンプトとスキルのセット「Manual」として公開。各チームは Manual の上にインスタンス (独自の設定とスキル) を書き、自分たちのリポジトリ、ボード、ホスティングに接続します。インスタンスにはゴールを定義でき、ファクトリーの挙動とすべての学習サイクルに反映されます。

🚀 設定方法

✅ 前提条件

✓Kiro CLI がインストールされていること
✓GitHub リポジトリと GitHub CLI が利用できること
⚠ワーカーはスケジュールに従って稼働しクレジットを消費するため、小さく始めること
⚠ファクトリー専用のアカウントを用意し、対象リポジトリのみへのアクセスに限定すること (詳細は README に記載)

📋 手順

1
Manual リポジトリの確認
Bash Manual のリポジトリを取得する 
# Manual のリポジトリを取得する
git clone https://github.com/kirodotdev-labs/sample-kiro-factory-manual

オープンソースの Manual (プロンプトとスキルのセット) を取得します。ボード、コードホスト、ホスティングはインテグレーションとして自分たちの環境に向けられます。

2
インスタンスの作成

既存のプロジェクトを選び、エージェントにリポジトリ内の factory-setup スキルを指定して、チーム用のインスタンス (設定とスキル) を一緒に作成します。インスタンスは Manual をチームのリポジトリ、タスクボード、ホスティングに接続し、必要に応じてゴールも定義します。

3
バックログの項目を投入

バックログからいくつかの作業項目をファクトリーに渡して処理させます。ワーカーがスケジュールに従って項目を拾い、各ステップを進め、人間の判断が必要な場合はボード項目やプルリクエスト上のコメントとして通知します。

⚖️ メリットと制約事項

👍 ビジネス面のメリット

✓人間の時間を高価値な意思決定へ集中: 起動や監視の時間を、何を作るべきかの判断に振り向けられる
✓スループットの向上: 多数の項目が誰も運転することなく同時に進行 (オープン項目の約 85% に PR が存在)
✓リリース後の効果検証の定着: Monitor がすべての変更の効果を確認し、学習にフィードバック

🛠️ 技術面のメリット

✓レビュー負荷の軽減: チェック済みの要約ページを起点に判断できる
✓品質基準の統一: すべての変更が同じ基準を満たし、有効な個人の実験はチーム全体に展開できる
✓継続的な自己改善: 人間の修正がすべて学習の入力となり、注意を減らしても安全かの証拠が蓄積
✓オープンな構成: ボード、コードホスト、ホスティングを自分たちの環境に差し替え可能

⚠️ 制限事項

✗現時点の対象はバックログ内の単発タスクとバグ。設計と分割が必要な大規模機能はまだ対象外
✗意図的にセミオートマチックな運用。メインブランチへのマージには必ず人間のレビューが必要
✗ワーカーは実行間で何も記憶しないため、コンテキストはすべてボードや PR 上に残す必要がある
✗大規模な既存リポジトリではコールドスタートとなり、コードベースの永続的な表現が必要 (検討中の領域)

🤔 考慮すべき点

⚠意思決定の分散により判断の回数自体は増え、無関係なタスク間を行き来する (「人間向けの宿題生成器」と感じる日もあると率直に記載)
⚠スループット優先のため、単一の項目は自分で作業するより時間がかかる場合がある (急ぎの項目は人間がワーカーを個別に起動可能)
⚠問い合わせの頻度が高すぎると停滞するため、エスカレーション条件の調整が必要 (Kiro チームは「元に戻しにくい選択のみ確認」へ調整)
⚠ワーカーは誰も見ていなくてもクレジットを消費するため、小さく始めることを推奨

💡 ユースケース

🐛 ユースケース 1: バックログの単発タスクとバグの自動処理

シナリオ: 小規模な修正タスクやバグ報告が溜まっており、エージェントへの手渡しとレビューに時間を取られている。

実装: factory-setup スキルでインスタンスを作成 → バックログから数件を投入 → Implement が実装、テスト、CI 対応まで完了した PR を作成 → 人間は検証可能なアウトプットのページを確認してマージを判断。

✨ 効果: 起動と監視の作業がなくなり、レビューはチェック済みの要約を起点に行えるため、人間の時間が意思決定に集中する。
📈 ユースケース 2: リリース後の効果検証とフォローアップの自動化

シナリオ: リリース後に効果を上げたかの確認が徹底されておらず、問題の発見が遅れる。

実装: インスタンスのスキルで Monitor が参照する本番テレメトリーを定義 → Release が各クライアントとチャネルへの展開を追跡 → Monitor が効果を確認し、問題があれば Discover 経由でボードに起票。

✨ 効果: すべての変更について効果が確認され、その結果が Learn を通じてファクトリーの改善に還元される。
🧠 ユースケース 3: レビューで得た知見のチーム全体への展開

シナリオ: レビューで繰り返し同じ指摘をしているが、知見が個人のメモにしか残らず、チーム全体の品質基準に反映されない。

実装: レビュアーはボード項目や PR 上で通常どおり修正を指摘 → Learn ステップが定期実行時にすべての修正を読み取る → 既存スキルへの変更が提案され、以後すべてのステップに反映。

✨ 効果: 誰かが教訓を書き留めなくても、チーム全体の修正がファクトリーの品質基準として蓄積される。
