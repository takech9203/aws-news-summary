Amazon SageMaker HyperPod

🕵️ Kubernetes Resource Monitoring Agent
トレーニング阻害要因を自動検出

📅 リリース日: 2026 年 11 月 23 日 ｜ 機能: HyperPod Kubernetes Resource Monitoring Agent

📝 概要

Amazon SageMaker HyperPod が、Amazon EKS オーケストレーションのクラスターにおいて、トレーニングを妨げる Kubernetes の問題 (クラッシュループするデバイスプラグイン、欠落した DaemonSet など) を検出できるようになりました。 新しい Kubernetes Resource Monitoring Agent がクラスターごとに 1 つ稼働し、すべてのノード、重要な Pod、必須の DaemonSet、分散トレーニングジョブを継続的に監視します。

検出した問題は影響を受ける特定のトレーニングジョブと関連付けられ、Kubernetes イベント、構造化 CloudWatch ログ、EventBridge 経由の HyperPod クラスターイベントとしてレポートされます。大規模 GPU クラスターを運用する ML インフラエンジニアにとって、障害発生時の原因特定時間 MTTR を大幅に短縮できる重要なアップデートです。

😣 Before: 手動での原因調査

  • ジョブのエラーに原因の Pod・ノード名が含まれず、kubectl 出力とランクごとのログを突き合わせて手動で根本原因を再構築
  • 既存の Health Monitoring Agent はハードウェア・ホスト障害のみ検出し、Kubernetes レイヤーの問題はカバー外
  • NCCL 集合通信が停滞しても、実行中にどのランクが原因か特定する手段がなかった

😊 After: 自動検出と関連付け

  • デバイスプラグインのクラッシュ、DaemonSet 欠落、GPU / EFA 容量減少などを自動検出し、影響ジョブと関連付け
  • ジョブ失敗時に失敗理由と関係する Pod・ノードを構造化ログとして記録
  • K8s イベント / CloudWatch / EventBridge の 3 経路で通知し、既存の運用ワークフローに統合
  • NCCL RAS により実行中ジョブの GPU 間通信の健全性を可視化

エージェントはクラスターごとに 1 つ稼働し、ノード・重要 Pod・DaemonSet・トレーニングジョブをクラスター全体のインフォーマーで監視します。検出した問題は Kubernetes イベント、CloudWatch Logs、EventBridge の 3 経路でレポートされます。

⚡ 主要機能

🖥️ 1. ノードの監視
  • Ready / MemoryPressure / DiskPressure / PIDPressure / NetworkUnavailable 状態の悪化を検出
  • 割り当て可能な NVIDIA GPU (nvidia.com/gpu) や EFA デバイス (vpc.amazonaws.com/efa) の容量減少を検出 (Ready 直後のノードには 10 分間の猶予期間)
  • GPU ノードの NVIDIA capability ラベル喪失を検出 (デバイスプラグインやドライバーの問題を示唆)
  • Taint の追加・変更を検出し、NoExecute の場合は退避される可能性のある Pod とジョブを記録
  • HyperPod 管理ラベルの欠落を検証 (新規ノードには 5 分間の猶予期間)
🧩 2. 重要インフラ Pod の監視
  • kube-system、aws-hyperpod、kubeflow、nvidia-gpu-addon 名前空間の DaemonSet 所有 Pod などを重要 Pod として扱う
  • 失敗、CrashLoopBackOff、コンテナエラー、5 分間実行状態にならない Pod を検出
  • 再起動回数の増加や 1 分以上 Not Ready が続く Pod を検出
  • 各 Pod を所有するトレーニングジョブとノードにマッピングし、リソース間で問題を関連付け
⚙️ 3. DaemonSet の監視
  • monitoring.necessaryDaemonsets に列挙された必須 DaemonSet (デフォルト: Health Monitoring Agent) の存在を 5 分ごとに検証
  • 5 分間すべての Pod が利用可能にならない部分的可用性低下を検出
  • 15 分間進捗のないロールアウト停滞や、スケジュールミスの Pod を検出
🏋️ 4. 分散トレーニングジョブの監視
  • HyperPod PyTorchJob、Kubeflow TrainJob (Trainer v2)、Kubeflow PyTorchJob (v1、レガシー) のライフサイクルを追跡
  • ジョブ失敗時に、失敗理由と影響を受けた Pod・ノードのコンテキストを含めてレポート
  • 対応する CRD が未インストールのジョブタイプは監視が自動的に無効化
📡 5. NCCL 集合通信ヘルスの監視 NCCL RAS
  • 各トレーニング Pod 上の NCCL RAS デーモン (デフォルト TCP ポート 28028) に定期接続し、ジョブレベルの健全性を判定
  • NCCL 2.24 以降が必要。トレーニングコンテナで NCCL_RAS_ADDR を Pod IP に設定
✅ healthy全エンドポイント正常
⚠️ degraded一部到達不能 = GPU 通信の部分的喪失
🚨 unhealthy全エンドポイント失敗 = 集合通信の停滞・停止の可能性

🧭 3 つのコンポーネントの役割分担

本エージェントは、既存の HyperPod 耐障害性コンポーネントを補完します。

コンポーネント実行単位役割
Health Monitoring Agent 各ノード NVIDIA GPU エラー、AWS Trainium エラー、EC2 プラットフォームエラーなどハードウェア・ホストレベルの障害検出。ノードの自動交換・再起動と連携
Kubernetes Resource Monitoring Agent (新規) クラスターごとに 1 つ ノード・Pod・DaemonSet・トレーニングジョブにまたがる Kubernetes クラスターレベルの問題検出
HyperPod training operator ジョブ単位 分散トレーニングジョブの実行と、プロセスレベル障害からの復旧
注意: 本エージェントはオブザーバビリティコンポーネントであり、問題の検出とレポートのみを行います。ノードやワークロードの修復は行いません (問題の原因がアプリケーションワークロード側にある可能性があるため)。

📋 レポートされる主な Kubernetes イベント

イベント理由意味
NodeConditionDegradedノードの状態 (Ready、MemoryPressure など) が悪化
NodeResourceDegraded割り当て可能な GPU / EFA デバイスが提供数または以前の報告数より減少
NodeGPUCapabilityLostGPU ノードが NVIDIA capability ラベルを喪失
NoExecuteTaintAppliedNoExecute Taint が適用され、Pod とジョブが退避される可能性
CriticalPodCrashLoop重要インフラ Pod が CrashLoopBackOff 状態に
NecessaryDaemonSetMissing必須の DaemonSet が欠落
DaemonSetRolloutStalledDaemonSet のロールアウトが停滞
TrainingJobFailed分散トレーニングジョブが失敗
NCCLProtocolErrorsPersistentNCCL RAS がジョブの持続的なプロトコルエラーを報告
MonitoringDegradedエージェント自身が一部リソースを監視できない状態

問題が解消した際は NodeRecovered、PodRecovered、DaemonSetRecovered などの Normal イベントが発行されます。

📤 3 つのレポート経路

1️⃣ Kubernetes イベント

影響を受けたノード・Pod・DaemonSet・ジョブに Warning イベントを作成。kubectl get events や kubectl describe で確認可能。

2️⃣ 構造化 CloudWatch ログ

影響リソースとトリガーとなった変化を含む JSON ログを、ロググループ /aws/sagemaker/Clusters/{cluster-name}/{cluster-id} のログストリーム SageMakerClusterMonitoringAgent/{instance-group}/{instance-id} に出力。

3️⃣ HyperPod クラスターイベント EventBridge

クラスタースコープの HyperPodKRMAConfig オブジェクトにヘルスレポートを保持し、HyperPod がクラスターイベントに変換。ListClusterEvents / DescribeClusterEvent API で一覧でき、デフォルトイベントバスにソース aws.sagemaker、詳細タイプ SageMaker HyperPod Cluster Event として配信 (NodeProvisioningMode が Continuous のクラスターで利用可能)。

🛠️ 設定方法

✅ 前提条件

✓Amazon EKS でオーケストレーションされた SageMaker HyperPod クラスター
✓Helm と kubectl がセットアップ済みであること
✓ノードから対象リージョンの Amazon ECR へのネットワーク経路があること
✓NCCL RAS モニタリングを使用する場合は NCCL 2.24 以降
1
HyperPod Helm チャートでエージェントを有効化してインストール
Bashサブチャートの有効化 (デフォルトは無効)
git clone https://github.com/aws/sagemaker-hyperpod-cli.git
cd sagemaker-hyperpod-cli/helm_chart
helm dependencies update HyperPodHelmChart
helm install dependencies HyperPodHelmChart \
  --namespace kube-system \
  --set hyperpod-kubernetes-resource-monitor.enabled=true \
  --set hyperpod-kubernetes-resource-monitor.region=<リージョン>

エージェントは aws-hyperpod 名前空間にデプロイされます。

2
既存クラスターへの追加 (チャートインストール済みの場合)
BashCRD を先に適用してからアップグレード
kubectl apply -f HyperPodHelmChart/charts/hyperpod-kubernetes-resource-monitor/crds/
helm upgrade dependencies HyperPodHelmChart \
  --namespace kube-system \
  --reuse-values \
  --set hyperpod-kubernetes-resource-monitor.enabled=true \
  --set hyperpod-kubernetes-resource-monitor.region=<リージョン>

Helm はアップグレード時に CRD をインストールしないため、先に HyperPodKRMAConfig CRD の適用が必要です。

3
デプロイの確認
BashDeployment / Pod / CRD オブジェクトの確認
kubectl get deployment -n aws-hyperpod hyperpod-kubernetes-resource-monitoring-agent
kubectl get pods -n aws-hyperpod -l app=cluster-monitoring-agent
kubectl get hyperpodkrmaconfigs default
4
エージェントが発行するイベントの確認
Bash全名前空間からエージェントのイベントを一覧
kubectl get events -A --field-selector source=hyperpod-kubernetes-resource-monitoring-agent
5
必須 DaemonSet の宣言 (任意)
YAMLHelm 値 monitoring.necessaryDaemonsets
monitoring:
  necessaryDaemonsets:
    - name: "health-monitoring-agent"
      namespace: "aws-hyperpod"
    - name: "dependencies-nvidia-device-plugin"
      namespace: "kube-system"
    - name: "dependencies-aws-efa-k8s-device-plugin"
      namespace: "kube-system"

5 分ごとに存在が検証され、欠落時に NecessaryDaemonSetMissing イベントが発行されます。リストを設定するとデフォルトが置き換えられるため、Health Monitoring Agent のエントリは必ず残します。

6
NCCL RAS モニタリングの有効化 (任意)
YAMLトレーニングコンテナの環境変数設定
env:
  - name: POD_IP
    valueFrom:
      fieldRef:
        fieldPath: status.podIP
  - name: NCCL_RAS_ADDR
    value: "$(POD_IP):28028"

NCCL はデフォルトで localhost のみで RAS クライアントを待ち受けるため、NCCL_RAS_ADDR を Pod IP に設定してエージェントから到達可能にします。セキュリティ上の影響を考慮し、ポート 28028 へのアクセスをエージェントの Pod のみに制限する Kubernetes NetworkPolicy の併用が推奨されています。

💰 メリット

💼 ビジネス面

✓MTTR の短縮: ジョブ失敗の原因となった Pod とノードが自動的に特定・記録され、高価な GPU クラスターのアイドル時間を最小化
✓GPU 投資の保護: デバイスプラグインのクラッシュなどで GPU がジョブから脱落する問題を早期に検知し、計算リソースの無駄を防止
✓運用負荷の軽減: kubectl 出力とランクごとのログを突き合わせる手作業の調査が不要に

🔧 技術面

✓ジョブとインフラ問題の自動関連付け: Kubernetes レベルの問題が、影響を受ける具体的なトレーニングジョブと紐付けてレポートされる
✓3 経路での通知: K8s イベント / CloudWatch Logs / EventBridge という標準的な仕組みで、既存の監視・アラートパイプラインに統合しやすい
✓トレーニングへの影響なし: 単一レプリカで GPU インスタンスを避けてスケジュールされ、CPU 100m / メモリ 512Mi の小さなフットプリントで動作
✓実行中ジョブの NCCL 可視化: ジョブ完了を待たずに、NCCL 集合通信の停滞やどのランクが遅れているかを把握

⚠️ デメリット・制約事項

🚫 制限事項

✗EKS オーケストレーションの HyperPod クラスターのみが対象 (Slurm オーケストレーションは対象外)
✗検出とレポートのみを行うオブザーバビリティコンポーネントであり、ノードやワークロードの自動修復は行わない
✗HyperPod 管理ノードでのみ動作 (非管理ノードで起動した場合はログを記録して終了)
✗HyperPod クラスターイベント (EventBridge 配信) は NodeProvisioningMode が Continuous のクラスターでのみ利用可能
✗Helm チャートではサブチャートがデフォルト無効のため、明示的な有効化が必要
✗ジョブタイプごとの監視は対応する CRD がインストールされている場合のみ動作

🤔 考慮すべき点

⚠️NCCL RAS モニタリングには NCCL 2.24 以降と、トレーニングコンテナでの NCCL_RAS_ADDR 設定が必要
⚠️NCCL_RAS_ADDR を Pod IP に設定すると任意の Pod から RAS 状態を照会できるため、NetworkPolicy によるアクセス制限を検討 (EKS では VPC CNI のネットワークポリシーサポート有効化が前提)
⚠️Pod モニターは monitoring.monitoredNamespaces (デフォルト: aws-hyperpod、kube-system、default、kubeflow) のみを監視。別の名前空間でジョブを実行する場合はリストへの追加が必要
⚠️monitoring.necessaryDaemonsets を設定するとデフォルトのリストが置き換えられるため、Health Monitoring Agent のエントリを残す必要がある

🎯 ユースケース

💡 1. デバイスプラグイン障害による GPU 脱落の早期検知

シナリオ大規模な事前学習ジョブの実行中、あるノードで NVIDIA デバイスプラグインが繰り返しクラッシュし、そのノードの GPU がジョブから脱落。従来はジョブ失敗後にランクごとのログから原因ノードを推測する必要があった。

Bash / Logs Insights問題ノードの特定
# エージェントが発行したイベントから問題のノードを特定
kubectl get events -A --field-selector source=hyperpod-kubernetes-resource-monitoring-agent

# CloudWatch Logs Insights で GPU 容量低下を検索
fields @timestamp, @message
| filter @message like /NodeResourceDegraded/
| sort @timestamp desc

効果GPU 脱落時点で NodeResourceDegraded / CriticalPodCrashLoop イベントにより問題ノードが特定され、ジョブ失敗時には失敗理由と関係する Pod・ノードが記録される。ノード修復とジョブ再開までの時間を大幅に短縮。

💡 2. クラスターイベントによる運用アラートの自動化

シナリオML プラットフォームチームが、Health Monitoring Agent の停止や GPU 容量低下などのクラスター健全性の問題を、既存のインシデント管理フローに自動で通知したい。

JSONEventBridge イベントパターン
{
  "source": ["aws.sagemaker"],
  "detail-type": ["SageMaker HyperPod Cluster Event"]
}

効果EventBridge ルールを作成し Amazon SNS トピックなどをターゲットに設定することで、障害発生時 (Warn) と回復時 (Info) のイベントを自動受信。未解消の障害は 6 時間ごとに繰り返し通知されるため、対応漏れを防止。

💡 3. 実行中ジョブの NCCL 通信停滞の特定

シナリオ数百 GPU を使用する分散トレーニングで、NCCL 集合通信が停滞してスループットが低下。従来はジョブを停止してログを解析するまで、どのランクが原因か分からなかった。

YAMLNCCL RAS を外部到達可能に設定
env:
  - name: POD_IP
    valueFrom:
      fieldRef:
        fieldPath: status.podIP
  - name: NCCL_RAS_ADDR
    value: "$(POD_IP):28028"

効果エージェントが 30 秒間隔 (デフォルト) で各トレーニング Pod の NCCL RAS デーモンに接続し、通信健全性を healthy / degraded / unhealthy の 3 段階で判定。実行中にどのランクが遅れているかを特定でき、問題ノードの切り離し判断を迅速化。

🔗 関連サービス・機能

→Amazon EKS: HyperPod クラスターのオーケストレーションレイヤー。本エージェントは EKS オーケストレーションのクラスター専用
→HyperPod Health Monitoring Agent: 各ノードで GPU / Trainium / EC2 プラットフォームレベルの障害を検出する既存コンポーネント。本エージェントはこれを補完し、必須 DaemonSet としての存在確認も実施

→Amazon EventBridge: HyperPod クラスターイベントの配信先。ルールを作成して SNS などへの通知を自動化

📝 まとめ

SageMaker HyperPod の Kubernetes Resource Monitoring Agent により、これまで kubectl 出力とランクごとのログから手動で推測するしかなかった Kubernetes レベルの障害原因 (クラッシュループするデバイスプラグイン、欠落した DaemonSet、Taint による退避など) が、影響を受けるトレーニングジョブと関連付けて自動検出されるようになりました。

EKS オーケストレーションの HyperPod クラスターを運用しているチームは、Helm チャートでサブチャートを有効化するだけで導入できるため、まず必須 DaemonSet の宣言と EventBridge ルールの設定から始めることを推奨します。NCCL 2.24 以降を利用している場合は、NCCL RAS モニタリングによる実行中ジョブの通信健全性の可視化も検討する価値があります。
