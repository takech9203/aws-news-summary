AWS Identity and Access Management 📅 2026 年 8 月 10 日

🔐 アカウントアクセスマネージャー

ワークフォースユーザーへの IAM ロール割り当てを簡素化 — IAM Identity Center の ID に既存 IAM ロールを直接リンク

📌 概要

IAM の新機能アカウントアクセスマネージャー (Account access manager) により、管理者は AWS アカウント内の既存の IAM ロールを、AWS IAM Identity Center で管理されているワークフォースユーザーおよびグループに直接リンクできるようになりました。

従来の「アカウントごとの個別フェデレーション」と「IAM Identity Center の許可セット」の利点を組み合わせ、以下の 3 つを同時に実現します。

❌ Before: アップデート前の課題
  • IAM ロールの柔軟性 (信頼ポリシー、ABAC、ロールパス) を使うには、外部 IdP からアカウントごとに個別フェデレーションが必要で、SAML アプリ構成の運用負荷が発生
  • 許可セットのロールはイミュータブルで、アカウントごとのカスタム IAM ロール要件に適合しにくい
  • ロールとユーザーのマッピングが外部 IdP 側にあり、AWS 側から「誰がどのロールにアクセスできるか」を把握しづらい
✅ After: アップデート後の改善
  • IAM Identity Center のユーザー / グループに、各アカウントの既存 IAM ロールを直接割り当て可能に
  • 信頼ポリシー、セッションタグによる ABAC、ロールパスなどIAM ロール本来の柔軟性を維持したまま単一フェデレーションで運用
  • 専用のアカウントアクセスポータルで割り当てを確認・利用でき、CLI では aws login で認証情報を取得
追加料金なし

ワークフォースユーザーは IAM Identity Center で一度サインインし、アカウントアクセスマネージャーの割り当てに基づいて、各アカウントの既存 IAM ロールへポータル経由でアクセスします。

⚡ 主要機能

1️⃣ IAM Identity Center ユーザー / グループへの IAM ロール割り当て
組織インスタンスのユーザーとグループに、AWS アカウント内の IAM ロールでアカウントアクセスを割り当て。ID ソースから同期した ID と直接作成した ID の両方に対応し、許可セットとの併用も単独使用も可能。
2️⃣ IAM ロールの柔軟性の活用
ロールタグとセッションタグによる属性ベースアクセス制御 (ABAC)、信頼ポリシーによるロール引き受け制限・ネットワーク条件・IdP アサートクレームの条件利用、ロールパスによる論理的グループ化に対応。
3️⃣ アカウントアクセスポータル
ユーザーが自分に割り当てられた AWS アカウントとロールを一覧・アクセスできる専用ポータル。IAM Identity Center ユーザーとしてサインイン後、ポータル URL 経由でアクセス。
4️⃣ CLI アクセス (aws login コマンド)
ブラウザで AWS にサインインした後、aws login コマンドで IAM ロールセッションの認証情報を取得。セッション有効期間中は再認証なしで AWS CLI を継続利用可能。
5️⃣ 専用 API 名前空間
IAM API とは別の独自 API 名前空間 account-access を提供。AWS CLI / SDK からの操作に加え、AWS CloudFormation / CDK による IaC 管理にも対応。

🛠️ 設定方法

✅ 前提条件

✓AWS Organizations が構成され、IAM Identity Center の組織インスタンスが有効化されていること
✓ID ソース (外部 IdP または IAM Identity Center 内) からユーザーとグループが同期または作成されていること
✓割り当て対象の IAM ロールが各 AWS アカウントに作成されていること (IaC または手動)

🚀 手順

1
IAM ロールの準備
割り当てに使用する IAM ロールを確認。ロールパスを活用すると、ワークフォース用ロールを論理的にグループ化して管理を簡素化できます。
Bash 割り当て対象となる IAM ロールを確認 
# 割り当て対象となる IAM ロールを確認
aws iam list-roles --path-prefix /workforce/
2
アカウントアクセスマネージャーでの割り当て
IAM コンソールのアカウントアクセスマネージャー画面から、IAM Identity Center のユーザーまたはグループを選択し、対象アカウントの IAM ロールにリンク。AWS CLI / SDK では account-access 名前空間の API、または CloudFormation / CDK で IaC として管理することも可能。
3
ユーザーによるアクセス
ユーザーは IAM Identity Center ユーザーとしてサインインし、アカウントアクセスポータルから割り当てられたアカウントとロールにアクセス。aws login はブラウザで確立したロールセッションの認証情報を CLI に取り込み、セッション有効期間中は再認証なしで CLI を利用できます。
Bash CLI で認証情報を取得 
# ブラウザでサインインしてロールにアクセスした後、CLI で認証情報を取得
aws login

⚖️ メリットと制約事項

💼 ビジネス面のメリット

✓運用負荷の削減: IdP でアカウントごとに SAML アプリを構成する必要がなくなり、単一のフェデレーションポイントに集約
✓ガバナンスの向上: ロールとユーザーのマッピングが AWS 側に保持され、アクセス状況を把握しやすい
✓追加コストなし: 既存の IAM ロール資産をそのまま活用可能

🔧 技術面のメリット

✓IAM ロールの柔軟性を維持: 信頼ポリシー、ABAC 用セッションタグ、ロールパスなど許可セットでは実現しにくい細かな制御
✓許可セットとの併用: ベースラインは許可セット、カスタムロールはアカウントアクセスマネージャーと使い分け可能
✓IaC 対応: CloudFormation / CDK で割り当てをコードとして管理

🚧 制限事項

✗IAM Identity Center の組織インスタンスが前提。AWS Organizations 未使用の環境では利用不可
✗IAM ロール自体の作成・管理は自動化されないため、IaC または手動でのプロビジョニングが必要
✗利用可能なのは AWS 商用リージョンのみ。他パーティションでの提供は発表に含まれていない

💭 考慮すべき点

⚠許可セット / アカウントアクセスマネージャー / 直接フェデレーションの 3 方式が併存するため、用途ごとの方針整理が必要
⚠CLI 体験が許可セット (aws sso login) と異なる (aws login) ため、ユーザーへの周知が必要
⚠信頼ポリシーや ABAC を活用する場合、設定ミスによる意図しないアクセス許可を防ぐレビュープロセスが重要

💡 ユースケース

🏢 ユースケース 1: アカウントごとに異なるカスタムロールの一元的な割り当て
シナリオ: 事業部ごとに AWS アカウントが分かれ、各アカウントで要件の異なるカスタム IAM ロール (データ分析用、開発用など) を運用。これまでは外部 IdP でアカウントごとにフェデレーションを構成していた。
実装例
Plaintext実装ステップ
1. 各アカウントのカスタム IAM ロールを IaC (CloudFormation / CDK) で管理
2. アカウントアクセスマネージャーで IAM Identity Center のグループ
   (例: data-analysts) を各アカウントの分析用ロールに割り当て
3. ユーザーはアカウントアクセスポータルから対象アカウントにアクセス
🎯 効果: IdP 側のアカウント別 SAML 構成が不要になり、フェデレーションポイントを一本化しながらカスタムロールの柔軟性を維持できる。
🏷️ ユースケース 2: セッションタグを使った ABAC によるアクセス制御
シナリオ: プロジェクトタグに基づいてリソースアクセスを制御したい。許可セットでは実現しにくい、セッションタグを条件とするきめ細かな権限制御が必要。
実装例
Plaintext実装ステップ
1. IAM ロールの許可ポリシーで aws:PrincipalTag/project 条件を使用
2. ロールタグやセッションタグでプロジェクト属性を付与
3. アカウントアクセスマネージャーで該当ユーザーグループにロールを割り当て
🎯 効果: ロール数を増やさずに、属性ベースでプロジェクト単位のアクセス制御を実現できる。
🔀 ユースケース 3: 許可セットとの併用によるハイブリッド運用
シナリオ: 全社共通の読み取り専用アクセスや管理者アクセスは標準化しつつ、一部のアカウントでは特殊な信頼ポリシー条件 (ネットワーク条件、IdP クレーム条件) を持つロールが必要。
実装例
Plaintext実装ステップ
1. 共通のベースラインアクセスは IAM Identity Center 許可セットで提供
2. 特殊要件のロールは各アカウントで作成し、信頼ポリシーに
   ネットワーク条件や IdP アサートクレームの条件を設定
3. アカウントアクセスマネージャーで該当ユーザーに割り当て
🎯 効果: 標準化と柔軟性を両立し、例外的な要件にも単一のフェデレーションポイントで対応できる。

💰 料金・利用可能リージョン

💵 料金
アカウントアクセスマネージャーは追加料金なしで利用できます。IAM および IAM Identity Center 自体も無料で利用可能です。
🌍 利用可能リージョン
すべての AWS 商用リージョンで利用可能。デフォルトで有効化されています。

🔗 関連サービス・機能

🎯AWS IAM Identity Center: ワークフォースユーザー / グループの管理と単一のフェデレーションポイントを提供。アカウントアクセスマネージャーはここで管理される ID を割り当て対象とする
🔑IAM ロール: 割り当ての対象となる既存のロール。信頼ポリシー、セッションタグ、ロールパスなどの柔軟な設定を活用できる
🏛️AWS Organizations: IAM Identity Center の組織インスタンスの前提となるマルチアカウント管理サービス
📜AWS CloudFormation / CDK: アカウントアクセスマネージャーの割り当てを IaC として管理可能

📝 まとめ

アカウントアクセスマネージャーは、IAM Identity Center の単一フェデレーションポイントとユーザー可視性に、IAM ロールの柔軟な権限制御を組み合わせる新しい選択肢です。

✓外部 IdP からの個別フェデレーションを運用している組織は、フェデレーションの一本化と運用負荷の削減を検討
✓許可セットでは対応しきれないカスタムロール要件を持つ組織に有効
✓まずは IAM コンソールで既存ロールの割り当てを試し、許可セットとの使い分け方針を整理するのがおすすめ
