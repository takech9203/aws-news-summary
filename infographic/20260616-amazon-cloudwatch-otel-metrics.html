🔍 概要

Amazon CloudWatch が OpenTelemetry メトリクスのネイティブサポートを開始しました。OpenTelemetry プロトコル (OTLP) でメトリクスを送信し、Prometheus Query Language (PromQL) でクエリを実行できます。料金は取り込み量に応じた GB 単位課金で、15 か月間のストレージが含まれます。

最大の特長は、アプリケーションのカスタムメトリクスと 70 を超える AWS サービスのメトリクスを単一のソリューションに統合し、PromQL で横断的にクエリできる点です。Prometheus 互換のクエリ API を提供するため、既存の Prometheus や Grafana のツールチェーンを変更せずに CloudWatch を保存先 (destination) として利用できます。

📈 Before / After

⛔ アップデート前の課題

  • 従来の CloudWatch メトリクス (Classic) は PutMetricData API や EMF 前提で、OTel / Prometheus 環境では形式変換が必要
  • クエリ言語が Metrics Insights (SQL) で、PromQL と非互換
  • メトリクスごとの月額課金で、高カーディナリティなコンテナ環境ではコスト予測が困難
  • ディメンションは 1 メトリクスあたり最大 30 個までの制約

✅ アップデート後の改善

  • OTLP エンドポイント経由で OTel SDK / コレクターをそのまま接続可能
  • PromQL でカスタム + AWS サービスメトリクスを横断クエリ
  • GB 単位課金で高カーディナリティでもコスト構造が明確
  • 1 データポイントあたり最大 150 ラベルをサポート

⚡ 主要機能

📥 1. OTLP によるネイティブメトリクス取り込み

  • OpenTelemetry プロトコル (OTLP) のエンドポイントを通じてメトリクスを送信
  • Prometheus / Grafana と連携する OTel SDK・コレクターを追加変換なしでそのまま利用
  • ベンダーニュートラルなオープンソース計装を維持したまま CloudWatch を保存先に

🔍 2. PromQL によるクエリ

  • Prometheus Query Language (PromQL) でメトリクスをクエリ
  • カスタムメトリクスと 70+ AWS サービスメトリクスを単一ソリューションで横断クエリ
  • Prometheus 互換クエリ API により既存ツールチェーンから接続可能

💾 3. GB 単位課金と長期保持

  • 取り込み量に応じた GB 単位の課金体系
  • 15 か月間のストレージが料金に含まれる
  • 1 データポイントあたり最大 150 ラベルで高カーディナリティに対応

🛠️ 技術仕様: 2 つのメトリクスモデル比較

CloudWatch は OpenTelemetry メトリクスと従来の CloudWatch メトリクス (Classic) の 2 モデルをサポートし、いずれも完全にサポートされています。

🧭 利用開始の指針

→初めて使う場合: OpenTelemetry メトリクス (推奨) から開始
→既に PutMetricData / EMF を使用: CloudWatch メトリクス (Classic) を継続利用
→AWS サービスメトリクスを PromQL で: AWS ベンドメトリクスの OTel 形式取り込みを有効化

STEP 1: OTel Collector / SDK のエクスポーター設定で送信先を CloudWatch の OTLP エンドポイントに設定。計装コードの変更は最小限。

STEP 2: AWS ベンドメトリクスの OTel 形式取り込みを有効化し、70+ サービスとカスタムメトリクスを単一クエリで扱えるように。

STEP 3: コンソール、Prometheus 互換 API、または Grafana から PromQL でクエリ。

💡 メリット

📊 ビジネス面

  • ▸ 既存ツールチェーン活用: Prometheus / Grafana を変えずに採用、移行コスト削減
  • ▸ コスト構造の明確化: GB 単位課金でコンテナ環境でも予測しやすい
  • ▸ 監視データの一元化: カスタム + AWS メトリクスを集約し運用分断を解消

🔧 技術面

  • ▸ オープンスタンダード準拠: OTel 標準でベンダーロックインを回避
  • ▸ 高カーディナリティ対応: 最大 150 ラベルで詳細なディメンション
  • ▸ 横断的なクエリ: PromQL でアプリ層 + インフラ層を一括分析

⚠️ デメリット・制約事項

制限事項

!一部リージョン (中東 (UAE)、中東 (バーレーン)、イスラエル (テルアビブ)) では利用不可
!OTel モデルと Classic でクエリ言語が異なる (PromQL と CloudWatch Metrics Insights)

考慮すべき点

!既存の PutMetricData / EMF 計装は Classic のまま。PromQL で扱うには OTel 形式への移行や AWS ベンドメトリクス有効化が必要
!取り込み量課金のため、高頻度・高カーディナリティ送信時は GB 量の見積もりが必要

🎯 ユースケース

① コンテナワークロードの統合監視

シナリオ: Amazon EKS 上のマイクロサービス群を Prometheus / Grafana で監視している組織が、運用基盤をマネージドサービスに集約したい。

Flow実装例
OTel Collector → CloudWatch OTLP エンドポイント → PromQL クエリ (Grafana)
✅ 効果: 既存の OTel Collector と Grafana ダッシュボードをそのまま利用しつつ、Prometheus サーバーの運用負荷を削減し、15 か月の長期保持を確保。

② カスタムメトリクスと AWS メトリクスの横断分析

シナリオ: アプリ固有のビジネスメトリクスと ELB / RDS などの AWS サービスメトリクスを同一クエリで相関分析したい。

Flow実装例
カスタムメトリクス (OTLP) + AWS ベンドメトリクス (OTel 形式) → 単一の PromQL クエリ
✅ 効果: アプリ層とインフラ層のメトリクスを横断分析でき、障害の根本原因分析を効率化。

③ ベンダーロックインを避けた監視基盤の構築

シナリオ: 将来的なマルチクラウドや他バックエンドへの移行を考慮し、オープンスタンダードに準拠した計装を維持したい。

Flow実装例
OpenTelemetry SDK (ベンダーニュートラル) → CloudWatch を含む複数の保存先に送信可能
✅ 効果: 計装コードを変更せず保存先を切り替えられ、ベンダー依存を回避しながら CloudWatch のマネージド機能を活用。

💰 料金

OpenTelemetry メトリクスは取り込み量に応じた GB 単位課金を採用し、15 か月間のストレージが料金に含まれます。従来の Classic がメトリクスごとの月額課金であるのに対し、本機能は取り込みデータ量で課金されます。

📝 まとめ

Amazon CloudWatch のネイティブ OpenTelemetry メトリクス対応は、Prometheus / Grafana を中心とするオープンソース監視エコシステムと CloudWatch を直接つなぐ重要なアップデートです。OTLP による取り込み・PromQL でのクエリ・GB 単位課金という構成により、既存ツールを維持したまま AWS のマネージド基盤を活用できます。

コンテナや高カーディナリティなワークロードを運用している組織は、OpenTelemetry メトリクスモデルへの移行を検討し、まずは小規模なワークロードで取り込み量とコストを評価することを推奨します。
