📌 概要

Amazon SageMaker Inference が コンテナイメージキャッシング をサポート。生成 AI モデルのスケールアウト時に、エンドツーエンドのスケーリングが最大 2 倍高速化されます。

エンドポイントのスケールアウト時、サービスがコンテナイメージを事前にキャッシュするため、新しいインスタンスは Amazon ECR から大きなイメージをプルする待ち時間なしに、より速くトラフィックの処理を開始できます。生成 AI ワークロードは 10 GB 以上 の大きなイメージ (LMI/vLLM、NVIDIA Triton など) を使うのが一般的で、これがコールドスタートの主要ボトルネックでした。

✓お客様による設定変更は一切不要。指定済みのイメージ URI を自動でキャッシュ
✓アクセラレーターインスタンスタイプ、単一モデルエンドポイント、推論コンポーネントベースのエンドポイントに対応

⏱️ アップデート前の課題

  • 新規インスタンスは毎回 ECR からイメージ全体をプルし、数分のコールドスタートが発生
  • 10 GB 以上の大きなイメージのプルがスケールアウトレイテンシーの最大要因
  • 既存インスタンス上のキャッシュは新規インスタンス起動時には無効

⚡ アップデート後の改善

  • イメージを事前キャッシュし、新規インスタンスのプル時間が実質 0 秒に
  • ネットワーク帯域の競合が解消され、モデルダウンロードも高速化
  • 設定変更不要、対象インスタンスで自動的に有効化

🔧 主要機能

💾 1. コンテナイメージの事前キャッシング
  • スケールアウト時に新規インスタンスへ起動するイメージをローカルに事前キャッシュ
  • 新規インスタンスでのイメージプル時間が実質 0 秒に
  • 推論コンポーネント使用時は、参照される各ユニークなイメージを保存
⚙️ 2. 設定変更不要の自動有効化
  • エンドポイント / 推論コンポーネント設定の指定イメージ URI を自動キャッシュ
  • サポート対象のアクセラレーターインスタンスタイプで自動有効化
  • カスタムイメージを含む任意の ECR ホスト型イメージで動作 (コンテナ変更も不要)
🛟 3. フォールバック動作
  • キャッシュ済みイメージが利用できない場合は ECR からプル
  • スケーリングがブロックされることはない
🚀 4. スケーリング最適化スイートの一部
  • サブミニット同時実行メトリクス (最大 6 倍高速な負荷検出)
  • instance-store コンテナキャッシング (既存インスタンス上での高速スケーリング)
  • コンテナイメージキャッシング (新規インスタンス上で最大 2 倍高速)

🛠️ サポート対象とセキュリティ

インスタンスタイプアクセラレーターインスタンスタイプ
エンドポイント種別単一モデルエンドポイント、推論コンポーネントベースのエンドポイント
イメージECR ホスト型イメージ全般 (カスタムイメージを含む)
有効化自動 (オプトイン不要)
🔒テナント分離を維持: 各キャッシュは単一のお客様のエンドポイント専用。アカウントやエンドポイント間で共有されず、エンドポイント削除時に自動パージされます。

📝 設定方法

前提条件

✓SageMaker Inference のエンドポイントまたは推論コンポーネントが構成されていること
✓サポート対象のアクセラレーターインスタンスタイプを使用していること
✓コンテナイメージが Amazon ECR にホストされていること

ステップ 1: 通常どおりエンドポイントをデプロイする

Bash 追加設定は不要 (通常のデプロイと同じ) 
# エンドポイント設定で使用するコンテナイメージ URI を指定
# (通常のデプロイと同じ。追加設定は不要)
aws sagemaker create-endpoint-config \
  --endpoint-config-name my-genai-config \
  --production-variants '[{"VariantName":"AllTraffic","ModelName":"my-genai-model","InstanceType":"ml.g6.2xlarge","InitialInstanceCount":1}]'

指定されたイメージ URI が、コンテナイメージキャッシングの対象として自動的に認識されます。追加のオプトイン操作は不要です。

ステップ 2: スケーリングポリシーを構成する (推奨)

Bash ターゲット追跡スケーリングポリシー 
# サブミニットメトリクスを活用した
# ターゲット追跡スケーリングポリシーの構成例
# ConcurrentRequestsPerModel または ConcurrentRequestsPerCopy を指定

サブミニット同時実行メトリクスを活用するポリシー (ConcurrentRequestsPerModel / ConcurrentRequestsPerCopy) を構成すると、負荷検出が最大 6 倍高速化され、イメージキャッシングと組み合わせてスケールアウト全体をさらに高速化できます。

💡 メリット

📈 ビジネス面
  • 応答性の向上: トラフィック急増時のレイテンシー悪化・リクエスト失敗のリスクを低減
  • 設定の容易さ: 設定・コード修正不要で導入コストが実質ゼロ
  • コスト効率の改善: 過剰なバッファインスタンス常時起動への依存を減らせる可能性
⚙️ 技術面
  • コールドスタートの解消: 10 GB 以上の大きなイメージのプルがボトルネックでなくなる
  • 並行処理の高速化: 帯域競合が解消され S3 モデルダウンロードも高速化
  • 耐障害性: キャッシュ不可時は ECR プルのフォールバックでスケーリング継続

⚠️ デメリット・制約事項

制限事項

!アクセラレーターインスタンスタイプが対象。対象外では効果が得られない
!改善率はインスタンスタイプ、イメージサイズ、モデルサイズによって変動
!単一モデルエンドポイントおよび推論コンポーネントベースのエンドポイントが対象

考慮すべき点

→本機能は新規インスタンスの起動を高速化。既存インスタンス上のスケーリングには instance-store コンテナキャッシングが用いられる
→全体最適化には、サブミニットメトリクスを活用したスケーリングポリシーの併用が推奨

🎯 ユースケース

1. トラフィック急増への対応

シナリオ: LLM チャットアプリで日中の特定時間帯にトラフィックが急増。従来は新規インスタンス起動に数分かかり、その間レイテンシーが悪化していた。

効果: イメージプルが実質 0 秒となりスケールアウトが最大 2 倍高速化。急増トラフィックへ迅速に対応できる。

2. 大きなコンテナイメージを使う生成 AI 推論

シナリオ: vLLM や NVIDIA Triton ベースの 17 GB 規模のイメージを使用。ECR からのプルがスケールアウトレイテンシーの大半を占めていた。

効果: 事前キャッシュでイメージプルを排除。ベンチマークでは 333 秒 → 0 秒、エンドツーエンドで約 51% 削減。

3. 推論コンポーネントによる複数モデルの集約

シナリオ: 推論コンポーネントベースのエンドポイントで複数の生成 AI モデルを集約運用。容量不足時の新規インスタンス追加の起動時間が課題だった。

効果: 参照される各ユニークなイメージがキャッシュされ、新規インスタンス追加時のスケーリングが高速化。

✅ まとめ

コンテナイメージキャッシングは、生成 AI ワークロードのスケールアウト時の最大のボトルネックであった大きなコンテナイメージのプルを排除し、エンドツーエンドのスケーリングを最大 2 倍高速化します。設定変更不要で対象インスタンスにて自動有効化されるため、生成 AI 推論を SageMaker で運用しているお客様は、サブミニットメトリクスを活用したスケーリングポリシーと組み合わせることで、トラフィック急増への応答性をさらに向上させることを検討してください。
