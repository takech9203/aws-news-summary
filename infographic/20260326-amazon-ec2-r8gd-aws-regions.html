R8gd インスタンスが追加の AWS リージョンで利用可能に

Graviton4 搭載メモリ最適化インスタンスのリージョン拡大 | 2026 年 3 月 26 日

📋 概要

Amazon EC2 R8gd インスタンスが、6 つの追加リージョンで新たに利用可能になりました。 R8gd は AWS Graviton4 プロセッサを搭載し、最大 11.4 TB のローカル NVMe ベース SSD ブロックレベルストレージを提供するメモリ最適化インスタンスです。 AWS Nitro System 上に構築されており、12 種類のインスタンスサイズが利用可能です。

R8gd インスタンスは Graviton4 プロセッサ、ローカル NVMe SSD、Nitro System を組み合わせ、I/O 集約型のデータベースやリアルタイム分析ワークロードに最適化されたパフォーマンスを提供します。

🖥️ AWS Graviton4 プロセッサ
  • 最新世代の AWS 設計 ARM ベースプロセッサを搭載
  • Graviton3 ベースのインスタンスと比較して最大 30% 優れたパフォーマンス
  • エネルギー効率の向上によるコスト最適化
💾 ローカル NVMe SSD ストレージ
  • 最大 11.4 TB のローカル NVMe ベース SSD ブロックレベルストレージ
  • I/O 集約型データベースワークロードで最大 40% のパフォーマンス向上
  • I/O 集約型リアルタイムデータ分析で最大 20% 高速なクエリ結果
🌐 ネットワークおよび EBS 帯域幅
  • 最大 50 Gbps のネットワーク帯域幅
  • 最大 40 Gbps の Amazon EBS 帯域幅
  • EC2 インスタンス帯域幅ウェイト設定により、ネットワークと EBS の帯域幅を 25% 調整可能
📐 スケーラブルなインスタンスサイズ
  • 12 種類の異なるインスタンスサイズが利用可能
  • ワークロードの要件に応じた柔軟なサイジングが可能

⚙️ 設定方法

前提条件

  • AWS アカウントを所有していること
  • 対象リージョンで EC2 インスタンスの起動権限があること
  • ARM ベース (Graviton) のインスタンスに対応した AMI を使用すること

ステップ 1: R8gd インスタンスの起動

Bash R8gd インスタンスの起動 
aws ec2 run-instances \
  --instance-type r8gd.xlarge \
  --image-id ami-xxxxxxxxxxxxxxxxx \
  --region us-west-1 \
  --key-name my-key-pair \
  --subnet-id subnet-xxxxxxxxxxxxxxxxx

対象リージョンで R8gd インスタンスを起動します。AMI は ARM64 (Graviton) 対応のものを指定してください。

ステップ 2: 帯域幅ウェイトの設定

Bash 帯域幅ウェイト設定 
aws ec2 modify-instance-attribute \
  --instance-id i-xxxxxxxxxxxxxxxxx \
  --instance-type r8gd.xlarge \
  --bandwidth-weighting default-ebs

ネットワーク帯域幅と EBS 帯域幅の配分を 25% の範囲で調整できます。

ステップ 3: ローカル NVMe ストレージの確認

Bash ストレージ確認 
lsblk

インスタンスに接続後、ローカル NVMe SSD ストレージが正しくマウントされていることを確認します。ローカル NVMe ストレージはインスタンスストアとして表示されます。

🎯 ユースケース

🗄️ I/O 集約型データベース
大規模な OLTP データベースをローカル NVMe ストレージ上で実行し、高い I/O スループットと低レイテンシーを必要とするシナリオ。
Bash ソウルリージョンでの起動例 
aws ec2 run-instances \
  --instance-type r8gd.16xlarge \
  --image-id ami-xxxxxxxxxxxxxxxxx \
  --region ap-northeast-2 \
  --block-device-mappings '[{"DeviceName":"/dev/sda1","Ebs":{"VolumeSize":100,"VolumeType":"gp3"}}]'
✅ Graviton3 ベースのインスタンスと比較して最大 40% のデータベース I/O パフォーマンス向上により、トランザクション処理のスループットが大幅に改善
📈 リアルタイムデータ分析
大量のデータストリームをリアルタイムで分析し、ローカルストレージを一時的なデータバッファとして使用するシナリオ。
Bash ジャカルタリージョンでの起動例 
aws ec2 run-instances \
  --instance-type r8gd.8xlarge \
  --image-id ami-xxxxxxxxxxxxxxxxx \
  --region ap-southeast-3 \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Purpose,Value=RealTimeAnalytics}]'
✅ 最大 20% 高速なクエリ結果により、リアルタイム分析のレスポンスタイムが改善され、ビジネスインサイトの迅速な取得が可能に
🧠 インメモリキャッシュ
大規模なインメモリキャッシュ (Redis、Memcached など) をローカル NVMe ストレージと組み合わせて、永続化付きの高速キャッシュレイヤーを構築するシナリオ。
Bash 香港リージョンでの起動例 
aws ec2 run-instances \
  --instance-type r8gd.4xlarge \
  --image-id ami-xxxxxxxxxxxxxxxxx \
  --region ap-east-1 \
  --tag-specifications 'ResourceType=instance,Tags=[{Key=Purpose,Value=InMemoryCache}]'
✅ Graviton4 の高いメモリパフォーマンスとローカル NVMe SSD の組み合わせにより、高速なキャッシュ読み書きと永続化を両立

⚖️ メリットと制約事項

✅ メリット

  • 6 つの追加リージョンでデータレジデンシー要件に対応
  • Graviton4 の優れた価格パフォーマンスで運用コスト削減
  • I/O 集約型ワークロードで最大 40% のパフォーマンス向上
  • 最大 11.4 TB の NVMe SSD で低レイテンシー I/O 処理
  • 帯域幅ウェイト設定でネットワークと EBS の帯域幅配分を最適化
  • 12 種類のサイズから最適なリソース配分を選択可能

⚠️ 制約・考慮点

  • ARM ベースのため x86 向けソフトウェアは再コンパイルが必要
  • ローカル NVMe はインスタンスストア。停止時にデータ消失
  • すべてのリージョンで利用可能ではない
  • Graviton4 への移行時にアプリケーション互換性テストが必要
  • データ永続性不要なら EBS のみの R8g も選択肢
  • Graviton3 からの移行時はベンチマーク実施を推奨
