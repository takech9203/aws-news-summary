Oracle Database@AWS

🛣️ ODB ピアリングが集約ルートとデフォルトルートに対応

📅 2026 年 10 月 15 日 | 集約ルート (スーパーネット) およびデフォルトルート 0.0.0.0/0 のアドバタイズをサポート

📋 概要

Oracle Database@AWS (ODB) が、Amazon VPC と ODB ネットワークを接続する ODB ピアリングにおいて、集約ルート (スーパーネット) と デフォルトルート (0.0.0.0/0) のアドバタイズをサポートしました。 ピア側ネットワークの CIDR として /0 から /32 までの任意の IPv4 プレフィックスを指定でき、 1 つのルートエントリでピアリングされた VPC 経由のすべてのネットワークをカバーできます。

ルーティングはロンゲストプレフィックスマッチ (最長プレフィックス一致) に従うため、 より具体的な CIDR を持つルートが常に優先されます。既存の個別 CIDR と共存させながら、 段階的かつ無停止で集約ルートへ移行できます。特に AWS Transit Gateway を経由して 多数のネットワークが接続するアーキテクチャで効果を発揮します。

  • 任意の CIDR レンジ (/0〜/32) をアドバタイズでき、単一の集約ルートで全ネットワークをカバー
  • Transit Gateway 経由のネットワーク追加時も CIDR の個別追加が不要
  • 既存のピアリング接続はそのまま動作し、再作成は不要

トランジット VPC の ODB ピアリング接続で集約ルート (例: 10.0.0.0/8) またはデフォルトルート (0.0.0.0/0) をアドバタイズすることで、Transit Gateway 配下のすべての VPC やオンプレミスネットワークが、 個別の CIDR 登録なしに ODB ネットワーク内のデータベースへ到達できます。

⚡ 主要機能

1️⃣ 任意の CIDR レンジのアドバタイズ
  • ピア側ネットワーク CIDR として /0 から /32 までの任意の IPv4 プレフィックスを指定可能
  • スーパーネット (例: 10.0.0.0/8) やデフォルトルート (0.0.0.0/0) を 1 エントリでアドバタイズ
  • 狭い CIDR を指定すればアクセスを必要なサブネットに限定でき、セグメンテーションにも対応
2️⃣ ロンゲストプレフィックスマッチによるルート解決
  • CIDR が重複する場合、最も具体的な CIDR が常に優先される
  • スーパーネットやデフォルトルートは、より具体的なルートが処理しないトラフィックのみを運ぶ
  • 複数のピアリング接続にまたがって広い CIDR と狭い CIDR を組み合わせ、ルート解決を自動化できる
3️⃣ ゼロダウンタイムのルート集約
  • 既存の個別 CIDR を残したまま、先に集約スーパーネットを追加できる (同一ピアリング上の重複は許容)
  • 動作確認後に個別 CIDR を削除すれば、無停止で集約ルートへ移行できる
  • 1 回の update-odb-peering-connection コマンドで CIDR の追加と削除を同時に実行可能
4️⃣ デフォルトルートの安全な取り扱い
  • 0.0.0.0/0 はピアリング接続上のピア側ネットワーク CIDR のみを指し、ODB ネットワークが VPC のデフォルトゲートウェイになるわけではない
  • 別のピアリングで直接接続された VPC の CIDR は、ロンゲストプレフィックスマッチにより引き続きそのピアリングが優先される

ピア側 CIDR のルールと制約

⚠️同一のプレフィックスを 2 つのピアリング接続に登録することはできない (ロンゲストプレフィックスマッチで優劣を判定できないため)
⚠️同じ ODB ネットワークに直接ピアリングされた 2 つの VPC の CIDR は重複してはならず、サブネットも同一であってはならない
⚠️ピア側 CIDR は ODB ネットワークのクライアントサブネットを包含できるが、同一であってはならない
⚠️直接ピアリングされた VPC の CIDR 重複はピアリング作成・更新時にのみ検証され、その後のセカンダリ CIDR 追加などによる重複はユーザー側で管理が必要

🛠️ 設定方法

前提条件

✓Oracle Database@AWS を AWS Marketplace 経由でサブスクライブ済みであること
✓複数の ODB ピアリング接続をサポートする ODB ネットワークが作成済みであること
✓ピアリング対象の Amazon VPC (トランジット VPC など) が存在し、必要に応じて AWS Transit Gateway にアタッチされていること

ステップ 1: 集約ルートを指定して ODB ピアリング接続を作成

Bash ピアリング接続の作成 
aws odb create-odb-peering-connection \
  --odb-network-id odbnet-1234567890abcdef \
  --peer-network-id vpc-abcdef1234567890 \
  --peer-network-cidrs-to-be-added "10.0.0.0/8"

ピア側ネットワーク CIDR としてスーパーネット 10.0.0.0/8 をアドバタイズし、Transit Gateway 配下の多数の宛先を 1 エントリに集約します。デフォルトルートを使う場合は "0.0.0.0/0" を指定します。

ステップ 2: 既存接続を無停止で集約ルートへ移行

Bash CIDR の追加と削除を同時実行 
aws odb update-odb-peering-connection \
  --odb-peering-connection-id odbpcx-1234567890abcdef \
  --peer-network-cidrs-to-be-added "10.0.0.0/16" \
  --peer-network-cidrs-to-be-removed "10.0.0.0/24,10.0.1.0/24"

より具体的なルートが常に優先されるため、先にスーパーネットを追加してから個別 CIDR を削除する順序であれば、トラフィックの中断は発生しません。

ステップ 3: VPC ルートテーブルを設定

Bash ODB ネットワーク宛てルートの追加 
aws ec2 create-route \
  --route-table-id rtb-1234567890abcdef \
  --destination-cidr-block 10.0.0.0/16 \
  --odb-network-arn arn:aws:odb:us-east-1:111111111111:odb-network/odbnet_1234567890abcdef

ピアリング接続の作成時に --peer-network-route-table-ids パラメータで暗黙的なルート管理を選択した場合、この手順は不要です。ODB ネットワーク側のルートテーブルは Oracle Database@AWS が自動的に設定します。

💡 メリット

💼 ビジネス面

✓運用コストの削減: ネットワーク追加のたびに発生していた CIDR 更新作業が不要になり、ネットワークチームの運用負荷が軽減される
✓拡張の俊敏性: 新しい VPC やオンプレミス拠点を Transit Gateway に接続するだけでデータベースへ到達でき、ビジネスの拡大に迅速に対応できる
✓設定ミスのリスク低減: 個別エントリ管理が不要になることで、CIDR の登録漏れや誤設定による接続障害を防止できる

⚙️ 技術面

✓ルート管理の簡素化: 単一の集約ルートまたはデフォルトルートで、トランジット VPC 経由のすべての宛先をカバーできる
✓ゼロダウンタイム移行: ロンゲストプレフィックスマッチを利用し、スーパーネット追加後に個別 CIDR を削除することで無停止でルートを集約できる
✓柔軟なセグメンテーション: 広い CIDR と狭い CIDR を組み合わせ、特定サブネットへのアクセス制限と広域の到達性を両立できる

⚠️ デメリット・制約事項

制限事項

✗本機能は、複数の ODB ピアリング接続をサポートする ODB ネットワークでのみ利用可能
✗同一の CIDR (0.0.0.0/0 を含む) は、1 つの ODB ネットワークにつき 1 つのピアリング接続にのみ登録できる
✗ピア側 CIDR は ODB ネットワークのクライアントサブネットと同一にはできない
✗ピア側 CIDR には ODB ネットワークと同じ制限付き IP アドレス範囲が適用される

考慮すべき点

⚠️広い CIDR やデフォルトルートをアドバタイズすると ODB ネットワークから到達可能な範囲が広がるため、セキュリティ要件に応じてより狭い CIDR によるセグメンテーションを検討する
⚠️直接ピアリングされた VPC の CIDR 重複はピアリング作成・更新時にのみ検証されるため、作成後にセカンダリ CIDR ブロックを追加する場合は重複が生じないようユーザー側での管理が必要
⚠️0.0.0.0/0 の登録はピアリング接続上のアドバタイズルートに限定され、VPC 自体のデフォルトゲートウェイ設定は変更されない点を理解した上で設計する

🎯 ユースケース

1. Transit Gateway ハブアンドスポーク構成の集約

シナリオ: 多数のアプリケーション VPC とオンプレミスネットワークが AWS Transit Gateway に接続されており、すべてのネットワークから ODB ネットワーク内の Oracle Exadata データベースへアクセスする。

  • トランジット VPC と ODB ネットワークの間に ODB ピアリング接続を作成
  • ピア側ネットワーク CIDR として 10.0.0.0/8 (または 0.0.0.0/0) を登録
  • Transit Gateway とトランジット VPC のルートテーブルを設定
  • 以降、スポーク VPC を追加してもピアリング設定の変更は不要
✅ 効果: ネットワーク追加時の CIDR 登録作業がなくなり、大規模なハブアンドスポーク環境でもルート管理を 1 エントリに集約できる。
2. 個別 CIDR から集約ルートへの無停止移行

シナリオ: 既存の ODB ピアリング接続に多数の個別 CIDR が登録されており、運用簡素化のため集約ルートへ移行したいが、本番データベースへの接続を中断できない。

  • update-odb-peering-connection で集約スーパーネット 10.0.0.0/16 を追加 (既存の具体的な CIDR が優先されるため、トラフィックへの影響なし)
  • ルーティングが正常であることを確認
  • 同コマンドの --peer-network-cidrs-to-be-removed で個別 CIDR を削除 (トラフィックはスーパーネットのルートへ無停止で移行)
✅ 効果: ロンゲストプレフィックスマッチを活用し、サービス停止なしでルート構成を簡素化できる。
3. デフォルトルートと直接ピアリングの併用

シナリオ: レイテンシー要件の厳しい主要アプリケーション VPC は ODB ネットワークへ直接ピアリングしつつ、その他の多数のネットワークからのトラフィックはトランジット VPC 経由で集約したい。

  • 主要アプリケーション VPC と ODB ネットワークを直接ピアリングし、VPC の CIDR を登録
  • トランジット VPC とのピアリング接続に 0.0.0.0/0 を登録
  • 直接ピアリングされた VPC 宛てのトラフィックは、より具体的な CIDR により直接ピアリング経由で転送され、それ以外はトランジット VPC 経由となる
✅ 効果: 重要なワークロードには低レイテンシーの直接経路を確保しながら、その他のネットワークはデフォルトルートで包括的にカバーできる。

🔗 関連サービス・機能

📦 Amazon VPC

ODB ピアリングの接続先となるアプリケーション実行環境。ルートテーブルの設定により ODB ネットワークへのトラフィックを制御する。

🔁 AWS Transit Gateway

多数の VPC やオンプレミスネットワークを集約するハブ。本アップデートにより、Transit Gateway 配下のネットワークを単一の集約ルートで ODB ネットワークへ到達させることが可能になった。

🌐 AWS Cloud WAN

Transit Gateway と同様に、Oracle Database@AWS のドキュメントで接続構成がガイドされているグローバルネットワークサービス。

🤝 AWS RAM

ODB ネットワークをアカウント間で共有し、クロスアカウントの ODB ピアリングを構成するためのサービス。

📝 まとめ

Oracle Database@AWS の ODB ピアリングが集約ルートとデフォルトルート (0.0.0.0/0) のアドバタイズに対応し、Transit Gateway 配下の多数のネットワークから ODB ネットワークへの接続を 単一のルートエントリで管理できるようになりました。 多数の VPC やオンプレミスネットワークから Oracle Exadata データベースへ接続しているお客様は、 ロンゲストプレフィックスマッチを活用した無停止のルート集約により、 ピアリング接続の CIDR 管理の簡素化を検討することを推奨します。
