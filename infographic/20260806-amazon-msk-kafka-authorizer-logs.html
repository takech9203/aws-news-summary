Amazon MSK

🔐 Kafka Authorizer Logs 配信サポート

📅 2026 年 8 月 6 日リリース ｜ Amazon Managed Streaming for Apache Kafka ｜ Authorizer Log Delivery (認可ログ配信)

📌 概要

Amazon MSK が Provisioned クラスター (Standard / Express ブローカー両対応) を対象に、 Kafka Authorizer ログの配信を追加料金なしでサポート。 認可判定 (アクセス許可/拒否) を記録し、ユーザーやアプリケーションのアクセス状況を詳細に可視化できます。

拒否された認可リクエストにはクライアントの IP アドレスと試行された API が記録されるため、認可エラーの根本原因を迅速に特定できます。 配信先は CloudWatch Logs、S3、Data Firehose の 3 種類から選択可能 (複数指定も可)。

追加料金 0 円
機能自体は無料 (配信先の標準料金のみ)
3 種類の配信先
CloudWatch Logs / S3 / Data Firehose
新規・既存 両対応
コンソール / CLI から簡単に有効化
❌ Before: アップデート前の課題
  • 認可判定ログを外部配信するマネージド手段がなく、ブローカーログを頼りに調査が必要
  • どのクライアントがどの API で拒否されたのかの特定が困難
  • アクセス監査・コンプライアンス対応に独自の収集の仕組みが必要
✅ After: アップデート後の改善
  • CloudWatch Logs / S3 / Data Firehose へマネージドに配信、追加コストなしで可視性を確保
  • 拒否リクエストごとにクライアント IP と試行 API を記録、根本原因を迅速に特定
  • 新規・既存クラスターともコンソール / CLI から簡単に有効化、監査要件への対応が容易

Kafka クライアントからのリクエストに対して MSK ブローカーの Authorizer が認可判定を行い、その判定結果 (特に拒否されたリクエストの詳細) を CloudWatch Logs、S3、Data Firehose のいずれか、または複数の宛先に配信するアーキテクチャです。

⚡ 主要機能

📝 Authorizer ログのマネージド配信

認可判定 (アクセス許可/拒否の決定) をログとして配信。追加料金なしで利用可能 (配信先サービスの標準料金は別途発生)。Standard / Express ブローカーの両方をサポート。

🔍 拒否リクエストの詳細な記録

拒否された認可リクエストごとにクライアントの IP アドレスと試行された API (操作) を記録。認可エラーの根本原因特定 (トラブルシューティング) に活用可能。

🗄️ 柔軟な配信先の選択

CloudWatch Logs (リアルタイムの検索・分析・アラート)、S3 (長期保管・コンプライアンス用アーカイブ)、Data Firehose (OpenSearch Service など下流システムへのストリーミング配信)。3 種類を同時に複数指定することも可能。

🖱️ 新規・既存クラスター両対応の簡単な有効化

新規作成時はコンソールの「Monitoring」セクション、既存クラスターは「Properties」タブの「Log delivery」から設定。AWS CLI では create-cluster / update-monitoring の logging-info パラメータで設定。

🛠️ 設定方法

✅ 前提条件

✓MSK Provisioned クラスター (Standard または Express ブローカー) が作成済み、または新規作成すること
✓配信先リソース (ロググループ / S3 バケット / Firehose 配信ストリーム) を事前に作成 (MSK は自動作成しない)
✓AmazonMSKFullAccess 相当の権限。S3 配信時は s3:PutBucketPolicy 権限も必要
✓SSE-KMS (カスタマーマネージドキー) の S3 バケット使用時は、KMS キーポリシーで delivery.logs.amazonaws.com に暗号化操作を許可
✓Firehose 使用時は、配信ストリームに LogDeliveryEnabled タグを true で設定
1
配信先リソースの作成
Bash CloudWatch Logs ロググループを作成する例 
# CloudWatch Logs ロググループを作成する例
aws logs create-log-group \
  --log-group-name /msk/authorizer-logs/my-cluster

S3 バケットや Firehose 配信ストリームを使用する場合は、それぞれ事前に作成してください。

2
既存クラスターで Authorizer ログ配信を有効化
Bash update-monitoring で有効化 
# 現在のクラスターバージョンを確認
aws kafka describe-cluster \
  --cluster-arn "arn:aws:kafka:ap-northeast-1:123456789012:cluster/my-cluster/xxxx" \
  --query "ClusterInfo.CurrentVersion"

# update-monitoring で Authorizer ログ配信を有効化
aws kafka update-monitoring \
  --cluster-arn "arn:aws:kafka:ap-northeast-1:123456789012:cluster/my-cluster/xxxx" \
  --current-version "K3AEGXETSR30VB" \
  --logging-info '{
    "AuthorizerLogs": {
      "CloudWatchLogs": {
        "Enabled": true,
        "LogGroup": "/msk/authorizer-logs/my-cluster"
      }
    }
  }'

describe-cluster で現在のバージョンを取得し、update-monitoring の logging-info パラメータに AuthorizerLogs 構造体を指定して有効化します。

3
新規クラスター作成時に有効化する場合
Bash create-cluster で AuthorizerLogs と BrokerLogs を同時設定 
aws kafka create-cluster \
  --cluster-name "my-new-cluster" \
  --broker-node-group-info file://brokernodegroupinfo.json \
  --kafka-version "3.6.0" \
  --number-of-broker-nodes 3 \
  --logging-info '{
    "AuthorizerLogs": {
      "S3": {
        "Enabled": true,
        "Bucket": "amzn-s3-demo-bucket",
        "Prefix": "authorizer-logs"
      }
    },
    "BrokerLogs": {
      "CloudWatchLogs": {
        "Enabled": true,
        "LogGroup": "/msk/broker-logs/my-new-cluster"
      }
    }
  }'

Authorizer ログとブローカーログは独立して配信先を設定できます。

4
コンソールでの設定

① MSK コンソールでクラスターを選択し「Properties」タブを開く → ② 「Log delivery」セクションの「Edit」を選択 → ③ 「Authorizer log delivery」で配信先 (CloudWatch Logs / S3 / Firehose) を指定して保存。

新規クラスター作成時は「Monitoring」セクションの「Authorizer log delivery」見出しから同様に設定できます。

💡 メリット・制約事項

👍 メリット
  • ビジネス面: 認可判定の記録を S3 に長期保管し、監査・コンプライアンス要件を追加開発なしで満たせる
  • 機能自体は無料のため、コストを増やさずアクセス可視性を強化できる
  • 認可エラーの調査時間が短縮され、問い合わせ対応の負荷が軽減される
  • 技術面: クライアント IP と試行 API の記録により根本原因を迅速に特定できる
  • Logs Insights / S3 + Athena / Firehose 経由 OpenSearch など、用途に応じた分析基盤を選択できる
  • 既存クラスターにも容易に適用でき、移行作業が不要
⚠️ 制限事項・考慮点
  • 対象は Provisioned クラスターのみ (MSK Serverless は対象外)
  • AWS European Sovereign Cloud (eusc-de-east-1) では利用不可
  • 配信先リソースは事前に自分で作成する必要がある (MSK は自動作成しない)
  • 配信先サービスの標準料金 (取り込み・保存など) は別途発生する
  • S3 の SSE-KMS 利用時は KMS キーポリシーへの delivery.logs.amazonaws.com の許可追加が必要
  • 認可拒否が大量発生する環境ではログ量が増加するため、保持期間・ライフサイクルポリシーの設計を推奨

🎯 ユースケース

1️⃣ クライアント認可エラーのトラブルシューティング

シナリオ: 新しいコンシューマーアプリケーションのデプロイ後、トピックの読み取りに失敗。IAM ポリシーまたは Kafka ACL のどの設定が原因かを特定したい。

Logs Insights 拒否された認可リクエストを検索 
fields @timestamp, @message
| filter @message like /DENIED/
| sort @timestamp desc
| limit 50
✅ 効果: 拒否されたリクエストのクライアント IP と試行 API が特定でき、IAM ポリシーや ACL を的確に修正して調査時間を大幅に短縮。
2️⃣ セキュリティ監査・コンプライアンス対応

シナリオ: 金融系システムで、Kafka クラスターへのアクセス制御が適切に機能していることを監査人に証明する必要があり、認可判定の記録を長期保管したい。

JSON S3 への配信設定 
{
  "AuthorizerLogs": {
    "S3": {
      "Enabled": true,
      "Bucket": "audit-logs-bucket",
      "Prefix": "msk-authorizer-logs/"
    }
  }
}
✅ 効果: 認可判定の証跡を S3 に保管し、ライフサイクルポリシーで規定期間の保持を自動化。Athena で監査時の検索・集計も容易に。
3️⃣ 不審なアクセス試行のリアルタイム検知

シナリオ: 本番の MSK クラスターへの想定外のアクセス試行 (権限のないクライアントからの接続) を早期に検知し、セキュリティチームへ通知したい。

Bash メトリクスフィルター + CloudWatch アラーム 
# 拒否された認可リクエストを検知するメトリクスフィルターを作成
aws logs put-metric-filter \
  --log-group-name /msk/authorizer-logs/my-cluster \
  --filter-name DeniedAuthRequests \
  --filter-pattern "DENIED" \
  --metric-transformations \
    metricName=MSKAuthDeniedCount,metricNamespace=Custom/MSK,metricValue=1

# しきい値超過でアラートを発報する CloudWatch アラームを作成
aws cloudwatch put-metric-alarm \
  --alarm-name msk-auth-denied-spike \
  --metric-name MSKAuthDeniedCount \
  --namespace Custom/MSK \
  --statistic Sum \
  --period 300 \
  --threshold 10 \
  --comparison-operator GreaterThanThreshold \
  --evaluation-periods 1 \
  --alarm-actions arn:aws:sns:ap-northeast-1:123456789012:security-alerts
✅ 効果: 認可拒否の急増時に SNS 経由でセキュリティチームへ即時通知され、不正アクセスの試行や設定ミスによる障害を早期に発見。

💰 料金

Authorizer Log Delivery 自体は追加料金なしで利用できます。ただし、ログの配信先となる各サービスの標準料金が別途発生します。

配信先発生する料金
📊 Amazon CloudWatch Logsログの取り込み料金、保存料金
🪣 Amazon S3ストレージ料金、リクエスト料金
🚚 Amazon Data Firehoseデータ取り込み料金

詳細は Amazon MSK 料金ページ および各配信先サービスの料金ページを参照してください。

🔗 関連サービス・機能

📊 Amazon CloudWatch Logs

Authorizer ログの配信先。Logs Insights によるアドホック検索や、メトリクスフィルター + アラームによるリアルタイム検知が可能。

🪣 Amazon S3

Authorizer ログの配信先。長期保管やコンプライアンス用アーカイブに適し、Athena と組み合わせた分析も可能。

🚚 Amazon Data Firehose

Authorizer ログの配信先。OpenSearch Service などの下流システムへのストリーミング配信に利用。

📝 MSK ブローカーログ

従来から提供されているブローカーのアプリケーションログ配信機能。Authorizer ログと同じ 3 種類の配信先をサポートし、独立して設定可能。

🛡️ AWS CloudTrail

MSK の API 呼び出し (コントロールプレーン操作) の記録。Authorizer ログ (データプレーンの認可判定) と組み合わせることで包括的な監査が可能。

📋 まとめ

Amazon MSK の Authorizer Log Delivery により、Provisioned クラスターの認可判定を追加料金なしで CloudWatch Logs、S3、Data Firehose へ配信できるようになりました。 拒否リクエストのクライアント IP アドレスと試行 API が記録されるため、認可エラーのトラブルシューティングとセキュリティ監査が大幅に効率化されます。

✓MSK Provisioned クラスターを運用中のチームは、まず既存クラスターで update-monitoring またはコンソールから有効化
✓CloudWatch Logs Insights やメトリクスフィルターと組み合わせた監視体制の整備を検討
