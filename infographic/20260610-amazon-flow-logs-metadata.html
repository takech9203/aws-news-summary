Amazon VPC

📋 VPC Flow Logs に追加メタデータ

EC2 リソースタグ + 次ホップインターフェイスメタデータ
📅 リリース日
2026年6月10日

🔍 概要

Amazon VPC Flow Logs が EC2 リソースタグ と 次ホップインターフェイスのメタデータ をサポート。 フローログデータとリソースメタデータを手動で関連付ける必要がなくなり、 ネットワークの監視とトラブルシューティングが大幅に簡素化されます。

タグ値 (ネットワークインターフェイス / EC2 インスタンス / Auto Scaling グループ) をログレコードに直接埋め込み、 どのアプリ・チーム・環境のトラフィックかを一目で把握。さらに次ホップの詳細 (インターフェイス ID、サブネット、AZ、VPC、タイプ) で NAT ゲートウェイや Transit Gateway の通過経路も追跡できます。

😓 アップデート前の課題
  • ログにはリソース ID のみ。タグ情報がなく、別システムで突き合わせが必要だった
  • NAT ゲートウェイや Transit Gateway などの経由経路を直接把握できなかった
  • ログとメタデータを手動で関連付ける運用負荷が発生していた
🎉 アップデート後の改善
  • インターフェイス / インスタンス / ASG のタグ値をログに直接埋め込み可能に
  • 各フローの次ホップ詳細 (ID、サブネット、AZ、VPC、タイプ) を取得可能に
  • 外部メタデータとの手動突き合わせが不要となり、監視・調査が効率化

タグ情報と次ホップメタデータがフローログレコードに直接埋め込まれ、CloudWatch Logs または Amazon S3 へ配信されます。配信後に外部メタデータと突き合わせる処理が不要になります。

⚡ 主要機能

🏷️ 1. EC2 リソースタグのサポート

  • ネットワークインターフェイス / EC2 インスタンス / Auto Scaling グループのタグ値をログに埋め込み可能
  • カスタムフォーマットの TagFieldSpecifications で含めるタグキーを指定
  • タグ値は UTF-8 のパーセントエンコーディングで特殊文字を変換して表示
  • 対象ごとに最大 2 つのタグフィールド (例: instance-tag、instance-tag-2) を指定可能

🔀 2. 次ホップインターフェイスメタデータ

  • 各フローの次ホップネットワークインターフェイスの詳細を記録
  • egress は受信側インターフェイス、ingress は送信側インターフェイスを示す
  • 取得フィールド: next-hop-interface-id、next-hop-subnet-id、next-hop-az-id、next-hop-vpc-id、next-hop-interface-type

🧭 3. インターフェイスタイプの識別

  • interface-type フィールドでフローをキャプチャしたローカルインターフェイスのタイプを識別
  • サポート値: nat_gateway、network_load_balancer、regional_nat_gateway、transit_gateway、vpc_endpoint
  • NAT ゲートウェイ / NLB / Transit Gateway を経由する経路把握に役立つ

🔧 技術仕様 — 新フィールド (バージョン 11)

新フィールドは VPC Flow Logs の バージョン 11 で導入され、カスタムフォーマットでのみ 利用可能です。デフォルトフォーマット (バージョン 2) には含まれません。
フィールド説明
instance-tag / instance-tag-2EC2 インスタンスタグの値
interface-tag / interface-tag-2ネットワークインターフェイスタグの値
asg-tag / asg-tag-2Auto Scaling グループタグの値
interface-typeフローをキャプチャしたローカルインターフェイスのタイプ
next-hop-interface-id次ホップインターフェイスの ID
next-hop-subnet-id次ホップインターフェイスが属するサブネット ID
next-hop-az-id次ホップインターフェイスが属する AZ ID
next-hop-vpc-id次ホップインターフェイスが属する VPC ID
next-hop-interface-type次ホップインターフェイスのタイプ

🔐 必要な IAM 権限

対象必要な権限
インスタンスタグ / インターフェイスタグec2:DescribeTags、iam:CreateServiceLinkedRole
Auto Scaling グループタグautoscaling:DescribeTags、iam:CreateServiceLinkedRole
ASG タグ値をリアルタイムで正確に追跡するには、アカウントで 少なくとも 1 つの CloudTrail 証跡 が有効である必要があります。また、これらのタグフィールドはサービスにリンクされたロール (Service-Linked Role) を使用します。

⚙️ 設定方法

前提条件

  • フローログの配信先 (CloudWatch Logs または Amazon S3) が準備されていること
  • タグフィールド使用時は対応する IAM 権限が付与されていること
  • ASG タグ使用時は有効な CloudTrail 証跡が存在すること

ステップ 1: カスタムフォーマットで新フィールドを指定

Bash aws ec2 create-flow-logs 
aws ec2 create-flow-logs \
  --resource-type VPC \
  --resource-ids vpc-0123456789abcdef0 \
  --traffic-type ALL \
  --log-destination-type cloud-watch-logs \
  --log-group-name my-flow-logs \
  --deliver-logs-permission-arn arn:aws:iam::123456789012:role/flow-logs-role \
  --log-format '${srcaddr} ${dstaddr} ${interface-type} ${next-hop-interface-id} ${next-hop-vpc-id} ${instance-tag} ${asg-tag}'

ソース・宛先アドレスに加え、インターフェイスタイプ、次ホップ ID / VPC ID、インスタンスタグ、ASG タグを含むフローログを作成します。

ステップ 2: タグフィールドの指定

タグフィールド (instance-tag、interface-tag、asg-tag など) を使う場合は、TagFieldSpecifications でどのタグキーを記録するかを指定します。

ステップ 3: フローログの確認

配信先のレコードを確認します。該当しない・計算できないフィールドは - 記号で表示。パケットヘッダー由来でないメタデータはベストエフォートの近似値で、欠落や不正確な値が含まれる場合があります。

✅ メリット

💼 ビジネス面

  • 運用効率の向上: 手動の突き合わせが不要となり分析工数を削減
  • コスト配分の明確化: チーム・環境・アプリ単位でトラフィックを識別
  • 調査の迅速化: 経路を直接把握でき障害切り分け時間を短縮

🛠️ 技術面

  • ワークロード単位の可視化: タグでフローを特定ワークロードに直接紐付け
  • トラフィック経路の把握: 次ホップで NAT / TGW 経由経路を明確化
  • 後処理の削減: 外部メタデータ結合パイプラインが不要に

⚠️ デメリット・制約事項

制限事項

  • 新フィールドはカスタムフォーマット (v11) でのみ利用可能。デフォルトフォーマットには含まれない
  • タグフィールドは対象あたり最大 2 つ (例: instance-tag、instance-tag-2) に限定
  • パケットヘッダー由来でないメタデータはベストエフォートの近似値で、欠落・不正確の可能性

考慮すべき点

  • タグフィールド利用には追加 IAM 権限とサービスにリンクされたロールが必要
  • ASG タグのリアルタイム追跡には有効な CloudTrail 証跡が前提
  • フィールドを増やすとログ量が増加し、配信先のストレージコストに影響

🎯 ユースケース

📊 1. ワークロード単位のトラフィック分析

シナリオ: 複数チームが同じ VPC を共有。どのチームがどれだけのトラフィックを生成しているか把握したい。

実装: instance-tag を追加し TagFieldSpecifications で "Team" タグを指定。Team タグ値ごとに集計。

効果: フローログだけでチーム単位を集計でき、コスト配分や容量計画が容易に。
🔀 2. NAT ゲートウェイ経由トラフィックの経路把握

シナリオ: アウトバウンドがどの NAT ゲートウェイを経由するか特定し、AZ をまたぐ転送コストを最適化したい。

実装: interface-type、next-hop-interface-id、next-hop-az-id を追加。egress で次ホップ AZ が送信元と異なるレコードを抽出。

効果: AZ をまたぐ NAT 経由トラフィックを特定し、不要なクロス AZ 転送を削減。
🛡️ 3. Auto Scaling グループ単位のセキュリティ監視

シナリオ: 動的に増減するインスタンス群で、特定アプリグループからの異常通信を監視したい。

実装: asg-tag を追加し ASG タグを指定。asg-tag 値ごとに通信パターンをベースライン化し逸脱を検知。

効果: インスタンス ID が頻繁に変わる環境でも ASG 単位で安定した監視が可能。

💰 料金

VPC Flow Logs の料金は ログの取り込みとストレージ に対して発生し、配信先 (CloudWatch Logs または Amazon S3) の料金体系に従います。 追加メタデータフィールド自体の追加料金は公式の料金ページを確認してください。 フィールドを追加するとレコードのデータ量が増えるため、取り込み量とストレージ量が増える点に留意してください。

🔗 関連サービス・機能

  • Amazon CloudWatch Logs: フローログの配信先。リアルタイム分析やメトリクスフィルタに利用
  • Amazon S3: フローログの配信先。Parquet 形式での保存や Amazon Athena による分析に利用
  • AWS Transit Gateway / NAT ゲートウェイ / Network Load Balancer: 次ホップメタデータと interface-type で経路を可視化
  • Amazon EC2 Auto Scaling: asg-tag により ASG 単位でのトラフィック識別が可能

📝 まとめ

VPC Flow Logs に EC2 リソースタグと次ホップインターフェイスメタデータが追加され、 フローログと外部メタデータの手動突き合わせが不要になりました。

ネットワークの可視化とトラブルシューティングを効率化したい場合は、 カスタムフォーマット (バージョン 11) で新フィールドを指定し、 必要な IAM 権限を整えたうえで導入を検討することを推奨します。
