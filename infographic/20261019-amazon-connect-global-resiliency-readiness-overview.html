🌐 Customer Global Resiliency
リージョン切り替え準備状況を 1 か所で可視化

📅 リリース日: 2026 年 10 月 19 日 | 機能: Global Resiliency ページによる準備状況の可視化

📌 概要

Amazon Connect Customer Global Resiliency の管理者向けウェブサイトに、新しい Global Resiliency ページが追加されました。リンクされたリージョン間でのリージョン切り替え (Region switch) の準備状況を 1 か所で確認できます。

ネイティブにレプリケーションされるリソースの一覧と同期ステータスが表示され、トラフィック分散グループに未関連付けの電話番号やユーザーといった設定ギャップをその場で修正できます。障害発生前の平常時から、レジリエンシー態勢を継続的に点検できるようになります。

✅ 同期済みin sync
⏳ 同期保留中pending
⚠️ 要対応needs action
リソースタイプごとに 3 区分のステータスで表示
❌ アップデート前の課題
  • 準備状況を一元的に確認する画面がなく、リソースの同期状態を個別に確認する必要があった
  • 電話番号やユーザーの関連付け漏れに気づきにくく、切り替え時に初めて問題が発覚するリスクがあった
  • 設定ギャップの修正には、個別の管理画面や API 操作が必要だった
✅ アップデート後の改善
  • Global Resiliency ページで全体的な準備状況を 1 か所で確認できる
  • リソースごとに同期済み・同期保留中・要対応のステータスを一覧で把握できる
  • 未関連付けの電話番号やユーザーを、同じページから直接関連付けて修正できる

管理者は Global Resiliency ページから、リンクされた 2 つのリージョンにまたがるリソースの同期状態と切り替え準備状況を一元的に確認し、設定ギャップをその場で修正できます。

⚡ 主要機能

1️⃣ 全体的な準備状況の表示
  • リージョン切り替えに対するインスタンス全体の readiness ステータスを表示
  • 障害発生時だけでなく、平常時にいつでもレジリエンシー態勢を確認可能
  • 定期的なフェイルオーバーテストや監査の起点として活用できる
2️⃣ レプリケーション対象リソースのステータス一覧
  • Global Resiliency がネイティブにレプリケーションするリソースを一覧表示
  • 各リソースタイプについて、同期済み・同期保留中・要対応のステータスを確認可能
  • どのリソースが切り替えの阻害要因になっているかを即座に特定できる
3️⃣ 影響を受けるリソースの直接修正
  • トラフィック分散グループに関連付けられていない電話番号やユーザーなどを検出
  • 検出された未関連付けリソースを、Global Resiliency ページから直接関連付け可能
  • 個別の管理画面や API 操作に移動することなく、設定ギャップを解消できる

🔧 技術仕様

Global Resiliency の基本構成要素

項目詳細
レプリカインスタンス ReplicateInstance API などで別リージョンに作成する Connect インスタンスの複製
トラフィック分散グループ 異なるリージョンの Connect インスタンスをリンクするリソース。電話番号を関連付け、トラフィックを 10% 刻みで分散可能
準備状況ステータス 同期済み (in sync)・同期保留中 (pending)・要対応 (needs action) の 3 区分でリソースを表示
利用画面 Amazon Connect 管理者向けウェブサイトの Global Resiliency ページ

前提となるドメイン形式

⚠️ 2021 年 3 月 31 日より前に作成されたインスタンスで https://{instance-alias}.awsapps.com/connect/ 形式のドメインを使用している場合、Global Resiliency を正しく構成できません。https://{instance-alias}.my.connect.aws/ 形式へのドメイン更新が必要です。

🛠️ 設定方法

前提条件

✓Amazon Connect Customer Global Resiliency が有効化されたインスタンスであること (利用には Amazon Connect の Solutions Architect または Technical Account Manager への連絡が必要)
✓インスタンスのドメインが https://{instance-alias}.my.connect.aws/ 形式であること
✓Global Resiliency がサポートされるリージョンペアでインスタンスを運用していること

手順

1
レプリカインスタンスとトラフィック分散グループの作成

ReplicateInstance API で既存インスタンスの複製を別リージョンに作成し、CreateTrafficDistributionGroup API で 2 つのリージョンのインスタンスをリンクします。

Bash レプリカ作成とトラフィック分散グループ作成 
# 既存インスタンスのレプリカを別リージョンに作成
aws connect replicate-instance \
  --instance-id <インスタンス ID> \
  --replica-region us-west-2 \
  --replica-alias <レプリカのエイリアス>

# トラフィック分散グループを作成
aws connect create-traffic-distribution-group \
  --name my-tdg \
  --instance-id <インスタンス ARN>
2
電話番号とユーザーの関連付け

UpdatePhoneNumber API で電話番号をトラフィック分散グループに割り当てます。ユーザー (エージェント) についても同様に関連付けを行います。

Bash 電話番号の割り当て 
# 電話番号をトラフィック分散グループに割り当て
aws connect update-phone-number \
  --phone-number-id <電話番号 ID> \
  --target-arn <トラフィック分散グループ ARN>
3
Global Resiliency ページで準備状況を確認

管理者向けウェブサイトにログインし、Global Resiliency ページを開きます。全体の準備状況と各リソースタイプのステータスを確認し、「要対応」と表示されたリソースがあれば、このページから直接関連付けを行います。

💡 メリット

💼 ビジネス面

✓ダウンタイムリスクの低減: 切り替えの阻害要因を平常時に発見・解消でき、障害時に切り替えが失敗するリスクを低減
✓運用負荷の削減: 準備状況の確認が 1 か所に集約され、監査やフェイルオーバーテスト前の点検作業が効率化
✓非技術者にも分かりやすい可視化: ビジネスユーザーや管理者が API を使わずにレジリエンシー態勢を把握できる

⚙️ 技術面

✓同期状態の透明性: リソースごとの同期状態 (in sync / pending / needs action) が明確になり、問題の切り分けが容易
✓設定ギャップのその場での修正: 未関連付けの電話番号やユーザーを検出し、同じページから関連付けまで完結
✓継続的なレジリエンシー点検: 月次のフェイルオーバーテストなど定期的な検証プロセスに組み込みやすい

⚠️ デメリット・制約事項

制限事項

✗Global Resiliency の利用には、Amazon Connect の Solutions Architect または Technical Account Manager への連絡によるアクセス付与が必要
✗レプリカを作成できるリージョンの組み合わせは固定 (バージニア北部とオレゴン、フランクフルトとロンドン、東京と大阪)
✗旧形式ドメイン (awsapps.com/connect) のインスタンスでは構成できず、ドメイン更新が必要

考慮すべき点

⚠本ページはネイティブにレプリケーションされるリソースの状態を表示するもの。Lambda 関数や外部連携などレプリケーション対象外のリソースは別途リージョン間での整合性確保が必要
⚠可視化に加えて、実際のリージョン切り替え手順 (トラフィック分散の更新) の定期的なテストは引き続き重要

🎯 ユースケース

🏦 ユースケース 1: 障害発生前の定期点検

シナリオ: 金融機関のコンタクトセンターで、月次のレジリエンシー点検を実施。従来は複数の画面と API でリソースの同期状態を個別に確認していた。

  1. Global Resiliency ページを開き、全体の準備状況を確認
  2. 「要対応」のリソースタイプを特定
  3. 未関連付けの電話番号・ユーザーをページ上で関連付け
  4. 全リソースが「同期済み」になったことを確認し、点検記録に残す
✅ 効果: 点検作業が 1 画面に集約され、確認漏れによる切り替え失敗のリスクを低減できる。
📈 ユースケース 2: 新規リソース追加後の整合性確認

シナリオ: コンタクトセンターの拡張に伴い、新しい電話番号の取得とエージェントの追加を実施。これらが DR 構成に正しく組み込まれているかを確認したい。

  1. 電話番号の取得とユーザー作成後、Global Resiliency ページを確認
  2. トラフィック分散グループに未関連付けのリソースが「要対応」として表示される
  3. ページ上から該当リソースをトラフィック分散グループに関連付け
✅ 効果: リソース追加のたびに発生しがちな DR 構成への組み込み漏れを、早期に検出・修正できる。
🧪 ユースケース 3: フェイルオーバーテスト前の事前チェック

シナリオ: 月次のフェイルオーバーテストの実施前に、リージョン切り替えが成功する状態にあるかを確認したい。

  1. テスト実施前に Global Resiliency ページで全体の準備状況を確認
  2. 同期保留中のリソースがあれば同期完了を待つ
  3. すべて同期済みであることを確認してから UpdateTrafficDistribution でトラフィックを切り替え
✅ 効果: テスト当日の手戻りを防ぎ、切り替え手順の検証に集中できる。

🔗 関連サービス・機能

🔀 Amazon Connect トラフィック分散グループ
異なるリージョンの Connect インスタンスをリンクし、電話番号のトラフィックを 10% 刻みで分散する機能。本アップデートで未関連付けリソースの検出・修正対象となる。
🧑‍💻 Amazon Connect エージェントワークスペース
エージェントが利用する統合ワークスペース。リージョン切り替え時にはエージェントのサインイン先も切り替わるため、準備状況の確認が重要。
🛡️ Amazon Route 53 Application Recovery Controller
AWS 全般のマルチリージョン切り替えを管理するサービス。Connect 以外のワークロードを含めた DR 戦略で併用を検討できる。

📝 まとめ

Amazon Connect Customer Global Resiliency の新しい Global Resiliency ページにより、リージョン切り替えの準備状況を管理画面上で一元的に可視化し、設定ギャップをその場で修正できるようになりました。マルチリージョン構成で Amazon Connect を運用しているチームは、月次のフェイルオーバーテストや定期点検のプロセスに本ページでの確認を組み込むことを推奨します。
