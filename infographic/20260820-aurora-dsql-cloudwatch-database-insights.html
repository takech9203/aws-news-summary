📊 Aurora DSQL が CloudWatch Database Insights に対応

リリース日: 2026 年 8 月 20 日 | ステートメント単位・クラスターレベルのパフォーマンスモニタリング

💡 概要

Amazon Aurora DSQL が CloudWatch Database Insights に対応しました。 DSQL Active Session History (DASH) と呼ばれるサンプラーが、クラスター上のすべてのアクティブセッションを 1 秒ごとにサンプリングし、各セッションの待機状態と正規化された SQL ステートメントを記録します。

収集データは 1 分間隔で集約され、CloudWatch OTel メトリクス db.active_sessions.avg (Average Active Sessions, AAS) として公開されます。分析手段は Database Insights ダッシュボード、PromQL、システム診断 AI スキルの 3 つです。

❌ Before: アップデート前の課題

  • セッションが何に時間を費やしているかを可視化する標準的な手段がなく、原因調査が困難
  • 最もリソースを消費する SQL をステートメント単位で特定できない
  • DPU ベース課金で処理時間がコストに直結するのに、時間の内訳を分析する手段が限られていた

✅ After: アップデート後の改善

  • DASH データを Database Insights の専用ダッシュボードでノーコード分析
  • PromQL でメトリクスを直接クエリでき、サードパーティツールとも統合可能
  • AI スキルにより自然言語で自動ヘルスチェックと診断レポート生成
  • デフォルト有効・追加コストなしで既存クラスターでも即利用可能

DASH がクラスター上の全アクティブセッションを 1 秒ごとにサンプリングし、1 分単位で集約した結果を CloudWatch OTel メトリクスとして発行します。データは Database Insights ダッシュボード、PromQL、AI スキルの 3 つの経路から分析できます。

🚀 主要機能

📊 1. DSQL Active Session History (DASH)

  • オープンなトランザクションを持つ全アクティブセッションを 1 秒ごとにサンプリング
  • 各サンプルは「待機イベント」と「実行中の SQL の先頭 256 文字」を記録
  • セッション状態は「CPU 使用中」「外部操作の待機中」「トランザクション内アイドル」のいずれかに分類
  • 1 分ごとに集約され、単一メトリクス db.active_sessions.avg (AAS) として発行

🖥️ 2. CloudWatch Database Insights の専用ダッシュボード

  • Aurora DSQL 専用にキュレーションされたノーコード UI。クラスターは自動的に表示
  • DB Load チャートで待機イベント別の AAS を積み上げ表示
  • Slice By コントロールで「Wait Events」と「SQL Text」を切り替え
  • DB Load Analysis で Top Wait Events と Top SQL を寄与度順に表示

📝 3. PromQL によるプログラマティックアクセス

  • CloudWatch Query Studio で db.active_sessions.avg を PromQL で直接クエリ
  • 待機イベント別の負荷集計、Top SQL のランキング、ストレージ読み取り待機の抽出が可能
  • サードパーティモニタリングツールとの統合にも利用可能

🤖 4. Aurora DSQL システム診断 AI スキル

  • awslabs/agent-plugins の databases-on-aws プラグインに含まれる AI ヘルスチェックエージェント
  • CloudWatch MCP サーバー経由で DASH データを分析し、複数の時間枠で待機イベント分布を比較
  • 問題のあるクエリを検出すると、SQL 単位の詳細診断ワークフローを自動実行し解決策を提示
  • 自然言語プロンプトで診断レポートを Markdown 生成

🔧 技術仕様

DASH メトリクスの仕様

項目詳細
メトリクス名db.active_sessions.avg (単位: Count)
意味サンプル期間中のアクティブセッションの平均数 (Average Active Sessions, AAS)
サンプリング間隔1 秒 (セッション単位)
発行間隔1 分 (集約済み)
形式CloudWatch OpenTelemetry (OTel) メトリクス
SQL 記録実行中 SQL の先頭 256 文字 (リテラル値を除去して正規化)
有効化全クラスターでデフォルト有効 (セットアップ不要)
追加コストなし (Database Insights Standard モード)

主なディメンション

ディメンション説明
db.wait.class待機イベントの分類 (例: class:oncpu は CPU 実行中、class:io は入出力待機)
db.wait.eventサンプリング時点の待機状態
db.session.stateセッション状態 (active または idle in transaction)
db.query.id正規化 SQL テキストのフィンガープリント
db.query.normalized_text正規化された SQL テキスト (リテラル値を除去)
aws.auroradsql.session.role.arn接続時に引き受けた IAM ロールの ARN
application.name接続パラメータで明示的に設定した場合のみ含まれるアプリケーション名

DASH 待機イベント一覧

待機イベントクラス説明
OnCpuoncpuパース、プラン作成、式評価、結果処理などを CPU 上で実行中
ClientReadclientトランザクション内でアプリからの次のステートメントを待機中。頻発はラウンドトリップ過多やトランザクション長時間保持を示唆
ClientWriteclient結果をアプリにネットワーク送信中。大きな結果セットやネットワークレイテンシーを示唆
SequentialScanReadioストレージから連続したキー範囲を読み取り中
ScatteredBatchReadio非連続の複数キーを 1 回のストレージ呼び出しでバッチ読み取り中
SingleReadio単一タプルのポイントルックアップ (現行ではバッチ読み取りにほぼ置き換え済み)
UniqueConstraintCheckio一意キー制約の検証のためのストレージ読み取り
FkExistenceCheckio外部キー参照先の行の存在確認のための読み取り
StartTransactionio分散トランザクションの開始準備中
Commitioコミットを開始し、コミットサービスからの応答を待機中
PgSleeptimeoutアプリケーションが pg_sleep() を呼び出したことによるスリープ

Aurora DSQL のクエリプロセッサはラッチ、データロック、プロセス間通信を回避する設計のため、待機イベントの種類は PostgreSQL (バージョン 18 で 273 種類) と比較して意図的に少なく保たれています。

⚙️ 設定方法

前提条件

  • Aurora DSQL クラスターが作成済みであること (DASH と Database Insights Standard モードはデフォルトで有効)
  • CloudWatch コンソールおよびメトリクスへのアクセス権限を持つ IAM プリンシパル
  • AI スキル利用時は、対応する AI コーディングエージェントと databases-on-aws プラグインのインストール
1

Database Insights で DASH データを確認する

  • CloudWatch コンソール → [Database Insights] → [Fleet Health] で対象クラスターを選択
  • [DB Identifier] から [Database Instance Dashboard] を開く
  • [DB Load] チャートで待機イベント別の AAS の推移を確認
  • [Slice By] で [Wait Events] と [SQL Text] を切り替え、[DB Load Analysis] で Top Wait Events と Top SQL を確認

クラスターを作成してトランザクションを実行するだけで自動的に表示され、追加のセットアップは不要です。

2

PromQL で Top SQL を分析する

PromQL 負荷寄与度の高い上位 5 つの SQL を抽出 
topk(5,
  avg by ("db.query.normalized_text") (
    {
      "db.active_sessions.avg",
      "@resource.aws.auroradsql.cluster_id"="{{cluster-id}}"
    }
  )
)

CloudWatch Query Studio で実行すると、AAS への寄与度が高い上位 5 つの SQL を返します。メトリクス名にドットが含まれるため、引用符付きセレクタ形式を使用します。

3

ストレージ読み取りの多いステートメントを特定する

PromQL ストレージ読み取り系の待機イベントに絞り込み 
topk(5,
  sum by ("db.query.normalized_text") (
    {
      "db.active_sessions.avg",
      "db.wait.event"=~"S.*Read|.*Check",
      "@resource.aws.auroradsql.cluster_id"="{{cluster-id}}"
    }
  )
)

正規表現 S.*Read|.*Check により、ストレージ読み取り系の待機イベントに絞り込み、最も時間を費やしている上位 5 つの SQL を抽出します。

4

AI スキルで自動診断を実行する

Prompt AI コーディングエージェントへのプロンプト例 
Check the performance of my Aurora DSQL cluster {{cluster-id}} in us-east-1
and write me a markdown report.

スキルは CloudWatch MCP サーバーで複数の時間枠を分析し、Markdown 形式の診断レポートを返します。「直近 4 時間を先週の月曜日と比較して」のように比較期間の指定も可能です。

✨ メリット

💼 ビジネス面

✓コスト最適化への直結: DPU ベースのオンデマンド課金では処理時間がコストに直結。時間の使われ方の可視化により、パフォーマンスチューニングがそのままコスト削減につながる
✓追加コストなし: DASH と Database Insights Standard モードはデフォルト有効かつ無料
✓運用負荷の軽減: AI スキルによる自動ヘルスチェックで、専門知識がなくても調査の初動を高速化

🔬 技術面

✓ステートメント単位の負荷分析: 正規化 SQL とクエリ ID により、負荷を個々のクエリに帰属させられる
✓待機イベントプロファイルによる健全性判断: 固定の vCPU 上限がないため、比率の変化をベースラインと比較して異常を検知
✓多様なアクセス手段: ノーコード UI、PromQL、AI スキルの 3 経路が同一の DASH データセットを参照
✓OTel 標準形式: PromQL 対応のサードパーティツールとの統合が容易

⚠️ デメリット・制約事項

制限事項

✗SQL テキストの記録は先頭 256 文字のみ (長大なクエリの全文は取得不可)
✗DB Load チャートに Max vCPU の基準線は表示されない (弾力的スケーリングのため固定上限が存在しない)
✗累積 SQL 統計や実行計画へのドリルダウンは提供されない (RDS/Aurora の Database Insights との相違点)
✗DASH はオープンなトランザクションを持つセッションのみを追跡
✗待機イベントは 1 秒間隔のサンプリングによる統計値であり、完全なトレースではない

考慮すべき点

⚡絶対値ではなく「比率 (プロファイルの形)」で健全性を判断する運用モデルへの慣れが必要。一様に倍増した場合は単に忙しいだけであり、比率が大きく変化した場合にアプリケーションやプランの変更を疑う
⚡application.name は接続パラメータで明示的に設定した場合のみ記録されるため、アプリケーション別分析には接続設定の見直しが必要
⚡待機イベントの一覧は今後拡張される可能性がある

🎯 ユースケース

🔍 1. パフォーマンス低下時の原因調査

シナリオ: アプリのレスポンスが特定の時間帯に悪化したという報告を受け、データベース側の要因を切り分けたい。

  • Database Insights で対象クラスターを選択し、報告のあった時間帯を指定
  • DB Load チャートで待機イベントの内訳を確認し、通常時のベースラインと比較
  • Slice By を SQL Text に切り替え、該当時間帯の Top SQL を特定
✅ 効果: ノーコードで「どの待機イベントが」「どの SQL によって」増加したかを特定でき、原因調査の初動を数分レベルに短縮。

💰 2. DPU コスト最適化のためのクエリチューニング

シナリオ: DPU 使用量が想定より多くコストを削減したい。最も時間を消費しているクエリを特定して優先的にチューニングする。

PromQL SQL と待機イベントの組み合わせで負荷を分析 
topk(5,
  avg by ("db.query.normalized_text", "db.wait.event") (
    {
      "db.active_sessions.avg",
      "@resource.aws.auroradsql.cluster_id"="{{cluster-id}}"
    }
  )
)
✅ 効果: ストレージ読み取り過多ならインデックス設計、ClientRead 過多ならラウンドトリップ削減など、的を絞った改善によって DPU 消費を削減。

🤖 3. AI スキルによる定期ヘルスチェックの自動化

シナリオ: 運用チームが毎朝クラスターの健全性を確認しているが、待機イベント分布の比較分析には専門知識が必要で属人化している。

Prompt AI コーディングエージェントへのプロンプト 
Check the performance of my Aurora DSQL cluster prod-cluster-01
in us-east-1 for the last 4 hours, compare against the same hour
yesterday and last week, and write me a markdown report.
✅ 効果: ベースライン比較を含む診断レポートが自動生成され、問題クエリには SQL 単位の詳細診断と解決策提示まで自動化。ヘルスチェックの属人化を解消。

💵 料金と利用可能リージョン

💳 料金

DASH によるメトリクス収集と CloudWatch Database Insights の Standard モード (1 分間隔メトリクス) は、追加コストなしでデフォルト有効です。PromQL クエリの実行など CloudWatch の他機能には標準料金が適用される場合があります。

🌍 利用可能リージョン

Aurora DSQL が利用可能なすべての AWS リージョンで提供されています。

🔗 関連サービス・機能

→Amazon CloudWatch Database Insights: 本アップデートの中核となる分析 UI。RDS/Aurora 向けの負荷分析機能が Aurora DSQL にも拡張
→CloudWatch PromQL / Query Studio: OTel メトリクスに対する PromQL クエリの実行環境
→CloudWatch MCP サーバー / Agent Plugins for AWS: AI スキルの実行基盤。awslabs/agent-plugins の databases-on-aws プラグインとして提供
→CloudWatch アラーム: 待機イベントごとの AAS に高低のバンドを設定し、プロファイル変化を自動検知

📝 まとめ

Aurora DSQL の CloudWatch Database Insights 対応により、これまで可視化が難しかったセッションの時間消費の内訳を、待機イベントと SQL ステートメント単位で追加コストなしに分析できるようになりました。

DPU ベースの課金モデルではパフォーマンスチューニングがそのままコスト削減につながるため、Aurora DSQL を利用中のすべてのユーザーにとって価値の高いアップデートです。
