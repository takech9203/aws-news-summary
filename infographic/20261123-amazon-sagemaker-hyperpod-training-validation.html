☁️ Amazon SageMaker HyperPod

🩺 MultiNodeTrainingValidation
実トレーニングでノードの計算正常性を検証

📅 2026 年 11 月 23 日リリース ｜ 新しいディープヘルスチェック ｜ Amazon EKS オーケストレーション対応

📌 概要

Amazon EKS でオーケストレーションされた SageMaker HyperPod クラスターが、新しいディープヘルスチェック MultiNodeTrainingValidation をサポート。ジョブがスケジュールされる前に、 固定の Megatron-LM ワークロードを各インスタンスおよび EFA を介した複数インスタンス間で実際にトレーニングし、 ノードが「正しくトレーニングできるか」を検証します。loss が NaN / 無限大 になった場合、発散した場合、 制限時間内に完了しない場合、そのインスタンスは失敗と判定されます。

微細な故障のある GPU は、DCGM 診断や NCCL テストをすべてパスしながら誤った計算結果を返すことがあります (silent data corruption)。この種の障害は本番トレーニング中に NaN loss として初めて顕在化し、 数日分の GPU 時間が無駄になる原因でした。本チェックにより、クラスターの goodput (有効稼働率) を向上できます。

😰 Before: アップデート前の課題
  • 既存チェック (InstanceStress / InstanceConnectivity) はハードウェアと通信の検証のみで、「正しい計算結果を返すか」は検証できなかった
  • 微細な故障のある GPU が全テストをパスし、本番中に NaN / 無限大 loss として初めて顕在化
  • 異常が数日後に発覚すると、消費した大量の GPU 時間が無駄に
  • 障害の原因がハードウェアかモデル・コードかの切り分けが困難
😊 After: アップデート後の改善
  • ジョブ実行前に固定の Megatron-LM ワークロードによる実トレーニングで計算正常性を検証
  • 固定ワークロードのため、失敗はハードウェア起因と明確に判断可能
  • 自動ノード復旧と連携し、失敗インスタンスを自動的に再起動・交換
  • インスタンスの追加・交換時に毎回チェックを自動実行可能
  • StartClusterHealthCheck API で任意のタイミングにオンデマンド実行

💡 MultiNodeTrainingValidation は、既存の InstanceStress と InstanceConnectivity に加わる 3 つ目のディープヘルスチェック。 実際のトレーニングワークロードにより GPU の計算正常性を検証し、失敗したインスタンスは自動ノード復旧により再起動または交換されます。

⚡ 主要機能

🎯 1. Tiny Megatron テスト (インスタンスレベル)

各インスタンスの全 GPU 上で短時間の Megatron-LM ベースのトレーニングワークロードを実行。 loss が NaN / 無限大、開始時平均に対するしきい値超過の上昇 (発散)、制限時間内の未完了で失敗と判定。 MultiNodeTrainingValidation を指定した場合にのみ実行されます。

🌐 2. Megatron テスト (クラスターレベル)

同じワークロードを同一インスタンスタイプの複数インスタンス間で EFA を介して実行。 インスタンス単体では検出できない、複数 GPU が協調トレーニングする際の数値異常を検出。 ワークロードが固定のため、失敗はモデルやコードではなくハードウェア起因と切り分け可能です。

🔄 3. 自動ノード復旧との連携

チェックに失敗したインスタンスには失敗ラベルが付与され、自動ノード復旧が有効な場合は HyperPod が自動的に再起動または交換。プロビジョニング時に実行すれば、ジョブ使用前に問題を排除できます。

⏰ 4. 柔軟な実行タイミング

インスタンスグループの OnStartDeepHealthChecks への指定で作成・更新時に自動実行。 StartClusterHealthCheck API で既存インスタンスに対するオンデマンド実行も可能 (特定のインスタンス ID の指定にも対応)。

🔬 技術仕様

ディープヘルスチェックの種類 (EKS オーケストレーション)

チェック実行内容検出できる問題
InstanceStress GPU / NVLink 数の確認、DCGM レベル 4 診断、EFA のレイテンシー・帯域テスト (Trainium は Neuron テスト) ハードウェアの欠落、故障、不安定性
InstanceConnectivity GPU インスタンス間の NCCL テスト (Trainium は NCCOM テスト) インスタンス間通信の低速化・断絶
MultiNodeTrainingValidationNEW 各インスタンスでの Tiny Megatron テストと、インスタンス間での Megatron テスト ハードウェアテストはパスするが正しくトレーニングできない GPU (NaN / 無限大 loss、発散、時間内未完了)

項目詳細

インスタンスグループ設定例

create-cluster または update-cluster に渡すインスタンスグループ設定の OnStartDeepHealthChecks に追加します。

JSON インスタンスグループ設定 
{
  "InstanceGroupName": "<instance-group>",
  "InstanceType": "ml.p5.48xlarge",
  "InstanceCount": 2,
  "LifeCycleConfig": {
    "SourceS3Uri": "s3://<bucket>/<prefix>",
    "OnCreate": "on_create.sh"
  },
  "ExecutionRole": "arn:aws:iam::<account-id>:role/<hyperpod-execution-role>",
  "OnStartDeepHealthChecks": [
    "InstanceStress",
    "InstanceConnectivity",
    "MultiNodeTrainingValidation"
  ]
}

🛠️ 設定方法

前提条件

  • Amazon EKS でオーケストレーションされた SageMaker HyperPod クラスター
  • EFA 対応の NVIDIA GPU インスタンスタイプ (例: ml.p5.48xlarge) のインスタンスグループ (Megatron テストは同一インスタンスタイプのインスタンス間で実行される)
  • 自動復旧を利用する場合は、自動ノード復旧 (automatic node recovery) の有効化
1
インスタンスグループでチェックを有効化

OnStartDeepHealthChecks に MultiNodeTrainingValidation を追加して create-cluster / update-cluster を実行後、設定内容を確認。 出力に 3 つのチェック名が表示されれば有効化は完了です。

Bash設定の確認
aws sagemaker describe-cluster \
  --cluster-name <cluster-name> \
  --query "InstanceGroups[?InstanceGroupName=='<instance-group>'].OnStartDeepHealthChecks"
2
オンデマンドでチェックを実行

既存インスタンスに対してオンデマンド実行。長期の事前トレーニング開始前の検証に有効です。 特定インスタンスのみ検証する場合は設定に "InstanceIds": [...] を追加。 オンデマンド実行は DeepHealthCheck タイプのクラスターオペレーションを作成します。

Bashオンデマンド実行
aws sagemaker start-cluster-health-check \
  --cluster-name <cluster-name> \
  --deep-health-check-configurations \
  '[{"InstanceGroupName": "<instance-group>", "DeepHealthChecks": ["MultiNodeTrainingValidation"]}]'
3
結果を確認

オペレーションイベントの一覧とノードラベル (Passed など) で合否を確認。詳細は CloudWatch ロググループ /aws/sagemaker/Clusters/<cluster-name>/<cluster-id> の DeepHealthCheckResults/<id> ログストリームにテストごとに 1 行ずつ記録されます。 トレーニングの詳細ログは各インスタンスの /var/log/aws/clusters/sagemaker-deep-health-check.log で確認できます。

Bash結果の確認
# クラスターオペレーションのイベントを確認
aws sagemaker list-cluster-events \
  --cluster-name <cluster-name> \
  --operation-id <operation-id>

# ノードラベルで合否を確認
kubectl get nodes \
  -l sagemaker.amazonaws.com/instance-group-name=<instance-group> \
  -L sagemaker.amazonaws.com/deep-health-check-status

⚖️ メリットと制約事項

👍 メリット

計算リソースの浪費防止: 数週間規模の事前トレーニングが数日後に NaN loss で失敗するリスクを低減
goodput の向上: 不良ハードウェアへのジョブスケジュールを防ぎ、有効なトレーニング時間の割合を向上
運用負荷の軽減: 自動ノード復旧との組み合わせで検出から交換まで自動化
計算正常性の検証: silent data corruption のような数値異常を実トレーニングで検出
原因の切り分けが容易: 固定の既知正常ワークロードにより失敗をハードウェア起因と明確に判断
継続的な検証: ノード追加・交換のたびに実行し、クラスターの計算正常性を継続的に担保

⚠️ 制限事項・考慮点

Amazon EKS オーケストレーションのクラスターのみサポート (Slurm は対象外)
EFA 対応の NVIDIA GPU インスタンスタイプのみ (Trainium は対象外)
Megatron テストは同一インスタンスタイプのインスタンス間でのみ実行
移動 (move) されたノードは再実行されないため、検証にはオンデマンド実行が必要
チェック実行時間が追加される (例: 約 8 分)。完了までインスタンスはワークロードを受け入れられないため、キャパシティ追加時は計画に考慮
合格は「固定の参照ワークロードを正しくトレーニングできた」ことの検証であり、ユーザー自身のジョブの収束を保証するものではない
ディープヘルスチェック全体では DCGM レベル 4 診断が所要時間の大半 (例: 約 74 分)

💼 ユースケース

🧠 1. 長期事前トレーニング前の検証

シナリオ: 数週間かかる基盤モデルの事前トレーニングを、数十台の ml.p5.48xlarge で開始する前に全ノードの計算正常性を確認したい。

Bash実装例
aws sagemaker start-cluster-health-check \
  --cluster-name llm-pretrain-cluster \
  --deep-health-check-configurations \
  '[{"InstanceGroupName": "gpu-group", "DeepHealthChecks": ["MultiNodeTrainingValidation"]}]'

✨ 効果: 微細な故障のある GPU を事前に検出し、トレーニング開始数日後に NaN loss で中断して GPU 時間を浪費するリスクを低減。

🔁 2. ノード追加・交換時の自動検証

シナリオ: スケールアップや障害ノードの交換が頻繁な環境で、新しいノードが常に検証済みの状態でジョブを受け入れるようにしたい。

JSON実装例
"OnStartDeepHealthChecks": [
  "InstanceStress",
  "InstanceConnectivity",
  "MultiNodeTrainingValidation"
]

✨ 効果: 新規ノードと交換ノードが、ジョブがスケジュールされる前に必ずトレーニング正常性を検証されるため、不良ハードウェアの混入を防止。

🤖 3. 自動ノード復旧と組み合わせた無人運用

シナリオ: 大規模クラスターの運用で、不良インスタンスの検出から復旧までを人手を介さずに完結させたい。

Bash実装例
# チェック結果をノードラベルで確認
kubectl get nodes \
  -l sagemaker.amazonaws.com/instance-group-name=gpu-group \
  -L sagemaker.amazonaws.com/deep-health-check-status

✨ 効果: 失敗したインスタンスは失敗ラベルが付与され、自動ノード復旧により再起動または交換されるため、運用チームの介入なしに健全なクラスター状態を維持。

💰 料金と利用可能リージョン

💵 料金

MultiNodeTrainingValidation 自体に関する追加料金の記載はなく、SageMaker HyperPod の通常のインスタンス料金が適用されます。 チェック実行中のインスタンスはワークロードを受け入れられないため、チェック時間分だけ有効活用の開始が遅れる点は考慮が必要です。 詳細は 料金ページ を参照。

🌍 利用可能リージョン

SageMaker HyperPod が利用可能なすべての AWS リージョンで、Amazon EKS でオーケストレーションされたクラスターに対して利用できます。

🔗 関連サービス・機能

  • Amazon EKS: 本チェックは EKS オーケストレーションの HyperPod クラスターでのみ利用可能
  • Elastic Fabric Adapter (EFA): Megatron テストはインスタンス間通信に EFA を使用するため、EFA 対応インスタンスタイプが必須
  • HyperPod 自動ノード復旧: チェックに失敗したインスタンスの再起動・交換を自動化
  • HyperPod Kubernetes Resource Monitoring Agent: 同時期に発表された Kubernetes レイヤーの問題を検出するエージェント。本チェックがハードウェアの計算正常性を、エージェントがクラスターレイヤーをカバーする補完関係
  • Amazon CloudWatch Logs: チェック結果が DeepHealthCheckResults ログストリームに記録される

🎯 まとめ

MultiNodeTrainingValidation は、ハードウェアテストでは検出できない「正しく計算できない GPU」を、 実際の Megatron-LM トレーニングワークロードによりジョブ実行前に検出する新しいディープヘルスチェックです。 silent data corruption による本番トレーニングの中断は大規模クラスターで現実に発生する問題であり、 長期の事前トレーニングを運用するチームへの影響は大きいアップデートです。

EKS オーケストレーションの HyperPod クラスターでは、インスタンスグループの OnStartDeepHealthChecks への追加を推奨
長期トレーニング開始前のオンデマンド実行を運用に組み込むことを推奨
