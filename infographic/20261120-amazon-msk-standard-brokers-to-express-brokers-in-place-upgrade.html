📝 概要

Amazon MSK は、MSK Provisioned クラスターを Standard ブローカーから Express ブローカーへインプレース (稼働中のクラスター内) でアップグレードする機能を発表しました。データ移行はフルマネージドで実行され、アプリケーションの変更は不要です。クラスターのエンドポイントは変わらないため、クライアント側の切り替え作業なしで Express ブローカーへ移行できます。

🚀 主要機能

1️⃣ フルマネージドなインプレースアップグレード

既存の MSK Provisioned クラスターに Express ブローカーが追加され、トピックが Express ブローカーへ移動されます。移動は自動実行またはバッチ単位での制御を選択可能。アップグレードは数時間で完了し、新規クラスター作成とワークロード移行という従来のプロセスが不要です。

2️⃣ アプリケーション無停止・無変更での移行

クラスターエンドポイントが維持されるため、アプリケーション側の接続先変更が不要。コンシューマーオフセットが保持されるため、Apache Flink や Kafka Streams などのステートフルアプリケーションも再処理や重複なしで継続稼働します。

3️⃣ 検証とロールバックのサポート

Standard ブローカーはユーザーが廃止するまでクラスター内に残ります。Express ブローカーでの動作を検証した上で廃止でき、必要に応じてロールバックも可能です。

4️⃣ 事前アセスメント機能

移行前にクラスターを評価する API (CreateAssessment など) が追加され、アップグレードの準備状況を確認できます。

ステップ 1: 移行前アセスメントの実行

Bashアセスメントの作成
aws kafka create-assessment \
  --cluster-arn <クラスター ARN>

クラスターが Express ブローカーへのアップグレードに適した状態かを評価します。結果は list-assessment-findings で確認できます。

ステップ 2: ブローカータイプのアップグレード開始

BashExpress ブローカーへのアップグレード
aws kafka update-broker-type \
  --cluster-arn <クラスター ARN> \
  --current-version <現在のクラスターバージョン> \
  --target-instance-type express.m8g.large

クラスターに Express ブローカーを追加し、アップグレードプロセスを開始します。進行状況は describe-cluster-operation-v2 で確認できます。

ステップ 3: トピック再割り当ての実行と確認

Bashトピック再割り当て
aws kafka start-topic-reassignment \
  --cluster-arn <クラスター ARN>

aws kafka list-topic-reassignments \
  --cluster-arn <クラスター ARN>

トピックを Express ブローカーへ移動する再割り当てを開始し、進行状況 (完了トピック数 / 総トピック数) を確認します。バッチ単位で段階的に移動を制御することも可能です。

ステップ 4: 検証と Standard ブローカーの廃止

Express ブローカー上でアプリケーションの動作を検証した後、Standard ブローカーを廃止します。問題が発生した場合は、廃止前であればロールバックが可能です。

✓ダウンタイムリスクの最小化: エンドポイント維持とオフセット保持により、サービス停止やデータ重複のリスクなしで移行

🛠️ 技術面

✓性能向上: ブローカーあたり最大 3 倍のスループットにより、少ないブローカー数で同等以上の性能を実現
✓運用性の向上: 最大 20 倍高速なスケーリングと最大 90% 高速な障害復旧により、運用負荷と障害影響を低減
✓安全な段階的移行: アセスメント、バッチ制御、検証、ロールバックという段階的プロセスでリスクを管理

⚠️ デメリット・制約事項

🚧 制限事項

⚠️Apache Kafka 3.9 (KRaft モード) で稼働する MSK Provisioned クラスターのみが対象
⚠️移行先は Express ブローカーの M7g または M8g インスタンスに限定
⚠️Express ブローカーが利用可能なリージョンでのみ利用可能

🤔 考慮すべき点

⚠️アップグレード進行中は Standard と Express の両方に料金が発生
⚠️Standard ブローカーの廃止はユーザー操作のため、検証完了後に速やかに廃止しないと二重課金期間が長くなる
⚠️ZooKeeper モードや古い Kafka バージョンの場合は、先に Kafka 3.9 (KRaft) へのアップグレードが必要

🎯 ユースケース

📈 ユースケース 1: 高スループットなイベント基盤の性能強化

シナリオ: ピーク時にブローカーのスループットが逼迫している大規模なイベントストリーミング基盤を、サービス停止なしで増強したい。

実装例: create-assessment で移行可否を評価 → update-broker-type で express.m8g へのアップグレードを開始 → トピックを自動再割り当てし、ピーク時間帯を避けて段階的に移行

✅ 効果: ブローカーあたり最大 3 倍のスループットにより、ブローカー数を増やさずに性能を強化できます。
🔄 ユースケース 2: Flink / Kafka Streams を使うステートフル処理基盤の移行

シナリオ: Apache Flink によるリアルタイム集計パイプラインが稼働しており、オフセットのずれによる再処理や重複を避けながら Express ブローカーへ移行したい。

実装例: インプレースアップグレードを開始 (エンドポイント変更なし) → コンシューマーオフセットは自動で保持 → Flink ジョブは変更なしで稼働を継続

✅ 効果: 再処理や重複なしでステートフルアプリケーションを継続稼働させたまま移行できます。
💾 ユースケース 3: ストレージ運用の自動化とコスト最適化

シナリオ: Standard ブローカーで EBS ストレージのサイジングと監視に運用負荷がかかっており、ストレージ管理を自動化したい。

実装例: express.m8g.large へインプレースアップグレード → 自動スケールする従量課金ストレージへ移行 → ストレージ容量の監視・拡張作業を廃止

✅ 効果: ストレージの事前プロビジョニングが不要になり、運用負荷の削減と M8g による最大 30% のコスト削減を実現できます。

💰 料金と利用可能リージョン

💵 料金

インプレースアップグレード自体に追加料金はありません。ただし、アップグレード進行中は Standard と Express の両方の料金が発生します。完了後は Express ブローカーのインスタンス料金と従量課金ストレージ料金が適用されます。M8g インスタンスは M7g と比較して最大 30% のコスト削減が見込めます。

詳細は Amazon MSK 料金ページ を参照してください。

🌍 利用可能リージョン

Express ブローカーが利用可能なすべての AWS リージョンで利用できます。

🔗 関連サービス・機能

  • Amazon MSK Express ブローカー: 本アップデートの移行先。高スループット、高速スケーリング、自動スケールするストレージを提供
  • Amazon Managed Service for Apache Flink: ステートフルなストリーム処理サービス。オフセット保持により移行後も継続稼働が可能
  • AWS Graviton (M7g / M8g): Express ブローカーの基盤。M8g は Graviton4 ベースで高いコスト効率を実現

🏁 まとめ

Amazon MSK のインプレースアップグレード機能により、クラスター再構築やアプリケーション変更なしで Standard ブローカーから Express ブローカーへ移行できるようになりました。Kafka 3.9 (KRaft) で稼働する MSK Provisioned クラスターを運用している場合は、まずアセスメント API で移行可否を評価し、性能向上とコスト最適化の効果を検討することを推奨します。
