Amazon CloudFront

🌐 VPC オリジンのデュアルスタック対応

📅 リリース日: 2026 年 10 月 15 日
🏷️ VPC オリジンの IPv4/IPv6 サポート

Amazon CloudFront が VPC オリジンのデュアルスタックサポートを発表。プライベートサブネット内の ALB / NLB / EC2 に対して、エンドツーエンドの IPv6 配信が可能になりました。オリジンをインターネットに公開することなく、IPv6 アーキテクチャ要件や規制要件を満たせます。

IPv4 + IPv6
CloudFront からプライベートオリジンまでデュアルスタック接続
追加料金なし
通常の CloudFront データ転送・リクエスト料金のみ
パラメータ 1 つ
IpAddressType: dualstack を設定するだけで有効化

📋 概要: Before / After

❌ アップデート前の課題
✗VPC オリジンへの接続は IPv4 のみ (パブリックオリジンはデュアルスタック対応済み)
✗IPv6 でオリジンに接続するには、オリジンをパブリックサブネットに移動する必要があった
✗プライベート維持なら IPv4 止まりで、IPv6 アーキテクチャ要件・規制要件を満たせない
✅ アップデート後の改善
✓プライベートサブネット内のオリジンまでエンドツーエンドの IPv6 配信が可能に
✓CloudFront を単一エントリポイントとするセキュリティモデルを維持したまま IPv6 要件を達成
✓追加コストなし。IpAddressType を dualstack に設定するだけ

従来は CloudFront から VPC オリジンへの接続が IPv4 に限定されていましたが、今回のアップデートにより、CloudFront が作成するサービス管理 ENI がデュアルスタックに対応し、プライベートサブネット内のオリジンまで IPv6 トラフィックを届けられるようになりました。

⚡ 主要機能

1️⃣ デュアルスタック VPC オリジン

→ VPC オリジン作成時・更新時に IP アドレスタイプとして ipv4 (デフォルト) または dualstack を選択可能

→ デュアルスタック選択で、CloudFront からオリジンへの接続に IPv4 と IPv6 の両方が利用可能に

→ ALB、NLB、EC2 インスタンスのいずれの VPC オリジンタイプでも利用可能

2️⃣ エンドツーエンドの IPv6 配信

→ ビューワーから CloudFront、CloudFront からプライベートオリジンまで通信経路全体で IPv6 を利用可能

→ IPv6 アーキテクチャ要件や各国の規制・コンプライアンス要件への対応を、オリジンを公開せずに実現

3️⃣ セキュリティモデルの維持

→ オリジンはプライベートサブネットに配置したまま、CloudFront のみを単一エントリポイントとする構成を維持

→ IPv6 用の CloudFront マネージドプレフィックスリスト com.amazonaws.global.ipv6.cloudfront.origin-facing をセキュリティグループで利用可能

🔧 技術仕様

デュアルスタック VPC オリジンの要件

項目詳細
IP アドレスタイプipv4 (デフォルト) または dualstack
対応オリジンALB、NLB (TLS リスナーなし、セキュリティグループ必須)、EC2 インスタンス
サブネット要件プライベートサブネットに利用可能な IPv4 アドレスが 1 つ以上、デュアルスタックの場合は加えて利用可能な IPv6 アドレスが 1 つ以上必要
ENICloudFront がサービス管理 ENI を作成してサブネットにルーティング
セキュリティグループIPv4 用に加えて IPv6 用プレフィックスリスト com.amazonaws.global.ipv6.cloudfront.origin-facing の許可が必要 (プレフィックスリスト方式の場合)
追加料金なし

🛠️ 設定方法

前提条件

  • VPC オリジンがサポートされているリージョンに VPC を作成し、インターネットゲートウェイをアタッチしていること (インターネットゲートウェイはオリジンへのルーティングには使用されない)
  • プライベートサブネットがデュアルスタック構成で、利用可能な IPv4 アドレスと IPv6 アドレスがそれぞれ 1 つ以上あること
  • オリジンとなる ALB、NLB、または EC2 インスタンスがプライベートサブネットにデプロイ済みで、セキュリティグループがアタッチされていること
1
デュアルスタック VPC オリジンの作成
Bash AWS CLI 
aws cloudfront create-vpc-origin \
  --vpc-origin-endpoint-config '{
    "Name": "my-dualstack-vpc-origin",
    "Arn": "arn:aws:elasticloadbalancing:ap-northeast-1:123456789012:loadbalancer/app/my-alb/abcdef1234567890",
    "HTTPPort": 80,
    "HTTPSPort": 443,
    "OriginProtocolPolicy": "https-only",
    "OriginSslProtocols": {"Quantity": 1, "Items": ["TLSv1.2"]},
    "IpAddressType": "dualstack"
  }'

ALB を対象とした VPC オリジンを IpAddressType: dualstack で作成します。コンソールの場合は [VPC origins] - [Create VPC origin] で dualstack を選択。デプロイ完了 (Deployed ステータス) まで最大 15 分程度かかります。

2
オリジンのセキュリティグループを更新
Bash プレフィックスリストの許可 
# IPv4 用プレフィックスリストの許可
aws ec2 authorize-security-group-ingress \
  --group-id sg-0123456789abcdef0 \
  --ip-permissions '[{"IpProtocol": "tcp", "FromPort": 443, "ToPort": 443, "PrefixListIds": [{"PrefixListId": "pl-xxxxxxxx", "Description": "CloudFront origin-facing IPv4"}]}]'

# IPv6 用プレフィックスリストの許可
aws ec2 authorize-security-group-ingress \
  --group-id sg-0123456789abcdef0 \
  --ip-permissions '[{"IpProtocol": "tcp", "FromPort": 443, "ToPort": 443, "PrefixListIds": [{"PrefixListId": "pl-yyyyyyyy", "Description": "CloudFront origin-facing IPv6"}]}]'

デュアルスタック VPC オリジンの場合は、IPv4 用の com.amazonaws.global.cloudfront.origin-facing と IPv6 用の com.amazonaws.global.ipv6.cloudfront.origin-facing の両方を許可する必要があります。代替として、サービス管理セキュリティグループ CloudFront-VPCOrigins-Service-SG からのトラフィックを許可する方法もあります。

3
ディストリビューションへの関連付けと確認

ディストリビューションのオリジン設定で、作成したデュアルスタック VPC オリジンを選択します。既存ディストリビューションに追加する場合は、継続的デプロイのステージングディストリビューションでテストしてから本番にプロモートする方法が推奨されています。既存の IPv4 VPC オリジンをデュアルスタックに変更する場合は、UpdateVpcOrigin API またはコンソールの編集画面で IpAddressType を変更します。

💡 メリット

💼 ビジネス面

✓規制・コンプライアンス対応: 政府機関や規制業界で求められる IPv6 義務化要件 (例: 米国 OMB の IPv6 移行方針) に、セキュリティを損なわずに対応
✓追加コストなし: デュアルスタック VPC オリジンの利用に追加料金は発生しない
✓運用負荷の軽減: IPv6 対応のためにオリジンの公開やネットワーク構成の大幅な変更が不要

⚙️ 技術面

✓エンドツーエンド IPv6: 通信経路全体で IPv6 を利用でき、IPv4 アドレス枯渇対策や NAT 依存の削減につながる
✓セキュリティ維持: オリジンをプライベートサブネットに保ち、CloudFront を単一エントリポイントとするモデルを維持
✓シンプルな移行: IpAddressType パラメータの変更のみで有効化でき、既存構成からの移行が容易

⚠️ デメリット・制約事項

制限事項

✗プライベートサブネットに利用可能な IPv6 アドレスが必要 (サブネット自体のデュアルスタック化が前提)
✗VPC オリジン共通の制約として、Gateway Load Balancer や TLS リスナー付き NLB はオリジンにできない
✗VPC オリジンでは gRPC トラフィック、Lambda@Edge のオリジンリクエスト/オリジンレスポンストリガーは非サポート
✗一部リージョンでは特定のアベイラビリティーゾーンが対象外 (例: 東京リージョンの apne1-az3)

考慮すべき点

⚠プレフィックスリスト方式では、IPv6 用プレフィックスリストの許可を追加し忘れると IPv6 接続が失敗する
⚠NACL のインバウンドルールは CloudFront から VPC オリジンへのトラフィックには評価されないが、アウトバウンドルールは戻りの経路で評価されるため、エフェメラルポート (1024-65535) の許可が必要
⚠VPC オリジンの作成・更新はデプロイ完了まで最大 15 分程度かかるため、本番適用は継続的デプロイ機能によるテストを推奨

🎯 ユースケース

1. 政府・公共機関向けシステムの IPv6 義務化対応

シナリオ: 政府調達要件により通信経路全体で IPv6 対応が義務付けられているが、オリジンサーバーはインターネットに公開したくない。

実装例: VPC とプライベートサブネットをデュアルスタック構成 → ALB をプライベートサブネットに配置 → IpAddressType: dualstack で VPC オリジンを作成 → ディストリビューションで IPv6 を有効化し関連付け

✅ 効果: オリジンを非公開に保ったまま、ビューワーからオリジンまでエンドツーエンドの IPv6 通信を実現し、規制要件を満たせる。
2. パブリックサブネットに置いていたオリジンのプライベート化

シナリオ: IPv6 対応のためにやむを得ず ALB をパブリックサブネットに配置していたが、セキュリティ強化のためプライベート化したい。

実装例: デュアルスタック VPC オリジンを作成しステージングディストリビューションでテスト → 本番にプロモート → ルートテーブルを変更してオリジンをプライベート化 → パブリックアクセス用セキュリティグループルールを削除

✅ 効果: IPv6 対応を維持したままオリジンへの直接アクセス経路を排除し、CloudFront を単一エントリポイントとするセキュアな構成に移行できる。
3. IPv4 アドレス管理負荷の軽減

シナリオ: 大規模な VPC 環境で IPv4 アドレスの枯渇が課題となっており、IPv6 中心のネットワーク設計へ段階的に移行したい。

実装例: 新規ワークロードをデュアルスタックサブネットにデプロイ → CloudFront 経由の配信はデュアルスタック VPC オリジンで構成 → 既存の IPv4 VPC オリジンは UpdateVpcOrigin で順次 dualstack に更新

✅ 効果: CloudFront からオリジンへの通信を IPv6 で処理でき、IPv4 アドレス空間への依存を段階的に削減できる。

💰 料金

✓デュアルスタック VPC オリジンの利用に追加料金なし。VPC オリジン自体も追加料金なし
✓CloudFront の通常のデータ転送・リクエスト料金のみが適用
✓CloudFront がサブネットに作成するサービス管理 ENI のプライベート IP アドレスにも追加コストは発生しない

🌏 利用可能リージョン

VPC オリジンがサポートされているすべての AWS 商用リージョンで利用可能です。東京 (ap-northeast-1、apne1-az3 を除く)、大阪 (ap-northeast-3) を含む 30 以上のリージョンがサポートされています。最新のリージョン一覧は公式ドキュメントを参照してください。

🔗 関連サービス・機能

→Amazon VPC: デュアルスタックサブネットの構成が前提。IPv6 CIDR の割り当てとサブネットへの関連付けが必要
→Elastic Load Balancing (ALB/NLB): VPC オリジンの代表的なオリジンタイプ。プライベートサブネットに配置して利用
→AWS Resource Access Manager (AWS RAM): VPC オリジンはアカウント間で共有可能で、マルチアカウント構成でも利用できる
→CloudFront 継続的デプロイ: 既存ディストリビューションへの VPC オリジン追加を安全にテスト・プロモートできる

📝 まとめ

CloudFront の VPC オリジンがデュアルスタックに対応したことで、プライベートサブネット内のオリジンに対してもエンドツーエンドの IPv6 配信が可能になりました。これまで「IPv6 対応のためにオリジンを公開する」か「プライベートを維持して IPv4 に留まる」かのトレードオフを迫られていた環境では、IpAddressType を dualstack に変更するだけで両立できます。IPv6 要件を持つワークロードや、パブリックサブネットに配置しているオリジンのプライベート化を検討している場合は、本機能の適用を推奨します。
