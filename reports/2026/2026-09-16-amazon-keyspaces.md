# Amazon Keyspaces (for Apache Cassandra) - 11 の追加リージョンで一般提供開始

**リリース日**: 2026 年 9 月 16 日
**サービス**: Amazon Keyspaces (for Apache Cassandra)
**機能**: 11 の追加リージョンでの一般提供開始

📊 [このアップデートのインフォグラフィックを見る](https://takech9203.github.io/aws-news-summary/20260916-amazon-keyspaces.html)

## 概要

Amazon Keyspaces (for Apache Cassandra) が、11 の追加 AWS リージョンで一般提供を開始しました。これらのリージョンの顧客は、データをリージョン内に保持してデータレジデンシー要件を満たしながら、より低いレイテンシーで Cassandra 互換アプリケーションを構築できるようになります。

Amazon Keyspaces は、スケーラブルで高可用性のマネージド Apache Cassandra 互換データベースサービスです。サーバーレスであるため、使用したリソースに対してのみ料金が発生し、事実上無制限のスループットとストレージにより、毎秒数千リクエストを処理するアプリケーションを構築できます。

今回の拡大により、Amazon Keyspaces の商用リージョンでの提供数は 35 リージョン (AWS GovCloud (US) 2 リージョン、中国 2 リージョンを除く) となり、アジアパシフィック、ヨーロッパ、中東、中南米の広い範囲をカバーします。

**アップデート前の課題**

- 今回追加された 11 リージョン (大阪、ジャカルタ、ハイデラバードなど) では Amazon Keyspaces を利用できず、Cassandra 互換のマネージドデータベースが必要な場合は他リージョンを使用する必要があった
- 他リージョンのエンドポイントへアクセスするとネットワークレイテンシーが増加し、リアルタイム性が求められるワークロードで不利だった
- データレジデンシー要件 (データを特定の国・地域内に保持する要件) がある場合、Amazon Keyspaces を採用できず、自己管理の Apache Cassandra クラスターを運用する必要があった

**アップデート後の改善**

- 追加された 11 リージョン内でアプリケーションと同一リージョンに Keyspaces テーブルを配置でき、低レイテンシーでのアクセスが可能になった
- データをリージョン内に保持できるため、各国のデータレジデンシー要件やコンプライアンス要件を満たしやすくなった
- 自己管理の Cassandra クラスターからマネージドサービスへの移行の選択肢が広がり、運用負荷を削減できるようになった

## サービスアップデートの詳細

### 主要機能

1. **11 リージョンへの提供拡大**
   - 公式発表では具体的なリージョン名は記載されておらず、最新の提供リージョンは AWS Capabilities by Region での確認が案内されている
   - Amazon Keyspaces 開発者ガイドのサービスエンドポイント一覧に基づくと、デュアルスタックエンドポイントのみで新たに掲載された以下の 11 リージョンが今回の追加分と考えられる (詳細は「利用可能リージョン」セクションを参照)
   - アジアパシフィック 6、ヨーロッパ 3、中東 1、中南米 1 の構成で、東京・大阪の国内 2 リージョン体制も実現

2. **サーバーレスな Cassandra 互換データベース**
   - Apache Cassandra 互換 (CQL) のため、既存の Cassandra アプリケーションコードやドライバーをほぼ変更せずに利用可能
   - サーバーのプロビジョニング、パッチ適用、クラスター管理が不要
   - 使用した読み込み/書き込みリクエストとストレージに対してのみ課金

3. **エンタープライズグレードの可用性とスケーラビリティ**
   - 事実上無制限のスループットとストレージ
   - 毎秒数千リクエストを処理するアプリケーションに対応
   - トラフィックに応じたテーブルの自動スケーリング (オンデマンドモード)

| アジアパシフィック (台北) | ap-east-2 | cassandra.ap-east-2.api.aws |
| ヨーロッパ (ミラノ) | eu-south-1 | cassandra.eu-south-1.api.aws |
| ヨーロッパ (スペイン) | eu-south-2 | cassandra.eu-south-2.api.aws |

### 接続方法

| アクセス方法 | ポート | プロトコル |
|--------------|--------|------------|
| CQLSH | 9142 | TLS |
| Cassandra ドライバー | 9142 | TLS |
| AWS CLI | 443 | HTTPS |
| AWS SDK | 443 | HTTPS |

なお、上記 11 リージョンでは CDC ストリーム用エンドポイント (`cassandra-streams.{region}.api.aws`) も同時に掲載されており、Amazon Keyspaces CDC streams も利用できます。

## 設定方法

### 前提条件

1. AWS アカウントを保有していること
2. 対象リージョンが有効化されていること (ハイデラバード、メルボルン、台北などのオプトインリージョンはアカウントで有効化が必要)
3. cqlsh または Cassandra 互換ドライバー、AWS CLI のいずれかが利用できること

### 手順

#### ステップ 1: キースペースの作成

```bash
aws keyspaces create-keyspace \
    --keyspace-name 'my_keyspace' \
    --region ap-northeast-3
```

AWS CLI を使用して、大阪リージョン (ap-northeast-3) にキースペースを作成します。

#### ステップ 2: テーブルの作成

```bash
aws keyspaces create-table \
    --keyspace-name 'my_keyspace' \
    --table-name 'my_table' \
    --schema-definition 'allColumns=[{name=id,type=text},{name=data,type=text}],partitionKeys=[{name=id}]' \
    --region ap-northeast-3
```

パーティションキー `id` を持つテーブルを作成します。キャパシティモードを指定しない場合はオンデマンドモードで作成されます。

#### ステップ 3: cqlsh での接続確認

```bash
cqlsh cassandra.ap-northeast-3.api.aws 9142 -u <username> -p <password> --ssl
```

サービス固有の認証情報または SigV4 認証プラグインを使用し、TLS 経由でエンドポイントに接続して動作を確認します。

## メリット

### ビジネス面

- **データレジデンシー要件への対応**: データを対象国・地域のリージョン内に保持でき、規制やコンプライアンス要件を満たしやすくなる
- **運用コストの削減**: 自己管理の Cassandra クラスターが不要になり、インフラ運用にかかる人的コストを削減できる
- **サーバーレスの従量課金**: 使用したリクエストとストレージのみの支払いで、初期投資や過剰なキャパシティ確保が不要

### 技術面

- **低レイテンシー**: アプリケーションと同一リージョンにデータベースを配置でき、ネットワークレイテンシーを削減できる
- **国内マルチリージョン構成**: 東京に加えて大阪でも利用可能になり、国内で完結する災害対策 (DR) 構成の選択肢が広がる
- **Cassandra 互換**: 既存の CQL コードや Cassandra ドライバーを活用でき、移行コストが低い

## デメリット・制約事項

### 制限事項

- 公式発表には追加された 11 リージョンの具体名が記載されておらず、正確な最新リストは AWS Capabilities by Region で確認する必要がある
- 新規追加リージョンのエンドポイントはデュアルスタック (`.api.aws`) 形式のみが掲載されており、従来の `cassandra.{region}.amazonaws.com` 形式の IPv4 エンドポイントは掲載されていないため、接続設定時に注意が必要
- 一部の追加リージョン (ハイデラバード、メルボルン、台北など) はオプトインリージョンのため、事前にアカウントでの有効化が必要

### 考慮すべき点

- リージョンによって料金単価が異なるため、利用前に対象リージョンの料金を確認することを推奨
- マルチリージョンレプリケーションなどの一部機能が新規リージョンで利用可能かは、個別にドキュメントで確認が必要

## ユースケース

### ユースケース 1: 国内完結の DR 構成

**シナリオ**: 金融機関や公共系システムで、データを日本国内に保持しながら Cassandra 互換データベースの災害対策構成を実現したい。

**実装例**:
```
東京リージョン (ap-northeast-1): プライマリの Keyspaces テーブル
大阪リージョン (ap-northeast-3): DR 用の Keyspaces テーブル
アプリケーション層でのレプリケーションまたはマルチリージョンレプリケーションを構成
```

**効果**: データを国内に保持したまま、地理的に分離された 2 リージョンでの可用性を確保できる。

### ユースケース 2: 自己管理 Cassandra からの移行

**シナリオ**: これまで Keyspaces が未提供だったリージョン (ジャカルタ、テルアビブなど) で EC2 上に Apache Cassandra クラスターを自己運用しており、運用負荷を削減したい。

**実装例**:
```
1. 既存 Cassandra クラスターのスキーマを CQL で Keyspaces に作成
2. DSBulk や AWS Glue を使用してデータを移行
3. アプリケーションの接続先をリージョン内の Keyspaces エンドポイントに変更
```

**効果**: ノード管理、パッチ適用、スケーリング作業が不要になり、運用負荷とコストを削減できる。

### ユースケース 3: データレジデンシー要件のある IoT ワークロード

**シナリオ**: メキシコ国内の IoT デバイスから送信される時系列データを、国内リージョンに保持しながら毎秒数千リクエスト規模で書き込みたい。

**実装例**:
```
IoT デバイス → AWS IoT Core (mx-central-1) → Lambda → Amazon Keyspaces (mx-central-1)
オンデマンドキャパシティモードでトラフィック変動に自動追従
```

**効果**: データレジデンシー要件を満たしつつ、サーバーレスでスパイクにも対応できる書き込み基盤を構築できる。

## 料金

Amazon Keyspaces はサーバーレスの従量課金制で、使用した分にのみ料金が発生します。主な課金要素は以下のとおりです。

| 課金要素 | 内容 |
|----------|------|
| オンデマンドキャパシティ | 書き込みリクエストユニット (WRU、1 KB/行まで) と読み込みリクエストユニット (RRU、LOCAL_QUORUM で 4 KB まで、LOCAL_ONE は半額) に基づく課金 |
| プロビジョンドキャパシティ | 予測可能なワークロード向けに WCU/RCU を事前指定 (Auto Scaling 対応) |
| ストレージ | テーブルの課金対象サイズに基づく継続課金 (事前プロビジョニング不要) |
| PITR バックアップ | 有効化中のテーブルサイズに基づく課金、復元時は復元データ量に基づく課金 |
| TTL 削除 | 削除/更新された行 1 KB あたり 1 ユニット |
| データ転送 | 受信および同一リージョン内は無料、リージョン間転送は双方向で課金 (マルチリージョンレプリケーションの転送は無料) |

無料利用枠として、最初の 3 か月間は毎月 3,000 万オンデマンド書き込みユニット、3,000 万読み込みユニット、1 GB のストレージが提供されます。料金単価はリージョンごとに異なるため、詳細は料金ページを確認してください。

## 関連サービス・機能

- **Amazon DynamoDB**: 同じくサーバーレスの NoSQL データベース。Cassandra 互換性が不要な場合の選択肢
- **Amazon Keyspaces CDC streams**: テーブルの変更データキャプチャ機能。新規追加リージョンでもストリームエンドポイントが提供されている
- **AWS Glue / DSBulk**: 自己管理 Cassandra から Keyspaces へのデータ移行に活用できるツール

## まとめ

Amazon Keyspaces の提供リージョンが 11 拡大し、大阪を含む幅広い地域で低レイテンシーかつデータレジデンシー要件に対応した Cassandra 互換データベースを利用できるようになりました。特に国内では東京・大阪の 2 リージョン体制となり、国内完結の DR 構成が可能になった点が重要です。対象リージョンで自己管理の Cassandra を運用している場合は、マネージドサービスへの移行を検討する良い機会です。
